# fix(seal): bake a serve manifest free of seal stage paths

[#9613](https://github.com/jaseci-labs/jac/pull/9613) by @akindu-k · opened 28 Sept 2026 · +35 −4 in 4 files

<!-- explainer -->

## In short
The seal step bakes a serve manifest into every `.jab` bundle. That manifest recorded a temporary build folder whose name changes on every run, so identical content produced different bytes each time. You changed `build_serve_manifest` to strip those temporary paths, so identical packs now produce identical bytes.

## Words to know
- **Seal**: the step that precompiles an app and packs it for deployment.
- **`.jab`**: the bundle file the seal produces. It is what gets shipped to the pod.
- **Serve manifest** (`.jac/serve_manifest.json`): JSON metadata baked into the bundle. It describes what the app exposes: its modules and "surface" declarations.
- **Surface**: the declarations of a module that are exposed to callers. Each surface entry is a record keyed by name.
- **Stage folder**: the temporary directory (`/tmp/jac-app-precompile-<pid>-<random>/app`) where the seal assembles the app before packing. Its name is different every time.
- **Content-addressed skip**: the deploy computes a digest (hash) of the bundle bytes. If the digest matches what is already deployed, it skips re-shipping. This only works if identical content gives identical bytes.
- **Determinism**: the same input always gives the same output bytes.
- **Pod**: the Kubernetes container where the sealed app runs.
- **`root`**: a manifest field naming the directory the app lives in.
- **`module`**: a surface-entry field that also held a path-like value.
- **`_prepare_sealed`**: code that runs on the pod. It sets `root` to the image it actually boots from.
- **`ModuleIntrospector` / `sealed_root_for`**: on the raw fallback path, when `root` is missing, the introspector works out the root from the module file using `sealed_root_for`.

## The problem
When sealing, `build_serve_manifest` copied the prepared manifests as they were. Those manifests held the stage folder path as `root`, and as `module` in each surface entry. The stage folder name contains a process id and a random part, so it differed on each pack.

The effect: pack the same app twice and the `.jab` bytes differ. The digest differs, so the "bundle unchanged" check missed on every deploy and the bundle was re-shipped each time.

The existing determinism tests missed this. Their fixture app had no resolvable entry file, so no serve manifest was baked at all.

The paths were also useless on the pod, because that stage folder does not exist there.

## The changes, one by one
### `jac/jaclang/dist/seal.jac`
This is the actual fix. You added two helpers and used them in `build_serve_manifest`.

- `_without_keys(record, dropped)` returns a copy of a dict without one key.
- `_portable_manifest(manifest)` drops `root` from the manifest. If the manifest has a `surface`, it rebuilds it with `module` dropped from every entry.

```diff
-        result = dict(prepared.manifests[str(entry_file.resolve())]);
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);
```
The entry manifest used to be copied as-is. Now it passes through `_portable_manifest`.

```diff
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(manifest)
```
Each entry of `module_manifests` is cleaned the same way.

Why dropping these is safe, per the description:
- `_prepare_sealed` sets `root` itself on the pod, for the entry and every module manifest.
- Declarations are found through the relative `src`. `module` is only passed through `SurfaceEntry.from_dict`.
- On the raw fallback in `serve_manifest_for`, a missing `root` makes `ModuleIntrospector` use `sealed_root_for` the module file, rather than trusting a stage path that doesn't exist.

## How it runs now
1. A user runs the seal or a `jac scale deploy`.
2. The seal resolves the entry file and calls `build_serve_manifest`.
3. It prepares the application in the stage folder, which gives manifests that include stage paths.
4. (changed) The entry manifest goes through `_portable_manifest`, removing `root` and each surface `module`.
5. (changed) Every manifest in `module_manifests` goes through `_portable_manifest` too.
6. The cleaned manifest is baked into the `.jab`. Its bytes no longer depend on the stage folder name.
7. The digest of identical content now matches, so the unchanged bundle is not shipped again.
8. On the pod, `_prepare_sealed` sets `root` to the real image path. On the raw fallback, `ModuleIntrospector` uses `sealed_root_for`.

## Tests
- **`test_application_preparation.jac`, "sealing retains each colocated service's access metadata"**: this existing test now also loops over the entry manifest and every module manifest. It asserts that none has a `root` key and that no surface entry has a `module` key. This proves the stripping works for both the entry and the module manifests.
- **`test_seed_determinism.jac`, "identical content packs to identical bytes"**: you renamed the fixture file from `svc.jac` to `main.jac`. A `main.jac` is a resolvable entry, so the pack now bakes a serve manifest and the determinism check really covers it. Before, the fixture hid the bug.

The test count is unchanged.

## Explaining it in one minute
"The seal baked a serve manifest that contained the temporary stage folder path, as `root` and as each surface entry's `module`. That path changes on every pack, so identical content gave different bytes and the deploy's digest check never matched. I added `_portable_manifest` in `seal.jac` to drop those two keys from the entry manifest and all module manifests. The pod doesn't need them: `_prepare_sealed` sets `root` itself, declarations resolve through the relative `src`, and the fallback uses `sealed_root_for`. I extended the preparation test to assert the keys are gone, and changed the determinism test's fixture to `main.jac` so it really bakes a manifest and would have caught this."
