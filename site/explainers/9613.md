## 1. The short version

When an app is sealed, a step called the "bake" writes a small JSON file, `.jac/serve_manifest.json`, into every `.jab` bundle. The pod reads this file at boot so it can serve the app without recompiling it. The seal happens in a temporary "stage" folder whose name changes on every run, for example `/tmp/jac-app-precompile-<pid>-<random>/app`.

**The baked manifest recorded that temporary stage path, both as the manifest's `root` and as each surface entry's `module`. Two packs of identical content therefore never produced identical bytes.** The deploy skips re-shipping a bundle whose content hash has not changed. Because the path changed every time, that skip missed on every redeploy. The existing determinism test did not catch this: its fixture app had no entry file the seal could resolve, so no serve manifest was baked at all.

**You fixed it by having `build_serve_manifest` drop `root` from every baked manifest and `module` from every surface entry, so the baked file holds no stage path.** You also renamed the determinism test's fixture file to `main.jac`, so that test now bakes a serve manifest and covers it.

## 3. The problem, step by step

### 3.1 The setup

- `pack_jab` (in jac-scale) copies the app into a fresh temporary stage folder and runs the seal there.
- The seal calls `bake_serve_payloads`, which calls `build_serve_manifest`. That function compiles the app, collects one manifest per module, and returns a dict that is written to `.jac/serve_manifest.json`.
- `pack_jab` tars the stage into a `.jab`.
- The deploy compares the `.jab`'s content hash with the last deploy's. If they match, it skips shipping.
- On the pod, `_prepare_sealed` reads the baked manifest and boots.

### 3.2 What went wrong

#### 3.2a Redeploying unchanged content

```text
1. Pack #1: stage = /tmp/jac-app-precompile-1201-ab12/app
2. build_serve_manifest copies prepared.manifests[entry] with dict(...)
     manifest.root                    = "/tmp/jac-app-precompile-1201-ab12/app"   ← WRONG: stage path baked in
     surface["walk"].module           = "/tmp/jac-app-precompile-1201-ab12/app/main.jac"
     module_manifests["x.jac"].root   = same stage path (copied as-is)
3. .jab #1 bytes → hash H1
4. Pack #2, same source: stage = /tmp/jac-app-precompile-1377-cd34/app
5. Baked root/module now contain "...1377-cd34..."
6. .jab #2 bytes → hash H2 ≠ H1                                                    ← WRONG: content same, bytes differ
7. Content-addressed skip misses → bundle re-shipped to every pod
```

#### 3.2b Why the existing test missed it

```text
1. test_seed_determinism writes the fixture as svc.jac
2. resolve_entry_file finds no entry → returns None
3. bake_serve_payloads returns True without writing a serve manifest
4. .jab contains no serve_manifest.json → nothing path-dependent inside
5. Two packs → identical bytes → test passes                                       ← blind spot
```

#### 3.2c The stale path on the pod (raw fallback)

According to your description, if pod code reached `serve_manifest_for`'s raw fallback, it would trust the baked `root`, which pointed at `/tmp/jac-app-precompile-…/app`. That folder never exists on a pod. The fallback code itself is not in the diff, so this case is described rather than shown.

### 3.3 Why it mattered

- Every `jac scale deploy` re-shipped the full bundle to every pod, even when nothing changed. That wastes upload time and causes pod churn.
- It blocks #9610, which fixes issue #9138 (the pack must fail on the host when the serve manifest is missing). #9610's fixture apps now bake a serve manifest, so its fat-bundle and seed-determinism tests would fail without this fix. @MusabMahmoodh noted that this PR "should land before #9610".
- This PR does **not** itself fix #9138. That issue is about missing manifests failing late on pods, not about determinism.

## 4. The idea of the fix (one sentence)

> **Bake only what the pod can't work out itself.** Remove the stage-dependent `root` and surface `module` keys from the baked manifest, because the pod re-derives the root from where it actually boots.

This removes the varying data at its source, instead of rewriting paths afterwards. The values were also wrong on the pod anyway, since the stage folder doesn't exist there.

## 5. Every code change, explained

### 5.1 `jac/jaclang/dist/seal.jac`: strip stage paths from the baked manifest

```diff
+def _without_keys(record: dict[str, any], dropped: str) -> dict[str, any] {
+    return {
+        key: value
+        for (key, value) in record.items()
+        if key != dropped
+    };
+}
+
+def _portable_manifest(manifest: dict[str, any]) -> dict[str, any] {
+    result = _without_keys(manifest, 'root');            # NEW: no stage root
+    if result.get('surface') {
+        result['surface'] = {
+            name: _without_keys(rec, 'module')           # NEW: no stage module path
+            for (name, rec) in result['surface'].items()
+        };
+    }
+    return result;
+}
@@ def build_serve_manifest(...)
-        result = dict(prepared.manifests[str(entry_file.resolve())]);          # OLD: full copy
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);  # NEW
         result['module_manifests'] = {
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest           # OLD: as-is
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(
+                manifest
+            ) for application in [prepared, *prepared.applications]                     # NEW
             for (path, manifest) in application.manifests.items()
         };
```

**What:** The entry's manifest and every module manifest pass through `_portable_manifest` before being baked. The baked file no longer contains `root` at any level, or `module` in any surface entry.

**Why:** Those two keys were the only parts of the baked file that held the per-run stage path. Removing them makes the `.jab` bytes depend only on the app's content.

**Things to notice:**
- The `module_manifests` keys were already relative (`os.path.relpath(path, prepared.root)`), so they were never the problem.
- `_without_keys` builds a new dict, so `prepared.manifests` isn't mutated. Before, module manifests were stored by reference; now they are copied. The copy is shallow, so other nested values are still shared, which is harmless here because nothing mutates them.
- `result.get('surface')` is a truthiness check. A missing or empty surface is left alone.
- The diff doesn't show whether any *other* manifest field holds an absolute path. The new test asserts only on `root` and `module`, and the seed determinism test passing is the evidence that nothing else varies for that fixture.
- `build_serve_manifest` is shared code in `dist/seal.jac`. Per the issue, `jac build --as jab` also uses this bake path, so those bundles change too. The diff can't show whether other callers read `root`.

## 6. How execution flows after the PR

### 6.1 Sealing and packing (host)

```text
pack_jab(app_dir, binary)
├─ copy app → /tmp/jac-app-precompile-<pid>-<rand>/app (stage)
├─ bake_serve_payloads
│   ├─ resolve_entry_file → main.jac (or None → skip bake, unchanged)
│   └─ build_serve_manifest(entry, stage)
│       ├─ compile & prepare application
│       ├─ result = _portable_manifest(entry manifest)          ← CHANGED (no root, no surface.module)
│       ├─ result.module_manifests = {rel: _portable_manifest(m)} ← CHANGED
│       └─ write .jac/serve_manifest.json
├─ precompile --seal
└─ tar stage → .jab  (bytes now independent of stage name)    ← CHANGED effect
```

### 6.2 Redeploy

```text
jac scale deploy
├─ pack_jab → .jab
├─ hash .jab
└─ same hash as last deploy?
    ├─ yes → skip re-ship        ← now reached for unchanged content
    └─ no  → ship to pods
```

### 6.3 Pod boot (not in the diff; as described by you and @MusabMahmoodh)

```text
jac run --serve web/main.jac
└─ _prepare_sealed(image_root)
    ├─ read .jac/serve_manifest.json   (no root key now)
    ├─ set root = image_root for entry and each module manifest
    └─ resolve declarations through relative `src`
       (SurfaceEntry.from_dict copes with missing `module`, per PR text)
```

### 6.4 Raw fallback (not in the diff)

```text
serve_manifest_for(module)
└─ ModuleIntrospector
    └─ root missing → sealed_root_for(module file)   ← now taken, instead of a dead /tmp path
```

| Scenario | Before | After |
|---|---|---|
| Two packs, same content | Different bytes, skip misses | Identical bytes, skip hits |
| Pod boot via `_prepare_sealed` | Overwrote stale `root` | Sets `root` (none baked) |
| Raw `serve_manifest_for` fallback | Trusted a `/tmp` stage path that doesn't exist on the pod | Uses `sealed_root_for` |
| App with no resolvable entry | No manifest baked | Same (out of scope; see #9138/#9610) |

What users will notice: redeploys of unchanged apps stop re-shipping bundles. The baked JSON also gets slightly smaller.

## 11. Questions your senior might ask

**Q: Why remove the keys instead of making them relative?**
The pod never needs them. `_prepare_sealed` sets `root` to the image it boots from, and `SurfaceEntry.module` is only read at compile time by `boundary_audit`. A relative value would just be dead data.

**Q: Does anything on the pod crash on a missing `root` or `module` key?**
Per your description and @MusabMahmoodh's review: no. `_prepare_sealed` sets `root` itself, `from_dict` only carries `module` through, and the raw fallback uses `sealed_root_for`. `test-in-package-sealed` and `test-scale` passed. That code isn't in the diff, so cite the files if asked.

**Q: Are there other absolute paths left in the baked manifest?**
The new assertions cover only `root` and `module`. The seed determinism test, now with a real entry, passes byte-for-byte. That shows nothing else varies for that fixture. A richer app (colocated services) isn't covered by the byte-identity test.

**Q: Why did the old determinism test pass?**
Its fixture was `svc.jac`. `resolve_entry_file` returned `None`, so no serve manifest was baked and nothing path-dependent ended up in the `.jab`.

**Q: Does this affect `jac build --as jab` too?**
Yes. It's shared code in `dist/seal.jac`, and that build path also bakes through it, so those bundles lose the two keys as well. Nothing in the diff indicates a consumer there needs them.

**Q: Will old bundles still boot on new pods, and new bundles on old pods?**
Old bundles still carry `root`, which `_prepare_sealed` overwrites anyway, so they should boot. New bundles on older pods depend on whether older pod code read `root` from the file. The PR doesn't say; the issue notes there is no format stamp on the manifest.

**Q: Is the `passes-native` failure yours?**
It's unlikely by file scope, since no files in that shard changed, but it's unconfirmed. Check the log or compare against `main`.

**Q: How does this relate to #9138 and #9610?**
#9138 is about the pack shipping a `.jab` without a serve manifest. #9610 fixes it, and its fixtures now bake a manifest, so its determinism tests need this PR first.

**Q: Why mutate nothing in place?**
`_without_keys` returns a new dict, so `prepared.manifests` (used elsewhere in the same compile) keeps its `root` for any in-process consumer.
