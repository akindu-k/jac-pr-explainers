# fix(seal): bake a serve manifest free of seal stage paths

[#9613](https://github.com/jaseci-labs/jac/pull/9613) by @akindu-k · opened 28 Sept 2026 · +35 −4 in 4 files

<!-- explainer -->

## In short

When you sealed an app, the baked serve manifest recorded the random temporary folder the seal ran in. So two packs of the same content never had the same bytes, and `jac scale deploy` re-shipped unchanged bundles every time. You now strip the two path fields (`root`, and each surface entry's `module`) before the manifest is baked. You also made the determinism test actually bake a manifest, so this case is now covered.

## Words to know

- **Seal / sealing**: The step that packs a Jac app into a ready-to-run bundle for deployment. It compiles the app and writes extra metadata into the bundle.
- **`.jab`**: The bundle file the seal produces. It is what gets shipped to the cluster.
- **Seal stage**: A temporary folder the seal copies the app into while it works, for example `/tmp/jac-app-precompile-<pid>-<random>/app`. The name contains the process id and a random part, so it changes on every run.
- **Serve manifest (`.jac/serve_manifest.json`)**: A JSON file baked into the `.jab`. It describes what the app serves: its root folder, its "surface", and one manifest per module (`module_manifests`).
- **Surface**: The list of declarations (functions, walkers and so on) that the app exposes to callers. Each entry is a small record, and before this PR it included a `module` path.
- **`root`**: A field in a manifest that holds the absolute path of the app's folder.
- **Content-addressed skip**: The deploy computes a digest (a fingerprint, like a hash) of the bundle's bytes. If the digest matches what is already deployed, it skips re-shipping. This only works if identical content gives identical bytes.
- **Deterministic / determinism**: The same input always gives the same output, byte for byte.
- **Pod**: A running container in Kubernetes. Kubernetes is the system jac-scale deploys apps onto. The `.jab` is unpacked and run inside a pod.
- **Fixture**: The small fake app a test builds to run against.
- **mtime**: A file's "last modified" time. The determinism test checks that changing it does not change the digest.
- **`_prepare_sealed`, `serve_manifest_for`, `ModuleIntrospector`, `sealed_root_for`, `SurfaceEntry.from_dict`**: Runtime code on the pod side that reads the baked manifest. This PR does not change them. What they do comes from your PR description, not the diff.

## The problem

1. `jac scale deploy` seals the app. The seal copies it into a fresh seal stage, such as `/tmp/jac-app-precompile-1234-abcd/app`.
2. `build_serve_manifest` compiles the app from there and builds the manifest. That manifest had `root` set to the stage path. Each surface entry had `module` set to a file path inside the stage.
3. That manifest was baked into the `.jab`.
4. On the next deploy with no code change, the stage folder is named, say, `/tmp/jac-app-precompile-5678-wxyz/app`. The manifest bytes differ, so the `.jab` bytes differ, and so does the digest.
5. The content-addressed skip never matched. Every deploy re-shipped the bundle, even when nothing changed.

The paths were also useless on the pod, because that `/tmp/...` folder does not exist there.

The existing test "identical content packs to identical bytes" did not catch this. Its fixture app was a single file named `svc.jac`, which the seal did not resolve as an entry. So no serve manifest was baked, and there was nothing unstable to detect.

## The changes, one by one

### `jac/jaclang/dist/seal.jac`: strip stage paths before baking

You added two small helpers and used them in `build_serve_manifest`.

```jac
def _without_keys(record: dict[str, any], dropped: str) -> dict[str, any] {
    return { key: value for (key, value) in record.items() if key != dropped };
}
```
- This builds a new dict holding every key of `record` except `dropped`.
- It makes a new dict, so it does not change the original.

```jac
def _portable_manifest(manifest: dict[str, any]) -> dict[str, any] {
    result = _without_keys(manifest, 'root');
    if result.get('surface') {
        result['surface'] = {
            name: _without_keys(rec, 'module')
            for (name, rec) in result['surface'].items()
        };
    }
    return result;
}
```
- Line 1 copies the manifest without `root`.
- If the manifest has a non-empty `surface`, the next lines replace it with a new dict. In it, each entry is copied without `module`.
- The surface dict and its entries are new objects, so the in-memory `prepared` manifests stay as they were. The old code used `dict(...)`, which also made a copy, so callers still see the same behaviour.

```diff
-        result = dict(prepared.manifests[str(entry_file.resolve())]);
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);
         result['module_manifests'] = {
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(manifest)
             for application in [prepared, *prepared.applications]
             for (path, manifest) in application.manifests.items()
         };
```
- The entry file's manifest is now cleaned instead of plainly copied.
- Every module manifest, from the main app and from each colocated application, is cleaned too.
- The keys of `module_manifests` were already relative paths with `/` separators, so they were already portable. Only the values needed cleaning.

**Why it is safe to drop these fields.** This comes from your description; the pod-side code is not in the diff:
- `_prepare_sealed` on the pod sets `root` itself, to the folder it actually boots from. It does this for the entry and for every module manifest.
- Declarations are found through the relative `src` field. The surface `module` field is only passed along by `SurfaceEntry.from_dict` and not used for lookup.
- In the raw fallback inside `serve_manifest_for`, a missing `root` makes `ModuleIntrospector` use `sealed_root_for(module file)`. Before, it would have trusted a stage path that does not exist on the pod.

## How it runs now

1. The user runs `jac scale deploy`.
2. The seal copies the app into a random seal stage under `/tmp`.
3. `resolve_entry_file` finds the entry (for example `main.jac`).
4. `build_serve_manifest` compiles the app and prepares manifests for the entry and for colocated services.
5. (changed) The entry manifest goes through `_portable_manifest`. `root` is removed, and `module` is removed from each surface entry.
6. (changed) Each module manifest is cleaned the same way and stored under its relative path in `module_manifests`.
7. The manifest is written to `.jac/serve_manifest.json` inside the `.jab`.
8. The deploy computes the bundle digest. (changed in effect) Identical content now gives identical bytes, so an unchanged bundle matches and is not re-shipped.
9. On the pod, `_prepare_sealed` fills in `root` with the real boot folder. If the raw fallback in `serve_manifest_for` is used instead, `ModuleIntrospector` finds the root through `sealed_root_for`. This is not changed by the PR, but it now gets no stale `root` to trust.

## Explaining it in one minute

"The seal bakes a serve manifest into every `.jab`. That manifest stored the temporary seal stage path, as `root` and as each surface entry's `module`. The path is random per run, so identical apps never packed to identical bytes, and the deploy's content-addressed skip never matched. Every deploy re-shipped the bundle. The pod never needed those paths. `_prepare_sealed` sets `root` to the real boot folder, lookups go through the relative `src`, and the fallback path finds the root with `sealed_root_for`. So in `build_serve_manifest` I strip `root` and the surface `module` from the entry manifest and every module manifest. For tests, I added assertions that no baked manifest has those keys. I also fixed the determinism test's fixture to use a `main.jac` entry. Before, it baked no manifest at all, which is why it missed this bug. Now it checks that two packs of the same content are byte-identical."
