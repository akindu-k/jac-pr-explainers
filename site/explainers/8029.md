## 1. The short version

Jac services deployed with jac-scale can call each other over HTTP. These are "sv-to-sv" calls (service-to-service). Each call retries up to 3 times on connection errors. A **circuit breaker** sits in front of each target service. After `_BREAKER_TRIP_THRESHOLD = 5` failures it "opens" and fails new calls immediately for a cooldown period, so callers stop waiting on a dead dependency.

**The bug: the breaker recorded one failure only after a whole 3-attempt retry loop had failed, so it needed about 15 failed round trips (each up to a 10s timeout) to open, not 5.** The same misplaced call existed twice, once in `service_call` and once in `walker_call`, because each had its own copy of the retry loop.

**The fix: you merged both loops into one helper, `_rpc_with_retries`. It records a breaker failure after every failed round trip and stops retrying as soon as the breaker opens.** One side effect: a recovery ("half-open") probe now costs 1 round trip instead of 3. When the breaker cuts a call short, the error message says so, for example `sv-to-sv RPC 'mod.ping' failed after 1 attempts (stopped by open circuit breaker): ...`. You also added a live Kubernetes check that the breaker really sheds load.

This PR fixes only Bug 1 of issue #7909. Bug 2 (unlimited concurrent half-open probes) is left for a follow-up.

**Status:** Merged on 2026-08-12. All non-skipped CI checks passed. @MusabMahmoodh left a "commented" review, and every point in it was fixed or answered before merge.

## 3. The problem, step by step

### 3.1 The setup

- `rpc.jac` has two entry points, `service_call` and `walker_call`. Each one built headers and the URL, then ran its **own copy** of a 3-attempt retry loop.
- Inside each loop, a successful transport call ran `breaker_record_success`.
- Failures were only stored in `last_err`. After the loop gave up, there was **one** `breaker_record_failure` call, followed by `raise RuntimeError(...)`.
- `breaker.jac` (not changed here) opens the breaker when `fails >= 5`.

### 3.2 What went wrong: slow tripping

Target service is down. Every round trip gets "connection refused".

```text
1. call #1: attempt 1 fails, attempt 2 fails, attempt 3 fails   fails=0 (nothing recorded yet)
2. call #1 loop ends -> breaker_record_failure                   fails=1   ← WRONG: 3 failures counted as 1
3. call #2: 3 failed round trips -> record once                  fails=2
4. call #3: 3 failed round trips -> record once                  fails=3
5. call #4: 3 failed round trips -> record once                  fails=4
6. call #5: 3 failed round trips -> record once                  fails=5 -> state=OPEN
7. Total: 15 failed round trips, each up to 10s timeout + backoff, before any shedding
```

### 3.2b What would go wrong with a naive fix: the cooldown keeps moving

If you only moved `breaker_record_failure` inside the loop, without stopping the loop:

```text
1. fails=4, call starts, attempt 1 fails -> fails=5 -> OPEN, opened_at=T
2. attempt 2 runs anyway, fails -> fails=6 -> opened_at=T+0.1+...   ← cooldown pushed forward
3. attempt 3 runs anyway, fails -> opened_at refreshed again         ← cooldown pushed forward
```

The half-open probe had the same problem, even in the old code:

```text
1. Breaker OPEN, cooldown passes -> breaker_should_skip flips to HALF_OPEN, returns False
2. Probe call runs all 3 attempts against a service that is still down   ← 3 round trips, not 1
3. Loop ends -> record_failure -> OPEN again
```

### 3.3 Why it mattered

Issue #7909 is rated "severity: high (robustness)". The breaker exists to shed load from a failing dependency. Callers waited through about 15 timeouts before shedding, so they got about a third of the protection that the threshold suggests.

@MusabMahmoodh and you found that the original design (commit 121fc6757, #5483) counted "transport-failure cycles" on purpose. So this is a **deliberate policy change**, not just a code-versus-intent correction. You kept the threshold at 5 and stated the new sensitivity in the release note.

## 4. The idea of the fix (one sentence)

> **One helper owns every attempt.** `_rpc_with_retries` records a breaker result after each round trip and stops retrying the moment the breaker opens.

Putting the attempt lifecycle in one place fixes both call sites at once. It also means a future RPC path cannot repeat the same mistake. The early stop is needed so that per-attempt counting does not keep pushing `opened_at` forward.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/runtime/rpc/rpc.jac`: shared retry helper with per-attempt breaker accounting

```diff
+glob _RPC_MAX_ATTEMPTS: int = 3,
+     _RPC_INITIAL_BACKOFF_SECONDS: float = 0.1;

+def _rpc_with_retries(module_name: str, label: str, send: any) -> any {
+    import time;
+    import from jaclang.runtimelib.serving.client { ClientConnectionError }
+    backoff: float = _RPC_INITIAL_BACKOFF_SECONDS;
+    last_err: Exception | None = None;
+    attempts: int = 0;
+    tripped: bool = False;
+
+    for attempt in range(_RPC_MAX_ATTEMPTS) {
+        attempts = attempt + 1;
+        try {
+            payload = send();
+            breaker_record_success(module_name);      # same spot as before: transport worked
+            return payload;
+        } except (ClientConnectionError, OSError) as e {
+            err_ref: any = e;
+            last_err = err_ref;
+            breaker_record_failure(module_name);      # NEW: once per round trip
+            if breaker_should_skip(module_name) {     # NEW: breaker just opened -> stop
+                tripped = True;
+                break;
+            }
+            if attempt < _RPC_MAX_ATTEMPTS - 1 {
+                time.sleep(backoff);
+                backoff = backoff * 2.0;
+            }
+        }
+    }
+
+    stopped_by = " (stopped by open circuit breaker)" if tripped else "";
+    raise RuntimeError(
+        f"sv-to-sv {label} failed after {attempts} attempts{stopped_by}: {last_err}"
+    );
+}
```

**What:** Both callers now build a `send` closure, which is one round trip, and hand it to `_rpc_with_retries`. The helper does the following:
- It tries up to 3 times.
- It records success or failure after each try.
- It breaks out as soon as `breaker_should_skip` says the breaker is open.
- It raises an error that reports the real attempt count and why the loop stopped.

Retry count and backoff are now module constants.

**Why:** This puts failure accounting where the breaker's unit of health is, the single round trip. The early break keeps `opened_at` from being refreshed and makes a half-open probe cost one round trip.

**Things to notice:**
- **Success is still recorded before envelope decoding.** It runs right after `post_stream_aware_sync` in `service_call`, and after `resp.json()` in `walker_call`, exactly as on `main`. An `{"ok": false}` envelope therefore still resets the counter and never trips the breaker. Greptile flagged this as P1. You showed it was unchanged by running a test against both branch and main (`fails=0 state=CLOSED` both times), and the bot agreed.
- **The message is unchanged in the normal case.** On the full 3-attempt failure path, `stopped_by` is empty. `func_label` is `module_name.func_name`, as @MusabMahmoodh checked. So the text is byte-identical to the old message for both functions.
- **A local `tripped` flag, not a second `breaker_should_skip` call.** @MusabMahmoodh suggested calling `breaker_should_skip` again while building the message. You declined because that function can flip OPEN to HALF_OPEN, which would use up the probe slot as a side effect of formatting an error. It could also give a stale answer if the cooldown ends between `break` and `raise`.
- **No sleep after a trip.** The `break` comes before the backoff sleep, so a tripped call returns right away.
- The `ClientConnectionError` import moved into the helper because the callers no longer catch it. `walker_call` dropped `import time`.
- Imports are still done inside each function at call time. That is why the tests' monkeypatching of `sv_http.post_stream_aware_sync` and `sv_http.request_sync` takes effect. This is inferred from the diff; the module layout is not shown.
- `breaker.jac` is unchanged, so Bug 2 (concurrent half-open probes) is still open.
- The pre-call breaker check in `service_call`, which produces the "open circuit breaker" skip message, is outside the shown hunks. It is not visible in the diff.

### 5.2 `jac/jaclang/scale/scripts/k8s_microservice_real_e2e.sh`: live cluster check of load shedding

```diff
+echo "=== verify the circuit breaker sheds load when a downstream service is gone ==="
+kubectl scale -n "${NAMESPACE}" deploy/cart-app-deployment --replicas=0 >/dev/null
+kubectl wait --for=delete pod -n "${NAMESPACE}" -l app=cart-app --timeout=120s >/dev/null 2>&1 || true
+while [ "${BREAKER_CALLS}" -lt 10 ]; do
+    BREAKER_CALLS=$((BREAKER_CALLS + 1))
+    CALL_START=$(date +%s)
+    CALL_BODY=$(curl -sS --max-time 60 -X POST "${GW_URL}/orders/function/create_order" ... || true)
+    BREAKER_SECS=$(( $(date +%s) - CALL_START ))
+    if printf '%s' "${CALL_BODY}" | grep -q "open circuit breaker"; then
+        BREAKER_BODY="${CALL_BODY}"; break
+    fi
+done
+# Restore before asserting so a failure here cannot leave cart_app scaled to 0.
+kubectl scale ... --replicas=1; kubectl rollout status ... --timeout=300s || { echo FAIL...; exit 1; }
+[ -z "${BREAKER_BODY}" ] && FAIL "breaker never opened"
+[ "${BREAKER_SECS}" -ge 5 ] && FAIL "not shedding load"
```

**What:** The script scales `cart_app` to zero. It then calls `orders_app.create_order`, which does a real `service_call` to `cart_app`, up to 10 times until a response mentions "open circuit breaker". It brings `cart_app` back, then checks two things: a breaker message appeared, and that call took under 5s.

**Why:** @MusabMahmoodh pointed out that before this, only `breaker_record_success` ever ran against a real cluster.

**Things to notice:**
- **It loops instead of assuming two calls.** Breaker state is per pod, and an HPA could add a second `orders_app` replica that splits the failures.
- **It restores before asserting.** Under `set -euo pipefail`, an early `exit` would otherwise leave `cart_app` at 0 replicas for later sections.
- **The grep matches two different messages.** `"open circuit breaker"` also appears in the new `"(stopped by open circuit breaker)"` text. So the check may pass on a call that tripped mid-call, not only on a fast pre-call skip, assuming that text reaches the HTTP body. The diff does not show this. The <5s timing check is what separates "shed load" from "did the work". Whether a refused connection to a zero-endpoint Service is already fast is not shown.

## 6. How execution flows after the PR

### 6.1 Calling a remote function (`service_call`)

```text
service_call(module, func, args)
├─ pre-call breaker check / URL / headers / timeout   (unchanged, partly outside the diff)
├─ define send() = one post_stream_aware_sync(...)    ← NEW
├─ _rpc_with_retries(module, "RPC 'module.func'", send)   ← NEW
│   └─ for attempt in 1..3
│       ├─ send() ok → breaker_record_success → return (kind, payload)
│       └─ ClientConnectionError/OSError
│           ├─ breaker_record_failure             ← CHANGED (was once, after the loop)
│           ├─ breaker_should_skip? → tripped, break   ← NEW
│           └─ else sleep 0.1s, then 0.2s
│   └─ raise RuntimeError("... failed after N attempts[ (stopped by open circuit breaker)]: err")
├─ kind == 'sse' → return payload
└─ _unwrap_sv_envelope(payload)   (may raise app error; breaker already saw success)
```

### 6.2 Spawning a remote walker (`walker_call`)

```text
walker_call(module, walker, args, stub_cls)
├─ URL / headers / timeout (unchanged)
├─ define send() = request_sync('POST', .../walker/...) then resp.json()   ← NEW
├─ _rpc_with_retries(module, "walker spawn '<label>'", send)              ← NEW (same loop as 6.1)
└─ _hydrate_walker_envelope(data, ...)
```

### 6.3 Half-open probe

```text
breaker OPEN, cooldown passes
├─ next call: breaker_should_skip flips to HALF_OPEN, returns False
├─ attempt 1 fails → record_failure → OPEN again, fresh opened_at
├─ breaker_should_skip → True → break                          ← NEW
└─ RuntimeError "failed after 1 attempts (stopped by open circuit breaker)"
```

| Scenario | Before | After |
|---|---|---|
| Dependency fully down, calls until OPEN | ~5 calls, 15 round trips | 2 calls, 5 round trips |
| Half-open probe against a still-down service | 3 round trips | 1 round trip |
| One call fails all 3 attempts (breaker stays closed) | `fails += 1` | `fails += 3` |
| Transport OK, app-error envelope | success recorded, no trip | same |
| Error text after 3 failed attempts | `...failed after 3 attempts: err` | identical |
| Error text when breaker cut the loop short | n/a | `...failed after 1 attempts (stopped by open circuit breaker): err` |

**Behaviour change users will notice:** callers open the breaker about 3× sooner. Two fully failed sv-to-sv calls now cause 30s of fail-fast in that process. Any successful round trip still resets the count, so a partly degraded service (for example during a rolling restart where most pods are serving) rarely reaches 5 consecutive failures.

## 11. Questions your senior might ask

**Q: Why not just move `breaker_record_failure` into the two existing loops?**
Then each remaining attempt would hit `fails >= threshold` again and refresh `opened_at`, pushing the cooldown out. The probe would still cost 3 round trips. Keeping two copies of the loop is also what let the bug happen twice, so you merged them into one helper.

**Q: Doesn't this triple the breaker's sensitivity?**
Yes: 2 fully failed calls now open it, instead of about 5. It was deliberate and is stated in the release note. Failures must be consecutive, and one success resets the count. So in practice only a fully unavailable dependency trips it, which is when fast shedding is wanted.

**Q: Can an application-error envelope now trip or delay the breaker?**
No. Success is still recorded right after the transport returns and before envelope decoding, exactly as on `main`. The existing test "application error envelope does NOT trip the breaker" still pins this.

**Q: Why didn't you call `breaker_should_skip` when building the error message?**
It flips OPEN to HALF_OPEN once the cooldown has passed. Formatting an error could therefore use up the probe slot, or report the wrong reason. The local `tripped` flag records why the loop actually stopped.

**Q: Is the error message unchanged for existing users?**
Yes, when all 3 attempts run: `stopped_by` is empty and `func_label` equals `module.func`. It differs only when the breaker cuts the loop short, and that case did not exist before.

**Q: What does this PR do about concurrent half-open probes?**
Nothing. That is Bug 2 of #7909, left for a follow-up. `breaker.jac` is unchanged. Per-process state and missing metrics are also out of scope.

**Q: Why does the e2e loop up to 10 calls instead of exactly 2?**
Breaker state is per pod, and the services have HPAs. A second `orders_app` replica would split failures across two breakers, so a fixed count could flake. The loop does not depend on the threshold arithmetic.

**Q: Does the e2e check really prove load shedding, given the grep also matches "(stopped by open circuit breaker)"?**
The grep alone does not tell a fast pre-call skip from a mid-call trip. The `< 5s` timing check is what shows the call did not do the full work. How fast refused connections are in that cluster is not shown in the PR.

**Q: Why are the transport imports still inside the functions?**
They resolve `sv_http.post_stream_aware_sync` and `request_sync` at call time. That is what lets the tests replace them with fakes. This is inferred from how the tests patch them; the rest of the module is not in the diff.
