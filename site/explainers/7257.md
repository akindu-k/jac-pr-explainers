## 1. The short version

On the jac-scale server, each walker HTTP request saves its graph changes through `ScaleTieredMemory`, the tiered memory layer used in scale mode. Saving means a "commit": it scans every in-memory (L1) anchor, hashes it, and writes the changed ones to the database (L3). **Each request ran that full O(N) scan up to three times: once when the walker finished, once while building the response, and once at context teardown.** That happened even for read-only requests. Issue #6699 measured about 340 ms per scan with about 10K anchors, so close to a second of waste per request.

A guard flag, `_committed`, was meant to make the later commits free. Only `acommit()` ever set it, so it almost never took effect. **You made `commit()` the owner of the flag. It clears `_committed` when it starts and sets it to `True` only when a full commit finishes cleanly. `put()` clears it too. The kernel commit stays the one real scan, and the later `acommit()` / `close()` calls skip in O(1).**

Your second commit (b095388) fixes a problem the first commit introduced. Without the reset on entry, a clean commit could leave `_committed = True`. A later commit could then fail with a write conflict, and the response-time `acommit()` would skip and hide the conflict. The result would be a silently lost update. The new unit test covers this case.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Walker | A Jac object that moves through the graph and runs code at each node. On the scale server, each walker is exposed as an HTTP endpoint. |
| Anchor | The wrapper that holds a graph object (node, edge, walker) plus its ID and storage metadata. Memory layers store anchors. |
| jac-scale / scale server | The plugin that runs Jac apps as a web service, here with FastAPI, and persists the graph to a database. |
| L1 / L2 / L3 | The memory tiers. L1 is the in-process memory of the current request, L2 is a shared cache, and L3 is the persistent database (for example SQLite). |
| `TieredMemory` | The base class that manages the tiers. It provides `put`, `delete`, `commit` and `_collect_into`. |
| `ScaleTieredMemory` | The scale plugin's subclass of `TieredMemory`. It owns the `_committed` flag. **This is where the bug is.** |
| Commit | Finding what changed in L1 and writing it to L3. In this class it is a full hash scan of L1. |
| `_collect_into(changes)` | Walks L1, compares each anchor's hash to its last saved hash, and adds the changed ones to a `ChangeSet`. This is the O(N) part. |
| `ChangeSet` | The list of pending writes collected for one commit. `is_empty()` means there is nothing to save. |
| `_committed` | A boolean meaning "L1 is clean as of the last commit". `acommit()` (and, per the PR, `close()`) read it to skip work. |
| `acommit()` | The async version of commit. If `_committed` is already True it returns early. Otherwise it runs `commit()` in a thread. |
| `close()` | Teardown of the memory at the end of the request context. It includes a safety-net commit. |
| `_sv_on_complete` | The kernel hook that runs when a top-level walker finishes. It calls `mem.commit()`. The CLI uses it as well. |
| `_finalize_call_response` | The server step that builds the HTTP response. It calls `Jac.acommit()`. |
| OCC / `WriteConflict` | Optimistic concurrency control. When two writers change the same object, the commit raises a conflict. The server turns that into a `409` and a retry. |
| Lost update | A write that is silently dropped, with no error reported. |
| `_mark_committed(anchor)` | New helper. It sets `_committed = True` only when `anchor is None`, meaning a full commit. |
| In-place field write | Code such as `here.count = here.count + 1`. It changes an existing object without calling `put()`, so only the hash scan notices it. |

## 3. The problem, step by step

### 3.1 The setup

- Kernel: `_sv_on_complete` → `mem.commit()` (scan #1).
- Server: `_finalize_call_response` → `Jac.acommit()` → `mem.acommit()` (scan #2 if the flag is False).
- Middleware: `ctx.mem.acommit()`, then `ctx.close()` → `mem.close()` → `commit()` (scan #3).
- `ScaleTieredMemory._committed` was supposed to coordinate these three, but only `acommit()` wrote to it.

### 3.2 What went wrong: redundant scans (performance)

```text
1. Request starts. _committed = False. L1 holds ~10K anchors. The walker is read-only.
2. Walker finishes → _sv_on_complete → mem.commit()
   → _collect_into scans 10K anchors → ChangeSet empty → return
   → _committed still False                         ← WRONG: commit() never set the flag
3. _finalize_call_response → mem.acommit()
   → _committed is False → runs commit() → scans 10K again (scan #2)
   → acommit sets _committed = True
4. Middleware → ctx.mem.acommit() → _committed True → skip
5. ctx.close() → mem.close() → commit() → scans again (scan #3)
   (per issue #6699: "close doesn't check _committed")
Result: 3 full scans for a request that wrote nothing.
```

### 3.3 The hazard your first fix created (correctness)

Commit 8087244 made `commit()` set the flag on success but did not clear it on entry. Your description shows the resulting timeline:

```text
1. Commit A runs clean → _committed = True
2. Walker does here.count = here.count + 1   (no put(), so the flag stays True)
3. Commit B scans, finds the change, applies it → WriteConflict raised
   → _committed is still True from step 1     ← WRONG: stale clean flag
4. The kernel completion hook swallows the conflict on purpose
   (finalize is meant to be the safety net)
5. _finalize_call_response → acommit() → sees True → SKIPS
6. No 409, no OCC retry → update silently lost
```

According to your description, this can happen when two commits run in one request. Examples are two top-level walkers, or an explicit `Jac.commit()` in the middle of a walker followed by a field-only write. Commit b095388 fixed it before merge.

### 3.4 Why it mattered

Issue #6699 measured on LittleX with 10K anchors:

- About 680 ms per request wasted on scans #2 and #3.
- About 650 ms of GC pause during response serialization. The issue blames allocation pressure from the redundant scans.
- About 1.3 s of avoidable overhead per walker request in total, read-only ones included (`load_feed`).

## 4. The idea of the fix (one sentence)

> **Make `commit()` the single source of truth for `_committed`.** It clears the flag on entry, sets it only after a full commit finishes cleanly, and `put()` clears it again, so later `acommit()`/`close()` calls skip only when nothing has been added since.

The issue proposed removing the kernel commit instead. That would drop CLI writes, because the CLI never reaches `_finalize_call_response`. Keeping the kernel commit as the one real scan and making the follow-up commits cheap keeps both the CLI and the server correct.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/memory/impl/memory_hierarchy.main.impl.jac`: flag ownership in `commit()` and `put()`

```diff
+impl ScaleTieredMemory._mark_committed(anchor: (Anchor | None)) -> None {
+    if anchor is None {
+        self._committed = True;          # NEW: only a full commit marks L1 clean
+    }
+}
+
+impl ScaleTieredMemory.put(anchor: Anchor) -> None {
+    self._committed = False;             # NEW: a new object means a pending write
+    super.put(anchor);
+}
+
 impl ScaleTieredMemory.commit(anchor: (Anchor | None) = None) -> None {
+    # clear the guard on entry so an earlier clean commit cannot mask a later one
+    self._committed = False;             # NEW (commit b095388)
     if self.l3 is None {
         self.changes.clear();
+        self._mark_committed(anchor);    # NEW: no-L3 path counts as clean
         return;
     }
     self._collect_into(self.changes);
     if self.changes.is_empty() {
+        self._mark_committed(anchor);    # NEW: nothing changed → clean
         return;
     }
 ...
     if (conflict := apply_report.primary_conflict()) {
         raise conflict;                  # flag stays False (cleared on entry)
     }
+    self._mark_committed(anchor);        # NEW: successful apply → clean
 }
```

**What:**

- `commit()` sets `_committed = False` first. It sets the flag back to True only on one of three clean exits:
  - no L3,
  - an empty changeset,
  - a successful apply with no conflict.
- Any exception, including a conflict, leaves the flag False.
- `put()` now clears the flag before delegating to the parent.

**Why:**

- Setting the flag in `commit()` lets the kernel commit "count". The finalize `acommit()` and teardown then skip, which removes scans #2 and #3.
- Clearing on entry fixes the lost-update hazard from 3.3.
- Clearing in `put()` means a brand-new object added after the scan still forces a real commit later.

**Things to notice:**

- `commit()` never reads the flag. A direct call always scans, so explicit callers cannot be skipped.
- A targeted `commit(anchor)` clears the flag but does not set it. The next `acommit()` therefore does a full scan, which is the safe direction.
- `delete()` is not overridden. Your description says the parent writes deletions to L3 immediately, and the kernel scan covers the rest. See Greptile's comment in section 9.
- Field-only writes made after the kernel scan do not clear the flag, so a later `acommit()`/`close()` would skip them. Your description relies on the kernel commit running after each walker to catch them. I cannot confirm from the diff that no code path writes after that point. This is the main residual risk.
- The hunk hides lines 104–123 of `commit()` (the apply logic). I could not see whether `anchor` changes what `_collect_into` collects.
- `acommit()` and `close()` are not in the diff. Your description says `close()` "keeps a guarded safety-net commit". Issue #6699, however, says `close()` did not check `_committed`. Either the guard already existed on `main` by the time of this PR, or it is somewhere I cannot see. The diff alone does not show how scan #3 goes away.

## 6. How execution flows after the PR

### 6.1 Server walker request

```text
HTTP request → spawn_walker_sync
├─ Jac.spawn() → osp_spawn() → walker runs
│  └─ _sv_on_complete → mem.commit()
│     ├─ _committed = False                         ← NEW
│     ├─ _collect_into(changes)  (full L1 scan, the only one)
│     ├─ empty?            → _mark_committed → True  ← NEW
│     ├─ applied clean     → _mark_committed → True  ← NEW
│     └─ conflict          → raise, flag stays False ← CHANGED
│        (the kernel hook swallows it)
├─ _finalize_call_response → mem.acommit()
│  ├─ _committed True  → skip, O(1)                  ← CHANGED (was a full scan)
│  └─ _committed False → commit() → re-raise conflict → 409 / OCC retry
└─ middleware
   ├─ ctx.mem.acommit() → skip if True
   └─ ctx.close() → mem.close() → guarded commit → skip if clean
      (per the PR description; close() is not in this diff)
```

### 6.2 Adding a new object

```text
mem.put(anchor)
├─ _committed = False      ← NEW
└─ TieredMemory.put(anchor)
```

### 6.3 CLI walker run

```text
walker finishes → _sv_on_complete → mem.commit() → full scan + persist (unchanged)
```

The CLI keeps its only persistence point.

| Scenario | Before | After |
|---|---|---|
| Read-only request | 3 scans | 1 scan |
| Write request, clean apply | 2–3 scans | 1 scan |
| Kernel commit conflicts | finalize rescans and raises | finalize rescans and raises (flag False) |
| Clean commit, then a field write that conflicts (first commit only) | n/a | conflict hidden, update lost: fixed by b095388 |
| `put()` after the kernel commit | rescanned anyway | flag cleared → rescan |
| Field-only write after the kernel commit | rescanned anyway | skipped (assumes no such writes happen on this path) |
| CLI | 1 kernel commit | unchanged |

Users will notice lower latency per request. Persistence behaviour stays the same as long as writes happen before or during the kernel commit.

### 7.1 `test "commit() re-arms _committed so an earlier clean commit cannot mask a later failure"`

**Setup:** It builds a bare `ScaleTieredMemory` with `object.__new__`, which skips `postinit`. It then gives it an empty `ChangeSet` and `l3 = None`.

**Steps:**

1. Call `mem.commit()`. This takes the no-L3 path, and the test asserts `_committed is True`.
2. Set `l3` to a dummy object and patch `TieredMemory._collect_into` to raise `RuntimeError`.
3. Call `commit()` again and assert two things:
   - the error propagates;
   - `_committed is False`.

**What it proves:** A failing commit cannot inherit the clean flag from an earlier commit. Your description says you checked that the test fails without the reset on entry. It uses a generic exception during collection, not a real `WriteConflict` from `primary_conflict()`. Since the flag is cleared before either point, the guarantee is the same.

**Why a new test:** It sits next to the existing `"acommit leaves _committed False when commit() raises"`, which covers `acommit()`. This one targets `commit()` itself, whose flag handling is new.

**Not covered by tests in this diff:**

- the scan count per request (your description mentions a scan-counting harness that was not committed);
- `put()` clearing the flag;
- a targeted `commit(anchor)` not setting the flag.

## 11. Questions your senior might ask

**Q: Why not remove the kernel commit, as the issue suggested?**
The CLI uses the same `_sv_on_complete` hook and never reaches `_finalize_call_response`. Removing the kernel commit would silently drop CLI writes.

**Q: Can `commit()` itself ever be skipped by the flag?**
No. `commit()` only writes the flag. Only `acommit()` and `close()` read it, so direct callers always get a full scan.

**Q: Why clear the flag on entry and not only on failure?**
Clearing on entry handles every exit path, including unexpected exceptions, without a `try/finally`. The flag always reflects the latest commit, and the OCC abort path needs no special reset.

**Q: What happens with a field-only write after the kernel commit?**
It does not clear the flag, so `acommit()`/`close()` would skip it. The design relies on the kernel commit running after every walker. The diff does not show whether any server code writes after that point, so this is the residual risk.

**Q: Why doesn't `commit(anchor)` set the flag?**
A targeted commit may not have saved everything in L1. Marking L1 clean would let later calls skip real pending writes. Not setting it means the next full commit scans, which is the safe choice.

**Q: Why not override `delete()`?**
Per Greptile and your description, the parent `delete()` writes to L3 immediately. Clearing the flag would only force a useless O(N) scan.

**Q: Where does the `close()` scan go away?**
Your description says `close()` has a guarded safety-net commit. `close()` is not in this diff, so be ready to point to the existing guard on `main`.

**Q: How do we know performance actually improved?**
Your description cites a local scan-counting harness (one scan instead of two or three) and an end-to-end SQLite run. Neither is in the committed tests. The ~1.3 s figure comes from the issue's LittleX measurements, not from a benchmark run in this PR.

**Q: Does the new test exercise a real `WriteConflict`?**
No. It makes `_collect_into` raise a `RuntimeError`. Because the flag is cleared before collection, the test still proves that a failing commit cannot inherit a stale True.
