## 1. The short version

The Jac runtime includes a small HTTP API server. It lets clients register (`POST /user/register`), log in (`POST /user/login`), and call functions and walkers. Each user gets a bearer token and a `root_id`, the ID of their personal graph root.

**Before this PR, a client could not ask the server "who am I?" after logging in.** The only way to learn your `username` and `root_id` was to save them from the register or login response. Issue #4130 asked for an endpoint that verifies the auth status and returns this information.

**You added `GET /user/info`. It checks the bearer token and returns the caller's `username`, `root_id` and stored `token` as JSON.** You also added the new endpoint to the root endpoint list, to the startup printout and to the endpoint docs. Five new tests cover it, and one existing test was extended.

**Status:** Merged on 2026-01-18, the same day it was opened. There were no reviews or comments. All six CI checks passed on the head commit `b85b3e8`.

## 3. The problem, step by step

This PR adds a feature, so this section describes the gap it fills.

### 3.1 The setup

- `JacAPIServer.create_handler` routes GET paths in an `if / elif` chain on `path`. Examples are `/functions`, `/walkers`, `/walker/<name>` and `/protected`.
- `AuthHandler` already had register, login, `update_username` and `update_password`.
- A client got `username`, `token` and `root_id` back only from register or login.

### 3.2 What was missing

```text
1. Client registers      → POST /user/register → {username, token, root_id}
2. Client saves only the token (for example in a browser's local storage)
3. Page reloads; the client still has the token, but not username or root_id
4. Client wants to show "logged in as alice" or use its root_id
5. No endpoint returns this for a token                     ← MISSING
6. Workarounds: store username/root_id on the client too, or log in again
   with the password, or call /protected just to see whether the token
   still works (that only checks validity; the diff does not show what
   /protected returns)
```

### 3.3 Why it mattered

Issue #4130 lists three uses:

- verifying that the client is still authenticated,
- displaying the user's information,
- getting the `root_id` for graph operations.

The diff and comments do not say which client (for example jac-client) needed this first.

## 4. The idea of the fix (one sentence)

> **Add an authenticated "who am I" route.** `GET /user/info` checks the bearer token, looks up the user it belongs to, and returns that user's `username`, `root_id` and `token`.

This follows the pattern of the existing auth routes: `AuthHandler` holds the logic and `create_handler` handles the routing. So the new code fits the way the server is already structured.

**What:** You added a new method signature to `obj AuthHandler`.

**Why:** In Jac, the declaration must exist before you can write `impl AuthHandler.get_user_info`.

**Things to notice:** The method takes a `token`, not a `username`. The other auth methods receive the username from the handler. This one validates the token again itself (see 6.1).

### 5.2 `jac/jaclang/runtimelib/impl/server.impl.jac`: the logic

#### 5.2.1 `AuthHandler.get_user_info`

```diff
+impl AuthHandler.get_user_info(token: str) -> TransportResponse {
+    import from jaclang.runtimelib.transport { TransportResponse, Meta }
+    username = self.user_manager.validate_token(token);
+    if not username {
+        return TransportResponse.fail(code='UNAUTHORIZED', message='Invalid or expired token',
+            meta=Meta(extra={'http_status': 401}));
+    }
+    user_data = self.user_manager.get_user(username);
+    if not user_data {
+        return TransportResponse.fail(code='NOT_FOUND', message='User not found',
+            meta=Meta(extra={'http_status': 404}));
+    }
+    # Return user info (note: get_user returns 'email' as key, but it's actually username)
+    return TransportResponse.success(
+        data={'username': username, 'root_id': user_data['root_id'], 'token': user_data['token']},
+        meta=Meta(extra={'http_status': 200}));
+}
```

**What:** The method works in three steps:

1. Turn the token into a username. If that fails, return 401.
2. Load the user record. If none exists, return 404.
3. Return `username`, `root_id` and the stored `token`.

**Why:** This is the core of the feature.

**Things to notice:**

- **The response includes `token`, but the PR description's example shows only `username` and `root_id`.** The tests assert that `token` is present. The description is the part that is out of date.
- `token` comes from `user_data['token']`, which is the token stored on the server. It is not necessarily the token in the request. If a user can hold more than one valid token, these two might differ. The diff does not show how `user_manager` stores tokens. In the after-login test, the returned token equals the login token. That suggests the stored token is the latest one.
- Echoing a bearer token back in a response is unusual. It adds no information for the caller, who already has it, and it is one more place a secret can leak, for example through logs.
- The comment about `'email'` does not match the code next to it. The code never reads an `email` key, and the `username` it returns comes from `validate_token`. The comment may describe how `get_user` stores records internally, which is not visible here. Either way it is confusing to a reader.
- The import inside the method body mirrors how other impls in this file do it. Only part of the file is visible, so this is not confirmed.

**What:** This is the new GET branch. It authenticates the request, extracts the raw token, and delegates to `AuthHandler`.

**Things to notice:**

## 6. How execution flows after the PR

### 6.1 Calling `GET /user/info`

```text
HTTP GET /user/info  (Authorization: Bearer <t>)
└─ create_handler GET dispatch
   └─ path == '/user/info'                                 ← NEW
      ├─ self._authenticate()
      │   └─ no/invalid token → 401 "Unauthorized - Authentication required"
      ├─ token = self._get_auth_token()                    ← NEW use
      └─ server.auth_handler.get_user_info(token)          ← NEW
         ├─ user_manager.validate_token(token) → username
         │   └─ falsy → 401 "Invalid or expired token"
         ├─ user_manager.get_user(username) → user_data
         │   └─ falsy → 404 "User not found"
         └─ 200 {username, root_id, token}
```

## 11. Questions your senior might ask

**Q: Why does the response include the token?**
The code returns `user_data['token']` and the tests assert it. The PR does not explain why, and the description's example leaves it out. The caller already holds the token, so you could drop it.

**Q: Is the returned token the same as the one in the request?**
Not guaranteed. It is the token stored by `user_manager`. The after-login test shows that it equals the latest login token. With multiple active tokens it could differ, but the diff does not show how tokens are stored.

**Q: Why is the token validated twice?**
The route calls `_authenticate()` first, and then `get_user_info(token)` validates again. It is redundant. The inner check makes the method safe to call on its own, but the outer `username` value is wasted.

**Q: When can the 404 happen?**
When `validate_token` returns a username but `get_user` returns nothing, for example if the user record is gone while the token is still valid. The diff cannot tell how likely that is, and no test covers it.

**Q: What does the "'email' as key" comment mean?**
It is not explained in the PR. The code here never reads `email`. It probably refers to how `user_manager` stores records internally, which is not visible in this diff.

**Q: Does jac-scale's server get the same endpoint?**
Only `jaclang/runtimelib` changed. Whether jac-scale reuses this handler or has its own cannot be told from the diff. test-scale passed, but that only shows nothing broke.

**Q: Why is this a GET with no body?**
It only reads data, and the identity comes from the `Authorization` header. That matches the issue's request.

**Q: Did you update the user-facing docs?**
Only the in-code listings were updated: the root endpoint JSON, the startup print and `print_endpoint_docs`. No docs or release notes files changed.
