## 1. The short version

`jac-scale` runs a Jac app as a FastAPI web server. Users register or log in, and the server gives them a **JWT**, a signed token that proves who they are. Each token expires after 7 days. The token is signed with a secret key.

**Before this PR, the signing secret (`'supersecretkey'`), the algorithm and the lifetime were hard-coded in `serve.jac`, and a client had no way to get a fresh token without logging in again.** Anyone who read the public source knew the key. That meant they could forge a token for any user on any deployment that never edited that file.

**You made the three JWT settings readable from environment variables (with the old values as defaults), and you added a `POST /user/refresh-token` endpoint.** The endpoint takes a still-valid token and returns a new one with a new 7-day expiry. You also changed the `iat` ("issued at") claim to a float timestamp, documented the variables in the README, fixed the order of the `git clone` commands in the README, and added 11 integration tests.

One problem is visible in the diff and was not caught. `os.getenv('JWT_EXP_DELTA_DAYS', 7)` returns a **string** when the variable is set. `timedelta(days="7")` then raises `TypeError`. The default case works only because the default value is the integer `7`.

**Status:** Merged on 2025-12-13. @marsninja approved it with no comments. All four CI checks passed on the head commit `fa8e7de`.

| `JEndPoint` / `APIParameter` | Objects that describe one endpoint (method, path, callback) and its inputs. They are passed to `server_impl.add_endpoint`. |
| `ParameterType.BODY` | Says the parameter comes from the JSON request body, e.g. `{"token": "..."}`. It does not come from a header. |
| FastAPI / OpenAPI | The Python web framework underneath. It builds `/docs` and `/openapi.json` automatically from the registered endpoints. |
| JWT (JSON Web Token) | A string with three parts: `header.payload.signature`. The payload holds claims like `{"username": "a@b.com", "exp": ..., "iat": ...}`. Only someone with the secret can make a valid signature. |
| `exp` claim | The expiry time. `jwt.decode` rejects the token after this time when `verify_exp` is on. |
| `iat` claim | "Issued at": when the token was made. |
| HS256 | An HMAC algorithm. One shared secret both signs and verifies tokens. |
| PyJWT (`jwt`) | The Python library used here. `jwt.encode` signs a payload and `jwt.decode` checks it. In the tests it is imported as `pyjwt`. |
| `create_jwt_token(username)` | An existing static method that builds the payload and signs it. |
| `refresh_jwt_token(token)` | A new static method. It verifies the token and, if valid, returns a brand-new token for the same username. Otherwise it returns `None`. |
| `refresh_token(self, token)` | The new endpoint callback. It checks the input, strips `Bearer `, calls `refresh_jwt_token`, and returns a 200, 400 or 401 response. |
| `Bearer` prefix | The common form `"Bearer <token>"` from `Authorization` headers. The endpoint accepts the token with or without it. |
| Environment variable | A setting given to the process from outside, e.g. `JWT_SECRET=abc jac serve app.jac`. `os.getenv(name, default)` reads it. The result is always a **string** when the variable is set. |
| 400 / 401 / 422 | HTTP status codes. 400 = bad request (your check), 401 = not authenticated, 422 = FastAPI's own validation error when a required body field is missing. |

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- `serve.jac` signs tokens in `create_jwt_token` using module constants set in `with entry`.
- Register and login return a token. (The diff shows `/user/register` returning `"token"`. The login code is not in the diff.)
- Tokens last `JWT_EXP_DELTA_DAYS = 7` days.

### 3.2 What was missing

**Case A: hard-coded secret**

```text
1. Operator deploys a jac-scale app; serve.jac has JWT_SECRET = 'supersecretkey'
2. The repo is public, so the secret is public
3. Attacker runs jwt.encode({"username": "victim@x.com", "exp": ...}, "supersecretkey", "HS256")
4. Server verifies the signature with the same key -> accepted        <-- WRONG: forged identity
5. The only fix was to edit library source code in each deployment
```

**Case B: no refresh**

```text
1. Day 0: user logs in -> token T1, exp = day 7
2. Day 6: client wants to keep the session alive
3. No endpoint exists to exchange T1 for a new token                   <-- MISSING
4. Day 7: T1 expires -> user must enter their password again
```

### 3.3 Why it mattered

No issue is linked and there are no discussion comments, so the motivation comes only from your description. It cites "improving security and configurability" and letting "clients obtain new tokens when their current ones are expiring." Case A is the stronger reason. The hard-coded secret meant every default deployment shared one public signing key.

## 4. The idea of the fix (one sentence)

> **Read JWT settings from the environment, and let a still-valid token buy a new one.** The server now takes `JWT_SECRET`, `JWT_ALGORITHM` and `JWT_EXP_DELTA_DAYS` from env vars and exposes `POST /user/refresh-token`, which verifies a token and re-issues it for the same username.

Env vars are the normal way to give secrets to a container, which fits how `jac-scale` deploys to Kubernetes. Reusing `create_jwt_token` for refresh means refreshed tokens look exactly like login tokens.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/serve.jac`: JWT config from env vars

```diff
 import jwt;
+import os;
 ...
 with entry {
-    JWT_SECRET = 'supersecretkey';
-    JWT_ALGORITHM = 'HS256';
-    JWT_EXP_DELTA_DAYS = 7;
+    JWT_SECRET = os.getenv('JWT_SECRET', 'supersecretkey');
+    JWT_ALGORITHM = os.getenv('JWT_ALGORITHM', 'HS256');
+    JWT_EXP_DELTA_DAYS = os.getenv('JWT_EXP_DELTA_DAYS', 7);   # string if set, int 7 if not
 }
```

**What:** Each constant now comes from the environment, and the old value is used if the variable is unset.

**Why:** This fixes Case A. Operators can set their own secret without editing code.

**Things to notice:**
- **Bug:** if `JWT_EXP_DELTA_DAYS` is set, its value is a string like `"7"`. `timedelta(days="7")` raises `TypeError: unsupported type for timedelta days component: str`. Token creation will then fail. The fix is `int(os.getenv('JWT_EXP_DELTA_DAYS', '7'))`. No test sets this variable, so CI could not catch it.
- If `JWT_SECRET` is unset, the server still quietly uses the public `'supersecretkey'`. There is no warning or refusal to start.
- `JWT_ALGORITHM` only makes sense for HMAC algorithms (HS256/384/512), because the code passes one shared secret to both encode and decode. Asymmetric algorithms like RS256 need a key pair, which this code does not support.
- The values are read once when the module loads. Changing an env var needs a restart.

### 5.2 `jac-scale/jac_scale/serve.jac`: `iat` as a timestamp

```diff
             'exp': (now + timedelta(days=JWT_EXP_DELTA_DAYS)),
-            'iat': now
+            'iat': now.timestamp()      # NEW: float seconds, e.g. 1765500000.123456
```

**What:** `iat` is now a float number of seconds instead of a `datetime`.

**Why:** The description says this is "for better standards compliance." Note that PyJWT already converts a `datetime` `iat` to an integer timestamp when encoding, so the old value was already numeric in the token.

**Things to notice:**
- The real effect is that `iat` now keeps fractional seconds. `exp` is still a `datetime`, so it is still rounded to whole seconds.
- This likely matters for `test_refresh_token_multiple_times`. That test refreshes twice with no sleep and asserts each token is different. With whole-second `iat` and `exp`, two tokens made within the same second for the same user would be byte-identical. The diff doesn't say this was the reason, but it is the visible consequence.
- Tokens issued before this change still decode fine.

### 5.3 `jac-scale/jac_scale/serve.jac`: `refresh_jwt_token` static method

```diff
+    static def refresh_jwt_token(token: str) -> (str | None) {
+        try {
+            decoded = jwt.decode(
+                token, JWT_SECRET,
+                algorithms=[JWT_ALGORITHM],
+                options={"verify_exp": True}       # expired tokens are rejected
+            );
+            username = decoded.get('username');
+            if not username { return None; }
+            return JacAPIServer.create_jwt_token(username);
+        } except Exception {
+            return None;                           # any failure -> None
+        }
+    }
```

**What:** It checks the signature and expiry, reads `username`, and signs a fresh token. It returns `None` on any problem.

**Why:** This is the core of Case B.

**Things to notice:**
- `verify_exp: True` is already PyJWT's default. Writing it out makes the intent clear. The commit history shows the design changed:
  - An earlier version had a separate `JWT_REFRESH_MAX_DAYS` window that allowed expired tokens to be refreshed.
  - Commit `ec962e0` removed it, so expired tokens now return `None`.
  - Commit `b3f0d26` then enabled the expiry check explicitly.
- **Result:** any valid token can be refreshed, again and again, forever. A stolen token stays usable as long as the thief keeps refreshing it. There is no separate long-lived refresh token, no revocation and no maximum session age.
- **No user lookup:** the method does not check that `username` still exists. A valid token for a deleted user can still be refreshed.
- `except Exception` hides everything, including the `TypeError` from 5.1. With `JWT_EXP_DELTA_DAYS` set, every refresh would return 401 "Invalid or expired token" instead of a server error. That would make the bug hard to diagnose.

### 5.4 `jac-scale/jac_scale/serve.jac`: `refresh_token` callback

```diff
+    def refresh_token(self: JacAPIServer, token: (str | None) = None) -> JSONResponse {
+        if (not token) {
+            return JSONResponse(status_code=400, content={'error': 'Token is required'});
+        }
+        if token.startswith('Bearer ') { token = token[7:]; }
+        new_token = self.refresh_jwt_token(token);
+        if (not new_token) {
+            return JSONResponse(status_code=401, content={'error': 'Invalid or expired token'});
+        }
+        return JSONResponse(status_code=200,
+            content={'token': new_token, 'message': 'Token refreshed successfully'});
+    }
```

**What:** It maps the inputs to responses:
- Empty or missing token → 400.
- Invalid or expired token → 401.
- Success → 200 with the new token.

**Why:** This is the HTTP face of the refresh logic.

**Things to notice:** The token travels in the JSON body. Stripping `Bearer ` is a convenience so clients can paste the value they use in headers.

### 5.5 `jac-scale/jac_scale/serve.jac`: endpoint registration

**Things to notice:**

## 6. How execution flows after the PR

### 6.1 Server start / module load

```text
import serve.jac
└─ with entry
   ├─ JWT_SECRET         = env JWT_SECRET or 'supersecretkey'          ← CHANGED
   ├─ JWT_ALGORITHM      = env JWT_ALGORITHM or 'HS256'                ← CHANGED
   └─ JWT_EXP_DELTA_DAYS = env value (str!) or 7 (int)                 ← CHANGED
JacAPIServer setup
├─ register_create_user_endpoint / login / page
├─ register_refresh_token_endpoint()  → POST /user/refresh-token       ← NEW
└─ client js / static / walkers ...
```

### 6.2 Creating a token (register, login, refresh)

```text
create_jwt_token(username)
├─ now = current UTC time
├─ payload = {username, exp: now + JWT_EXP_DELTA_DAYS days, iat: now.timestamp()}  ← CHANGED (iat float)
│     └─ if JWT_EXP_DELTA_DAYS is a str → TypeError                     ← NEW failure mode
└─ jwt.encode(payload, JWT_SECRET, JWT_ALGORITHM)
```

### 6.3 `POST /user/refresh-token`

```text
client sends {"token": "Bearer eyJ..."}
└─ FastAPI body validation (may return 422 if "token" is absent)
   └─ refresh_token(token)                                             ← NEW
      ├─ token empty?          → 400 {"error": "Token is required"}
      ├─ strip "Bearer "
      └─ refresh_jwt_token(token)                                       ← NEW
         ├─ jwt.decode(verify signature + exp)
         │   └─ fails (bad sig, malformed, expired) → None
         ├─ no username         → None
         ├─ create_jwt_token(username) (any exception → None)
         ├─ None  → 401 {"error": "Invalid or expired token"}
         └─ token → 200 {"token": new, "message": "Token refreshed successfully"}
```

| Scenario | Before | After |
|---|---|---|
| Client wants a new token before expiry | Must log in again | `POST /user/refresh-token` → 200 |
| Token already expired | Must log in again | 401; must log in again |
| Body `{"token": ""}` | n/a | 400 |
| Body `{}` | n/a | Likely 422 from FastAPI (not confirmed by the diff) |
| `JWT_SECRET=xyz` set | Ignored; key is `supersecretkey` | Key is `xyz`; old tokens become invalid |
| `JWT_EXP_DELTA_DAYS=30` set | Ignored | `TypeError` when creating tokens; refresh returns 401 |
| Valid token for a deleted user | n/a | Refresh succeeds |

**User-visible changes:**
- Deployments that set `JWT_SECRET` will invalidate all tokens issued under the old key.
- Sessions can now be extended without limit by refreshing.

## 11. Questions your senior might ask

**Q: What happens if I set `JWT_EXP_DELTA_DAYS=30`?**
`os.getenv` returns `"30"`, a string. `timedelta(days="30")` raises `TypeError`. Register and login would fail, and refresh would return 401 because of the broad `except`. It needs an `int(...)` cast.

**Q: Can an expired token be refreshed?**
No. `verify_exp: True` makes `jwt.decode` reject it, and the endpoint returns 401. Commit `ec962e0` removed the earlier `JWT_REFRESH_MAX_DAYS` grace window on purpose.

**Q: Doesn't this make sessions last forever?**
Yes. Any valid token can be exchanged for a new 7-day token over and over. There is no maximum session age and no revocation. A leaked token stays usable as long as someone keeps refreshing it.

**Q: Why change `iat` to `now.timestamp()`?**
The description says standards compliance. PyJWT already turned the `datetime` into an integer. The practical change is fractional seconds, which makes tokens issued in the same second different. `test_refresh_token_multiple_times` depends on that.

**Q: Does refresh check that the user still exists?**
No. It only reads `username` from the token. The `nonexistent_user` test passes only because its token is expired.

**Q: Why is the token in the body and not the `Authorization` header?**
The parameter is declared as `ParameterType.BODY`. The `Bearer ` stripping lets clients send the header value as-is. The PR doesn't explain why a header was not used.

**Q: Is the system safer now if nobody sets `JWT_SECRET`?**
No. The default is still the public `'supersecretkey'`. The change only helps operators who set the variable, and nothing warns those who don't.

**Q: Can I use RS256 through `JWT_ALGORITHM`?**
Not with this code. The same `JWT_SECRET` string is used to sign and verify, which only fits HMAC algorithms like HS256.

**Q: Why are there README `git clone` changes in this PR?**
They came from earlier commits on your fork's `main` (`ab85596`, `7fca7a3`). They fix the order so `git submodule update` runs inside the cloned repo. They are unrelated to JWT.
