## 1. The short version

jac-scale serves Jac walkers and functions over HTTP through a FastAPI server. Each request gets a Jac *context*: the per-request runtime state, including which user's graph root the code reads and writes. Before this PR, the endpoint callbacks parsed the JWT from the `Authorization` header themselves. Only after that did they switch the context to the real user.

**Per the PR description, the context started out as `system_root` (the shared root every user can reach) and only switched to the real user later, inside the endpoint, so any code that ran in between ran as the system root.** JWT parsing was also copied into two callbacks, and nothing rejected a bad token in one central place.

**You added `jwt_validation_middleware`, which runs before `request_context_middleware`. It validates the Bearer token, looks up the user's `root_id`, stores both on `request.state`, and returns `401` at once for any token it cannot validate.** The endpoint callbacks now just read `request.state.username`. `get_root_id()` gained a small per-request cache, so the middleware and the endpoint don't both hit storage.

One thing to check before you present: the diff does **not** change `request_context_middleware`. The description says it now reads `user_root_id` from `request.state`, but that code is not in this diff (see §5.2 and §10).

**Status:** Merged on 2026-04-17. All test checks passed on the head commit. The data shows one inline review question, which you answered, and no recorded approval.

## 3. The problem, step by step

### 3.1 The setup

- `JFastApiServer.init` registers `request_context_middleware`. That middleware creates the Jac context (`create_j_context(user_root=None)`) and sets it as the request context.
- The endpoint callback (`create_walker_callback` / `create_function_callback`) then reads the `Authorization` header, validates the JWT, and runs the walker or function.
- Per the description, the endpoint path calls `set_user_root()` to move the context from system root to the real user.

### 3.2 What went wrong

#### 3.2.1 The timing window (as described in the PR)

```text
1. Request arrives with "Authorization: Bearer <alice-token>"
2. request_context_middleware: ctx created          → current root = system_root
3. call_next(request) → endpoint callback starts      → current root = system_root
4. callback parses header, validate_jwt_token → "alice"
5. ... any code running here ...                      → current root = system_root   ← WRONG
6. set_user_root(alice_root)                          → current root = alice_root
7. walker runs as alice
```

The "before" code for steps 2 and 6 is mostly outside the diff. This timeline comes from the PR description.

#### 3.2.2 Duplicated, endpoint-only token checks

```text
1. create_walker_callback:   own copy of "Bearer " parsing + validate_jwt_token
2. create_function_callback: identical second copy
3. Public endpoint (requires_auth = False) + forged token
   → parsing skipped entirely, token silently ignored              ← no central rejection
4. Non-walker routes never look at the token at all
```

### 3.3 Why it mattered

- The system root is shared by all users. Anything that wrote data during the window could land somewhere every user can see. That breaks per-user isolation.
- Bad tokens were not rejected centrally. On public endpoints they were quietly treated as anonymous.
- No issue is linked and no comment reports a real incident. The impact as stated comes only from the PR description.

## 4. The idea of the fix (one sentence)

> **Authenticate before the context exists.** A new outermost middleware validates the JWT and puts the user's identity on `request.state`, so everything downstream already knows who the user is.

This removes the "switch user later" step and puts token handling in one place. Every route now gets the same check, and the two duplicated copies go away.

**What:**
- `set_user_manager` stores the manager and refuses `None`.
- The middleware handles every HTTP request:
  - No `Bearer` header: it records `username=None` and `user_root_id=None` and continues.
  - A `Bearer` token that validates: it records the username and root id.
  - A `Bearer` token that does not validate: it returns `401` without calling the rest of the app.

**Why:** It gives one central point that rejects bad tokens. It also makes the user's identity available before `request_context_middleware` runs.

**Things to notice:**
- **`request_context_middleware` itself is not modified.** This file is exactly +54 −0, which is all setter, middleware, comment and registration lines. The description says that middleware now reads `request.state.user_root_id` and calls `ctx.set_user_root()` at creation. If that happens, it is in code outside this diff (perhaps it already existed). Confirm this before presenting, because it is the core of the "timing window" claim.
- The rejection is broad. Any route with a bad Bearer token gets 401, including public walkers. If no other route-level exemption exists, that may also include `/user/login`, `/user/register` and static files. The diff alone can't tell.
- If `_user_manager` is never set, every Bearer request gets 401, because `token_attempted` is true and `username` is `None`. The error text in `set_user_manager` says such requests would "run as the guest user", which does not match what the code does.
- The 401 body is a hand-built `JSONResponse`, not `TransportResponse.fail(...)`. It has no `meta.http_status`, so the shape may differ from the old endpoint 401.
- `validate_jwt_token` and `get_root_id` are synchronous calls inside an async middleware. A slow storage lookup blocks the event loop.
- `postinit` adds `CORSMiddleware` after the server exists. It is therefore registered later and sits outside the JWT middleware, so 401 responses should still get CORS headers. Verify this in the code that is not shown.

## 6. How execution flows after the PR

### 6.1 Request with a valid token

```text
HTTP request "Authorization: Bearer <valid>"
├─ (CORSMiddleware, outermost, unchanged)
├─ jwt_validation_middleware                                   ← NEW
│   ├─ token = header[7:], token_attempted = True
│   ├─ validate_jwt_token(token) → "alice"
│   ├─ get_root_id("alice")                                    ← CHANGED (cache)
│   │   ├─ cache miss → identity storage → "root-123"
│   │   └─ cache["alice"] = "root-123"
│   ├─ request.state.username = "alice", user_root_id = "root-123"
│   └─ call_next
├─ request_context_middleware
│   ├─ create_j_context(user_root=None)
│   └─ (description: set_user_root from request.state — not visible in diff)
└─ walker/function callback                                    ← CHANGED
    ├─ username = request.state.username → "alice"
    ├─ requires_auth and username → OK
    └─ execute walker/function
```

### 6.2 Request with a bad token (forged, expired or malformed)

```text
HTTP request "Authorization: Bearer <bad>"
├─ jwt_validation_middleware                                   ← NEW
│   ├─ token_attempted = True
│   ├─ validate_jwt_token → falsy
│   └─ return JSONResponse 401 {ok:false, error:{code:UNAUTHORIZED}}
└─ (context and endpoint never run)
```

### 6.3 Request with no token

```text
HTTP request (no Authorization header)
├─ jwt_validation_middleware → state.username = None, user_root_id = None ← NEW
├─ request_context_middleware
└─ callback
    ├─ requires_auth → TransportResponse.fail 401              ← CHANGED (single check)
    └─ public       → runs anonymously
```

| Scenario | Before | After |
|---|---|---|
| Valid token, auth endpoint | 200, validated in callback | 200, validated in middleware |
| Valid token, public endpoint | 200, token ignored (`username=None`) | 200, `username` set from token (**change**) |
| Bad token, auth endpoint | 401 via `TransportResponse` | 401 via middleware `JSONResponse` (body shape may differ) |
| Bad token, public endpoint | 200, token ignored | **401** |
| Bad token, any other route (login, static…) | token not checked | **401** (unless exempted elsewhere; not visible) |
| No token, auth endpoint | 401 | 401 |
| No token, public endpoint | 200 | 200 |
| Non-Bearer header (e.g. `Basic …`) | treated as no token | treated as no token |

The user-visible change: a client holding a stale or expired token and calling a public endpoint now gets 401 where it used to succeed.

## 11. Questions your senior might ask

**Q: Where exactly is the context switched to the user root now?**
The description says `request_context_middleware` does it from `request.state.user_root_id`, but that change is not in this diff. Check the unchanged part of that function before answering.

**Q: Why register `request_context_middleware` first if JWT must run first?**
Starlette inserts each middleware at index 0. The last one registered becomes the outermost and runs first. The code comment states this.

**Q: Does a stale token now break public pages or login?**
Yes for public walkers: the test asserts 401. For login, register and static routes, the middleware covers every HTTP request, so a stale Bearer header would also get 401 unless something not in this diff exempts those routes.

**Q: Do API keys use the `Authorization: Bearer` header?**
Unknown from this diff. If they do, `validate_jwt_token` would fail on them and the middleware would return 401. Needs checking.

**Q: Is the `ContextVar` cache safe across concurrent requests?**
Each request normally runs in its own async context, so values don't leak between requests. Writes copy the dict, so a child context never changes its parent's dict. Nothing clears the cache explicitly.

**Q: Why a dict and not a single value?**
You answered @kugesan1105: a future admin handler may look up several users in one request.

**Q: Does the 401 body look the same as before?**
Not necessarily. The middleware returns `{'ok': False, 'error': {...}}` directly, while endpoints use `TransportResponse.fail` with `meta.http_status`. Clients parsing `meta` may see a difference.

**Q: What happens if `set_user_manager` is never called?**
Every Bearer request gets 401, because the middleware can't validate anything. Calling it with `None` raises a `RuntimeError` at start-up.

**Q: Do public walkers now run as the logged-in user when a valid token is sent?**
`username` is now filled in for public endpoints too. How it is used after that is outside the diff, but it likely changes which root they run under.

**Q: Does the new test prove the timing window is fixed?**
No. It proves rejection and per-user isolation. It does not check which root the context holds at creation.
