## 1. The short version

`jac.toml` can point a setting at an environment variable, for example `OPENAI_API_KEY = "${OPENAI_API_KEY}"`, or `namespace = "${K8S_NAMESPACE:?set K8S_NAMESPACE}"`. When Jac loads the file, it swaps in the value from the machine running the command. If the variable is missing, both forms are documented to be an error. The `:?` form exists only to stop a deploy when something required is missing.

**Before this PR, a missing variable never stopped anything: the config loader caught the error and kept the literal text, so `jac scale deploy` (dry run included) shipped `${OPENAI_API_KEY}` into a Kubernetes Secret as the real API key.** The pods then failed much later with an authentication error from OpenAI. That error pointed away from the real cause.

**You made loading record every reference it could not fill in (on `JacConfig.unresolved`, with the setting's path), and you made the Kubernetes deploy refuse to continue when one of those unresolved values is about to be shipped as a secret or a target setting.** Loading itself stays silent, so `jac check`, `jac fmt` and `jac lsp` still work without production variables exported. That was the problem with the earlier attempt, #9045.

A reviewer found gaps after merge. `${VAR:+alt}` and `${VAR:0:3}` still slip through (tracked in #9184). @MusabMahmoodh also showed that app-level `scale.env`, gateway env, labels and annotations are not checked.

**Status:** merged on 2026-09-20. No review was recorded before merge. One post-merge comment from @MusabMahmoodh (2026-09-21) raises two open points. All CI checks on the head commit passed or were skipped.

| `resolve_env_refs` | New walker. It resolves a whole config tree and returns `(resolved_data, refs)`. This is the "gather" step. |
| `report_env_findings` | New function that raises one `ValueError` listing every ref, or does nothing if there are none. This is the "policy" step. |
| `JacConfig.unresolved` | New field on the loaded config holding the `UnresolvedRef`s found at load. |
| `validate_against_schema` / `report_schema_findings` | An existing gather-then-report pair in the codebase. This PR copies that pattern. |
| jac-scale | The plugin that deploys a Jac app to Kubernetes. |
| `[scale.secrets]` | TOML section whose entries become a Kubernetes `Secret`. |
| `[scale.kubernetes]` | TOML section of deploy target settings: namespace, app name and so on. It becomes `KubernetesConfig` (`k8s_config`). |
| `ManifestBuilder` | jac-scale class that turns config into Kubernetes YAML manifests. |
| `_check_pod_config_resolves` | Existing check from #9199. It verifies that the `jac.toml` shipped to pods can resolve in the *pod's* environment. The new check is called from inside it. |
| `_check_deploy_settings_resolve` | New check. It verifies that values resolved on the *deploy machine* aren't still `${...}`. |
| `--dry-run` | Print the deploy plan without applying it. The original complaint was that it reported a clean plan. |
| Table-driven test | One test that loops over a list of `(input, expected)` rows. |

## 3. The problem, step by step

### 3.1 The setup

- `interpolate_env_vars` (in `config.impl.jac`) raised `ValueError` for `${VAR}` or `${VAR:?msg}` when `VAR` was unset. That part was correct.
- `_interpolate_recursive` walked the TOML data and called it on each string.
- `ManifestBuilder` took the resolved `secrets` and `k8s_config` and wrote them into manifests.

### 3.2 What went wrong: unset required variable

```text
1. jac.toml: [scale.kubernetes] namespace = "${K8S_NAMESPACE:?set K8S_NAMESPACE}"
2. K8S_NAMESPACE is not exported on the deploy machine
3. Config load → _interpolate_recursive("${K8S_NAMESPACE:?set K8S_NAMESPACE}")
4. interpolate_env_vars raises ValueError("... is required: set K8S_NAMESPACE")
5. _interpolate_recursive catches it and returns the original string      ← WRONG
6. k8s_config.namespace == "${K8S_NAMESPACE:?set K8S_NAMESPACE}"
7. jac start --scale --dry-run prints "Namespace: ${K8S_NAMESPACE:?...}" and
   "check: no errors or warnings"
8. A real deploy writes that literal into the manifests
```

### 3.3 What went wrong: unset plain secret

```text
1. jac.toml: [scale.secrets] OPENAI_API_KEY = "${OPENAI_API_KEY}"
2. OPENAI_API_KEY not exported
3. interpolate_env_vars raises "not set"; the walker swallows it       ← WRONG
4. secrets == {"OPENAI_API_KEY": "${OPENAI_API_KEY}"}
5. Secret manifest: stringData.OPENAI_API_KEY: ${OPENAI_API_KEY}
6. Pods start and look healthy
7. First call to OpenAI → authentication error
8. Debugging goes to the OpenAI account, not to the deploy machine
```

### 3.4 A side effect: one missing variable wiped the whole string

Before the PR, the raise aborted the whole `re.sub` for that string. The walker then returned the *original* string. #9184 records this, and this PR fixed it:

```text
SET=s, MISSING unset
"${SET}/${MISSING}"
  before: "${SET}/${MISSING}"   (even SET was not substituted)
  after:  "s/${MISSING}"        (only MISSING remains, and it is recorded)
"${MISSING}/${ALSO}"
  before: one error, then swallowed
  after:  both MISSING and ALSO recorded
```

### 3.5 Why it mattered

- #8773 calls `:?` "silently inert". The one guard rail for "must be set before you deploy" quietly produced the bad value it was meant to prevent.
- The failure surfaced far away, as a provider auth error inside the running app. The release note says the same.
- The obvious fix, #9045 (raise at load), broke `jac check`, `jac fmt` and `jac lsp` for anyone without production secrets. @MusabMahmoodh also pointed out, in that PR's review, two jac-scale paths it broke:
  - pods read the shipped `jac.toml` at boot under a different environment;
  - some scale commands load the project `.env` *after* the config loads.

## 4. The idea of the fix (one sentence)

> **Remember what didn't resolve, and let the command that uses the value decide.** Loading records every unresolved `${...}` with its setting path, and only the deploy refuses when one of those values is about to be shipped.

This is the right idea because whether a missing variable matters depends on what you do next. Raising at load forces "fail for everyone" (#9045). Swallowing forces "fail for nobody" (the bug). Keeping the answer allows a per-command decision.

**What:**
1. It loads the project config.
2. It collects every string value that will be shipped as a secret or a top-level target setting.
3. It keeps only the unresolved refs whose `raw` value is one of those strings.

**Why:** This is the policy step. Only the deploy cares, and only about values it actually ships.

**Things to notice:**
- **Matching is by value, not by path.** The upside: a value that reaches `secrets` through `[apps.<name>]` or a profile overlay is still caught if the same string was recorded at load. The downside: if a non-shipped setting has the identical text (e.g. `[serve] x = "${OPENAI_API_KEY}"`), its path also shows in the error list. That makes the list noisier, though it never causes a stop on its own.
- Only `self.secrets` and the **top-level** string fields of `k8s_config.to_dict()` are checked. App-level `scale.env`, gateway `env`, labels and annotations are not. This is @MusabMahmoodh's post-merge point 1.

- `get_config_for_path` reflects the environment at the moment it loads. The diff doesn't show whether it caches a config loaded *before* the project `.env` is applied. If it does, the "put it in the project .env" hint could fail to help.

## 6. How execution flows after the PR

### 6.1 Loading config (every command: `check`, `fmt`, `lsp`, `start`, deploy)

```text
JacConfig.load(toml_path)
└─ _parse_toml_data(data)
   ├─ resolve_env_refs(raw)                              ← NEW (was _interpolate_recursive)
   │  └─ walk(item, path)
   │     ├─ str  → interpolate_env_vars(item, environ, sink=found)   ← CHANGED
   │     │        ├─ VAR set           → value substituted
   │     │        ├─ ${VAR:-d} unset   → "d"
   │     │        ├─ non-identifier    → literal kept, nothing recorded
   │     │        ├─ ${VAR:+x}/${VAR:0:3} → no pattern match, literal kept, nothing recorded
   │     │        └─ VAR unset         → UnresolvedRef appended, literal kept   ← NEW
   │     │        then ref.path = path, ref.raw = resolved               ← NEW
   │     ├─ dict → walk each value with "a.b" paths
   │     └─ list → walk each item with "a[i]" paths
   ├─ config.unresolved = refs                           ← NEW
   └─ command continues; nothing printed or raised
```

`merge_from_toml_file` follows the same path and appends to `self.unresolved`.

## 11. Questions your senior might ask

**Q: Why not just raise at load, like #9045?**
Every command loads `jac.toml`. Raising there broke `jac check`, `fmt` and `lsp` for anyone without production secrets. It also broke pods booting under a different environment and commands that load `.env` after the config. Recording at load and deciding at use avoids all three.

**Q: Why match unresolved refs by value instead of by path?**
A value can reach `secrets` through `[apps.<name>]` or a profile overlay, so its path is not under `scale.secrets`. Matching the shipped string still catches it. The cost: an unrelated setting with identical text also gets listed in the error, though it can't cause a stop on its own.

**Q: Does this catch `${VAR:+alt}`?**
No. That form doesn't match the parser's pattern, so no `UnresolvedRef` is produced and the check has nothing to report. #9184 tracks it. The proposed fix there is to record any `${...}` the parser doesn't understand.

**Q: What about env vars set per app under `[apps.X.scale.env]`?**
They are not checked. @MusabMahmoodh showed they ship as literals and that the #9199 pod check is fooled too. That is the main open follow-up.

**Q: Does anything change for commands other than deploy?**
Only one thing. A string mixing set and unset variables now expands the set ones (`"s/${MISSING}"`) instead of staying fully raw. Otherwise those commands stay silent, as before.

**Q: Could the config be loaded before the project `.env` is applied, making the check stale?**
`_check_deploy_settings_resolve` calls `get_config_for_path` at check time. Whether that function caches an earlier load isn't visible in the diff. The test resets `config_mod._config` elsewhere, which suggests a cache exists. Verify this before trusting the ".env" hint.

**Q: Why plain `ValueError` and not a dedicated exception?**
It matches the existing raises in `interpolate_env_vars` and the schema-report pattern. The PR gives no other reason. A dedicated type would let callers distinguish this failure, as #8773 suggested.

**Q: Does the deploy test prove the real secret collection is checked?**
Not end to end. It passes `secrets` and `namespace` into `ManifestBuilder` by hand, matching what the config would produce. It proves the gate works on what it is given, not that every path feeding it is covered.

**Q: Why keep `_interpolate_recursive`?**
It is now a two-line wrapper over `resolve_env_refs`, so any remaining callers keep working unchanged. The diff doesn't show who still calls it.

**Q: Is the error message helpful?**
It lists every offending setting path and variable in one run, with the `:?` message when there is one. It then suggests exporting the variable, using `.env`, or adding a default. For pod-resolved settings, though, that hint can conflict with the #9199 check (Musab #2).
