## 1. The short version

jac-scale is the plugin that serves Jac apps over HTTP. It keeps each request's graph nodes in a memory object called `ScaleTieredMemory`. At the end of a request it "commits": it saves any changed nodes to MongoDB and Redis.

**Every HTTP request committed twice, and the second commit ran synchronously on the uvicorn event loop.** The first commit, `await Jac.acommit()` in `_finalize_call_response`, already wrote everything and ran in a thread. The second commit, `ctx.mem.commit()` in the request middleware, found nothing to write. It still walked the whole L1 cache and recomputed a hash for every node. Your PR description gives the cost: with 50 nodes in L1 at 200 requests per second, that is about 10,000 hash computations per second. All of them block every other request.

**You added a `_committed` flag to `ScaleTieredMemory`. `acommit()` now returns at once if a full commit already succeeded, and the middleware calls `await ctx.mem.acommit()` instead of the blocking `commit()`.** On the normal path the second pass costs nothing. On error paths and non-walker routes the first commit never happens. The middleware then still commits, and now it does so in a thread.

**Status:** Merged on 2026-05-11. There were no reviews or comments. All test checks passed on head commit `bba5a21`.

| `_committed` flag | New boolean on `ScaleTieredMemory`. It is True after a successful `acommit()`. **This is what the PR adds.** |

## 3. The problem, step by step

### 3.1 The setup

- **Middleware** (`jfast_api.impl.jac`, around line 1147) wraps every request. After `call_next(request)` it commits.
- **Walker handler path** (`server.impl.jac`, `_finalize_call_response`, around line 323 per the description) also commits, with `await Jac.acommit()`.
- Both commits act on the same `ScaleTieredMemory`, because the child context shares `mem` with the parent context.

The middleware commit is the original one. It stays as a safety net for error paths and routes that are not walkers. The handler's `acommit()` was added later to make the commit async, and nobody removed the old commit.

### 3.2 What went wrong (walker request, happy path)

```text
1. Request arrives → middleware creates ctx with ScaleTieredMemory M (L1 empty)
2. Walker runs → loads 50 anchors into M.L1, changes 1 of them (dirty)
3. _finalize_call_response → await Jac.acommit()
     → M.commit() in a thread → sync(): 50 hashes, 1 write to Mongo, Redis updated
     → all 50 anchors now clean (stored hash == current hash)
4. Handler returns to middleware
5. Middleware → ctx.mem.commit()  (sync, ON THE EVENT LOOP)         ← WRONG
     → sync(): iterates 50 anchors, computes 50 hashes, finds 0 dirty, writes nothing
     → event loop blocked for all of this; other requests wait
6. Response sent
```

Step 5 does no useful work, but the CPU cost grows with L1 size and is paid on every request.

### 3.3 Why it mattered

- It is finding **1g** in the scalability audit, issue #5874. The audit says "O(graph-size) CPU work on the event loop, twice per request."
- The event loop is single-threaded. Any time spent there blocks every other in-flight request, including health checks.
- The audit (1c) estimated that synchronous calls already cap throughput at about 28 req/s. This removes one more blocking step.
- Line numbers in the issue (`server.impl.jac:306`, `jfast_api.impl.jac:868`) differ from the ones in your description (`:323`, `:1147`). The code moved on `main` between the audit and the PR. It is the same problem.

## 4. The idea of the fix (one sentence)

> **Commit once, remember it.** `ScaleTieredMemory` records that a full commit succeeded, so any later `acommit()` in the same request returns immediately, and the middleware's commit becomes async.

This keeps both commit points. The base `JacServer` still needs its own commit, and the middleware still covers error paths. The only thing removed is the redundant work. It also moves the remaining safety-net commit off the event loop.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/memory_hierarchy.jac`: add the flag

```diff
 obj ScaleTieredMemory(TieredMemory) {
     has _cache_available: bool = False,
+        _committed: bool = False,       # NEW: True after a successful acommit()
         _persistence_type: PersistenceType = PersistenceType.NONE,
```

**What:** It gives every `ScaleTieredMemory` a `_committed` field that starts as False.

**Why:** It gives the memory object a place to remember that the request's data is already saved.

**Things to notice:**
- The flag is never reset to False. That is safe only because a new `ScaleTieredMemory` is created per request (issue finding 1a confirms this).
- If an instance is ever reused across requests, a later `acommit()` would skip saving.

### 5.2 `jac-scale/jac_scale/impl/memory_hierarchy.main.impl.jac`: guard `acommit()`

```diff
 impl ScaleTieredMemory.acommit(anchor: (Anchor | None) = None) -> None {
     import asyncio;
+    if self._committed {          # NEW: already saved → skip
+        return;
+    }
     await asyncio.to_thread(self.commit);
+    self._committed = True;       # NEW: only reached if commit() did not raise
 }
```

**What:** `acommit()` returns early if `_committed` is True. Otherwise it commits in a thread and sets the flag. If `commit()` raises, the flag line is never reached, so the flag stays False.

**Why:** This makes the second commit free.

**Things to notice:**
- **Only `acommit()` is guarded.** The sync `commit()` is not. Any caller of `commit()` (for example `close()`, per your description) still runs a full `sync()`.
- The `anchor` parameter is ignored. That was already true before this PR: it always committed everything. With the guard, `acommit(some_anchor)` after a first commit also does nothing.
- **Writes after the first `acommit()` are not saved by a later `acommit()`.** They are only saved if something calls `commit()` directly (for example `close()`). This is fine if nothing mutates the graph after `_finalize_call_response`. You cannot tell from the diff whether anything does.
- The check-then-set is not atomic. Two `acommit()` calls running at the same time on one instance could both commit. In this flow they run one after the other, so this does not happen.

### 5.3 `jac-scale/jac_scale/jserver/impl/jfast_api.impl.jac`: middleware uses `acommit()`

```diff
         try {
             response = await call_next(request);
             try {
-                ctx.mem.commit();                 # OLD: blocking, on event loop
+                await ctx.mem.acommit();          # NEW: free if already committed, else threaded
             } except Exception as e {
                 logger.error(
                     f"CRITICAL: Failed to commit request data: {e}. Request will fail.",
```

**What:** The middleware commit becomes async and goes through the guard.

**Why:** On the happy path it returns at once. On other paths it still commits, but no longer blocks the loop.

**Things to notice:**
- The existing `except` that logs `CRITICAL` still catches failures, because `acommit()` passes `commit()`'s exception up.
- This assumes `ctx.mem` is always a `ScaleTieredMemory`, or another class with an async `acommit`. The diff does not show whether the base `TieredMemory` defines `acommit()`.

### 5.4 `docs/docs/community/release_notes/unreleased/jac-scale/5925.bugfix.md`: release note

```diff

```

**What:** A one-line bugfix entry for the next jac-scale release. Commit `347317d` ("fix docs") was a follow-up to it.

## 6. How execution flows after the PR

### 6.1 Walker request, happy path

```text
HTTP request
└─ request_context_middleware
   ├─ create ctx + ScaleTieredMemory M (_committed = False)
   ├─ await call_next(request)
   │  └─ walker route → spawn walker → _finalize_call_response
   │     └─ await Jac.acommit() → M.acommit()
   │        ├─ _committed is False → continue                   ← NEW check
   │        ├─ await to_thread(M.commit) → sync() + Redis update
   │        └─ M._committed = True                              ← NEW
   ├─ await ctx.mem.acommit()                                   ← CHANGED (was sync commit())
   │  └─ _committed is True → return immediately                ← NEW
   └─ cleanup / response
```

This assumes `Jac.acommit()` reaches `M.acommit()`. Your description says it does; the diff does not show that code.

### 6.2 Non-walker route, or error before `_finalize_call_response`

```text
HTTP request
└─ request_context_middleware
   ├─ ctx + M (_committed = False)
   ├─ await call_next(request) → no acommit reached
   ├─ await ctx.mem.acommit()                                   ← CHANGED
   │  ├─ _committed is False → continue
   │  ├─ await to_thread(M.commit)   (off the event loop)       ← NEW: was on the loop
   │  └─ M._committed = True
   └─ response
```

### 6.3 First commit raises (for example MongoDB is down)

```text
_finalize_call_response → M.acommit()
├─ to_thread(M.commit) raises
└─ _committed stays False                                       ← NEW guarantee (tested)
   → whatever _finalize_call_response does with the error (not visible in diff)
   → middleware: await M.acommit() runs the full commit again
      ├─ succeeds → flag set
      └─ fails → logger.error("CRITICAL: ...") as before
```

### 6.4 Base `JacServer` without jac-scale

This path is unchanged. There is no middleware, so `_finalize_call_response`'s `acommit()` is the only commit.

| Scenario | Before | After |
|---|---|---|
| Walker request, success | 2 full `sync()` passes; the 2nd blocks the event loop | 1 pass, in a thread; the 2nd call returns at once |
| Non-walker route | 1 pass, blocking the event loop | 1 pass, in a thread |
| Handler error before finalize | 1 pass, blocking | 1 pass, in a thread |
| First commit fails | Middleware retries, blocking | Middleware retries, in a thread |
| Writes after the first `acommit()` in the same request | Saved by the middleware's `commit()` | **Not saved by `acommit()`.** Only saved if something calls `commit()` (for example `close()`, if it runs) |

Users will not see a functional change on normal paths. The visible effect is lower event-loop blocking under load. The last row is the one behaviour change to be aware of.

## 7. Test changes, explained

| File | Before | After |
|---|---|---|
| `jac-scale/jac_scale/tests/test_memory_hierarchy.jac` | N (full count not visible) | N + 2 |

Both tests build the object with `object.__new__(ScaleTieredMemory)`, which skips `postinit` and so needs no Redis or Mongo. They set `_committed = False` by hand and replace `commit` with `patch.object`. Each `acommit()` call runs on a fresh loop with `asyncio.run`.

### 7.1 `test "acommit is idempotent — _committed flag prevents second sync pass"`

- **Setup:** `commit` is replaced by a function that increments `call_count[0]`.
- **Checks:**
  - After the first `acommit()`, the count is 1 and `_committed is True`.
  - After the second `acommit()`, the count is still 1.
- **Proves:** The guard short-circuits the second call. This is the core of the fix.

### 7.2 `test "acommit leaves _committed False when commit() raises"` (added in `d114585`)

- **Setup:** `commit` raises `RuntimeError("simulated commit failure")`.
- **Checks:**
  - `acommit()` passes the exception up.
  - `_committed is False` afterwards.
- **Proves:** A failed commit does not disable the middleware's retry.

**What the tests do not cover:**
- They do not run the middleware and `_finalize_call_response` together end to end.
- They do not check that the real `sync()` is skipped. They count calls to a patched `commit` instead.

## 11. Questions your senior might ask

**Q: Why not just delete the middleware commit?**
It is the safety net for non-walker routes and for errors before `_finalize_call_response`. On those paths it is the only commit.

**Q: Why not delete the commit in `_finalize_call_response` instead?**
The base `JacServer` (without jac-scale) has no middleware and depends on that call to save data.

**Q: What if the first commit fails?**
`_committed` is only set after `to_thread(self.commit)` returns without raising. A failure leaves it False, so the middleware's `acommit()` tries again. The second test covers this.

**Q: Is the flag ever reset?**
No. That is fine because the middleware creates a new `ScaleTieredMemory` per request. If an instance were reused, later `acommit()` calls would skip saving.

**Q: Could a write after the first commit be lost?**
It would not be saved by `acommit()`. It would only be saved if `commit()` is called directly, for example by `close()`. The diff does not show any code that writes after `_finalize_call_response`, but you cannot rule it out from this PR alone.

**Q: Does moving the middleware commit into a thread cause thread-safety problems?**
By the time the middleware commits, the handler has finished, and L1 belongs to this request only. So no other code touches that dict at the same time. The thread-safety of the Mongo and Redis clients themselves is not shown in this PR.

**Q: Why does `close()` have no guard?**
Your description says scheduled-job contexts each get a fresh `ScaleTieredMemory` and must flush on close. It does not say whether `close()` also runs a full `commit()` on every HTTP request. That is worth checking.

**Q: How do the tests avoid needing MongoDB?**
They create the object with `object.__new__`, which skips the constructor and its backend probes. They also replace `commit` with a mock, so no real `sync()` runs.

**Q: How much does this save?**
It removes one full L1 scan and hash pass per walker request from the event loop. Your description estimates about 10,000 hashes per second at 50 nodes and 200 RPS. The PR includes no benchmark.
