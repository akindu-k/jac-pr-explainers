## 1. The short version

The Jac server sends files to the browser through one function, `file_response` in `jac/jaclang/server/serving/files.jac`. Each response carries an **ETag**, a version tag. The browser sends that tag back on its next reload to ask whether its copy is still current. If the server answers `304 Not Modified`, the browser keeps its cached copy.

**The ETag was built from the file's modified time and size. The build sets every file's modified time to `0` (1 January 1970) on purpose, and a new `index.html` usually has the same size as the old one. So every build of the page got the same tag, for example `W/"0-448"`, and browsers were told "nothing changed" after a redeploy.** Those browsers kept the old `index.html`, which points to the old `client.<hash>.js` bundle, so they kept running the old app. In the issue's real app, every call from the old bundle failed with `409 ENDPOINT_CONTRACT_MISMATCH`.

**You changed the ETag to a BLAKE2b hash of the file's bytes, cached per file path and recomputed when the file's inode, size or nanosecond mtime changes. You also stopped sending `Last-Modified`, and stopped honouring `If-Modified-Since`, when the mtime is 0.** After the fix, build 1 gets `W/"14b6ee50…"` and build 2 gets `W/"26cd99e0…"`. A browser holding the old tag now gets `200` and the new page.

**Status:** Merged on 2026-09-30. Approved by @MusabMahmoodh after both of his points were addressed. All CI checks that ran on head commit `29893ae` passed.

## 3. The problem, step by step

### 3.1 The setup

- **Build:** `det_tar_member` sets mtime 0 on all packed files, so the build is reproducible.
- **Unpack:** A pod runs `tar xzf`; a local run uses `jac run app.jab`. Both leave mtime 0 on disk.
- **Serve:** `file_response` returns `index.html` with `no-cache`.
  - Old ETag: `W/"{int(st_mtime)}-{st_size}"`.
  - `Last-Modified` came from the same mtime.
- **Revalidate:** `_not_modified` returns `304` if the tag matches, or if `mtime <= If-Modified-Since`.

### 3.2 What went wrong: `If-None-Match` (normal reload)

```text
1. Build 1: index.html → loads client.CK5baSzP.js, size 448, mtime 0
2. Server sends ETag W/"0-448", Last-Modified: Thu, 01 Jan 1970
3. Browser caches index.html and client.CK5baSzP.js (immutable, 1 year)
4. Redeploy. Build 2: index.html → loads client.BGSOCOxw.js, still size 448, mtime 0
5. Server now computes ETag W/"0-448"            ← same tag for different content (BUG)
6. Browser reloads: If-None-Match: W/"0-448"
7. _not_modified: tag matches → 304               ← WRONG
8. Browser keeps build-1 HTML → loads client.CK5baSzP.js from cache
9. Old bundle calls the new server → 409 ENDPOINT_CONTRACT_MISMATCH
```

### 3.3 What went wrong: `If-Modified-Since`

```text
1. File mtime = 0 → Last-Modified: Thu, 01 Jan 1970 00:00:00 GMT
2. Browser sends If-Modified-Since: Tue, 01 Sep 2026
3. _not_modified: int(0) <= int(since) → always true
4. 304, whatever the content                      ← WRONG
```

### 3.4 Why it mattered

- Per the issue, after every redeploy anyone with the app already open kept running the previous bundle, and nothing told them.
- In the reporter's app the walker modules moved from `walkers/` to `services/<section>/`. Every walker call from the cached bundle got `409`. Pages rendered empty, and the onboarding redirect never fired.
- A user reported the app as broken, while a fresh browser worked. Only a hard reload or clearing site data fixed it.
- If no endpoint contract changes, the old UI silently runs against the new server instead.
- The bug was confirmed on a live jac-scale deploy (`etag: W/"0-814"`, a `304` for any `If-Modified-Since`).
- The issue also warns that #9098, which proposes routing gateway static handlers through `_etag` and `_not_modified`, would spread the bug to those assets.

## 4. The idea of the fix (one sentence)

> **Tag the content, not the clock.** The ETag is now a hash of the file's bytes, and a fake 1970 mtime is never used as a validator.

This keeps builds reproducible, because mtime 0 stays in the tarball. Every pod behind a load balancer computes the same tag for the same file. And it fixes both the pod path and the `.jab` path. The rejected alternative was `tar xzmf` (unpack with real mtimes). It would give each pod a different tag for the same file and would not fix `.jab` runs.

## 5. Every code change, explained

### 5.1 `jac/jaclang/server/serving/files.jac`: content-based ETag with a cache

```diff
+import hashlib;
 ...
-glob DEFAULT_CACHE_CONTROL: str = 'public, max-age=3600';
+glob DEFAULT_CACHE_CONTROL: str = 'public, max-age=3600',
+     _DIGESTS: dict[str, tuple[tuple[int, int, int], str]] = {};   # NEW: path -> (key, etag)

-def _etag(stat: any) -> str {
-    return f'W/"{int(stat.st_mtime)}-{stat.st_size}"';               # OLD: "0-448" at mtime 0
+def _etag(path: str, stat: os.stat_result) -> str {
+    key = (stat.st_ino, stat.st_size, stat.st_mtime_ns);            # NEW: cache key
+    cached = _DIGESTS.get(path);
+    if cached is not None and cached[0] == key {
+        return cached[1];                                           # NEW: cache hit, no read
+    }
+    digest = hashlib.blake2b(digest_size=16);
+    with open(path, 'rb') as fh {
+        while chunk := fh.read(1024 * 1024) {                       # NEW: 1 MiB chunks
+            digest.update(chunk);
+        }
+    }
+    etag = f'W/"{digest.hexdigest()}"';                             # NEW: still weak
+    _DIGESTS[path] = (key, etag);
+    return etag;
 }
```

**What:**
- `_etag` now takes the path as well as the stat result.
- It returns a cached tag if the file's `(inode, size, mtime_ns)` still matches the cached key.
- Otherwise it hashes the whole file in 1 MiB chunks, stores the result, and returns `W/"<32 hex chars>"`.

**Why:** Two builds of `index.html` with the same size and mtime 0 now get different tags, because their bytes differ.

**Things to notice:**
- **The key is inode, size and `st_mtime_ns` only.** The first commit (`b2c190a`) also used `st_ctime_ns`. @MusabMahmoodh showed that ctime comes from a coarse kernel clock on Ubuntu 24.04, so it can't reliably catch a same-size in-place rewrite. Commit `5deea2e` dropped it.
- **Accepted limitation:** a file rewritten in place, with the same size and the same mtime, while the server is running would keep its old cached tag. The review thread argues no deploy path does this:
  - `.jab` extracts into a fresh `<sha256>` directory and renames it into place.
  - The PVC holds only the tarball, mounted read-only.
  - Each pod unpacks into its own `emptyDir` before the server starts.
- **Why not skip the cache for mtime 0?** @MusabMahmoodh offered this as an option. You declined: every deployed file has mtime 0, so it would rehash whole files on every `304` and Range request.
- **Cost:** the first request for each file in each process reads the whole file once. For large static assets that is one full read per process, then cached.
- **Memory:** `_DIGESTS` has no size limit. It grows with the number of distinct paths served. That is bounded by the app's files, but nothing evicts entries.
- **Weak tag kept:** gzip in `compression.jac` reuses the same tag, and HTTP only allows that for weak tags. The reviewer confirmed this.
- **Other callers:** the signature changed from `_etag(stat)` to `_etag(path, stat)`. The diff does not show whether anything outside this file calls `_etag`. CI passed, which suggests nothing broke, but I can't confirm from the PR alone.

**Things to notice:** `If-None-Match` is still checked first and returns early. The date check only runs when the browser sends no tag. The call site that passes `mtime` into `_not_modified` is not in the diff. Presumably it passes `stat.st_mtime`, but that can't be seen here.

**What:**
- The hash runs inside the `try` block.

**Why:**
- `_etag` now opens the file. If the open fails (the file was removed between `stat` and `open`, or a permission error), the request becomes a clean `404` instead of an unhandled exception.

**Things to notice:** Files with a real mtime behave as before, except that their ETag format also changes to a hash.

## 6. How execution flows after the PR

### 6.1 Serving a file (`file_response`)

```text
GET /  (or SPA fallback path)
└─ file_response(path, cache_control, ...)
   ├─ os.stat(path)
   ├─ _etag(path, stat)                                   ← CHANGED
   │  ├─ key = (st_ino, st_size, st_mtime_ns)             ← NEW
   │  ├─ _DIGESTS[path] has same key? → return cached tag ← NEW
   │  └─ else read file in 1 MiB chunks → blake2b →
   │     W/"<hex>" → store in _DIGESTS                    ← NEW
   ├─ OSError from stat or open → 404 JSON                ← CHANGED (open now covered)
   ├─ headers: Cache-Control, ETag, Accept-Ranges
   ├─ st_mtime > 0 ? add Last-Modified                    ← NEW (was always added)
   ├─ merge extra_headers
   └─ (304 check / body / range handling, not in diff)
```

### 6.2 Revalidation (`_not_modified`)

```text
request arrives with headers
├─ If-None-Match present?
│  └─ '*' or etag in tags → 304, else not-modified = False
└─ If-Modified-Since present AND mtime > 0?               ← CHANGED
   ├─ yes → parse date; mtime <= since → 304
   └─ no  → treat as modified → 200
```

| Scenario (file mtime 0) | Before | After |
|---|---|---|
| Redeploy, same size, browser sends old tag | `304`, stale page | `200`, new page |
| Browser sends current tag | `304` | `304` |
| `If-Modified-Since` any date | `304` | `200` |
| `Last-Modified` header | `Thu, 01 Jan 1970` | omitted |
| ETag format | `W/"0-448"` | `W/"<32 hex>"` |
| Two pods, same file | same tag | same tag |
| File with real mtime, `If-Modified-Since` | date check | date check (unchanged) |

**Behaviour changes users will notice:**
- After upgrading to this version, every cached file's tag changes format. Each browser gets one `200` per file on first revalidation. That is a one-time cost.
- `Last-Modified` disappears for deployed files.
- The first request for each file in each process now reads the full file to hash it.

## 11. Questions your senior might ask

**Q: Why hash content instead of fixing mtimes at unpack with `tar xzmf`?**
Real mtimes would differ per pod, so the same file would get different tags behind a load balancer. It also wouldn't fix `jac run app.jab`. The content hash keeps the tarball deterministic and gives the same tag on every pod.

**Q: Isn't hashing on every request slow?**
It doesn't happen on every request. The hash is cached per path and only recomputed when the inode, size or `st_mtime_ns` changes. The first request per file per process pays one full read.

**Q: What if a file changes in place with the same size and mtime while the server runs?**
The stale cached tag would be served. That is an accepted invariant: `.jab` extracts into a fresh content-addressed directory, and pods unpack into their own `emptyDir` before starting. The test uses `os.replace` because that is how a redeploy actually replaces files.

**Q: Why was ctime removed from the key?**
On Ubuntu 24.04, ctime uses a coarse per-tick clock. An in-place rewrite could land on the same key and return the old digest. That made CI fail, so ctime was not a reliable signal.

**Q: Why keep the tag weak?**
`compression.jac` may gzip the body under the same tag. HTTP only allows different byte encodings under one tag if the tag is weak.

**Q: Why not skip the cache for mtime-0 files to be exact?**
Every deployed file has mtime 0. Skipping the cache would rehash whole files on every `304` and every Range request.

**Q: Does this change behaviour for files with a real mtime?**
`Last-Modified` and `If-Modified-Since` still work for them. Their ETag format changes from `W/"mtime-size"` to a hash, which causes one extra `200` per cached file after upgrading.

**Q: Why move `_etag` inside the `try`?**
It now opens the file. A missing or unreadable file at that point should give the same `404` as a failed `stat`, not an unhandled error.

**Q: Does the gateway have the same bug?**
Per @MusabMahmoodh, the gateway's static handlers send no validators at all, so no. #9098 would route them through `_etag`, and they now get the fixed behaviour.

**Q: How do you know the end-to-end result comes from this change and not other differences between the binaries?**
The released 0.37.21 and the PR binary differ in more than this fix. The unit test ties the result to the change: it fails with `main`'s `files.jac` and passes with this PR's.
