## 1. The short version

`ScaleTieredMemory` is the storage layer jac-scale uses when several pods (copies of the app) run together. It has three cache levels: each pod's own memory (L1), a shared Redis cache (L2), and MongoDB as the source of truth (L3). A **root** node also carries a **topology index**, a packed blob that lets type-filtered traversals like `[root ->[?:TypeA]]` skip edges of the wrong type.

**When a pod added or removed an edge on a root, MongoDB got the new topology index, but Redis kept the old one and no other pod was told to drop its copy.** Issue #7334 shows the effect. Pod B adds a 101st `TypeA` edge, but Pod A still answers `[root ->[?:TypeA]]` with **100**, because Mongo holds 101 entries and Redis holds 100.

This happened on purpose for ordinary nodes. The commit code skips edge-list changes (`EDGE_LIST_DELTA`) when it updates Redis and notifies other pods, which avoids an "invalidation storm" on busy nodes. That is safe because a node's edge list can be rebuilt from the edge records. The topology index cannot be rebuilt that way, so it fell through the gap.

**You added one extra branch to the commit loop. If an edge-list-delta lands on a node that carries a topology index, the code deletes that node from Redis and broadcasts an invalidation, so every pod reloads it from MongoDB.** Ordinary nodes keep the old storm-avoiding behaviour.

## 3. The problem, step by step

### 3.1 The setup

- Two pods, A and B. Each runs a `ScaleTieredMemory` with its own L1, and both share one Redis (L2) and one MongoDB (L3).
- `root` has 100 edges to `TypeA` nodes, and its topology index lists those 100.
- Adding an edge creates an `EDGE_LIST_DELTA` intent for the endpoint node, in this case `root`.
- In `commit`, the L2 loop has two branches:
  - If the intent is a delete, it calls `l2.invalidate` and `publish_invalidation`.
  - Otherwise, if the anchor is **not** in `self_broadcasting`, it calls `l2.put` and `publish_invalidation`.
  - Edge-list-deltas match neither branch, so nothing happens for them.

### 3.2 What went wrong

```text
1. Builder: root -> 100 TypeA, commit.      Mongo root: index=100  Redis root: index=100
2. Pod A: [root ->[?:TypeA]]  -> 100        Pod A L1/L2 warm with index=100
3. Pod B: root ++> TypeA(), commit
   3a. intent for root = EDGE_LIST_DELTA     root.id added to self_broadcasting
   3b. l3.apply(changes)                     Mongo root: index=101   ✓
   3c. L2 loop: not delete, IS in self_broadcasting
       -> no l2.put, no l2.invalidate, no publish_invalidation   ✗ WRONG STEP
                                             Redis root: index=100 (stale)
4. Pod A: [root ->[?:TypeA]]  -> served from stale L1/L2 -> 100   ✗ (should be 101)
5. Stays wrong until root is evicted or reloaded for some other reason.
```

The issue also notes that the whole root anchor in Redis is stale, including its edge list. The index is the worst part because nothing can rebuild it from the edges.

### 3.3 Why it mattered

- It is a correctness bug in multi-pod deployments. Type-filtered traversals from a root return wrong results on every pod that did not make the write.
- Pods running the L1-invalidation listener are not protected either, because no message is ever published for the root.
- Single-pod setups are not affected in the way described, because the pod that wrote the edge has fresh data.

## 4. The idea of the fix (one sentence)

> **Treat edge changes on index-carrying roots like deletes for caching.** When an edge-list-delta hits a node that has a topology index, remove it from Redis and broadcast an invalidation, so every pod reloads it from Mongo.

This closes the one hole that edge anchors cannot fill and leaves storm-avoidance in place for ordinary nodes. The extra cost is about one invalidation per edge add or remove on a root, and roots are few.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/memory/impl/memory_hierarchy.main.impl.jac`: invalidate index-carrying roots on edge-list-delta

```diff
+def _carries_topology_index(anchor: Anchor) -> bool {
+    return isinstance(anchor, NodeAnchor) and anchor.topology_index_data is not None;
+}
+
 impl ScaleTieredMemory._mark_committed(anchor: (Anchor | None)) -> None {
@@ impl ScaleTieredMemory.commit(anchor: (Anchor | None) = None) -> None {
                     cast(RedisBackend, self.l2).publish_invalidation(
                         str(intent.anchor.id), self._l1_id
                     );
+                } elif _carries_topology_index(intent.anchor) {      # NEW: edge-list-delta on a root
+                    self.l2.invalidate(intent.anchor.id);             # NEW: drop the stale Redis copy
+                    cast(RedisBackend, self.l2).publish_invalidation( # NEW: tell other pods
+                        str(intent.anchor.id), self._l1_id
+                    );
                 }
             } except Exception as l2_err {
                 logger.warning(f"L2 cache update failed: {l2_err}");
```

**What:**
- A new module-level helper, `_carries_topology_index`, checks whether an anchor is a node that has topology index data.
- The new `elif` comes after the existing "not in `self_broadcasting`" branch. In practice, the only intents that reach it are edge-list-deltas.
- For those intents, if the anchor carries an index, the code clears it from Redis and publishes an invalidation. This mirrors the delete branch.

**Why:** It fixes step 3c in the timeline. Mongo already had the right data, and now Redis and the other pods' L1 caches stop serving the old copy.

**Things to notice:**
- **Invalidate, not put.** The new branch deletes the Redis copy instead of writing the new one. That copies the delete branch and makes the next reader fetch from Mongo. The PR does not say why `put` was not used.
- **The check is on data, not on "is this root".** Any `NodeAnchor` with a non-`None` `topology_index_data` qualifies. The description treats this as "a root". The diff can't show whether only roots ever carry an index.
- **Possible edge case: a root with no index yet.** If `topology_index_data` were still `None` on the in-memory anchor at commit time (for example, on a root's first edge), the branch would not fire. The diff doesn't show when the index field is set, so this can't be confirmed either way.
- **The whole anchor is invalidated.** That also fixes the stale root edge list the issue mentions, not just the index.
- **Errors are swallowed.** The new calls sit inside the existing `try` block. A Redis failure is logged as a warning and does not fail the commit, which is the same as the existing branches.
- The `cast(RedisBackend, ...)` call assumes L2 is Redis, as the existing branches already do.

## 6. How execution flows after the PR

### 6.1 Committing an edge add or remove

```text
ScaleTieredMemory.commit()
├─ build self_broadcasting = ids of EDGE_LIST_DELTA intents
├─ l3.apply(changes)                         → Mongo updated (unchanged)
└─ if l2: for each intent
   ├─ is_delete()            → l2.invalidate + publish_invalidation   (unchanged)
   ├─ id not in self_broadcasting → l2.put + publish_invalidation     (unchanged)
   ├─ _carries_topology_index(anchor)                                  ← NEW
   │   ├─ l2.invalidate(anchor.id)                                     ← NEW
   │   └─ publish_invalidation(str(id), self._l1_id)                   ← NEW
   └─ otherwise (edge-list-delta on ordinary node) → nothing           (unchanged)
   (any exception → logger.warning, commit continues)
```

### 6.2 Another pod reading the root afterwards

```text
Pod A: [root ->[?:TypeA]]
├─ receives invalidation for root.id (if running L1 listener) → drops L1 copy
├─ L2 miss (Redis copy was invalidated)                        ← NEW effect
└─ load from L3 (Mongo) → index=101 → result 101
```

| Scenario | Before | After |
|---|---|---|
| Edge added or removed on a root that has an index | Mongo updated. Redis stale. No broadcast. | Mongo updated. Redis cleared. Broadcast sent. |
| Edge added or removed on an ordinary node | Mongo updated only | Same (storm-avoidance kept) |
| Normal field write | `l2.put` and broadcast | Same |
| Delete | `l2.invalidate` and broadcast | Same |

The change users would notice: traversals from a root on other pods become correct after an edge write. After each edge write on a root, the next read of that root costs one extra Mongo read.

## 11. Questions your senior might ask

**Q: Why not just remove the `EDGE_LIST_DELTA` exclusion entirely?**
A: It prevents invalidation storms on hot nodes with many concurrent edge writes. Ordinary nodes can rebuild their edge list from edge anchors, which are invalidated, so only index-carrying nodes needed an exception.

**Q: Why `l2.invalidate` and not `l2.put` with the fresh anchor?**
A: You mirrored the delete branch, which also invalidates, so the next reader loads the authoritative copy from Mongo. The PR does not give any other reason.

**Q: How much extra cost does this add?**
A: About one Redis delete and one pub/sub message per edge add or remove on a root, plus one Mongo read on the next access. Roots are per-user or per-session, so there are few of them.

**Q: Does the check only match roots?**
A: It matches any `NodeAnchor` with non-`None` `topology_index_data`. The PR assumes that means roots. The diff can't show whether other nodes ever carry an index.

**Q: What if the Redis call fails?**
A: The code sits in the existing `try` block, so the failure is logged as "L2 cache update failed" and the commit still succeeds. In that case Redis could stay stale, which is the same risk as the other branches.

**Q: Do pods without the L1-invalidation listener get fixed too?**
A: Their reads through L2 now miss and go to Mongo. Any copy they hold in L1 would only drop if they listen for invalidations. The diff doesn't show how L1 behaves without the listener.

**Q: Where's the test?**
A: It isn't in the PR. Verification was manual with testcontainers, including a negative control, and is shown only in screenshots.

**Q: What about the perf idea in the issue (caching the decoded index)?**
A: It isn't in this PR. The issue lists it as optional and separate.
