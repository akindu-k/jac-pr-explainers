## 1. The short version

Jac can compile a function to native machine code. When the native compiler meets something it can't handle, it should give up on that function ("demote" it) so Python runs it instead. Python always gets the answer right.

**Before this PR, `sorted(xs)` with `xs: list[any]` compiled natively and silently returned the list in its original order.** The inner sorting step (`emit_sort`) correctly gave up, because it has no way to compare `any` values. The outer `sorted()` step (`emit_sorted`) only passed that failure on when keyword arguments such as `reverse=True` or `key=` were present. For a plain `sorted(items)` on `[3, 1, 2]`, the native code returned `[3, 1, 2]`, so `ordered[0]` was `3` instead of `1`.

**You removed the keyword-argument condition, so any failure in `emit_sort` now makes `sorted()` fail too.** The compiler reports `E5092 builtin call 'sorted'` and the function runs in Python, which returns `1`. `xs.sort()` already behaved this way. You added both cases to an existing refusal test.

**Status:** Open and waiting for human review. All CI checks on head `32cb955` passed, and a few were skipped. The only comment so far is an automated Greptile summary.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The language in this repo. A function looks like `def first_after_sort -> int { ... }`. |
| `any` | A type that can hold any value: a number, a string, an object. `items: list[any] = [3, 1, 2]` is a list whose element type the compiler doesn't pin down. |
| Native backend | The part of the compiler that turns Jac into fast machine code instead of Python bytecode. It lives under `jac/jaclang/compiler/backends/native/`. |
| Lowering | Translating a high-level construct (like a `sorted()` call) into lower-level native instructions (IR). "Lowers successfully" means the native compiler produced code for it. |
| IR | Intermediate representation. The instruction list the native backend builds before it makes machine code. |
| Demote / refuse | When lowering a function fails, the native compiler drops that function and Python runs it instead. This is slower, but correct. |
| E5092 | The diagnostic code the native compiler emits when it refuses a call. The test looks for `[E5092]`. |
| `impl` file (`*.impl.jac`) | Jac keeps a declaration in one place and its body in an `impl Class.method(...) { ... }` block, often in a separate file. `primitives_native.impl.jac` holds the bodies of many native emitters. |
| Emitter | A class that writes IR for one kind of thing. Its methods are named `emit_...`. |
| `NativeListEmitter` (`_le` in the diff) | Emits IR for list operations, including sorting. |
| `emit_sort` | `NativeListEmitter` method that emits an in-place sort. It returns `None` when it can't, for example when the element kind is `jacval`. |
| Element kind / `jacval` | How the native backend stores list elements. `jacval` means "boxed": each element is wrapped as a generic Jac value. The backend has no comparison function for boxed values, so it can't sort them. |
| `NativeBuiltinEmitter` | Emits IR for built-in functions such as `sorted()` and `len()`. |
| `emit_sorted` | `NativeBuiltinEmitter` method that lowers `sorted(...)`. It returns the list value on success and `None` to refuse. **This is where the bug is.** |
| `ctx` / `_ctx2` | Context objects passed to emitters. They describe the call being lowered (`arg_nodes`, `call_node`, `call_kwargs`). |
| `call_kwargs` | The keyword arguments of the call being lowered, for example `{reverse: True}`. An empty dict is "falsy" (counts as false in a condition). |
| `ctx?.call_kwargs` | Null-safe access. If `ctx` is null, the result is null instead of a crash. |
| Fixture | A small Jac file the test compiles. Here it is `any_receiver_method_refusal.jac`. |
| Seam | In this test, the per-function text the test inspects for refusal messages. `seam_for(seams, fn)` gets the one for function `fn`. The helper bodies are not in the diff. |
| `passes-native` | The CI job that runs `tests/compiler/backends/native`. It is where the changed test runs. |
| Release note | A small Markdown file under `release_notes/unreleased/` that is gathered into the changelog. |
| Greptile | An AI review bot that posts a summary comment on PRs. |

## 3. The problem, step by step

### 3.1 The setup

- `emit_sorted` lowers `sorted(items)`. Its plan is to sort the list with `NativeListEmitter.emit_sort` and return the list.
- `emit_sort` gives up (returns `None`) when elements are boxed `jacval`. That is the case for `list[any]`.
- If `emit_sorted` returns `None`, the call is refused with E5092 and the function demotes to Python.

### 3.2 What went wrong

Old code:

```jac
if _le.emit_sort(_ctx2, items, []) is None and (ctx?.call_kwargs or {}) {
    return None;
}
return items;
```

Timeline for `sorted(items)` with `items: list[any] = [3, 1, 2]` and no keyword arguments:

```text
1. Native compiler lowers first_after_sort.
2. Reaches sorted(items) → calls NativeBuiltinEmitter.emit_sorted.
3. emit_sorted calls _le.emit_sort(_ctx2, items, []).
4. Element kind is jacval → emit_sort returns None (no comparator). Correct so far.
5. Condition part 1: (None is None) → true.
6. Condition part 2: (ctx?.call_kwargs or {}) → {} → falsy.      ← WRONG STEP
7. true and falsy → false → the "return None" refusal is skipped.
8. emit_sorted returns items (the original, unsorted list value).
9. Function lowers "successfully". No E5092, no warning.
10. At run time: ordered = [3, 1, 2]; ordered[0] = 3.  Python gives 1.
```

With a keyword argument, for example `sorted(items, reverse=True)`, step 6 is truthy. The call refused correctly and the function demoted.

`xs.sort()` on the same list was already refused (`Native lowering failed for method 'list[Any].sort'`), according to your fork CI run. So only the `sorted()` path was broken.

### 3.3 Why it mattered

- It was a silent miscompile: wrong data, no diagnostic. The issue calls it "a silent miscompile class."
- It caused a real failure on #10544. `json.dumps(..., sort_keys=True)` in `na_stdlib` sorted keys in bytecode but not in native code. A native kernel therefore produced interface digests the host could not reproduce, and the sealed-kernel kit smoke test failed with "the kernel returned a native interface that does not decode" for every lowered unit.
- The issue notes this hits any list whose element kind is boxed, not just `list[any]`.

## 4. The idea of the fix (one sentence)

> **If the sort can't be lowered, `sorted()` can't be either.** `emit_sorted` now refuses whenever `emit_sort` returns `None`, whether or not keyword arguments were passed.

The issue offered two fixes: implement a boxed-value comparison sort, or refuse so the call demotes. Refusing is a one-line change and can't produce wrong data. It also matches how `xs.sort()` already behaves. A boxed comparator would need to copy Python's comparison rules (mixed types, `TypeError` on incomparable values), which is a much bigger job.

## 5. Every code change, explained

### 5.1 `jac/jaclang/compiler/backends/native/impl/primitives_native.impl.jac`: refuse `sorted()` whenever the sort fails

```diff
@@ -5569,7 +5569,7 @@ impl NativeBuiltinEmitter.emit_sorted(
         arg_nodes=ctx.arg_nodes,
         call_node=ctx.call_node
     );
-    if _le.emit_sort(_ctx2, items, []) is None and (ctx?.call_kwargs or {}) {   # OLD: refuse only if kwargs were passed
+    if _le.emit_sort(_ctx2, items, []) is None {                                 # NEW: refuse on any sort failure
         return None;
     }
     return items;
```

**What:** `emit_sorted` returns `None` (refuse) any time `emit_sort` returns `None`. Otherwise it returns the sorted list value as before.

**Why:** This removes step 6 of the timeline. The plain `sorted(xs)` case can no longer skip the refusal.

**Things to notice:**
- The change is wider than `list[any]`. Any reason `emit_sort` returns `None` now demotes `sorted()`. Before, every such failure without kwargs gave unsorted output. That is the intended effect, and it also covers the issue's "`list[SomeType]` whose elem kind is boxed" case. The new test only covers `list[any]`.
- `emit_sort` is called with `[]` as its third argument. The diff doesn't show what that argument is, or how `reverse=`/`key=` are handled in the lines above 5569. You can't tell from this diff why the old `call_kwargs` check existed.
- The diff doesn't show whether `emit_sort` leaves partly emitted IR behind when it returns `None`. Since the whole function demotes, that IR should be thrown away, but this file doesn't show it.
- The fix depends on `emit_sort` returning non-`None` on success. If it returned `None` on success, every `sorted()` would now demote. The issue's description of `emit_sort` and the green `passes-native` job both suggest that is not the case.

## 6. How execution flows after the PR

### 6.1 `sorted(xs)` over `list[any]`, no kwargs

```text
Native compile of the function
├─ lower sorted(items) → NativeBuiltinEmitter.emit_sorted
│  ├─ build _ctx2 from ctx (arg_nodes, call_node)
│  ├─ _le.emit_sort(_ctx2, items, []) → None   (jacval elements, no comparator)
│  └─ condition is now just "is None" → return None        ← CHANGED
├─ call refused: [E5092] builtin call 'sorted'             ← NEW for this case
└─ function demotes → runs in Python → sorted([3,1,2])[0] = 1
```

### 6.2 `sorted(xs)` over a list with a sortable element kind (for example `list[int]`)

```text
emit_sorted
├─ emit_sort(...) → non-None (sort IR emitted)
└─ return items → lowered natively, result sorted   (unchanged)
```

### 6.3 `sorted(xs, reverse=True)` over `list[any]`

```text
emit_sorted
├─ emit_sort(...) → None
└─ return None → E5092 → demote   (unchanged; it already refused because kwargs were truthy)
```

### 6.4 `xs.sort()` over `list[any]`

```text
list method lowering
└─ refused: Native lowering failed for method 'list[Any].sort' → E5092 → demote   (unchanged; now covered by a test)
```

| Scenario | Before | After |
|---|---|---|
| `sorted(list[any])`, no kwargs | Lowered natively, returned unsorted (`3`) | E5092, demotes, correct (`1`) |
| `sorted(list[any], reverse=True)` / `key=` | E5092, demotes | Same |
| `sorted(list[int])` | Native, sorted | Same |
| `list[any].sort()` | E5092, demotes | Same |
| Module forced to be fully native that uses `sorted(list[any])` | Builds, wrong result at run time | Build-time E5092 error (per the PR description; the mechanism is not in the diff) |

**Behaviour change users will notice:** affected functions now run in Python. They give correct results but run slower. Strict all-native builds may now fail to build where before they "worked."

### 7.2 `jac/tests/compiler/backends/native/test_native_any_receiver_method.jac`

- The module docstring is widened from "a method call on an `any` receiver" to "a call over `any` values."
- The test is renamed from "mutating and reading methods on an any receiver demote their callable" to "calls over any values demote their callable" (commit `32cb955`). The old three-line comment is replaced by one line (commit `d6a9bf0`).
- The loop changes from a list of names to `(fn, refusal)` pairs. Each pair has its own expected text:

| Row | Expected refusal text | Proves |
|---|---|---|
| `any_field_append` | `on an `any` receiver` | Existing: append on an `any` field is refused |
| `any_field_bytearray_append` | `on an `any` receiver` | Existing: bytearray append is refused |
| `any_param_count` | `on an `any` receiver` | Existing: `.count` on an `any` parameter is refused |

Each row asserts that `"[E5092]"` and the row's refusal text both appear in that function's seam.

**Why extend instead of adding a test:** the new cases are the same shape as the existing ones (a call over `any` values must refuse with E5092). One table keeps them together, and the per-row refusal string lets different messages share one loop.

**What it does not check:** that the demoted function returns `1` at run time. Your pre-fix fork run used a temporary probe (`PROBE any_list_sorted first element = 3`) that is not part of this PR.

## 11. Questions your senior might ask

**Q: Why was the `call_kwargs` check there in the first place?**
The diff doesn't show the history or the code above line 5569. From what is visible, the check only made plain `sorted(xs)` skip the refusal, and that is exactly the bug. Be ready to say you couldn't find a case that needed it.

**Q: Does this slow down any code that was correct before?**
Only if `emit_sort` returned `None` for a case whose unsorted output happened to be acceptable. Every such case was returning unsorted data, so the slowdown only hits code that was already wrong. `sorted(list[int])` and other sortable lists still lower natively.

**Q: What if `emit_sort` returns `None` on success?**
Then every native `sorted()` would now demote. The issue describes `None` as the failure signal. The old kwargs branch already relied on it, and the `passes-native` suite still passes.

**Q: Does this cover lists other than `list[any]`?**
Yes. The check is on `emit_sort`'s result, not the declared type, so any boxed element kind now refuses. Only `list[any]` is tested.

**Q: Why not implement sorting for boxed values instead?**
It would have to match Python's comparison rules, including errors on incomparable types. Demoting is correct now and much smaller. That work could be a follow-up.

**Q: How do you know the result is now correct, not just refused?**
The test proves the refusal (E5092). Correctness then follows from Python running the function. Your fork run showed the native value was `3` against Python's `1`. No automated run-time check is added.

**Q: Will this fix #10544's `json.dumps(sort_keys=True)` failure?**
The issue says that failure came from this bug, so the native kernel should now demote that path and match the host. This PR doesn't test #10544 directly.

**Q: Could `emit_sort` leave partial IR behind when it bails?**
The diff doesn't show that. The function demotes as a whole after the refusal, which should discard its native IR, but that logic isn't in this diff.
