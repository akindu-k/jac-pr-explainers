## 1. The short version

Jac stores graph data (nodes, edges, walkers) in three memory layers. **L1** is a plain in-process memory cache. **L2** is a shared cache, Redis in jac-scale. **L3** is the database, MongoDB here. When Jac code touches a node, the runtime looks in L1 first, then L2, then L3. Changes are written back down when the context commits.

**Before this PR, a jac-scale web server used one global execution context for all HTTP requests, so its L1 cache was shared by every request and was never cleared.** Issue #4616 describes the effect. If you run two server instances and instance A runs `root ++> some_node();`, instance B keeps serving its old cached copy of `root` from its own L1. L1 also grew until it held most of the database.

**You added a FastAPI middleware that gives every HTTP request its own fresh `ExecutionContext`, and therefore its own empty L1. The context is stored in a Python `ContextVar`. It is committed when the request finishes and then closed.** `JacRuntime.get_context()` now returns that per-request context when one is set. Otherwise it falls back to the old global one, so `jac run`, tests and scripts behave as before.

The issue's third problem, lost updates when two requests write the same node at the same time, is **not** fixed here. Your concurrent-write tests failed and were removed (commits 01b9d99, d459dfb, 21e8ce6).

**Status:** Merged on 2026-03-19. @Thamirawaran requested changes, you addressed them in 21e8ce6, and @Thamirawaran then approved. All CI test checks passed.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Anchor | The stored record behind a Jac node, edge or walker: its id, its data and its edge list. This is what the caches hold. |
| L1 / L2 / L3 | The three memory layers. L1 is an in-process dict (fastest, private to one server process). L2 is Redis (shared by instances). L3 is MongoDB (the source of truth). |
| `ExecutionContext` | The runtime object that holds the current user root, the system root and `mem`, the memory stack that owns L1. One context means one L1. |
| `ctx.mem.commit()` | Writes changed anchors from memory down to L2/L3. |
| `ctx.close()` | Shuts the context down. The new docstring says it "commits changes". What `close()` does exactly is not in the diff. |
| `JacRuntime.exec_ctx` | The single global context, created lazily the first time `get_context()` is called. Before this PR, the web server used it too. **This is where the bug is.** |
| `JacBasics.get_context()` | The function all runtime code calls to get "the current context". You changed it to check the request context first. |
| `ContextVar` | A Python stdlib variable whose value is separate for each asyncio task or thread context. Example: `v = ContextVar('x', default=None); v.set(1)` inside request A is not seen by request B. |
| `_request_context` | The new module-level `ContextVar` in `runtime.jac`, with default `None`. **This is what the PR adds.** |
| `set_request_context` / `clear_request_context` | New static methods on `JacRuntime`. They put a context into `_request_context`, or close it and reset the variable to `None`. |
| User root vs system root | Each logged-in user has their own root node. Without one, the context uses the system root. `ctx.set_user_root(id)` switches to the user's root. |
| FastAPI middleware | A function that wraps every HTTP request: `async def mw(request, call_next)`. Code before `call_next` runs before the endpoint, and code after it runs after the endpoint. Registered with `app.middleware('http')(mw)`. |
| `JFastApiServer` | jac-scale's FastAPI wrapper. Its `init` creates the FastAPI `app`, and it is where you register the middleware. |
| `request.state` | A per-request scratch object in Starlette/FastAPI where earlier code can store values, such as `user_root_id`. |
| Lost update (race condition) | Two requests read the same node, each changes it, and each writes the whole node back. The last write wins and the other change disappears. Issue #4616 describes this for `root ++> some_node()`. |
| Testcontainers (`MongoDbContainer`) | A library that starts a real MongoDB in Docker for a test. |

## 3. The problem, step by step

### 3.1 The setup

- **jaclang runtime** (`jac0core/runtime.jac`): `get_context()` lazily creates one global `ExecutionContext` in `JacRuntime.exec_ctx` and returns it forever.
- **jac-scale server** (`JFastApiServer`): serves walkers over HTTP. Before the PR it added no per-request context handling of its own, so it used that global context. The diff does not show the rest of the request handling code, so I can't confirm whether endpoints created contexts elsewhere. The issue text says L1 was not invalidated per request.
- **Storage**: L1 lives inside the process's context. L2 (Redis) and L3 (MongoDB) are shared by all instances.

### 3.2 What went wrong: stale data across instances

```text
1. Instance A and instance B both serve a request that reads root.
   A.L1[root] = {edges: []}      B.L1[root] = {edges: []}
2. A request on A runs `root ++> some_node();`
   A.L1[root] = {edges: [n1]}  → committed → L2/L3[root] = {edges: [n1]}
3. A new request hits B and reads root.
   B checks L1 first and finds the old copy: {edges: []}      ← WRONG: stale, L2/L3 never consulted
4. B's request may even modify root and commit {edges: [n2]},
   overwriting n1 in L2/L3.                                    ← WRONG: data loss
```

### 3.3 What went wrong: unbounded memory

```text
1. Request 1 touches anchors a1..a100   → global L1 size 100
2. Request 2 touches anchors a101..a200 → global L1 size 200 (nothing evicted)
3. ... after enough traffic, L1 ≈ every anchor ever read ≈ size of the DB
4. Server RAM fills up → slowdown / hang / OOM crash          ← WRONG
```

### 3.4 Why it mattered

Issue #4616 (filed for Pocketnest, jaclang 0.10.0 / jac-scale 0.1.7) says plainly: "As of this version scaling will not work." Running more than one replica or worker gives inconsistent data. The issue also says server RAM and Redis would need to be as large as the database, and that Redis evicting data under pressure makes another bug (#4552) more likely. This PR addresses the L1 side. The L2/Redis growth and the lost-update race described in the issue are not changed by this diff.

## 4. The idea of the fix (one sentence)

> **One request, one context, one L1.** Each HTTP request gets a fresh `ExecutionContext` stored in a `ContextVar`, which is committed and closed when the request ends.

A `ContextVar` lets you change which context `get_context()` returns per request without touching any of its callers. Code outside a web server never sets it, so the global fallback keeps CLI and tests unchanged.

**What:** You add one module-level `ContextVar` named `request_context` that defaults to `None`. You also declare two new static methods on `JacRuntime`. In Jac, declarations live in `.jac` files and bodies live in `impl` files.

**Why:** The runtime needs a place to hold "this request's context" that concurrent requests cannot see.

**Things to notice:**
- The variable is created once at module level, which is the correct way to use `ContextVar`. Creating one per call would break isolation.
- `set_context` stays. It now only affects the global fallback, as its new docstring says.

### 5.2 `jac/jaclang/jac0core/impl/runtime.impl.jac`: resolve and manage the request context

```diff
 impl JacBasics.get_context -> ExecutionContext {
+    # Try request-scoped context first (for web servers)
+    ctx = _request_context.get();
+    if ctx is not None {
+        return ctx;                                   # NEW: request context wins
+    }
+
+    # Fallback to global context (CLI, tests, non-web environments)
     if (JacRuntime.exec_ctx is None) {
         JacRuntime.exec_ctx = JacRuntimeInterface.create_j_context(user_root=None);
     }
 ...
+impl JacRuntime.set_request_context(context: ExecutionContext) -> None {
+    _request_context.set(context);
+}
+
+impl JacRuntime.clear_request_context -> None {
+    ctx = _request_context.get();
+    if ctx is not None {
+        ctx.close();                                  # NEW: release the context (and its L1)
+        _request_context.set(None);
+    }
+}
```

**What:** `get_context()` returns the request context if one is set. Otherwise it does exactly what it did before. `clear_request_context()` closes the current request context and resets the variable.

**Why:** Every piece of runtime code that asks for "the current context" now gets the request's private context, and so the request's private L1, without any change to its own code.

**Things to notice:**
- While a request context is set, a call to `JacRuntime.set_context(...)` changes the global `exec_ctx`, but `get_context()` will not return it. If any jac-scale code calls `set_context` during a request, that call now has no effect. I can't tell from the diff whether such calls exist.
- `clear_request_context` uses `set(None)` rather than the token returned by `set()` and `ContextVar.reset(token)`. This works because each request runs in its own copied context. The token form would be the stricter idiom.
- The docstring says "and commit changes", but this function only calls `close()`. Whether `close()` commits depends on `ExecutionContext.close`, which is not in the diff.

### 5.3 `jac-scale/jac_scale/jserver/impl/jfast_api.impl.jac`: the per-request middleware

```diff
 impl JFastApiServer.init(...) {
     self.app = app or FastAPI();
     ...
+    async def request_context_middleware(request: Request, call_next: Callable) {
+        ctx = JacRuntimeInterface.create_j_context(user_root=None);   # fresh context, empty L1
+        JacRuntime.set_request_context(ctx);
+
+        user_id = getattr(request.state, 'user_root_id', None)
+            if request?.state else None;
+        if user_id {
+            try { ctx.set_user_root(user_id); }
+            except ValueError { logger.warning(f"Invalid user_root_id: {user_id}, using system root"); }
+        }
+
+        try {
+            response = await call_next(request);                     # endpoint runs here
+            try { ctx.mem.commit(); }                                # persist to L2/L3
+            except Exception as e {
+                logger.error(f"CRITICAL: Failed to commit request data: {e}. Request will fail.", exc_info=True);
+                raise;
+            }
+            return response;
+        } finally {
+            try { JacRuntime.clear_request_context(); }              # close + reset, always
+            except Exception as e { logger.warning(f"Failed to clear request context: {e}", exc_info=True); }
+        }
+    }
+    self.app.middleware('http')(request_context_middleware);
 }
```

**What:** For every HTTP request, the middleware:
1. Creates a new context.
2. Stores it in the `ContextVar`.
3. Switches to the user's root if `request.state.user_root_id` is set.
4. Runs the endpoint.
5. Commits.
6. Always closes and clears the context.

**Why:** This is where "one request, one L1" actually happens. When the request ends, the context and its L1 become unreachable and can be garbage collected, so L1 no longer grows across requests. The next request starts with an empty L1 and reads current data from L2/L3.

**Things to notice:**
- **Where `user_root_id` comes from.** The middleware runs before the endpoint. `request.state.user_root_id` will only be set if some code earlier in the stack set it. In Starlette, middleware added later wraps middleware added earlier. The diff doesn't show what sets this value. If nothing does, this branch never runs, and the endpoint's own auth code must set the user root on `get_context()`. Be ready to explain which is true.
- **Commit timing.** The commit runs only when `call_next` returns normally. If the endpoint raises, the code skips the explicit commit, but `finally` still calls `close()`. Whether partial writes get persisted then depends on what `close()` does.
- **Commit happens even for error responses** (for example a returned 4xx/5xx `Response`), because those still come back through `call_next` normally.
- **Commit failure is fatal.** It is logged and re-raised, so the client gets an error instead of a false "success".
- **Streaming responses.** With `BaseHTTPMiddleware`-style middleware, the response body can be streamed after `call_next` returns. Any code that runs while streaming would run after the context is cleared and would fall back to the global context. Nothing in the diff shows whether jac-scale streams walker output.
- **Why the `ContextVar` reaches the endpoint.** Starlette runs the downstream app in a child task, and FastAPI runs sync endpoints in a thread pool. Both copy the current `contextvars` context, so a value set before `call_next` is visible inside the endpoint. This is standard Python/Starlette behaviour, not something the diff shows.
- **Not in the code, despite the PR description.** The description promises "comprehensive logging … with L1 size metrics". The code has no lifecycle or L1-size logging, only the three warning/error logs above.

## 6. How execution flows after the PR

### 6.1 An HTTP request to a jac-scale walker

```text
HTTP POST /walker/CreateTask
├─ request_context_middleware                               ← NEW
│  ├─ create_j_context(user_root=None)  → ctx (empty L1)
│  ├─ JacRuntime.set_request_context(ctx)  → _request_context = ctx
│  ├─ if request.state.user_root_id → ctx.set_user_root(id)
│  │    └─ ValueError → log warning, keep system root
│  ├─ await call_next(request)
│  │  └─ endpoint / walker runs
│  │     └─ JacRuntime.get_context()                        ← CHANGED
│  │        └─ _request_context.get() is ctx → return ctx
│  │           └─ reads: L1 (empty at start) → L2 → L3
│  ├─ ctx.mem.commit()  → write changes to L2/L3            ← NEW
│  │    └─ exception → log CRITICAL, re-raise → request fails
│  ├─ return response
│  └─ finally: JacRuntime.clear_request_context()           ← NEW
│       ├─ ctx.close()
│       └─ _request_context = None  (L1 discarded)
└─ client gets response
```

### 6.2 `get_context()` outside a web server (`jac run`, tests, scripts)

```text
JacRuntime.get_context()
├─ _request_context.get() → None (never set)                ← NEW check
└─ fallback: create JacRuntime.exec_ctx once, return it     (unchanged)
```

### 6.3 Two requests at the same time on one instance

```text
Request A (task A)                       Request B (task B)
├─ _request_context = ctxA               ├─ _request_context = ctxB
├─ get_context() → ctxA, L1_A            ├─ get_context() → ctxB, L1_B
├─ load root → copy A                    ├─ load root → copy B
├─ root ++> n1                           ├─ root ++> n2
└─ commit root {edges:[n1]}              └─ commit root {edges:[n2]}   ← last write wins
```

| Scenario | Before | After |
|---|---|---|
| Instance B reads a node that instance A just changed | B could return its stale L1 copy | B starts with an empty L1 and reads from L2/L3 |
| Long-running server, many requests | L1 grows without limit | L1 lives only for one request |
| `jac run` / tests / scripts | Global context | Global context (unchanged) |
| Code calls `JacRuntime.set_context()` during a request | Took effect | Changes the global context only; `get_context()` still returns the request context |
| Two concurrent writes to the same node, same instance | Likely shared one in-memory object (shared L1) | Each has its own copy, so last commit wins and one write can be lost |
| Two concurrent writes, different instances | Lost update / stale data | Lost update still possible (not fixed) |
| Commit fails at end of request | (no per-request commit in this code path) | Logged as CRITICAL and the request errors |

**Behaviour change to call out:** per-request isolation means every request reads from L2/L3 at the start, which adds some read cost. The concurrent-write race from the issue now also applies inside a single instance. Your commit 01b9d99 ("commented out failing test. need to handle concurrent writes separately") points to exactly this. The concurrent tests were then removed.

## 11. Questions your senior might ask

**Q: Why a `ContextVar` and not a dict keyed by request id or a thread-local?**
A `ContextVar` is per asyncio task and is copied into thread-pool calls. FastAPI uses both, so it isolates async and sync endpoints alike. A thread-local would break under async, because many requests share one thread. A dict would need its own cleanup and locking.

**Q: Does the context set in middleware actually reach the endpoint?**
Yes, under standard Starlette/FastAPI behaviour. The downstream app runs in a child task, and sync endpoints run via the thread pool. Both copy the current context. The `test-scale` run passing, with writes persisted across requests, supports this.

**Q: Where does `request.state.user_root_id` come from?**
The diff doesn't show it. The middleware runs before the endpoint. Unless an outer middleware sets it, the value is `None`, and user-root handling must happen inside the endpoint on the same `get_context()` object. Check this before the meeting.

**Q: What happens if the walker raises an exception?**
The explicit `ctx.mem.commit()` is skipped. The `finally` block still runs `clear_request_context()` → `ctx.close()`. Whether `close()` writes anything depends on its implementation, which is not in this PR.

**Q: Does this fix the race condition in #4616?**
No. Each request still loads a full copy of a node and writes the whole anchor back, so the last commit wins. The concurrent-write tests failed (commit 01b9d99) and were removed. Within one instance this may now happen more often, because requests no longer share one in-memory object.

**Q: Is there a performance cost?**
Likely yes. Every request starts with an empty L1, so it reads from L2 (Redis) or L3 (MongoDB) instead of process memory. That is the intended trade: correctness and bounded memory over cache hits. The PR includes no benchmarks.

**Q: Is anything not backward compatible?**
CLI, tests and scripts are unchanged because the `ContextVar` is never set there. Inside a web request, `JacRuntime.set_context()` no longer changes what `get_context()` returns. Any jac-scale code relying on that would behave differently.

**Q: What about L2/Redis memory growth mentioned in the issue?**
Not addressed. This PR only bounds L1.

**Q: Why commit in the middleware and also call `close()`?**
The middleware commit makes a failed write fail the request loudly. `close()` releases the context. If `close()` also commits, the second commit should have little or nothing left to write, but the diff doesn't show that.

**Q: How would you test isolation properly?**
Run two server instances against the same Mongo and Redis. Write through instance A, read through instance B, and assert B sees the new data. Add the concurrent-write tests back once a locking or merge strategy exists for the race.
