## 1. The short version

jac-scale deploys a Jac app to Kubernetes. When Redis is enabled, it also runs one Redis pod that acts as a cache (the "L2" layer) in front of MongoDB. Before this PR, that Redis pod started with only two flags (`--save '' --appendonly no`). It had no memory limit inside Redis, no eviction rule, and no key expiry.

**Redis kept every anchor it was given and never dropped anything, so the cache grew toward a full copy of MongoDB (issue #4665) and could be killed by the pod's 256Mi memory limit.**

**You now generate a `redis.conf` from a template using new `jac.toml` settings (memory limit, eviction policy, samples, keyspace notifications), ship it as a ConfigMap, and restart Redis only when that config's hash changes. You also make `RedisBackend.put` write keys with `SETEX` when `redis_default_ttl > 0`, so cached anchors expire.** For example, `redis_default_ttl = 3600` makes every newly cached anchor disappear from Redis one hour after it was written. With the defaults, Redis caps itself at `200mb` and evicts the least-recently-used keys.

The PR also adds liveness and readiness probes, renames labels (`managed` → `managed-by`), and adds a release-note line. No tests were added.

**Status:** Merged on 2026-03-03. @juzailmlwork approved it, and all 10 CI checks on `bb22f0c` passed.

## 3. The problem, step by step

### 3.1 The setup

- `KubernetesRedisProvider.deploy()` builds Python dicts for a Redis Deployment and a Service.
- `KubernetesTarget` sends them to the cluster. Before the PR, it created the Deployment only if missing and never updated it.
- In the app, `RedisBackend.put` stores each anchor in Redis with plain `SET`.
- The Redis container had `resources.limits.memory: 256Mi` but only `--save '' --appendonly no`. There was no `maxmemory`.

### 3.2 What went wrong

#### 3.2a Memory grows without limit

```text
1. App starts. Redis pod is up, used memory ≈ few MB, maxmemory = 0 (unlimited)
2. App writes anchors → RedisBackend.put → SET key value (no expiry)
3. More traffic → Redis memory 50MB → 150MB → 240MB
4. Redis has no maxmemory, so it never evicts anything             ← WRONG
5. Container passes 256Mi limit → Kubernetes OOM-kills the pod     ← WRONG
6. Pod restarts empty (no persistence) → cache is cold, then grows again
```

#### 3.2b Keys never expire

```text
1. Anchor A is written to Redis with SET (no TTL)
2. Anchor A is never read again
3. A stays in Redis forever                                         ← WRONG
4. Over time Redis holds "almost all the data as MongoDB" (issue #4665)
```

### 3.3 Why it mattered

- Issue #4665 says Redis "has almost all the data as mongodb", while in production "we only keep most important data alive". A cache that mirrors the database wastes memory.
- Your description names the risk of OOM kills in production. It also points out that there was no way to tune Redis from `jac.toml`.
- @juzailmlwork asked that TTL live in the memory-hierarchy Redis code itself, because that is where anchors are written.

---

## 4. The idea of the fix (one sentence)

> **Generate Redis's config from `jac.toml` and set TTLs at write time.** You render a `redis.conf` (memory cap plus eviction policy) into a ConfigMap and roll the Redis pod only when that file's hash changes, and `RedisBackend.put` uses `SETEX` when a default TTL is set.

Redis has no global "default TTL" setting, so expiry has to be set per key by the writer. Memory caps and eviction, on the other hand, belong in `redis.conf`. Splitting the two this way matches how Redis works.

**What:** Adds five keys with defaults. `get_database_config()` now returns them, converting samples and TTL to `int`.

**Things to notice:**

- There is **no environment-variable support** for the new keys. Only `MONGODB_URI` and `REDIS_URL` read env vars. Commit `d4a9a56 "rm env ttl"` suggests this was removed on purpose. The PR description still says "Environment variable support with fallbacks".

### 5.2 `jac-scale/jac_scale/providers/database/redis.conf.template` (new): the Redis config

```diff
+maxmemory {redis_max_memory}
+maxmemory-policy {redis_eviction_policy}
+maxmemory-samples {redis_eviction_samples}
+save ""
+appendonly no
+tcp-keepalive 300
+timeout 0
+loglevel notice
+lazyfree-lazy-eviction yes
+lazyfree-lazy-expire yes
+lazyfree-lazy-server-del yes{redis_keyspace_events_line}
```

**What:** A Redis config with four placeholders. `save ""` and `appendonly no` keep the old "no persistence" behaviour that used to come from command-line args.

**Why:** It sets the memory cap and eviction policy, which fixes case 3.2a.

**Things to notice:**
- The last placeholder is either `''` or `'\nnotify-keyspace-events Ex'`. That is why it sits at the end of a line with no space before it.
- The file is filled with `str.format`. Any literal `{` or `}` added later would break it. The `except KeyError` in the provider catches a missing placeholder.
- TTL is **not** in this file. That is correct, because Redis has no default-TTL option.

### 5.3 `jac-scale/jac_scale/providers/database/kubernetes_redis.jac`: build ConfigMap and new Deployment

**Config generation and validation**

```diff
+    def _load_redis_config(self: KubernetesRedisProvider) -> str {
+        scale_config = get_scale_config();
+        db_config = scale_config.get_database_config();
+        ...
+        if redis_eviction_policy not in valid_policies {
+            logger.warning(f"Invalid Redis eviction policy ... Using default 'allkeys-lru'...");
+            redis_eviction_policy = 'allkeys-lru';
+        }
+        # samples: 1–10 else 5 ; ttl: <0 → 0
+        if redis_enable_keyspace_notifications {
+            redis_keyspace_events_line = '\nnotify-keyspace-events Ex';
+        } else { redis_keyspace_events_line = ''; }
+        template_path = Path(__file__).parent / 'redis.conf.template';
+        template_content = template_path.read_text(encoding='utf-8');
+        config_content = template_content.format(redis_max_memory=..., redis_eviction_policy=...,
+            redis_eviction_samples=..., redis_keyspace_events_line=...);
+        return config_content;
+    }
+
+    def _calculate_config_hash(self, config_content: str) -> str {
+        return hashlib.md5(config_content.encode('utf-8')).hexdigest()[:8];
+    }
```

**What:**
- `_load_redis_config` reads the settings and validates them. A bad policy becomes `allkeys-lru`, samples outside 1–10 become `5`, and a negative TTL becomes `0`. Each fallback logs a warning.
- It then loads the template next to the file and fills it in.
- File errors are re-raised: a missing template raises `FileNotFoundError`, and other errors become `ValueError`.
- `_calculate_config_hash` returns the first 8 hex characters of the MD5 hash.

**Why:** It turns user settings into a safe `redis.conf`, plus a short fingerprint for change detection.

**Things to notice:**
- `redis_max_memory` is **not validated**. A value like `"1gb"` passes, but the container limit stays hard-coded at `256Mi`. Redis would then grow past the container limit and be OOM-killed again. Nothing ties the two values together.
- The TTL is validated here but only used for the log line. The real TTL is applied in 5.4.
- A `volatile-*` policy with `redis_default_ttl = 0` means no key has a TTL. Redis then has nothing it may evict, and it acts like `noeviction`. Nothing warns about this combination.
- `import hashlib;` now appears twice in the file. This is harmless.
- MD5 is used only as a change fingerprint, not for security, so the 8-character truncation is fine.

### 5.4 `jac-scale/jac_scale/impl/memory_hierarchy.redis.impl.jac`: TTL on write

```diff
         key = storage_key(anchor.id);
-        self.redis_client.set(key, json.dumps(data));
+        db_config = _get_db_config();
+        ttl = db_config.get('redis_default_ttl', 0);
+        if ttl > 0 {
+            self.redis_client.setex(key, ttl, json.dumps(data));   # NEW: expires
+        } else {
+            self.redis_client.set(key, json.dumps(data));          # OLD behaviour
+        }
```

**What:** When TTL is greater than 0, each anchor written to Redis expires after `ttl` seconds.

**Why:** This fixes case 3.2b. It was added in `dd61490 "support in MHM"` after @juzailmlwork asked for it.

**Things to notice:**
- `_get_db_config()` is defined outside this diff. I can't tell whether it caches the result. If it doesn't, the config is re-read on every `put`.
- This runs in the **app** pods, not the Redis pod. The TTL only applies if the app pod's config contains `redis_default_ttl`. Changing the TTL does not change `redis.conf`, so it does not change the hash and does not restart Redis. That is correct, because Redis doesn't need it.
- TTL is set on write only. A key that is read often but not rewritten still expires `ttl` seconds after its last write.
- Errors are still swallowed (`logger.debug`). With `noeviction` and a full Redis, writes fail silently, and the cache simply misses.

**What:**
- **ConfigMap:** if it exists, compare the text and replace it when different. If it is missing (404), create it.
- **Deployment:** if it exists, compare the hash annotation and replace the Deployment when the hash differs or the ConfigMap was just updated. If it is missing, create it. Logging was added throughout.

**Why:** Before, the Deployment was never updated after the first deploy. Now config changes roll out on the next deploy, and re-running a deploy with the same config does nothing.

**Things to notice:**
- **Possible upgrade crash.** Deployments created before this PR have a pod template with labels only and no annotations. - When the ConfigMap is created through the 404 path, `config_updated` stays `False`. The hash comparison still catches the change, so this is fine.
- The Service is still create-only. Existing Services keep the old `managed` label and won't get the port name or `type` changes.

### 6.3 Caching an anchor

```text
RedisBackend.put(anchor)
├─ serialize anchor, build key
├─ ttl = _get_db_config()['redis_default_ttl']                 ← NEW
├─ ttl > 0 → SETEX key ttl value                               ← NEW
└─ else   → SET key value
```

| Scenario | Before | After |
|---|---|---|
| Fresh deploy | Deployment + Service created; Redis unlimited | ConfigMap + Deployment + Service; Redis capped at 200mb, LRU |
| Redeploy, same config | Nothing changes | Nothing changes |
| Redeploy, changed `redis_eviction_policy` | Ignored (Deployment never updated) | ConfigMap replaced, pod rolled, cache emptied |
| Redeploy, changed only `redis_default_ttl` | n/a | No Redis restart; app writes use new TTL |
| Redeploy over a pre-PR cluster | n/a | Intended: one restart. Possible `AttributeError` if annotations are `None` (5.5) |
| Redis fills up | Grows until OOM kill at 256Mi | Evicts per policy at `maxmemory` |
| `redis_default_ttl = 3600` | Keys never expire | Keys expire 1h after write |

**Behaviour changes users will notice:**
- Redis now evicts at 200mb by default, so cache misses may rise.
- Any config change restarts Redis. Redis has no persistence, so **the cache is emptied**. Calling this "zero-downtime" is generous: the rolling update keeps availability through the readiness probe, but the cached data is lost.
- Labels changed from `managed` to `managed-by`.

## 11. Questions your senior might ask

**Q: Why isn't the TTL in `redis.conf`?**
Redis has no default-TTL setting. Expiry is per key, so it's set in `RedisBackend.put` with `SETEX`.

**Q: What happens when someone changes only the TTL?**
`redis.conf` is unchanged, so the hash is unchanged and Redis isn't restarted. App pods use the new TTL for new writes. Existing keys keep their old TTL, or no TTL.

**Q: What happens the first time this runs against a cluster deployed before the PR?**
The ConfigMap is missing, so it is created. The old Deployment has no pod-template annotations. If the client returns `None` for them, `.annotations.get` raises `AttributeError` and the deploy fails. This needs a `or {}` guard.

**Q: Why compare both the ConfigMap text and a hash annotation?**
The text comparison decides whether to replace the ConfigMap. The hash annotation is what makes k8s restart the pod, because pods don't reload a mounted `redis.conf` by themselves. Checking `config_updated` as well covers the case where the ConfigMap changed but the hash was somehow already equal.

**Q: Is the rollout really zero-downtime?**
Availability mostly yes: the readiness probe gates the new pod. Data no: persistence is off, so every config change starts with an empty cache.

**Q: What if a user sets `redis_max_memory = "1gb"`?**
Nothing stops it. The container limit is still `256Mi`, so the pod would be OOM-killed before Redis starts evicting.

**Q: What does `volatile-lru` do with the default TTL of 0?**
No keys have a TTL, so nothing is evictable, and writes fail once memory is full. `put` swallows that error, so caching just stops silently.

**Q: Do invalid values like `redis_default_ttl = "abc"` get the fallback?**
No. `get_database_config()` calls `int()` first and raises `ValueError` before `_load_redis_config` can fall back.

**Q: Why are there no tests?**
The PR adds none. Verification was CI's fresh k8s deploy plus manual RedisInsight screenshots after merge.

**Q: Will future changes to the Redis Deployment spec roll out?**
Only if `redis.conf` also changes, because the replace call is gated on the config hash.
