## 1. The short version

jac-scale turns Jac walkers and functions marked with `@restspec` into HTTP endpoints. When a request comes in, a generic route builder in `jfast_api.impl.jac` collects the URL's query parameters and passes them to the endpoint's callback as keyword arguments.

**The bug: the route builder forwarded every query parameter in the URL, including ones the endpoint never declared, so any extra parameter crashed walker and function endpoints with a 500.** For example, `GET /function/get_func_with_params?name=Bob&age=40&v=1708012345` failed with `get_func_with_params() got an unexpected keyword argument 'v'`. Browsers add parameters like `v` for cache-busting, and proxies add tracking parameters, so this happened often in real traffic.

**The fix: you added a per-endpoint flag, `forward_undeclared_query_params`, to `JEndPoint`. Walker and function endpoints set it to `False`, and the route builder then drops undeclared query parameters before it calls the callback.** The flag defaults to `True`, so every other endpoint (static pages, webhooks) behaves exactly as before.

**Status:** Merged on 2026-06-18. All test jobs passed on the head commit `084effc`. The only review comments in the data come from the Greptile bot. No human approval appears in the data you were given, so you can't tell from it who approved.

## 3. The problem, step by step

### 3.1 The setup

- **`JEndPoint`** describes an endpoint. It carries its declared `parameters` and a `callback`.
- **`_create_endpoint_function`** builds a FastAPI handler around the callback. Walker and function callbacks accept `**kwargs`, because one callback serves many different walkers or functions.
- **The rule before the PR:** if the callback accepts `**kwargs`, forward all query parameters to it, declared or not. Static-page rendering relies on this rule.
- **Walker and function callbacks** pass those kwargs straight into `walker.init(...)` or the user's function. Both have strict signatures.

### 3.2 What went wrong: function endpoint

```text
1. Client sends: GET /function/get_func_with_params?name=Bob&age=40&v=1708012345&t=abc
2. FastAPI handler runs. Declared params: {name, age}
3. Route builder: callback accepts **kwargs → forward ALL query params
   kwargs = {name: "Bob", age: 40, v: "1708012345", t: "abc"}
4. Function callback calls get_func_with_params(**kwargs)
5. Python raises TypeError: got an unexpected keyword argument 'v'      ← WRONG
6. jac-scale catches it → 500 {"code":"EXECUTION_ERROR", "message": "...unexpected keyword argument 'v'"}
```

### 3.3 What went wrong: walker endpoint

```text
1. Client sends: GET /walker/GetWalkerWithParams?name=Alice&age=30&v=1708012345
2. Route builder forwards ALL query params
   kwargs = {name: "Alice", age: 30, v: "1708012345"}
3. Walker callback calls GetWalkerWithParams.init(**kwargs)
4. init has no field v → TypeError                                       ← WRONG
5. Response: 500
```

### 3.4 Why it mattered

Issue #4661 (verified on `jaclang==0.10.2`, `jac-scale==0.1.9`) explains the impact:

- Any `@restspec` GET endpoint broke as soon as one unexpected parameter arrived.
- Browsers, CDNs, proxies and frontend frameworks add such parameters without the developer's control. The issue gives `?_data=routes/index` as a frontend example.
- The issue says this made `@restspec` endpoints "unusable in production behind CDNs, load balancers, or with real browser traffic."

## 4. The idea of the fix (one sentence)

> **Let each endpoint say whether it wants undeclared query params.** The route builder already knows which parameters are declared, so it drops the undeclared ones for endpoints that opt out, and walkers and functions opt out.

This puts the decision in the one place that already has the declared-parameter list, so you don't need per-callback cleanup. It also keeps static-page rendering working, because that code needs arbitrary query parameters. Your audit comment on 2026-06-17 confirmed that a single global "ignore unknown params" rule would have broken static pages.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/jserver/jserver.jac`: new field on `JEndPoint`

```diff
 obj JEndPoint {
         ...
-        description: (str | None) = None;
+        description: (str | None) = None,
+        forward_undeclared_query_params: bool = True;   # NEW: opt-out switch
 }
```

**What:** Every endpoint description now carries a boolean flag that defaults to `True`.

**Why:** The route builder needs a per-endpoint signal for whether to forward undeclared parameters.

**Things to notice:** Because the default is `True`, any code that builds a `JEndPoint` without the flag keeps the old behavior. Only endpoints that set the flag explicitly change.

### 5.2 `jac-scale/jac_scale/jserver/jfast_api.jac` and `jserver/impl/jfast_api.impl.jac`: the route builder honors the flag

The declaration in `jfast_api.jac` gets the new parameter. The implementation adds it in four places:

```diff

     ...
-    request_model: (type[BaseModel] | None) = None
+    request_model: (type[BaseModel] | None) = None,
+    forward_undeclared_query_params: bool = True        # NEW parameter
 ) -> Callable[..., any] {
```

```diff

-                        query_params = dict(__jac_request__.query_params);
+                        query_params = dict(__jac_request__.query_params)
+                            if forward_undeclared_query_params
+                            else {};                    # NEW: empty when opted out

                                 **{'request': __jac_request__, ** query_params}
```

```diff

-    if accepts_kwargs {
+    if accepts_kwargs and forward_undeclared_query_params {   # CHANGED: skip extra-param forwarding
         declared_params = [
             p.name

```

```diff

+        forward_undeclared_query_params=endpoint.forward_undeclared_query_params   # NEW: pass flag through

```

**What:**
1. `_create_fastapi_route` reads the flag from the `JEndPoint` and passes it to `_create_endpoint_function`.
2. There are two hand-written handlers, one async and one sync. When the flag is `False`, they build `query_params` as an empty dict instead of copying the request's query string.
3. There is also a code-generation path. When the flag is `False`, it skips building `extra_query_params_code`. Judging by the visible `declared_params` list, that code copies query parameters not in `declared_params` into the callback call. The rest of that block is cut off in the diff.

**Why:** This is the actual fix. Undeclared parameters never reach walker or function callbacks, so `.init` and the user's function never see `v` or `t`.

**Things to notice:**
- In the two hand-written handlers, `False` empties the whole query dict, not just the undeclared keys. The branch is guarded by something like `needs_request_no_params`, which suggests it runs only when the endpoint has no declared parameters. In that case "all" and "undeclared" mean the same thing. The exact condition that picks this branch is not visible in the diff, so be ready to explain it.
- Declared parameters still reach the callback through FastAPI's normal parameter handling. The new tests prove this: `name` and `age` come back correctly.
- This is not the issue's suggested fix, which was `inspect.signature()` filtering in the callback. Your early commits (`7de201d`, `e02fc7f`) took that route. Commit `d558628` replaced it with the flag.

### 5.3 `jac-scale/jac_scale/impl/serve.endpoints.impl.jac`: walkers and functions opt out

```diff
 impl JacAPIServerEndpoints.register_walkers_endpoints -> None {
                 summary='API Entry',
-                description='API Entry'
+                description='API Entry',
+                forward_undeclared_query_params=False      # NEW
 ...
                 summary='API Root',
-                description='API Root'
+                description='API Root',
+                forward_undeclared_query_params=False      # NEW
 ...

                 summary='This is a summary',
-                description='This is a description'
+                description='This is a description',
+                forward_undeclared_query_params=False      # NEW
```

**What:** The two walker endpoint registrations ("API Entry" and "API Root") and the function endpoint registration now set the flag to `False`.

**Why:** These are the only endpoints whose callbacks pass kwargs into strict signatures, so they are the only ones that crashed.

**Things to notice:**
- The webhook and static-page registrations are untouched on purpose. Your audit comment says webhooks ignore `kwargs`, so the flag doesn't matter for them. Static pages need the forwarding.
- The diff doesn't show which URL paths "API Entry" and "API Root" map to.
- The diff also doesn't show whether custom `@restspec(path="/items")` paths (the issue's example) go through these same registrations. The tests only cover the default `/function/...` and `/walker/...` paths.

## 6. How execution flows after the PR

### 6.1 Server start-up: registering endpoints

```text
JacAPIServerEndpoints.register_walkers_endpoints / register_functions_endpoints
├─ build JEndPoint(..., forward_undeclared_query_params=False)        ← CHANGED
└─ server.add_endpoint(endpoint)
   └─ JFastApiServer._create_fastapi_route(endpoint)
      └─ _create_endpoint_function(callback, parameters, [], request_model,
                                   forward_undeclared_query_params=False)  ← NEW arg
         ├─ accepts_kwargs = callback has **kwargs (true for walker/function)
         ├─ handler path: query_params = {} when flag is False         ← NEW
         └─ generated path: skip extra_query_params_code when flag is False ← CHANGED
```

### 6.2 Request to a function or walker endpoint

```text
GET /function/get_func_with_params?name=Bob&age=40&v=1708012345&t=abc
├─ FastAPI parses declared params: name="Bob", age=40
├─ undeclared v, t → dropped (not forwarded)                         ← NEW
├─ callback(name="Bob", age=40)
│  └─ get_func_with_params(name="Bob", age=40)   (walker case: Walker.init(name=..., age=...))
└─ 200 {"result": {"message": "...executed", "name": "Bob", "age": 40}}
```

### 6.3 Request to a static page (unchanged)

```text
GET /page/home?theme=dark&lang=fr
├─ JEndPoint flag = True (default)
├─ all query params forwarded as before
└─ render_page(..., theme="dark", lang="fr")
```

| Scenario | Before | After |
|---|---|---|
| Function GET with only declared params | 200 | 200 |
| Function GET with extra `?v=...` | 500 `unexpected keyword argument 'v'` | 200, `v` ignored |
| Walker GET with extra `?v=...` | 500 | 200, `v` ignored |
| Static page with arbitrary params | params passed to renderer | unchanged |
| Webhook with extra query params | ignored by `_process` | unchanged |

**Behavior change users will notice:** extra query parameters on walker and function endpoints are now silently ignored instead of causing a 500. A client that sends a misspelled parameter (say `nmae=Bob`) now gets the default value instead of an error. This matches FastAPI's behavior and what the issue asked for.

## 11. Questions your senior might ask

**Q: Why not just change the default to drop undeclared params everywhere?**
Static-page callbacks (`render_page_callback`, `render_base_route_callback`) deliberately pass all query parameters to `render_page`. A global change would break them. Your audit comment lists every `**kwargs` endpoint.

**Q: Why not use `inspect.signature()` in the callback, as the issue suggested?**
You tried that first (`7de201d`, `e02fc7f`). It needed special handling for walker classes versus `.init`, and it spread the logic across callbacks. The route builder already has the declared-parameter list, so filtering there gives one source of truth.

**Q: In the hand-written handlers you set `query_params = {}`. Doesn't that drop declared params too?**
That branch is guarded by `needs_request_no_params`, which suggests the endpoint has no declared parameters there. If so, nothing declared is lost. The full branch condition isn't visible in the diff, so check the surrounding code before you answer firmly. The tests show declared `name` and `age` still arrive.

**Q: Does this fix custom `@restspec(path="/items")` routes from the issue?**
The tests only exercise `/function/...` and `/walker/...`. The diff doesn't show whether custom paths are registered through `register_functions_endpoints` or `register_walkers_endpoints`. Verify this in the code.

**Q: Does anything still forward undeclared params to walkers?**
Webhooks keep the default `True`, but their `_process` ignores `kwargs` and filters the request body against the walker's fields itself. So walkers no longer receive undeclared query parameters from any endpoint.

**Q: Is there a downside to silently ignoring unknown params?**
A typo such as `nmae=Bob` now falls back to the default value instead of failing loudly. That matches FastAPI and what the issue asked for.

**Q: Could third-party code building `JEndPoint` be affected?**
No. The new field defaults to `True`, so existing constructors behave as before.

**Q: How do you know the tests actually reproduce the bug?**
Per the PR description, both new tests fail without the fix with `got an unexpected keyword argument 'v'` and pass with it.
