## 1. The short version

`by llm()` lets a Jac function hand its body to a large language model (LLM). The compiler turns such a function into a call to a runtime hook, `call_llm`. The byllm plugin answers that hook by calling the model through `litellm`, the `openai` client, or `requests`. All three of those were **synchronous** (blocking).

**The bug: `Model.model_call_no_stream`, `model_call_with_stream` and `model_call_http` used blocking clients, so a `by llm()` call made on jac-scale's single uvicorn event loop froze that loop for the whole LLM round-trip, typically 0.5–30 s.** While it was frozen, no other request, health check or coroutine could run. This is finding **1f** of the scalability audit #5874.

**The fix: when a `by llm()` function is declared `async`, the compiler now emits `await acall_llm(...)` instead of `call_llm(...)`. A new async hook path in the runtime and in byllm then calls the model with `litellm.acompletion`, `AsyncOpenAI` or `httpx.AsyncClient`, so the event loop stays free.** Calls that use tools (the ReAct loop) still run the old sync code, but now on a worker thread through `asyncio.to_thread`. Sync `by llm()` functions still compile to `call_llm`. The sync HTTP path also switched from `requests` to `httpx.Client`.

**Status:** Merged on 2026-05-17. All test checks passed on head commit `a9caa31`. The release jobs were skipped. One review comment by @asimsalim is visible. No formal approval is shown in the data you gave.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Event loop | The single thread that runs all `async` code in turn. If one task blocks it, everyone waits. |
| uvicorn | The web server jac-scale runs on. It has one event loop per process. |
| jac-scale | Plugin that serves Jac apps over HTTP (FastAPI/uvicorn) and deploys to Kubernetes. Every route handler is `async def`. |
| Walker | A Jac object that moves across the graph and runs abilities. jac-scale exposes walkers as HTTP endpoints. |
| Ability | A method or function in Jac. `nd.is_async` on its AST node says whether it was declared `async`. |

| Blocking call | A call that holds the thread until IO finishes, for example `requests.post(...)` or `client.chat.completions.create(...)` on the sync `OpenAI` client. |
| `await` / coroutine | `async def f()` returns a coroutine. `await` pauses it and gives the loop back to other tasks while IO is pending. |
| Async generator | An `async def` that contains `yield`. You consume it with `async for`. You **cannot** `await` it directly. |
| `asyncio.to_thread(fn, ...)` | Runs a blocking `fn` on a worker thread and lets the loop wait without blocking. |
| byllm | The plugin that actually talks to LLMs. Main classes are `BaseLLM` and `Model(BaseLLM)`. |
| `MTRuntime` (`mt_run`) | The object holding one LLM call's prompt, tools, stream flag and conversation. |
| `call_llm` | Existing runtime hook. Compiled `by llm()` code calls it, and byllm implements it as `model.invoke(mt_run)`. |
| `acall_llm` | New async twin of `call_llm`. byllm implements it as `await model.ainvoke(mt_run)`. **This is what the PR adds.** |
| `ainvoke` | New `BaseLLM` method. It picks the native async path or the thread fallback. |
| `adispatch_no_streaming` / `adispatch_streaming` | New async copies of the existing dispatchers. They build params, call the model, parse the reply or yield chunks. |
| `model_call_no_stream` / `model_call_with_stream` / `model_call_http` | The low-level sync calls to the provider. **This is where the bug is.** |
| `*_async` variants | New `async` versions of the three calls above. |
| litellm | Library that wraps many LLM providers. `completion` is sync and `acompletion` is async. |
| `AsyncOpenAI` | The async client from the `openai` package. byllm uses it when `Model.proxy` is true. |
| httpx | HTTP library with both `Client` (sync) and `AsyncClient`. Used when `Model.http_client` is true. |
| ReAct loop | byllm's tool-calling loop: ask the model, run a tool, ask again. It is sync code, `_invoke_react_loop`. |
| pluggy / `@hookimpl` | Plugin system. The runtime declares hooks, and plugins like byllm implement them with `@hookimpl`. |
| `generate_plugin_helpers` / `make_proxy` | Runtime code that builds proxy functions forwarding `Jac.<hook>(...)` to pluggy. |
| `pyast_gen_pass` | The compiler pass that turns Jac's AST into Python's `ast` (`ast3` here). |
| `_invoke_llm_call` / `gen_llm_body` | Compiler helpers that emit the `call_llm(...)` expression for a `by llm()` body. |
| `jaclib` | Module of runtime names that compiled Jac code imports, such as `call_llm` and now `acall_llm`. |

## 3. The problem, step by step

### 3.1 The setup

- Compiled `by llm()` code always called `call_llm(model=..., mt_run=...)`, whether or not the function was `async`.
- byllm's `call_llm` implementation did `model.invoke(mt_run)`.
- `invoke` ends in `model_call_no_stream` or `model_call_with_stream`. The issue points at `model.impl.jac:80,118,149`: `client.chat.completions.create(...)` (sync OpenAI) and `requests.post(...)`.
- jac-scale runs handlers on uvicorn's single event loop.

### 3.2 What went wrong: async walker or async function

```text
1. t=0.0s  Request A arrives → async handler runs on the event loop
2. t=0.0s  Walker calls an async `by llm()` function
3. t=0.0s  Compiled body runs call_llm(...)            (no await, plain call)
4. t=0.0s  byllm → model.invoke → litellm.completion / OpenAI.create / requests.post
5. t=0.0s  Thread blocks on the socket                  ← WRONG: this thread IS the event loop
6. t=0–Ns  Requests B, C, health checks sit in the queue; nothing runs
7. t=Ns    LLM replies (N = 0.5–30 s), loop resumes, B finally starts
```

### 3.3 What went wrong: sync walkers under load

The PR description says sync walkers already run in `asyncio.to_thread` via `spawn_walker_sync`:

```text
1. 10 users trigger sync walkers that call by llm()
2. Each walker occupies one worker thread for 0.5–30 s
3. Thread pool fills; new sync walkers wait for a free thread   ← still a bottleneck
```

This PR does not change the sync-walker case, apart from swapping `requests` for `httpx.Client`.

### 3.4 Why it mattered

The audit (#5874, finding 1f) says: "At 10 concurrent users each triggering an LLM call: requests queue serially — user 10 waits 10× the LLM latency before their response even starts." A frozen loop also means health checks fail. In Kubernetes that can make the pod look dead.

## 4. The idea of the fix (one sentence)

> **Give `async` `by llm()` functions their own awaited hook, backed by real async clients.** The compiler emits `await acall_llm(...)` for async functions, and byllm answers with `litellm.acompletion` / `AsyncOpenAI` / `httpx.AsyncClient`, falling back to a worker thread only where the code is still sync.

Choosing the path at compile time from `nd.is_async` keeps sync code exactly as it was. It also gives async code a path that never touches the loop thread for IO.

## 5. Every code change, explained

### 5.1 `jac/jaclang/jac0core/passes/pyast_gen_pass.jac` + `impl/pyast_gen_pass.impl.jac`: emit `await acall_llm` for async functions

```diff
 impl PyastGenPass._invoke_llm_call(
-    model: ast3.expr, caller: ast3.expr, args: ast3.Dict
-) -> ast3.Call {
+    model: ast3.expr, caller: ast3.expr, args: ast3.Dict, is_async: bool = False
+) -> ast3.expr {                                   # NEW: may return Await, not Call
 ...
-    return self.sync(
+    hook_name = 'acall_llm' if is_async else 'call_llm';
+    call = self.sync(
         ast3.Call(
-            func=self.jaclib_obj('call_llm'),
+            func=self.jaclib_obj(hook_name),
 ...
+    if is_async {
+        return self.sync(ast3.Await(value=call));
+    }
+    return call;
 }
 ...
-    llm_call = self._invoke_llm_call(model=model_expr, caller=caller, args=args);
+    llm_call = self._invoke_llm_call(
+        model=model_expr, caller=caller, args=args, is_async=nd.is_async
+    );
```

**What:** For a `by llm()` ability whose node has `is_async`, the generated Python is `await acall_llm(model=..., mt_run=...)`. Otherwise it is still `call_llm(...)`.

**Why:** Without an `await` in the generated code, no async runtime path could ever be reached.

**Things to notice:**
- The default `is_async=False` keeps any other caller of `_invoke_llm_call` unchanged. The diff does not show whether other callers exist.
- The return type widened from `ast3.Call` to `ast3.expr`, because `Await` is not a `Call`.
- The switch is on **the `by llm()` function itself** being `async`. It does not look at the walker calling it. A plain `def f() -> str by llm();` called from an async walker still compiles to blocking `call_llm`. See 10 and 11.

**What:**
- `acall_llm` is declared as a static async hook.
- The base stub is used when byllm is not installed. It returns a random value of the function's return type, the same as `call_llm`'s stub.
- `make_proxy` now builds an `async def` proxy for any hook whose spec is a coroutine function. That proxy awaits the plugin's result if it is a coroutine.

**Why:**
- Compiled code does `await acall_llm(...)`, so `acall_llm` must return something awaitable.
- The `iscoroutine(result)` guard lets one proxy work with both async and sync hook implementations.

**Things to notice:**
- `await asyncio.sleep(0)` is there only so the Jac `impl` compiles to `async def`. The docstring says this is deliberate, so that `inspect.iscoroutinefunction` is `True` without byllm. This was @asimsalim's comment #2.
- `make_proxy` is generic. Any future async hook gets an async proxy for free.
- If pluggy returned a list of results (a non-`firstresult` hook), `iscoroutine(list)` would be False and the coroutines inside would never be awaited. The diff does not show how `call_llm`/`acall_llm` are configured in pluggy.

### 5.6 `jac-byllm/byllm/llm.impl/basellm.impl.jac`: `ainvoke`, async dispatchers, fallbacks

```diff
+impl BaseLLM.ainvoke(mt_run: MTRuntime) -> object {
+    logging_stream = mt_run.stream and mt_run.call_params.get("logging", False);
+    no_tools = len(mt_run.tools) == 0;
+    if not mt_run.stream and no_tools and not logging_stream {
+        try { resp = await self.adispatch_no_streaming(mt_run); }
+        finally { mt_run.write_back_conversation(); }
+        return resp.output;
+    }
+    if mt_run.stream and no_tools and not logging_stream {
+        return self.adispatch_streaming(mt_run);      # returns an async generator
+    }
+    return await asyncio.to_thread(self.invoke, mt_run);   # tools / logging → thread
+}
```

```diff
+impl BaseLLM.adispatch_no_streaming(mt_run: MTRuntime) -> CompletionResult {
+    params = self.make_model_params(mt_run);
+    ...
+    response = await self.model_call_no_stream_async(params);
+    ... same parsing as dispatch_no_streaming: add_message, tool_calls, parse_response ...
+}
+
+impl BaseLLM.adispatch_streaming(mt_run: MTRuntime) {
+    ...
+    response = await self.model_call_with_stream_async(params);
+    async for chunk in response { ... yield delta.content or ""; }
+}
```

```diff
+impl BaseLLM.model_call_no_stream_async(params: dict) -> dict {
+    return await asyncio.to_thread(self.model_call_no_stream, params);
+}
+
+impl BaseLLM.model_call_with_stream_async(params: dict) {
+    def _next_chunk(gen) { try { return (True, next(gen)); } except StopIteration { return (False, None); } }
+    gen = self.model_call_with_stream(params);
+    while True {
+        (has_value, chunk) = await asyncio.to_thread(_next_chunk, gen);
+        if not has_value { break; }
+        yield chunk;                                   # makes this an async GENERATOR
+    }
+}
```

**What:** `ainvoke` picks one of three paths:

| Case | Path |
|---|---|
| Not streaming, no tools, no logging | Native async `adispatch_no_streaming` |
| Streaming, no tools, no logging | Native async generator `adispatch_streaming` |
| Anything else (tools or streaming with logging) | The sync `invoke` on a worker thread |

The `BaseLLM` fallbacks let custom subclasses work without writing async code.

**Why:** These changes free the event loop on every path. Only the simple paths get true async IO. The ReAct loop stays sync on purpose, as the docstring says ("out of scope").

**Things to notice:**
- `_next_chunk` turns `StopIteration` into a flag. A `StopIteration` cannot cross `to_thread`/`await` cleanly. Python turns it into a `RuntimeError` inside coroutines.
- The fallback runs `next()` in a thread for each chunk. This addresses a real trap: `to_thread(model_call_with_stream)` alone would only create the generator off-loop.
- **Possible bug in the streaming fallback.** `BaseLLM.model_call_with_stream_async` contains `yield`, so it is an async generator. `adispatch_streaming` does `response = await self.model_call_with_stream_async(params)`. In Python, `await` on an async generator raises `TypeError: object async_generator can't be used in 'await' expression`. `Model` is not affected, because its override has no `yield` and returns the stream from an `await`. A custom `BaseLLM` subclass that streams from an async function would hit this. No test covers this path. This assumes Jac compiles `async def` + `yield` the way Python does; the diff does not prove that.
- Streaming results: for async functions, the hook now returns an **async** generator. Sync streaming returns a normal generator, so callers must use `async for`.
- `adispatch_no_streaming` calls `response.get(...)` and `response.get("choices", [])[0].get("message")`. That matches the sync dispatcher. Whether the `AsyncOpenAI` proxy response supports `.get` like a dict depends on code not in the diff, in the same way as the sync proxy path.

```diff
+    ... same three branches with stream=True, same exception mapping ...
+}

+impl Model.model_call_http_async(...) -> object {
+    async with httpx.AsyncClient(verify=ca_bundle or True, timeout=60.0) as client {

```

**What:**
- Three backends are used natively in async form.
- Provider errors are mapped to byllm's own `AuthenticationError`, `RateLimitError` and `ModelNotFoundError`, with the same logging as the sync path.
- `AsyncOpenAI` is created once per `Model` and reused.

**Why:** These are the actual non-blocking IO calls that free the loop.

**Things to notice:**
- The catch-all `except Exception` in the streaming version was added in the later commits. The PR description says so ("adds missing `except Exception` catch-all").
- `httpx.AsyncClient` is still created per call. Only the proxy client is cached.
- **Streaming with `http_client=True` looks broken.** `model_call_http_async` returns `response.json()`, a dict, and `adispatch_streaming` then does `async for chunk in response` on it. That would fail. A streamed HTTP reply is also usually server-sent events, not one JSON body. The sync `model_call_with_stream` is not in the diff, so you can't tell whether this mirrors an existing limit.
- Sync-path behaviour change: `httpx.Client` does not follow redirects by default, while `requests` did. This affects every sync user with `http_client=True`, not only async ones.
- The impl declares `ca_bundle: str`, but the declaration says `str | bool`. This is cosmetic.

## 6. How execution flows after the PR

### 6.1 Compiling a `by llm()` function

```text
Jac source: async def get_summary(text: str) -> str by llm();
└─ pyast_gen_pass.gen_llm_body(nd)
   ├─ build model_expr, caller, args
   └─ _invoke_llm_call(..., is_async=nd.is_async)        ← CHANGED
      ├─ is_async → Await(Call(acall_llm, model=..., mt_run=get_mtir(...)))  ← NEW
      └─ not async → Call(call_llm, ...)                  (unchanged)
```

### 6.2 Calling an async `by llm()` function, no tools, no streaming

```text
await get_summary(text="hello")
└─ await acall_llm(model, mt_run)                         ← NEW (jaclib → async_proxy)
   └─ async_proxy → pluggy → byllm acall_llm hookimpl     ← NEW
      └─ await model.ainvoke(mt_run)                      ← NEW
         ├─ adispatch_no_streaming(mt_run)                ← NEW
         │  ├─ make_model_params / format_prompt
         │  ├─ await Model.model_call_no_stream_async     ← NEW
         │  │  ├─ http_client → await httpx.AsyncClient.post
         │  │  ├─ proxy       → await cached AsyncOpenAI.create
         │  │  └─ else        → await litellm.acompletion
         │  └─ parse message, tool_calls, usage → CompletionResult
         ├─ finally: mt_run.write_back_conversation()
         └─ return resp.output
```

### 6.3 Async function with streaming

```text
await acall_llm(...)
└─ ainvoke → returns adispatch_streaming(mt_run)  (async generator, not awaited)  ← NEW
   └─ caller does `async for` over it
      └─ await model_call_with_stream_async(params)
         ├─ Model: litellm.acompletion(stream=True) / AsyncOpenAI(stream=True)
         │         / http_async (returns dict → `async for` would fail; see 5.7)
         └─ BaseLLM fallback: async generator → `await` on it likely TypeError (see 5.6)
```

### 6.4 Async function with tools (ReAct), or streaming with logging

```text
await acall_llm(...)
└─ ainvoke
   └─ await asyncio.to_thread(self.invoke, mt_run)        ← NEW (loop free, thread busy)
      └─ old sync ReAct loop → sync model calls
```

### 6.5 Sync `by llm()` function

```text
get_summary_sync(text=...)
└─ call_llm(...) → model.invoke(mt_run)   (unchanged; http path now httpx.Client ← CHANGED)
```

| Scenario | Before | After |
|---|---|---|
| `async def f() by llm()`, no tools | Blocked the loop for the whole LLM call | Native async; loop free |
| `async def f() by llm()`, with tools | Blocked the loop | Runs on a worker thread; loop free, one thread busy |
| `async def f() by llm()`, streaming | Sync generator, loop blocked per chunk | Async generator; caller must `async for` |
| Plain `def f() by llm()` called from an async walker | Blocked the loop | **Still blocks the loop** (compiles to `call_llm`) |
| Sync walker via `spawn_walker_sync` | Ran in a thread | Unchanged |
| `Model(http_client=True)` sync call | `requests.post` | `httpx.Client.post` (no redirect following by default) |

Users will notice two things:
- To get the fix, the `by llm()` function itself must be declared `async` and awaited.
- Async streaming now hands back an async generator.

## 11. Questions your senior might ask

**Q: Does an async walker that calls a normal `def f() -> str by llm();` stop blocking the loop now?**
No. The compiler looks at `nd.is_async` on the `by llm()` ability itself. A plain `def` still compiles to `call_llm(...)` and blocks. The user must write `async def f() -> str by llm();` and `await` it.

**Q: Why not make the ReAct tool loop fully async too?**
The docstring on `ainvoke` says the ReAct logic is sync state machinery and rewriting it is out of scope. `asyncio.to_thread(self.invoke, mt_run)` frees the loop now, at the cost of one thread per call. @asimsalim called this "the right interim approach".

**Q: Why `await asyncio.sleep(0)` in the base `acall_llm` stub?**
A Jac `impl` with no `await` would compile to a plain `def`. The stub needs to be a real coroutine function so that `iscoroutinefunction` is True and `make_proxy` builds an async proxy, even when byllm is not installed.

**Q: Why does the streaming fallback call `next()` in a thread for each chunk instead of wrapping the whole call once?**
`to_thread(model_call_with_stream, params)` would only create the generator off-loop. The network reads happen while iterating, so each `next()` must also run off-loop.

**Q: Does the streaming fallback actually work?**
Probably not as written. It is an async generator (it contains `yield`), and `adispatch_streaming` does `await` on it, which raises `TypeError` in Python. `Model` overrides it with a coroutine, so normal users are fine. No test covers custom subclasses.

**Q: Why cache `AsyncOpenAI` but not `httpx.AsyncClient`?**
The description says the proxy client is cached to avoid a new connection pool per request. The HTTP path still opens an `AsyncClient` per call. The PR does not explain the difference.

**Q: Is replacing `requests` with `httpx` in the sync path safe?**
Mostly. Timeout, verify and JSON handling map across directly. One difference is that httpx does not follow redirects by default, so an endpoint behind a redirect would now fail. No test covers the sync change.

**Q: What does an async streaming `by llm()` return to the user?**
An async generator from `adispatch_streaming`. The caller must use `async for`, whereas the sync version returns a normal generator.

**Q: What happens with multiple plugins implementing `acall_llm`?**
`async_proxy` only awaits the result when it is a single coroutine. If the hook returned a list, the coroutines inside would not be awaited. Whether the hook is `firstresult` is not visible in the diff.

**Q: How do you know the generated code is correct and not just containing the right string?**
The codegen test walks the Python AST. It checks that there is at least one `Await` whose value is a `Call` to `acall_llm`, and that no `acall_llm` call is left un-awaited. The end-to-end test then runs the compiled module with a fake `acall_llm` and gets `"summary"` back.
