## 1. The short version

Jac stores the graph (nodes and edges) in a database: SQLite by default, or MongoDB when you use jac-scale. Sometimes a stored row can't be turned back into a Jac object, for example because its node type (`app.Foo`) was deleted between deploys. When that happens, the runtime moves the row into a side table called the quarantine, so the app doesn't crash.

**Before this PR, quarantine moved only the node. The edges pointing at it stayed live, and the source node's `data.edges` list still named those edges.** The database was left with edges into nowhere. In production (`jac-builder`), users then hit `NodeAnchor [<uuid>] is not a valid reference!` when running `walker/me`.

**You made quarantining a node cascade: every edge whose `source` or `target` is that node is also quarantined, and its ID is removed from every live node's `data.edges`.** This works in both backends. You also did two related things:

- When an edge is later recovered, its ID is added back to the right node(s).
- A node is now quarantined when a field comes back as `None` but its type does not allow `None`. This happens, for example, when the field held a nested object whose class was removed.

**Status:** Merged on 2026-05-18. All test checks passed. @kugesan1105 commented (no formal approval appears in the data) and confirmed the "not a valid reference" errors were gone. Two of his follow-ups were moved to #6035.

## 3. The problem, step by step

### 3.1 The setup

- A user's graph is `root → e1 → foo1`, `root → e2 → foo2`, `root → e3 → foo3`. Every link is stored as a row in `_anchors`.
- `root.data.edges = [e1, e2, e3]`. Each `eN` has `source=root`, `target=fooN`.
- Version 2 of the app removes `node Foo`.
- Loading a `Foo` row fails. The backend calls `_quarantine` / `_mongo_quarantine`.

### 3.2 What went wrong: Case 1, node class removed

```text
1. v1 running. _anchors: root, foo1..3, e1..3.  root.data.edges=[e1,e2,e3]. quarantine: empty
2. Deploy v2 (Foo removed). Same DB.
3. Walker loads foo1 → "Refused to deserialize unregistered class: app.Foo"
4. _mongo_quarantine(foo1): copy foo1 → _anchors_quarantine, delete foo1 from _anchors
5. ✗ e1 stays in _anchors with target=foo1 (foo1 now only in quarantine)
6. ✗ root.data.edges still = [e1,e2,e3]
7. Same for foo2, foo3 → Live NodeAnchors 3, Live EdgeAnchors 3, Quarantined 3
8. Later traversal from root dereferences e1 → target not live
   → prod: "NodeAnchor [<uuid>] is not a valid reference!"
```

Quarantine is lazy. Your Case 1 comment shows that `foo2` and `e2` stay live until a walker actually reaches them. Only then does the same process run for them.

### 3.3 What went wrong: Case 2, nested field class removed

```text
1. Node _TypedProfile { score: int } stored with score = {__type__:"RemovedClass", ...}
2. _deserialize_archetype → _deserialize_value(score) → None (class not found)
3. coerce(None, int) → ok = False
4. ✗ OLD: setattr(arch, "score", None); logger.debug(...); node returned as if fine
5. Caller gets a node whose int field is None. No quarantine, only a debug log.
```

### 3.4 Why it mattered

- Production `jac-builder` collected 9 orphan edges over months (issue #5987). Seven of them had "source exists, target missing", all from `user_root`.
- Affected users could not run `walker/me`.
- Operators had a 4-step manual cleanup script:
  1. Quarantine the orphan edges.
  2. `$pullAll` the stale IDs.
  3. Clear the Redis cache.
  4. Restart the pods.
- The issue notes this is a different bug from the race fixed by #5644.
- After testing the PR, @kugesan1105 reported that neither the `NodeAnchor ... is not a valid reference` nor the `EdgeAnchor ...` error appears any more.

## 4. The idea of the fix (one sentence)

> **Quarantine the node's edges with it, and undo that on recovery.** When a `NodeAnchor` is quarantined, every edge that touches it is also moved to quarantine and its ID is removed from every live node's `data.edges`; when such an edge is recovered, its ID is put back.

This keeps the live table consistent: nothing live points at something that isn't live. It also reuses the existing quarantine and recover tools, so no new storage or CLI is needed.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/impl/memory.impl.jac`: SQLite cascade on quarantine

```diff
 def _quarantine(conn, id, ..., anchor_type, ...) {
     try {
+        now_ts = datetime.now(timezone.utc).isoformat();     # NEW: one timestamp for node + edges
         conn.execute("INSERT OR REPLACE INTO anchors_quarantine ...", (..., now_ts, ...));
         conn.execute("DELETE FROM anchors WHERE id = ?", (id, ));
+        if anchor_type == 'NodeAnchor' {
+            cursor = conn.execute("""SELECT id, type, arch_module, arch_type, fingerprint, data, format_version
+                FROM anchors WHERE type = 'EdgeAnchor'
+                  AND (json_extract(data, '$.source') = ? OR json_extract(data, '$.target') = ?)""", (id, id));
+            orphaned_edges = cursor.fetchall();
+            if orphaned_edges {
+                cascade_error = f"cascade quarantine: connected node {id} was quarantined";
+                try {
+                    conn.execute("SAVEPOINT cascade_q");
+                    for row in orphaned_edges { ... INSERT OR REPLACE INTO anchors_quarantine ... }
+                    placeholders = ','.join('?' * len(orphan_edge_ids));
+                    conn.execute(f"DELETE FROM anchors WHERE id IN ({placeholders})", orphan_edge_ids);
+                    live_nodes = conn.execute(f"""SELECT id, data FROM anchors WHERE type = 'NodeAnchor'
+                          AND EXISTS (SELECT 1 FROM json_each(json_extract(data, '$.edges')) je
+                                      WHERE je.value IN ({placeholders}))""", orphan_edge_ids).fetchall();
+                    for (node_id, node_data_str) in live_nodes {
+                        try { ... filter edges, UPDATE anchors SET data = ? ... }
+                        except Exception as patch_err { logger.error(...); }
+                    }
+                    conn.execute("RELEASE cascade_q");
+                    logger.info("SqliteMemory: cascade-quarantined N edge(s) ...");
+                } except Exception as cascade_err {
+                    try { conn.execute("ROLLBACK TO SAVEPOINT cascade_q"); } except Exception { }
+                    try { conn.execute("RELEASE cascade_q"); } except Exception { }
+                    logger.error("... cascade quarantine for node {id} failed (rolled back to savepoint) ...");
+                }
+            }
+        }
         conn.commit();
```

**What:**
1. After the node is moved, the code finds every edge row whose JSON `source` or `target` equals the node ID.
2. It copies those rows into `anchors_quarantine` with the error text `cascade quarantine: ...`.
3. It deletes them from `anchors` in one statement.
4. It rewrites every live node whose `data.edges` contains any of them, removing those IDs.
5. Everything is committed once.

**Why:** This fixes steps 5 and 6 of the Case 1 timeline for SQLite.

**Things to notice:**
- If the cascade fails, it rolls back to the savepoint. The node quarantine still commits, so you can end up with the old one-sided state, but with an error log.
- A failure while patching one node is caught *inside* the loop. That node keeps its stale IDs and the savepoint is still released. So a cascade can partly succeed.
- `set(orphan_edge_ids)` is rebuilt for every node inside the loop. This is harmless but wasteful.
- `json_extract` on `data` cannot use an index, so each quarantine scans all edge rows and all node rows. Issue #5987 suggested indexes; this PR adds none.
- The `IN (?,?,...)` list grows with the number of edges. SQLite has a limit on bound parameters. Whether a node with very many edges could hit it depends on the SQLite build, which can't be told from the diff.
- The ID strip applies to *every* live node, not only the source. That is correct for undirected edges, and for any target-side bookkeeping.

**What:** When a recovered row is an edge, its ID is added back to the source node's `data.edges`. For undirected edges it is added to the target's list as well. It is only added if missing.

**What:** This is the same logic as SQLite, written with Mongo operators:
1. `find` the connected edges.
2. Copy them to quarantine with one `bulk_write`.
3. Remove them with `delete_many`.
4. Strip their IDs from live nodes with `$pullAll`.

On recovery, `$addToSet` puts the edge ID back.

**Why:** This is the backend where production broke (#5987).

**Things to notice:**
- There is no Mongo transaction. The issue suggested `with_transaction()`. The order of steps is copy → delete → strip. A failure halfway is caught by the outer `except` and logged, but steps already done are not undone. Example: if `update_many` fails, live nodes keep the stale IDs.
- `ordered=False` means one failed upsert doesn't stop the others.
- `$addToSet` on a node that isn't live matches nothing. That is the same silent skip as in SQLite.
- The variable is called `orphaned_edges` because @kugesan1105 asked for it in an inline comment (commit 43d33d9).

**Things to notice:**

## 6. How execution flows after the PR

### 6.1 Loading a node whose class was removed

```text
walker traverses edge → backend.get(foo_id)
├─ _deserialize_anchor → archetype class app.Foo not found → None
├─ _quarantine / _mongo_quarantine(foo_id, anchor_type='NodeAnchor')
│  ├─ copy foo row → quarantine table (quarantined_at = now_ts)
│  ├─ delete foo from live table
│  ├─ find EdgeAnchors with source==foo_id OR target==foo_id        ← NEW
│  ├─ copy them → quarantine, error "cascade quarantine: ..."        ← NEW
│  ├─ delete them from live table (one DELETE IN / delete_many)      ← NEW
│  ├─ strip their IDs from every live NodeAnchor's data.edges        ← NEW
│  │   (SQLite: inside SAVEPOINT cascade_q; Mongo: no transaction)
│  └─ commit (SQLite, once) ; log "cascade-quarantined N edge(s)"   ← NEW
└─ get() returns None
```

### 6.2 Loading a node with an unresolvable nested field

```text
backend.get(id) → _deserialize_archetype
├─ for each field k: deser_v = _deserialize_value(...)
├─ (coerced, ok) = coerce(deser_v, field_type)
├─ if not ok:
│  ├─ deser_v is None and type not Optional → raise TypeError        ← NEW
│  │   └─ caught (existing except) → None → quarantine → cascade (6.1)
│  └─ otherwise → logger.warning, keep value                         ← CHANGED (was debug)
└─ setattr(arch, k, coerced)                                         ← CHANGED (moved after check)
```

### 6.3 Recovering one quarantined edge (`jac db recover-one`, or each row of `recover-all`)

```text
_sqlite_attempt_recover / _mongo_attempt_recover(row)
├─ re-deserialize (GenericEdge always resolves)
├─ write back to live table, delete from quarantine
├─ if EdgeAnchor:                                                     ← NEW
│  ├─ relink_ids = [source] (+ target if is_undirected and ≠ source)
│  └─ for each: if node live → add edge ID to data.edges if missing
│               else → skip silently (warning added in #6035 per thread)
└─ return (True, "recovered")
```

| Scenario | Before | After |
|---|---|---|
| Node type removed, edges point at it | Node quarantined; edges and `data.edges` entries left dangling | Node and its edges quarantined; `data.edges` cleaned |
| `jac db inspect` after 2 nodes quarantined | `quarantined=2` | `quarantined=4` (2 nodes + 2 edges) |
| `recover-all` after alias add | "Recovered 2 of 2"; edges never moved | "Recovered 4 of 4"; root `data.edges` re-linked |
| Recover undirected edge | n/a | Edge ID re-added to both ends |
| Non-Optional field deserializes to `None` | Loaded with `None`, debug log | Node quarantined (plus cascade) |
| Other coercion miss (e.g. set as str) | Kept, debug log | Kept, **warning** log |

Behaviour changes users will notice:
- Quarantine counts are larger.
- Edges appear in `jac db quarantine list`.
- Nodes with `None` in non-Optional fields now disappear from the live graph instead of loading.

## 11. Questions your senior might ask

**Q: Why not use a Mongo transaction, as the issue suggested?**
The PR doesn't use one, and the reason isn't stated. Transactions need a replica set, which may explain the choice, but the PR doesn't say so. The steps are ordered copy → delete → strip, and a mid-way failure is only logged.

**Q: What happens if the SQLite cascade fails halfway?**
It rolls back to `SAVEPOINT cascade_q`, so the edges stay live, and the node quarantine still commits. That is the old one-sided state, plus an error log. A failure while patching a single node is caught per node, so the cascade still releases.

**Q: Does recovering in the wrong order lose links?**
It can. If an edge is recovered while its endpoint is still quarantined, the re-link finds nothing and skips silently. @kugesan1105 flagged this, and it is deferred to #6035.

**Q: Why re-link directed edges only to the source?**
The PR treats the source's `data.edges` as the owner of directed edges, and the tests only assert the source/root side. The cascade strips IDs from *all* live nodes, though. Whether target nodes also store directed edge IDs can't be confirmed from this diff.

**Q: Could the new serializer rule quarantine valid data?**
Yes, if a non-Optional field was ever stored as `null`. The check is `deser_v is None and not is_optional`, not "class missing".

**Q: What does the cascade cost?**
Each node quarantine runs one query over edge rows by `source`/`target`, plus one over node rows by `edges`. There are no new indexes, and SQLite's `json_extract` scans the table. Quarantine is rare and happens on load, so this is probably fine, but it is not measured.

**Q: Why did existing CLI tests change from 2 to 4?**
The connecting `GenericEdge`s are now quarantined too. The `quarantine show` test had to filter to a `NodeAnchor` because edge rows can now come first.

**Q: Does this clean up databases that are already corrupted?**
No. The cascade only runs when a node is quarantined from now on. Existing orphan edges whose target was quarantined earlier stay in place. Operators still need the cleanup script, or a re-quarantine, for those.

**Q: Is the Redis/L2 cache handled?**
The diff only touches the quarantine and recover functions. The issue's workaround also cleared Redis keys, and nothing in this PR does that, so it's unclear whether cached copies of the source nodes keep stale `edges`.
