## 1. The short version

The Jac API server has a `UserManager` (in `jac/jaclang/runtimelib`). It registers users, logs them in, checks tokens, and maps each username to that user's graph root. **Before this PR, users and tokens lived in a separate JSON file (`.jac/data/users.json`), outside the memory hierarchy that stores everything else.** The memory hierarchy is the layered storage (in-process memory, then SQLite or MongoDB) that holds the graph. Issue #3979 asks for users to move into it. Issue #3851 reports a flaky registration failure in CI, `{'error': 'Registration failed: pickle data was truncated'}`, where the first user is created and later ones fail at random.

**You replaced the JSON file with a new `User` object that is saved as a persistent anchor in the memory hierarchy. Every lookup now goes through a new `TieredMemory.query(filter=...)` method that scans memory and the database.** You also added two features the issues don't mention: `PUT /user/username` and `PUT /user/password`, in both the core server and jac-scale (the FastAPI server). The littleX example test was switched to use them, and a `JacTestClient.put` helper was added.

The branch still contains a lot of debug output. Some of it prints passwords, tokens and decoded JWTs. It also contains one clear regression: in `do_POST`, the line that should attach `_jac_spawn_node` to a walker's fields no longer does anything, so walkers sent to `/walker/<name>/<node_id>` would start at root instead of the chosen node. Two CI jobs (`test-core`, `test-scale`) failed.

**Status:** Closed (the metadata does not show it as merged). There were no reviews or comments, and `test-core` and `test-scale` failed on head commit `1ae22e0`.

## 3. The problem, step by step

### 3.1 The setup

- **`UserManager`** (`jac/jaclang/runtimelib/server.jac` plus `impl/server.impl.jac`) held two dicts:
  - `_users`: `username → {password_hash, token, root_id}`
  - `_tokens`: `token → username`
- `postinit` created `.jac/data/` and loaded `users.json`. Every change called `_persist()`, which rewrote the whole file.
- **The graph** (each user's `Root` and everything under it) was stored through the execution context's memory (`ctx.mem`): L1, then SQLite or Mongo.
- So there were **two separate stores**: users in a JSON file, and graph data in the memory hierarchy.

### 3.2 What went wrong: users stored outside the memory hierarchy (#3979)

```text
1. Server starts → UserManager.postinit → _db_path = .jac/data/users.json → _load_db() fills _users/_tokens
2. POST /user/register alice → Root created in ctx.mem (L1 → L3: SQLite or Mongo)
3.   → _users['alice'] = {hash, token, root_id}; _tokens[token] = 'alice'
4.   → _persist() rewrites users.json on the local disk                      ← WRONG: separate store
5. L3 (e.g. Mongo in jac-scale) now holds alice's Root but NOT alice's login record
6. Any other process or pod that reads the same L3 has no users.json, so it cannot find alice
```

Step 6 is an inference. The old jac-scale test comment ("initial docs is two, because super root, guest_user") shows Mongo held users' roots but not their login records. The PR text doesn't spell out the multi-pod case.

### 3.3 What went wrong: flaky "pickle data was truncated" (#3851)

```text
1. CI backend test registers user #1 → OK
2. Registers user #2, #3 ... → sometimes: {'error': 'Registration failed: pickle data was truncated'}
3. Rerun → usually passes
```

The diff doesn't show the root cause. The existing comment in `create_user` ("Use existing context instead of creating new one (avoids shelf locking issues)") hints that earlier work found concurrent access to the pickled store. This PR adds no test that reproduces the flake, so you can't show it is fixed. You can only argue it is less likely now that a second store is gone.

### 3.4 Why it mattered

- #3979 is filed as a bug: user management should use the same persistence as everything else.
- #3851 made CI flaky. Registration failed at random and people had to rerun jobs.

## 4. The idea of the fix (one sentence)

> **Make users graph objects.** Each user becomes a persistent `User` anchor in the same memory hierarchy as the graph, and every user lookup becomes a filtered query over that memory.

This removes the second store. User records then go wherever the graph goes (SQLite locally, Mongo in jac-scale) and share one commit path. The trade-off is that a lookup by username or token becomes a scan of all stored anchors instead of a dict lookup.

#### 5.2.3 New `update_username` / `update_password` on `UserManager`

```diff
+impl UserManager.update_username(current_username: str, new_username: str) -> dict[str, str] {
```

**Why:** This is new functionality, not required by either issue.

**Things to notice:**
- `root_id` does not change, so the user keeps their graph.
- The core token does not change on a password update, so an old session stays valid. A reviewer may ask about this.

### 5.3 `jac/jaclang/runtimelib/memory.jac` + `impl/memory.impl.jac`: new `TieredMemory.query`, lots of prints

```diff
+impl TieredMemory.query(filter: (Callable[[Anchor], bool] | None) = None) -> Generator[Anchor, None, None] {
+    seen_ids = set();
+    for anchor in self.__mem__.values() { if filter is None or filter(anchor) { seen_ids.add(anchor.id); yield anchor; } }
+    if self.l3 {
+        if self.l3?.find_all and callable(self.l3.find_all) {     # MongoMemory
+            for anchor in self.l3.find_all() { ...skip seen, filter, yield... }
+        } else {                                                  # SqliteMemory
+            if not self.l3.__conn__ and os.path.exists(self.l3.path) { self.l3._ensure_connection(); }
+            if self.l3.__conn__ {
+                cursor = self.l3.__conn__.execute("SELECT id, data FROM anchors");
+                for row in cursor.fetchall() { ...UUID(row[0]) not seen → loads(row[1]) → filter → yield... }
+            }
+        }
+    }
+}
```

**What:** The method yields matching anchors from L1, then from L3. Mongo goes through `find_all()`. SQLite does a full table read and unpickles each row, skipping rows that fail to unpickle.

**Why:** `UserManager` needs to find records by field, not by id.

**Things to notice:**
- L2 (Redis) is skipped.
- It reaches into SQLite internals (`__conn__`, `path`, `_ensure_connection`). Real backend-specific `query` methods would be cleaner.
- The `seen_ids` check prefers L1, so an in-memory edit wins over the stale DB copy. That is good.
- **An L1 anchor is yielded even if it isn't persistent.** But the L3 side only sees what was synced.
- Whether `self.l3?.find_all` handles an attribute that doesn't exist (as opposed to `None`) depends on Jac's `?.` rules. The diff can't confirm it.
- The history shows Mongo support being added, removed and re-added (`04d895b`, `b4ea70d`, `0ab5bcf`).
- `SqliteMemory.sync` gained about 20 `print` lines, and `TieredMemory.put` gained one. They run on every commit, and one is inside a loop over all anchors. `except (...) as e` was added only to print `e`.

- The routes are registered directly on FastAPI, skipping the project's `JEndPoint` wrapper (per the code comment), and marked as needing Bearer auth in OpenAPI.

**Things to notice:**
- **Old JWTs still carry the old username.** After a rename, any client that keeps the old JWT gets `validate_jwt_token → 'olduser'`, which no longer matches a user. That user's walker calls would fail until they switch to the new token.
- `HTTPBearer()` uses `auto_error=True` by default. With no header, FastAPI rejects the request **before** your callback runs, returning its own `{"detail": "Not authenticated"}`. Depending on the FastAPI version this is a 403 or a 401. The jac-scale tests expect 401 **and** a transport-style `error` field. That mismatch is a likely cause of the `test-scale` failure, but you'd have to check the logs to confirm.
- The `print` of the token and the decoded JWT is a credential leak in production logs.
- The `'patch'` method in the OpenAPI loop isn't registered anywhere. It's harmless.

## 11. Questions your senior might ask

**Q: How does a login find the user now?**
`UserManager.authenticate` calls `mem.query` with a filter on `isinstance(a.archetype, User)` and the username. That yields L1 anchors, then every L3 row: SQLite `SELECT id, data FROM anchors` plus unpickling, or Mongo `find_all()`. It's a linear scan, not an index.

**Q: What happens to existing users in `.jac/data/users.json`?**
Nothing reads that file anymore. They won't be found and can't log in. The PR adds no migration.

**Q: Why add `jaclang.runtimelib.server` to `reset_machine`'s keep list?**
The lookups use `isinstance(..., User)`. If the module reloaded, a `User` unpickled from the DB could belong to a different class object than the current one, and the check would fail. Keeping the module keeps `User` stable.

**Q: Does this fix the pickle truncation flake (#3851)?**
The PR can't show it. It removes the separate JSON store but adds no test reproducing the flake, and the root cause isn't in the diff.

**Q: Why did you set `Jac.exec_ctx` in `JacAPIServer.postinit`?**
`UserManager.postinit` reads `Jac.get_context().mem`, so a context has to exist before `UserManager` is created (commit `e86c04b`).

**Q: What happens to a jac-scale client's old JWT after a rename?**
It still decodes to the old username, which no longer matches any `User`, so authenticated calls with it fail. The client must switch to the `token` returned by `PUT /user/username`.

**Q: Will a rename persist after a server restart?**
It isn't tested. `query` doesn't load L3 anchors into L1, and `SqliteMemory.sync` only walks L1. It depends on how `TieredMemory.commit(anchor)` handles an anchor not in L1, and that code isn't in the diff.

**Q: Why does `POST /walker/foo/<id>` start at root now?**
`{'_jac_spawn_node': node_id};` is a statement that builds a dict and discards it, so `spawn_walker` never sees the target id. It's a bug introduced in this PR.

**Q: Why did the littleX tests stop calling `update_profile`?**
The PR doesn't say. The new calls rename the login user instead of updating the app's profile node, so the example's walker is no longer covered.

**Q: Why does jac-scale bypass `JEndPoint` for the new routes?**
The code comment says the routes are registered "directly with FastAPI (bypassing JEndPoint parameter processing)". This lets the route take a Pydantic body together with an `HTTPBearer` dependency. As a side effect, a missing token is rejected by FastAPI with its own error format, not a `TransportResponse`.
