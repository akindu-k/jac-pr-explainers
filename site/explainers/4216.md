## 1. The short version

jac-scale is the Jac plugin that runs Jac apps as a production web server and deploys them to Kubernetes. It has login, JWT tokens and Google Single Sign-On (SSO). Before this PR, all of that logic sat inside the `JacAPIServer` class. The core Jac runtime also always built a plain `UserManager` with the line `UserManager(base_path=self.base_path)`.

**Nothing was broken. The gap was that the core server hard-coded `UserManager`, so no plugin could swap in its own user manager, and jac-scale's auth and SSO code was locked inside the HTTP server class and tied directly to the `fastapi_sso` `GoogleSSO` library.** Adding a second SSO provider, or reusing the auth logic, meant editing `JacAPIServer` itself.

**The PR adds a hookable `Jac.get_user_manager(base_path)` to the core runtime. jac-scale overrides that hook to return a new `JacScaleUserManager`. You moved all JWT and SSO logic into `JacScaleUserManager`, put Google behind a new `SSOProvider` interface (`GoogleSSOProvider`), and added an `sso_accounts` table with link, unlink and lookup methods.** `JacAPIServer` now delegates every call to `self.user_manager`. For example, `self.validate_jwt_token(token)` became `self.user_manager.validate_jwt_token(token)`. The HTTP endpoints, paths and error codes stay the same.

**Status:** Merged on 2026-01-24. @musab-mah-7 requested changes twice on 2026-01-23 (about the docs) and approved on 2026-01-24. All 6 CI checks passed on head commit `866919a`.

## 3. The problem, step by step

This is a refactor plus a feature, so this section describes what was missing.

### 3.1 The setup

- **Core server** (`jac/jaclang/runtimelib/impl/server.impl.jac`): `JacAPIServer.postinit` built the user store directly with `UserManager(base_path=self.base_path)`.
- **jac-scale server** (`jac-scale/jac_scale/serve.jac` + `impl/serve.impl.jac`): its `JacAPIServer` subclass declared:
  - the static methods `create_jwt_token`, `validate_jwt_token` and `refresh_jwt_token`;
  - `get_sso`, which returned a raw `GoogleSSO`;
  - `sso_initiate` and `sso_callback`;
  - `postinit`, which filled `self.SUPPORTED_PLATFORMS` from config.
- Every protected endpoint (walker calls, function calls, update username/password, refresh, login, create user) called `self.validate_jwt_token(...)` or `self.create_jwt_token(...)` on the server.

### 3.2 What was missing

```text
1. Plugin author wants a custom user store (e.g. extra tables, JWT instead of stored tokens).
2. Core JacAPIServer.postinit runs:  self.user_manager = UserManager(base_path=...)
3. ✗ No hook here → plugin cannot replace the class. Only option: subclass the whole server.
4. jac-scale wants a 2nd SSO provider (e.g. GitHub).
5. get_sso() returns GoogleSSO directly; sso_initiate calls sso.get_login_redirect();
   sso_callback calls sso.verify_and_process()   ← Google-library method names baked in
6. ✗ Adding GitHub means editing JacAPIServer and branching on library-specific APIs.
7. User logs in with Google; only `email` is used to find the local user.
8. ✗ No place to record "Google id 12345 belongs to user X", so no way to link several providers.
```

### 3.3 Why it mattered

There is no linked issue. The PR's task list states the goals: a `get_user_manager()` hook in `JacRuntimeInterface`, moving SSO logic "from JacAPIServer (serve.impl.jac:1171-1370) into JacScaleUserManager", an `SSOProvider` abstraction "for easy addition of other vendors (Microsoft, GitHub, SAML, etc.)", and an `sso_accounts` table so users can have "multiple SSO providers linked". The people affected are plugin developers and anyone extending jac-scale auth. App users would not see the change.

## 4. The idea of the fix (one sentence)

> **Make the user manager a pluggable object that owns all auth.** The core asks a hook for the user manager, jac-scale answers with a subclass that holds JWT, SSO and account linking, and the server only forwards requests to it.

This is the right idea because the auth logic is about users, not about HTTP plumbing. Once it lives on the user manager, one hook gives plugins full control, and the `SSOProvider` interface removes the Google-specific calls from the shared code.

### 5.4 `jac-scale/jac_scale/user_manager.jac`: declares `JacScaleUserManager`


**What:** The public shape of the new class.

**Why:** It gives auth a home outside the HTTP server.

**Things to notice:**
- JWT secret, algorithm, expiry and `SSO_HOST` are read **at import time**. `SUPPORTED_PLATFORMS` is read fresh in each `postinit`. This keeps the old split: the old code had a comment saying it loaded SSO credentials fresh "to support env var overrides at runtime". That comment was dropped.
- `has SUPPORTED_PLATFORMS: dict = {}` uses a mutable default. If Jac shared one dict across instances, the `..._without_jac_toml_credentials` test would likely fail after setup builds a configured instance. CI is green, which suggests each instance gets its own dict. That is worth confirming with whoever owns Jac's `has` semantics.
- The top-level import of `GoogleSSOProvider` is unused at runtime, because `get_sso` imports it again locally (see 5.5).
- `validate_token` is overridden to use JWT. Any core code that calls `user_manager.validate_token(...)` now gets JWT checking instead of the base behaviour. The base implementation and its callers are not in this diff.

**What:** The same validation chain as before: `INVALID_PLATFORM` 400, `SSO_NOT_CONFIGURED` 501, `INVALID_OPERATION` 400, `SSO_INIT_FAILED` 500. After that it calls the interface methods. **Why:** These are the provider-neutral flows.

**Things to notice:**
- The `with sso { ... }` context-manager block moved into `GoogleSSOProvider`.
- The new `UNKNOWN_ERROR` fallback only runs if the operation is neither login nor register. That is unreachable after the operation check, but it means the function no longer falls off the end and returns `None`.
- `sso_callback` does **not** call `link_sso_account` or `get_user_by_sso`. `external_id` is returned by the provider but never stored.

**5.5e Account-linking methods (new)**

| Method | Behaviour |
|---|---|
| `link_sso_account(user_id, platform, external_id, email)` | If `(platform, external_id)` already exists: returns `{'message': 'SSO account already linked to this user'}` when it is the same user, or `{'error': '...already linked to another user'}` otherwise. If not, it inserts the row and returns a success dict. |
| `unlink_sso_account(user_id, platform)` | Deletes **all** rows for that user and platform. Returns `{'error': 'SSO account not found'}` if 0 rows were deleted. |
| `get_sso_accounts(user_id)` | Returns a list of `{platform, external_id, email, linked_at}`, newest first. |
| `get_user_by_sso(platform, external_id)` | Joins with `users` and returns `{'email': user_id, 'token', 'root_id'}` or `None`. |

**Things to notice:** No endpoint or flow calls these yet. They are a library API for future use.

### 5.8 `jac-scale/jac_scale/google_sso_provider.jac`: Google wrapper

```diff
+obj GoogleSSOProvider(SSOProvider) {
+    has client_id: str, client_secret: str, redirect_uri: str,
+        allow_insecure_http: bool = True, _google_sso: (GoogleSSO | None) = None;
+    def postinit -> None { self._google_sso = GoogleSSO(...); }
+    async def initiate_auth(operation: str) -> Response {
+        with self._google_sso { return await self._google_sso.get_login_redirect(); } }
+    async def handle_callback(request: Request) -> SSOUserInfo {
+        with self._google_sso {
+            user_info = await self._google_sso.verify_and_process(request);
+            return SSOUserInfo(email=user_info.email, external_id=user_info.id,
+                               platform=self.get_platform_name(),
+                               display_name=user_info?.display_name); } }   # ?. = null-safe
+    def get_platform_name -> str { return "google"; }
+}
```

**What:** Moves the Google-library calls behind the interface. It maps Google's `id` to `external_id`.

**Things to notice:**
- `initiate_auth` ignores its `operation` argument. The operation is already baked into `redirect_uri` by `get_sso`.
- Both methods raise `RuntimeError` if `_google_sso` is missing. That error is caught by `sso_callback`'s `try`, but `sso_initiate` has no `try`.

## 6. How execution flows after the PR

### 6.1 Server startup: choosing the user manager

```text
jac start (jac-scale installed)
├─ jac-scale JacAPIServer constructed
│  └─ core JacAPIServer.postinit
│     └─ Jac.get_user_manager(base_path)                       ← NEW (was UserManager(...))
│        └─ pluggy → JacScalePlugin.get_user_manager            ← NEW hookimpl
│           └─ JacScaleUserManager(base_path)
│              └─ postinit
│                 ├─ super.postinit()  (base users DB)
│                 ├─ CREATE TABLE IF NOT EXISTS sso_accounts   ← NEW
│                 ├─ CREATE INDEX idx_sso_accounts_user_id     ← NEW
│                 └─ fill SUPPORTED_PLATFORMS from config      ← CHANGED (moved from server)
├─ ExecutionManager(user_manager=self.user_manager)
└─ jac-scale postinit: middleware, etc. (SSO config load removed)   ← CHANGED
```

Without jac-scale, `Jac.get_user_manager` returns a plain `UserManager`, the same as before.

### 6.2 Authenticated walker or function call

```text
HTTP POST /walker/... with "Authorization: Bearer <jwt>"
├─ strip "Bearer " → token
├─ self.user_manager.validate_jwt_token(token)                  ← CHANGED (was self.validate_jwt_token)
│  └─ jwt.decode(token, JWT_SECRET, [JWT_ALGORITHM]) → username | None
├─ None → TransportResponse.fail(UNAUTHORIZED)
└─ username → run walker or function
```

## 11. Questions your senior might ask

**Q: Where is the hook spec actually declared? I only see a static method.**
In `JacRuntimeInterface` in `runtime.py`. The diff shows no explicit `@hookspec`, so the method must be turned into a hook by machinery outside the diff (likely around `generate_plugin_helpers`). `test_hooks.py` finds `pm.hook.get_user_manager` with jac-scale's implementation, and CI passed.

**Q: Does the hook return a class or an instance?**
An instance: `JacScaleUserManager(base_path=base_path)`. The guide wrongly shows it returning the class with no arguments.

**Q: What happens if two plugins implement `get_user_manager`?**
The diff doesn't show how `Jac.get_user_manager` resolves several implementations (for example, first result wins). That needs checking in the plugin dispatch code.

**Q: Did any user-visible API behaviour change?**
The HTTP paths, status codes and error codes are the same. Two developer-facing changes: the static `JacAPIServer.create_jwt_token`, `validate_jwt_token` and `refresh_jwt_token` are gone, and `validate_token` on the user manager now does JWT validation under jac-scale.

**Q: What if something gives the jac-scale server a plain `UserManager`?**
Every auth call (`self.user_manager.validate_jwt_token`, `.sso_initiate`, etc.) would raise `AttributeError`. The server now assumes the hook returned a `JacScaleUserManager`.

**Q: Is the `sso_accounts` table used during SSO login?**
No. Login still looks users up by email via `get_user(email)`. `external_id` is returned by `GoogleSSOProvider` but never stored. The link, unlink and lookup methods are tested but have no caller or endpoint yet.

**Q: Does `ON DELETE CASCADE` work?**
Only if the SQLite connection has `PRAGMA foreign_keys=ON`. The base `UserManager` connection setup is not in this diff, so this can't be confirmed from the PR.

**Q: How do I add GitHub SSO now?**
Write a subclass of `SSOProvider` that implements the three methods and returns `SSOUserInfo`. Add `GITHUB` to the `Platforms` enum so validation and config loading pick it up. Add a branch in `JacScaleUserManager.get_sso`. Provider selection is still an `if` chain, not a registry.

**Q: Why were several tests deleted?**
The diff doesn't say. The enum tests and the endpoint-tag assertions were low value. The `USER_CREATION_FAILED` and token-generation tests covered real branches and could be restored as-is against `self.user_manager`.

**Q: When is the JWT config read, and can env changes at runtime take effect?**
`JWT_SECRET`, the algorithm, the expiry and `SSO_HOST` are read once, when `user_manager.jac` is imported (`plugin.jac` imports it at load). SSO client credentials are re-read in every `JacScaleUserManager.postinit`, which keeps the old split.
