## 1. The short version

Jac stores graph nodes and edges in a database. Each stored item has an **anchor**, which is its persistence record. At the end of every request, jac-scale decides which anchors to write back to MongoDB (the main database) and Redis (the cache). Before this PR, that decision used an `is_updated` flag. The flag was set by an `Archetype.__setattr__` hook whenever a field was assigned.

**The flag was wrong in both directions.** Anchors loaded from storage started as `is_updated = True` because that was the class default. So a read-only request like `GetAllTasks` or `GetTask` still re-wrote documents to MongoDB/Redis (issue #5263 shows the `put` logs). The flag also missed changes made without assignment, such as `here.tags.append("urgent")` or `here.metadata["priority"] = "high"`. Those changes stayed in memory and were silently lost.

**Your fix removes the flag and uses hash-based dirty checking instead.** An anchor's serialized state is hashed when it is loaded. At sync time the hash is computed again, and only anchors whose hash changed are written. After a write, the stored hash is refreshed. New anchors start with `hash = 0`, so they always differ and get written.

| Dirty checking | Deciding whether something changed since it was saved. Before: a flag. After: a hash comparison. |

## 3. The problem, step by step

### 3.1 The setup

- **jaclang core:** `Anchor` had `is_updated: bool = True`. `Archetype.__setattr__` set it to `True` on any non-underscore field write. `build_edge`, `remove_edge` and `reset_graph` also set it by hand.
- **jac-scale:** `MongoBackend.sync()` skipped anchors where `not anchor.is_updated`. `ScaleTieredMemory.commit()` used the same flag to build the list of anchors to push to Redis. `MongoBackend.get()`/`query()` reset `is_updated = False` after loading, as a workaround.
- SQLite's `sync()` already used hash-based detection. The removed comment in `memory_hierarchy.main.impl.jac` says so.

### 3.2 What went wrong: case A, read-only request writes

```text
1. Client calls POST /walker/GetAllTasks (read-only).
2. Anchors for root and tasks are loaded from storage and built by the Serializer.
     new Anchor(...)  -> is_updated = True   (class default)
3. Mongo get()/query() reset is_updated = False, but per the PR title and
   issue logs, loads through the Redis L2 cache path still ended up with
   is_updated = True.
4. Walker reads [-->] and reports. No field changes.
5. End of request: commit() -> l2_pending includes anchors with is_updated = True
                   l3.sync() -> put() each anchor with is_updated = True
6. ✗ WRONG: MongoDB update_one and Redis writes happen for unchanged data.
```

The Redis implementation file is not in this diff, so the exact Redis load path is not visible here. The description's "Changes" table says `memory_hierarchy.redis.impl.jac` was edited, but that file is not in the changed-files list.

### 3.3 What went wrong: case B, in-place mutation lost

```text
1. Item loaded: tags = [], anchor.is_updated = False (after reset).
2. Walker runs: here.tags.append("urgent")
     -> list object changed in memory
     -> __setattr__ NOT called (no assignment to here.tags)
     -> is_updated stays False
3. End of request: sync() sees is_updated == False -> skip.
4. ✗ WRONG: "urgent" never reaches MongoDB. The client may even see it in the
   response, because L1 holds it, but after a restart it is gone.
```

The same applies to `dict[k] = v`, `set.add()` and nested object changes. The issue reporter called this out.

### 3.4 Why it mattered

- The reporter of #5263 (title "Saving even no update happens (Reopen)") showed `put` logs firing on `GetAllTasks` and `GetTask`. That is extra database load on every read.
- The reporter also noted that the previous test only checked whether document *contents* changed. It did not check whether an update *command* was issued.
- Silent data loss on `append`/`dict[k]=v` is a correctness bug, which is worse than the performance one.
- The issue also raises a concern about full-document writes to L2/L3 causing races. This PR does not address that. `put()` still `$set`s the whole `data`.

## 4. The idea of the fix (one sentence)

> **Compare snapshots, don't trust a flag.** Hash each anchor's serialized form when it is loaded, hash it again at sync, and write only when the two differ.

This catches every kind of change that shows up in the serialized output, however it happened. It also matches what the SQLite backend already did, so the backends now share one model.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/serializer.jac` + `impl/serializer.impl.jac`: compute and record the hash

```diff
+    static def _compute_hash(anchor: object) -> int;
```
```diff
@@ impl Serializer._deserialize_anchor(...)
+
+        anchor.hash = Serializer._compute_hash(anchor);   # NEW: baseline on load
         return anchor;
@@
+impl Serializer._compute_hash(anchor: Anchor) -> int {
+    import from json { dumps }
+    try {
+        data = Serializer.serialize(anchor, include_type=True);
+        return hash(dumps(data, sort_keys=True));
+    } except Exception {
+        return 0;
+    }
+}
```

**What:** Every anchor built from stored data now carries a hash of its state. `_compute_hash` serializes the anchor, turns it into canonical JSON (`sort_keys=True`), and hashes the string.

**Why:** This gives sync a "last known saved" baseline to compare against. That fixes case A (unchanged means same hash, so no write) and case B (an appended list item changes the JSON, so the hash changes and the anchor is written).

**Things to notice:**
- `hash()` on a Python `str` is randomized per process. That is fine here, because the baseline and the comparison happen in the same process, and every load recomputes the baseline.
- **Failure returns `0`.** If serialization fails both at load and at sync, then `0 == 0` and the anchor is skipped silently. A brand-new anchor whose serialization fails is also never written. Nothing is logged in that branch.
- The description says "hash == 0 (new anchor) → always written". There is no explicit special case in the code. It works only because a successful compute is non-zero (in practice), so it differs from `0`.
- Correctness depends on `Serializer.serialize` including everything that matters (fields, edges) and **not** including `hash` itself. If it included `hash`, the value would change every time you stored it. The unit test's "No mutation → same hash" assertion guards this.
- Whether sets serialize in a stable order can't be seen in this diff. An unstable order would cause extra writes, not lost data.


**What:** `sync()` writes an anchor only when its current hash differs from the stored one. `put()` refreshes the hash after a successful write. The "reset after load" workarounds are gone, because the deserializer now sets the baseline.

**Why:** This is the main fix for MongoDB writes on read-only requests and for lost in-place changes.

**Things to notice:**
- The hash refresh is inside `put()`'s `try`, after `update_one`. If the write throws, the hash stays old, so the anchor is retried on the next sync. That is good behaviour.
- After a successful write, `put()` re-serializes the anchor a second time to get the new hash. It probably serializes once for `data` already. Reusing that output would save work.
- The removal of the `get()`/`query()` resets relies on `_load_anchor` going through `Serializer._deserialize_anchor`. `_load_anchor` isn't in the diff.
- The diff doesn't show an import of `Serializer` being added, so it was presumably already in scope. `test-scale` passes.

## 6. How execution flows after the PR

### 6.1 Loading an anchor

```text
Walker touches a node (e.g. [-->])
└─ MongoBackend.get()/query()  (or Redis L2 load)
   └─ _load_anchor(doc)
      └─ Serializer._deserialize_anchor(data)
         ├─ build Anchor, archetype, edge stubs
         └─ anchor.hash = _compute_hash(anchor)        ← NEW
   └─ (no is_updated reset)                             ← CHANGED (removed)
```

### 6.2 Changing data during a request

```text
here.completed = True        → Archetype.__setattr__ → object.__setattr__ only   ← CHANGED
here.tags.append("x")        → plain list mutation (no hook)
a ++> b (build_edge)         → source/target.edges.append(...)  (no flag)        ← CHANGED
remove_edge                  → nd.edges.pop(idx)                (no flag)        ← CHANGED
```

### 6.3 End-of-request batch commit

```text
ScaleTieredMemory.commit()  (no anchor)
├─ l2_pending = persistent ∧ writable ∧ _compute_hash(a) != a.hash   ← CHANGED
├─ l3.sync()  (MongoBackend.sync)
│  └─ for each L1 anchor
│     ├─ skip if not persistent or no write access
│     ├─ current = _compute_hash(anchor)                               ← NEW
│     └─ if current != anchor.hash
│        └─ put(anchor)
│           ├─ update_one($set data, upsert)
│           └─ anchor.hash = _compute_hash(anchor)                     ← CHANGED
└─ write l2_pending to Redis  (code not in diff)
```

### 6.4 Explicit single-anchor commit (`Jac.commit(anchor)`)

```text
commit(anchor)
├─ return if not persistent / no write access
├─ (no is_updated = True)                                              ← CHANGED
├─ l3.put(anchor)  → writes, then refreshes hash
└─ l2 write (if L2)
```

| Scenario | Before | After |
|---|---|---|
| `GetAllTasks` / `GetTask` (read-only) | Loaded anchors re-written to Mongo/Redis | No writes (verified by `opcounters.update`) |
| `task.title = "new"` | Written | Written |
| `item.tags.append("x")` | **Lost** | Written |
| `item.metadata[k] = v` | **Lost** | Written |
| `set.add`, nested obj change | **Lost** | Should be written if `serialize` reflects it (not tested) |
| New node created | Written (`is_updated` default True) | Written (`hash = 0` differs from computed hash) |
| Serialization throws | Written if flagged | Skipped silently (`0 == 0`) |
| `Jac.commit(anchor)` | Written | Written |

**Behaviour change users will notice:** in-place collection edits now persist without workarounds. Users who previously reassigned a list (`here.tags = here.tags + [x]`) to force a save can keep doing so; it still works.

## 11. Questions your senior might ask

**Q: Why hashing instead of fixing the flag default to `False`?**
A flag can't see in-place mutations like `list.append` or `dict[k]=v`, because no `__setattr__` call happens. Your first commit (`d78b638`) tried "mark deserialized anchors clean"; commit `c7fd8d8` switched to hashing to fix both bugs with one mechanism.

**Q: Python's `hash()` of strings is randomized per process. Is that a problem?**
No. The baseline is computed when the anchor is loaded, and the comparison happens in the same process. Each new process recomputes the baseline on load.

**Q: What does this cost in performance?**
Each loaded anchor is serialized and JSON-dumped once on load, about twice at commit (the L2 pending list and `sync()`), and once more per actual write in `put()`. This trades database writes for CPU. No benchmark is in the PR.

**Q: What happens if serialization throws?**
`_compute_hash` returns `0`. If that happens both at load and at sync, the anchor is considered clean and is **not** written, with nothing logged.

**Q: Why build `l2_pending` before `l3.sync()`?**
`put()` overwrites `anchor.hash` after writing. If you built the list afterwards, every anchor would look clean and Redis would never get the update.

**Q: How are new nodes still saved?**
New anchors have `hash = 0`. The computed hash is non-zero in practice, so they differ and get written. There is no explicit "new anchor" branch.

**Q: How do edge changes get saved now that `build_edge`/`remove_edge` don't set a flag?**
`edges.append`/`pop` change the node's serialized form, so its hash changes. This assumes `Serializer.serialize` includes edges; the serializer body isn't in the diff, but the tests pass with node creation via `++>`.

**Q: Does your read-only test really prove zero writes?**
It checks MongoDB's server-wide `opcounters.update` before and after 3 read-only calls and requires no change. It does not measure Redis writes directly.

**Q: Did the Redis implementation change?**
Not in this diff. The description says it did, but no `memory_hierarchy.redis.impl.jac` appears in the changed files. Redis behaviour changes only through `commit()`'s hash-based `l2_pending` list.

**Q: Is removing `Anchor.is_updated` a breaking change?**
Yes, for any external code that reads it. Within the repo, CI passes, but the diff can't show whether other packages reference it.
