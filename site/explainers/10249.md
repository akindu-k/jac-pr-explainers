## 1. The short version

In the 0.34.x line, jac-scale stores each node or edge ("anchor") in three tiers. L1 is a per-request dict in memory. L2 is Redis, shared by all pods. L3 is MongoDB, the source of truth. A read that misses L1 tries Redis, then Mongo, and copies what it found back into Redis. A write goes to Mongo at commit time, and then Redis is updated.

**On three paths, Redis was written with a request's own copy of an anchor, and that copy could be older than what Mongo held. Every later read from every pod then returned the stale value.**

- **A, field update:** Mongo got only the changed fields, but Redis got the whole in-memory anchor. A field that another request had just committed went back to its old value in Redis.
- **B, late refill:** a reader fetched from Mongo and then did an unconditional `SET` in Redis. A write that finished between the read and the `SET` was overwritten.
- **C, re-save:** `save()` and similar calls pushed the request's copy into Redis right away, before commit.

The reporter's example: Mongo holds `pointer = "sandbox-one"`, but Redis and a fresh pod read `pointer = ""`.

**You fixed this in three ways:**

1. A field-update commit now *invalidates* the Redis key instead of writing it.
2. A cache refill is only allowed to land if it holds a short Redis "lease" that no write has cancelled since the read began.
3. `ScaleTieredMemory.put` no longer touches Redis before commit.

The PR targets `release/jaclang-0.34.24-prep`, because `main` no longer has this Mongo/Redis design.

## 3. The problem, step by step

### 3.1 The setup

- Pods P1 and P2 each have their own L1 and share Redis and Mongo.
- Before the PR:
  - `ScaleTieredMemory.commit` called `self.l2.put(intent.anchor)` for every intent except deletes and edge deltas.
  - `get` and `batch_get` on a Redis miss read Mongo and then called `l2.put(anchor)` with no condition.
  - `ScaleTieredMemory.put` called `TieredMemory.put`, which writes to Redis immediately.
- The witness node starts as `pointer="" stamp="seed"` in Mongo and Redis.

### 3.2 What went wrong — A: field-only commit publishes a stale full anchor

```text
1. P1 loads witness            P1.L1 = {pointer:"",  stamp:"seed"}
2. P2 loads witness            P2.L1 = {pointer:"",  stamp:"seed"}
3. P2 sets stamp               P2.L1 = {pointer:"",  stamp:"second-request"}
4. P1 sets pointer             P1.L1 = {pointer:"sandbox-one", stamp:"seed"}
5. P1 commits (FIELD_UPDATE)   Mongo = {sandbox-one, seed}
                               Redis = {sandbox-one, seed}
6. P2 commits (FIELD_UPDATE)   Mongo = {sandbox-one, second-request}   (only stamp written)
                               Redis = {"", second-request}   ← WRONG: P2's whole stale anchor
7. Fresh pod reads             gets {"", second-request} from Redis; Mongo disagrees
```

### 3.3 What went wrong — B: late cache refill

```text
1. Redis has no witness key (evicted or invalidated)
2. Reader misses Redis, reads Mongo        reader holds {"", seed}
3. Writer commits pointer="sandbox-two"    Mongo = {sandbox-two, seed}; Redis key deleted
4. Reader SETs its Mongo copy into Redis   Redis = {"", seed}   ← WRONG: older than Mongo
5. Fresh pod reads                          gets {"", seed}
```

This affects `get` and `batch_get`, and also `execute_plan` (the description says it filled Redis too; the base code is not in the diff).

### 3.4 What went wrong — C: unchanged re-save before commit

```text
1. Stale pod loads witness                 stale.L1 = {"", seed}
2. Writer loads, sets pointer, commits     Mongo = {sandbox-three, seed}; Redis updated or cleared
3. Stale pod calls save(witness), no edits
   → ScaleTieredMemory.put → TieredMemory.put
                                           Redis = {"", seed}   ← WRONG: written before commit
4. Stale pod commits                       nothing changed → no intent → Redis never corrected
5. Fresh pod reads                          gets {"", seed}
```

The description lists the callers of `put` on already-loaded anchors: `save()`, `perm_grant`, `allow_root`, `object_ref` and serializer ref mode.

### 3.5 Why it mattered

- Mongo stayed correct, but Redis serves every later read from every pod. Users would see a field "revert" with no error. The issue's schedules show commits returning without errors while Redis held the old value.
- The issue (#9840) reproduced A and B on the official v0.34.20 and v0.34.21 binaries, with real Mongo 7.0.43 and Redis 7.4.11.
- The issue explicitly does **not** claim this caused jacBuilder#2152.
- Your later run (fork run 39414089086) showed that the earlier attempt (#10046) still missed path C and `aput`.

## 4. The idea of the fix (one sentence)

> **Only Mongo-confirmed data may enter Redis, and a refill may land only if no write happened since it started reading.** Field updates drop the Redis key, re-saves stay in L1 until commit, and refills go through a lease that every write cancels.

This works without adding version numbers to anchors, because it handles each race at the moment Redis is written. The edge-delta path (#6297) already proved the invalidate-and-broadcast pattern in this code.

```diff
+impl RedisBackend.lease(ids: list[UUID]) -> dict[UUID, str] {
+    leases = {id: uuid4().hex for id in ids};
+        pipe = self.redis_client.pipeline(transaction=False);
+        for (id, token) in leases.items() {
+            pipe.set(_lease_key(storage_key(to_uuid(id))), token, px=_REFILL_LEASE_MS, nx=True);
+        }
+        taken = pipe.execute();
+    except → return {}                                  # Redis down: no leases, no fills
+    return {id: leases[id] for (id, ok) in zip(leases, taken) if ok};
+}
+
+impl RedisBackend.fill(anchor: Anchor, token: (str | None)) -> None {
+    if self.redis_client is None or token is None { return; }   # no lease → never write
+    span = start_memory_span("memory.put redis", {...});
+        self.put_count += self.redis_client.eval(
+            _FILL_IF_LEASED, 2, key, _lease_key(key), token, data, ttl
+        );                                               # adds 1 only if it landed
+    finally { end_memory_span(span); }
+}
+
+impl RedisBackend.release(leases: dict[UUID, str]) -> None {
+        for (id, token) in leases.items() {
+            pipe.eval(_RELEASE_IF_LEASED, 1, key, token);   # delete only my own lease
+        }
+}
```

**What:**
- **`lease`:** tries to take a lease for each id with `SET NX`. It returns only the ids it actually got. A second, concurrent reader gets nothing.
- **`fill`:** writes the anchor only if the lease key still holds this reader's token. The check, the lease delete and the `SET` all happen atomically in one Lua script.
- **`release`:** removes a lease, but only if it is still this reader's, so it never deletes another reader's lease.
- **`put`, `aput` and `delete`:** always remove the lease in the same step as their write.

**Why:** This closes path B. Any write between "lease taken" and "fill" deletes the lease, so the old snapshot is rejected.

**Things to notice:**
- The `put` and `aput` pipelines use the redis-py default `pipeline()`, which is transactional (MULTI/EXEC). So the value and the lease delete apply together. `lease` and `release` use `transaction=False` because each command is independent.
- Field-update commits call `l2.invalidate`, not `delete`, and `invalidate`'s code is not in the diff. The "delayed get/batch_get refill" rows only pass if invalidate also clears the lease. So it most likely calls `delete`, but you should confirm this before presenting.
- `put_if_exists` (declared on `RedisBackend`) was not changed. From the diff I can't tell whether it is called on a path that should also cancel a lease.
- Script caching: `EVAL` sends the script text on every refill. Claude review F2 on #10046 suggested `register_script`, and you chose not to change it.
- Errors in `fill` and `release` are logged at debug level and swallowed. A failed fill only means a later Redis miss.

**What:**
1. `put` now only updates L1.
2. A field-update commit drops the Redis key and broadcasts the invalidation, the same way deletes and edge deltas already did.
3. `get` and `batch_get` take a lease before reading Mongo, release it if they found nothing or crashed, and otherwise refill through `fill`.
4. `execute_plan` no longer refills Redis at all.

**Why:**
- Change 1 fixes path C.
- Change 2 fixes path A.
- Changes 3 and 4 fix path B.

**Things to notice:**
- **Leasing order.** The lease is taken *before* the Mongo read. This is what makes the scheme safe: any writer that changes Mongo after the read must clear Redis afterwards, which cancels the lease.
- **Creates.** Creates and other non-delete, non-field-update intents still go through the existing `l2.put` (write-through after Mongo). The "Not covered" section says two concurrent creates or upserts can still reach Redis in a different order from Mongo.
- **`get` bypasses `super.get` on the Redis-hit and Mongo-miss paths.** Any side effects of `TieredMemory.get` on those paths (tracing, counters) are not visible in this diff. Check that nothing is lost.
- **`execute_plan` uses `setdefault`.** If L1 already has the anchor, the request's existing (possibly dirty) copy is returned, not the fresh Mongo one. The base `TieredMemory.execute_plan` is untouched, per reviews on #9911 and #10046.
- **No lease without L3.** When there is no L3, `get` returns early and `batch_get` checks `self.l3`. This matches Claude review F1 on #10046.

## 6. How execution flows after the PR

### 6.1 Reading one anchor (`ScaleTieredMemory.get`)

```text
get(id)
├─ _refresh_if_stale(id)
├─ no L2, no L3, or id in L1? → super.get(id)                        (unchanged)
├─ Redis hit? → store in L1 → return                                  ← CHANGED (done here, not in super)
└─ Redis miss                                                         ← NEW path
   ├─ lease([id])  SET lease:anchor:<id> token NX PX 10000
   │   └─ another reader holds it → no token
   ├─ Mongo get
   │   └─ None or exception → release(lease) (compare-and-delete)
   ├─ None → return None
   ├─ store in L1
   ├─ fill(anchor, token)
   │   ├─ token None → skip
   │   ├─ lease still mine → DEL lease, SET key, put_count += 1
   │   └─ lease gone (a write happened) → reject, put_count += 0
   └─ return anchor
```

### 6.2 Reading many anchors (`batch_get`)

```text
batch_get(ids)
├─ L1 and Redis lookups (unchanged) → l2_misses
└─ l2_misses and L3
   ├─ lease(l2_misses)                                                ← NEW
   ├─ try: Mongo batch_get (or per-id get)
   ├─ finally: release leases for ids Mongo did not return            ← NEW
   └─ for each found: L1 ← anchor; fill(anchor, token)                ← CHANGED (was put)
```

### 6.3 Query (`execute_plan`)

```text
execute_plan(plan)                                                    ← NEW override
├─ no L3 → nothing
└─ for each Mongo result: yield L1.setdefault(id, anchor)              (Redis untouched)
```

### 6.4 Saving and committing

```text
save()/perm_grant/allow_root/object_ref/serializer ref
└─ ScaleTieredMemory.put → L1 only, _committed = False                ← CHANGED

commit()
└─ for each intent
   ├─ delete or FIELD_UPDATE → Mongo write → l2.invalidate + publish_invalidation  ← CHANGED (FIELD_UPDATE added)
   ├─ edge delta → invalidate (unchanged since #6297)
   └─ create / other → Mongo write → l2.put (SET + DEL lease in one transaction)  ← CHANGED (lease cleared)
```

### 6.5 Scenarios

| Scenario | Before | After |
|---|---|---|
| Two requests update different fields | Redis gets the later request's full stale anchor | Redis key deleted; next read loads Mongo |
| Write lands between a reader's Mongo read and its refill | Old snapshot overwrites Redis | Lease cancelled; refill rejected |
| Unchanged `save()` after another pod committed | Stale copy written to Redis, never fixed | Redis untouched |
| `put` or `aput` while a refill is leased | Stale refill could overwrite the newer value | Lease cleared; refill rejected |
| Mongo miss or error on a refill | (no lease concept) | Lease released, so later refills work |
| Two concurrent misses on one key | Both SET | Only the first fills; the other reads Mongo without filling |
| Query via `execute_plan` | Results also written to Redis (per the description) | L1 only |
| Concurrent creates or upserts | Can diverge | Can still diverge (not covered) |

**Behaviour changes users may notice:**
- After any field update, the next read of that anchor from every pod is a Redis miss followed by a Mongo read. This adds Mongo load on hot, frequently updated nodes.
- Query results no longer warm Redis.
- A crashed reader's lease blocks refills of that key for up to 10 s. Reads still succeed.

## 11. Questions your senior might ask

**Q: Why not add a version number to anchors and do CAS on the version instead?**
A: The lease guards the exact window that was broken (read → refill) without changing the anchor format or Mongo documents. Field updates and re-saves are handled by simply not writing to Redis from request-local copies.

**Q: Why invalidate on field updates instead of writing the merged anchor?**
A: The request only knows its own dirty fields. Mongo is the only place with the merged result. Invalidating forces the next reader to load the merged anchor from Mongo, which is the same pattern edge deltas have used since #6297.

**Q: What is the performance cost?**
A: Every field update causes one Mongo read per anchor on the next access, plus a lease `SET NX` and a Lua `EVAL` on each Redis miss. `execute_plan` no longer warms Redis. The PR includes no benchmarks.

**Q: What happens if a reader crashes holding a lease?**
A: The lease expires after 10 s (`_REFILL_LEASE_MS`). Until then other readers still read Mongo correctly but cannot refill Redis.

**Q: Can a stale refill still slip through?**
A: The lease is taken before the Mongo read, and every Redis write path (`put`, `aput`, `delete`, and invalidate through delete) removes it. So any write that commits to Mongo after the read and then touches Redis cancels the fill. The unchanged `put_if_exists` and the concurrent create/upsert ordering are not addressed by this PR.

**Q: Why does `ScaleTieredMemory.get` reimplement the miss path instead of calling `super.get`?**
A: The lease has to be taken between the Redis miss and the Mongo read, which `TieredMemory.get` does not allow for. Overriding keeps the base class unchanged for non-scale backends.

**Q: Why is `execute_plan` L1-only?**
A: Its ids aren't known until Mongo returns, so no lease can be taken before the read. Filling Redis without a lease would reopen path B.

**Q: Does `put` becoming L1-only break anything that expected `save()` to reach Redis early?**
A: The data still reaches Mongo, and Redis for creates, at commit. All 173 scale data tests passed in fork run 39415090456. Beyond that, the diff doesn't show whether any caller relied on an uncommitted value being visible in Redis.

**Q: Why target `release/jaclang-0.34.24-prep` and not `main`?**
A: Per the description, `main` replaced the Mongo/Redis hierarchy (#7947, #8000), so these code paths no longer exist there.

**Q: Is this validated across processes?**
A: No. The tests use separate contexts in one process sharing real Mongo and Redis, just like the issue's fixture. The issue lists cross-process validation as still pending.
