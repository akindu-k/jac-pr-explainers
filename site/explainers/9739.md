# fix(scale): Prometheus scrapes every app pod and gateway replica (#9672)

## In short
When monitoring was on, Prometheus only scraped one fixed address, `gateway-service`. So metrics from the app pods never arrived, and the Grafana request panels stayed empty. Prometheus also reached only one gateway replica. You changed Prometheus to discover pods itself and scrape every gateway and app pod.

## Words to know
- **Prometheus**: a tool that collects numbers (metrics) by calling a `/metrics` URL on many targets every few seconds.
- **Scrape**: one call by Prometheus to a target's `/metrics` URL to read its metrics.
- **Scrape target**: an address Prometheus scrapes.
- **Static target (`static_configs`)**: a fixed address written in the config.
- **`kubernetes_sd_configs`**: "service discovery". Prometheus asks Kubernetes for a list of objects (here pods) and makes targets from them.
- **`role: pod`**: discover each pod as its own target.
- **Relabel config**: rules that filter discovered targets (`action: keep`) or set labels on them (`target_label`).
- **Pod**: the smallest running unit in Kubernetes. A replica is one copy of a pod.
- **Service**: a stable Kubernetes address that forwards traffic to one of several pods.
- **`sessionAffinity: ClientIP`**: a Service setting that sends the same client always to the same pod. Here the "client" is Prometheus, so it hit only one gateway replica.
- **Gateway**: the jac-scale component in front of the app and microservices. It exposes its own `gateway_*` metrics.
- **Grafana**: the dashboard tool that draws charts from Prometheus data.
- **Counter rate**: counters like `*_http_requests_total` only go up. Rates are computed from consecutive readings of the same pod, so mixing pods gives wrong numbers.
- **Basic auth / `password_file`**: the username and password Prometheus sends to `/metrics`, read from a mounted secret file.
- **ClusterProvider**: a class with per-cloud behaviour (`AWSProvider`, `LocalProvider`).
- **ClusterRole**: Kubernetes permissions. Prometheus's already allows listing and watching pods.

## The problem
1. `KubernetesTarget._deploy_observability` called `monitoring.deploy(...)` with `scrape_target_service="gateway-service"`.
2. The Prometheus config then had one static target: `gateway-service:<port>`.
3. The gateway's `/metrics` only serves `gateway_*` metrics. The app pods' series (`*_http_requests_total`, `*_http_request_duration_seconds`, `*_walker_duration_seconds`) were never scraped. The Grafana request, latency and walker panels were empty.
4. `gateway-service` has `sessionAffinity: ClientIP`, so Prometheus always landed on the same gateway replica. The other replicas were never scraped.

## The changes, one by one
### `monitoring.jac`
This is the core change.

- You split the config-building code out of `_deploy_prometheus` into a new method, `_scrape_config(app_name, namespace) -> str`. This makes the YAML testable on its own.
- The app job no longer uses `static_configs`. It now uses pod discovery limited to the deploy namespace:

```
"    kubernetes_sd_configs:\n"
"      - role: pod\n"
"        namespaces:\n"
f"          names: ['{namespace}']\n"
```
  Prometheus lists pods in that namespace only and makes one target per pod.
- `metrics_path` and `basic_auth` are kept, so the same credential is used.
- New `relabel_configs`:
  - A `keep` rule requires the pod labels `managed=jac-scale` and `jac-scale.role` to match `jac-scale;(gateway|microservice)`. Other pods (like Prometheus itself) are dropped.
  - A second `keep` rule keeps only the container port equal to `container_port`.
  - Three label rules copy the pod's role, `app` label and pod name to the target labels `role`, `app` and `pod`.
- There is deliberately no `service` target label. It would shadow the gateway's own `service` label, which the admin Services page groups by.
- `_deploy_prometheus` and `deploy` lose the `provider` and `scrape_target_service` parameters. `_deploy_prometheus` now calls `self._scrape_config(...)`. The `ClusterProvider` import is removed, since it is unused.

Why pods and not each app's Service: a Service with several replicas sends each scrape to a random pod, which breaks counter rates. Pods scaled to zero just disappear as targets.

### `target.jac`
`_deploy_observability` now calls `monitoring.deploy(app_name, obs_config.namespace, apps_v1, core_v1)`. The hard-coded `scrape_target_service="gateway-service"` and `provider` are gone.

### `cluster_provider.jac`
You removed `prometheus_scrape_port` from the abstract `ClusterProvider`, `AWSProvider` and `LocalProvider`. Both providers just returned `container_port`, and the only caller was the old static target.

### `release_notes/unreleased/jaclang/9739.bugfix.md`
A one-line release note: the Grafana request panels now show data because Prometheus scrapes every app and gateway replica.

## How it runs now
1. `KubernetesTarget._deploy_observability` builds a `MonitoringDeployer` and calls `deploy(app_name, namespace, apps_v1, core_v1)` (changed: fewer arguments).
2. If monitoring is enabled, `deploy` may deploy kube-state-metrics and node-exporter, then calls `_deploy_prometheus` (changed signature).
3. `_deploy_prometheus` calls `_scrape_config` (new) to build the YAML.
4. The YAML is hashed and put in the Prometheus ConfigMap, as before.
5. At run time, Prometheus lists pods in the namespace (changed), keeps gateway and microservice pods on the app port, and scrapes each one with basic auth (changed).
6. Series now carry `role`, `app` and `pod` labels (new), and Grafana panels get data from app pods.

## Tests
- **New** `"prometheus scrapes every gateway and app pod in the fleet"` in `test_monitoring_switch.jac`. It builds a `MonitoringDeployer` with `container_port=8000`, calls `_scrape_config("t", "t-ns")` and parses the YAML. It checks that:
  - the app job has no `static_configs`;
  - `kubernetes_sd_configs` is exactly `role: pod` limited to `t-ns`;
  - `password_file` is the secret path;
  - the two `keep` rules have the expected labels and regexes (`jac-scale;(gateway|microservice)` and port `8000`);
  - the target labels are `["role", "app", "pod"]`.
  
  This proves the discovery scope, filters, credential and labels.
- **Changed** `test_cluster_provider.jac`: you removed the four `prometheus_scrape_port` assertions, since the method no longer exists. The rest is unchanged.

## Explaining it in one minute
Prometheus was only scraping `gateway-service`, a single static target. App pod metrics never reached it, so the Grafana request panels were empty. Session affinity also meant only one gateway replica was seen. I switched the app's Prometheus job to Kubernetes pod discovery in the deploy namespace. It keeps only jac-scale gateway and microservice pods on the app port, and it uses the same basic-auth credential. I chose pods over Services because a Service would hit a random replica and break counter rates. I removed the unused `scrape_target_service` and `provider` parameters and `prometheus_scrape_port`. I tested it by splitting out `_scrape_config` and adding a test that parses the YAML and checks the scope, filters, credential and labels. One caveat from the description: with more than one serve worker, app pod `/metrics` may still be empty until #9671 is fixed.
