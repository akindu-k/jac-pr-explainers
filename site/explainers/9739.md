# fix(scale): Prometheus scrapes every app pod and gateway replica (#9672)

[#9739](https://github.com/jaseci-labs/jac/pull/9739) by @akindu-k · opened 3 Oct 2026 · +62 −48 in 6 files

<!-- explainer -->

## In short

Before this PR, Prometheus scraped only one fixed address, `gateway-service`. The app pods were never scraped, so the Grafana request, latency and walker panels stayed empty. Because of session affinity, only one gateway replica was ever scraped too. You replaced the fixed address with Kubernetes pod discovery, so Prometheus now finds and scrapes every gateway and microservice pod in the app's namespace. You also removed the parameters and the provider method that only existed to build the old fixed address.

## Words to know

- **Prometheus**: A monitoring server. It regularly sends an HTTP request to each "target" (a URL, usually `/metrics`), reads the numbers it gets back, and stores them as time series. jac-scale deploys one per app when `[scale.monitoring]` is on.
- **Scrape / scrape target / scrape job**: A *scrape* is one of those requests. A *target* is one address being scraped. A *job* is a named group of targets in the Prometheus config. Here the job is named after the app.
- **Scrape config**: The YAML file that tells Prometheus what to scrape. jac-scale builds it as a string in `monitoring.jac` and stores it in a Kubernetes ConfigMap.
- **`static_configs`**: A Prometheus setting that lists target addresses by hand. The old config used this with one address.
- **`kubernetes_sd_configs` / service discovery**: A Prometheus setting that asks the Kubernetes API for objects and turns them into targets automatically. With `role: pod`, each pod (more exactly, each declared container port of each pod) becomes a candidate target. The target list updates as pods come and go.
- **Relabeling (`relabel_configs`)**: Rules Prometheus runs on each discovered target before scraping. `action: keep` drops every target whose labels don't match a regex. `target_label` copies a value into a label that is attached to every series from that target.
- **`__meta_kubernetes_*` labels**: Temporary labels that discovery gives each target, such as the pod's name, its Kubernetes labels and its port number. Characters like `-` and `.` in Kubernetes label names become `_`. So the pod label `jac-scale.role` appears as `__meta_kubernetes_pod_label_jac_scale_role`.
- **Kubernetes Pod / Service / replica**: A *pod* is one running copy of a container. *Replicas* are several pods of the same app. A *Service* is one stable address that forwards each request to one of those pods.
- **`sessionAffinity: ClientIP`**: A Service setting that always sends the same client IP to the same pod. Prometheus is a single client, so it always reached the same gateway pod.
- **Gateway**: The jac-scale component that receives outside traffic and routes it to app pods (microservices). It has its own `/metrics` with `gateway_*` series.
- **Microservice pod**: A pod running the app itself. It produces the `*_http_requests_total`, `*_http_request_duration_seconds` and `*_walker_duration_seconds` series that the Grafana panels query.
- **Counter rate**: Prometheus counters only go up. Graphs use `rate()` to turn them into "per second" values. If successive scrapes hit different pods, the counter seems to jump up and down, and the rate comes out wrong.
- **Grafana**: The dashboard tool that draws graphs from Prometheus queries.
- **Basic auth / scrape credential**: A username and password sent with each scrape. The password is read from a mounted secret file, `/etc/prometheus/scrape-secret/password`.
- **ClusterRole**: A Kubernetes permission set. Prometheus needs permission to "list/watch pods" so that pod discovery works.
- **`ClusterProvider`**: A jac-scale abstract class with one implementation per cluster type (`AWSProvider`, `LocalProvider`). It answers questions like "which port should Prometheus scrape?"

## The problem

1. When you deploy to Kubernetes with monitoring on, `KubernetesTarget._deploy_observability` calls `MonitoringDeployer.deploy(...)` with `scrape_target_service="gateway-service"`. That value was added in #6884 because the earlier default, `{app_name}-service`, did not exist.
2. `_deploy_prometheus` built a scrape config with exactly one target: `gateway-service:<port>`. The port came from `provider.prometheus_scrape_port(...)`.
3. That caused two problems:
   - **App pods were never scraped.** The series the Grafana request panels query live on the app pods, not on the gateway. So those panels were always empty.
   - **Only one gateway replica was scraped.** `gateway-service` uses `sessionAffinity: ClientIP`, so Prometheus always landed on the same gateway pod. The other replicas' `gateway_*` metrics were never collected.

Example: an app with 2 gateway replicas and 3 microservice pods. Before, Prometheus saw 1 of the 5 pods, and none of the microservice pods. After, it sees all 5.

Everyone using `[scale.monitoring]` on a Kubernetes deployment was affected (issue #9672).

## The changes, one by one

### `jac/jaclang/scale/deploy/target/kubernetes/monitoring.jac`

This is the core of the fix.

**1. Building the config now has its own method, `_scrape_config(app_name, namespace) -> str`.** Before, the YAML was built inline inside `_deploy_prometheus`. Moving it out lets a test generate and check the config without any Kubernetes calls. `_deploy_prometheus` now just calls it:

```jac
def _deploy_prometheus(app_name: str, namespace: str, apps_v1: any, core_v1: any) {
    prometheus_name = f"{app_name}-prometheus";
    scrape_config = self._scrape_config(app_name, namespace);
    config_hash = hashlib.md5(scrape_config.encode()).hexdigest()[:12];
```

- Line 1: the `provider` and `scrape_target_service` parameters are gone.
- Line 3: the config string now comes from the new method.
- Line 4: the config hash is computed as before. The rest of the function, which creates the ConfigMap and Deployment, is not in the diff and seems unchanged.

The extra jobs for kube-state-metrics and node-exporter, added when `k8s_metrics_enabled` is on, are still appended inside `_scrape_config`. The diff only shows the start and end of that block.

**2. The app job now uses pod discovery instead of one fixed target.**

```yaml
  - job_name: '{app_name}'
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: ['{namespace}']
```

- `role: pod`: discover pods.
- `namespaces.names`: only look in the app's own namespace, not the whole cluster.

`metrics_path: '/metrics'` and the `basic_auth` block (the admin username plus the password file) are kept, so each pod is scraped with the same credential as before.

**3. Relabel rules filter targets and set labels.**

```yaml
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_managed, __meta_kubernetes_pod_label_jac_scale_role]
        regex: 'jac-scale;(gateway|microservice)'
        action: keep
      - source_labels: [__meta_kubernetes_pod_container_port_number]
        regex: '{container_port}'
        action: keep
      - source_labels: [__meta_kubernetes_pod_label_jac_scale_role]
        target_label: role
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
```

- **Rule 1:** Prometheus joins the two label values with `;` and keeps the target only if the result is `jac-scale;gateway` or `jac-scale;microservice`. In other words, the pod must have the label `managed=jac-scale` and the label `jac-scale.role` set to `gateway` or `microservice`. This drops everything else, including Prometheus, Grafana, Redis-type pods and the exporters.
- **Rule 2:** Pod discovery creates one target per declared container port. This keeps only the app's `container_port` (for example 8000), so a pod isn't scraped on a port that has no `/metrics`.
- **Rules 3–5:** Copy the role, the `app` label and the pod name into labels `role`, `app` and `pod` on every series. Each pod's data stays separate, so counter rates are correct.

**No `service` target label on purpose.** The gateway's metrics already carry their own `service` label, which the admin Services page groups by. If Prometheus attached a target label with the same name, it would clash with the gateway's label. By default, Prometheus renames the scraped label to `exported_service`, which would break that grouping.

**4. `deploy(...)` has a shorter signature:** `deploy(app_name, namespace, apps_v1, core_v1)`. It passes the same four arguments to `_deploy_prometheus`.

**5. The `ClusterProvider` import is removed**, because this file no longer uses it.

**Why pods and not each app's Service:** A Service with several replicas sends each scrape to a random pod. A counter then looks like it keeps resetting or jumping, and `rate()` gives wrong numbers. Scraping pods directly avoids that. Pods scaled to zero simply drop out of the target list.

**Why requests are not counted twice:** This comes from your description; the gateway code is not in this diff. The gateway's `/metrics` serves only its `gateway_*` metrics. Its own HTTP request collector is used only in-process for `/admin/metrics`. So `{prefix}_http_*` series come only from app pods, and the existing Grafana queries still count each request once. That is why the dashboards were left unchanged.

### `jac/jaclang/scale/deploy/target/kubernetes/target.jac`

```jac
monitoring.deploy(app_name, obs_config.namespace, apps_v1, core_v1);
```

The call no longer passes `provider` or `scrape_target_service="gateway-service"`. This removes the hard-coded single target at its source.

### `jac/jaclang/scale/deploy/target/kubernetes/cluster_provider.jac`

You removed the abstract method `prometheus_scrape_port(container_port) -> int` from `ClusterProvider`, along with its two implementations in `AWSProvider` and `LocalProvider`. Both just returned `container_port`. Its only caller was the old static target line. Pod discovery reads the port from `self.k8s_config.container_port` directly, so the hook had no remaining use.

## How it runs now

1. You run a Kubernetes deploy with monitoring enabled. `KubernetesTarget._deploy_observability` creates `MonitoringDeployer(obs_config, logger)`.
2. It calls `monitoring.deploy(app_name, namespace, apps_v1, core_v1)` with no provider and no scrape target. **(changed)**
3. If `k8s_metrics_enabled`, `deploy` first deploys kube-state-metrics and node-exporter. This step is unchanged.
4. `deploy` calls `_deploy_prometheus(app_name, namespace, apps_v1, core_v1)`. **(changed signature)**
5. `_deploy_prometheus` calls `_scrape_config(app_name, namespace)`, which returns YAML with a pod-discovery job for the app. **(new)**
6. `_deploy_prometheus` hashes the config, writes it into the Prometheus ConfigMap and deploys Prometheus. This is unchanged as far as the diff shows.
7. At runtime, Prometheus asks the Kubernetes API for pods in the app's namespace, using its existing ClusterRole permission to list/watch pods. **(new)**
8. For each pod and port, it applies the relabel rules. It keeps only `managed=jac-scale` pods with role `gateway` or `microservice`, on `container_port`, and adds the `role`, `app` and `pod` labels. **(new)**
9. It scrapes `http://<pod-ip>:<container_port>/metrics` on each kept pod with basic auth. This means every gateway replica and every app replica is scraped separately. **(changed)**
10. Grafana's request panels query the `{prefix}_http_*` and walker series, which now exist because app pods are scraped. The queries themselves are unchanged.

## Tests

**`tests/deploy/test_monitoring_switch.jac`: new test "prometheus scrapes every gateway and app pod in the fleet"**

- **Setup:** creates a `MonitoringDeployer` with `KubernetesConfig(app_name="t", namespace="t-ns", container_port=8000)`, calls `_scrape_config("t", "t-ns")` and parses the result with `yaml.safe_load`. No cluster is needed.
- **Checks:**
  - The `t` job has no `static_configs`, so the old single target is gone.
  - `kubernetes_sd_configs` is exactly `role: pod`, limited to namespace `t-ns`.
  - `basic_auth.password_file` is still the scrape secret path.
  - The `keep` rules are exactly two: the `managed` plus `jac_scale_role` rule with regex `jac-scale;(gateway|microservice)`, and the port rule with `"8000"`.
  - The target labels are exactly `["role", "app", "pod"]`, in that order. This also proves no `service` label was added.
- **What it proves:** the generated config discovers the right pods, filters them correctly, keeps the credential and does not add a clashing `service` label.
- **What it does not cover:** it does not run Prometheus or check the Grafana queries.

## Explaining it in one minute

"Our Prometheus config had one fixed target, `gateway-service`. So it never scraped the app pods, which are where the request, latency and walker metrics live. That's why those Grafana panels were empty. And because that Service uses ClientIP session affinity, Prometheus only ever hit one gateway replica. I switched the app's scrape job to Kubernetes pod discovery in the deploy namespace. It keeps only jac-scale pods with role gateway or microservice, on the container port, uses the same basic-auth credential, and labels each series with role, app and pod. I scrape pods instead of Services because a multi-replica Service sends each scrape to a random pod, which breaks counter rates. I left out a `service` target label so it doesn't clash with the gateway's own `service` label that the admin page groups by. Dashboards didn't need to change: the gateway's `/metrics` only exposes `gateway_*`, so HTTP request series come only from app pods and aren't double counted. I removed the now-unused `scrape_target_service` and `provider` parameters and `prometheus_scrape_port`. I added a test that parses the generated YAML and checks the discovery scope, filters, credential and labels. One known gap: with more than one serve worker, app pod `/metrics` can still be empty until #9671 is fixed."
