## 1. The short version

When an app is deployed with jac-scale and `[scale.monitoring] enabled = true`, jac-scale also deploys a Prometheus server. Prometheus collects metrics by "scraping" HTTP `/metrics` endpoints. The Grafana dashboards and the admin Services page then read from Prometheus.

**Before this PR, Prometheus had exactly one scrape target: the static address `gateway-service:<port>`. The app pods were never scraped.** Series such as `*_http_requests_total`, `*_http_request_duration_seconds` and `*_walker_duration_seconds` exist only on app pods, so they never reached Prometheus and the Grafana request panels stayed empty. `gateway-service` also has `sessionAffinity: ClientIP`. Prometheus always calls from the same IP, so it only ever reached one gateway replica.

**You replaced the static target with Kubernetes pod discovery (`kubernetes_sd_configs` with `role: pod`), limited to the deploy namespace.** Prometheus now keeps only pods labelled `managed=jac-scale` with role `gateway` or `microservice`, on the configured container port. This gives one target per pod, so every gateway replica and every app pod is scraped. You also removed the now-unused `scrape_target_service` and `provider` parameters and the `ClusterProvider.prometheus_scrape_port` hook.

**Status:** Open and still a **draft**. CI is green on `49aefe2`. @MusabMahmoodh left one "commented" review on 2026-10-06 with three points. None has a reply or a follow-up commit yet, because the last commit is from 2026-10-03.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| jac-scale | The Jac plugin that deploys a Jac app to Kubernetes. |
| Pod | One running copy of a container in Kubernetes. "3 replicas" means 3 pods. |
| Service (Kubernetes) | A stable network name in front of a set of pods. Each request goes to one of those pods. |
| `sessionAffinity: ClientIP` | A Service setting that sends every request from the same client IP to the same pod. Prometheus has one IP, so it always hit the same gateway pod. |
| Gateway | The jac-scale pod(s) in front of the app (`[scale.gateway]`). Labelled `jac-scale.role=gateway`. Its `/metrics` serves only `gateway_*` metrics. |
| Microservice / app pod | The pods that run your Jac app code. Labelled `jac-scale.role=microservice`. Their `/metrics` has HTTP and walker metrics. |
| Fleet | The set of jac-scale pods for a deploy (gateway plus microservices). |
| `FLEET_SELECTOR` | A constant in `target.jac:62`: `managed=jac-scale,jac-scale.role in (microservice,gateway)`. The deployer uses it to find fleet pods. It is referenced in the review; this PR does not change it. |
| Prometheus | A metrics server. It pulls ("scrapes") `/metrics` from targets on a timer (here every 15s). |
| Scrape job / target | A job is one block in the Prometheus config. A target is one address the job scrapes. |
| `static_configs` | A fixed list of target addresses written in the config. **This is where the bug is.** It held only `gateway-service`. |
| `kubernetes_sd_configs` (`role: pod`) | Service discovery: Prometheus asks the Kubernetes API for pods and turns each declared container port into a target. It follows pods as they come and go. |
| `__meta_kubernetes_pod_*` labels | Temporary labels that discovery attaches to each target, for example `__meta_kubernetes_pod_label_managed` for the pod label `managed`. Kubernetes label names have `.` and `-` turned into `_`, so `jac-scale.role` becomes `..._label_jac_scale_role`. |
| `relabel_configs` | Rules Prometheus runs on each discovered target before scraping. `action: keep` drops targets that don't match the regex. `target_label: X` copies a value into a permanent label `X`. |
| Target label shadowing | If the target has a label with the same name as a label on a scraped series, Prometheus keeps the target's value. It renames the series' own label to `exported_<name>`. That is why this PR sets no `service` target label. |
| `basic_auth` / `password_file` | The username and password Prometheus sends with each scrape. App-pod `/metrics` accepts the admin basic auth, according to the issue. |
| `ClusterProvider` (`AWSProvider`, `LocalProvider`) | Small objects that hide the differences between cloud providers. This PR removes their `prometheus_scrape_port` method. |
| `MonitoringDeployer` | The class in `monitoring.jac` that creates Prometheus, Grafana, Tempo and the exporters. |
| `_scrape_config` | **This is what the PR adds.** A new method that builds and returns the Prometheus YAML as a string, so a test can check it. |
| `KubernetesConfig` | Deploy settings such as `container_port`, `admin_username` and the monitoring switches. |
| ConfigMap / `config_hash` | Prometheus reads its config from a ConfigMap. `_deploy_prometheus` computes an md5 hash of the config. The diff doesn't show where the hash is used; it is likely used to roll Prometheus when the config changes. |
| Serve workers / #9671 | An app pod can run several worker processes. Issue #9671 says pod `/metrics` comes back empty with more than one worker. |

## 3. The problem, step by step

### 3.1 The setup

- `KubernetesTarget._deploy_observability` (`target.jac`) creates a `MonitoringDeployer` and calls `deploy(...)`.
- `MonitoringDeployer._deploy_prometheus` builds a scrape config as one f-string. It has one job named after the app, plus optional kube-state-metrics and node-exporter jobs.
- The address of the app job came from the `scrape_target_service` argument, falling back to `{app_name}-service`. The port came from `provider.prometheus_scrape_port(container_port)`.
- #6884 had already changed the caller to pass `"gateway-service"`, because `{app_name}-service` does not exist.

### 3.2 What went wrong: app pods never scraped

```text
1. jac scale deploy, monitoring enabled, gateway + 2 app replicas
2. target.jac calls monitoring.deploy(..., provider, scrape_target_service="gateway-service")
3. _deploy_prometheus: service_port = provider.prometheus_scrape_port(8000) -> 8000
4. scrape_target = "gateway-service"
5. Config written: static_configs: targets: ['gateway-service:8000']   ← WRONG: only target
6. Prometheus scrapes gateway-service:8000/metrics
7. Gateway /metrics returns only gateway_* series
8. App pod series (*_http_requests_total, *_walker_duration_seconds, ...) never reach Prometheus
9. Grafana request panels query {pfx}_http_* -> no data -> empty panels
```

### 3.3 What went wrong: only one gateway replica

```text
1. Gateway runs as 2+ replicas behind gateway-service
2. gateway-service has sessionAffinity: ClientIP
3. Prometheus pod has one IP -> every scrape lands on the same gateway pod   ← WRONG
4. The other gateway replicas' gateway_* counters are never collected
5. Gateway totals in Prometheus undercount traffic
```

### 3.4 Why it mattered

- Issue #9672 (Jac 0.37.23) says Prometheus "only ever holds `*_gateway_requests_total`", so "Grafana and the admin Services page show gateway counters only."
- Any user who turned on monitoring got empty request, latency and walker panels on the default fleet layout.
- The issue also says per-pod scraping is what makes the multi-worker merging in #9671 matter. That bug is still open, so pods with more than one worker will be up as targets but return no samples.

## 4. The idea of the fix (one sentence)

> **Discover the pods, not a Service.** Let Prometheus list the fleet's pods in the namespace and scrape each one directly on the container port.

Scraping through a Service is wrong for counters even without session affinity. Each scrape hits a random pod, so `rate()` jumps between different pods' counters. Pod discovery gives one stable series per pod, and pods that scale to zero simply disappear as targets.

**What:**
- The app job now discovers pods in the deploy namespace.
- The first `keep` rule joins the two labels with `;` and keeps only fleet pods.
- The second `keep` rule drops every port except `container_port`.
- Three permanent labels are added: `role`, `app` and `pod`.
- The YAML building moved into `_scrape_config`, which returns a string. `_deploy_prometheus` calls it and continues as before.
- `deploy` and `_deploy_prometheus` lost the `provider` and `scrape_target_service` parameters.

**Why:**
- One target per pod fixes both failures: app pods get scraped, and every gateway replica is reached instead of the one chosen by session affinity.
- Splitting out `_scrape_config` makes the config testable without a cluster.

**Things to notice:**
- **No `service` target label, on purpose.** The gateway's metrics carry their own `service` label, which the admin Services page groups by. A `service` target label would win and rename the gateway's label to `exported_service`.
- **No dashboard change.** Your description says the gateway's `/metrics` serves only `gateway_*`, and its own HTTP collector stays in-process for `/admin/metrics`. So `{pfx}_http_*` comes only from app pods and nothing is counted twice. Commit `629ddfe` ("count each request once") followed by `73a5359` ("keep the Grafana request panels on the app pod series") suggests an earlier version touched the panels and was then reverted. The final diff has no panel changes.
- **`metrics_path` is still hard-coded to `/metrics`.** @MusabMahmoodh says app pods serve at `[scale.monitoring].endpoint`. With a custom endpoint, microservice targets would 404. This is still open.
- **The keep regex copies `FLEET_SELECTOR`.** If a role is added to `FLEET_SELECTOR`, this rule won't follow it. This is still open.
- **The same port is used for the gateway and app pods.** The diff does not show whether the gateway pod declares `container_port` as its containerPort. Pod discovery only creates targets for declared container ports. If the gateway declared a different port or none, it would be dropped silently. The old static target used the same port, which is a hint that it matches, but only a real-cluster check proves it.
- **Discovery now watches every pod in the namespace** and filters them inside Prometheus. The reviewer's selector suggestion would filter on the API server instead.
- **Permissions.** Pod discovery needs `pods` list/watch. You state the Prometheus ClusterRole already grants this. The RBAC definition is not in the diff.
- The change to the config string changes `config_hash`. That probably makes existing deploys roll Prometheus on upgrade, but the diff doesn't show how the hash is used.

## 6. How execution flows after the PR

### 6.1 Deploying with monitoring enabled

```text
jac scale deploy
└─ KubernetesTarget._deploy_observability
   └─ MonitoringDeployer(obs_config, logger).deploy(app_name, ns, apps_v1, core_v1)   ← CHANGED (no provider / target args)
      ├─ if k8s_metrics_enabled: deploy kube-state-metrics, node-exporter
      └─ _deploy_prometheus(app_name, ns, apps_v1, core_v1)                           ← CHANGED
         ├─ _scrape_config(app_name, ns)                                              ← NEW
         │  ├─ job '<app>': kubernetes_sd_configs role=pod, namespace=ns              ← NEW
         │  ├─ relabel keep: managed=jac-scale & role gateway|microservice            ← NEW
         │  ├─ relabel keep: container port == container_port                         ← NEW
         │  ├─ target labels: role, app, pod                                          ← NEW
         │  └─ + ksm / node-exporter jobs (unchanged)
         ├─ config_hash = md5(config)[:12]
         └─ create ConfigMap + Prometheus Deployment (unchanged)
```

### 6.2 One Prometheus scrape cycle

```text
Prometheus (every 15s)
├─ list/watch pods in <ns>                                       ← NEW
├─ for each pod × declared container port:
│  ├─ not managed=jac-scale or role not gateway|microservice → drop   ← NEW
│  ├─ port != container_port → drop                                  ← NEW
│  └─ set role / app / pod labels                                    ← NEW
└─ GET http://<podIP>:<port>/metrics with basic auth
   ├─ gateway pod → gateway_* series, labelled role="gateway"
   └─ app pod     → {pfx}_http_*, walker series, labelled role="microservice"
      └─ (>1 serve worker: may be empty until #9671 is fixed)
```

| Scenario | Before | After |
|---|---|---|
| 1 gateway + N app pods | 1 target (`gateway-service`) | 1 + N targets, one per pod |
| Gateway with 3 replicas | Only 1 replica scraped (ClientIP affinity) | All 3 scraped |
| Grafana request/latency/walker panels | Empty | Filled from app pod series |
| App scaled to zero | n/a (never scraped) | Pod targets disappear |
| Custom `[scale.monitoring].endpoint` | No effect (only gateway scraped) | Microservice targets 404 → shown down (open review point) |
| App pod with >1 serve worker | n/a | Target up, but may have no samples (#9671) |

**Behaviour change users will notice:**
- Prometheus's Targets page now lists every pod, and series carry `role`, `app` and `pod` labels.
- Gateway counters are now collected from every replica, so gateway totals will go up compared with before. The old totals undercounted.

## 11. Questions your senior might ask

**Q: Why not scrape each app's Service instead of pods?**
A Service sends each scrape to a random pod (or a fixed one with ClientIP affinity). Counter rates then mix different pods or miss replicas. Pod discovery gives one stable series per pod.

**Q: Can a request be counted twice, once at the gateway and once at the app pod?**
No, according to the description. The gateway's `/metrics` serves only its `gateway_*` registry, and its HTTP collector stays in-process for `/admin/metrics`. So `{pfx}_http_*` comes only from app pods.

**Q: Why no `service` target label?**
The gateway's metrics already carry a `service` label, which the admin Services page groups by. A target label with the same name would win and rename the gateway's label to `exported_service`.

**Q: Does Prometheus have permission to list pods?**
The description says the existing ClusterRole already grants `pods` list/watch. The RBAC manifest isn't in the diff, so the planned e2e targets check is what would confirm it.

**Q: What happens with a custom `[scale.monitoring].endpoint`?**
Right now microservice targets would 404, because `metrics_path` is fixed to `/metrics`. The reviewer's per-role `__metrics_path__` relabel is the planned fix. It's still open.

**Q: Will these targets actually have data today?**
With one serve worker, yes. With more than one, pods may return an empty body until #9671 is fixed. The targets will be up but have no samples.

**Q: Do the gateway and app pods both listen on `container_port`?**
The port keep rule assumes it. The old static target used the same port for `gateway-service`, which suggests it holds, but the diff doesn't show the pod specs. A real-cluster targets check would prove it.

**Q: Why remove `prometheus_scrape_port` instead of keeping it for later?**
Both providers returned `container_port` unchanged, and the static target was its only caller. Keeping it would leave dead code in an abstract interface.

**Q: Why did you extract `_scrape_config`?**
So the YAML can be built and checked without a cluster. That is what the new unit test does.

**Q: What does an existing deployment see on upgrade?**
The config string changes, so its md5 `config_hash` changes. The diff doesn't show how the hash is used; it most likely triggers a Prometheus rollout. After that, the Targets page shows one entry per fleet pod, and gateway totals rise because every replica is now counted.
