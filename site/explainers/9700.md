# fix(scale): build deployed pods from the app's [serve] config, not the deployer's (#9382)

[#9700](https://github.com/jaseci-labs/jac/pull/9700) by @akindu-k · opened 2 Oct 2026 · +138 −17 in 3 files

<!-- explainer -->

## In short
When jac-scale deployed an app, it built the pods' server settings (drain time, worker count, trusted proxies, login secret) from the program running the deploy, not from the app. So one app's settings, even its secret, could leak into another. You changed `ManifestBuilder` to read these settings only from the app folder's own `jac.toml`, and you ignore the deployer's env vars and config.

## Words to know
- **jac-scale**: the plugin that deploys Jac apps to Kubernetes.
- **Deployer**: the program that runs the deploy. Here, jacBuilder, which itself runs in a jac-scale pod.
- **Pod**: the unit Kubernetes runs. Your app's server runs inside pods.
- **`ManifestBuilder`**: the class that builds the Kubernetes manifests (the YAML-like specs) for the app, including each pod's environment variables.
- **`[serve]` section**: the part of `jac.toml` that holds server settings: timeouts, workers, proxy, auth.
- **`jac.toml`**: the project's config file.
- **Drain timeout**: how long a pod keeps finishing requests before it shuts down. A long drain makes destroying an app slow.
- **Trusted proxies**: the network ranges whose forwarded headers the server believes.
- **JWT / auth secret**: the key used to sign login tokens. Sharing it between apps is a security problem.
- **`JAC_SERVE_*` env vars**: environment variables that override `[serve]` settings at runtime.
- **Placeholder secret (`PLACEHOLDER_JWT_SECRET`)**: a marker value from #9551. The pod swaps it for a freshly generated secret for that app only.
- **`"auto"` workers**: the pod picks its worker count from its own CPU limit.
- **`ServeConfig` / `JacConfig`**: the config objects for the `[serve]` section and for the whole `jac.toml`.
- **`resolve_count`**: a helper that checks a worker-count string and raises `ServeConfigError` if it is invalid.

## The problem
Since #8981, `ManifestBuilder._serve_settings()` loaded settings through `get_scale_config().get_jac_config()` and `ServeSettings.load`. That used the deployer's `jac.toml` and also applied the deployer's `JAC_SERVE_*` env vars.

There were two leaks:
1. The deployer's `jac.toml` was read instead of the app's. jacBuilder uses `drain = 900`, so every user app got a 900 second drain. Destroying an app took about 3 minutes instead of about 40 seconds.
2. The deployer's env vars overrode the values. jacBuilder runs in a jac-scale pod, so it has `JAC_SERVE_AUTH_SECRET` set. An app with no secret of its own could get jacBuilder's login secret.

The fix suggested in the issue only covered leak 1.

## The changes, one by one

### `jac/jaclang/scale/deploy/target/kubernetes/manifest_builder.jac`
This is the core fix.

**`_serve_settings()` becomes `_serve_config()`.** It returns a `ServeConfig` (the raw `[serve]` section) instead of `ServeSettings`, which merges in env vars. The cache field is renamed to `_serve_config_cache`.

```
project = self._shipped_config()
    if self.project_dir
    else get_scale_config().get_jac_config();
serve: ServeConfig = project.serve if project is not None else ServeConfig();
```
- If the builder has a `project_dir`, it uses `_shipped_config()`, the app's own config.
- If not, it falls back to the global config, as before.
- If there is no config, it uses a default `ServeConfig()`.

**New `_shipped_config()`.** It checks that `<project_dir>/jac.toml` exists. If it doesn't, it returns `None`, so the pods get defaults. This stops a parent folder's `jac.toml`, such as the deployer's, from being found. If the file exists, it calls `JacConfig.resolve(start_path=app_dir)`. This reads the same file the deploy ships to the pod.

**`_drain_timeout`, `_signing_secret` and `_serve_env`** now use `_serve_config()`. `_signing_secret` still checks `[scale.secrets] JAC_SERVE_AUTH_SECRET` first. Then it uses the app's `[serve.auth] secret`. Last, it returns `PLACEHOLDER_JWT_SECRET`.

**New `_worker_count_env()`.** The worker count comes from the service config or the app's `[serve.workers] count`. `resolve_count(raw, 1, ...)` checks it at deploy time, but the original string is returned. So `"auto"` reaches the pod unchanged, and the pod works it out from its own CPU limit. Invalid values such as `"0"` or `"many"` still fail at deploy time.

Env vars still override `jac.toml` inside the running pod. That part is unchanged.

### `release_notes/unreleased/jaclang/9700.bugfix.md`
A one-line release note. It says each app now gets its own `[serve]` settings, and that `"auto"` is sized by the pod's CPU quota.

## How it runs now
1. `jac scale deploy` creates a `ManifestBuilder` with the app's `project_dir`.
2. The builder calls `_serve_env(svc_name, svc_cfg)` for each service.
3. `_serve_env` calls `_serve_config()` (changed).
4. `_serve_config()` calls `_shipped_config()` (new). That reads only `<project_dir>/jac.toml`, or returns `None` if the file is missing.
5. `_worker_count_env()` (new) checks the worker count with `resolve_count` and returns the raw string (changed).
6. The drain timeout and trusted proxies come from the app's `ServeConfig` (changed).
7. `_signing_secret()` picks the `[scale.secrets]` value, then the app's secret, then the placeholder (changed source).
8. In the pod, `JAC_SERVE_*` env vars override `jac.toml`, as before.

## Tests
You extended the existing test `embedder-supplied overrides reach the builder with gateway defaults`. The file still has 17 tests.

**Setup:** the helper `_builder` takes a `project_dir`, and a new helper `_project_with` writes a temp `jac.toml`. The test creates a deployer with `drain = 900` and a secret. It sets `JAC_SERVE_*` env vars (drain, secret, workers 7, trusted proxy) and pins the deployer config with `get_scale_config`. A `finally` block resets the config and restores the env vars.

**Four apps are checked** for drain, workers, trusted proxies and secret:
- A `jac.toml` with no `[serve]` gets the defaults (drain 10, placeholder secret, 1 worker, private ranges).
- An app with its own settings gets its own values (30, `"app"`, 3, `10.1.0.0/16`).
- An app with no `jac.toml`, inside the deployer's folder, gets the defaults, not the deployer's.
- An app with `count = "auto"` sends `"auto"` unchanged.

These prove that neither the deployer's file, nor its env vars, nor a parent folder's file leaks.

**Worker validation:** a service-level `workers` value is checked. `"2"` and `" auto "` pass (the second is stripped to `"auto"`). `"0"` and `"many"` raise `ServeConfigError`. This covers `_worker_count_env`.

## Explaining it in one minute
Deployed pods were getting their drain time, workers, proxies and login secret from the deployer's config and env vars, not the app's. So jacBuilder's 900 second drain, and even its login secret, could end up in user apps. I replaced `_serve_settings()` with `_serve_config()`. It reads only the `[serve]` section of the app folder's own `jac.toml`. It ignores env vars, parent folders and pinned deployer config. If there is no `jac.toml`, it uses defaults, and an app with no secret gets the placeholder, which becomes a per-app secret. The worker count is still validated at deploy time, but sent as written, so `"auto"` is resolved per pod. I extended one existing test with four app scenarios under a deliberately polluted deployer, plus worker validation cases. It runs in-process with no cluster.
