## 1. The short version

`JacScaleUserManager` is the jac-scale class that stores user accounts: usernames, password hashes, tokens, roles, admin flags and linked SSO (single sign-on) accounts. Before this PR it inherited from a base `UserManager` and kept everything in a local **SQLite** file through `self._conn`.

**Before this PR, every user record lived in a SQLite file on the local disk of the process that served the request.** The PR description is empty and no issue is linked, so the motivation is not stated. From the title and the code, the likely goal is to share user data across a deployment. jac-scale deploys to Kubernetes, and a local file is not shared between pods. That is an inference, not something the PR states.

**You rewrote every user-storage method to read and write two MongoDB collections, `users` and `sso_accounts`, in database `jac_db`.** `postinit` now requires `mongodb_uri` in the config and raises `ValueError("MongoDB URI not configured. ...")` if it is missing. You also added a test helper that starts a real MongoDB in Docker (via `testcontainers`), and you moved four SSO tests to it. No data is copied from existing SQLite files. "Migration" here means moving the storage layer, not moving data.

## 3. The problem, step by step

This is a storage change, not a bug fix. There is no issue or description, so what follows is based only on the code.

### 3.1 The setup

- `user_manager.jac` declares `JacScaleUserManager(UserManager)`.
- `impl/user_manager.impl.jac` holds the method bodies.
- Before the PR, the core methods (`create_user`, `authenticate`, `get_user` and the others) came from the base `UserManager`. They used SQLite at `_db_path`.
- jac-scale's own `postinit` called `super.postinit()`. It then created an `sso_accounts` table and used `ALTER TABLE` to add `role`, `requires_password_reset`, `is_password_required` and `user_id` columns.
- All SSO and admin methods called `self._ensure_connection()` and ran SQL on `self._conn`.

### 3.2 What was missing

The flow below is a likely reason for the change. It is inferred from the fact that jac-scale targets Kubernetes. The PR does not state it.

```text
1. App deployed with 2 replicas: pod A and pod B, each with its own disk.
2. User signs up; request hits pod A → row written to pod A's SQLite file.
3. User logs in; request hits pod B → pod B's SQLite file has no such user.   ← WRONG: login fails / user "missing"
4. Admin lists users on pod B → only sees users created on pod B.            ← WRONG
5. Pod A restarts without a persistent volume → its users are gone.          ← WRONG (if no volume)
```

### 3.3 Why it mattered

Nothing in the PR, comments or issues describes a user report. If the inference above is right, the problem affects any multi-pod or restart-prone jac-scale deployment. To check, ask whether a tracking issue exists. Before the PR, the workaround would have been a single replica with a persistent volume. This cannot be confirmed from the data.

## 4. The idea of the fix (one sentence)

> **Store users and SSO links in MongoDB instead of local SQLite.** Every method that ran SQL on `self._conn` now calls `find_one`, `update_one`, `insert_one` or `delete_one` on the `users` or `sso_accounts` collection.

A shared server database is what lets every pod see the same accounts. jac-scale already has a MongoDB connection pool (`get_mongo_client`), so reusing it avoids adding a new service.

### 5.3 Same file: core user methods (new overrides)

```diff
+impl JacScaleUserManager.create_user(username: str, password: str) -> dict[str, str] {
+    if self._users_col.find_one({'username': username}) { return {'error': 'User already exists'}; }
+    ctx = Jac.get_context();          # assigned, never used
+    user_root = Root(); root_anchor = user_root.__jac__;
+    Jac.save(root_anchor); Jac.commit(root_anchor);
+    root_id = root_anchor.id.hex;
+    token = secrets.token_urlsafe(32);
+    password_hash = hashlib.sha256(password.encode()).hexdigest();
+    self._users_col.insert_one({ 'username', 'password_hash', 'token', 'root_id',
+        'role': 'user', 'requires_password_reset': False, 'is_password_required': True,
+        'user_id': None, 'created_at': datetime.now(timezone.utc) });
+    return {'username': username, 'token': token, 'root_id': root_id};
+}
+impl authenticate  -> find_one({'username', 'password_hash'})
+impl get_root_id   -> find_one({'username'})['root_id']
+impl get_user      -> {'email': username, 'token', 'root_id'}
+impl user_exists   -> count_documents({'username'}, limit=1) > 0
+impl update_username -> check new name free, update_one $set username
+impl update_password -> verify old hash, update_one $set password_hash
```

**What:** These methods re-implement user create, login, lookup and rename against Mongo.

**Why:** These were the methods that previously went to the base class's SQLite file.

**Things to notice:**
- **Password hashing:** passwords are hashed with plain SHA-256, with no salt. You cannot tell from the diff whether the base class uses the same scheme. If it uses something stronger, this is a security downgrade. If it differs at all, hashes copied from old SQLite data would not match. A senior is likely to ask about this.
- **Race in `create_user`:** the code checks with `find_one` and then calls `insert_one`. If two sign-ups with the same name race, the unique index raises `DuplicateKeyError`, which is not caught. The `Root` node has already been saved and committed by then, so it is left behind with no user.
- **Race in `update_username`:** the same check-then-write pattern means it can also raise `DuplicateKeyError`.
- `update_username` does not update `sso_accounts.user_id`. SSO links keyed on the old username stop resolving. The old SQLite foreign key had no `ON UPDATE CASCADE` either, so this may match old behaviour. It is still worth stating.
- `get_user` returns the username under the key `'email'`, matching the old SQL code's shape.
- `ctx` is unused, and `Root` is imported twice: once at the top and once inside the method.

## 11. Questions your senior might ask

**Q: Why not keep SQLite as a fallback when no Mongo URI is set?**
The PR does not explain this. `postinit` raises `ValueError` instead. That makes local or single-pod use require Mongo, which is a deliberate or accidental breaking change you need to justify.

**Q: What happens to users already stored in SQLite?**
Nothing moves them. After upgrading, they are invisible, because the new code only reads `jac_db.users`.

**Q: Why did you drop `super.postinit()`?**
The parent sets up SQLite, which is no longer used. You set `_db_path` and `_conn` by hand to keep the interface. Whether the parent did anything else is not visible in this diff.

**Q: Is the password hashing safe and compatible?**
It is `hashlib.sha256` with no salt. That is weak for passwords. Whether it matches the base class cannot be seen here.

**Q: What replaces the `ON DELETE CASCADE` on SSO accounts?**
Nothing. `delete_user` only deletes the user document, so SSO links are left behind.

**Q: What if two people register the same username at the same time?**
The unique index on `username` rejects the second insert with an uncaught `DuplicateKeyError`. The second request's `Root` node has already been committed and is left behind.

**Q: Why is `testcontainers` in the main dependencies?**
Only the test fixture uses it. It should move to a test extra.

**Q: Why does `test-scale` fail?**
The logs are not available. Likely causes are tests that still use the old SQLite helper without a Mongo URI, or Docker being unavailable for testcontainers in that job.

**Q: Is `_db_name = 'jac_db'` configurable?**
No. It is a hard-coded default, so all apps on one Mongo server would share one user collection unless something sets it.

**Q: Did any API response shape change?**
Mostly no. The exception is `get_sso_accounts`, whose `linked_at` is now an ISO string instead of SQLite's timestamp text. Flags are now real booleans in storage, but the returned values are still passed through `bool(...)`.
