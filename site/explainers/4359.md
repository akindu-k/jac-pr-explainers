## 1. The short version

jac-scale turns your Jac walkers and functions into REST endpoints. A walker `Foo` is served at `/walker/Foo` and a function `bar` at `/function/bar`. The `@restspec(method=...)` decorator lets you pick which HTTP method an endpoint uses, and `@restspec(method=HTTPMethod.GET)` was already accepted before this PR.

**Before this PR, GET endpoints could not really take arguments. The code that builds each endpoint's parameter list did not know the HTTP method, and the dynamic (HMR) catch-all routes only existed for POST and only read a JSON body.** A walker with `has name: str; has age: int;` marked as GET had no sound way to receive `?name=Alice&age=30`.

**You pass the HTTP method into the parameter builders so that GET fields become query parameters. You also add GET versions of the three dynamic catch-all routes, which read `request.query_params` instead of the JSON body.** POST behaviour is unchanged, because the new `method` argument defaults to `HTTPMethod.POST`.

**Status:** Merged on 2026-01-30. @Thamirawaran first requested changes (about the release notes), then approved. All 9 CI checks passed on head commit `312f71d`.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. It is a superset of Python with graph features. |
| Node / `root` | A vertex in Jac's object graph. Each user has a `root` node, and walkers usually start there. |
| Walker | A Jac object that "walks" the graph and runs abilities on nodes. Its fields are declared with `has`, for example `has name: str;`. |
| `report` | A Jac statement that adds a value to the walker's output list. It shows up as `reports` in the HTTP response. |
| Function (`def`) | An ordinary Jac function. jac-scale can also expose these over HTTP. |
| `: pub` | Marks a walker as public, so it can be called without an auth token. |
| jac-scale | A plugin that serves Jac apps as a REST API and deploys them to Kubernetes. |
| `.jac` / `.impl.jac` | Jac splits declarations (`serve.jac`) from implementations (`impl/serve.impl.jac`). Changing a signature means editing both files. |
| `JacAPIServer` | The jac-scale class that registers all HTTP endpoints. |
| HTTP GET vs POST | GET requests usually carry their inputs in the URL. POST requests carry them in a request body. |
| Query string | The part of a URL after `?`. Example: `/walker/W?name=Alice&age=30`. |
| Request body | Data sent after the HTTP headers, usually JSON for POST. GET requests normally have no body. |
| `@restspec` | A decorator that sets an endpoint's HTTP method and path. Example: `@restspec(method=HTTPMethod.GET)`. |
| `HTTPMethod` | An enum of HTTP methods: `GET`, `POST`, and so on. |
| `JEndPoint` | An object that describes one route: method, path, callback, parameters, tags. |
| `APIParameter` / `ParameterType` | Describes one input to a route and where it comes from: `PATH`, `QUERY`, `HEADER`, `FILE`, or a body (the body branch is not shown in the diff). |
| `UploadFile` | A field type for uploaded files. These fields become `FILE` parameters. |
| Introspector | The jac-scale component that knows each walker's and function's fields, types, and auth needs. |
| Static endpoint | A route registered per walker or function at startup, for example `GET /walker/GetWalker`. |
| HMR / dynamic endpoint | Hot Module Replacement. Catch-all routes like `/walker/{walker_name}` look up the walker at request time, so code edits show up without a restart. |
| `create_walker_parameters` / `create_function_parameters` | Build the `APIParameter` list for a static endpoint. **This is where the bug is.** They picked the parameter type from the field type only, never from the method. |
| `register_dynamic_walker_endpoint` / `register_dynamic_function_endpoint` | Register the HMR catch-all routes and their handlers. **This is what the PR adds to:** GET routes and query-string parsing. |
| OpenAPI | The machine-readable API description at `/openapi.json`. The tests read it to check which methods each path has. |

## 3. The problem, step by step

### 3.1 The setup

- **Static routes.** `register_walkers_endpoints` and `register_functions_endpoints` loop over all walkers and functions. They read the `@restspec` method (`spec_method`) and path, then register a `JEndPoint`. The route already used `spec_method`. The parameter list came from `create_*_parameters(name)`, which did not receive the method.
- **Dynamic routes.** `register_dynamic_walker_endpoint` registered `POST /walker/{walker_name}/{node}` and `POST /walker/{walker_name}`. `register_dynamic_function_endpoint` registered `POST /function/{function_name}`. Each handler ran `await request.json()` to get the arguments.

### 3.2 What went wrong: static GET endpoint with fields

```text
1. Fixture: @restspec(method=HTTPMethod.GET) walker GetWalkerWithParams { has name: str; has age: int; }
2. Startup: register_walkers_endpoints → spec_method = GET, route = GET /walker/GetWalkerWithParams
3. Calls create_walker_parameters("GetWalkerWithParams", invoke_on_root=True)   ← method not passed
4. Field "name" (str): not _jac_spawn_node, not UploadFile → falls to the else branch
5. Field "age"  (int): same → else branch                                      ← WRONG for GET
   (the else branch is not in the diff; from context it is the non-query/body type used for POST)
6. Client: GET /walker/GetWalkerWithParams?name=Alice&age=30
7. Route expects the fields from somewhere other than the query string → values not mapped
```

### 3.3 What went wrong: dynamic (HMR) routes

```text
1. Client: GET /walker/GetWalkerWithParams?name=Alice&age=30
2. Dynamic routes registered: POST /walker/{walker_name}, POST /walker/{walker_name}/{node} only
3. No GET catch-all exists → a GET to a walker is only served if a static GET route exists  ← MISSING
4. Even for a POST, the handler only ran `await request.json()`; query params were ignored
5. Same for functions: only POST /function/{function_name}, body only
```

### 3.4 Why it mattered

There is no linked issue and no discussion beyond the release-note review comment. From the PR description, the goal is to make `@restspec(method=HTTPMethod.GET)` actually usable for walkers and functions that take inputs. That covers "read-only" queries that clients naturally send as GET with a query string. Before the PR, the GET option was only practical for parameterless endpoints like the existing `GetWalker` / `get_func` fixtures.

## 4. The idea of the fix (one sentence)

> **Let the HTTP method decide where inputs come from.** For GET, non-file fields are declared and read as query parameters, and every dynamic catch-all route gets a GET twin that parses `request.query_params`.

This is the smallest change that matches HTTP conventions. The method was already known at registration time and only needed to flow one level down. The default `method=HTTPMethod.POST` keeps every existing caller and every POST endpoint unchanged.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/serve.jac`: new signatures

```diff
     def create_walker_parameters(
-        walker_name: str, invoke_on_root: bool
+        walker_name: str, invoke_on_root: bool, method: HTTPMethod = HTTPMethod.POST

+        func_name: str, method: HTTPMethod = HTTPMethod.POST
```

**What:** Both parameter builders now take an optional `method`.

**Why:** The builders need the method to choose `QUERY` for GET.

**Things to notice:** The default of `POST` means any other caller (none visible in the diff) keeps the old behaviour. The declarations in `serve.jac` must match the `impl` signatures.

### 5.2 `jac-scale/jac_scale/impl/serve.impl.jac`: static endpoints pass the method


**Why:** This connects the route's method to its parameter types (the step 3 problem in 3.2).

### 5.4 `jac-scale/jac_scale/impl/serve.impl.jac`: dynamic handlers read the query string on GET

```diff

-        try {
-            body = await request.json();
-        } except Exception {
-            body = {};
+        # Parse request body or query params to get walker fields
+        if request.method == 'GET' {
+            kwargs: dict[str, Any] = dict(request.query_params);   # NEW

+            } except Exception {
+                body = {};
+            }
+            kwargs = dict(body) if body else {};
         }
-        kwargs: dict[str, Any] = dict(body) if body else {};
```

The same change is made in `dynamic_function_handler`.

**What:** One handler serves both methods and branches on `request.method`.

**Why:** Without this, the new GET routes in 5.5 would try to parse a JSON body that GET requests don't have.

**Things to notice:**
- Query values are always strings, so `age=30` arrives as `"30"`. The new test expects `age == 30` as an integer and passes, so conversion happens somewhere. The diff does not show where: it may be the introspector, walker construction, or the static route's typed `QUERY` parameter, depending on which route serves the request.
- `dict(request.query_params)` keeps one value per key. Repeated keys such as `?tag=a&tag=b` cannot express a list.
- Nothing in the visible diff checks that the walker or function was declared GET. Through the dynamic routes, any walker may now be callable by GET, including one marked `@restspec(method=HTTPMethod.POST)`. The rest of the handler is not in the diff, so this can't be confirmed either way.

### 5.5 `jac-scale/jac_scale/impl/serve.impl.jac`: three new dynamic GET routes

```diff
+    # Register catch-all route for walkers with node parameter (GET)
+    self.server.add_endpoint(
+        JEndPoint(

+            path='/walker/{walker_name}/{node}',

+    # Register GET endpoint
+            method=HTTPMethod.GET, path='/function/{function_name}', ...
+            parameters=[ function_name (PATH), Authorization (HEADER) ]
```

**What:** These routes mirror the existing POST catch-alls and reuse the same handlers.

**Why:** They fix the missing GET routes in 3.3. HMR-mode GET calls now reach a handler.

**Things to notice:**
- The routes declare no query parameters, because the walker is unknown until request time. The handler reads them straight from `request.query_params`, so OpenAPI will not list them for these routes.
- The routes are large copy-pastes of the POST versions. They could be generated in a loop over `[POST, GET]`, but this is cosmetic.

## 6. How execution flows after the PR

### 6.1 Server start: static walker endpoints

```text
register_walkers_endpoints
├─ for each walker: read @restspec → spec_method (default POST), spec_path
├─ register JEndPoint(method=spec_method, path=f"{spec_path}/{node}")
│   └─ create_walker_parameters(name, invoke_on_root=False, method=spec_method)   ← CHANGED
└─ register JEndPoint(method=spec_method, path=spec_path)
    └─ create_walker_parameters(name, invoke_on_root=True, method=spec_method)    ← CHANGED
        └─ per field:
            ├─ _jac_spawn_node        → PATH
            ├─ method==GET & not file → QUERY                                     ← NEW
            ├─ UploadFile             → FILE
            └─ else                   → (unchanged default, not shown)
```

### 6.2 Server start: static function endpoints

```text
register_functions_endpoints
└─ JEndPoint(method=spec_method, path=final_path)
    └─ create_function_parameters(name, method=spec_method)                       ← CHANGED
        └─ per field: GET & not file → QUERY ← NEW; UploadFile → FILE; else → default
```

### 6.3 Server start: dynamic routes

```text
register_dynamic_walker_endpoint
├─ POST /walker/{walker_name}/{node}
├─ GET  /walker/{walker_name}/{node}     ← NEW
├─ POST /walker/{walker_name}
└─ GET  /walker/{walker_name}            ← NEW
register_dynamic_function_endpoint
├─ POST /function/{function_name}
└─ GET  /function/{function_name}        ← NEW
```

### 6.4 A request hitting a dynamic handler

```text
GET /walker/GetWalkerWithParams?name=Alice&age=30
└─ dynamic_walker_handler(request, walker_name, node=None, Authorization)
    ├─ request.method == 'GET' → kwargs = {"name": "Alice", "age": "30"}          ← NEW
    │   (POST → kwargs = await request.json(), or {} on error)                     (unchanged)
    ├─ reload introspector if _hmr_pending
    └─ … run walker, return TransportResponse (rest of handler not in diff)
```

The diff does not show whether the static `GET /walker/GetWalkerWithParams` route or the dynamic `GET /walker/{walker_name}` route wins for this URL. That depends on registration order, which is not visible here.

| Scenario | Before | After |
|---|---|---|
| GET walker/function with fields, static route | Fields not declared as query params | Fields are `QUERY` params and appear in OpenAPI |
| GET to `/walker/X` via dynamic route | No GET catch-all | Handled, args from query string |
| GET to `/function/x` via dynamic route | No GET catch-all | Handled, args from query string |
| POST walker/function (explicit or default) | JSON body | Unchanged |
| GET endpoint with an `UploadFile` field | `FILE` | Still `FILE` (odd for GET, not handled) |

**User-visible change:** Clients can now call GET-declared walkers and functions with `?key=value` arguments. As noted in 5.4, the new dynamic GET routes may also accept GET for walkers not declared as GET. Confirm this against the full handler.

## 11. Questions your senior might ask

**Q: Didn't `@restspec(method=HTTPMethod.GET)` already work?**
Partly. Static routes were already registered with the declared method, and parameterless GET endpoints already passed tests. What was missing was mapping fields to query parameters, plus any GET route in HMR/dynamic mode.

**Q: Query values are strings. How does `age` come back as the integer 30?**
The test proves it does. The diff doesn't show where the conversion happens. It is either FastAPI-style typed `QUERY` parameters on the static route, or coercion when the walker or function is built from `kwargs`. I would need to check the rest of `serve.impl.jac` to say which.

**Q: Can a walker declared POST now be called with GET?**
Possibly, through `GET /walker/{walker_name}`. The visible handler code branches only on `request.method` and never checks the walker's `@restspec`. The OpenAPI test only covers the static path. This is worth verifying.

**Q: Why default `method` to POST instead of making it required?**
So existing callers and all POST endpoints behave exactly as before, without touching every call site.

**Q: What happens to an `UploadFile` field on a GET endpoint?**
It stays a `FILE` parameter, because the GET branch explicitly skips file fields. Sending files over GET is unusual, and the PR neither handles nor tests it.

**Q: Why reuse the same handler for GET and POST?**
The only difference is where `kwargs` come from. Everything after that (HMR reload, auth, execution, response) is shared, so one branch at the top avoids duplicating the handler.

**Q: Do the dynamic GET routes show their query parameters in OpenAPI?**
No. They declare only the path name and the `Authorization` header, because the target walker is unknown at registration. Static GET routes do list their `QUERY` parameters.

**Q: What about repeated query keys or list-typed fields?**
`dict(request.query_params)` keeps one value per key, so lists can't be passed through the dynamic GET route. This is not tested.

**Q: Which route serves `GET /walker/GetWalkerWithParams`, static or dynamic?**
It depends on registration order, which isn't visible in the diff. The test passes either way, but it doesn't pin down which path was exercised.
