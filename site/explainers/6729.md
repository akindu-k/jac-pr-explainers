## 1. The short version

Jac programs store their graph (nodes and edges) in a database. In jac-scale that database is MongoDB. A common walker pattern is "look for a child node; if it is missing, create it." Writes are not sent to MongoDB during the request. They are held in memory and flushed when the request ends, and each new node gets a fresh random id.

**When two requests run this check-then-create on the same root at the same time, both see "missing," both create the node, and MongoDB stores two copies. Every request still returns `200 OK`.** The issue's repro fires 4 concurrent `/walker/me` calls and ends with `countDocuments({"arch_type":"UserProfile"})` returning more than 1. In production, each duplicate also re-ran side effects such as signup bonuses and billing customer creation.

**You added a way to declare that an archetype is unique, `register_unique_index(UserProfile, scope="root")`. MongoDB enforces it as a unique partial index, and the losing write becomes a typed `UniqueViolation` that the server returns as HTTP 409.** You also wired the change set so a failed node create skips its edge and the parent's edge-list entry. That way no dangling reference is written. A later commit makes startup fail with `IndexMigrationRequired` when a declared index cannot be built.

## 3. The problem, step by step

### 3.1 The setup

- **The walker:** `walker me` reads `[-->(?:UserProfile)]` from the root. If that is empty, it runs `here ++> UserProfile(...)`.
- **Staging:** `++>` builds a node anchor and an edge anchor in L1. `MongoBackend.put` is a no-op (per the issue), so nothing reaches Mongo yet.
- **Flush:** at the end of the request, `commit()` → `apply()` writes each anchor with `update_one({'_id': <new uuid>}, {'$set': doc}, upsert=True)`. The root's edge list is merged server-side with `$setUnion` (from #5644).
- **Nothing enforces uniqueness:** no index exists, and there is no logical key. If an operator added an index by hand, the issue says the `DuplicateKeyError` was swallowed by `except Exception` blocks.

### 3.2 What went wrong: two racing requests, no index

```text
1. A loads root R. R.edges = []. Query UserProfile children → empty.
2. B loads root R. R.edges = []. Query UserProfile children → empty.
3. A: here ++> UserProfile  → L1(A): node U_A, edge E_A, R.edges=[E_A]   (nothing in Mongo)
4. B: here ++> UserProfile  → L1(B): node U_B, edge E_B, R.edges=[E_B]   (nothing in Mongo)
5. A commits: upsert {_id:U_A}, upsert {_id:E_A}, R.data.edges ∪= [E_A]  → 200
6. B commits: upsert {_id:U_B} → new doc (different _id, nothing objects)   ← WRONG
             upsert {_id:E_B}, R.data.edges ∪= [E_B]                       → 200
Mongo end state: R.data.edges=[E_A,E_B], UserProfile docs = 2, both clients got 200.
```

### 3.3 What went wrong: operator adds a unique index by hand (before this PR)

```text
1-5. Same as above. A's U_A is stored.
6. B commits: upsert {_id:U_B} → MongoDB raises DuplicateKeyError
7. except Exception → logger.error(...) and continue                     ← WRONG (swallowed, per issue)
8. E_B and R.data.edges ∪= [E_B] are still written                       ← WRONG (edge to a missing node)
9. B's client gets 200 with a UserProfile that does not exist in Mongo
```

The current base already re-raises in `_write_to_db` (the diff context says "Propagate: apply() must know…"). So step 7 described the issue's snapshot. Step 8 (the create direction never poisoning the edge) is what the `changeset.jac` change closes.

### 3.4 Why it mattered

- The issue reports this on `jacBuilder/services/ideServer.jac`. One login fans out into several `me` calls across replicas.
- Each duplicate re-ran side effects: signup-bonus grant, billing customer creation, ws-token registration. Per your description, a duplicated walker could also create a second duplicate of another archetype.
- There was no signal: every response was 200. The issue argues against app-level Redis locks for four reasons. The lock must cover the whole walker. Every call site must add one. Writers that skip the lock bypass it. And uniqueness belongs to the archetype, not the caller.

## 4. The idea of the fix (one sentence)

> **Let the database be the referee.** Declare uniqueness once per archetype, turn it into a MongoDB unique partial index, and turn the database's rejection into a typed 409 that cleanly skips everything that depended on the failed create.

Only MongoDB sees every write from every pod, so it is the only place that can settle a race between replicas. This follows the same direction as #5644, which moved edge-merge correctness into the backend.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/index_registry.jac`: the declaration API (new file)

```diff
+obj UniqueIndexSpec {
+    has archetype_cls: type, fields: list[str], scope: str = "global", name: (str | None) = None;
+    def arch_name -> str { return getattr(self.archetype_cls, '__name__', str(self.archetype_cls)); }
+}
+glob _unique_indexes: list[UniqueIndexSpec] = [];
+def register_unique_index(archetype_cls, fields=None, scope="global", name=None) -> None {
+    spec = UniqueIndexSpec(...fields if fields is not None else []...);
+    for existing in _unique_indexes {
+        if existing.arch_name() == spec.arch_name() and existing.fields == spec.fields
+           and existing.scope == spec.scope { return; }     # dedup
+    }
+    _unique_indexes.append(spec);
+}
+def get_unique_indexes -> list[UniqueIndexSpec] { return list(_unique_indexes); }
+def clear_unique_indexes { _unique_indexes.clear(); }      # tests only
+def lookup_scope(arch_type: str, field: str) -> str { ... }
```

**What:** A process-wide list of uniqueness rules. Apps call `register_unique_index` at import time.

**Why:** Uniqueness becomes a property of the archetype, declared in one place. The backend reads this list when it builds indexes.

**Things to notice:**
- The registry is global to the process, and the backend only reads it in `postinit`. A registration that runs after the backend connects will not create an index. The diff doesn't show what guarantees this ordering.
- The dedup check ignores `name`. If two registrations differ only by name, the first one wins.
- `lookup_scope` is never called in this diff. `_translate_duplicate` works out the scope from the error's `keyValue` instead. This looks like dead code.
- `scope` is a plain string. A typo such as `"roots"` is silently treated like `global`, because the index code only checks `== "root"`.

The header file `memory_hierarchy.jac` only adds the declaration `def _ensure_unique_indexes(ascending: int) -> None;`.

**What:** At connect time, one unique partial index is built per registered spec. On writes, duplicate-key errors from the three write methods become `UniqueViolation`. `apply()` records them and poisons the failed intent, so its dependents are skipped.

**Why:**
- The index makes the second write physically impossible.
- The translation removes the silent or generic failure.
- Poisoning stops the edge and edge-list entry from pointing at a node that was never stored.

**Things to notice:**
- **Root-scope keys** are `[data.root, arch_type]` plus the fields. With `fields=[]`, that means one per root. A node with no `data.root` is indexed as `null`. All such nodes of a root-scoped type would then collide with each other. The diff doesn't show whether that can happen.
- **Fail-loud startup** came from commit `a69ea6b` after Greptile's P1. Note the gap: if one of the earlier `create_index` calls in `ensure_indexes` throws, the code never reaches `_ensure_unique_indexes`. The outer `except Exception` then logs at debug level and boots without the unique indexes.
- **Existing duplicate data now blocks startup.** Code 11000 at index build raises `IndexMigrationRequired`. Your description lists "a startup gate that refuses to deploy when existing data already violates a newly declared constraint" as out of scope. The code effectively already does this, though as a crash rather than a reported gate.
- **Not all write paths are covered.** The issue lists `sync`, `bulk_put` and `acommit` as paths with the same swallow. The diff only touches `_write_to_db`, `put_partial` and `_put_node_atomic`. Your execution-flow comment says production goes `commit → apply → _apply_one`, so those three may be enough. The diff alone can't confirm that the other paths never hit a unique index.
- `put_partial` has no upsert. It can still raise when an update changes a unique field to a value another node already has (global field scope).
- The default index name `uniq_root__UniqProfile` has a double underscore because the class name starts with `_`.
- `background=True` matches the existing calls in `ensure_indexes`.

### 5.5 `jac/jaclang/runtimelib/impl/memory.impl.jac` and `jac-scale/jac_scale/impl/memory_hierarchy.main.impl.jac`: raise after commit


**What:** Both `TieredMemory.commit` (core) and `ScaleTieredMemory.commit` (jac-scale) raise the primary violation after they finish re-baselining.

**Why:** This is how the conflict leaves the persistence layer and reaches the server.

**Things to notice:**
- The raise comes *after* `_post_apply` and `changes.clear()`. Writes that succeeded stay in Mongo, and their bookkeeping stays consistent.
- This is **not a transaction**. Unrelated writes from the losing request that don't depend on the failed node are kept, even though the client gets a 409.
- The core `TieredMemory` change is harmless for other backends: no violations are produced there, because SQLite parity is out of scope.

## 6. How execution flows after the PR

### 6.1 Startup

```text
MongoBackend(...) → postinit
├─ connect to MongoDB
└─ try ensure_indexes()
   ├─ existing indexes (updated_at, ...)
   └─ _ensure_unique_indexes(ASCENDING)                       ← NEW
      └─ for spec in get_unique_indexes()
         ├─ build keys [data.root?] + arch_type + data.archetype.<f>...
         ├─ create_index(unique, partial on arch_type)          (no-op if identical one exists)
         └─ on error → raise IndexMigrationRequired             ← NEW
   except IndexMigrationRequired → re-raise → app does not boot ← NEW
   except other Exception → debug log, continue (unchanged)
```

### 6.2 A walker request that creates a unique node

```text
POST /walker/me
├─ walker reads [-->(?:UserProfile)] → empty (race window, unchanged)
├─ here ++> UserProfile → node + edge staged in L1
└─ _finalize_call_response → commit()
   ├─ collect L1 into ChangeSet
   │  ├─ edge intent.depends_on += {root.id, node.id}           ← NEW
   │  └─ root intent.depends_on += {edge.id}                    ← NEW
   ├─ MongoBackend.apply(changeset), in dependency order
   │  ├─ node write → DuplicateKeyError → UniqueViolation       ← NEW
   │  │   └─ poisoned += node; report.violations += uv          ← NEW
   │  ├─ edge: depends on poisoned node → skipped               ← CHANGED
   │  └─ root edge-list add: depends on poisoned edge → skipped ← CHANGED
   ├─ _post_apply, changes.clear()
   └─ raise report.primary_violation() (siblings attached)      ← NEW
      └─ ExecutionManager except UniqueViolation                ← NEW
         ├─ ctx.mem.abort()
         └─ {'error_code':'unique_violation','http_status':409,'detail':...}
            └─ create_walker_callback → TransportResponse.fail(409)  ← CHANGED
```

### 6.3 Scenarios

| Scenario | Before | After |
|---|---|---|
| 4 concurrent `me` calls, no registration | 4 docs, all 200 | Same: uniqueness is opt-in |
| 4 concurrent `me` calls, `register_unique_index(UserProfile, scope="root")` | 4 docs, all 200 | 1 doc; winner 200, losers 409 `unique_violation` (per your verification comment) |

**Behaviour changes users will notice:**
1. Clients can now get 409 with `error_code: unique_violation` and need to retry.
2. Deployments that declare a constraint over dirty data will not start until the data is cleaned.

## 11. Questions your senior might ask

**Q: Why not just lock in Redis around the find-or-create?**
The issue gives four reasons. The lock would have to cover the whole walker, because writes are deferred. Every call site would need its own lock. Writers that skip the lock would bypass it. And uniqueness belongs to the archetype. Only the database sees every write from every replica.

**Q: The losing request still did its other writes. Isn't that a partial commit?**
Yes. `apply()` is not transactional. Only the failed node and its dependents (its edge, the root's edge-list add) are skipped. Unrelated writes in the same request that succeeded stay in Mongo. The violation is raised after `_post_apply` and `changes.clear()`.

**Q: How do you know no dangling edge is left?**
`ChangeSet.record` now makes an edge depend on its source and target. `record_edges` makes the root's list-add depend on the edge. A poisoned node therefore skips both. That is verified by reasoning, not by a committed test. The tests only use bare nodes.

**Q: What happens on deploy if production already has duplicate `UserProfile`s?**
`create_index` fails with code 11000. You raise `IndexMigrationRequired` ("run a dedupe migration, then redeploy"), and the backend's `postinit` re-raises it, so the app won't boot. Operators must dedupe first.

**Q: What does `scope="root", fields=[]` index on, and could it collide wrongly?**
The key is `(data.root, arch_type)`, partial on `arch_type`. That gives one node of that type per root. Any node of that type with no `data.root` is indexed as null and would collide with others like it. Whether such nodes exist can't be told from the diff.

**Q: Does every write path translate `DuplicateKeyError`?**
`_write_to_db`, `put_partial` and `_put_node_atomic` do. The issue also lists `sync`, `bulk_put` and `acommit`, which are unchanged. Your flow comment says production commits go through `apply → _apply_one`, so those three paths cover it, but this should be confirmed.

**Q: Why does the 409 not include the winner's node id?**
`_translate_duplicate` sets `existing_id=None`. Mongo's error gives the key values, not the existing `_id`. Fetching it would need an extra read. The client is expected to retry, and the retry reads the winner's node. Idempotent find-or-create is a stated follow-up.

**Q: What if `register_unique_index` runs after the backend has started?**
The indexes are built only in `MongoBackend.postinit` from the registry snapshot. A late registration won't create an index until the next start. The diff doesn't enforce or document this ordering.

**Q: Does this change anything for SQLite or local runs?**
The core `TieredMemory.commit` now raises `primary_violation()`, but only the Mongo backend produces violations. SQLite parity is out of scope, so declared uniqueness is not enforced there.

**Q: Will existing API clients break?**
Only when a constraint is registered and a race occurs. They then get HTTP 409 with `code: "unique_violation"` instead of 200. Other errors keep `EXECUTION_ERROR` / 500. The `details` field now prefers the structured `detail` over the traceback when both exist.
