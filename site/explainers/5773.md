## 1. The short version

jac-scale turns Jac functions and walkers marked with `@restspec` into HTTP endpoints. When a request comes in, the query parameters (the `?key=value` parts of the URL) become keyword arguments to your function or walker.

**Before this PR, any query parameter the function or walker did not declare was still passed in, so Python raised `TypeError` and the endpoint returned HTTP 500.** For example, `GET /items?category=books&v=1708012345` failed with `get_items() got an unexpected keyword argument 'v'`. Browsers, CDNs and proxies add parameters like `v` all the time, so this broke real traffic.

**You fixed it by reading each walker's or function's signature once, when the endpoint is registered, and then dropping every incoming key that is not in that signature before the walker or function runs.** If the target itself declares `**kwargs`, nothing is dropped. If the signature cannot be read, nothing is dropped either. The shared routing layer (`jfast_api`) is left unchanged, because another caller depends on it forwarding everything.

## 3. The problem, step by step

### 3.1 The setup

- A Jac function or walker with `@restspec` becomes an endpoint.
- `serve.endpoints.impl.jac` creates a `callback` for it. For walkers, the callback signature is `callback(request, nd=None, **kwargs)`. For functions, it is `callback(request, **kwargs)`.
- Because the callback has `**kwargs`, `jfast_api`'s `extra_query_params_code` copies **every** raw query parameter into `kwargs`, including ones nobody declared.
- The callback passes `kwargs` straight to `spawn_walker` or `execute_function`.

### 3.2 What went wrong (function endpoint)

```text
1. Request:  GET /items?category=books&v=1708012345
2. FastAPI binds declared params          kwargs = {category: "books"}
3. jfast_api extra_query_params_code      kwargs = {category: "books", v: "1708012345"}
4. create_function_callback.callback      passes kwargs unchanged
5. execute_function(get_items, kwargs)    get_items(category="books", v="1708012345")
6. ✗ TypeError: get_items() got an unexpected keyword argument 'v'   ← WRONG
7. Response: 500 {"ok":false,"error":{"code":"EXECUTION_ERROR",...}}
```

### 3.3 What went wrong (walker endpoint)

```text
1. Request:  GET /search?q=hello&v=1708012345
2. kwargs after jfast_api                 {q: "hello", v: "1708012345"}
3. create_walker_callback.callback        passes kwargs unchanged
4. spawn_walker(SearchWalker, kwargs)     constructs SearchWalker(q=..., v=...)
5. ✗ walker init has no 'v' → TypeError → 500                          ← WRONG
```

The walker case comes from the PR description ("walker/function that doesn't declare them"). The issue itself only shows the function case.

### 3.4 Why it mattered

Issue #4661 (reproduced on `jaclang==0.10.2`, `jac-scale==0.1.9`) explains the impact:

- Any `@restspec` GET endpoint could be broken by a single extra parameter.
- Browsers add cache-busting parameters (`?v=...`, `?t=...`). CDNs and proxies add tracking parameters. Frameworks add state parameters (`?_data=...`). Users bookmark URLs with extra parameters.
- The issue's words: it "makes `@restspec` endpoints unusable in production behind CDNs, load balancers, or with real browser traffic".

## 4. The idea of the fix (one sentence)

> **Filter at the walker/function boundary, not in the shared router.** Read the target's signature once at registration, and at request time keep only the keys it declares, unless it declares `**kwargs` itself.

This is the right place because `jfast_api` serves other callers, like `render_page_callback`, that need every extra parameter. Only walker and function callbacks know which names their target accepts. It also matches FastAPI's own default of ignoring undeclared query parameters, which the issue asked for.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/serve.endpoints.impl.jac`: walker callback filter

```diff
     requires_auth = self.introspector.is_auth_required_for_walker(walker_name);
+    walker_cls = self.get_walkers()[walker_name];
+    _filter_walker_kwargs = False;                 # NEW: permissive by default
+    _walker_allowed_keys = set();
+    try {
+        _wsig = inspect.signature(walker_cls.init);
+        _has_var_kw = any(
+            p.kind == inspect.Parameter.VAR_KEYWORD for p in _wsig.parameters.values()
+        );
+        if not _has_var_kw {
+            _filter_walker_kwargs = True;
+            _walker_allowed_keys = {
+                name
+                for (name, p) in _wsig.parameters.items()
+                if name != 'self'                  # NEW: unbound init includes self
+                and p.kind not in (VAR_POSITIONAL, VAR_KEYWORD)
+            };
+        }
+    } except Exception {
+        _filter_walker_kwargs = False;             # NEW: fall back to old behaviour
+    }
 ...
         if nd {
             kwargs['_jac_spawn_node'] = nd;
         }
+        if _filter_walker_kwargs {
+            kwargs = {
+                k: v
+                for (k, v) in kwargs.items()
+                if k in _walker_allowed_keys or k == '_jac_spawn_node'   # NEW
+            };
+        }
         result = await self.execution_manager.spawn_walker(...)
```

**What:** At registration, the code reads the walker's `init` signature. If there is no `**kwargs`, it records the allowed names: every parameter except `self`, `*args` and `**kwargs`. On each request, after `nd` has been added, it rebuilds `kwargs` with only allowed names plus `_jac_spawn_node`.

**Why:** This fixes the walker crash in 3.3.

**Things to notice:**
- `_jac_spawn_node` must be kept on purpose. The filter runs on **every** request when filtering is on, not only when unknown parameters are present. Without the `or k == '_jac_spawn_node'` exception, every node-routed request would lose its node ID and the walker would start on the root. The code comment calls this guard "load-bearing, not redundant".
- `self.get_walkers()[walker_name]` sits outside the `try`. If the name were missing it would raise at registration. The callback already does the same lookup, so this is not a new failure mode.
- The "comment about self" commit (`fb54c59`) explains why walkers skip `self` and functions do not.

### 5.2 `jac-scale/jac_scale/impl/serve.endpoints.impl.jac`: function callback filter

```diff
+    func_obj = self.get_functions()[func_name];
+    _filter_func_kwargs = False;
+    _func_allowed_keys = set();
+    try {
+        _fsig = inspect.signature(func_obj);
+        _has_var_kw = any(p.kind == VAR_KEYWORD for p in _fsig.parameters.values());
+        if not _has_var_kw {
+            _filter_func_kwargs = True;
+            _func_allowed_keys = { name for (name, p) in _fsig.parameters.items()
+                                   if p.kind not in (VAR_POSITIONAL, VAR_KEYWORD) };
+        }
+    } except Exception { _filter_func_kwargs = False; }
 ...
+        if _filter_func_kwargs {
+            kwargs = { k: v for (k, v) in kwargs.items() if k in _func_allowed_keys };
+        }
         console.print(f"Executing function '{func_name}' with params: {kwargs}");
```

**What:** This does the same as 5.1 for free functions. There is no `self` to skip and no synthetic key to keep.

**Why:** This fixes the function crash in 3.2, which is the exact case in the issue.

**Things to notice:** The filter runs before the `console.print` log line. The logs now show only the parameters that were actually passed.

### 5.3 `jac-scale/jac_scale/impl/serve.endpoints.impl.jac`: `create_function_parameters` skips `*args`/`**kwargs`

```diff
     func_fields = self.introspector.introspect_callable(func_obj)['parameters'];
+    _var_param_names: set = set();
+    try {
+        _fsig = inspect.signature(func_obj);
+        _var_param_names = { name for (name, p) in _fsig.parameters.items()
+                             if p.kind in (VAR_POSITIONAL, VAR_KEYWORD) };
+    } except Exception { }
 ...
     for field_name in func_fields {
+        if field_name in _var_param_names {
+            continue;                               # NEW: don't register "kwargs" as a param
+        }
```

**What:** When building the FastAPI parameter list for a function, the code no longer registers `*args` or `**kwargs` as if they were named parameters.

**Why:** The code comment says `introspect_callable` does not filter them out. So a function like `passthrough_func(**kwargs)` would otherwise get a FastAPI parameter literally named `kwargs`. This change is what lets the `**kwargs` pass-through case (see the table in 6.3) work. Exactly how it failed before cannot be seen from the diff.

**Things to notice:** **The PR description does not mention this change.** It says only the two callback functions were changed. You should be ready to explain it. Walkers get no matching change, and the diff does not show whether walker parameter building has the same gap.

### 5.4 `docs/docs/community/release_notes/unreleased/jac-scale/5773.bugfix.md`: release note

+- **Fix: Unknown query parameters no longer crash `@restspec` endpoints**: Extra query parameters not declared in a walker or function signature (e.g. cache-busting `?v=...` appended by CDNs or browsers) are now silently dropped instead of triggering a `TypeError` and HTTP 500.

## 6. How execution flows after the PR

### 6.1 Server start: registering a walker endpoint

```text
create_walker_callback(walker_name)
├─ requires_auth = introspector.is_auth_required_for_walker(...)
├─ walker_cls = get_walkers()[walker_name]                       ← NEW
├─ try inspect.signature(walker_cls.init)                        ← NEW
│   ├─ has **kwargs?  → filter OFF
│   └─ no **kwargs    → filter ON, allowed = params − {self, *args, **kwargs}
├─ on exception       → filter OFF (permissive)                  ← NEW
└─ return callback (closure holds filter flag + allowed set)
```

Function registration is the same, using `inspect.signature(func_obj)` and without the `self` step. `create_function_parameters` now skips `*args`/`**kwargs` names (← NEW).

### 6.2 Request to a walker endpoint

```text
GET /search?q=hello&v=1708012345
├─ FastAPI + jfast_api build kwargs = {q, v}
├─ callback: auth check (unchanged)
├─ if nd: kwargs['_jac_spawn_node'] = nd
├─ if filter ON: keep k in allowed or k == '_jac_spawn_node'     ← NEW
│      kwargs = {q: "hello"}
└─ spawn_walker(SearchWalker, kwargs) → 200, reports [{"q":"hello"}]
```

### 6.3 Request to a function endpoint

```text
GET /items?category=books&v=1708012345
├─ kwargs = {category, v}
├─ callback: auth check (unchanged; returns 401 if needed)
├─ if filter ON: keep k in allowed                               ← NEW
│      kwargs = {category: "books"}
├─ console.print(... kwargs)
└─ execute_function(get_items, kwargs) → 200 {"category":"books"}
```

| Scenario | Before | After |
|---|---|---|
| Function, unknown query parameter | 500 `TypeError` | 200, extra dropped |
| Walker, unknown query parameter | 500 `TypeError` | 200, extra dropped |
| Function declaring `**kwargs` | Extras forwarded | Extras still forwarded; `kwargs` no longer registered as a FastAPI parameter |
| Walker routed to a node (`nd`) | Node ID passed | Node ID still passed (explicit exception) |
| Signature can't be inspected | Extras forwarded | Extras forwarded (no change) |
| `render_page_callback` / other `add_endpoint` users | Extras forwarded | Unchanged |

**Behaviour change users will notice:** Unknown query parameters are now ignored silently. A typo such as `?catgory=books` no longer raises an error. The declared parameter just falls back to its default, or fails validation if it is required.

## 11. Questions your senior might ask

**Q: Why not just remove `extra_query_params_code` from `jfast_api`?**
A: `render_page_callback` in `serve.static.impl.jac` (`def callback(page_name: str, **kwargs)`) needs every extra query parameter forwarded to the page renderer. Filtering only in the walker and function callbacks fixes the crash without breaking it.

**Q: Why compute the allowed keys at registration instead of per request?**
A: The signature never changes after startup. Calling `inspect.signature` once and keeping the result in the closure avoids repeated reflection. Each request only does a set-membership filter.

**Q: What if a walker or function wants arbitrary query parameters?**
A: If it declares `**kwargs`, `_has_var_kw` is true, filtering stays off, and everything is forwarded. The `passthrough` test covers this for functions.

**Q: Why is `_jac_spawn_node` special-cased?**
A: The callback adds it from the `nd` path parameter. It is not a walker field, so it is never in `_walker_allowed_keys`. Without the exception, every node-routed request would lose its target node, because the filter runs on all requests, not just ones with extra parameters.

**Q: Does the test prove that guard works?**
A: Not fully. The unknown parameter is in the body, which FastAPI drops earlier. And `TaggedWalker` reports the same output whether it starts on the given node or on the root. You deferred the fix to #6615.

**Q: Why the `self` asymmetry between walkers and functions?**
A: `walker_cls.init` is read unbound from the class, so its signature includes `self`. Free functions have no `self`. The comment added in `fb54c59` explains this.

**Q: What happens if `inspect.signature` throws?**
A: The flag stays `False`, so the endpoint behaves exactly as before and forwards everything. This is a "no regression" fallback, but it also means such endpoints could still hit the original crash.

**Q: Why did `create_function_parameters` change?**
A: `introspect_callable` returns `*args`/`**kwargs` as ordinary fields. Without skipping them, a `**kwargs` function would register a FastAPI parameter named `kwargs`. The diff doesn't show the exact earlier failure, only the comment explaining the skip.

**Q: Could silently dropping parameters hide client bugs?**
A: Yes. A misspelled parameter is now ignored instead of raising an error. That is the behaviour the issue asked for, and it matches FastAPI's default. Required parameters still fail validation when they are missing.

**Q: Do walker endpoints need the same `*args`/`**kwargs` skip in their parameter builder?**
A: This PR doesn't touch the walker parameter builder, and the diff doesn't show whether it has the same gap. It is worth checking separately.
