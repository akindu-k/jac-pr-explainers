## 1. The short version

`jac scale deploy` reads your project's `jac.toml` on your machine. Any `${VAR}` in it is filled in from your machine's environment variables. The pods later read the same `jac.toml` again, but they fill in `${VAR}` from **their own** environment, which is different.

**The bug: a variable exported only on the deploy host made the deploy look clean, but the pod could not resolve it at boot.** On `main` the pod quietly used the literal text `${ECR_REGISTRY}` as the value. After the upcoming #9045, the pod would crash on start instead. jacBuilder's real `jac.toml` has four such values (`ECR_REGISTRY`, `K8S_SERVICE_ACCOUNT_NAME`, `GITHUB_PUBLIC_LINK`, `SHARED_DATA_PVC`).

**The fix: before anything is created in the cluster, you rebuild each pod's real environment from the manifests the deploy generates, resolve every `${...}` in the config files that pod will load against only that environment, and fail the deploy with a full list if anything is missing.** Example output:

```
[ERROR] Error: --dry-run failed: jac.toml reads environment variables the deployed pods will not have, so these settings cannot resolve at boot:
  jac.toml: scale.kubernetes.image_registry: Environment variable ECR_REGISTRY is not set (every pod)
Supply each one through [scale.secrets] or the app's env, or give it a ${VAR:-default}.
```

This is a **breaking change** on its own. Projects that deploy fine today with a host-only bare `${VAR}` will now fail.

**Status:** Merged on 2026-09-15. Approved by @MusabMahmoodh. All CI checks that ran passed. It must land before #9045.

## 3. The problem, step by step

### 3.1 The setup

- **Your machine** runs `jac scale deploy`. It loads `jac.toml`, filling in `${...}` from your shell.
- **The bundle** ships `jac.toml`, plus any `jac.<profile>.toml` and `jac.local.toml`, into the pods.
- **Each pod** gets env from the Deployment manifest (`env`, `envFrom` Secret, `JAC_DB_URL` via `secretKeyRef`), plus a few Kubernetes always sets.
- **On pod boot** the loader reads the shipped files again and fills in `${...}` from the pod env.

### 3.2 What went wrong: host-only variable

```text
1. Laptop: export ECR_REGISTRY=123.dkr.ecr...
2. jac.toml: image_registry = "${ECR_REGISTRY}"
3. jac scale deploy --dry-run → host resolves image_registry = "123.dkr.ecr..."
4. Dry run reports: OK                                   ← WRONG: checked against host env only
5. Real deploy: jac.toml shipped into pod as-is
6. Pod env: K8S_APP_NAME, K8S_NAMESPACE, peer URLs, secret keys, ... (no ECR_REGISTRY)
7a. On main: loader catches ValueError → image_registry = "${ECR_REGISTRY}" (literal text)
7b. After #9045: loader raises → pod crash-loops
```

### 3.3 What went wrong: the same, hidden in an overlay

@greptile-apps found this case. Your first commit only checked the root and nested `jac.toml`.

```text
1. jac.toml: [environment] default_profile = "prod"
2. jac.prod.toml: prod_only = "${PROD_ONLY}"   (shipped, merged at boot)
3. Check (commit 59470d2) looks only at jac.toml → nothing reported   ← WRONG
4. Pod loads jac.prod.toml → PROD_ONLY unresolved
```

Fixed in 47cb6fc.

### 3.4 What went wrong: check ran after provisioning on a real deploy

@MusabMahmoodh found this case.

```text
1. deploy(): runtime preflight
2. DatabaseProvisioner.provision → namespace + Postgres StatefulSet + secrets now exist
3. generate_manifests → new check fails on ECR_REGISTRY      ← WRONG: too late
4. User gets an error, and leftover Postgres stays in the cluster
```

Fixed in b7a34d5.

### 3.5 Why it mattered

- `--dry-run` said "clean" when the pod could not resolve the config. That is the same false signal #8773 complained about for `:?`.
- Once #9045 makes the loader strict, every jacBuilder pod would crash, because of its four host-only values.
- On `main` the cost was quieter: settings got garbage literal values.

## 4. The idea of the fix (one sentence)

> **Check the config against the pod's environment, not the host's.** For each generated pod, build its env from the manifests the deploy actually produces, resolve every `${...}` in every config file that pod loads, and stop the deploy before provisioning if anything is missing.

This avoids a hand-kept list of "variables pods have". It derives the env from the real manifests, so it does not drift from what pods get. @MusabMahmoodh called this out as "the right shape".

### 5.2 `jac/jaclang/scale/injector/bundle.jac`: list unresolved references in one TOML text

```diff
+def unresolved_toml_references(text: str, environ: dict[str, str]) -> list[str] {
+    import from jaclang.project.config { interpolate_env_vars }
+    found: list[str] = [];
+    def collect(item: any, path: str) {
+        if isinstance(item, dict) { ... collect(value, f"{path}.{key}" ...) }
+        elif isinstance(item, list) { ... collect(element, f"{path}[{i}]") }
+        elif isinstance(item, str) {
+            try { interpolate_env_vars(item, environ); }
+            except ValueError as e { found.append(f"{path}: {e}"); }
+        }
+    }
+    collect(tomllib.loads(text), "");
+    return found;
+}
```

**What:** Parses the TOML and walks every value. It tries to resolve each string against `environ` and collects `"dotted.path: error"` for each failure, e.g. `scale.gateway.shared_volumes[0].name: Environment variable SHARED_DATA_PVC is not set`.

**Why:** It gives the check a precise setting path for each problem, and it collects all problems instead of stopping at the first.

**Things to notice:**
- Only values are checked, not keys.
- `tomllib` is used without a local import, so it must already be imported at the top of `bundle.jac`. That part is not in the diff.

**What:** For every Deployment, this:
1. Builds the pod env from the container's `env` and the user Secret's keys, plus the three variables Kubernetes always sets, plus a predicted `JAC_DB_URL` when a database is configured.
2. Picks the files the pod loads: root `jac.toml`, the nearest nested `jac.toml` for the pod's `JAC_SV_FILE`, and for each of these the active profile overlay and `jac.local.toml`, if they ship.
3. Resolves every string in them against only that env.
4. Groups the problems by setting, notes which pods each one affects, and raises one `ValueError` listing them all.

**Why:**
- This is the core fix for 3.2.
- The overlay handling (`_pod_tomls`) fixes 3.3 (commit 47cb6fc).
- `check_pod_config` plus the `database_enabled()` prediction make 3.4 possible (commit b7a34d5).

**Things to notice:**
- **Values matter for resolution.** `env` entries keep their real value, so `${K8S_APP_NAME}` resolves to the real app name. Entries using `valueFrom` (like `JAC_DB_URL`) count as present with `""`.
- **Skip, don't guess.** Any `envFrom` that is not the user Secret makes `_pod_environ` return `None`, and that pod is not checked at all. This avoids false failures from a ConfigMap added by `deployment_overlay`.
- **`JAC_DB_URL`.** It used to be predicted only under dry run (per your reply to @MusabMahmoodh). Now it is predicted whenever `database_enabled()`. Before provisioning, its `secretKeyRef` env entry does not exist yet.
- **Service-link variables** (`FOO_SERVICE_HOST`) are deliberately not counted. Users can write `${FOO_SERVICE_HOST:-}`.
- **Inactive profiles** are not checked, because the pod never reads them.
- **Profile choice** comes from `JAC_PROFILE` in the pod env, else `default_profile` from that same toml. For a nested project it reads the nested toml's `[environment]` table.
- **Real deploys run the check twice:** once in `check_pod_config` before provisioning, and again at the end of `generate_manifests`.

## 11. Questions your senior might ask

**Q: Why not keep a list of variables the pods have?**
Because it would drift. You read each pod's env from the Deployment manifests the builder actually generates, so new env vars are picked up automatically.

**Q: Can this fail a deploy that would actually boot?**
You guarded three cases:
- `JAC_DB_URL` is predicted when a database is configured.
- Pods with unknown `envFrom` sources are skipped.
- `${1}` stays literal.

Two strict cases remain on purpose, `${1:?msg}` and service-link variables, and both have an escape: `:-`.

**Q: Why does a real deploy run the check before provisioning, and run it twice?**
Before, a refused config left a namespace and Postgres behind. `check_pod_config` builds only pod specs, Deployments and the user Secret, so the early run is cheap. The second run inside `generate_manifests` is what protects `--dry-run` and `preview()`.

**Q: Why is `${1:?usage}` an error but `${1}` is not?**
`${1}` has no other way to be written, and nothing can export `1`. `:?` explicitly asks to fail when the value is missing, and #9045's loader does fail on it. The check has to agree with the loader the pod runs.

**Q: Which config files does a pod load?**
- The root `jac.toml`.
- The nearest nested `jac.toml` for its `JAC_SV_FILE`.
- For each of those, `jac.<profile>.toml` for the active profile (from `JAC_PROFILE` or `default_profile`) and `jac.local.toml`, if they ship in the bundle.

**Q: Does this change behaviour on `main` before #9045?**
Yes. It is breaking. A host-only bare `${VAR}` that pods never read deployed fine before and now fails. That is why the note is `breaking`.

**Q: Why are only the first of two missing variables in one string reported?**
`interpolate_env_vars` raises on the first missing match inside `re.sub`. Every other setting is still listed. This is a documented known limitation.

**Q: What if a user adds a ConfigMap through `deployment_overlay`?**
`_pod_environ` returns `None` for any `envFrom` other than the user Secret, so that pod is skipped rather than guessed at. Its config is not checked.

**Q: Does the check ever read `os.environ`?**
No. It always passes an explicit env to `interpolate_env_vars`. The new `test_config.jac` test proves that a variable set only in the process env is ignored.
