## 1. The short version

`jac start` runs an HTTP API server for a Jac app. Its docs page (`jac_serve.md`) already described `POST /user/register` and `POST /user/login`. It did not describe any way to read or change an account after creating it.

**The docs and release notes had nothing about three user-management endpoints: `GET /user/info`, `PUT /user/username` and `PUT /user/password`.** A reader had no request format, response format or error codes for them.

**You added 180 lines to `jac_serve.md` and a 6-line entry to the jaclang 0.9.9 release notes.** The new docs cover each endpoint with headers, request and response bodies, error codes and a `curl` example. They also add a summary table, a "Security Features" list and a four-step example shell workflow.

The PR changes no code. The description says "Added new authenticated endpoints to the API server", and commit `0d4df83` is titled "feat: Add user management endpoints…". Even so, the diff contains only the two Markdown files. From this PR alone, you cannot confirm that the endpoints exist or behave as documented.

**Status:** Merged on 2026-01-18, the same day it was opened. Nobody reviewed it. All six CI checks passed.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac / jaclang | The Jac programming language and its core package. Release notes are grouped by jaclang version. |
| `jac start` | The command that starts the built-in HTTP API server for a Jac app. |
| `jac_serve.md` | The docs page (`docs/docs/learn/tools/jac_serve.md`) that describes that server's endpoints. **This is what the PR adds to.** |
| Release notes (`jaclang.md`) | The per-version changelog. New items go under "jaclang 0.9.9 (Unreleased)". |
| Endpoint | A URL plus an HTTP method that the server answers, e.g. `GET /user/info`. |
| HTTP methods GET / POST / PUT | GET reads data. POST creates something (register, login). PUT updates something (username, password). |
| Bearer token | A secret string the server gives you at register or login. You send it back on each request as `Authorization: Bearer <token>`. |
| Authenticated / protected endpoint | An endpoint that rejects requests without a valid token. |
| `root_id` | The ID of the user's root node. A node is an object in Jac's graph, and each user's data hangs off their own root. Returned by `/user/info`. |
| 400 / 401 / 403 | HTTP status codes. 400 means bad input. 401 means a missing or invalid token. 403 means the token is valid but you are not allowed (e.g. editing another user). |
| SHA-256 | A hash function. The docs say passwords are stored as SHA-256 hashes. |
| `main.db` | The SQLite file where, per the previous release note, `jac start` now stores users together with app data. |
| `curl` / `jq` | Command-line tools. `curl` sends HTTP requests. `jq` pulls fields out of JSON, e.g. `jq -r '.token'`. |
| jac-scale | The plugin that deploys Jac apps to Kubernetes. It overrides the basic user system in production, per the existing release note. |
| pre-commit.ci | A bot that runs formatting hooks and pushes fixes. It made commit `742f770`. |

## 3. The problem, step by step

### 3.1 The setup

- **Server:** `jac start` exposes user endpoints. The docs list `/user/register` and `/user/login`, followed by a section called "Protected Endpoints (Authentication Required)".
- **Docs:** `jac_serve.md` explains each endpoint with headers, body and a `curl` example.
- **Changelog:** `jaclang.md` lists changes for the unreleased 0.9.9. It already mentions moving users into `main.db`.

### 3.2 What was missing

This is a docs gap, not a bug. Here is what a user experienced before the PR:

```text
1. User reads jac_serve.md → sees POST /user/register, POST /user/login
2. User registers "alice" → gets a token
3. User wants to show "logged in as alice" in their app → no documented endpoint
4. User wants to rename or change password → no documented endpoint   ← GAP
5. User must read the server source, or guess the URL and body fields
6. Release notes for 0.9.9 don't mention the endpoints at all         ← GAP
```

### 3.3 Why it mattered

There is no linked issue and there are no comments, so the PR does not say who asked for this. The general cost is that undocumented endpoints are effectively hidden. The request bodies are also not guessable. For example, `PUT /user/username` needs `current_username` as well as the token.

## 4. The idea of the fix (one sentence)

> **Document the three account endpoints where the others already live.** Add a reference entry for each endpoint to `jac_serve.md`, plus a summary table and an example workflow, and announce them in the 0.9.9 release notes.

The new entries follow the same format as the existing `/user/login` entry. That keeps the page consistent and puts the new endpoints where readers will look for them.

## 5. Every code change, explained

### 5.1 `docs/docs/learn/tools/jac_serve.md`: reference for the new endpoints

```diff
+#### GET /user/info
+Get information about the currently authenticated user.
+Authorization: Bearer YOUR_TOKEN_HERE
+{ "username": "alice", "token": "abc123...", "root_id": "uuid-of-root-node" }
+- **401 Unauthorized**: Invalid or missing authentication token
+{ "ok": false, "error":  { "code": "UNAUTHORIZED", "message": "Invalid or expired token" } }
+
+#### PUT /user/username
+{ "current_username": "alice", "new_username": "alice_2024" }
+→ { "username": "alice_2024", "token": "abc123.. .", "root_id": ... }   # stray space in "abc123.. ."
+- 400 taken/validation, 401 bad token, 403 another user's username
+
+#### PUT /user/password
+{ "username": "alice", "current_password": "secret123", "new_password": "newsecret456" }
+→ { "username": "alice", "message": "Password updated successfully" }
+- 400 wrong current password/validation, 401 bad token, 403 another user's password
```

**What:** Each endpoint gets a `####` block with headers, request body, response, a `curl` example and error codes. Only `/user/info` shows the JSON shape of an error response.

**Why:** This fills the missing reference for reading and updating an account.

**Things to notice:**
- Both PUT endpoints ask for the username in the body, even though the token already identifies the user. The documented 403 implies the server compares the two. The code that does this is not in this PR.
- `/user/info` returns the `token` itself. That is worth knowing if a senior asks about exposing secrets.
- The rename response returns a `token`. The docs don't say whether it is the same token or a new one.

```diff
+## User Management Endpoints
+| `/user/register` | POST | No  | Create new user account |
+| `/user/login`    | POST | No  | Authenticate and get token |
+| `/user/info`     | GET  | Yes | Get current user information |
+| `/user/username` | PUT  | Yes | Update username |
+| `/user/password` | PUT  | Yes | Update password |
+**Security Features:** Bearer tokens; SHA-256 password hashing;
+  users can only modify their own account; tokens validated on every request
+**Example Workflow:**
+TOKEN=$(curl -s -X POST .../user/register ... | jq -r '. token')   # should be '.token'
+curl http://localhost:8000/user/info -H "Authorization: Bearer $TOKEN"
+curl -X PUT .../user/username -H "Authorization:  Bearer $TOKEN" ...   # double space
+curl -X PUT .../user/password ... "username": "alice_updated" ...
 
 ### Protected Endpoints (Authentication Required)
```

**What:** Adds a quick-reference table, four security claims and a register → info → rename → change-password script.

**Why:** It gives readers an overview and a runnable end-to-end example.

**Things to notice:**
- **Heading levels.** The new `## User Management Endpoints` is a level-2 heading. It sits just before the existing `### Protected Endpoints`, so that section now appears *under* "User Management Endpoints" in the page outline. The diff doesn't show which heading sits above the new `####` blocks, so the full effect on the outline can't be confirmed here.
- **The workflow script likely fails at step 1.** `jq -r '. token'` has a space after the dot. jq expects `.token`, and the spaced form will likely be a syntax error. Every later step then sends an empty `$TOKEN`.
- **The workflow makes assumptions you can't check here.** It assumes `/user/register` returns `token`. It also keeps using the same `$TOKEN` after the rename, which implies the token survives a username change. Neither is shown in this diff.
- **Formatting noise.** There are double spaces in `"Authorization:  Bearer"`, `"error":  {` and `"root_id":  "…"`. These are harmless: servers trim header whitespace and JSON ignores it. They are still untidy, and the `"abc123.. ."` typo is visible to readers.
- **Security claim.** "Passwords are hashed using SHA-256" is a public statement about the code. The code isn't in this PR. Plain SHA-256 is also generally considered weak for password storage compared with a salted, slow hash. Expect a question on this.

## 11. Questions your senior might ask

**Q: Where is the code for these endpoints?**
Not in this PR. It only touches two Markdown files. You should name the PR or commit that implemented them. This PR doesn't show it.

**Q: Why does the description say you added endpoints?**
It was worded as a feature description. The actual change is docs only. The description should be corrected.

**Q: Did you run the example workflow?**
Answer honestly. As written, `jq -r '. token'` will likely fail, so `$TOKEN` ends up empty and the later calls return 401.

**Q: Why do the PUT endpoints need a username in the body when the token already identifies the user?**
The docs imply the server checks that the body username matches the token and returns 403 otherwise. Confirm this against the implementation.

**Q: Does renaming invalidate the token?**
The docs don't say. The workflow reuses the old token after the rename, which implies it stays valid. Verify in the code.

**Q: Is SHA-256 safe for passwords?**
Unsalted, fast SHA-256 is weaker than bcrypt, scrypt or argon2. The docs now state it publicly, so confirm it is accurate and consider whether the team wants to keep advertising it.

**Q: Why does `/user/info` return the token?**
That is what the docs show. It only goes to a caller who already holds the token, but it is worth confirming that this is intended.

**Q: Does this apply to jac-scale deployments too?**
The release note is under jaclang and says `jac start`. The neighbouring note says jac-scale overrides the user system in production. Whether jac-scale supports these endpoints can't be told from this PR.

**Q: Why was it merged without review?**
There are no reviews on the PR, and it was opened and merged the same day. Be ready to propose the follow-up fixes listed above.
