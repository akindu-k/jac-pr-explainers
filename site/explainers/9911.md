## 1. The short version

jac-scale stores graph nodes and edges ("anchors") in three tiers. L1 is per-request memory, L2 is Redis (a shared cache) and L3 is MongoDB (the durable store). Readers try Redis first and fall back to Mongo. Writers save to Mongo and then update or clear Redis.

**On the 0.34.x line, Redis could end up holding an older copy of a node than Mongo, and every later read got that stale copy.** There were two ways in:

- **A field-only save** wrote just the changed fields to Mongo, then pushed the request's *whole* in-memory node to Redis. That copy could carry an old value for a field another request had just saved.
- **A cache-miss refill** read Mongo, and then wrote that snapshot to Redis without any check. If a save finished in between, the newer state was overwritten with the older one.

The issue (#9840) reproduces both. For example, Mongo held `pointer='sandbox-one'` while Redis and a fresh reader saw `pointer=''`.

**You fixed it in two ways. Field updates now delete the Redis key instead of rewriting it. Refills only write to Redis if they still hold a short per-key "lease" that any write clears.** You also stopped `execute_plan` (query results) from refilling Redis, because it cannot take a lease for ids it does not know in advance.

**Status:** Open, targeting `release/jaclang-0.34.21-prep`. There are no human reviews yet. The Greptile bot gave 5/5 confidence, and both of its inline comments are addressed in later commits. The only reported check is Greptile Review (success). The real test suite did not run upstream, because this branch's `ci.yml` only runs on PRs to `main`.

## 3. The problem, step by step

### 3.1 The setup

- Two requests (possibly on different pods) each have their own L1 but share Redis and Mongo.
- At commit time, `ScaleTieredMemory.commit` applies intents to Mongo:
  - Deletes and edge deltas then **invalidated** Redis. Edge deltas have done this since #6297.
  - Everything else, including `FIELD_UPDATE`, called `self.l2.put(intent.anchor)` with the full in-memory anchor.
- On a read miss, `get` / `batch_get` / `execute_plan` read Mongo and then called `l2.put(anchor)` without any check.

### 3.2 What went wrong: field update (schedule A)

```text
State: Mongo {pointer:'', stamp:'seed'}   Redis {pointer:'', stamp:'seed'}
1. Req1 loads node into its L1           Req1 L1 {'', 'seed'}
2. Req2 loads node into its L1           Req2 L1 {'', 'seed'}
3. Req2 sets stamp='second-request'       Req2 L1 {'', 'second-request'}
4. Req1 sets pointer='sandbox-one'        Req1 L1 {'sandbox-one', 'seed'}
5. Req1 commits: Mongo put_partial(pointer) → Mongo {'sandbox-one','seed'}
   then Redis put(full L1)                → Redis {'sandbox-one','seed'}
6. Req2 commits: Mongo put_partial(stamp) → Mongo {'sandbox-one','second-request'}  ✓
   then Redis put(full L1)                → Redis {'', 'second-request'}           ✗ WRONG
7. Any later reader hits Redis → sees pointer=''  (Mongo says 'sandbox-one')
```

`_refresh_if_stale` does not save Req2. It keeps dirty in-flight L1 anchors, so Req2 never sees Req1's field. The PR does not change this.

### 3.3 What went wrong: delayed refill (schedule B)

```text
State: Mongo {'', 'seed'}   Redis: (empty, key evicted)
1. Reader misses Redis
2. Reader reads Mongo                     → snapshot {'', 'seed'}
3. Writer sets pointer='sandbox-two', commits
   Mongo {'sandbox-two','seed'};  Redis put → {'sandbox-two','seed'}
4. Reader does Redis SET(snapshot)        → Redis {'', 'seed'}   ✗ WRONG (older than Mongo)
5. Later readers see pointer=''
```

The same window exists in `batch_get` and in `execute_plan`.

### 3.4 Why it mattered

- Redis has no version check, and every reader prefers Redis. One bad write therefore poisons all reads until the key expires or is invalidated.
- Mongo is correct, so the data looks fine in the database while the app reads the wrong value.
- #9840 confirmed both schedules on the official v0.34.20 and v0.34.21 binaries, using real MongoDB 7.0.43 and Redis 7.4.11.
- The issue says plainly that this "does not establish the original cause of jacBuilder#2152". It also says "cross-process validation and backport disposition remain pending."
- `main` no longer has this Mongo/Redis hierarchy (#7947, #8000), so the fix only matters for 0.34.x users.

## 4. The idea of the fix (one sentence)

> **Never write a possibly-stale whole anchor to Redis.** Field updates delete the cache entry, and readers only refill if no write happened since they started reading Mongo.

Deleting on field update is safe because the next reader rebuilds the entry from Mongo, which is always right. The lease turns "nothing changed since my read" into an atomic Redis check, without adding versions to anchors.

```diff
+impl RedisBackend.lease(ids) -> dict[UUID, str] {
+    leases = {id: uuid4().hex for id in ids};
+    pipe = self.redis_client.pipeline(transaction=False);
+    for (id, token) in leases.items() {
+        pipe.set(_lease_key(storage_key(to_uuid(id))), token, px=_REFILL_LEASE_MS, nx=True);  # first taker wins
+    }
+    taken = pipe.execute();
+    return {id: leases[id] for (id, ok) in zip(leases, taken) if ok};
+}
+impl RedisBackend.fill(anchor, token) {
+    if self.redis_client is None or token is None { return; }
+    self.put_count += 1;                                         # counted like put (Greptile)
+    span = start_memory_span("memory.put redis", {...});         # same span as put
+    self.redis_client.eval(_FILL_IF_LEASED, 2, key, _lease_key(key), token, data, ttl);

```

**What:**
- `lease` takes one random-token lease per id with `SET NX PX 10000` and returns only the ones it won.
- `fill` runs the Lua script. The script writes the anchor only if the lease key still holds this reader's token, and it removes the lease in the same step.
- `put` and `delete` now also remove the lease key, atomically with the main write.

**Why:** A write between "lease" and "fill" deletes the lease, so the Lua check fails and the stale snapshot is dropped.

**Things to notice:**
- `nx=True` came in the last commit (bc9c6af, "only the first concurrent miss takes the refill lease"). Without it, a second reader could overwrite the first reader's token. The first reader's correct fill would then be cancelled for no reason.
- `put_count` and the span count fill *attempts* that held a token, including ones the script rejected. Fills without a token are not counted.
- All Redis errors are logged at debug level and swallowed. A failed fill just leaves the cache cold.
- **Possible issue with Redis Cluster:** the Lua script, the two-key `DEL` and the MULTI pipeline all touch both `anchor:<id>` and `lease:anchor:<id>`. In Redis Cluster, these keys can hash to different slots, and Redis would return a CROSSSLOT error. Because errors are swallowed, refills would then silently never happen. The PR does not say whether jac-scale supports Cluster mode, so this needs an answer. Hash-tagged keys would avoid it.
- `eval` sends the full script on every call. `register_script`/EVALSHA would be cheaper, but this is minor.

## 6. How execution flows after the PR

### 6.1 Committing a field update

```text
ScaleTieredMemory.commit()
├─ MongoBackend applies FIELD_UPDATE via put_partial (dirty fields only)
└─ intent is delete OR FIELD_UPDATE?                       ← CHANGED
   ├─ l2.invalidate(id)  → Redis key removed (and lease, if invalidate→delete)
   └─ publish_invalidation(id) → other pods drop it from L1
```

### 6.2 Single read: `ScaleTieredMemory.get(id)`

```text
get(id)
├─ _refresh_if_stale(id)
├─ no Redis, or id in L1 → super.get(id)                   ← CHANGED (explicit split)
├─ Redis hit → store in L1, return
└─ Redis miss
   ├─ lease([id])  SET lease:anchor:<id> token NX PX 10000 ← NEW
   ├─ Mongo get(id)
   │  ├─ found → store in L1
   │  │   └─ fill(anchor, token)                          ← NEW
   │  │      ├─ token None → skip
   │  │      └─ Lua: lease==token ? DEL lease; SET anchor : skip
   │  └─ return anchor
   └─ not found → return None (lease expires on its own)
```

### 6.3 Batch read: `batch_get(ids)`

```text
batch_get(ids)
├─ L1 / Redis lookups → l2_misses
└─ l2_misses and Mongo
   ├─ lease(l2_misses) (only winners get tokens)           ← NEW
   ├─ Mongo batch_get(l2_misses)
   └─ for each result: L1 store; fill(anchor, token)      ← CHANGED (was put)
```

### 6.4 Query: `execute_plan`

```text
execute_plan(plan)
├─ Mongo query
└─ each anchor: L1 store if absent; yield               ← CHANGED (no Redis put)
```

### 6.5 Any write or delete to Redis

```text
RedisBackend.put   → MULTI: SET/SETEX anchor; DEL lease; EXEC   ← CHANGED
RedisBackend.delete→ DEL anchor lease                           ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| Two requests update different fields | Redis keeps the last committer's full copy; the other field is stale | Redis key deleted; next read gets Mongo's merged state |
| Write lands between a reader's Mongo read and its refill | Stale snapshot overwrites Redis | Lease cleared by the write; refill skipped |
| Two readers miss at once | Both `SET` | First takes lease and fills; second reads Mongo without filling |
| Query results | Written to Redis | L1 only |
| Two full-anchor creates/upserts racing | Possible reorder | Still possible (out of scope) |

**Behaviour users may notice:**
- Redis hit rate drops for nodes that get field updates often, and for nodes only reached through queries.
- Mongo read load rises accordingly.

## 11. Questions your senior might ask

**Q: Why invalidate on field update instead of writing the merged anchor?**
The writer's L1 copy may hold other requests' old fields, and building a correct merged copy would need a Mongo re-read. Deleting the key is simpler, and the next reader refills from Mongo, which is correct. This also matches the edge-delta path from #6297.

**Q: What stops a refill from overwriting a newer write?**
The reader takes `lease:anchor:<id>` before reading Mongo. Every `put` and `delete` removes that lease in the same atomic step as its write. The Lua `fill` only writes if the lease still holds the reader's token, so any write in between cancels the fill.

**Q: Does the field-update path actually clear the lease? It calls `invalidate`, not `delete`.**
The diff doesn't show `invalidate`. The delayed-refill rows pass because the writer's field-update commit cancels the reader's fill, which implies `invalidate` goes through `delete`. Confirm this in the code.

**Q: What if two readers miss at the same time?**
`SET NX` lets only the first take the lease. The second gets no token, reads Mongo, and returns correct data without filling Redis. The final assertion in the test checks this.

**Q: What if a reader crashes holding a lease?**
The lease expires after `_REFILL_LEASE_MS` = 10 s. Until then nobody refills that key, but reads still go to Mongo and stay correct.

**Q: Why remove the Redis put from `execute_plan`, and does it affect non-scale code?**
Query ids aren't known before the Mongo read, so no lease can protect the fill. The change is in base `TieredMemory`, so it applies to every subclass. Query results are no longer cached in Redis.

**Q: Will this work on Redis Cluster?**
The script and pipelines touch `anchor:<id>` and `lease:anchor:<id>` together, which can be different hash slots. The PR doesn't say whether Cluster is supported. Errors are swallowed, so a CROSSSLOT failure would silently stop refills rather than crash.

**Q: What's still not fixed?**
Two concurrent full-anchor writers (create/upsert) can still reach Redis in a different order than Mongo. Separately, the issue's `_refresh_if_stale` point is unchanged: dirty L1 anchors are not merged with newer fields. That doesn't hurt Redis anymore, because field updates no longer write to it.

**Q: Why target `release/jaclang-0.34.21-prep` and not `main`?**
`main` removed the Mongo/Redis hierarchy (#7947, #8000). The bug exists only on 0.34.x.

**Q: How do you know the test fails without the fix?**
Fork run 37917790026 on unfixed 0.34.21 failed `field update` (Redis `pointer=''`, Mongo `'sandbox-one'`) and `delayed refill` (`''` vs `'sandbox-two'`). That run predates the `batch_get` row, so the failure of that row without the fix is not shown.
