# fix(scale): Redis never serves an anchor older than Mongo after a field update or a late refill (#9840)

[#9911](https://github.com/jaseci-labs/jac/pull/9911) by @akindu-k · opened 9 Oct 2026 · +176 −15 in 6 files

<!-- explainer -->

## In short

The jac-scale memory layer keeps nodes in MongoDB (the source of truth) and caches them in Redis. In two situations Redis could end up holding an older copy of a node than MongoDB, and every later read would get that stale copy. Your PR fixes both:
- A commit that changed only some fields now removes the Redis entry instead of writing the whole node.
- A cache refill now writes to Redis only if no write happened while it was reading MongoDB. This uses a short "lease" and an atomic Lua compare-and-set.

## Words to know

- **Anchor**: Jac's internal record for a node or edge. It holds the id, the fields (the "archetype"), edges and metadata. This is the object that gets cached and stored.
- **MongoDB / `MongoBackend`**: the database where anchors are stored for good. In this code it is the **L3** tier.
- **Redis / `RedisBackend`**: an in-memory key/value store shared by all pods. Here it is the **L2** cache. Anchors are stored under a key like `anchor:<id>`.
- **L1 (`__mem__`)**: a plain dictionary inside one execution context (one request). It holds the anchors that request has loaded.
- **`ScaleTieredMemory`**: the jac-scale class that ties L1, L2 and L3 together. It decides where to read from and what to write on commit.
- **`TieredMemory`**: the shared base class in `jaclang/runtimelib`. `ScaleTieredMemory` builds on it.
- **Pod**: one running copy of the app in Kubernetes. Several pods share the same Redis and MongoDB.
- **Cache**: a fast copy of data kept so you don't have to ask the slow database every time.
- **Cache miss / refill**: the data isn't in the cache, so you read it from MongoDB and then put it into Redis for next time.
- **Invalidate**: delete a cache entry so the next reader is forced to go to MongoDB.
- **Broadcast (`publish_invalidation`)**: a message sent through Redis to other pods, telling them to drop their own L1 copy of that anchor.
- **Write intent / `WriteOp.FIELD_UPDATE`**: on commit, each changed anchor gets an intent that says what kind of write it is: create, delete, field update, and so on.
- **`put_partial`**: the `MongoBackend` method that writes only the changed ("dirty") fields of an anchor, not the whole document.
- **Edge delta**: an existing special write path for edge-list changes. Since #6297 it already invalidates Redis instead of writing to it. Your fix copies that behaviour.
- **Race condition**: the result depends on which of two actions running at the same time finishes first.
- **Lease**: a short-lived Redis key `lease:anchor:<id>`. It holds a random token and means "I'm refilling this key." In this PR it expires after `_REFILL_LEASE_MS` = 10 000 ms.
- **`SET ... NX PX`**: a Redis command. `NX` means "set only if the key doesn't exist yet". `PX` sets an expiry time in milliseconds. You use it so only one reader can hold a lease at a time.
- **Lua script / compare-and-set**: Redis can run a small Lua script as one atomic step, so nothing else can run in the middle of it. "Compare-and-set" means "write the value only if some other value is still what I expect."
- **Pipeline**: sends several Redis commands in one round trip. With redis-py's default (`transaction=True`) the commands run together as a transaction (MULTI/EXEC).
- **TTL**: "time to live". After this many seconds Redis deletes the key by itself. It is set by the config value `redis_default_ttl`.
- **`execute_plan` / query plan**: the path that runs a query, for example "find nodes matching X", against the database. You don't know which ids come back until the query finishes.
- **testcontainers**: a library that starts real MongoDB and Redis in Docker containers for tests.
- **`patch.object`**: from Python's `unittest.mock`. It swaps out a method for the length of a `with` block. The test uses it to inject a write in the middle of a read.

## The problem

There were two separate bugs (A and B in your description).

**A. A field-only commit put a full, stale anchor into Redis.**

1. Request 1 loads node N into its L1. The node has `pointer=""` and `stamp="seed"`.
2. Request 2 loads the same node N into its own L1.
3. Request 2 sets `stamp="second-request"`. Request 1 sets `pointer="sandbox-one"`.
4. Request 1 commits. Mongo gets only `pointer` (through `put_partial`). Redis gets request 1's whole anchor: `pointer="sandbox-one"`, `stamp="seed"`.
5. Request 2 commits. Mongo gets only `stamp`, so Mongo is now correct: `("sandbox-one", "second-request")`. But Redis gets request 2's whole anchor, and that copy still has `pointer=""`.
6. From now on, every pod reads N from Redis and sees `pointer=""`. Request 1's change is lost for every cached read, even though Mongo has it.

**B. A late refill overwrote a newer write.**

1. A reader misses Redis and reads N from Mongo. It gets `pointer=""`.
2. Before the reader writes to Redis, a writer commits `pointer="sandbox-two"`. The commit updates Mongo and clears or updates Redis.
3. The reader now does its unconditional `SET` with the old snapshot. Redis holds `pointer=""` again.

This happened in `get`, `batch_get` and `execute_plan`.

Both bugs hit every user of jac-scale with Redis turned on and more than one request touching the same node. The damage lasts until the TTL expires, or forever if there is no TTL.

## The changes, one by one

### `jac/jaclang/scale/memory/impl/memory_hierarchy.redis.impl.jac`: lease and guarded fill

This is the core of the fix for bug B. You added two new `RedisBackend` methods and changed two existing ones.

**The Lua script `_FILL_IF_LEASED`:**

```lua
if redis.call('GET', KEYS[2]) ~= ARGV[1] then return 0 end
redis.call('DEL', KEYS[2])
if tonumber(ARGV[3]) > 0 then
    redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
else
    redis.call('SET', KEYS[1], ARGV[2])
end
return 1
```

- `KEYS[1]` is the anchor key and `KEYS[2]` is its lease key. `ARGV[1]` is the reader's token, `ARGV[2]` is the serialized anchor, and `ARGV[3]` is the TTL.
- Line 1: if the lease key doesn't hold *my* token, give up and write nothing. The lease may have been deleted by a write, expired, or been replaced by someone else's lease.
- Line 2: the lease has done its job, so remove it.
- Lines 3–7: write the anchor, with a TTL if one is configured.
- All of this runs as one atomic step. No write can slip in between the check and the `SET`.

`_lease_key(key)` just returns `f"lease:{key}"`.

**`RedisBackend.lease(ids)`** (new):
- It creates a random token (`uuid4().hex`) for each id.
- For each id it sends `SET lease:<key> token PX=10000 NX=True`. All commands go in one non-transactional pipeline.
- It returns only the ids whose `SET` succeeded. Because of `NX`, if another reader already holds the lease, you don't get one. This was the last commit, "only the first concurrent miss takes the refill lease." Without `NX`, a second reader could overwrite the first reader's token, and the first reader's correct refill would be skipped.
- If Redis fails, it returns `{}`. That means no lease, so there will be no fill.

**`RedisBackend.fill(anchor, token)`** (new):
- If there is no token, it does nothing.
- Otherwise it runs the Lua script with the anchor and the token.
- It increases `put_count` and opens a tracing span, the same way `put` does. Your second commit, "count lease-guarded refills", was about keeping these counters correct.

**`RedisBackend.put`** (changed):
- It now uses a pipeline: write the anchor (`setex` or `set`), then `delete(_lease_key(key))`, then `execute()`.
- Because `pipeline()` defaults to a transaction, both commands run together.
- This means any real write cancels any refill that is in progress for that key.

**`RedisBackend.delete`** (changed):
- It now deletes the anchor key and its lease key in one `DEL` call. Same reason as `put`.

One caveat you should be ready to explain: the field-update path calls `self.l2.invalidate(...)`, not `delete`. The diff doesn't show `invalidate`'s body. For the "delayed refill" test to pass (the writer in that test does a field update), `invalidate` must also clear the lease. Most likely it calls `delete`. Check this in the file before your review. Your description only says "`put` and `delete` clear the lease."

### `jac/jaclang/scale/memory/impl/memory_hierarchy.main.impl.jac`: commit, `get`, `batch_get`

**`ScaleTieredMemory.commit`** (fixes bug A):

```diff
-                if intent.is_delete() {
+                if intent.is_delete() or intent.op == WriteOp.FIELD_UPDATE {
                     self.l2.invalidate(intent.anchor.id);
                     cast(RedisBackend, self.l2).publish_invalidation(
```

- A field update now goes down the same branch as a delete. It removes the Redis key and broadcasts so other pods drop their L1 copy.
- It no longer writes the request's whole in-memory anchor, which might have old values for fields it didn't touch.
- The next reader refills from Mongo, which has the correct merged result.
- Creates still write through to Redis, as before.

**`ScaleTieredMemory.batch_get`**:
- Before reading the Redis misses from Mongo, it calls `lease(l2_misses)`.
- After the Mongo read, it calls `fill(anchor, leases.get(id))` for each id instead of the old `self.l2.put(anchor)` inside an empty `try/except`.
- An id with no lease simply isn't filled.

**`ScaleTieredMemory.get`**: this used to just call `super.get(id)`, the base `TieredMemory.get`, which did the unguarded refill. It now does its own lookup:
1. If there is no Redis, or the id is already in L1, use `super.get` as before.
2. Try Redis. On a hit, store the anchor in L1 and return it.
3. On a miss, take a lease for this id, read Mongo, store the result in L1, and `fill` it with the lease token.
4. If Mongo doesn't have it either, return `None`. The lease is left to expire after 10 s.

`_refresh_if_stale(id)` still runs first, as before.

### `jac/jaclang/runtimelib/impl/memory.impl.jac`: `execute_plan` stops refilling Redis

```diff

-            if self.l2 {
-                self.l2.put(anchor);
```

- Query results still go into L1, but no longer into Redis.
- Why: you can only take a lease *before* reading Mongo, and here you don't know the ids until the query has run. So there is no safe way to guard the fill, and you removed it.
- The cost is that queried anchors aren't warmed into Redis. A later `get` will refill them safely.

- It imports `uuid4` for the lease tokens.
- It adds `glob _REFILL_LEASE_MS: int = 10000`. A lease lasts 10 seconds, so a crashed reader can't block refills for that key forever.
- It declares `lease` and `fill` on `RedisBackend`.

## How it runs now

**Reading a node (`ScaleTieredMemory.get`):**
1. `_refresh_if_stale(id)` runs.
2. If the id is in L1, or there is no Redis, the base `get` handles it. (changed: this is now an explicit check)
3. `RedisBackend.get`: on a hit, the anchor is stored in L1 and returned. (changed: now done here directly)
4. On a miss, `RedisBackend.lease([id])` tries `SET lease:anchor:<id> <token> NX PX 10000`. (new)
5. `MongoBackend.get(id)` reads the anchor, and it is stored in L1.
6. `RedisBackend.fill(anchor, token)` runs the Lua script. It writes to Redis only if the lease still holds this token. (new)

**`batch_get`** follows the same steps for a list of ids, using one `lease` call and one `fill` per id. (changed)

**`execute_plan`**: the query runs, results go into L1, and nothing is written to Redis. (changed)

**Committing (`ScaleTieredMemory.commit`):**
1. Each write intent is processed.
2. For a delete or a field update, `l2.invalidate(id)` removes the Redis key (and, as far as the test implies, the lease). Then `publish_invalidation` tells the other pods. (changed: field updates now take this path)
3. Other writes, such as creates, go through `RedisBackend.put`. That writes the key and deletes the lease in one transaction. (changed: lease delete added)
4. Any refill that started before this write now fails its Lua check and writes nothing. (new)

## Tests

All changes are in `jac/jaclang/scale/tests/data/test_memory_hierarchy.jac`. The existing #6295 test was renamed to "L2 Redis never serves an anchor older than Mongo (issues 6295, 9840)". Its edge-delta part is unchanged. You added a loop and a lease check after it, so the file still has 28 tests.

**Helpers:**
- `_CacheWitness`: a tiny node with `pointer=""` and `stamp="seed"`.
- `_cache_pod()`: a fresh `ExecutionContext` with its own `ScaleTieredMemory`, set as the current context. It stands in for a separate request or pod with its own L1.
- `_seed_witness()`: creates a persistent root, connects a witness to it, commits (a create, so it writes through), and returns the witness id.

**Row "field update"** (`_field_update_race`):
- Two pods load the witness. The second sets `stamp="second-request"`, the first sets `pointer="sandbox-one"`. The first commits, then the second commits.
- A fresh pod must read `("sandbox-one", "second-request")`.
- This proves bug A is fixed. Without the fix, Redis held `pointer=''`.

**Rows "delayed get refill" and "delayed batch_get refill"** (`_delayed_refill_race`):
- A writer pod loads the witness. A reader pod invalidates the Redis key so it will miss.
- `MongoBackend.get` (or `batch_get`) is patched. After the real Mongo read, and only for the reader's backend, the writer sets `pointer="sandbox-two"` and commits.
- The reader then continues with its old snapshot and tries to fill Redis.
- A fresh pod must read `("sandbox-two", "seed")`.
- This proves bug B is fixed for both `get` and `batch_get`. The write cancels the lease, so the stale fill is dropped.

**Lease check at the end:**
- After an invalidate, the first `lease` call gets a token. A second `lease` call must return `{}`.
- Then `fill` with the first token must land in Redis (`cache.get` is not `None`).
- This proves that a second concurrent miss can't steal the lease and block the first reader's correct refill. That was the fix in your last commit.

The test saves the current runtime context in `prior` and restores it in `finally`, because the helpers change the global context.

**Validation** (per your description; this branch's CI only runs on PRs to `main`, so you ran it on your fork):
- Without the fix, the "field update" and "delayed refill" schedules fail and edge delta passes.
- With the fix, 28/28 pass, and all 23 files in `scale/tests/data` pass.

**Not covered:** two requests that both write a whole anchor (create or upsert) can still reach Redis in a different order than Mongo.

## Explaining it in one minute

"In jac-scale, Redis caches anchors that live in Mongo. Two races let Redis end up older than Mongo.

First, a field-only commit wrote just the dirty fields to Mongo but pushed the request's whole in-memory anchor to Redis. That could undo another request's field change in the cache. I made field updates invalidate the Redis key and broadcast, the same thing edge-delta writes already do.

Second, a cache-miss refill could read Mongo, lose the race to a writer, and then overwrite Redis with the older snapshot. Now a reader takes a short `SET NX` lease with a random token before reading Mongo. It fills Redis through a Lua script that writes only if its token is still there. `put` and `delete` clear the lease atomically, so any write in between cancels the fill. `execute_plan` no longer refills Redis, because its ids aren't known before the query, so it can't take a lease.

I turned the old #6295 test into a table covering field update, delayed `get` refill and delayed `batch_get` refill, plus a check that a second concurrent miss can't take the lease. It fails on the unfixed branch and all 28 tests pass with the fix. The case of two concurrent full-anchor writes landing out of order is still open and is out of scope."
