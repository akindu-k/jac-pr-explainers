# fix(scale): Redis never serves an anchor older than Mongo after a field update or a late refill (#9840)

[#9911](https://github.com/jaseci-labs/jac/pull/9911) by @akindu-k · opened 9 Oct 2026 · +176 −15 in 6 files

<!-- explainer -->

## In short

In jac-scale, Redis (the cache) could end up holding an older version of a node than MongoDB (the database). This happened in two cases: when a request saved only some fields, and when a cache refill finished after a newer save. You changed field updates to delete the Redis entry instead of overwriting it. You also made cache refills use a short "lease" so a refill is dropped if anything was written in the meantime.

## Words to know

- **Anchor**: the stored form of a node or edge in Jac's graph. It is what gets saved in Mongo and cached in Redis.
- **MongoDB (L3)**: the main database. It is the source of truth.
- **Redis (L2)**: a fast in-memory key-value store used as a shared cache between pods.
- **L1**: the per-request in-memory cache (`__mem__`) inside one process.
- **`ScaleTieredMemory`**: the class that reads and writes through L1, then L2 (Redis), then L3 (Mongo).
- **Cache miss / refill**: a miss is when Redis has no entry. A refill is reading Mongo and putting the result into Redis.
- **Field update / `put_partial`**: a write that sends only the changed fields to Mongo, not the whole anchor.
- **Write-through**: writing to the cache and the database together.
- **Invalidate**: delete the cache entry so the next reader reloads from Mongo.
- **Broadcast (`publish_invalidation`)**: a message telling other pods to drop their copy.
- **Lease**: a short-lived marker key (`lease:anchor:<id>`) set with an expiry. A reader holds it while refilling. Any write removes it.
- **Compare-and-set (Lua script)**: Redis runs a small script atomically. `_FILL_IF_LEASED` writes only if the lease still has the reader's token.
- **Race condition**: a bug that depends on the timing of two concurrent operations.
- **TTL**: how long a Redis entry lives before it expires.
- **Edge delta**: an atomic write of edge changes. It already invalidated Redis (issue #6295).

## The problem

There were two timing bugs. Both leave Redis older than Mongo, and later reads are served the stale Redis copy.

**A. Field-only commits.** `MongoBackend.put_partial` wrote only the dirty fields to Mongo. But `ScaleTieredMemory.commit` then wrote the request's whole in-memory anchor to Redis.

Example: request 1 and request 2 both loaded the same node. Request 2 saved `stamp`. Request 1 then saved `pointer`, and its full anchor still had the old `stamp`. Mongo had both new values. Redis got request 1's whole anchor, so `stamp` went back to its old value.

**B. Late refills.** `get`, `batch_get` and `execute_plan` read Mongo and then unconditionally ran `SET` in Redis. If a write finished between the read and the `SET`, the older snapshot overwrote the newer data.

## The changes, one by one

### `memory_hierarchy.redis.impl.jac` (Redis backend)

This holds the new lease mechanism.

- `_FILL_IF_LEASED` is a Lua script. It checks that the lease key still holds the caller's token. If not, it returns 0 and writes nothing. If so, it deletes the lease and sets the anchor, with a TTL if one is configured.
- `_lease_key(key)` builds `lease:<key>`.
- `RedisBackend.lease(ids)` makes a random token per id and runs `SET ... NX PX` in one pipeline. `NX` means only the first caller gets the lease. It returns only the ids where the lease was taken. On any Redis error it returns `{}`, so no refill happens.
- `RedisBackend.fill(anchor, token)` runs the script. If the token is `None`, it does nothing.
- `put` now uses a pipeline: write the anchor, then delete the lease key. `delete` also deletes the lease.

```python
pipe.delete(_lease_key(key));
pipe.execute();
```

This is what cancels a pending refill. Any write between the Mongo read and the fill removes the lease, so the fill fails the check.

### `memory_hierarchy.main.impl.jac` (tiered memory)

- In `commit`, the branch that invalidates Redis and broadcasts now covers `intent.op == WriteOp.FIELD_UPDATE` as well as deletes. This is the same path edge-delta writes use. Creates still write through. This fixes problem A.
- In `batch_get`, it takes leases for the Redis misses before reading Mongo. After the read it calls `fill(anchor, leases.get(id))` instead of a plain `put`.
- `get` is now overridden. If L1 has the id, it uses the normal path. Otherwise it checks Redis, then takes a lease, reads Mongo, and fills with the lease token. If the node is not in Mongo, it returns `None`. This fixes problem B.

### `memory_hierarchy.jac`

- It imports `uuid4` for lease tokens.
- It adds the constant `_REFILL_LEASE_MS = 10000`, so a lease lives 10 seconds.
- It declares `lease` and `fill` on `RedisBackend`.

### `runtimelib/impl/memory.impl.jac`

`execute_plan` no longer calls `self.l2.put(anchor)`. Its ids are not known before the query runs, so it cannot take a lease. Results still go into the request's L1.

A one-line user-facing note about the fix.

## How it runs now

1. A request calls `get(id)` for a node that is not in L1. (changed)
2. It checks Redis. On a hit, it uses that.
3. On a miss, it calls `lease([id])`. Only the first concurrent reader gets a token. (new)
4. It reads Mongo.
5. It calls `fill(anchor, token)`. The Lua script writes to Redis only if the lease is still there. (new)
6. If a write ran in between, `put` or `delete` already removed the lease, so the fill is dropped. (new)
7. `batch_get` follows the same order for all its misses. (changed)
8. On `commit`, a field-update intent writes the partial fields to Mongo, then invalidates Redis and broadcasts. It no longer writes the whole anchor. (changed)
9. The next reader misses in Redis and refills from Mongo through steps 3 to 5.
10. `execute_plan` only fills L1. (changed)

## Tests

All changes are in `test_memory_hierarchy.jac`. The old #6295 test is renamed "L2 Redis never serves an anchor older than Mongo (issues 6295, 9840)". Its edge-delta checks are kept, and a table of three more schedules is added. The file still has 28 tests.

- **Helpers**: `_CacheWitness` is a node with `pointer` and `stamp` fields. `_cache_pod` makes a fresh pod, which is a new context with its own empty L1. `_seed_witness` saves a node and returns its id.
- **`field update` row**: `_field_update_race` has two pods load the same node. The second sets `stamp`, the first sets `pointer`, and both commit. Expected: a fresh pod reads `("sandbox-one", "second-request")`, so neither update is lost. This proves fix A.
- **`delayed get refill` and `delayed batch_get refill` rows**: `_delayed_refill_race` patches the Mongo read. Right after the reader reads Mongo, a writer commits `pointer = "sandbox-two"`. Expected: a fresh pod reads `("sandbox-two", "seed")`. This proves the lease cancels the late fill (fix B).
- **Lease check**: after an invalidate, the first `lease` call succeeds and a second returns `{}`. The first holder's `fill` lands. This proves only the first concurrent miss refills.
- The test also saves and restores the runtime context in `finally`.

The PR reports that without the fix, the field update and delayed refill rows fail. With the fix, all 28 tests pass, and the whole `scale/tests/data` group passes (23 files).

**Not covered**: two requests that both write a whole anchor (create or upsert) can still reach Redis in a different order from Mongo.

## Explaining it in one minute

Redis could end up older than Mongo in two ways. A field-only save still wrote the request's full anchor to Redis, overwriting fields another request had just saved. And a cache refill that read Mongo could land in Redis after a newer write. I made field updates invalidate the Redis key and broadcast, as edge-delta writes already did. For refills, a reader now takes a short lease before reading Mongo and fills Redis through a Lua compare-and-set that only writes if the lease is still there. Any `put` or `delete` clears the lease, so a late refill is dropped. `execute_plan` no longer fills Redis because it cannot lease ids it does not know yet. I tested it with a three-row table of race schedules. Without the fix, two rows fail. With the fix, all 28 tests pass. One known gap remains: two whole-anchor writes can still reach Redis out of order.
