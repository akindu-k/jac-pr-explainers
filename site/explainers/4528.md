## 1. The short version

jac-scale stores a Jac app's graph (nodes, edges and their data) in layers: an in-process memory (L1), an optional cache (L2), and a persistent backend (L3). In deployments, L3 is MongoDB. When the server shuts down, `ScaleTieredMemory.close()` is supposed to make sure everything reaches MongoDB.

The PR title says **data written while the server was running was missing from MongoDB after a restart.** The PR description is empty and no issue is linked. The diff shows what the old code did: `close()` called `self.l3.sync()`, and that was the only flush. The diff does not show why that call was not enough for MongoDB.

**You added a `ScaleTieredMemory.commit()` method. For a MongoDB backend, it walks every persistent anchor in L1 memory, finds the new or changed ones, and writes them to MongoDB, respecting access rights. `close()` now calls `commit()` instead of `l3.sync()`.** For non-Mongo backends, `commit()` falls back to the old `sync()` call.

The PR also adds a scratch file, `new.jac`, at the repository root. It holds payment walkers that look like a manual reproduction script. There are no automated tests.

**Status:** Closed. The metadata does not say it was merged. There are no reviews or comments. Three checks failed on the head commit `3145cb6`: `test-core`, `Check Release Notes Updated` and `jac-check`.

## 3. The problem, step by step

### 3.1 The setup

- **Walkers** such as `set_payment` in `new.jac` create a `payment_details` node under `Root`.
- The new node's anchor lands in **L1** (`__mem__`), with `persistent = true`.
- On shutdown, **`ScaleTieredMemory.close()`** must push L1 changes to **L3 (MongoDB)**.
- After a restart, walkers such as `get_all_payments` read from MongoDB.

### 3.2 What went wrong

This is the likely sequence, based on the title, the old `close()` and the `new.jac` reproduction. The exact failure inside `MongoBackend.sync()` is not visible in the diff.

```text
1. Server starts. L1 (__mem__) is empty. MongoDB has Root.
2. POST set_payment(amount=10) → new payment_details node P in L1, persistent=true, hash=0.
   Root's edges in L1 now include Root→P. Root's hash in L1 no longer matches its content.
3. get_all_payments → returns [P]  (read from L1, looks fine).
4. Server shuts down → ScaleTieredMemory.close()
     └─ self.l3.sync()      ← WRONG: P and the updated Root edges do not end up in MongoDB
     └─ self.l3.close()
5. Server restarts. L1 is empty again. Root is loaded from MongoDB (old edges, no P).
6. get_all_payments → returns []   ← data "lost"
```

### 3.3 Why it mattered

Any jac-scale app on MongoDB could lose data that users created, once the server restarted (deploys, pod restarts). No issue is linked and there are no comments. The only evidence is the PR title and the payment example in `new.jac`, which looks like a real app's flow ("Payment Processed").

## 4. The idea of the fix (one sentence)

> **Explicitly write every changed persistent anchor to MongoDB before closing.** On close, compare each L1 anchor's current fingerprint with its saved one, and write the new or changed ones to MongoDB.

This puts the "what changed?" logic in jac-scale's own class, where it knows L3 is MongoDB. It no longer depends on what `MongoBackend.sync()` does. The access checks keep the save from bypassing permissions.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/memory_hierarchy.main.impl.jac`: add `commit()` and call it from `close()`

```diff
+"""Commit - sync all modified persistent anchors to MongoDB."""
+impl ScaleTieredMemory.commit(anchor: (Anchor | None) = None) -> None {
+    import from jaclang { JacRuntimeInterface as Jac }
+    if not isinstance(self.l3, MongoBackend) {      # non-Mongo: old behaviour
+        if self.l3 {
+            self.l3.sync();
+        }
+        return;
+    }
+    for (id, mem_anchor) in list(self.__mem__.items()) {
+        if not mem_anchor.persistent { continue; }   # skip temporary anchors
+        if mem_anchor.hash == 0 {                    # never saved → write as-is
+            self.l3.put(mem_anchor);
+            continue;
+        }
+        current_hash = hash(dumps(mem_anchor));
+        if current_hash == mem_anchor.hash { continue; }  # unchanged
+        stored = self.l3.get(id);
+        if stored {
+            updated = False;
+            if (isinstance(stored, NodeAnchor) and isinstance(mem_anchor, NodeAnchor)
+                and Jac.check_connect_access(mem_anchor)) {
+                stored.edges = mem_anchor.edges;      # copy edges
+                updated = True;
+            }
+            if Jac.check_write_access(mem_anchor) {
+                stored.access = mem_anchor.access;    # copy permissions
+                stored.archetype = mem_anchor.archetype;  # copy user data
+                updated = True;
+            }
+            if updated {
+                self.l3.put(stored);
+                mem_anchor.hash = hash(dumps(stored));
+            }
+        }
+    }
+}
```

```diff
 impl ScaleTieredMemory.close -> None {
-    # Sync and close L3 persistence
+    # Flush any pending modifications before closing
+    self.commit();                     # NEW
+    # Close L3 persistence
     if self.l3 {
-        self.l3.sync();                # OLD
         self.l3.close();
     }
```

**What:** `commit()` writes the changed state of L1 to MongoDB, and `close()` now runs it first.

- New anchors (`hash == 0`) are written whole.
- Changed anchors are merged into the stored copy. Edges are copied only with connect access. Data and access are copied only with write access.

**Why:** This makes sure that the new node P and Root's new edge to P (steps 2 and 4 in 3.2) are in MongoDB before shutdown.

**Things to notice:**
- **The `anchor` parameter is never used.** It is accepted, probably to match a base-class signature, then ignored.
- **The fix may reach beyond shutdown.** If the base `TieredMemory` already has a `commit` method that the runtime calls (for example after each request), this override replaces it for jac-scale. The diff cannot confirm whether such a caller exists.
- **Changed anchors that are missing from MongoDB are skipped silently.** If `hash != 0` but `l3.get(id)` returns nothing, nothing is written.
- **New anchors keep `hash == 0` after the write.** In the `hash == 0` branch, `mem_anchor.hash` is not updated. A second `commit()` would `put` them again, unless `put` sets the hash itself (not visible).
- **For Mongo, `close()` no longer calls `sync()`.** If `MongoBackend.sync()` did anything else, that no longer runs on close.
- **Hard kills still lose data.** `commit()` only runs from `close()` in this diff, so a crash or `SIGKILL` before `close()` still loses unsaved changes.
- **Some imports cannot be checked.** `MongoBackend`, `NodeAnchor` and `dumps` must already be imported in this file. The diff does not show those imports. If any is missing, that could explain the `jac-check` failure.
- **The import style is unusual.** `JacRuntimeInterface` is imported inside the function, not at the top of the file.

## 6. How execution flows after the PR

### 6.1 Server shutdown

```text
ScaleTieredMemory.close()
├─ self.commit()                                   ← NEW
│   ├─ l3 is not MongoBackend → l3.sync() if l3, return   (same as old close)
│   └─ l3 is MongoBackend
│       └─ for each (id, anchor) in __mem__
│           ├─ not persistent → skip
│           ├─ hash == 0 → l3.put(anchor)
│           ├─ hash(dumps(anchor)) == anchor.hash → skip
│           └─ changed
│               ├─ stored = l3.get(id); none → skip
│               ├─ NodeAnchor + connect access → copy edges
│               ├─ write access → copy access + archetype
│               └─ any copied → l3.put(stored), update anchor.hash
├─ l3.close()                                      ← CHANGED (no sync() before it)
└─ close L2 cache                                  (unchanged)
```

### 6.2 Any other caller of `commit()`

Something else might call `commit()` on the memory object, such as the runtime after a request. If so, it now takes the same path as the `self.commit()` branch above. Whether such a caller exists cannot be seen in this diff.

| Scenario | Before | After |
|---|---|---|
| Mongo, new node created, clean shutdown | Lost after restart (per title) | Written by `put` on close |
| Mongo, existing node gets a new edge | Edge lost after restart (inferred) | Edges copied if connect access passes |
| Mongo, node data changed without write access | Not saved (inferred) | Not saved (blocked by access check) |
| Mongo, changed anchor not found in DB | Not saved (inferred) | Silently skipped |
| Non-Mongo L3 | `sync()` then `close()` | Same |
| Process killed without `close()` | Lost | Still lost |

The behaviour change users will notice: on MongoDB deployments, data created before a clean restart should survive.

## 11. Questions your senior might ask

**Q: Why didn't the old `l3.sync()` save the data?**
The diff doesn't show `MongoBackend.sync()`, so this PR doesn't explain it. You should find and state the root cause.

**Q: Does `commit()` run after each request, or only at shutdown?**
In this diff, only `close()` calls it. If the base `TieredMemory` has a `commit` that the runtime calls, your override now handles that too. Check this in the runtime.

**Q: What if the server crashes instead of shutting down cleanly?**
`close()` never runs, so unsaved changes are still lost.

**Q: Why copy fields into `stored` instead of writing `mem_anchor` directly?**
So that access checks decide what is saved. Edges are copied only with connect access. Data and access are copied only with write access.

**Q: What does `hash == 0` mean?**
It appears to mark an anchor that was never saved. Such anchors are written whole with `put`. Their hash is not updated afterward.

**Q: What happens to a changed anchor that isn't in MongoDB?**
It is skipped silently, because `l3.get(id)` returns nothing and there is no `else` branch.

**Q: Did behaviour change for non-Mongo backends?**
No. `commit()` calls `l3.sync()` and returns, so `close()` behaves as before.

**Q: Why is `new.jac` in the PR?**
It is a manual reproduction script for the payment scenario and should be removed.

**Q: Why are three checks red?**
Release notes are missing. `jac-check` and `test-core` need their logs checked; `new.jac` or missing imports are plausible causes.
