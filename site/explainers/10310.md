## 1. The short version

jac-scale stores graph data in three layers. **L1** is a request's own in-memory copy. **L2** is Redis, a shared cache. **L3** is MongoDB, the source of truth. A read checks L1, then Redis, then Mongo, and copies what it finds back into the faster layers.

**On the 0.34.x line, Redis could end up holding an older copy of a node than Mongo, and every later read would return that old copy.** There were three ways this happened:

- **A.** A request saved only the fields it changed to Mongo, then wrote its whole copy of the node to Redis.
- **B.** A cache-miss read fetched from Mongo and then wrote to Redis after a newer save had already landed.
- **C.** `save()` on an unchanged node pushed the request's old copy to Redis.

Example from #9840: Mongo holds `pointer = "sandbox-one"`, but Redis and every fresh reader see `pointer = ""`.

**You fixed it by never letting a request's own copy overwrite Redis.** The three paths are handled like this:

- A field-only save now deletes the Redis key instead of writing it.
- A cache refill must first take a short Redis "lease". Any write to that key cancels the lease. The refill uses a Lua compare-and-set, so it only lands if its lease is still there.
- `ScaleTieredMemory.put` now keeps the node in L1 only.
- `execute_plan` (queries) no longer fills Redis.

This PR targets `release/jaclang-0.34.28-prep`, because `main` no longer has the Mongo/Redis layers. It replaces #10249, #10046 and #9911, which closed when their release branches were deleted.

## 3. The problem, step by step

### 3.1 The setup

- **Readers:** `ScaleTieredMemory.get`, `batch_get` and `execute_plan` read Mongo on a Redis miss. Before this PR they then ran a plain `SET` into Redis (via `self.l2.put` or the base class).
- **Writers:** `ScaleTieredMemory.commit` writes intents to Mongo. Before this PR, for anything that was not a delete or an edge delta, it then called `self.l2.put(intent.anchor)`, which wrote the request's whole anchor.
- **`ScaleTieredMemory.put`** called `TieredMemory.put`. The PR description says that writes to Redis immediately. These call it: `save()`, `perm_grant`, `allow_root`, `object_ref`, and serializer ref mode.
- **`RedisBackend.put`:** an unconditional `SET`/`SETEX`. It never compares against what is already there.

### 3.2 What went wrong — A: field update publishes a stale full anchor

```text
1. Mongo: {pointer: "", stamp: "seed"}             Redis: same
2. Request 1 loads node → L1₁ {pointer:"", stamp:"seed"}
3. Request 2 loads node → L1₂ {pointer:"", stamp:"seed"}
4. Request 2 sets stamp = "second-request"
5. Request 1 sets pointer = "sandbox-one"
6. Request 1 commits: put_partial(pointer) → Mongo {pointer:"sandbox-one", stamp:"seed"}
                      Redis ← L1₁ {pointer:"sandbox-one", stamp:"seed"}
7. Request 2 commits: put_partial(stamp)   → Mongo {pointer:"sandbox-one", stamp:"second-request"}  ✔
                      Redis ← L1₂ {pointer:"", stamp:"second-request"}      ✘ WRONG: old pointer
8. Fresh pod reads → Redis hit → pointer "" (Mongo says "sandbox-one")
```

### 3.3 What went wrong — B: delayed cache refill

```text
1. Mongo: {pointer:"", stamp:"seed"}    Redis: key missing
2. Reader: Redis miss → reads Mongo → snapshot {pointer:""}
3. Writer: sets pointer = "sandbox-two", commits → Mongo {pointer:"sandbox-two"}, Redis updated/cleared
4. Reader: SET Redis ← snapshot {pointer:""}                               ✘ WRONG: older than Mongo
5. Fresh pod reads → pointer "" (Mongo says "sandbox-two")
```

This happened in `get`, `batch_get` and `execute_plan`.

### 3.4 What went wrong — C: re-save of an unchanged anchor

```text
1. Mongo: {pointer:""}  Redis: {pointer:""}
2. Stale request loads node → L1ₛ {pointer:""}
3. Writer sets pointer = "sandbox-three", commits → Mongo and Redis cleared/updated
4. Stale request calls save(node) → ScaleTieredMemory.put → TieredMemory.put
                                   → Redis ← L1ₛ {pointer:""}                ✘ WRONG
5. Stale request commits: anchor unchanged → no intent → nothing fixes Redis
6. Fresh pod reads → pointer "" (Mongo says "sandbox-three")
```

The PR's run 2 shows that #10046's fix still failed this path and `aput`: `unchanged save after a newer commit: a fresh pod read ('', 'seed'), Mongo holds ('sandbox-three', 'seed')`.

### 3.5 Why it mattered

- Every read after the bad step returns wrong data until the Redis key expires or is overwritten. Mongo is correct, but nobody reads it because Redis hits.
- #9840 reproduced A and B on the official 0.34.20 and 0.34.21 binaries, with real Mongo 7 and Redis 7. The issue states it does **not** prove that this caused the original jacBuilder#2152 incident.
- The issue asks for a fix or backport decision on the 0.34.x line. `main` uses a different (Postgres) design (#7947, #8000).

## 4. The idea of the fix (one sentence)

> **Only Mongo's own latest state may reach Redis.** Writers that hold a partial or possibly old copy delete the Redis key instead of writing it, and readers may only refill a key if no write happened since they started reading.

Deleting is always safe: the worst case is one extra Mongo read. The lease check turns "read then write" into a check that fails when a newer write happened in between, using only Redis operations that are atomic.

**What:** Three new methods.

- `lease` tries to take `lease:anchor:<id>` with `SET NX PX 10000` for each id. It returns only the ids it won, each with its random token.
- `fill` runs a Lua script. The script writes the anchor only if the lease still holds the caller's token, and deletes the lease in the same atomic step.
- `release` deletes a lease only if it still holds the caller's token.

`put`, `aput` and `delete` now also delete the lease, in the same command or pipeline as their write.

**Why:** This is the fix for path B. Any write after a reader took its lease removes the lease, so the reader's later `fill` finds no matching token and does nothing.

**Things to notice:**

- `put`/`aput` use the default `pipeline()`. In redis-py that is a `MULTI`/`EXEC` transaction, so the `SET` and the lease delete apply together. `lease` and `release` use `transaction=False`. That is fine, because each `SET NX` and each `EVAL` is atomic on its own.
- `put_count` now goes up by the script's return value (1 if the fill landed, 0 if not). This addresses Claude review F3 on #10046.
- `fill` keeps the tracing span, as Greptile asked on #9911.
- The scripts are sent with `EVAL` on every refill, not cached with `register_script`. You chose this on purpose (Claude F2 on #10046). The script is short and runs only on a miss.
- Compare-and-delete in `release` matters. If the lease had expired and another reader took it, a plain `DEL` would wipe that other reader's lease.
- If Redis fails, `lease` returns `{}`, so no fill happens. Readers still get Mongo's data. The failure only costs caching.
- The diff does not show `RedisBackend.invalidate`. The description says a field update "deletes the key and lease", which suggests `invalidate` goes through `delete`. The passing delayed-refill test rows depend on this. Be ready to confirm it in the code.

## 6. How execution flows after the PR

### 6.1 Reading one node (`ScaleTieredMemory.get`)

```text
get(id)
├─ _refresh_if_stale(id)
├─ no L2, no L3, or id in L1 → super.get(id)                    ← CHANGED (guard)
├─ L2 hit → put in L1, return                                    ← CHANGED (done here, not in base)
└─ L2 miss
   ├─ lease([id])  → SET lease:anchor:<id> token NX PX 10000      ← NEW
   ├─ L3.get(id)
   │  └─ finally: if nothing loaded → release(leases)             ← NEW
   ├─ None → return None
   ├─ put in L1
   ├─ fill(anchor, token) → Lua: token still there? SET : skip    ← NEW
   └─ return anchor
```

### 6.2 Reading many nodes (`batch_get`)

```text
batch_get(ids)
├─ L1, then L2 lookups → l2_misses
└─ l2_misses and L3
   ├─ lease(l2_misses)                                            ← NEW
   ├─ L3.batch_get / L3.get loop
   │  └─ finally: release leases for ids not returned             ← NEW
   └─ per result: L1 ← anchor; fill(anchor, token)                ← CHANGED (was plain put)
```

### 6.3 Committing

```text
commit()
├─ write intents to Mongo (put_partial for FIELD_UPDATE)
└─ per applied intent
   ├─ delete OR FIELD_UPDATE → invalidate key (+lease) + publish  ← CHANGED (FIELD_UPDATE added)
   ├─ edge delta → invalidate (unchanged, #6297)
   └─ other (create) → l2.put → SET + DEL lease (atomic)          ← CHANGED (lease cancel)
```

### 6.4 `save()` / `perm_grant` / `allow_root` / `object_ref` on a loaded node

```text
ScaleTieredMemory.put(anchor)
├─ _committed = False
└─ L1[id] = anchor                                                ← CHANGED (no Redis write)
   later commit(): unchanged anchor → no intent → Redis untouched
```

### 6.5 Query (`execute_plan`)

```text
ScaleTieredMemory.execute_plan(plan)                              ← NEW override
├─ no L3 → nothing
└─ for each Mongo result → yield L1.setdefault(id, anchor)        (no Redis fill)
```

| Scenario | Before | After |
| --- | --- | --- |
| Two requests update different fields | Redis keeps the slower request's whole copy (stale field) | Redis key deleted; next read refills from Mongo |
| Refill finishes after a newer commit | Old snapshot overwrites Redis | Writer deleted the lease; fill rejected |
| Two readers miss at once | Both `SET` Redis | First fills; second returns Mongo data without filling |
| Mongo miss or error during refill | n/a | Lease released at once, so refill isn't blocked for 10 s |
| `save()` on an unchanged, old copy | Old copy written to Redis | L1 only; Redis untouched |
| Query results | Written to Redis | L1 only |
| Create of a new anchor | Write-through | Write-through (unchanged; two racing creates still unordered) |

**Behaviour changes users may notice:**

- After a field update, the next read on any pod is a Redis miss plus a Mongo read.
- Queries no longer warm Redis.
- A cache miss now costs extra Redis round trips (lease, then `EVAL`).

Data is now correct. The cost is a lower Redis hit rate.

### `test_memory_hierarchy.jac`

The renamed test is `"L2 Redis never serves an anchor older than Mongo (issues 6295, 9840)"`. Its original edge-delta part is kept. It runs on testcontainers Mongo and Redis.

**New helpers**

- `_CacheWitness`: a node with `pointer = ""` and `stamp = "seed"`.
- `_cache_pod()`: a new `ExecutionContext` with its own `ScaleTieredMemory`, set as current. It plays the part of a separate pod or request with its own L1.
- `_seed_witness()`: creates and commits a witness under a persistent `Root` and returns its id.
- `_field_update_race`, `_stale_save_race`, `_delayed_refill_race`: one helper per schedule from §3.
- The test saves and restores the previous context (`prior`) in `finally`.

**Table rows.** Each row seeds a fresh witness, runs its race, then reads from a brand-new pod and compares against Mongo's expected state.

| Row | Setup | Expected fresh read | Proves |
| --- | --- | --- | --- |
| field update | Two pods load; one sets `stamp`, the other `pointer`; both commit | `("sandbox-one", "second-request")` | Path A fixed (FIELD_UPDATE invalidates) |
| delayed get refill | Reader's Redis key invalidated; `patch.object` wraps the real `MongoBackend.get` and commits a writer change after the real read returns | `("sandbox-two", "seed")` | Path B for `get`; also that `get` leases before reading Mongo |
| delayed batch_get refill | Same, wrapping `batch_get` | `("sandbox-two", "seed")` | Path B for `batch_get` |
| unchanged save after a newer commit | Stale pod loads; writer commits `pointer="sandbox-three"`; stale pod calls `JacRuntime.save` and commits | `("sandbox-three", "seed")` | Path C fixed |

The wrapper only acts when `backend is reader.mem.l3`, so the writer's own reads are not affected.

**Lease checks after the table**

## 11. Questions your senior might ask

**Q: Why delete the Redis key on a field update instead of writing the merged state?**
The request only knows its own dirty fields. Building a correct full anchor would mean reading Mongo again inside commit, which brings back the read-then-write race. Deleting is always safe, and it matches what edge-delta writes already do (#6297).

**Q: Why a lease instead of a version number compare?**
#9840 shows Mongo and Redis anchor versions were both `0` in these schedules, so versions don't separate old from new here. The lease needs no data-model change. It only needs "did any write touch this key since I started reading?", and the atomic delete-on-write answers that.

**Q: What if the Mongo read takes longer than 10 seconds?**
The lease expires. The fill's Lua check then fails (key missing or a different token), so nothing is written. The caller still gets its data. Only the cache fill is lost.

**Q: Many pods miss the same key at once. Do they all hit Mongo?**
Yes, they all read Mongo. Only the first one that wins the lease fills Redis; the rest return their read without filling. The PR prevents duplicate or out-of-order fills, not duplicate Mongo reads.

**Q: Is the write + lease delete really atomic?**
`put`/`aput` use the default `pipeline()`, which in redis-py runs as `MULTI`/`EXEC`, so the `SET` and `DEL lease` apply together. `delete` removes both keys in one `DEL`. `fill` and `release` are single Lua scripts.

**Q: Does this cost performance?**
Yes, in three ways. Reads after a field update now miss Redis once. Queries no longer warm Redis. Each miss adds a lease `SET` and an `EVAL`. These only affect the miss path and writes.

**Q: Why not change `TieredMemory.execute_plan` and `put` directly?**
Those are base classes that other back ends use. Earlier review (Claude F1/F4) asked to keep Scale-only reasons out of the base. So `put`, `get` and `execute_plan` are overridden in `ScaleTieredMemory`.

**Q: What is still not covered?**
Two requests that both create or upsert a whole anchor can reach Redis in a different order from Mongo; creates still write through. Also, there is no `execute_plan` race test, and nothing proves the fix across separate processes or over HTTP.

**Q: Why does this target a release branch and not `main`?**
`main` replaced the Mongo/Redis layers with a Postgres design (#7947, #8000), so this code does not exist there. Earlier attempts closed when their `0.34.2x-prep` base branches were deleted.

**Q: How do we know the tests catch the bug?**
Run 37917790026 fails the field-update row on unfixed 0.34.21. Run 39414089086 fails the unchanged-save and `aput` rows on #10046's code. Run 39415090456 passes everything with the fix. All of these runs were on 0.34.24 or earlier, not on this PR's 0.34.28 base.
