## 1. The short version

Jac Scale keeps graph data in three tiers: the request's own memory (L1), Redis (L2, shared cache) and MongoDB (L3, the source of truth). When a request reads a node, it tries L1, then Redis, then Mongo. A Mongo hit is copied back into Redis so the next reader is fast.

**On the 0.34.x line, Redis could end up holding an older copy of a node than Mongo, and every later reader then got that old copy.** There were three ways this happened:

- **A field update:** Mongo saved only the changed fields, but Redis got the request's whole, possibly stale, copy.
- **A late cache refill:** a slow refill overwrote a newer write.
- **A re-save:** `save()` on an unchanged node pushed that request's copy into Redis before commit.

In the issue's run, Mongo held `pointer = "sandbox-one"` while Redis and every fresh reader saw `pointer = ""`.

**Your fix keeps Redis from ever being written with a request's private copy:**

- A field update now deletes the Redis key instead of writing it.
- A cache refill only lands if it still holds a short "lease" that any newer write cancels.
- `ScaleTieredMemory.put` stays in L1 until commit.

## 3. The problem, step by step

### 3.1 The setup

- `ScaleTieredMemory.commit`: for each applied intent that wasn't a delete or edge delta, it called `self.l2.put(intent.anchor)`. That wrote the request's **whole in-memory anchor** to Redis.
- `MongoBackend.put_partial`: for a field update, it wrote **only the dirty fields** to Mongo.
- `TieredMemory.get` / `batch_get` / `execute_plan`: on a Redis miss they read Mongo, then did an unconditional `SET` into Redis.
- `ScaleTieredMemory.put` called `TieredMemory.put`, which wrote L1 **and** Redis immediately. Callers include `save()`, `perm_grant`, `allow_root`, `object_ref` and serializer ref mode.
- `RedisBackend.put`: a plain `SET`/`SETEX`, with no version check.

### 3.2 What went wrong

#### Case A: field update publishes a stale full anchor

```text
1. Seed: Mongo {pointer:"", stamp:"seed"}; Redis same
2. Pod 1 loads node → L1 copy {"", "seed"}
3. Pod 2 loads node → L1 copy {"", "seed"}
4. Pod 2 sets stamp="second-request"  (dirty field: stamp)
5. Pod 1 sets pointer="sandbox-one"   (dirty field: pointer)
6. Pod 1 commits: Mongo {"sandbox-one","seed"}; Redis {"sandbox-one","seed"}
7. Pod 2 commits: put_partial writes only stamp
     Mongo {"sandbox-one","second-request"}   ✔ correct
     l2.put(whole copy) → Redis {"", "second-request"}   ✘ WRONG: pointer rolled back
8. Fresh pod reads Redis → {"", "second-request"}  ✘
```

#### Case B: delayed refill overwrites a newer write

```text
1. Mongo {"", "seed"}; Redis key empty (miss)
2. Reader: Redis miss → reads Mongo → gets {"", "seed"}
3. Writer: sets pointer="sandbox-two", commits
     Mongo {"sandbox-two","seed"}; Redis updated/invalidated
4. Reader: SET Redis ← {"", "seed"}   ✘ WRONG: older snapshot wins
5. Fresh pod reads Redis → {"", "seed"}  ✘
```

The same thing happened through `batch_get` and `execute_plan`.

There was a second variant in #10046's earlier fix. It added a lease, but `aput` did not clear it. So: a refill takes its lease, then `aput` writes a newer value, then the refill still holds a valid lease and overwrites. Your run 2 shows this as `"aput: a refill leased before aput overwrote it with ''"`.

#### Case C: re-save of an unchanged anchor

```text
1. Mongo {"", "seed"}
2. Stale pod loads node → L1 {"", "seed"}
3. Writer pod sets pointer="sandbox-three", commits → Mongo {"sandbox-three","seed"}
4. Stale pod calls save(node) → ScaleTieredMemory.put → TieredMemory.put
     Redis ← {"", "seed"}   ✘ WRONG: written before (and without) any commit
5. Stale pod commits: node unchanged → no intent → nothing corrects Redis
6. Fresh pod reads Redis → {"", "seed"}  ✘
```

### 3.3 Why it mattered

- Every later read on any pod returned the stale value until the key expired (`redis_default_ttl`), or forever if the TTL is `0`. Mongo was correct, so the data was not lost, but the app behaved as if it were.
- Issue #9840 reproduced cases A and B on the official 0.34.20 and 0.34.21 binaries with real Mongo 7 and Redis 7. The issue says this does not establish the cause of jacBuilder#2152.
- @MichaelAshley2000 notes JacBuilder production is pinned to 0.34.28 and uses Mongo/Redis graph storage. So this line is live for them.
- Version numbers didn't help. In the issue's schedules, Mongo and Redis anchor versions were both `0`.

## 4. The idea of the fix (one sentence)

> **Only Mongo-confirmed data may reach Redis, and only if no newer write happened in between.** Field updates delete the Redis key, refills must hold a lease that every write cancels, and `put` waits for commit.

This is the right idea because the request's in-memory copy is never guaranteed to be current. Deleting the key forces the next reader to fetch Mongo's merged state. The lease turns "read Mongo then SET" into a check that fails safely: the refill is skipped, never wrong. Field updates now use the same invalidate path edge deltas have used since #6297.

### 5.2 Same file: the lease, fill and release machinery

```diff
+glob _FILL_IF_LEASED = """
+if redis.call('GET', KEYS[2]) ~= ARGV[1] then return 0 end   -- lease gone or not mine
+redis.call('DEL', KEYS[2])
+if tonumber(ARGV[3]) > 0 then
+    redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
+else
+    redis.call('SET', KEYS[1], ARGV[2])
+end
+return 1
+""",
+     _RELEASE_IF_LEASED = """
+if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
+return 0
+""";
+def _lease_key(key: str) -> str { return f"lease:{key}"; }

+impl RedisBackend.lease(ids) -> dict[UUID, str] {
+    leases = {id: uuid4().hex for id in ids};
+    pipe = self.redis_client.pipeline(transaction=False);
+    ... pipe.set(_lease_key(...), token, px=_REFILL_LEASE_MS, nx=True);
+    taken = pipe.execute();
+    ... except → return {};
+    return {id: leases[id] for (id, ok) in zip(leases, taken) if ok};
+}
+impl RedisBackend.fill(anchor, token) -> None {
+    if self.redis_client is None or token is None { return; }
+    span = start_memory_span("memory.put redis", ...);
+    self.put_count += self.redis_client.eval(_FILL_IF_LEASED, 2, key, _lease_key(key), token, data, ttl);
+}
+impl RedisBackend.release(leases) -> None {
+    ... pipe.eval(_RELEASE_IF_LEASED, 1, key, token) for each lease
+}
```

**What:**
- `lease` tries `SET NX` with a 10 s expiry for each id. It returns only the ones it won.
- `fill` writes the anchor only if the lease still holds its token, and consumes the lease. The check and the write happen atomically in Lua.
- `release` deletes a lease only if it is still yours.

**Why:** This is the guard for case B. The Lua script makes "check the lease, then write" impossible to interleave with another write.

**Things to notice:**
- Missing lease means `GET` returns nil, which is never equal to the token, so the fill is rejected. The same happens if the lease expired after 10 s.
- `fill` with `token=None` (lease not taken, or `lease` errored) does nothing. Failures only lose a cache fill. They never write stale data.
- Only the first concurrent miss gets a lease (commit 4758805). Other readers still read Mongo but do not refill.
- `put_count` now goes up by the script's return value (0 or 1). So rejected refills are not counted, which was Claude review F3 on #10046. The span is kept, which was Greptile on #9911.
- `EVAL` resends the script each time. You kept this on purpose rather than `register_script`, because that would tie a cached script object to one client.

## 6. How execution flows after the PR

### 6.1 Committing a field update

```text
request changes node.pointer → commit()
├─ build intents → WriteOp.FIELD_UPDATE
├─ MongoBackend.put_partial (only dirty fields)
├─ l2.invalidate(id) → RedisBackend.delete: DEL key + lease:key     ← CHANGED (was l2.put)
│   └─ on error: logger.warning                                   ← CHANGED (was debug)
└─ publish_invalidation(id) → other pods drop unchanged L1 copies ← NEW for field updates
```

### 6.2 Reading one node (`get`) on a Redis miss

```text
ScaleTieredMemory.get(id)
├─ _refresh_if_stale(id)
├─ no L2, no L3, or in L1 → super.get(id)
├─ Redis hit → store in L1, return                               ← NEW (own code path)
└─ Redis miss
    ├─ lease([id]): SET lease:key token NX PX 10000              ← NEW
    ├─ l3.get(id)
    ├─ finally: if nothing loaded → release(leases)              ← NEW
    ├─ None → return None
    └─ store in L1, fill(anchor, token)                          ← NEW
        └─ Lua: lease still == token? DEL lease, SET key : skip
```

### 6.3 Reading many nodes (`batch_get`)

```text
ScaleTieredMemory.batch_get(ids)
├─ L1, then Redis hits
└─ misses and L3 present
    ├─ lease(misses) (only uncontested ids get tokens)           ← NEW
    ├─ L3 batch_get (or per-id get)
    ├─ finally: release leases for ids Mongo didn't return       ← NEW
    └─ for each loaded: L1 store, fill(anchor, token)            ← CHANGED (was put)
```

### 6.4 `save()` and other `put` callers

```text
save(node) / perm_grant / allow_root / object_ref / serializer ref
└─ ScaleTieredMemory.put
    ├─ _committed = False
    └─ __mem__[id] = anchor                                      ← CHANGED (no Redis write)
       (Redis updated later by commit, only if there is an intent)
```

### 6.5 Query (`execute_plan`)

```text
ScaleTieredMemory.execute_plan(plan)                             ← NEW override
├─ no L3 → yield nothing
└─ for anchor from Mongo: yield L1 existing copy or this one (no Redis)
```

### 6.6 Direct `put` / `aput` (e.g. create write-through)

```text
RedisBackend.put / aput
└─ MULTI: SET/SETEX key; DEL lease:key; EXEC                     ← CHANGED
```

| Scenario | Before | After |
| --- | --- | --- |
| Two pods update different fields | Redis rolls back the other field | Redis key deleted; next read gets Mongo's merged state |
| Refill finishes after a newer commit | Old snapshot overwrites Redis | Lease was deleted, so the refill is rejected |
| Refill in progress, then `put`/`aput` writes | Refill overwrites newer value | `put`/`aput` cleared the lease, so the refill is rejected |
| `save()` on an unchanged stale node | Stale copy written to Redis, never corrected | L1 only; Redis untouched |
| Two concurrent misses on the same key | Both SET | First leases and fills; second reads Mongo but doesn't fill |
| Mongo miss or read error | Nothing cached | Lease released, so later refills are not blocked |
| Query results | Written to Redis | L1 only |
| Redis DEL fails during invalidation | Debug log | Warning log; Redis may be stale until TTL |

**Changes users may notice:**
- More Mongo reads right after field updates, because the next read misses Redis.
- Query results no longer warm Redis.
- Concurrent misses fill Redis once.
- Uncommitted `save()` data is not visible in Redis.

Correctness depends on the invalidation DEL succeeding. If it fails, you now get a warning.

### `test_memory_hierarchy.jac`

The existing #6295 test was renamed to `"L2 Redis never serves an anchor older than Mongo (issues 6295, 9840)"`. Its edge-delta part is kept, and new rows are appended. It saves the current context in `prior` and restores it in `finally`, because the helpers switch contexts.

**New helpers:**
- `_CacheWitness`: a node with `pointer=""` and `stamp="seed"`.
- `_cache_pod()`: a fresh `ExecutionContext` with its own `ScaleTieredMemory`. It simulates a separate pod in one process.
- `_seed_witness()`: creates a persistent root, connects a witness, commits, and returns its id.
- `_field_update_race`: case A. Two pods edit different fields; the first commits, then the second.
- `_stale_save_race`: case C. The stale pod loads; the writer commits `sandbox-three`; the stale pod calls `save()` and commits.
- `_delayed_refill_race(id, read)`: case B. It uses `patch.object` to wrap the real `MongoBackend.get`/`batch_get`. After the real read returns (only for the reader's backend), the writer commits `pointer="sandbox-two"`.

**Race table.** Each row seeds a new witness, runs the schedule, then checks that a fresh pod reads Mongo's state.

| Row | Schedule | Expected `(pointer, stamp)` | Proves |
| --- | --- | --- | --- |
| field update | `_field_update_race` | `("sandbox-one","second-request")` | Field update no longer publishes a stale full anchor |
| delayed get refill | `_delayed_refill_race(.., "get")` | `("sandbox-two","seed")` | `get` takes the lease before reading Mongo; the writer's invalidate cancels it |
| delayed batch_get refill | `_delayed_refill_race(.., "batch_get")` | `("sandbox-two","seed")` | Same for `batch_get` |
| unchanged save after a newer commit | `_stale_save_race` | `("sandbox-three","seed")` | `put` no longer writes Redis before commit |

## 11. Questions your senior might ask

**Q: Why delete the Redis key on a field update instead of writing the correct merged anchor?**
The request only knows its own dirty fields. Its other fields may be older than Mongo. Building a correct anchor would need a Mongo read. Deleting is cheap and lets the next reader fetch Mongo's merged state. It is also the path edge deltas have used since #6297.

**Q: Why not compare versions instead of using a lease?**
In the issue's schedules, both Mongo and Redis anchor versions were `0`. A version check would not have caught the bug.

**Q: What happens if a Mongo read takes longer than 10 seconds?**
The lease expires, the Lua script finds no matching token, and the refill is skipped. The reader still gets the data in L1. Only the Redis fill is lost, never correctness.

**Q: What if the Redis DEL during commit fails?**
Redis keeps the pre-update anchor until `redis_default_ttl` runs out. dfcf0f7 makes that a warning instead of a silent debug log.

**Q: Does the lease add cost?**
On a Redis miss there is one extra round trip: `SET NX` before the read, then an `EVAL` instead of a plain `SET`. Hits are unchanged. Field updates now cause one extra Mongo read on the next access.

**Q: Why does `execute_plan` skip Redis entirely?**
Its ids are unknown until Mongo returns, so no lease can be taken before the read. Writing without a lease would bring back case B. The base `TieredMemory.execute_plan` is left alone. The override has no test yet.

**Q: Does `put` staying in L1 break anything that expected immediate Redis visibility?**
Other pods no longer see saved-but-uncommitted data in Redis, which is the intended behaviour. Creates still reach Redis at commit. The 173-test Scale run passed with this change. I can't tell from the diff whether code outside these tests relied on the old behaviour.

**Q: Is there any race left?**
Yes. Two requests that both create or upsert a whole anchor can reach Redis in a different order from Mongo; your description lists this as not covered. All tests also run "pods" as contexts in one process, so there is no true cross-process proof yet.

**Q: Why target the release branch, not `main`?**
`main` no longer has the Mongo/Redis memory hierarchy (#7947, #8000). JacBuilder production runs 0.34.28 on Mongo/Redis.

**Q: Why `patch.object` in the refill rows instead of calling `lease`/`fill` directly?**
The rows must prove that `get` and `batch_get` take the lease *before* reading Mongo. Wrapping the real Mongo read and committing inside it tests the real call order. @MusabMahmoodh accepted this.
