## 1. The short version

jac-scale keeps a running Jac app's graph in three memory layers: L1 (in-process memory), L2 (Redis cache) and L3 (MongoDB, or SQLite as a fallback). At the end of each request, `ScaleTieredMemory.commit()` flushes L1 into L2 and L3.

**Before this PR, `commit()` wrote every persistent, writable anchor in L1 to L3 and L2 on every request, even when the walker changed nothing.** Issue #5038 shows this with an empty walker, `walker :pub get {}`. Calling it still saved everything. The issue also points out that full saves of unchanged data make lost-update races more likely.

**You added an `is_updated` "dirty" flag to `Anchor`, set it automatically whenever a public archetype field is assigned (or an edge is added or removed), and changed `commit()` so that only anchors with `is_updated = True` are written to MongoDB and Redis.** Anchors loaded from MongoDB start clean (`False`). New anchors start dirty (`True`). A successful Mongo write sets the flag back to `False`.

During review, @Thamirawaran found that L2 was never updated, because the L3 write cleared the flag before the L2 loop ran. Commit a652eb5 fixed this by building the L2 list *before* the L3 sync.

**Status:** Merged on 2026-03-19. @Thamirawaran requested changes, then approved. All test CI jobs passed; release jobs were skipped.

## 3. The problem, step by step

### 3.1 The setup

- A request runs a walker. Any nodes it touches are loaded into L1 (`__mem__`) from L2 or L3.
- When the request finishes, `ScaleTieredMemory.commit()` is called with no argument (a "batch commit").
- `MongoBackend.sync()` did nothing ("writes are immediate"), so `commit()` did the flushing itself.

### 3.2 What went wrong: a read-only request still writes

```text
1. Request: POST /walker/GetAllTasks          (walker only reads)
2. Root + Task nodes loaded into L1           __mem__ = {root, task1, task2, ...}
3. Walker reports tasks, modifies nothing
4. commit() with no anchor
5. for each anchor in __mem__:
     persistent? yes   writable? yes
     l3.put(anchor)  -> Mongo upsert          ← WRONG: nothing changed
     l2.put(anchor)  -> Redis write           ← WRONG: nothing changed
6. Every loaded anchor is rewritten on every request
```

### 3.3 What went wrong during review: L2 skipped (first version of the fix)

```text
1. CreateTask makes a new Task               task.is_updated = True
2. commit(): self.l3.sync()
     MongoBackend.put(task) succeeds          task.is_updated = False
3. Then loop for L2: "if mem_anchor.is_updated"
     task.is_updated is False -> skipped      ← WRONG: Redis never gets the new task
```

@Thamirawaran flagged this. Commit a652eb5 fixed it.

### 3.4 Why it mattered

- Wasted I/O: every request, including pure reads, rewrote every touched document in Mongo and Redis.
- Races: the issue says it "save[s] everything no partial update. **Subject for race condition**". Request A, which only read node X, could overwrite node X with stale data after request B had changed it.
- The issue's reproduction is a single empty `:pub` walker, so every deployment was affected.

## 4. The idea of the fix (one sentence)

> **Track dirtiness, write only what's dirty.** Each anchor carries an `is_updated` flag that is set on change and cleared on load or save, and the commit path skips clean anchors.

This is the right idea because the cost now scales with what a request changes, not with what it reads. Read-only requests write nothing. The flag also lives in core `jaclang`, so other backends can use it later.

**What:** Every `Anchor` now has `is_updated`, defaulting to `True`. `Archetype` declares a custom `__setattr__`.

**Why:** The default of `True` means a brand-new node is always saved the first time.

### 5.2 `jac/jaclang/jac0core/impl/archetype.impl.jac`: auto-mark on field assignment

```diff

+    object.__setattr__(self, name, value);               # do the real assignment

+        try {
```

**What:** `task.completed = True` now also sets `task.__jac__.is_updated = True`.

**Why:** Without this, user code would have to mark changes by hand. This hook makes tracking automatic.

**Things to notice:**
- It only catches *assignment*. An in-place change such as `task.tags.append("x")` or `task.meta["k"] = 1` does not call `__setattr__`, so the anchor stays clean. Before this PR, such changes were still saved because everything was saved. With MongoDB now, they are skipped unless something else marks the anchor dirty. The PR does not address or test this.
- Fields whose names start with `_` never mark the anchor dirty.
- `name != '__jac__'` is redundant, because `__jac__` already starts with `_`.
- The `try/except` covers the window during `__init__` when `__jac__` may not exist yet.
- This runs on every attribute set of every archetype in core Jac, not just in jac-scale. That adds a small overhead to a hot path.

### 5.3 `jac/jaclang/jac0core/impl/runtime.impl.jac`: mark nodes dirty on edge changes

**What:** When a node's `edges` list changes, the node is marked dirty.

**Why:** `edges` lives on the anchor, not the archetype, and is changed with `append` or `pop`. The `__setattr__` hook in 5.2 never sees these changes. Without these lines, connecting a new task to root would save the task and edge but not root's updated edge list.

**Things to notice:**
- The PR description only mentions `build_edge`. `remove_edge` (commit 7020132) and `reset_graph` were added too.
- Other anchor-level changes, such as changes to `access` permissions, are not marked in this diff. You can't tell from the PR whether they go through `commit(anchor)` (which forces a save, see 5.4) or not.

**What:**
- **Single-anchor commit** forces the flag to `True`, then writes to L3 and L2. An explicit `commit(anchor)` still always writes.
- **Batch commit** does three things in order:

  2. Calls `l3.sync()`, which writes only dirty anchors and clears their flags.
  3. Writes the recorded anchors to Redis.

**Why:** This is the core fix. The snapshot taken before `sync()` is the fix for @Thamirawaran's review comment, because `MongoBackend.put()` clears the flag.

**Things to notice:**
- The comment says SQLite's `sync()` does hash-based change detection. The SQLite backend is not in this diff, so you can't confirm from the PR that its `sync()` writes everything that the old loop wrote.
- The L2 list is built only from `is_updated` and does not depend on L3 success. If a Mongo `put` fails, `put` logs and swallows the error. The anchor still goes to Redis, and its flag stays `True`. The old loop behaved similarly.
- `if self.l3 {` is redundant because of the early return at the top.
- The `isinstance` check was removed, so a non-`Anchor` argument would now fail later instead of being ignored.

## 6. How execution flows after the PR

### 6.1 End of a request (batch commit, Mongo + Redis)

```text
request finishes
└─ ScaleTieredMemory.commit()
   ├─ l3 is None? → return
   ├─ l2_pending = persistent ∧ is_updated ∧ writable anchors in __mem__   ← NEW
   ├─ l3.sync()                                                            ← CHANGED (was the put-all loop)
   │  └─ MongoBackend.sync()                                               ← NEW body
   │     ├─ for anchor in _mem_ref:
   │     │  ├─ not persistent / no write access / not is_updated → skip    ← NEW
   │     │  └─ put(anchor) → upsert → is_updated = False                   ← NEW
   └─ for anchor in l2_pending: l2.put(anchor)                             ← CHANGED
```

### 6.2 Loading a node from MongoDB

```text
walker touches node X (not in L1/L2)
└─ MongoBackend.get(id) or query()
   ├─ _load_anchor(doc)  (rebuilds archetype; __setattr__ / default may set is_updated=True)
   └─ anchor.is_updated = False                                            ← NEW
```

### 6.3 Writing a field

```text
task.title = "New"
└─ Archetype.__setattr__("title", "New")                                   ← NEW
   ├─ object.__setattr__(task, "title", "New")
   └─ name public → task.__jac__.is_updated = True
```

### 6.4 Changing edges

```text
root ++> Task(...)   /  edge removal  /  reset_graph
├─ build_edge  → source.is_updated = True, target.is_updated = True         ← NEW
├─ remove_edge → nd.is_updated = True                                      ← NEW
└─ reset_graph → ranchor.is_updated = True, then commit(ranchor)           ← NEW
```

### 6.5 Explicit single-anchor commit

```text
commit(anchor)
├─ not persistent / no write access → return
├─ anchor.is_updated = True                                                ← NEW (forces write)
├─ l3.put(anchor)  → flag cleared on success
└─ l2.put(anchor)
```

| Scenario | Before | After |
|---|---|---|
| Read-only walker (Mongo) | All loaded writable anchors written to Mongo and Redis | Nothing written |
| Walker assigns `task.completed = True` | Written (with everything else) | Only that task written |
| New node + edge from root | Written | Node, edge and root written (root via `build_edge` mark) |
| In-place mutation `task.items.append(x)` | Written (because everything was) | **Not written** unless something else marks it dirty |
| Mongo `put` fails | Logged; Redis still updated | Logged; flag stays `True`; Redis still updated |
| SQLite backend | Every anchor `put` | Depends on SQLite `sync()` (not in diff) |

Users will notice that read-only requests no longer touch the database. The one intended-looking but risky change is the in-place mutation row. Treat it as a possible data-loss regression on MongoDB until it is checked.

## 11. Questions your senior might ask

**Q: What happens if a walker does `task.tags.append("x")`?**
`__setattr__` is not called, so `is_updated` stays `False`. On MongoDB that change is not written unless something else marks the anchor dirty. The PR has no test for it. This is a known gap.

**Q: Why reset `is_updated = False` in `get()` and `query()`?**
Rebuilding an anchor from Mongo uses the `True` default and runs `__setattr__` on each field. Without the reset, every loaded anchor would look dirty and get rewritten, which is the original bug.

**Q: Why build `l2_pending` before calling `l3.sync()`?**
`MongoBackend.put()` sets `is_updated = False` after writing. If you filtered afterwards, nothing would qualify, and Redis would never get updates. @Thamirawaran caught exactly this; a652eb5 fixed it.

**Q: Why mark nodes dirty in `build_edge` and `remove_edge`?**
Those functions change `anchor.edges` with `append` and `pop` on the anchor, not on the archetype. The `__setattr__` hook never sees them, and without the marks a node's new edge list would not be saved.

**Q: Does this change SQLite?**
`commit()` now calls `l3.sync()` for SQLite too, instead of `put` on every anchor. The code comment says SQLite's `sync()` uses hash-based detection, but that code is not in the diff, and none of the new tests cover SQLite.

**Q: Why does `commit(anchor)` force `is_updated = True`?**
An explicit single-anchor commit (used by `reset_graph`, for example) should always write, whatever the flag says.

**Q: Does this fix the race condition in #5038?**
Partly. Read-only requests no longer overwrite data, so that source of lost updates is gone. Writes are still whole-document `$set data` operations, so two requests that change the same node concurrently are still last-writer-wins.

**Q: Is the `__setattr__` override costly?**
It runs on every attribute set on every archetype in core Jac. It does one prefix check, one attribute read and one set. The PR includes no benchmark.

**Q: What if a Mongo write fails?**
`put()` logs the error and keeps `is_updated = True`, so the anchor is retried at the next commit. Redis still gets the anchor from `l2_pending`, so L2 can briefly be ahead of L3.
