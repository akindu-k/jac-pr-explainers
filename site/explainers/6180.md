## 1. The short version

`test_mongo_layer123.jac` tests the jac-scale `MongoBackend`. These tests cover how it stamps documents with metadata, quarantines broken documents, recovers them, and writes nodes atomically. The tests use **testcontainers**, a library that starts a real MongoDB (and in one case Redis) in Docker for the test.

**Before this PR, every one of the 13 tests started and stopped its own Docker container. That made 13 MongoDB starts plus 1 Redis start per run.** The suite was also not in CI. Because nobody ran it there, one test had quietly broken: it called `backend.put(anchor)` and then expected the document in Mongo. Your description says `put()` is now a no-op. Two other tests also carried a cache workaround that existed only because each test had a different container.

**You changed the file so all tests share one lazily started MongoDB container and one Redis container, stopped at process exit via `atexit`. Each test now starts by wiping data (`_reset_mongo()` / `_reset_redis()`), and the suite is now a step in the CI workflow.** Along the way you fixed the broken test (`put` → `_write_to_db`), removed the dead `_process_cache.pop(...)` calls, and renamed short variables.

**Status:** Merged on 2026-06-02. No reviews or comments are recorded on the PR. All test checks on the head commit `c8325c8` passed. The release jobs were skipped, which is normal for a non-release PR.

| Quarantine (`_anchors_quarantine`) | A side collection. Documents that can't be loaded are moved there instead of being deleted. |
| `recover_all` / `recover_one` / aliases | Ways to move quarantined documents back. Aliases map an old class name to a live class. |
| `put()` | Backend write call. Per your description it is now an empty no-op, and real writes happen in `sync()`. |
| `_write_to_db(anchor)` | Private method that does a full upsert (insert-or-update) of an anchor. `sync()` uses it. The first test now calls it. |
| `_put_node_atomic` | Private method that atomically merges a node's edge list in Mongo (issue #6076). |
| `_process_cache` | A process-wide cache in jac-scale that, from the removed comments, holds `mongo_client` / `mongo_available`. |
| Docker / testcontainers | Docker runs throwaway services. `MongoDbContainer` / `RedisContainer` start them from a test and give you a URL. |
| Container lifecycle | One `start()` + `stop()` of a container. It takes seconds each time. **This is where the problem is: one per test.** |
| `glob _shared: dict` | A Jac module-level (global) variable. Here it is a dict that holds the shared container, URI and client. |
| Lazy init | Create something on first use, not up front. `_get_mongo()` starts the container only the first time it is called. |
| `atexit.register(fn)` | Python stdlib. Runs `fn` when the interpreter exits. Used to stop the shared containers. |

| Test isolation | One test's data must not affect another's. Before, a fresh container guaranteed it. Now the reset helpers do. |

## 3. The problem, step by step

### 3.1 The setup

- **The test file:** `test_mongo_layer123.jac`, with 13 tests.
- **Each test** needed a MongoDB. The last test also needed Redis.
- **A sister file** `test_memory_hierarchy.jac` already used a shared-container pattern (`_shared`, `_get_mongo`, `_reset_mongo`), per issue #6168.
- **The CI workflow** ran `test_mongo_user_manager.jac` and `test_serializer_social.jac`, but not this file.

### 3.2 What went wrong: one container per test

```text
1. Test 1 starts       -> MongoDbContainer("mongo:latest").start()   (port A)
2. Test 1 body runs    -> MongoBackend(mongo_url=A)
3. Test 1 finally      -> container.stop()
4. Test 2 starts       -> new container .start()                     (port B)
   ... repeated ...
13. Last test          -> starts a Mongo AND a Redis container, stops both
=> 13 Mongo + 1 Redis start/stop cycles per run   <-- WRONG: slow, and the reason
                                                     the suite was kept out of CI
```

The issue said "8 tests × Docker start/stop". The file actually has 13 tests that each started their own Mongo container.

### 3.3 What went wrong: the first test could not pass

```text
1. person = _MongoLayer123Person(name="alice", age=30); anchor.persistent = True
2. backend.put(anchor)            -> per description: put() is now a no-op
3. Mongo _anchors collection      -> still empty
4. find_one({'_id': anchor.id})   -> None
5. assert doc is not None         -> FAILS   <-- WRONG: test is stale vs. current put()
   (Not noticed because the file never ran in CI.)
```

The diff does not show `MongoBackend.put()` itself. The claim that it is a no-op comes from your description.

### 3.4 What went wrong: the cache workaround

```text
1. Test X (port A) creates MongoBackend -> _process_cache['mongo_client'] = client(A)
2. Test X stops container A
3. Test Y starts container B, creates MongoBackend
4. Backend reuses _process_cache['mongo_client'] -> still points at A (dead)  <-- WRONG
   Workaround: the two _put_node_atomic tests did _process_cache.pop('mongo_client')
               and pop('mongo_available') before starting.
```

### 3.5 Why it mattered

- **CI time.** Every container lifecycle costs Docker start/stop time. The issue calls the saving "meaningfully faster in CI".
- **No coverage.** Without CI, the quarantine, recovery and #6076 tests could break silently. That is what happened to the `put` test.
- **Consistency.** The issue asked to match `test_memory_hierarchy.jac`.

## 4. The idea of the fix (one sentence)

> **Start the containers once, wipe the data per test.** Containers are started lazily on first use, kept in a module-level dict, and stopped at exit. Each test drops its databases and flushes Redis instead of getting a new container.

Wiping a database gives the same clean slate as a fresh container, and costs milliseconds instead of seconds. All tests use the same `db_name="jac_test_l123"`, so dropping non-system databases covers everything they touch.


### 6.2 A Mongo-only test (12 of 13 tests)

```text
test "..." {
├─ _reset_mongo()                                    ← NEW
│   ├─ first test: "mongo_client" not in _shared -> return (nothing to wipe)
│   └─ later tests: drop every DB except admin/config/local
├─ (client, uri) = _get_mongo()                      ← NEW
│   ├─ first call: start MongoDbContainer, store container/uri/client,
│   │              atexit.register(container.stop)
│   └─ later calls: return cached (client, uri)
├─ backend = MongoBackend(mongo_url=uri, db_name="jac_test_l123")
├─ seed docs / call backend method
├─ assert via the shared `client`                    ← CHANGED (was a new MongoClient per test)
└─ backend.close()                                   ← no container.stop() any more
```

### 6.3 The Redis + Mongo test ("cascade quarantine invalidates Redis L2 cache")

```text
├─ _reset_mongo(); _reset_redis()                    ← NEW
├─ (_, mongo_uri) = _get_mongo()                     ← CHANGED (shared)
├─ (_, redis_url) = _get_redis()                     ← NEW (shared Redis, port=6379 exposed)
├─ _process_cache.clear()
├─ os.environ["MONGODB_URI"/"REDIS_URL"] = ...       ← CHANGED: now set before `try`
├─ try { ScaleTieredMemory().postinit(); ... asserts }
└─ finally { _process_cache.clear(); pop env vars }  ← containers NOT stopped here any more
```

### 6.4 Process exit

```text
interpreter exits
└─ atexit handlers run -> redis_container.stop(), mongo_container.stop()   ← NEW
   (The shared MongoClient / redis.Redis are never explicitly closed.)
```

| Scenario | Before | After |
|---|---|---|
| Containers started per run | 13 Mongo + 1 Redis | 1 Mongo + 1 Redis |
| Clean state between tests | New container | `drop_database` / `FLUSHALL` |
| Suite in CI | No | Yes |
| First test's write | `put()` (no-op, so the assert fails) | `_write_to_db()` (real upsert) |

### 7.1 `jac-scale/jac_scale/tests/test_mongo_layer123.jac`

**New shared infrastructure**

```diff
+import atexit;
+import redis;
+glob _shared: dict = {};
+
+def _get_mongo -> tuple {
+    if "mongo_client" not in _shared {
+        container = MongoDbContainer("mongo:latest");
+        container.start();
+        uri = container.get_connection_url();
+        _shared["mongo_container"] = container;
+        _shared["mongo_uri"] = uri;
+        _shared["mongo_client"] = MongoClient(uri);
+        atexit.register(container.stop);
+    }
+    return (_shared["mongo_client"], _shared["mongo_uri"]);
+}
+
+def _reset_mongo -> None {
+    if "mongo_client" not in _shared { return; }
+    system_dbs = {"admin", "config", "local"};
+    for db_name in _shared["mongo_client"].list_database_names() {
+        if db_name not in system_dbs { _shared["mongo_client"].drop_database(db_name); }
+    }
+}
+
+def _get_redis -> tuple { ... RedisContainer("redis:latest", port=6379) ...
+    redis.Redis(host=host, port=int(exposed_port), decode_responses=False) ... }
+def _reset_redis { if "redis_client" in _shared { _shared["redis_client"].flushall(); } }
```

- **Mongo helpers.** `_get_mongo` follows the pattern from `test_memory_hierarchy.jac` that issue #6168 points to. The diff doesn't show that file, so you can't verify line-for-line parity from here.
- **Reset is called before get.** On the very first test, the reset is a no-op. That is fine because the container is brand new.
- **Redis helpers.** `_get_redis` / `_reset_redis` go beyond what the issue asked for. They exist because the last test needs Redis too.
- **Not shown in the diff.** The `MongoDbContainer`, `RedisContainer` and `_process_cache` imports are outside the hunks, so they presumably already existed.

## 11. Questions your senior might ask

**Q: How much faster is it?**
Container lifecycles drop from 13 Mongo + 1 Redis to 1 + 1 per run. The PR doesn't report timings, so you can't give seconds.

**Q: How do you keep tests isolated without fresh containers?**
Every test calls `_reset_mongo()` first, which drops every non-system database. The Redis test also calls `_reset_redis()` (`FLUSHALL`). All tests use `jac_test_l123`, so this matches a fresh container.

**Q: Why `_write_to_db` and not `put`?**
Per your description, `put()` is now a no-op and writes happen in `sync()`, which calls `_write_to_db`. The test checks the stored document's metadata, so it calls the real write directly. The diff doesn't show `put()`, so this relies on your knowledge of `MongoBackend`.

**Q: Is it safe to remove the `_process_cache.pop` calls?**
They existed because each test had its own port, so a cached client pointed at a dead container. With one shared container, the URI never changes inside this file's process. The Redis test also clears `_process_cache` before and after it runs.

**Q: What if this file runs in the same pytest process as `test_memory_hierarchy.jac`?**
Each file has its own `_shared` and container. Whether `_process_cache` could hand one file's client to the other depends on how `MongoBackend` keys the cache, which this PR doesn't show. CI runs this file in its own pytest call, so CI is not affected.

**Q: What happens if the test process crashes before `atexit` runs?**
The containers would not be stopped by your code. testcontainers usually has its own reaper container, but the PR doesn't confirm that it is enabled.

**Q: Why does `_reset_mongo` run before `_get_mongo`?**
On the first test, `_reset_mongo` sees no client and returns. That is fine because the container is new. On later tests it wipes the leftover data. It also keeps `_reset_mongo` from starting a container as a side effect.

**Q: Why also share Redis when the issue only mentioned Mongo?**
Only one test uses Redis, but it used to start both containers itself. Giving Redis the same lazy helper keeps the file consistent and removes its per-test lifecycle too.

**Q: Did any test logic change?**
Only the first test's write call and its name ("on put" → "on write"). The rest are boilerplate removal, variable renames (`col` → `anchors_col`, `q_col` → `quarantine_col`, `p` → `person_node`, `s` → `summary`), and removal of some comments.
