## 1. The short version

`MongoBackend.execute_plan` runs a query plan against MongoDB and yields the matching anchors, which are the stored records behind Jac nodes and edges. When the plan carries a slice (a page, such as "rows 50 to 100"), the backend hands that slice to MongoDB as `.skip()` and `.limit()` instead of fetching everything and slicing in Python. This is called "slice pushdown".

**The bug: `execute_plan` called `.skip()`/`.limit()` with no `.sort()` first, so MongoDB returned pages from its "natural order", which is not stable. Pages could overlap, repeat rows, or drop rows, and the same request could return a different page each time.**

**The fix: every `execute_plan` query now runs `.sort('_id', 1)` before skip/limit. Pages are taken from a stable, index-backed order, and sliced and unsliced queries see the same sequence.**

Your first commit sorted only sliced queries. A Greptile review comment pointed out that this made pushed-down slices disagree with "full scan, then slice in memory". Your second commit therefore sorts all plan queries.

**Status:** Merged on 2026-07-14. There were no human reviews, only the Greptile bot (confidence 5/5). All CI test checks passed.

## 3. The problem, step by step

### 3.1 The setup

- A caller asks for a page of results, which becomes a `QueryPlan` with `slc = slice(0, 50)`.
- `_try_pushdown` sees that MongoDB supports `slice`, so it lets `MongoBackend.execute_plan` handle the slice.
- `_plan_to_mongo_filter` gives `(filt, skip_n=0, limit_n=50)`.
- `execute_plan` builds `collection.find(filt)`, adds `.skip()`/`.limit()`, and yields anchors.

### 3.2 What went wrong: unstable pages

```text
1. Collection holds docs A B C D E F (by _id). After updates/deletes,
   natural order on disk is now: C A F B E D
2. Request page 1: find(filt).skip(0).limit(3)          (no sort)
   → MongoDB walks natural order → returns C A F
3. Some writes happen; natural order shifts to: A C B F E D
4. Request page 2: find(filt).skip(3).limit(3)          (no sort)
   → returns F E D
5. Union of pages: C A F + F E D
   → F appears twice, B never appears              ← WRONG: overlap + dropped row
6. Re-run page 1 later → A C B (different from step 2) ← WRONG: not repeatable
```

### 3.3 Why the first fix was not enough: pushdown transparency

This was your first commit (307e5d6), which sorted only sliced queries.

```text
1. Natural order: C A F B E D ; _id order: A B C D E F
2. Sliced query slice(0,3), pushed down → sorted by _id → A B C
3. Same query, no slice (or a backend without slice capability):
   full scan → natural order C A F B E D → in-memory [0:3] → C A F
4. A B C != C A F                                   ← WRONG: pushdown changes the answer
```

The Greptile bot flagged this case. Your second commit (dfe2d0f) fixes it by sorting every query.

### 3.4 Why it mattered

Issue #6747 says it plainly: the same paginated request could return a different page, and successive pages could overlap or leave gaps. Any MongoDB-backed deployment that pages through results (lists, feeds, admin views) could show duplicate items or silently skip items. The issue also says that a backend which advertises slice pushdown should be *required* to apply a deterministic sort.

## 4. The idea of the fix (one sentence)

> **Always sort by `_id`.** Every MongoDB plan query is ordered by the indexed `_id` field before any skip/limit, so the order is stable and the same whether or not a slice is present.

`QueryPlan` has no ordering field, so `_id` is the only key that is always present and unique. Its index makes the sort cheap. Sorting all queries, not just sliced ones, is what keeps a pushed-down slice equal to an in-memory slice of the full scan.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/memory/impl/memory_hierarchy.mongo.impl.jac`: sort every plan query by `_id`

```diff
     (filt, skip_n, limit_n) = _plan_to_mongo_filter(plan);
     try {
-        cursor = self.collection.find(filt);
+        # sort every query by _id so a pushed-down slice matches an in-memory slice
+        cursor = self.collection.find(filt).sort('_id', 1);   # NEW: stable ascending _id order
         if skip_n {
             cursor = cursor.skip(skip_n);
         }
```

**What:** The cursor is now sorted ascending by `_id` before the existing `skip`/`limit` lines run. The sort applies whether or not the plan has a slice.

**Why:**
- It fixes the unstable pages (3.2), because skip/limit now walk a fixed order.
- It fixes the transparency problem (3.3), because unsliced scans use the same order as sliced ones.

**Things to notice:**
- The change is one functional line plus a comment, which is why the size is +2 −1.
- PyMongo applies `sort` before `skip`/`limit` no matter which order you chain them. Putting it right on `find()` simply reads clearly.
- `_id` order is stable, but it is not necessarily "meaningful" order. If `_id` is an ObjectId, it roughly follows insertion time. If it is a UUID string, the order is effectively random but fixed. The diff does not show which type jac-scale uses. The issue's "Better" suggestion was to sort by the query's intended ordering field. That was left out because `QueryPlan` has no such field.
- Only `execute_plan` changed. Other MongoDB read paths in this file (if any) are not visible in the diff.
- The issue names the old path `jac-scale/jac_scale/impl/memory_hierarchy.mongo.impl.jac`. The code now lives under `jac/jaclang/scale/memory/impl/`, so it seems to have moved after the issue was filed.

## 6. How execution flows after the PR

### 6.1 Running a sliced (paginated) plan on MongoDB

```text
caller requests result[50:100]
└─ _try_pushdown: backend has `slice` capability → push down
   └─ MongoBackend.execute_plan(plan)
      ├─ _plan_to_mongo_filter(plan) → (filt, skip_n=50, limit_n=50)
      ├─ cursor = collection.find(filt).sort('_id', 1)     ← CHANGED
      ├─ if skip_n → cursor.skip(50)
      ├─ if limit_n is not None → cursor.limit(50)
      └─ yield anchors in _id order, rows 50–99
```

### 6.2 Running an unsliced plan on MongoDB

```text
caller requests full result (or a backend slices in memory afterwards)
└─ MongoBackend.execute_plan(plan)
   ├─ _plan_to_mongo_filter(plan) → (filt, 0, None)
   ├─ cursor = collection.find(filt).sort('_id', 1)        ← CHANGED
   └─ yield all matching anchors in _id order
      └─ (optional) in-memory result[a:b] → same rows as 6.1 would push down
```

| Scenario | Before | After |
|---|---|---|
| Same page requested twice | Could differ | Identical |
| Page 1 + page 2 | Could overlap or have gaps | Disjoint and contiguous |
| Pushed-down slice vs full scan + in-memory slice | Could differ | Identical |
| Order of unsliced results | Natural order (unstable) | Ascending `_id` |
| Cost | Plain scan | Index-backed sort on `_id` (no blocking in-memory sort) |

**User-visible change:** Unsliced MongoDB plan results now come back in `_id` order instead of natural order. Code that relied on natural order was relying on undefined behaviour anyway, but the order a user sees may change.

## 11. Questions your senior might ask

**Q: Why `_id` and not some other field?**
`QueryPlan` has no ordering field. `_id` is the only key that is always present, unique (so there are no ties) and indexed.

**Q: Does the sort make queries slower?**
Not much. `_id` always has an index, so MongoDB walks the index instead of doing a blocking in-memory sort. One possible cost: when a filter would be better served by another index, MongoDB may need to choose between that index and the `_id` sort. The PR shows no benchmark for this.

**Q: Why sort unsliced queries too?**
To keep pushdown transparent. A pushed-down slice must equal "full scan, then slice in memory". If only sliced queries were sorted, the two would disagree. Greptile flagged exactly this on your first commit.

**Q: Is `_id` order meaningful to users?**
It is stable, not meaningful. If `_id` is an ObjectId it roughly follows creation time. The diff does not show what type jac-scale uses for anchor `_id`s.

**Q: Where is the regression test?**
It is not in the diff. The description mentions it and describes testcontainers verification, but no test file changed. You should add it in a follow-up or correct the description.

**Q: Does pagination still break if rows are inserted or deleted between page requests?**
Yes, somewhat. Offset paging over a stable order can still shift by one when rows before the offset are added or removed. This fix removes the randomness from natural order. It does not give snapshot or keyset (cursor-based) paging.

**Q: Could anything depend on the old natural order?**
Natural order was never guaranteed, so nothing should depend on it. Unsliced result order is now `_id` ascending, which is a visible change.

**Q: Does the in-memory backend behave the same way?**
The description says it returns a consistent sequence for `result[plan.slc]`. The diff does not show its code, so I can't confirm its order matches `_id` order.

**Q: Are other MongoDB read paths affected?**
Only `execute_plan` changed. Whether other `find()` calls in the file also do skip/limit without a sort can't be told from this diff.
