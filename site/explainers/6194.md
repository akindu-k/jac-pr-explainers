## 1. The short version

jac-scale stores Jac graph data (nodes and edges, called "anchors") in three tiers. L1 is in-process memory. L2 is a Redis cache shared by all pods. L3 is MongoDB, the source of truth. When MongoDB holds a node that can no longer be loaded (for example, its class no longer exists), `_mongo_quarantine` moves it to a quarantine collection. It also "cascade-quarantines" every edge connected to it and removes those edge IDs from every other live node's `data.edges` list.

**The bug: all of that cleanup happened only in MongoDB. Redis kept the old copies of the affected nodes, and those copies still listed the deleted edge IDs.** Reads check Redis before Mongo, so any pod that read such a node got the stale edge list. It then looked up an edge that no longer existed and failed with `EdgeAnchor [7a1d285c-...] is not a valid reference`. Restarting pods did not help, because Redis is shared and outlives them. On jac-builder-dev this broke `create_session` for every user (issue #6184).

**The fix: `MongoBackend` now holds a reference to the Redis backend (`_l2_ref`), and `_mongo_quarantine` deletes the matching Redis key after each of its three Mongo writes.** Those keys are the quarantined node, each orphaned edge, and each live node whose edge list was trimmed. The next read misses Redis, falls through to Mongo, and gets the clean data.

**Status:** Merged on 2026-05-27. @udithishanka approved it. All test checks passed. One follow-up (remove the `any` types) is tracked in #6208.

## 3. The problem, step by step

### 3.1 The setup

- **Read path:** `TieredMemory.get` → L1 → L2 (Redis) → L3 (Mongo).
- **Load failure:** `MongoBackend.get` and `MongoBackend._load_anchor` call `_mongo_quarantine` when a document fails to deserialize or its class can't be found. That gives four call sites.
- **What `_mongo_quarantine` writes to Mongo:**
  1. `delete_one` removes the bad node.
  2. `delete_many` removes the orphaned edges.
  3. `update_many` with `$pullAll` removes those edge IDs from live nodes.
- **What it could reach:** before this PR it was given only `backend` (L3). It had no handle to Redis.

### 3.2 What went wrong

This follows the production timeline in #6184:

```text
1. System root R is in Mongo and Redis.   R.data.edges = [..., E]   (E = 7a1d285c, links R -> node N)
2. A pod loads N; deserialize fails       -> _mongo_quarantine(N)
3. Mongo: delete_one(N)                   -> N gone from Mongo        Redis: unchanged
4. Mongo: delete_many([E])                -> E gone from Mongo        Redis: unchanged (E was never cached)
5. Mongo: update_many $pullAll [E]        -> Mongo R.data.edges = 189 edges, no E
                                             Redis anchor:R still contains E   <-- WRONG: never invalidated
6. Pods restart (09:43Z). L1 is empty, Redis is not.
7. create_session walks from R            -> L2 hit, returns stale R with E
8. mem.get(E)                             -> L2 miss, L3 miss, returns None
9. Walker raises: EdgeAnchor [7a1d285c-...] is not a valid reference
10. Fixing Mongo by hand does not help    -> Redis still serves stale R
```

A smaller version of the same gap: the quarantined node N and any cached edge E could also remain in Redis. If so, a cache hit would bypass the quarantine entirely. The PR invalidates those keys as well.

### 3.3 Why it mattered

- #6184 says this was "blocking jac-builder-dev right now (every user, old and new)."
- The damage persists. Redis is shared across replicas, so restarts don't clear it.
- The existing manual repair ("hand-fixing Mongo") was not enough without also flushing Redis.
- #6181 is the separate upstream cause: why the node failed to load in the first place. This PR only fixes the cache staying stale afterwards.

## 4. The idea of the fix (one sentence)

> **Give Mongo a handle to Redis and delete every key it changes.** After each Mongo write in the quarantine cascade, the matching Redis entry is removed, so the next read reloads the corrected document from Mongo.

Deleting cache entries is simpler and safer than rewriting them. The next normal read refills Redis from the source of truth. Passing the reference the same way as the existing `_mem_ref` / `set_memory_ref` keeps the design consistent.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/memory_hierarchy.jac`: declare the new field and method

```diff
         _mem_ref: (dict[UUID, Anchor] | None) = None,
+        _l2_ref: (any | None) = None,          # NEW: handle to the Redis backend
         fetch_count: int = 0,
...
     def set_memory_ref(mem: dict[UUID, Anchor]) -> None;
+    def set_cache_ref(cache: (any | None)) -> None;   # NEW
```

**What:** `MongoBackend` gets an optional `_l2_ref` field, empty by default, and a setter for it.

**Why:** `_mongo_quarantine` needs a way to reach Redis. This is that way.

**Things to notice:** The type is `any | None`, not `RedisBackend | None`. @kugesan1105 asked for this to be tightened, and that work is tracked in #6208. A likely reason for `any` is to avoid a circular reference between backend types, but the PR doesn't say.

### 5.2 `jac-scale/jac_scale/impl/memory_hierarchy.main.impl.jac`: wire L2 into L3

```diff
         mongo_backend.set_memory_ref(self.__mem__);
+        # Give MongoDB access to L2 cache so quarantine ops can invalidate Redis
+        mongo_backend.set_cache_ref(self.l2);
```

**What:** When `ScaleTieredMemory.postinit` sets up Mongo, it hands Mongo the Redis backend.

**Why:** Without this line `_l2_ref` stays `None`, and none of the new invalidations run.

**Things to notice:** If Redis isn't configured, `self.l2` is `None` (an assumption; the test asserts `mem.l2 is not None` only when Redis exists). Every new `if l2` check then skips, so Mongo-only setups behave as before. The PR description says L2 is initialised before this line. The diff does not show the L2 setup code, so you can't confirm the ordering from the diff alone.

### 5.3 `jac-scale/jac_scale/impl/memory_hierarchy.mongo.impl.jac`: invalidate Redis during quarantine

**(a) New parameter and invalidation of the quarantined node**

```diff
-    from_format_version: (int | None) = None
+    from_format_version: (int | None) = None,
+    l2: (any | None) = None                     # NEW: optional Redis backend
 ...
         backend.collection.delete_one({'_id': id_str});
+        if l2 {
+            l2.delete(to_uuid(id_str));           # NEW: drop quarantined node from Redis
+        }
```

**(b) Record the affected live nodes before Mongo changes them**

```diff
                 orphan_edge_ids = [e['_id'] for e in orphaned_edges];
+                affected_node_ids = [];
+                if l2 {
+                    affected_nodes = backend.collection.find(
+                        {'type': 'NodeAnchor', 'data.edges': {'$in': orphan_edge_ids}},
+                        {'_id': 1}                # only fetch IDs
+                    );
+                    affected_node_ids = [doc['_id'] for doc in affected_nodes];
+                }
```

**(c) Invalidate the edges and the affected nodes after the Mongo writes**

```diff
                 backend.collection.delete_many({'_id': {'$in': orphan_edge_ids}});
+                if l2 {
+                    for eid in orphan_edge_ids {
+                        l2.delete(to_uuid(eid));   # NEW: drop orphaned edges from Redis
+                    }
+                }
                 backend.collection.update_many(
                     {'type': 'NodeAnchor', 'data.edges': {'$in': orphan_edge_ids}},
                     {'$pullAll': {'data.edges': orphan_edge_ids}}
                 );
+                if l2 {
+                    for nid in affected_node_ids {
+                        l2.delete(to_uuid(nid));   # NEW: drop trimmed live nodes from Redis
+                    }
+                }
```

**(d) Setter, the four call sites, and cleanup on close**

```diff
+impl MongoBackend.set_cache_ref(cache: (any | None)) -> None {
+    self._l2_ref = cache;
+}
 ...
             from_format_version=fmt_version,
+            l2=self._l2_ref                       # same change in get() x2, _load_anchor() x2
 ...
 impl MongoBackend.close -> None {
     self._mem_ref = None;
+    self._l2_ref = None;                          # NEW (commit b3bd26d)
```

**What:** `_mongo_quarantine` can now take a Redis backend. When it gets one, it deletes the Redis key for:
- the quarantined node,
- every orphaned edge,
- every live node whose `data.edges` it trimmed.

All four internal callers pass `self._l2_ref`. `close()` drops the reference, the same way it already drops `_mem_ref`.

**Why:** Step (c)'s second loop fixes the production failure, the stale system root. The other two deletions stop a cache hit from returning an anchor that Mongo has already quarantined.

**Things to notice:**
- **Ordering matters.** The `find` for affected nodes runs before `update_many`. After the `$pullAll`, no document matches `data.edges: {$in: orphan_edge_ids}`, so querying afterwards would return nothing.
- **The extra query only runs when Redis is present.** It fetches only `_id`.
- **Each key is deleted on its own.** There is one `l2.delete` call per key, with no batching. In the incident in #6184, about 1774 documents were cascaded. Whether that cost matters depends on `RedisBackend.delete`, which isn't in the diff.
- **Error handling is not visible.** All of this runs inside the function's existing `try`. The diff doesn't show the `except` branch, so you can't tell from it what happens if a Redis delete fails partway through.
- **The guard uses truthiness** (`if l2`), not `is not None`.
- **Other callers keep working.** The parameter is optional with default `None`, so any other caller is unaffected.
- **The design differs from the issue's suggestion.** The issue suggested moving `_mongo_quarantine` onto `ScaleTieredMemory`. You chose to pass a reference instead, mirroring `set_memory_ref`.
- **No existing stale entries are repaired.** Redis entries that were already stale before deploy (as on jac-builder-dev) still need a manual flush. The PR only stops new divergence.

## 6. How execution flows after the PR

### 6.1 Startup wiring

```text
ScaleTieredMemory.postinit
├─ init L2 (RedisBackend) → self.l2  (or None if no Redis)
└─ init L3 (MongoBackend) → self.l3
   ├─ set_memory_ref(self.__mem__)
   └─ set_cache_ref(self.l2)                       ← NEW
```

### 6.2 Loading a node that can't be rehydrated

```text
mem.get(bad_id)
├─ L1 miss, L2 miss
└─ MongoBackend.get / _load_anchor
   ├─ deserialize fails or class unresolvable
   └─ _mongo_quarantine(..., l2=self._l2_ref)      ← CHANGED
      ├─ upsert into _anchors_quarantine
      ├─ delete_one(bad node)
      ├─ l2.delete(bad node)                        ← NEW
      └─ if NodeAnchor and has edges:
         ├─ find live nodes referencing those edges ← NEW (before update)
         ├─ bulk_write edges into quarantine
         ├─ delete_many(edges)
         ├─ l2.delete(each edge)                    ← NEW
         ├─ update_many $pullAll on live nodes
         └─ l2.delete(each affected live node)      ← NEW
   └─ return None
```

### 6.3 The next read of a trimmed live node

```text
mem.get(source_id)  (any pod)
├─ L1 miss
├─ L2 miss  (key was deleted)                       ← CHANGED (was a stale hit)
└─ L3 read → data.edges without dead IDs → re-cached in L2
   └─ walker traversal finds no dangling edge
```

| Scenario | Before | After |
|---|---|---|
| Live node cached in Redis, its edge cascade-quarantined | Redis serves stale `data.edges`; traversal fails "not a valid reference" | Redis key deleted; fresh read from Mongo |
| Quarantined node itself cached in Redis | Cache hit could still return it | Key deleted |
| Orphaned edge cached in Redis | Could still resolve from cache | Key deleted |
| No Redis configured (`l2` is None) | Mongo-only cascade | Same; no extra query |
| Pod restart after cascade | Stale entries persist | Nothing stale left to persist |
| Redis already stale before deploy | Broken | Still broken until manually flushed |

The change users will notice: traversals no longer fail after a cascade quarantine. The cost is one extra Mongo `find` plus N Redis deletes, paid only when a cascade happens.

**Test: "cascade quarantine invalidates Redis L2 cache for connected live nodes"**

1. Start real Mongo and Redis containers and point `MONGODB_URI` and `REDIS_URL` at them.
2. Build a `ScaleTieredMemory` and assert both `l3` and `l2` exist.

## 11. Questions your senior might ask

**Q: Why query affected nodes before `update_many` instead of after?**
After the `$pullAll`, no document's `data.edges` contains the orphan IDs, so the same filter would return nothing.

**Q: Why not move `_mongo_quarantine` onto `ScaleTieredMemory`, as the issue suggested?**
You followed the existing `_mem_ref` / `set_memory_ref` pattern. It is a smaller change and keeps the function where its four callers live.

**Q: Why delete Redis keys instead of writing the corrected document?**
Deleting is simpler and can't write a wrong value. The next read refills Redis from Mongo, the source of truth.

**Q: What happens when Redis isn't configured?**
`self.l2` is `None`, every `if l2` block is skipped, and the extra `find` is not run. Behaviour is the same as before.

**Q: Does this fix the Redis data already broken on jac-builder-dev?**
No. It only prevents new divergence. Existing stale keys must be flushed once.

**Q: Is there still a race between pods?**
Possibly, and the PR doesn't address it. A pod could read the old node from Mongo just before `update_many` and write it to Redis after your delete. The window is small. The PR has no locking or versioning for this.

**Q: What if a Redis delete throws midway?**
The code runs inside the function's existing `try`. The diff doesn't show the `except` branch, so you would need to check the rest of the function to answer this precisely.

**Q: Is one Redis call per key a performance problem for large cascades?**
It costs N round trips, and a cascade only happens on a quarantine, which is rare. The incident involved about 1774 documents. Pipelining could be a later improvement. It depends on how `RedisBackend.delete` is built, which isn't in the diff.

**Q: Why the `any` types?**
They were left loose in this PR. @kugesan1105 flagged them, and #6208 tracks the fix.

**Q: Does the test cover all three invalidations?**
It asserts only the live-node invalidation, which is the one that caused the outage. The quarantined node and edge were not cached in the test, so those deletes run but are not checked.
