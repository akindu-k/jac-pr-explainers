## 1. The short version

Jac can save graph data (nodes and edges) to a database. When a saved record can't be loaded safely, the runtime moves it to a side table called the **quarantine**. `recover_all` later tries to move quarantined records back to the live table. When it restores an edge, it also "re-links" the edge: it adds the edge's id to the `data.edges` list of the node at each end.

**Bug 1: `recover_all` processed quarantined records in whatever order the database returned them. If an edge came before its own node, the re-link step found no live node, did nothing, and the node came back with an empty `data.edges` list.** For example, quarantine holds edge `E` and then node `N`. `recover_all` returns `(2, [])`, which looks like full success, yet `N.data.edges == []`.

**Bug 2: when the re-link target node was missing, neither backend said anything.** In SQLite the `if node_row { ... }` had no `else`. In Mongo the result of `update_one` was thrown away, so a write that matched nothing looked the same as a write that worked.

**Your fix sorts each recovery batch so every `NodeAnchor` is restored before any `EdgeAnchor`. It also logs a `logger.warning` whenever a re-link target node is not live.** The fix is applied the same way in both backends: `SqliteMemory` in jaclang and `MongoBackend` in jac-scale. You also added four regression tests and two release-note fragments.

**Status:** Merged on 2026-05-26. No reviews or comments were left. All test checks on the head commit `30aadfe` passed. The release-pipeline jobs were skipped, which is normal for a non-release PR.

## 3. The problem, step by step

### 3.1 The setup

- **Two places store anchors.** There is a live store (`anchors` / `_anchors`) and a quarantine store (`anchors_quarantine` / `_anchors_quarantine`).
- **A cascade quarantine can leave a node and its edges side by side in quarantine.**
- **`recover_all` does three things:**
  1. Reads all quarantine rows or documents. You cannot see the query in the diff, but it has no ordering that favours nodes.
  2. Loops over them and calls the attempt-recover helper for each.
  3. Counts successes.
- **Re-linking an edge** means looking up each endpoint node in the *live* store and adding the edge id to its `data.edges`. If the node isn't live yet, there is nothing to patch.

### 3.2 What went wrong

#### 3.2.1 Edge recovered before its node (both backends)

```text
1. Quarantine contains:   [ E (EdgeAnchor, source=N, target=N),  N (NodeAnchor, edges=[]) ]
   Live store contains:   [ ]
2. recover_all reads rows in DB order          -> [E, N]
3. attempt_recover(E):
     E copied to live store                    live = [E]
     re-link: look up N in live store          -> not found
     SQLite: `if node_row {...}` false, no else -> nothing happens        ✗ WRONG
     Mongo:  update_one matches 0 docs, result discarded -> nothing happens ✗ WRONG
4. attempt_recover(N):
     N copied to live store with its stored edges list   live = [E, N], N.edges = []
5. recover_all returns (2, [])                 -> looks like full success
6. Final state: E is live, N is live, but N.data.edges = []   ✗ edge is not linked
```

The bug depends on the order the database returns rows. With an unordered SELECT or `find()`, SQLite and Mongo often return rows in insertion order, but neither promises any order. So the failure was intermittent and depended on data.

#### 3.2.2 Missing endpoint gives no signal (both backends)

```text
1. Quarantine contains:   [ E (source=G, target=G) ]     live store has no G
2. recover_all -> attempt_recover(E)
3. E copied to live store
4. re-link: look up G                           -> not found
     SQLite: no else branch                     -> no log   ✗ WRONG
     Mongo:  matched_count = 0, ignored         -> no log   ✗ WRONG
5. recover_all returns (1, [])                  -> operator sees "1 recovered", nothing else
```

The same silence happens in 3.2.1. It is also what you would see if a node stayed stuck in quarantine while its edge was recovered.

### 3.3 Why it mattered

- **No linked issue exists.** The problem was raised in a comment on PR #6003 (`jaseci-labs/jaseci#6003`, comment 4478869678).
- **Lost links.** After recovery, the node's `data.edges` did not list the edge. Code that reads a node's edges from `data.edges` would probably not see the edge. The diff doesn't show the load path, so this impact is inferred.
- **Misleading result.** `recover_all` reported every record as recovered. Operators had no warning that recovery was only partial, so they had no reason to look.

## 4. The idea of the fix (one sentence)

> **Nodes first, and never fail quietly.** Sort each quarantine batch so `NodeAnchor`s are restored before `EdgeAnchor`s, and log a warning whenever a re-link target node is not live.

Sorting removes the dependency on database order using one line per backend, with no schema or query changes. The warning covers the cases sorting cannot fix: the node truly doesn't exist, or the node stays stuck in quarantine.

```text

├─ SELECT rows from anchors_quarantine        (undefined order)
├─ rows.sort(nodes first, edges after)        ← NEW
```

| Scenario | Before | After |
|---|---|---|
| Node and edge both quarantined, DB returns node first | Linked correctly | Linked correctly |
| Node and edge both quarantined, DB returns edge first | `(2, [])`, `N.data.edges = []`, no log | `(2, [])`, edge linked |
| Edge quarantined, node already live | Linked | Linked (no change) |
| Edge quarantined, node absent everywhere | `(1, [])`, silent | `(1, [])`, warning logged |

## 11. Questions your senior might ask

**Q: Why not add `ORDER BY` to the query instead of sorting in Python?**
A: The sort works the same way for SQLite rows (`r[1]`) and Mongo dicts (`d.get('type')`) and needs no query change. Both lists are already fully in memory, because `recover_all` reads every row before looping. For very large quarantines a DB-side sort would avoid one extra pass, but it isn't needed for correctness.

**Q: Does the sort change the order of nodes among themselves?**
A: No. Python's sort is stable, so nodes keep their DB order and so do edges. Only nodes-versus-edges is reordered.

**Q: Why check `matched_count` and not `modified_count`?**
A: `$addToSet` leaves the document unchanged if the edge id is already present. `modified_count` would be 0 and cause a false warning. `matched_count` is 0 only when no live `NodeAnchor` with that id exists, which is exactly the "missing endpoint" case.

**Q: If the node is missing, why is the edge still recovered and counted?**
A: You kept the existing behaviour and only made it visible. The edge record itself loads fine, and holding it back would need new rules (for example, when to retry). The trade-off is that a dangling edge can end up live. The warning tells the operator so they can act.

**Q: Could the update create the missing node by accident?**
A: No. `update_one` is called without `upsert`, and the filter includes `type: 'NodeAnchor'`. Both "ghost node" tests check that no node row or document appears.

**Q: Do the ordering tests really fail without the fix?**
A: They insert the edge first. SQLite (fresh table, no `ORDER BY`) and Mongo (`find()` with no sort) almost always return insertion order, so the old code would restore the edge first and leave `data.edges` empty. But neither database guarantees that order. The PR doesn't show a run of the tests against the old code.

**Q: What still goes wrong that the PR doesn't fix?**
A: Two cases:
- A node stays in quarantine (still stuck) while its edge recovers. The edge is live but unlinked; now with a warning.
- The node is in a different batch or never existed. Same result: warning only.

The fix only guarantees correct linking when the node and edge are in the same batch and the node recovers successfully.

**Q: Why are there two release-note files?**
A: The change touches two packages, jaclang (`SqliteMemory`) and jac-scale (`MongoBackend`), and each has its own unreleased notes folder.

**Q: What are the `cast(NodeAnchor, ...)` and `bool(any(...))` changes for?**
A: They are type-checker fixes in existing jac-scale tests and do not change behaviour. They were added in `fc7c2d2` / `30aadfe`, probably so the test file passes `jac-check`. The commit messages hint at this, but the PR doesn't explain it.
