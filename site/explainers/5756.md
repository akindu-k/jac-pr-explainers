## 1. The short version

`DesktopConfig` is the part of jac-client that holds settings for desktop app builds. Its method `get_default_config()` returns a dictionary of default settings: name, version, window size, platforms, features and so on. PR #5494 added a new desktop build mode called `client_only`. It also added a method `is_client_only()` and a test that checks the default config has a `client_only` key.

**The bug: #5494 never added the `client_only` key to the dictionary that `get_default_config()` returns, so the existing test `test_client_only_config_is_supported` failed whenever it actually ran.** It went unnoticed because, on main CI, the `test-client` job stopped early (`pytest -x`) before it reached that test. PR #5754 changed CI in a way that made the test run, and the failure showed up for the first time.

**The fix: you added one line, `'client_only': False`, to the dict in `get_default_config()`.** You also added a release note. No tests changed, because the existing test already covers the behaviour.

**Status:** Merged on 2026-04-30. There were no reviews or comments. All test checks on the head commit passed, and the release pipeline jobs were skipped.

## 3. The problem, step by step

### 3.1 The setup

- `DesktopConfig.get_default_config()` builds the default settings dict.
- `is_client_only()` reads `client_only` from the loaded config.
- `test_client_only_config_is_supported` checks that `get_default_config()` contains `client_only` with the value `False`.
- The CI job `test-client` runs `pytest -x jac-client -n auto`.

### 3.2 What went wrong

```text
1. PR #5494 adds is_client_only() and test_client_only_config_is_supported.
2. PR #5494 does NOT add 'client_only' to get_default_config()'s dict.   ← WRONG STEP
   default config keys: name, identifier, version, window, platforms, features, ...
   'client_only' in config → False
3. On main CI, test-client runs with -x and -n auto.
4. Some earlier E2E test fails → -x tells xdist to stop the run.
5. Because worker scheduling is random, the client_only test is never reached.
6. The failing test stays hidden; CI looks fine for this test.
7. PR #5754 (jac format --check now enforced on test files) runs CI again.
8. This time the scheduler reaches test_client_only_config_is_supported.
9. The assertion that 'client_only' is in the default config fails. The bug is now visible.
```

### 3.3 Why it mattered

- Code that reads the default config directly would not find `client_only`. Whether `is_client_only()` itself was affected depends on how it reads the key (for example with a fallback). The diff does not show that method, so this can't be confirmed here.
- The test failure blocked or confused unrelated PRs such as #5754, which is how it was found.
- There is no linked issue and no comments, so no user reports are recorded.

## 4. The idea of the fix (one sentence)

> **Make the default config match what the code and tests expect.** Add `'client_only': False` to the dict returned by `get_default_config()`.

The test and `is_client_only()` already agree that the key should exist and default to `False`. The only part out of line was the defaults dict, so the smallest correct fix is to add the key there.

## 5. Every code change, explained

### 5.1 `jac-client/jac_client/plugin/src/impl/desktop_config.impl.jac`: add the missing default key

```diff
@@ -47,6 +47,7 @@ impl DesktopConfig.get_default_config(self: DesktopConfig) -> dict[str, Any] {

+        'client_only': False,        # NEW: default for the client_only build mode
```

**What:** The default config dict now includes `'client_only': False` as a top-level key.

**Why:** This was the key #5494 forgot. Its test expects the key to be present with the value `False`.

**Things to notice:**
- The default is `False`, so the client_only mode stays off unless a project turns it on. Normal desktop builds keep working as before.
- The PR description's diff shows the key placed right after `'version'`. In the real diff it sits after the window block (`'resizable'`, `'fullscreen'`) and before `'platforms'`. Order in a dict does not matter here, but the description does not match the code.
- It is a top-level key, not nested under `features`. That fits a key that `is_client_only()` reads directly, but the diff does not show that method, so this can't be checked here.

## 11. Questions your senior might ask

**Q: Why wasn't this caught when #5494 merged?**
The `test-client` job runs `pytest -x -n auto`. Earlier E2E failures stopped the run before xdist reached this test, so it never ran.

**Q: How was it finally found?**
CI for PR #5754 (which enforced `jac format --check` on test files) happened to reach and run the test, and it failed.

**Q: Does this change behaviour for existing desktop builds?**
It shouldn't. The default is `False`, so client_only mode stays off. The diff doesn't show how `is_client_only()` reads the key, so we can't confirm whether it previously had a fallback.

**Q: Why no new test?**
`test_client_only_config_is_supported` already checks both that the key exists and that it defaults to `False`. That is exactly this bug.

**Q: Why put the key at the top level and not under `features`?**
The PR says `is_client_only()` reads `client_only` from the loaded config, and the test checks the default config for it. A top-level key matches that. The method body is not in this diff.

**Q: Does the key's position in the dict matter?**
No. Dict order doesn't affect lookups. The description shows a different position than the code, but that is only cosmetic.

**Q: Is the CI hiding problem fixed?**
No. This PR only fixes the missing key. `-x` with parallel workers can still hide other failing tests, so it is worth a separate issue.

**Q: How do we know the test ran on this PR's CI?**
From the check results alone, we can't. `test-client` passed, but that doesn't prove this specific test executed. Checking the job log would confirm it.
