## 1. The short version

`jac scale deploy app.jac` builds a **sealed bundle** for Kubernetes. A sealed bundle is a packed file that holds the compiled app plus a precomputed "serving manifest", the metadata a pod needs to start serving. The pod later boots the file named on the command, here `app.jac`.

**The bug: for a single-app (non-workspace) deploy, the seal bakes the serving manifest for the `jac.toml` entry (`[project] entry-point`, or `main` when none is set), not for the file the pod actually boots.** When the two differ, one of two things happens. If there is no `main.jac` and no `entry-point`, the pack fails with `sealing without serve payloads`, even though the project is valid. If `entry-point` names a different module, the pack succeeds, but every pod crash-loops with `Sealed application is missing serving metadata`.

The PR description says it lands in two commits: first the failing test rows, then the fix. **What is actually on the branch is only the test half.** It adds two new table rows to an existing seal test, plus a one-line import declaration in `archwire.jac` so the test can import `solo_fleet`. The fix itself, which would make the bake use the deployed file, is not in the diff yet.

**Status:** Open, draft, no reviews. On head `ce5ab18`, "Contribution Checks" fails, `build-kit` is still running, and several test jobs were skipped.

## 3. The problem, step by step

### 3.1 The setup
- **Deploy side:** `jac scale deploy app.jac` → `deployed_tree` returns `app.jac` → `ManifestBuilder._derive_fleet` builds `solo_fleet(name, "app.jac")` → the pod gets `JAC_SV_FILE=app.jac`.
- **Seal side:** `pack_jab` → `_precompile_app` → `bake_serve_payloads(config, project, app="")` → `sealed_app_name` gives `""` → `bundle_app` → `implicit_app` uses `entry-point` or `main`.

Nothing passes the deployed file to the seal side.

### 3.2 Case A: no `main.jac`, no `entry-point`

```text
1. jac.toml: [project] name="mini" kind="service"   (no entry-point)
2. Files: app.jac, svc.jac                           (no main.jac)
3. User runs: jac scale deploy app.jac  → fleet = solo_fleet("mini","app.jac")
4. Seal: bake_serve_payloads(app="") → implicit_app → entry = "main"   ← WRONG: should be "app"
5. resolve_entry_file("main") finds nothing → no payloads written
6. #9610 gate: "sealing without serve payloads" → pack fails
7. Result: valid project cannot deploy
```

### 3.3 Case B: `entry-point` differs from the deployed file

```text
1. jac.toml: [project] entry-point="svc"
2. User runs: jac scale deploy app.jac  → pod JAC_SV_FILE=app.jac
3. Seal: implicit_app → entry = "svc" → manifest built for svc.jac   ← WRONG module
4. #9610 gate: payloads exist → pack succeeds
5. Pod boots app.jac → _prepare_sealed finds no metadata for app.jac
6. "Sealed application is missing serving metadata" → crash-loop on every pod
```

### 3.4 Why it mattered
- Issue #10398 notes that the docs use `jac scale deploy app.jac` everywhere, so Case A is easy to hit.
- Case B is worse. It passes on the host and only fails in the cluster.
- Workspace deploys are not affected, because `sealed_app_name` passes the root app.
- The issue also answers the open question on #9610: why the bake did not find the entry file.

## 4. The idea of the fix (one sentence)

> **Seal what the pod boots.** For a non-workspace deploy, take the module from the fleet's root member and use it as the entry point when baking.

The fleet is the same object that decides `JAC_SV_FILE`, so deriving the bake entry from it removes the mismatch at its source. Note that this idea comes from the issue's "Suggested fix". **This PR does not implement it yet** (see 5.1 and 10).

## 11. Questions your senior might ask

**Q: Why do workspace deploys not have this bug?**
Because `sealed_app_name` returns the root app for workspaces, so `bake_serve_payloads` gets a real app name. For non-workspace projects it returns `""`, and the bake falls back to `implicit_app`, which uses the `jac.toml` entry.

**Q: Why didn't the #9610 gate catch Case B?**
That gate only checks that some serve payloads exist. In Case B a manifest exists, but for `svc.jac`, so the pack passes and the failure only shows up at pod start.

**Q: Where does this PR actually fix the bug?**
It doesn't yet. It adds only the reproducing test rows and an import declaration. The fix in `pack_jab` is still to come.

**Q: Why put the override in the host-generated bake script instead of in `bake_serve_payloads`?**
According to the issue, the script is generated on the host. Setting the entry there works even with older pod binaries whose `bake_serve_payloads` doesn't know about the deployed file.

**Q: Why must the entry go into the seal cache key?**
Otherwise a later deploy of a different file could reuse a bundle sealed for the old entry and hit the same crash-loop.

**Q: Why does the test build the fleet with `solo_fleet` instead of passing nothing?**
A real single-app deploy passes `solo_fleet(name, file)` to `pack_jab`. Using the same fleet makes the test follow the real deploy path.

**Q: What is the `archwire.jac` change for?**
It declares that the test module now imports `solo_fleet`. The commit name implies the import graph must list every such import. Exactly what enforces this can't be seen from the PR.

**Q: Does Case A rely on anything outside the diff?**
Yes. It relies on `_mini_app()` not creating a `main.jac`. That helper isn't shown, so confirm it.

**Q: Did CI prove the new rows fail on `main`?**
Not visibly. The relevant test jobs appear skipped, and the only failure is "Contribution Checks", whose cause isn't shown.
