## 1. The short version

`jac scale deploy app.jac` packs your project into a sealed bundle (a `.jab` file) and ships it to Kubernetes pods. While it packs, a "bake" step builds a serving manifest for the app. When the pod starts, it boots the file you named on the command line, here `app.jac`, and reads that manifest.

**On `main`, the bake for a single-app (non-workspace) deploy built the manifest for the `jac.toml` `entry-point` (or `main.jac` when none is set), not for the file the pod boots.** This failed in two ways:
- With no `entry-point` and no `main.jac`, the pack failed on a valid project: `The app stage has no .../serve_manifest.json`.
- With `entry-point = "svc"`, the pack succeeded. Every pod then crash-looped with `Sealed application is missing serving metadata`.

**You now work out the module the pod boots (`app`) from the fleet's root member. The bake script sets the config's entry point to that module before baking, and the module is part of the seal cache key.** You also reject two cases early, on the host: file names that are not valid module names (`my-app.jac`), and files hidden by a package with the same name (`app.jac` next to `app/__init__.jac`). A single-app deploy also no longer checks that the `jac.toml` entry file ships, because the pod never boots it.

**Status:** Open. No human review yet. The two Greptile bot findings are answered and fixed. All CI checks on `1d1ac29` pass; a few were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **Pod side:** `jac scale deploy app.jac` → `deployed_tree` returns `app.jac` → `ManifestBuilder._derive_fleet` builds `solo_fleet(name, "app.jac")` → the pod gets `JAC_SV_FILE=app.jac`.
- **Bake side:** `pack_jab` → `_precompile_app(..., app="")`, because `sealed_app_name` returns `""` for a non-workspace project → the bake script calls `bake_serve_payloads(config, project, app="")` → `implicit_app` → entry is `entry-point` or `main`.
- Nothing connected the two. The fleet knew `app.jac`, but the bake never saw it.

### 3.2 What went wrong: no `entry-point`, no `main.jac`

```text
1. Project: jac.toml has [project] name="mini", no entry-point; files: app.jac
2. User runs: jac scale deploy app.jac       → fleet root member file = "app.jac"
3. pack_jab → _precompile_app(app="")        → bake script has no idea about app.jac
4. bake_serve_payloads → implicit_app        → entry = kind_entry → "main"
5. resolve entry → app/main.jac not found    ← WRONG: looked for the wrong file
   ⚠ app 'mini' entry-point '.../app/main.jac' not found; sealing without serve payloads
6. #9610's gate: no manifest in stage        → RuntimeError: The app stage has no .../serve_manifest.json
7. Deploy fails on the host, although the project is valid
```

### 3.3 What went wrong: `entry-point = "svc"`, deploying `app.jac`

```text
1. Project: jac.toml entry-point="svc"; files: app.jac, svc.jac
2. User runs: jac scale deploy app.jac       → fleet root member file = "app.jac"
3. bake → implicit_app → entry = "svc"       ← WRONG: manifest built for svc.jac
4. serve_manifest.json exists                → #9610's gate passes
5. .jab shipped, pod boots JAC_SV_FILE=app.jac
6. _prepare_sealed: app.jac not in manifest  → "Sealed application is missing serving metadata"
7. Every pod crash-loops
```

### 3.4 Why it mattered

- The issue notes that the docs use `jac scale deploy app.jac` throughout, so the first failure is easy to hit for anyone following them.
- The second failure is worse. It passes on the host and only breaks in the cluster, where every pod crash-loops.
- This was the open question from #9610: why the bake couldn't find the entry file.
- Workspace deploys were not affected, because `sealed_app_name` passes the root app to the bake.

## 4. The idea of the fix (one sentence)

> **Bake what the pod boots.** For a single-app deploy, take the file from the fleet's root member, turn it into a module name, check that the name really resolves to that file, and force the bake to use it as the entry point.

The pod's file comes from the fleet, so the fleet is the one source that is always right for both sides. The override is written into the host-generated bake script. Because of that, it also works with older pod binaries, without changing `bake_serve_payloads` itself (as the issue notes).

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: new `sealed_entry_module`

```diff
+impl sealed_entry_module(project_dir: str, fleet: (FleetSpec | None)) -> str {
+    served = fleet.root_member() if fleet is not None else None;
+    if served is None or not served.file {
+        return "";                                   # no fleet / no file → old path
+    }
+    config = _project_config(project_dir);
+    if config is not None and config.is_workspace {
+        return "";                                   # workspaces already correct
+    }
+    base = Path(project_dir).resolve();
+    rel = Path(_fleet_entry_rel(base, served.app, served.file));
+    parts = [*rel.parent.parts, rel.stem];          # "pkg/app.jac" → ["pkg", "app"]
+    if not all(part.isidentifier() for part in parts) {
+        raise ValueError(f"App '{served.app}' boots '{rel.as_posix()}', which is not an "
+            "importable module name, ... such as 'my_app.jac'.");
+    }
+    module = ".".join(parts);
+    resolved = Path(resolve_entry_path(module, str(base))).resolve();
+    if resolved != (base / rel).resolve() {
+        raise ValueError(f"... its module name '{module}' resolves to "
+            f"'{resolved.relative_to(base).as_posix()}', so the deploy would seal the wrong file. Rename one of the two.");
+    }
+    return module;
+}
```

**What:** Returns the dotted module name of the file the pod boots, e.g. `"app"`. It returns `""` when there is no fleet, the root member has no file, or the project is a workspace. It raises `ValueError` when the path isn't a valid module name, or when the module name resolves to a different file.

**Why:** The bake can only take a module name, not a path. You don't want the bake to quietly bake a different file than the pod boots, so you check the round trip from path to module and back to path.

**Things to notice:**
- The shadow check came from Greptile's P1 finding (commit `3d8687f`). It catches any case where `resolve_entry_path` lands elsewhere, not only `app/__init__.jac`.
- Greptile suggested keeping the selected file instead of re-resolving it. You chose to refuse the deploy instead. This works because the bake only accepts a module name.
- `_project_config` and `_fleet_entry_rel` are existing helpers. Their bodies are not in the diff.
- `resolved.relative_to(base)` would raise its own `ValueError` if `resolve_entry_path` ever returned a path outside `base`. The diff doesn't show whether that can happen.
- `isidentifier()` accepts Python keywords such as `class`. Whether such names break later is not tested here.

**Why:** `bake_serve_payloads(app="")` goes to `implicit_app`, which reads the entry point. Changing the config is enough to make it bake the right file.

**Things to notice:**

- `getattr(config, 'apps', {})` handles config objects without `apps`, likely older pod binaries.
- `repr(entry_module)` quotes the value safely inside the generated Python.
- The `+ ... if ... else ""` chain parses as "whole concatenation, or empty". The outer parentheses make that clear.

```text

└─ pack_jab(project_dir, seal_binary, fleet=fleet)

   │  └─ return "app"
   ├─ entry_module set → skip assert_entry_module_ships                ← CHANGED

         ├─ config = get_config_for_path(project)
```

## 11. Questions your senior might ask

**Q: Why override the config in the bake script instead of passing the entry to `bake_serve_payloads`?**
The script is generated on the host, so the fix works with older pod binaries without changing the bake's signature. The `getattr(config, 'apps', {})` guard is there for that reason.

**Q: Why set both `config.project.entry_point` and every `config.apps[*].entry_point`?**
Commit `aefe6b5` found that the config had already built its app objects from the old entry. Changing only the project field didn't reach the app that `implicit_app` uses.

**Q: Does this change workspace deploys?**
No. `sealed_entry_module` returns `""` for workspaces, so `assert_entry_module_ships` runs, the digest gets `""`, and the bake script is unchanged.

**Q: Is it safe to skip `assert_entry_module_ships` for single-app deploys?**
The pod never boots the `jac.toml` entry in that case. `check_fleet_entries` still checks that the deployed file ships. The jacignore test covers the skip.

**Q: Why refuse `app.jac` + `app/__init__.jac` instead of baking `app.jac` directly, as Greptile suggested?**
The bake only takes a module name, and `app` resolves to the package. Failing on the host with a clear message is safer than guessing.

**Q: Will adding `entry_module` to the digest invalidate existing seal caches?**
