## 1. The short version

`jac scale deploy app.jac` deploys a Jac app to Kubernetes. Before shipping it, jac-scale packs the project into a `.jab` bundle and **seals** it. Sealing runs a pod binary that pre-compiles the app and writes a **serve manifest**: the metadata a pod needs to serve the app's walkers and functions. The pod then boots the file named on the command, here `app.jac`.

**The bug: for a single-app (non-workspace) project, the seal baked the entry named in `jac.toml` (or `main.jac` if none was set), not the file the pod boots.** Nothing tied the two together, so when they differed one of two things happened:

- With no `entry-point` in `jac.toml`, the pack failed on your machine with `The app stage has no .../serve_manifest.json`, even though the project was valid.
- With `entry-point = "svc"`, the pack succeeded, but every pod crash-looped with `Sealed application is missing serving metadata`.

**The fix: `pack_jab` now works out the module the pod will boot (for example `app`) and passes it into the bake script. That script overrides the config's entry point before baking.** You also:

- added that module to the seal cache key,
- reject file names that can't be sealed (`my-app.jac`, or `app.jac` hidden by `app/__init__.jac`) on the host with a clear message,
- skip the "`jac.toml` entry must ship" check for single-app deploys.

**Status:** Open and not approved. All CI checks on head `1511ccf` pass, and both Greptile findings are fixed. One open question from @MusabMahmoodh (2026-11-02) about where the override should live has no reply yet.

## 3. The problem, step by step

### 3.1 The setup

Two pieces of code each decided "which file is the app", and they used different sources:

| Who | Where it gets the entry | Example |
|---|---|---|
| The pod | The deploy command → `solo_fleet(name, "app.jac")` → `JAC_SV_FILE=app.jac` | boots `app.jac` |
| The bake | `bake_serve_payloads(config, project, app="")` → implicit app → `jac.toml` `entry-point`, else `main` | bakes `svc.jac` or `main.jac` |

A workspace deploy was fine, because `sealed_app_name` passes the real root app to the bake.

### 3.2 What went wrong

#### Case A: no `entry-point`, no `main.jac`

```text
myapp/  jac.toml (no entry-point)   app.jac
1. You run: jac scale deploy app.jac
2. Deploy builds fleet = solo_fleet("myapp", "app.jac")        → pod will get JAC_SV_FILE=app.jac
3. pack_jab → sealed_app_name(...) returns ""                  → not a workspace
4. Bake script: config = get_config_for_path(project)          → implicit app entry = "main" (default)
5. bake_serve_payloads(config, project, app="")                → looks for main.jac   ← WRONG FILE
6. main.jac not found → "⚠ ... entry-point '.../main.jac' not found; sealing without serve payloads"
7. No serve_manifest.json written
8. Since #9610, the pack checks for it → RuntimeError: The app stage has no .../serve_manifest.json
9. Deploy stops, although the project is valid
```

#### Case B: `entry-point = "svc"` in `jac.toml`, deploy `app.jac`

```text
1. You run: jac scale deploy app.jac
2. fleet = solo_fleet("myapp", "app.jac")                      → JAC_SV_FILE=app.jac
3. Bake: implicit app entry = "svc"
4. bake_serve_payloads bakes svc.jac                           → manifest describes svc.jac   ← WRONG FILE
5. Pack check: serve_manifest.json exists → passes             (#9610's gate can't tell it's for the wrong file)
6. .jab shipped
7. Pod boots app.jac from the seal → _prepare_sealed: "Sealed application is missing serving metadata"
8. Pod exits → restarted → same error → crash-loop on every pod
```

#### Cases found during review

These were not in the issue. They came up while fixing it (see the "Review findings" table in the PR description):

```text
my-app.jac deployed
1. Module name would be "my-app" → not a valid identifier, so it cannot be imported by name
2. Before this PR: per the PR description, it "broke inside the pod"     ← late failure
   (the exact error is not shown in the diff)

app.jac deployed next to app/__init__.jac
1. Module name "app" → resolve_entry_path picks app/__init__.jac          ← would seal the package, not app.jac
2. Pod boots app.jac → its serving data is missing                       (Greptile P1)

jac.toml entry parked by .jacignore, single-app deploy of a different file
1. assert_entry_module_ships fails the pack                              ← blocks a deploy that never boots that entry
```

### 3.3 Why it mattered

- The docs use `jac scale deploy app.jac` throughout (issue #10398). Case A is the normal path for a newcomer who names their file `app.jac`.
- Case A blocked valid deploys outright.
- Case B is worse: the deploy looks successful, and every pod then crash-loops in the cluster, far from the cause.
- This was the open question left on #9610 ("why does the bake fail to find the entry file?"). #9610 added the manifest gate that turned silent failures into Case A's loud one.

## 4. The idea of the fix (one sentence)

> **Bake the file the pod boots.** For a single-app deploy, `pack_jab` takes the booted file from the fleet's root member, turns it into a module name, and tells the bake script to use that as the entry point.

This removes the second, disagreeing source of truth instead of trying to keep the two in sync. The issue also points out that putting the override in the host-generated script makes it work with older pod binaries. @MusabMahmoodh questions that choice (see section 9).

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: new `sealed_entry_module`

```diff
+impl sealed_entry_module(project_dir: str, fleet: (FleetSpec | None)) -> str {
+    served = fleet.root_member() if fleet is not None else None;
+    if served is None or not served.file {
+        return "";                                   # no fleet / no file → old behaviour
+    }
+    config = _project_config(project_dir);
+    if config is not None and config.is_workspace {
+        return "";                                   # workspaces already pass the right app
+    }
+    base = Path(project_dir).resolve();
+    rel = Path(_fleet_entry_rel(base, served.app, served.file));
+    parts = [*rel.parent.parts, rel.stem];          # sub/app.jac → ["sub", "app"]
+    if not all(part.isidentifier() for part in parts) {
+        raise ValueError(... "not an importable module name" ... "'my_app.jac'.");
+    }
+    module = ".".join(parts);
+    resolved = Path(resolve_entry_path(module, str(base))).resolve();
+    if resolved != (base / rel).resolve() {
+        raise ValueError(... f"module name '{module}' resolves to '...'" ... "Rename one of the two.");
+    }
+    return module;
+}
```

**What:** Returns the dotted module name of the file the pod boots, such as `"app"` or `"sub.app"`. It returns `""` when there is no fleet, no file, or the project is a workspace. It raises `ValueError` on the host in two cases:

- any path part is not a valid identifier (`my-app.jac`);
- the module name resolves back to a different file (the `app/__init__.jac` shadowing case).

**Why:** This is the single place that answers "what does the pod boot?" in a form the bake understands. A module name is used rather than a path because `entry-point` in `jac.toml` is a module name.

**Things to notice:**
- The shadowing check is a round-trip: path → module → path, then compare. Greptile suggested *preserving the selected file* when baking. You chose to *refuse* instead (commit `3d8687f`). That is simpler, because the bake only understands module names, but users with that layout must rename a file.
- `_fleet_entry_rel` is not in the diff. From its use, it maps the member's file to a path relative to the project root.
- `resolved.relative_to(base)` would itself raise a different `ValueError` if `resolve_entry_path` ever returned a path outside the project. The diff doesn't show whether that can happen.
- `pack_jab` calls this *before* `check_fleet_entries`. The diff doesn't show how `resolve_entry_path` behaves if the deployed file doesn't exist.

### 5.2 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: the bake script override in `_precompile_app`

```diff
-    seed: (Path | None) = None
+    seed: (Path | None) = None,
+    entry_module: str = ""                                     # NEW parameter
 ...
             + "config = get_config_for_path(project)\n"
+            + (
+                f"config.project.entry_point = {repr(entry_module)}\n"

```

**What:** When `entry_module` is set (say `"app"`), the generated script gains three lines before baking:

```text
config.project.entry_point = 'app'
for served in getattr(config, 'apps', {}).values():
    served.entry_point = 'app'
```

`bake_serve_payloads(..., app="")` then bakes `app.jac`. When `entry_module` is `""`, the script is unchanged.

**Why:** This is the core fix for Cases A and B. The bake now uses the deployed file instead of `jac.toml`.

**Things to notice:**
- The `apps` loop came in commit `aefe6b5` ("the bake override reaches the app the config already built"). The commit title suggests the config has already built its implicit app from `jac.toml` by the time the script runs, so setting `config.project.entry_point` alone would not change what gets baked. The diff doesn't show the config code that confirms this.
- `getattr(config, 'apps', {})` guards against config objects without `apps`. This presumably keeps the script safe on older pod binaries, since the script runs inside the pod binary's own `jaclang`.
- `repr(entry_module)` safely quotes the value inside generated code. After 5.1 it can only contain identifiers and dots.
- The override only affects this script. @MusabMahmoodh points out that the next step, `jac precompile --seal`, re-reads the staged `jac.toml`, so the `.jab`'s recorded `entry` still reflects `jac.toml`. This is open; see section 9.

### 5.3 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: cache key in `seal_input_digest`

```diff
     app_name: str,
+    entry_module: str,                     # NEW positional parameter
     sanitized: (str | None),
 ...
         app_name,
+        entry_module,                      # NEW part of the hash
         "fat" if fat else "thin",
```

**What:** The seal cache key now includes the deployed module.

**Why:** Without it, deploying `app.jac` after a cached seal for `svc.jac` (same sources, same toml) could reuse the wrong bundle. That would bring Case B back through the cache.

**Things to notice:**
- The new parameter is positional and sits in the middle, so every caller must be updated. Only the `pack_jab` call appears in the diff, and CI is green. This suggests there are no other callers, but the diff alone can't confirm it.
- Adding a part to the hash probably changes every existing digest, which would mean a one-time cache miss after upgrade. This depends on how the parts are hashed, which isn't shown.


**What:** `pack_jab` computes the entry module once and uses it in three places:

**Why:**

- Points 2 and 3 fix Cases A and B.

**Things to notice:** When `entry_module` is set, nothing checks that the `jac.toml` entry ships. That is fine for pods, which never boot it. But it ties into @MusabMahmoodh's point: the `.jab` metadata may still name that entry.

## 6. How execution flows after the PR

### 6.1 Single-app deploy: `jac scale deploy app.jac`

```text
jac scale deploy app.jac
├─ deploy builds fleet = solo_fleet("myapp", "app.jac")     (per issue #10398, unchanged)
└─ pack_jab(project_dir, seal_binary, fleet=fleet)
   ├─ excluded = source_filter_for(base)
   ├─ entry_module = sealed_entry_module(project_dir, fleet)            ← NEW
   │  ├─ root member file = "app.jac", project not a workspace
   │  ├─ parts ["app"] all identifiers?           no → ValueError on host  ← NEW
   │  ├─ resolve_entry_path("app") == app.jac?    no → ValueError on host  ← NEW
   │  └─ return "app"
   ├─ entry_module set → skip assert_entry_module_ships                  ← CHANGED
   ├─ check_fleet_entries(...)
   ├─ digest = seal_input_digest(..., app_name, "app", sanitized, ...)  ← CHANGED (cache key)
   │  └─ cache hit → reuse bundle (only one sealed for "app")
   └─ _precompile_app(..., entry_module="app")                           ← CHANGED
      ├─ _stage_app writes staged project + sanitized jac.toml (unchanged)
      ├─ bake script (run by pod binary):
      │  ├─ config = get_config_for_path(project)
      │  ├─ config.project.entry_point = 'app'                           ← NEW
      │  ├─ every config.apps[*].entry_point = 'app'                     ← NEW
      │  └─ bake_serve_payloads(config, project, app="") → bakes app.jac
      ├─ serve_manifest.json for app.jac exists → pack continues
      └─ jac precompile --seal  (re-reads staged jac.toml; .jab "entry" still from jac.toml — open comment)
Pod boots JAC_SV_FILE=app.jac → serving metadata found → serves /walker/echo
```

### 6.2 Workspace deploy (unchanged)

```text
pack_jab(..., fleet=<workspace fleet>)
├─ sealed_entry_module → config.is_workspace → ""
├─ assert_entry_module_ships runs (as before)
├─ digest includes "" for entry_module
└─ bake script has no override; bake_serve_payloads(app=<root app>) as before
```

### 6.3 Pack with no fleet (unchanged)

```text
pack_jab(..., fleet=None)
├─ sealed_entry_module → ""
└─ same as before the PR: jac.toml entry is checked and baked
```

| Scenario | Before | After |
|---|---|---|
| `deploy app.jac`, no `entry-point`, no `main.jac` | Host fails: `The app stage has no .../serve_manifest.json` | Seals `app.jac`, pod serves |
| `deploy app.jac`, `entry-point = "svc"` | Pack OK, pods crash-loop: `Sealed application is missing serving metadata` | Seals `app.jac`, pod serves |
| `deploy my-app.jac` | Failed inside the pod (per PR description) | Host `ValueError: ... not an importable module name ...` |

| Workspace deploy | Correct | Unchanged |
| Cached seal from deploying `svc.jac`, now deploying `app.jac` | Could reuse wrong seal | Different cache key, re-seals |

**Behaviour changes users will notice:**
- Two new host-side errors, for hyphenated file names and package-shadowed files.
- Deploys that used to fail or crash-loop now work.
- Likely a one-time re-seal because the cache key changed.

## 11. Questions your senior might ask

**Q: Why not fix `sealed_app_name` to return the deployed app, like workspaces do?**
A: For a single-app project there is no named app in `jac.toml` to pass. `bundle_app` falls back to the implicit app, whose entry comes from `jac.toml`. So the fix overrides the entry point itself rather than the app name.

**Q: Why put the override in the bake script instead of the staged `jac.toml`?**
A: The issue's reasoning was that a host-generated script works even with older pod binaries. @MusabMahmoodh argues the staged toml is better because `jac precompile --seal` would then agree, and the digest key and `apps` loop could go. That question is still open; you need to answer it.

**Q: Why the loop over `config.apps`? Isn't `config.project.entry_point` enough?**
A: Commit `aefe6b5` says the override must "reach the app the config already built". By the time the script runs, the config has already built its implicit app from `jac.toml`, so changing only the project field wouldn't change what gets baked. The config code that does this isn't in the diff.

**Q: Why reject `app.jac` next to `app/__init__.jac` instead of sealing the right file, as Greptile suggested?**
A: The bake takes a module name, and `app` resolves to the package. Refusing early with a message naming both files is simpler and fails on the host rather than in the pod. The cost is that users must rename one of them.

**Q: Does this change anything for workspace deploys?**
A: No. `sealed_entry_module` returns `""` for workspaces, so the old checks and the old bake script run unchanged. Only the cache digest gains an empty part. The workspace row in the real-binary test still passes.

**Q: Why skip `assert_entry_module_ships` for single-app deploys? Isn't that check protecting something?**
A: It protects the `jac.toml` entry, which a single-app pod never boots. Requiring it to ship blocked valid deploys. The side effect: combined with the open `.jab` `entry` issue, the bundle's metadata could name a file that isn't in it.

**Q: Will the cache key change cause re-seals?**
A: Probably once after upgrade, because a new part is hashed into every digest. After that, the key correctly separates seals for different deployed files.

**Q: What happens with `jac run` on a `.jab` produced by this fix?**
A: Per @MusabMahmoodh, it would use the `entry` stamped from `jac.toml`: `svc.jac`, or no entry plus `attachable`. It would not use `app.jac`. Pods aren't affected because they use `JAC_SV_FILE`.

**Q: How do you know the new tests actually catch the bug?**
A: The PR links a CI job where the new rows fail before the fix with the exact Case A error (`main.jac not found; sealing without serve payloads` → `RuntimeError`), and a later job where the same tests pass (372 passed in `test-scale (microservices)`).

**Q: Why does the `.jacignore` test pass a fake binary?**
A: It only needs to show the pack doesn't fail with "entry module". It catches any exception and asserts that phrase is absent, so the later failure from the fake binary doesn't matter. It is a weak but targeted check.
