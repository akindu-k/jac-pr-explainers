## 1. The short version

`jac scale deploy app.jac` packs your project into a sealed bundle (a `.jab` file) and ships it to Kubernetes pods. Each pod boots the file you named on the command, `app.jac`. Before the bundle ships, a "bake" step pre-builds the serving metadata for one entry file. A second step, `jac precompile --seal`, records which entry the bundle has.

**For a single-app (non-workspace) deploy, both steps chose their entry from `jac.toml` (`entry-point`, or `main` if it is unset) and ignored the file the pod would actually boot.** This failed in two ways:

- With no `entry-point` set and no `main.jac`, the pack failed on your machine with `The app stage has no .../serve_manifest.json`, even though the project was valid.
- With `entry-point = "svc"`, the pack succeeded, but every pod crash-looped with `Sealed application is missing serving metadata`.

**The PR works out the module the pod boots (`app.jac` → `app`) and writes it as `entry-point` into the staged copy of `jac.toml`, so the bake, the seal and the shipped `jac.toml` all read the same entry.** It also rejects two cases early, on your machine: a file name that is not a valid module name (`my-app.jac`), and a file hidden by a package with the same name (`app.jac` next to `app/__init__.jac`). It also skips a `jac.toml` entry check that does not apply to single-app deploys.

**Status:** Open. Approved by @MusabMahmoodh on 2026-11-03. All CI checks on head `3b2a0f6` passed; a few were skipped.

## 3. The problem, step by step

### 3.1 The setup

The deploy chose the pod's file and the bake's file in two separate places:

- **The pod's file:** `jac scale deploy app.jac` makes `deployed_tree` return `app.jac`. `ManifestBuilder._derive_fleet` then builds `solo_fleet(name, "app.jac")`. The pod gets `JAC_SV_FILE=app.jac`.
- **The bake's file:** `pack_jab` → `bake_serve_payloads(config, project, app="")`. Because `sealed_app_name` returns `""` for single-app projects, `bundle_app` falls back to `implicit_app`, whose entry comes from `jac.toml`.
- **The seal's file:** `jac precompile --seal` also reads the staged `jac.toml` and stamps `entry` from it. This was raised by @MusabMahmoodh.

Nothing tied these together. Workspace deploys were fine, because `sealed_app_name` passes the root app to the bake.

### 3.2 What went wrong

Case A: no `entry-point`, no `main.jac`

```text
1. Project: jac.toml has no entry-point; app.jac exists; main.jac does not.
2. User runs: jac scale deploy app.jac
3. Fleet = solo_fleet("myapp", "app.jac")       → pod will boot app.jac
4. pack_jab stages the project; staged jac.toml has no entry-point
5. Bake: app="" → implicit_app → entry = main     ✗ WRONG: should be app
6. resolve_entry_file finds no main.jac → bake writes no serve_manifest.json
   "⚠ app 'mini' entry-point '.../app/main.jac' not found; sealing without serve payloads"
7. #9610's gate: RuntimeError: The app stage has no .../.jac/serve_manifest.json
8. Deploy stops on the host, although the project is valid.
```

Case B: `entry-point = "svc"`

```text
1. Project: jac.toml has entry-point = "svc"; app.jac and svc.jac exist.
2. User runs: jac scale deploy app.jac
3. Fleet = solo_fleet("myapp", "app.jac")       → pod will boot app.jac
4. Bake: app="" → implicit_app → entry = svc      ✗ WRONG
5. serve_manifest.json is written for svc.jac    → #9610 gate passes (a manifest exists)
6. jac precompile --seal stamps MANIFEST.json entry = svc.jac   ✗ WRONG
7. .jab ships. Pod boots JAC_SV_FILE=app.jac
8. _prepare_sealed: "Sealed application is missing serving metadata"
9. Every pod crash-loops.
```

Case C: problems the first fix exposed (found in review, not on `main`)

```text
1. my-app.jac deployed → module name "my-app" is not importable
   → per the PR description, this broke inside the pod
2. app.jac next to app/__init__.jac → module "app" → resolve_entry_path picks app/__init__.jac
   → the bake would seal the package, not the file the pod boots (Greptile P1)
3. jac.toml entry parked in .jacignore, deploying another file
   → assert_entry_module_ships fails the pack for a file the pod never boots
```

### 3.3 Why it mattered

- The docs use `jac scale deploy app.jac` throughout (issue #10398), so Case A is easy to hit with a fresh project.
- Case B is worse: the deploy looks successful, and the failure only shows up as crash-looping pods in the cluster.
- @MusabMahmoodh also pointed out that `jac run` on such a `.jab` would use the wrong recorded entry, even though pods ignore it.
- This answers the open question left on #9610: "why does the bake fail to find the entry file?"

## 4. The idea of the fix (one sentence)

> **Make the staged `jac.toml` name the file the pod boots.** For a single-app deploy, `pack_jab` writes the deployed module as `entry-point` into the sanitized `jac.toml` before staging, so every step that reads it agrees.

Every downstream step (the bake, `jac precompile --seal`, the shipped `jac.toml`) already reads that one file. Fixing it there corrects all of them at once without patching each step. Because the sanitized TOML is already part of the cache key, the cache is also correct for free.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: work out the deployed module and stage it

```diff
+impl sealed_entry_module(project_dir: str, fleet: (FleetSpec | None)) -> str {
+    served = fleet.root_member() if fleet is not None else None;
+    if served is None or not served.file {
+        return "";                                   # no fleet / no file: old behaviour
+    }
+    config = _project_config(project_dir);
+    if config is not None and config.is_workspace {
+        return "";                                   # workspaces already pass the root app
+    }
+    base = Path(project_dir).resolve();
+    rel = Path(_fleet_entry_rel(base, served.app, served.file));
+    parts = [*rel.parent.parts, rel.stem];           # src/app.jac -> ["src", "app"]
+    if not all(part.isidentifier() for part in parts) {
+        raise ValueError(... "not an importable module name" ...);   # my-app.jac
+    }
+    module = ".".join(parts);
+    resolved = Path(resolve_entry_path(module, str(base))).resolve();
+    if resolved != (base / rel).resolve() {
+        raise ValueError(... f"'{module}' resolves to '{...}'" ... "Rename one of the two.");
+    }
+    return module;
+}
+
+impl staged_jac_toml(sanitized: (str | None), entry_module: str) -> (str | None) {
+    if not entry_module {
+        return sanitized;                            # unchanged when nothing to override
+    }
+    text = sanitized if sanitized is not None else PLACEHOLDER_JAC_TOML;
+    old_doc = tomllib.loads(text);
+    project = {** old_doc.get("project", {}), "entry-point": entry_module};
+    new_doc = {** old_doc, "project": project};
+    return toml_minimal_update(text, old_doc, new_doc, ["project"])
+        or serialize_toml(new_doc);
+}
```

```diff
@@ impl pack_jab(
     excluded = source_filter_for(base);
-    assert_entry_module_ships(base, excluded);
+    entry_module = sealed_entry_module(project_dir, fleet);
+    if not entry_module {
+        assert_entry_module_ships(base, excluded);   # only when jac.toml's entry is what boots
+    }
 ...
-    sanitized = sanitized_jac_toml(base);
+    sanitized = staged_jac_toml(sanitized_jac_toml(base), entry_module);
     app_name = sealed_app_name(project_dir, fleet);
```

**What:**
- `sealed_entry_module` returns the dotted module the pod boots, but only for a single-app deploy with a fleet. It returns `""` for workspaces and when no fleet is passed.
- It raises `ValueError` on the host for two cases: a non-identifier path part, or a module name that resolves to a different file.
- `staged_jac_toml` sets `[project] entry-point` in the sanitized TOML text. It changes only that key when it can, and falls back to re-serializing the whole document.
- `pack_jab` now feeds this staged text forward and skips `assert_entry_module_ships` when an override is in effect.

**Why:**
- Writing the module into the staged `jac.toml` fixes Cases A and B.
- The two `ValueError`s fix Case C items 1 and 2.
- Skipping the ship check fixes Case C item 3.

**Things to notice:**
- The project's real `jac.toml` is never touched. Only the sanitized copy changes.
- The order is deliberate. `sealed_entry_module` runs before the bundle is staged, so a bad name fails before any sealing work.
- The value written is a module name (`app`, `src.app`), not a file name. This matches how `entry-point` is written elsewhere, e.g. `entry-point="app"`.
- The shadowing check compares resolved absolute paths. It does not re-check by name, as Greptile asked ("preserve the selected file").
- When `sanitized` is `None`, `PLACEHOLDER_JAC_TOML` is used, so a project without a usable `jac.toml` still gets an entry. Its contents are not in the diff.
- `isidentifier()` accepts Python keywords such as `class`, which are not importable. This edge case is not handled.
- `resolved.relative_to(base)` raises its own `ValueError` if `resolve_entry_path` returns a path outside `base`. The diff does not show whether that can happen.
- The cache key: `input_key`'s body is not shown in the diff. The claim that `sanitized` feeds the key comes from @MusabMahmoodh's comment and your reply. Since `sanitized` now holds the staged text, a deploy of a different file gets a different key.
- Earlier commits (`5d4c104`, `aefe6b5`) patched the bake's `-c` script and added an `entry_module` cache-key part and an `apps` loop. Commit `647458a` removed all three, and the final diff shows none of them.

## 6. How execution flows after the PR

### 6.1 Single-app deploy: `jac scale deploy app.jac`

Steps after staging (the stage, bake and seal order) come from the issue and comments; they are not in the diff.

```text
jac scale deploy app.jac
├─ deployed_tree → "app.jac"
├─ ManifestBuilder._derive_fleet → solo_fleet("myapp", "app.jac")
└─ pack_jab(project_dir, pod_binary, fleet=solo_fleet)
   ├─ source_filter_for(base)
   ├─ sealed_entry_module(project_dir, fleet)                         ← NEW
   │  ├─ root member file = app.jac; not a workspace
   │  ├─ parts ["app"] all identifiers?      no → ValueError (host)  ← NEW
   │  ├─ resolve_entry_path("app") == app.jac? no → ValueError (host) ← NEW
   │  └─ returns "app"
   ├─ assert_entry_module_ships → SKIPPED (entry_module is set)        ← CHANGED
   ├─ bundle_source_files / check_fleet_entries
   ├─ staged_jac_toml(sanitized_jac_toml(base), "app")                ← NEW
   │  └─ [project] entry-point = "app" in the staged text
   ├─ sealed_app_name → ""; nested_sanitized_tomls; input_key (cache)
   ├─ stage project with the staged jac.toml
   ├─ bake: app="" → implicit_app → entry-point "app" → serve_manifest for app.jac  ← CHANGED
   ├─ jac precompile --seal → MANIFEST.json entry = app.jac (not attachable)       ← CHANGED
   └─ require_serve_manifest → .jab
Pod: JAC_SV_FILE=app.jac → _prepare_sealed finds metadata → serves
```

### 6.2 Workspace deploy, or `pack_jab` with no fleet

```text
pack_jab(project_dir, pod_binary, fleet=workspace fleet | None)
├─ sealed_entry_module → ""                    ← NEW (but no effect)
├─ assert_entry_module_ships(base, excluded)   (runs as before)
├─ staged_jac_toml(sanitized, "") → sanitized unchanged
└─ rest as before (workspace: sealed_app_name passes the root app to the bake)
```

| Scenario | Before | After |
|---|---|---|
| `app.jac` deployed, no `entry-point`, no `main.jac` | Host error: `The app stage has no .../serve_manifest.json` | Packs; pod serves `app.jac` |
| `app.jac` deployed, `entry-point = "svc"` | Packs; pods crash-loop with `missing serving metadata`; `.jab` entry `svc.jac` | Manifest and `.jab` entry both for `app.jac`; pod serves |
| `my-app.jac` deployed | Broke inside the pod (per description) | Host `ValueError: ... not an importable module name` |
| `app.jac` next to `app/__init__.jac` | On `main`: bake used the `jac.toml` entry. On an early version of this PR: would seal `app/__init__.jac` | Host `ValueError` naming both files |
| `jac.toml` entry parked by `.jacignore`, deploying another file | Pack fails: "entry module ... .jacignore" | Check skipped; that error no longer raised |
| Workspace deploy | Works | Unchanged |
| `pack_jab` without a fleet | Works | Unchanged |

**Behaviour changes users will notice:**

1. For single-app deploys, the file on the command now wins over `jac.toml`'s `entry-point`.
2. The `jac.toml` shipped inside the bundle names the deployed module.
3. `jac run` on the `.jab` runs the deployed file.
4. Two layouts that used to fail later now fail early with a new error.

**Test: "a seal that cannot yield a bootable .jab fails the pack instead of the pod"**

Each row is a tuple of `(label, entry_line, binary, expected, deployed, others)`. When `deployed` is set, the test writes that file (plus any `others`) and packs with `solo_fleet("mini", deployed)`.

| Row | Setup | Expects | Proves |
|---|---|---|---|
| an unrunnable pod binary | existing | existing | unchanged (two empty columns added) |
| a bake that writes no manifest over a stale local copy | existing | `RuntimeError`, `sealing without serve payloads` | unchanged |
| a deployed file that is not a module name | `my-app.jac`, binary `b"not-an-elf"` | `ValueError`, `my-app.jac`, `not an importable module name` | Bad names fail before sealing. A broken binary would raise a different error, so the row also proves the check runs first. |

A `deployed` column was added. The fleet is now chosen with `if served … elif deployed …`, so a row cannot pick the wrong fleet. The shared `app_jac` dict (an `app.jac` that imports `svc` and defines `walker echo`) is reused across rows.

| Row | `jac.toml` | Fleet | Proves |
|---|---|---|---|

The diff does not show the boot-and-request part of this test, or what `_mini_app()` creates (presumably `svc.jac`, since every row asserts `"svc.jac" in names`).

### 7.2 `test_bundle_jacignore.jac`

**Test: "parking the entry module fails the pack, not the fleet"** gained one extra step. With the `jac.toml` entry still parked by `.jacignore`, it calls `pack_jab(str(base), b"binary", fleet=solo_fleet("mini", "svc.jac"))` and asserts `"entry module" not in caught`.

This proves the ship check is skipped for single-app deploys. It does not require the pack to succeed: with a fake binary, a later error is expected and allowed. It extends the existing test because the setup (a project with a parked entry) is the same.

## 11. Questions your senior might ask

**Q: Why write the entry into `jac.toml` instead of passing it to the bake directly?**
Two steps read the entry: the bake and `jac precompile --seal`. Patching only the bake script left the `.jab` entry wrong, as @MusabMahmoodh found. The staged `jac.toml` is the one input both steps already share.

**Q: Does this modify the user's `jac.toml`?**
No. Only the sanitized copy that goes into the stage and the bundle is changed.

**Q: How do you avoid reusing a bundle sealed for a different file?**
The sanitized TOML text is already part of the cache key (per the review thread; `input_key`'s body isn't in the diff). It now contains the deployed `entry-point`, so different files produce different keys.

**Q: Why skip workspaces?**
For workspaces, `sealed_app_name` already passes the root app to the bake, so they never had this gap. A `jac.toml` with `[apps]` is always a workspace, so `sealed_entry_module` returns `""` for it.

**Q: What happens if `jac.toml` has no `[project]` table, or no sanitized TOML at all?**
`staged_jac_toml` merges into `old_doc.get("project", {})`. If `sanitized` is `None`, it starts from `PLACEHOLDER_JAC_TOML`. If `toml_minimal_update` returns nothing, it falls back to `serialize_toml`.

**Q: Why reject `my-app.jac` instead of supporting it?**
`entry-point` takes a dotted module name, and `my-app` cannot be one. Before this PR the failure happened inside the pod. Now it happens on the host, with a message suggesting `my_app.jac`.

**Q: Why is skipping `assert_entry_module_ships` safe?**
For a single-app deploy, the pod boots the deployed file, not `jac.toml`'s entry. Whether the deployed file ships is checked by `check_fleet_entries`, which still runs.

**Q: Could the shadowing check misfire for files in subfolders?**
It builds `src.app` from `src/app.jac` and compares absolute resolved paths, so nested files work. One gap: Python keywords used as names pass `isidentifier()` but are not importable. That is not handled.

**Q: How do the tests prove the `.jab` is correct, not just that a manifest exists?**
Every row of the real-pod-binary test checks `_precompiled/MANIFEST.json`. The `entry.path` must equal the served file, and `attachable` must be absent. The test also boots the extracted bundle and calls the route, though that part isn't shown in the diff.

**Q: Does this change anything for older pod binaries?**
The diff can't confirm it directly. The fix lives in host-side staging that the bake and seal read, so it should not depend on pod-binary changes; the issue's earlier suggestion relied on the same property.
