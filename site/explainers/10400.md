## 1. The short version

`jac scale deploy app.jac` packs your project into a sealed bundle (a `.jab` file) that Kubernetes pods boot from. While it packs, the deploy runs a "bake" step. The bake pre-builds a **serving manifest**, the metadata a pod needs to serve an app. The pod then boots the file you named on the command (`app.jac`).

**Before this PR, a single-app deploy baked the manifest for the entry named in `jac.toml` (or `main.jac` if none was set), not for the file the pod boots.** When the two differed, one of two things happened:

- With no `entry-point`, the pack failed on a valid project with `The app stage has no .../serve_manifest.json`.
- With `entry-point = "svc"`, the pack succeeded, but every pod crash-looped with `Sealed application is missing serving metadata`.

**You now work out the module the pod will boot (`sealed_entry_module`) and pass it into the bake script. The script overrides the config's entry point before baking, and the same module is added to the bundle cache key.** You also reject two files that can't be sealed correctly, on the host and before any sealing:

- a file whose name isn't a valid module name (`my-app.jac`)
- a file hidden by a package with the same name (`app.jac` next to `app/__init__.jac`)

Single-app deploys also no longer require the `jac.toml` entry to ship, because the pod never boots it.

**Status:** Open. There is no human review yet. Greptile's two P1 findings were answered with fix commits. All CI checks on head `243f4b8` pass, and some are skipped.

## 3. The problem, step by step

### 3.1 The setup

There are two places that decide "which file is the app", and nothing tied them together:

- **The pod side.** `deployed_tree` returns `app.jac`. `ManifestBuilder._derive_fleet` builds `solo_fleet(name, "app.jac")`. The pod gets `JAC_SV_FILE=app.jac`.
- **The bake side.** `_precompile_app` ran `bake_serve_payloads(config, project, app="")`. With `app=""`, the bake used `implicit_app`, whose entry is `[project] entry-point`, or `main` when none is set.

Workspaces were fine, because `sealed_app_name` passes the real root app to the bake.

### 3.2 What went wrong: no `entry-point` in `jac.toml`

```text
1. Project: jac.toml (no entry-point), app.jac, no main.jac
2. User runs: jac scale deploy app.jac
3. Fleet = solo_fleet("mini", "app.jac")          → pod will boot app.jac
4. pack_jab → _precompile_app(app="")
5. Bake script: config.project.entry_point = unset → implicit entry = main
6. resolve_entry_file looks for main.jac → not found   ← WRONG FILE
7. Bake writes no serve_manifest.json
8. Gate from #9610: "sealing without serve payloads"
   RuntimeError: The app stage has no .../serve_manifest.json
9. Deploy fails on a valid project
```

### 3.3 What went wrong: `entry-point = "svc"` set

```text
1. Project: jac.toml entry-point="svc", app.jac, svc.jac
2. User runs: jac scale deploy app.jac
3. Fleet = solo_fleet("mini", "app.jac")          → pod will boot app.jac
4. Bake script: entry = svc → manifest built for svc.jac   ← WRONG FILE
5. Manifest exists → #9610 gate passes → .jab ships
6. Pod boots app.jac (JAC_SV_FILE=app.jac)
7. _prepare_sealed: no metadata for app.jac
   "Sealed application is missing serving metadata"
8. Every pod crash-loops
```

### 3.4 Why it mattered

- The issue notes that the docs use `jac scale deploy app.jac` throughout, so case 3.2 is easy to hit.
- Case 3.3 is worse. It passes on the host and fails only in the cluster.
- This also answers the open question from #9610 ("why does the bake not find the entry file?"). The PR's CI proof shows the new tests failing before the fix with `entry-point '.../app/main.jac' not found; sealing without serve payloads`.

## 4. The idea of the fix (one sentence)

> **Bake the file the pod boots.** For a single-app deploy, take the module from the fleet's root member, check that it can be sealed, and force the bake's entry point to it.

This ties both sides to one source of truth: the fleet, which is also what sets `JAC_SV_FILE`. The override lives in the host-generated script, so it works with older pod binaries too. That was the approach suggested in #10398.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: new `sealed_entry_module`

```diff
+impl sealed_entry_module(project_dir: str, fleet: (FleetSpec | None)) -> str {
+    served = fleet.root_member() if fleet is not None else None;
+    if served is None or not served.file { return ""; }          # no fleet → old behaviour
+    config = _project_config(project_dir);
+    if config is not None and config.is_workspace { return ""; } # workspaces unchanged
+    base = Path(project_dir).resolve();
+    rel = Path(_fleet_entry_rel(base, served.app, served.file));
+    parts = [*rel.parent.parts, rel.stem];                       # src/app.jac → ["src","app"]
+    if not all(part.isidentifier() for part in parts) {
+        raise ValueError(f"App '{served.app}' boots '{rel.as_posix()}', which is not an "
+            "importable module name, ... such as 'my_app.jac'.");
+    }
+    module = ".".join(parts);
+    resolved = Path(resolve_entry_path(module, str(base))).resolve();
+    if resolved != (base / rel).resolve() {
+        raise ValueError(f"... its module name '{module}' resolves to "
+            f"'{resolved.relative_to(base).as_posix()}', so the deploy would seal the wrong file. ...");
+    }
+    return module;
+}
```

**What:** It returns the dotted module name of the file the pod boots, or `""` when there is no fleet or the project is a workspace. It raises `ValueError` for two cases:

- a path that isn't a valid module name
- a module name that resolves to a different file

**Why:** It fills the gap from 3.1 by giving the bake the pod's file. The two checks stop the bake from silently sealing the wrong thing.

**Things to notice:**
- The bake works on module names, not file paths. So `my-app.jac` (stem `my-app`) can't be expressed as a module. Before this PR it would have failed inside the pod; now it fails on the host.
- The shadow check answers Greptile's P1. Greptile suggested "preserve the selected file" instead. You chose to refuse the ambiguous layout with a message naming both files.
- `_fleet_entry_rel` isn't in the diff, so its exact rules can't be seen here.
- Edge cases (none tested):
  - `isidentifier()` accepts Python keywords such as `class`.
  - `resolved.relative_to(base)` would itself raise if `resolve_entry_path` returned a path outside `base`. That is still a `ValueError`, but with a less clear message.

## 11. Questions your senior might ask

**Q: Why put the override in the host-generated bake script instead of changing `bake_serve_payloads` in the pod?**
The pod binary used for sealing may be older than the host. A script-level override works with any binary. That was the approach #10398 suggested.

**Q: Why set `entry_point` on every entry in `config.apps`, not just `config.project`?**
The config had already built the implicit app from the old entry. Setting only `project.entry_point` didn't reach it; commit `aefe6b5` fixed that. `getattr` keeps it safe on configs without `apps`.

**Q: Why refuse `app.jac` next to `app/__init__.jac` instead of baking the file directly, as Greptile suggested?**
The bake and `resolve_entry_path` work on dotted module names. In that layout, `app` really means the package, so you can't tell the bake "the file" through the existing API. Failing on the host with both names is clear and safe.

**Q: Does this change anything for workspace deploys?**
No. `sealed_entry_module` returns `""` for workspaces. The bake script and `assert_entry_module_ships` then behave as before. Only the digest gains an (empty) extra part.

**Q: Will adding `entry_module` to the digest invalidate existing cached bundles?**
Possibly once. It depends on how `seal_input_digest` joins parts, and that code isn't shown. The cost is one fresh seal.

**Q: Why is it safe to skip `assert_entry_module_ships` for single-app deploys?**
The pod boots the fleet's file, not the `jac.toml` entry. `check_fleet_entries` still checks that the booted file ships, and `sealed_entry_module` checks it resolves to itself.

**Q: What happens with a deployed file in a subfolder, like `src/app.jac`?**
The module becomes `src.app`. It must pass the identifier check and resolve back to the same file. No test covers a subfolder.

**Q: Could the new `ValueError`s break someone who deploys today?**
Only setups that were already broken. `my-app.jac` failed inside the pod, and a shadowed `app.jac` sealed the wrong module. They now fail earlier with a clear message.

**Q: How do you know the tests actually catch the bug?**
Your CI link shows the new rows failing on the pre-fix code with `entry-point '.../app/main.jac' not found; sealing without serve payloads`. The same rows pass after the fix (372 passed in test-scale microservices).
