## 1. The short version

Jac stores every node, edge and object in a database row. The runtime's `Serializer` turns that row into a JSON blob. The memory layer (SQLite in core `jaclang`, MongoDB in `jac-scale`) writes the blob back during `sync()`. **Before this PR, a nested archetype was copied inline into its parent's blob. Changing one small field, such as `root.profile.display_name`, therefore rewrote the parent's whole row: every edge, every access entry, every other nested object. Two walkers appending to the same list overwrote each other.**

**You added a new serializer flag, `storage_mode=True`. Each nested archetype now becomes a pointer `{"$ref": <uuid>, "$type": "object"}` and gets its own row. On top of that you added per-field "snapshots", so when only list, set or dict fields changed, `sync` sends small element-level writes (`$addToSet`, `$push`, `$pullAll`, `$set` and `$unset` on Mongo; `json_insert`, `json_set` and `json_remove` on SQLite) instead of the whole row.** You also added a PATCH body model to jac-scale's HTTP server, and a 652-line design document, `PARTIAL_UPDATES_PLAN.md`.

The code covers Phases 1–5 of your own plan. Phase 6 (version / CAS), Phase 7 (`by owned`) and Phase 8 (nested PATCH) are not in the diff. The plan lists about 20 tests, but the PR adds none. Every CI test suite fails. The diff points to at least one likely cause: a docstring in `memory.impl.jac` was split in two (see 5.2).

**Status:** Closed. It has no description, no reviews and no linked issues. Every test job and `jac-check` failed on head commit `7abaa60`. The data does not say whether it was merged; given the failing checks, it was most likely closed without merging.

## 3. The problem, step by step

### 3.1 The setup

- A Jac program builds a graph. For example, `Root` is a node with a `profile: Profile` field, and `Profile` has an `avatar: Avatar` field.
- When a walker finishes, the runtime calls `mem.sync()`.
- For each anchor in `__mem__`, `sync` computes `_compute_hash(anchor)`. If the hash changed, it writes the row: `SqliteMemory` through a field-merge path, `MongoBackend` through `put` → `update_one({'$set': doc})`.
- The row is built from `Serializer.serialize(anchor, include_type=True)`. Without `ref_mode`, nested archetypes are fully inlined.

### 3.2 What went wrong

The plan describes these failing cases. There is no linked issue in this repo. The plan cites `jaseci-labs/jaseci#5451` for the concurrency case.

#### Case A: a tiny change rewrites the whole parent

```text
1. Load Root row R.   R.data.archetype.profile = {display_name:"Alice", avatar:{url:..., width:128}}
2. Walker sets root.profile.display_name = "Bob"
3. sync(): hash(Root) is computed over the INLINED profile → hash changed
4. Root's full blob is rewritten: all edges, access, the topology index, all nested objects   ← WRONG: cost ∝ blob size, not change size
5. Profile may ALSO exist as its own row (created by ref_mode elsewhere) → two copies that can drift   ← WRONG
```

#### Case B: two writers append to the same list

```text
1. Walker A loads Root: edges = [e1]          Walker B loads Root: edges = [e1]
2. A appends e2 → local edges = [e1, e2]      B appends e3 → local edges = [e1, e3]
3. A syncs → full $set → DB edges = [e1, e2]
4. B syncs → full $set → DB edges = [e1, e3]   ← WRONG: e2 is lost (last-writer-wins)
```

The same race applies to any `list`, `set` or `dict` field, such as `self.tags.append(...)`.

#### Case C: no PATCH at the HTTP boundary

```text
1. Client wants to change only `name` on a User {name:"a", age:30}
2. jac-scale's body model requires the full archetype shape
3. Client must send every field, or omitted fields are reset or rejected   ← missing feature
```

### 3.3 Why it mattered

- Write cost grows with the size of the parent blob. A deep or wide graph pays for every unrelated field on each mutation.
- The plan says Case B is the incident reported in jaseci#5451, on Mongo deployments. Edges silently go missing under concurrent walkers.
- The PR has no description, no linked issue and no comments. The only "why" evidence is the plan file.

## 4. The idea of the fix (one sentence)

> **One archetype, one row; ship only what changed.** Store each nested archetype as a `$ref` to its own row, so the existing per-anchor hash check skips untouched parents, and turn pure collection changes into atomic element-level database operators.

This reuses the dirty check and the `$ref` resolution that already exist. The hash check was too coarse only because the blobs were too big. Atomic operators are the standard way to make concurrent appends safe without locks.

`_compute_anchor_deltas` works like this:
- For node edges, it compares edge-id sets and records `added` / `removed`, with `set_semantics=True` and path `$.edges`.
- For each archetype field whose serialized value differs from the snapshot:
  - A field that is not a collection sets `scalars_unchanged = False`.
  - A `list` field gives `added` / `removed`, compared by JSON key.
  - A `set` field gives the same, compared over `items`.
  - A `dict` field gives `added_or_changed` keys and `removed` keys.
- A field that existed in the snapshot but is now missing, and is not a collection, also clears `scalars_unchanged`.

- **What:** SQLite rows now hold `$ref`s. Anchors carry a snapshot. `sync` skips anchors whose hash did not change. When only collections changed, `sync` sends one small SQL `UPDATE` per added or removed element, and falls back to the old merge on any exception.
- **Why:** These are Layer 2 (SQLite hash short-circuit) and Layer 4.3 (atomic JSON1 ops), which fix Cases A and B for SQLite.
- **Things to notice:**
  - **Broken docstring, a likely CI breaker.** The new `"""Apply element-level JSON1 ...` docstring and the whole `_put_collection_delta` impl were pasted *inside* the existing, still-open `"""Sync memory to database with access control checks.` docstring. Its first `"""` closes that string. The next line, `Apply element-level JSON1 operators ...`, is then bare text, which is a parse error, and the following `"""` opens a string that swallows code. This file is core runtime, so a parse failure would explain why every test suite and `jac-check` fail. Move the new impl above the sync docstring.
  - **Access, `root` and `persistent` changes are lost on the delta path.** The snapshot covers only edges and archetype attributes. Suppose access rules changed at the same time as a list. The hash differs, but `scalars_unchanged` stays `True`. Only the list is written, and then `anchor.hash` is set to the full local hash. The access change is never written.
  - **Lists with duplicates or reordering.** `added` and `removed` are computed by set membership. Three cases give no delta while still leaving `scalars_unchanged=True`:

    - `[a, b] → [b, a]`
    - `list[i] = v` where `v` already appears in the list

    If another collection field has a real delta in the same sync, the fast path runs and this change is silently dropped.
  - **`json(value)` on string elements.** `json_each` returns string elements as plain SQL text without quotes, and `json('abc')` is malformed JSON. Edge ids are plain strings. So the set-semantics guard and the remove query probably raise as soon as the array is non-empty, and the code falls back to the full merge every time. This needs a test. A related risk: when `json_group_array` passes through a subquery, `json_set` may store its result as a quoted string instead of an array.
  - If the row no longer exists, `UPDATE ... WHERE id = ?` touches 0 rows. The snapshot is still refreshed and the code `continue`s, so the change is dropped silently.
  - Dict keys are pasted straight into JSON paths (`$.archetype.f.{k}`). Keys that contain `.`, `"` or `[` will target the wrong path.
  - The four helper functions are duplicated nearly word for word in the Mongo file (5.3).

## 6. How execution flows after the PR

### 6.1 Loading an anchor

```text
SqliteMemory.get(id)  /  MongoBackend._load_anchor(raw)
├─ read row/doc, deserialize (nested $ref → mem.get, lazy stubs)
├─ _snapshot_anchor_collections(anchor)                           ← NEW
│   ├─ __edges__ = [edge ids]           (NodeAnchor)
│   └─ __arch__  = _serialize_attrs(storage_mode=True)            ← NEW (may call mem.put on nested archetypes)
└─ store in __mem__ / return
```

## 11. Questions your senior might ask

**Q: Why not track dirty fields directly instead of hashing and snapshotting?**
The plan's bet is that shrinking each blob to its own fields makes the *existing* per-anchor hash check good enough, with "no new dirty-field tracking". The snapshot is only for collection deltas.

**Q: Does computing a hash now write to the database?**
Possibly. `_compute_hash` uses `storage_mode=True`, which calls `Jac.get_context().mem.put` for each nested archetype, and `SqliteMemory.put` persists immediately. This needs a test or a redesign so the side effect happens only on real writes.

**Q: What happens with a cycle such as `self.parent = self`, or A ↔ B?**
For `self.parent = self`, the nested value has an anchor, so the serializer `put`s itself and emits a `$ref`. Whether that recurses depends on `put`'s behaviour, which the diff does not show. For A ↔ B, there is no guard visible in the diff. The plan's cycle test was not added.

**Q: Are old, inlined rows still readable?**
The plan says yes: the old inline deserialization path is untouched and `$ref` is already supported. No test proves it in this PR.

**Q: Why use set semantics for edges?**
An edge id should appear only once, so `$addToSet` and the SQLite `NOT EXISTS` guard make concurrent appends idempotent.

**Q: What if a walker both appends and removes items in the same list?**
On Mongo, the update has two operators on the same path, which MongoDB rejects. The code then falls back to a full `put`, which brings back last-writer-wins.

**Q: Does the delta path respect access control?**
On SQLite, yes: connect access for edge-only changes, write access otherwise. On Mongo, the fast path sits after an existing check that is not shown in the diff. Changes to `access` itself can be silently skipped on the fast path.

**Q: How does PATCH tell "absent" apart from "null"?**
Through `model_fields_set`. But the code uses `pydantic.Undefined` as the default, which likely does not import in Pydantic v2 and would make fields required. It also builds a fresh archetype instead of patching the loaded one.

**Q: Why did every CI job fail, even the compiler tests?**
Most likely a core file fails to parse: the new docstring opened inside the existing `SqliteMemory.sync` docstring in `memory.impl.jac`. The logs aren't in the PR data, so confirm by running `jac check` locally.

**Q: What parts of the plan are deliberately left out?**
Layer 4.4 (version / CAS), Layer 5 (`by owned`), Layer 3.3 (nested PATCH) and `@jac.set_semantics`. In the code, a plain `list` always uses `$push`, and only `set` fields and edges use set semantics.
