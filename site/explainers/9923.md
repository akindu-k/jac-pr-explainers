# fix(seal): bake a serve manifest free of seal stage paths

<!-- explainer -->

## In short

When you seal an app into a `.jab` bundle, the seal also writes a serve manifest into it. Before this PR, that manifest recorded the path of a temporary build folder whose name is random on every run. So two packs of the same code never had the same bytes, and the deploy step could never tell that a bundle was unchanged. You now remove those path fields (`root` and each surface entry's `module`) before the manifest is baked, and you fixed a test fixture so the determinism test actually covers the manifest.

## Words to know

- **Seal / sealing**: The step that packs a Jac app into a self-contained bundle that a pod can run. The code lives in `jac/jaclang/dist/seal.jac`.
- **`.jab`**: The bundle file the seal produces. `jac scale deploy` ships it to the cluster.
- **Seal stage**: A temporary folder where the seal copies and prepares the app before packing it. According to your description, its path looks like `/tmp/jac-app-precompile-<pid>-<random>/app`. Here `<pid>` is the process id, so the name changes on every run.
- **Serve manifest (`.jac/serve_manifest.json`)**: A JSON file baked into the `.jab`. It tells the server what the app exposes, so the pod does not have to work that out again at startup.
- **`root`**: A field in a serve manifest that holds the absolute folder path of the app.
- **Surface / surface entry**: The "surface" is the set of declarations a module exposes to callers (for example, walkers or functions served over HTTP). Each surface entry is one exposed declaration. Before this PR, each entry had a `module` field holding an absolute path.
- **Module manifests**: Per-file serve manifests for the other modules or services in the app. They are stored under `module_manifests` and keyed by a relative path such as `scoring.jac`.
- **Pod**: In Kubernetes, the running container that serves your app. jac-scale deploys the `.jab` to pods.
- **Content-addressed / digest**: The bundle is identified by a hash (digest) of its bytes. If the digest matches the one already deployed, the deploy skips re-shipping it. This only works if identical content always gives identical bytes.
- **Determinism**: Here, the property that packing the same input always produces the same output bytes.
- **Fixture**: The small sample app a test builds and runs against.
- **mtime**: A file's "last modified" time. The determinism test checks that a different mtime alone does not change the digest.

## The problem

Here is what happened before this PR:

1. You run `jac scale deploy`.
2. The seal copies the app into a fresh stage folder, for example `/tmp/jac-app-precompile-4121-ab9f/app`.
3. `build_serve_manifest` compiles the app from that folder and takes the manifest for the entry file. It also takes the manifest for every other module.
4. Each manifest had `root: "/tmp/jac-app-precompile-4121-ab9f/app"`. Each surface entry had a `module` path inside that same folder.
5. That JSON goes into the `.jab`.
6. The next deploy, with no code change, uses a different stage folder, for example `/tmp/jac-app-precompile-5307-c21e/app`. The manifest bytes differ, so the `.jab` bytes differ, so the digest differs.
7. The content-addressed skip never matches, so every deploy re-ships the bundle even when nothing changed.

Those paths were also useless on the pod, because the `/tmp/...` folder only existed on the machine that ran the seal.

The existing determinism test did not catch this. Its fixture app had only a `svc.jac` file and no entry the seal could resolve, so no serve manifest was baked at all. The test was comparing bundles that did not contain the broken part.

Who was affected: anyone redeploying with jac-scale. They paid for a full re-ship on every deploy. Your description also says PR #9610 depends on this fix, because its fixture apps do bake a serve manifest, so its determinism tests would fail without it.

## The changes, one by one

### `jac/jaclang/dist/seal.jac`: strip stage paths before baking

You added two small helpers and used them inside `build_serve_manifest`.

```jac
def _without_keys(record: dict[str, any], dropped: str) -> dict[str, any] {
    return {
        key: value
        for (key, value) in record.items()
        if key != dropped
    };
}
```

- This builds a **new** dict that has every key of `record` except `dropped`.
- It does not change the original dict, so the in-memory manifests in `prepared` are left as they were.
- Despite the plural name, it drops exactly one key.

```jac
def _portable_manifest(manifest: dict[str, any]) -> dict[str, any] {
    result = _without_keys(manifest, 'root');
    if result.get('surface') {
        result['surface'] = {
            name: _without_keys(rec, 'module')
            for (name, rec) in result['surface'].items()
        };
    }
    return result;
}
```

- Line 2 makes a copy of the manifest without `root`.
- Lines 3–7: if the manifest has a non-empty `surface`, it replaces it with a new dict. In that dict, each surface entry is copied without its `module` key. Other keys in each entry, such as the relative `src`, are kept.
- It returns the cleaned copy. Nothing is mutated in place: the new `surface` dict is assigned onto `result`, which is already a copy.

Then in `build_serve_manifest`:

```jac
-        result = dict(prepared.manifests[str(entry_file.resolve())]);
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);
         result['module_manifests'] = {
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(
+                manifest
+            ) for application in [prepared, *prepared.applications]
             for (path, manifest) in application.manifests.items()
         };
```

- The entry file's manifest used to be a plain `dict(...)` copy. Now it is a cleaned copy with no `root` and no surface `module`.
- `module_manifests` was already keyed by a **relative** path (`os.path.relpath(..., prepared.root)`, with `/` separators), so the keys were already portable. Before this PR, the values were the raw manifests with absolute paths inside them. Now each value goes through `_portable_manifest` too.
- The loop over `[prepared, *prepared.applications]` is unchanged. It still covers the main app and each colocated service.

Why removing the fields is safe: your description gives three reasons. That code is not in this diff, so these are claims from the description:

- `_prepare_sealed`, on the pod, sets `root` to the image path it actually boots from. It does this for the entry manifest and for every module manifest.
- Declarations are resolved through the relative `src`. The surface `module` is only carried through `SurfaceEntry.from_dict`, so nothing depends on its value.
- In the raw fallback in `serve_manifest_for`, a missing `root` makes `ModuleIntrospector` fall back to `sealed_root_for` the module file. Before, it would have trusted a `/tmp` stage path that does not exist on the pod.

## How it runs now

1. A user runs `jac scale deploy`.
2. The seal copies the app into a temporary stage folder (`/tmp/jac-app-precompile-<pid>-<random>/app`).
3. `resolve_entry_file` finds the app's entry file.
4. `build_serve_manifest(entry_file, proj_root)` compiles the program and prepares manifests for the entry, its modules and any colocated services.
5. **(changed)** The entry's manifest is passed through `_portable_manifest`, which removes `root` and every surface entry's `module`.
6. **(changed)** Each module manifest under `module_manifests` is also passed through `_portable_manifest`. The keys stay relative paths, as before.
7. The manifest is written as `.jac/serve_manifest.json` into the `.jab`. Because nothing in it depends on the stage folder name, the same content now gives the same bytes.
8. The deploy computes the bundle digest and compares it with what is already deployed. It now matches when the content is unchanged, so the bundle is not re-shipped.
9. On the pod, according to your description (this code is not changed in this diff):
   - `_prepare_sealed` fills in `root` with the image's real path.
   - On the raw fallback in `serve_manifest_for`, the missing `root` makes `ModuleIntrospector` use `sealed_root_for` the module file.

## Tests

- Setup: this is an existing test that seals an app with colocated services and reads the baked manifest (`manifest`) and its module manifests (`modules`). It already checked things like `private_score` not appearing in `scoring.jac`'s surface.
- New check: it loops over the entry manifest plus every module manifest. It asserts:

  - no surface entry in any of them has a `module` key.
  - `(entry_manifest.get('surface') or {})` handles manifests that have no surface.
- What it proves: `_portable_manifest` is applied both to the top-level manifest and to every entry in `module_manifests`. Any future change that leaks a stage path back into either field will fail this test.

## Explaining it in one minute

"The seal bakes a serve manifest into every `.jab`. That manifest stored the absolute path of the temporary stage folder, both as `root` and as each surface entry's `module`. The folder name is random per run, so identical apps never packed to identical bytes, and the deploy's content-addressed skip never hit. Every redeploy re-shipped the bundle.

I added a `_portable_manifest` helper in `build_serve_manifest`. It removes `root` and the surface `module` from the entry manifest and from every module manifest before baking. Neither field is needed on the pod: `_prepare_sealed` sets the real `root` there, declarations resolve through the relative `src`, and on the raw fallback `ModuleIntrospector` uses `sealed_root_for` when `root` is missing.

For tests, I extended the application-preparation test to assert those keys are gone from every baked manifest. I also fixed the seed determinism test's fixture to use `main.jac`, so it actually bakes a manifest. Before, it had no resolvable entry, which is why it missed the bug. #9610 depends on this."
