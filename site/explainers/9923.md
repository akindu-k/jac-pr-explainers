## 1. The short version

When an app is **sealed** (precompiled into a deployable bundle), the seal writes a small JSON file, `.jac/serve_manifest.json`, into every `.jab` bundle. The pod reads it at boot to know what the app serves. `jac scale deploy` also has a shortcut: if a new bundle's bytes match the one already deployed, it skips re-shipping it.

**The baked manifest recorded the temporary seal folder (`/tmp/jac-app-precompile-<pid>-<random>/app`) as its `root` and as each surface entry's `module`. That folder name changes on every pack, so two packs of identical content never produced identical bytes, and the "unchanged bundle" skip never fired.** The existing determinism test did not catch this. Its fixture file was named `svc.jac`, which is not a resolvable entry, so no serve manifest was baked at all.

**You added `_portable_manifest` in `seal.jac`. It strips `root` from every baked manifest (the entry's and each module's) and strips `module` from every surface entry, so the baked file no longer contains any stage path.** You also renamed the determinism test's fixture to `main.jac`, so the test now bakes a manifest and compares the bytes. The test for colocated services now asserts that the two keys are absent.

**Status:** Open, with no human review yet. The Greptile bot gave it 5/5 confidence. Most CI checks pass, but `jac-check` failed, which makes the aggregate "Everything Passed" check fail too.

## 3. The problem, step by step

### 3.1 The setup

- **Host side:** `pack_jab` copies the app into a fresh seal stage, runs the bake (`build_serve_manifest`), seals, then tars the stage into a `.jab`.
- **Deploy side:** the bundle's bytes are hashed. If the hash matches what is already deployed, the bundle is not re-shipped.
- **Pod side:** the bundle is extracted, and `_prepare_sealed` reads the serve manifest and boots from the image.

### 3.2 What went wrong

```text
1. Pack #1: stage = /tmp/jac-app-precompile-111-aaaa/app
2.   build_serve_manifest copies prepared.manifests[entry] as-is
3.   baked JSON: "root": "/tmp/jac-app-precompile-111-aaaa/app",
                 surface.X.module: "/tmp/jac-app-precompile-111-aaaa/app/..."   ← WRONG: temp path baked in
4.   module_manifests entries also carry their own "root"/"module"           ← WRONG
5.   bundle hash = H1
6. Pack #2, same content: stage = /tmp/jac-app-precompile-222-bbbb/app
7.   baked JSON now contains ".../222-bbbb/..." instead
8.   bundle hash = H2 ≠ H1                                                    ← WRONG: identical content, different bytes
9. Deploy compares hashes → "changed" → re-ships bundle every time
```

### 3.3 Why the tests missed it

```text
1. test_seed_determinism writes the fixture as svc.jac
2. resolve_entry_file finds no entry → bake writes no serve manifest
3. bundle has no stage paths → H1 == H2 → test passes
4. Real apps (with an entry) were never covered
```

### 3.4 Why it mattered

- Every redeploy of an unchanged app re-shipped its bundle, which wastes time and transfer. The release note says: "Redeploying an app whose content did not change no longer re-ships its bundle".
- The baked paths were also wrong on the pod, because `/tmp/jac-app-precompile-…` does not exist there. The PR description says pod code either overwrites `root` or should fall back when it is missing.
- **Dependency:** the description says #9610 (the fix for issue #9138) depends on this PR. #9610 makes fixture apps bake a serve manifest, so its fat-bundle and seed determinism tests would fail on stage paths without this fix.

## 4. The idea of the fix (one sentence)

> **Don't bake machine-specific paths.** Drop `root` and surface `module` from every baked manifest, because the pod works them out from where it actually boots.

The seal stage path is meaningless after packing, so storing it makes the output non-deterministic and adds nothing. The alternative, rewriting the paths to some fixed placeholder, would still leave a value the pod has to ignore or replace.

## 5. Every code change, explained

### 5.1 `jac/jaclang/dist/seal.jac`: bake a portable manifest

```diff
+def _without_keys(record: dict[str, any], dropped: str) -> dict[str, any] {
+    return { key: value for (key, value) in record.items() if key != dropped };
+}
+
+def _portable_manifest(manifest: dict[str, any]) -> dict[str, any] {
+    result = _without_keys(manifest, 'root');                 # NEW: drop stage path
+    if result.get('surface') {
+        result['surface'] = {
+            name: _without_keys(rec, 'module')                 # NEW: drop per-entry path
+            for (name, rec) in result['surface'].items()
+        };
+    }
+    return result;
+}
 ...
-        result = dict(prepared.manifests[str(entry_file.resolve())]);          # OLD: plain copy
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);  # NEW
         result['module_manifests'] = {
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest           # OLD: raw
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(
+                manifest
+            ) for application in [prepared, *prepared.applications]                      # NEW
             for (path, manifest) in application.manifests.items()
         };
```

**What:** The entry manifest and every module manifest are now passed through `_portable_manifest` before baking. Each loses its `root` key, and each surface record loses its `module` key.

**Why:** These were the two places the temporary stage path leaked into the bundle bytes.

**Things to notice:**
- **No mutation of the original.** `_without_keys` builds a new dict, and `surface` is replaced with a new dict. The in-memory `prepared.manifests` is left untouched, the same as the old `dict(...)` copy. Before the PR, module manifests were inserted by reference, not copied. Now they are copied.
- **Shallow copy only.** Nested values other than `surface` records are shared. That is fine because nothing here mutates them.
- **`if result.get('surface')`** skips both a missing and an empty surface. It assumes every surface value is a dict.
- **Keys of `module_manifests` were already portable.** They are paths relative to `prepared.root`, with `/` separators. Only the values needed cleaning.
- **The removal is targeted.** Only `root` and surface `module` are dropped. If another field held an absolute path, it would still leak. The determinism test (section 7) would now catch that, but only for its simple fixture.
- **Pod-side claims are not in the diff.** The description says three things about pod code: `_prepare_sealed` sets `root` itself, declarations resolve through the relative `src`, and `ModuleIntrospector` falls back to `sealed_root_for` when `root` is missing. None of that code is in this diff, so you should be ready to point at it (see section 11).

## 6. How execution flows after the PR

### 6.1 Packing a bundle on the host

```text
pack_jab(app_dir, binary)
├─ copy app into /tmp/jac-app-precompile-<pid>-<rand>/app
├─ resolve_entry_file → main.jac (or None → no manifest baked, unchanged)
├─ build_serve_manifest(entry, stage)
│   ├─ prepare application (manifests keyed by absolute stage paths)
│   ├─ result = _portable_manifest(entry manifest)            ← CHANGED
│   │   ├─ drop "root"                                         ← NEW
│   │   └─ drop surface[*].module                              ← NEW
│   └─ module_manifests[relpath] = _portable_manifest(m)       ← CHANGED
├─ write .jac/serve_manifest.json (no stage paths)
├─ seal, tar deterministically
└─ bundle bytes now depend only on content → stable hash
```

### 6.2 Booting on the pod (as described, not in the diff)

```text
extract .jab → jac run --serve <entry>
├─ _prepare_sealed reads serve_manifest.json
│   └─ sets root = image it boots from (entry + each module manifest)
└─ raw fallback path (serve_manifest_for)
    └─ root absent → ModuleIntrospector uses sealed_root_for(module file)
```

| Scenario | Before | After |
|---|---|---|
| Redeploy, identical content, app has an entry | New hash every time, bundle re-shipped | Same hash, bundle skipped |
| App has no resolvable entry | No manifest, stable hash | Unchanged |
| Pod reads `root` from baked manifest | Got a `/tmp/...` path that doesn't exist on the pod | Key absent, so the pod derives it (per description) |

**User-visible change:** unchanged redeploys become no-ops for the bundle upload. One compatibility point is not covered by the PR: any code that reads the baked `root` or surface `module` directly would now get a missing key. The description says the only consumers handle that.

## 11. Questions your senior might ask

**Q: Why drop the keys instead of rewriting them to a relative path?**
A: The pod never needs them. Per the description, `_prepare_sealed` sets `root` from the image it boots, and declarations resolve through the relative `src`. A placeholder would just be another value to ignore.

**Q: What happens on the pod if something reads `manifest['root']` directly?**
A: It would get a `KeyError`. The description says the readers are `_prepare_sealed`, which overwrites `root`, and the raw fallback in `serve_manifest_for`, where `ModuleIntrospector` falls back to `sealed_root_for`. That code isn't in this diff, so be ready to show it.

**Q: Are `module_manifests` keys also stage paths?**
A: No. They were already `os.path.relpath(path, prepared.root)` with `/` separators, so only the values needed cleaning.

**Q: Could other fields still leak absolute paths?**
A: The PR only removes `root` and surface `module`. The determinism test now compares the bytes of a bundle with a baked manifest, so any remaining leak would show up there for that simple app. A richer app is not byte-compared.

**Q: Does this mutate `prepared.manifests`?**
A: No. `_without_keys` returns new dicts, and `surface` is replaced, not edited in place.

**Q: Why didn't the old determinism test catch this?**
A: Its fixture was `svc.jac`, which `resolve_entry_file` doesn't resolve as an entry. No serve manifest was baked, so there were no stage paths in the bundle. Renaming it to `main.jac` makes the test bake one.

**Q: Does this close #9138?**
A: No. #9138 is about failing the pack when the manifest is missing. This PR makes bundles that do have a manifest deterministic, which #9610 (the #9138 fix) needs for its tests.

**Q: Why is `jac-check` red?**
A: The CI data here doesn't say. Check the log before the review.

**Q: Do old bundles with `root` still boot on new pods?**
A: Per the description, the pod overwrites `root` anyway, so a stale baked value is ignored. This compatibility case isn't tested in this PR.
