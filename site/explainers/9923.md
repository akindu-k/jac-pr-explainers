# fix(seal): bake a serve manifest free of seal stage paths

[#9923](https://github.com/jaseci-labs/jac/pull/9923) by @akindu-k · opened 10 Oct 2026 · +35 −4 in 4 files

<!-- explainer -->

## In short
The seal step bakes `.jac/serve_manifest.json` into every `.jab`, and that file recorded the temporary seal stage path, which changes on every pack. This PR strips the `root` and surface-entry `module` fields from the baked manifests, so identical content now packs to identical bytes and unchanged bundles are skipped on redeploy.

## Why it was needed
The baked manifest stored the stage folder (`/tmp/jac-app-precompile-<pid>-<random>/app`) as the manifest's `root` and as each surface entry's `module`. The folder name differs on every pack, so two packs of the same content produced different bytes. The content-addressed check that avoids re-shipping an unchanged bundle therefore missed on every `jac scale deploy`.

The existing determinism tests did not catch it. Their fixture apps had no resolvable entry, so no serve manifest was baked in those tests. The PR also says #9610 (#9138) depends on this, because its fixtures now bake a serve manifest. It supersedes #9613, which was closed for inactivity.

## What changed
- **`jac/jaclang/dist/seal.jac`**
  - Added `_without_keys(record, dropped)`, which returns a copy of a dict without one key.
  - Added `_portable_manifest(manifest)`, which drops `root` from a manifest and `module` from each entry in its `surface`.
  - `build_serve_manifest` now passes the entry manifest and every item in `module_manifests` through `_portable_manifest`.
- **`jac/tests/compiler/test_application_preparation.jac`**: the "sealing retains each colocated service's access metadata" test now asserts that no baked manifest has `root` and no surface entry has `module`.
- **`jac/jaclang/scale/tests/microservices/test_seed_determinism.jac`**: the fixture file is renamed from `svc.jac` to `main.jac`.
- **`release_notes/unreleased/jaclang/9923.bugfix.md`**: a bugfix release note.

## How it works
`build_serve_manifest` prepares the application in the stage directory, then builds the manifest dict from `prepared.manifests`. Before this PR it copied that dict as is, so the stage-specific absolute paths went into the file. Now each manifest goes through `_portable_manifest`:

```
result = _without_keys(manifest, 'root');
if result.get('surface') {
    result['surface'] = {
        name: _without_keys(rec, 'module') for (name, rec) in ...
    };
}
```

According to the PR description, the pod does not need these fields:
- `_prepare_sealed` sets `root` to the image the pod actually boots from, for the entry and for every module manifest.
- Declarations are resolved through the relative `src`. The surface `module` is only carried through `SurfaceEntry.from_dict`.
- On the raw fallback in `serve_manifest_for`, a missing `root` makes `ModuleIntrospector` fall back to `sealed_root_for` the module file, rather than trusting a stage path that does not exist on the pod.

The `module_manifests` keys were already relative to `prepared.root`, so they were stable. Only the values contained the unstable paths.

## Tests
- The access-metadata test in `test_application_preparation.jac` loops over the entry manifest and every module manifest. It checks that none has `root` and that no surface record has `module`.
- `test_seed_determinism.jac` ("identical content packs to identical bytes") now uses a `main.jac` entry, so the pack bakes a serve manifest and the byte-equality check covers it. The test count is unchanged.

## Worth knowing
- Baked manifests no longer contain `root` or surface `module`. Anything reading a baked `.jab` manifest directly and expecting those keys would need to rely on the pod-side logic described above. The diff does not show other consumers, so I could not check this.
- The determinism test only covers the `main.jac` fixture. Other stage-dependent content in a bundle, if any exists, is not addressed by this PR.
