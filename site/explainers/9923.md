# fix(seal): bake a serve manifest free of seal stage paths

[#9923](https://github.com/jaseci-labs/jac/pull/9923) by @akindu-k · opened 10 Oct 2026 · +35 −4 in 4 files

<!-- explainer -->

## In short

When Jac seals an app into a `.jab` bundle, it bakes a serve manifest into it. That manifest recorded a temporary build folder whose name changes on every pack. So the same content gave different bytes each time, and the "unchanged bundle" check never matched. You removed the two fields that held that path (`root` and each surface entry's `module`), so identical content now packs to identical bytes.

## Words to know

- **Seal**: the step that packs an app into a `.jab` bundle for deployment. It works in a temporary "stage" folder.
- **`.jab`**: the bundle file produced by the seal. It holds the app, its metadata and a runtime binary.
- **Stage folder**: the temporary directory, like `/tmp/jac-app-precompile-<pid>-<random>/app`, where the seal assembles the app. Its name differs on every run.
- **Serve manifest** (`.jac/serve_manifest.json`): a JSON file baked into the bundle. It describes what the app serves: its entry, its surface (the exposed declarations) and per-module manifests.
- **Surface**: the list of declarations a module exposes to callers. Each surface entry may have a `module` field.
- **`root`**: a manifest field naming the folder the app lives in.
- **Content-addressed skip**: the deploy computes a digest (hash) of the bundle bytes. If it matches what is already deployed, the bundle is not shipped again.
- **Determinism**: the same input always gives the same output bytes.
- **Pod**: the container in Kubernetes that runs the deployed app.
- **`_prepare_sealed`**: code that runs on the pod. It sets `root` to the image the app actually boots from.
- **`ModuleIntrospector` / `sealed_root_for`**: the runtime code that inspects a module. When `root` is missing, it works out the sealed root from the module file's location.
- **Fixture**: sample data or a sample app a test builds to run against.

## The problem

1. `build_serve_manifest` compiles the entry and builds manifests while the app sits in the stage folder.
2. Those manifests held the stage path in `root` and in each surface entry's `module`.
3. The stage folder name contains a process id and a random part, so it differs on every pack.
4. The manifest is part of the `.jab`, so the bundle bytes differed on every pack, even for identical source.
5. The deploy's digest check therefore missed every time, and an unchanged bundle was shipped again.

The stage path is also useless on the pod, because that folder does not exist there.

The existing determinism tests did not catch this. Their fixture app had no resolvable entry file, so no serve manifest was baked and the bug never showed.

## The changes, one by one

### `jac/jaclang/dist/seal.jac`

This is the fix. You added two helpers and used them in `build_serve_manifest`.

- `_without_keys(record, dropped)` returns a copy of a dict without one key.
- `_portable_manifest(manifest)` removes `root` from the manifest. If it has a `surface`, it also removes `module` from each surface entry.

```jac
result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);
result['module_manifests'] = {
    os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(manifest)
    for application in [prepared, *prepared.applications]
    for (path, manifest) in application.manifests.items()
};
```

- The entry manifest used to be copied with `dict(...)`. It now goes through `_portable_manifest`.
- Every manifest in `module_manifests` also goes through `_portable_manifest`. The relative-path keys were already portable, so they stay the same.

Why dropping these fields is safe (from the PR description):

- `_prepare_sealed` sets `root` on the pod for the entry and every module manifest, so the baked value is overwritten anyway.
- Declarations are found through the relative `src` field. The surface `module` is only passed along by `SurfaceEntry.from_dict`.
- In the raw fallback in `serve_manifest_for`, a missing `root` makes `ModuleIntrospector` use `sealed_root_for` the module file, instead of a stage path that does not exist on the pod.

I only see the diff of `seal.jac`, not those other functions, so these claims come from the PR description.

## How it runs now

1. A user runs `jac scale deploy`, which packs the app with the seal.
2. The seal assembles the app in a temporary stage folder.
3. `build_serve_manifest` compiles the entry and gets the prepared manifests.
4. (changed) The entry manifest goes through `_portable_manifest`, so `root` and surface `module` are removed.
5. (changed) Each manifest in `module_manifests` goes through `_portable_manifest` too.
6. The manifest is baked into the `.jab`. (changed) Its bytes no longer depend on the stage folder name.
7. The deploy hashes the bundle. (changed) For identical content the digest now matches, so the bundle is not shipped again.
8. On the pod, `_prepare_sealed` sets `root` to the real image path. If the raw fallback is used instead, `ModuleIntrospector` derives the root with `sealed_root_for`.

## Explaining it in one minute

"The seal bakes a serve manifest into every `.jab`. That manifest recorded the temporary stage folder in `root` and in each surface entry's `module`. The folder name has a random part, so identical content gave different bytes and the deploy's digest check never skipped an unchanged bundle. I added `_portable_manifest`, which drops those two fields, and used it on the entry manifest and every module manifest in `build_serve_manifest`. The pod doesn't need them: `_prepare_sealed` sets `root` itself, declarations use the relative `src`, and the fallback derives the root from the module file. I extended the access-metadata test to assert the fields are gone. I also changed the determinism test fixture to ship a `main.jac`, so a serve manifest is actually baked and the test covers this case."
