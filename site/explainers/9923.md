## 1. The short version

When Jac Scale deploys an app, it first **seals** the app. Sealing means precompiling it into a self-contained `.jab` bundle. Part of that bundle is a file called `.jac/serve_manifest.json`, which tells the pod what to serve. Jac Scale then hashes the bundle bytes. If the hash matches what is already deployed, it skips re-shipping. This is the "content-addressed skip".

**The baked serve manifest recorded the temporary seal folder, for example `/tmp/jac-app-precompile-<pid>-<random>/app`, as the manifest's `root` and as each surface entry's `module`. That folder name changes on every pack, so two packs of identical content never had identical bytes, and the skip missed on every deploy.** The existing determinism test did not catch this. Its fixture app had no entry file that could be resolved, so no serve manifest was baked at all.

**You changed `build_serve_manifest` in `jac/jaclang/dist/seal.jac` to drop `root` from every baked manifest and `module` from every surface entry before they are written.** You also changed the determinism test fixture so it actually bakes a manifest, and you added assertions that the stage path is gone.

**Status:** Open and waiting for human review. No human has reviewed it yet. The Greptile bot gave it 5/5. One CI check (`build-kit`) is still running, and two checks were skipped. This PR supersedes #9613, which was closed for inactivity. #9610 depends on it.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac Scale (`jac-scale`) | The plugin that deploys Jac apps to Kubernetes pods. |
| `.jab` | A Jac application bundle. It is a tarball holding the sealed app that every pod extracts and boots. |
| Seal / sealing | Precompiling an app on the host so the pod can boot without compiling. |
| Seal stage | A temporary folder where the seal happens, named `/tmp/jac-app-precompile-<pid>-<random>/app`. The name differs on every run. |
| Serve manifest (`.jac/serve_manifest.json`) | JSON baked into the `.jab` that describes what the server exposes. The pod reads it at boot. |
| `build_serve_manifest` | The function in `seal.jac` that builds that JSON from the compiled program. **This is where the bug is.** |
| `root` | A key in each manifest holding the absolute folder of the app. Before this PR, the baked copy held the seal stage path. |
| `module_manifests` | A sub-map in the entry manifest with one manifest per module, keyed by relative path, e.g. `"scoring.jac"`. |
| Surface / surface entry | The list of declarations a module exposes to the outside. Each entry had a `module` key, which was an absolute stage path, and a relative `src`. |
| `_without_keys` / `_portable_manifest` | New helpers. The first copies a dict minus one key. The second strips `root`, and strips `module` from each surface entry. **This is what the PR adds.** |
| Content-addressed skip | Deploy logic that compares a hash of the bundle bytes with the deployed one and skips shipping when they match. Example: same digest means no upload. |
| Deterministic / byte-identical | Same input gives exactly the same output bytes. The skip needs this. |
| `pack_jab` | Builds the `.jab` tarball. The determinism test calls it twice. |
| `_prepare_sealed` | Pod-side code that loads the sealed bundle. According to the PR description, it sets `root` itself to the folder it boots from. |
| `serve_manifest_for`, `ModuleIntrospector`, `sealed_root_for` | Pod-side code paths that the description says handle a missing `root`. They are not in the diff. |
| `SurfaceEntry.from_dict` | According to the description, this is where the surface `module` key is only carried through and not used. |

## 3. The problem, step by step

### 3.1 The setup

- **Host side:** `jac scale deploy` stages the app in a fresh temp folder. It runs the bake, which calls `build_serve_manifest`, then runs `precompile --seal`, then calls `pack_jab` to make the tarball and hashes it.
- **Deploy logic:** If the hash equals the last deployed hash, it skips shipping.
- **Pod side:** The pod extracts the `.jab` and boots it with `_prepare_sealed`, which reads the serve manifest.

### 3.2 What went wrong

```text
1. Deploy #1: stage = /tmp/jac-app-precompile-1234-ab12/app
2.   build_serve_manifest -> {"root": "/tmp/jac-app-precompile-1234-ab12/app",
                              "surface": {"f": {"module": "/tmp/...-1234-ab12/app/main.jac", "src": ...}},
                              "module_manifests": {"scoring.jac": {"root": "/tmp/...-1234-ab12/app", ...}}}
3.   pack_jab -> digest D1, bundle shipped
4. Deploy #2, no source change: stage = /tmp/jac-app-precompile-5678-cd34/app
5.   build_serve_manifest -> same JSON, but every "root"/"module" now says ...-5678-cd34
6.   pack_jab -> digest D2 != D1                       <-- WRONG: same content, different bytes
7.   content-addressed skip misses -> bundle re-shipped to every pod
```

There is a second, smaller problem. The description says that on the pod's raw fallback path in `serve_manifest_for`, a baked `root` pointed at a `/tmp/...` folder that does not exist on the pod. You cannot see this path in the diff.

### 3.3 Why it mattered

- Every deploy re-shipped the bundle, even when nothing changed. The skip existed precisely to avoid that.
- The test that should guard this ("identical content packs to identical bytes") passed by accident. Its fixture `svc.jac` did not resolve as an entry, so no manifest was baked.
- #9610 (the work on #9138) changes its fixtures so they *do* bake a manifest. With this bug present, its fat-bundle and seed determinism tests would fail. That is why it depends on this PR.

## 4. The idea of the fix (one sentence)

> **Don't bake host-only paths.** Strip `root` and the surface `module` from the baked manifest, because the pod works them out from where it actually runs.

The other options are worse. A fixed stage folder name would let parallel seals collide. Rewriting the paths to relative ones would add a format the pod does not need. Removing data the pod already overrides is the smallest change that makes the bytes deterministic.

## 5. Every code change, explained

### 5.1 `jac/jaclang/dist/seal.jac`: strip stage paths from the baked manifest

```diff
+def _without_keys(record: dict[str, any], dropped: str) -> dict[str, any] {
+    return { key: value for (key, value) in record.items() if key != dropped };
+}
+
+def _portable_manifest(manifest: dict[str, any]) -> dict[str, any] {
+    result = _without_keys(manifest, 'root');                 # NEW: drop root
+    if result.get('surface') {
+        result['surface'] = {
+            name: _without_keys(rec, 'module')                # NEW: drop module per entry
+            for (name, rec) in result['surface'].items()
+        };
+    }
+    return result;
+}
 ...
-        result = dict(prepared.manifests[str(entry_file.resolve())]);          # OLD: plain copy
+        result = _portable_manifest(prepared.manifests[str(entry_file.resolve())]);  # NEW
         result['module_manifests'] = {
-            os.path.relpath(path, prepared.root).replace(os.sep, '/'): manifest           # OLD
+            os.path.relpath(path, prepared.root).replace(os.sep, '/'): _portable_manifest(
+                manifest
+            ) for application in [prepared, *prepared.applications]                   # NEW
             for (path, manifest) in application.manifests.items()
         };
```

**What:** The entry manifest and every module manifest now go through `_portable_manifest` before they are returned and written. The function removes the top-level `root` key. It also rebuilds `surface` so that each entry lacks `module`.

**Why:** These were the only fields in the diff that carried the per-run stage path. Removing them makes the JSON, and therefore the `.jab` bytes, the same across packs of the same content.

**Things to notice:**
- **No mutation.** `_without_keys` builds new dicts, and `surface` is replaced with a new dict rather than edited in place. The in-memory `prepared.manifests` is left untouched. Before, module manifests were inserted by reference, not copied.
- **Edge cases:** `if result.get('surface')` skips both a missing surface and an empty surface. An empty `{}` stays as it is.
- **The keys stay relative.** The `module_manifests` keys still use `prepared.root`, but only through `relpath`, so they stay relative and portable.
- **The copy is shallow.** The rest of each surface entry, including `src`, is shared with the original.
- **Other fields are not checked.** The diff does not show whether any other field holds an absolute path. The determinism test is the safety net for that.
- **Pod-side claims are unverified here.** The description says `_prepare_sealed`, `SurfaceEntry.from_dict`, and `ModuleIntrospector`/`sealed_root_for` cope without these keys. None of that code is in the diff, so a reviewer may want to see it.

## 6. How execution flows after the PR

### 6.1 Packing a bundle on the host

```text
jac scale deploy
├─ stage app in /tmp/jac-app-precompile-<pid>-<random>/app
├─ bake -> build_serve_manifest(entry_file, proj_root)
│   ├─ compile program, prepare application + services
│   ├─ entry manifest -> _portable_manifest              ← CHANGED (no root, no surface.module)
│   ├─ module_manifests[relpath] -> _portable_manifest   ← CHANGED
│   └─ write .jac/serve_manifest.json
├─ precompile --seal
├─ pack_jab -> .jab bytes now identical for identical content  ← CHANGED (result)
└─ digest == deployed digest? → skip shipping (now actually hits)
```

### 6.2 Booting on the pod (per the description, code not in diff)

```text
jac run --serve web/main.jac
├─ _prepare_sealed reads .jac/serve_manifest.json
│   └─ sets root = image folder it boots from (entry + every module manifest)
├─ declarations resolved via relative src (surface module not needed)
└─ raw fallback in serve_manifest_for: no root → ModuleIntrospector uses sealed_root_for(module file)
    (before: trusted a /tmp stage path that doesn't exist on the pod)
```

| Scenario | Before | After |
|---|---|---|
| Redeploy, no source change | New digest, bundle re-shipped | Same digest, ship skipped |
| Two packs of the same content | Different bytes | Identical bytes |
| Pod normal boot | `root` overridden by the pod | Same, with nothing to override |
| Pod raw fallback | Used the non-existent stage path | Uses `sealed_root_for` |

The behaviour change users will notice is that unchanged redeploys stop uploading the bundle.

## 11. Questions your senior might ask

**Q: Why remove the fields instead of making them relative?**
The pod already sets `root` from the folder it boots from, and resolves declarations through the relative `src`. Relative copies would be unused data.

**Q: Why not use a fixed stage folder name?**
The pid and random suffix keep concurrent seals from colliding. Stripping the path fixes determinism without giving that up.

**Q: Will a pod read a manifest with no `root` correctly?**
According to the description, yes. `_prepare_sealed` fills in `root`, and the raw fallback uses `sealed_root_for` when `root` is absent. That code is not in this diff.

**Q: What about bundles built before this change?**
They still contain `root` and `module`. The description says the pod overrides `root` on normal boot, so those bundles should behave as before. The diff does not test this.

**Q: Could other fields still make packs non-deterministic?**
The diff only removes these two keys. `test_seed_determinism` now bakes a manifest and compares bytes, so any remaining difference would fail it.

**Q: Why did the old determinism test pass?**
Its only file was `svc.jac`, which does not resolve as an entry, so no serve manifest was baked. Renaming the file to `main.jac` fixes that.

**Q: Does `_portable_manifest` change the in-memory manifests used elsewhere?**
No. It builds new dicts, and before this PR the module manifests were shared by reference.

**Q: Does this fix #9138?**
No. #9138 is about failing on the host when the manifest is missing. That work is #9610, which depends on this PR.

**Q: Why does #9610 need this first?**
Its fixtures now bake a serve manifest, so its fat-bundle and seed determinism tests would see the non-deterministic stage paths without this fix.
