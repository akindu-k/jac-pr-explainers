## 1. The short version

`ScaleTieredMemory` is jac-scale's storage layer. Its `commit(anchor)` method writes changed graph data out to storage, and `acommit(anchor)` is the async wrapper around it. Code running inside an async request handler can `await` `acommit()` without blocking the event loop.

**Before this PR, `acommit()` accepted an `anchor` argument but never passed it on: it called `asyncio.to_thread(self.commit)`, so `commit()` always got `None`.** Calling `acommit(some_anchor)` behaved like a plain `acommit()`. It ran a full commit and set the `_committed` flag. A later "safety-net" `acommit()` would then skip its work.

**You now forward the argument (`asyncio.to_thread(self.commit, anchor)`), and the `_committed` short-circuit and flag apply only when `anchor is None`, meaning a full commit.** This is "option 2" from issue #5931. The issue says the bug had no practical impact yet, because no caller in jac-scale passes an anchor to `acommit()`.

`commit(anchor)` itself still ignores the anchor and does a full L1 scan plus `l3.sync()`. @kashmithnisakya flagged this as follow-up work, and you agreed to do it.

**Status:** Merged on 2026-05-12. Approved by @kashmithnisakya. All test checks passed.

## 3. The problem, step by step

### 3.1 The setup

- **Caller**: async code that awaits `mem.acommit(...)`.
- **`ScaleTieredMemory.acommit`**: checks `_committed`, runs `commit` in a thread, then sets `_committed = True`.
- **`ScaleTieredMemory.commit`**: does a full L1 scan and `l3.sync()`, whatever anchor it gets.

### 3.2 What went wrong: the anchor is dropped

```text
1. Caller runs:  await mem.acommit(node_a)          anchor = node_a, _committed = False
2. acommit checks `if self._committed`               False → continue
3. acommit runs asyncio.to_thread(self.commit)       ← WRONG: anchor not passed
4. commit(anchor=None) runs                          sees None, does full L1 scan + l3.sync()
5. acommit sets _committed = True                    ← WRONG: a "partial" call marked as full commit
```

### 3.3 What went wrong: an anchored call after a full commit is skipped

```text
1. Earlier: await mem.acommit()                      full commit, _committed = True
2. Code changes node_b, then: await mem.acommit(node_b)
3. acommit checks `if self._committed`               True → return immediately  ← WRONG
4. commit() is never called for node_b               the caller's explicit request is a silent no-op
```

### 3.4 Why it mattered

- Issue #5931 says the impact today is **"None in practice"**. No call site in jac-scale passes an anchor to `acommit()`.
- It was a "latent footgun": the signature promises something the code does not do. Anyone who later used `acommit(anchor)` as a partial-commit API would get a full commit and a flipped `_committed` flag.
- It also broke the contract of the base `Memory.acommit()`, which does forward the anchor.
- It was found while reviewing PR #5925, the change that added the `_committed` short-circuit.

## 4. The idea of the fix (one sentence)

> **Pass the anchor through, and let only full commits touch the flag.** `acommit` now hands `anchor` to `commit`, and the `_committed` early return and flag update only happen when `anchor is None`.

A commit for one anchor is not a full commit, so it should neither be skipped by a past full commit nor mark the memory as fully committed. This matches option 2 in the issue, which says to "only set `_committed = True` when `anchor is None`".

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/memory_hierarchy.main.impl.jac`: forward the anchor and limit the flag to full commits

```diff
 impl ScaleTieredMemory.acommit(anchor: (Anchor | None) = None) -> None {
     import asyncio;
-    if self._committed {
+    if anchor is None and self._committed {          # NEW: only full commits short-circuit
         return;
     }
-    await asyncio.to_thread(self.commit);
-    self._committed = True;
+    await asyncio.to_thread(self.commit, anchor);    # NEW: anchor forwarded
+    if anchor is None {                               # NEW: only full commits set the flag
+        self._committed = True;
+    }
 }
```

**What:**
1. `acommit()` with no argument works as before. It returns early if a full commit already happened. Otherwise it runs `commit(None)` and sets `_committed = True`.
2. `acommit(x)` always runs `commit(x)` and never reads or writes `_committed`.

**Why:** It fixes both failure cases from 3.2 and 3.3. The anchor is no longer dropped, and anchored calls no longer interact wrongly with the flag.

**Things to notice:**
- The PR description's "AFTER" snippet shows only the `to_thread` change. Its "BEFORE" snippet leaves out the `_committed` lines. The flag logic was added in a later commit (probably 4b34968 "anchor is always forwarded"; the diff per commit is not shown). The final code does more than the description says.
- `commit(anchor)` still ignores `anchor`. So `acommit(x)` today runs a **full** L1 scan plus `l3.sync()` but does **not** set `_committed`. A later safety-net `acommit()` will then run a second full sync. That is correct but redundant. It does not matter yet because no caller passes an anchor.
- The PR description says ignoring `anchor` in `commit()` is intentional and documented in a comment there, and out of scope for this PR.

### 5.2 `docs/docs/community/release_notes/unreleased/jac-scale/5932.bugfix.md`: release note

```diff
+- **Fix: `ScaleTieredMemory.acommit()` now forwards `anchor` argument to `commit()`**: Previously the `anchor` parameter was accepted but silently dropped. ... now forwarded correctly via `asyncio.to_thread(self.commit, anchor)`, matching the contract of the base `Memory.acommit()` interface.
```

**What:** Adds a bugfix entry for the next release.

**Things to notice:** The note does not mention the `_committed` change: anchored calls no longer short-circuit and no longer set the flag. It also does not warn that `commit()` still does a full sync for any anchor.

## 6. How execution flows after the PR

### 6.1 Full async commit: `await mem.acommit()`

```text
acommit(anchor=None)
├─ anchor is None and self._committed?           ← CHANGED (adds anchor check)
│   ├─ yes → return (already fully committed)
│   └─ no  → continue
├─ await asyncio.to_thread(self.commit, None)    ← CHANGED (arg passed explicitly)
│   └─ commit(None): full L1 scan + l3.sync()
└─ anchor is None → self._committed = True       ← CHANGED (now conditional)
```

### 6.2 Anchored async commit: `await mem.acommit(x)`

```text
acommit(anchor=x)
├─ anchor is None and ...?  → False, never short-circuits   ← NEW behaviour
├─ await asyncio.to_thread(self.commit, x)                  ← NEW: x reaches commit
│   └─ commit(x): still full L1 scan + l3.sync() (anchor ignored, unchanged)
└─ anchor is not None → _committed left as is               ← NEW behaviour
```

| Scenario | Before | After |
|---|---|---|
| `acommit()`, flag False | `commit(None)`, flag → True | Same |
| `acommit()`, flag True | Returns early | Same |
| `acommit(x)`, flag False | `commit(None)`, flag → True | `commit(x)`, flag stays False |
| `acommit(x)`, flag True | Returns early, nothing written | `commit(x)` runs, flag stays True |
| What `commit` receives from `acommit(x)` | `None` | `x` |

Users will see no change today, since no jac-scale caller passes an anchor (per #5931). For a future caller of `acommit(x)`, the behaviour is now correct at the `acommit` level, but `commit` still does a full sync.

## 11. Questions your senior might ask

**Q: Why not take option 1 and remove the parameter, as the issue calls simpler and safer?**
A: The base `Memory.acommit()` has an `anchor` parameter and forwards it. Removing it would break the shared interface. Forwarding keeps `ScaleTieredMemory` consistent with its parent.

**Q: Does `acommit(x)` now write only `x`?**
A: No. `commit(x)` still ignores the anchor and does a full L1 scan plus `l3.sync()`. Only the hand-off from `acommit` to `commit` is fixed. Real partial writes are the follow-up @kashmithnisakya described.

**Q: Why not set `_committed` after an anchored call, since it does a full sync anyway?**
A: The flag means "a full commit happened". Tying it to `anchor is None` keeps that meaning correct once `commit(x)` becomes a true single-anchor write. The cost today is one possibly redundant full sync, and only if someone calls `acommit(x)`, which nobody does.

**Q: Could an anchored call now cause a double write?**
A: Yes, in theory: `acommit(x)` does a full sync, then the safety-net `acommit()` does another. No current caller passes an anchor, and `l3.sync()` is described as merge-aware, so this is redundant work rather than corruption. The diff can't confirm the second point.

**Q: Does the test cover the `_committed` change?**
A: Partly. Case 2 runs after case 1 has set the flag, so it proves anchored calls aren't skipped. Nothing checks that anchored calls leave the flag alone.

**Q: How does the test work without MongoDB?**
A: `object.__new__` makes a bare instance with no backends, and `patch.object` replaces `commit` with a function that only records its argument. No real I/O happens.

**Q: Is #5931 really fixed?**
A: The forwarding bug in `acommit` is fixed. The broader goal of single-anchor commits is not, as @kashmithnisakya pointed out. The issue was closed by this PR, and the remaining work is only tracked in your promise of a follow-up.

**Q: Which callers rely on the `_committed` short-circuit?**
A: Per issue #5931, it is the middleware safety-net `acommit()` call. Those calls pass no anchor, so their behaviour is unchanged.
