## 1. The short version

Jac-Scale keeps graph data in three layers. L1 is an in-process cache, L2 is Redis, and L3 is MongoDB, which holds the real copy. Every anchor (a stored node or edge) that gets touched is also written to Redis, so the next read is fast.

The issue (#6864) said these Redis keys never expire. On current `main` that was already untrue, because `redis_default_ttl` defaulted to `3600`. You found the real gap. **Only the Redis that Jac-Scale provisions itself in Kubernetes got a `maxmemory` limit and an eviction policy. Any other Redis (managed, docker-compose, standalone) had no ceiling. Setting `redis_default_ttl = 0` on such a Redis wrote keys that could never expire and never be evicted.**

**Your fix makes the cache bound its own memory.** On connect, and again at most every 5 minutes, it reads the server's `maxmemory` and policy. If they are unbounded, it applies the configured limit with `CONFIG SET`, or logs a warning if the server refuses. All writes now go through one TTL resolver. That resolver only allows "no expiry" when the server evicts all keys. The policy and samples validation moved into shared helpers. A new `redis_enforce_eviction` flag lets operators opt out.

**Status:** Closed without merging. On 2026-08-10 you closed it as obsolete: the Postgres clean-break (#8000, merged as #8002) deleted the whole Redis/Mongo tier, and the branch now conflicts with `main`. CI on the head commit `e1fa175` (2026-07-15) was all green before that.

## 3. The problem, step by step

### 3.1 The setup

- `RedisBackend.put`/`aput` read `redis_default_ttl` with their own fallback of `0`. They called `setex` if the TTL was > 0 and `set` otherwise.
- `KubernetesRedisProvider` validated the eviction policy and samples and configured the Redis it created. That was the only place a memory bound was ever set.
- A Redis the app merely connected to (via `REDIS_URL`) was used exactly as found. A plain `redis:latest` starts with `maxmemory=0` and `noeviction`.

### 3.2 What went wrong: connecting to a Redis you didn't provision

```text
1. Operator runs app with REDIS_URL pointing at a docker-compose redis:latest
   server state: maxmemory=0, policy=noeviction
2. RedisBackend.is_available() pings → redis_available=True
   (no config check at all)
3. put(anchor) → ttl = 3600 → setex(key, 3600, ...)
4. Under steady load, keys are written faster than they expire
   memory ≈ write rate × 3600s, with no ceiling          ← WRONG: no hard bound
5. A traffic spike pushes Redis past host memory → OOM / crash
```

### 3.3 What went wrong: `redis_default_ttl = 0`

```text
1. Operator sets redis_default_ttl = 0 ("let Redis handle eviction")
2. Redis is unprovisioned: maxmemory=0, policy=noeviction
3. put(anchor) → ttl = 0 → set(key, ...)               ← WRONG: key never expires
4. Redis has no eviction, so the key can never leave
5. Every anchor ever touched stays in Redis → unbounded leak
```

### 3.4 What went wrong: validation only on one path

```text
1. Policy allowlist + samples clamp lived only inside KubernetesRedisProvider
2. Your first self-configure path (first commit) called CONFIG SET with the raw value
3. Invalid policy → Redis raises → exception swallowed → Redis left unbounded  ← WRONG
4. maxmemory-samples was never applied on that path
```

Your own description says this was found during the PR and fixed in `bd01633`.

### 3.5 Why it mattered

#6864 flagged `test_redis_memory_leak` as "a genuine reliability concern, not a stale test". Redis running out of memory takes the L2 cache down for every request. You showed the issue's headline (TTL defaults to 0) was out of date. The real exposure was any non-Kubernetes deployment plus the `ttl=0` setting.

## 4. The idea of the fix (one sentence)

> **The cache guarantees its own memory bound.** On connect it checks the Redis server, applies a ceiling and eviction policy if there is none, and never writes a key that can neither expire nor be evicted.

This is the right layer for the fix. A TTL bounds memory only by write rate, while a `maxmemory` ceiling plus eviction is a true bound. Evicting a cache key is harmless because MongoDB still has the data.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/memory/memory_hierarchy.jac`: the memory-bound logic

```diff
+import time;
+import from jaclang.scale.config.config_loader {
+    get_scale_config, normalize_redis_eviction_policy, normalize_redis_eviction_samples
+}
+glob DEFAULT_REDIS_TTL = 3600,
+     REDIS_BOUND_RECHECK_SECONDS = 300;
+
+def _redis_config_value(client, name, fallback) -> str {
+    value = client.config_get(name).get(name, fallback);
+    if isinstance(value, bytes) { value = value.decode(); }
+    return str(value or fallback);
+}
+
+def _evicts_all_keys(maxmemory: int, policy: str) -> bool {
+    return maxmemory > 0 and policy.startswith('allkeys');
+}
+
+def _apply_redis_eviction(client, db_config, cur_max, cur_policy) -> tuple[int, str] {
+    ...normalize policy and samples...
+    # Policy before cap so a partial failure never leaves a cap with noeviction.
+    try { client.config_set('maxmemory-policy', policy); }
+    except Exception as e { logger.debug(...); return (cur_max, cur_policy); }
+    try { client.config_set('maxmemory-samples', samples); } except ... { debug }
+    try { client.config_set('maxmemory', max_memory); } except ... { debug }
+    new_max = int(_redis_config_value(client, 'maxmemory', '0'));      # read back
+    new_policy = _redis_config_value(client, 'maxmemory-policy', 'noeviction');
+    ...
+    return (new_max, new_policy);
+}
+
+def _ensure_redis_memory_bound(client) -> None {
+    now = time.monotonic();
+    last = _process_cache.get('redis_bound_checked_at', 0.0);
+    if last and now - last < REDIS_BOUND_RECHECK_SECONDS { return; }
+    _process_cache['redis_bound_checked_at'] = now;   # throttle BEFORE the work
+    try {
+        ...read maxmemory/policy...
+        bounded = maxmemory > 0 and policy != 'noeviction';
+        if not bounded and db_config.get('redis_enforce_eviction', True) {
+            (maxmemory, policy) = _apply_redis_eviction(...);
+            bounded = ...;
+        }
+        _process_cache['redis_evicts_all_keys'] = _evicts_all_keys(maxmemory, policy);
+        if not bounded { logger.warning("Redis has no memory bound ..."); }
+    } except Exception as e {
+        _process_cache['redis_evicts_all_keys'] = False;   # fail safe
+    }
+}
+
+def _resolve_write_ttl(db_config) -> int {
+    ttl = int(db_config.get('redis_default_ttl', DEFAULT_REDIS_TTL));
+    if ttl > 0 { return ttl; }
+    if _process_cache.get('redis_evicts_all_keys', False) { return 0; }
+    ...warn once (redis_ttl_fallback_warned)...
+    return DEFAULT_REDIS_TTL;
+}
```

**What:** You added four helpers. `_ensure_redis_memory_bound` checks the server and fixes it if needed, at most once per 5 minutes per process. `_apply_redis_eviction` sets policy, then samples, then cap, and reads back what actually took effect. `_resolve_write_ttl` is now the single place that decides the write TTL. `_evicts_all_keys` records whether "no TTL" is safe.

**Why:** These close cases 3.2 and 3.3. Any Redis gets a ceiling, and `ttl=0` is only honoured when every key can be evicted.

**Things to notice:**
- **Why only `allkeys-*` makes `ttl=0` safe:** `volatile-*` policies only evict keys that have a TTL, so a key with no TTL could never leave.
- **The `bounded` check is looser than that.** It counts `volatile-*` as bounded. That is fine because, under `volatile-*`, `_resolve_write_ttl` still forces a TTL.
- **Order of `CONFIG SET`:** policy is set first. If that fails, the function stops before setting a cap. This is the Greptile P2 fix: a cap with `noeviction` would make Redis refuse writes.
- **Readback:** the function trusts what the server reports, not what it asked for. So a silently ignored `CONFIG SET` is still detected.
- **The throttle is set before the work.** A failing or ACL-blocked `CONFIG GET` is retried only after 5 minutes, not on every request.
- **The outer `try`** makes the check unable to raise. That matters because it runs inside `is_available()`.
- **Before the first check**, `redis_evicts_all_keys` is missing and defaults to `False`. So early writes use the safe fallback TTL.
- **Edge case: configured `redis_eviction_policy = 'noeviction'`.** The normalizer accepts it. `_apply_redis_eviction` would then set `noeviction` and a cap. Redis would refuse writes when full, and the check would log "no memory bound". The diff does not show whether `put` catches that write error. The `try` is visible, but not its `except`.
- **Shared Redis:** with `redis_enforce_eviction=true` (the default), the app changes server-wide settings. On a Redis shared with other apps, `allkeys-lru` could evict *their* keys. The only guard is the opt-out flag. Nothing in the PR discusses this.

## 6. How execution flows after the PR

### 6.1 First connect

```text
RedisBackend.is_available()
├─ redis_available not cached
├─ redis_client.ping()
├─ _ensure_redis_memory_bound(client)                         ← NEW
│  ├─ not throttled → set redis_bound_checked_at = now
│  ├─ CONFIG GET maxmemory, maxmemory-policy
│  ├─ bounded? ── yes → record evicts_all_keys
│  │            └─ no and redis_enforce_eviction
│  │               └─ _apply_redis_eviction
│  │                  ├─ CONFIG SET policy (fail → stop, keep old values)
│  │                  ├─ CONFIG SET samples (fail → ignore)
│  │                  ├─ CONFIG SET maxmemory (fail → ignore)
│  │                  └─ CONFIG GET readback → effective values
│  ├─ redis_evicts_all_keys = maxmemory>0 and allkeys-*
│  ├─ still unbounded → logger.warning
│  └─ any exception → redis_evicts_all_keys = False (no raise)
├─ redis_available = True
└─ return True
```

### 6.2 Later availability checks

```text
RedisBackend.is_available()
├─ redis_available cached True
├─ _ensure_redis_memory_bound(client)                         ← NEW
│  ├─ < 300s since last → return immediately
│  └─ ≥ 300s → rerun 6.1's check (re-bounds a restarted Redis)
└─ return True
```

### 6.3 Writing an anchor (`put` / `aput`)

```text
put(anchor)
├─ serialize anchor
├─ ttl = _resolve_write_ttl(db_config)                        ← CHANGED
│  ├─ redis_default_ttl > 0 → that value
│  ├─ == 0 and redis_evicts_all_keys → 0
│  └─ == 0 otherwise → warn once, 3600
├─ ttl > 0 → SETEX
└─ ttl == 0 → SET (only reachable under allkeys-* with cap)
```

### 6.4 Kubernetes provisioning

```text
KubernetesRedisProvider
├─ normalize_redis_eviction_policy(...)                       ← CHANGED (shared helper)
├─ normalize_redis_eviction_samples(...)                      ← CHANGED (shared helper)
└─ rest unchanged
```

| Scenario | Before | After |
|---|---|---|
| Bare `redis:latest`, default config | Keys with TTL 3600, no ceiling | Cache sets 200mb + `allkeys-lru`; keys TTL 3600 |
| Bare Redis, `redis_default_ttl=0` | `SET` without expiry → unbounded leak | Ceiling applied → `allkeys-lru` → `SET` allowed |
| Managed Redis blocking `CONFIG`, `ttl=0` | `SET` without expiry | Warning logged; writes use TTL 3600 |
| Redis with `volatile-lru`, `ttl=0` | `SET` without expiry (never evictable) | Warn once; TTL 3600 |
| Redis restarted (runtime config lost) | n/a | Re-bounded within ~5 min |
| `redis_enforce_eviction=false` on bare Redis | n/a | No `CONFIG SET`; warning; TTL forced if `ttl=0` |
| Invalid `redis_eviction_policy` | K8s: fallback; other path: none | Both paths fall back to `allkeys-lru` |

**Behaviour users would notice:** the app now changes server settings on any Redis it can reach. Also, `redis_default_ttl = 0` is silently turned into 3600 unless the server uses `allkeys-*`. There is a one-time warning, but no error.

## 11. Questions your senior might ask

**Q: The issue said keys have no TTL. Was that true?**
Not on current `main`. `get_default_config` and `get_database_config` already default `redis_default_ttl` to `3600`. The real gap was having no `maxmemory` ceiling outside the Kubernetes provider, plus the `ttl=0` setting.

**Q: Why isn't a TTL enough?**
A TTL bounds memory by write rate times TTL. That number grows with traffic. Only `maxmemory` plus an evicting policy puts a hard ceiling on memory.

**Q: Why allow `ttl=0` only under `allkeys-*`?**
`volatile-*` policies only evict keys that have a TTL. A key written with `SET` and no expiry would be unevictable under them.

**Q: Isn't it risky for an app to `CONFIG SET` a Redis it doesn't own?**
Yes, if the Redis is shared. Setting `allkeys-lru` could evict another app's keys. The PR's only answer is the `redis_enforce_eviction=false` opt-out, and the default is on. Nothing in the PR discusses this trade-off.

**Q: What happens on ElastiCache or Memorystore where `CONFIG` is blocked?**
The check fails inside the outer `try` and `redis_evicts_all_keys` is set to `False`. A debug or warning log is written. Writes use a positive TTL (the configured one, or 3600 as a fallback). The throttle stops retries for 5 minutes.

**Q: Does this slow down every request?**
After the first check, each `is_available()` adds one `time.monotonic()` call and one dict lookup. The real `CONFIG` round-trips happen at most once per 300 s per process.

**Q: What if Redis restarts?**
`CONFIG SET` values are lost unless they were persisted with `CONFIG REWRITE`. The next check after the 300 s window re-applies them. Writes in between still carry the configured TTL.

**Q: Why order the `CONFIG SET` calls policy, then samples, then cap?**
If only the cap were applied, Redis would sit at `noeviction` with a ceiling, and writes would fail at the limit. Setting the policy first, and aborting if that fails, prevents that state.

**Q: Why close instead of rebasing?**
#8002 retired the Redis/Mongo tier entirely. None of the touched Redis files exist on `main`, and no `redis_*` config remains. The sibling fix #7696 was closed for the same reason.
