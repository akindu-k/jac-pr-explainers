## 1. The short version

When a freshly installed `jac` runs for the first time, it unpacks its runtime into a cache folder. It then deletes the older runtime folders ("stale generations") that the new one replaced. Only after that does it run the command the user typed.

**The bug: if any file inside a stale folder refused to delete, `jac` died with an uncaught error before running the user's command.** The new runtime was already in place and usable, so the failure was pointless. The error message also made things worse. Native `rmtree` ignored the return value of `unlink`, so it blamed the parent folder (for example `.../websocket/tests`) instead of the file that was stuck, and it gave no reason. This turned `main` red on `jac-check` and cost CI runs on unrelated PRs.

**The fix: `gc_stale` now wraps each stale-folder removal in `try`/`except` and prints a warning instead of crashing, and native `rmtree` now checks `unlink`, so the error names the stuck file and adds the OS reason.** After the fix, a stuck stale folder prints something like `could not remove it: rmtree: could not remove '.../test_app.py': Permission denied; leaving it for the next run`, and the command runs normally.

**Status:** Closed without merging. @MusabMahmoodh approved on 2026-09-14. On 2026-09-18 you wrote that the PR is superseded by #9246 and that #9053 is closed. Two checks failed on the head commit `320c854`: `jac-check` and the aggregate `Everything Passed`.

|---|---|
| Jac | The programming language in this repo. It compiles to Python ("sv"/server lane), JavaScript ("cl"/client lane), or native machine code ("na" lane). |
| Native backend / "na" lane | The compiler path that turns Jac into machine code (through LLVM JIT in tests). Native code can't simply call Python functions. |
| `na_stdlib` | Jac's own reimplementation of parts of Python's standard library (for example `shutil.jac`) for native code. It calls C functions directly. |
| libc / C function | Low-level OS functions such as `unlink` (delete a file) and `rmdir` (delete an empty folder). They report failure by **returning** `-1`, not by raising. |
| `errno` | A number the OS sets when a C call fails. For example `EACCES` means permission denied. |
| `errno_message()` | Helper from main's `_errno_native.jac`. It turns the current `errno` into readable text such as `Permission denied`, much like C's `strerror`. |
| `shutil.rmtree(path)` | Deletes a folder and everything in it. It empties the folder first (deletes each child), then calls `rmdir` on the folder. **This is where the bug is** (the message part). |
| Fused runtime | The bundled runtime (Python plus libraries) that a distributed `jac` binary carries and unpacks on first run. |
| Runtime cache / generation | Unpacked runtimes live under `<cache>/rt/<name>`, for example `rt/f4ca7e3e22fe2d5d-2796bddb91431b70`. Each folder is one "generation". |
| `keep_key` | The name of the generation that was just unpacked and must stay. |
| Stale generation | An older generation of the same binary that the new one replaced. Nothing reads it again. |
| `materialize.jac` | The file that unpacks the fused runtime on cold start. |
| `gc_stale(cache_dir, keep_key)` | The function in `materialize.jac` that sweeps stale generations. **This is where the bug is** (the crash part). |
| `say(...)` | Prints a `jac:`-prefixed status line during materialization. |
| `.tmp.<pid>` folder | A generation that another process is unpacking right now. The sweep must not touch it. |
| Mode `555` on a folder | Read and execute, no write. On POSIX, deleting a file needs write permission on its **folder**, so files inside a `555` folder can't be deleted. Root ignores this. |
| `uid 0` / root | The superuser. Mode bits don't stop root, so these tests skip under root. |
| Equivalence test (`run_with_both`) | Runs the same fixture through several lanes and checks that they return the same dict. |
| `jac.toml` (fixtures) | Maps fixture functions to a lane, for example `"prim_shutil._locked_error_na" = "native"`. |
| `compile_native` / `get_func` | Test helpers in `tests.support`. They JIT-compile a Jac file and fetch a callable for a function in it. |
| `_stage_fused_runtime` | Helper from the desktop builder that lays the fused runtime source next to a work folder so it can be compiled. |
| E1053 | A Jac type-checker error. It hit an earlier version of the new test at `ctypes.CFUNCTYPE(ctypes.c_int64)`. |

## 3. The problem, step by step

### 3.1 The setup

- **`materialize.jac`** unpacks the runtime on first run and then calls `gc_stale` to delete stale generations.
- **`gc_stale`** loops over `<cache>/rt/*`. It skips `keep_key`, other binaries' generations and in-flight `.tmp.*` folders. For each stale one it calls `shutil.rmtree(full)` with no guard. The skip rules are in parts of `gc_stale` the diff doesn't show. The issue describes them as "`name != keep_key`, same path hash".
- **Native `shutil.rmtree`** recurses into subfolders, calls `unlink` on files, then `rmdir` on the folder.

### 3.2 What went wrong: the crash

```text
1. jac starts, cache holds stale generation  rt/f4ca...-2796...
2. extract new runtime into rt/<new>            -> OK
3. publish rt/<new> as ready                    -> OK (runtime usable now)
4. gc_stale: say("removing stale runtime rt/f4ca...")
5. shutil.rmtree(rt/f4ca...) raises ValueError  -> not caught          <-- WRONG
6. "Uncaught exception: rmtree: could not remove '...'"; exit 1
7. user's command never runs
```

### 3.3 What went wrong: the misleading message

```text
1. rmtree(.../websocket/tests)
2.   child test_app.py is a file -> unlink() returns -1 (EACCES)
3.   return value discarded; loop continues                          <-- WRONG
4.   loop ends; folder still holds test_app.py
5.   rmdir(.../websocket/tests) returns -1 (ENOTEMPTY)
6.   raise "rmtree: could not remove '.../websocket/tests'"         <-- names parent, no reason
```

### 3.4 Why it mattered

- `main` went red on `jac-check` at `9b02a4b2d9`. The preceding commit was green on the same job, so the failure depended on which cache `actions/cache/restore` handed the job, not on any diff.
- The issue says it "cost a cycle on #9045 and on #8175 this week". People re-ran jobs or went hunting through innocent PRs.
- Any machine with a stale generation was exposed, including local developer caches, not just CI.
- The CI logs named directories and stopped there, so nobody could tell which file was stuck or why. The issue author left that question open ("permissions from the cache restore, or a concurrent reader").

## 4. The idea of the fix (one sentence)

> **Cleanup of garbage must not be fatal, and errors must name the real culprit.** `gc_stale` catches and warns on each failed removal, and `rmtree` raises at the failing `unlink` with the OS reason attached.

This is the right line to draw because the sweep runs strictly after the new runtime is published. Every folder it touches is already garbage, so a failure costs disk space, not correctness. The `rmtree` change keeps strict behaviour for callers that really need the delete to succeed. It only makes the error accurate.

## 5. Every code change, explained

### 5.1 `jac/jaclang/dist/fused/materialize.jac`: make the stale sweep best effort

```diff
         say(f"  removing stale runtime {full}...");
-        shutil.rmtree(full);
+        try {
+            shutil.rmtree(full);
+        } except Exception as e {
+            say(f"  could not remove it: {e}; leaving it for the next run");   # NEW: warn, keep looping
+        }
     }
 }
```

**What:** If removing one stale generation raises, `gc_stale` prints the error and moves on to the next generation.

**Why:** This fixes the crash (3.2). The user's command now runs.

**Things to notice:**
- Only the `rmtree` call is guarded. The skip rules and the extraction stay strict.
- It catches any `Exception`, not just `ValueError`. That is deliberate: anything that goes wrong while deleting garbage is harmless.
- The next run retries the leftover folder, because it is still stale.

### 5.2 `jac/jaclang/runtime/na_stdlib/shutil.jac`: check `unlink`, add the OS reason

```diff
 import from _directory_native { directory_names }
+import from _errno_native { errno_message }          # NEW: reuse main's helper
 ...
         if os.path.isdir(child) {
             rmtree(child);
-        } else {
-            unlink(child);                             # OLD: result thrown away
+        } elif unlink(child) != 0 {                    # NEW: check it
+            raise ValueError(f"rmtree: could not remove '{child}': {errno_message()}");
         }
     }
     if rmdir(path) != 0 {
-        raise ValueError(f"rmtree: could not remove '{path}'");
+        raise ValueError(f"rmtree: could not remove '{path}': {errno_message()}");
     }
```

**What:** A file that won't unlink now raises immediately. The error names that file and includes text such as `Permission denied`. A failing `rmdir` also includes the reason.

**Why:** This fixes the misleading message (3.3).

**Things to notice:**
- `errno_message()` is called right after the failing C call, with nothing in between that could overwrite `errno`.
- The import uses main's existing `_errno_native.jac`. Earlier versions of this PR added their own `_errno_native.jac` and a `.darwin.jac` variant. Both reviewers flagged that. The merges from main removed it, so the final diff has no errno file of its own.
- **Behaviour change:** `rmtree` now stops at the first stuck file. The old loop deleted every other file before failing at `rmdir`. A stuck generation now reclaims less space. Your description lists this as "Partial reclamation", and @MusabMahmoodh noted it as a follow-up.
- `move` still ignores its own `unlink` result. That is deliberate and listed as out of scope.
- The error type is still `ValueError`, not CPython's `OSError`. That is an existing, documented divergence.

### 5.3 `jac/jaclang/runtime/na_stdlib/README.md`: document the diagnostic

```diff
   rather than CPython's `OSError` subclasses.
+  `rmtree` checks every `unlink`, so the error carries the path that actually failed plus the `strerror` text: an un-unlinkable child names that child, not the parent whose `rmdir` failed in consequence.
```

**What / Why:** This records the new error contract next to the existing divergence notes.

## 6. How execution flows after the PR

### 6.1 Cold start of `jac`

```text
jac <command>
├─ materialize: extract fused runtime -> rt/<keep_key>
├─ publish rt/<keep_key>
├─ gc_stale(cache_dir, keep_key)
│  └─ for each name in rt/
│     ├─ skip keep_key / other binary / *.tmp.*
│     ├─ say("removing stale runtime ...")
│     └─ try shutil.rmtree(full)                       ← CHANGED (guarded)
│        └─ except: say("could not remove it: ...; leaving it for the next run")  ← NEW
└─ run <command>                                        (now always reached)
```

### 6.2 Native `rmtree(path)`

```text
rmtree(path)
├─ for nm in directory_names(path)
│  ├─ child is dir  -> rmtree(child)
│  └─ child is file -> unlink(child)
│     └─ != 0 -> raise "could not remove '<child>': <errno text>"   ← NEW
└─ rmdir(path) != 0 -> raise "could not remove '<path>': <errno text>"  ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| Stale generation deletes cleanly | Deleted, command runs | Same |
| Stale generation has an un-unlinkable file | Uncaught exception, exit 1, command never runs | Warning printed, command runs, folder stays for next run |
| Second stale generation after a stuck one | Never reached | Still deleted |
| Native `rmtree` on a folder holding a stuck file | Error names the parent, no reason | Error names the file plus `Permission denied` |
| Native `rmtree` with a stuck file among others | Deletes the others, then fails | Stops at the stuck file, keeps the rest |

Users will notice two things: a new warning line on cold start, and more precise `rmtree` errors.

### 7.1 `jac/tests/dist/test_materialize.jac` (new)

**Setup:**
1. It seeds `/tmp/jac_gc_stale_probe/rt/` with five generations, each holding `pinned.py`. "Locked" generations get mode `555`.
2. It stages the fused runtime with `_stage_fused_runtime` into a temp work folder.
3. It writes a probe `gc_probe.jac` whose `sweep()` calls `gc_stale(_CACHE, _KEEP)` and returns `1`.
4. It compiles the probe natively with `compile_native`, runs `jac_entry` if present, and calls `sweep`.

**Checks:** `sweep() == 1`, which means the process didn't abort. It also checks which generation folders survive:

| Generation | Locked | Survives | What it proves |
|---|---|---|---|
| `2222…-aaaa…` | yes | yes | The crash case: no abort, folder stays |
| `3333…-aaaa…` | no | no | The sweep keeps working after a failure. A "swallow everything" fix would fail here. |
| `2222…-bbbb…` | no | yes | Another binary's generations are untouched |
| `4444…-aaaa….tmp.4242` | no | yes | In-flight extraction is untouched |
| `1111…-aaaa…` (`_KEEP`) | no | yes | The live generation survives |

Before the fix, the test process dies with SIGABRT (exit 134), according to the description. It skips under root, and `finally` restores the mode bits and deletes everything. Commit `9597ad2` turned the generations into this table. Using `compile_native`/`get_func` instead of a hand-written `ctypes.CFUNCTYPE` avoids the E1053 error @christianwilkins hit.

Note that `_CACHE` is a fixed `/tmp` path. Two runs on the same machine at the same time could collide.

### 7.2 `jac/jaclang/compiler/tests/fixtures/prim_shutil.jac`

- It adds `_locked_error_py` and `_locked_error_na`. Each makes a folder containing `pinned.txt`, runs `chmod 555`, tries `rmtree`, captures the error text, and restores `755`.
- The two helpers are identical in body. They are written once per lane because a plain `def` is a Python symbol that native code could only reach through the JIT interop bridge.
- They use `os.system("chmod ...")` rather than `os.chmod`. The diff doesn't say why. Possibly native `os` has no `chmod`, but that can't be confirmed from the PR.
- Both `shutil_py` and `shutil_na` gain `locked_rmtree_raised` and `locked_dir_kept`. Both lanes must report `1`/`1`.
- The new `locked_error_names_file_na()` returns `1` if the native error contains `pinned.txt`.

### 7.3 `jac/jaclang/compiler/tests/test_prim_equivalence.jac`

- `bundled shutil` still runs `run_with_both` first, which now includes the two new rows.
- It then skips under root and compiles the fixture natively. It asserts `locked_error_names_file_na() == 1` with the message `"rmtree must report the file it could not unlink, not its parent"`.
- This check is native-only because CPython words its error differently.
- The test was extended rather than duplicated, per your description.
- Under root, the equivalence rows still agree: both lanes report `0`/`0` because root deletes the folder.

## 11. Questions your senior might ask

**Q: Why is it safe to swallow errors in `gc_stale`?**
The sweep runs only after the new runtime is extracted and published, and it only touches generations it has already judged stale. A failure leaves garbage on disk; it can't affect what `jac` runs.

**Q: Could the `try`/`except` hide a real bug, like deleting the wrong folder?**
No. Only the `rmtree` call is wrapped, and the skip rules are unchanged. The test checks that the live generation, other binaries' generations and `.tmp.*` folders survive, and that an ordinary stale generation is still deleted.

**Q: Why catch `Exception` instead of `ValueError`?**
Any failure while deleting garbage is harmless. Native `rmtree` raises `ValueError` today, but the guard shouldn't depend on that detail.

**Q: Does the stricter `rmtree` change behaviour for other callers?**
Yes, slightly. It now stops at the first file it can't unlink instead of deleting the rest and then failing. It still raises in both versions, so callers that need success see an error either way, now with the right path.

**Q: Why not fix `move`'s unchecked `unlink` too?**
Checking it would turn a completed copy into a failure over a leftover source file. That is a behaviour change that deserves its own PR and its own equivalence row.

**Q: Why do the tests skip under root?**
Root ignores the folder's write bit, so the "undeletable" file would delete. The assertions would then prove nothing.

**Q: Why is the file-name check native-only?**
CPython's `shutil.rmtree` words its error differently, so comparing the text across lanes would fail for a reason that isn't a bug.

**Q: What happened with the errno module conflict?**
#9022 landed `_errno_native.jac` on main the same day this PR opened. Your version lacked `clear_errno` and `raise_os_error`, which `_directory_native` imports. The merges from main dropped your copy, and `shutil.jac` now imports `errno_message` from main's module.

**Q: Why did `jac-check` fail on the head?**
The data here doesn't say. Someone would need to read that job's log to know whether it was this issue, a different flake, or something on main.

**Q: What did #9246 not carry over, and does it matter?**
It doesn't include the OS reason in `rmtree` errors or the warning when a generation can't be removed. Without them, the next stuck generation is silent and its cause harder to find. That is a small follow-up.
