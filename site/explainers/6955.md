## 1. The short version

jac-scale stores user passwords as bcrypt hashes. Every time a jac-scale server starts, it hashes two fixed credentials: the bootstrap admin user and the internal guest user. Before this PR, `IdentityStorage.hash_password` always called `bcrypt.gensalt()` with no arguments, so it always used bcrypt's default work factor of 12.

**The in-process test suite boots a fresh server for every test, so every test paid about 1.5 s of bcrypt hashing for two throwaway credentials.** Profiling showed this was most of each roughly 1.8 s boot.

**You added a `password_hash_rounds` auth setting (default 12) and a `JAC_SCALE_BCRYPT_ROUNDS` environment variable that overrides it. Both are clamped to bcrypt's valid range of 4 to 31. The in-process test client sets the env var to `4`.** Production behaviour does not change. On CI, `test_admin.jac` went from 64.66 s to 43.40 s with all 29 tests passing. One isolated boot-and-login cycle went from about 1680 ms to about 200 ms.

**Status:** Merged on 2026-07-13. The only review activity came from the Greptile bot, and its one suggestion was addressed. No human review is visible in the PR data. All CI checks on `be5df90` passed or were skipped.

| Jac | The programming language in this repo. `.jac` files hold code. `impl` blocks hold function bodies, and the matching `.jac` file holds the declarations. |
| `.jac` / `.impl.jac` split | Declarations such as `def resolve_password_hash_rounds(...) -> int;` live in `config_loader.jac`. The bodies live in `impl/config_loader.impl.jac`. |
| `with entry { ... }` | A Jac block that runs once when the module is loaded, like top-level code in Python. |

| bcrypt | A password-hashing algorithm. It is slow on purpose, so attackers can't guess passwords quickly. |
| Work factor / rounds / cost | bcrypt's slowness knob. The work is 2^rounds, so each +1 doubles the time. 12 is the library default. 4 is the minimum and is about 256× cheaper than 12. The valid range is 4 to 31. |
| Salt / `bcrypt.gensalt(rounds=...)` | Random data mixed into each hash. `gensalt` creates it and also encodes the work factor into it. |
| `bcrypt.hashpw` | Hashes a password with a given salt. The result string records the cost, e.g. `$2b$12$...`. |
| `IdentityStorage.hash_password` | jac-scale's function that turns a plain password into a stored hash. **This is where the bug is.** It always used the default cost. |
| Bootstrap admin / internal guest user | Two accounts that every server creates at startup. Their passwords are hashed during boot. |
| Auth config | The `auth` section of jac-scale's configuration, read through `JacScaleConfig.get_auth_config()`. |
| `get_scale_config()` | Returns the shared `JacScaleConfig` object. |
| `get_default_config()` | Holds the built-in defaults that are used when a project doesn't set a key. |
| `password_hash_rounds` | The new auth setting that holds the bcrypt cost. Default 12. **This is what the PR adds.** |
| `JAC_SCALE_BCRYPT_ROUNDS` | The new environment variable. When set, it wins over the config value. Example: `JAC_SCALE_BCRYPT_ROUNDS=10`. |
| `resolve_password_hash_rounds` | The new helper. It picks the env value or the config value, checks that it is an integer, and clamps it to 4..31. |
| Clamping | Forcing a value into a range: `max(4, min(31, x))`. So 2 becomes 4 and 50 becomes 31. |
| `os.environ.setdefault(k, v)` | Sets an environment variable only if it isn't already set. |
| `make_client` / `ScaleTestClient` | The in-process test helper. It boots a jac-scale app inside the test process, without a real port, for each test. |
| In-process vs subprocess tests | In-process tests boot the app inside pytest. Subprocess tests run `jac start` as a separate process with a real port. This PR mainly speeds up in-process tests. |

## 3. The problem, step by step

### 3.1 The setup

- **`IdentityStorage.hash_password`** hashed every password with `bcrypt.gensalt()`, so cost was always 12.
- **Server boot** hashes two fixed passwords: the admin and the guest user.
- **Test suite**: `make_client` builds a brand-new server per test. This is good for isolation and expensive for boot cost.
- **Config**: the `auth` config had no setting for hashing cost.

### 3.2 What went wrong

```text
1. Test N starts                        → make_client("test_api.jac")
2. New server boots                     → creates bootstrap admin
3. hash_password(admin_pw)              → bcrypt.gensalt() → cost 12 → ~0.75s
4. Server creates internal guest user
5. hash_password(guest_pw)              → cost 12 → ~0.75s
6. Boot done                            → ~1.5s of ~1.8s spent on step 3 + 5   ← WRONG: production-grade cost for throwaway test credentials
7. Test runs its actual assertions      → fast
8. Test N+1 starts                      → back to step 1, pay ~1.5s again
```

There was also no way to tune the cost in production. Anyone who wanted 13 or 14 rounds on fast hardware couldn't set it.

### 3.3 Why it mattered

- Issue #6956 reports that the jac-scale server test group took about **7m47s**. `test_admin.jac` alone took 101.7 s. For contrast, `test_sso.jac` runs 51 tests in 4.4 s because it doesn't boot a server.
- The issue names the per-boot rehash as root cause #1. It is part of an umbrella effort to get the server group "well under ~2m".
- Slow tests slow down CI for every contributor touching jac-scale.

## 4. The idea of the fix (one sentence)

> **Make bcrypt's cost a setting, and turn it down only in tests.** Read the work factor from config or an env var, keep 12 as the default, and have the test client set it to the minimum of 4.

This is the right idea because it removes the waste without weakening production or sharing state between tests. Each test still gets its own fresh server. It also gives real deployments a tuning knob they may want anyway.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/config/impl/config_loader.impl.jac`: add the setting and its resolver

```diff
             'token_collection': 'auth_tokens'
+            'token_collection': 'auth_tokens',
+            'password_hash_rounds': 12            # NEW: secure default = bcrypt's own default
         },
...
+impl resolve_password_hash_rounds(configured_rounds: int) -> int {
+    env_val = os.environ.get('JAC_SCALE_BCRYPT_ROUNDS');
+    if not env_val {
+        return max(4, min(31, configured_rounds));      # no env → use config, clamped
+    }
+    try {
+        rounds = int(env_val);
+    } except ValueError as e {
+        raise ValueError(
+            f"JAC_SCALE_BCRYPT_ROUNDS must be an integer in 4..31, got: {env_val!r}"
+        ) from e;                                       # NEW in da746d5: clear error
+    }
+    return max(4, min(31, rounds));                     # env wins, clamped
+}
...
         'token_collection': auth_config.get('token_collection', 'auth_tokens'),
+        'password_hash_rounds': resolve_password_hash_rounds(
+            int(auth_config.get('password_hash_rounds', 12))
+        ),
```

**What:**
- The defaults now include `password_hash_rounds: 12`.
- `get_auth_config()` returns a resolved `password_hash_rounds`. The value comes from the env var if it is set and non-empty, otherwise from the config. Either way it is clamped to 4..31.

**Why:** This gives one place that decides the bcrypt cost, so `hash_password` can read it.

**Things to notice:**
- **Precedence:** the env var beats the config file. An empty string (`JAC_SCALE_BCRYPT_ROUNDS=`) counts as "not set" because `not ""` is true.
- **Out-of-range values are clamped silently, not rejected.** The error message says "must be an integer in 4..31". However, `JAC_SCALE_BCRYPT_ROUNDS=99` doesn't raise; it quietly becomes 31. So the message slightly overstates the check.
- **Cost 31 is extremely slow.** Each step doubles the time, so a single hash at 31 would take a very long time. Clamping to 31 is technically "valid" for bcrypt but not practical. Nothing warns about high values.
- **A non-integer value in the config file** (not the env) goes through the bare `int(...)` in `get_auth_config`. It would raise a plain `ValueError` without the friendly message. Only the env path got the clear error.
- **The `os` import:** this file uses `os`, but the diff shown doesn't add an `import os` to `config_loader.jac`. Commit `2474034` "imported os" exists. Either `os` was already imported, or that commit's change is net-zero against `main` in the final diff. This can't be confirmed from the diff alone.

### 5.2 `jac/jaclang/scale/config/config_loader.jac`: declare the helper

```diff
+"""Resolve the bcrypt work factor from env override or config, clamped to bcrypt's valid 4..31 range."""
+def resolve_password_hash_rounds(configured_rounds: int) -> int;
```

**What:** This is the public declaration and docstring for the new function. Its body is in 5.1.

**Why:** This follows Jac's split between declaration (`.jac`) and implementation (`.impl.jac`).

### 5.3 `jac/jaclang/scale/identity/identity_storage.jac` + `impl/identity_storage.impl.jac`: use the setting when hashing

```diff
+import from jaclang.scale.config.config_loader { get_scale_config }
```

```diff
 impl IdentityStorage.hash_password(password: str) -> str {
+    rounds = get_scale_config().get_auth_config()['password_hash_rounds'];
     return str(
-        bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt()).decode('utf-8')          # OLD: always cost 12
+        bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt(rounds=rounds)).decode(     # NEW: configured cost
+            'utf-8'
+        )
     );
 }
```

**What:** Every password hash now uses the resolved work factor.

**Why:** This is the actual fix. It is the one line where cost was hard-coded to the library default.

**Things to notice:**
- **Config is read on every hash.** `get_auth_config()` calls `self.load()` and re-reads the env var each time. Whether `load()` is cached isn't visible in this diff. Either way, this cost is tiny next to a bcrypt hash.
- **Existing hashes still verify.** A bcrypt hash string records its own cost (`$2b$12$...`), and bcrypt's check function reads it from there. So lowering or raising the setting doesn't break old passwords. The verify function isn't in this diff, so this relies on standard bcrypt behaviour.
- **Upgrading old hashes is out of scope.** Changing the setting doesn't re-hash old passwords to the new cost. The PR doesn't add that.
- **New import edge:** `identity_storage` now imports from `config_loader`. Whether this creates any import cycle can't be checked from the diff. CI passed, which suggests not.

### 5.4 `jac/jaclang/scale/tests/scale_test_client.jac`: tests opt into minimum cost

```diff
+import os;
...
+# Hash throwaway fixture credentials at minimum bcrypt cost so it does not dominate test time.
+with entry {
+    os.environ.setdefault('JAC_SCALE_BCRYPT_ROUNDS', '4');
+}
```

**What:** When the test-client module is first loaded, it sets the env var to `4` unless something already set it.

**Why:** This is how the test suite gets the speedup without touching production defaults.

**Things to notice:**
- **`setdefault` is deliberate.** A developer or CI job can still run tests at a real cost, e.g. `JAC_SCALE_BCRYPT_ROUNDS=12 pytest ...`.
- **The env var is process-wide.** It affects everything in that pytest process after import. Child processes started afterwards inherit it, so subprocess `jac start` servers in the same session may also hash at cost 4. That depends on test import order, which isn't visible here.
- This is a test helper, not a test, so it is listed here. Section 7 covers tests.

## 6. How execution flows after the PR

### 6.1 Server boot hashing bootstrap credentials

```text
Server boot
├─ create bootstrap admin
│  └─ IdentityStorage.hash_password(pw)
│     ├─ get_scale_config().get_auth_config()                       ← CHANGED (now includes password_hash_rounds)
│     │  └─ resolve_password_hash_rounds(int(config or 12))         ← NEW
│     │     ├─ JAC_SCALE_BCRYPT_ROUNDS set?  → int() → clamp 4..31  ← NEW
│     │     │   └─ not an int → ValueError "JAC_SCALE_BCRYPT_ROUNDS must be..."  ← NEW
│     │     └─ not set      → clamp(config value) 4..31            ← NEW
│     ├─ bcrypt.gensalt(rounds=rounds)                              ← CHANGED
│     └─ bcrypt.hashpw(...) → "$2b$<rounds>$..."
└─ create internal guest user → same path
```

The same path runs for every user registration and password change, not just at boot.

### 6.2 Test run

```text
pytest imports test file
├─ imports scale_test_client
│  └─ with entry: os.environ.setdefault('JAC_SCALE_BCRYPT_ROUNDS','4')   ← NEW
└─ each test: make_client(...)
   └─ fresh server boot → 6.1 with rounds = 4 → ~ms instead of ~1.5s   ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| Production, nothing configured | cost 12 | cost 12 (unchanged) |
| Config `password_hash_rounds = 14` | ignored, cost 12 | cost 14 |
| Env `JAC_SCALE_BCRYPT_ROUNDS=10` | ignored, cost 12 | cost 10 (beats config) |
| Env `=2` or `=50` | ignored | clamped to 4 / 31, no error |
| Env `=fast` | ignored | server fails with clear `ValueError` |
| Env set to empty string | ignored | treated as unset |
| In-process tests | cost 12, ~1.5 s per boot | cost 4 |
| Existing stored hashes | verify fine | still verify fine (cost is stored in the hash) |

**User-visible behaviour change:** none by default. The only new failure mode is a typo in `JAC_SCALE_BCRYPT_ROUNDS`, which now stops startup with a clear message.

## 11. Questions your senior might ask

**Q: Does this weaken production password security?**
No. The default stays 12, which is the same as `bcrypt.gensalt()`'s built-in default. Only an explicit config value or env var lowers it. The test client is the only place that sets it to 4.

**Q: If someone changes the rounds, do existing users' passwords stop working?**
No. bcrypt stores the cost inside each hash (`$2b$12$...`), and verification reads it from there. Old hashes keep their old cost until the password is changed. No rehash-on-login was added.

**Q: Which wins, the config file or the env var?**
The env var, when it is non-empty. Otherwise the config value is used, or 12 if it is unset. Both are clamped to 4..31.

**Q: What happens with `JAC_SCALE_BCRYPT_ROUNDS=2` or `=40`?**
It is silently clamped to 4 or 31. Only a non-integer like `fast` raises an error. That error message says "must be an integer in 4..31", which is a bit misleading for out-of-range values.

**Q: Why an env var in the test client instead of setting it in the fixture's config?**
`setdefault` at import time covers every `make_client` boot with one line, and a developer can still override it to test at real cost. The trade-off is that it affects the whole pytest process, and any subprocesses started from it inherit it.

**Q: Does per-test isolation still hold?**
Yes. Each test still boots its own fresh server. Only the hashing cost changed, and no state is shared.

**Q: Why is the file-level speedup (~33%) much smaller than the boot speedup (~8.5×)?**
Per your description, the rest of `test_admin.jac` time is dominated by two heavy `jac build` subprocess tests, which this PR doesn't touch.

**Q: Is reading config on every `hash_password` call a cost concern?**
Not compared to bcrypt itself. Whether `load()` caches the config isn't visible in this diff.

**Q: Where are the tests for the new resolver?**
There aren't any. The PR only relies on existing suites passing. Adding focused unit tests is a reasonable follow-up.

**Q: What's left for issue #6956?**
Root cause #2: subprocess tests wipe the `.jac/` compile cache before each spawn and cold-compile every time. The issue also lists sharing a server across read-only tests, moving non-port tests in-process, and trimming fixed sleeps. None of these are in this PR.
