## 1. The short version

Jac's native backend compiles `.na.jac` files to machine code through LLVM (a compiler toolkit). Native code often talks to C libraries, and those libraries hand back raw pointers to memory. Jac code needs to read and write that memory, as C does with `p[i]`.

**Before this PR, `p[i]` on a pointer did not compile in either direction.** A write such as `p[0] = 255;` failed with `Native pathway does not yet support subscript assignment 'p'`. A read such as `v: int = p[0];` failed with `Native pathway does not yet support subscript/index access 'p'` and `Cannot assign <Unknown> to int`. People had to write small C "shim" functions such as `shim_write16` and `shim_read16` to touch the memory. Your PR description adds one more point: on `main`, `ptr` was not defined at all, so every use gave `E2018: Undefined name 'ptr'`.

**The PR adds `ptr[T]` as a generic pointer type that lowers to an LLVM `T*`.** `p[i]` reads become "compute address, then load". `p[i] = v` writes become "compute address, then store". The type checker learns that `p[i]` has type `T`, so it is no longer `<Unknown>`.

**Status:** Closed while still a draft, with no reviews and no comments. One check failed on the head commit `8c18b81` (`jac-check`). All other checks passed. Both linked issues (#6707, #6708) show as closed. The PR itself was never marked ready, so it is not clear from this data what closed them.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac Native / `.na.jac` | Jac code compiled to machine code instead of running on Python. Files end in `.na.jac`. |
| `jac nacompile` | The CLI command that compiles native Jac. The issues use it to reproduce the bug. |
| LLVM | A compiler toolkit. The native backend produces LLVM IR (a low-level program form) and LLVM turns it into machine code. |
| `ir.` (llvmlite) | The Python library that builds LLVM IR. `ir.IntType(8)` is an 8-bit integer type. `.as_pointer()` makes a pointer to that type. |
| FFI | "Foreign function interface": calling C functions from Jac, e.g. `import from .some_lib { def alloc(n: i32) -> ptr; }`. |
| C shim | A tiny C function written only so Jac can do something it can't do itself. The issues needed `shim_write16`/`shim_read16`. |
| Raw pointer | A memory address with no safety checks. `T*` in C means "address of a `T`". |
| `ptr[T]` | The new Jac type: a pointer whose elements are type `T`. Example: `ptr[i64]` is C's `int64_t*`. **This is what the PR adds.** |
| Bare `ptr` | `ptr` without `[T]`. This PR treats it as `i8*`, i.e. a byte pointer. |
| Element type / stride | The type each slot holds, and how far apart slots are. For `ptr[i64]` the stride is 8 bytes, so `p[3]` is at byte offset 24. |
| GEP (`getelementptr`) | The LLVM instruction that computes `base + i * sizeof(T)`. It only computes an address. It does not read memory. |
| load / store | LLVM instructions that read a value from an address or write one to it. |
| Type stub (`na_builtins.pyi`) | A Python-style declarations file the type checker reads to learn the native built-in types. It has no real code. |
| `Generic[_T]`, `__getitem__`, `__setitem__` | Python typing tools. `Generic[_T]` makes `ptr[i64]` valid. `__getitem__` describes the type of `p[i]`. `__setitem__` describes the type of `p[i] = v`. |
| `<Unknown>` / `E2018` | Type-checker results. `<Unknown>` means "couldn't work out the type". `E2018` is the "undefined name" error. |
| `NaIRGenPass` | The compiler pass that turns the Jac syntax tree into LLVM IR. It is declared in `na_ir_gen_pass.jac`, and its methods live in `na_ir_gen_pass.impl/*.impl.jac`. |
| `uni.AtomTrailer` | The syntax-tree node for `target[...]` or `target.attr`. `nd.is_attr` is false for subscripts. `nd.right.slices` holds the index. |
| `_lower_type` / `_lower_class_type` | Methods that turn a checked Jac type into an LLVM type ("lowering"). |
| `expr.type.mangle()` | Gives a type as a string, e.g. `"ptr[i64]"`. The new code uses it to detect pointers. |
| `_coerce_type` | An existing helper that converts a value to a target LLVM type, e.g. `i32` to `i64`. Its exact rules (sign-extend or zero-extend, truncate) are not shown in the diff. |
| ctypes | Python's C-interop library. The test uses it to make a C buffer and call the compiled functions. |

## 3. The problem, step by step

### 3.1 The setup

- **Type checker**: reads `na_builtins.pyi` to learn which names exist in native code. Before the PR, the stub's `__all__` listed `File`, `BinaryFile`, `open`, `Iterable`, `Iterator`, `iter`, `next`, but no `ptr`.
- **Type lowering** (`types.impl.jac`): maps Jac types to LLVM types. It had cases for `list`, iterators and others, but none for `ptr`.
- **Subscript read** (`_codegen_atom_trailer` in `expr.impl.jac`): handles `x[i]` for lists and dicts.
- **Subscript write** (`_codegen_assignment` in `stmt.impl.jac`): handles `x[i] = v` for lists and dicts.

### 3.2 What went wrong: subscript write (#6707)

```text
1. Source:      p: ptr = alloc(4);  p[0] = 255;
2. Type check:  "ptr" not in stub → E2018 Undefined name 'ptr'
                (per the PR description; the issue says ptr worked as an FFI type, see 3.4)
3. Codegen:     _codegen_assignment sees target `p[0]`
4. Dispatch:    tries dict path, list path … none matches a pointer
5. ✗ Result:    "Native pathway does not yet support subscript assignment 'p'"
6. Workaround:  call C shim_write16(p, 0, 255)
```

### 3.3 What went wrong: subscript read (#6708)

```text
1. Source:      v: int = p[0];
2. Type check:  no __getitem__ known for p → type of p[0] = <Unknown>
3. ✗ Type err:  "Cannot assign <Unknown> to int"
4. Codegen:     _codegen_atom_trailer index branch → list/dict checks fail
5. ✗ Result:    "Native pathway does not yet support subscript/index access 'p'"
6. Workaround:  call C shim_read16(p, 0)
```

### 3.4 A disagreement in the inputs

The issues say `ptr` "is otherwise fully functional: it compiles as FFI return/param". Your PR description says that on `main`, `ptr` gave `E2018: Undefined name 'ptr'` everywhere. Both can't be fully true for the same code. The data here can't settle it: maybe the reporter's branch was different, or FFI declarations are handled another way. Expect this question.

### 3.5 Why it mattered

The reporter found this while porting `opentui_helpers.c` (an OpenTUI C bridge) to Jac Native. Each pointer access needed a C helper, which "forces C code into what should be pure Jac NA". The goal of native Jac is to avoid that.

## 4. The idea of the fix (one sentence)

> **Make the pointer's element type part of its type.** `ptr[T]` becomes an LLVM `T*`, so `p[i]` is just GEP plus load or store, with the width and stride taken from `T`.

LLVM's GEP already scales the index by `sizeof(T)`. Once the pointer has the right pointee type, there is no guessing of element width and no casting. Putting `T` in the stub's `Generic[_T]` also gives the type checker the result type for free.

## 5. Every code change, explained

### 5.1 `jac/jaclang/compiler/type_system/na_builtins.pyi`: defines the `ptr` type for the checker

```diff
-from typing import Literal, Protocol, TypeVar, overload
+from typing import Generic, Literal, Protocol, TypeVar, overload
-__all__ = ["File", "BinaryFile", "open", "Iterable", "Iterator", "iter", "next"]
+__all__ = [ ..., "next", "ptr", ]                      # NEW: export ptr
+class ptr(Generic[_T]):  # noqa: N801
+    def __getitem__(self, index: int) -> _T: ...       # NEW: p[i] has type T
+    def __setitem__(self, index: int, value: _T) -> None: ...   # NEW: p[i] = T
```

- **What:** Declares a generic class `ptr`. Reading `p[i]` gives a `T`. Writing `p[i] = v` requires `v` to be a `T`.
- **Why:** Fixes `E2018` and the `<Unknown>` result in #6708.
- **Things to notice:**
  - `# noqa: N801` silences the Python linter rule "class names should be CapWords". The lowercase name is deliberate.
  - The index is typed `int`. The test passes an `i64`, so `i64` is evidently accepted where `int` is expected, but the diff doesn't show how.
  - The diff doesn't show what the checker gives for `p[i]` on a bare `ptr` (no `T`). It is probably still unknown or `Any`.

### 5.2 `jac/jaclang/compiler/passes/native/na_ir_gen_pass.impl/types.impl.jac`: lowers `ptr[T]` and detects pointers

```diff
+impl NaIRGenPass._ptr_elem_llvm_of(expr) -> (ir.Type | None) {
+    if not isinstance(expr, uni.Expr) or expr.type is None { return None; }
+    mangled = expr.type.mangle();
+    if mangled != "ptr" and not mangled.startswith("ptr[") { return None; }
+    args = expr.type.private.type_args or [];
+    if not args { return ir.IntType(8); }               # bare ptr → i8
+    elem = self._lower_type(args[0]);
+    return elem if elem is not None else ir.IntType(8);
+}
 ...
 impl NaIRGenPass._lower_class_type(t) {
+    if cname == "ptr" {
+        if not type_args { return ir.IntType(8).as_pointer(); }   # ptr  → i8*
+        _pe = self._lower_type(type_args[0]);
+        if _pe is None { return None; }                          # unknown T → fail
+        if isinstance(_pe, ir.VoidType) { return ir.IntType(8).as_pointer(); }  # ptr[void] → i8*
+        return _pe.as_pointer();                                 # ptr[T] → T*
+    }
```

- **What:**
  - `_ptr_elem_llvm_of` answers "is this expression a `ptr`?". It returns the element type if so, and `None` if not. It mirrors the existing `_list_elem_llvm_of`.
  - The new branch in `_lower_class_type` maps `ptr[T]` to `T*`.
- **Why:** Gives LLVM the pointee type that GEP, load and store need.
- **Things to notice:**
  - **Fallbacks differ between the two helpers.**
    - If `T` can't be lowered, the detector falls back to `i8`, but `_lower_class_type` returns `None`, so lowering fails.
    - For `ptr[void]`, `_lower_class_type` makes `i8*`. The detector returns `VoidType`, because `_lower_type` gives `VoidType` rather than `None`.
    - The read and write code only check the detector for "not `None`" and then use the real pointee from the lowered value, so this does no harm today. A reviewer may still ask for the two to match.
  - `ptr[void]` → `i8*` mirrors C's `void*`, which LLVM can't index.
  - Matching on the mangled string `"ptr"` or `"ptr["` means a user class named `ptr` would also match. The diff doesn't say whether that is possible.

### 5.3 `jac/jaclang/compiler/passes/native/na_ir_gen_pass.impl/lists.impl.jac`: two small GEP helpers

```diff
+impl NaIRGenPass._codegen_ptr_index(target_val, index_val) -> (ir.Value | None) {
+    if not isinstance(target_val.type, ir.PointerType) { return None; }
+    idx = self._coerce_type(index_val, ir.IntType(64));
+    addr = self.builder.gep(target_val, [idx], name="ptr.idx");
+    return self.builder.load(addr, name="ptr.get");
+}
+impl NaIRGenPass._codegen_ptr_index_set(target_val, index_val, value) -> None {
+    if not isinstance(target_val.type, ir.PointerType) { return; }    # silent no-op
+    idx = self._coerce_type(index_val, ir.IntType(64));
+    addr = self.builder.gep(target_val, [idx], name="ptr.idx");
+    self.builder.store(self._coerce_type(value, target_val.type.pointee), addr);
+}
```

- **What:** Read is `load(gep(p, i))`. Write is `store(coerce(v, T), gep(p, i))`. The index is always widened to `i64` first.
- **Why:** This is the actual code that does the memory access for both issues.
- **Things to notice:**
  - **No bounds checks.** Negative indices work like C, because GEP indices are signed.
  - The stored value is converted to `T`. For example, storing an `i64` into `ptr[i8]` probably truncates it, but that depends on `_coerce_type`, which the diff doesn't show.
  - **The write helper returns silently if the target is not a pointer, but the caller still marks the store as done** (see 5.5). That would drop a write without any error.
  - The helpers live in `lists.impl.jac` next to the list-index helpers, even though they are not about lists.

### 5.4 `jac/jaclang/compiler/passes/native/na_ir_gen_pass.impl/expr.impl.jac`: subscript read

```diff

+        if self._ptr_elem_llvm_of(nd.target) is not None {      # NEW: ptr first
```

- **What:** If the target is a `ptr`, the code generates the pointer and the index, and returns the loaded value. Otherwise it falls through to the existing list and dict code.
- **Why:** Fixes #6708.
- **Things to notice:**
  - The "try the node, then try `.start`" pattern for the index copies the existing write path in `stmt.impl.jac`.
  - **Slices are not rejected.** For `p[1:3]`, the code may fall back to `.start`, so it would act like `p[1]`. Only `slices[0]` is used, so `p[i, j]` ignores `j`.
  - **The target can be generated twice.** If the pointer path fails partway, it falls through and the existing code generates `nd.target` again. If the target has side effects, such as a function call, that call would be emitted twice.

## 6. How execution flows after the PR

### 6.1 Type-checking `p: ptr[i64]`

```text
annotation ptr[i64]
├─ checker looks up "ptr" in na_builtins.pyi                ← NEW (was E2018)
├─ ptr is Generic[_T] → _T = i64                            ← NEW
└─ expression p[j] → __getitem__ → type i64                 ← NEW (was <Unknown>)
```

### 6.2 Lowering the type

```text
_lower_class_type(ptr[...])
├─ cname == "ptr"                                           ← NEW
│  ├─ no type args        → i8*
│  ├─ T lowers to None    → None (lowering fails)
│  ├─ T is void           → i8*
│  └─ otherwise           → T*   (ptr[i64] → i64*)
└─ (else: existing list[T] … branches)
```

### 6.3 Reading `v = p[i]`

```text
_codegen_atom_trailer(p[i])
├─ subscript (not attr) with slices
├─ _ptr_elem_llvm_of(p) != None ?                           ← NEW
│  ├─ yes: ptr_val = codegen(p); idx_val = codegen(i or slice.start)
│  │  └─ _codegen_ptr_index                                 ← NEW
│  │     ├─ idx → i64
│  │     ├─ gep(ptr_val, idx)   "ptr.idx"
│  │     └─ load                "ptr.get" → returned
│  └─ any step None → fall through
└─ existing list/dict index path
```

### 6.4 Writing `p[i] = val`

```text
_codegen_assignment(p[i] = val)
├─ (existing) compute target_val, value, idx_val
├─ idx_val ok AND _ptr_elem_llvm_of(p) != None ?            ← CHANGED
│  └─ _codegen_ptr_index_set                                ← NEW
│     ├─ idx → i64; gep
│     ├─ store coerce(val, pointee)
│     └─ _idx_stored = True
└─ elif idx_val ok → existing dict/list path
```

| Scenario | Before | After |
|---|---|---|
| `p: ptr[i64]` declared | `E2018` (per PR) | type checks, lowers to `i64*` |
| `v = p[3]` on `ptr[i64]` | "does not yet support subscript/index access" | load from byte offset 24 |
| `p[3] = 7` on `ptr[i64]` | "does not yet support subscript assignment" | store at byte offset 24 |
| bare `ptr`, `p[1] = 255` | error | stores one **byte** at offset 1 |
| `p[1:3]` | error | probably treated as `p[1]` (not tested) |
| list/dict subscripts | unchanged | unchanged (the ptr check returns `None` first) |

**Behaviour users will notice:** a bare `ptr` steps one byte at a time. The issue reproductions used 16-bit shims (`uint16_t`). To match them, users must write `ptr[i16]`. Even then the read side may differ for values above 32767, because LLVM integers carry no sign and the shim read the value as unsigned.

## 11. Questions your senior might ask

**Q: Why put the element type in the type rather than inferring it at each use?**
GEP already scales the index by `sizeof(T)`, so a typed `T*` gives the right width and stride with no casts. #6708 suggested "inferred from context or an explicit cast". A typed pointer is the explicit option.

**Q: What does bare `ptr` mean now?**
`i8*`, a byte pointer. `p[i]` reads or writes one byte at offset `i`. The diff doesn't show what type the checker gives `p[i]` when there is no `T`.

**Q: Was `ptr` really undefined on `main`?**
Your PR says yes (`E2018`). Issue #6707 says it worked in FFI signatures. You need to check `main` again to settle this. The data here can't.

**Q: What happens if `T` can't be lowered?**
`_lower_class_type` returns `None` and lowering fails. The detector `_ptr_elem_llvm_of`, however, would fall back to `i8`. Today that is harmless, because the codegen uses the lowered pointer's real pointee.

**Q: Is there any bounds checking?**
No. It works like C: GEP plus load or store, and negative indices are allowed.

**Q: What if the value has a different width from `T`, e.g. writing `i64` into `ptr[i8]`?**
`_coerce_type(value, pointee)` converts it, probably by truncating. The exact rule lives in `_coerce_type`, which this diff doesn't show. The type stub's `__setitem__(value: _T)` should catch many mismatches before codegen runs.

**Q: Can the read path generate the target expression twice?**
Yes. If the pointer path generates `nd.target` and then fails, the code falls through to the list path, which generates it again. For a call like `get_ptr()[i]`, that would emit two calls.

**Q: Does this change list or dict subscripts?**
No. The pointer check runs first and returns `None` for anything whose mangled type is not `ptr` or `ptr[...]`, so those paths are unchanged.
