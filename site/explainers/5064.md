## 1. The short version

jac-scale is the Jac plugin that deploys a Jac app to Kubernetes. When it deploys Redis, it reads a config file called `redis.conf.template` that sits next to the Redis deployment code (`jac_scale/providers/database/`). It fills that template in and hands it to the Redis pod.

**When jac-scale was installed normally (`pip install jac-scale`), the template file was not packed into the wheel, so `jac start --scale` crashed with `Redis config template not found at: .../site-packages/jac_scale/providers/database/redis.conf.template`.** It only worked for developers using an editable install (`pip install -e .`), because that reads straight from the source folder.

**You added one glob pattern, `"providers/**/*.template"`, to `[tool.setuptools.package-data]` in `jac-scale/pyproject.toml`, so setuptools now copies `.template` files under `providers/` into the wheel.** You also added a release note and a test that looks for the file through `importlib.resources`.

**Status:** Merged on 2026-03-11. @udithishanka approved, then requested changes to the test, then approved again after you updated it. All CI checks that ran passed. The release and publish jobs were skipped, which is expected on a PR.

## 3. The problem, step by step

### 3.1 The setup

- **Source tree:** `jac-scale/jac_scale/providers/database/redis.conf.template` exists on disk.
- **Build config:** `package-data` for `jac_scale` listed only `_precompiled/**/*.jir`, `_precompiled/manifest.json` and `templates/*.html`. The `"*"` key covered only `.jac` files.
- **Runtime:** the Redis deploy code looks for the template next to its own source file.

### 3.2 What went wrong

```text
1. Release build runs setuptools on jac-scale/
     package-data patterns: *.jac, _precompiled/..., templates/*.html
2. setuptools walks jac_scale/providers/database/
     kubernetes_redis.jac   -> matches "*.jac"         -> INCLUDED
     redis.conf.template    -> matches nothing         -> DROPPED   <-- WRONG
3. Wheel jac_scale-0.2.x-py3-none-any.whl is published (no template inside)
4. User runs: pip install jac-scale
     site-packages/jac_scale/providers/database/ has kubernetes_redis.jac, no template
5. User runs: jac start app.jac --scale
6. Redis deployment builds path: <site-packages>/jac_scale/providers/database/redis.conf.template
7. File does not exist -> error:
     "Redis config template not found at: .../site-packages/jac_scale/providers/database/redis.conf.template"
8. Deployment aborts
```

Compare the editable install, which is why developers never saw the bug:

```text
1. Developer runs: pip install -e jac-scale
2. Python imports jac_scale from the source folder
3. Path(__file__).parent / 'redis.conf.template' -> source folder -> file exists -> OK
```

### 3.3 Why it mattered

- Issue #5057 says it hits **every non-editable install of `jac-scale>=0.2.0` that deploys Redis**. That is every real user who installs from PyPI.
- It was found in another project's CI, `jaseci-labs/Agentic-AI` (job linked in the issue). So it blocked downstream deployments, not just local testing.

## 4. The idea of the fix (one sentence)

> **Tell the build to ship the template.** Add `providers/**/*.template` to `package-data` so setuptools copies the file into the wheel.

The code that reads the file was already correct; only the packaging list was incomplete. Fixing the list is the smallest change. It also covers any future `.template` file under `providers/`.

## 5. Every code change, explained

### 5.1 `jac-scale/pyproject.toml`: ship `.template` files in the wheel

```diff
 [tool.setuptools.package-data]
 "*" = ["*.jac", "*.impl/*.jac", "*.cl/*.jac"]
-jac_scale = ["_precompiled/**/*.jir", "_precompiled/manifest.json", "templates/*.html"]
+jac_scale = ["_precompiled/**/*.jir", "_precompiled/manifest.json", "templates/*.html", "providers/**/*.template"]  # NEW: last pattern
```

**What:** When setuptools builds the `jac_scale` package, it now also includes every file ending in `.template` anywhere under `jac_scale/providers/`.

**Why:** This is exactly the missing rule from step 2 of the timeline. `redis.conf.template` now lands in the wheel and in `site-packages`.

**Things to notice:**
- Issue #5057 offered two options: `providers/**/*.template` or the broader `**/*.template`. You picked the narrower one. It is scoped to the providers folder, so a `.template` file elsewhere in `jac_scale` would still not ship.
- Recursive `**` in `package-data` was, as far as I know, added in setuptools 62.3. `[build-system]` only requires `>=61.0`.
  - This is low risk. The existing `_precompiled/**/*.jir` line already relies on the same feature.
  - On an older setuptools, `**` would act like `*`, which still matches `providers/database/redis.conf.template` (one folder deep).
- No runtime code changed. `kubernetes_redis.jac` still uses `Path(__file__).parent`, and that works now that the file is actually installed next to it.

### `jac-scale/jac_scale/tests/test_deploy_k8s.jac`

The test is a new block at the end of the file, plus `import importlib.resources;` at the top.

```jac
test "redis template file in package" {
    try {
        ref = importlib.resources.files("jac_scale") / "providers" / "database" / "redis.conf.template";
        assert ref.is_file() , ("...not discoverable as package data...");
        content = ref.read_text(encoding='utf-8');
        assert len(content) > 0 , "...should not be empty";
        assert 'maxmemory-policy' in content , ("...should contain Redis configuration directives");
    } except (FileNotFoundError, ModuleNotFoundError) as e {
        raise AssertionError(f"redis.conf.template not found via importlib.resources: {e}. ...");
    }
}
```

**Setup:** None. It asks the installed `jac_scale` package for the template.

**What it checks:**
1. The file exists as a resource of the installed package.
2. It is non-empty.
3. It contains `maxmemory-policy`, a real Redis directive, so it is not some unrelated file.
4. A missing module or file becomes a clear `AssertionError` instead of a raw traceback.

**History:**
- Your first version (commit `89baa75`) found the file with `Path(__file__).parent.parent`.
- @udithishanka pointed out that this walks the source tree, so it passes whether or not the wheel contains the file.
- You switched to `importlib.resources` in `f6fcea6` / `648365c`.

**Difference from the suggestion:** @udithishanka suggested `files("jac_scale.providers.database") / "redis.conf.template"`. You used `files("jac_scale") / "providers" / "database" / "redis.conf.template"`. Both reach the same file. Yours does not require `providers.database` to be importable as its own package.

**Caveat to understand before your meeting:** `importlib.resources` returns wherever `jac_scale` was imported from.
- If the test runs against an editable install, it resolves to the source folder. The file is always there, so the test passes even without the `pyproject.toml` fix.
- The test only catches the bug when the suite runs against a non-editable wheel install.
- How `test-scale` / `test-scale-k8s` install jac-scale is not visible in this PR, so this can't be confirmed either way.

## 11. Questions your senior might ask

**Q: Why didn't anyone catch this earlier?**
Developers and most local runs use `pip install -e`, which reads from the source folder where the file exists. The bug only shows with a real wheel install. It surfaced in `jaseci-labs/Agentic-AI` CI.

**Q: Why `providers/**/*.template` and not `**/*.template`?**
It is scoped to where templates actually live today. It still picks up future templates under `providers/`. The broader pattern would also work. The issue offered both options.

**Q: Does `**` work with `setuptools>=61.0`?**
Recursive globs in `package-data` arrived, to my knowledge, in setuptools 62.3. The existing `_precompiled/**/*.jir` line already depends on that. Even on an older version, `**` would behave like `*`, which still matches the one-folder-deep `providers/database/redis.conf.template`.

**Q: Does the new test actually fail without the fix?**
Only if the tests run against a wheel install. With an editable install, `importlib.resources` points to the source tree and the test passes anyway. This PR doesn't show how CI installs jac-scale. The strongest evidence of the fix is your manual wheel build and install.

**Q: Why did you write `files("jac_scale") / "providers" / "database"` instead of the reviewer's `files("jac_scale.providers.database")`?**
Both reach the same file. Yours only needs `jac_scale` to be importable as a package, which avoids depending on `providers.database` being importable on its own. The commit message `648365c` ("fx test") suggests the first attempt needed a fix, but the PR doesn't say what failed.

**Q: Why catch `FileNotFoundError` and `ModuleNotFoundError`?**
`read_text` can raise `FileNotFoundError`, and `files()` raises `ModuleNotFoundError` if the package can't be imported. Turning both into an `AssertionError` with a hint about `pyproject.toml` makes a failure easier to understand.

**Q: Are there other non-`.jac` data files at risk of the same bug?**
`.jac`, `.jir`, `manifest.json` and `templates/*.html` are covered. Anything else (for example YAML or other config files) would also be dropped. The diff doesn't show the rest of the tree, so this needs a separate audit.

**Q: Did any runtime code change?**
No. Only `pyproject.toml`, the release note and a test changed. The loader in `kubernetes_redis.jac` is untouched.

**Q: When do users get the fix?**
In the next jac-scale release built after 2026-03-11. Already-published wheels (`>=0.2.0` up to 0.2.4) still lack the file.
