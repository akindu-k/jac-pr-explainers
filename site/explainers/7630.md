## 1. The short version

The Jac serializer reads stored objects (graph "anchors") back into live objects. When stored data does not match the current code, it logs a line. Examples are an unregistered class, a field whose type changed, or a missing required field. Before #7603 these lines printed once per object read, and production services hit about 85 lines per second. #7603 changed each one to print **once per process**.

**That fix removed a signal: a problem that happened once and a problem that happened a million times both produced exactly one log line.** @Thamirawaran put it this way: "we can't tell 1 from 1M anymore."

**You replaced the yes/no "warn once" gate with an occurrence counter. Each line is now re-emitted only on occurrence #1, #10, #100, #1000, and so on, and carries its running count, e.g. `Refused to deserialize unregistered class: app.X (occurrence #100)`.** One million occurrences produce 7 lines, not 1 and not 1,000,000.

**Status:** Merged on 2026-08-10. The only review was from the Greptile bot (confidence 5/5, one P1 note about concurrency, which the PR description treats as an accepted trade-off). All CI checks that ran passed. The rest were skipped.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. It compiles to and runs on Python, so `logging`, `threading` and dicts behave as in Python. |
| `.jac` / `.impl.jac` | Jac splits a class into a declaration file (`serializer.jac`, which lists fields and method signatures) and an implementation file (`impl/serializer.impl.jac`, which holds method bodies written as `impl Serializer.foo(...) {...}`). |
| Archetype | A Jac user type such as `node DonationNode { has amount: int; }`. |
| Anchor | The stored "envelope" around an archetype: id, edges, access info, and the archetype's fields under `"archetype"`. |
| `Serializer` | Runtime class (`jaclang.runtimelib.serializer`) that turns anchors into dicts and back again. |
| Deserialization hot path | Code that runs once per anchor read. A service can run it thousands of times per second, so anything done here is multiplied. |
| Drift | Stored data no longer matches the current class: a renamed class, a changed field type, a missing field. |
| Unregistered class | A class name in stored data that this process does not define. `_get_class` returns `None` for it, which is expected behaviour. |
| Scope / key / dedup key | Each log site has a *scope* (e.g. `"unregistered"`, `"coercion-fallback"`) and a *key* (e.g. a class or field name). Together they form `dedup_key = "scope:key"`, which is what gets counted. |
| `_should_warn_once` (old) | The gate added by #7603. It returned `True` the first time it saw a dedup key and `False` forever after. |
| `_warn_occurrence(scope, key) -> int` | The new gate. It counts every occurrence and returns the count when it is on the ladder, otherwise `0`. **This is what the PR adds.** |
| `0` sentinel | A special return value meaning "don't log this one". It does not mean "zero occurrences". |
| Power-of-10 ladder | The occurrence numbers that get logged: 1, 10, 100, 1000, … Log volume grows like log₁₀(N). |
| `_is_report_threshold(n)` | New helper. It returns `True` when `n` is 1, 10, 100, …. |
| `_occurrence_note(n)` | New helper. It returns the suffix `" (occurrence #n)"`. |
| `_warn_counts` | New static `dict[str, int]` mapping dedup key to count. It replaces the old set `_warned_class_keys`. |
| `_MAX_WARNED_CLASS_KEYS` / saturation | A cap on how many distinct keys are tracked, to bound memory. Once it is hit, new keys are logged only at DEBUG, and a one-time notice says so. |
| `_warn_lock` | A `threading.Lock`. It is taken only when a key is seen for the first time. |
| Walrus `(n := expr)` | Assigns and tests in one step: `if (n := f()) { ... }` runs the block only when `n` is truthy, i.e. not 0. |
| GIL | Python's Global Interpreter Lock. It keeps a dict internally consistent across threads, but it does not make `get` → `+1` → `set` atomic. |
| Read-modify-write race | Two threads read the same count, both add 1, and both write it back. One increment is lost. |

## 3. The problem, step by step

### 3.1 The setup

- Many services share one store. A service may read anchors written by other programs whose classes it does not define. Issue #7602 calls this the normal multi-app jac-scale shape.
- `Serializer._get_class`, `_deserialize_anchor`, `_deserialize_archetype`, `deserialize` and `repair` each have one or more log sites for drift and failures.
- Since #7603 (and part 1, #7629, which covered the remaining per-anchor paths), every one of these sites was guarded by `_should_warn_once(scope, key)`.

### 3.2 What went wrong

Take the reproduction from issue #7602: reading the same foreign `DonationNode` anchor many times.

```text
Before #7603:
1. read #1        -> "Refused ... __main__.DonationNode"  + "archetype reconstruction failed ..."
2. read #2        -> same 2 lines again
3. read #200      -> total 400 WARNING lines  (flood: 23,305 lines / 5 min in builder-sv)

After #7603 (once per process), before this PR:
1. read #1        -> _warned_class_keys = {"unregistered:__main__.DonationNode", ...}; 2 lines
2. read #2..#200  -> key in set -> False -> nothing logged
3. read #1,000,000-> still nothing logged
4. Log shows 2 lines whether there was 1 read or 1,000,000   <-- WRONG: magnitude lost
```

The same blind spot applied to every gated site: coercion fallback per field, alias resolution, non-dict archetype, missing required field, and the others.

### 3.3 Why it mattered

- Operators could not tell a one-off bad record from systemic drift affecting every read. @Thamirawaran raised this ("can't tell 1 from 1M anymore").
- The workaround suggested in issue #7602, a logging filter, also hid information. #7603 fixed the volume, but at the cost of this second kind of observability loss.

## 4. The idea of the fix (one sentence)

> **Count every occurrence, but only log on powers of ten.** Each dedup key keeps an integer counter, and a line is emitted, with its count attached, only when the counter reaches 1, 10, 100, 1000, …

This keeps log volume logarithmic, so the flood stays gone. The last line printed for a key always tells you the order of magnitude. Message prefixes are unchanged, so existing greps and alerts still match.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/serializer.jac`: new state and method signatures

```diff
 obj Serializer {
     static has _registry: dict[str, type] = {},
         _aliases: dict[str, str] = {},
-        _warned_class_keys: set[str] = set(),
+        _warn_counts: dict[str, int] = {},          # NEW: key -> occurrence count
         _warn_dedup_saturated: bool = False,
         _warn_lock: any = threading.Lock();
 ...
-    static def _should_warn_once(scope: str, key: str) -> bool;
+    static def _warn_occurrence(scope: str, key: str) -> int;
+    static def _is_report_threshold(n: int) -> bool;
+    static def _occurrence_note(n: int) -> str;
```

**What:** The set of "already warned" keys becomes a dict of counts. Three method signatures replace the old one.

**Why:** A set can only answer "seen or not". You need a number to know where on the ladder each key is.

**Things to notice:** The cap, the saturation flag and the lock are unchanged. Each entry now also stores an int, so it costs slightly more memory, but the number of entries is still capped.

### 5.2 `jac/jaclang/runtimelib/impl/serializer.impl.jac`: the counter

```diff
-impl Serializer._should_warn_once(scope: str, key: str) -> bool {
+impl Serializer._warn_occurrence(scope: str, key: str) -> int {
     dedup_key = f"{scope}:{key}";
-    seen = Serializer._warned_class_keys;
-    if dedup_key in seen {
-        return False;
+    counts = Serializer._warn_counts;
+    seen_count = counts.get(dedup_key);
+    if seen_count is not None {                       # fast path, no lock
+        n = seen_count + 1;
+        counts[dedup_key] = n;
+        return n if Serializer._is_report_threshold(n) else 0;
     }
     if Serializer._warn_dedup_saturated {
         ... logger.debug(... "dedup cap reached" ...)
-        return False;
+        return 0;
     }
     with Serializer._warn_lock {
-        if dedup_key in seen {
-            return False;
+        seen_count = counts.get(dedup_key);           # re-check under lock
+        if seen_count is not None {
+            n = seen_count + 1;
+            counts[dedup_key] = n;
+            return n if Serializer._is_report_threshold(n) else 0;
         }
-        if len(seen) >= _MAX_WARNED_CLASS_KEYS {
+        if len(counts) >= _MAX_WARNED_CLASS_KEYS {
             ... one-time saturation warning ...
-            return False;
+            return 0;
         }
-        seen.add(dedup_key);
-        return True;
+        counts[dedup_key] = 1;
+        return 1;                                     # first occurrence always reported
     }
 }
+
+impl Serializer._is_report_threshold(n: int) -> bool {
+    if n < 1 { return False; }
+    while n % 10 == 0 { n //= 10; }
+    return n == 1;
+}
+
+impl Serializer._occurrence_note(n: int) -> str {
+    return f" (occurrence #{n})";
+}
 
 impl Serializer._reset_warn_cache -> None {
-        Serializer._warned_class_keys.clear();
+        Serializer._warn_counts.clear();
```

**What:**
- A key seen before is incremented without taking the lock. It returns `n` when `n` is on the ladder, else `0`.
- A new key is inserted with count 1 under the lock, and 1 is returned, so the first occurrence is always logged.
- `_is_report_threshold` strips trailing zeros and checks whether 1 remains.

**Why:** This is the core of the fix. The gate now carries magnitude instead of a bare yes/no.

**Things to notice:**
- The `n < 1` guard is required, not just defensive. Without it, `0 % 10 == 0` would loop forever.
- After saturation, a key that is already tracked keeps counting on the fast path. Only *new* keys are suppressed.
- The fast path is a read-modify-write with no lock. Greptile flagged this as P1: increments can be lost, and a ladder line can be emitted twice. The description accepts this on purpose (see section 9). The alternative it names, storing `itertools.count` objects, was not adopted.

### 5.3 `jac/jaclang/runtimelib/impl/serializer.impl.jac`: every call site

All 14 gated sites follow the same pattern:

```diff
-    if Serializer._should_warn_once("unregistered", key) {
-        logger.warning(f"Refused to deserialize unregistered class: {key}");
+    if (n := Serializer._warn_occurrence("unregistered", key)) {
+        logger.warning(
+            f"Refused to deserialize unregistered class: {key}"
+                + Serializer._occurrence_note(n)         # NEW suffix
+        );
     }
```

| Method | Scopes converted | Level |
|---|---|---|
| `deserialize` | `deserialize-failed` | error |
| `repair` | `drift-detected`, `repaired` | info |
| `_get_class` | `alias-resolved` (info), `alias-missing`, `unregistered` | info / warning |
| `_deserialize_anchor` | `archetype-not-dict`, `archetype-failed` (warning), `anchor-failed` (error) | warning / error |
| `_deserialize_archetype` | `stored-none-no-default`, `stored-none-defaulted`, `coercion-fallback`, `required-missing` (warning), `attic-preserved` (info), `archetype-error` (error) | info / warning / error |

**What:** Each site gets a count, logs only when the count is non-zero, and appends ` (occurrence #n)`.

**Why:** The ladder must apply everywhere #7603 and #7629 applied the once-gate. Otherwise some lines would keep the "1 vs 1M" blind spot.

**Things to notice:**
- The ladder applies to INFO and ERROR lines too, not only warnings.
- In `repair`, `steps and (n := ...)` short-circuits. When there are no steps, nothing is counted, so only real drift is counted.
- The message is built only when `n != 0`. The **key** f-strings (e.g. `f"{cls.__module__}.{type_name}:{type(e).__name__}"` and `dedup_key = f"{scope}:{key}"`) are still built on every call. "Suppressed calls never pay for an f-string" is therefore true for the message but not for the key. This was also true under #7603.
- Adjacent string literals join before `+`, so the note is appended to the whole message. The tests confirm `(occurrence #10)` appears in the output.
- The counter increments even when the logger level would drop the line. The count reflects occurrences, not lines emitted.
- Commit 75ce622 ("qualify serializer dedup keys so distinct classes never share a slot") is on the branch. The final diff shows already-qualified keys only as unchanged context, so that change appears to have reached `main` through #7629. This can't be confirmed from the diff alone.
- Commit cc8e353 only reflowed formatting to match the formatter's operator-chain wrapping. That explains the multi-line walrus blocks.

## 6. How execution flows after the PR

### 6.1 Any gated log site is reached

```text
Serializer site hits a drift/failure condition
├─ build key string (e.g. "__main__.DonationNode")
├─ n = _warn_occurrence(scope, key)                         ← CHANGED (was bool)
│   ├─ dedup_key = "scope:key"
│   ├─ key already in _warn_counts?
│   │   └─ yes → n = count+1, store, return n if on ladder else 0   ← NEW (no lock)
│   ├─ saturated? → DEBUG "suppressed (dedup cap reached)", return 0
│   └─ take _warn_lock
│       ├─ re-check: present → same increment path          ← NEW
│       ├─ len(counts) >= cap → one-time saturation WARNING, return 0
│       └─ counts[key] = 1, return 1
├─ n == 0 → skip, no message built
└─ n != 0 → logger.<level>(message + " (occurrence #n)")   ← NEW suffix
```

### 6.2 Example from issue #7602 (one foreign anchor read N times)

```text
read k (k = 1..N)
├─ _deserialize_anchor → _deserialize_archetype → _get_class
│   └─ _warn_occurrence("unregistered", "__main__.DonationNode") → k if k∈{1,10,100,...}
└─ _deserialize_anchor
    └─ _warn_occurrence("archetype-failed", "__main__.DonationNode") → same k
```

| Scenario | Before #7603 | Before this PR (#7603) | After this PR |
|---|---|---|---|
| 1 read | 2 lines | 2 lines | 2 lines (`#1`) |
| 50 reads | 100 lines | 2 lines | 4 lines (`#1`, `#10`) |
| 200 reads | 400 lines | 2 lines | 6 lines (`#1`, `#10`, `#100`) |
| 1,000,000 reads | 2,000,000 lines | 2 lines | 14 lines (up to `#1000000`) |
| New key after cap reached | — | DEBUG only | DEBUG only (unchanged) |
| Tracked key after cap reached | — | silent | keeps laddering |
| Concurrent threads, same key | — | exact once | count is a floor; a ladder line may repeat |

**Behaviour change users will notice:**
- Recurring problems now produce a few extra lines, each ending in `(occurrence #N)`.
- Counts are per process. Each pod ladders on its own, so `#1000` on one pod is not a fleet-wide total.

## 11. Questions your senior might ask

**Q: Why powers of 10 and not a time-based rate limit?**
A: A power-of-10 ladder keeps volume bounded by log₁₀(N) per key, and each emitted line is itself a magnitude reading. A time-based limit would make the line count depend on uptime, and it would not show the total.

**Q: What does `_warn_occurrence` returning 0 mean?**
A: "Don't log this one." It is a sentinel, not a count. Call sites test it with the walrus operator for truthiness.

**Q: Can two threads corrupt the counter?**
A: Not the dict, because the GIL protects it. But the unlocked get → +1 → set can lose increments, and two threads can both reach the same ladder value and print the same line twice. Greptile flagged this. You accepted it because the count is a magnitude signal, and fixing it would mean a lock on every call or `itertools.count` values.

**Q: Why not just take the lock every time?**
A: These calls run on the per-anchor hot path. The point of #7603's design was a lock-free steady state, and taking the lock on every occurrence gives that up.

**Q: What happens after the key cap is reached?**
A: New keys return 0 and log only at DEBUG, with a one-time saturation warning. Keys already tracked keep incrementing and laddering.

**Q: Is the count fleet-wide?**
A: No, it is per process. N pods give about N × log₁₀(count) lines in total, still bounded.

**Q: Why return an int rather than the formatted note?**
A: So the message f-string is built only when a line will actually be emitted. Note that the key f-strings are still built on every call.

**Q: Why does `_is_report_threshold` check `n < 1`?**
A: For `n = 0`, `0 % 10 == 0` is always true, so the loop would never end. Negative numbers are excluded as well.

**Q: Will existing alerts or greps still match?**
A: Yes. The count is added as a suffix and every message prefix is unchanged.

**Q: Why does the test expect exactly 2 lines for 50 reads?**
A: Occurrences 1 to 50 contain two ladder points, 1 and 10. That shows there is no flood (not 50 lines) and that the magnitude is visible (`#10` appears).
