## 1. The short version

jac-scale keeps a user store for its API server: usernames, password hashes, tokens, the user's graph root, roles, and linked SSO accounts. Before this PR, `JacScaleUserManager` always kept that data in a local SQLite database. It got this from its parent class `UserManager` and then added its own SQLite columns and tables on top.

**The gap was that user data could only live in SQLite, even when a jac-scale deployment already had MongoDB configured.** The diff shows that jac-scale already has a Mongo client (`jac_scale.db.get_mongo_client`). The PR description does not explain the operational reason beyond "alternative backend".

**You added a `MongoUserStorage` class and made `JacScaleUserManager` choose a backend once at start-up.** If a `mongodb_uri` is configured, every user method delegates to Mongo (collections `users` and `sso_accounts` in database `jac_db`). If not, the old SQLite code runs as before. Along the way you also:

- added a `GUEST = '__guest__'` constant to jaclang and replaced the hard-coded `'__guest__'` strings with it;
- added logging to several exception handlers;
- tried bcrypt, then removed it again.

**Status:** Merged on 2026-03-09. It was approved by @kugesan1105 and @musab-mah-7. Earlier "changes requested" reviews came from @MusabMahmoodh. All test checks on head commit `59d3caa` passed.

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- `JacScaleUserManager.postinit` called `super.postinit()`, which is SQLite set-up in the base `UserManager`.
- It then created the `sso_accounts` table and used `ALTER TABLE` to add the `role`, `requires_password_reset`, `is_password_required` and `user_id` columns.
- Basic CRUD methods (`create_user`, `authenticate`, `get_user`, …) were inherited from `UserManager`, which uses SQLite.
- Role, SSO-linking and admin methods ran SQL directly on `self._conn`.
- The server creates the `'__guest__'` user at start-up and uses it for anonymous requests. The string was repeated in about 15 places.

### 3.2 What was missing

```text
1. Operator configures jac-scale with mongodb_uri (Mongo is already in use for other jac-scale data)
2. Server starts → JacScaleUserManager.postinit → super.postinit() → SQLite connection opened
3. create_user("alice", ...) → row lands in the local SQLite file, not in Mongo
4. Role / SSO / admin calls → raw SQL on self._conn → SQLite again
5. ✗ No way to put users in MongoDB: the code had no branch for it
```

### 3.3 Why it mattered

There is no linked issue, and the description does not state the pain point. The title says the goal is to "Move Users to MongoDB from SQLite". The release note frames it as "User storage now supports both MongoDB and SQLite".

Note that the PR does **not** move existing data. Mongo is opt-in, and SQLite stays the default. Users already stored in SQLite are not migrated, and the diff contains no migration code.

## 4. The idea of the fix (one sentence)

> **Pick the storage backend once, then delegate.** At start-up, `JacScaleUserManager` creates a `MongoUserStorage` if a Mongo URI is configured, and every user method sends its call there, or falls back to the old SQLite path when `_storage` is `None`.

This keeps every public method signature the same, so callers like the server, admin portal and SSO flow need no changes. The SQLite path is left almost untouched, which limits the risk for existing installs.

### 5.2 `jac-scale/jac_scale/mongo_storage.jac` (new): the Mongo implementation

```diff
+import hashlib;
+obj MongoUserStorage {
+    has users_col: Collection, sso_col: Collection;
+    def create_user(username: str, password: str) -> dict[str, str] {
+        if self.users_col.count_documents({'username': username}, limit=1) > 0 {
+            return {'error': 'User already exists'};
+        }
+        user_root = Root(); Jac.save(user_root); Jac.commit(user_root);
+        root_id = user_root.__jac__.id.hex;
+        token = secrets.token_urlsafe(32);
+        password_hash = hashlib.sha256(password.encode()).hexdigest();
+        self.users_col.insert_one({ 'username':..., 'password_hash':..., 'token':...,
+            'root_id':..., 'role': 'user', 'requires_password_reset': False,
+            'is_password_required': True, 'user_id': None });
+        ...
+    def authenticate(...)   # find_one({'username', 'password_hash'})
+    def update_username(...) # also update_many on sso_col user_id
+    def delete_user(username, admin_user_id) # blocks admin, delete_many on sso_col
+    def list_all_users(...)  # {'username': {'$ne': Con.GUEST.value}}, hides password_hash
+    def update_user_fields(username, fields) -> bool  # generic $set helper
+    ...
```

**What:** There is one method per user operation, each returning the same dict shapes as the SQLite code. For example, `get_user` returns `{'email': username, 'token', 'root_id'}`, and errors are `{'error': '...'}`.

**Why:** This is the Mongo half of the delegation.

**Things to notice:**
- **Passwords are hashed with plain, unsalted SHA-256.** You added bcrypt in `a4135e0`/`d95e171`. @MusabMahmoodh asked whether that would break existing users and wanted @marsninja to confirm. You removed bcrypt in `59d3caa` and said it would come in a separate PR if needed. Whether this hash matches the SQLite base can't be told from the diff.
- `create_user` checks for the username first, then inserts. Two concurrent creates could both pass the check. The unique index would then make the second `insert_one` raise `DuplicateKeyError`, which is not caught. Also, a `Root` is saved before the insert. If the insert fails, that root is left orphaned.
- In `update_password`, the `user = self.users_col.find_one(...)` line is never used (dead code). A missing user returns "Current password is incorrect", not "User not found".
- `update_username` uses `modified_count`, while the setters use `matched_count`. Both are fine here, because renaming to the same name is caught earlier by the "already taken" check.
- `linked_at` is stored as a `datetime`, and `get_sso_accounts` returns it with `str(...)`. The SQLite format may differ.

## 6. How execution flows after the PR

### 6.1 Server start-up / building the user manager

```text
JacScaleUserManager(base_path=...)
└─ postinit                                         ← CHANGED
   ├─ load SSO config → SUPPORTED_PLATFORMS         ← moved to the top
   ├─ db_config.get('mongodb_uri')                  ← NEW
   ├─ URI set?
   │  ├─ yes → get_mongo_client() → db 'jac_db'      ← NEW
   │  │        ├─ create indexes on users / sso_accounts
   │  │        └─ self._storage = MongoUserStorage   (no SQLite opened)
   │  └─ no  → self._storage = None                  ← NEW
   │           ├─ super.postinit()                   (SQLite, as before)
   │           └─ _init_sqlite_schema()              ← NEW name, same SQL
   └─ server then calls create_user(Con.GUEST.value, '__no_password__')  ← CHANGED (constant)
```

### 6.2 A user call (example: login)

```text
POST login → user_manager.authenticate(u, p)        ← NEW override
├─ self._storage set → MongoUserStorage.authenticate
│  └─ find_one({username, password_hash=sha256(p)}) → {username, token, root_id} | None
└─ else → super.authenticate(u, p)                  (base SQLite, unchanged)
```

All other user, SSO, role and admin methods follow the same shape.

### 6.3 Admin bootstrap

```text
bootstrap_admin_user
├─ admin disabled → return
├─ admin exists?
│  ├─ role != 'admin'
│  │  ├─ Mongo  → update_user_fields(role, user_id)                 ← NEW
│  │  └─ SQLite → set_user_role + UPDATE user_id (try/except + log)  ← CHANGED
│  └─ return "Admin user already exists"
└─ else create_user → then
   ├─ Mongo  → update_user_fields(role, user_id, requires_password_reset)  ← NEW
   └─ SQLite → set_user_role + set_requires_password_reset + UPDATE user_id (logged)  ← CHANGED
```

### 6.4 Deleting a user

```text
delete_user(name)
├─ Mongo  → block if user_id == ADMIN_USER_ID → delete_one → delete_many sso_accounts  ← NEW
└─ SQLite → block admin → DELETE users → DELETE sso_accounts rows                      ← CHANGED (explicit SSO cleanup)
```

| Scenario | Before | After |
|---|---|---|
| No `mongodb_uri` configured | SQLite | SQLite (same SQL) |
| `mongodb_uri` / `MONGODB_URI` set | SQLite (URI ignored for users) | Mongo `jac_db.users` / `jac_db.sso_accounts` |
| Existing SQLite users, then Mongo turned on | n/a | Not migrated: they will not be found in Mongo |
| `delete_user` on SQLite | Relied on FK cascade for SSO rows | Deletes SSO rows explicitly |
| Bad or expired JWT | Silently `None` | `None` plus a debug log line |
| `um.close()` | Base behaviour (not visible here) | No-op |
| Anonymous request | `'__guest__'` | `Con.GUEST.value` (same value) |

Behaviour changes users may notice:
- Turning on Mongo starts with an empty user store. The admin is re-bootstrapped and the guest is re-created.
- `close()` no longer does anything.

## 11. Questions your senior might ask

**Q: How does someone turn MongoDB on?**
They set `mongodb_uri` in the `jac.toml` database section, or set the `MONGODB_URI` env var. `postinit` reads `get_database_config()['mongodb_uri']`, and if it is not `None`, user storage goes to Mongo database `jac_db`.

**Q: What happens to users already in SQLite when Mongo is switched on?**
Nothing moves. The Mongo store starts empty: the admin gets re-bootstrapped and the guest is re-created. Old accounts must re-register. The PR has no migration.

**Q: Why unsalted SHA-256 in the new backend?**
You tried bcrypt, but @MusabMahmoodh raised backward compatibility for existing users and asked for @marsninja's view. You removed bcrypt to keep the PR scoped and deferred it to a separate PR.

**Q: Why not make `MongoUserStorage` and a `SqliteUserStorage` share one interface?**
The SQLite logic is spread across the base `UserManager` and `JacScaleUserManager`, so you kept SQLite as the `super`/inline path. You used `_storage = None` as the "SQLite" signal to keep the change small. The cost is an `if self._storage` check in every method.

**Q: Does the SQLite path behave differently now?**
Mostly no:
- The same SQL runs, apart from collapsed formatting.
- `delete_user` now also deletes SSO rows.
- JWT failures log at debug level.
- Bootstrap uses separate updates.
- `close()` is now a no-op.

**Q: Why did `test_sso.jac` need to change?**
`postinit` now always calls `get_database_config()`, and the test's `MockScaleConfig` didn't have it. The added method returns `mongodb_uri: None`, so SSO tests stay on SQLite.

**Q: How is the Mongo code tested in CI?**
A testcontainers `mongo:7.0` container is started by the new `test_mongo_user_manager.jac`. A new workflow step runs it, and `test-scale` passed. The runner needs Docker.

**Q: Is `create_user` safe under concurrent requests?**
Not fully. It does count-then-insert, so a race would hit the unique `username` index and raise an uncaught `DuplicateKeyError`. A `Root` would already have been saved by then.

**Q: Why did jaclang's `Constants` change in a jac-scale PR?**
A reviewer asked to replace the repeated `'__guest__'` literal. Both jaclang's stdlib server and jac-scale use it, so the constant lives in jaclang (`Con.GUEST`). The value is unchanged.

**Q: Does every SQLite user need `pymongo` installed now?**
Yes, if it isn't already a dependency. `user_manager.jac` imports `mongo_storage.jac` at module level, which imports `pymongo.collection`. The diff doesn't show jac-scale's full dependency list, but the existing `jac_scale.db.get_mongo_client` suggests pymongo is already required.
