## 1. The short version

jac-scale turns every walker in a Jac program into HTTP endpoints when you run `jac start`. Before this PR, every walker got exactly two fixed routes: `POST /walker/<Name>` (run on the user's root node) and `POST /walker/<Name>/{node}` (run on a given node). **You could not choose a walker's URL or its HTTP method. There was no way to expose a walker as `GET /custom/get`.**

**This PR adds an `@meta(path=..., method=...)` decorator in `jac_scale`. It stores a `__meta__` dict on the walker class. At startup, the server registers that walker at the custom path and method instead of the default `/walker/...` routes.** For example, `@meta(path="/custom/get", method="GET")` on `GetWalker` makes `GET /custom/get` run the walker on the caller's root node.

The linked issue #4299 asked for more than this: custom headers, query parameters and timeouts, configured through a `__meta__` field. The PR delivers only path and method. It also leaves a `TODO` saying that GET requests still read walker fields from the request body, not from query parameters.

**Status:** Closed on GitHub. There are no reviews and no comments, and all 8 CI checks passed on head commit `250ce93`. The data given does not say whether the PR was merged or closed without merging. Issue #4299 shows as closed.

## 3. The problem, step by step

### 3.1 The setup

- **Your Jac file** defines walkers.
- **`jac start`** launches `JacAPIServer`.
- **`register_walkers_endpoints`** loops over `get_walkers()` and calls `self.server.add_endpoint(JEndPoint(...))` for each walker.
- **Clients** (a browser, a frontend, curl) call those routes.

### 3.2 What was missing

```text
1. You write:        walker GetWalker { can run with `root entry { report {...}; } }
2. You run:          jac start app.jac
3. Server registers: POST /walker/GetWalker/{node}   (fixed)
                     POST /walker/GetWalker          (fixed)
4. Client wants:     GET /custom/get
5. Server answers:   no such route                    ← MISSING: no way to pick path or method
```

There was no knob at all. Path prefix `/walker/` and method `POST` were hard-coded in `register_walkers_endpoints`.

### 3.3 Why it mattered

Issue #4299 says users "cannot specify" the HTTP method, headers, query parameters or other HTTP settings. Without a custom path or method, an app could not offer a REST-style API such as `GET /todos`. The only option was to put a proxy or a wrapper in front of the server. The PR does not show which workaround people used. The issue thread has no comments.

## 4. The idea of the fix (one sentence)

> **Let a decorator tag the walker, and let the router read the tag.** `@meta` writes `{path, method}` onto the walker class, and `register_walkers_endpoints` uses those values instead of the defaults when it finds them.

This keeps the change local. The decorator only stores data, and route registration is the single place that reads it. Walkers without `@meta` take exactly the same code path as before.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/builtins.jac`: defines the `@meta` decorator

```diff
+import from typing { Any }
+
+def meta(path: str, method: str = "POST") -> Any {
+    def decorator(cls: Any) -> Any {
+        cls.__meta__ = {'path': path, 'method': method};   # NEW: tag the walker class
+        return cls;
+    }
+    return decorator;
+}
```

**What:** `meta(path, method="POST")` returns a decorator. The decorator sets `__meta__` on the class and returns the same class.

**Why:** This gives users a way to attach route settings to a walker.

**Things to notice:**
- The decorator does not check its inputs. A bad method such as `"FETCH"` or a path without a leading `/` is stored as-is. Any error surfaces later, at server startup (see 5.3).
- Only `path` and `method` exist. The issue's `headers`, `query_params` and `timeout` are not implemented.
- The issue proposed writing `__meta__ = {...}` inside the walker body. The PR uses a decorator instead. If someone sets `__meta__` by hand, the server code will read it too, because it only does `getattr(walker_cls, '__meta__')`.

### 5.2 `jac-scale/jac_scale/__init__.py`: exports `meta`

```diff
+from .builtins import meta
+
+__all__ = ["meta"]  # allowing all the users to to import meta
```

**What:** Users can now write `import from jac_scale { meta }`, as the fixture does.

**Things to notice:**
- The diff header shows `@@ -0,0 +1,3 @@`, so the file was empty before. The file list calls it "modified", which fits an existing empty file.
- Importing a `.jac` module from a Python `__init__.py` depends on Jac's import hook being active. It works under `jac start`, because the tests pass. The diff does not show whether a plain `python -c "import jac_scale"` works.
- The comment has a typo ("to to").

### 5.3 `jac-scale/jac_scale/impl/serve.impl.jac`: registers custom routes

```diff
 impl JacAPIServer.register_walkers_endpoints -> None {
     for walker_name in self.get_walkers() {
+        walker_cls = self.get_walkers()[walker_name];         # NEW: look up the class
+        meta = getattr(walker_cls, '__meta__', None);         # NEW: read the tag
+
+        if meta {
+            path = meta.get('path');
+            method_str = meta.get('method', 'POST').upper();  # "get" -> "GET"
+            method = HTTPMethod(method_str);
+            self.server.add_endpoint(JEndPoint(
+                method=method, path=path,
+                callback=self.create_walker_callback(walker_name, has_node_param=False),
+                parameters=self.create_walker_parameters(walker_name, invoke_on_root=True),
+                ... summary=f'Custom Endpoint for {walker_name} on Root Node' ...));
+            self.server.add_endpoint(JEndPoint(
+                method=method, path=path,                      # SAME method + path as above
+                callback=self.create_walker_callback(walker_name, has_node_param=True),
+                parameters=self.create_walker_parameters(walker_name, invoke_on_root=False),
+                ... summary=f'Custom Endpoint for {walker_name} on Node' ...));
+        } else {
+            # Default behavior: unchanged POST /walker/{name}/{node} and POST /walker/{name}
+            ...
+        }
     }
 }
@@ impl JacAPIServer.create_walker_parameters(
         field_type = walker_fields[field_name]['type'];
+        # TODO: Fix parameter type for GET requests (should be QUERY)
         if (field_name == '_jac_spawn_node') {
             param_type = ParameterType.PATH;
```

**What:**
- For each walker, the server looks for `__meta__`.
- **Tagged walker:** it upper-cases the method, converts it to `HTTPMethod`, and registers two endpoints, a "root" one and a "node" one, on the custom path.
- **Untagged walker:** it registers the same two default POST routes as before. The code was only re-indented.

**Why:** This is where the custom path and method actually take effect.

**Things to notice:**
- **Both custom endpoints use the identical method and path.** The "node" variant does not add `{node}` to the path, but its parameters come from `invoke_on_root=False`. That likely includes `_jac_spawn_node` as a `PATH` parameter, and the path has no placeholder for it. The diff does not show how the underlying server handles two identical routes or a path parameter missing from the URL. In many routers the first route wins, which here is the root one. If that holds, the node variant is unreachable. No test covers calling a custom-path walker on a specific node.
- The order flips compared with the default branch. Custom registers root first, then node. Default registers node first, then root.
- **A tagged walker loses its default routes.** After `@meta(path="/custom/get")`, `POST /walker/GetWalker` no longer exists. The PR description does not mention this.
- `HTTPMethod(method_str)` with an unknown verb probably raises at startup, if `HTTPMethod` is an enum. Its definition is not in the diff.
- If `__meta__` lacks `path` (possible only when set by hand), `path` is `None`, and the result is not handled.
- Custom paths are not checked for clashes with built-in routes such as `/user/login`, or with other walkers' paths.
- `self.get_walkers()` is called again inside the loop. If it is expensive, this repeats work. The diff does not show its cost.
- The new `TODO` admits that GET walkers still get their fields as body parameters, not query parameters.

## 6. How execution flows after the PR

### 6.1 Loading the Jac file (decorator runs)

```text
jac start test_meta.jac
└─ Jac module is loaded
   ├─ import from jac_scale { meta }              ← NEW
   └─ @meta(path="/custom/get", method="GET") walker GetWalker
      └─ meta(...) returns decorator              ← NEW
         └─ decorator(GetWalker)
            └─ GetWalker.__meta__ = {'path': '/custom/get', 'method': 'GET'}  ← NEW
```

### 6.2 Server startup (routes registered)

```text
JacAPIServer.register_walkers_endpoints
└─ for walker_name in get_walkers()
   ├─ walker_cls = get_walkers()[walker_name]                 ← NEW
   ├─ meta = getattr(walker_cls, '__meta__', None)            ← NEW
   ├─ if meta:                                                ← NEW
   │  ├─ method = HTTPMethod(meta['method'].upper())
   │  ├─ add_endpoint(method, meta['path'], root callback)    ← NEW
   │  └─ add_endpoint(method, meta['path'], node callback)    ← NEW (same route as above)
   └─ else:
      ├─ add_endpoint(POST, /walker/{name}/{node}, node callback)   (unchanged)
      └─ add_endpoint(POST, /walker/{name}, root callback)          (unchanged)
```

### 6.3 A client calls a custom route

```text
GET /custom/get  (Authorization: Bearer <token>)
└─ server matches the custom route (root variant registered first)  ← NEW
   └─ create_walker_callback(GetWalker, has_node_param=False)
      ├─ walker fields read as body params (not query)              ← TODO in PR
      └─ walker spawns on user's root → report → JSON {"reports": [...]}
```

| Scenario | Before | After |
|---|---|---|
| Walker without `@meta` | `POST /walker/X`, `POST /walker/X/{node}` | Same |
| Walker with `@meta(path="/p", method="GET")` | Not possible | `GET /p` runs on root |
| Same walker, `POST /walker/X` | Worked | **Gone** (behaviour change) |
| Same walker, run on a specific node | `POST /walker/X/{node}` | Unclear: the node variant shares `/p` and has no `{node}` |
| GET walker with fields, sent as `?val=x` | n/a | Probably not read (see TODO) |
| GET walker with fields, sent as JSON body | n/a | Works (tested) |
| `@meta(method="FOO")` | n/a | Likely error at startup |

## 10. Is it ready to merge?

**Not yet.**

1. The "node" custom endpoint duplicates the root endpoint's path and method and has no `{node}` placeholder. It is probably dead or broken, and nothing tests it.
2. GET walkers take their fields from the body (see the `TODO`). Many clients and proxies drop GET bodies, so GET with fields is fragile.
3. Tagged walkers silently lose their default routes. This behaviour change is not documented.
4. The PR "Closes #4299", but implements only a part of it: no headers, query params or timeout, and a decorator instead of a `__meta__` field.
5. There is no input validation or route-clash detection.
6. On the good side, CI is fully green and the untagged path is unchanged.

The PR is already closed, so these items apply to a reopen or a follow-up PR.

**Before merging (or in a follow-up):**
- Decide the node-variant route. Use e.g. `f"{path}/{{node}}"`, or drop the second endpoint.
- Make GET fields `ParameterType.QUERY` and change `test_custom_query_endpoint` to use `params=`.
- Validate `method` against `HTTPMethod` in `meta()` with a clear error message.
- Document that `@meta` replaces the default routes, or keep both.
- Fix the release note "(GET/POST)" wording and the "specs" naming in the test file.
- Open a follow-up issue for headers, query params and timeout, or reopen #4299, since the description claims to close it.

**Where the description disagrees with the code:**

- The description says the tests verify "correct walker execution over both POST and GET". The "query" test sends a body, not query parameters.

## 11. Questions your senior might ask

**Q: Where does the custom route get registered?**
In `JacAPIServer.register_walkers_endpoints` in `serve.impl.jac`. It reads `walker_cls.__meta__` and calls `add_endpoint` with the custom path and method.

**Q: What happens to `POST /walker/GetWalker` once `@meta` is added?**
It is no longer registered. The `if meta` branch replaces the default branch completely.

**Q: How do I run a `@meta` walker on a non-root node?**
It is unclear that you can. The second custom endpoint uses the same path with no `{node}`, so it likely collides with the root endpoint. No test covers it.

**Q: Do GET walkers read query parameters?**
No. Fields are still treated as body parameters, which the PR's own `TODO` notes. The "query" test passes data as a JSON body on a GET.

**Q: What if someone writes `@meta(path="/x", method="fetch")`?**
It becomes `"FETCH"`, and `HTTPMethod("FETCH")` probably raises at startup. Nothing checks it earlier.

**Q: Why a decorator instead of the `__meta__ = {...}` field the issue proposed?**
The PR does not say. The decorator only sets `__meta__`, so the server would also honour a hand-set `__meta__` attribute.

**Q: Does this cover headers, query params and timeout from #4299?**
No. Only `path` and `method` exist in `meta()`.

**Q: Could a custom path clash with `/user/login` or with another walker?**
Yes. Nothing checks for clashes. What happens then depends on the underlying router, which the diff does not show.

**Q: Did existing behaviour change for normal walkers?**
No. The `else` branch registers the same two POST routes as before. Only indentation changed, and `test-scale` passed.
