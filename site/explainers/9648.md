# fix(scale): add the default memory HPA trigger only when memory_request is configured

[#9648](https://github.com/jaseci-labs/jac/pull/9648) by @akindu-k · opened 29 Sept 2026 · +78 −26 in 6 files

<!-- explainer -->

## In short

Every app deployed with jac-scale got a memory autoscaling rule at 80% of its memory request, even when you never set `memory_request`. In that case the request was a `1Gi` fallback (`2Gi` for the gateway). A Jac server that idles above ~819Mi then looked "overloaded" with zero traffic, and Kubernetes scaled it to the maximum pod count and kept it there. Your PR adds the default memory rule only when `memory_request` was actually set by the user. The `1Gi`/`2Gi` fallback still applies to the pod itself.

## Words to know

- **Kubernetes**: A system that runs your app as containers on a cluster of machines. jac-scale generates Kubernetes config ("manifests") for Jac apps.
- **Pod / replica**: A pod is one running copy of your app. "Replicas" is how many copies run at once.
- **HPA (Horizontal Pod Autoscaler)**: A Kubernetes object that adds or removes replicas based on metrics such as CPU or memory use.
- **Memory request (`memory_request`)**: The amount of memory a container asks Kubernetes to reserve. The HPA measures memory use as a percentage of this number. For example, 900Mi used against a 1Gi request is about 88%.
- **Fallback / default request**: When you don't set `memory_request`, jac-scale still gives the container `1Gi`, or `2Gi` for the gateway, so the pod has a reservation.
- **Gateway**: The front service in a microservice deployment that routes requests to the other services. It gets a bigger default request.
- **Trigger**: One scaling rule, such as "scale when CPU > 50%" or "scale when memory > 80%". `KubernetesTarget` builds a list of `Trigger` objects for each service.
- **KEDA**: An alternative autoscaler engine that jac-scale supports alongside the plain HPA. It is only mentioned here because the docs say the skip rule applies under both engines.
- **`max_replicas`**: The upper limit on replica count. `ScalingLimited=TooManyReplicas` is the HPA status saying "I want more pods, but I'm at the limit."
- **Idle RSS**: How much memory a process actually uses while doing nothing (RSS = resident set size). For Jac apps it ranges from ~150 MiB to 3.2 GiB (#8222).
- **`ManifestBuilder`**: The jac-scale class that turns config into Kubernetes manifests. It also produces a per-service "autoscaler config" dictionary.
- **`KubernetesTarget`**: The deploy target that reads that autoscaler config and builds the trigger list.
- **`[scale.kubernetes]` / `[apps.<name>.scale]`**: Sections in `jac.toml`. The first sets global Kubernetes settings. The second sets per-app overrides.
- **e2e test / fixture**: An end-to-end test runs against a real cluster. The fixture is the sample project it deploys. Here it is a "zero-config" project, meaning it sets almost nothing.
- **Heredoc**: A shell syntax (`<<'TOML' ... TOML`) for writing a multi-line block of text into a file or command.
- **Table-driven test**: One test that loops over a list of input/expected-output rows instead of repeating assertions.
- **Release-notes fragment**: A small file under `release_notes/unreleased/` that is later collected into the changelog.

## The problem

Here is what happened before your PR for a service with no `memory_request`:

1. `ManifestBuilder._resolved_memory_request` looked for the service's `memory_request`. If there was none, it used the global `[scale.kubernetes]` value. If there was still none, it used `"1Gi"`, or `"2Gi"` for the gateway.
2. The autoscaler config set `has_memory_request = bool(<that resolved value>)`. Because of the fallback, this was always `True`, unless someone explicitly wrote `memory_request = ""`.
3. `KubernetesTarget` saw `has_memory_request` was true and added a default `memory` trigger at 80%.
4. The HPA therefore had `metrics = [cpu, memory 80]` against a `1Gi` request. The PR description says you reproduced this on main.
5. 80% of 1Gi is ~819Mi. A Jac server that idles above that reads over 100% with no traffic.
6. The HPA adds a pod. The new pod boots to the same idle memory, so the average never drops. The HPA keeps adding pods until `max_replicas` and stays there (`ScalingLimited=TooManyReplicas`).

Any app that didn't set `memory_request` and idled above ~80% of its fallback was affected. It ran (and paid for) the maximum number of pods all the time.

The guard was meant to answer "did the user give a memory request?" But it was computed after the default was filled in, so it could never say no.

The issue also suggested a bigger default request instead. You didn't take that route: idle memory varies too much across apps and releases (~150 MiB to 3.2 GiB) for any fixed default to be safe.

## The changes, one by one

### `manifest_builder.jac`: separate "configured" from "resolved"

You split the lookup into two methods:

```jac
def _configured_memory_request(svc_cfg: dict[str, any]) -> str | None {
    val = svc_cfg.get("memory_request");
    return self.k8s_config.memory_request if val is None else val;
}

def _resolved_memory_request(svc_cfg: dict[str, any], is_gateway: bool) -> str {
    val = self._configured_memory_request(svc_cfg);
    if val is None {
        val = "2Gi" if is_gateway else "1Gi";
    }
    ...
```

- `_configured_memory_request` returns what the user set. It checks the service value first, then the global `[scale.kubernetes]` value. It has no default, so it can return `None`.
- It checks `is None`, not "is empty". So a service that sets `memory_request = ""` overrides a global value, and a service value like `"512Mi"` overrides a global `""`.
- `_resolved_memory_request` now calls the new method and then applies the `1Gi`/`2Gi` fallback, exactly as before. The pod's actual memory request is unchanged.

In `_get_autoscaler_config` you added one key:

```jac
"has_memory_request": bool(
    self._resolved_memory_request(svc, svc_name == GATEWAY_NAME)
),
"memory_request_configured": bool(self._configured_memory_request(svc)),
```

- `has_memory_request` keeps its old meaning: "after defaults, is there a non-empty request?"
- `memory_request_configured` is new. It is true only if the user set a non-empty value. Both `None` and `""` give `False`.

**Why:** this is the root-cause fix. It gives the target a signal that isn't spoiled by the fallback.

### `target.jac`: seed the default memory trigger only when configured

```jac
-            if has_memory_request {
+            if cfg.get("memory_request_configured", False) {
                 triggers.append(
                     Trigger(
                         type="memory",
```

- `KubernetesTarget` builds the default trigger list: a CPU trigger, plus a memory trigger only if this condition is true.
- Before, the condition was `has_memory_request`, which was effectively always true. Now it reads `memory_request_configured` from the autoscaler config.
- `.get(..., False)` means a config dict without the key, such as an older or hand-built one, gets no memory trigger.

**Why:** this is where the bad memory trigger was added. Only this one line changed.

Things the diff does not show, so I can't confirm the code myself:

- The PR description says two other behaviours are unchanged: a memory trigger you list yourself in `triggers` is still used against a defaulted request, and the existing skip-with-warning for `memory_request = ""` still applies.
- The tests support the first claim. A user-listed memory trigger with only a defaulted request produces `["memory"]`.
- `has_memory_request` presumably still drives that skip guard, but that code isn't in the diff.

### `k8s_microservice_real_e2e.sh`: the real-cluster test expects CPU-only HPAs by default

This nightly script deploys a zero-config fixture to a real cluster and checks the HPAs. Your PR changes two things in it.

**1. It appends a `memory_request` for one app**, so the cpu+memory path is still tested on a real cluster:

```bash
if ! grep -q "e2e-harness memory_request" "${PROJECT_DIR}/jac.toml"; then
    cat >> "${PROJECT_DIR}/jac.toml" <<'TOML'
# --- e2e-harness memory_request (appended by k8s_microservice_real_e2e.sh) ---
[apps.cart_app.scale]
memory_request = "1Gi"
TOML
```

- `grep -q` checks for a marker comment, so running the script twice doesn't append the block twice.
- The block uses its own marker, not the existing overlay's. The code comment explains why: the earlier overlay is already committed in the fixture, so that overlay's guard never appends anything.
- The heredoc adds `memory_request = "1Gi"` under `cart_app` only.

**2. It changes the HPA check** from "every HPA must have cpu+memory" to:

```python
MEMORY_DEPLOYMENT = "cart-app-deployment"
if not any(h["spec"]["scaleTargetRef"]["name"] == MEMORY_DEPLOYMENT for h in items):
    sys.exit(f"FAIL: no managed HPA targets {MEMORY_DEPLOYMENT}")
...
expected = ["cpu", "memory"] if spec["scaleTargetRef"]["name"] == MEMORY_DEPLOYMENT else ["cpu"]
```

- The first check fails if no HPA targets the cart app's Deployment. Without it, the memory case could silently go untested.
- For each HPA, the expected metrics are cpu+memory for the cart app and cpu only for everything else.
- The `echo` header text was updated to match.

**Why:** the old assertion would fail after the fix. The new one checks both sides of the new rule.

### `jac-scale-kubernetes.md`: docs

There are two doc edits:

- The note under the autoscaler settings used to say the memory trigger is skipped only when `memory_request = ""`. It now says the default memory trigger is added only when `memory_request` is set for the app or in `[scale.kubernetes]`. It also says the `1Gi`/`2Gi` fallback never adds one, and explains why: an idle server can exceed 80% and pin the HPA at `max_replicas`.
- The `hpa.memory_target` row no longer says "always, unless `memory_request` is explicitly set to `""`". It now gives the same new rule.

This is a one-line changelog entry: idle apps are no longer pinned at max replicas, because the memory trigger is only added when `memory_request` is set.

## How it runs now

1. A user runs `jac scale deploy`. jac-scale reads `jac.toml`, including the `[scale.kubernetes]` and `[apps.<name>.scale]` sections.
2. For each service, `ManifestBuilder` builds the Deployment. The container's memory request comes from `_resolved_memory_request`: service value, else global value, else `1Gi`/`2Gi`. This is unchanged in behaviour; it now calls the helper internally.
3. `ManifestBuilder._get_autoscaler_config(svc)` builds the autoscaler dict:
   - It computes `has_memory_request` from the resolved value, as before.
   - (new) It computes `memory_request_configured` from `_configured_memory_request`, which never applies a default.
4. `KubernetesTarget` reads that dict and starts the default trigger list with a CPU trigger.
5. (changed) It appends a default memory trigger only if `memory_request_configured` is true.
6. If the user listed their own `triggers`, those are used, including a memory trigger against a defaulted request. The existing guard still skips a memory trigger with a warning when the request resolves to `""`. This step is unchanged according to the description; the code isn't in the diff.
7. The triggers become HPA metrics. A service without a configured `memory_request` now gets a CPU-only HPA, so idle memory no longer drives it to `max_replicas`.

## Tests

All tests are in `tests/deploy/test_memory_trigger_guard.jac`. The test count stays at 9.

**`builder resolves has_memory_request from service, global, and defaults`** is now table-driven. Each row builds a `ManifestBuilder` with some services and a global `memory_request`, then checks both `has_memory_request` and `memory_request_configured`:

| Service setting | Global | Service checked | has_memory_request | configured | What it proves |
|---|---|---|---|---|---|
| none | none | `billing_ops` | True | **False** | The fallback no longer counts as "configured" |
| none | none | gateway | True | **False** | Same for the gateway's `2Gi` fallback |
| `"512Mi"` | none | `billing_ops` | True | True | A per-service value counts |
| none | `"2Gi"` | `billing_ops` | True | True | A global value counts |
| `""` | none | `billing_ops` | False | False | Explicit empty still disables |
| none | `""` | `billing_ops` | False | False | Empty global disables |
| `"512Mi"` | `""` | `orders_ops` | True | True | A service value overrides an empty global |

Each assertion includes the row as its failure message, so a failing case is easy to identify.

**`memory triggers are seeded or skipped based on the configured request`** runs the `_triggers` helper, which turns an autoscaler config into trigger types, over these rows:

- `{}` gives `["cpu"]`. The old expectation was `["cpu", "memory"]`, so this row shows the behaviour change directly.
- `has_memory_request: True` alone gives `["cpu"]`. A resolved request is no longer enough.
- `has_memory_request` plus `memory_request_configured` gives `["cpu", "memory"]`.
- `has_memory_request: False` gives `["cpu"]`, as before.
- A real builder config with no request gives `["cpu"]`. A real builder config with `"512Mi"` gives `["cpu", "memory"]`. These two rows come from the later commit "cover the builder-to-target memory trigger handoff". They check that the key the builder writes is the key the target reads.
- A user-listed memory trigger with only a defaulted request gives `["memory"]`. This shows user triggers are still honoured. It also shows they replace the default CPU trigger rather than adding to it.

The rest of that test, the `explicit = {...}` part, is cut off in the diff, so I can't describe it.

## Explaining it in one minute

"Every jac-scale HPA got a memory trigger at 80% of the memory request, even when the app never set `memory_request`. The check for whether to add it ran after we filled in the `1Gi` default, so it was always true. A Jac server that idles above about 819Mi then reads over 100% with no traffic. Every new pod boots to the same memory, so the HPA climbs to `max_replicas` and sticks there. I split the lookup in `ManifestBuilder`: `_configured_memory_request` returns only what the user set, and the autoscaler config now exposes a `memory_request_configured` flag. `KubernetesTarget` adds the default memory trigger only when that flag is true. The pod still gets the `1Gi`/`2Gi` request, and user-listed memory triggers still work. I didn't raise the default instead, because idle memory ranges from 150 MiB to 3.2 GiB across apps, so no fixed number is safe. The unit tests are now table-driven over service, global, default and empty settings, and they check the builder-to-target handoff. The nightly e2e now sets `memory_request` on one app and expects cpu+memory there and cpu-only everywhere else. Local tests couldn't run, so we're relying on CI."
