## 1. The short version

`jac scale deploy` builds a Kubernetes HPA (Horizontal Pod Autoscaler) for every managed app. Since #7445, the HPA got a second metric next to CPU: memory at 80% of the container's memory **request**. If the app never set `memory_request`, jac-scale quietly used a fallback request of `1Gi` (`2Gi` for the gateway).

**The guard that decides whether to add the memory metric, `has_memory_request`, was computed after that fallback, so it was always true, and every HPA got a memory metric based on a request nobody chose.** A jac server idles at about 1.7 GiB. Against 80% of `1Gi` (about 819 MiB), the HPA in the issue read `memory: 166%/80%` with zero traffic. New pods boot to the same 1.7 GiB, so the HPA scaled to `max_replicas` (10) and stayed there with `ScalingLimited=TooManyReplicas`.

**You split "what the user configured" from "what the pod finally gets". The builder now also reports `memory_request_configured`, and the target adds the default memory trigger only when that is true.** Pods still get the `1Gi`/`2Gi` fallback request. A memory trigger that the user lists in `triggers` is still honored. Docs, a release note, the unit tests and the nightly real-cluster e2e script were updated to match.

## 3. The problem, step by step

### 3.1 The setup

- **Config:** the app sets CPU scaling (e.g. `cpu_target = 70`, min 2, max 10) and no `memory_request`.
- **`ManifestBuilder`:**
  - It resolves the pod's memory request, falling back to `1Gi`/`2Gi`.
  - It builds the autoscaler config dict, including `has_memory_request = bool(resolved request)`.
- **`KubernetesTarget`:**
  - It seeds a `cpu` trigger.
  - It adds a default `memory` trigger (target 80) when `has_memory_request` is true.
- **Kubernetes HPA:** it evaluates memory as a percent of the request.

### 3.2 What went wrong: no `memory_request` set

```text
1. jac.toml: no memory_request for the app, none under [scale.kubernetes]
2. _resolved_memory_request: service → None, global → None → fallback "1Gi"
3. has_memory_request = bool("1Gi") = True          ← WRONG: true even though nobody chose 1Gi
4. Target seeds triggers = [cpu 70, memory 80]
5. HPA memory target = 80% of 1Gi ≈ 819Mi per pod
6. Pods idle at ~1700Mi → memory reads 166%/80%, CPU reads 0%/70%
7. HPA scales up: 2 → … → 10 replicas (each new pod also idles at ~1700Mi)
8. At 10: desired = ceil(10 × 166/80) = 21 > max 10 → ScalingLimited=TooManyReplicas
9. The metric never drops below 80%, so the HPA stays at 10 forever
```

There was no config that removed the memory trigger except `memory_request = ""`. With that setting the pod has no memory request at all.

### 3.3 Why it mattered

- The issue's example app ran 10 × 1.7 GiB = 17 GiB reserved for zero requests. That is 5× its `min_replicas` cost. jacBuilder#1530 says memory is the binding constraint on that cluster.
- The user's `cpu_target` became dead configuration, because the memory metric always dominated.
- It hit every app without an explicit `memory_request`, including every jacBuilder app, since those apps cannot set one.
- It defeated the guardrail's own purpose: a fleet already at max cannot scale when real memory pressure arrives.
- `jac scale doctor` never warned, because the fallback hid the unset value.

## 4. The idea of the fix (one sentence)

> **Decide on the memory trigger from the configured request, not the defaulted one.** Keep the `1Gi`/`2Gi` fallback for the pod, but add the default memory trigger only when the user set `memory_request`.

A bigger default would not have been safe. As your description says, idle RSS ranges from ~150 MiB to 3.2 GiB (#8222), so no fixed number keeps 80% of it above idle for every app and release. Asking for an explicit request is the precondition `doctor` already names.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/deploy/target/kubernetes/manifest_builder.jac`: separate "configured" from "resolved"

```diff
-    def _resolved_memory_request(svc_cfg: dict[str, any], is_gateway: bool) -> str {
+    def _configured_memory_request(svc_cfg: dict[str, any]) -> str | None {   # NEW: no fallback

-        if val is None {

+        return self.k8s_config.memory_request if val is None else val;

+    def _resolved_memory_request(svc_cfg: dict[str, any], is_gateway: bool) -> str {
+        val = self._configured_memory_request(svc_cfg);                     # reuse the lookup
         if val is None {
             val = "2Gi" if is_gateway else "1Gi";                              # fallback unchanged
         }
@@ _get_autoscaler_config
             "has_memory_request": bool(
                 self._resolved_memory_request(svc, svc_name == GATEWAY_NAME)
             ),
+            "memory_request_configured": bool(self._configured_memory_request(svc)),  # NEW
```

**What:**
- `_configured_memory_request` returns the service's `memory_request` if the key is present, else the global `[scale.kubernetes]` value. It returns `None` when neither is set.
- `_resolved_memory_request` now calls it and only then applies the `1Gi`/`2Gi` fallback.
- The autoscaler config gains `memory_request_configured`.

**Why:** this gives the target a truthful answer to "did the user choose a request?". Before, it only had `has_memory_request`, which was always true unless the request was `""`.

**Things to notice:**
- The check is `val is None`, not "falsy". A service `memory_request = ""` overrides a global `"2Gi"`. The result is `""`, so both flags are false.
- `bool("")` is false, so an explicit empty request is "not configured". This matches the old skip behaviour.
- `has_memory_request` is kept on purpose. The target still uses it to skip a user-listed memory trigger when the request is `""`.
- Pod resources are unchanged. The container still gets `1Gi`/`2Gi`.

## 6. How execution flows after the PR

### 6.1 Rendering the autoscaler for one service

```text
jac scale deploy app.jac
└─ ManifestBuilder._get_autoscaler_config(svc_name)
   ├─ (hpa.enabled = false → returns None, unchanged)
   ├─ has_memory_request = bool(_resolved_memory_request(svc, is_gateway))
   │   └─ _configured_memory_request(svc)               ← NEW (shared lookup)
   │       ├─ svc["memory_request"] if the key is present
   │       └─ else k8s_config.memory_request (may be None)
   │   └─ None → "1Gi" / "2Gi" gateway (pod request; unchanged)
   ├─ memory_request_configured = bool(_configured_memory_request(svc))   ← NEW
   └─ returns {…, has_memory_request, memory_request_configured, triggers, behavior}
└─ KubernetesTarget trigger seeding (_resolve_service_triggers per the issue)
   ├─ no user triggers → seed [cpu]
   │   └─ if memory_request_configured → append memory(80)  ← CHANGED (was has_memory_request)
   └─ user triggers listed → honored; a memory trigger is skipped only if the resolved request is ""
└─ HPA manifest metrics = cpu-only or cpu+memory
```

### 6.2 Nightly real-cluster e2e

```text
k8s_microservice_real_e2e.sh
├─ append overlay: [apps.cart_app.scale] memory_request = "1Gi"        ← NEW
├─ deploy the fixture to the cluster
└─ verify HPAs
   ├─ fail if no HPA targets cart-app-deployment                     ← NEW
   ├─ cart-app-deployment → expect [cpu, memory]                     ← CHANGED
   └─ every other HPA → expect [cpu]                                 ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| No `memory_request` anywhere | cpu + memory (against 1Gi/2Gi) | **cpu only** |
| Gateway, no `memory_request` | cpu + memory (against 2Gi) | **cpu only** |
| Service `memory_request = "512Mi"` | cpu + memory | cpu + memory |
| Global `memory_request = "2Gi"` | cpu + memory | cpu + memory |
| Service or global `memory_request = ""` | cpu only | cpu only |
| Global `""`, service `"512Mi"` | cpu + memory | cpu + memory |
| User lists a memory trigger, request defaulted | memory kept | memory kept |
| Pod container memory request when unset | 1Gi / 2Gi | 1Gi / 2Gi (unchanged) |

**Behaviour change users will notice:** apps without `memory_request` lose the memory metric on their next deploy. They then scale on CPU only and can settle back to `min_replicas`.

Anyone who relied on the implicit memory guardrail must now set `memory_request`. The diff does not show how an already-deployed HPA is updated when its metrics shrink. It presumably happens on the next `jac scale deploy`, but that can't be confirmed from the diff.

## 11. Questions your senior might ask

**Q: Why not just raise the default request instead?**
Idle RSS has ranged from ~150 MiB to 3.2 GiB across apps and releases (#8222). Any fixed default either wastes memory or still sits below some app's idle footprint. Requiring an explicit request matches what `doctor` already says is needed.

**Q: Does this change what pods reserve?**
No. `_resolved_memory_request` still falls back to `1Gi`/`2Gi` for the container request. Only the HPA metric list changes.

**Q: Why keep `has_memory_request` at all?**
The target still uses it to skip a user-listed memory trigger when the request is explicitly `""`, because Kubernetes cannot compute utilization without a request. The new flag only controls the *default* memory trigger.

**Q: What happens if someone sets `memory_request = ""` for a service but `"2Gi"` globally?**
The service key is present (not `None`), so `""` wins. Both flags are false, and the service gets no request and no memory trigger. This is the same as before.

**Q: Does this cover both the HPA and KEDA engines?**
Yes, per @MusabMahmoodh. `_get_autoscaler_config` → `_resolve_service_triggers` is the only path that seeds the default trigger, and both engines use it.

**Q: The flags default in opposite directions. Couldn't that hide a bug?**
That is why the test now feeds real `_get_autoscaler_config` output into the target, in both directions. A missing or renamed key would show up as a test failure, not a silent default.

**Q: Will existing deployments change?**
Apps without `memory_request` lose the memory metric on their next deploy and can settle back to `min_replicas`. The diff does not show how jac-scale updates an existing HPA. That depends on the apply logic, which is outside this PR.

**Q: Is the real-cluster change verified?**
Not yet. The script runs only in nightly CI. PR CI covers the same logic through the new table rows.

**Q: Does this fix jacBuilder users today?**
Not until it is backported. jacBuilder pins 0.34.x, and this PR merged to `main`. The issue asks for it to ride the #8940 backport line.

**Q: Why use `1Gi` for `cart_app` in the e2e?**
It equals the fallback, so the cart pod's resources match the other apps. The only difference is that the value is *configured*, which isolates the flag being tested.
