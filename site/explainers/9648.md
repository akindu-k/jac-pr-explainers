## 1. The short version

jac-scale deploys Jac apps to Kubernetes. For each app it writes an **HPA** (Horizontal Pod Autoscaler), the Kubernetes object that adds or removes pods based on metrics. Since #7445, that HPA has carried two metrics: CPU, and memory at 80% of the container's memory **request**.

**The bug: the memory metric was added even when nobody set `memory_request`, because the check ran after the silent `1Gi` fallback (`2Gi` for the gateway), so it was always true.** A jac server idles at about 1.7 GiB, which reads as `memory: 166%/80%` at zero traffic. New pods boot to the same 1.7 GiB, so the number never drops. The HPA scales to `max_replicas` and stays there, reporting `ScalingLimited=TooManyReplicas`. In the issue, one app ran 10 pods at 1–3 millicores of CPU each.

**The fix: the builder now records whether `memory_request` was actually configured (on the service or under `[scale.kubernetes]`), and the target adds the default memory trigger only when it was.** The pod still gets the `1Gi`/`2Gi` request. A memory trigger that the user lists explicitly is still honored. Docs, a release note and the nightly real-cluster e2e script are updated to match.

**Status:** Open, with no approval yet. @MusabMahmoodh left one "commented" review and called the PR a draft at that time. You answered both of his inline comments. The Greptile bot scored it 5/5. `build-kit` is still running on head `6c00870`.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Pod / Deployment | A pod is one running copy of your app. A Deployment keeps N identical pods running. |
| Resource request | The amount of CPU or memory a pod reserves, e.g. `requests: {memory: "1Gi"}`. |
| Resource limit | The hard cap. Above it, the pod is killed (OOM, "out of memory"). In the issue: limit `4Gi`, request `1Gi`. |
| Utilization % | Usage divided by **request**, not by limit. 1700Mi ÷ 1024Mi ≈ 166%. |
| RSS | Resident memory: what the process actually holds in RAM. A jac server idles at roughly 150 MiB to 3.2 GiB depending on release (#8222). |
| HPA | Kubernetes Horizontal Pod Autoscaler. It computes `desired = ceil(current × actual/target)` and adds or removes pods between min and max. |
| `max_replicas` / `ScalingLimited=TooManyReplicas` | The HPA's upper bound, and the status it shows when it wants more pods than that bound allows. |
| metrics-server | The cluster component that feeds CPU and memory usage to the HPA. |
| KEDA | An alternative autoscaler engine that jac-scale supports (`autoscaler_engine = "keda"`). |
| Trigger | jac-scale's internal description of one scaling rule (type `cpu`, `memory`, …). Each trigger becomes one HPA metric or one KEDA trigger. |
| `[scale.kubernetes]` | The global jac-scale section in `jac.toml`. It can set `memory_request` for all apps. |
| `[apps.<name>.scale]` | The per-app override section in `jac.toml`. |
| Gateway | The special front service in microservice deploys (`GATEWAY_NAME`). Its fallback request is `2Gi`. |
| `ManifestBuilder` | Class in `manifest_builder.jac` that turns config into Kubernetes manifests and autoscaler config. |
| `_resolved_memory_request` | Returns the request the **pod** gets: service value, else global value, else `1Gi`/`2Gi`. |
| `_configured_memory_request` | New. The same lookup without the fallback. Returns `None` if nobody set it. **This is what the PR adds.** |
| `_get_autoscaler_config` | Builds the per-service dict passed to the target: `has_memory_request`, `triggers`, `behavior`, and now `memory_request_configured`. |
| `has_memory_request` | `bool(_resolved_memory_request(...))`. Because of the fallback, it is true unless someone sets `memory_request = ""`. **This is where the bug is:** it was used as the "add memory trigger?" guard. |
| `memory_request_configured` | New key: `bool(_configured_memory_request(svc))`. |
| `KubernetesTarget` / `_resolve_service_triggers` | Code in `target.jac` that reads the autoscaler dict and builds the trigger list. Per the reviewer, it is the only place the default memory trigger is created, for both engines. |
| `jac scale deploy` / `jac scale doctor` | The deploy command, and a config checker that warns about problems (the issue says it warns when `memory_request` is unset, but the fallback hid that). |
| Table-driven test | One test that loops over rows of `(input, expected)`. |
| Real-cluster e2e | `k8s_microservice_real_e2e.sh`: deploys a fixture project to a real cluster and checks the result. It runs only nightly. |
| Release-note fragment | A small file in `release_notes/unreleased/` that is collected into the changelog. |

## 3. The problem, step by step

### 3.1 The setup

- `ManifestBuilder._get_autoscaler_config(svc)` produces a dict for one service.
- `KubernetesTarget._resolve_service_triggers` turns that dict into triggers. When the user lists no triggers, it seeds a default `cpu` trigger and, if a guard is true, a default `memory` trigger at `memory_utilization_target = 80`.
- Before this PR the guard was `has_memory_request`.

### 3.2 What went wrong: app with no `memory_request`

```text
1. jac.toml: no memory_request on the app, none under [scale.kubernetes]
2. _resolved_memory_request(svc) → service None → global None → fallback "1Gi"
3. has_memory_request = bool("1Gi") = True              ← WRONG: true for a value nobody chose
4. _resolve_service_triggers: seeds cpu, then memory (80% of request)
5. Pod spec: requests.memory = 1Gi; HPA metrics = [cpu 70%, memory 80%]
6. Pod boots, idles at ~1700Mi → memory = 166% of 1Gi (threshold is 819Mi)
7. HPA: desired = ceil(2 × 166/80) = 5 → scale up
8. New pods also idle at ~1700Mi → still 166%
9. Repeats until replicas = max_replicas (10); ScalingLimited=TooManyReplicas, permanently
```

### 3.3 Why it mattered

- The issue says every app deployed without `memory_request` hits this. That includes every jacBuilder app, because they cannot set one (jaseci-labs/jacBuilder#1658).
- One app held 10 × 1.7 GiB = 17 GiB for zero requests, five times its `min_replicas` cost. Memory is the scarce resource on that cluster (jacBuilder#1530).
- The user's `cpu_target` became dead configuration.
- The guardrail also defeated itself: a fleet already at max has no room to scale when real memory pressure arrives.

## 4. The idea of the fix (one sentence)

> **Only a memory request someone chose may add a memory trigger.** The builder now reports whether `memory_request` was configured, separately from the value the pod gets, and the target uses that flag to decide on the default memory trigger.

This follows the issue's first suggested fix. Raising the default request instead would not work, because idle RSS ranges from about 150 MiB to 3.2 GiB across apps and releases (#8222), so no fixed default is safe.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/deploy/target/kubernetes/manifest_builder.jac`: separate "configured" from "resolved"

```diff
-    def _resolved_memory_request(svc_cfg: dict[str, any], is_gateway: bool) -> str {
+    def _configured_memory_request(svc_cfg: dict[str, any]) -> str | None {   # NEW: no fallback
         val = svc_cfg.get("memory_request");
-        if val is None {
-            val = self.k8s_config.memory_request;
-        }
+        return self.k8s_config.memory_request if val is None else val;
+    }
+
+    def _resolved_memory_request(svc_cfg: dict[str, any], is_gateway: bool) -> str {
+        val = self._configured_memory_request(svc_cfg);                       # reuses the new helper
         if val is None {
             val = "2Gi" if is_gateway else "1Gi";                               # fallback unchanged
         }
@@
             "has_memory_request": bool(
                 self._resolved_memory_request(svc, svc_name == GATEWAY_NAME)
             ),
+            "memory_request_configured": bool(self._configured_memory_request(svc)),  # NEW key
```

**What:** You split the lookup in two. `_configured_memory_request` returns the service value, else the global value, else `None`. `_resolved_memory_request` calls it and then applies the `1Gi`/`2Gi` fallback. The autoscaler dict gets a new key, `memory_request_configured`.

**Why:** `has_memory_request` could never be false for an unset request. The new key can.

**Things to notice:**
- The pod's container request is unchanged. It still gets `1Gi`/`2Gi`.
- `has_memory_request` is kept. It still powers the existing skip guard for user-listed memory triggers when the request is `""`.
- The `None` checks are against `None`, not falsy values. So a service with `memory_request = ""` returns `""` and does **not** fall through to the global value. `bool("")` is `False`, so the result is "not configured", which is the same outcome as before for that case.
- The rest of `_resolved_memory_request` (its `return`) is outside the hunk. It is assumed to be unchanged.

## 6. How execution flows after the PR

### 6.1 Building the autoscaler config for one service

```text
_get_autoscaler_config(svc_name)
├─ (hpa.enabled false → returns None, unchanged)
├─ has_memory_request = bool(_resolved_memory_request(svc, is_gateway))
│    └─ _configured_memory_request(svc) → else fallback 1Gi/2Gi         ← CHANGED (refactor)
├─ memory_request_configured = bool(_configured_memory_request(svc))   ← NEW
└─ returns {has_memory_request, memory_request_configured, triggers, behavior}
```

### 6.2 Resolving triggers (HPA and KEDA)

```text
_resolve_service_triggers(cfg)
├─ user listed triggers? → use them; a memory trigger is skipped only if has_memory_request is False (unchanged)
└─ no user triggers → seed defaults
     ├─ cpu trigger (always)
     └─ memory trigger at 80% only if cfg.memory_request_configured     ← CHANGED
```

The user-listed branch is inferred from the test rows, not from visible code. The rest of `_resolve_service_triggers` is outside the diff.

| Scenario | Before | After |
|---|---|---|
| No `memory_request` anywhere | cpu + memory (80% of 1Gi) | **cpu only** |
| Gateway, no `memory_request` | cpu + memory (80% of 2Gi) | **cpu only** |
| Service sets `512Mi` | cpu + memory | cpu + memory |
| Global `[scale.kubernetes]` sets `2Gi` | cpu + memory | cpu + memory |
| `memory_request = ""` | cpu only | cpu only |
| User lists a memory trigger, request defaulted | memory kept | memory kept |
| Pod container memory request | 1Gi/2Gi fallback | unchanged |

**User-visible change:** On the next deploy, apps without `memory_request` lose the memory metric. Their HPA can then fall back to `min_replicas` at idle. The trade-off is that those apps also lose any memory-based scale-out. To get it back, they must set `memory_request`. Whether existing HPAs are rewritten on redeploy (rather than patched) is not visible in this diff.

## 11. Questions your senior might ask

**Q: Why not just raise the default request so 80% sits above idle RSS?**
Idle RSS ranges from about 150 MiB to 3.2 GiB across apps and releases (#8222), so no fixed default is safe. A larger default would also reserve memory nobody asked for.

**Q: Doesn't this remove OOM protection for apps that relied on the default memory trigger?**
Yes, for apps without `memory_request`. But that trigger never protected them: it pinned them at max, leaving no room to scale. To get memory scaling, set `memory_request`.

**Q: Does the pod's memory request change?**
No. `_resolved_memory_request` still applies `1Gi`/`2Gi` to the container. Only the HPA metric is affected.

**Q: Why keep `has_memory_request` at all?**
It still drives the existing guard that skips a user-listed memory trigger when the request is explicitly `""`. The PR leaves that behaviour unchanged.

**Q: Does KEDA get the fix too?**
Per @MusabMahmoodh, `_get_autoscaler_config` → `_resolve_service_triggers` is the only path that seeds the default, so both engines pick it up.

**Q: What if a service sets `""` but the global is `2Gi`?**
The service's `""` is not `None`, so the global is not consulted. `configured` is False and there is no memory trigger. This matches the old `has_memory_request` behaviour, but no test row covers it.

**Q: How do you know the builder and target agree, given the keys default in opposite directions?**
Two test rows pass the builder's real output into `_triggers`. The no-request row fails on `main`.

**Q: Was this run anywhere real?**
You reproduced the bug in-process on `main`: the HPA for a service with no request rendered `[cpu, memory 80]`. The fixed behaviour is checked by unit tests in CI and, for a real cluster, only by the nightly e2e.

**Q: What about `jac scale doctor` staying silent?**
Not changed here. With the memory trigger no longer seeded from a fallback, the "HPA pins at max" warning matters less. A doctor message about unset `memory_request` could be a follow-up.

**Q: Will 0.34.x users (jacBuilder) get this?**
Not from this PR, which targets `main`. The issue asks for a backport alongside #8940.
