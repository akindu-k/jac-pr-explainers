# fix(scale): add the default memory HPA trigger only when memory_request is configured

[#9648](https://github.com/jaseci-labs/jac/pull/9648) by @akindu-k · opened 29 Sept 2026 · +78 −26 in 6 files

<!-- explainer -->

## In short
Every autoscaler (HPA) that jac-scale created had a memory metric at 80% of the memory request, even when the app never set `memory_request`. The default request (`1Gi`) was used for the math, so an idle jac server could read over 100% and the HPA scaled to the maximum. You changed the code so the default memory trigger is added only when the user actually configured `memory_request`.

## Words to know
- **HPA (HorizontalPodAutoscaler)**: a Kubernetes object that adds or removes pods based on metrics such as CPU or memory use.
- **Memory request**: the amount of memory a container asks Kubernetes to reserve. HPA memory utilization is measured as a percentage of this number.
- **Trigger**: one metric rule for the autoscaler (for example `cpu` or `memory`, each with a target percentage).
- **`max_replicas`**: the upper limit on how many pods the HPA may run.
- **`ScalingLimited=TooManyReplicas`**: an HPA status saying it wants more pods than the maximum allows.
- **`ManifestBuilder`**: the class in jac-scale that builds the Kubernetes manifests (Deployment, HPA and so on).
- **`KubernetesTarget`**: the deploy class that takes the builder's autoscaler config and creates the trigger list.
- **`[scale.kubernetes]`**: the global section of `jac.toml` for Kubernetes settings. `[apps.NAME.scale]` holds per-app overrides.
- **Fallback / default request**: the `1Gi` value (`2Gi` for the gateway) used for the container when nothing is configured.
- **RSS**: the memory a process actually holds in RAM. The PR says idle jac RSS varies a lot between apps.
- **e2e script**: a shell script that deploys to a real cluster and checks the result (the nightly test).

## The problem
1. The builder worked out the memory request with `_resolved_memory_request`. If nothing was set, it fell back to `1Gi` (or `2Gi` for the gateway).
2. `has_memory_request` was computed from that resolved value, after the fallback. So it was always true unless the user wrote `memory_request = ""`.
3. Because of that, every HPA got a `memory` trigger at 80% of the request.
4. A jac server that idles above about 819Mi (80% of 1Gi) reads over 100% with no traffic. New pods start at the same baseline, so the HPA keeps adding pods until `max_replicas` and stays there.

So apps that never asked for memory-based scaling were pinned at maximum replicas while idle, which wastes resources.

## The changes, one by one

### `manifest_builder.jac`
You split the lookup in two:
- New `_configured_memory_request(svc_cfg)` returns the service's `memory_request`, else the global `[scale.kubernetes]` value, else `None`. It has no default.
- `_resolved_memory_request` now calls it and only then applies the `1Gi`/`2Gi` fallback. Pod resources do not change.

```
"has_memory_request": bool(self._resolved_memory_request(...)),
"memory_request_configured": bool(self._configured_memory_request(svc)),
```

- `has_memory_request` still means "the container has a non-empty request" (used for the skip guard).
- The new key `memory_request_configured` means "the user actually set a non-empty value". An empty string gives false for both.

### `target.jac`
The seeding of the default memory trigger changed from `if has_memory_request` to `if cfg.get("memory_request_configured", False)`. The default is `False`, so a config without the key gets CPU only. A memory trigger the user lists explicitly in `triggers` is still kept, and the existing skip for an empty request is unchanged.

### `k8s_microservice_real_e2e.sh`
The nightly cluster test expected `cpu+memory` on every HPA, which is no longer true.
- It appends `memory_request = "1Gi"` for `cart_app` to `jac.toml`, using its own marker, because the earlier overlay is already committed and its guard never appends.
- The check now requires an HPA for `cart-app-deployment`, expects `["cpu", "memory"]` for it and `["cpu"]` for all others.

### Docs and release note
`jac-scale-kubernetes.md` now says the default memory trigger is added only when `memory_request` is set, and that the fallback request never adds one. `9648.bugfix.md` adds the release note.

## How it runs now
1. `jac scale deploy` builds the manifests with `ManifestBuilder`.
2. `_get_autoscaler_config` runs for each service. It computes `has_memory_request` from the resolved request and (new) `memory_request_configured` from `_configured_memory_request`.
3. `KubernetesTarget` creates a CPU trigger always.
4. (changed) It adds the default memory trigger only if `memory_request_configured` is true.
5. User-listed triggers are applied as before, so a listed memory trigger still works, and the skip guard for an empty request still applies.
6. The container still gets the `1Gi`/`2Gi` fallback request.

## Tests
Both changes are in `test_memory_trigger_guard.jac`. The test count stays at 9. The PR says local `jac test` could not run, so it relies on CI.
- **Builder resolves `has_memory_request`**: now table-driven. Cases cover a service value, a global value, defaults (including the gateway), and empty values at service and global level. It asserts both `has_memory_request` and `memory_request_configured`. This proves the new builder flag is false for defaults and true only for configured values.
- **Memory triggers seeded or skipped**: rows check that an empty config or a defaulted request gives `["cpu"]`, a configured request gives `["cpu", "memory"]`, and a user-listed memory trigger with a defaulted request is kept (`["memory"]`). Two rows pass the builder's real output into the target logic, which covers the handoff between the two classes.

## Explaining it in one minute
Every HPA got a memory trigger because the "has a memory request" check ran after the `1Gi` fallback, so it was always true. Idle jac servers often use more than 80% of 1Gi, so apps were scaled to max replicas with no traffic. I added `_configured_memory_request`, which has no default, and a `memory_request_configured` flag. `KubernetesTarget` now seeds the memory trigger only when that flag is true. The pod still gets the fallback request, and explicit memory triggers still work. I did not raise the default request, because idle memory ranges from about 150 MiB to 3.2 GiB, so no fixed value is safe. I extended the unit tests for the builder and target, and updated the e2e script and docs. Local tests could not run, so CI is the check.
