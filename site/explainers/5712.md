## 1. The short version

Jac programs keep their graph (nodes, edges and their fields) in a memory layer. In local mode that layer is `SqliteMemory`, which keeps loaded objects in memory and writes them back to a SQLite database when `sync()` runs. Each walker (a Jac unit of work, such as one HTTP request) loads the nodes it touches and syncs them when it finishes.

**Before this PR, `sync()` compared the whole in-memory object with the database copy. If they differed in any way, it overwrote the database copy with the whole in-memory object, even if this walker never changed anything.** So a slow read-only walker holding an old copy could undo a newer write from another walker. In issue #5696, a user's `github_connected = True` silently went back to `False`, and `github_username` went back to `''`.

**You changed `sync()` so it writes back only the fields this walker actually changed.** On load, you store a hash (a short fingerprint number) of every field. On sync, you rehash each field and compare. Only fields whose hash changed, plus fields already flagged by the existing `__jac_dirty_fields__` tracking, are copied onto the database copy. A walker that changed nothing writes nothing and never reaches the write-access check.

**Status:** Merged on 2026-05-07. All test and lint checks on the head commit `3f2d155` passed. The release-pipeline jobs were skipped. No formal "Approve" review is recorded; the reviews were comments only.

## 3. The problem, step by step

### 3.1 The setup

- Several walkers can run in one process, each with its own `SqliteMemory` view of the same SQLite file. The tests model this with `mem_a`, `mem_b` and so on.
- On exit, a walker's memory runs `sync()`. For each anchor that already exists in the DB, the old code:
  1. computed `access_changed` and `archetype_changed` with `_canonical_json`;
  2. if either was true and `check_write_access` passed, replaced `stored_anchor.archetype` with the in-memory archetype as a whole;
  3. wrote the row.

### 3.2 What went wrong: read-only walker clobbers a newer write

```text
1. DB:            name="original"
2. Walker A get() A's copy: name="original"       (A only reads)
3. Walker B get() B's copy: name="original"
4. B sets name    B's copy: name="written_by_B"
5. B sync()       DB: name="written_by_B"
6. A sync()       stored_anchor.name="written_by_B", A's copy name="original"
                  archetype_changed = True                       ← WRONG: "differs" ≠ "A changed it"
7.                check_write_access(A's anchor) runs for a read-only walker
8.                stored_anchor.archetype = A's whole archetype
9. DB:            name="original"                               ✗ B's write silently lost
```

### 3.3 Failing case: two walkers change different fields

```text
1. DB:            name="init_name", count=0
2. A get()        A: name="init_name", count=0
3. B get()        B: name="init_name", count=0
4. B sets name="name_from_B", B sync()   DB: name="name_from_B", count=0
5. A sets count=42                       A: name="init_name", count=42
6. A sync()       whole archetype differs → replace whole archetype   ← WRONG
7. DB:            name="init_name", count=42                         ✗ B's name lost
```

### 3.4 Why the new design also needs hashes: in-place mutation

```text
1. DB: tags=["a"]
2. get() → loaded.tags.append("b")   no __setattr__ call → __jac_dirty_fields__ stays empty
3. If sync used only __jac_dirty_fields__, "tags" would be missed  ✗
```

The old whole-object comparison would probably have caught this case, because the lists differ. This case is therefore a risk of the new design, not a bug that existed before. The hash comparison covers it. The release note's phrase "in-place container mutations ... are also detected correctly" can read as if this was broken before. The diff does not show that.

### 3.5 Why it mattered

- The issue author (jacBuilder) lost days. A GitHub "Connect" looked successful, then `push_new` saw `github_connected=False`. There was no error and no log line.
- Later investigation showed MongoDB-backed production is not affected. The real production symptom was a separate bug: dangling edge references after a class rename. But local dev behaved differently from production, and that misled app authors.
- The issue suggested three fixes, smallest first: skip commits for read-only walkers, field-level dirty tracking, or an optimistic version check. You chose field-level dirty tracking, which also covers the read-only case.
- Side effect: read-only walkers reached `check_write_access` and could log access-denied. The existing test `test_serve_sync_skips_write_access_check_on_unchanged_anchors` forbids that.

## 4. The idea of the fix (one sentence)

> **Write back only what this walker changed.** Hash every field when the node is loaded, then on `sync()` copy only the fields whose hash changed (or that were explicitly assigned) onto the stored copy.

This targets the real mistake: the old code treated "my copy differs from the DB" as if it meant "I changed something". Merging field by field also keeps concurrent edits to different fields. A whole-object version check would instead reject or overwrite one of them.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/impl/memory.impl.jac`: snapshot on load

```diff
         self.__mem__[id] = cast(Anchor, anchor);
+        _sqlite_snapshot_field_hashes(cast(Anchor, anchor));   # NEW: baseline for dirty detection
         return cast(Anchor, anchor);
```

**What:** Right after `get()` caches an anchor loaded from the DB, it records a hash of each field.

**Why:** This gives `sync()` a "what it looked like when I loaded it" baseline. Without it, `sync()` can only compare against the DB, which another walker may have changed.

**Things to notice:** Only the DB-load path in `get()` snapshots. Anchors created with `put()` get no snapshot until a later sync write on the stored-anchor path (see 5.3). The diff does not show the "No stored or stored is a stub" branch, so you cannot tell from it whether brand-new anchors get a snapshot after their first save.

### 5.2 `jac/jaclang/runtimelib/impl/memory.impl.jac`: three new helpers

```diff
+def _sqlite_field_hash(val: object) -> int {
+    try { return hash(json.dumps(val, sort_keys=True, default=str)); }
+    except Exception { return hash(str(val)); }          # fallback for odd values
+}
+
+def _sqlite_snapshot_field_hashes(anchor: Anchor) -> None {
+    if not anchor.is_populated() or anchor.archetype is None { return; }
+    known = Serializer._get_field_types(type(arch)).keys();
+    for name in known {
+        serialized = Serializer._serialize_value(val, include_type=True, _seen=_seen);
+        hashes[name] = _sqlite_field_hash(serialized);
+    }
+    object.__setattr__(arch, '__jac_field_hashes__', hashes);   # bypasses archetype __setattr__
+}
+
+def _sqlite_derive_dirty_from_field_hashes(anchor: Anchor) -> set[str] {
+    stored = arch.__dict__.get('__jac_field_hashes__', {});
+    if not stored { return set(); }                      # no baseline → nothing hash-dirty
+    for name in known {
+        if _sqlite_field_hash(serialized) != stored.get(name) { dirty.add(name); }
+    }
+    return dirty;
+}
```

**What:**
- `_sqlite_field_hash` makes one number from a field's serialized value. It uses sorted-key JSON so dict key order doesn't matter.
- `_sqlite_snapshot_field_hashes` stores `{field: hash}` on the archetype.
- `_sqlite_derive_dirty_from_field_hashes` returns the names of fields whose current hash differs from the snapshot.

**Why:** Hashing the serialized value catches in-place changes (`list.append`, dict edits) that `__setattr__`-based tracking misses.

**Things to notice:**
- `object.__setattr__` writes the snapshot without going through the archetype's own `__setattr__`. The likely reason is so the snapshot itself is not tracked as a field change; the diff doesn't show the archetype's `__setattr__`.
- Python's string `hash()` changes per process. The PR description calls the hash "stable". It is only stable within one process, which is enough because the snapshot lives in memory.
- If there is no snapshot, the function returns an empty set. `sync()` then relies only on `__jac_dirty_fields__`.
- A field added to the class after the snapshot was taken has `stored.get(name) == None`, so it counts as dirty. That is probably the "schema-drift-aware" claim in the description.
- Each `sync()` now serializes every field of every cached anchor. There is a CPU cost, but no extra DB reads.

### 5.3 `jac/jaclang/runtimelib/impl/memory.impl.jac`: `sync()` merges only dirty fields

**What:**
- The dirty set is the union of explicitly assigned fields and hash-changed fields.
- The write-access check runs only if access or some field actually changed.
- Only dirty fields are copied onto `stored_anchor.archetype`, which is the DB version. The merged row is then written.
- After a write, the dirty tracking is cleared and a new snapshot is taken. A second `sync()` in the same session therefore writes nothing extra.

**Why:**
- Fixes 3.2: a read-only walker has an empty `dirty` set, so there is no write and no access check.
- Fixes 3.3: A copies only `count`, so B's `name` stays.

**Things to notice:**
- `changed = True` moved inside each branch. Before, passing the gate always meant a write.
- `AttributeError` is skipped silently, for example for a field that no longer exists.
- If two walkers change the same field, the last writer still wins with no warning. The issue asked for a "loud" failure (a log line); the PR adds none.
- Edge changes are not handled here. The new logic only looks at archetype fields and `access`. How edges are persisted is not visible in this diff.
- The gate order (dirty first, then the access check) is what @RagavRida asked for after the first push broke `test-core-runtime`. See section 9.

## 6. How execution flows after the PR

### 6.1 Loading a node

```text
SqliteMemory.get(id)
├─ (cache lookup / DB read / deserialize — not shown in diff)
├─ self.__mem__[id] = anchor
├─ _sqlite_snapshot_field_hashes(anchor)                       ← NEW
│   ├─ skip if not populated or archetype is None
│   ├─ for each declared field: serialize → hash
│   └─ arch.__jac_field_hashes__ = {field: hash}
└─ return anchor
```

### 6.2 Syncing an anchor that already exists in the DB

```text
SqliteMemory.sync()
└─ for each anchor in __mem__ with a stored_anchor
   ├─ access_changed = canonical_json(stored.access) != canonical_json(anchor.access)
   ├─ setattr_dirty = arch.__jac_dirty_fields__                ← NEW
   ├─ hash_dirty = fields whose hash ≠ snapshot                ← NEW
   ├─ dirty = setattr_dirty ∪ hash_dirty                       ← NEW
   ├─ if (access_changed or dirty) and check_write_access     ← CHANGED (was archetype_changed)
   │   ├─ access_changed → copy access, changed=True
   │   └─ dirty → copy each dirty field onto stored archetype, changed=True   ← CHANGED (was whole object)
   └─ if changed
       ├─ write merged row to SQLite
       ├─ clear __jac_dirty_fields__                           ← NEW
       └─ re-snapshot field hashes                             ← NEW
```

### 6.3 Results

| Scenario | Before | After |
|---|---|---|
| Read-only walker A syncs after B wrote `name` | A's stale `name` overwrites B's | No write; B's value kept |
| A changes `count`, B changes `name` | Whichever syncs last overwrites both fields | Both survive |
| A and B change the same field | Last writer wins | Last writer wins (no warning) |
| `tags.append("b")` after load | Written (whole object differs) | Written (hash differs) |
| Read-only walker without write permission | `check_write_access` called, access-denied log possible | Not called |
| Anchor with no snapshot and no `__jac_dirty_fields__`, mutated in place | Written (whole object differs) | Not written, per the code. Whether this case can happen depends on code not in the diff |

User-visible change: concurrent walkers in local mode now keep each other's writes to different fields. Access-denied log noise from read-only walkers goes away.

## 11. Questions your senior might ask

**Q: Why not just skip sync for read-only walkers?**
That fixes 3.2 only. Two walkers writing different fields (3.3) would still clobber each other. Field-level merging fixes both.

**Q: Why hashes as well as `__jac_dirty_fields__`?**
`__jac_dirty_fields__` only sees assignments. `tags.append("b")` doesn't call `__setattr__`. The hash comparison catches that, and the in-place list test proves it.

**Q: Python's `hash()` is randomized. Is that safe?**
Yes, here. Snapshots are made and compared in the same process and are never saved to the DB.

**Q: What happens if two walkers change the same field?**
The last sync wins, silently. The PR doesn't detect or log that conflict.

**Q: What does it cost?**
Each `sync()` serializes and hashes every declared field of every cached anchor, and `get()` does the same once on load. There are no extra DB queries.

**Q: What if an anchor has no snapshot?**
`_sqlite_derive_dirty_from_field_hashes` returns an empty set, so only assigned fields count. In-place changes on such an anchor would not be written. Whether that can happen depends on the new-anchor save branch, which the diff doesn't show.

**Q: Does this change the access-check contract?**
It restores it. The check runs only when access or a field actually changed, which is what `test_serve_sync_skips_write_access_check_on_unchanged_anchors` requires.

**Q: Does this make local mode match MongoDB?**
The comments suggest jac-scale's MongoDB backend already does field-level updates, and @kugesan1105 describes this change as "aligned with jac-scale MongoDB". The diff doesn't include the MongoDB code, so you can't show the exact match from this PR.

**Q: Are edge changes still saved?**
This hunk only merges `access` and archetype fields. How edges are persisted is outside the visible diff, and no new test covers edges.
