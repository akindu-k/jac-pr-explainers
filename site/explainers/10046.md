## 1. The short version

jac-scale stores every node in three layers: the request's own memory (L1), Redis (L2, a shared cache) and MongoDB (L3, the source of truth). A read checks L1, then Redis, then Mongo. Every pod trusts Redis, so a wrong value in Redis is what every pod reads next.

**Redis could hold an older copy of a node than Mongo, and every later read returned that stale copy.** Two paths caused this:

- **A.** A request that changed one field wrote only that field to Mongo, then wrote its whole in-memory node to Redis. If another request had already committed a different field, that field went back to its old value in Redis. The issue's example: Mongo held `pointer='sandbox-one'`, but Redis held `pointer=''`.
- **B.** A reader that missed Redis read Mongo and then always wrote what it read into Redis. If a write finished between that read and the Redis write, the older snapshot replaced it.

**Your fix stops publishing whole anchors on field updates and guards every cache refill with a short Redis "lease" that any write cancels.**

- A field update now deletes the Redis key and broadcasts an invalidation, the same way edge-delta writes already work.
- A reader that misses Redis takes a lease before it reads Mongo. It refills Redis through an atomic Lua compare-and-set that writes only if its lease is still there. `put` and `delete` clear the lease.
- `execute_plan` (queries) no longer refills Redis at all.

## 3. The problem, step by step

### 3.1 The setup

- Two or more contexts (pods) share one Redis and one Mongo. Each has its own L1.
- At commit, `ScaleTieredMemory.commit`:
  - writes intents to Mongo;
  - for deletes and edge deltas, invalidates Redis;
  - for **everything else**, calls `self.l2.put(intent.anchor)`, which writes the whole anchor.
- On a read miss, `get`, `batch_get` and `execute_plan` read Mongo and then always run `l2.put(anchor)`.

### 3.2 What went wrong: case A, field update publishes a stale full anchor

```text
Start: Mongo {pointer:"", stamp:"seed"}  Redis {pointer:"", stamp:"seed"}
1. Pod "first" loads witness into its L1        → L1(first)  {pointer:"",  stamp:"seed"}
2. Pod "second" loads witness into its L1       → L1(second) {pointer:"",  stamp:"seed"}
3. second sets stamp="second-request" (dirty, not committed)
4. first sets pointer="sandbox-one", commits
     Mongo put_partial(pointer)                 → Mongo {pointer:"sandbox-one", stamp:"seed"}
     Redis put(whole anchor)                    → Redis {pointer:"sandbox-one", stamp:"seed"}
     publish invalidation → second's L1 copy is dirty, so _refresh_if_stale keeps it
5. second commits
     Mongo put_partial(stamp)                   → Mongo {pointer:"sandbox-one", stamp:"second-request"}  ✓
     Redis put(whole anchor from L1(second))    → Redis {pointer:"",  stamp:"second-request"}  ✗ WRONG
6. A fresh pod reads                            → Redis hit: pointer=""  ✗ (Mongo says "sandbox-one")
```

### 3.3 What went wrong: case B, a late cache refill overwrites a newer write

```text
Start: Mongo {pointer:"", stamp:"seed"}; Redis key removed (cache miss)
1. Reader misses Redis, reads Mongo            → reader holds {pointer:"", stamp:"seed"}
2. Writer sets pointer="sandbox-two", commits  → Mongo {pointer:"sandbox-two", stamp:"seed"}
                                                 Redis {pointer:"sandbox-two", ...} (or invalidated)
3. Reader finishes: l2.put(snapshot from step 1)
                                               → Redis {pointer:"", stamp:"seed"}  ✗ WRONG
4. A fresh pod reads                           → Redis hit: pointer=""  ✗ (Mongo says "sandbox-two")
```

Fixing only case A does not fix case B. The invalidation at step 2 runs before the refill at step 3, so the refill still lands.

### 3.4 Why it mattered

- Issue #9840 reproduces both cases on the official v0.34.20 and v0.34.21 binaries, against real MongoDB 7.0.43 and Redis 7.4.11. In both, a fresh owner traversal read the stale value. Every pod reads Redis first, so one bad entry poisons all later reads until it is overwritten, deleted or expired. With TTL 0 it never expires.
- Mongo stays correct. The data is not lost; it is hidden behind the cache.
- The issue says it does **not** establish whether this caused the original incident (jacBuilder#2152).

## 4. The idea of the fix (one sentence)

> **Never write a possibly-old anchor into Redis unless nothing has written it since you read it.** Field updates delete the cache entry instead of overwriting it, and refills go through a lease that any write cancels.

Redis has no version to compare against: the issue shows both Mongo and Redis at version `0`. A token that writes delete is a cheap stand-in for "has anything changed since my read". Invalidating on field updates also avoids having to merge partial updates into a full cached copy.

### 5.2 `jac/jaclang/scale/memory/impl/memory_hierarchy.redis.impl.jac`: lease, guarded fill, and writes that cancel leases

```diff
+impl RedisBackend.lease(ids: list[UUID]) -> dict[UUID, str] {
+    if self.redis_client is None or not ids { return {}; }
+    leases = {id: uuid4().hex for id in ids};
+    try {
+        pipe = self.redis_client.pipeline(transaction=False);
+        for (id, token) in leases.items() {
+            pipe.set(_lease_key(storage_key(to_uuid(id))), token, px=_REFILL_LEASE_MS, nx=True);
+        }
+        taken = pipe.execute();

+    return {id: leases[id] for (id, ok) in zip(leases, taken) if ok};   # only ids we actually got

+
+impl RedisBackend.fill(anchor: Anchor, token: (str | None)) -> None {
+    if self.redis_client is None or token is None { return; }            # no lease → no refill
+    self.put_count += 1;
+    ...
+        self.redis_client.eval(_FILL_IF_LEASED, 2, key, _lease_key(key), token, data, ttl);
```

**What:**
- `lease` tries `SET lease:<key> <random token> NX PX 10000` for each id. It returns only the ids it won.
- `fill` writes the anchor only if `lease:<key>` still holds that exact token. It consumes the lease in the same step.
- `put` and `delete` now also remove the lease atomically: `put` through a `MULTI` pipeline, `delete` through one multi-key `DEL`.

**Why:** This fixes case B. Any write between "reader read Mongo" and "reader fills Redis" deletes the lease, so the late fill becomes a no-op.

**Things to notice:**
- **`nx=True` is from commit 396ac21** ("only the first concurrent miss takes the refill lease"). Other readers that miss while a lease is held get no token. They read Mongo but do not fill.
- **Expiry.** The 10 s expiry only frees the key if a reader crashes or never fills. An expired lease is still safe: an old token never matches a missing or new lease.
- **Failures are silent.** Every failure only logs at debug level. A failed `lease` returns `{}`, so no fill happens: safe, just a colder cache.
- **Metrics (commit 861fbda).** `fill` increments `put_count` even when the CAS does not write, so the metric counts attempts. A `None` token returns before the increment.
- **Log order.** In `put`, the "Stored anchor" debug log now runs before `pipe.execute()`.
- **`invalidate` is not in the diff.** Case B is cancelled by the writer's `FIELD_UPDATE` → `invalidate`. That only works if `invalidate` also removes the lease, most likely by calling `delete`. The passing delayed-refill rows suggest it does, but you can't confirm it from this diff. Check it before you present.

## 6. How execution flows after the PR

### 6.1 Reading one node (`ScaleTieredMemory.get`)

```text
get(id)
├─ _refresh_if_stale(id)
├─ no Redis OR id in L1? → super.get(id) (old path)                    ← CHANGED (split out)
├─ Redis hit → store in L1 → return
└─ Redis miss
   ├─ lease([id]): SET lease:<key> token NX PX 10000                    ← NEW
   │   └─ another reader already holds it → no token
   ├─ Mongo get(id) → store in L1
   ├─ fill(anchor, token)                                               ← NEW
   │   ├─ no token → skip refill
   │   └─ Lua: lease == token? → DEL lease, SET key  :  do nothing
   └─ return anchor
```

### 6.2 Reading many nodes (`batch_get`)

```text
batch_get(ids)
├─ L1 / Redis lookups → l2_misses
└─ l2_misses and Mongo
   ├─ lease(l2_misses) → {id: token} for leases won                     ← NEW
   ├─ Mongo batch_get(l2_misses)
   └─ for each result: L1 ← anchor; fill(anchor, token or None)          ← CHANGED (was put)
```

### 6.3 Committing (`ScaleTieredMemory.commit`)

```text
commit()
└─ for each applied intent
   ├─ delete OR FIELD_UPDATE                                            ← CHANGED (FIELD_UPDATE added)
   │   ├─ l2.invalidate(id)   (removes key; lease too, if invalidate → delete — not visible in diff)
   │   └─ publish_invalidation(id, own L1 id) → other pods drop clean L1 copies
   ├─ edge delta → invalidate (unchanged, #6297)
   └─ other (e.g. create) → l2.put(anchor)
        └─ MULTI: SET key; DEL lease:<key>                              ← CHANGED (clears lease)
```

### 6.4 Queries (`TieredMemory.execute_plan`)

```text
execute_plan(plan)
└─ for each anchor from Mongo
   ├─ new to L1 → L1 ← anchor; yield   (no Redis write)                  ← CHANGED
   └─ already in L1 → yield existing
```

| Scenario | Before | After |
|---|---|---|
| Two requests update different fields (case A) | Redis gets the later request's whole anchor, so the other field is stale | Redis key deleted; the next read refills from Mongo |
| Write lands between a reader's Mongo read and its refill (case B) | Stale snapshot overwrites Redis | Write removes the lease, so the fill is a no-op |
| Two readers miss at the same time | Both refill | Only the first takes the lease and fills; the second reads Mongo without filling |
| Query returns nodes | Each result written to Redis | Results stay in L1 only |
| Two whole-anchor writes (create/upsert) race | Last Redis `SET` wins, possibly in a different order from Mongo | Same: not covered |
| `save()` → `ScaleTieredMemory.put` of a loaded anchor (Musab) | Whole anchor `SET` to Redis | Same, and it now also cancels a pending lease |

**Behaviour users will notice:** after a field update, the next read of that node on every pod costs one Mongo read. Query results no longer warm Redis. Neither returns different data, only fewer cache hits.

### `test_memory_hierarchy.jac`

**New helpers:**

|---|---|

## 11. Questions your senior might ask

**Q: Why invalidate on field update instead of writing the merged anchor to Redis?**
The request only knows its own dirty fields. Another pod's committed fields are in Mongo, not in this request's L1, so any full write from L1 can be stale. Deleting the key forces the next reader to load Mongo's full state.

**Q: What does that cost?**
One extra Mongo read per updated node on the next access. Query results also no longer warm Redis. The PR includes no performance measurement.

**Q: What if a reader's Mongo read takes longer than the 10 s lease?**
The lease expires and the fill finds no matching token, so nothing is written. This is safe; the reader just doesn't warm the cache. If a new reader has taken a fresh lease, its token differs from the old one, so the old fill still fails.

**Q: How does a field-update commit cancel a pending fill? You only changed `put` and `delete`.**
Commit calls `l2.invalidate`. That must clear the lease, most likely by delegating to `delete`. The delayed-refill rows pass with the fix, which suggests it does, but `invalidate`'s body isn't in this diff. Have the line ready.

**Q: Does this work on Redis Cluster?**
The diff can't answer this. `_FILL_IF_LEASED` uses two keys (`anchor:<id>` and `lease:anchor:<id>`), and `put` and `delete` touch both in one transaction or `DEL`. In Redis Cluster these usually fall in different hash slots and fail with CROSSSLOT unless hash tags are used. The failures are swallowed at debug level, so a failed `delete` could leave a stale entry. Check what Redis topology jac-scale deploys.

**Q: Why did you change `runtimelib`'s `execute_plan`, which isn't scale code?**
That is where the unguarded refill lives, and its ids are unknown before the query, so it can't take a lease first. The change affects any `TieredMemory` with an `l2`. Whether anything other than jac-scale sets one isn't visible here.

**Q: Does your new `get` skip anything that `TieredMemory.get` did?**
On a Redis miss it no longer calls the base method. It does L2 → lease → L3 → L1 → fill itself. You should compare it with `memory.impl.jac` lines 1665–1683 to confirm nothing else, such as hooks or flags, is lost.

**Q: Is `save()` → `ScaleTieredMemory.put` still a stale-write path?**
That is Musab's open comment. Yes: it writes the in-memory anchor to Redis with an unconditional `SET`, and an unchanged anchor produces no intent to invalidate afterwards. You need to either fix it or call it out of scope.

**Q: What's still not covered?**
Two whole-anchor writes (create/upsert) can still reach Redis in a different order from Mongo, as the PR states. There is also the `put` path above.

**Q: Why target `release/jaclang-0.34.23-prep` and not `main`?**
`main` replaced the Mongo/Redis hierarchy (#7947, #8000), so these code paths don't exist there. This PR replaces #9911, which closed when the 0.34.21 prep branch was deleted.
