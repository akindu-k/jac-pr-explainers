## 1. The short version

`jac scale deploy` compiles your app on the deploy machine before it ships. This step is called "sealing". Every Kubernetes pod gets the compiled copy, so it can start in seconds instead of compiling the app itself.

**In a workspace (a project with several apps), the deploy always sealed the `default-app`, not the app you were deploying.** In jacBuilder's setup, `default-app = "builder_sv"` (a service) was sealed, but `main` (the web-app being deployed) was not. The `main` pod found no compiled copy of itself, compiled everything at boot, and was OOMKilled (killed for running out of memory) at its 12Gi limit. In your test, the bug shows up as `KeyError: 'hello'`: the serve manifest was built for `svc`, not `web`.

**You pass the name of the app the deploy serves (the fleet's `root_app`) into both sealing steps: the bake (`app=`) and the seal (`--app=`).** All the production changes are in one file, `jac/jaclang/scale/injector/bundle.jac`. Single-app projects get exactly the same flags as before.

**Status:** Merged on 2026-09-17. It was approved by @MalithaPrabhashana. Greptile scored it 5/5. Every CI check on the head commit `c0f7991` passed or was skipped.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. `.jac` files are source files. |
| jac-scale | The part of the repo that deploys Jac apps to Kubernetes. Your change lives here (`jaclang/scale/...`). |
| Kubernetes pod | One running copy (replica) of your app in the cluster. |
| OOMKilled | Kubernetes killed the pod because it used more memory than its limit allowed. |
| Workspace | A project whose `jac.toml` declares several apps under `[apps.<name>]`. Example: `[apps.web]` and `[apps.svc]`. |
| `default-app` | The app in a workspace that is used when no app is named. Example: `default-app = "svc"`. |
| App kind | The type of app: `web-app`, `service`, `service-mesh`, and others. Only kinds that run a server can be served. |
| Fleet / `FleetSpec` | The deploy's description of which apps run and how. It is built by `fleet_from_config(config, served_app)`. |
| `root_app` | The field on the fleet that names the app this deploy serves. Example: `web`. |
| `.jab` | The bundle file (a gzip tar) that ships to pods. It holds the source plus the sealed output. |
| `.jir` | A compiled module file. Example: `web.jir` is the compiled form of `web.jac`. |
| Sealing | Compiling the app ahead of time and writing `_precompiled/` (the `.jir` files plus `MANIFEST.json`, the index of compiled modules). |
| Bake / `bake_serve_payloads` | The step that writes `.jac/serve_manifest.json`: the list of the app's endpoints and per-function settings that the server reads at startup. |
| Serve manifest | `.jac/serve_manifest.json`. Its keys include `func_access` and `module_manifests` (one entry per bootable app file). |
| `pack_jab` | Builds the `.jab`. It stages the project, calls `_precompile_app`, then tars everything. |
| `_precompile_app` | Runs the bake and the seal inside a staged copy of the project, using the pod's own `jac` binary. **This is where the bug is.** It never received the served app's name. |
| `sealed_app_name` | A new helper. It returns the served app's name for a workspace deploy and `""` otherwise. **This is what the PR adds.** |
| Legacy sealer fallback | If `jac precompile` fails, `_precompile_app` retries with a generated script (`_legacy_sealer_script_for`). This supports older pod binaries. |
| `prepare_application` / `sealed_root_for` | Pod-side code that decides between "load the sealed image" (prints `Loading sealed application artifacts`) and "compile from source" (prints `Compiling server modules...`). This PR does not change it. |

## 3. The problem, step by step

### 3.1 The setup

- **Deploy machine:** `jac scale deploy web.jac` builds a fleet with `root_app = "web"` and then calls `pack_jab(..., fleet=fleet)`.
- **`pack_jab`:** calls `_precompile_app(base, seal_binary, sanitized_toml, timeout)`. This runs two steps with the pod binary:
  1. The bake: a generated script calls `bake_serve_payloads(config, project, bake_client=False)`.
  2. The seal: `jac precompile <stage> --seal`.
- **Pod:** runs `jac start <entry>`. It boots from the seal only if its entry is a module key in `_precompiled/MANIFEST.json` and the serve manifest covers it.

### 3.2 What went wrong

```text
1. jac.toml: default-app = "svc"; apps: web (web-app), svc (service)
2. jac scale deploy web.jac → fleet.root_app = "web"
3. pack_jab(base, binary, fleet=fleet)
4. _precompile_app(base, binary, toml, timeout)     ← WRONG: fleet/root_app not passed
5. bake_serve_payloads(config, project, ...)        ← no app → falls back to default-app "svc"
      serve_manifest.module_manifests = ["svc.jac"]   (no web.jac, no "hello" in func_access)
6. jac precompile <stage> --seal                    ← no --app → seals "svc"
      _precompiled/MANIFEST.json lists svc.jac, "web.jac" appears 0 times
7. Pod web-deployment: jac start web.jac
      sealed check misses → "Compiling server modules and placement metadata..."
8. svc-deployment pod: "Loading sealed application artifacts" (it happened to be the default)
```

Two independent reviewer probes confirmed this state.

- @MalithaPrabhashana's probe on `main`: `"web.jac"` appeared 0 times in `MANIFEST.json`, and `module_manifests` held only `svc.jac`.
- On jacBuilder's shape (`default-app = "builder_sv"`), `main` compiled at boot and both services booted sealed.

### 3.3 Why it mattered

- Issue #9136 reports about 7 minutes and 4.5Gi per pod at boot on jaclang.org. This repeats on every restart, rollout, and HPA scale-up (HPA is Kubernetes autoscaling).
- The issue also notes that the seal work on the deploy machine was wasted.
- jacBuilder's `main` pod was OOMKilled at 12Gi.
- The pod printed no hint that a seal was present and ignored. That silence is why the investigation was hard.

Note the issue's original theory: it observed `.jac/serve_manifest.json` missing on the pod and suspected the pod-side gate. This PR's root cause is different: the wrong app was sealed. The PR does not explain the missing-file observation on the jaclang.org pod (image 0.37.11), and I can't tell from the PR whether it has the same cause. The pod-side diagnostics the issue asked for were split into #9139, #9138 and #9140.

## 4. The idea of the fix (one sentence)

> **Seal the app being served, not the default app.** Pass the fleet's `root_app` into `_precompile_app`, so both the bake and the seal target it in a workspace.

The deploy already knew the right app; the name just wasn't passed through. This is the same rule `jac build --as jab --app <name>` already follows, so nothing on the pod side needs to change.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/bundle.jac`: new `sealed_app_name` helper

```diff
+def sealed_app_name(project_dir: str, fleet: (FleetSpec | None)) -> str {
+    if fleet is None or not fleet.root_app {
+        return "";                                   # no fleet / no served app → default behavior
+    }
+    config = _project_config(project_dir);
+    if config is None or not config.is_workspace {
+        return "";                                   # single-app project → default behavior
+    }
+    return fleet.root_app;                           # workspace → the served app
+}
```

- **What:** It decides which app name to seal. It returns a name only when there is a fleet with a `root_app` and the project is a workspace. Otherwise it returns `""`.
- **Why:** This is the missing link between "what the deploy serves" and "what gets sealed".
- **Things to notice:**
  - `""` means "don't pass an app". That keeps single-app projects and `jac scale deploy` with no app named on the old path.
  - `_project_config` is an existing helper. Its body isn't in the diff.

### 5.2 `jac/jaclang/scale/injector/bundle.jac`: `_precompile_app` takes `app`

```diff
 def _precompile_app(
-    base: Path, seal_binary: bytes, sanitized_toml: (str | None), timeout_s: int
+    base: Path, seal_binary: bytes, sanitized_toml: (str | None), timeout_s: int,
+    app: str = ""                                                    # NEW
 ) -> Path {
+    seal_flags: list[str] = ["--seal"] + ([f"--app={app}"] if app else []);
 ...
-    if not bake_serve_payloads(config, project, bake_client=False) {
+    if not bake_serve_payloads(
+        config, project, app={repr(app)}, bake_client=False         # NEW: app= in generated script
+    ) {
 ...
-    [str(jac_path), "precompile", str(stage_root), "--seal"],
+    [str(jac_path), "precompile", str(stage_root)] + seal_flags,     # NEW: --app=<name>
 ...
-    [str(jac_path), "run", str(script), str(stage_root), "--seal"],
+    [str(jac_path), "run", str(script), str(stage_root)] + seal_flags,  # legacy fallback too
```

- **What:** The app name now reaches all three places:
  - the bake script, as `app=`;
  - the main seal, as `--app=`;
  - the legacy seal fallback, as `--app=`.
- **Why:** Before this, both steps fell back to `default-app`. Fixing only one would leave the serve manifest and the compiled modules out of sync.
- **Things to notice:**
  - `repr(app)` turns the name into a quoted string literal inside the generated script. For example, `web` becomes `'web'`.
  - When `app == ""`, the seal flags are exactly `["--seal"]`, the same as before.
  - The bake, however, now gets `app=''` explicitly instead of not receiving `app` at all. The PR says `''` keeps default behavior, and single-app CI tests pass, but the diff doesn't show `bake_serve_payloads` itself.
  - Old pod binaries: the PR says `--app` and `app=` both shipped in 0.37.5, the same release as the bake step this path already needs. The diff can't confirm whether the legacy sealer script accepts `--app`; the PR says it does.

### 5.3 `jac/jaclang/scale/injector/bundle.jac`: `pack_jab` passes the served app

```diff
     staged = _precompile_app(
-        base, seal_binary, sanitized, seal_timeout_setting(project_dir)
+        base, seal_binary, sanitized, seal_timeout_setting(project_dir),
+        sealed_app_name(project_dir, fleet)                          # NEW
     );
```

- **What:** `pack_jab` already received `fleet`. It now uses it to choose the app to seal.
- **Why:** This closes the gap from step 4 of the timeline.
- **Things to notice:** Services are still sealed next to the served app. @MalithaPrabhashana checked this: a servable app is always `web-app`, `service` or `service-mesh`, and `_application_sources` always adds the service apps.

### 5.4 `release_notes/unreleased/jaclang/9228.bugfix.md`

```diff
+- **Fix: `jac scale deploy` seals the app it serves**: Deploying a workspace app that is not `default-app` now seals that app, so its pods boot from the sealed image instead of compiling the whole app at startup.
```

- **What:** A one-line user-facing release note.

## 6. How execution flows after the PR

### 6.1 Deploying a workspace app that is not the default

```text
jac scale deploy web.jac
├─ kubernetes_realizer._resolve_fleet → fleet_from_config(cfg, "web")  → fleet.root_app = "web"
├─ binary_injector → pack_jab(project_dir, seal_binary, fleet=fleet)
│   ├─ sealed_app_name(project_dir, fleet) → "web"                     ← NEW
│   └─ _precompile_app(..., app="web")                                 ← CHANGED
│       ├─ _stage_app → stage_root/app
│       ├─ bake script: bake_serve_payloads(config, project, app='web')← CHANGED
│       │     serve_manifest.module_manifests = [svc.jac, web.jac]
│       ├─ jac precompile <stage> --seal --app=web                     ← CHANGED
│       │     (on failure: legacy script ... --seal --app=web)         ← CHANGED
│       └─ _precompiled/ now contains web.jir, svc.jir + MANIFEST.json
├─ tar → .jab (includes _precompiled/ and .jac/serve_manifest.json)
└─ pods
    ├─ web pod: jac start web.jac → "Loading sealed application artifacts"   ← fixed
    └─ svc pod: jac start svc.jac → "Loading sealed application artifacts"   (unchanged)
```

### 6.2 Single-app project, or no fleet

```text
pack_jab(project_dir, seal_binary, fleet=None or non-workspace)
├─ sealed_app_name → ""                                                ← NEW
└─ _precompile_app(..., app="")
    ├─ bake: bake_serve_payloads(..., app='', ...)                     ← CHANGED (explicit '')
    └─ jac precompile <stage> --seal                                   (same flags as before)
```

| Scenario | Before | After |
|---|---|---|
| Workspace, deployed app = `default-app` | Sealed, boots from seal | Same |
| Workspace, deployed app ≠ `default-app` (web-app) | Served app not sealed; pod compiles at boot | Served app sealed; boots from seal |
| Workspace, service apps in the same deploy | Sealed | Still sealed |
| Single-app project | `--seal`, default app | Same `--seal`; bake gets `app=''` |
| No fleet passed | Default app | Default app |

The behaviour change users will notice: web-app pods in multi-app workspaces start in seconds, and their startup log reads `Loading sealed application artifacts` instead of `Compiling server modules...`.

### `test_app_precompile.jac`

The test was renamed from `a real pod binary seals and serves an entry named app` to `a real pod binary seals the app each pod serves and boots it from the seal`. It became table-driven.

| Case | `jac.toml` | Files | Served app | `func_access` key checked | Boots (entry → endpoint) | Proves |
|---|---|---|---|---|---|---|
| an entry named app | single-app service, entry `app` | `app.jac` (imports `svc`) | `""` (no fleet) | `ping` | `app.jac` → `/walker/echo` | The old behavior is kept |
| a web-app that is not the default app | workspace, `default-app="svc"`, apps `web` and `svc` | `web.jac` | `web` | `hello` | `web.jac` → `/function/hello`, `svc.jac` → `/function/ping` | The bug is fixed and services stay sealed |

For each case, the test does the following:

1. It writes the project and builds a real fleet with `fleet_from_config(...)` when the case has a served app.
2. It calls `pack_jab(..., fleet=fleet)` with the real `jac` binary.
3. It checks the serve manifest:
   - `func_access[func]` is `False`. Without the fix, this line raises `KeyError: 'hello'`.
   - Every boot entry is in `module_manifests`.
   - The serve manifest is listed in `_precompiled/MANIFEST.json["payloads"]`.
4. It checks that `svc.jir` and each boot entry's `.jir` are in `_precompiled/`.
5. It extracts the bundle and runs `jac run --serve --no-client --faux <entry>` with `JAC_NO_DEV_SOURCE=1` for each entry. It then asserts:
   - the return code is 0;
   - the endpoint is printed;
   - `Loading sealed application artifacts` is present;
   - `Compiling server modules` is absent;
   - `Preparing dynamically imported module` is absent.

Why this test was extended instead of a new one added: the PR says "extended, not added" so both cases share one real-binary pack-and-boot harness. That is also why the count stays at 17.

Commit `d5ca103` added the `svc.jac` boot and the `module_manifests` checks, after @MalithaPrabhashana's suggestion. A smaller change in the same rewrite: the original test ran without `--no-client`, and the new one adds it.

## 11. Questions your senior might ask

**Q: Why not just change `default-app` in jacBuilder's config?**
That only hides the bug for one project. Any workspace that deploys a non-default app would still compile at boot. The deploy already knows the served app, so it should seal that app.

**Q: Why return `""` for single-app projects instead of the fleet's `root_app`?**
To keep the seal flags identical to before. A single-app project has no `[apps.*]` table to select from. The PR states the goal is "exactly the same seal flags as before".

**Q: Does passing `--app=web` stop the services from being sealed?**
No. Service apps are always added alongside the served app (`_application_sources`). The test proves this by booting `svc.jac` from the seal. Forcing `service_apps` to return nothing makes the test fail.

**Q: Will old pod binaries choke on `--app` or `app=`?**
The PR says both shipped in 0.37.5. That is the same release as the bake step this path already requires, so no supported binary lacks them. The diff alone can't confirm the version.

**Q: Why change the legacy fallback too?**
If the main `precompile` call fails and the fallback runs without `--app`, you would get the default app again. That would reintroduce the bug only on older binaries.

**Q: Does this change pod startup code?**
No. `prepare_application` and `sealed_root_for` are untouched. Only what goes into the `.jab` changes.

**Q: Why `repr(app)` in the bake script?**
The bake runs as generated Jac source. `repr` produces a correctly quoted string literal, for example `'web'`, so the name can't break the script's syntax.

**Q: Does this fix the "pod gives no reason for not loading the seal" part of #9136?**
No. That is #9139 (logging). Failing early when the serve manifest is missing is #9138. Both were split out on purpose.

**Q: How do we know the test isn't silently skipped in CI?**
The reviewer ran it with `JAC_TEST_STRICT=1`, and the CI microservices job reported 0 skipped.
