## 1. The short version

The Jac API server (`JacAPIServer`) keeps a list of users. Each user has a username, a password hash, a login token and the ID of their own root node. A class called `UserManager` handles this list. Before this PR, `UserManager` held users in two Python dicts and wrote both dicts to a JSON file (`<session_path>.users.json`) on every change.

**The user list lived in its own hand-written JSON file, outside Jac's memory hierarchy. When that file could not be read, `UserManager` silently started with an empty list.** Issue #3979 asks for this to be refactored. Issue #3851 reports flaky registrations in CI: the first user registers, later ones sometimes fail with `{'error': 'Registration failed: pickle data was truncated'}`.

**The PR removes the JSON file. Each user is now a `UserAnchor` object stored in a `PersistentMemory`. If no memory is passed in, it falls back to a new `ShelfMemory` at `<session_path>.users`. Every lookup becomes a `mem.query(...)` filter.** The four places in the HTTP handler that create the `__guest__` user were also rewritten to query the memory. The PR also adds two debug `print` calls in jac-scale's `plugin.jac`.

**Status:** Closed, with no reviews and no CI checks reported. On 2026-01-12, @RandiJay96 commented that "#4036 includes these changes", so this PR appears to have been replaced by #4036. The data does not say whether this PR was merged. Everything points to it being closed unmerged.

## 3. The problem, step by step

### 3.1 The setup

- `JacAPIServer` owns a `UserManager(session_path=...)`.
- On start, `UserManager.postinit` set `_db_path = "<session_path>.users.json"` and called `_load_db()`.
- `create_user` added entries to `_users` and `_tokens`, then called `_persist()`. That rewrote the entire JSON file.
- The HTTP handler read `server.user_manager._users` directly to check whether `__guest__` existed.
- The graph itself (root nodes and other nodes) is stored separately, in the memory hierarchy. The comment in `create_user` ("avoids shelf locking issues") shows that store is a shelf.

### 3.2 What went wrong: users stored outside the memory hierarchy (#3979)

```text
1. Server starts. _load_db opens "<session>.users.json".
2. The file is missing, half-written, or has bad JSON.
3. except Exception  →  _users = {}, _tokens = {}          ← WRONG: error swallowed, all users "gone"
4. Someone registers "bob". _users = {"bob": {...}}.
5. _persist() rewrites the whole file with only "bob".     ← WRONG: earlier users are now erased on disk
6. Old users' tokens no longer validate; their root_ids are lost from the user list.
```

There is a second issue. Users live in a JSON file, while their root nodes live in the memory hierarchy. These are two stores with two save paths and no shared lifecycle. #3979 asks for one store.

### 3.3 What went wrong: flaky "pickle data was truncated" (#3851)

```text
1. Test registers user 1  → OK.
2. Test registers user 2  → sometimes {'error': 'Registration failed: pickle data was truncated'}.
3. Rerun the test         → usually passes.
```

You need to be clear about one thing here. JSON does not use pickle, so this error does not come from the old `.users.json` file. It comes from a shelf: the graph store that `create_user` touches when it builds the root node. The diff does not show the root cause. It also does not show whether this PR fixes it. The PR adds a *second* shelf (`<session>.users`), so it could add more of the same risk rather than less (see section 11).

### 3.4 Why it mattered

- #3851: CI backend tests failed at random, so people had to rerun them.
- #3979: user data could silently disappear, and user storage did not follow the same persistence rules as everything else.

## 4. The idea of the fix (one sentence)

> **Store users as objects in persistent memory, not in a JSON file.** Each user becomes a `UserAnchor` that is put into a `PersistentMemory`, and every lookup becomes a query on that memory.

This is the right direction because it gives one storage mechanism with `put`/`sync`/`close` instead of a custom file format. One caveat: in this diff nothing passes in the server's existing memory. In practice users go to a separate new shelf.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/server.jac`: new `UserAnchor`, new `mem` field

```diff
+import from jaclang.runtimelib.memory { PersistentMemory, ShelfMemory }
...
+obj UserAnchor {
+    has username: str,
+        password_hash: str,
+        token: str,
+        root_id: str;
+}
+
 obj UserManager {
     has session_path: str,
-        _users: dict[(str, dict[(str, str)])] = {},
-        _tokens: dict[(str, str)] = {},
-        _db_path: str = "";
+        mem: (PersistentMemory | None) = None;   # NEW: injectable store
     def postinit -> None;
-    def _load_db -> None;
-    def _persist -> None;
```

**What:** This declares a record type for one user. It replaces the two dicts with one optional `mem` field and removes the file helpers.

**Why:** It is the data-model half of #3979. Users become objects that memory can store.

**Things to notice:**
- `UserAnchor` is a plain `obj`, not a subclass of Jac's `Anchor` classes. The diff cannot tell you whether `PersistentMemory.put` accepts any object or needs an `Anchor` with an `.id`. Check this.
- All four fields have no defaults. In Jac an `obj` with fields that lack defaults usually needs them as constructor arguments. Yet `create_user` calls `UserAnchor()` with no arguments and sets the fields afterwards. That may raise a `TypeError` at runtime. The diff cannot confirm it, and no tests ran.
- The `_tokens` reverse map is gone. Token lookups now scan users (see 5.2).

**Lookups** (`authenticate`, `validate_token`, `get_root_id`, `get_user`) all follow the same pattern:

```diff
 impl UserManager.validate_token(token: str) -> (str | None) {
-    return self._tokens.get(token);                        # OLD: dict lookup
+    for anc in self.mem.query(
+        filter=lambda a: isinstance(a, UserAnchor) and a.token == token
+    ) {
+        return anc.username;                               # NEW: first match
+    }
+    return None;
 }
```

**What:** Each method now runs a query and returns from the first matching `UserAnchor`. `authenticate` still compares SHA-256 hashes and returns `None` on a wrong password. `get_user` still returns the key `'email'`, holding the username, as before.

**Why:** Users now come from `mem`, not from in-process dicts loaded from JSON.

**Things to notice:**
- Commit f624fc3 says "change UserManager.get_user return to email from usernam". The final diff shows `'email'` both before and after, so the public output of `get_user` does not change.
- Every lookup is a filtered scan. `validate_token` runs on authenticated requests, so cost may grow with the number of stored objects. The diff does not show how `query` is implemented.
- The username check and the `put` are not atomic. Two concurrent signups for the same name can both pass the check. The old code had the same gap.
- No migration step. Users already in `<session>.users.json` are not read. After upgrading, existing accounts and tokens stop working.
- The lambdas use the untyped form `lambda a: expr`. Commit bb0ccec is titled "fix syntax", so check that this form compiles in Jac.
- `json` may now be unused in this file. The diff does not show the import list.

### 5.3 `jac/jaclang/runtimelib/impl/server.impl.jac`: guest-user checks in the HTTP handler (4 places)

```diff

-        username = '__guest__';
-        if (username not in server.user_manager._users) {
+    if (not username) {
+        username = "__guest__";
```

**Why:** `_users` no longer exists, so the old `in` check would crash.

**Things to notice:**
- The same 15 lines are copied into four handlers. A single `user_manager.get_user("__guest__") is None` call, or a new `ensure_guest()` method, would do the same thing.
- The handler reaches into `user_manager.mem` directly. The old code also reached into `_users`, but this is a good chance to stop.
- `create_user` already returns `'User already exists'` when the user exists, so the pre-check is not even strictly needed.

## 6. How execution flows after the PR

### 6.1 Server start

```text
JacAPIServer created
└─ UserManager(session_path=...) built
   └─ postinit
      ├─ mem passed in? (nothing in this diff passes one)        ← NEW
      └─ no → mem = ShelfMemory(path="<session>.users")           ← CHANGED (was: read .users.json)
```

### 6.2 Register

```text
POST register
└─ UserManager.create_user(username, password)
   ├─ mem.query(UserAnchor with username) → found? return error    ← CHANGED
   ├─ create root node in existing context (unchanged)
   ├─ build UserAnchor, set 4 fields                               ← NEW
   ├─ mem.put(user_anchor)                                         ← NEW
   ├─ mem.sync()                                                   ← NEW (was: rewrite JSON)
   └─ return {username, token, root_id}
```

### 6.3 Login and token check

```text
login → authenticate → mem.query(username) → compare hash → dict | None   ← CHANGED
request with token → validate_token → mem.query(token) → username | None  ← CHANGED
```

### 6.4 Request without a token

```text
handler → _authenticate() → None
└─ username = "__guest__"
   ├─ mem.query(UserAnchor "__guest__")                            ← CHANGED
   └─ not found → create_user("__guest__", "__no_password__")
```

### 6.5 Shutdown

```text
UserManager.close → mem.sync() → mem.close()                      ← CHANGED (was: write JSON)
```

| Scenario | Before | After |
|---|---|---|
| Fresh install, register user | Written to `<session>.users.json` | Written to shelf `<session>.users` |
| Upgrade with existing users | Loaded from JSON | **Not loaded. Old accounts and tokens stop working.** |
| Users file unreadable | Silently reset to empty, then overwritten | Depends on `ShelfMemory` error handling (not shown) |
| Token check | Dict lookup | Scan via `mem.query` |
| Starting the jac-scale server | Quiet | Prints the server object and a "try to start" line |

User-visible changes: the new storage file name, lost pre-existing users, and the extra console output in jac-scale.

## 11. Questions your senior might ask

**Q: Where did the "pickle data was truncated" error come from, if users were stored as JSON?**
Not from the users file. Pickle is used by `shelve`, so it came from a shelf: the graph store that `create_user` touches when it builds a root node. The diff does not show the root cause, and this PR does not clearly fix it.

**Q: Is the user store actually part of the memory hierarchy now?**
Only if someone passes `mem=` to `UserManager`. Nothing in this diff does that, so `postinit` always creates a separate `ShelfMemory` at `<session>.users`.

**Q: Does opening a second shelf risk more locking or truncation problems?**
It might. Two shelf files are open in the same process, and possibly across processes. The diff gives no evidence either way, which is why a multi-signup test matters.

**Q: Can `mem.put` store a `UserAnchor`?**
The diff does not show `PersistentMemory.put`. `UserAnchor` is a plain `obj` with no `id`. If `put` keys objects by anchor ID, this fails. Check before relying on it.

**Q: What happens to users who registered before this change?**
They are lost. The old `.users.json` is never read, and there is no migration.

**Q: Is token validation slower now?**
Probably. It went from a dict lookup to a filtered `query` over stored objects on every authenticated request. How much slower depends on how `query` is implemented, which is not shown.

**Q: Did you change what `get_user` returns?**
No. It returned `{'email': username, ...}` before and still does, despite the wording of commit f624fc3.

**Q: Why are there `print` calls in jac-scale?**
They are leftover debugging, unrelated to the issues, and should be removed.

**Q: Why not a helper for the guest user?**
There is no good reason. The same block appears four times and could be a single `UserManager` method or a `get_user("__guest__")` check.

**Q: How do you know any of this works?**
From this PR alone, you don't. There are no tests and no CI checks on fe1dbff.
