## 1. The short version

jac-scale serves Jac apps over HTTP. On every request it builds a new execution context, `JScaleExecutionContext`, and that context gets a new `ScaleTieredMemory`, a three-level cache. The first thing `init()` does is look up the **system root**, the fixed top node of the graph, by its well-known UUID.

**Because the in-memory cache (L1) starts empty on every request, that lookup always fell through to Redis and then MongoDB. The result was one MongoDB `find_one` per request for an object that, in practice, is created once and reused.** Finding 1b of audit issue #5874 reported this.

**You fixed it by keeping the system root anchor in the existing process-wide dict `_process_cache['system_root']`. After the first request, each new context copies that anchor into its own L1 before the lookup, so `mem.get()` returns from L1 and MongoDB is never called.** The change is 5 lines in `context.impl.jac`. You also added four tests that count MongoDB fetches per context, plus a release note.

**Status:** Merged on 2026-05-11, the same day it was opened. No reviews or comments were recorded. All test jobs passed on head commit `440432e`, and the release-pipeline jobs were skipped.

## 3. The problem, step by step

### 3.1 The setup

- `request_context_middleware` creates `JScaleExecutionContext()` for each HTTP request.
- `init()` creates a new `ScaleTieredMemory` whose L1 dict is empty.
- `init()` then calls `self.mem.get(UUID(Con.SUPER_ROOT_UUID))`. If nothing comes back, it creates a new `Root`, gives it the super-root UUID, and calls `mem.put` on it.
- `_process_cache` already existed in `memory_hierarchy`, but it was never used for the root.

### 3.2 What went wrong

```text
1. Request #1 arrives        → new context, L1 = {}
2. mem.get(SUPER_ROOT)       → L1 miss → L2 (Redis) → L3 MongoDB find_one   [fetch 1]
3. Root found (or created)   → stored in L1 for this request only
4. Request ends              → ctx.close() → L1 cleared
5. Request #2 arrives        → new context, L1 = {} again
6. mem.get(SUPER_ROOT)       → L1 miss → Redis → MongoDB find_one           [fetch 2]  ← WRONG: same object fetched again
7. ... every request N       → MongoDB fetch N                              ← WRONG
```

### 3.3 Why it mattered

- Issue #5874 explains that all IO drivers are synchronous and run inside `async def` handlers. A blocking call stops uvicorn's single event loop until it returns.
- This lookup is item #3 in the issue's table of 7 to 8 blocking network calls per request. At about 5 ms per call, the issue estimates the loop is blocked for 35 ms or more per request, which caps throughput at roughly 28 req/s.
- Removing one guaranteed `find_one` per request is a direct cut to that list. The other findings (availability pings, user root lookup, double commit, and so on) are not touched by this PR.

## 4. The idea of the fix (one sentence)

> **Warm each new L1 from a process-level copy of the system root.** After the first request resolves the system root, keep the anchor in `_process_cache` and put it into every later context's L1 before the lookup runs.

This leaves `TieredMemory.get()` unchanged and does not add a new cache. It reuses the existing L1-first short-circuit and the `_process_cache` slot that was already reserved for this purpose.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/context.impl.jac`: cache and reuse the system root anchor

```diff
 impl JScaleExecutionContext.init(self: JScaleExecutionContext) -> None {
-    import from jac_scale.memory_hierarchy { ScaleTieredMemory }
+    import from jac_scale.memory_hierarchy { ScaleTieredMemory, _process_cache }   # NEW: process-wide dict
 ...
     self.custom: Any = MISSING;
+    cached_root = _process_cache.get('system_root');                              # NEW: warm path
+    if cached_root is not None {
+        self.mem.__mem__[cached_root.id] = cached_root;                            # NEW: seed L1
+    }
     system_root_anchor: (Anchor | None) = self.mem.get(UUID(Con.SUPER_ROOT_UUID)); # now an L1 hit when warm
     if not isinstance(system_root_anchor, NodeAnchor) {
         system_root_anchor = Root().__jac__;
         system_root_anchor.id = UUID(Con.SUPER_ROOT_UUID);
         self.mem.put(system_root_anchor);
     }
+    _process_cache['system_root'] = system_root_anchor;                           # NEW: remember for next request
     self.system_root = system_root_anchor;
```

**What:**
1. `init()` reads `_process_cache['system_root']`.
2. If an anchor is there, `init()` writes it straight into L1 under its UUID.
3. `mem.get` then finds it in L1. MongoDB is not called.
4. After resolution, whether from L1, Redis, MongoDB or a newly created `Root`, `init()` stores the anchor in `_process_cache`.

**Why:** This removes steps 5 to 7 of the timeline. Only the first context in each process pays for the MongoDB fetch.

**Things to notice:**
- **Shared object.** Every context in the process now holds the same Python `NodeAnchor` object, not a copy. Any in-place change one request makes to it, such as adding an edge, is immediately visible to all other requests in the process, including concurrent ones, even before that request commits. The PR description says this is safe because `Root` has no user-mutable fields and edge writes go through the delta-merge in `_put_node_atomic`. The diff does not show that code, and the tests do not exercise mutation.
- **Edges do change.** Your own description says user registration adds edges to the system root. The issue says the root is "written once at boot and never mutated". These two claims disagree on whether the root's edges change.
- **No invalidation.** The cache has no TTL and is never refreshed. If another process or pod adds an edge to the system root, this process keeps its older copy of the edge list until it restarts. Whether that matters depends on code outside this diff, such as how the root's edges are read and whether `_put_node_atomic` merges against the DB.
- **Cold-create case.** If no root exists in the DB, a new `Root` is created and `put` into L1, and it is cached immediately, before any commit. If that request fails before committing, the cache holds a root that MongoDB does not have. Later requests would get it from L1 and would only persist it if their commit's `sync()` decides it is dirty. The diff doesn't show how that hash check treats it.
- **Repeated write.** `_process_cache['system_root'] = ...` runs on every request. On the warm path it stores the same object again, so it is harmless.
- **Scope.** "Process level" means one copy per uvicorn worker or pod. Each one warms independently.

### 5.2 `docs/docs/community/release_notes/unreleased/jac-scale/5919.bugfix.md`: release note

```diff
+- **Fix: redundant MongoDB system root lookup on every request eliminated**: ... The `_process_cache` dict now caches the system root anchor after the first resolve; subsequent requests inject it directly into L1 before the lookup, reducing per-request MongoDB round-trips to zero for this path.
```

## 6. How execution flows after the PR

### 6.1 First request in a process (cold cache)

```text
HTTP request
└─ request_context_middleware → JScaleExecutionContext()
   └─ init()
      ├─ mem = ScaleTieredMemory()  (L1 = {})
      ├─ _process_cache.get('system_root') → None                  ← NEW
      ├─ mem.get(SUPER_ROOT_UUID)
      │  ├─ L1 miss
      │  ├─ L2 (Redis, if configured)
      │  └─ L3 MongoDB find_one  (fetch_count = 1)
      ├─ if not found → Root() created, id = SUPER_ROOT_UUID, mem.put
      ├─ _process_cache['system_root'] = anchor                     ← NEW
      └─ system_root = user_root = entry_node = anchor
```

### 6.2 Every later request in the same process (warm cache)

```text
HTTP request
└─ JScaleExecutionContext()
   └─ init()
      ├─ mem = ScaleTieredMemory()  (L1 = {})
      ├─ _process_cache.get('system_root') → anchor                 ← NEW
      ├─ mem.__mem__[anchor.id] = anchor                            ← NEW
      ├─ mem.get(SUPER_ROOT_UUID) → L1 hit, return                  ← CHANGED (no Redis/Mongo)
      ├─ _process_cache['system_root'] = anchor  (same object)      ← NEW
      └─ system_root = user_root = entry_node = anchor
```

| Scenario | Before | After |
|---|---|---|
| First request, root in DB | 1 MongoDB fetch | 1 MongoDB fetch, then cached |
| First request, empty DB | 1 fetch + create | 1 fetch + create, then cached (before commit) |
| Later requests, same process | 1 MongoDB fetch each | 0 fetches |
| New worker or pod | 1 fetch each request | 1 fetch on its first request only |
| Root edges changed by another process | Seen on next request | Not seen by this process's cached object (unless other code reloads it; not shown) |

Users should notice no change in behaviour, only less latency and load on MongoDB. The last row is the one behaviour change you should be ready to discuss.

## 11. Questions your senior might ask

**Q: Why not just cache it in Redis?**
Redis is still a network round-trip and a blocking call on the event loop. The process-level dict costs nothing to read. Also, L2 already sits in the lookup path, and the issue shows the request still reached MongoDB.

**Q: Is the cached anchor a copy or the same object?**
It is the same object. Every context in the process puts that exact `NodeAnchor` into its L1.

**Q: What if two requests modify the system root at the same time?**
Both modify the same in-memory object. The PR relies on `_put_node_atomic`'s delta-merge to keep the DB correct. In-memory isolation between requests is not shown or tested in this PR.

**Q: How do other pods see changes to the system root?**
Through this cache, they don't. Each process keeps the anchor it loaded first. Whether the edge list gets reloaded elsewhere can't be told from this diff.

**Q: What happens on a brand-new database?**
The first context finds nothing, creates a `Root` with `SUPER_ROOT_UUID`, `put`s it into L1, and caches it right away. Saving it to MongoDB depends on that request's commit.

**Q: How do the tests prove MongoDB was skipped?**
They read `MongoBackend.fetch_count` on each context's new L3 backend. It is at least 1 for the first init and exactly 0 for every later one. Redis is turned off so L2 cannot hide a miss.

**Q: Does this fix the whole audit?**
No. It only fixes finding 1b. The availability pings, the `get_root_id` and `set_user_root` lookups, the double commit, Redis TTLs, the scheduler context leak and the other findings are untouched.

**Q: Why write into `mem.__mem__` directly?**
That keeps `TieredMemory.get()` unchanged and uses its L1-first short-circuit. The PR doesn't discuss whether a public API for seeding L1 would be better.

**Q: Could the cache hold the wrong thing?**
It only ever stores the anchor that `init()` resolved for `SUPER_ROOT_UUID`, and the first test checks its type and id. Stale contents are the real risk, not the wrong object.
