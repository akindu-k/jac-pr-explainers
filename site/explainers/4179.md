## 1. The short version

jac-scale runs a Jac app as a web server; the class that does this is `JacAPIServer`. Before this PR, users could register (`POST /user/register`) and log in (`POST /user/login`). **There was no API endpoint for a logged-in user to change their username or password.** Issue #4158 asked for these endpoints. The issue has no text.

**You added two authenticated endpoints, `PUT /user/username` and `PUT /user/password`.** Each one does the following:

1. Reads the `Authorization: Bearer <token>` header.
2. Checks that the token belongs to the same user named in the request body.
3. Passes the change to `self.user_manager`.

A username change returns a new token, because the old token carries the old name. A password change requires the current password.

Example: user `olduser_ab12` sends `{"current_username": "olduser_ab12", "new_username": "newuser_cd34"}` with their token. They get back the new `username`, the same `root_id` and a fresh `token`. After that, logging in as `olduser_ab12` returns `401`.

You also marked both paths as protected in the generated API docs (Swagger UI, described in section 2). The docs now use the page's global "Authorize" button instead of a per-endpoint `Authorization` text field.

**Status:** Merged on 2026-01-20, the same day it was opened. No other reviewer left a review or comment. All six CI checks passed on head commit `2f1cd0f`.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. It is a superset of Python, so Python libraries (FastAPI, pydantic, jwt) can be imported directly. |
| `.jac` / `.impl.jac` | Jac splits a class into two files. The *declaration* (`serve.jac`) lists method signatures. The *implementation* (`impl/serve.impl.jac`) holds the bodies, written as `impl Class.method(...) { ... }`. |
| jac-scale | A plugin that serves a Jac app as an HTTP API and can deploy it to Kubernetes. |
| `JacAPIServer` | The jac-scale server class. Its `start()` method registers all endpoints. **This is what the PR adds to:** two new methods, two new endpoint registrations and an OpenAPI tweak. |
| Endpoint | A URL plus an HTTP method that the server answers, e.g. `PUT /user/username`. |
| `PUT` | The HTTP method for "replace/update this resource". |
| `JEndPoint` | A jac-scale object that describes one endpoint: method, path, callback function, parameters, docs text. It is passed to `self.server.add_endpoint(...)`. |
| `APIParameter` / `ParameterType.BODY` | Describes one input of an endpoint. `BODY` means it comes from the JSON request body. |
| FastAPI `Request` | The raw incoming HTTP request object. The new handlers use it to read headers: `request.headers.get('Authorization')`. |
| JWT (JSON Web Token) | A signed token that proves who you are. In jac-scale it encodes the username. |
| Bearer token | The header format `Authorization: Bearer <jwt>`. The code removes the first 7 characters (`"Bearer "`) to get the token. |
| `validate_jwt_token` / `create_jwt_token` | Existing `JacAPIServer` helpers. The first returns the username inside a valid token, or nothing if the token is bad or expired. The second makes a new token for a username. Their bodies are not in this diff. |
| `user_manager` | The existing object that stores users. The PR calls `update_username(...)` and `update_password(...)` on it. Those methods are **not in this diff**, so they must already exist elsewhere (the tests pass). |
| `root_id` | The id of a user's root node in the Jac graph, where their data hangs. A rename must keep it the same. |
| `TransportResponse` | jaclang's standard response wrapper, built with `.success(data=...)` or `.fail(code=..., message=...)`. |
| `Meta(extra={'http_status': N})` | Metadata on a `TransportResponse` that tells the server which HTTP status code to send. |
| 400 / 401 / 403 | HTTP status codes. 400 = bad input. 401 = not authenticated (no token or bad token). 403 = authenticated but not allowed. |
| OpenAPI / Swagger UI | OpenAPI is a machine-readable description of the API. Swagger UI is the interactive docs page built from it. |
| `BearerAuth` security scheme | An entry in the OpenAPI schema. When an operation has `security: [{'BearerAuth': []}]`, Swagger UI sends the token from its "Authorize" button with that request. |
| pydantic `BaseModel` / `Field` | A Python library for typed data classes. `Field(...)` means "required". The PR declares two such models but does not use them (see 5.2). |

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- `JacAPIServer.start()` registers the user endpoints (login, register, SSO), static files and walker endpoints.
- `_configure_openapi_security()` edits the generated OpenAPI schema so that protected paths show a lock in Swagger UI.
- `user_manager` stores users. From the tests, a user has a `username`, a password and a `root_id`.

### 3.2 What was missing

```text
1. User registers:  POST /user/register {"username":"alice","password":"p1"}
   -> token(alice), root_id=R1
2. User wants to be called "alice2"
   -> no HTTP endpoint exists for this            <-- MISSING
3. User wants to change password p1 -> p2
   -> no HTTP endpoint exists for this            <-- MISSING
4. Only option visible from the PR: register a new account
   -> new root_id=R2, so the old graph data at R1 is not linked to the new account
```

The diff does not show whether another way existed, such as a CLI command or direct database edits.

### 3.3 Why it mattered

Issue #4158 ("Implement update username and PW end points") has no body, so the PR description is the only stated reason. It calls this "user profile management". Any app built on jac-scale that has accounts needs these operations. The rename test checks that `root_id` stays the same. That shows the goal: the user keeps their data after a rename.

## 4. The idea of the fix (one sentence)

> **Token-guarded self-service updates.** Each endpoint checks that the bearer token's username matches the account named in the body, then delegates the change to `user_manager` and maps every outcome to a clear HTTP status.

This fits the existing code. The rules about who may do what live in `JacAPIServer` methods that return `TransportResponse`, next to `login` and `create_user`. Storage stays in `user_manager`. The endpoints follow the same `JEndPoint` registration pattern as the existing login endpoint.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/serve.impl.jac`: the endpoint logic and registration

**(a) Registering at start-up**

```diff
     self.register_static_file_endpoint();
+    self.register_update_username_endpoint();
+    self.register_update_password_endpoint();
     # Use dynamic routing for HMR support, static routing for production
```

**What:** Both endpoints are added on every server start, before the walker endpoints.
**Why:** Without this, the routes would not exist.
**Things to notice:** They are registered in both watch mode and normal mode, because they come before the `if watch` branch.

**(b) Marking them as protected in OpenAPI**

```diff
+            } elif path in ['/user/username', '/user/password'] {
+                for method in path_item {
+                    if (method in ['put', 'patch']) {
+                        path_item[method]['security'] = [{'BearerAuth': []}];
+                    }
+                }
             }
```

**What:** For these two paths, any `put` or `patch` operation in the schema gets the `BearerAuth` requirement.
**Why:** Swagger UI then sends the token from its global "Authorize" button. Your comment on the PR explains this. It is what let you remove the per-endpoint `Authorization` text field.
**Things to notice:**
- Only `PUT` is registered, so the `'patch'` entry is future-proofing.
- The earlier branches of this `if/elif` chain are not visible in the diff.
- This only changes the docs. The real check happens in the methods below.

**(c) `update_username`**

```diff
+impl JacAPIServer.update_username(self, current_username: str, new_username: str,
+                                  Authorization: (str | None) = None) -> TransportResponse {
+    token = Authorization[7:] if it starts with 'Bearer '          # (condensed)
+    token_username = self.validate_jwt_token(token) if token else None;
+    if not token_username        -> fail UNAUTHORIZED      (401)
+    if token_username != current_username -> fail FORBIDDEN (403)
+    if not new_username          -> fail VALIDATION_ERROR  (400)
+    result = self.user_manager.update_username(current_username, new_username);
+    if 'error' in result         -> fail UPDATE_FAILED     (400)
+    result['token'] = self.create_jwt_token(new_username);   # NEW token for new name
+    return TransportResponse.success(data=result, 200)
```

**What:** Four checks in a fixed order. If all pass, it calls `user_manager` and adds a new JWT to the result.
**Why:** This is the core feature. The 403 check stops one user from renaming another.
**Things to notice:**
- The order matters. Authentication comes first, then permission, then validation. A wrong `current_username` gives 403 even if that user does not exist, so the endpoint does not reveal which usernames exist.
- The duplicate-name error comes from `user_manager`. It is returned as 400 `UPDATE_FAILED` with that message. It is not a 409 "Conflict".
- The **old token is not revoked** in this code. It still carries the old username. Whether other endpoints accept it after the rename depends on code not in the diff.
- `Authorization` is a plain method parameter, so the method can be called and tested without HTTP.

**(d) `update_password`**

```diff
+impl JacAPIServer.update_password(self, username, current_password, new_password,
+                                  Authorization=None) -> TransportResponse {
+    (same token parsing / 401 / 403 as above, message "...another user's password")
+    if (not current_password or not new_password) -> VALIDATION_ERROR (400)
+    result = self.user_manager.update_password(username, current_password, new_password);
+    if 'error' in result -> UPDATE_FAILED (400)
+    return TransportResponse.success(data=result, 200)
```

**What:** The same guard pattern. The current password is passed to `user_manager`, which presumably checks it. The test with a wrong password expects 400, so something rejects it.
**Why:** Requiring the current password means a stolen token alone cannot change the password.
**Things to notice:**
- A wrong current password returns **400**, not 401 or 403.
- There is no password strength rule here, only "not empty".
- Existing tokens are not invalidated after a password change, as far as this diff shows.
- The token-parsing block is copied in both methods. It could become a small helper.

**(e) Registration functions**

```diff
+impl JacAPIServer.register_update_username_endpoint(self) -> None {
+    import from fastapi { Request }
+    async def update_username_handler(request: Request, current_username: str,
+                                      new_username: str) -> TransportResponse {
+        authorization = request.headers.get('Authorization');   # NEW: header, not a param
+        return self.update_username(current_username, new_username, authorization);
+    }
+    self.server.add_endpoint(JEndPoint(method=HTTPMethod.PUT, path='/user/username',
+        callback=update_username_handler,
+        parameters=[APIParameter('current_username', BODY, required),
+                    APIParameter('new_username', BODY, required)],
+        tags=['User APIs'], summary='Update username', ...));
+}
```

`register_update_password_endpoint` is the same, with three body parameters: `username`, `current_password` and `new_password`.

**What:** This wraps each method in an `async` handler. The handler pulls the `Authorization` header from the raw `Request`, then registers the route.
**Why:** Your PR comment explains it. Earlier versions listed `Authorization` as an `APIParameter`, which made a text box appear on every endpoint in Swagger. Reading the header directly removes that box.
**Things to notice:**
- The handler is `async`, but it calls synchronous methods. If `user_manager` hashes passwords slowly, this blocks the event loop while it runs. The diff cannot show how expensive that is.
- The commit history went through several approaches before landing here:
  - returning `JSONResponse` (`8b898f2`),
  - a TransportResponse→JSONResponse helper (`eeb3339`),
  - "request handlers for authorization" (`a1329aa`).
- The final diff returns `TransportResponse` and has no helper. Those earlier approaches were dropped.

## 6. How execution flows after the PR

### 6.1 Server start

```text
JacAPIServer.start()
├─ register_login_endpoint / sso / client_js / static ...
├─ register_update_username_endpoint()          ← NEW  (PUT /user/username)
├─ register_update_password_endpoint()          ← NEW  (PUT /user/password)
└─ walker endpoints (dynamic if watch, else static)
```

### 6.2 `PUT /user/username`

```text
HTTP PUT /user/username  body {current_username, new_username}
└─ update_username_handler(request, ...)                      ← NEW
   ├─ authorization = request.headers['Authorization']
   └─ update_username(...)                                     ← NEW
      ├─ no/invalid "Bearer ..." token     → 401 UNAUTHORIZED
      ├─ token user ≠ current_username     → 403 FORBIDDEN
      ├─ new_username empty                → 400 VALIDATION_ERROR
      ├─ user_manager.update_username(...)
      │   └─ returns {'error': ...}        → 400 UPDATE_FAILED (e.g. name taken)
      └─ result + token=create_jwt_token(new_username) → 200
```

### 6.3 `PUT /user/password`

```text
HTTP PUT /user/password  body {username, current_password, new_password}
└─ update_password_handler(request, ...)                      ← NEW
   └─ update_password(...)                                     ← NEW
      ├─ bad token                         → 401
      ├─ token user ≠ username             → 403
      ├─ either password empty             → 400 VALIDATION_ERROR
      ├─ user_manager.update_password(...)
      │   └─ {'error': ...} (e.g. wrong current pw) → 400 UPDATE_FAILED
      └─ result                            → 200 (no new token)
```

### 6.4 OpenAPI schema

```text
_configure_openapi_security()
└─ for each path
   ├─ (existing branches, not shown in diff)
   └─ path in /user/username, /user/password      ← NEW
      └─ put/patch → security = [BearerAuth]       → lock icon + global Authorize in Swagger
```

## 11. Questions your senior might ask

**Q: Where is the actual username/password change stored?**
In `user_manager.update_username` / `update_password`. Those methods are not in this diff. The PR only adds the HTTP layer and the authorization checks.

**Q: Why return a new token on rename but not on password change?**
The JWT encodes the username. After a rename, the old token names a user who no longer exists, so the client needs a token for the new name. A password change does not change the username.

**Q: Does the old token still work after a rename?**
This code does not revoke it. What other endpoints do with it depends on `validate_jwt_token` and code not in the diff. No test covers it.

**Q: Why check `token_username != current_username` if we already have the token?**
So that one user cannot change another user's account. The body names the target, and the token must match it, otherwise the request gets 403.

**Q: Why is a wrong current password a 400 and not a 401?**
Every `user_manager` error maps to `UPDATE_FAILED` with status 400. The caller is already authenticated, so 401 would be misleading. It is a design choice you could defend or change.

**Q: Why read `Authorization` from `Request` instead of declaring it as a parameter?**
Declaring it showed an extra text field on every endpoint in Swagger. Reading the header directly, together with the `BearerAuth` security entry, uses Swagger's global "Authorize" button instead.

**Q: What are `UpdateUsernameRequest` and `UpdatePasswordRequest` for?**
Nothing in the final diff uses them. Body parameters are declared with `APIParameter`. They should be removed or wired in.

**Q: Why does the OpenAPI branch check `'patch'` when only `PUT` is registered?**
It is future-proofing. It has no effect today.

**Q: Does an `async` handler calling sync code cause problems?**
It runs on the event loop thread. If password hashing in `user_manager` is slow, it blocks other requests for that time. The cost cannot be judged from this diff.
