## 1. The short version

`jac start` runs a small built-in HTTP server for a Jac app. Since #4125, that server keeps its users in one SQLite table. A user can register (`POST /user/register`) and log in (`POST /user/login`) to get a token.

**Before this PR, a user could not change their username or password after registering.** The server had no handler for HTTP `PUT` at all. Its CORS header also did not allow `PUT`, so browsers would block such requests anyway.

**You added two authenticated endpoints, `PUT /user/username` and `PUT /user/password`.** Each one checks the bearer token, refuses to change another user's account, and writes the change to the SQLite `users` table. The password endpoint also checks the current password first. You also added `PUT` to the CORS allowed methods, added a `put()` helper to `JacTestClient`, and wrote eight tests.

Example: after `PUT /user/username` with `{"current_username": "olduser", "new_username": "newuser"}`, logging in as `newuser` works and logging in as `olduser` fails. The user's `root_id` stays the same, so their graph data is kept.

**Status:** Merged on 2026-01-18, the same day it was opened. There were no reviews or comments. All six CI checks passed on head commit `d3275b2`.

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- `UserManager` could create users, check logins, validate tokens, and read user data. It had no way to change a user's row.
- `AuthHandler` exposed `create_user` and `login` only.
- `JacRequestHandler` had `do_GET`, `do_POST` and `do_OPTIONS`, but no `do_PUT`.
- The CORS header sent `GET, POST, OPTIONS`.
- `JacTestClient` could send `GET`, `POST` and `OPTIONS` only.

### 3.2 What went wrong: a user wants a new password

```text
1. Alice registers: users row = {username: alice, password_hash: H(old), token: T, root_id: R}
2. Alice wants to change her password to "newpass"
3. No endpoint exists for it                                   ← MISSING
4. If she sends PUT /user/password anyway:
   Python's BaseHTTPRequestHandler finds no do_PUT
   → it replies 501 "Unsupported method ('PUT')"                ← MISSING
5. From a browser frontend: the preflight OPTIONS response lists
   "GET, POST, OPTIONS", so the browser blocks the PUT before sending it ← MISSING
6. Only workaround: register a new account
   → new root_id, so Alice loses access to her graph data under R
```

The 501 in step 4 is standard Python `http.server` behaviour when a `do_<METHOD>` method is missing. The diff does not show it directly.

### 3.3 Why it mattered

Issue #4129 asks for logged-in users to "update their own username or password securely". It lists the rules: users only change their own data, tokens are validated, and the current password must be checked. The issue and the PR give no other user report. It is a basic account-management gap for any app built on `jac start` auth.

## 4. The idea of the fix (one sentence)

> **Add `PUT` routes that check the token against the target account.** The new `do_PUT` handler reads the token, `AuthHandler` confirms it belongs to the user named in the body, and `UserManager` updates that user's SQLite row in place.

Updating the row in place keeps `root_id` and the stored token unchanged. So the user keeps their graph and stays logged in. Checking ownership in `AuthHandler` keeps `UserManager` as a plain data layer, matching how `create_user` and `login` are already split.

### 5.2 `jac/jaclang/runtimelib/impl/server.impl.jac`: `UserManager` SQL

```diff
+impl UserManager.update_username(current_username: str, new_username: str) -> dict[str, str] {
+    import hashlib;                                   # unused here
+    self._ensure_connection();
+    cursor = self._conn.execute("SELECT 1 FROM users WHERE username = ? ", (new_username, ));
+    if cursor.fetchone() { return {'error': 'Username already taken'}; }
+    cursor = self._conn.execute(
+        "UPDATE users SET username = ? WHERE username = ?", (new_username, current_username));
+    self._conn.commit();
+    if cursor.rowcount == 0 { return {'error': 'User not found'}; }
+    cursor = self._conn.execute("SELECT token, root_id FROM users WHERE username = ?", (new_username, ));
+    row = cursor.fetchone();
+    return {'username': new_username, 'token': row[0], 'root_id': row[1]};
+}
+
+impl UserManager.update_password(username: str, current_password: str, new_password: str) -> dict[str, str] {
+    import hashlib;
+    self._ensure_connection();
+    current_password_hash = hashlib.sha256(current_password.encode()).hexdigest();
+    cursor = self._conn.execute(
+        "SELECT 1 FROM users WHERE username = ?  AND password_hash = ?", (username, current_password_hash));
+    if not cursor.fetchone() { return {'error': 'Current password is incorrect'}; }
+    new_password_hash = hashlib.sha256(new_password.encode()).hexdigest();
+    cursor = self._conn.execute(
+        "UPDATE users SET password_hash = ? WHERE username = ?", (new_password_hash, username));
+    self._conn.commit();
+    return {'username': username, 'message': 'Password updated successfully'};
+}
```

**What:**
- `update_username` refuses a name that is already taken. Otherwise it renames the row and returns the row's existing `token` and `root_id`.
- `update_password` checks the hash of the current password. If it matches, it stores the hash of the new one.

**Why:** These are the actual data changes the feature needs. All SQL uses `?` parameters, so user input is not pasted into the SQL text.

**Things to notice:**
- **The token is not rotated.** The returned `token` is the same one already stored, so old tokens keep working after a rename or a password change.
  - Issue #4129 says the endpoint should return "a new token if the username is changed". The code returns the existing token, not a new one.
  - The tests only check that `"token" in data`.
  - After a password change, any stolen token stays valid.
- Hashing is unsalted SHA-256. It must match whatever `login` uses; the passing "login with new password" test shows it does. Unsalted SHA-256 is weak for passwords, but that scheme comes from existing code, not this PR.
- **Renaming to your own current name fails.** The `SELECT` finds your own row, so you get `'Username already taken'`.
- **Check-then-update is not atomic.** Two concurrent renames to the same name could both pass the `SELECT`. The diff does not show whether `username` has a `UNIQUE` constraint. If it does, the second `UPDATE` would raise an `IntegrityError` that is not caught here. If it does not, you could end up with duplicate usernames.
- `commit()` runs before the `rowcount` check. That is harmless, because a zero-row update changes nothing.
- `import hashlib` in `update_username` is unused.
- `update_password` has no `rowcount` check. The verify step already proved the row exists.

### 5.3 `jac/jaclang/runtimelib/impl/server.impl.jac`: `AuthHandler` checks

```diff
+impl AuthHandler.update_username(current_username: str, new_username: str, token: str) -> TransportResponse {
+    token_username = self.user_manager.validate_token(token);
+    if not token_username                 → fail UNAUTHORIZED     (401)
+    if token_username != current_username → fail FORBIDDEN        (403)
+    if not new_username                   → fail VALIDATION_ERROR (400)
+    result = self.user_manager.update_username(current_username, new_username);
+    if 'error' in result                  → fail UPDATE_FAILED    (400)
+    return TransportResponse.success(data=result, meta=Meta(extra={'http_status': 200}));
+}
+
+impl AuthHandler.update_password(username, current_password, new_password, token) -> TransportResponse {
+    # same shape: 401 → 403 → 400 if either password empty → UPDATE_FAILED 400 → success 200
+}
```

The block above is condensed. The real code builds each failure with `TransportResponse.fail(code=..., message=..., meta=Meta(extra={'http_status': N}))`.

**What:** Each method runs four checks in a fixed order: valid token, then same user, then non-empty input, then the database result. Only after all of them does it return success.

**Why:** This is where the issue's security rules live. Only the token owner can change their own account.

**Things to notice:**
- The body must name the user (`current_username` or `username`), even though the token already identifies them. The body name is only used to compare against the token. A reviewer may ask why the server doesn't take the username from the token alone.
- The ownership check runs before the empty-field check. So a body with a missing `current_username` returns **403**, not 400.
- A wrong current password returns **400 `UPDATE_FAILED`**, not 401 or 403. The test `test_update_password_wrong_current` locks this in.
- There is no format or length check on the new username or password beyond "not empty".

## 6. How execution flows after the PR

### 6.1 `PUT /user/username`

```text
Client PUT /user/username  {current_username, new_username}  + Bearer token
└─ JacRequestHandler.do_PUT                                          ← NEW
   ├─ _read_json() fails                → 400 {"error":"Invalid JSON"}
   ├─ _get_auth_token() empty           → 401 {"error":"Authentication required"}
   └─ path == /user/username
      └─ AuthHandler.update_username                                 ← NEW
         ├─ validate_token fails        → 401 UNAUTHORIZED
         ├─ token user ≠ current_username → 403 FORBIDDEN
         ├─ new_username empty          → 400 VALIDATION_ERROR
         └─ UserManager.update_username                              ← NEW
            ├─ new name exists          → 400 UPDATE_FAILED "Username already taken"
            ├─ UPDATE matches 0 rows    → 400 UPDATE_FAILED "User not found"
            └─ SELECT token, root_id    → 200 {username, token (unchanged), root_id (unchanged)}
```

### 6.2 `PUT /user/password`

```text
Client PUT /user/password  {username, current_password, new_password} + Bearer token
└─ do_PUT (same JSON + token gate)                                   ← NEW
   └─ AuthHandler.update_password                                    ← NEW
      ├─ bad token                      → 401 UNAUTHORIZED
      ├─ token user ≠ username          → 403 FORBIDDEN
      ├─ either password empty          → 400 VALIDATION_ERROR
      └─ UserManager.update_password                                 ← NEW
         ├─ sha256(current) ≠ stored    → 400 UPDATE_FAILED "Current password is incorrect"
         └─ UPDATE password_hash        → 200 {username, message}
```

### 6.3 Other `PUT` paths and CORS

```text
PUT /anything-else (with token)  → do_PUT → 404 {"error":"Not found"}      ← NEW
OPTIONS preflight                → Allow-Methods: GET, POST, PUT, OPTIONS  ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| `PUT /user/username` with valid token, own account | 501 (no `do_PUT`) | 200, row renamed, same token and `root_id` |
| `PUT /user/password` with correct current password | 501 | 200, new hash stored |
| `PUT` with no token | 501 | 401 raw JSON |
| Token for user1, body names user2 | 501 | 403 |
| Rename to an existing name, or to your own name | 501 | 400 |
| Wrong current password | 501 | 400 |
| Old token after a rename or password change | n/a | Still valid. Not rotated. |
| Browser cross-origin `PUT` | Blocked by CORS | Allowed |

Changes users will notice: the new routes, `PUT` in the CORS header, and the two new banner lines at startup. Nothing changes for existing `GET` and `POST` behaviour.

## 11. Questions your senior might ask

**Q: Does the user keep their data after renaming?**
Yes. The `UPDATE` changes only `username`. The `root_id` stays the same, and `test_update_username` asserts this.

**Q: After a username change, does the old token still work?**
The same token is returned and stays in the row. Whether it maps to the new name depends on `validate_token`, which this diff doesn't show. The fact that the endpoint returns the stored token suggests the lookup is by token in the table, so it would follow the rename. No test checks this.

**Q: Why doesn't a password change invalidate existing tokens?**
The PR doesn't rotate tokens. That is a gap: a leaked token survives a password change. It would need a follow-up.

**Q: Why send `current_username` in the body if the token identifies the user?**
It is only compared against the token's username, giving 403 on a mismatch. The design could take the username from the token alone. The PR doesn't explain the choice.

**Q: What stops user1 from changing user2's password if user1 knows it?**
The ownership check. The token must belong to the named user. `test_update_password_cannot_update_other_users` covers this exact case.

**Q: Is the SQL safe from injection?**
Yes. Every query uses `?` parameters with tuple arguments.

**Q: What if two requests rename to the same name at once?**
Both could pass the `SELECT` check. The outcome depends on whether `username` has a `UNIQUE` constraint, which isn't visible here. If it does, the second `UPDATE` raises an uncaught error. If it doesn't, you get duplicate usernames.

**Q: Why did you touch CORS?**
Browsers send a preflight `OPTIONS` request before a cross-origin `PUT`. Without `PUT` in `Access-Control-Allow-Methods`, frontends could never call these endpoints.

**Q: Does jac-scale get these endpoints too?**
This diff only changes `jaclang/runtimelib`. Whether jac-scale reuses this server or has its own auth layer can't be told from the PR. Its CI checks passed.
