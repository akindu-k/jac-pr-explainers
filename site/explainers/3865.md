## 1. The short version

`UserManager` lives in the Jac runtime server. It keeps a table of users in memory and in a `<session>.users.json` file. When someone signs up, `create_user` makes a fresh root node for that user, saves it, and records the username, a password hash and a token. `ShelfDB` is jac-scale's storage layer, built on Python's `shelve` file database. Each `ShelfDB` object guarded its file with its own private lock.

No linked issue describes a failure, so the bug has to be read from the code. **Before this PR, nothing stopped two threads from running `create_user` for the same username at the same time.** Both could pass the "User already exists" check. Both would then build a root and write `_users["alice"]`, and the second write would silently replace the first. In the same way, two `ShelfDB` objects pointing at the same file each had their own lock. That meant they did not block each other.

**You added a lock per username around the whole of `create_user`, a separate lock around writing the users file, and one shared `RLock` per shelf file path for every `ShelfDB` that opens that path.** You made no test changes, and some parts of the description do not match the code (see section 10).

## 3. The problem, step by step

### 3.1 The setup

- **`UserManager`** has three key fields: `_users` (username → `{password_hash, token, root_id}`), `_tokens` (token → username) and `_db_path` (the JSON file).
- **`create_user`** runs these steps: check name → new context → create and commit `Root` → reset context → make token → update both dicts → `_persist()`.
- **`ShelfDB.postinit`** used to do `self._lock = RLock()`, giving every instance its own lock. The commit messages (`65ee063`, `44a6e09`) say methods such as `find_by_id` and `commit` use `self._lock`. The final diff does not show those methods, so that is either already on `main` or was dropped. I can't tell which.

### 3.2 What went wrong: same username created twice at once

```text
1. Thread A: create_user("alice", "pw1")
2. Thread B: create_user("alice", "pw2")
3. A: "alice" in _users? → no
4. B: "alice" in _users? → no            ← WRONG: A hasn't written yet, both pass the check
5. A: creates Root, commit → root_id = R1
6. B: creates Root, commit → root_id = R2
7. A: _users["alice"] = {hash(pw1), tokenA, R1}; _tokens[tokenA] = "alice"
8. B: _users["alice"] = {hash(pw2), tokenB, R2}; _tokens[tokenB] = "alice"   ← overwrites A
9. A returns {token: tokenA, root_id: R1}  → caller A holds a root that is no longer linked to "alice"
10. _tokens still has tokenA → "alice", so A's token now acts on B's account (root R2)
11. A and B both call _persist() with no lock  → two writes to the same file at once
```

Step 10 follows from the code as shown, assuming token lookups go through `_tokens`. The lookup code is not in the diff.

### 3.2b What went wrong: two `ShelfDB` objects on one file

```text
1. ShelfDB #1 opens "data.shelf", lock = RLock#1
2. ShelfDB #2 opens "data.shelf", lock = RLock#2
3. Thread X writes via #1, holding RLock#1
4. Thread Y writes via #2, holding RLock#2 (does not wait, different lock)   ← WRONG
5. Two handles write the same shelve file at once → possible corruption / lost writes
```

How often several `ShelfDB` objects exist for one path cannot be seen in this diff. The commit `94f156e` ("Refactor shelf management ... for improved concurrency") suggests it happens, for example one per context.

### 3.3 Why it mattered

The PR has no linked issue and no comments, so no one has reported a concrete failure. The branch is named `fix/user-creation`, which points at the duplicate-signup race. What it could hurt: duplicate or hijacked accounts, orphaned root nodes, a corrupted `users.json`, and a corrupted shelf store under parallel load.

## 4. The idea of the fix (one sentence)

> **Lock per thing that can collide.** Serialize work on the same username, the same users file and the same shelf path, and let unrelated work run in parallel.

A per-username lock blocks only the case that actually conflicts, two signups for one name. A per-path shelf lock makes every object that touches one file agree on a single lock.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/server.jac`: declare the new fields

```diff
     has session_path: str,
         _users: dict[(str, dict[(str, str)])] = {},
         _tokens: dict[(str, str)] = {},
-        _db_path: str = "";
+        _db_path: str = "",
+        _user_locks: Any = None,     # NEW: filled in postinit
+        _persist_lock: Any = None;   # NEW: filled in postinit
```

- **What:** Adds two fields that start as `None`.
- **Why:** Jac objects need fields declared before `postinit` assigns them.
- **Things to notice:** The type is `Any` rather than `defaultdict[str, Lock]`, which is the loosest choice. The locks are created in `postinit`, not as defaults, so each `UserManager` gets its own. A shared mutable default would be a bug. Note that `_users`/`_tokens` use `{}` as a default. Whether Jac copies that default per instance is not visible here.

### 5.2 `jac/jaclang/runtimelib/impl/server.impl.jac`: lock user creation and file writes

```diff
 impl UserManager.postinit -> None {
+    import from threading { Lock }
+    import from collections { defaultdict }
+    self._user_locks = defaultdict(Lock);   # NEW: one Lock per username, made on first use
+    self._persist_lock = Lock();            # NEW: one lock for the users.json file
     self._db_path = f"{self.session_path}.users.json";
     self._load_db();
 }
```

```diff
 impl UserManager.create_user(username: str, password: str) -> dict[str, str] {
-    if (username in self._users) {
+    with self._user_locks[username] {            # NEW: everything below runs under alice's lock
+        if (username in self._users) {
             return {'error': 'User already exists'};
         }
         ctx = Jac.create_j_context(session=self.session_path);
         ... create Root, save, commit, reset context (unchanged, re-indented) ...
         token = secrets.token_urlsafe(32);
         ...
         self._tokens[token] = username;
-    self._persist();
+        with self._persist_lock {                # NEW: only one writer to users.json
+            self._persist();
+        }
+        return {'username': username, 'token': token, 'root_id': root_id};
+    }
```

```diff
 impl UserManager.close -> None {
-    self._persist();
+    with self._persist_lock {                    # NEW: close can't write while a signup writes
+        self._persist();
+    }
 }
```

- **What:** The check, root creation, dict updates and file write for one username now happen as one locked block. File writes from any path (`create_user`, `close`) go through `_persist_lock`.
- **Why:** This fixes steps 4 and 11 of the timeline in 3.2. The second "alice" waits, then sees "User already exists".
- **Things to notice:**
  - **This does not match the description.** The description says the persist lock lets you avoid "holding user locks during I/O". In the code, `with self._persist_lock` is *inside* `with self._user_locks[username]`, so the user lock is held during the file write. It is also held during `Jac.commit`, which is I/O too. This is only a contention cost, not a correctness bug. Either the description or the code should change.
  - **Different usernames still run in parallel through shared state.** `Jac.set_context(ctx)` and the `finally` reset `Jac.set_context(Jac.create_j_context())` run with no shared lock. If the Jac context is process-global rather than per-thread, thread B could swap the context while A is building its root. Whether the context is thread-local is not visible in this diff, and a reviewer should ask.
  - `self._users[...] = ...` in one thread can run while `_persist()` reads `_users` in another, because inserts are not under `_persist_lock`. If `_persist` iterates the dict (for example `json.dump`), it could raise `RuntimeError: dictionary changed size during iteration`. `_persist`'s body is not in the diff.
  - `_user_locks` entries are never removed, so the dict grows by one lock for every distinct username ever tried, including rejected ones.
  - `defaultdict` creating a missing key is effectively atomic in CPython because of the GIL (the global interpreter lock that lets only one thread run Python code at a time). Python does not formally promise this, though, and it would not hold on free-threaded Python.
  - `authenticate`, `get_user` and other readers were not given locks.
  - `return` inside `with` is fine: the lock is released on return.

### 5.3 `jac-scale/jac_scale/memory_hierarchy.jac`: global lock registry

```diff
 glob _db_config = get_scale_config().get_database_config(),
-     ID = TypeVar('ID');
+     ID = TypeVar('ID'),
+     _shelf_locks: dict[str, RLock] = {};   # NEW: shelf_path → shared RLock
```

- **What:** Adds a module-level dict that every `ShelfDB` in the process shares.
- **Why:** A lock has to be shared to protect a shared file.
- **Things to notice:** Commit `9798943` "fix type in shelf locks" touched this annotation. In Python, `threading.RLock` is a factory function rather than a class, which is why some type checkers complain about `dict[str, RLock]`. The diff does not show where `RLock` is imported in this file.

### 5.4 `jac-scale/jac_scale/impl/memory_hierarchy.impl.jac`: use the shared lock

```diff
 impl ShelfDB.postinit{
-    self._lock = RLock();                                   # OLD: private lock per instance
+    import from jac_scale.memory_hierarchy { _shelf_locks }
+    if (self.shelf_path not in _shelf_locks) {
+        _shelf_locks[self.shelf_path] = RLock();
+    }
+    self._lock = _shelf_locks[self.shelf_path];             # NEW: same lock for same path
     self._open_shelf();
 }
```

- **What:** All `ShelfDB` objects with the same `shelf_path` string now share one `RLock`. Every existing method that uses `self._lock` gets the protection without any change.
- **Why:** This fixes step 4 of 3.2b.
- **Things to notice:**
  - **The registry has its own check-then-act race.** If two `ShelfDB` objects for a new path are built at the same moment, both can see "not in", and each creates an `RLock`. The second overwrites the first, so the first instance keeps a lock nobody else shares. `self._lock = _shelf_locks.setdefault(self.shelf_path, RLock())` closes that gap in CPython.
  - The key is the raw string, so `"./data.shelf"` and `"/app/data.shelf"` get different locks even if they are the same file.
  - The lock is in-process only. Several worker processes or Kubernetes pods sharing one shelf file are still unprotected.
  - The locks are never removed.

No release notes or docs changed.

## 6. How execution flows after the PR

### 6.1 Creating a user

```text
create_user("alice", pw)
├─ take _user_locks["alice"] (created on first use)          ← NEW
│   ├─ "alice" in _users? → yes → return {'error': 'User already exists'}  (lock released)
│   ├─ ctx = create_j_context(session); set_context(ctx)
│   ├─ Root() → save → commit → root_id
│   ├─ finally: ctx.mem.close(); set_context(new default ctx)
│   ├─ token, password_hash; _users["alice"] = {...}; _tokens[token] = "alice"
│   ├─ take _persist_lock                                      ← NEW
│   │   └─ _persist() → write <session>.users.json
│   └─ release _persist_lock                                   ← NEW
└─ return {...}; release alice's lock                          ← CHANGED (whole body is locked)
```

### 6.2 Closing the manager

```text
close()
└─ with _persist_lock → _persist()     ← CHANGED
```

### 6.3 Opening a shelf

```text
ShelfDB(shelf_path=P)
└─ postinit
   ├─ P in _shelf_locks? no → _shelf_locks[P] = RLock()   ← NEW
   ├─ self._lock = _shelf_locks[P]                         ← CHANGED (shared, not private)
   └─ _open_shelf()
```

| Scenario | Before | After |
|---|---|---|
| Two signups, same name, same time | Both could succeed; the last write wins | Second waits, then gets "User already exists" |
| Two signups, different names | Parallel | Still parallel (separate locks); the shared context and dict access are not locked |
| Signup write + `close()` at once | Two writers to users.json | Serialized |
| Two `ShelfDB` on the same path | Independent locks → concurrent writes | Shared lock → serialized (in one process) |
| Two processes/pods on one shelf | Unprotected | Still unprotected |

User-visible change: the only one is that a duplicate signup racing another now reliably gets the error. Signups for the same name, and shelf operations on the same path, may now wait on each other.

## 10. Is it ready to merge?

**Not yet.**

1. The PR is closed with no review or approval. Any merge needs it reopened (or a new PR).
2. The description disagrees with the code. It says "reducing contention by not holding user locks during I/O", but `_persist()` runs while the user lock is held, and so does `Jac.commit`.
3. `_shelf_locks` population is itself racy, which defeats the point of the change in the exact case it targets.
4. Parallel signups of *different* users still share `Jac.set_context` and the `_users` dict without a common lock. Whether that is safe can't be told from this diff.
5. There is no test showing the duplicate-signup race is fixed.
6. The lock dicts are unbounded (minor).

Before merging:
- Reopen the PR, or open a new one, and get a review.
- Either move `_persist()` outside the user lock (keeping it under `_persist_lock`) or fix the description.
- Change the shelf lock setup to `_shelf_locks.setdefault(self.shelf_path, RLock())`, and consider normalizing the path with `os.path.abspath`.
- Confirm the Jac context is thread-local, or explain why parallel `set_context` calls are safe.
- Put the `_users`/`_tokens` updates under `_persist_lock`, or snapshot them inside `_persist`.
- Add a test: N threads call `create_user("alice")`, and exactly one must succeed.
- Clarify whether the `find_by_id`/`commit` locking from earlier commits is meant to be part of this PR.

## 11. Questions your senior might ask

**Q: What bug did you actually see?**
The PR has no linked issue or report. The fix targets the check-then-act race in `create_user`, where two signups for one name both pass the existence check and the last one overwrites the first.

**Q: Why a per-username lock instead of one lock for `create_user`?**
So that different usernames can sign up in parallel. Only same-name signups conflict on the existence check.

**Q: Your description says user locks aren't held during I/O. Is that true?**
No. `with self._persist_lock { self._persist(); }` sits inside `with self._user_locks[username]`, and `Jac.commit` also runs under the user lock.

**Q: Are parallel signups of different users safe?**
Only if `Jac.set_context` is per-thread. Each signup sets a context and then resets it to a fresh default one. If the context is global, threads can interfere. This diff does not show which it is.

**Q: Can two `ShelfDB` objects still end up with different locks for one path?**
Yes. Two can be created at the same instant for a new path, and the `if not in → assign` gap lets each create its own lock. `setdefault` fixes it.

**Q: Does this protect a shelf shared by several pods?**
No. `threading` locks only work inside one process. Cross-process access would need file locking or a real database.

**Q: Why `RLock` for shelves but `Lock` for users?**
The shelf code already used `RLock`, presumably because locked methods call each other. User creation does not re-enter its own lock, so a plain `Lock` is enough.

**Q: Do the lock dictionaries leak?**
They grow with every distinct username or shelf path and are never cleaned up. That is small per entry, but unbounded for usernames.

**Q: How do we know it works?**
Today we don't: CI passes, but no test runs concurrent signups. A threaded test asserting exactly one success is the missing proof.
