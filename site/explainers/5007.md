## 1. The short version

`jac format` rewrites a `.jac` file in a standard layout. With `--lintfix`, it also applies automatic lint fixes. Internally it builds a `JacProgram` from the file, reads the generated source text from `prog.mod.main.gen.jac`, and writes that text back over the original file.

**When the file had a parse error, the generated text was an empty string, and the command wrote that empty string to disk, so the user's file was wiped.** For example, with `can say_name() {` (which should be `def say_name() {`), the user saw `✖ Error: ParseError at line 5: Expected 'with' after 'can' ability name ...` and then found `test.jac` empty.

**You added a guard just before the write: if the formatted output is empty and the program recorded errors, print those errors and return `(False, False, 0)` without touching the file.** Files with valid syntax and only type or lint errors still produce non-empty output, so they are still formatted. You also added a regression test and a release-note entry.

**Status:** Merged on 2026-03-06. No reviews or comments. All test checks passed, and the release-pipeline jobs were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **CLI entry:** `jac format --lintfix test.jac` calls `format(...)` in `analysis.impl.jac`.
- **Per-file helper:** `format_single_file()` runs `JacProgram.jac_file_formatter(str(path_obj), auto_lint=lintfix)`. It then reads `gen.jac` and calls `write_formatted_code` inside a `try` block.
- **Compiler behaviour:** on a parse error, the compiler does not raise an exception. It records the error in `errors_had` and leaves `gen.jac` as `""`.

### 3.2 What went wrong

```text
1. test.jac on disk = "obj User {\n    can say_name() {\n ... }\n}\n"   (valid text, bad syntax)
2. prog = JacProgram.jac_file_formatter("test.jac", auto_lint=True)
     → parse fails, prog.errors_had = [ParseError at line 2 ...]
3. formatted_code = prog.mod.main.gen.jac        → ""   (no tree, nothing generated)
4. original_code  = prog.mod.main.source.code    → original text
5. changed = ("" != original_code)               → True
6. write_formatted_code("", "test.jac")          ← WRONG: overwrites file with ""
7. test.jac on disk = ""                          (content lost)
8. Error is reported to the user                  (too late; file already empty)
```

Nothing between step 3 and step 6 checked whether the output was usable. Because no exception was raised, the `try`/`except` never stepped in before the write.

### 3.3 Why it mattered

- This is permanent data loss. The issue (#5006) shows the whole file becoming empty after one command.
- The trigger is common. Using `can` instead of `def` is an easy mistake, and the error message itself hints at it.
- A formatter is a tool people run without thinking, often on save or across many files. One typo could erase a file the user had not committed yet.
- The issue's expected behaviour: report the error, and do **not** modify the file.

## 4. The idea of the fix (one sentence)

> **Never write empty output when the compiler reported errors.** If `gen.jac` is empty and `prog.errors_had` is not, print the errors and leave the file alone.

Empty output plus recorded errors is the exact signal of "parsing failed", and it is cheap to check right before the write. It also does not block formatting of files that only have type or lint errors, because those still produce non-empty output.

## 5. Every code change, explained

### 5.1 `jac/jaclang/cli/commands/impl/analysis.impl.jac`: guard before writing

```diff
             try {
                 formatted_code = prog.mod.main.gen.jac;
                 original_code = prog.mod.main.source.code;
+
+                if not formatted_code or len(formatted_code.strip()) == 0 {   # NEW: output empty/whitespace?
+                    if prog.errors_had {                                       # NEW: and compiler had errors?
+                        for error in prog.errors_had {
+                            console.error(f"{error}");                         # NEW: show each error
+                        }
+                        return (False, False, 0);                              # NEW: bail out, no write
+                    }
+                }
+
                 changed = formatted_code != original_code;
                 write_formatted_code(formatted_code, str(path_obj));
```

**What:** Before computing `changed` and writing, the code checks two things:

1. Is the formatted output `None`, `""` or only whitespace?
2. Did the compiler record any errors?

If both are true, it prints every error to stderr and returns `(False, False, 0)` from `format_single_file`, so `write_formatted_code` is never reached.

**Why:** This blocks step 6 of the timeline in 3.2. The empty string never reaches the disk.

**Things to notice:**

- **Three cases, as your description explains:**
  - Empty output with errors: skip the write.
  - Empty output with no errors: still writes. This covers a genuinely empty file.
  - Non-empty output with errors: still writes. This covers type or lint errors.
- **Partly redundant condition.** `not formatted_code` covers `None` and `""`, and `len(...strip()) == 0` covers whitespace-only output. The second check alone would fail on `None`, so keeping both is safe.
- **Any error counts.** The check uses all of `errors_had`, not only parse or lex errors. The release note and description say "parse/lex errors". In practice this only matters if some non-parse error could also empty the output, and the diff does not show whether that can happen.
- **Partial output is not covered.** If a parse error ever produced *non-empty but truncated* `gen.jac`, this guard would not catch it, and the truncated text would be written. The diff does not show whether the compiler can do that.
- **Possible double reporting.** The issue shows the error being printed already, in the `✖ Error: ...` style. Your loop prints the errors again via `console.error`. Whether users now see each error twice cannot be told from the diff.
- **Placement.** The guard sits inside the existing `try`, so a `return` from it skips the later write but stays under the same exception handling.

### 5.2 `docs/docs/community/release_notes/jaclang.md`: release note

```diff
 ## jaclang 0.12.1 (Unreleased)
 
+- **Fix: `jac format --lintfix` File Deletion on Parse Errors**: Fixed a critical bug where ... The formatter now preserves the original file when parse/lex errors are present, while still allowing files with type errors (but valid syntax) to be formatted normally. Added a safety check in `format_single_file()` that prevents writing empty formatted output to disk.
```

**What:** Adds an entry under the unreleased 0.12.1 section.

**Why:** The "Check Release Notes Updated" CI job requires it, and users need to know about a data-loss fix.

**Things to notice:** "Preserves the original file when parse/lex errors are present" is slightly stronger than the code. The code preserves the file when errors are present **and** the output is empty.

## 6. How execution flows after the PR

### 6.1 Running `jac format --lintfix file.jac`

```text
jac format --lintfix file.jac
└─ format([...], lintfix=True)                     (analysis.impl.jac)
   └─ format_single_file(path)
      ├─ prog = JacProgram.jac_file_formatter(path, auto_lint=True)
      └─ try
         ├─ formatted_code = prog.mod.main.gen.jac
         ├─ original_code  = prog.mod.main.source.code
         ├─ if formatted_code empty/whitespace                    ← NEW
         │  └─ if prog.errors_had                                 ← NEW
         │     ├─ console.error(each error)                       ← NEW
         │     └─ return (False, False, 0)   (file untouched)     ← NEW
         ├─ changed = formatted_code != original_code
         └─ write_formatted_code(formatted_code, path)
```

The new branch does not depend on `lintfix`, so plain `jac format` takes the same path. There was already a test called "format preserves file on syntax error" for the non-lintfix case. Why that case was already safe before this PR is not visible in the diff.

| Scenario | Before | After |
|---|---|---|
| Parse/lex error, `gen.jac` empty | File overwritten with `""` (data loss) | File unchanged, errors printed, returns `(False, False, 0)` |
| Valid file, no errors | Formatted and written | Same |
| Valid syntax, type/lint errors, non-empty output | Formatted and written | Same |
| Empty/whitespace file, no errors | Written (empty) | Same (guard falls through) |
| Parse error with non-empty partial output (if possible) | Written | Still written. Not covered by this guard. |

**User-visible change:** a file with a syntax error is no longer emptied. The user sees the error list, and the file is reported as not formatted.

### `jac/tests/language/test_cli.jac`

New test: **"format --lintfix preserves file on parse error"**

- **Setup:** Creates a temp directory and writes `parse_error.jac` containing `obj User { can say_name() { print("hi"); } }`, which is the `can`-without-`with` parse error from the issue.
- **Action:** Redirects `sys.stderr` to a `StringIO`, which hides the error output. It then calls `analysis.format([test_file], lintfix=True)` and restores stderr in `finally`.
- **Check:** Reads the file back and asserts the content is exactly the original. On failure, the message shows both versions with `repr`.
- **Proves:** The exact reproduction from #5006 no longer changes the file.

**Why a new test:** The test right above it, "format preserves file on syntax error", already covers the non-lintfix path. This one adds the `lintfix=True` path that the issue reports.

**Gaps a reviewer could point out:**

- It does not assert on the captured stderr, so it does not check that the error was actually printed.
- It does not check the return value.
- There is no test for "type errors still get formatted" or "empty valid file", which are the other two cases your description lists.

## 11. Questions your senior might ask

**Q: Why not just check `prog.errors_had` and skip writing whenever it is non-empty?**
Files with valid syntax but type or lint errors would then never be formatted. With `--lintfix`, that is exactly when people want the tool to run. Your description lists this case as intentional.

**Q: Why does an empty file with no errors still get written?**
An empty output with no errors is a legitimate result for an empty or whitespace-only file. The inner `if prog.errors_had` deliberately lets that case through.

**Q: Why didn't the existing `try/except` protect the file?**
The compiler does not raise on parse errors. It records them and returns `""` from `gen.jac`. No exception happened before `write_formatted_code`, so the handler only ran afterwards, if at all.

**Q: Does this also protect plain `jac format` without `--lintfix`?**
Yes. The guard does not look at `lintfix`. A separate existing test, "format preserves file on syntax error", already covered the non-lintfix path.

**Q: What does `(False, False, 0)` mean?**
From the diff, it is the "failed, not changed, zero" result of `format_single_file`. The diff does not show the caller, so I can't confirm each field's exact meaning.

**Q: Could a partial parse produce non-empty, truncated output that still gets written?**
This guard would not catch it. Whether the compiler can produce that is not visible in this PR. A stricter rule ("any parse error → don't write") would close that gap.

**Q: Will users see the error twice?**
Possibly. The issue shows the error being printed already, and you now print `errors_had` again. This should be checked by running the command.

**Q: Why does the test redirect stderr?**
To keep test output clean, since the formatter prints the parse error. It does not assert on the captured text. Adding that assertion would also prove the error is reported.

**Q: Why are so many CI jobs skipped?**
They are release-workflow jobs (publish, tag, build binaries) that only run for releases. All the test jobs ran and passed.
