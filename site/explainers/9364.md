## 1. The short version

`jac.toml` values can point at environment variables, for example `API_KEY = "${MY_KEY}"`. When jac loads the config, it swaps in the variable's value. #9350 added a deploy check: if a setting about to ship still holds `${...}` because the variable is unset, `jac scale deploy` stops and names the setting.

**The bug: that check only sees what the config parser writes down, and the parser only understands three forms: `${VAR}`, `${VAR:-default}` and `${VAR:?message}`. Any other form, such as `${MY_KEY:+on}`, `${MY_KEY:0:3}` or `${MY_KEY-default}`, was skipped without a word.** The deploy then exited clean and wrote the literal text `${MY_KEY:+on}` into a Kubernetes Secret.

**The fix: the parser now matches every `${...}`. If the body starts with a variable name but is not one of the three supported forms, it records an "unsupported" reference. The deploy refuses that reference, even when the variable is set.** The new error line reads:

```
scale.secrets.API_KEY: ${MY_KEY:+on} is not a form jac reads (use ${VAR}, ${VAR:-default} or ${VAR:?message})
```

Shell syntax under `[scripts]` and `[environments.<name>.scripts]` is left alone, because a shell expands it later. Bodies that do not start with a name, such as `${1}` or `${#arr[@]}`, also stay as they are.

**Status:** Merged on 2026-09-30. @MusabMahmoodh first requested changes, approved on 2026-09-24, and re-approved the head commit `014f870`. All CI checks on the head commit passed or were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **Parser:** `interpolate_env_vars` in `jac/jaclang/project/impl/config.impl.jac`. Old pattern: `\$\{([^}:]+)(?:(:[-?])([^}]*))?\}`. The name group is "anything except `}` or `:`". The optional operator is only `:-` or `:?`.
- **Recorder:** config load passes a sink, so every unresolved `${...}` becomes an `UnresolvedRef` with a `path` such as `scale.secrets.KEY`.
- **Consumers:** the deploy check (#9350) and the pod-boot check (#9199) both act *only* on the recorded refs. No ref means nothing to report.

### 3.2 What went wrong

#### Case A: `${VAR:+alt}` or `${VAR:0:3}` (colon forms other than `:-` and `:?`)

```text
1. jac.toml:  [scale.secrets] SAFE = "${MISSING_PLAIN}"  SNEAKY = "${MISSING_ALT:+on}"
2. Neither MISSING_PLAIN nor MISSING_ALT is exported.
3. Parser scans SAFE  → pattern matches, var unset → UnresolvedRef(SAFE) recorded.
4. Parser scans SNEAKY → name "MISSING_ALT", then ":+" is neither ":-" nor ":?",
   and the next char is not "}" → NO MATCH.                          ← WRONG STEP
5. SNEAKY keeps the text "${MISSING_ALT:+on}". Recorded refs: [SAFE] only.
6. Deploy check reports: "scale.secrets.SAFE: MISSING_PLAIN is not set". SNEAKY is never named.
7. If SAFE were absent: refs = [] → deploy exits 0 → Secret SNEAKY = "${MISSING_ALT:+on}".
```

The same happens when `MISSING_ALT` *is* exported. The form never matches, so jac never reads the variable, and the literal ships either way.

#### Case B: no-colon forms `${VAR-default}`, `${VAR?msg}`, `${VAR/a/b}`

@MusabMahmoodh found this case in review. Your first commit did not cover it.

```text
1. jac.toml: KEY = "${MY_KEY-default}"
2. Old name group [^}:]+ eats the whole body → var_name = "MY_KEY-default".
3. source.get("MY_KEY-default") → None; there is no operator.
4. "MY_KEY-default".isidentifier() is False → return text verbatim, nothing recorded.  ← WRONG STEP
5. Literal "${MY_KEY-default}" ships; no check fires.
```

#### Case C: a regression the first version would have caused (`[scripts]`)

This was caught in review before merge.

```text
1. jac.toml: [scripts] build = "npm run build ${CI:+--ci}"   (valid shell)
2. sanitized_jac_toml keeps [scripts] → it ships to the pods.
3. First version of the PR: parser now records ${CI:+--ci} as unsupported.
4. Pod-boot check walks the whole shipped file → reports scripts.build.   ← WRONG STEP
5. Every deploy with that script fails, although the shell would expand it fine.
6. Same for [environments.ci.scripts] (path environments.ci.scripts.build), fixed in 014f870.
```

### 3.3 Why it mattered

- #8773 was the original bug: a literal `${...}` became a live config value, in that case a Kubernetes namespace. #9350 built the deploy check to stop that. Case A let the same symptom happen *inside* that check.
- The issue says a check that names some unresolved values but not others is worse than no check, because a clean exit now looks like a positive answer.
- The real-world cost: pods start fine, then the first API call fails with a bad key, and the error points at the API provider instead of `jac.toml`.
- Issue #9184 asked for this gap to be fixed first and on its own. The issue also notes that `service_urls.jac` still keeps a `"${" not in raw` guard because of this hole.

## 4. The idea of the fix (one sentence)

> **Record what you can't read.** Match every `${...}`, and if its body starts with a variable name but is not one of the three supported forms, record it as an unsupported reference instead of returning it silently.

This makes every existing consumer refuse the value through the path it already has, with no change to the checks themselves. It also covers future unsupported forms, not just the two the issue named. The alternative, implementing `:+` and `:0:3`, would only fix those two.

**What:** The outer pattern now catches every `${...}`. Inside the callback there are three outcomes:
1. The body does not start with an identifier. The text stays verbatim, as before.
2. The body is one of the three forms. Behaviour is the same as before.
3. Anything else is recorded with `unsupported=True` and the full original text in `form`.

`report_env_findings` now gets each line's text from the new `reason()` method.

**Why:** This fixes Cases A and B. Recording means both the deploy check and the pod-boot check see the value without any change to their own logic.

**Things to notice:**
- **Unsupported forms are recorded before the environment is read.** `${DEPLOY_REGION:+on}` fails even with `DEPLOY_REGION` exported, because the literal would ship anyway.
- **You used two regexes (`supported` plus `leading`) instead of @MusabMahmoodh's suggested "reconcile `parts` after" shape.** You offered to switch. He said the two-regex version is fine. The cost is that the identifier pattern is written twice.
- **`reason()` came from @MusabMahmoodh's inline suggestion and was applied in `87d0216`.** Without it, the line would have read `MY_KEY is not set` when the variable is set and the form is the real problem.
- **The two methods use different wording for different callers.** `describe()` ("Unsupported form ...") is used when raising and by the pod-boot check. `reason()` ("... is not a form jac reads ...") is used by the deploy check. The tests assert each wording on its own path.
- **Behaviour change you noted:** calling `interpolate_env_vars` without a sink now *raises* on an unsupported form. The description says the only in-tree caller passes a sink.
- **A subtle change worth knowing, worked out from the diff (not mentioned in the PR):** the old code checked `:-` *before* `isidentifier()`. So `${1:-x}` used to return `x`. Now `leading` is `None`, so `${1:-x}` stays verbatim. This is unlikely to matter in config, but it is a real difference.
- **Nested braces are unchanged.** `${A:-${B}}` still matches only up to the first `}`. That is gap 3 of #9184 and stays open.

## 6. How execution flows after the PR

### 6.1 Interpolating one `${...}`

```text
interpolate_env_vars(value, sink, environ)
└─ re.sub(r"\$\{([^}]*)\}", replace_env_var, value)          ← CHANGED (matches any ${...})
   └─ replace_env_var(match)
      ├─ body = text between the braces
      ├─ leading = identifier at the start of body?           ← NEW
      │  └─ no  → return text verbatim (${1}, ${#arr[@]}, ${})
      ├─ parts = fullmatch(supported, body)?                  ← NEW
      │  ├─ no  → record = UnresolvedRef(unsupported=True, form=...)   ← NEW
      │  └─ yes → var set?        → return value
      │           op ":-"?        → return default
      │           else            → record = UnresolvedRef(required=op==":?")
      └─ sink given? → append record, return text verbatim
         else        → raise ValueError(record.describe())
```

### 6.2 `jac scale deploy`: the deploy check

```text
jac scale deploy
├─ JacConfig.load → resolve_env_refs → refs collected via sink
├─ _check_deploy_settings_resolve (from #9350)
│  └─ refs on shipped settings? → report_env_findings(refs, context, hint)
│     ├─ header (generic "machine does not have" wording, unchanged)
│     ├─ "  {path}: {ref.reason()}" per ref                  ← CHANGED
│     │  └─ unsupported → "${X:+on} is not a form jac reads (use ...)"  ← NEW
│     └─ hint (generic "Export each one..." wording, unchanged)
└─ no refs → deploy continues
```

### 6.3 Pod-boot check on the shipped `jac.toml`

```text
unresolved_toml_references(text, pod_environ)
├─ resolve_env_refs(tomllib.loads(text), environ)
├─ for each ref: _is_shell_script_ref(ref)?                  ← NEW
│  ├─ unsupported AND path under scripts.* / environments.*.scripts.* → skip
│  └─ otherwise → "{path}: {ref.describe()}"
└─ non-empty list → deploy stops before pods start
```

| Scenario | Before | After |
|---|---|---|
| `scale.secrets` `${MISSING_ALT:+on}`, var unset | Ships literal, exit 0 | Deploy stops: "is not a form jac reads" |
| `scale.secrets` `${DEPLOY_REGION:+on}`, var set | Ships literal, exit 0 | Deploy stops (same message) |
| `${VAR:0:3}`, `${VAR-default}`, `${VAR?msg}`, `${VAR/a/b}` | Verbatim, unrecorded | Recorded as unsupported |
| `[plugins.demo] alt = "${DEMO_ALT:+on}"` (pod path) | Passes | Fails: `Unsupported form ${DEMO_ALT:+on}` |
| `[scripts] build = "... ${CI:+--ci}"` | Passes | Passes (exempt) |
| `[environments.ci.scripts] build = "... ${CI:+--ci}"` | Passes | Passes (exempt) |
| `[scripts]` `${UNSET_ONE}` | Reported | Reported (unchanged) |
| `${1}`, `${1:+x}`, `${#arr[@]}`, `${}` | Verbatim | Verbatim |
| `${A}` / `${A:-d}` / `${A:?m}` | Unchanged | Unchanged |
| `interpolate_env_vars("${A:+x}")` with no sink | Returns text | Raises `ValueError` |
| `${1:-x}` (worked out from the diff) | `x` | `${1:-x}` verbatim |

**User-visible change:** projects that used an unsupported form in a shipped setting, even one that "worked" because nobody noticed the literal, now fail `jac scale deploy` until the value is rewritten with a supported form.

## 11. Questions your senior might ask

**Q: Why record unsupported forms instead of implementing `:+` and `:0:3`?**
The issue offered both options. Recording is smaller, and it covers every future unsupported form, not just two. As you told @kugesan1105, config has no use case for those operators.

**Q: Why fail when the variable is set? Isn't that over-strict?**
jac cannot evaluate `:+` either way, so the literal `${VAR:+on}` would reach the Secret whether or not the variable is set. Stopping only when it is unset would leave the same literal shipping.

**Q: Why put this in the parser rather than in the deploy check?**
Both checks act only on recorded refs. Fixing the parser means every consumer of `resolve_env_refs` gets the fix for free. @MusabMahmoodh called this the right place.

**Q: Won't this break `${1}` or `${#arr[@]}` in values?**
No. A body that does not start with an identifier returns verbatim before any classification. Test rows `echo ${1:+on}` and `echo ${#arr[@]}` pin this.

**Q: Why are only *unsupported* refs exempt in scripts, not unset ones?**
An unset `${VAR}` in a script was already reported before this PR, because it is jac's own interpolation. The exemption only stops the new rule from breaking valid shell syntax.

**Q: Why are there two message methods, `describe()` and `reason()`?**
`describe()` is the full error used when raising and by the pod-boot check. `reason()` is the short text after the setting's path in the deploy check's list. It names the supported forms, so a user with the variable exported is not told to export it.

**Q: Did anything change for direct callers of `interpolate_env_vars`?**
Yes. With no sink, it now raises on an unsupported form, which matches what it already did for an unset `${VAR}`. The description says the only in-tree caller passes a sink. `${1:-x}` also no longer returns `x`.

**Q: Does this let us remove the `"${" not in raw` guard in `service_urls.jac`?**
The PR does not touch it, and the diff alone cannot tell. Verbatim cases such as `${1}` and exempted scripts can still carry a raw `${`, so removing it would need a separate check.

**Q: What about nested braces and the `$${...}` escape?**
They are out of scope. They are gaps 2 and 3 of #9184, which touch the same brace matching. `${A:-${B}}` still behaves as before.

**Q: Could the header and hint mislead users now?**
Slightly. For an exported variable with an unsupported form, the header ("this machine does not have") and the hint ("Export each one") are still generic, but the line itself names the correct fix. The reviewer accepted leaving them unchanged.
