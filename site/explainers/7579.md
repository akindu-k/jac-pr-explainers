## 1. The short version

Every anonymous visitor to a Jac Scale app shares one "guest" workspace. That workspace is a single root node of the graph, and the server finds it through a `root_id` saved on a special guest user row. **Before this PR, that `root_id` was a random UUID created once, so nothing could recompute it. If the row or the node was lost (a migration, a prune, a partial restore), anonymous requests failed. The earlier repair from #6498 also let each pod (server instance) invent its own replacement id, so visitors could land on different guest graphs.**

**You replaced the random id with a computed one: `uuid5(uuid5(NAMESPACE, project_name), "__guest__")`.** Every pod gets the same value with no coordination. You also changed three behaviours:

- An existing deployment keeps its old random id for as long as that id still points at a real `Root`.
- When the id is broken, the resolver switches to the computed id and writes it back to the guest user row.
- When the node is missing, `get_shared_root` now creates it instead of raising an error.

Example: for a project named `shop` in `jac.toml`, every pod derives the same 32-character hex id, on every restart.

On 2026-08-20, @MusabMahmoodh checked the branch against current `main`. He found three things:

- The branch was 373 commits behind `main`.
- The split-brain race is now handled on `main` by different code (`IdentityStorage.ensure_user_by_id`).
- The layer this diff patches has been deleted.

He also said the core problem (a random id that cannot be recovered) is still present on `main`.

**Status:** Closed without merging on 2026-09-04 by @marsninja ("no activity in 10+ days"). All CI checks passed on head commit `e85824c`, but they ran against July's `main`. @MusabMahmoodh's review was never answered.

## 3. The problem, step by step

### 3.1 The setup

- At startup, `serve.core.impl.jac` (full server) and `inprocess.jac` (in-process runtime) create the guest user with `create_internal_user(Con.GUEST.value, '__no_password__')`.
- `IdentityStorage.create_user` makes a fresh `Root()`, saves it, and stores its random id as `root_id` on the user row.
- The server registers a resolver that returns `get_root_id(Con.GUEST.value)`. That is just a read of the stored row.
- `JacRuntime.get_shared_root` calls the resolver, then `mem.get(UUID(root_id))`. If the result is not a `Root`, it raises `RuntimeError`.

### 3.2 What went wrong: broken pointer

```text
1. First boot: guest row created, root_id = a3f1... (random), Root a3f1... saved
2. Anonymous requests read/write graph under Root a3f1...           OK
3. Data loss: Root node a3f1... is pruned / lost in a partial restore
4. Guest row still says root_id = a3f1...
5. get_shared_root -> mem.get(a3f1...) -> None
6. isinstance(None, Root) is False -> RuntimeError                ← WRONG: every anonymous request fails
7. Nobody can say what the id "should" be; it was random
```

### 3.3 What went wrong: split-brain after repair (#6498 path)

Per the issue, the repair from #6498 re-ran the resolver and wrote a *new random* id. Its `threading.Lock` only covers one process. That lock is not visible in this diff.

```text
1. Pod A and Pod B both detect the stale root_id a3f1...
2. Pod A mints root_id = 7c20... and writes it
3. Pod B mints root_id = e914... and writes it (about the same time)
4. Pod A caches 7c20..., Pod B caches e914...                     ← WRONG: two guest graphs
5. Visitor hits Pod A -> writes to graph 7c20...
6. Same visitor hits Pod B -> sees graph e914..., its data is "gone"
```

### 3.4 Why it mattered

- Anonymous/public features of a Jac Scale app could break entirely after routine operations: a migration, a data prune, or a pod restart with partial data.
- In multi-pod Kubernetes deployments, the repair could split anonymous data across disconnected graphs.
- Issue #6698 says this explicitly: the per-process lock "does not coordinate across pods". It asks for a computable id so that any repair always writes the same value.
- @MusabMahmoodh later confirmed that the "lose the row, lose the workspace" problem is still true on `main` (`identity_storage.impl.jac:73`, `:111`, `:148` still use a random `Root()` id, and `reset_root` mints another random id).

## 4. The idea of the fix (one sentence)

> **Compute the guest root id instead of inventing it.** The id is `uuid5` of a fixed namespace, the project name and `"__guest__"`, so every pod and every restart arrives at the same value and can rebuild it.

A computed id cannot get lost and cannot diverge, so "repair" becomes an idempotent write of one known value. The fix also keeps any old random id that still works, so live deployments do not lose their anonymous data.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/identity/guest_root.jac`: computes the deterministic id (new file)

```diff
+glob _GUEST_ROOT_NAMESPACE: UUID = uuid5(NAMESPACE_DNS, 'jaseci.scale.guest-root'),
+     _DEFAULT_SCOPE: str = 'jaseci',
+     _scope_fallback_warned: list = [False],
+     logger = logging.getLogger(__name__);
+
+def resolve_project_scope -> str {
+    import from jaclang.project.config { get_config }
+    config = get_config();
+    if config is not None and config.project.name {
+        return config.project.name;
+    }
+    if not _scope_fallback_warned[0] {          # NEW in 959c57c: warn once
+        _scope_fallback_warned[0] = True;
+        logger.warning("Guest root scope falling back to '%s' ...", _DEFAULT_SCOPE);
+    }
+    return _DEFAULT_SCOPE;
+}
+
+def compute_guest_root_id(project_scope: str | None = None) -> str {
+    scope = project_scope or resolve_project_scope();
+    project_namespace = uuid5(_GUEST_ROOT_NAMESPACE, scope);
+    return uuid5(project_namespace, Con.GUEST.value).hex;
+}
```

**What:** This file builds a fixed namespace from the string `'jaseci.scale.guest-root'`. It derives a per-project namespace from the project name, then hashes the guest user's name into it. It returns hex with no dashes, the same format as `__jac__.id.hex`.

**Why:** This is the core of the fix. Any pod can compute the id at any time with no shared state.

**Things to notice:**
- If `[project] name` is missing, the scope falls back to `'jaseci'`. Every unnamed project on a shared backend then gets the *same* guest root. Greptile flagged this as P1. Commit 959c57c only adds a one-time warning; the collision still happens.
- Two projects with the same name also collide.
- Renaming a project changes the computed id. Because of 5.2, a deployment still keeps its stored id while that id is valid.
- `_scope_fallback_warned` is a one-item list used as a mutable flag. It is not thread-safe. The worst case is a duplicate warning.
- `project_scope` is an optional override. No caller in the diff uses it, but it makes testing easier.
- The issue proposed `UUIDv5(namespace=project_uuid, name="__guest__")`. The code builds that `project_uuid` from the project name, because there is no stored project UUID to use.

```diff
+impl JacScaleUserManager.resolve_shared_root_id -> str {
+    guest = self.get_user(Con.GUEST.value);
+    stored = guest.get('root_id') if guest else None;
+    if stored {
+        anchor = Jac.get_context().mem.get(UUID(stored));
```

The interface file `user_manager.jac` adds the matching signatures and `def resolve_shared_root_id -> str;`.

**What:**
- `create_internal_user` can now pass a fixed `root_id` down to storage.
- `resolve_shared_root_id` follows this order:
  1. Keep a stored id if it still points at a real `Root`.
  2. Otherwise use the computed id.
  3. If the row disagrees with the computed id, update the row.

**Why:** The resolver gives the safe migration path the issue asked for ("dual-lookup fallback"). Old deployments with a working random id keep their data. Broken ones converge on the computed id.

**Things to notice:**
- `create_internal_user` used to call `self.create_user(username, password)`. It now calls `create_user_with_identities` with hand-built identity and credential dicts. The body of `create_user` is not in the diff, so you cannot confirm from the diff that the two paths are equivalent (for example, the same normalisation or validation). Expect to be asked.
- Whether "stored id valid" is judged correctly depends on `mem.get`. If `mem.get` only checks an in-process cache and not the database, a valid legacy id could look missing. The row would then be overwritten with the computed id, which strands the old graph. The diff does not show which way `mem.get` behaves.
- If the write fails, the method still returns `deterministic`. That pod uses the right id, but the row stays stale. The log message says "next restart", which suggests the runtime caches the resolver's result per process (`_shared_root_resolver[1] = root_id`).
- If `guest` is `None`, no row is written; the method just returns the computed id.

## 6. How execution flows after the PR

### 6.1 Server start (`JacAPIServerCore.start`)

```text
start()
├─ compute_guest_root_id()                                   ← NEW
│   ├─ resolve_project_scope() -> jac.toml [project] name or 'jaseci' (+ warn once)
│   └─ uuid5(uuid5(NS, scope), GUEST).hex
├─ create_internal_user(GUEST, '__no_password__', root_id=<computed>)   ← CHANGED
│   └─ create_user_with_identities(..., root_id)             ← CHANGED (was create_user)
│       └─ IdentityStorage.create_user(..., root_id)
│           ├─ Root(); id = UUID(root_id)                    ← NEW
│           └─ save, commit, store row with root_id
└─ set_shared_root_resolver(() -> resolve_shared_root_id())  ← CHANGED
```

The in-process path (`prepare_inprocess_runtime`) is the same, except that it creates the guest user only when `get_root_id(GUEST)` is `None`.

### 6.2 Anonymous request needs the shared root

```text
JacRuntime.get_shared_root()
├─ (earlier code, not in diff) call resolver, cache in _shared_root_resolver[1]
│   └─ resolve_shared_root_id()                              ← NEW
│       ├─ guest row has root_id AND mem.get(id) is a Root -> return stored
│       └─ else: id = compute_guest_root_id()
│           ├─ guest row exists and differs -> update_user_fields(root_id=id)
│           │   └─ failed -> logger.warning                  ← NEW
│           └─ return id
├─ mem.get(UUID(root_id))
├─ None? -> new Root with that id, save, commit             ← NEW
└─ not a Root? -> RuntimeError (unchanged)
```

| Scenario | Before | After |
|---|---|---|
| Fresh deployment | Random guest root id | Computed id, the same on every pod |
| Old deployment, random id still valid | Uses it | Still uses it (no migration) |
| Guest row present, node lost | `RuntimeError` on every anonymous request | Row rewritten to computed id; empty root created there |
| Two pods repairing at once | Could write different random ids (split-brain) | Both write the computed id |
| Guest row lost, node with computed id exists | n/a (ids were random) | New `Root` saved at same id; effect on existing edges not visible in diff |
| No `[project] name`, several apps on one backend | Separate random roots | **Shared** guest root, plus a warning |

User-visible changes:

- Anonymous requests no longer fail on a missing root. They get an *empty* recreated workspace instead, so lost anonymous data stays lost, but the app works.
- Unnamed projects on a shared backend now share guest data.

**Q: Why UUIDv5 and not just a fixed constant id?**
A constant would make every project share one guest root. UUIDv5 over the project name keeps the id stable *and* separate per project.

**Q: What happens to existing deployments with a random guest id?**
`resolve_shared_root_id` keeps the stored id as long as `mem.get` returns a `Root` for it. It switches to the computed id only when the old one is already broken.

**Q: What if `[project] name` is not set?**
The scope falls back to `'jaseci'` and a warning is logged once. All unnamed projects on one backend then share a guest graph. Greptile flagged this, and only the warning was added.

**Q: If the guest user row is lost but the node survives, do we really "point back" at it?**
`IdentityStorage.create_user` builds a new empty `Root()` with the same id and saves it. Whether that overwrites the stored node and its edges depends on `Jac.save` and `commit`, which are not in this diff. This needs to be checked before claiming recovery.

**Q: Can two pods racing in `get_shared_root` still cause trouble?**
They now agree on the id, so there is no split-brain. Both may still save an empty `Root` at that id. The diff does not show whether a late save could clobber data the other pod just wrote.

**Q: Why change `jaclang` core instead of only the scale plugin?**
The `RuntimeError` on a missing node lived in `get_shared_root`, so get-or-create had to go there. That change affects every shared-root resolver, not just Jac Scale's.

**Q: Why does `create_internal_user` now call `create_user_with_identities` instead of `create_user`?**
`create_user` does not take a `root_id`. The new path builds the username identity and password credential directly. You cannot confirm from the diff that this matches what `create_user` did.
