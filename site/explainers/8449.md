## 1. The short version

Jac Scale puts one gateway process in front of all your services. It receives each HTTP request and forwards it to the service that owns the path. The HTTP server underneath it is the "serving core" (`ServingServer` plus `ServingApp`).

**The bug: the serving core read the whole request body into memory before routing, and the outbound client then made a second copy while sending it, so every in-flight upload cost the gateway about twice its size in RAM.** Your measurement shows the problem. One 90 MiB `POST` raised gateway peak RSS from 208.2 MiB to 395.0 MiB (+186.7 MiB). The serving core also had no read timeout on a declared-length body.

**The fix: the body now reaches the app as an async chunk stream, and the gateway's `forward_to` passes that stream straight to the upstream connection.** Ordinary endpoints call `load_body()` first, so they still see a complete `request.body`. Builtin passthrough still buffers on purpose, because it replays the body to several services. After the fix, the same 90 MiB upload leaves gateway peak RSS flat at 262.5 MiB.

**Status:** Closed without merging on 2026-09-11 by the stale bot (`github-actions[bot]`, "no activity in 10+ days"). All CI checks on head `5c401c5` passed or were skipped. @MusabMahmoodh wants it reopened. He listed three semantic conflicts with newer `main` (#8121, #8981, #8119) that a rebase must fix first.

## 3. The problem, step by step

### 3.1 The setup

- A client sends `POST /api/orders/...` with a 90 MiB body to the gateway.
- The gateway runs on `ServingServer`. The old `_read_body` read every byte (`readexactly(length)` or a list of chunks joined) into `Request.body` before any middleware or route ran.
- `forward_to` took `request.body` (bytes) and gave it to `stream_forward` → `arequest`.
- `arequest` wrote `blob + body`. That concatenation creates another full-size bytes object.

### 3.2 What went wrong: a large upload through the proxy path

```text
1. Client sends headers: Content-Length: 94371840            gateway RSS ≈ 208 MiB
2. ServingServer._read_body: readexactly(94371840)            Request.body = 90 MiB  (copy #1)
3. Middleware → gateway forward_to: body = request.body       still copy #1
4. stream_forward → arequest: writer.write(blob + body)       blob+body = 90 MiB     (copy #2)  ← WRONG: second full copy
5. Peak RSS ≈ 395 MiB (+186.7 MiB ≈ 2 × 90 MiB)                ← WRONG: cost grows with upload size × concurrent uploads
6. Upstream receives 94371840 bytes; response returned
```

### 3.3 What went wrong: the builtin passthrough path

```text
1. Request for /walker/<name> with a body arrives
2. Body fully buffered (same as step 2 above)
3. Passthrough loop sends the same bytes to service A → 404, then B → 404, then C …
```

This path needs the bytes kept, because it replays them. #7901 covers the replay itself. This PR leaves the path buffering on purpose.

### 3.4 Smaller gaps in the old reader

```text
- Content-Length bodies: readexactly() had no timeout   ← a stalled client could hold the read open
- Chunked trailers: readline() had no timeout
```

The new `_read_exact` and `_read_body_line` put `body_timeout` on every read.

### 3.5 Why it mattered

#7908 rated this "high (robustness)". The gateway is "the single ingress for the fleet". Concurrent uploads multiply the cost, and "nothing equivalent guards the gateway itself". Your PR description adds that the cost is "per replica, per in-flight request, on the one process that fronts the whole fleet."

## 4. The idea of the fix (one sentence)

> **Hand the body over as a lazy stream, not a finished blob.** The server attaches a generator that reads the socket on demand, endpoints drain it when they need bytes, and the gateway pipes it straight into the upstream socket.

This is the right seam because only the consumer knows whether it needs the whole body. Endpoints, form parsing and passthrough need it. A pure proxy does not. Putting `load_body()` at the top of `_route_and_call` keeps every existing endpoint unchanged.

**What:** At header time the server only works out the body length. It rejects a malformed length (400) and a declared length over the cap (413), exactly as before. It then attaches a generator instead of the bytes. The generator reads 64 KiB blocks for a declared length, or one chunk at a time for chunked bodies. It checks the running total against the cap, puts `body_timeout` (default 30 s) on every read, and clears `request.stream` when it finishes cleanly.

**Why:** This removes copy #1. No byte of the body is read until someone asks for it.

**Things to notice:**
- A chunked body has length `-1`, so the upfront `declared > max_body_bytes` check never fires for it. The cap is enforced inside the generator. This is @MusabMahmoodh's point 1 (see §9).
- A short body (fewer bytes than `Content-Length`) is now a **400**, not an escaping `IncompleteReadError`. This came from commit `58116ad`.
- A stall or hang-up mid-body becomes `ClientDisconnected`. The connection handler now swallows it, so nothing is logged.
- When chunked is present, `Content-Length` is removed from the headers, so a stale length never reaches handlers. @MusabMahmoodh says #8981 now *rejects* requests that carry both headers, so this branch and its test should be dropped on rebase.
- A single chunked frame can still be as large as the client declares (up to the cap). `readexactly(size)` reads it whole. Only declared-length bodies are cut into 64 KiB blocks.
- Errors raised inside the generator (413, 400) now leave as `HTTPError` through `ServingApp.dispatch`. The old reader wrote them directly with `_bare_error`. So a mid-stream 413 or 400 is now a JSON response (`{"detail": ...}`), and middleware runs before it. The diff does not show what `_bare_error` writes, so how much the body format changed can't be told from it.
- Keep-alive is refused while a stream is unread or failed. Otherwise leftover body bytes would be parsed as the next request.

### 5.2 `jac/jaclang/server/serving/datatypes.jac`: `Request` learns to carry a stream

```diff

+    async def load_body -> bytes {
```

**What:** `load_body()` drains the stream once and caches the bytes in `body`. `body_source()` gives the live stream, or the bytes if already read. `body_unread()` is the keep-alive guard. `json()` now loads the body first.

**Why:** Each consumer picks buffered or streamed access. Once a read fails, it stays failed.

**Things to notice:**
- `load_body()` is idempotent: a second call returns the cached bytes.
- After a failure, every later `load_body()` or `body_source()` raises **400**, even if the first error was 413. This stops a half-read body being handed on as an empty one. Commits `b39615e` and `96a91e8` added this.
- Only `json()` was updated here. The diff does not show whether other accessors (form, multipart) exist on `Request` and read `body` directly. They are protected anyway because `_route_and_call` loads the body first (§5.3).

**What:** `arequest` now owns the framing headers. A caller's `Content-Length` is kept only as the declared length for a stream. A caller's `Transfer-Encoding` is always dropped. With a stream and no length, it sends chunked. It writes the stream with a `drain()` after each chunk and checks that the bytes sent match the declared length. It also skips interim 1xx responses.

**Why:** This removes copy #2. With a stream, nothing is concatenated. With per-chunk `drain()`, the gateway holds about one chunk at a time.

**Things to notice:**
- Errors raised by the source stream (an `HTTPError` 413/400, or `ClientDisconnected`) pass through `arequest` unchanged after the socket is closed. This is how a truncated client upload becomes a 400 and not a 502 (point 2 in §9).
- For a bytes body, a caller-supplied `Content-Length` is now dropped and recomputed. Before, the client sent its own `Content-Length` plus the caller's.
- The 1xx loop is needed because forwarding `Expect: 100-continue` makes the upstream send `100 Continue` first. The old code would have returned that as the final status. It is covered by a test but not mentioned in the PR description.
- Whether `stream_forward` catches `ClientRequestSent` (the length-mismatch case) and turns it into a 502 depends on the exception hierarchy, which the diff does not show.

## 6. How execution flows after the PR

### 6.1 A request with a body arrives

```text
ServingServer connection loop
├─ parse request line + headers
├─ (Expect: 100-continue → write "100 Continue")
├─ _declared_body_length(headers)                         ← NEW
│   ├─ None (bad / negative Content-Length) → bare 400, stop
│   ├─ -1 (chunked) → remove Content-Length header         ← NEW
│   └─ declared > max_body_bytes → bare 413, stop (body never read)
├─ build Request (no body bytes)                           ← CHANGED
├─ declared != 0 → request.stream = _stream_request_body(...)   ← NEW
├─ ServingApp.dispatch → middleware → … (see 6.2 / 6.3)
└─ _should_keep_alive: body_unread() → close connection    ← NEW
```

### 6.2 A normal endpoint

```text
middleware (sees request.stream, request.body == b'')
└─ _route_and_call
    ├─ await request.load_body()                            ← NEW
    │   ├─ drains generator → request.body = bytes; stream = None
    │   ├─ chunked total > cap → HTTPError 413 → dispatch → JSON 413; _body_failed
    │   ├─ short body → HTTPError 400
    │   └─ stall/hang-up → ClientDisconnected → re-raised → connection closed silently
    ├─ router.resolve(...)
    └─ endpoint sees request.body as before
```

### 6.3 Gateway `forward_to`

```text
forward_to(request, entry, url)
├─ build_forward_headers(request)
├─ X-Forwarded-For = "unknown"                                ← REGRESSION (re-added lines)
├─ body = request.body_source()  → the live stream            ← CHANGED
└─ stream_forward → arequest(data=stream)
    ├─ Content-Length known → send it; else Transfer-Encoding: chunked   ← NEW
    ├─ write headers, then _pump_body: chunk → write → drain  ← NEW
    │   ├─ client stream raises 413/400 → close upstream socket, re-raise → dispatch → 413/400 to client
    │   └─ sent != declared → ClientRequestSent
    ├─ _read_response_head skips 1xx                          ← NEW
    └─ generator end sets request.stream = None → keep-alive allowed
```

### 6.4 Builtin passthrough

```text
handle_builtin_passthrough
├─ body = await request.load_body()   (bytes kept)             ← CHANGED (explicit)
└─ for svc in candidates: forward body; 404/405 → next        (unchanged replay, #7901)
```

### 6.5 Embedded gateway

```text
EmbeddedGateway.dispatch
├─ body = await request.load_body()   (errors propagate)      ← CHANGED
├─ json.loads → payload (parse failure → {})
└─ _call_member(service, remainder, payload)
```

| Scenario | Before | After |
|---|---|---|
| 90 MiB declared upload via `forward_to` | +186.7 MiB peak RSS | +0.0 MiB |
| Declared `Content-Length` > cap | 413, body never read | Same |
| Chunked body over cap, normal endpoint | Bare 413 from server | 413 via `dispatch` (JSON), connection closed |
| Chunked body over cap, gateway `forward_to` | 413, upstream never contacted | Up to the cap forwarded, upstream sees an unterminated body (400 there), client gets 413 |
| Client sends fewer bytes than `Content-Length` | `IncompleteReadError` swallowed, connection dropped | 400 Bad Request |
| Client stalls mid-body | No timeout on `readexactly` | `ClientDisconnected` after `body_timeout` (30 s), closed silently |
| Middleware answers early on a bodied request | Body already read, keep-alive OK | Connection closed |
| Chunked + `Content-Length` together | Chunked used, header passed on | Chunked used, header removed (conflicts with #8981) |
| Upstream answers `100 Continue` first | 100 treated as final status | Skipped, real status returned |
| Endpoint raises `ConnectionRefusedError` | 500 | 500 (unchanged; test pins it) |

**Changes users will notice:** the partial-forward trade for over-cap chunked uploads (in the release note), 400s for truncated bodies, the body timeout, and connections closed after middleware short-circuits a bodied request.

## 11. Questions your senior might ask

**Q: Where do the two 90 MiB copies come from?**
One is `Request.body` from `readexactly`. The other is `blob + body` in `arequest`. With a stream, neither exists: `_pump_body` writes and drains one chunk at a time.

**Q: Why does peak RSS start at 262.5 MiB after the fix but 208.2 MiB before?**
The PR doesn't explain the different baseline. What it shows is the delta: +186.7 → +0.0. Re-measure after the rebase and be ready to explain or note it.

**Q: Doesn't `load_body()` in `_route_and_call` just bring the buffering back?**
Only for real endpoints that need the bytes. The gateway handles proxied requests before routing; the middleware test shows the stream is still unread there. The diff doesn't show the gateway's wiring in detail.

**Q: Is memory really bounded for chunked uploads?**
Mostly. Declared-length bodies are read in 64 KiB blocks. A chunked frame is read whole, so a client that sends one huge frame can still make the gateway hold up to `max_body_bytes` (100 MiB) at once.

**Q: What does the upstream service see when a chunked upload goes over the cap?**
A truncated chunked body with no terminating `0\r\n\r\n`. It answers 400, and the client gets a 413 from the gateway. A service that streams to disk must clean up, the same as for any client that disconnects mid-upload. The release note records this.

**Q: Why close the connection when the body wasn't read?**
The unread bytes are still on the socket. Reusing it would parse them as the next request, which desyncs framing. Bodiless requests never get a stream, so normal keep-alive is unaffected.

**Q: What happens if a client stalls halfway?**
Each read has `body_timeout` (default 30 s). On timeout it raises `ClientDisconnected`, which `dispatch` re-raises and the connection handler swallows. You get no 500 and no log entry; there's a test for this.

**Q: Why does passthrough still buffer?**
It replays the same body to each candidate until one stops returning 404/405, and a stream can be read only once. #7901 should change that; a test pins the current replay.

**Q: How does this interact with #8119's retries?**
In the rebased code it can be wrong: a stream is consumed by the first attempt, so a retry would send a truncated body. Per @MusabMahmoodh, `replayable` must exclude stream bodies.

**Q: Is the issue's "configurable gateway-level max" implemented?**
No. The cap is the serving core's existing `max_body_bytes`: enforced upfront for declared lengths and inside the stream for chunked bodies. There is no gateway-specific setting.
