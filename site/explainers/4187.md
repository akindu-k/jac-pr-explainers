## 1. The short version

jac-scale turns a Jac app into a web API server. Users register (`POST /user/register`) and log in (`POST /user/login`). Each call returns a **JWT**, a signed token that proves who the user is.

**Before this PR, a user had no way to change their username or password once the account existed.** The server had register and login routes but nothing for updating an account.

**You added two authenticated routes, `PUT /user/username` and `PUT /user/password`.** Each one checks the Bearer token and rejects requests where the token's user differs from the user named in the body. It then calls the existing user manager to do the update. A username change also returns a fresh JWT for the new name, and the user's graph root (`root_id`) stays the same. You added 11 end-to-end tests that cover success, missing token (401), acting on another user (403), duplicate or empty values (400) and a combined rename-then-change-password flow.

**Status:** Closed. There are no reviews or comments, and the description is empty. All 6 CI checks passed on head commit `408c707`. Nothing in the data shows the PR was merged.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | A language that compiles to and mixes with Python. It uses `obj`, `class`, `has` fields and `impl` blocks. |
| jac-scale | A plugin that serves Jac apps as an HTTP API and deploys them to Kubernetes. |
| `serve.jac` / `serve.impl.jac` | Jac splits declarations from bodies. `serve.jac` declares methods (`def update_username(...) -> TransportResponse;`). `impl/serve.impl.jac` holds the bodies (`impl JacAPIServer.update_username(...) { ... }`). |
| `JacAPIServer` | The jac-scale server class. It extends `JServer` and registers every HTTP route in `start()`. **This is what the PR adds to.** |
| FastAPI | The Python web framework under the server. `self.server.app` is the FastAPI app. |
| Endpoint / route | A URL plus an HTTP method that the server answers, e.g. `PUT /user/username`. |
| `PUT` | The HTTP method usually used to replace or update a resource. |
| JWT | A signed token string that holds the username. `create_jwt_token(name)` makes one. `validate_jwt_token(token)` returns the username, or a falsy value if the token is invalid or expired. |
| Bearer token | How the JWT is sent: an HTTP header `Authorization: Bearer <jwt>`. |
| `HTTPBearer(auto_error=False)` | A FastAPI helper that reads the Bearer header. With `auto_error=False` it returns `None` instead of failing on its own, so your code decides the error. |
| `Depends(...)` | FastAPI dependency injection. It runs `security` before your handler and passes the result in as `credentials`. |
| Pydantic `BaseModel` / `Field(...)` | Request-body schemas. `Field(...)` means "required". A missing field makes FastAPI reply 422 before your code runs. |
| `UpdateUsernameRequest` / `UpdatePasswordRequest` | The two new body models: `{current_username, new_username}` and `{username, current_password, new_password}`. |
| `TransportResponse` | jaclang's internal result type, built with `.success(data=...)` or `.fail(code=..., message=...)`. `Meta(extra={'http_status': 401})` carries the intended HTTP status. |
| `_transport_response_to_json_response` | A helper that turns a `TransportResponse` into a FastAPI `JSONResponse` with the right status code. It is **not in the diff**, so it must already exist in the file. |
| `user_manager` | The object that stores users. The PR calls its `update_username(old, new)` and `update_password(user, cur, new)`. Neither method is in the diff; they must already exist (CI passing suggests they do). They return a dict that holds `'error'` on failure. |
| `root_id` | The id of the user's root node in the Jac graph, where their data hangs. The tests check it does not change on rename. |
| OpenAPI schema | The auto-generated API description behind `/docs`. Marking a route with `BearerAuth` security makes the docs UI show a lock and send the token. |
| 401 / 403 / 400 / 422 | 401 means not logged in or bad token. 403 means logged in but not allowed. 400 means a bad value. 422 means the body does not match the schema. |

## 3. The problem, step by step

### 3.1 The setup
- `JacAPIServer.start()` registers routes: login, register, SSO, static files, walkers and functions.
- `user_manager` stores username/password records and links each user to a graph `root_id`.
- Clients authenticate with the JWT they got from register or login.

### 3.2 What was missing
```text
1. Alice registers:  POST /user/register {username:"alice", password:"p1"}
   -> token(alice), root_id=R1
2. Alice wants to rename to "alice2" or change password to "p2"
3. She looks for a route: none exists for username or password          <-- MISSING
4. Her only options: keep the old values, or register a new account
   -> new account = new root_id R2, so her graph data under R1 is not reachable
```
The PR shows no admin or workaround path, and I can't tell from the diff whether one existed elsewhere.

### 3.3 Why it mattered
No issue is linked and the description is empty, so the PR does not state a user report or a motivation. From the code, the gap is basic account management: users can't rotate a leaked password or fix a username without losing their data.

## 4. The idea of the fix (one sentence)

> **Add two token-protected update routes that only let users change their own account.** Each route checks the JWT, compares its username to the one in the body, validates the inputs, and hands the change to the existing `user_manager`.

This reuses the existing pieces: JWT helpers, `user_manager`, `TransportResponse` and the JSON converter. The new code is mostly glue and auth checks, and the storage logic stays in one place.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/serve.jac`: declare the new methods and request models

```diff
+import from pydantic { BaseModel, Field }
 ...
+    def update_username(self, current_username: str, new_username: str,
+        Authorization: (str | None) = None) -> TransportResponse;
+    def update_password(self, username: str, current_password: str,
+        new_password: str, Authorization: (str | None) = None) -> TransportResponse;
+    def register_update_username_endpoint(self: JacAPIServer) -> None;
+    def register_update_password_endpoint(self: JacAPIServer) -> None;
 ...
+class UpdateUsernameRequest(BaseModel) {
+    has current_username: str = Field(..., description='Current username'),
+        new_username: str = Field(..., description='New username');
+}
+
+class UpdatePasswordRequest(BaseModel) {
+    has username: str = Field(..., description='Username'),
+        current_password: str = Field(..., description='Current password'),
+        new_password: str = Field(..., description='New password');
+}
```

**What:** The file declares four new methods on `JacAPIServer` and two Pydantic body models.

**Why:** Jac needs declarations here for the `impl` blocks in 5.2. The models give FastAPI a typed JSON body and a schema for `/docs`.

**Things to notice:**
- These are `class` (Python-style) rather than `obj`, because they subclass Pydantic's `BaseModel`.
- `Field(...)` makes every field required. A missing key gets FastAPI's 422, not your 400. An empty string `""` passes the schema and reaches your own 400 check.
- The parameter is named `Authorization` with a capital A. This mirrors the header name, but it is passed in by the wrapper, not read directly from the header.

### 5.2 `jac-scale/jac_scale/impl/serve.impl.jac`: logic, routes and OpenAPI security

**a) Register the routes at start-up**

```diff
+    self.register_update_username_endpoint();

     if watch {
```
**What:** Both routes are added in normal mode and in `--watch` mode.

**Why:** They must be registered before the app serves requests.

**b) Mark the routes as Bearer-protected in OpenAPI**
```diff
+            } elif path in ['/user/username', '/user/password'] {
+                for method in path_item {
+                    if (method in ['put', 'patch']) {
+                        path_item[method]['security'] = [{'BearerAuth': []}];
```

**What:** The `/docs` UI now shows these routes as needing a token.

**Things to notice:** `patch` is listed, but only `put` routes are registered. The `patch` entry has no effect today.

**c) `update_username`: the business logic**
```diff
+    if (Authorization and isinstance(Authorization, str)
+        and Authorization.startswith('Bearer ')) {
+        token = Authorization[7:];                       # strip "Bearer "
+    }
+    token_username = self.validate_jwt_token(token) if token else None;
+    if not token_username { ... fail UNAUTHORIZED, 401 }
+    if (token_username != current_username) { ... fail FORBIDDEN, 403 }
+    if (not new_username) { ... fail VALIDATION_ERROR, 400 }
+    result = self.user_manager.update_username(current_username, new_username);
+    if ('error' in result) { ... fail UPDATE_FAILED, 400 }
+    result['token'] = self.create_jwt_token(new_username);   # NEW token for new name
+    return TransportResponse.success(data=result, meta=Meta(extra={'http_status': 200}));
```
**What:** The method runs four guards in a fixed order: token valid, same user, non-empty value, storage succeeded. On success it returns the user manager's result plus a new JWT.

**Why:** The old token carries the old username. After a rename, that token would fail the same-user check on later calls, so the client needs a new one. The integration test uses this new token to change the password.

**Things to notice:**
- Duplicate usernames are rejected by `user_manager` (the error comes back as 400). This method does no duplicate check of its own.
- The old token is not revoked. The diff does not show whether `validate_jwt_token` checks that the user still exists. If it doesn't, the old token stays valid until it expires, and it would match anyone who later registers the old name. Confirm this before re-proposing.
- Renaming to the same name is not handled here. What happens depends on `user_manager`.

**d) `update_password`: the business logic**
```diff
+    if (token_username != username) { ... FORBIDDEN 403 }
+    if (not current_password or not new_password) { ... VALIDATION_ERROR 400 }
+    result = self.user_manager.update_password(username, current_password, new_password);
+    if ('error' in result) { ... UPDATE_FAILED 400 }
+    return TransportResponse.success(data=result, ...);
```
**What:** It uses the same guard pattern. It requires the current password, and `user_manager` checks that password.

**Things to notice:**
- A wrong current password returns **400 `UPDATE_FAILED`**, not 401. The test expects 400.
- There is no password-strength rule, only a non-empty check.
- Existing tokens stay valid after a password change, and no new token is issued.
- The first ~20 lines (token parsing, 401, 403) are copied from `update_username`. A shared helper would remove the duplication.

**e) `register_update_username_endpoint` / `register_update_password_endpoint`: the HTTP glue**
```diff
+    security = HTTPBearer(auto_error=False);
+    def wrapper_callback(
+        body: UpdateUsernameRequest,
+        credentials: HTTPAuthorizationCredentials | None = Depends(security)
+    ) -> JSONResponse {
+        if not credentials {
+            raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED, detail="Not authenticated");
+        }
+        token = credentials.credentials if credentials else None;
+        authorization = f'Bearer {token}' if token else None;
+        transport_response = self.update_username(body.current_username, body.new_username, authorization);
+        return _transport_response_to_json_response(transport_response);
+    }
+    self.server.app.put('/user/username', response_model=None, tags=['User APIs'],
+        summary='Update username', description='...Requires authentication.')(wrapper_callback);
```
**What:** Each function builds a FastAPI handler. The handler reads the body and the Bearer header, returns 401 if the header is missing, rebuilds a `Bearer <token>` string, calls the logic method, and converts the result to JSON with the right status.

**Why:** Commit `8b898f2` switched the return from `TransportResponse` to `JSONResponse`. Without that conversion, the 401/403/400 in `Meta` would not become real HTTP status codes.

**Things to notice:**
- `auto_error=False` plus a manual 401 makes "no header" always return 401. Some FastAPI versions return 403 from `HTTPBearer` by default. The diff doesn't show which version the project uses, so treat that as the likely reason, not a confirmed one.
- `if credentials else None` after the guard is dead code, because `credentials` is always set at that point.
- The header is parsed by `HTTPBearer`, turned back into `"Bearer ..."`, and parsed again inside `update_*`. It works, but the logic methods could take the token directly.
- These routes use `self.server.app.put(...)` directly. Login uses `self.server.add_endpoint(JEndPoint(...))`. A reviewer may ask why the PR uses a different mechanism.
- No release notes or docs changed.

## 6. How execution flows after the PR

### 6.1 Server start
```text
JacAPIServer.start(watch)
├─ register login / register / SSO / client JS / static endpoints
├─ register_update_username_endpoint()      ← NEW  (PUT /user/username)
├─ register_update_password_endpoint()      ← NEW  (PUT /user/password)
├─ register walker/function endpoints (dynamic if watch, else static)
└─ _configure_openapi_security()
   └─ add BearerAuth to put/patch on /user/username, /user/password   ← NEW
```

### 6.2 `PUT /user/username`
```text
Client: PUT /user/username  {current_username, new_username}  [Authorization: Bearer T]
├─ FastAPI validates body against UpdateUsernameRequest      ← NEW
│  └─ missing field → 422
├─ HTTPBearer reads header → credentials or None
│  └─ None → HTTPException 401 "Not authenticated"           ← NEW
├─ update_username(cur, new, "Bearer T")                     ← NEW
│  ├─ validate_jwt_token(T) falsy → 401 UNAUTHORIZED
│  ├─ token user ≠ current_username → 403 FORBIDDEN
│  ├─ new_username empty → 400 VALIDATION_ERROR
│  ├─ user_manager.update_username(...) has 'error' → 400 UPDATE_FAILED
│  └─ result + token=create_jwt_token(new) → 200
└─ _transport_response_to_json_response → JSONResponse with status
```

### 6.3 `PUT /user/password`
```text
Client: PUT /user/password  {username, current_password, new_password}  [Bearer T]
├─ body validated against UpdatePasswordRequest (422 if missing)   ← NEW
├─ no header → 401                                                  ← NEW
├─ update_password(...)                                             ← NEW
│  ├─ bad token → 401
│  ├─ token user ≠ username → 403
│  ├─ either password empty → 400
│  ├─ user_manager.update_password → error (e.g. wrong current pw) → 400
│  └─ success → 200 (no new token)
└─ converted to JSONResponse
```

## 11. Questions your senior might ask

**Q: Where is the user data actually changed?**
In `user_manager.update_username` and `user_manager.update_password`. This PR only calls them. They are not in the diff, so they existed already.

**Q: Why return a new token after a username change?**
The old JWT holds the old name. Later calls compare the token's username to the body's username, so the old token would get 403. The integration test uses the new token to change the password.

**Q: Does the old token stop working?**
Not explicitly. Nothing revokes it. Whether it still validates depends on `validate_jwt_token`, which this diff doesn't show.

**Q: Why `HTTPBearer(auto_error=False)` and a manual 401?**
So that a missing header always returns 401 with "Not authenticated". With `auto_error=True`, some FastAPI versions return 403 instead.

**Q: Why does the user send their username in the body if the token has it?**
The design compares the two and returns 403 on a mismatch. You could drop the field and use the token's username. That would be simpler and remove a whole error case.

**Q: What does a wrong current password return?**
400 `UPDATE_FAILED`, carrying the error message from `user_manager`. `test_update_password_wrong_current_password` checks this.

**Q: Does renaming lose the user's graph data?**
No. `root_id` stays the same. Both `test_update_username_success` and the integration test check this.

**Q: What happens if a body field is missing?**
FastAPI rejects the request with 422 before your code runs, because every field uses `Field(...)`. An empty string passes the schema and gets your 400.

**Q: Why register with `self.server.app.put` instead of `add_endpoint`?**
The PR doesn't say. A likely reason is that direct FastAPI registration made it easy to use `Depends(HTTPBearer)` and a Pydantic body, but it is not the pattern login uses.
