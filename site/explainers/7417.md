## 1. The short version

jac-scale signs a JWT (a signed login token) for each user session. Other services read that token to learn who the user is. RFC 7519 and OIDC put the user's identifier in a claim named `sub`. **Before this PR, jac-scale session tokens put the user's UUID only in a custom `user_id` claim and had no `sub`, so standard tools (API gateways, mobile auth SDKs, OIDC relying parties) could not find the user's identity.**

**You now emit `sub` (same value as `user_id`) and `preferred_username` in every new session token. You keep `user_id` for backwards compatibility. Validation and refresh now accept either `sub` or `user_id`.** Old tokens that carry only `user_id` still validate and refresh.

Your first commit created a hole. The bot reviewer @greptile-apps flagged it: API-key tokens already carry `sub`, so the refresh endpoint would now turn an API-key token into a normal session token. Your second commit (`0a9f27d`) makes refresh reject tokens with `type: 'api_key'`. A test checks that the endpoint answers `401` for them.

**Status:** Merged on 2026-07-14. All CI checks that ran passed. The only review was from the Greptile bot (confidence 5/5). The input shows no human review.

## 3. The problem, step by step

### 3.1 The setup

- **Login** calls `create_jwt_token(user_id)`. Before the PR, the payload was `{user_id, exp, iat, [role]}`.
- **Every request** with a session token goes through `validate_jwt_token_detail`. It rejects API-key tokens, then reads `user_id`.
- **Refresh** goes through `refresh_jwt_token`. It decodes the token, reads `user_id`, and mints a new token.
- **API-key tokens** are signed with the same secret and algorithm. They use `sub` and `type: 'api_key'`, not `user_id`.
- **Outside consumers** (gateways, SDKs, SIEM tools) read `sub`.

### 3.2 What went wrong: missing standard claims

```text
1. User logs in                       → create_jwt_token("3f2a…uuid")
2. Payload signed                     → {"user_id": "3f2a…", "exp": …, "iat": …}
3. Token sent to an API gateway       → gateway looks for "sub"
4. "sub" not present                  ← WRONG: identity is in a non-standard field
5. Gateway rejects or misroutes; mobile SDK reads identity as empty
```

### 3.3 The case your first commit introduced: API key becomes a session

This happened between your two commits. It never reached `main`.

```text
1. Client holds an API-key token      → {"type": "api_key", "sub": "3f2a…", "exp": …}
2. Client POSTs it to /user/refresh-token
3. refresh_jwt_token decodes it (same secret → signature valid)
4. Before PR:  decoded.get('user_id') → None → returns None (safe)
5. After e189492: decoded.get('sub') or decoded.get('user_id') → "3f2a…"
6. create_jwt_token("3f2a…")          ← WRONG: a full user session is minted from an API key
7. Fixed in 0a9f27d: type == 'api_key' → return None → endpoint returns 401
```

`validate_jwt_token_detail` already had this `api_key` check. `refresh_jwt_token` did not. The hole appeared only because `sub` became an accepted source of the user ID.

### 3.4 Why it mattered

Issue #6068 lists the consumers that break when `sub` is missing:
- API gateways (Kong, AWS API Gateway, nginx-lua) reject the token or route it wrongly.
- Mobile SDKs (AppAuth, MSAL) read the identity as empty.
- Third-party auth middleware cannot extract the user.
- Audit and SIEM tools cannot match events to a user.
- OIDC relying parties see a spec violation.

The issue says the UUID is the right value; it was just in the wrong field. The issue also notes that the API-key path already used `sub`, so the two token types were inconsistent.

## 4. The idea of the fix (one sentence)

> **Write the subject to both `sub` and `user_id`, and read it from either one.** New tokens follow the standard, and old tokens and old consumers keep working during one release cycle.

Writing both fields serves old and new consumers at the same time. Reading both lets tokens issued before the deploy keep working until they expire. That makes it a safe rename with a clean later step: drop `user_id`.

## 6. How execution flows after the PR

### 6.1 Login / creating a session token

```text
create_jwt_token(user_id)
├─ build payload {sub, user_id, exp, iat}         ← CHANGED (sub added)
├─ get_username(user_id)                          ← NEW
│   └─ if non-empty → payload.preferred_username  ← NEW
├─ if include_role → add role
└─ sign and return token
```

### 6.2 Validating a request token

```text
validate_jwt_token_detail(token)
├─ decode and verify signature/expiry
├─ type == 'api_key' → invalid ("API key tokens are not valid user sessions")
├─ user_id = sub or user_id                       ← CHANGED
│   └─ missing → invalid ("Token has no subject")  ← CHANGED message
├─ check_existence → user must exist
└─ valid
```

### 6.3 Refreshing a token

```text
POST /user/refresh-token → refresh_jwt_token(token)
├─ decode and verify (exp checked)
│   └─ exception → log debug, return None
├─ type == 'api_key' → return None                ← NEW
├─ user_id = sub or user_id                       ← CHANGED
├─ user_id present → create_jwt_token(user_id)    (now includes sub, preferred_username)
└─ else → None   (endpoint returns 401, per test)
```

| Scenario | Before | After |
|---|---|---|
| New login token payload | `user_id`, `exp`, `iat` | `sub`, `user_id`, `preferred_username` (if available), `exp`, `iat` |
| Validate a legacy `user_id`-only token | Valid | Valid |
| Validate a token with only `sub` | Invalid ("Token has no user_id") | Valid |
| Refresh a legacy token | New token without `sub` | New token with `sub` |
| Refresh an API-key token | `None` (no `user_id`) → 401 | `None` (explicit check) → 401 |
| Validate an API-key token | Rejected | Rejected (unchanged) |
| Token with no subject at all | Reason "Token has no user_id" | Reason "Token has no subject" |

Behaviour changes users will notice:
- Tokens are slightly larger and carry new claims.
- The error reason text changed.
- A token with only `sub` (not signed as an API key) is now accepted as a session.

## 11. Questions your senior might ask

**Q: Why keep `user_id` at all?**
Existing consumers read it. Dropping it immediately would break them. Both the issue and the PR plan to remove it after one release cycle.

**Q: Was the API-key-to-session hole ever on `main`?**
No. It existed only in your first commit, `e189492`. Your second commit, `0a9f27d`, fixed it before merge. Before the PR, refresh read only `user_id`, which API-key tokens don't have, so it returned `None`.

**Q: Why does validation not need the same new check?**
`validate_jwt_token_detail` already rejected `type == 'api_key'` before reading the subject. You copied that pattern into refresh.

**Q: What if `sub` and `user_id` disagree in a token?**
`sub` wins because of `sub or user_id`. Tokens you mint always have equal values. A mismatch would need a token signed with the server secret by someone else.

**Q: What does `preferred_username` contain, and what if there is none?**
It contains whatever `get_username(user_id)` returns. The test shows it equals the registered username. If the result is empty, the claim is left out. The method body is not in this diff.

**Q: Does this add cost to login?**
Yes: one extra `get_username` call per token creation. Its cost is not visible in this diff.

**Q: Did any user-visible message change?**
Yes. The invalid reason changed from `'Token has no user_id'` to `'Token has no subject'`.

**Q: Why not add `email` as the issue suggested?**
The PR does not explain. Only `sub` and `preferred_username` were added.

**Q: Can a token with only `sub` now act as a session?**
Yes, if it is signed with the server secret and is not marked `type: 'api_key'`. That matches the standard. It is safe only as long as every other token type that uses `sub` is marked by `type`.

**Q: How do we know old tokens still work?**
The test hand-signs a `user_id`-only token and refreshes it. It gets `200` and a new token with `sub`. Validating legacy tokens is covered only by the code path, not by a test.
