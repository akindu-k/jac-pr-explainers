## 1. The short version

jac-scale can store the Jac graph (nodes and edges) in MongoDB. When a node gains or loses edges, the method `MongoBackend._put_node_atomic` writes the change. It uses a special MongoDB update form, the "aggregation pipeline". That form lets it merge the edge list atomically, meaning in one indivisible step.

**MongoDB rejects that update form whenever the payload contains an empty object `{}`. Every node's default access data contains one at `access.roots.anchors = {}`, so every write through `_put_node_atomic` failed with error 40180.** The code caught the error and only logged it:

```
ERROR - MongoDB _put_node_atomic failed: Invalid $set :: caused by :: an empty object is not a valid value.
Found empty object at path data.access.roots.anchors
```

The data still looked correct on the pod that made the change, because it sat in that pod's in-memory cache. It was missing after a restart and on other pods.

**You added a recursive helper, `_strip_empty_dicts`, and applied it to the non-archetype, non-edge fields (`non_arch_top`) before they go into the pipeline `$set`.** The update still uses the aggregation pipeline, so the edge merge stays atomic. You also added two integration tests that run against a real MongoDB container, plus a release note.

**Status:** Merged on 2026-05-25. @MichaelAshley2000 approved it with no comments. All test checks passed. @kugesan1105 left a non-blocking follow-up: `partial_data` is not stripped. You tracked that as #6167.

## 3. The problem, step by step

### 3.1 The setup

- A walker runs `root ++> SomeNode()`. Root gains an edge.
- On sync, a node that is already stored and has an edge change goes through `_put_node_atomic`. The test comments describe this flow: first `_write_to_db`, then `_put_node_atomic` for edge deltas.
- `_put_node_atomic` builds `set_doc` from three sources:
  1. an edge-merge expression for `data.edges`
  2. `partial_data` (the dirty archetype fields)
  3. `non_arch_top` (things like `access`)
- It then calls `collection.update_one({'_id': _id}, [{'$set': set_doc}], upsert=True)`. This call is quoted in the issue. It is outside the diff.

### 3.2 What went wrong

```text
1. Walker runs root ++> SomeNode()          root.edges += [edge-id]  (in L1 cache)
2. Sync calls _put_node_atomic(root, [edge-id], [])
3. full = Serializer.serialize(root)        full["access"] = {"all": -1, "roots": {"anchors": {}}}
4. non_arch_top = {"access": {...anchors: {}}}       (copied as-is)
5. set_doc["data.access"] = {..."anchors": {}}       set_doc also has data.edges = $setUnion(...)
6. update_one(_id, [{'$set': set_doc}], upsert=True)
7. MongoDB: error 40180 at data.access.roots.anchors       ← WRONG: whole update rejected
8. Exception caught, "MongoDB _put_node_atomic failed" logged; request still returns 200
9. Mongo document unchanged: edge-id NOT in data.edges
10. Same pod reads root from L1                              → edge present (looks fine)
11. Pod restart or other pod reads from Mongo                → edge missing
```

Brand-new nodes still got a document from `_write_to_db`, because regular `$set` accepts `{}`. That partly hid the failure, as your live-verification comment notes.

### 3.3 Why it mattered

- Edge changes on stored nodes were lost from MongoDB. The issue's wording is broader: "No graph mutations persist."
- In multi-pod setups, other pods could not see the new nodes or edges.
- The issue calls out old user accounts in particular. Their existing `UserProfile` node needs edge updates (new Projects), and those updates kept failing.
- The only workaround was a manual `$unset` of `data.access.roots.anchors`. It had to be run again after every write.

## 4. The idea of the fix (one sentence)

> **Strip empty dicts before they reach the pipeline `$set`.** Remove every empty-dict leaf from the non-archetype fields so MongoDB accepts the atomic update, while the edge merge keeps using the pipeline.

The other option was a regular `$set` (the issue's Option C). That would lose the server-side `$setUnion`/`$setDifference` edge merge, which is the reason `_put_node_atomic` exists. Stripping is safe only because, per the PR, the Serializer restores `default_factory=dict` fields to `{}` on load. That Serializer behaviour is outside the diff.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/impl/memory_hierarchy.mongo.impl.jac`: new helper `_strip_empty_dicts`

```diff
+def _strip_empty_dicts(v: object) -> object {
+    if isinstance(v, dict) {
+        cleaned = {k: _strip_empty_dicts(vv) for (k, vv) in v.items()};   # recurse first
+        return {
+            k: vv
+            for (k, vv) in cleaned.items()
+            if not (isinstance(vv, dict) and not vv)                       # drop {} children
+        };
+    }
+    if isinstance(v, list) {
+        return [_strip_empty_dicts(item) for item in v];                   # clean inside lists
+    }
+    return v;                                                              # scalars unchanged
+}
```

**What:** The helper cleans children before checking them. A parent that becomes empty after cleaning is therefore removed too:
- `{"all": -1, "roots": {"anchors": {}}}` becomes `{"all": -1}`
- `{"roots": {"anchors": {"uuid-1": 2}}}` stays unchanged

**Why:** It removes exactly the kind of value MongoDB rejects (error 40180).

**Things to notice:**
- **The top-level value is never removed.** `_strip_empty_dicts({})` returns `{}`. If a whole `non_arch_top` value were `{}`, `set_doc["data.k"] = {}` would still be sent. For `access` this cannot happen, because `all` is always present.
- **Lists are cleaned inside but their items are never dropped.** `[{}]` stays `[{}]`, and `[{"a": {}}]` becomes `[{}]`. Lists are not edited, so their length and positions are kept. Whether MongoDB rejects `{}` inside an array in a pipeline `$set` cannot be told from the PR.
- **It strips any empty dict, not just `anchors`.** That is only lossless if every such field's default is `{}`.
- It is a module-level function with a docstring explaining the reason.

### 5.2 `jac-scale/jac_scale/impl/memory_hierarchy.mongo.impl.jac`: apply it in `_put_node_atomic`

```diff
         partial_data = Serializer.serialize_fields(anchor, dirty) if dirty else {};   # NOT stripped
 
         # Non-archetype, non-edge top-level data fields (e.g. access control).
+        # Strip empty nested dicts before including in the aggregation-pipeline
+        # $set: MongoDB rejects empty embedded documents (error 40180) ...
         full = dict(Serializer.serialize(anchor, include_type=True));
         non_arch_top = {
-            k: v
+            k: _strip_empty_dicts(v)                    # NEW
             for (k, v) in full.items()
             if k not in ('edges', 'archetype')
         };
```

**What:** Each non-archetype, non-edge field is cleaned before it is copied into `set_doc` as `data.<k>`.

**Why:** `access` lives here, and `access.roots.anchors = {}` was the trigger.

**Things to notice:**
- **`partial_data` (archetype fields) is not stripped.** Both sources land in the same `set_doc`. An archetype field such as `has settings: dict = {}` that is dirty would still cause error 40180. @kugesan1105 raised this, and #6167 tracks it.
- Other write paths (`_write_to_db`, `put_partial`) are unchanged on purpose. They use regular `$set`. As a result, `anchors: {}` still appears in documents written by `_write_to_db`, as your verification comment says.
- **Because `$set` replaces the whole `data.access` value, a stored `{"roots": {"anchors": {}}}` becomes `{"all": -1}` after this write.** Nothing else changes in the stored shape.

## 6. How execution flows after the PR

### 6.1 Writing an edge change on a stored node

```text
walker: root ++> SomeNode()
└─ sync → MongoBackend._put_node_atomic(anchor, added=[edge-id], removed=[])
   ├─ partial_data = Serializer.serialize_fields(anchor, dirty)   (unchanged, not stripped)
   ├─ full = Serializer.serialize(anchor, include_type=True)
   ├─ non_arch_top = {k: _strip_empty_dicts(v) ...}                ← CHANGED
   │   └─ access {"all": -1, "roots": {"anchors": {}}} → {"all": -1}  ← NEW
   ├─ set_doc = data.edges merge expr + partial_data + data.<non_arch_top>
   └─ update_one(_id, [{'$set': set_doc}], upsert=True)
      └─ MongoDB accepts → edge-id now in data.edges               ← now succeeds
```

### 6.2 Reading the node on another pod (cold L1)

```text
backend2.get(anchor.id)
├─ L1 miss → load document from Mongo
├─ data.access has no "roots" key
└─ Serializer rebuilds Access → roots.anchors = {} via default_factory   (per PR; Serializer not in diff)
   └─ anchor has archetype fields + edge-id
```

| Scenario | Before | After |
|---|---|---|
| Edge added to stored node, default access | Error 40180 logged, edge lost in Mongo | Persisted |
| Node with granted access (`anchors={"uuid":2}`) | Worked | Works, unchanged |
| Dirty archetype dict field set to `{}` | Error 40180 | Still error 40180 (#6167) |
| First insert via `_write_to_db` | Worked, stores `anchors: {}` | Same |
| Restart or cross-pod read after an edge write | Edge missing | Edge present |

**Behaviour change users will notice:** edges and nodes now survive restarts and are visible across pods. The stored `data.access` may also now lack the `roots` key.

## 11. Questions your senior might ask

**Q: Why not just switch to a regular `$set`?**
`data.edges` uses `$setUnion`/`$setDifference`/`$ifNull` expressions, and those only work in a pipeline update. Dropping the pipeline would lose the atomic server-side edge merge.

**Q: Is stripping really lossless?**
It is lossless if every stripped field defaults to `{}` through `default_factory=dict`. The PR relies on the Serializer restoring those defaults. The Serializer is not in the diff, and the tests only check that `name` and the edges come back, not `access`.

**Q: Can error 40180 still happen?**
Yes, in two cases:
- A dirty archetype field whose value is `{}` reaches `set_doc` through `partial_data`, which is not stripped. This is #6167.
- A `non_arch_top` value that is itself `{}` at the top level is not removed.

**Q: Why did nobody notice?**
The exception was caught and only logged, and the API returned 200. The writing pod served data from its L1 cache. New nodes also got a first document from `_write_to_db`, which uses regular `$set`.

**Q: Does existing data need a migration?**
No. Documents with `anchors: {}` still load. The next pipeline write replaces `data.access` with the stripped version.

**Q: What happens to edges that were lost before the fix?**
This PR does not recover them. Edge deltas that failed are gone from MongoDB. The PR does not address this.

**Q: Why clear `_process_cache` in the tests?**
Each test starts its own container on a different port. A cached `mongo_client` from an earlier test would point at a container that has already stopped.

**Q: Why strip only in `_put_node_atomic`?**
It is the only path in this file that uses a pipeline `$set`. `_write_to_db` and `put_partial` use regular `$set`, which accepts `{}`.

**Q: Does `_strip_empty_dicts` change list shapes?**
No. It recurses into list items but never removes them, so list lengths and positions are kept.
