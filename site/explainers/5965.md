## 1. The short version

jac-scale signs a JWT (a signed login token) when a user logs in. On every authenticated request, `validate_jwt_token` checks that token and returns the `user_id` inside it.

**Before this PR, a token stayed valid until its `exp` time (default 7 days), whatever happened to the account.** A user could change their password after a suspected break-in, and the attacker's stolen token kept working. A deleted user's token kept working too. Every request also re-ran `jwt.decode()`, which is a cryptographic check, even for a token checked milliseconds before.

**You rewrote `validate_jwt_token` into three layers. First it checks a per-process cache of recently validated tokens. On a miss it runs `jwt.decode()`. Then it runs a "credential epoch" check: the token is rejected if its `iat` (issued-at) is older than a per-user `tokens_valid_from` timestamp.** A new `invalidate_user_tokens(user_id)` sets that timestamp to "now" and clears the caches for that user. `update_password` and `delete_user` call it. New tokens also carry a `jti` (unique token ID), which nothing uses yet; issue #5976 tracks that follow-up. SQLite storage gets a new `tokens_valid_from` column plus a startup migration.

**Status:** The PR is closed. The data does not say whether it was merged or closed without merging; check the PR page before you present it. All 10 CI checks passed on head commit `99734d6`. There are no reviews from anyone else. The only comment is your own backward-compatibility note.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| jac-scale | The Jac plugin that runs Jac apps as servers (and on Kubernetes). It includes user accounts and login. |
| JWT | JSON Web Token. A signed string holding claims such as `{"user_id": "u1", "exp": ..., "iat": ...}`. The server can check the signature without a DB lookup. |
| Claim | One field inside a JWT. |
| `exp` | Claim: when the token expires. `jwt.decode()` rejects expired tokens. |
| `iat` | Claim: "issued at", the Unix time the token was made. Here it is set to `now.timestamp()`, a float such as `1747123456.38`. |
| `jti` | Claim: "JWT ID", a unique ID per token (here a UUID). **This PR adds it.** Nothing reads it yet. |
| HS256 / HMAC-SHA256 | The signing algorithm. Checking it costs CPU on every decode. |
| `jwt.decode()` | PyJWT function that verifies the signature and `exp` and returns the claims dict. It raises an error if the token is bad. |
| `JacScaleUserManager` | The jac-scale class for users: create, delete, password change, and JWT create/validate. Declared in `user_manager.jac`, implemented in `impl/user_manager.impl.jac`. |
| `validate_jwt_token(token)` | Returns `user_id` if the token is valid, otherwise `None`. **This is where the bug is:** before the PR it never checked whether the account had been revoked. |
| Identity storage | The backend that stores user documents. It is MongoDB or SQLite (`SqliteIdentityStorage`). The manager calls `self._identity_storage.get_user_by_id`, `update_user_fields`, and so on. |
| Token revocation | Making an issued, unexpired token stop working. |
| Credential epoch / `tokens_valid_from` | A per-user Unix timestamp. Tokens with `iat` earlier than it are rejected. One number revokes every older token at once. Missing means `0.0`, so nothing is revoked. |
| `invalidate_user_tokens(user_id)` | New method. It writes `tokens_valid_from = time.time()` and clears this process's caches for that user. |
| `glob` | Jac's module-level global variable. The three caches are `glob` dicts, so each worker process has its own copy. |
| TTL | Time to live: how long a cache entry is trusted. |
| `time.monotonic()` | A clock that only moves forward. Used for cache expiry. It is not a wall-clock time. |
| `time.time()` | Wall-clock Unix time. Used for `tokens_valid_from`, so it can be compared with `iat`. |
| L1 decode cache (`_decoded_token_cache`) | `sha256(token) → (user_id, monotonic_expiry)`. TTL 30 s, max 50,000 entries. |
| Reverse index (`_user_token_hashes`) | `user_id → set of token hashes`. It lets revocation find and remove one user's L1 entries. |
| Revocation cache (`_revocation_ts_cache`) | `user_id → (tokens_valid_from, monotonic_expiry)`. TTL 60 s, so the DB is read at most once per user per minute in each worker. |
| Worker | One server process (uvicorn/gunicorn). Caches are not shared between workers. |
| `ALTER TABLE ... ADD COLUMN` | SQL that adds a column to an existing table. Used here as a small schema migration. |
| `row?.field` | Jac null-safe access. It gives `None` if `row` is `None`. |

## 3. The problem, step by step

### 3.1 The setup

- `create_jwt_token(user_id)` builds `{user_id, exp, iat}` and signs it.
- `validate_jwt_token(token)` ran `jwt.decode()` and returned `decoded['user_id']`. Its old docstring said a DB check per request was "unnecessary and costly", so it never touched storage.
- `update_password` and `delete_user` changed storage only. They did nothing to tokens.

### 3.2 What went wrong: password change does not end a stolen session

```text
1. t=0      User logs in → token A {user_id: u1, iat: 1000, exp: 1000+7d}
2. t=10     Attacker steals token A
3. t=20     User suspects compromise, calls update_password(u1, old, new) → storage updated
4. t=21     Attacker sends token A
5. t=21     validate_jwt_token: jwt.decode OK (signature valid, exp in future) → returns u1   ← WRONG
6. ...      Token A keeps working until exp (up to 7 days)
```

### 3.3 What went wrong: deleted account keeps authenticating

```text
1. User u2 has token B (exp in 7 days)
2. delete_user(u2) → user document removed from storage
3. Request with token B → jwt.decode OK → returns "u2"                      ← WRONG
4. Downstream code runs with a user_id that no longer exists
```

### 3.4 What went wrong: repeated crypto work

```text
1. Request 1 with token A → jwt.decode (HMAC verify)
2. Request 2 with token A, 5 ms later → jwt.decode again
3. ... at 500 RPS → 500 HMAC verifications/s, mostly on the same few tokens
```

### 3.5 Why it mattered

The PR description lists three cases with no fix: account deletion, password change after compromise, and admin force-logout. Issue #5976 is the follow-up. It confirms that this PR's epoch revocation is meant for "full logout" cases (password change, deletion). Per-device logout is left for later. The issue and comments describe no outside bug report or incident. The motivation comes from your description.

## 4. The idea of the fix (one sentence)

> **One timestamp per user, cached cheaply.** Store a `tokens_valid_from` time on each user and reject any token issued before it. Put two small in-process caches in front so the hot path needs neither crypto nor the DB.

It is the right idea for this PR's cases because one comparison (`iat < tokens_valid_from`) revokes every older token for a user without storing a list of tokens. The caches keep the added DB cost to about one read per user per minute in each worker.

### 5.1 `jac_scale/impl/user_manager.impl.jac`: three-layer validation

```diff

+    global _decoded_token_cache,_revocation_ts_cache,_user_token_hashes;
+    now_m = time.monotonic();

+        if hashes is not None { hashes.discard(token_hash); }

+    if not user_id { return None; }

+    iat = float(decoded.get('iat', 0.0));
+    rev_entry = _revocation_ts_cache.get(user_id);
+    if rev_entry is None or now_m >= rev_entry[1] {

+        if user_doc is None {
+            _revocation_ts_cache[user_id] = (float('inf'), now_m + _REVOCATION_CACHE_TTL);
+            return None;                                # NEW: deleted user → reject, remember it
+        }
+        _raw_vf = user_doc.get('tokens_valid_from');
+        valid_from_ts = 0.0 if _raw_vf is None else float(_raw_vf);
+        _revocation_ts_cache[user_id] = (valid_from_ts, now_m + _REVOCATION_CACHE_TTL);
+        rev_entry = (valid_from_ts, now_m + _REVOCATION_CACHE_TTL);
+    }
+    valid_from_ts = rev_entry[0];
+    if iat < valid_from_ts {
+        logger.debug(f"JWT rejected for {user_id}: iat predates revocation boundary");
+        return None;
+    }
+
+    if len(_decoded_token_cache) >= _TOKEN_CACHE_MAX_SIZE {
+        _decoded_token_cache.clear();                   # NEW: crude overflow: drop everything
+        _user_token_hashes.clear();
+    }
+    _decoded_token_cache[token_hash] = (user_id, now_m + _TOKEN_CACHE_TTL);
+    _user_token_hashes.setdefault(user_id, set()).add(token_hash);
+    return user_id;
 }
```

**What:** Validation now has three steps:
- **L1:** look up the token hash in the decode cache.
- **L2:** on a miss, run `jwt.decode`.
- **L3:** compare `iat` against the user's `tokens_valid_from`. This value comes from the 60 s revocation cache or one DB read.

Only tokens that pass all three are added to L1.

**Why:** L3 fixes both revocation cases. L1 removes the repeated crypto work.

**Things to notice:**
- The cache key is `sha256(token)`, not the raw token, so full tokens are not kept as dict keys.
- An L1 hit skips L3 completely. That is safe in the worker that revoked, because `invalidate_user_tokens` evicts the entries. In other workers it adds delay (see 5.3 and 6.5).
- A missing user is cached as `float('inf')`, so every `iat` is less than it and is rejected for 60 s without more DB reads.
- When the cache is full, it is cleared completely; there is no LRU (least-recently-used) eviction. All users pay a burst of `jwt.decode` calls after a clear.
- `_user_token_hashes` keeps hashes for tokens that expired but were never looked up again. It only shrinks on revocation, on an expired-entry hit, or on the overflow clear.
- The dicts are changed with no lock. Python dict operations are each safe under the GIL. But `del _decoded_token_cache[token_hash]` could raise `KeyError` if two threads remove the same expired entry at once. Whether validation runs on several threads depends on the server setup, which the diff does not show.
- `iat` comes from the token's issuing machine. `tokens_valid_from` comes from `time.time()` on the revoking machine. Clock skew between machines could move the boundary by that amount.
- The old docstring was removed. The function now has none.

## 6. How execution flows after the PR

### 6.1 Validating a token

```text
validate_jwt_token(token)
├─ token_hash = sha256(token)                               ← NEW
├─ L1 lookup in _decoded_token_cache                        ← NEW
│   ├─ fresh hit → return user_id (no crypto, no DB)
│   └─ expired → delete entry + remove from reverse index
├─ L2 jwt.decode(token)                                     (existing)
│   └─ fails → return None
├─ user_id missing → return None                            ← NEW
├─ L3 revocation boundary                                   ← NEW
│   ├─ _revocation_ts_cache fresh → use cached boundary
│   └─ miss/expired → get_user_by_id
│       ├─ None → cache +inf, return None
│       └─ found → boundary = tokens_valid_from or 0.0, cache 60 s
├─ iat < boundary → return None                             ← NEW
├─ cache size ≥ 50 000 → clear L1 + reverse index           ← NEW
├─ store L1 entry (30 s) + reverse index                    ← NEW
└─ return user_id
```

### 6.2 Changing a password

```text
update_password(user_id, cur, new)
├─ identity_storage.update_password(...)
└─ no 'error' in result → invalidate_user_tokens(user_id)   ← NEW
    ├─ update_user_fields(user_id, {tokens_valid_from: time.time()})
    ├─ evict this user's L1 entries via reverse index
    └─ evict this user's revocation-cache entry
```

### 6.3 Deleting a user

```text
delete_user(user_id)
├─ (existing cleanup, not shown in diff)
├─ identity_storage.delete_user(user_id)
└─ invalidate_user_tokens(user_id)                          ← NEW (writes to a now-missing user)
    → next validate: L1 miss → L2 ok → L3 user_doc None → +inf → reject
```

### 6.4 Issuing a token

```text
create_jwt_token(user_id)
└─ payload {user_id, jti: uuid4, exp, iat}                  ← CHANGED (jti added)
```

### 6.5 Scenarios

| Scenario | Before | After |
|---|---|---|
| Same token twice within 30 s | 2× `jwt.decode` | 1× decode + 1× dict lookup |
| Password changed, old token, same worker | Accepted until `exp` | Rejected on next request |
| Password changed, old token, other worker | Accepted until `exp` | Rejected once that worker's caches expire (up to ~60 s, ~90 s worst case with L1) |
| User deleted, old token, same worker | Accepted until `exp` | Rejected on next request |
| Wrong current password on change | No effect on tokens | No effect on tokens |
| Legacy user with no `tokens_valid_from` | Accepted | Accepted (`0.0` boundary) |
| Old token without `jti` | Accepted | Accepted (`jti` not checked) |
| Token for unknown/deleted user | Accepted | Rejected (new DB check on L3 miss) |

**Behaviour changes users will notice:**
- After a password change, the user's own existing sessions are logged out too.
- A token for a user that does not exist in storage is now rejected. Before, it was accepted.

## 11. Questions your senior might ask

**Q: Why not check the DB on every request instead of caching?**
The old code avoided that on purpose; its docstring said a per-request DB call was "costly". The 60 s revocation cache limits reads to one per user per minute in each worker.

**Q: Can a revoked token still work, and for how long?**
In the worker that revoked, no: both caches are evicted. In other workers, it works until their caches expire. That is up to 60 s for the revocation cache, plus up to 30 s if the token was put into L1 just before the stale entry expired.

**Q: What happens to existing tokens and users after upgrade?**
Nothing changes for them. With no `tokens_valid_from`, the boundary is `0.0`, and the legacy test covers this. Old tokens without `jti` still decode.

**Q: Why hash the token for the cache key?**
So full bearer tokens are not kept as keys in a long-lived dict. SHA-256 is cheap next to HMAC verification plus claim parsing.

**Q: What if the cache fills up?**
At 50,000 entries, the L1 cache and the reverse index are cleared completely. The overflow test checks that this does not crash and that exactly one entry remains.

**Q: Why does `update_password` log the user out of their own sessions?**
The epoch boundary applies to every token issued before "now". There is no per-token exception yet; that is the `jti` work in #5976.

**Q: Why the SQLite change but none for MongoDB?**
SQLite needs a real column, so the PR adds one, with an `ALTER TABLE` for existing databases. MongoDB documents accept new fields without a schema change.

**Q: Is this thread-safe?**
Single dict operations are atomic under the GIL. The expired-entry `del` can raise `KeyError` if two threads hit it at once. Whether validation runs on several threads is not visible in this diff.

**Q: What is `jti` for if nothing reads it?**
It is groundwork for per-token revocation and audit tracing, tracked in #5976. Issuing it now means tokens will not need to be reissued later.
