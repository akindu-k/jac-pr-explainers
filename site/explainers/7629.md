## 1. The short version

The Jac runtime has a `Serializer` that turns stored graph data ("anchors") back into live Jac objects. It is called once for every anchor a service reads, so anything it logs is multiplied by the number of anchors read.

Issue #7602 showed that this causes log floods. **Several log lines on this per-anchor read path fire every single time, so 200 reads of the same anchor give 200 identical lines, and production services saw about 23,000 lines in 5 minutes that carried only 7 lines of real information.** PR #7603 fixed the seven WARNING lines named in the issue. Reviewers then pointed out that the same pattern was still present on other info, warning and error lines in the same file. That includes the alias-resolved line, which fires on the *success* path, and the schema-drift lines.

**Your PR wraps each of the eight remaining per-anchor log calls in the existing `Serializer._should_warn_once(scope, key)` gate. Each call gets its own scope and a key that names the class. A given message then prints once per class (and, for errors, once per exception type) per process, not once per anchor.** Message text and deserialization results are unchanged. Only the number of repeats drops. After a bot review (Greptile) you made the keys module-qualified, so two different classes never share a slot. You also added three regression tests.

**Status:** Merged on 2026-08-03. All CI checks passed. The skipped jobs are release and publishing jobs. There were no human review approvals on the PR thread, only automated Greptile comments, and the follow-up commit addressed them.

| `repair(data, cls)` | Serializer method that computes and maybe applies drift fix-up steps. |

| Log level | `debug` < `info` < `warning` < `error`. Services usually show `info` or `warning` and above. |

## 3. The problem, step by step

### 3.1 The setup

- A service reads anchors from a store. Some were written by other programs, some have old field shapes, some use renamed classes.
- For each anchor: `deserialize` → `_deserialize_anchor` → `_deserialize_archetype` → `_get_class` → `repair`.
- Each of these steps can log. Before #7603 none of them deduplicated. #7603 gated seven WARNING sites, mainly the "unregistered class" and "archetype reconstruction failed" lines from the issue. This PR covers the rest.

### 3.2 What went wrong: success path (alias resolution)

```text
1. Class renamed: oldmod.LegacyName is aliased to its new name in _aliases
2. Read anchor #1  → _get_class("oldmod","LegacyName") → alias found → INFO "resolving aliased class ..."
3. Read anchor #2  → same lookup → INFO again
4. ...
5. Read anchor #N  → INFO again                         ← WRONG: N lines for a normal, successful lookup
```

### 3.3 What went wrong: schema drift

```text
1. JAC_SCHEMA_REPAIR=repair, stored DonationNode rows have an old field shape
2. Read anchor #1 → repair() returns steps → INFO "repaired __main__.DonationNode: [...]"
3. Read anchor #1 also has unknown fields → INFO "preserved unknown fields in attic on ..."
4. Read anchors #2..#N → both lines again for each anchor   ← WRONG: 2N lines for one class
(detect mode: same pattern with "drift detected on ...")
```

### 3.4 What went wrong: bad data and errors

```text
1. Stored anchor has archetype = "not-a-dict"
2. Each read → WARNING "archetype field is not a dict (str); dropping anchor."   ← per anchor
3. A class whose constructor raises ValueError
4. Each read → ERROR "Failed to deserialize archetype X: ..."                    ← per anchor
   (and/or "Failed to deserialize anchor: ..." / "Failed to deserialize X: ...")
```

### 3.5 Why it mattered

- The issue measured about 85 lines/sec/service in production (`builder-sv`, `jac-coder-sv`). Real errors could not be found during a live load test.
- Building each log string costs CPU on the hot path. The f-string is evaluated even if a handler later drops the line.
- After #7603, @Thamirawaran and @udithishanka noted in review (according to your description) that these other paths would still flood "exactly like before". The drift case is a common one in real deployments.

## 4. The idea of the fix (one sentence)

> **Gate every remaining per-anchor log line behind `_should_warn_once`, keyed by class.** The first occurrence for each class (and exception type) is still logged with its full message; identical repeats are silently skipped.

This reuses the mechanism #7603 already added and tested, so there is one dedup design in the file instead of two. Keeping the first line preserves the useful signal that a plain logging filter would hide, which was the issue's complaint about the workaround.

## 6. How execution flows after the PR

### 6.1 Loading an anchor

```text
Serializer.deserialize(blob)
└─ _deserialize_anchor(data)
   ├─ archetype not a dict?
   │  ├─ _should_warn_once("archetype-not-dict", "<AnchorType>.<valuetype>")   ← NEW
   │  │  └─ first time → WARNING; later → silent
   │  └─ return None (every time, unchanged)
   ├─ _deserialize_archetype(arch_data, anchor)
   │  ├─ _get_class(module, type)
   │  │  ├─ alias hit → _should_warn_once("alias-resolved", key) → INFO once   ← NEW
   │  │  └─ unknown class → (gated in #7603)
   │  ├─ repair(data, cls)
   │  │  ├─ detect + steps → _should_warn_once("drift-detected", cls_key) → INFO once   ← NEW
   │  │  └─ repair + steps → _should_warn_once("repaired", cls_key) → INFO once        ← NEW
   │  ├─ dropped fields, repair mode → _should_warn_once("attic-preserved", ...) → INFO once   ← NEW
   │  ├─ dropped fields, other modes → DEBUG every time (unchanged)
   │  └─ exception → _should_warn_once("archetype-error", "mod.Type:Exc") → ERROR once   ← NEW
   └─ any exception in anchor load
      └─ _should_warn_once("anchor-failed", "<arch mod.Type | AnchorType>:Exc") → ERROR once   ← NEW
```

### 6.2 Deserializing a generic typed value

```text
Serializer.deserialize(data)  (non-anchor typed value)
└─ build instance
   └─ exception → _should_warn_once("deserialize-failed", "cls.__module__.Type:Exc") → ERROR once   ← NEW
      └─ return None (unchanged)
```

| Scenario | Before | After |
|---|---|---|
| 50 reads of a renamed (aliased) class | 50 INFO lines | 1 |
| N reads, same class, `JAC_SCHEMA_REPAIR=repair`, drifted | N "repaired" + N "attic" lines | 1 + 1 |
| 50 anchors with `archetype: "not-a-dict"` (all `NodeAnchor`) | 50 WARNING lines | 1 |
| One bad `NodeAnchor` and one bad `EdgeAnchor` | 2 | 2 (separate slots) |
| Same class fails with `ValueError` then `KeyError` | 2 | 2 |
| Same class fails twice with `ValueError`, different messages | 2 | 1 (second message hidden) |
| Two classes with the same name in different modules, same exception | 2 | 2 (after commit 1e7c8b2) |
| Return values of all deserialize calls | — | Unchanged |

**Behaviour change users will notice:** logs are much quieter. Later variants of a message for the same key (different drift steps, different error text with the same exception type) are no longer shown. You can't see how often something happened anymore. Your description says that occurrence counts are part 2.

## 11. Questions your senior might ask

**Q: Doesn't dedup hide real problems?**
The first occurrence per key is always logged with its full message. What is lost is repeats and frequency. Counting is deferred to part 2.

**Q: Why key errors on the exception type and not just the class?**
So distinct failure kinds for one class (for example `ValueError` vs `KeyError`) each get logged once. Only identical repeats are suppressed.

**Q: Why include the module in the keys?**
Greptile showed that two classes with the same name in different modules would share a slot. The first one's failure would silence the other's *first* failure. Commit 1e7c8b2 qualified the keys.

**Q: Why use `cls.__module__` in `deserialize` instead of the stored module name?**
That key names the class actually being built. For an aliased class it is the new module. It still separates same-named classes across modules. You should confirm `cls` is always bound when that `except` runs, since the diff doesn't show it.

**Q: What does the non-dict warning key on, and is it fine-grained enough?**
`<AnchorType>.<valuetype>`, for example `NodeAnchor.str`. With no archetype dict there is no class name, so this is the finest key available. Different corrupt `NodeAnchor` rows share one line.

**Q: Is the dedup memory bounded? Is it thread-safe?**
Its size grows with the number of distinct (scope, key) pairs, which is small (classes × exception types). The helper `_should_warn_once` comes from #7603 and isn't in this diff, so its data structure and locking can't be judged here.

**Q: Does gating also save CPU?**
Yes for the message: the f-string is only built when the gate returns `True`. The key f-string is still built every time, but it is short.

**Q: Why leave DEBUG lines alone?**
DEBUG is normally disabled in production, so those lines don't flood. The description calls them "effectively free".

**Q: Which paths aren't tested?**
`deserialize-failed`, `anchor-failed`, `archetype-error`, `drift-detected`, `repaired` and `attic-preserved` have no dedicated test. They share the same helper and pattern as the tested paths.

**Q: How do the tests avoid leaking state into other tests?**
Each one calls `_reset_warn_cache()` before and after (in `finally`), and restores the logger's handler and level.
