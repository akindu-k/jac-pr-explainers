## 1. The short version

Jac programs keep their data as a graph of nodes and edges. When the jac-scale plugin is installed, it saves that graph to MongoDB for you. Before this PR, Jac code had no supported way to talk to the database directly, for example to run `find_one` on a collection. Issue #4355 asked for this, so people coming from jac-cloud could keep using raw queries. **Before this PR, Jac code could not run its own database queries. There was no `db` builtin, and pluggy dropped any hook argument that had a default value.**

**You added a new `Db` object in jac-scale and exposed it as a global builtin, so `db()` or `db(db_name="my_app", db_type="redis")` returns a handle with ten CRUD methods for MongoDB or Redis.** For example: `db().find_one("users", {"name": "John"})`. To make keyword arguments like `db_name` actually reach the plugin, you also made `plugin.jac` strip default values from the `create_j_context`, `store` and `db` hook signatures.

The PR grew a lot after it was opened. Reviewers asked for a builtin instead of `get_db()` and for five more methods, and you then added Redis support. The PR description and release notes still describe the first version: MongoDB only and five methods.

**Status:** Closed. The metadata says "closed", not "merged", so check GitHub to see whether it was merged. @kashmithnisakya's review is still "changes requested" with no later approval. On the head commit `1bad321`, `test-core` and `jac-check` fail. All other checks pass.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | A programming language that compiles to Python. Files end in `.jac`. |
| `obj` / `has` | Jac's way to declare a class (`obj Db { ... }`) and its fields (`has db_name: str = 'jac_db';`). |
| `impl` file | Jac lets you declare a method in one file (`def find_one(...)`) and write its body in another (`impl Db.find_one(...) { ... }`), usually under `impl/`. |
| `glob` | A module-level global variable in Jac. Example: `glob _mongo_client = None;`. |
| walker / `root` | A walker is a Jac object that moves across the graph. `root` is the user's starting node. The examples run code inside walkers. |
| jaclang | The core Jac compiler and runtime package (`jac/jaclang/...`). |
| jac-scale | A plugin that adds production features: MongoDB/Redis persistence, Kubernetes deployment, file storage (`store()`). **This is what the PR adds to.** |
| Plugin / pluggy | jaclang uses the Python library *pluggy* for plugins. Core declares a "hookspec" (a function signature). A plugin provides a matching `@hookimpl`. Calling the hook runs the plugin's version. |
| `argnames` vs `kwargnames` | pluggy sorts a hook's parameters: those **without** defaults go in `argnames`, those **with** defaults go in `kwargnames`. pluggy only passes `argnames` to implementations. |
| `strip_defaults` | New helper in `plugin.jac`. It rewrites a function's `__signature__` so no parameter has a default, which puts every parameter into pluggy's `argnames`. |
| `JacRuntime` | The core runtime interface in `jaclang/pycore/runtime.py`. Its methods (`store`, `commit`, now `db`) are the hooks plugins can override. |
| Builtin module | `jaclang/runtimelib/builtin.jac`. Names in its `__all__` are visible in every `.jac` file without an import, like `store`, `commit`, and now `db`. |
| Lazy `__getattr__` | Python feature: a module-level `__getattr__(name)` runs when a missing attribute is looked up. Here it returns `JacRuntime.db` on first use. |
| MongoDB / `pymongo` | A document database and its Python driver. Data is grouped as database → collection → document (a dict). |
| `MongoClient` | pymongo's connection object. `client["jac_db"]["users"]` gets a collection. |
| `ObjectId` | MongoDB's default 12-byte ID type for `_id`. `ObjectId("abc")` raises an error if the string is not 24 hex characters. |
| Cursor | What `col.find()` returns in pymongo: a lazy iterator, not a list. |
| Redis | An in-memory key/value store. Here, each document is stored as JSON at key `{db_name}:{collection}:{_id}`. |
| `KEYS pattern` | Redis command that scans **all** keys matching a pattern. It blocks the server while it runs. |
| `$set` | MongoDB update operator: `{"$set": {"age": 31}}` changes only `age`. |
| Upsert | "Update, or insert if missing." pymongo's `upsert=True`. |

| `get_scale_config()` | jac-scale's config reader (`jac.toml` and possibly env vars). It is called in the diff, but its code is not part of this PR. |
| `Db` | New object in `jac_scale/db.jac`. It holds `client`, `db_name` and `db_type`, and has the ten CRUD methods. **This is what the PR adds.** |
| testcontainers | Python library that starts a real Docker container (here `mongo:latest`) for a test. |

## 3. The problem, step by step

This is a feature, plus one real bug that the feature exposed.

### 3.1 The setup

- **jaclang core** declares runtime hooks on `JacRuntime` (for example `store(base_path="./storage", create_dirs=True)`). It exports the matching names as builtins through `builtin.jac`.
- **jac-scale** registers `JacScalePlugin` with the plugin manager. Its `@hookimpl` methods replace the core stubs.
- jac-scale already had a `DatabaseProviderFactory`. Judging by its imports (`DeploymentTarget`, `DatabaseProvider`), it creates database *deployments* for Kubernetes, not clients for app code. The diff does not show the full file.

### 3.2 What went wrong: no way to query the database from Jac

```text
1. User writes a .jac app with jac-scale installed; the graph is persisted to MongoDB.
2. User needs a raw query, e.g. "find the user with name John" in a "users" collection.
3. They look for something like db.find_one(...) as in jac-cloud / issue #4355.
4. No `db` name exists in builtin.__all__; JacRuntime has no `db` hook.     ← MISSING
5. Only option: import pymongo by hand, build a MongoClient, and copy the
   connection string from config — duplicated per app, no shared client.
```

### 3.3 What went wrong: hook arguments with defaults were dropped

The comment block in `plugin.jac` describes this. The release note calls it "Fix: Plugin Hook Keyword Arguments".

```text
1. Plugin declares   @hookimpl static def db(db_name='jac_db', ...)
2. pluggy inspects it: db_name has a default → goes to kwargnames, argnames = ()
3. User calls        db(db_name="my_custom_db")
4. pluggy's _multicall passes only argnames → calls JacScalePlugin.db()       ← WRONG
5. db_name falls back to 'jac_db'; the user's "my_custom_db" is silently lost
```

Before this PR, only `create_j_context` had its defaults stripped. The PR now also strips them from `store`. That suggests `store(base_path=...)` may have had the same problem, but the PR does not state this.

### 3.4 Why it mattered

- Issue #4355 asks for low-level methods (`find_one`, `find`, `insert`, `commit`) "while maintaining consistency across backend systems".
- @kashmithnisakya: jac-cloud already has `insert_many`, `update_many`, `update_by_id`, `find_by_id` and `delete_by_id`. Matching them makes it "much easier to migrate existing applications with minimal changes".
- @musab-mah-7 wanted it shaped like `store()`: a builtin called `db`, not a `get_db()` import.

## 4. The idea of the fix (one sentence)

> **Add a plugin-backed `db` builtin that returns a small `Db` wrapper.** Core declares `db()` and exports it. jac-scale implements it, builds or reuses a shared MongoDB or Redis client, and wraps it in an object with pymongo-style CRUD methods.

This copies the existing `store()` pattern exactly: a core stub, a plugin hookimpl, and a lazy builtin. Core stays free of database dependencies, and users get one global name.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/db.jac`: the `Db` object and shared clients

```diff
+import from pymongo { MongoClient }
+import from redis { Redis }                       # NEW: hard import of redis
+import from bson { ObjectId }                     # unused in this file
+
+glob _mongo_client: (MongoClient | None) = None,
+     _redis_client: (Redis | None) = None;
+
+def get_mongo_client(uri: (str | None) = None) -> MongoClient {
+    global _mongo_client;
+    if _mongo_client is None {
+        _mongo_client = DatabaseProviderFactory.create_client(DatabaseType.MONGODB, uri=uri);
+    }
+    return _mongo_client;                          # uri ignored after first call
+}
+def get_redis_client(...)  # same shape for Redis
+
+obj Db {
+    has client: (MongoClient | Redis),
+        db_name: str = 'jac_db',
+        db_type: DatabaseType = DatabaseType.MONGODB;
+    def find_one(col_name: str, filter: dict) -> dict | None;
+    def find / insert_one / update_one / delete_one ...
+    def insert_many / update_many ...              # bulk
+    def find_by_id / update_by_id / delete_by_id ...  # by id
+}
```

**What:** Declares one shared client per backend, created on first use. Declares `Db` with ten method signatures. The bodies live in `impl/db.impl.jac`.

**Why:** Gives users a single object to call, and keeps one connection pool per process instead of one per `db()` call.

**Things to notice:**
- **The client cache ignores `uri` after the first call.** `db(uri="mongodb://A")` followed by `db(uri="mongodb://B")` returns the client for A. Nothing warns about this. The docs present `uri` as a per-call option.
- **`import from redis` is at the top of the module.** If the `redis` package is not installed, importing `jac_scale.db` fails, even for MongoDB-only users. The diff does not show whether `redis` is a jac-scale dependency, because no `pyproject` change is included.
- `ObjectId` is imported but not used here.
- `db_name` creates a new *database* on the same server, not a new connection. That is why `db("db_one")` and `db("db_two")` share one client.

### 5.2 `jac-scale/jac_scale/impl/db.impl.jac`: method bodies for MongoDB and Redis

```diff
+impl Db.find_one(col_name: str, filter: dict) -> dict | None {
+    if self.db_type == DatabaseType.MONGODB {
+        return self.client[self.db_name][col_name].find_one(filter);   # straight pymongo
+    } elif self.db_type == DatabaseType.REDIS {
+        if '_id' in filter {                                           # only _id lookups work
+            data = self.client.get(f"{self.db_name}:{col_name}:{filter['_id']}");
+            if data { return json.loads(data); }
+        }
+        return None;
+    }
+    raise ValueError(f"Unsupported database type: {self.db_type}");
+}
+
+impl Db.find(col_name: str, filter: dict) -> Any {
+    ... MONGODB: return col.find(filter);                 # cursor
+    ... REDIS:   keys = self.client.keys(pattern);        # KEYS scan, filter ignored
+                 return results;                          # list
+}
+
+impl Db.insert_one(...) {
+    ... REDIS: if '_id' not in document { document['_id'] = str(uuid4()); }
+               class InsertResult { has inserted_id: str; }   # class defined per call
+               return InsertResult(inserted_id=document['_id']);
+}
+
+impl Db.find_by_id(col_name: str, id: str) -> dict | None {
+    ... MONGODB: return col.find_one({'_id': ObjectId(id)});   # assumes ObjectId ids
+    ... REDIS:   GET {db_name}:{col_name}:{id}
+}
+
+def get_db -> Db {                                     # leftover helper from v1
+    return Db(client=get_mongo_client(), db_name='jac_db', db_type=DatabaseType.MONGODB);
+}
```

**What:** Each method checks `self.db_type`. For MongoDB it calls the pymongo method with the same name and returns pymongo's result. For Redis it stores JSON at `{db_name}:{col}:{_id}` and returns small result objects shaped like pymongo's (`inserted_id`, `matched_count`, `modified_count`, `deleted_count`).

**Why:** This is the "direct access" the issue asked for. It also covers @kashmithnisakya's five extra methods.

**Things to notice:** The two backends do not behave the same, even though the docs say "Both MongoDB and Redis support the same interface".

| Method | MongoDB | Redis |
|---|---|---|
| `find_one` | any filter | only `{'_id': ...}`; anything else returns `None` |
| `find` | cursor, filter applied | list, **filter ignored** (returns the whole collection) via `KEYS` |
| `update_one` | any filter, `$set` etc. | only `_id` filter; always reports `modified_count=1` on a hit |
| `update_many` | full | exact-match filter; `upsert_mode` ignored |
| `delete_one` | any filter | only `_id`; other filters silently return `deleted_count=0` |
| `*_by_id` | wraps id in `ObjectId(id)`, so string or custom `_id`s fail | plain string key |

Other points:
- The Redis code only treats `$set` specially. Any other operator, such as `$inc`, would be merged into the document as a literal key.
- Result classes like `class UpdateResult` are defined inside the function, so they are re-created on every call.
- `get_db` is never declared in `db.jac` and nothing in the diff calls it. It looks like a leftover from the first version (the one @musab-mah-7 commented on). The module docstring says this file is a "dispatcher".
- The parameters `id` and `filter` shadow Python builtins. This is harmless but could be flagged.
- Because this is an `impl` file, defining nested `class`es and a free `def get_db` inside it is unusual. It may be related to the `jac-check` failure, but that cannot be confirmed without the logs.

### 5.3 `jac-scale/jac_scale/factories/database_factory.jac`: `DatabaseType` and `create_client`

```diff
+import os;                                            # unused in the shown code
+enum DatabaseType { MONGODB = "mongodb", REDIS = "redis" }
 ...
+    static def create_client(
+        db_type: (DatabaseType | str),
+        uri: Optional[str] = None,                     # Optional / Dict / cast: imports not shown
+        config: Optional[Dict[(str, Any)]] = None
+    ) -> Any {
+        if isinstance(db_type, str) {
+            try { db_type = DatabaseType(db_type); } except ValueError { ; }
+        }
+        if (db_type == DatabaseType.MONGODB) {

**What:** Picks the URI in this order: the explicit `uri` argument, then the scale config (`mongodb_uri` / `redis_url`). It then builds the client.

**Why:** Gives `db.jac` one place to create clients, following the existing `storage_factory` pattern according to `IMPLEMENTATION_SUMMARY.md`.

**Things to notice:**
- The code calls `Optional`, `Dict`, `cast` and `get_scale_config`. The visible hunks only import `Any`. Line 1 of the file is not in the diff, so I cannot tell whether these names are imported. If `get_scale_config` is missing, any call without `uri` would raise `NameError`. `jac-check` failing makes this worth checking first.
- `import os` is added but never used. The docs say `MONGODB_URI` / `REDIS_URL` env vars are read, but this code does not read `os.environ`. That only works if `get_database_config()` reads them, and its code is not in the diff. The test sets `MONGODB_URI`, and `test-scale` passes, which suggests it does, at least for MongoDB.
- The `try ... except ValueError { ; }` lets an unknown string fall through to the `else` branch, which gives a clearer error message.

**Things to notice:**

│     │     ├─ uri given → use it
│     │     ├─ else get_scale_config().get_database_config()['mongodb_uri']
│     │     ├─ still None → ValueError("MongoDB URI not provided ...")
│     │     └─ MongoClient(uri)
│     ├─ REDIS → get_redis_client(uri) → ... Redis.from_url(uri)
│     └─ return Db(client, db_name, db_type)
```

### 6.3 Calling a method, e.g. `handle.find_one("users", {"name": "John"})`

```text
Db.find_one                                                          ← NEW
├─ db_type == MONGODB → client["my_app"]["users"].find_one(filter) → dict | None
├─ db_type == REDIS
│  ├─ '_id' in filter → GET my_app:users:<id> → json.loads → dict
│  └─ otherwise → None
└─ else → ValueError("Unsupported database type")
```

| Scenario | Before | After |
|---|---|---|
| `db()` in a `.jac` file, no jac-scale | `NameError` (no such name) | `NotImplementedError` with install hint |
| `db()` with jac-scale + MongoDB configured | Not available | `Db` on database `jac_db` |
| `db(db_name="x")` | Not available | `Db` on database `x` (works because of `strip_defaults`) |
| `db(db_type="redis")` | Not available | `Db` backed by Redis JSON keys |
| `db(db_type="postgres")` | Not available | `ValueError` from enum conversion |
| Second call with a different `uri` | Not available | **Silently reuses the first client** |
| `store(base_path=...)` | Defaults kept on hookimpl (the PR does not say whether args were lost) | Defaults stripped like other hooks |

**User-visible changes:** a new global name `db` in every Jac file, and possibly different argument passing for `store()`.

## 11. Questions your senior might ask

**Q: Why do hook defaults need stripping at all?**
pluggy only passes parameters without defaults (`argnames`) to implementations. If `db(db_name='jac_db')` keeps its default, pluggy sees no args and drops the caller's `db_name`. Removing defaults from the `__signature__` fixes that. `test_direct_db_access` checks it with `db_name="my_custom_db"`.

**Q: Why did you also strip defaults from `store`?**
The PR applies the same fix to every hook that has defaulted parameters. The diff has no `store` test or note saying `store` was broken, so be ready to show it was, or that nothing regresses.

**Q: What happens if I call `db(uri="A")` and then `db(uri="B")`?**
You get client A both times. `get_mongo_client` caches the first client and ignores later `uri` values.

**Q: Are MongoDB and Redis really interchangeable behind `Db`?**
No. On Redis, `find` returns every document in the collection regardless of filter. `find_one`, `update_one` and `delete_one` only match on `_id`. `find` returns a list on Redis but a cursor on MongoDB.

**Q: What if `redis` isn't installed and I only use MongoDB?**
`db.jac` imports `redis` at the top, so importing it fails. Whether `redis` is a declared dependency of jac-scale is not shown in this PR.

**Q: Where does the URI come from if I don't pass one?**
From `get_scale_config().get_database_config()` (`mongodb_uri` / `redis_url`). The docs also promise `MONGODB_URI`/`REDIS_URL` env vars, but the new code does not read env vars itself. That relies on config code outside this diff.

**Q: Will `find_by_id` work for documents created by jac-cloud or by Jac's own persistence?**
Only if their `_id` is an `ObjectId`. The code always wraps the id in `ObjectId(id)`, so string or UUID ids raise an error.

**Q: Why are `test-core` and `jac-check` red?**
The logs are not available here. Likely causes are the new builtin and hook in core, and type-check problems in the new `.jac` files, such as names that may not be imported in `database_factory.jac` and the `-> Db` annotation. Confirm by reading the logs.

**Q: Why is `db.jac` in `.jacignore`?**
The PR says it is for "corelib implementation inclusion". An ignore list usually excludes files, so check which tool reads `.jacignore` and whether the bare filename hides your new `jac_scale/db.jac` from checks.

**Q: Does the issue's `commit()` example work?**
`Db` has no `commit` method. The issue's `db.commit()` is not implemented. MongoDB writes through pymongo apply immediately, and Jac's existing `commit` builtin is a separate thing.
