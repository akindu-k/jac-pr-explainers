# feat(scale): the admin Logs page reads pod logs when Loki is not deployed (#9673)

## In short

The admin Logs page only knew how to ask Loki (a log database) for logs. If a deployment had logs turned off in config, no Loki existed, and the page showed `502 Log backend unavailable`. You made both log endpoints fall back to reading the app's pod logs directly from the Kubernetes API when Loki is not configured and the gateway runs inside the cluster.

## Words to know

- **Loki**: a log storage and query system. The Logs page used it as its only source.
- **LogQL**: Loki's query language. `_build_logql` builds these queries.
- **Alloy**: the agent that ships pod logs into Loki. It is part of the "Loki + Alloy stack".
- **Pod**: the smallest unit Kubernetes runs. It holds one or more containers.
- **Container**: one running process image inside a pod. Logs are read per container.
- **Kubernetes API / `CoreV1`**: the cluster's control API. `CoreV1` is the part that handles pods. `list_namespaced_pod` lists pods and `read_namespaced_pod_log` returns a container's log text.
- **Namespace**: a named group of resources inside a cluster.
- **Label / label selector**: a key on a Kubernetes object. A selector such as `jac-scale.role` returns only objects that have it. Every gateway and fleet Deployment carries this label.
- **RBAC / Role**: Kubernetes permissions. A Role says which API calls an identity may make.
- **`ops_console`**: the setting `[scale.kubernetes].ops_console`. When true, it creates a Role (`OPS_READ_RULES`) that allows listing pods and reading `pods/log`.
- **In-cluster**: the gateway is running inside Kubernetes, so it can reach the cluster API. `k8s_available()` checks this.
- **403**: the HTTP "Forbidden" status. Here it means the gateway lacks permission to read pods.
- **`before` cursor**: a paging value. The page asks for lines older than a timestamp.
- **Trace ID**: an identifier that links log lines from one request across services.
- **RFC3339 timestamp**: a text date such as `2026-10-03T00:00:01.000000001Z`. Kubernetes adds one in front of each line when you ask for `timestamps=True`.
- **`ts_ns`**: a timestamp in nanoseconds since 1970, stored as a string in each log line.
- **`asyncio.to_thread`**: runs a blocking function in a worker thread so the async server is not stuck.

## The problem

1. An admin sets `[scale.gateway.logs] enabled = false`, so no Loki is deployed.
2. The admin opens the Logs page. It calls `/admin/logs` or `/admin/logs/trace/{id}`.
3. Both handlers always built a LogQL query and called `_loki_request`.
4. There was no Loki to answer, so a `ConnectionError` was raised and the endpoint returned `502 Log backend unavailable`.

Nothing in `scale/` read pod logs, even though the cluster already held the data and a Role for reading it existed. Any deployment without the Loki stack had a dead Logs page.

## The changes, one by one

### `jac/jaclang/scale/admin/impl/logs.impl.jac`

This file holds the main change. It adds a pod-log path and routes both endpoints through one new function.

**`_use_pod_logs()`** picks the backend. It returns true only if all of these hold:
- `LOKI_URL` is unset or empty.
- The gateway's `logs.enabled` config is false (an unreadable config counts as `{}`, so also off).
- `k8s_available()` is true.

So off-cluster runs and Loki-configured runs behave as before.

**`_rfc3339_to_ns(stamp)`** turns the kubelet's timestamp into epoch nanoseconds. It strips the `Z`, splits at the dot, parses the seconds part with `time.strptime`, and uses `calendar.timegm` to read it as UTC. It pads and cuts the fraction to 9 digits. It returns `0` when parsing fails.

**`_line_matches(body, level, search, trace_id)`** does in Python what LogQL did in Loki:
- The level must appear in the line, upper-cased.
- If a trace ID is given, the line must contain `trace_id":"<id>` (JSON logs) or `[trace=<first 8 chars>]` (plain logs).
- The search text must be a substring.

**`_pod_log_lines(...)`** splits log text into lines. For each line it separates the timestamp from the body, drops lines with an invalid timestamp or outside the `start_ns`..`end_ns` window, applies `_line_matches`, and reuses `_parse_log_body`. That reuse keeps the response shape the same.

**`_collect_pod_logs(...)`** talks to Kubernetes:
```
pods = core.list_namespaced_pod(namespace=ns, label_selector="jac-scale.role").items
```
- It lists pods that have the `jac-scale.role` label.
- If a service name is given, it keeps pods whose name fully matches `_service_to_pod_regex(service)`.
- For each container it calls `read_namespaced_pod_log` with `timestamps=True`, `since_seconds` computed from `start_ns`, and `tail_lines=_POD_LOG_TAIL_LINES` (5000).
- A 403 raises `ConnectionError(api_error_detail(e))`, which carries the existing "set ops_console = true" hint. Other read errors are logged as warnings and that container is skipped.
- A missing client or a failed pod list also becomes `ConnectionError`.

**`_fetch_log_lines(...)`** is the new single entry point. If `_use_pod_logs()` is true, it runs `_collect_pod_logs` in a thread (`asyncio.to_thread`, since the Kubernetes client is blocking), sorts by `ts_ns` (newest first unless `ascending`), cuts to `limit`, and returns the lines with an empty query string. Otherwise it builds the LogQL, calls `_loki_request`, and returns the flattened result plus the query.

**The two handlers** (`/admin/logs` and `/admin/logs/trace/{id}`) now call `_fetch_log_lines` instead of building and sending Loki queries themselves. The `/admin/logs` call passes `ascending=False`, and the trace endpoint uses `ascending=True`, a 500 limit and a 24-hour window. Log messages changed from "Loki query failed" to "Log query failed". The `except ConnectionError` blocks still return the 502.

### `jac/jaclang/scale/admin/ui/pages/admin/logs/LogsPage.jac`

The offline banner used to say only to enable `[scale.gateway.logs]` with the Loki stack. It now also says you can keep that off and set `[scale.kubernetes].ops_console` to true to read pod logs directly. This tells users about the new route.

## How it runs now

1. The admin opens the Logs page, which calls `/admin/logs` or `/admin/logs/trace/{id}`.
2. The handler calls `_fetch_log_lines(...)` (changed; it used to build LogQL and call Loki itself).
3. `_fetch_log_lines` calls `_use_pod_logs()` (new).
4. If true (no `LOKI_URL`, logs off, in-cluster) (new):
   1. `_collect_pod_logs` runs in a worker thread.
   2. It lists pods with the `jac-scale.role` label, filters by service name, and reads each container's log.
   3. `_pod_log_lines` parses timestamps, applies the time window and filters, and builds the line dicts.
   4. The results are sorted, cut to `limit`, and returned with `query == ""`.
5. If false, the old Loki path runs: build LogQL, call `_loki_request`, flatten the result.
6. The handler adds the `before` cursor or the services touched, and returns JSON. On `ConnectionError` (including a 403 mapped to the `ops_console` hint) it returns a 502.

## Tests

All tests are in `tests/server/test_admin_logs.jac`, which goes from 8 to 10 tests.

- **`FakePodApi`** (helper): a fake CoreV1 client. It lists one pod per entry in `logs_by_pod`, each with a container `app`, and returns the canned log text for it.
- **"logs fall back to pod logs only when Loki is unconfigured and in-cluster"**: a table of four cases over `LOKI_URL`, `logs.enabled` and in-cluster status. It patches the environment, `get_scale_config` and `k8s_available`. Only "no Loki URL, logs off, in-cluster" gives true. This proves the backend selection in `_use_pod_logs`.
- **"pod log fallback applies the service, level, search, trace and before filters"**: two pods (`gateway-deployment-abc-1` and `builder-sv-deployment-def-1`, the latter a fleet name via a patched `_fleet_names`). It runs `_fetch_log_lines` on the pod path for seven cases:
  - no filter, which checks newest-first order,
  - service,
  - level,
  - search,
  - trace ID, which matches both the JSON and the `[trace=...]` forms,
  - a `before`-style end time,
  - `limit=1`.

  It also checks that `query == ""`, that the first line has the right `pod` and `ts_ns`, and that a 403 `ApiException` from `list_namespaced_pod` makes `_collect_pod_logs` raise `ConnectionError` containing `ops_console = true`.

Both tests run in-process with no cluster. The existing handler logic is still covered only by the real-cluster e2e script, as the file's docstring says.

## Explaining it in one minute

"With logs turned off in config, the admin Logs page always failed with a 502, because both log endpoints only queried Loki and Loki wasn't deployed. I added a fallback. When `LOKI_URL` is unset, logs are off, and we're in-cluster, a new `_fetch_log_lines` reads the app's pods through the Kubernetes API. It selects them by the `jac-scale.role` label and reads up to 5000 recent lines per container. It applies the service, level, search, trace and `before` filters in Python and reuses `_parse_log_body`, so the response shape doesn't change. No new RBAC is needed, because the ops console Role already allows listing pods and reading their logs. If it's missing, the 502 tells the user to set `ops_console = true`, and the banner says the same. I added two table-driven tests with a fake CoreV1 client for backend selection, each filter, ordering, limit, the cursor and the 403 mapping. Pod logs only cover each container's current log, which fits the 'recent lines' request."
