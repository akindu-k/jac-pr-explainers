# feat(scale): the admin Logs page reads pod logs when Loki is not deployed (#9673)

## In short

The admin Logs page only knew how to read logs from Loki. If Loki was not deployed, you got `502 Log backend unavailable`. Your PR adds a fallback. When Loki is not configured and the gateway runs inside the cluster, the two log endpoints read the app's pod logs directly from the Kubernetes API and filter them in Python, returning the same response shape as before.

## Words to know

- **jac-scale**: the Jac plugin that deploys Jac apps to Kubernetes. Its code lives under `jac/jaclang/scale/`.
- **Kubernetes / pod / container**: Kubernetes runs your app. A *pod* is one running instance of a service. It holds one or more *containers*, and each container writes its own log.
- **Deployment**: a Kubernetes object that keeps a set of identical pods running. Every jac-scale gateway and fleet Deployment puts a `jac-scale.role` label on its pods.
- **Label selector**: a filter for listing Kubernetes objects by label. `label_selector="jac-scale.role"` means "pods that have this label, whatever its value".
- **Gateway**: the jac-scale front service that serves the admin API (`/admin/...`), including the log endpoints.
- **Fleet**: the other app services jac-scale deploys next to the gateway (for example `builder-sv` in the test).
- **Loki**: a log storage and search system. **Alloy** is the agent that ships pod logs into Loki. Together they are the "Loki + Alloy stack", switched on by `[scale.gateway.logs] enabled = true`.
- **LogQL**: Loki's query language. `_build_logql` builds this query from the page's filters.
- **`LOKI_URL`**: environment variable that points the gateway at a Loki server.
- **CoreV1 API / `core_api()`**: the Python Kubernetes client object for core resources like pods. `list_namespaced_pod` lists pods. `read_namespaced_pod_log` returns a container's log text.
- **Kubelet**: the Kubernetes agent on each node. It stores container logs and, with `timestamps=True`, puts an RFC3339 timestamp in front of each line.
- **RFC3339Nano**: a timestamp format like `2026-10-03T00:00:01.000000001Z`, with up to 9 digits of fractional seconds. `Z` means UTC.
- **Epoch nanoseconds**: time counted as nanoseconds since 1970-01-01 UTC. The log API uses this for `ts_ns`, `start_ns` and `end_ns`.
- **RBAC / Role**: Kubernetes permissions. A Role lists what an account may do, for example "list pods" or "get pods/log".
- **Ops console / `OPS_READ_RULES`**: an existing jac-scale feature, turned on by `[scale.kubernetes].ops_console = true`. Its Role already allows listing pods and reading `pods/log`.
- **403**: the HTTP status for "forbidden". Here it means the RBAC rules do not allow the call.
- **502**: the HTTP status for "bad gateway". The log endpoints return it when the log backend can't be reached.
- **`before` cursor**: pagination for the log list. The response gives the timestamp of the oldest line returned (`next_before`). The next page asks for lines older than that.
- **Trace ID**: an ID that ties together all log lines from one request. `/admin/logs/trace/{id}` shows all lines for one trace.
- **`asyncio.to_thread`**: runs a blocking function in a worker thread, so the async web server is not frozen while it waits on network calls.
- **Table-driven test**: one test that loops over a list of (input, expected) rows.

## The problem

Before this PR:

1. An operator deploys an app with `[scale.gateway.logs] enabled = false`, so there is no Loki.
2. They open the admin Logs page. The page calls `/admin/logs` (or `/admin/logs/trace/{id}` for the trace view).
3. Both handlers always built a LogQL query and sent it to Loki with `_loki_request`.
4. With no Loki, the request failed with a `ConnectionError`, and the handler answered `502 Log backend unavailable`.

Nothing in `scale/` could read pod logs any other way. So anyone running without Loki had a Logs page that never showed anything, even though the logs existed in the pods. Issue #9673 asked for recent lines in that case.

## The changes, one by one

### `jac/jaclang/scale/admin/impl/logs.impl.jac`: the pod-log fallback

This is the core of the PR. You added six helpers and routed both endpoints through one of them.

**New imports.** You import `asyncio` and `calendar`, plus five helpers from `jaclang.scale.admin.k8s_ops`: `core_api`, `ops_namespace`, `k8s_available`, `api_error_detail`, `unavailable_detail`. These already exist for the ops console, so you reuse its Kubernetes client and error messages. You also added a constant `_POD_LOG_TAIL_LINES = 5000`.

**`_use_pod_logs()`: picks the backend.**

```jac
if os.getenv("LOKI_URL", "").strip() {
    return False;
}
try {
    logs_cfg = get_scale_config().get_gateway_config().get("logs") or {};
} except Exception {
    logs_cfg = {};
}
return not bool(logs_cfg.get("enabled", False)) and k8s_available();
```

- If `LOKI_URL` is set (and not just spaces), use Loki.
- Read the `[scale.gateway.logs]` config. If reading the config fails, treat it as empty.
- Use pod logs only if logs are not enabled **and** `k8s_available()` says we are in a cluster.

Why: the fallback should only kick in when Loki is truly absent. Loki setups and off-cluster runs keep their old behavior.

**`_rfc3339_to_ns(stamp)`: parses kubelet timestamps.**

```jac
(head, _, frac) = stamp.rstrip("Z").partition(".");
secs = calendar.timegm(time.strptime(head, "%Y-%m-%dT%H:%M:%S"));
return secs * 1_000_000_000 + int((frac + "000000000")[:9]);
```

- Drop the trailing `Z` and split into the seconds part and the fraction.
- `calendar.timegm` turns the seconds part into epoch seconds as UTC. Plain `time.mktime` would use local time.
- Pad the fraction to 9 digits and cut to 9, so `.5` becomes 500000000 ns and a missing fraction becomes 0.
- If parsing fails, return `0`. The caller treats `0` as "no valid timestamp".

Why: the existing code and the `before` cursor work in epoch nanoseconds, the same as Loki. Pod lines must use the same unit.

Note: it only handles a `Z` (UTC) suffix. Kubelet writes `Z`, so this matches what the API returns.

**`_line_matches(body, level, search, trace_id)`: the in-process filters.**

```jac
if level and level.upper() not in body { return False; }
if trace_id
    and f'trace_id":"{trace_id}' not in body
    and f"[trace={trace_id[:8]}]" not in body { return False; }
return not search or search in body;
```

- Level: the upper-cased level (for example `ERROR`) must appear somewhere in the line.
- Trace: the line must hold either the JSON field `trace_id":"<full id>` or the short text prefix `[trace=<first 8 chars>]`. These are the two formats the app writes; `_TRACE_PREFIX_RE` already parses the second one.
- Search: plain case-sensitive substring.

Why: with no Loki, nothing runs LogQL, so the same filters are redone in Python. The docstring calls them "the LogQL level, trace and search filters". The level check is a substring test, so it is looser than a parsed level. A line that only *mentions* "ERROR" in its message would match an `error` filter. `_build_logql` is not in the diff, so I can't say exactly how close the two are. Your senior may ask about this.

**`_pod_log_lines(text, labels, start_ns, end_ns, level, search, trace_id)`: turns raw text into log entries.**

For each line, it splits off the timestamp at the first space and converts it with `_rfc3339_to_ns`. It keeps the line only if:

- the timestamp is valid (non-zero),
- `start_ns <= ts <= end_ns`, and
- `_line_matches` passes.

Kept lines go through the existing `_parse_log_body(body, labels, str(ts_ns))`. That function is reused, so each entry has the same fields as a Loki entry. Here, `labels` is `{"pod": ..., "container": ...}`.

**`_collect_pod_logs(service, level, search, trace_id, start_ns, end_ns)`: talks to Kubernetes.**

1. Get `core_api()`. If it is `None`, raise `ConnectionError(unavailable_detail())`.
2. Get the namespace from `ops_namespace()`.
3. If a service is chosen, build a regex with the existing `_service_to_pod_regex(service)`. This is the same regex the Loki path uses to match pod names.
4. Compute `since_s`, the seconds from `start_ns` until now, plus 1 and at least 1. Kubernetes then only sends lines from that window.
5. List pods with `label_selector="jac-scale.role"`. Any error here becomes a `ConnectionError(api_error_detail(e))`.
6. For each pod whose name fully matches the regex (or every pod if no service was given), and each container in it:
   - call `read_namespaced_pod_log(..., timestamps=True, since_seconds=since_s, tail_lines=5000)`;
   - on a **403**, raise `ConnectionError(api_error_detail(e))`, because missing permissions affect every pod;
   - on any other error, log a warning and skip that container, so one bad pod doesn't break the page;
   - otherwise, add the parsed lines from `_pod_log_lines`.

The error messages from `api_error_detail` / `unavailable_detail` are the existing ops-console ones. The test shows the 403 message contains "set ops_console = true". So a missing permission tells the operator exactly what to switch on.

`e?.status` is Jac's null-safe attribute access. It gives `None` instead of crashing if the exception has no `status`.

**`_fetch_log_lines(...)`: the single entry point for both endpoints.**

```jac
if _use_pod_logs() {
    lines = await asyncio.to_thread(
        _collect_pod_logs, service, level, search, trace_id, start_ns, end_ns
    );
    lines.sort(key=lambda (line) { int(line["ts_ns"]); }, reverse=not ascending);
    return (lines[:limit], "");
}
logql = _build_logql(_app_namespace(), service, level, search, trace_id);
payload = await _loki_request("/loki/api/v1/query_range", {... "direction": "forward" if ascending else "backward"});
return (_flatten_loki_response(payload, ascending=ascending), logql);
```

- Pod path: run the blocking Kubernetes calls in a thread. Lines come from many pods in no set order, so sort them all by timestamp (newest first unless `ascending`). Then cut to `limit` and return `""` as the query text.
- Loki path: the same request the handlers used to make inline. `direction` now comes from `ascending` instead of being hard-coded.
- It returns `(lines, query)` so the handler can still fill in the `query` field of its response.

**Handler changes.** In `/admin/logs` and `/admin/logs/trace/{id}`, the inline `_build_logql` + `_loki_request` + `_flatten_loki_response` code is replaced with one call:

- `/admin/logs`: `_fetch_log_lines(service, level, search, trace, start_ns, end_ns, limit, False)`, newest first, as before ("backward").
- trace view: `_fetch_log_lines("", "", "", trace_id, start_ns, now_ns, 500, True)`, oldest first over the last 24 hours with a cap of 500, the same values as before.

The warning messages changed from "Loki query failed" to "Log query failed", since the failure may now come from Kubernetes. The 502 response itself is unchanged. The pagination code (`next_before = lines[-1].get("ts_ns")` when the page is full) still runs on whatever lines come back, so the `before` cursor works on both paths.

One thing to know before your review: the pod path filters with `ts <= end_ns` (inclusive). The code that turns `before` into `end_ns` is not in the diff. So I can't tell whether a line exactly at the cursor timestamp could show up on two pages. You may want to check that.

## How it runs now

1. A user opens the admin Logs page, or a trace. The UI calls `/admin/logs` or `/admin/logs/trace/{id}` on the gateway.
2. The handler checks the request and works out `start_ns`, `end_ns` and `limit`, as before.
3. (changed) The handler calls `_fetch_log_lines(...)` instead of calling Loki itself.
4. (new) `_fetch_log_lines` calls `_use_pod_logs()`:
   - `LOKI_URL` is set, or `[scale.gateway.logs].enabled` is true, or the gateway is not in a cluster → **Loki path** (step 5).
   - Otherwise → **pod path** (step 6).
5. Loki path (unchanged logic, moved): `_build_logql` → `_loki_request("/loki/api/v1/query_range", ...)` → `_flatten_loki_response`. It returns the lines and the LogQL string.
6. (new) Pod path: `asyncio.to_thread(_collect_pod_logs, ...)`:
   1. `core_api()` and `ops_namespace()`.
   2. `list_namespaced_pod(label_selector="jac-scale.role")`.
   3. Keep the pods matching `_service_to_pod_regex(service)`, if a service was given.
   4. For each container: `read_namespaced_pod_log(timestamps=True, since_seconds=..., tail_lines=5000)`.
   5. `_pod_log_lines` parses each timestamp (`_rfc3339_to_ns`), keeps lines in the time window that pass `_line_matches`, and builds entries with `_parse_log_body`.
   6. Back in `_fetch_log_lines`: sort by `ts_ns`, cut to `limit`, return with an empty query.
7. If either path raises `ConnectionError`, the handler returns 502 "Log backend unavailable". (changed) On the pod path, the detail is the ops-console message, for example the "set ops_console = true" hint on a 403.
8. Otherwise the handler builds the response as before: `next_before` for paging in `/admin/logs`, `services_touched` for the trace view.

## Tests

All in `jac/jaclang/scale/tests/server/test_admin_logs.jac`. The test count goes from 8 to 10. You added a small fake, `FakePodApi`. It takes a dict of pod name → log text. `list_namespaced_pod` returns one pod per key, each with a single container `"app"`. `read_namespaced_pod_log` returns that pod's text.

**"logs fall back to pod logs only when Loki is unconfigured and in-cluster"**

A table of four cases. Each one patches `LOKI_URL`, the gateway config (`logs.enabled`) and `k8s_available`, then calls `_use_pod_logs()`:

| `LOKI_URL` | logs enabled | in cluster | pod logs? |
|---|---|---|---|
| empty | no | yes | **yes** |
| empty | yes | yes | no |
| `http://loki:3100` | no | yes | no |
| empty | no | no | no |

It proves the backend choice: the fallback is used only in the one intended situation. Loki setups and off-cluster runs are left alone.

**"pod log fallback applies the service, level, search, trace and before filters"**

Setup: two pods.

- `gateway-deployment-abc-1` has a JSON ERROR line at `00:00:01.000000001` (with a `trace_id` field and msg `boom`) and a text line `[trace=abc12345] INFO hello` at `00:00:02`.
- `builder-sv-deployment-def-1` has `INFO built` at `00:00:03`.

`_use_pod_logs`, `_fleet_names` (returns `["builder-sv"]`), `core_api` (returns the fake) and `ops_namespace` are patched. Each row then runs `_fetch_log_lines(..., start_ns=0, end_ns, limit, ascending=False)` and checks the `msg` list:

- No filters → all three lines, newest first. This proves the merge across pods and the sort.
- `service="gateway"` → only the gateway pod's two lines. Proves the service filter.
- `level="error"` → `boom`. Proves the level filter, including lower-case input.
- `search="hello"` → the hello line. Proves the search filter.
- `trace="abc12345-0000"` → both gateway lines. Proves both trace formats: the full JSON `trace_id` and the 8-character `[trace=...]` prefix.
- `end_ns` = `00:00:02` → the builder line at `:03` is dropped. Proves the time window, which is how the `before` cursor is applied.
- `limit=1` → only `INFO built`, the newest. Proves sort-then-cut.

Every row also checks that the returned query is `""`. After the loop, it checks that the last result's entry has `pod == "builder-sv-deployment-def-1"` and `ts_ns == "1790985603000000000"`. This proves the labels are attached and that the timestamp became epoch nanoseconds, as a string.

Last, it patches `core_api` with a mock whose `list_namespaced_pod` raises `ApiException(status=403)`. It checks that `_collect_pod_logs` raises a `ConnectionError` whose message has "ops_console = true". This proves the RBAC-denied case gives the helpful hint.

These are in-process unit tests with fakes. They do not hit a real cluster. The handler bodies themselves are still covered only by the real-cluster e2e script mentioned in the test file's docstring. The diff does not show any change to that script.

## Explaining it in one minute

"When an app ran without Loki, the admin Logs page always returned a 502, because the log endpoints could only query Loki. I added `_fetch_log_lines`, which both `/admin/logs` and the trace endpoint now call. If `LOKI_URL` is unset, logs are off in config, and we're in-cluster, it lists the app's pods by the `jac-scale.role` label and reads each container's recent log through the Kubernetes API, at most 5000 lines per container. It runs that in a thread so the event loop isn't blocked. Then it applies the same service, level, search, trace and time filters in Python, and sorts and limits the merged lines. It reuses `_parse_log_body`, so the response shape doesn't change. No new RBAC: the existing ops console Role already allows listing pods and reading pod logs. A 403 turns into a 502 telling you to set `ops_console = true`, and the UI banner now mentions that option. Loki and off-cluster behavior is unchanged. I added two table-driven tests: one for when the fallback is chosen, and one that runs the pod path against a fake Kubernetes client to check each filter, the ordering, the limit, the cursor window and the 403 message."
