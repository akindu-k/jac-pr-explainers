## 1. The short version

`test_user_isolation` is a test in `jac-scale/jac_scale/tests/test_serve.py`. It registers two users on a running jac-scale server, then checks that each user's data stays separate from the other's. **The PR title says that registering the two users back to back causes a "race condition".** The PR does not say what the failure looked like: there is no error message, no linked issue and no failing CI log.

**Your fix adds one line, `time.sleep(5)`, between the first and the second `/user/register` call.** That waits five seconds before the second registration, so the two requests never come close together in time. No production code changes.

Both @ThakeeNathees and @marsninja disagree with this approach. A delay in the test (the client) hides the problem instead of fixing the server, and jac-scale is supposed to handle hundreds of concurrent requests per second. @marsninja asked which database is responsible.

**Status:** Changes requested by @ThakeeNathees on 2026-01-03. @marsninja agreed on 2026-01-09. The PR is now **closed**. The data does not show a merge, and the objections were never answered, so treat it as closed without merging. All six CI checks passed on the head commit `eaca6dd`.

## 3. The problem, step by step

### 3.1 The setup

- A jac-scale server running during the test.
- A storage layer behind it that holds users. The PR does not say which database this is, and @marsninja asked exactly that.
- `test_user_isolation`, which sends two `/user/register` requests one right after the other, then runs isolation checks.

### 3.2 What went wrong

The PR gives no failure output, so this is the scenario the title implies, not a confirmed trace:

```text
1. Test sends POST /user/register {username1, "pass1"}
2. Server starts creating user1 (writes to its user store / database)
3. Test immediately sends POST /user/register {username2, ...}
4. Server handles user2 while user1's work may not be finished      ← WRONG (suspected)
5. Some shared state clashes (unknown which: ID, file, DB write, session)
6. user2 registration or a later isolation check fails, but only sometimes
```

What the PR does not tell us:
- the actual error or assertion that failed;
- how often it failed;
- which component, such as the database, has the race.

### 3.3 Why it mattered

- An intermittently failing test makes CI unreliable. That is the cost you were trying to remove.
- The reviewers point to a larger cost. If two registrations about 0 seconds apart can break the server, then real traffic will break it too. @ThakeeNathees: "Jac scale supposed to be stress tested with 100s of concurrent requests per second."

## 4. The idea of the fix (one sentence)

> **Space out the two registrations.** Wait five seconds after creating the first user so the second request cannot overlap with it.

This makes the test stop hitting the timing window. It does not remove the window. That is why the reviewers argue it is not the right fix: the race stays in the server and is only hidden from this test.
