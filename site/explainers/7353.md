## 1. The short version

The test file `test_topology_slice_pushdown.jac` checks a performance property of jac-scale. When Jac code slices an edge reference, such as `[edge -->][0:50]`, the slice bound should be "pushed down" to the database. Only about 50 nodes should be loaded from MongoDB, not the whole neighbourhood of 120 nodes. The test had been moved to `tests/quarantine/` (disabled) in PR #6850 because it was failing.

Issue #6865 suspected one of two causes: a real push-down regression, or a threshold (`fetch_count <= 60`) that was too tight. **You found it was neither: the test never reached that assertion, because the system root was never saved to MongoDB.** The test made an `ExecutionContext()`, whose root lives in the default memory, and then swapped `ctx.mem` to a Mongo/Redis `ScaleTieredMemory`. The commit therefore saved the 120 nodes and 120 edges but not the root. The second context then failed at `assert root_anchor is not None`.

**You fixed the test harness only: the root is now registered with the tiered memory (`mem.put(ctx.system_root)`), so it is saved and reloads.** You also:
- flush Redis before the MongoDB assertion, so `fetch_count` measures real database load;
- moved repeated setup into helpers;
- close contexts in `finally`;
- moved the file to `tests/data/`.

No production code changed. You measured `fetch_count = 50` against the `<= 60` limit, so push-down works and the threshold stays as it was.

**Status:** Merged on 2026-07-14. All relevant CI checks passed. The only review was an automated Greptile summary. No human review is visible in the data.

## 3. The problem, step by step

### 3.1 The setup

The file has two tests. Both follow the same shape:

1. Context 1 builds a graph: root → 100 `_PushdownLead` nodes plus 20 `_PushdownOther` nodes. It commits, then closes.
2. Context 2 starts with a fresh memory, loads the root by id, runs a sliced traversal `[0:50]`, and checks a counter:
   - Test A ("bounds mongodb fetches"): `mongo2.fetch_count <= 60`.
   - Test B ("bounds redis cache promotions"): a bound on `redis2.put_count`. The exact limit is in lines the diff does not show.

### 3.2 What went wrong (both tests)

```text
1. ctx1 = ExecutionContext()            → ctx1.system_root created in DEFAULT memory
2. ctx1.mem = mem1 (ScaleTieredMemory)  → root still only known to default memory   ✗ WRONG
3. root ++> 120 nodes                   → nodes + edges registered in mem1
4. ctx1.mem.commit()                    → Mongo gets 120 nodes + 120 edges, NO root, NO topology index
5. ctx1.close()
6. ctx2 = ExecutionContext(); ctx2.mem = mem2
7. ctx2.mem.get(root_id)                → None (root never stored)
8. assert root_anchor is not None       → FAILS; slice assertion never reached
```

### 3.3 A hidden weakness in test A (Mongo)

Test B already ran `flushall()` before loading. Test A did not:

```text
4. commit                               → items also written to Redis (L2)
7. ctx2 loads root and slices [0:50]    → Redis serves the items; Mongo barely asked
8. fetch_count ≈ 0                      → passes even if push-down were broken   ✗ WEAK
```

Your description says that with the flush, a regression would show as 120 fetches instead of 0.

### 3.4 Why it mattered

- The test was disabled, so nothing in CI guarded slice push-down. A regression would have caused silent full-neighbourhood loads from MongoDB.
- Issue #6865 (child of tracker #6853) worried there might be a real performance bug. The harness bug made it impossible to tell.

## 4. The idea of the fix (one sentence)

> **Register the root with the memory that actually commits.** After swapping `ctx.mem`, call `mem.put(ctx.system_root)` so the root and its topology index are saved and can be reloaded.

This fixes the cause, the orphaned root, instead of loosening the threshold. The real measurement (50 fetches) showed the product code was already correct.

### 5.1 `jac/jaclang/scale/tests/data/test_topology_slice_pushdown.jac`: new helpers

```diff
+import from typing { cast }

+def _bind_scale_memory(ctx: ExecutionContext, persist_root: bool) -> tuple {
+    (mem, mongo, redis_be) = _make_scale_memory();
+    ctx.mem = mem;
+    if persist_root {
+        mem.put(ctx.system_root);      # NEW: root now saved on commit
+    }
+    JacRuntime.set_context(ctx);

+}
+
+def _seed_pushdown_graph {
+    for i in range(100) { root ++> _PushdownLead(idx=i); }
+    for i in range(20)  { root ++> _PushdownOther(idx=i); }
+}
+
+def _close_ctx(ctx: (ExecutionContext | None)) {
+    if ctx is not None { cast(ExecutionContext, ctx).close(); }
+}
```

**What:**
- `_bind_scale_memory` does the memory swap and can optionally register the root.
- `_seed_pushdown_graph` builds the 120-node graph.
- `_close_ctx` safely closes a context that may be `None`.

**Why:** `mem.put(ctx.system_root)` is the actual bug fix. The other two helpers remove copy-paste between the two tests.

**Things to notice:**
- `persist_root=True` is used only for the writing context. The reading context (`persist_root=False`) loads the root from Mongo by id. It does not need its own fresh root saved.
- The helper returns only the backends, not `mem`. The tests reach memory through `ctx.mem`.
- `cast` is only there for the type checker. It narrows `ExecutionContext | None` after the `None` check.

## 11. Questions your senior might ask

**Q: Was there a real push-down bug?**
No. With the root saved and Redis flushed, `fetch_count = 50` for `[0:50]`, against 120 for the full neighbourhood. The query log shows `slc=0:50`.

**Q: Why didn't you change the `<= 60` threshold?**
The measured value is 50, which is under 60 with some margin. A regression would give about 120, so the bound still catches it.

**Q: Why `persist_root=True` only for ctx1?**
Only ctx1 writes the graph. ctx2 loads the saved root by `root_id` from Mongo, so its own new root does not need saving.

**Q: Why flush Redis in the Mongo test?**
Without the flush, Redis served the items and Mongo saw almost no fetches. A push-down regression would have passed unnoticed.

**Q: Is this a product bug? Should `ExecutionContext` handle a swapped `mem`?**
The PR treats it as a test-harness bug. Whether production code ever swaps `ctx.mem` like this can't be told from the diff. That would be worth checking separately.

**Q: Why `ctx1 = None` after `close()`?**
It stops `finally` from closing ctx1 a second time.

**Q: Why `cast` in `_close_ctx`?**
It is for the type checker only, to narrow `ExecutionContext | None`. It has no runtime effect.

**Q: How did you verify it?**
You ran it against live MongoDB and Redis using testcontainers (`2 passed`), and CI's `test-scale (data)` passed.
