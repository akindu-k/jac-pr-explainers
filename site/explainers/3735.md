## 1. The short version

`jac-scale` keeps a Jac app's graph data (nodes, edges, users) in a stack of stores called the **memory hierarchy**: an in-process memory first, then Redis as a cache, then MongoDB as the database, with a local "shelf" file as a fallback. The class that routes every read and write through this stack is `MultiHierarchyMemory`.

**Before this PR, the routing depended only on whether Redis answered a ping. MongoDB was never checked.** With Redis down, MongoDB was ignored completely and everything went to the shelf file, even if MongoDB was running. With Redis up and MongoDB unreachable, writes went to Redis and then failed inside pymongo. Two other problems:

- Deleting an anchor while Redis was down called `self.shelf.commit(anchor)`, which **saves** the anchor instead of removing it.
- The default config pointed at `mongodb://root:rootpassword123@localhost:27017/`, so a password was hardcoded in the defaults.

**You now check Redis and MongoDB once at startup, make MongoDB (or the shelf, if both are down) the only place writes are stored, and let Redis fill up only when data is read ("read-through" instead of "write-through").** You also:

- split the 442-line impl file into four files, one per store;
- added `mongo_is_available()`;
- removed the hardcoded URLs so they come from `MONGODB_URI` / `REDIS_URL` or the config file;
- added one end-to-end test that runs `jac serve` against real Redis and MongoDB containers.

**Status:** Merged on 2026-01-05. @marsninja approved on 2025-12-26 without comments. All five CI checks passed on head commit `a4e59d7`.

## 3. The problem, step by step

This is mainly a feature (first-class MongoDB support plus a caching change). The old code also had real routing bugs. Both are covered below.

### 3.1 The setup

- `MultiHierarchyMemory` owns four stores: `mem` (in-process), `redis` (`RedisDB`), `mongo` (`MongoDB`) and `shelf` (`ShelfDB`).
- Store URLs came from `get_database_config()`. The defaults pointed at local servers with hardcoded passwords:
  - `mongodb://root:rootpassword123@localhost:27017/`
  - `redis://:mypassword123@localhost:6379/0`
- In the old code, every `commit`, `sync`, `delete` and `find_by_id` started by calling `self.redis.redis_is_available()`, which pinged Redis. That one answer decided everything:

```text
Redis up    → use Redis + MongoDB
Redis down  → use shelf only
```

- The shelf was only created in `init` if Redis was down at startup.

### 3.2 What went wrong

#### Case A: MongoDB is running, Redis is not

```text
1. init: redis_is_available() → False
2. init: shelf = ShelfDB()                     # MongoDB is never checked
3. User creates a Task → commit(task_anchor)
4. commit: redis_is_available() → False
5. commit: shelf.set(task_anchor)              ← WRONG: MongoDB is up but unused
6. State: MongoDB empty, anchor_store.db has the Task
7. Another pod (Kubernetes) with its own shelf file cannot see the Task
```

#### Case B: Redis is running, MongoDB is not reachable

```text
1. init: redis_is_available() → True ; shelf not created
2. commit(task_anchor)
3. redis.set(task_anchor)                      # Redis now has the Task
4. mongo.set(task_anchor) → collection.find_one(...)
5. pymongo cannot reach a server → raises      ← WRONG: no fallback, error escapes
6. State: Task only in Redis (a cache), nowhere durable
```

#### Case C: Deleting while Redis is down

```text
1. Task anchor T is in the gc set (marked for deletion)
2. commit() → delete(T)
3. delete: mem.remove(T.id)
4. delete: redis_is_available() → False
5. delete: shelf.commit(T)                      ← WRONG: commit() calls set(); T is SAVED again
6. State: T is still in anchor_store.db and comes back on the next load
```

#### Case D: Write-through filled Redis with everything

```text
1. Both servers up. CreateTask runs; anchors = {root, task node, edge}
2. sync(): redis.commit(keys=anchors) → redis.set() for every anchor
3. sync(): mongo.commit(keys=anchors)
4. State: Redis holds a full copy of every anchor ever written,
   whether or not anyone reads it                ← cache used as a second database
5. Every operation also paid an extra network ping to Redis (step 0 of each call)
```

### 3.3 Why it mattered

There is no linked issue and no review discussion, so the impact here is inferred from the PR description and the code.

- The description's goal is to make MongoDB "a first-class backend" and the system of record. Case A shows that the old code could not use MongoDB without Redis.
- Case C is silent data resurrection in shelf mode.
- Case D wastes Redis memory and makes Redis look like a store of record.
- The hardcoded credentials in defaults are a security smell. A deployment that forgot to configure URLs would quietly try `localhost` with those passwords.

---

## 4. The idea of the fix (one sentence)

> **Decide once which stores exist, store data only in MongoDB (or the shelf), and use Redis as a read cache.**
> At startup you ping Redis and MongoDB separately. Writes go to MongoDB (shelf if both are down). Redis only receives an anchor when it was read from MongoDB, and is updated later only if that key is already cached.

This matches the usual cache-aside pattern: losing Redis never loses data, and Redis only holds what is actually read. Checking MongoDB on its own makes it usable without Redis.

**What:**
- The availability of each store is computed once and saved in two flags.
- MongoDB is used whenever it is up, regardless of Redis.

- Deletes now really delete from the shelf.
- `close` releases the MongoDB client and the shelf file.

**Why:** This fixes cases A, C and D from section 3. It also removes the per-call Redis ping.

**Things to notice:**
- **`delete` vs `remove` mismatch.** You renamed the method to `remove` in both the declaration and the impl, but `commit` still calls `self.delete(anchor)` in two places. The diff does not show whether the base `Memory` class defines a `delete`. If it does not, this raises `AttributeError`, and the new `except Exception { }` swallows it. Garbage-collected anchors would then never be deleted from Redis, MongoDB or the shelf. This matches the TODO in the new test: *"delete method in jac serve is not working as expected"*.
- **Redis up + MongoDB down now stores nothing durable.** The shelf is only created when *both* are down. With `redis_available=True, mongo_available=False`:
  - `commit(anchor)` does nothing;
  - `sync` only refreshes keys that are already cached;
  - `find_by_id` can only hit Redis.

  The description says MongoDB "and shelf storage" remain the system of record, but in this case there is none. A condition of `not self.mongo_available` would match the stated design.
- **Flags never change after startup.** The old per-call ping could switch to the shelf at runtime. Now, if MongoDB goes away after startup, writes raise inside `commit`/`sync`, get swallowed, and are lost with no log line.
- **Errors are silent.** `commit` and `sync` use bare `except Exception { }`. That hides real problems: serialization failures, auth errors, and the `delete` issue above.
- **Single-anchor commit skips Redis.** `commit(anchor)` updates MongoDB but not Redis. If that anchor was cached, Redis keeps the old version until a later bulk `sync` refreshes it, and `find_by_id` checks Redis before MongoDB. The bulk path does refresh cached keys.
- `remove` no longer sits behind a Redis check, so a MongoDB-only setup deletes correctly.

| Scenario | Before | After |
|---|---|---|
| Redis up, MongoDB up | Writes to Redis **and** MongoDB; reads Redis → MongoDB | Writes to MongoDB; Redis refreshed only for cached keys; reads Redis → MongoDB, which fills Redis |
| Redis down, MongoDB up | Shelf only; MongoDB ignored | MongoDB is the store |
| Redis up, MongoDB down | Redis write, then pymongo error | Nothing durable: no shelf, no Mongo writes; errors swallowed |

| No config at all | Tried the hardcoded localhost URLs with passwords | URLs are `None` → shelf |
| Delete with no Redis | Anchor was **re-saved** to the shelf | Removed from MongoDB or the shelf (if `remove` is reached; see 5.2) |
| A server dies after startup | Per-call Redis ping could switch to the shelf | Flags fixed; failures silently dropped |

**Behaviour changes users will notice:**
1. Local setups that relied on the default localhost URLs now use the shelf unless `MONGODB_URI` / `REDIS_URL` are set.
2. Redis only holds data that has been read.
3. MongoDB works without Redis.

## 11. Questions your senior might ask

**Q: Why switch from write-through to read-through?**
So Redis is only a cache. Losing Redis never loses data, and Redis only holds anchors someone actually read. MongoDB, or the shelf, is the single place data is stored.

**Q: How is the cache kept fresh if writes don't go to Redis?**
In bulk `sync`, `RedisDB.commit` overwrites keys that already exist (`redis_key_exists`). Single-anchor `commit(anchor)` does not touch Redis, so a cached copy can be stale until the next bulk sync.

**Q: What if Redis is up but MongoDB isn't?**
The shelf is not created, so nothing durable is stored and failures are swallowed. That is a gap against the stated design.

**Q: What if MongoDB goes down after startup?**
The availability flags are set once in `init`. Later failures raise inside `commit`/`sync`, are caught by `except Exception { }`, and are dropped silently.

**Q: Does delete work now?**
The shelf path no longer re-saves deleted anchors, which was a real fix. But `commit` still calls `self.delete`, which is no longer declared on `MultiHierarchyMemory`. The test file admits delete is broken and defers it.

**Q: How long can startup block on a wrong `MONGODB_URI`?**
`maxTimeMS=100` only limits server-side execution. The connect wait is `serverSelectionTimeoutMS`, which is left at pymongo's default. A 5 s value was added in `c40e0c8` and reverted in `7659698`.

**Q: Will existing users see a difference?**
Yes. The hardcoded localhost URLs are gone. Without `MONGODB_URI` / `REDIS_URL` or config values, `jac-scale` now uses the shelf.

**Q: What does the test actually prove?**
With both containers running:
- users and tasks are written to MongoDB (2 → 3 → 7 docs);
- reading tasks fills Redis with exactly the 5 node anchors.

It does not test fallback or delete. Its "Redis unchanged after writes" check measures before the writes happen.

**Q: Why split the impl file into four?**
One file per backend (main, mongo, redis, shelf) keeps each store's logic separate. Most of the MongoDB and shelf code moved over unchanged, so you can review the real changes per file.
