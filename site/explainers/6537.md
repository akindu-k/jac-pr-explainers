## 1. The short version

`MongoBackend.sync()` in jac-scale takes the graph objects that changed in memory during a request and writes them to MongoDB. When you run `root ++> Node()`, one sync has to write three documents: the new node, the new edge, and the source node's updated edge list. These are three separate writes, not one transaction.

**Before this PR, `sync()` wrote objects in the order they were registered in memory. That order always put the new target node last, so a process killed between the edge write and the node write left an edge pointing at a node that never existed.** Every later traversal across that edge failed with `ValueError: NodeAnchor [<uuid>] is not a valid reference!`. Issue #6488 traced this to real production data. Rolling deploys, OOM kills and pod evictions can all kill a process at that moment.

**You changed `sync()` to sort pending writes into four buckets and flush them in dependency order: node documents, then edge documents, then edge-list updates on existing nodes, then plain field updates.** After this change, a crash can at worst leave an orphan node that nothing points to. It can no longer leave a dangling edge. You chose not to use Mongo transactions because they need a replica set and many deployments run a standalone Mongo.

**Status:** Merged on 2026-06-09. All test checks on head `12ed0c7` passed. Release and publish jobs were skipped. The only review was from the Greptile bot, and both of its inline points were handled in later commits.

## 3. The problem, step by step

### 3.1 The setup

- The request runs `root ++> Item()`.
- `JacBasics.save` puts anchors into `_mem_ref`. `Root` was already loaded at request start, so it comes first. Then the edge, then the new target node (from issue #6488, `runtime.impl.jac` around L1353–1376).
- At the end of the request, `MongoBackend.sync()` loops over `_mem_ref` in that order. Before this PR it wrote each anchor immediately.

### 3.2 What went wrong

```text
1. _mem_ref order: [Root, Edge E (Root -> X), Node X]     # insertion order
2. sync(): Root has edge_delta added=[E]
   -> _put_node_atomic($setUnion)                         # DB: Root.data.edges = [..., E]
3. sync(): E has hash==0
   -> _write_to_db(E)                                     # DB: E {source: Root, target: X}
4. *** process SIGKILLed here (~1 ms window) ***          # <-- WRONG: X not yet written
5. (never runs) _write_to_db(X)
6. Later request: [root -->]
   -> Root.data.edges has E -> load E -> load target X -> not found
   -> ValueError: NodeAnchor [X] is not a valid reference!
```

The bug is a property of the write order. A crash at any point after step 3 and before step 5 produces it.

### 3.3 Why it mattered

- Issue #6488 shows a real dangling `GenericEdge` from a production-derived database. Its target existed nowhere, and the edge's `updated_at` was never changed after creation. That rules out a deletion and points to a lost create.
- A single dangling edge breaks `/walker/me` and any `[node -->]` traversal for the affected user's root. Over many deploys and kills these edges pile up.
- This is not the concurrency race fixed by #5446/#5644. That fix makes the `data.edges` update itself safe. It does nothing about the order of separate writes.

## 4. The idea of the fix (one sentence)

> **Never write a reference before the thing it points to exists.** `sync()` now collects all pending writes first, then flushes nodes, then edges, then edge-list updates, then field updates.

This works on every Mongo topology, including standalone, which transactions do not. It adds no extra round-trips. It turns the worst crash outcome from "broken traversal" into "an unreachable orphan node".

**What:** The loop now only decides what kind of write each anchor needs and appends it to one of four lists. Four flush loops then do the writes in a fixed order. Each write keeps its own `try/except` and logs a warning on failure. The return value (`self._atomic_written`) is unchanged.

**Why:** In the old order, the new target node came after the edge. Now every full node write happens before any edge write. Every edge write happens before any `$setUnion` that makes the edge reachable from an existing node.

**Things to notice:**
- **Per-anchor fault isolation.** In your first commit, the `try` only covered the flush loops. Greptile (P1) pointed out that an exception in `edge_delta()` or `_derive_dirty_from_field_hashes()` would abort the whole sync. Commit `fe8f37a` wrapped the categorization step in its own `try/except` with a separate log message ("categorization failed").
- **Small behaviour change in that commit.** The hash check and `check_write_access` used to sit outside the `try`. They are now inside it. An exception from either is now logged and that anchor is skipped. Before, it propagated out of `sync()`.
- **`node_inserts` is really "full upserts of nodes", not only new nodes.** An existing node with `hash != 0` but no detected dirty fields also falls through to `_write_to_db` and lands here. The same applies to `edge_inserts`. The ordering is still correct, but the name is narrower than the content.
- **Updates to existing edges go to phase 4.** An existing edge with dirty fields takes the `put_partial` path, so it is written after the edge-list updates. That is fine, because changing fields doesn't change topology.
- **The `cast(EdgeAnchor, ...)` and `list[EdgeAnchor]` type** came from Greptile's P2 comment and commit `67ea0d4` "type narrowing". The `else` branch assumes the only non-node anchor is an `EdgeAnchor`. Greptile said it confirmed this by grepping.
- **A comment was deleted.** The comment explaining why setattr-dirty and hash-derived-dirty fields must be unioned is gone. The logic it described is unchanged. A reviewer may ask why it was removed.
- **This protects against crashes, not individual write errors.** If `_write_to_db(X)` throws in phase 1, it is logged, and phase 2 still writes the edge to X. The old code behaved the same way.

## 6. How execution flows after the PR

### 6.1 Syncing after `root ++> Item()`

```text
request ends -> MongoBackend.sync()
├─ _atomic_written = set()
├─ create 4 empty buckets                                  ← NEW
├─ for each anchor in _mem_ref (order: Root, Edge E, Node X)
│   ├─ skip if not persistent
│   ├─ try:                                                ← CHANGED (hash/access now inside try)
│   │   ├─ skip if hash unchanged / no write access
│   │   ├─ Root: edge_delta added=[E] -> atomic_updates      ← CHANGED (queued, not written)
│   │   ├─ E: hash==0 -> edge_inserts                        ← NEW
│   │   └─ X: hash==0 -> node_inserts                        ← NEW
│   └─ except: log "categorization failed", skip anchor     ← NEW
├─ phase 1: _write_to_db(X)                                ← NEW order
├─ phase 2: _write_to_db(E)                                ← NEW order
├─ phase 3: _put_node_atomic(Root, [E], [])  ($setUnion)   ← NEW order
├─ phase 4: put_partial(...) for field-only changes        ← NEW order
└─ return _atomic_written
```

### 6.2 What a crash leaves behind

| Crash point | Before | After |
|---|---|---|
| After Root's `$setUnion`, before E | Root lists E, E missing → dangling reference in `data.edges` | n/a (Root's update is now last) |
| After E, before X | **Dangling edge E → traversal error** | n/a (X is now first) |
| After X, before E | n/a | X is an orphan node. Nothing points to it. Harmless. |
| After E, before Root's `$setUnion` | n/a | E and X exist, but Root doesn't list E. Unreachable. Harmless. |
| After everything | Consistent | Consistent |

The second "Before" row is the bug from #6488. The first row also reads as unsafe in the old order. The issue focused on the second row.

Users don't see any behaviour change in normal (no-crash) runs. The same writes happen, only reordered. The one other change: an exception during the hash or access check is now logged per anchor instead of escaping `sync()`.

One case the PR does not discuss: after a phase-1-only crash, the new node X's own `data.edges` contains E, which doesn't exist yet. That is harmless only as long as nothing can reach X. Whether some lookup path reaches nodes without going through an edge can't be told from this diff.

### `test_mongo_layer123.jac`: "sync writes endpoint nodes before the edges that reference them"

**Setup:**
- Resets Mongo and creates a `MongoBackend` on the test container.
- `source` is a person node written to the DB up front, simulating `Root` loaded at request start. It then gets `hash = 0` so the write-access check needs no request context. It also gets `_initial_edge_ids = frozenset()`, so `edge_delta()` reports the new edge as "added" and source takes the `$setUnion` path, like a real connect.
- `target` is a new node and `eanch` a new `GenericEdge` from source to target. Both are marked persistent and wired into each node's `edges`.
- `_mem_ref` is set in the adversarial order `{source, eanch, target}`, the same order the issue traced.
- `_write_to_db` and `_put_node_atomic` are swapped on the instance for wrappers that record each anchor to `written`, then call the original.

**Checks:**
1. Replays `written` with a `live` set seeded with `source`. When an `EdgeAnchor` comes up, both `source.id` and `target.id` must already be live. This is the core invariant: if it holds, cutting the sequence at any point can't produce a dangling edge.
2. The first `NodeAnchor` in `written` comes before the first `EdgeAnchor`.
3. After sync, the edge, target and source documents all exist in `_anchors`.

**What it proves:** The invariant holds no matter what order `_mem_ref` is in. The PR says you confirmed the test fails on the old inline ordering. That matches the code: the old loop would write `source` (atomic), then `eanch` before `target`, and fail assertion 1.

**Limits:**
- `put_partial` is not recorded, so phase 4 isn't checked. Phase 4 doesn't affect topology, so this matters little.
- The test proves the order. It doesn't simulate a real kill. The PR describes a separate manual `os._exit(137)` experiment (1 dangling edge before the fix, 0 after) that was not committed.

## 11. Questions your senior might ask

**Q: Why not use a Mongo transaction?**
Transactions need a replica set. Many deployments, including the issue's reproducer, run standalone Mongo, where the code would fail. Reordering works everywhere and adds no round-trips.

**Q: Does this change anything when nothing crashes?**
No. The same writes happen, only in a different order. The one difference is that hash and access-check exceptions are now caught per anchor.

**Q: What's the worst state a crash can leave now?**
An orphan node: a new node document that nothing references. Traversal can't reach it, so nothing breaks. It does take up storage until reclaimed. This PR adds no reclaim job.

**Q: What if `_write_to_db` for the node raises an error instead of the process dying?**
The error is logged and the edge is still written in phase 2. That can still produce a dangling edge. The old code had the same behaviour. This PR targets crashes, not write failures.

**Q: Does the new node's own `data.edges` point at a missing edge after a phase-1 crash?**
Yes, it lists the edge id. That only matters if something can reach the orphan node, and with the source's `$setUnion` coming last, nothing can through traversal. Other lookup paths can't be checked from this diff.

**Q: Is the delete path fixed?**
No. `delete()` is still a bare `delete_one`, with edge and neighbour cleanup synced separately. The PR leaves this as a follow-up because it needs reordering of the `destroy()` cascade and there is no deterministic reproducer yet.

**Q: How do you know the test isn't a no-op?**
It seeds `_mem_ref` in the exact bad order from the issue. With the old inline loop, the edge is recorded before the target, so the endpoint assertion fails. You report checking that it failed before the fix and passes after.

**Q: Why record writes by patching instance methods rather than reading the DB?**
The bug is about the order of writes, and the final DB state is the same in both versions. Only the write sequence shows whether a crash in the middle would be safe.

**Q: Could any anchor other than `NodeAnchor`/`EdgeAnchor` reach the `cast(EdgeAnchor, ...)` branch?**
Greptile reports that only these two concrete anchor types exist. If a new anchor type is ever added, this `else` branch would need revisiting.

**Q: Does this interact with the #5446/#5644 concurrency fix?**
It keeps it. Edge-list changes still go through `_put_node_atomic` (`$setUnion`/`$setDifference`); they are just deferred to phase 3.
