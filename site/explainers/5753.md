## 1. The short version

jac-scale serves each Jac walker and function as an HTTP endpoint (`/walker/<name>`, `/function/<name>`). A piece of code called a **middleware** runs before every request. It reads the `Authorization: Bearer <token>` header, checks the token, and records who the user is. Each endpoint then decides whether it needs a logged-in user. Endpoints marked `pub` do not.

**The middleware rejected every request whose bearer token failed validation with HTTP 401, before the request reached the endpoint. This included `pub` endpoints that need no login at all.** For example, `curl` with `Authorization: Bearer not-a-valid-token` against `def:pub greet` returned `{"ok":false,"error":{"code":"UNAUTHORIZED",...}}`. A browser with a stale `jac_token` in `localStorage` could not call any public API until the user cleared storage.

**You deleted the early-return 401 block from `jwt_validation_middleware`. An invalid token now just leaves `username` as `None`, and the request goes on.** According to the PR description, the per-endpoint check (`requires_auth and not username`) still returns 401 for protected endpoints. Public endpoints now treat a bad token the same as no token and run as guest. You also fixed a test that had asserted the buggy 401, and you extended it to cover `pub` functions.

**Status:** Merged on 2026-04-30. @kugesan1105 and @marsninja approved. @musab-mah-7's review was dismissed. All test checks passed.

## 3. The problem, step by step

### 3.1 The setup

- **Middleware** (`jwt_validation_middleware`): runs first on every request and validates any bearer token.
- **Endpoint handler**: built by `create_walker_callback` or `create_function_callback`. It knows whether the endpoint is `pub` (`requires_auth`).
- **Client**: often a browser that sends the token saved in `localStorage` on every call.

The middleware cannot see which endpoint is being called or whether that endpoint is `pub`. Only the handler knows that.

### 3.2 What went wrong: bad token on a `pub` endpoint

```text
1. Browser has jac_token = "<expired JWT>" in localStorage from a past session.
2. Browser sends POST /function/greet with header Authorization: Bearer <expired JWT>.
3. Middleware: header starts with "Bearer " → token = "<expired JWT>", token_attempted = True.
4. Middleware: validate_jwt_token(token) → fails → username = None.
5. Middleware: (token_attempted and not username) → True
   → return JSONResponse(401, UNAUTHORIZED)            ✗ WRONG: endpoint is pub
6. greet's handler never runs; it never checks requires_auth (False for pub).
7. Client gets 401 on every public call until storage is cleared.
```

Compare this with the same request sent **without** a header. `token_attempted` stays False, the request passes, the handler sees `requires_auth = False`, and the client gets 200. A bad token was treated worse than no token.

The same thing happened for `pub` walkers (`/walker/<name>`), as the issue says.

### 3.3 Why it mattered

- Issue #5752: browsers with a stale `jac_token` failed on public endpoints that worked fine in a fresh tab. The only workaround was clearing storage by hand.
- The existing test in `test_serve.jac` asserted `401` for bad tokens on `PublicInfo`. The bug was written into the test suite as expected behaviour.

## 4. The idea of the fix (one sentence)

> **Authenticate in the middleware, authorize in the endpoint.** The middleware only works out who the caller is (or `None`), and each endpoint decides whether `None` is acceptable.

This is the right split because only the endpoint knows whether it is `pub`. The endpoint-level `requires_auth` check already existed, so the middleware's 401 was redundant for protected endpoints and wrong for public ones.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/jserver/impl/jfast_api.impl.jac`: stop rejecting bad tokens in middleware

```diff
     async def jwt_validation_middleware(request: Request, call_next: Callable) {
-        import from fastapi.responses { JSONResponse }        # OLD: only used by the 401 below

-        token: (str | None) = None;

-            token_attempted = True;

         }

-        if token_attempted and not username {                # OLD: global reject
-            return JSONResponse(
-                status_code=401,
-                content={'ok': False, 'error': {'code': 'UNAUTHORIZED', 'message': 'Unauthorized'}}
-            );
-        }
-

         setattr(request.state, 'username', username);
```

**What:** The middleware now always sets `request.state.username` (a name, or `None`) and `user_root_id`, then continues. It never returns a response itself.

**Why:** This removes step 5 of the timeline. Without it, the request reaches the handler, and the handler's `requires_auth` check decides.

**Things to notice:**
- This is a pure deletion (+0 −14). No new logic was added.
- `token` is now declared only inside the `if` block, where it is used, so the outer declaration was dead. The `JSONResponse` import was only used by the removed block.
- Some lines between the `validate_jwt_token` call and the closing brace are hidden in the diff. Presumably they set `user_root_id`. I cannot see them, and they did not change.
- **Behaviour change for every route behind this middleware, not only `/walker` and `/function`.** If any other route (admin, user, static, websocket, and so on) relied on the middleware's 401 instead of its own check, it will now see `username = None` and continue. The diff does not show whether such routes exist. Each would need its own check. This is the main thing a reviewer should confirm.
- The "Fix" section of the PR description says protected endpoints still return 401 through the handler check. The handler code is not in the diff. The unchanged test assertions in `test_serve.jac` (bad token on `CreateTask` → 401) support it.

## 6. How execution flows after the PR

### 6.1 Request with a bearer token

```text
POST /walker/<name> or /function/<name> with Authorization: Bearer <tok>
├─ jwt_validation_middleware
│  ├─ token = header[7:]
│  ├─ username = validate_jwt_token(token)  → name, or None if bad
│  ├─ (no early 401)                                        ← CHANGED
│  ├─ request.state.username = username / user_root_id set
│  └─ call_next(request)                                    ← now always reached
└─ endpoint handler (create_walker_callback / create_function_callback)
   ├─ requires_auth and not username → UNAUTHORIZED (401)   (unchanged, per description)
   ├─ username set → run as that user
   └─ pub and username None → run as guest (__guest__)      ← NEW path for bad tokens
```

### 6.2 Request without a bearer token

```text
POST ... (no Authorization header)
├─ jwt_validation_middleware → username = None → call_next   (unchanged)
└─ handler: 401 if protected, guest if pub                    (unchanged)
```

| Scenario | Before | After |
|---|---|---|
| `pub` endpoint, no token | 200 (guest) | 200 (guest) |
| `pub` endpoint, valid token | 200 (user) | 200 (user) |
| `pub` endpoint, forged / expired / malformed token | **401 from middleware** | **200 (guest)** |
| Protected endpoint, no token | 401 (handler) | 401 (handler) |
| Protected endpoint, bad token | 401 (middleware) | 401 (handler) |
| Protected endpoint, valid token | 200 | 200 |

**Behaviour change users will notice:** a client with an expired token that calls a `pub` endpoint now quietly gets **guest** results instead of an error. If a `pub` endpoint shows personalized data when logged in, a user with a stale token will see guest data, and the response gives no sign that the token is bad. @kugesan1105 hinted at this ("think about guest user and personalization").

## 11. Questions your senior might ask

**Q: Why remove the check instead of making the middleware aware of `pub` endpoints?**
A: The middleware cannot see the target endpoint's access level. Handlers already enforce `requires_auth`, so the middleware check was redundant for protected endpoints and wrong for public ones. Keeping authorization in one place is simpler.

**Q: Do protected endpoints still return 401 for bad tokens?**
A: Yes, according to the PR description. The handler's `requires_auth and not username` check returns `UNAUTHORIZED`. The test's protected-endpoint assertions were left unchanged and CI passed.

**Q: Did any other route depend on the middleware's 401?**
A: The diff does not show. Every route behind this middleware now gets `username = None` instead of an early 401 for a bad token. Any route without its own auth check would now continue. This should be checked.

**Q: Is the response still 401 with the same body for protected endpoints?**
A: It now comes from `TransportResponse.fail(code='UNAUTHORIZED', ...)` in the handler, not the middleware's `JSONResponse`. The test checks only the status code, so it does not confirm the body is identical.

**Q: What does a user with an expired token see on a personalized `pub` endpoint?**
A: Guest data, with no error. That is the concern @kugesan1105 raised, and it was not addressed in this PR.

**Q: How does the frontend learn its token expired now?**
A: On `pub` endpoints, it doesn't. It finds out only when it calls a protected endpoint and gets 401.

**Q: Why was the old test asserting 401 on a public endpoint?**
A: It encoded the buggy behaviour as expected. You flipped it to 200, which matches no-token behaviour.

**Q: Does this weaken security?**
A: Not for protected endpoints, which still reject. For public endpoints, a bad token now has the same effect as no token: guest access, which was already allowed.

**Q: Why are there four merge commits from `main`?**
A: To keep the branch current before merging. They carry no changes to this fix in the diff.
