## 1. The short version

`arequest` in `jac/jaclang/server/serving/client.jac` is the runtime's own async HTTP client. The gateway uses it to forward requests to services. The SSO token exchange and the admin probe, log and trace fetches use it too.

**Before this PR, every `arequest` call opened a brand-new TCP connection, sent `Connection: close`, and on HTTPS built a fresh TLS context (which reloads the system CA bundle). Three requests in a row to the same service meant three TCP handshakes.** Issue #7907 reported this against the gateway's old aiohttp forwarders. Those were removed in #7969, but the cost moved down one layer into `arequest`.

**You added a per-event-loop connection pool to `arequest`. Idle keep-alive connections are reused per origin, with bounds on count, idle time and age.** Reuse is only safe if every response is read to its exact end, so you also fixed several framing bugs:

- the chunked terminator and trailers were not consumed;
- there was no notion of a response without a body (`HEAD`, 204, 304);
- trailing bytes after `Content-Length` were not detected;
- caller-supplied `Content-Length` could be sent twice.

You also added a one-time retry for idempotent requests on a dead pooled connection, and made the jac server send `Connection: close` on the last response before a worker recycles. The gateway's two hop-by-hop header lists are now one shared set.

## 3. The problem, step by step

### 3.1 The setup

- **Callers of `arequest`:** the gateway (`raw_forward`, `stream_forward`), the SSO token exchange, the admin probe/log/trace fetches, and, through the sync wrappers, service-to-service calls (`sv_client`, `rpc.jac`).
- **`arequest` before the PR:** `_open_stream` → write request with `Connection: close` → `_read_response_head` → read body → `writer.close()`.
- **The gateway** copied inbound headers and filtered them against its own `HOP_BY_HOP_HEADERS = {host, transfer-encoding, connection, keep-alive}`. Response headers were filtered against a different list in `http_forward.jac`.
- **The jac server** decided whether to recycle a worker only *after* writing the response.

### 3.2 What went wrong

#### Case A: one handshake per request (the reported bug)

```text
1. Gateway forwards GET /a to http://svc:8000      → _open_stream: new TCP (conn #1)
2. If https: ssl.create_default_context()           → reload CA bundle (every time)
3. Request sent with "Connection: close"
4. Response read, writer.close()                    → conn #1 gone
5. Gateway forwards GET /b to http://svc:8000      → new TCP (conn #2)   ← WRONG: should reuse #1
6. Gateway forwards GET /c to http://svc:8000      → new TCP (conn #3)   ← WRONG
   Result: 3 requests = 3 TCP handshakes (+3 TLS handshakes on https)
```

Your test `connection reuse follows the response framing` saw exactly this: three connections for three requests before the change.

#### Case B: framing bugs that were hidden by `Connection: close`

These did no harm while every socket was thrown away. They would corrupt responses as soon as sockets were reused.

```text
Chunked body "5\r\nalpha\r\n4\r\nbeta\r\n0\r\n\r\n"
1. Reader reads "alpha", "beta"
2. Reader sees "0" size line → break
3. Trailing "\r\n" (and any trailers) left unread in the socket   ← WRONG if reused
4. Next response on this socket would start with "\r\n"

HEAD /x or 204 No Content
1. Old code had no "bodiless" notion
2. With no Content-Length it fell into "read until EOF"           ← WRONG if kept alive
3. On a keep-alive socket EOF never comes → hang, or eats next response

Upstream overruns: "Content-Length: 5\r\n\r\nhelloEXTRA"
1. Reader reads 5 bytes "hello", marks done
2. "EXTRA" left in reader buffer                                   ← WRONG if reused
3. Next request on this socket parses "EXTRA..." as its status line
   (greptile P1, found in the first version of this PR)
```

#### Case C: duplicate `Content-Length` through the gateway (@MusabMahmoodh, item 1)

```text
1. Client sends POST to gateway with Content-Length: 12
2. build_forward_headers copies it (content-length not in gateway's hop-by-hop set)
3. arequest adds its own "Content-Length: {len(body)}"
4. Upstream receives two Content-Length headers                    ← WRONG
5. With Connection: close: costs one exchange. With reuse: classic desync shape.
```

#### Case D: retry replaying a POST (greptile P1, first version)

```text
1. POST sent on pooled conn, upstream executes it
2. Connection dies before the response head arrives
3. First version retried every method                              ← WRONG for POST/PATCH
4. Walker runs twice, or a one-time OAuth code is consumed then "fails"
```

#### Case E: worker recycle hands the pool a dying connection (@MusabMahmoodh, 2026-09-11)

```text
1. App runs with [serve.workers] max_requests = N; request N arrives
2. _connection_loop writes response with "Connection: keep-alive"   ← WRONG
3. Client pool parks that connection (top of LIFO stack)
4. Server then stops the worker and closes the socket
5. Next POST takes that connection → dies before head → not replayable
6. ClientRequestSent → gateway's forward_to returns 502
```

#### Case F: busy connections never rebalance (@MusabMahmoodh, 2026-09-11)

```text
1. Gateway reaches app via ClusterIP; kube-proxy picks pod per TCP connection
2. Pool keeps connections to old pods A, B hot; expires_at reset on every release
3. HPA adds pod C
4. No new connections needed → C gets no traffic                    ← WRONG
   (Connection: close used to rebalance on every request)
```

### 3.3 Why it mattered

- Issue #7907 (severity high, performance): the gateway is the single entry point for the whole fleet, so per-request setup is "the first throughput ceiling the system hits" and inflates tail latency.
- Your description notes the same cost hit the SSO token exchange and the admin fetches, because they share `arequest`. @MusabMahmoodh agreed that fixing it below the gateway was the right call.
- Cases B to F are the risks that reuse itself introduces. Reviewers flagged two of them as security or correctness P1s.

## 4. The idea of the fix (one sentence)

> **Keep connections, but only clean ones.** Reuse a connection per origin on the current event loop only when its response was fully and exactly read and its headers allow reuse; otherwise close it.

Fixing it in `arequest` instead of the gateway means every async caller benefits. The strict "drained, framed, empty buffer, not too old" rule is what makes reuse safe against the framing bugs that `Connection: close` used to hide.

### 5.2 `client.jac`: `ConnectionPool` and its loop ownership

```diff
+obj ConnectionPool {
+    has max_idle_per_host: int = MAX_IDLE_PER_HOST,
+        max_idle_total: int = MAX_IDLE_TOTAL,
+        idle_timeout: float = IDLE_TIMEOUT,
+        max_age: float = MAX_CONNECTION_AGE,
+        _idle: dict[str, list[tuple[any, any, float, float]]] = {};  # (reader, writer, opened_at, expires_at)
+
+    def acquire(origin: str) -> (tuple[any, any, float] | None) {
+        bucket = self._idle.get(origin) or [];
+        while bucket {
+            (reader, writer, opened_at, expires_at) = bucket.pop();   # LIFO
+            if time.monotonic() >= expires_at or _is_unusable(reader, writer) {
+                _close_writer(writer); continue;
+            }
+            return (reader, writer, opened_at);
+        }
+        if origin in self._idle and not self._idle[origin] { del self._idle[origin]; }
+        return None;
+    }
+
+    def release(origin: str, reader: any, writer: any, opened_at: float) {
+        now = time.monotonic();
+        retire_at = opened_at + self.max_age;
+        if now >= retire_at or _is_unusable(reader, writer) {        # too old or dirty
+            _close_writer(writer); return;
+        }
+        self._sweep();                                               # expire idle conns on ALL origins
+        bucket = self._idle.get(origin) or [];
+        if len(bucket) >= self.max_idle_per_host
+            or self.idle_count() >= self.max_idle_total {
+            _close_writer(writer); return;
+        }
+        bucket.append((reader, writer, opened_at, min(now + self.idle_timeout, retire_at)));
+        self._idle[origin] = bucket;
+    }
+    ...
+}
+
+def connection_pool -> ConnectionPool {
+    loop = asyncio.get_running_loop();
+    pool = getattr(loop, _POOL_ATTR, None);
+    if pool is None { pool = ConnectionPool(); setattr(loop, _POOL_ATTR, pool); }
+    return pool;
+}
+
+def close_connection_pool { ... delattr(loop, _POOL_ATTR); pool.close_all(); }
```

**What:**
- `acquire` takes the newest idle connection for an origin. It throws away expired or unusable ones and removes an empty bucket.
- `release` closes a connection that is past its maximum age or unusable. Otherwise it sweeps expired idle connections across every origin, enforces the per-host and total limits, and parks the connection.
- The idle deadline is capped at the connection's retirement time.
- The pool lives as an attribute on the running event loop.

**Why:** This is the core of Case A. `opened_at` and `max_age` fix Case F. The sweep and the "no empty buckets" rules fix @MusabMahmoodh's items 3 and 4a.

**Things to notice:**
- **Only idle connections are bounded.** A burst of 500 concurrent requests still opens 500 sockets. This is listed under "Not addressed here".
- **Why the pool lives on the loop:** asyncio streams cannot be used from another loop. Your description and the 2026-09-08 refactor (f4a1566, "drop the unreachable pool registry") explain that a module-level registry keyed by loop would leak. The pooled writers hold the loop through their transports, so even a weak key stays alive.
- **`weakref.finalize` was not taken.** @MusabMahmoodh suggested `weakref.finalize(loop, pool.close_all)`. Your reply (partly cut off) argued it cannot fire. He accepted it as "a note, not an ask". The test `a loop with pooled connections is still collectable` backs the design.
- **The sweep only runs inside `release`.** If nothing is released, expired idle sockets stay open until the next `acquire` or release on that loop. This is a reasonable trade-off, but worth knowing.

### 5.6 `client.jac`: `_read_response` and the new `arequest` loop

```diff
+    connect_timeout = min(DEFAULT_CONNECT_TIMEOUT, timeout);
+    origin = f"{scheme}://{host}:{port}";
+    pool = connection_pool();
+    retried = False;
+    replayable = method.upper() in _IDEMPOTENT_METHODS;
+    while True {
+        pooled = None if retried else pool.acquire(origin);    # retry never draws from pool
+        conn = pooled;
+        if conn is None {
+            (reader, writer) = await _open_stream(scheme, host, port, connect_timeout);
+            conn = (reader, writer, time.monotonic());
+        }
+        (reader, writer, _opened_at) = conn;
+        try {
+            writer.write(blob); await writer.drain();
+            head = await _read_response_head(reader, timeout);
+        } except (asyncio.TimeoutError, ClientReadTimeout) {
+            _close_writer(writer); raise;                       # timeouts: never retried
+        } except (ConnectionError, OSError, asyncio.IncompleteReadError, ClientConnectionError) as e {
+            _close_writer(writer);
+            if pooled is not None and not retried and replayable {
+                retried = True; continue;                       # one retry, fresh socket
+            }
+            if isinstance(e, ClientConnectionError) { raise; }
+            raise ClientRequestSent(detail=f"connection lost during or after send: {e!r}");
+        }
+        return await _read_response(pool, origin, conn, head, method, stream);
+    }
```

`_read_response` builds the `ClientResponse` with `_reusable = status >= 200 and _is_reusable(...)`. With `stream=True` it returns right away. Otherwise it reads the body and calls `await response.aclose()`, which parks or closes the socket. Mid-body errors still raise `ClientRequestSent` and close the socket.

**What:** Take a pooled connection or open a new one, send the request, and read the head. If a *pooled* connection fails before a usable head, retry once on a *fresh* socket, but only for idempotent methods.

**Why:**
- This fixes Case D: `POST` and `PATCH` are never replayed.
- It handles servers that close idle sockets: the "fresh socket" rule from f4a1566 means a server that expired the whole idle bucket can't hand you a second dead socket.
- The separate connect timeout keeps a slow handshake from eating the whole read window, which #7907 also raised.

**Things to notice:**
- `_open_stream` sits outside the `try`, so connect failures are never retried. They raise from `_open_stream`; its error handling is not shown in the diff.
- A malformed status line raises `ClientRequestSent`, which is caught as `ClientConnectionError`. So "overrun bytes that arrived after parking" become a retry for `GET` and a surfaced error for `POST`. This matches your description.
- A `ClientReadTimeout` presumably also subclasses `ClientConnectionError`. It is caught by the earlier clause, so it is not retried.
- If a `stream=True` caller never drains the body or never calls `aclose`, the socket is not pooled. A missing `aclose` leaks the socket, as it did before.

├─ pool = connection_pool()  (attribute on running loop)                    ← NEW
└─ loop:
   ├─ pool.acquire(origin)  (skipped on retry)                              ← NEW
   │  └─ pops newest; closes expired / closing / EOF / buffered-bytes ones

   ├─ write + drain + _read_response_head (returns version)                 ← CHANGED

## 11. Questions your senior might ask

**Q: Why fix this in `arequest` instead of giving the gateway a shared session, as #7907 suggested?**
The aiohttp forwarders the issue names were removed in #7969, and the cost moved into `arequest`. That function also backs SSO token exchange and the admin fetches, so a gateway-only fix would leave those paying a handshake per call. @MusabMahmoodh agreed with this retargeting.

**Q: Why store the pool on the event loop object instead of a module-level dict?**
asyncio streams can't cross loops, so the pool must be per loop. A dict keyed by loop, even a weak one, would be pinned: the pooled writers reach the loop through their transports. On the loop itself, the loop, the pool and the sockets form one cycle the GC can free together. The test `a loop with pooled connections is still collectable` proves it.

**Q: How do you make sure leftover bytes from one response never reach another caller?**
A connection is only parked when four things hold: the body was read to its exact framed end (`_drained`), the headers allow reuse (`_is_reusable`), the reader buffer is empty, and the socket is not at EOF. The emptiness check runs both when parking and when taking a connection out. Since the client never pipelines, any leftover byte is a protocol violation and the socket is closed.

**Q: When is a request retried, and why not POST?**
Only when a *pooled* connection fails before a usable response head, only once, only for idempotent methods, and always on a fresh socket. A POST that dies there may already have run on the server, for example a walker or a one-time OAuth code. RFC 7230 §6.3.1 allows automatic retry only for idempotent methods. Connect failures and read timeouts are never retried.

**Q: Why retry on a fresh connection instead of the next pooled one?**
When a server's keep-alive timer fires, it usually kills every idle socket at once. Drawing again from the pool would likely hit another dead one. The test `the retry opens a fresh connection…` shows this.

**Q: Doesn't keep-alive break load balancing across pods in Kubernetes?**
It would, because kube-proxy picks a pod per connection. That is why connections are retired 120 s after opening, however busy they are. Busy traffic re-spreads at least every two minutes after an HPA scale-out.

**Q: What happens if an upstream closes an idle connection just as we reuse it?**
If the FIN has already arrived, `acquire` sees EOF and discards the socket. If it races with the write, GET/PUT/DELETE are retried on a fresh socket, and POST/PATCH surface `ClientRequestSent`, which the gateway turns into a 502. The diff doesn't show the upstream servers' keep-alive timeouts, so I can't say how often this race would happen against our 60 s idle timeout.

**Q: Is the number of connections bounded now?**
Only idle ones: 32 per host and 256 total. Concurrent in-flight requests can still open unlimited sockets. Capping those needs a semaphore and a wait queue, which is listed as out of scope under #7900.

**Q: Do service-to-service calls get faster?**
No. `sv_client` and `rpc.jac` use `request_sync` and `post_stream_aware_sync`, which run each call on a private loop and close its pool afterwards. This is tracked as #9300, and the release note was reworded so it doesn't claim otherwise.

**Q: Could dropping `Upgrade` and `Proxy-Authorization` in the gateway break anything?**
They are hop-by-hop by RFC and must not be forwarded by a proxy, and the response side already dropped them. Whether any service relied on receiving them, for example WebSocket upgrades through `build_forward_headers`, can't be told from this diff. It is worth confirming that WebSocket proxying uses a different path.
