## 1. The short version

Jac lets you filter graph queries in several ways. For example, `[root-->[?:A, val == 2]]` means "give me the `A` nodes off root where `val == 2`". When a project has a `jac.toml`, the runtime answers many of these queries from a **topology index**, a stored map of the graph, instead of walking the graph node by node. Before it uses that shortcut, it inspects the compiled filter functions to work out what they check.

**The spelling `[root-->[?:A]][?val == 2]` returned every node connected to root, including unrelated `B` nodes.** The cause was in `refs()`. It glued the in-arrow type filter and the trailing condition into one wrapper lambda. The runtime's bytecode and closure inspection could not see inside that wrapper. It decided "no type, no condition", took the index fast path with an empty filter, and never ran the lambda. In the issue's repro, `mixed` printed `[A(val=1), A(val=2), A(val=3), B(tag='x')]` instead of `[A(val=2)]`.

**You stopped gluing the two filters together. The trailing filter now lives in its own field, `nd_post`, on the destination, and the planner inspects both fields.** A destination with both a hop filter and a trailing filter always takes the slower walk path. You also added a safety guard: any filter that closes over other functions is treated as having a condition, so a future wrapper falls back to the slow path instead of dropping filters.

Before anyone reviewed it, you closed this PR in favour of #7856. That PR deletes the whole lambda-inspection subsystem instead of hardening it.

**Status:** Closed without merging on 2026-08-03, superseded by #7856. All CI checks on `fce86a0` passed. No reviews from anyone else.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Node / edge | Jac's graph objects. `node A { has val: int; }` defines a node type. `root ++> A(val=1)` connects a new `A` to root. |
| `root` | The starting node of a user's graph. |
| Edge reference `[root-->]` | A query: "the nodes that root's outgoing edges point to". |
| Filter comprehension `[?:A, val == 2]` | A filter. `?:A` keeps only type `A`. `val == 2` is a field condition (a "predicate"). It can sit inside the arrow (`[root-->[?:A]]`) or be chained after (`[root-->][?:A]`). |
| Lowering | How the compiler turns Jac syntax into Python calls. You can see it with `jac tool jac2py`. |
| `OPath(...).edge_out(nd=...)` | Lowered form of a hop. `nd` is the node filter lambda written inside the arrow. |
| `ObjectSpatialPath` / `ObjectSpatialDestination` | The runtime path object, and one hop on it. A destination has `direction`, `edge` (edge filter) and `nd` (node filter). After this PR it also has `nd_post`. |
| `refs()` (`JacGraph.refs`) | Runtime function that runs a path query. It takes one optional `post_filter` for the first chained filter. **This is where the bug is**: it fused `post_filter` into `nd` with a wrapper lambda. |
| `post_filter` | The first filter chained after an edge reference. In `[root-->[?:A]][?val == 2]` it is `lambda i: i.val == 2`. |
| `filter_on(...)` | A plain list comprehension that applies the second and later chained filters after `refs()` returns. It runs outside the query engine. |
| Topology index | A per-root stored map of node types and adjacency. It is on by default when `jac.toml` exists. Turn it off with `[run] topology_index = false`. |
| Fast path vs walk path | Fast path: answer from the index, narrowing only by type name, and never call the lambdas. Walk path: load nodes and call the filter lambdas on each. |
| Resolver (`resolve_hop`, `resolve_path_anchors`, `_build_hops`) | Code that picks fast or walk per hop and applies the final filter. |
| `ChainHop` | The resolver's per-hop record: `dest`, `edge_type`, `node_type`, `direction`. |
| Bytecode / `dis` | The low-level Python instructions of a function. `_filter_has_predicates` looks for ops like `COMPARE_OP` and `LOAD_ATTR` to guess "this tests a field". |
| Closure / `__closure__` / cell | Variables a lambda captured from its enclosing scope. `_filter_type_name` searches captured variables for an `Archetype` class to guess the type. |
| `_filter_has_predicates` | Returns True if a filter seems to test fields. It must never under-report. |
| `_filter_type_name` | Returns the node type name a filter checks, or `None`. |
| `nd_post` / `add_node_post_filter` | **This is what the PR adds**: a separate slot for the trailing filter, and the method that sets it. |
| `_wraps_callables` | New guard. True if a filter's closure holds a non-class callable, meaning it wraps other filters. |
| `_dest_has_node_predicates` / `_dest_node_type_name` | New helpers that look at both `nd` and `nd_post` of a destination. |
| `JAC_QUERY_TRACE=1` | Env var that prints the plan, e.g. `hop[0]:index:ordered node=* out=250`. |
| `.jir` | Cached compiled artifacts. They are unaffected here because codegen did not change. |

## 3. The problem, step by step

### 3.1 The setup

- **Compiler:** lowers the three spellings into three different shapes (from your PR description):
  - nested: `refs(OPath(root()).edge_out(nd=lambda i: isinstance(i, A) and i.val == 2))`
  - chained: `filter_on(items=refs(OPath(root()).edge_out(), post_filter=lambda i: isinstance(i, A)), func=lambda i: i.val == 2)`
  - mixed: `refs(OPath(root()).edge_out(nd=lambda i: isinstance(i, A)), post_filter=lambda i: i.val == 2)`
- **`refs()`** (`runtime.impl.jac`): merges `post_filter` into the last destination.
- **Resolver** (`resolver.impl.jac`): uses the `query_utils` helpers to choose index or walk.
- **Topology index:** can only narrow by one node type name. It never runs lambdas.

### 3.2 What went wrong: the mixed form `[root-->[?:A]][?val == 2]`

```text
1. Graph: root → A(1), A(2), A(3), B('x').  jac.toml present → topology_index = on.
2. Compiled call: refs(path with dest.nd = λ isinstance(i, A), post_filter = λ i.val == 2)
3. refs(): last.nd is not None → else branch
   dest.nd = λ orig_nd(i) and post_filter(i)          ← WRONG: opaque wrapper
4. _build_hops: node_type = _filter_type_name(wrapper)
   closure = {orig_nd: <function>, post_filter: <function>} → no Archetype → None   ← type lost
5. resolve_hop: _filter_has_predicates(wrapper)
   bytecode = LOAD_DEREF / CALL only, no COMPARE_OP → False                        ← condition lost
6. has_pred = False and index exists → fast path, node=* (no type)
   trace: hop[0]:index:ordered edge=* node=* dir=2 in=1 out=250
7. resolve_path_anchors: last_has_post_filter = _filter_has_predicates(wrapper) = False
   → post_filter = None → the lambda is never called
8. No filter_on downstream (only one chained filter) → nothing re-applies it
9. Result: [A(1), A(2), A(3), B('x')]                                               ← WRONG
```

The other two forms were correct for different reasons:

| Form | Why it was correct |
|---|---|
| nested | `nd` is one flat lambda, so the bytecode contains the comparison and the closure contains `A`. |
| chained | `nd` was `None`, so `post_filter` was stored as-is (no wrapper), and `val == 2` ran later in `filter_on`. |

### 3.3 Why it mattered

- The bug was silent: no error and no warning. It was only visible with the index on, which is the default for any real project.
- It was a data-isolation risk. The issue notes that jac-code has 9+ session lookups written as `[root()-->][?:Session][?id==...]`. That form is correct today, but "tidying" it to `[root()-->[?:Session]][?id==...]` would make a single-session lookup return every session.
- The issue calls this "the same class of bug" as an earlier fix, where typed-edge predicates were dropped by the same fast path. So the class of bug had already come back once.

## 4. The idea of the fix (one sentence)

> **Keep the trailing filter in its own slot and never trust a filter the planner can't read.** `refs()` stores the trailing filter in `nd_post` instead of wrapping it into `nd`, and the planner treats any wrapper, or any pair of node filters, as "has conditions → walk".

This fixes the trigger, which is the wrapper in `refs()`. It also makes the detector fail safe, so a similar wrapper added later costs speed instead of correctness. You say in the PR that the real cure, not guessing from lambdas at all, belongs to #7831. #7856 later went that way.

**What:** A destination now has two node filters: `nd` (in-arrow) and `nd_post` (trailing). It also gains a method to set the trailing one.

**Why:** Keeping the two filters apart means each can still be inspected on its own.

**What:** `node_filter` passes only if both filters pass. `add_node_post_filter` stores the first trailing filter as-is. If called again, it composes the new filter with the existing one.

**Why:** Any code that calls `node_filter` now applies both halves. The resolver's final post-filter is `last_hop.dest.node_filter`, so this matters there.

**Things to notice:**
- The `else` branch still builds a wrapper lambda, the same pattern that caused the bug. `refs()` takes only one `post_filter`, so in the shown flow it should only run once per destination. - Any code that reads `dest.nd` directly, instead of calling `node_filter`, would now miss `nd_post`. The diff doesn't show whether such readers exist outside the resolver, for example in the non-index walk or walker traversal. CI passing is some evidence, but not proof.

The `.jac` declaration file adds the three declarations and the `ObjectSpatialDestination` import. It also exports `_dest_has_node_predicates` and `_dest_node_type_name`. `_wraps_callables` is declared but not added to the export list.

**What:**
- `_wraps_callables` flags any filter whose captured variables include a function. Classes are excluded, so a captured node type like `A` doesn't trigger it.
- `_filter_has_predicates` now returns True for such wrappers.
- `_dest_has_node_predicates` returns True if both slots are set, or if either slot has a condition.
- `_dest_node_type_name` takes the type from `nd`, or from `nd_post` if `nd` has none.

**Why:**
- Two set slots means two filters, and the index can narrow by only one type name. So even `[r-->[?:BaseContent]][?:PostNode]` (two type filters, no condition) must walk. Commit a99824e ("keep a trailing type filter off the index fast path") appears to be where this rule landed.
- Falling back to `nd_post` for the type keeps `[-->][?:T]` on the fast path with narrowing.
- `_wraps_callables` is the mitigation you describe: composed filters downgrade to the walk path.

**Things to notice:**
- `_wraps_callables` is broad. A legitimate single lambda that captures a helper function or a bound method from its enclosing scope is now treated as having conditions. The result is still correct, but such a query may lose the fast path. The diff doesn't show how common that is.
- Both rules are conservative on purpose. They err toward walking.

## 6. How execution flows after the PR

### 6.1 Building the path in `refs()`

```text
refs(path, post_filter)
├─ path.destinations[-1] has nd from the in-arrow [?:...] (or None)
├─ post_filter is None → nothing to do
└─ post_filter set → dest.add_node_post_filter(post_filter)        ← CHANGED
   ├─ nd_post is None → nd_post = post_filter                        ← NEW
   └─ nd_post already set → nd_post = λ prev(i) and filt(i)          ← NEW (wrapper, caught by guard)
```

### 6.2 Choosing a strategy per hop (`_build_hops` + `resolve_hop`)

```text
_build_hops
└─ node_type = _dest_node_type_name(dest)                            ← CHANGED
   ├─ _filter_type_name(nd)       → e.g. 'A'
   └─ else _filter_type_name(nd_post)                                ← NEW
resolve_hop
├─ has_pred = _dest_has_node_predicates(dest) or edge has predicates ← CHANGED
│  ├─ nd and nd_post both set → True                                  ← NEW
│  └─ else _filter_has_predicates(nd) or (nd_post)
│     └─ _wraps_callables(filt) → True                                ← NEW
├─ not has_pred and index exists → index fast path, narrow by node_type
└─ has_pred → walk path (calls the filters)
```

### 6.3 Final filter (`resolve_path_anchors`)

```text
resolve_path_anchors
├─ resolve prefix hops
├─ last_has_post_filter = _dest_has_node_predicates(last dest)       ← CHANGED
└─ post_filter = dest.node_filter if True else None
   └─ node_filter: nd(arch) must pass, then nd_post(arch)            ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| `[root-->]` | index, `node=*` | same |
| `[root-->[?:A]]` | index, `node=A` | same |
| `[root-->[?:A, val==2]]` | walk, correct | same |
| `[root-->][?:A]` | type in `nd`, index `node=A` | type in `nd_post`, index `node=A` |
| `[root-->][?:A][0:50]` | index, sliced | same (per your trace) |
| `[root-->[?:A]][?val==2]` | index `node=*`, **returns everything** | walk `node=A`, returns `[A(val=2)]` |
| `[root-->[?:A]][?:B]` (two types) | wrapper → index `node=*`, presumably wrong in the same way | walk, correct intersection |
| A single lambda that captures a helper function | depends on bytecode | always walk (slower, correct) |

Behaviour change users would notice: the mixed form now returns correct results. It costs a walk, the same as the nested form. You note that recovering index narrowing for conditional queries was left to Problem 3.

## 11. Questions your senior might ask

**Q: Why did only the mixed spelling break?**
It is the only lowering that puts two node filters into one `refs()` call, so it is the only one that hit the wrapper branch. It also has no `filter_on` afterwards to re-apply the hidden condition.

**Q: Is this a compiler change? Do cached `.jir` files need rebuilding?**
No. `jac2py` output is byte-identical on main and on this branch. It is a runtime-only fix.

**Q: `add_node_post_filter` still composes lambdas. Isn't that the same bug?**
It only composes if called twice on one destination. `refs()` accepts a single `post_filter`, so the shown flow calls it once. If it ever is called twice, `_wraps_callables` makes the planner treat the result as having conditions, so it walks instead of dropping filters.

**Q: What is the performance cost?**
- The mixed form now costs a walk, the same as the nested form.
- Type-only, unfiltered and sliced queries keep the index, per your query traces.
- Two stacked type filters now walk.
- Lambdas that capture a helper function also walk.

**Q: Why not attach the type name and a predicate flag to the fused lambda instead?**
The issue suggested that as an option. Separate fields avoid having to keep that metadata correct through wrapping. Your conclusion, and #7856's approach, is that the real fix is a typed query representation rather than metadata on lambdas.

**Q: Why treat two type filters as needing a walk?**
The index narrows by one type name. Choosing one type would silently skip the other filter, the same class of bug.

**Q: Could other code ignore `nd_post`?**
Anything that calls `node_filter` sees it. The diff doesn't show whether other places read `.nd` directly. CI passing with the index on and off by default is reassuring but not proof.
