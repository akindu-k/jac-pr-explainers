## 1. The short version

Jac keeps graph data (nodes, edges and their fields) in a three-layer memory: an in-process cache (L1), an optional shared cache (L2, for example Redis), and a database (L3: SQLite locally, MongoDB in jac-scale). At the end of each request the runtime writes changed objects back to L3. **Before this PR, every write replaced the whole stored object. So if two concurrent requests changed different fields of the same node, the request that finished last silently erased the other one's change.** For example, request A sets `task.title = "Updated Title"` and request B sets `task.completed = True`. After both finish, only one of the two changes is in the database.

**This PR records which fields you assign on a persistent object (the "dirty fields"). At commit time it writes only those fields to L3, using a version number to detect concurrent writers and retrying when it finds one.** On MongoDB this is a `$set` on `data.archetype.<field>` plus `$inc` on `version`. On SQLite it is a `json_set(...)` `UPDATE ... WHERE version = ?`. To make the SQLite part possible, the PR also changes the SQLite storage format from pickled BLOBs to JSON text with a `version` column, and adds a one-time migration.

The PR does **not** cover the race the linked issue #4616 mainly describes, which is concurrent `root ++> node` (edge connects). Edges are not archetype fields, so dirty-field tracking never sees them. Reviewers @amadolid and @juzailmlwork raised this and other questions on 2026-03-24. No reply to them is visible.

| Full-document write (last write wins) | `put`/`sync` write the **whole** anchor, overwriting whatever is in the database. **This is where the bug is.** |
| Race condition | The result depends on which of two concurrent operations finishes last. |
| Partial update | Writing only some fields of a stored object. **This is what the PR adds.** |
| Dirty fields | The set of field names assigned since the last save, stored in `archetype.__dict__['__jac_dirty_fields__']`. |
| `__setattr__` | Python hook that runs on every `obj.x = value`. The PR uses it to record dirty fields. |
| `__jac_force_full_sync__` | A flag the PR sets when "too many" fields are dirty. Commit then does a full `put` instead. |
| `version` | New integer on `Anchor` and in the database. It goes up by one on each write. |
| Optimistic locking | "Write only if the version is still the one I read." If it changed, someone else wrote first, so re-read and retry. |
| Exponential backoff | Waiting longer before each retry. Here the waits are 0.1 s, then 0.2 s, and they block the thread (`time.sleep`). |

## 3. The problem, step by step

### 3.1 The setup

- A jac-scale server runs walkers per HTTP request. Each request loads anchors (L1 → L2 → L3), runs the walker, then calls `ScaleTieredMemory.commit()`.
- `commit()` calls `MongoBackend.sync()`. For each changed anchor (hash differs), it writes the **full** serialized anchor.
- The same holds for local jaclang with `TieredMemory` + `SqliteMemory`. There, the anchor is stored as one pickled BLOB, so a field-level write is impossible.

### 3.2 What went wrong

#### Case A: two requests change different fields of one node (the case this PR targets)

```text
1. DB:  Task 999 = {title: "Original", completed: false}
2. Req A loads Task 999 → A's copy {title: "Original", completed: false}
3. Req B loads Task 999 → B's copy {title: "Original", completed: false}
4. A sets title = "Updated Title"   → A's copy {title: "Updated Title", completed: false}
5. B sets completed = true         → B's copy {title: "Original", completed: true}
6. A commits: full write           → DB {title: "Updated Title", completed: false}
7. B commits: full write           → DB {title: "Original", completed: true}   ← WRONG: A's title is lost
```

#### Case B: two requests connect edges to the same node (the main case in #4616, not addressed here)

```text
1. DB:  root.edges = []
2. Req A loads root → edges []
3. Req B loads root → edges []
4. A runs root ++> NodeX → A's root.edges [e1]
5. B runs root ++> NodeY → B's root.edges [e2]
6. A commits full anchor → DB root.edges [e1]
7. B commits full anchor → DB root.edges [e2]   ← WRONG: e1 is lost
```

Edges live on the anchor (`anchor.edges`), not as archetype fields set through `__setattr__`. The PR's dirty tracking never sees them, so this case still uses the full write.

### 3.3 Why it mattered

- Issue #4616 (Pocketnest) says "As of this version scaling will not work." It lists three problems:
  1. L1 is never invalidated, so replicas disagree.
  2. L1 and L2 grow without bound.
  3. Full-anchor writes cause lost updates "even on different fields".
- Issue #4666 asks for partial updates specifically, and notes that it may need a serialized stored anchor. That is why SQLite moved from pickle to JSON.
- This PR targets problem 3 for plain field assignments only. It does not touch problems 1 and 2.

## 4. The idea of the fix (one sentence)

> **Write only what changed, and only if nobody else wrote first.** Track which fields were assigned, then at commit send just those fields to the database with a version check, and retry on conflict.

Field-level writes are what make two "different field" updates commute: neither write touches the other's field. The version check adds safety when two requests touch the same field or when the stored copy has moved on.

**What:**
- Every public field assignment on an archetype whose anchor already exists and is persistent adds the field name to `__jac_dirty_fields__`.
- If enough fields are dirty, it sets `__jac_force_full_sync__`. "Enough" means at least 80% of the count, and never fewer than 10.
- `__jac_clear_dirty__` empties the set and removes the flag.

**Why:** Commit needs to know *which* fields to send in a partial update. The hash alone only says *whether* something changed.

**Things to notice:**
- The anchor must already be in `__dict__` and be persistent. The comment says this avoids "1M+ UUID generations" during compilation. Commit 1a6ffa7 limits tracking to fields modified after the anchor is marked persistent. Fields set on a brand-new node in the same request are therefore not dirty; they go through the normal full write.
- In-place mutations (`task.tags.append(x)`) do not call `__setattr__`, so they are not tracked. They still rely on hash-based `sync`, which does a full write. The comment in `ScaleTieredMemory.commit` says the same.
- `total_fields` counts `self.__class__.__dict__` keys. That includes methods, and may miss `has` fields that have no default. It is a rough count, and it is recomputed on every tracked assignment.
- This runs on **every** attribute set of every persistent archetype, which adds cost to a very hot path. Whether that matters can't be judged from the diff.

**What:**
- New databases use a JSON text column plus a version.
- Old databases are converted in place the first time a connection opens.
- Reads still accept pickle rows. Writes always produce JSON.

**Why:** `json_set` can patch one field inside a JSON column. It can't patch a pickle blob.

**Things to notice:**
- This is a **storage format change for every local Jac user**. The PR description and the release notes don't mention it.
- Rows that fail to convert are logged and **dropped**. The old table is deleted even when `failed > 0`.
- `put` and `sync` write with `INSERT OR REPLACE` and **no version check**. They set the stored version to "my local version + 1", so a stale writer can move the stored version *backwards*. That weakens the optimistic lock in 5.4.
- In `put`, the version is incremented after serializing. If `Serializer` includes `version` in the data (the diff doesn't show whether it does), the JSON would hold the old value.
- In the pickle fallback branch, `l3_fetch_count` is incremented a second time.

### 5.4 `jac/jaclang/runtimelib/impl/memory.impl.jac`: `SqliteMemory.partial_update`

```diff
+impl SqliteMemory.partial_update(anchor, fields = None) {
+    if not anchor.persistent or not Jac.check_write_access(anchor) { return; }
+    if not fields { self.put(anchor); return; }
+    for attempt in range(3) {
+        if attempt > 0 { time.sleep(0.1 * 2 ** (attempt - 1)); }
+        current_version = anchor.version;
+        update_chain = "data";
+        for (name, value) in fields.items() {
+            update_chain = f"json_set({update_chain}, ?, ?)";
+            params.extend([f"$.archetype.{name}", json.dumps(Serializer._serialize_value(value, include_type=True))]);
+        }
+        UPDATE anchors SET data = {update_chain}, version = version + 1 WHERE id = ? AND version = ?
+        if rowcount == 0 {
+            if row exists { fresh = self.get(anchor.id); anchor.version = fresh.version; continue; }
+            else { rollback; self.put(anchor); return; }
+        } else {
+            commit; anchor.version = current_version + 1;
+            del self.__mem__[anchor.id];                  # L1 invalidation
+            return;
+        }
+    }
+    self.put(anchor);                                     # retries exhausted → full write
+}
```

**What:** One `UPDATE` patches each dirty field inside the JSON and bumps the version, but only if the version still matches. On a mismatch it re-reads and retries up to 3 times. After that it does a full `put`.

**Why:** This is the core fix for Case A on SQLite. Two different fields are patched independently instead of the whole row being replaced.

**Things to notice:**
- **Likely value-encoding bug.** SQLite's `json_set` stores a bound TEXT parameter as a *JSON string*, even if the text looks like JSON. `json.dumps("Updated")` is the text `"Updated"` with quotes, and `json.dumps(True)` is the text `true`. Both are bound as text, so the stored values would likely become the strings `"\"Updated\""` and `"true"` instead of a string and a boolean. The usual form is `json_set(data, ?, json(?))`. No SQLite test exercises this path, so please verify it.
- When a conflict is detected, it calls `self.get(anchor.id)`. The top of `get` is not in the diff. If it returns the cached L1 copy first, it returns the same stale version, every retry fails the same way, and the code ends in the full `put` it was trying to avoid.
- The final fallback after any failure is a full `put` with no version check, which is the original last-write-wins behaviour.
- The description says SQLite "reads the stored anchor, patches fields, writes back the full anchor". The code no longer does that; it does a single atomic `json_set` update.

### 5.5 `jac/jaclang/runtimelib/impl/memory.impl.jac`: `SqliteMemory.commit` and `TieredMemory.commit` auto-persist

```diff
 impl TieredMemory.commit(anchor = None) {
+    for cached_anchor in list(self.__mem__.values()) {
+        if populated and persistent {
+            if archetype.__dict__.get('__jac_force_full_sync__') { self.put(cached_anchor); clear... }
+            elif dirty_fields := archetype.__jac_dirty_fields__() {
+                fields_dict = {f: getattr(archetype, f) for f in dirty_fields};
+                dirty_copy = set(dirty_fields); archetype.__jac_clear_dirty__();
+                try {
+                    if self.l3?.partial_update {
+                        self.l3.partial_update(cached_anchor, fields_dict);

+                        self.l2.invalidate(cached_anchor.id);      # L2 invalidation
+                    } else { self.put(cached_anchor); }

+            }
+        }
+    }
     if self.l3 { self.l3.sync(); }
```

`SqliteMemory.commit` gets the same loop, calling its own `partial_update`.

**What:** Before the usual `sync`, every L1 anchor with dirty fields is written with `partial_update`, or with `put` if the force flag is set. In `TieredMemory`, the anchor is then dropped from L1 and invalidated in L2.

**Why:** It connects dirty tracking to the database write, so walkers can just assign (`task.title = x`) with no explicit API call.

**Things to notice:**
- Dirty fields are cleared *before* the write and restored on exception. The outer `except` then logs and moves on (`0;` is used as a no-op statement).
- Removing an anchor from L1 mid-process is exactly what @amadolid warned about on 2026-03-09: another in-flight request holding that anchor loses its link to the cache. Commit history shows L1 invalidation was removed (3450f5f) and then re-added (62f009f).
- This loop is copied, almost word for word, into three places: `SqliteMemory.commit`, `TieredMemory.commit` and `ScaleTieredMemory.commit`.

**What:** It sends only `data.archetype.<field>` values, bumps `version`, and filters on the expected version. Loaded anchors now carry the stored version.

**Why:** This is the core fix for Case A on jac-scale.

**Things to notice:**
- **The conflict path probably never works as the comments describe.** The filter is `{_id, version}` and `upsert=True` is set. When the document exists with a *different* version, the filter matches nothing, so MongoDB tries to *insert* a new document with the same `_id`. That normally fails with a duplicate-key error. The `except` branch retries **without re-reading the version**, so all 3 attempts fail (with 0.1 s + 0.2 s sleeps), and then it does a full `put`. That is last-write-wins again. The `result is None` branch can't be reached while `upsert=True`.
- **Possible path conflict on every call.** `$setOnInsert: {data: ...}` overlaps `$set: {"data.archetype.title": ...}`, and `version` appears in both `$inc` and `$setOnInsert`. MongoDB normally rejects updates whose operators touch overlapping paths. If that holds here, *every* partial update raises and ends in the full `put` fallback. This needs a check against a real MongoDB with debug logs on. The passing test (section 7) would not catch it.
- `put` sets the stored version to "local version + 1" with no filter, so a stale writer can move the version backwards.
- The description says `update_one` with `upsert=False`. The code uses `find_one_and_update` with `upsert=True`.
- `partial_update` does not update `anchor.hash`, while `put` does. That matters for 5.7.

## 6. How execution flows after the PR

### 6.1 Assigning a field in a walker

```text
task.title = "Updated Title"
└─ Archetype.__setattr__("title", ...)                         ← CHANGED
   ├─ name starts with "_" or is "reports" → plain set, return  ← NEW
   ├─ object.__setattr__ (value set in memory)
   └─ anchor in __dict__ and persistent?                        ← NEW
      ├─ no  → done (nothing tracked)
      └─ yes → add "title" to __jac_dirty_fields__              ← NEW
               └─ dirty count ≥ max(80% of class keys, 10)?
                  └─ yes → set __jac_force_full_sync__          ← NEW
```

### 6.2 End of request in jac-scale (Mongo)

```text
ScaleTieredMemory.commit()
├─ (existing steps above the hunk, not shown)
├─ for each anchor in L1:                                       ← NEW
│  ├─ force flag → l3.put(anchor)  (full write, version = local+1)
│  └─ dirty fields → MongoBackend.partial_update(anchor, {title: ...})
│     ├─ find_one_and_update({_id, version: v},
│     │     $set data.archetype.title, $inc version, $setOnInsert ..., upsert)
│     ├─ success → anchor.version = v+1 → return
│     ├─ exception (e.g. duplicate key / path conflict) → retry up to 3 (sleep 0.1, 0.2)
│     └─ exhausted → full put  (last-write-wins)
├─ compute l2_pending by hash   (anchor still in L1, hash not refreshed)
├─ l3.sync()   (hash-based; may fully rewrite the same anchor — not visible in diff)
└─ update L2 for l2_pending
```

### 6.3 End of request in local jaclang (TieredMemory + SQLite)

```text
TieredMemory.commit()
├─ for each anchor in L1:                                       ← NEW
│  ├─ force flag → self.put(anchor)
│  └─ dirty → SqliteMemory.partial_update(anchor, fields)
│     ├─ UPDATE anchors SET data=json_set(...), version=version+1
│     │     WHERE id=? AND version=?
│     ├─ 1 row → commit, anchor.version+1, drop from SqliteMemory.__mem__
│     ├─ 0 rows, row exists → self.get() for fresh version → retry
│     ├─ 0 rows, no row → full put
│     └─ retries exhausted / errors → full put
│  then: del L1 entry, l2.invalidate(id)                        ← NEW
└─ l3.sync()   (JSON + version format)                          ← CHANGED
```

### 6.4 Opening a SQLite database

```text
SqliteMemory._ensure_connection()
├─ connect, WAL, synchronous=NORMAL
├─ table "anchors" exists?                                      ← NEW
│  ├─ yes, data column is BLOB → _migrate_blob_to_json()
│  │  ├─ unpickle each row → JSON → anchors_new (version 0)
│  │  ├─ rows that fail → logged and dropped
│  │  └─ DROP anchors; RENAME anchors_new; CREATE INDEX
│  └─ no → CREATE TABLE (id, data TEXT, version) + index
└─ commit
```

### 6.5 Loading an anchor

```text
SqliteMemory.get(id) / MongoBackend._load_anchor(raw)
├─ SQLite: json.loads → Serializer.deserialize → anchor.version = row.version   ← CHANGED
│   └─ JSON fails → try pickle (old rows) → fails → delete row
└─ Mongo: deserialize → anchor.version = raw["version"]                         ← NEW
```

| Scenario | Before | After |
|---|---|---|
| Two requests set different fields of one node (Mongo) | Last full write wins, one change lost | Intended: both kept. In practice it depends on whether `$set`/`$setOnInsert` succeeds and whether `sync` rewrites the anchor afterwards (see 5.6, 5.7) |
| Two requests set the **same** field | Last write wins | Version conflict → retry → still last write wins on that field, or a full put after 3 failures |
| Many concurrent updates (> 3 conflicts) | Last write wins | Falls back to full `put`, so lost updates are still possible |
| Concurrent `++>` on the same node | Edges lost | Unchanged (not tracked) |
| In-place mutation (`list.append`) | Full write via hash | Unchanged |
| Existing local SQLite file | Pickle BLOB | Migrated to JSON on first open. Rows that fail to convert are dropped |
| New node created this request | Full write | Full write (not dirty-tracked) |

User-visible changes: the local SQLite file format changes one way (no downgrade path is shown), every field assignment on a persistent object does extra work, and commits can now sleep up to 0.3 s per anchor while retrying.

## 11. Questions your senior might ask

**Q: Does this fix concurrent `root ++> node` on the same node?**
No. Edges are on the anchor, not archetype fields set through `__setattr__`, so they are never dirty-tracked and still go through a full write.

**Q: Why did SQLite move from pickle to JSON?**
`json_set` can patch one field inside a JSON column. A pickle blob can only be replaced whole. Issue #4666 anticipated needing a serialized stored anchor.

**Q: What happens to an existing local database?**
On first open, `_migrate_blob_to_json` converts every row and drops the old table. Rows that fail to unpickle or serialize are logged and lost.

**Q: What happens when two requests update the same field?**
Optimistic locking makes the second one detect a version change, re-read, and retry. Its value then wins. After 3 failed tries it does a full `put`.

**Q: With `upsert=True` and a `version` filter, what does Mongo do on a version mismatch?**
The filter misses, so Mongo tries to insert a document with an existing `_id`. That is likely a duplicate-key error. The code retries with the same version and then falls back to a full `put`. I need to verify this, along with whether the overlapping `$setOnInsert`/`$set` paths are rejected outright.

**Q: After the partial update, does `MongoBackend.sync` write the anchor again?**
Possibly. `ScaleTieredMemory.commit` keeps it in L1, and `partial_update` doesn't refresh `anchor.hash`. `MongoBackend.sync` isn't in the diff, so I'd need to check it.

**Q: Does the test prove the partial path ran?**
No. It only checks the final Mongo document. A full-write path that happens not to overlap, or a fallback `put`, also passes.

**Q: Why the 80% / minimum-10 threshold?**
Commit 365c103 replaced a hard-coded 100 with a percentage, so that when most fields are dirty a single full write is cheaper than many `$set`s. The field count is approximate, because it counts class `__dict__` keys.

**Q: Does `time.sleep` in the retry block the server?**
It blocks the thread running the commit for up to 0.3 s per anchor. Whether that stalls other requests depends on how the server runs commits, which the diff doesn't show.

**Q: Is `JacPersistence` public API?**
It is still defined in `runtime.jac`, but nothing in the diff uses it and the release notes don't mention it. It should be removed or documented.
