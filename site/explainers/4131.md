## 1. The short version

The Jac runtime includes a small built-in HTTP server (`JacAPIServer`). Its `AuthHandler` already supports `POST /user/register` and `POST /user/login`. After a client logs in and gets a token, it has no way to ask "who am I?" (issue #4130).

**This PR adds `GET /user/info`. With a valid `Authorization: Bearer <token>` header, it returns `{"username": ..., "root_id": ...}`. It returns 401 if the token is missing or invalid, and 404 if the user no longer exists.** The PR also lists the endpoint on the server's root (`/`) page and adds two tests.

**As committed, the new code in `server.impl.jac` is split in two and does not parse.** The first half of `get_user_info` stops at `if not username {` and is never closed. The second half (user lookup and success return) landed inside the existing `update_password` implementation, and its `TransportResponse.success(...)` call is missing `);` and `}`. This very likely explains why `test-core`, `test-client` and `test-scale` fail.

**Status:** Closed (not shown as merged) with no reviews. Three CI jobs failed on head commit `3642fc0`. Issue #4130 is also closed. The data doesn't show whether the feature landed some other way.

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- `JacAPIServer.create_handler` routes requests by path.
- `AuthHandler` handles register and login and returns a token.
- No endpoint returned the logged-in user's own details.

### 3.2 What went wrong

```text
1. Client: POST /user/register {username: "alice", password: ...}  → user created, has a root_id
2. Client: POST /user/login                                         → token "abc..."
3. Client wants: "Am I still logged in? What's my root_id?"
4. Client: GET /user/info  → no such route                          ← MISSING
5. Client must keep root_id from register/login itself, or has no way to check the token
```

### 3.3 Why it mattered

Issue #4130 gives three uses: checking authentication status, showing user information, and getting `root_id` for graph operations. There are no comments from other users, so the data doesn't show who asked for it.

## 4. The idea of the fix (one sentence)

> **Look up the caller from their token.** Validate the bearer token, find that user, and return their username and `root_id`.

This reuses the same token check (`user_manager.validate_token`) that the update endpoints already rely on, so the new endpoint authenticates the same way as the existing ones.

## 11. Questions your senior might ask

**Q: Does the server even start with this change?**
Almost certainly not. `get_user_info` stops at an open `if not username {`, and the rest of it sits inside `update_password` with an unclosed call. That fits the three failing test jobs.

**Q: How did the code end up split?**
The diff alone doesn't show it. The second half was placed right after identical 401-error lines in `update_password`, which points to a bad edit or the merge commit `3642fc0`. Diffing each commit separately will tell.

**Q: Why validate the token inside `AuthHandler` instead of using `_authenticate()` like `/protected`?**
The PR doesn't explain this. Keeping the check in `AuthHandler` matches `update_username` and `update_password`, which also take a token. Using `_authenticate()` would be shorter and more consistent with `/protected`.

**Q: Can one user read another user's info?**
No. The method takes only a token, and the username comes from `validate_token`.

**Q: When would 404 happen?**
When the token is valid but `get_user(username)` finds nothing, for example if the user was deleted after logging in.

**Q: What's the exact response body?**
The description shows `{"username", "root_id"}`. Whether `TransportResponse.success` adds an envelope can't be told from this diff.

**Q: Do the tests prove the feature works?**
No. They only cover the two 401 cases plus the root listing. No test checks a successful call.

**Q: Does `_get_auth_token()` exist?**
It isn't defined in this diff. The code assumes it already exists in the request handler. Check `main` before relying on it.

**Q: Is the issue resolved?**
Issue #4130 is closed, but this PR is closed and doesn't appear merged, so the data doesn't show that the endpoint shipped.
