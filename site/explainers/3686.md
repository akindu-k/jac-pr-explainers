## 1. The short version

The contributor guide (`docs/docs/internals/contrib.md`) tells new contributors how to clone their fork of the repository and set it up. One setup step pulls in **typeshed**, a bundle of type stubs that the project keeps as a **git submodule**.

**The guide ran `git submodule update --init --recursive` *before* `cd jaseci`, so the command ran outside the freshly cloned repository and failed.** Git submodule commands only work inside a git repository. Run from a plain directory, git stops with an error such as `fatal: not a git repository (or any of the parent directories): .git`.

**You moved `cd jaseci` up one line so the submodule command runs inside the cloned repository.** This is a one-line swap in one Markdown file. No code, tests or config changed.

**Status:** Merged on 2025-12-10. @marsninja approved it (no comments), and all four CI checks passed on the head commit `2ee2af6`.

## 3. The problem, step by step

### 3.1 The setup

- A new contributor follows the "clone your fork" code block in `contrib.md`.
- The block has three steps: clone, fetch submodules, enter the folder.
- The submodule step needs to be inside the repository to work.

### 3.2 What went wrong

```text
1. Shell is in ~/code (not a git repo)
2. git clone https://github.com/YOUR_USERNAME/jaseci.git
      → creates ~/code/jaseci ; shell still in ~/code
3. git submodule update --init --recursive        ← WRONG: runs in ~/code
      → git looks for a .git folder in ~/code and its parents, finds none
      → fatal: not a git repository ...
      → typeshed is NOT downloaded
4. cd jaseci
      → shell now in ~/code/jaseci, but the typeshed folder is still empty
```

There is one more case that the PR doesn't mention. If `~/code` were itself inside some other git repository, step 3 would act on *that* repository instead of failing. That would be even more confusing. This is general git behaviour; the PR doesn't discuss it.

### 3.3 Why it mattered

- New contributors copy-pasting the block hit an error on their very first setup step.
- Anyone who ignored the error ended up with an empty typeshed submodule.
- No issue is linked and there is no discussion beyond the approval. So the PR text doesn't show how many people hit this or what failed later because of it.

## 4. The idea of the fix (one sentence)

> **Enter the repo before touching its submodules.** Move `cd jaseci` above `git submodule update` so the command runs inside the cloned repository.

This is the smallest correct fix. It keeps the same commands and the same comment, and only fixes the order the reader runs them in.

## 5. Every code change, explained

### 5.1 `docs/docs/internals/contrib.md`: fix the clone-and-setup order

```diff
 # Clone your fork (replace YOUR_USERNAME with your GitHub username)
 git clone https://github.com/YOUR_USERNAME/jaseci.git
-git submodule update --init --recursive # Pulls in typeshed   # OLD: ran outside the repo
 cd jaseci
+git submodule update --init --recursive # Pulls in typeshed   # NEW: runs inside the repo

 # Add the original repository as upstream (may already exist)
 git remote add upstream https://github.com/jaseci-labs/jaseci.git
```

**What:** The guide now says to `cd jaseci` first and then initialise submodules.

**Why:** Submodule commands need the current directory to be inside the parent repository. The old order broke that.

**Things to notice:**
- The next step, `git remote add upstream ...`, also needs to run inside the repo. It already came after `cd jaseci`, so it was fine before and is still fine.
- `git clone --recurse-submodules <url>` would have done both steps in one command. You kept the two-step style, which is a valid choice and keeps the diff minimal.
- The clone URLs point to `jaseci.git` and `jaseci-labs/jaseci`, while this repository is listed as `jaseci-labs/jac`. Whether those URLs are still correct can't be told from the PR, and the PR didn't change them.

## 11. Questions your senior might ask

**Q: What exactly fails with the old order?**
`git submodule update` runs in the parent folder, which isn't a git repository. Git exits with `fatal: not a git repository`, and typeshed is never downloaded.

**Q: Why does the submodule need to be initialised at all?**
The comment says it "pulls in typeshed", a set of type stubs. A plain `git clone` leaves submodule folders empty until you run this command.

**Q: Why not `git clone --recurse-submodules`?**
That would also work and saves a step. You kept the existing two-command style so the fix stays a one-line swap.

**Q: Did the `git remote add upstream` step have the same bug?**
No. It already came after `cd jaseci`, so it ran inside the repo.
