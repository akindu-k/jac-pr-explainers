## 1. The short version

Jac **walkers** are units of code that move through a graph. jac-scale turns each walker into an HTTP API endpoint. Before this PR, every walker got the same two fixed routes: `POST /walker/<Name>` and `POST /walker/<Name>/{node}`. **You could not choose a walker's URL path or HTTP method. A walker could never be a `GET /todos` route, for example.**

**The PR adds a `@meta(path=..., method=...)` decorator in jaclang core. It also adds a new plugin hook, `get_walker_specs`, that jac-scale implements. When the server registers routes, a walker with `@meta` gets its custom path and method instead of the default routes.** For example, `@meta(path="/custom/get", method="GET")` makes `GET /custom/get` run the walker on the user's root node.

The PR is narrower than the linked issue #4299. The issue asked for headers, query parameters and a timeout, all set through a `__meta__` object "when invoking remote walkers". The PR only does server-side path and method. There are also some correctness concerns, covered in sections 5, 6 and 10:
- The custom branch registers two routes with the same path and method.
- GET fields are still read from the request body.
- jac-scale now registers itself with the plugin manager when it is imported.

**Status:** Closed. All 8 CI checks passed on head commit `99059fa`. There is no approving review. The only feedback is one design comment from @Thamirawaran, with no reply. The data does not show a merge. Linked issue #4299 is also marked closed.

## 3. The problem, step by step

This is a feature, so this section describes what was missing.

### 3.1 The setup

- The **user code** is a `.jac` file with walkers.
- At **server start**, `JacAPIServer.register_walkers_endpoints` loops over `self.get_walkers()`. It registers two `POST` routes per walker.
- The **client** (a browser, `jac-client` or `curl`) must call those exact URLs.

### 3.2 What was missing

```text
1. User writes:   walker list_todos { can run with `root entry { report ...; } }
2. jac start app.jac
3. register_walkers_endpoints runs:
     add POST /walker/list_todos/{node}
     add POST /walker/list_todos
4. User wants:    GET /todos
5. No way to say so in Jac code            <-- MISSING
6. Clients must use POST /walker/list_todos, even for a pure read
```

### 3.3 Why it mattered

Issue #4299 says users "cannot specify" the HTTP method, headers, query parameters or other HTTP settings. Without this, you cannot build normal REST-style routes. Every walker is a POST under `/walker/`.

The issue's proposal was larger than what the PR does:
- It used a `__meta__ = {...}` field inside the walker.
- It included `headers`, `query_params` and `timeout`.
- It described invoking remote walkers, which reads as client-side.

The PR does not cover headers, query_params or timeout.

## 4. The idea of the fix (one sentence)

> **Tag the walker class, let the plugin read the tag.** `@meta` stores a path and method on the walker class, and jac-scale asks for it through a core plugin hook when it builds routes.

This keeps core free of HTTP logic. Core only stores data and declares a hook. Any server plugin can decide what to do with the data. This roughly follows @Thamirawaran's split between a core decorator and a plugin function used by `JacAPIServer`.

## 5. Every code change, explained

### 5.1 `jac/jaclang/pycore/archetype.py`: defines the `meta` decorator

```diff
-from typing import Any, ClassVar, TypeAlias, TypeVar
+from typing import Any, ClassVar, TypeAlias, TypeVar, cast
@@
+def meta(path: str, method: str = "POST") -> Callable[[T], T]:
+    """Decorate walker with custom specs."""
+
+    def decorator(cls: T) -> T:
+        cast(Any, cls).__meta__ = {"path": path, "method": method}  # store specs on the class
+        return cls
+
+    return decorator
```

**What:** `meta("/x", "GET")` returns a decorator. The decorator sets `cls.__meta__ = {"path": "/x", "method": "GET"}` and returns the same class.

**Why:** It gives Jac code a place to declare the route.

**Things to notice:**
- The `cast(Any, cls)` exists so mypy accepts writing an attribute on a generic `T`. Commits `e6c3796`/`8660ba2` ("setattr") and then `9dfd1f4` ("use typing.cast") show the back-and-forth.
- The decorator does **no validation**. `method="GTE"` or an empty path is accepted here and only fails later at server start (see 6.3).
- `Callable` is used in the signature, but this hunk does not import it. It must already be imported elsewhere in the file; that part is not shown. The type-check checks pass, which suggests it is.
- The decorator works on any class, not only walkers.
- The jaclang release note says it is "exposed via archetype". It is actually *defined* in archetype and *re-exported* from constructs. The PR description says the reverse ("re-exported via `archetype`").

## 6. How execution flows after the PR

### 6.1 Loading the Jac file (decorating a walker)

```text
jac start app.jac
└─ module executes
   └─ @meta(path="/custom/get", method="GET") walker GetWalker {...}
      ├─ meta("/custom/get", "GET") returns decorator             ← NEW
      └─ decorator(GetWalker)
         ├─ GetWalker.__meta__ = {"path": "/custom/get", "method": "GET"}   ← NEW
         └─ returns GetWalker unchanged otherwise
```

### 6.2 Plugin setup

```text
import jaclang.pycore.runtime
├─ plugin_manager.add_hookspecs(JacPlugin)    ← NEW: get_walker_specs exists
└─ ...
import jac_scale
└─ plugin_manager.register(JacScalePlugin())  ← NEW: side effect on import
```

### 6.3 Registering endpoints at server start

```text
JacAPIServer.register_walkers_endpoints()
└─ for walker_name in get_walkers()
   ├─ walker_cls = get_walkers()[walker_name]                       ← NEW
   ├─ meta = plugin_manager.hook.get_walker_specs(walker_cls=...)   ← NEW
   │  └─ JacScalePlugin.get_walker_specs → getattr(cls, "__meta__", None)
   ├─ if meta:                                                      ← NEW
   │  ├─ method = HTTPMethod(meta["method"].upper())   (bad verb → ValueError, server fails)
   │  ├─ add <method> <path>  → root callback, body/field params
   │  └─ add <method> <path>  → node callback, _jac_spawn_node as PATH  (same route; unreachable)
   └─ else:
      ├─ add POST /walker/<name>/{node}   (unchanged)
      └─ add POST /walker/<name>          (unchanged)
```

### 6.4 Handling a request

```text
GET /custom/query  (Authorization: Bearer <token>, JSON body {"val": "testval"})
├─ route match → first registered custom route (root variant)
├─ params from create_walker_parameters(invoke_on_root=True)
│  └─ "val" read from body, not query string   (TODO left in code)
├─ walker spawned on user's root
└─ response: {"data": {"reports": [{"message": "Query walker ran", "val": "testval"}]}}
```

| Scenario | Before | After |
|---|---|---|
| Walker without `@meta` | `POST /walker/X`, `POST /walker/X/{node}` | Same |
| `@meta(path="/a", method="POST")` | Decorator didn't exist | `POST /a` runs on root; `/walker/X` routes **gone** |
| `@meta(..., method="GET")` with fields | — | `GET /a` works only if fields are sent in a body |
| Run decorated walker on a specific node | `POST /walker/X/{node}` | No working route |
| `@meta(method="FOO")` | — | Server start fails with `ValueError` |
| jac-scale hook not registered | — | Hook returns `None`; default routes |

**User-visible change:** Adding `@meta` to a walker *replaces* its default routes. It does not add new ones alongside them.

## 11. Questions your senior might ask

**Q: Why put `meta` in core instead of jac-scale?**
A: Core stays generic. It stores the data and declares a hook, and any server plugin can use them. This follows @Thamirawaran's comment and commit `e32c782` ("move to the core").

**Q: What happens if jac-scale isn't installed but a walker uses `@meta`?**
A: The decorator still sets `__meta__`. No plugin answers `get_walker_specs`, so `firstresult` returns `None` and nothing reads the attribute.

**Q: Why do you register two endpoints with the same path and method?**
A: The intent was to mirror the default root and node pair. As written, the second route has no `{node}` placeholder, so it can't be reached. It needs a distinct path.

**Q: Why does `jac_scale/__init__.py` register the plugin now?**
A: The PR doesn't explain this. You need to answer it, and check that jac-scale isn't already registered by its normal loading path. A second instance would run non-`firstresult` hooks twice.

**Q: How do GET walkers get their arguments?**
A: Today they come from the JSON body. The test sends a body with GET. The TODO in `create_walker_parameters` admits these should be QUERY parameters.

**Q: Does adding `@meta` break existing clients?**
A: Yes, for that walker. Its `/walker/<Name>` routes are no longer registered.

**Q: What if two walkers use the same path and method, or an invalid method?**
A: Nothing checks for duplicates, so the routes collide. An invalid method raises `ValueError` from `HTTPMethod(...)` at server start.

**Q: Does this close issue #4299?**
A: Only partly. Path and method are done. Headers, query params, timeout and the client-side `__meta__` usage from the issue are not.

**Q: Why a new `JacPlugin` spec class instead of adding the hook where the other hooks are declared?**
