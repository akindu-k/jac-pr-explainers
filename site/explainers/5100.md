## 1. The short version

`ExecutionContext` is the runtime object that holds the state for one run of Jac code: memory, reports, and the graph roots the code starts from. Three of its fields point at graph nodes: `system_root`, `user_root` and `entry_node`. **They were declared as `NodeAnchor | None` ("an anchor or nothing"), but `postinit` always fills them with a real anchor. So the type checker treated every read of them as "might be `None`".**

Your first commit (f69dcb0) satisfied the type checker by adding `if jroot ...` null checks in access-control and persistence code. @kugesan1105 pointed out that this was a workaround, not a real fix. You then changed approach.

**The final PR removes `| None` from the three field annotations in `jac/jaclang/runtimelib/context.jac`, so code that reads them no longer needs null guards.** It also adds one release-note line. Code behaviour at runtime is unchanged. Only the declared types change.

**Status:** Merged on 2026-03-25. @kugesan1105 approved it, and all test and lint checks passed. One follow-up remains: the release note is in the wrong section, and you said PR #5296 will move it.

## 3. The problem, step by step

### 3.1 The setup

- `ExecutionContext` declares `system_root`, `user_root` and `entry_node` with `by postinit`.
- `ExecutionContext.postinit` (not shown in the diff) sets them. The release note says `user_root` and `entry_node` default to `system_root`.
- Runtime code reads these fields: access checks (`check_access_level`), persistence (`save`), and possibly other places this PR doesn't show.
- The Jac type checker reads the declared type, not what `postinit` actually does.

### 3.2 What went wrong

```text
1. ExecutionContext is declared:
      user_root: NodeAnchor | None by postinit         ← WRONG: claims it can be None
2. At runtime, postinit runs and sets user_root = <NodeAnchor> (never None)
3. Runtime code reads jctx.user_root and uses it as a NodeAnchor
4. Type checker sees type "NodeAnchor | None" → reports a possible-None error
5. Commit f69dcb0 adds guards: `if jroot ...`, checks on `to` and `jctx.user_root`
      → errors go away, but the guards can never be false at runtime
6. @kugesan1105: "This feels like a workaround to enable type checking."
```

The wrong step is 1. Steps 4 and 5 are consequences of it.

### 3.3 Why it mattered

- The incorrect type made the type checker report false errors on valid runtime code.
- The only quick fix was to add guards that never fail. They add noise and suggest to readers that `None` is possible when it isn't.
- @kugesan1105 suggested improving the type checker instead. You replied, with a screenshot (its content isn't visible in this data), that removing the `None` cases fixes the root cause. The reviewer then approved.

No issue is linked, so who first hit this can't be told from the PR.

## 4. The idea of the fix (one sentence)

> **Make the declared type match reality.** Since `postinit` always assigns a `NodeAnchor`, declare the fields as `NodeAnchor` and drop `| None`.

This fixes the source of the false errors in one place. It doesn't patch each caller, and it doesn't teach the type checker to understand `postinit`, which would be a bigger and riskier change.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/context.jac`: field types made non-optional

```diff
 obj ExecutionContext {
     has mem: Memory by postinit,
         reports: list[Any] = [],
         custom: Any = MISSING,
-        system_root: NodeAnchor | None by postinit,   # OLD: may be None
-        user_root: NodeAnchor | None by postinit,     # OLD: may be None
-        entry_node: NodeAnchor | None by postinit,    # OLD: may be None
+        system_root: NodeAnchor by postinit,          # NEW: always an anchor
+        user_root: NodeAnchor by postinit,            # NEW
+        entry_node: NodeAnchor by postinit,           # NEW
         call_state: ContextVar[CallState] = ContextVar('call_state');
```

**What:** The three fields are now typed as plain `NodeAnchor`. They are still set by `postinit`.

**Why:** This removes the false "may be None" type. Readers of these fields now type-check without guards.

**Things to notice:**
- This is annotation-only. The generated runtime behaviour is unchanged.
- `mem: Memory by postinit` already used the same non-optional pattern, so the new fields are consistent with it.
- The new type is only correct if every `postinit`, including `JScaleExecutionContext.postinit`, always assigns these fields. The diff doesn't show either `postinit` body, so that claim rests on your description.
- Any code that assigns `None` to these fields would now be flagged by the type checker. CI passed, so the checked code apparently has none.

### 5.2 `docs/docs/community/release_notes/jaclang.md`: release note

## 6. How execution flows after the PR

The PR doesn't change how code runs. It only changes what the type checker believes about three fields.

### 6.1 Creating an execution context (runtime, unchanged)

```text
ExecutionContext() is constructed
└─ postinit runs
   ├─ sets mem
   ├─ sets system_root = <NodeAnchor>
   ├─ sets user_root   = <NodeAnchor> (defaults to system_root, per release note)
   └─ sets entry_node  = <NodeAnchor> (defaults to system_root, per release note)
```

### 6.2 Type-checking code that reads the fields

```text
Jac type checker visits `jctx.user_root.<something>`
├─ looks up declared type of user_root
│  └─ gets NodeAnchor                       ← CHANGED (was NodeAnchor | None)
└─ attribute access / argument passing accepted
   └─ no "may be None" error, no guard needed   ← CHANGED
```

| Scenario | Before | After |
|---|---|---|
| Read `ctx.user_root` and use it as an anchor | Type error unless guarded | OK |
| Runtime value of `ctx.user_root` | A `NodeAnchor` | A `NodeAnchor` (same) |
| Code assigns `None` to `ctx.entry_node` | Accepted by checker | Flagged by checker |

Users won't notice any change in program behaviour. Only people who type-check runtime code, or who extend it, see a difference.

## 11. Questions your senior might ask

**Q: Does this change anything at runtime?**
No. Only type annotations changed. `postinit` still sets the same values.

**Q: How do you know these fields are never `None`?**
`postinit` always assigns them, with `user_root` and `entry_node` defaulting to `system_root` per the release note. The description says `JScaleExecutionContext.postinit` does the same. `jac-check` and the full test suites pass with the stricter type.

**Q: What if some code reads them before `postinit` runs?**
`by postinit` fields are set right after construction, so normal code can't see them unset. The diff doesn't show any code that runs earlier.

**Q: Why not improve the type checker, as the reviewer suggested?**
The checker was right given the declared type. The declaration was wrong. Fixing the annotation is a one-line root-cause fix. Changing the checker would mean special-casing `by postinit` semantics.

**Q: Your description says you removed null guards. Where are they in the diff?**
They aren't. You added them in f69dcb0 and removed them later in this same branch, so the net diff against `main` has no guard removals. The description wording is misleading.

**Q: Could anything now break for plugin authors?**
Only code that assigns `None` to these fields, or relies on them being optional. The type checker would now flag it. No such code showed up in the CI suites, including jac-scale.

**Q: Why is there no test?**
It is a type-only change. The `jac-check` CI job is the effective test that the codebase type-checks with the new annotations.

**Q: Why is the release note under 0.13.1?**
It was placed in the "Latest Release" section by mistake. The reviewer asked for it to move to unreleased, and you said PR #5296 handles that.
