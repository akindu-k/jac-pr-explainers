## 1. The short version

`jac scale deploy` takes a Jac project, picks one folder, zips it and sends it to a Kubernetes cluster. A *workspace* project lists several apps in `jac.toml`: one served app plus service apps. Every one of those apps has to sit inside the zipped folder.

**The bug: the deploy chose the folder that holds the entry file (`web/`), not the project root. Any service that sat beside it (`core/svc.jac`) fell outside the zip.** The deploy then refused:

```
Deploy failed: app 'svc': entry '<root>/core/svc.jac' resolves outside the
deployed tree '<root>/web', so the bundle cannot ship it. Deploy from the
project root.
```

The message told users to deploy from the project root, which they were already doing. The only workaround was a dummy `main.jac` at the root, passed as the argument.

**The fix: a new helper, `deployed_tree`, returns the project root as the folder to ship when the project is a workspace. It also rewrites the entry path relative to that root (`web/main.jac`).** The terminal deploy, the SDK deploy, `destroy` and `status` all use it now. The last two matter because all four commands must read the same `.env`. Projects that are not workspaces behave as before.

**Status:** Merged on 2026-09-24. All CI checks on the head commit passed or were skipped. @MusabMahmoodh left a "commented" review with four inline notes and two general points. None of them has a visible reply or follow-up commit, so they remain open.

## 3. The problem, step by step

### 3.1 The setup

```
myproject/
├── jac.toml        [apps.web] entry-point="web.main", [apps.svc] entry-point="core.svc", default-app="web"
├── web/main.jac    served app
└── core/svc.jac    service app
```

The pieces involved:

- `KubernetesRealizer.realize` (terminal), `ScaleClient._app_config` (SDK), and `deploy_destroy` / `deploy_status` (plugin) each worked out a folder from the entry file.
- The realizer used that folder for two jobs. It was the tree to zip, and it was the reference point for the fleet's containment check (`_resolve_fleet(code_folder)`).

### 3.2 What went wrong: terminal deploy

```text
1. User runs (from myproject/): jac scale deploy web/main.jac --target kubernetes --dry-run
   (no-arg and "web" forms resolve to the same entry, web/main.jac)
2. realize(): filename = "web/main.jac"
3. code_folder = os.path.dirname(filename) or '.'      -> "web"            ← WRONG STEP
4. _resolve_fleet("web") builds the fleet: web (web/main.jac), svc (core/svc.jac)
5. Containment check: is <root>/core/svc.jac inside <root>/web ?  -> No
6. Deploy failed: app 'svc' ... resolves outside the deployed tree '<root>/web' ... Deploy from the project root.
   (The current directory was never used, so "deploy from the project root" changes nothing.)
```

Here is why the placeholder worked: `jac scale deploy main.jac` gives `dirname("main.jac")` = `"."`, which is the root. With no argument, the issue's table shows it still failed, because the default app's own entry (`web/main.jac`) was used.

### 3.3 What went wrong: SDK deploy

```text
1. ScaleClient._app_config(spec)
2. (code_folder, file_name) = spec.resolve_entry()       -> ("…/web", "main.jac")   ← WRONG STEP (same bug, written separately)
3. AppConfig(code_folder="web", file_name="main.jac")    -> tree excludes core/
```

### 3.4 The hidden `.env` split (appears once the deploy is fixed)

```text
1. Fix the deploy only: deploy now uses tree = <root>, reads <root>/.env       -> NS=prod
2. destroy still does dirname(web/main.jac) = web, reads web/.env              -> NS=staging
3. namespace = "${NS}" resolves differently for the two commands
4. destroy deletes a different namespace than the deploy created               ← DANGER
```

That is why `plugin.jac` is changed in the same PR (commit 1beb6ad).

### 3.5 Why it mattered

- Every multi-folder workspace needed a dummy root file to deploy, including the repo's own `jac/examples/jaclang_org` (issue #9256).
- jaclang.org had been deployed with that placeholder since 2026-09-11. Once jachammer bound it to this repo without the placeholder, the next deploy failed (issue).
- The error text sent users to the wrong cause (the working directory).
- @udithishanka confirmed it on 0.37.18 and 0.37.21.
- @MusabMahmoodh pointed out a quieter effect. With the tree at `web/`, `sanitized_jac_toml` found no `jac.toml`, so the placeholder toml was staged and the root `arch.jac` never shipped.

## 4. The idea of the fix (one sentence)

> **For a workspace, ship the project root and address the entry inside it.** When `jac.toml` declares `[apps]`, the deployed tree is the folder holding `jac.toml`, and the entry path becomes relative to it (`web/main.jac`).

The project root is the only folder sure to contain every declared app. Your description also notes that changing the containment check or its message would have hidden the bug instead of fixing it.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/config/app_config.jac`: the new `deployed_tree` helper

```diff
+import os;
 import from pathlib { Path }
+import from jaclang.project.config { get_config_for_dir }
+
+def deployed_tree(entry_path: str) -> tuple[str, str] {
+    folder = os.path.dirname(entry_path) or '.';                  # the OLD answer
+    cfg = get_config_for_dir(folder);                              # walks up to jac.toml
+    if cfg is None or not cfg.is_workspace or cfg.project_root is None {
+        return (folder, os.path.basename(entry_path));             # not a workspace: unchanged
+    }
+    base = Path(cfg.project_root).resolve();
+    try {
+        return (str(base), Path(entry_path).resolve().relative_to(base).as_posix());  # NEW: (root, "web/main.jac")
+    } except ValueError {
+        return (folder, os.path.basename(entry_path));             # entry outside root: old answer
+    }
+}
```

**What:** It returns two values that must change together: the folder to ship and the entry path inside that folder. For a workspace this is `(<abs root>, "web/main.jac")`. In every other case it is exactly the old `(dirname, basename)`.

**Why:** It replaces the one bad line (`dirname`) at every call site with a single shared rule.

**Things to notice:**
- The entry name has to change along with the folder. Keeping `main.jac` while shipping the root would point at a file that is not there.
- `as_posix()` keeps forward slashes on Windows, which matters because the path is used inside a Linux container.
- In the workspace case the folder is absolute and resolved. In the fallback case it stays relative. Both callers later run `os.path.relpath`, so this does not matter downstream.
- The `except ValueError` fallback is the subject of an open review comment (9.2 #2). Your description says it "cannot be reached in practice". @MusabMahmoodh points out that a symlinked entry, which `resolve()` follows, *could* reach it, and the user would then get the original containment error back without explanation. He suggested reusing `_member_file` from `runtime/fleet.jac`, which raises a clear error.
- Gating on `is_workspace` is deliberate per your description ("Single-app projects are unaffected"). @MusabMahmoodh asked whether that is right for a single-app project with `entry-point = "src.main"` (open, 9.2 #3).

### 5.3 `jac/jaclang/scale/sdk/client.jac`: SDK deploy uses the helper

```diff
-        (code_folder, file_name) = spec.resolve_entry();
```

**Why:** The SDK had its own copy of the same bug. The issue did not mention it.

**Things to notice:** @MusabMahmoodh's inline comment is still open. ### 5.4 `jac/jaclang/scale/plugin.jac`: `destroy` and `status` read the same tree

```diff
+import from .config.app_config { deployed_tree }
@@ deploy_destroy
-    code_folder = os.path.dirname(file_path) or '.';
```

- With `plugin.jac` counted twice, there are four call sites in three files. That is why the description says "three call sites" in one place and "four call sites" in another.

## 6. How execution flows after the PR

### 6.1 `jac scale deploy` (terminal)

```text
jac scale deploy [web/main.jac | web | <none>] --target kubernetes
└─ KubernetesRealizer.realize(filename="web/main.jac")
   ├─ file exists?                                   (unchanged)
   ├─ deployed_tree(filename)                        ← NEW
   │  ├─ folder = "web"
   │  ├─ get_config_for_dir("web") → walks up → <root>/jac.toml
   │  ├─ is_workspace? yes → base = <root> (resolved)
   │  └─ return (<root>, "web/main.jac")
   ├─ _resolve_fleet(<root>)                         ← CHANGED (was web/)
   │  └─ containment check: web/main.jac ✓, core/svc.jac ✓
   ├─ banner: "Deploying 1 service app plus 'web' behind a gateway."
   ├─ code_folder = relpath(<root>) → "."
   └─ AppConfig(code_folder=".", file_name="web/main.jac", served_app=…)   ← CHANGED
      └─ dry-run: print plan / real: hand off to pinned toolchain (unchanged)
```

### 6.2 SDK deploy

```text
ScaleClient._app_config(spec)
├─ spec.resolve_entry() → ("…/web", "main.jac")    (unchanged; raises if spec.source is a folder with no main.jac)
├─ deployed_tree("…/web/main.jac") → (<root>, "web/main.jac")   ← NEW
└─ AppConfig(code_folder=relpath(<root>), file_name="web/main.jac", served_app=spec.app)
```

### 6.3 `destroy` / `status`

```text
deploy_destroy(file_path) / deploy_status(file_path)
├─ deployed_tree(file_path) → (<root>, _)          ← CHANGED
├─ load_project_env(<root>) → reads <root>/.env    ← CHANGED (was web/.env)
└─ get_scale_config() → ${VAR} (e.g. namespace) now matches the deploy
```

| Scenario | Before | After |
|---|---|---|
| Workspace, `deploy web/main.jac`, no root file | Fails: containment error | Ships root; entry `web/main.jac` |
| Workspace, `deploy` (no arg) or `deploy web` | Fails (even with placeholder) | Works (CI binary run, dry-run) |
| Workspace, placeholder passed as `deploy main.jac` | Works, tree = root | Same result |
| Single app, `jac.toml` + `main.jac` at root | Tree = root | Unchanged |
| Single app (no `[apps]`), entry `src/main.jac` | Tree = `src/`, placeholder toml staged | Unchanged (open question 9.2 #3) |
| No `jac.toml` | Tree = entry folder | Unchanged |
| Workspace with `web/.env` | Read by all commands | **Not read**: move it next to `jac.toml` |
| SDK, `source` = workspace folder with no `main.jac` | Fails "has no main.jac" | Still fails (open 9.2 #1) |
| Real deploy of a workspace pinned to ≤0.37.21 | Fails | Still fails until the pin moves |

Behaviour changes users will notice:

1. `.env` location for workspaces moves to the project root.
2. The bundle now includes the whole root, so sibling trees like `mobile/` or `desktop/` ship unless `.jacignore` excludes them.
3. Per @MusabMahmoodh, the workspace's real `jac.toml` and root `arch.jac` now ship instead of a placeholder toml.

## 11. Questions your senior might ask

**Q: Why not just fix the containment check or its message?**
The check was right. It was handed the wrong folder. Loosening it would ship a bundle that is missing the service.

**Q: Why does `deployed_tree` return two values?**
The folder and the entry path must change together. Shipping the root while recording `main.jac` would point at a missing file.

**Q: Why only for workspaces?**
Only a workspace declares several apps that must share one tree. Non-workspace projects keep their old behaviour. @MusabMahmoodh's question about `src.main` single-app projects is still unanswered.

**Q: Why touch `destroy` and `status` at all?**
`.env` is read from the tree folder with no walk-up. Without the change, `destroy` could resolve `${namespace}` from `web/.env` while the deploy used `<root>/.env`, and delete the wrong namespace.

**Q: Will existing users break?**
Workspaces that kept `.env` beside the served app must move it next to `jac.toml`. Workspace bundles also get bigger, since the whole root ships unless `.jacignore` trims it.

**Q: Does this fix jaclang.org today?**
Not on its own. Real deploys hand off to the pinned jac (`==0.37.21`), which lacks this fix. `jaclang_org` also fails to compile on its pin, for a separate reason (#9447 / #9437).

**Q: Is the SDK fully fixed?**
Only when you point it at an entry file. Pointing it at the workspace folder still fails in `resolve_entry` (@MusabMahmoodh's open comment).

**Q: What proves the shipped binary works, not just the source?**
The fork CI run built a binary and ran it with `JAC_NO_DEV_SOURCE=1` in dry-run. Both forms reached fleet assembly with both apps. It stopped on missing `yaml` and did not test the pinned handoff.

**Q: When can the `except ValueError` branch fire?**
When the resolved entry is not under the resolved project root, for example through a symlink. It then silently returns the old folder, so the user sees the old containment error.

**Q: Is the new tree tested end to end through manifests and bundle staging?**
No. `print_plan` is patched in the new tests. A subprocess dry-run test was suggested but not added.
