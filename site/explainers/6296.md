## 1. The short version

`JacAPIServer` is the HTTP server that serves a Jac app's walkers and, for client apps, its HTML pages. In tests, `JacTestClient` runs this server in the same Python process as the tests. It calls the request handler directly, without opening a network port. To decide what `GET /` should return, the handler read the project config from `get_config()`. That function returns one config object shared by the whole process.

**The SPA tests in `test_serve_client.jac` changed that shared config with `set_config(... base_route_app="client_page")` and only reset it on their last line, so a failed assertion left the change in place. A later test on the same pytest-xdist worker (`get root endpoint`) then had `GET /` routed to a page that did not exist, got a 500, and failed with `assert response.ok` → `AssertionError`.** The issue (#6169) says this happened about 1 run in 20.

**Your fix gives each `JacAPIServer` its own config, read once at startup from its own `base_path` (plus the profile / `jac.local.toml` overlay). The request router reads that private copy instead of the shared one, and the SPA tests now write a real `jac.toml` into their temp folder instead of calling `set_config()`.** You also added one regression test for the overlay case.

**Status:** Closed as a draft on 2026-06-01 without merging. Your own comment says it is "addressed by #6318". There were no reviews. All CI checks passed except `minikube real-app smoke`, which failed.

| `JacConfig` | The Python/Jac object that holds a parsed config. |

| `apply_profile_overlay(profile)` | A `JacConfig` method that merges `jac.local.toml` and the profile file on top of the base config. |
| `active_profile` | The name of the profile in use, taken from the global config. |

| `ServeConfig.base_route_app` | A setting that says "serve this client page for `/` and for unknown clean URLs". This is the SPA catch-all. |

## 3. The problem, step by step

### 3.1 The setup

- **`do_GET`** in `server.impl.jac` did this on every request:
  ```jac
  import from jaclang.project.config { get_config }
  config = get_config();
  ```
  Routing for `/` depends on `config.serve.base_route_app`. If it is set, the server renders that client page.
- **The client-error logging endpoint** (also in `create_handler`) read `get_config().client_errors.verbose` in the same way.
- **`make_spa_client`** in the tests set the global config:
  ```jac
  set_config(JacConfig(serve=ServeConfig(base_route_app="client_page")));
  ```
- **Every SPA test** ended with `spa.close(); set_config(JacConfig());` to reset the config. This line was not in a `finally` block.
- **`get root endpoint`** (in `test_testing.jac`) serves `serve_api.jac`, which has no client bundle. It expects `GET /` to return 200.

### 3.2 What went wrong

This is the timeline your PR description gives:

```text
1. xdist worker gw1 starts; global config = JacConfig()                 (base_route_app = None)
2. gw1 runs a SPA test → make_spa_client → set_config(base_route_app="client_page")
3. An assertion in that SPA test fails before the last line
   → set_config(JacConfig()) never runs                                  ← WRONG: no cleanup
4. Global config on gw1 is still base_route_app="client_page"
5. gw1 runs "get root endpoint" (serve_api.jac, no client bundle)
6. do_GET("/") → get_config() → base_route_app="client_page"            ← WRONG: reads leaked global
7. do_GET → _render_page("client_page") → RuntimeError
8. Handler returns 500 → `assert response.ok` → AssertionError
```

The issue's own hypothesis was different. It blamed shared module state (`Jac.loaded_modules`, `ModuleIntrospector._walkers`) and races between workers. Your PR names a different cause: the shared config leaking between tests that run **one after another in the same worker**, not a race between workers. The CI logs listed in the PR only show `get root endpoint` failing. The diff does not show the SPA test failure that supposedly came first.

### 3.3 Why it mattered

- The issue says the failure happened in about 1 of 20 runs. It was seen on `main` and on unrelated branches. The PR links three CI runs (26417727074, 26466744981, and the run for PR #6294).
- Because CI uses `-x`, one flaky failure stops the whole run. Unrelated PRs went red and had to be re-run.
- The underlying design issue goes beyond tests. Any code in the process that calls `set_config()` could change routing for every server in that process.

## 4. The idea of the fix (one sentence)

> **Each server owns its config.** `JacAPIServer` reads its config once from its own `base_path` (with overlays) and the request handler uses that copy instead of the process-wide singleton.

This fixes the cause, not just the symptom. A `try/finally` around `set_config()` in the tests would stop this one leak. It would still leave any other `set_config()` caller able to change one server's routing through another.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/server.jac`: declare the new field

```diff
-import from jaclang.project.config { get_config }
+import from jaclang.project.config { get_config, JacConfig }
 ...
         is_sv_sibling: bool = False,
+        _app_config: (JacConfig | None) by postinit,
         user_manager: UserManager by postinit,
```

**What:** You added a private field `_app_config` to `JacAPIServer`. It is filled by `postinit`. You also imported `JacConfig` so the type can be named.

**Why:** It gives the server a place to keep its own config.

**Things to notice:**
- Your PR description says the field is declared `= None`. The code uses `by postinit` instead. The description is out of date.
- `get_config` is still imported here. The diff does not show where else this file uses it.

### 5.2 `jac/jaclang/runtimelib/impl/server.impl.jac`: load the config at startup, read it per request

**Startup (`postinit`):**

```diff
     self.scheduler = Scheduler.instance();
+    self._app_config = JacConfig.discover(
+        start_path=Path(self.base_path) if self.base_path else None
+    );
+    if self._app_config is not None {
+        _existing_cfg = get_config();
+        _active_profile = _existing_cfg.active_profile if _existing_cfg else None;
+        self._app_config.apply_profile_overlay(_active_profile or None);
+    }
```

**What:**
1. `discover` finds `jac.toml` from `base_path`.
2. If a config was found, the code takes only the **profile name** from the global config.
3. It then merges `jac.local.toml` and the profile file on top.

**Why:** It builds a per-server copy that matches what the CLI would build, without depending on the global object's values.

**Things to notice:**
- Your comment explains why the overlay step exists. Without it, `--profile` and `jac.local.toml` values for `[serve]` and `[plugins.client]` would be used by `get_config()` readers (the startup banner, response headers) but ignored by the router. The new overlay test covers this.
- `_active_profile or None` turns an empty string into `None`.
- If `base_path` is empty, `discover(start_path=None)` is called. The diff does not show what `discover` does then. It probably falls back to the current directory, but that is not confirmed.
- If no `jac.toml` is found, `_app_config` stays `None`. The handler already handled `config` being `None` (`if config else None`).
- The copy is a **snapshot**. Changes to the global config after the server is built are no longer seen by the router.
- The server still reads `get_config()` in one place: to get the profile name, at construction time. A leaked profile name could still reach the server, but no config values can.

**Request routing (`do_GET`):**

```diff
             is_static_path = path.startswith('/static/');
-            import from jaclang.project.config { get_config }
-
-            config = get_config();
+            config = server._app_config;
             client_cfg = config.get_plugin_config("client") if config else None;
```

**What:** `do_GET` now uses the server's own config for routing and client asset settings.

**Why:** This is the line that caused the 500. Leaked global state can no longer reach it.

**Client-error logging endpoint:**

```diff
-                    import from jaclang.project.config { get_config }
                     ...
-                        cfg = get_config();
+                        cfg = server._app_config;
                         verbose = cfg.client_errors.verbose if cfg else False;
```

**What:** `client_errors.verbose` now comes from the server's own config.

**Why:** For consistency. Without this change, the same server would read two different configs depending on the endpoint.

**Things to notice:** Other `get_config()` readers, such as the startup banner and response headers mentioned in your comment, were left alone on purpose. The diff does not show them.

### 5.3 `docs/docs/community/release_notes/unreleased/jaclang/6296.bugfix.md`: release note

```diff
+- **Fix: Eliminate intermittent `GET /` 500 failure under parallel test runs**: `JacAPIServer` now snapshots its routing config from its own `base_path` at startup (resolving profile and `jac.local.toml` overlays the same way the CLI does) instead of reading the shared process-level singleton on each request. ...
```

## 6. How execution flows after the PR

### 6.1 Building a server

```text
JacAPIServer(...)  (via JacTestClient.from_file or the CLI)
├─ postinit
│  ├─ user_manager, execution_manager, introspector, scheduler set up
│  ├─ JacConfig.discover(start_path=base_path or None)            ← NEW
│  ├─ if found:
│  │  ├─ profile = get_config().active_profile                    ← NEW (name only)
│  │  └─ _app_config.apply_profile_overlay(profile or None)       ← NEW
│  └─ if port > 0 → Jac.create_server(...)
└─ server ready; _app_config is fixed from now on
```

### 6.2 Handling `GET /`

```text
do_GET(path="/")
├─ is_static_path = path.startswith('/static/')
├─ config = server._app_config                                   ← CHANGED (was get_config())
├─ client_cfg / assets from config
└─ base_route_app set in config?
   ├─ yes → _render_page(base_route_app) → HTML
   └─ no  → normal API root response
```

### 6.3 Client-error logging endpoint

```text
POST client error
├─ rate limiter says throttle? → 200 {ok, throttled}
└─ else
   ├─ cfg = server._app_config                                    ← CHANGED
   └─ verbose = cfg.client_errors.verbose → format/log
```

| Scenario | Before | After |
|---|---|---|
| A SPA test leaks `set_config(base_route_app=...)`, then `get root endpoint` runs on the same worker | 500, `AssertionError` | 200 (leak ignored) |
| `base_route_app` set in the project's `jac.toml` | Worked (the CLI loaded it into the global config) | Works (loaded from `base_path`) |
| `base_route_app` set only in `jac.local.toml` | Worked via the global config | Works via `apply_profile_overlay` (new test) |
| Code calls `set_config()` **after** the server is built | Router saw the new value | **Router ignores it** |
| Config is set only through `set_config()` and there is no `jac.toml` in `base_path` | Router used it | **Router does not see it** (`_app_config` is `None` or comes from another file) |

**Behaviour change to call out:** routing config is now frozen at server construction and tied to `base_path`. Any production or plugin path that sets serve or client config programmatically, instead of through files, would stop affecting routing. The diff does not show whether any such path exists, for example in jac-scale or jac-client. The failing `minikube real-app smoke` check is the place to look for that.

## 11. Questions your senior might ask

**Q: Why did a config leak cause a 500 and not a 404?**
`base_route_app="client_page"` made `do_GET` call `_render_page("client_page")`. `serve_api.jac` has no client bundle, so `_render_page` raised `RuntimeError`, which became a 500.

**Q: The issue blamed module state and races between workers. Why do you think it's config?**
xdist workers are separate processes, so they cannot share a singleton. The leak has to come from an earlier test in the same worker. The SPA tests changed a global and reset it only on their last line, and the symptom (`GET /` failing) matches exactly what a leaked `base_route_app` does. This is reasoning from the code. The diff and linked logs do not prove it.

**Q: Wouldn't a `try/finally` in the tests have been enough?**
It would stop this specific leak. It would still let any `set_config()` caller change routing for every server in the process. Giving the server its own config removes that whole class of bug.

**Q: Why apply the profile overlay, and why read the profile name from `get_config()`?**
`discover()` loads only `jac.toml`. Without the overlay, `jac.local.toml` and `--profile` settings would apply to the banner and headers but not to routing. The profile name comes from the CLI flag, so the global config is where it is available. All config *values* still come from `base_path`.

**Q: What changes for real users?**
Routing config is read once when the server is built. Changing the config at runtime with `set_config()` no longer affects routing. Config that is not on disk under `base_path` is also not seen by the router.

**Q: Could that explain the minikube smoke failure?**
Possibly, but the data here does not show it. Check the job log, and check whether the deployed app's `base_path` has its `jac.toml`.

**Q: What if `base_path` is empty or there is no `jac.toml`?**
`discover` is called with `None` (behaviour not visible in the diff). If nothing is found, `_app_config` is `None`, and the handler already treats `None` as "no client config". The 404 test covers the "no `jac.toml`" case.

**Q: Which readers still use the global config?**
Your comment names the startup banner and response headers. They were not changed. The overlay step keeps them in line with the router in normal CLI use.

**Q: Why was this PR closed?**
Your comment says #6318 addresses the issue. This PR does not say what #6318 does differently, so read it before the meeting.
