## 1. The short version

`jac scale deploy` puts your app on Kubernetes. Your app signs login tokens (JWTs) with a secret called `JAC_SERVE_AUTH_SECRET`. The secret is stored in a Kubernetes Secret named `{app}-secrets`. If you did not configure one, the deploy code made one up: a random `secrets.token_urlsafe(48)` string.

**The bug: a new random secret was minted on every deploy and written over the live Secret. Every redeploy therefore signed out every user and invalidated every issued token. Changing the Secret also rolled (restarted) every pod.** The deploy still reported success. `--show-yaml` and dry runs showed their own throwaway random value, so the rendered manifest never matched what a real deploy applied.

**The fix: the manifest builder now renders a fixed placeholder (`PLACEHOLDER_JWT_SECRET`) instead of a random value. Just before the Secret is written, a new function `resolve_signing_secret` reads the live Secret. It reuses the existing value, and it mints a new one only when there is none (or only the placeholder).** Any other read error, such as 403 Forbidden, stops the deploy instead of silently re-keying. The first time a secret is minted, one log line tells the user to set `[scale.secrets] JAC_SERVE_AUTH_SECRET`.

**Status:** Merged on 2026-10-02. @MusabMahmoodh approved on 2026-09-30 after you addressed his three inline comments. All CI checks on the head commit `a8caf45` passed or were skipped.

## 3. The problem, step by step

### 3.1 The setup

- `ManifestBuilder._signing_secret` picks the signing secret in this order: `[scale.secrets]`, then serve settings (`[serve.auth]`), then a minted random value.
- `_build_user_secret_manifest` puts that value into the user Secret's `stringData`.
- `KubernetesTarget` (in `target.jac`) calls `create_k8s_secret`. That call tries create, and on 409 it calls replace.
- Pods read the Secret by `envFrom`. The Secret's `resourceVersion` is stamped on the pod template.

### 3.2 What went wrong: redeploy with no configured secret

```text
1. Deploy #1: new ManifestBuilder, _minted_secret = ""
2.   _signing_secret → mints "Ab3x..."           (no config anywhere)
3.   create_k8s_secret → creates app-secrets {JAC_SERVE_AUTH_SECRET: "Ab3x..."}, rv=10
4.   Pods start, sign JWTs with "Ab3x...". Users log in.
5. Deploy #2 (any change, or none): new ManifestBuilder, _minted_secret = ""
6.   _signing_secret → mints "Qz9k..."           ← WRONG: memo was per-builder, lost
7.   create_k8s_secret → 409 → replace app-secrets with "Qz9k...", rv=11   ← WRONG: live value overwritten
8.   Pod template revision 10 → 11 → every pod rolls
9.   New pods verify tokens with "Qz9k..." → every old token gets 401, everyone signed out
10.  Deploy prints success. Nothing mentions the re-key.
```

### 3.3 What went wrong: rendered manifests lie

```text
1. jac scale deploy --show-yaml → new builder → mints "Mm1p..." → printed
2. Real deploy → new builder → mints "Tt7r..." → applied
3. The YAML you reviewed never matched what was applied   ← WRONG
```

### 3.4 Why it mattered

Issue #9080 says the no-secret path is the documented quickstart path, because the key has no default. So the default setup logged out every user and broke every client token on each deploy, with no warning. It also forced a full fleet roll even when nothing else changed.

## 4. The idea of the fix (one sentence)

> **The cluster is the source of truth for the signing secret.** Render a placeholder at build time, and at apply time reuse the live Secret's value, minting only when none exists.

This keeps manifest rendering free of cluster access (dry runs and `--show-yaml` stay offline). It also makes redeploys idempotent: re-running with the same input gives the same Secret. @kugesan1105 summed it up as "cluster is the source of truth. JWT will only create if it is missing."

- **What:** When neither `[scale.secrets]` nor serve settings give a secret, the builder returns the placeholder constant. The `_minted_secret` memo field is gone.
- **Why:** The builder can't know the live value without calling the cluster, and it must not call the cluster. So it leaves a marker for the apply step to fill in. This also fixes the `--show-yaml` mismatch: rendered output shows the placeholder, never a fake real value.
- **Things to notice:**
  - Removing the `_minted_secret` constructor field would break any caller that passed it. The diff doesn't show other callers, so this can't be confirmed either way.
  - Per @MusabMahmoodh's review, `_signing_secret` has one caller, and the `plan.jac` uses are display-only.

### 5.2 `jac/jaclang/scale/deploy/target/kubernetes/utils/kubernetes_utils.impl.jac` and `kubernetes_utils.jac`: new `resolve_signing_secret`

```diff
+impl resolve_signing_secret(core_v1, namespace, secret_name, secret_data: dict[str, str]) -> bool {
+    key = "JAC_SERVE_AUTH_SECRET";
+    if secret_data.get(key) != PLACEHOLDER_JWT_SECRET {
+        return False;                                   # configured value: no read at all
+    }
+    live: dict[str, str] = {};
+    try {
+        found = core_v1.read_namespaced_secret(name=secret_name, namespace=namespace);
+        live = found.data or {};
+    } except ApiException as e {
+        if e.status != 404 { raise; }                   # 403 etc. → stop the deploy
+    }
+    try {
+        kept = base64.b64decode(live.get(key) or "").decode("utf-8");
+    } except UnicodeDecodeError {
+        raise RuntimeError(f"The live Secret '{secret_name}' in namespace '{namespace}' holds a "
+            f"{key} that is not valid UTF-8. Fix or delete that key, then redeploy.") from None;
+    }
+    if kept and kept != PLACEHOLDER_JWT_SECRET {
+        secret_data[key] = kept;                        # reuse live value
+        return False;
+    }
+    secret_data[key] = secrets.token_urlsafe(48);       # mint
+    return True;
+}
```

The `.jac` file adds the matching declaration (`def resolve_signing_secret(...) -> bool;`).

- **What:** The function edits `secret_data` in place and returns `True` only when it minted a new secret.
  1. A configured value passes through untouched, with no API call.
  2. If the field holds the placeholder, it reads the live Secret and base64-decodes the key.
  3. A real live value is reused.
  4. A missing Secret (404), a missing or empty key, or a live placeholder leads to a mint.
- **Why:** This is the "mint once, then persist" fix from the issue.
- **Things to notice:**
  - **Non-404 errors re-raise.** @MusabMahmoodh called this the line that "stops #9080 from coming back". Without it, a deployer lacking `get` on secrets (403) would mint a fresh secret every time.
  - **Live placeholder → mint.** This covers someone applying `--show-yaml` output by hand. Commit `3b551a2` added it.
  - **UTF-8 error message.** Commit `9332068` added it after Musab's nit. `from None` hides the raw `UnicodeDecodeError` chain.
  - **Invalid base64 is not caught.** Bad base64 would raise `binascii.Error` uncaught. The Kubernetes API normally returns valid base64, so this is unlikely.
  - **Removing a configured secret keeps it.** If a user removes a configured secret, the builder renders the placeholder, the function reads the live value, and the old configured value is kept. The release note documents this.
  - **Edge case: a configured value equal to the placeholder.** It would be treated as "not configured". Per the PR description, in-cluster `AuthSettings.resolve_secret` rejects the placeholder anyway. That code is not in this diff.

## 6. How execution flows after the PR

### 6.1 Real deploy (`jac scale deploy`)

```text
jac scale deploy
├─ KubernetesTarget builds a new ManifestBuilder
│  └─ _build_user_secret_manifest
│     └─ _signing_secret
│        ├─ [scale.secrets] set?  → that value
│        ├─ [serve.auth] set?     → that value
│        └─ else                  → PLACEHOLDER_JWT_SECRET            ← CHANGED
└─ apply_manifests
   ├─ resolve_signing_secret(core_v1, ns, "app-secrets", stringData)   ← NEW
   │  ├─ value != placeholder → return False (no read)
   │  ├─ read_namespaced_secret
   │  │  ├─ 404 → live = {}
   │  │  └─ other error (403...) → raise, deploy stops
   │  ├─ decode live key (non-UTF-8 → RuntimeError naming Secret/key)
   │  ├─ real live value → reuse, return False
   │  └─ missing/empty/placeholder → mint token_urlsafe(48), return True
   ├─ minted and logger → log "Minted a JWT signing secret..."         ← NEW
   └─ create_k8s_secret (create, or replace on 409) → resourceVersion
      └─ stamped as config revision on pod templates
```

### 6.2 Rendering only (`--show-yaml`, dry run, SDK `generate_manifests`)

```text
render
└─ ManifestBuilder._signing_secret → configured value or PLACEHOLDER_JWT_SECRET   ← CHANGED
   (no apply_manifests, so no cluster read, per the PR description)
```

| Scenario | Before | After |
|---|---|---|
| First deploy, nothing configured | Mint, create | Read → 404 → mint, create, log once |
| Redeploy, nothing configured | **New mint, replace, all sessions lost, pods roll** | Reuse live value. Per @MusabMahmoodh, an unchanged re-send no longer rolls pods |
| Secret configured | Used | Used, no read |
| Configured secret later removed | Fresh mint | Keeps last value (documented) |
| Live Secret holds placeholder | n/a | Mint real value |
| No `get` permission on secrets (403) | Mint every time | **Deploy fails with ApiException** |
| Live value not UTF-8 | n/a | RuntimeError naming Secret, namespace, key |
| `--show-yaml` output | Random value never applied | Placeholder |
| Apps deployed before the fix | n/a | Keep their last minted value (Musab's review) |

**Behaviour changes users will notice:**
1. Redeploys no longer sign users out.
2. A deployer without `get` on secrets that relies on the minted fallback now fails.
3. Rotation now requires an explicit action: set a new value, or delete `{app}-secrets`.

## 11. Questions your senior might ask

**Q: Why not read the live Secret inside `ManifestBuilder`?**
Because dry runs, `--show-yaml` and the SDK's `generate_manifests` must not touch the cluster. Apply is the only step that already talks to the API.

**Q: What happens if the deployer can't read secrets?**
`read_namespaced_secret` raises a non-404 `ApiException`. It is re-raised, so the deploy stops before `create_k8s_secret` replaces anything. The 403 row tests this. A configured secret skips the read, so those users are unaffected.

**Q: Can the placeholder end up signing tokens in production?**
`resolve_signing_secret` replaces it whenever it is present. The live placeholder case also mints. @MusabMahmoodh checked that `target.jac` is the only apply path for the user Secret. As a last guard, the description says `AuthSettings.resolve_secret` rejects the placeholder in-cluster. That code is not in this diff.

**Q: Do existing apps lose their sessions when they upgrade to this version?**
No. The first deploy after upgrading reads the last minted value from the live Secret and keeps it. Musab confirmed this in his review.

**Q: How does a user rotate the secret now?**
Set a new `[scale.secrets] JAC_SERVE_AUTH_SECRET`, or delete the `{app}-secrets` Secret before redeploying. Removing a configured value keeps its last value. The release note documents this.

**Q: Does a redeploy still roll every pod?**
Not because of this Secret any more. The value is unchanged, and @MusabMahmoodh noted that an unchanged re-send no longer rolls pods. Other config changes still roll pods as before.

**Q: What if someone applied the `--show-yaml` output by hand?**
The live Secret then holds the placeholder. The function treats that as "no secret" and mints a real one. The "live placeholder is replaced" row covers this.

**Q: Why mutate `stringData` in place instead of returning the value?**
The resolved value has to be exactly what `create_k8s_secret` sends. Mutating the bundle's dict does that with no extra plumbing. The `bool` return value only drives the one-time log line.

**Q: Is anything left untested?**
Three things: invalid base64 in the live value (it would raise an uncaught `binascii.Error`), the log line, and the `target.jac` call site. The test mirrors the call site's order but does not call it.
