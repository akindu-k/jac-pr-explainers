# fix(scale): keep the minted JWT signing secret across redeploys (#9080)

[#9551](https://github.com/jaseci-labs/jac/pull/9551) by @akindu-k · opened 25 Sept 2026 · +167 −17 in 6 files

<!-- explainer -->

## In short

When you deployed a Jac app to Kubernetes without setting `JAC_SERVE_AUTH_SECRET`, every redeploy made a brand new random JWT signing secret and overwrote the live one. That signed every user out and restarted every pod. You changed it so the manifest only holds a placeholder, and a new step at apply time reuses the live Secret's value (or mints one only if none exists).

## Words to know

- **JWT (JSON Web Token)**: a signed token the server gives a user after login. The server checks the signature on each request to know the user is logged in.
- **Signing secret (`JAC_SERVE_AUTH_SECRET`)**: the key used to sign and verify those JWTs. If it changes, all old tokens fail to verify and users must log in again.
- **Kubernetes Secret**: a Kubernetes object that stores sensitive values such as keys and passwords. Here it is named `{app}-secrets`.
- **`resourceVersion`**: a value Kubernetes changes every time an object changes. Here it is used as a config revision, so a change rolls the pods.
- **Pod rollout / roll pods**: Kubernetes restarts the pods one by one so they pick up new config.
- **Manifest / `ManifestBuilder`**: the YAML-like description of what to deploy. `ManifestBuilder` is the Jac class that builds it.
- **`PLACEHOLDER_JWT_SECRET`**: a fixed, known dummy string (from `authcrypt`) that stands for "no real secret yet". It must never be used for real signing.
- **`--show-yaml` / dry run**: modes that print or simulate the manifest without touching the cluster.
- **`apply_manifests`**: the step that actually sends the manifests to the cluster.
- **404 / 409 / 403**: HTTP statuses from the Kubernetes API. 404 = not found, 409 = already exists (conflict), 403 = forbidden.
- **RBAC**: Kubernetes permissions. `get` on secrets is the right to read them.
- **`AuthSettings.resolve_secret`**: existing code that, in a cluster, rejects the placeholder so the app fails loudly.
- **Table-driven test**: one test that loops over a list of cases (inputs and expected results).
- **Fake / in-process fake**: a small stand-in class that imitates the Kubernetes API in tests.

## The problem

1. You deploy without `JAC_SERVE_AUTH_SECRET` in `[scale.secrets]` or `[serve.auth]`.
2. `ManifestBuilder._signing_secret` falls back to `secrets.token_urlsafe(48)`, a random value cached only on that builder object.
3. A new builder is created on every deploy, so every deploy has a different random value.
4. `create_k8s_secret` replaces the live Secret with it.

Results:
- Every JWT stops verifying, so all users are signed out on every redeploy.
- The Secret's `resourceVersion` changes, so every pod rolls.
- `--show-yaml` and dry runs each showed their own throwaway value, which was never the one applied.

## The changes, one by one

### `kubernetes_utils.impl.jac` and `kubernetes_utils.jac`

The `.jac` file declares the new function `resolve_signing_secret(core_v1, namespace, secret_name, secret_data) -> bool`. The `.impl.jac` file implements it. It returns `True` only if it minted a new secret.

How it works:
- It reads `JAC_SERVE_AUTH_SECRET` from `secret_data`. If that value is not the placeholder, a real secret is configured, so it returns `False` and does not read the cluster.
- Otherwise it reads the live Secret with `read_namespaced_secret`. A 404 (`ApiException`) is treated as "nothing there yet". Any other API error is re-raised, so a failed read never silently re-keys.
- It base64-decodes the live value. If it is not valid UTF-8, it raises a `RuntimeError` naming the Secret and namespace.
- If the live value exists and is not the placeholder, it copies it into `secret_data` and returns `False` (reuse).
- Otherwise it mints `secrets.token_urlsafe(48)`, stores it, and returns `True`.

```
if kept and kept != PLACEHOLDER_JWT_SECRET {
    secret_data[key] = kept;
    return False;
}
secret_data[key] = secrets.token_urlsafe(48);
return True;
```

This reuses a real live value. Otherwise (missing, empty, or placeholder, for example from a `--show-yaml` output applied by hand) it mints a real one.

### `target.jac`

`resolve_signing_secret` is imported. In the apply code, before `create_k8s_secret`, it is called on the `user_secret` bundle (`user_secret["stringData"]` is modified in place). If it returns `True` and a logger exists, it logs one line saying a secret was minted and pointing to `[scale.secrets] JAC_SERVE_AUTH_SECRET`. This is what makes the secret persist: the replacement Secret now carries the old value.

### `manifest_builder.jac`

`_signing_secret` no longer mints anything. When nothing is configured, it returns `PLACEHOLDER_JWT_SECRET`. You also removed the `_minted_secret` field. Manifest generation (dry runs, `--show-yaml`, the SDK's `generate_manifests`) stays free of cluster access, and a rendered manifest no longer shows a value that will never be applied.

### `9551.bugfix.md`

A release note. It also says that removing a configured secret keeps its last value, so to rotate you set a new value or delete the `{app}-secrets` Secret.

### `test_pod_env.jac`

Covered in the Tests section.

## How it runs now

1. A deploy builds manifests with `ManifestBuilder`. With no configured secret, `_signing_secret` returns `PLACEHOLDER_JWT_SECRET` (changed).
2. `apply_manifests` reaches the `user_secret` bundle.
3. `resolve_signing_secret` is called (new).
4. If a secret is configured, it returns immediately. Otherwise it reads the live Secret (new).
5. It reuses the live value, or mints one on 404, missing key or placeholder (new). Other API errors and undecodable values raise.
6. A first-time mint logs one info line (new).
7. `create_k8s_secret` creates the Secret, or replaces it on 409. The value is now the same as before, so the `resourceVersion` change no longer comes from a re-key.
8. If the placeholder ever reached a pod, `AuthSettings.resolve_secret` rejects it in-cluster.

The PR notes the trade-off: a deployer without `get` on secrets who relies on the minted fallback now gets an API error instead of a silent re-key.

## Tests

Changes are in `test_pod_env.jac`. The fake `_FakeSecrets` gains `reads` and a `read_namespaced_secret` that always raises 404. `_FakeSecretsExisting` gains `live` (the stored data, base64-encoded when read) and `read_status` (an error to raise). The old redeploy test becomes a table-driven one, which keeps the original assertions (revision `"88"`, one replace, no create):

- **redeploy reuses live**: no configured secret, live value `kept`. Result is `kept`, one read, no mint. Proves reuse.
- **configured wins**: configured `mine`. Result is `mine`, zero reads. Proves no cluster read when configured.
- **live placeholder is replaced**: the live value is the placeholder. A real secret is minted and `True` is returned.
- **denied read fails the deploy**: read status 403. `ApiException` is raised and nothing is replaced. Proves other errors are not swallowed.
- **non UTF-8 live value fails loud**: live bytes `\xff\xfe`. `RuntimeError` is raised and nothing is replaced.

After the loop:
- A builder with no secret renders `PLACEHOLDER_JWT_SECRET`.
- Using `_FakeSecrets` (404), `resolve_signing_secret` mints a real secret on a first deploy.

The PR reports `test_pod_env.jac` at 42 tests before and after, all passing, plus passing runs of `test_identity_fail_loud`, `test_dev_signing_secret`, `test_show_yaml_autoscalers` and `test_access_hint`.

## Explaining it in one minute

"Without a configured `JAC_SERVE_AUTH_SECRET`, each deploy built a new `ManifestBuilder` that minted a random JWT secret and overwrote the live Secret. That signed out all users and rolled all pods on every redeploy. Now the builder only renders a placeholder, so manifests stay cluster-free and honest. A new `resolve_signing_secret` runs in `apply_manifests` just before `create_k8s_secret`. It reuses the live Secret's value and mints one only if it is missing or still the placeholder. Other API errors and undecodable values fail rather than re-key. I did it at apply time because dry runs, `--show-yaml` and `generate_manifests` must not touch the cluster. I tested it with a table-driven test using in-process fakes: reuse, configured wins, live placeholder, denied read, bad bytes, placeholder rendering and first-deploy mint."
