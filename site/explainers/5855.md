## 1. The short version

Jac stores graphs of nodes and edges. Each node's storage record (its "anchor") can carry a **topology index**: a compact list of which node and edge types sit under it. Typed queries such as `[root -->(?:Project)]` read this index to find results quickly. PR #5663 changed the runtime so that writes happen once, at `sync()` time, and only for anchors whose **hash** (a fingerprint of their data) has changed.

**The bug: `Serializer._compute_hash()` deliberately leaves `topology_index_data` out of the hash. So when a walker changes only the root's topology index, the hash does not change, `sync()` skips the root, and the index update is silently lost.** Here is the case from issue #5669. A user creates a `Project` under their `UserProfile`. The `Project` node and edge are saved, but the root's index never learns about `Project`. After that, `[-->(?:Project)]` returns `[]`.

**The fix: you add an explicit `is_topology_dirty` flag to `NodeAnchor`. `set_topology_index` sets it when the encoded index really changes. Both `SqliteMemory.sync` and `MongoBackend.sync` treat a set flag as "must write", and clear it after a successful write.** On MongoDB, a dirty topology also forces a full upsert, because the partial-update path cannot reach the index field.

## 3. The problem, step by step

### 3.1 The setup

- A `NodeAnchor` (often the root) holds `edges`, archetype fields, and `topology_index_data`.
- When an edge is created, `on_edge_created` calls `root.set_topology_index(idx)`, according to the issue.
- At the end of a walker, `sync()` loops over anchors. It computes `_compute_hash(anchor)`, which ignores the topology blob, and skips the anchor if the hash equals the hash taken at load time.
- Before #5663 the root was sometimes written anyway, as a side effect. If `root.edges` changed in the same walker, the hash changed and the blob "rode along". The issue notes that nothing ever explicitly saved the root after `set_topology_index`.

### 3.2 What went wrong: the second walker only changes the index

```text
1. Walker 1: root ++> UserProfile
   root.edges changed  → hash changed → root written (full)
   DB root index = {Root, UserProfile, GenericEdge}                       OK
2. Walker 2: profile ++> Project(...)
   edge added to UserProfile.edges, NOT root.edges
   root.set_topology_index(idx + Project)
   in-memory root index = {Root, UserProfile, GenericEdge, Project}
3. Walker 2 sync, root anchor:
   _compute_hash(root) → drops topology_index_data → same as anchor.hash
   → `continue`, root NOT written                                ← WRONG STEP
4. Project node + edge are new anchors → written via _write_to_db       OK
   UserProfile.edges updated via _put_node_atomic                        OK
5. DB state: Project exists, edge exists, root index still lacks Project
6. Walker 3: [-->(?:Project)] → plan_query reads stale index → []       BUG VISIBLE
```

### 3.3 MongoDB-only second trap: the partial update path

Suppose the hash check did let the anchor through. `MongoBackend.sync` would still prefer `put_partial` whenever it found dirty archetype fields:

```text
1. Root has a changed archetype field AND a changed topology index
2. sync: hash differs → continue to write logic
3. dirty fields found → put_partial(anchor, dirty)
   writes only data.archetype.<field>
4. data.topology_index_data untouched                             ← WRONG STEP
```

You found and closed this second gap too. The issue's suggested fix (Option 2) did not mention it.

### 3.4 Why it mattered

- It was seen in production on jac-builder-dev: a 3-pod Kubernetes cluster sharing one MongoDB, running jac-scale 0.2.14 and jaclang 0.14.0.
- The reporter confirmed it in Mongo. The root's decoded blob held only `Root`, `UserProfile`, `GenericEdge`, while the `Project` node and its edge existed.
- Users saw empty results for typed queries on data they had just created.
- The only workaround was `topology_index = false` in `jac.toml`. That gives up the speed-up the index exists to provide.
- The issue also notes that already-saved roots are stale and would need a one-time rebuild. This PR does not include one.

## 4. The idea of the fix (one sentence)

> **Track topology changes with their own dirty flag instead of the hash.** `set_topology_index` raises `is_topology_dirty` when the blob really changes, and both `sync()` implementations treat that flag as a reason to write, then clear it.

This keeps the hash cheap, which was the original reason for leaving the blob out. It also makes "the index changed" an explicit signal, so it no longer depends on some other field changing at the same time. The issue recommended this as Option 2, over re-adding the blob to the hash (Option 1) or making the setter write to the database itself (Option 3).

## 5. Every code change, explained

### 5.1 `jac/jaclang/jac0core/archetype.jac`: new field on `NodeAnchor`

```diff
 obj NodeAnchor(Anchor) {
     has archetype: NodeArchetype,
         edges: list[EdgeAnchor],
-        topology_index_data: (bytes | None) = None;
+        topology_index_data: (bytes | None) = None,
+        is_topology_dirty: bool = False;
```

**What:** Every `NodeAnchor` now has `is_topology_dirty`, which starts as `False`.

**Why:** It is the explicit "index needs saving" signal that the hash cannot give.

**Things to notice:**
- The description says the field is transient: the serializer only writes `topology_index_data` explicitly, so the flag never reaches SQLite or Mongo.
- `NodeAnchor` has a custom `__getstate__` that the diff does not show. So the diff cannot prove the flag stays out of the saved data. The tests indirectly support it: reloaded anchors are never asserted to be dirty, and the hash precondition in the Mongo test holds.

### 5.2 `jac/jaclang/jac0core/impl/archetype.impl.jac`: set the flag only on real change

```diff
 impl NodeAnchor.set_topology_index(index: Any) -> None {
-    self.topology_index_data = index.encode();
+    new_blob = index.encode();
+    if new_blob != self.topology_index_data {   # NEW: compare bytes
+        self.topology_index_data = new_blob;
+        self.is_topology_dirty = True;           # NEW: mark for sync
+    }
 }
```

**What:** It encodes the index and compares the result to the stored blob. It stores the blob and raises the flag only if they differ.

**Why:** It raises the signal, and avoids extra writes when nothing changed.

**Things to notice:**
- The first call on a fresh anchor compares against `None`, so it always marks the anchor dirty. That is correct.
- The flag is only set here. Code that assigns `topology_index_data` directly would bypass it. The diff does not show whether such code exists.

**What:** SQLite sync merges the in-memory anchor into the stored row (`stored_anchor`). When the flag is set, it copies the new blob onto `stored_anchor` and sets `changed = True`, which forces the write. The flag is cleared after a write, both on the merge path and on the new-insert path.

**Why:** Without this, a topology-only change left `changed` as `False` and nothing was written.

**Things to notice:**
- `getattr(..., False)` protects against anchors that lack the attribute, for example objects built some other way.
- The flag is cleared only inside `if changed`, so it is never cleared without a write.
- The issue suggested changing a hash early-out in `SqliteMemory.sync`. The diff does not show whether such an early-out runs before this block. If it does, this block might never be reached. **What:**
1. A dirty topology now bypasses the hash early-out.
2. If there is an edge delta, `_put_node_atomic` still handles the anchor. That path is said to write the full anchor, so it clears the flag.
3. Otherwise a dirty topology skips `put_partial` and falls through to `_write_to_db`.
4. Both write functions clear the flag inside their `try`, after the write, so a failed write leaves the flag set.

**Why:** It fixes both the skip (3.2) and the partial-update gap (3.3).

**Things to notice:**
- The flag is cleared inside the write helpers, not in `sync`. The PR description's snippet shows the reset in `sync` after `_write_to_db`, so the code differs from the description.
- A dirty topology now means a full upsert of the whole document. `put_partial` exists so that concurrent pods do not overwrite each other's field changes. A full upsert could replace a field another pod just changed. The PR does not discuss this trade-off.
- The delta path is not guarded by `topology_dirty`. It relies on `_put_node_atomic` writing the topology blob. The diff does not show its body, but a test (7.2, test 3) checks the result.
- On write failure, the error is logged and the flag stays `True`. The next sync of that anchor in the same context will try again.

## 6. How execution flows after the PR

### 6.1 Updating the index during a walker

```text
edge created (e.g. profile ++> Project)
└─ on_edge_created  (per issue; not in diff)
   └─ root.set_topology_index(idx)
      ├─ new_blob = idx.encode()
      ├─ new_blob == current blob? → do nothing              ← NEW
      └─ else: store blob, is_topology_dirty = True          ← NEW
```

### 6.2 `SqliteMemory.sync` for one anchor

```text
sync()
└─ anchor in memory
   ├─ stored row exists (and is not a stub)
   │  ├─ existing merge logic → may set changed
   │  ├─ NodeAnchor and is_topology_dirty?                   ← NEW
   │  │   └─ copy blob to stored_anchor, changed = True
   │  └─ changed?
   │      └─ write merged row, clear is_topology_dirty       ← NEW
   └─ no stored row / stub
      └─ insert new row, clear is_topology_dirty             ← NEW
```

### 6.3 `MongoBackend.sync` for one anchor

```text
sync()
└─ anchor in L1
   ├─ current_hash == anchor.hash and not topology_dirty → skip   ← CHANGED
   ├─ no write access → (existing handling)
   ├─ edge delta present → _put_node_atomic → clears flag         ← CHANGED
   ├─ anchor.hash != 0 and not topology_dirty                      ← CHANGED
   │   └─ dirty archetype fields → put_partial → done
   └─ _write_to_db (full upsert) → clears flag                     ← CHANGED
```

### 6.4 Loading an anchor later

```text
backend.get(id)
└─ deserialize → topology_index_data = saved blob
               → is_topology_dirty = False (default; never saved)
```

| Scenario | Before | After |
|---|---|---|
| Only the topology index changed (SQLite) | Not written; index lost | Written via merge |
| Only the topology index changed (Mongo) | Skipped by hash check | Full `_write_to_db` |
| Topology + archetype field changed (Mongo) | `put_partial`; index lost | Full `_write_to_db`; both saved |
| Topology + edge delta (Mongo) | `_put_node_atomic` (blob rode along) | Same; flag cleared |
| `set_topology_index` with identical content | Blob reassigned, no flag | No-op, no flag |
| Nothing changed | Skipped | Skipped |

What users would notice: typed filter queries return new types correctly. Mongo would also do more full-document writes for roots whose index changes.

## 11. Questions your senior might ask

**Q: Why not just put `topology_index_data` back into the hash?**
That would undo a deliberate speed-up; the comment in `_compute_hash` warns it would "double the cost of every serialize round-trip". A flag adds no cost to hashing and makes the intent explicit. The issue recommended this option.

**Q: Why couldn't Mongo use `put_partial` for the index?**
`put_partial` writes only `data.archetype.*`. The blob lives at `data.topology_index_data`, so a dirty topology must fall through to `_write_to_db`.

**Q: Can a full upsert overwrite another pod's concurrent change?**
Possibly. A full upsert replaces the whole document, which is what `put_partial` and `_put_node_atomic` exist to avoid. The PR does not address this, and it is a fair concern for a 3-pod deployment.

**Q: What happens if the write fails?**
The flag is cleared only after a successful write, inside the `try`. On an exception it stays `True`, so a later sync can retry.

**Q: Is `is_topology_dirty` ever saved to the database?**
The description says no, because the serializer writes only the blob. The diff does not show `__getstate__`, so this is asserted rather than proven. Tests that reload anchors never see a stale `True`.

**Q: Why compare the blobs in `set_topology_index`?**
To avoid marking the anchor dirty, and forcing a full write, when the index is rebuilt with the same content. The "not set when content unchanged" test covers this.

**Q: Do the tests prove `MongoBackend.sync` works?**
Not directly. They check `_write_to_db`, `_put_node_atomic`, and hand-written copies of the guard conditions. Only the SQLite test drives the real `sync()`.

**Q: Does this fix existing user data?**
No. Roots saved before the fix keep their stale index until the index changes again or a rebuild script runs. The issue proposed such a script, and this PR does not include one.
