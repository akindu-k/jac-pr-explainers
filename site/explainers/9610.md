## 1. The short version

`jac scale deploy` packs your app into a `.jab` on your machine (the host) and ships it to every Kubernetes pod. A pod can only boot quickly from a `.jab` if it contains `.jac/serve_manifest.json`, the "serving metadata" that a step called the *bake* writes during the *seal*.

**Before this PR, the host could pack and ship a `.jab` with no `.jac/serve_manifest.json`, report success, and leave every pod to crash-loop with `Sealed application has no serving manifest`.** The issue (#9138) describes the error on 0.37.12 as `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`. It happened in three ways:

- The bake returned success without writing the file when the app entry (for example `entry-point = "missing"`) did not resolve.
- The tar step skipped the file when it was missing, instead of refusing to pack.
- A stale copy in your working tree could be force-shipped. That stale copy could hide the problem, or end up in the bundle twice next to the fresh one.

**You added one host-side check, `require_serve_manifest`, and call it right after the bake and again in the tar step. You also stopped shipping working-tree copies of the manifest, and the seal cache now reuses a cached `.jab` only if it is a readable archive that contains the manifest.** A broken deploy now fails on the developer's machine with a message that names the missing path and includes the bake's `sealing without serve payloads` warning.

**Status:** Merged on 2026-10-26. @MusabMahmoodh first requested changes, then dismissed that review and left a "commented" review. Greptile's findings were addressed. @kugesan1105 merged it and asked for a follow-up on the root cause. All CI checks on `0c5f000` passed or were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **Host:** `pack_jab` → `_precompile_app`. This makes the stage, runs the bake through the pod binary, then runs `jac precompile --seal`. Back in `pack_jab`, the tar step adds `_precompiled/*`, the serve manifest, vendored wheels and the sources.
- **Pod:** `_prepare_sealed` reads `.jac/serve_manifest.json` without guarding the read (`application.jac:216` per the issue).
- **Existing gate:** `_precompile_app` already raised "App seal did not complete" if `_precompiled/MANIFEST.json` was missing. The serve manifest had no such gate.

### 3.2 What went wrong

#### 3.2.1 Entry does not resolve

```text
1. jac.toml: entry-point = "missing"   (or the default main.jac does not exist)
2. _precompile_app runs the bake in the pod binary
3. resolve_entry_file → None; stdout gets "sealing without serve payloads"
4. bake_serve_payloads returns True → exit code 0
5. _precompile_app checks the exit code only → OK             ← WRONG: no file check
6. stage/.jac/serve_manifest.json: absent
7. tar step: if serve_manifest.is_file() → False → skip       ← WRONG: silent skip
8. pack_jab returns a .jab → host reports success
9. every pod: _prepare_sealed reads the manifest → FileNotFoundError → exit 1 → crash-loop
```

#### 3.2.2 Stale local manifest in the working tree

```text
1. Working tree has an old .jac/serve_manifest.json
2. _is_bundle_required(".jac/serve_manifest.json") → True       ← WRONG: force-ships it
3. Stale copy lands in the stage AND in the source members
4a. Entry missing: the stage file exists (stale), so any existence check passes
    → the pod boots on wrong metadata
4b. Entry valid: the bake writes a fresh manifest
    → the .jab has TWO members named .jac/serve_manifest.json (stale + fresh)
    → extraction order decides which one the pod gets
```

#### 3.2.3 Cached bundle from before the gate (found in review by Greptile)

```text
1. An older host packed a manifest-less .jab; the seal cache stored it under key K
2. Host upgraded; pod binary pinned; sources unchanged → key is still K
   (the key does not cover the host's bundler)
3. pack_jab: _cached_seal(K) returns bytes → reused early            ← WRONG: both gates bypassed
4. The broken .jab ships again
```

### 3.3 Why it mattered

- Per #9138, a deploy "completes" and only the pods find out, so N pods crash-loop on 0.37.12.
- On 0.37.11 the pod silently recompiled the whole server side at boot. That is the 7 minute / 4.5Gi boot measured in #9136.
- The issue calls this "silent fallback at a decision point, twice on the host". It is the same class of bug as #7936 and the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Fail on the host, not in the pod.** If the stage has no freshly baked `.jac/serve_manifest.json` (or the cached bundle lacks one), refuse to pack and say why.

The host already has every fact it needs, and failing there costs one error message instead of N crash-looping pods. You put the gate in the scale bundler rather than in `bake_serve_payloads` because the bake runs inside the pod binary, which may be an older release, and `jac build --as jab` should keep its current behaviour.

## 6. How execution flows after the PR

### 6.1 Packing (`pack_jab`)

```text
pack_jab(base, pod_binary)
├─ key = input_key(base, seal_sources)
├─ cached = _cached_seal(base, key)
├─ cached is not None AND _bundle_ships(cached, ".jac/serve_manifest.json")?   ← CHANGED
│   ├─ yes → log "Reusing the sealed bundle..." → return cached
│   └─ no (missing / no manifest / not an archive) → continue to seal          ← NEW
├─ _precompile_app(...)            (see 6.2)
├─ tar step
│   ├─ add _precompiled/* artifacts
│   ├─ tar.add(require_serve_manifest(staged), ...)  → raises if absent       ← CHANGED
│   ├─ add _vendor wheels, sources (no working-tree serve_manifest)          ← CHANGED (6.3)
└─ _remember_seal(base, key, raw) → return raw
```

### 6.2 Sealing (`_precompile_app`)

```text
_precompile_app(...)
├─ build the stage from project files (filtered by _is_bundle_required etc.)
├─ run the bake via the pod binary → `prepared`
│   └─ non-zero exit → RuntimeError (unchanged)
├─ require_serve_manifest(stage, tail of prepared.stdout)                    ← NEW
│   └─ missing → RuntimeError "The app stage has no .../.jac/serve_manifest.json,
│                 so the deploy cannot produce a .jab a pod can boot from.
│                 ... sealing without serve payloads"
├─ run `jac precompile <stage> --seal`
└─ _precompiled/MANIFEST.json missing → "App seal did not complete" (unchanged)
```

### 6.3 Choosing force-shipped files (`_is_bundle_required`)

```text
_is_bundle_required(rel)
├─ .jac/admin/...              → True
└─ .jac/serve_manifest.json    → False                                       ← CHANGED (was True)
```

| Scenario | Before | After |
|---|---|---|
| Entry resolves, no local manifest | Ships fresh manifest | Same |
| Entry missing, no local manifest | Ships `.jab` without manifest; pods crash-loop | Host raises after the bake, with the warning in the message |
| Entry missing, stale local manifest | Stale manifest shipped; pods boot on wrong metadata | Host raises (stale copy no longer staged) |
| Entry valid, stale local manifest | Two members with the same name; extraction order wins | Only the fresh manifest ships |
| Cached `.jab` without manifest | Reused, broken bundle ships | Reseal; gate reports any real problem |
| Cached file is not an archive | Reused (bytes returned as-is) | Reseal |
| `jac build --as jab` with missing entry | Warns, succeeds | Unchanged |

**Behaviour change users will notice:** a project whose entry doesn't resolve now fails `jac scale deploy` on the host. Before, it "succeeded" and broke in the pods. Also, a local `.jac/serve_manifest.json` is no longer shipped.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return `False` when the entry is missing?**
The bake runs inside the pod binary, which may be an older release, so a fix there wouldn't reach pinned pods. It would also change `jac build --as jab`, which is meant to keep warning and succeeding. The host-side bundler is where the pod's fate is decided.

**Q: Why two gates? Isn't the one after the bake enough?**
The bake gate is the one a real deploy hits, and it carries the bake's stdout as the explanation. The tar-step gate is a backstop for the file vanishing between the bake and the tar, which is reproduction path 1 in the issue. It costs one `is_file()` call.

**Q: Could anyone have relied on shipping a local `.jac/serve_manifest.json`?**
Not usefully. The seal always bakes a fresh one, and the local copy either hid a missing bake or created a duplicate tar member with the same name. The diff doesn't show any other use of that rule.

**Q: Why not add the host bundler version to the cache key instead of opening the cached `.jab`?**
That would only invalidate on host upgrades. Checking the bytes catches any manifest-less or corrupt cache entry, whatever its origin. The PR doesn't discuss the key option.

**Q: What does the cache check cost?**
On each cache hit it opens the gzip tar and lists all member names, which reads the whole archive. A full reseal costs far more, but the PR includes no measurement.

**Q: What does the user see now when the entry is wrong?**
A `RuntimeError`: "The app stage has no `<stage>/.jac/serve_manifest.json`, so the deploy cannot produce a .jab a pod can boot from." It is followed by the tail of the bake's output, including `sealing without serve payloads` and, per @MusabMahmoodh's CI log, `entry-point '.../main.jac' not found`.

**Q: Why did existing fixtures have to change? Does that weaken them?**
They packed apps whose default entry `main.jac` didn't exist, so no pod could have booted them, and the new gate rightly refuses them. You added a valid entry and kept all assertions. `test_pvc_injector`'s `app.jac` → `main.jac` check is a rename.

**Q: Is the tar-step gate tested?**
Not on its own. @MusabMahmoodh advised dropping the mock-based case because scale tests stay mock-free, and the bake gate is the path real deploys take.

**Q: Does the unrunnable-binary row still run on machines without the pod binary?**
Yes. It runs before `require_pod_binary()` is called for the second row. Locally the test then shows as skipped, and on CI `JAC_TEST_STRICT` turns that skip into a failure. Greptile agreed after your reply.

**Q: What root cause is still open?**
Why projects reach the bake with an entry that doesn't resolve, as @kugesan1105 raised. This PR makes the failure loud and early on the host, but it doesn't add earlier entry validation.
