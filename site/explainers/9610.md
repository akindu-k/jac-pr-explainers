## 1. The short version

`jac scale deploy` builds a `.jab` on your machine (the host) and ships it to every service pod. That bundle must contain `.jac/serve_manifest.json`, the file that tells a pod how to serve the sealed app. A "bake" step writes this file during the seal.

**Before this PR, the host could pack and ship a `.jab` with no serve manifest, report success, and leave every pod to crash at boot with `Sealed application has no serving manifest` (on 0.37.12: `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`).** There were three causes:

- The bake silently "succeeded" when the app entry did not resolve to a file.
- The tar step skipped the file when it was missing instead of refusing.
- A stale working-tree copy of the manifest could be force-shipped next to the fresh one.

**You added one host-side check, `require_serve_manifest(stage, detail)`. It raises a `RuntimeError` that names the missing path. It runs right after the bake (with the bake's stdout in the message) and again in the tar step. You also stopped force-shipping the working-tree `.jac/serve_manifest.json`.** A project with `entry-point = "missing"` now fails on the host, and the error contains `sealing without serve payloads`.

**Status:** Open. @MusabMahmoodh's 2026-09-30 review requested changes, and his follow-up review (2026-10-08) was dismissed, so there is no approval. On head `31862a2`, CI is red: `test-scale (microservices)`, `jac-check` and the aggregate `Everything Passed` all failed.

## 3. The problem, step by step

### 3.1 The setup

- `pack_jab` copies the project into a stage. Files for which `_is_bundle_required` returns `True` are always included.
- `_precompile_app` runs two subprocesses with the pod binary:
  1. the bake, which writes `stage/.jac/serve_manifest.json`;
  2. `jac precompile --seal`, which writes `_precompiled/MANIFEST.json`.
- `_precompile_app` already raised `App seal did not complete` when `_precompiled/MANIFEST.json` was missing. The serve manifest had no such check.
- `pack_jab` then tars the stage, including the serve manifest.
- The pod extracts the `.jab` and runs `jac run --serve`, which reads the manifest without checking that it exists.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml has entry-point = "missing" (or the default main.jac does not exist)
2. pack_jab stages the project                     stage: no .jac/serve_manifest.json
3. _precompile_app runs the bake subprocess
4. resolve_entry_file -> None, prints "sealing without serve payloads" to stdout
5. bake_serve_payloads returns True -> exit code 0
6. _precompile_app checks only the exit code -> OK        <-- WRONG: no file check
7. precompile --seal writes _precompiled/MANIFEST.json   -> seal gate passes
8. tar step: if serve_manifest.is_file() -> False -> skip <-- WRONG: silent skip
9. Host reports success; .jab is shipped to N pods
10. Each pod: "Loading sealed application artifacts" -> [Errno 2] ... serve_manifest.json
    -> exit 1 -> crash-loop
```

### 3.3 What went wrong: stale local manifest

```text
1. Working tree has an old .jac/serve_manifest.json (from an earlier local run)
2. _is_bundle_required(".jac/serve_manifest.json") -> True        <-- WRONG
3. Stale copy is force-copied into the stage and into the source members
4a. Entry missing: bake writes nothing, but stage/.jac/serve_manifest.json EXISTS (stale)
    -> any is_file() check passes; pod gets stale metadata
4b. Entry valid: bake writes a fresh manifest in the stage
    -> .jab has TWO members named .jac/serve_manifest.json (stale + fresh)
    -> extraction order decides which one the pod reads              <-- WRONG
```

The issue listed this case under "Scope note (c)" as unverified. Your description says you reproduced it ("the pack shipped it twice").

### 3.4 What went wrong: manifest removed between bake and pack

This is the issue's reproduction path 1. The bake writes the file, and something in between (a failure or a cleanup) removes it before the tar step. The tar step's `is_file()` skip let it through. The new tar-step gate covers this case, but no test exercises it (see 7).

### 3.5 Why it mattered

- **On 0.37.12:** every pod crash-loops, while the deploy itself looked successful.
- **On 0.37.11:** pods silently recompiled the whole server at boot. Issue #9136 measured this at 7 minutes and 4.5Gi per boot.
- **Root cause, in the issue's words:** "silent fallback at a decision point, twice on the host". The host had every fact it needed to refuse the pack, but the failure was pushed onto N pods.
- **Similar cases:** the issue compares it to #7936 and to the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Refuse the pack on the host when the stage has no serve manifest.** After the bake and again at the tar step, check that `.jac/serve_manifest.json` exists and raise a clear error if not, and never ship a working-tree copy of it.

This puts the check where the pod's fate is decided, on the host, and matches the existing `_precompiled/MANIFEST.json` gate. It also leaves `bake_serve_payloads` alone. That function runs inside the possibly-older pod binary, and `jac build --as jab` still depends on its lenient behaviour.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/bundle.jac`: stop force-shipping the manifest

**What:** `_is_bundle_required` now returns `True` only for `.jac/admin/...`. A local `.jac/serve_manifest.json` is no longer staged or shipped.

**Why:** This fixes the stale-copy case (3.3). The stale copy can no longer make the existence check pass, and the `.jab` can no longer carry two members with the same name.

**Things to notice:**
- This is safe only because the seal always bakes a fresh manifest. @MusabMahmoodh agreed: "dropping the `.jac/serve_manifest.json` bundle-required rule is right".
- The diff does not show whether some other rule (for example `.jacignore` or a default exclude for `.jac/`) still lets the local file through. That depends on code outside this diff. The new test's second row does cover it end to end, though: a stale file is present and the pack must still raise.

### 5.2 `jac/jaclang/scale/injector/bundle.jac`: new `require_serve_manifest`

```diff
+def require_serve_manifest(stage: Path, detail: str = "") -> Path {
+    import from jaclang.server.sealed_serve { SERVE_MANIFEST_REL }
+
+    serve_manifest = stage / SERVE_MANIFEST_REL;
+    if not serve_manifest.is_file() {
+        raise RuntimeError(
+            f"The app stage has no {serve_manifest}, so the deploy cannot "
+            f"produce a .jab a pod can boot from. {detail}".rstrip()
+        );
+    }
+    return serve_manifest;
+}
```

**What:** It returns the manifest path if the file exists. Otherwise it raises a `RuntimeError` that names the full stage path and adds an optional `detail`.

**Why:** One shared gate for both places where the file used to slip through.

**Things to notice:**
- `.rstrip()` removes the trailing space when `detail` is empty.
- It returns the path, so the tar step can use it directly in `tar.add(...)`.

## 6. How execution flows after the PR

### 6.1 Packing a `.jab` (`jac scale deploy` → `pack_jab`)

```text

├─ stage project files
│  └─ _is_bundle_required: .jac/serve_manifest.json no longer forced in   ← CHANGED
├─ _precompile_app

│  ├─ exit code != 0 → raise (unchanged)
│  ├─ require_serve_manifest(stage, bake stdout)                           ← NEW
│  │  └─ missing → RuntimeError "...has no .../.jac/serve_manifest.json... sealing without serve payloads"
│  ├─ run precompile --seal
│  └─ _precompiled/MANIFEST.json missing → "App seal did not complete" (unchanged)

   ├─ add _precompiled artifacts
   ├─ tar.add(require_serve_manifest(staged))                              ← CHANGED (raises if missing)
   └─ _vendor wheels, etc.
```

### 6.2 Pod boot (unchanged code, different input)

```text
pod: tar xzf app.jab → jac run --serve $JAC_SV_FILE
└─ _prepare_sealed reads .jac/serve_manifest.json
   └─ now always present and freshly baked, because the host refuses otherwise
```

### 6.3 `jac build --as jab`

This path is unchanged. `bake_serve_payloads` still returns `True` and only warns when no entry resolves.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return `False` when no entry resolves?**
The bake runs inside the pod binary, which may be an older release, so a fix there would not reach every deploy. `jac build --as jab` also relies on the current lenient behaviour. The host-side gate works with any pod binary.

**Q: Why two gates instead of one?**
The bake gate catches the real-world case early, with an explanation in the error. The tar gate catches the file disappearing between the bake and the tar step, and replaces a silent skip.

**Q: Could a valid project lose a manifest it needs, now that the local file isn't shipped?**
No. The seal always bakes a fresh manifest into the stage, and the gate guarantees it is there. The local copy could only ever be stale or a duplicate.

**Q: Is the tar-step gate tested?**
Not separately. Testing it would need a mock, and the reviewer preferred dropping it because the bake gate is the one a real deploy hits.

**Q: What happens to users whose project has no `main.jac` and no `entry-point`?**
Their deploy now fails on the host with an error naming `.jac/serve_manifest.json` and including `sealing without serve payloads`. Before, the deploy "succeeded" and the pods broke. Four test fixtures had exactly this mistake.

**Q: Why does the test pass `b""` as a binary?**
It is a falsy sentinel. `binary or require_pod_binary().read_bytes()` then loads the real pod binary only for the second row, so the first row runs even on machines without the binary.

**Q: Why is CI red if the keyword was renamed?**
The data here can't tell. The rename is in the diff, so the failure comes from something else. The next step is to read the job logs.

**Q: Did you add the boot-side assertion the issue suggested (`Loading sealed application artifacts`, no `Compiling server modules`)?**
No. This PR only adds the negative host-side case. That tightening could be a follow-up.

**Q: Does this conflict with #9615's `_precompile_app` rewrite?**
@MusabMahmoodh said it composes cleanly with that rewrite on `main`.
