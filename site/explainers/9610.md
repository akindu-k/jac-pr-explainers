## 1. The short version

`jac scale deploy` packs your Jac app into a `.jab` bundle on your machine (the "host") and ships it to Kubernetes pods. Each pod reads a file called `.jac/serve_manifest.json` from the bundle to learn how to serve the app. A step called the "bake" writes that file during the seal.

**The host could ship a `.jab` with no `.jac/serve_manifest.json` and still report success. Every pod then crash-looped at boot with `Sealed application has no serving manifest` (on 0.37.12, `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`).** There were three ways this happened:

- The bake returned success without writing anything when the app entry did not resolve, for example `entry-point = "missing"`.
- The tar step silently skipped a missing manifest.
- A stale working-tree copy of the manifest was force-copied into the bundle. It could satisfy any existence check, and it could also end up as a second, duplicate tar member.

**You added `require_serve_manifest()`, which raises on the host when the seal stage has no serve manifest. It runs right after the bake (with the bake's stdout attached) and again in the tar step, in place of the silent skip. You also stopped treating `.jac/serve_manifest.json` as a "must ship" file.** A broken deploy now fails on your machine before any pod is touched.

**Status:** Open. @MusabMahmoodh requested changes on 2026-09-30. His 2026-10-08 review said it was "good to go" once the keyword was renamed, but that review is now marked dismissed, so a fresh approval is needed. On head `e6c3da2`, **`test-scale (microservices)` is failing** and `test-compiler (passes-native …)` is still running.

## 3. The problem, step by step

### 3.1 The setup

- **`bundle.jac` (host):** copies the app into a stage, using `_is_bundle_required` as part of the copy rules. `_precompile_app` then runs the pod binary twice: once to bake, once to `precompile --seal`. Finally `pack_jab` tars the stage into a `.jab`.
- **`seal.jac` (runs inside the pod binary):** `bake_serve_payloads` writes `.jac/serve_manifest.json`, or returns `True` without writing when there is no entry.
- **Pod:** extracts the `.jab`, runs `jac run --serve`, and reads the manifest unguarded.

There was already a gate for the seal itself: `_precompile_app` raises "App seal did not complete" if `_precompiled/MANIFEST.json` is missing. The serve manifest had no such gate.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml has entry-point = "missing"; no such file in the project
2. Host copies project into stage                 stage: no .jac/serve_manifest.json
3. Bake subprocess runs                           resolve_entry_file → None
                                                  stdout: "sealing without serve payloads"
                                                  bake_serve_payloads → True, exit 0
4. _precompile_app checks exit code only → OK     ← WRONG: nothing was written
5. precompile --seal → _precompiled/MANIFEST.json written; existing gate passes
6. pack_jab: `if serve_manifest.is_file()` → False → skip   ← WRONG: silent skip
7. Host reports success; .jab shipped to N pods
8. Each pod: read .jac/serve_manifest.json → FileNotFoundError → exit 1 → crash-loop
```

### 3.3 What went wrong: stale local manifest

```text
1. Working tree has an old .jac/serve_manifest.json (from an earlier build)
2. _is_bundle_required(".jac/serve_manifest.json") → True   ← WRONG
   → stale copy is staged and added to the source members
3a. Entry missing: bake writes nothing, but the stale file is in the stage,
    so any "does it exist?" check passes → pod gets stale metadata
3b. Entry valid: bake writes a fresh manifest too
    → .jab has TWO members with arcname .jac/serve_manifest.json (stale + fresh)
    → extraction order decides which one the pod reads
```

### 3.4 What went wrong: manifest removed between bake and pack

```text
1. Bake writes the manifest (subprocess 1)
2. Something fails or cleans up before the tar step
3. pack_jab: is_file() → False → skip, .jab still returned   ← WRONG
```

This is reproduction path 1 from issue #9138. Only the tar-step gate covers it.

### 3.5 Why it mattered

Issue #9138 says the deploy "completes, ships the bundle to every pod, and only the pod discovers" the problem:

- On 0.37.12 the pod crash-loops.
- On 0.37.11 it silently recompiled the whole server side at boot (the 7 minute / 4.5Gi boot in #9136).

You reproduced the 0.37.12 failure on `e8b3d8ad5`. The issue calls the root cause a "silent fallback at a decision point" taken on the host, where the deploy could still fail cheaply. It compares this to the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, not in the pod.** If the seal stage has no serve manifest after the bake, or at tar time, the pack raises an error that names the missing file. A working-tree copy is never allowed to stand in for it.

The gate sits in the scale bundler because `bake_serve_payloads` runs inside the pod binary. That binary may be an older release, and `jac build --as jab` also calls the bake and should keep its current behaviour. The scale bundler is the one place that decides what pods receive.

```diff
+def require_serve_manifest(stage: Path, detail: str = "") -> Path {
+    import from jaclang.server.sealed_serve { SERVE_MANIFEST_REL }
+    serve_manifest = stage / SERVE_MANIFEST_REL;
+    if not serve_manifest.is_file() {
+        raise RuntimeError(
+            f"The app stage has no {serve_manifest}, so the deploy cannot "

+    return serve_manifest;

```

**What:** It returns the manifest path if the file exists. Otherwise it raises `RuntimeError` with the full path and an optional `detail`.

**Why:** One shared gate for both places that used to let a missing file through.

**Things to notice:**
- It returns the path, so `pack_jab` can use it inline in `tar.add(...)`.
- `.rstrip()` removes the trailing space when `detail` is empty.

## 6. How execution flows after the PR

### 6.1 Packing a deploy (`jac scale deploy` → `pack_jab`)

```text
pack_jab(project, pod_binary)
├─ copy project into seal stage
│   └─ _is_bundle_required: .jac/serve_manifest.json no longer forced   ← CHANGED
├─ _precompile_app(stage)
│   ├─ run pod binary: bake (bake_serve_payloads)
│   ├─ exit code != 0 → RuntimeError (unchanged)
│   ├─ require_serve_manifest(stage, bake stdout)                         ← NEW
│   │   └─ missing → RuntimeError "The app stage has no …/.jac/serve_manifest.json … sealing without serve payloads"
│   ├─ run pod binary: precompile --seal
│   └─ _precompiled/MANIFEST.json missing → "App seal did not complete" (unchanged)
└─ build tar
    ├─ add _precompiled artifacts
    ├─ tar.add(require_serve_manifest(staged), arcname=.jac/serve_manifest.json)   ← CHANGED
    └─ add _vendor wheels, … → return .jab bytes
```

### 6.2 Pod boot

Unchanged in this PR. The pod still reads the manifest unguarded. It just should never receive a bundle without one now. The issue's scope note lists boot-side diagnostics as separate follow-ups.

| Scenario | Before | After |
|---|---|---|
| Valid entry, no local manifest | Pack OK, pod boots | Same |
| Valid entry, stale local manifest | Two `.jac/serve_manifest.json` members; extraction order decides | One fresh member only |
| Entry missing, no local manifest | Pack "succeeds"; pods crash-loop | Host raises `RuntimeError` naming the file plus the bake warning |
| Entry missing, stale local manifest | Stale manifest shipped | Host raises (stale copy not staged) |
| Manifest vanishes between bake and tar | `.jab` shipped without it | Tar step raises |
| `jac build --as jab` | Warning, continues | Unchanged (gate is only in scale) |

**Behaviour change users will notice:** deploys that used to "succeed" with an unresolvable entry now fail on the host. Projects whose entry is not `main.jac` and that do not set `entry-point` would hit this. As the test fixture changes show, those bundles could never boot anyway.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return `False` when there is no entry?**
The bake runs inside the pod binary, which may be an older release, so the host can't rely on it. `jac build --as jab` also calls it and should keep warning and continuing. The scale bundler is where the pod's fate is decided.

**Q: If the bake gate exists, why keep the tar-step gate?**
Something can delete the manifest between the bake and the tar step (issue reproduction path 1). The tar gate also replaces a silent skip that should never have existed.

**Q: Why is the tar-step gate untested?**
@MusabMahmoodh asked to drop the mock-based case. Reaching that branch without a mock is hard, and the bake gate is the one a real deploy hits.

**Q: How does one test row cover both the gate and the `_is_bundle_required` change?**
It writes a stale `.jac/serve_manifest.json`. If the stale copy were still staged, the gate would see a file and not raise, and the test would fail.

**Q: Could the "sealing without serve payloads" text be lost?**
Yes, in principle. Only the last 4000 characters of bake stdout are kept. The test asserts the text is present, so it would catch this for the test app.

**Q: Does this change `jac build --as jab`?**
No. Only `bundle.jac` in jac-scale changed.

**Q: Who is affected by the behaviour change?**
Anyone deploying an app whose entry doesn't resolve, for example an entry file not named `main.jac` with no `entry-point` set. They now get a host error instead of crash-looping pods.

**Q: Is anything else under `.jac/` still force-shipped?**
Only `.jac/admin/...`.

**Q: Why did three unrelated test files change?**
Their fixture apps had no `main.jac`, so they had no resolvable entry. The new gate correctly refuses them, and they were never bootable. Renaming or adding `main.jac` fixes the fixtures without weakening any assertion.
