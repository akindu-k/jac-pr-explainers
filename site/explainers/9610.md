## 1. The short version

`jac scale deploy` builds a `.jab` bundle on your machine and ships it to every pod. For a pod to boot, the bundle has to contain `.jac/serve_manifest.json`, the "serving metadata" that a step called the **bake** writes during the **seal**.

**Before this PR, the host could pack and ship a `.jab` with no serve manifest and still report success. Every pod then crash-looped at boot with `Sealed application has no serving manifest`, or on 0.37.12 with `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`.** There were three holes:

- The bake returned success without writing anything when the app entry (for example `entry-point = "missing"`) did not resolve.
- The tar step skipped a missing manifest instead of refusing it.
- A stale working-tree `.jac/serve_manifest.json` was force-copied into the bundle. It could hide the missing file, or end up as a second, duplicate tar member.

**You added `require_serve_manifest(stage, detail)`, a host-side check that raises a `RuntimeError` naming the missing path. It runs right after the bake (with the bake's stdout attached) and again at the tar step. You also stopped force-shipping the working-tree manifest.** A test table now drives a real bake of a project with a missing entry over a stale local manifest. Four other test fixtures gained a `main.jac`, because they were packing apps no pod could boot.

The branch also carries #9613's commit (`fb5c792`, "portable serve manifest" in `seal.jac`). The fixture apps now bake a manifest, so the determinism tests need it.

**Status:** Open. @MusabMahmoodh's latest review (2026-10-08) is "changes requested". The only point it raised, the `entry` keyword, was fixed in `86ea8d9` on 2026-10-10, but no re-review has happened yet. On head `79f459c`, `build-kit` is still running, and the scale test jobs are not in the reported checks. The PR also depends on #9613 merging first.

## 3. The problem, step by step

### 3.1 The setup

- **Host side (`bundle.jac`):** `pack_jab` calls `_precompile_app`, which:
  1. copies the project into a stage,
  2. runs the bake subprocess with the pod binary,
  3. runs `jac precompile --seal`,
  4. checks that `_precompiled/MANIFEST.json` exists.

  Then `pack_jab` tars the stage into the `.jab`.
- **Bake (`seal.jac`):** writes `.jac/serve_manifest.json`, unless the entry does not resolve. In that case it prints a warning and still returns success.
- **Pod side:** extracts the `.jab`, then `_prepare_sealed` reads `.jac/serve_manifest.json` with no guard.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml has entry-point = "missing"; no such file in the staged tree
2. _precompile_app runs the bake subprocess (pod binary)
3. resolve_entry_file → prints "sealing without serve payloads", returns None
4. bake_serve_payloads → returns True; stage/.jac/serve_manifest.json: ABSENT
5. bake exit code 0 → _precompile_app continues            ← WRONG: no file check
6. precompile --seal → _precompiled/MANIFEST.json: PRESENT → seal gate passes
7. pack_jab: `if serve_manifest.is_file()` is False → manifest skipped  ← WRONG: silent skip
8. host prints success; .jab shipped to every pod
9. pod: _prepare_sealed reads .jac/serve_manifest.json → Errno 2 → exit 1 → crash-loop
```

You reproduced this on `e8b3d8ad5`: the pack succeeded, and `jac run --serve` on the extracted bundle exited 1.

### 3.3 What went wrong: a stale local manifest

```text
1. working tree has an old .jac/serve_manifest.json (left from a local build)
2. _is_bundle_required(".jac/serve_manifest.json") → True
   → stale copy goes into the stage AND into the source members            ← WRONG
3a. entry missing: bake writes nothing, but the stale copy is in the stage
    → any is_file() check passes → pod gets stale metadata
3b. entry valid: bake writes a fresh manifest into the stage
    → .jab has TWO members with arcname .jac/serve_manifest.json (stale + fresh)
    → extraction order decides which one the pod sees
```

The issue listed this as unverified scope note (c). Your description says you confirmed the double member.

### 3.4 What went wrong: manifest gone between bake and pack

```text
1. bake writes stage/.jac/serve_manifest.json
2. a later step (precompile --seal subprocess, cleanup, failure) removes it
3. _precompiled/MANIFEST.json still present → seal gate passes
4. pack_jab: is_file() False → skip                                        ← WRONG
5. .jab shipped without serving metadata
```

This is route 1 in issue #9138. Only the tar-step gate catches it.

### 3.5 Why it mattered

- On 0.37.12, every pod of the deploy crash-loops. The host has already reported success.
- On 0.37.11 (before #9088), the pod silently recompiled the whole server at boot. That is the 7-minute / 4.5 Gi boot measured in #9136.
- The issue's root-cause wording: "Silent fallback at a decision point, twice on the host." The host had every fact needed to refuse the pack cheaply, and instead the failure landed on N pods.

## 4. The idea of the fix (one sentence)

> **Refuse the pack on the host when the seal leaves no serve manifest.** Check for the file right after the bake and again when tarring, and never ship a working-tree copy that could fake its presence.

This matches the existing `_precompiled/MANIFEST.json` gate and `check_fleet_entries`, which already refuse pods that would crash-loop. It also keeps the check on the host, where the deploy's outcome is decided. The bake itself runs inside the pod binary, which may be an older release.

## 6. How execution flows after the PR

### 6.1 `jac scale deploy` with an entry that does not resolve

```text
jac scale deploy
└─ pack_jab(project, pod_binary)
   └─ _precompile_app
      ├─ stage files (working-tree .jac/serve_manifest.json NOT copied)   ← CHANGED
      ├─ bake subprocess (pod binary)
      │  └─ resolve_entry_file → None, prints "sealing without serve payloads"
      │  └─ bake_serve_payloads → True, writes nothing, exit 0
      ├─ exit code check → passes
      └─ require_serve_manifest(stage, bake stdout)                       ← NEW
         └─ RuntimeError: "The app stage has no <stage>/.jac/serve_manifest.json,
            so the deploy cannot produce a .jab a pod can boot from. ...sealing
            without serve payloads..."  → deploy fails on the host
```

### 6.2 `jac scale deploy` with a valid entry (normal path)

```text
pack_jab
├─ _precompile_app
│  ├─ stage files (no stale manifest copied)                      ← CHANGED
│  ├─ bake → writes fresh, portable .jac/serve_manifest.json      ← CHANGED (#9613)
│  ├─ require_serve_manifest(stage, ...) → ok                     ← NEW
│  ├─ precompile --seal → _precompiled/MANIFEST.json
│  └─ existing seal gate → ok
└─ tar step
   ├─ precompiled artifacts added
   ├─ tar.add(require_serve_manifest(staged)) → exactly one member ← CHANGED
   └─ vendor wheels, etc.
```

### 6.3 Manifest removed after the bake

```text
pack_jab tar step
└─ require_serve_manifest(staged) → RuntimeError (no bake detail)  ← NEW
```

### 6.4 `jac build --as jab`

Unchanged. It does not go through `bundle.jac`. `bake_serve_payloads` still returns `True` with a warning when there is no entry.

| Scenario | Before | After |
|---|---|---|
| Entry missing, no local manifest | Pack succeeds; pods crash-loop | Host raises `RuntimeError` with bake stdout |
| Entry missing, stale local manifest | Pack succeeds with the stale manifest | Host raises (stale copy not staged) |
| Entry valid, stale local manifest | Two `.jac/serve_manifest.json` members; extraction order decides | One fresh member |
| Manifest deleted between bake and tar | Pack succeeds without it | Host raises at the tar step |
| Entry valid, no local manifest | Works | Works (manifest now portable) |
| `jac build --as jab`, no entry | Warning, success | Same |

**Behaviour change users will notice:** a project whose entry does not resolve (including a project relying on a default `main.jac` it doesn't have) now fails `jac scale deploy` on the host. Before, it "succeeded" and then failed in the cluster.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` fail when there is no entry?**
The bake runs inside the pod binary, which may be an older release, so a fix there would not reach every deploy. `jac build --as jab` also calls it and is meant to keep its warn-and-continue behaviour. The scale bundler on the host is where the pod's fate is decided.

**Q: Why two gates instead of one?**
The bake gate catches the common case (no entry) early, before `precompile --seal`, and attaches the bake's stdout as the reason. The tar-step gate catches a manifest that disappears after the bake (issue route 1), where no bake output is in scope.

**Q: Is the tar-step gate tested?**
No. Its earlier test used a mock, and the reviewer asked you to drop it, because the bake gate is the one a real deploy hits.

**Q: Could dropping `.jac/serve_manifest.json` from `_is_bundle_required` break anyone?**
Only someone relying on a hand-written or leftover local manifest being shipped. The seal always bakes a fresh one, so a local copy was at best redundant and at worst stale or duplicated.

**Q: How does the test prove the `_is_bundle_required` change?**
Row 2 writes a stale `.jac/serve_manifest.json` and has no resolvable entry. With the old rule, the stale file would be in the stage, the gate would pass, and nothing would raise. The test asserts that a `RuntimeError` is raised.

**Q: Why are the `seal.jac` changes in this PR?**
They are #9613's commit. The fixtures now bake a manifest, and without the portable manifest the absolute stage path would end up in it and break the "identical content gives identical bytes" test. They should vanish after the rebase.

**Q: Why did four unrelated tests change?**
Their fixtures had no `main.jac` (the default entry), so they packed bundles no pod could boot. Under the new gate those packs would fail. Adding `main.jac` makes them realistic, and no assertion was weakened.

**Q: What does the user see now when the entry is wrong?**
A host-side `RuntimeError` naming `<stage>/.jac/serve_manifest.json` and saying the deploy cannot produce a bootable `.jab`. It is followed by up to 4000 characters of bake output, which includes "sealing without serve payloads".

**Q: Does the pod side still crash with a bare `Errno 2` if a bad bundle gets through somehow?**
Yes. This PR does not change `_prepare_sealed` in `application.jac`. Better boot-side diagnostics and a manifest format stamp were split into separate issues.

**Q: What happens on a dev machine without the pod binary?**
Row 1 of the table still runs and asserts. Row 2 skips, so the test shows as "skipped". On CI, `JAC_TEST_STRICT=1` turns that skip into a failure.
