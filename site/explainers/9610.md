## 1. The short version

`jac scale deploy` builds your Jac app into a single bundle file (a `.jab`), ships it to Kubernetes, and every service pod boots from it. To boot quickly, a pod needs a small file inside the bundle: `.jac/serve_manifest.json`, the "serving metadata". A step called the bake writes that file on the host while the app is being sealed.

**Before this PR, the host could pack and ship a `.jab` with no serve manifest and still report success. Every pod then crash-looped at boot with `Sealed application has no serving manifest` (on 0.37.12, `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`).** The easiest way to hit it is a `jac.toml` with `entry-point = "missing"`. The bake prints `sealing without serve payloads`, returns success, and nothing downstream checks for the file. A second problem: a stale `.jac/serve_manifest.json` in your working tree was force-copied into the bundle, so the `.jab` could hold two members with the same name.

**You added one host-side gate, `require_serve_manifest(stage, detail)`. It raises a `RuntimeError` naming the missing path, and it runs in two places: right after the bake, and in the tar step of `pack_jab`. You also stopped treating a working-tree `.jac/serve_manifest.json` as a file that must always be bundled.** The deploy now fails on your machine, and the bake's own warning appears in the error.

**Status:** Open, not approved. @MusabMahmoodh requested changes on 2026-09-30. His 2026-10-08 review was dismissed, and his latest review (2026-10-13) is a comment that names a test this PR breaks. ## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. Its source files end in `.jac`. |
| Declaration / `impl` split | Jac can declare a function in one file (`bundle.jac`: `def require_serve_manifest(...) -> Path;`) and implement it in another (`impl/bundle.impl.jac`: `impl require_serve_manifest(...) { ... }`). That is why the PR touches both files. |
| jac-scale | The plugin that deploys Jac apps to Kubernetes. |
| Kubernetes pod | One running copy of a service. A deploy starts many pods, and each one boots from the same bundle. |
| Crash-loop | A pod that fails at boot, gets restarted by Kubernetes, fails again, and repeats. |
| `.jab` | The bundle file: a gzipped tar archive holding app sources, precompiled artifacts and metadata. Each pod extracts it and runs `jac run --serve`. |
| Host | The machine running `jac scale deploy` (your laptop or CI). The PR moves the failure here, where it is cheap. |
| Pod binary / `seal_binary` | The `jac` executable the pods will run, passed to `pack_jab` as bytes. The host runs it as a subprocess, so the artifacts it produces match the pod's Jac version. This binary may be an older release than the host's Jac. |
| Seal / sealing | Precompiling the app ahead of time so the pod does not compile at boot. It produces `_precompiled/MANIFEST.json` and related files. |
| Seal stage (`stage`, `staged`) | A temporary directory where the app is copied, baked and sealed before it is tarred into the `.jab`. |
| Entry point | The app's main file, set by `entry-point` in `jac.toml` (default `main.jac`). `resolve_entry_file` turns that setting into a file path, or `None` if no such file exists. |
| Bake / `bake_serve_payloads` | The step, run inside the pod binary, that writes the serve manifest. If the entry does not resolve, it prints `sealing without serve payloads` and still returns success. |
| Serve manifest (`.jac/serve_manifest.json`, `SERVE_MANIFEST_REL`) | The serving metadata the pod reads at boot. `SERVE_MANIFEST_REL` is the constant holding its relative path. **This is where the bug is: nothing on the host required it to exist.** |
| `_precompile_app` | Host function that runs the bake subprocess and then `jac precompile --seal`. Before this PR it checked only their exit codes. |
| `pack_jab` | Host function that builds the `.jab`: it seals the app, then writes the tar archive. |
| `_is_bundle_required` | Returns `True` for paths that must always go into the bundle, whatever the filters say. It used to include `.jac/serve_manifest.json`. |
| `require_serve_manifest` | **The new gate this PR adds.** It returns the manifest path, or raises `RuntimeError` if the file is missing. |
| `arcname`, `det_tar_member` | `arcname` is the path a file gets inside the tar archive. `det_tar_member` is a filter that makes tar entries deterministic (same input gives the same bytes). |
| Fail closed / fail fast | Refuse early with a clear error instead of carrying on and failing later somewhere worse. |
| `require_pod_binary()` | Test helper that returns the built pod binary. It skips the test if the binary is absent, or fails it when `JAC_TEST_STRICT=1` (as on CI). |
| Table-driven test | One test that loops over a list of cases (rows), each with its own inputs and expected results. |
| Mock / `patch.object` | Replacing a real function with a fake during a test. The reviewer asked for no mocks in new scale tests. |
| Bundle cache (#9988) | A newer feature on main: if the sources and the pod binary are unchanged, `pack_jab` reuses a previously sealed `.jab` instead of sealing again. |

## 3. The problem, step by step

### 3.1 The setup

- **Host:** `jac scale deploy` calls `pack_jab(project_dir, seal_binary)`.
- **`_precompile_app`:**
  1. Runs the pod binary to bake. This should write `stage/.jac/serve_manifest.json`.
  2. Runs `jac precompile --seal`. This writes `_precompiled/MANIFEST.json`, and that file was already gated.
- **Tar step in `pack_jab`:** adds sources, `_precompiled/` and the serve manifest to the `.jab`.
- **Pod:** extracts the `.jab` and runs `jac run --serve`. At boot, `_prepare_sealed` reads the serve manifest with no existence check.

### 3.2 What went wrong: the entry does not resolve

```text
1. jac.toml says entry-point = "missing"; no such file exists
2. pack_jab → _precompile_app copies the app into the seal stage
3. Bake subprocess: resolve_entry_file → None
   stdout: "...sealing without serve payloads"
   bake_serve_payloads returns True → exit code 0
   stage/.jac/serve_manifest.json: ABSENT
4. _precompile_app checks only the exit code → OK               ← WRONG: no check for the file
5. precompile --seal succeeds → _precompiled/MANIFEST.json present (gate passes)
6. Tar step: `if serve_manifest.is_file()` → False → silently skipped   ← WRONG
7. pack_jab returns a .jab; the deploy reports success
8. Every pod: "Loading sealed application artifacts"
   → "[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'"
   → exit 1 → crash-loop
```

The issue lists a second route to the same state: the manifest is deleted between the bake and the tar step. `_precompiled/MANIFEST.json` exists, the serve manifest does not, and step 6 skips it in the same silent way.

### 3.3 What went wrong: a stale local manifest

```text
1. Working tree has an old .jac/serve_manifest.json (left over from an earlier run)
2. _is_bundle_required(".jac/serve_manifest.json") → True → force-copied into the stage
   and into the source members                                  ← WRONG
3a. Entry missing: the bake writes nothing, but the stale copy sits in the stage
    → any existence check would pass with stale data
3b. Entry valid: the bake writes a fresh manifest
    → the .jab has TWO members with arcname .jac/serve_manifest.json (stale + fresh)
4. Pod extraction order decides which one wins                  ← WRONG
```

The issue's "Scope note (c)" flagged this as unverified. Your description says you reproduced it on `e8b3d8ad5` ("the pack shipped it twice").

### 3.4 Why it mattered

- The failure was pushed out to N pods instead of one host process. That makes it slower and more expensive to notice, and the boot error does not mention the entry point.
- On 0.37.12, pods crash-loop. On 0.37.11 the same gap meant a silent full recompile at boot: the 7 minute / 4.5Gi boot measured in #9136.
- The issue calls this "silent fallback at a decision point". It is the same class of bug as #7936 and the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, not in the pod.** If the seal stage has no serve manifest after the bake, or at tar time, `pack_jab` raises with the path and the bake's own output, and a working-tree copy can never stand in for the fresh one.

The check sits in the scale bundler, not in `bake_serve_payloads`, for two reasons. The bake runs inside the pod binary, which may be an older release, so changing it would not reach existing binaries. And `jac build --as jab` legitimately relies on the bake's lenient behaviour.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/injector/impl/bundle.impl.jac`: the new gate

```diff
+impl require_serve_manifest(stage: Path, detail: str = "") -> Path {
+    import from jaclang.server.sealed_serve { SERVE_MANIFEST_REL }
+
+    serve_manifest = stage / SERVE_MANIFEST_REL;
+    if not serve_manifest.is_file() {
+        raise RuntimeError(
+            f"The app stage has no {serve_manifest}, so the deploy cannot "
+            f"produce a .jab a pod can boot from. {detail}".rstrip()
+        );
+    }
+    return serve_manifest;
+}
```

- **What:** It builds `stage/.jac/serve_manifest.json`. If the file is missing, it raises a `RuntimeError` naming the full path. Otherwise it returns the path.
- **Why:** This is the single "fail closed" rule both call sites share.
- **Things to notice:**
  - `.rstrip()` removes the trailing space when `detail` is empty.
  - Returning the path lets the tar step use the gate inline.

### 5.2 `bundle.impl.jac`: gate after the bake in `_precompile_app`

```diff

             );
         }
+        require_serve_manifest(stage, (prepared.stdout or "").strip()[-4000:]);
 
         result = subprocess.run(
             [str(jac_path), "precompile", str(stage_root)] + seal_flags,
```

- **What:** The bake subprocess's result is `prepared`. If it exited 0, the new line checks for the manifest before `precompile --seal` runs. It passes the last 4000 characters of the bake's stdout as `detail`.
- **Why:** This fixes step 4 of 3.2. The error is blamed on the bake, and it carries the `sealing without serve payloads` line that explains the cause. Musab quoted the resulting message: `entry-point '.../main.jac' not found; sealing without serve payloads`.

## 6. How execution flows after the PR

### 6.1 `jac scale deploy` → `pack_jab`

```text
pack_jab(project_dir, seal_binary)
├─ (bundle cache from #9988: may return saved bytes early; see 6.3)
├─ collect sources into the seal stage
│   └─ _is_bundle_required(.jac/serve_manifest.json) → False      ← CHANGED
├─ _precompile_app(...)
│   ├─ run pod binary: bake serve payloads
│   │   └─ non-zero exit → RuntimeError (unchanged)
│   ├─ require_serve_manifest(stage, bake stdout tail)            ← NEW
│   │   └─ missing → RuntimeError "...has no .../.jac/serve_manifest.json...
│   │                 sealing without serve payloads"
│   ├─ run pod binary: precompile --seal
│   └─ _precompiled/MANIFEST.json missing → "App seal did not complete" (unchanged)
└─ tar step
    ├─ add _precompiled artifacts
    ├─ tar.add(require_serve_manifest(staged), arcname=SERVE_MANIFEST_REL) ← CHANGED
    │   └─ missing → RuntimeError
    └─ add _vendor wheels, etc.
→ returns .jab bytes, which now always contain exactly one fresh serve manifest
```

### 6.2 Pod boot

```text
pod: tar xzf app.jab → jac run --serve $JAC_SV_FILE
└─ _prepare_sealed reads .jac/serve_manifest.json (unchanged, still unguarded,
   but the host now guarantees the file is there)
```

### 6.3 Cached bundle (not changed by this PR)

```text
pack_jab → cache hit (same sources + same pod binary)
└─ return saved bytes   ← neither gate runs (per Greptile; ordering not visible in the diff)
```

### 6.4 `jac build --as jab`

This path is unchanged. It does not go through the scale bundler, so a missing entry is still only a warning there.

| Scenario | Before | After |
|---|---|---|
| Valid entry, no local manifest | `.jab` with one manifest | Same |
| Valid entry, stale local manifest | `.jab` with two same-named members; extraction order decides | One fresh member |
| Entry missing (`entry-point = "missing"`) | Deploy succeeds; pods crash-loop | **Deploy fails on host** with path + `sealing without serve payloads` |
| Entry missing, stale local manifest | Stale copy shipped; pods may boot on wrong metadata | Fails on host |
| Manifest vanishes after bake, before tar | Shipped without it | Fails at tar step |

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return `False` when the entry is missing?**
The bake runs inside the pod binary, which may be an older release, so a change there would not reach existing binaries. And `jac build --as jab` relies on the lenient behaviour. The host is where the pod's fate is decided, so the gate goes there.

**Q: Why two gates instead of one?**
The bake gate attributes the failure to the bake and includes its stdout, which is what a real deploy hits. The tar gate covers anything that removes the file between the bake and the tar step (the issue's route 1), and it replaces the silent `is_file()` skip.

**Q: Is the tar-step gate tested?**
Not on its own. The mock-based case was dropped on Musab's request, because the bake gate is the path a real deploy takes.

**Q: How does the test prove the stale local manifest is no longer shipped?**
Row 2 writes a stale `.jac/serve_manifest.json` and a missing entry. If `_is_bundle_required` still force-copied it, the stage would contain a manifest, the gate would pass, and the test would not get the expected `RuntimeError`.

**Q: Could this break existing users' deploys?**
Yes, deliberately, but only for projects whose entry does not resolve. Those bundles could never have booted on 0.37.12. The PR's own fixtures (`test_fat_bundle`, `test_pvc_injector`, `test_bundle_jacignore`) were in exactly that state.

**Q: What about bundles already in the #9988 cache?**
This is open. Greptile says a cache hit returns before either gate runs. You need to confirm this and then invalidate or validate cached bundles.

**Q: Why is `test-scale (microservices)` red?**
The #9988 cache test packs `_mini_app()`, which has only `svc.jac`, while the default entry is `main.jac`. The new gate correctly refuses it. The test fixture needs an entry.

**Q: Why pass only the last 4000 characters of stdout?**
It keeps the error message bounded while still including the final `sealing without serve payloads` warning. The existing bake error path above it uses the same `[-4000:]` cut.

**Q: Does the pod side still read the manifest unguarded?**
Yes. `_prepare_sealed` is unchanged. The issue's scope note leaves boot-side diagnostics and a manifest format stamp to separate issues.
