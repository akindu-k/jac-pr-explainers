## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine (the host), then ships that bundle to every Kubernetes pod. Each pod boots from a "sealed" (precompiled) image inside the bundle. To boot, it needs the file `.jac/serve_manifest.json`, which a "bake" step writes during the seal.

**Before this PR, the host could pack and ship a `.jab` with no `.jac/serve_manifest.json` and still report success. Every pod then failed at boot with `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'` and crash-looped.** The simplest trigger is an `entry-point` that does not resolve to a file. In that case the bake prints `sealing without serve payloads`, writes nothing, and still exits 0. A third problem made this worse: a stale `.jac/serve_manifest.json` left in your working tree was force-copied into the bundle. It could hide the missing fresh file, or end up as a second tar member with the same name.

**The PR adds one host-side gate, `require_serve_manifest(stage, detail)`. It raises a `RuntimeError` that names the missing path. It runs right after the bake and again in the tar step, and the PR stops shipping the working-tree copy of the manifest.** The deploy now fails on your machine with the bake's own warning in the message, instead of failing in N pods.

**Status:** Open. There is no approval yet. @MusabMahmoodh's earlier points all appear addressed, and his last review (2026-10-13) was "commented". On head `4eec4a7`, `test-compiler (equivalence, ...)` fails, so the aggregate `Everything Passed` check is red.

## 3. The problem, step by step

### 3.1 The setup

- **Host, `_precompile_app`:** this runs two subprocesses with the pod binary.
  1. The bake (`bake_serve_payloads`) writes `.jac/serve_manifest.json`.
  2. `jac precompile --seal` writes `_precompiled/MANIFEST.json`.
  
  Only the second output had an existence check ("App seal did not complete").
- **Host, `pack_jab`:** tars the stage into the `.jab`. It added the serve manifest only `if serve_manifest.is_file()`.
- **Host, `_is_bundle_required`:** force-included `.jac/serve_manifest.json` from your working tree.
- **Pod:** `_prepare_sealed` in `compiler/driver/application.jac:216` does `json.loads((Path(image_root) / SERVE_MANIFEST_REL).read_text())` with no check.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml has entry-point = "missing" (or the default main.jac does not exist)
2. pack_jab → _precompile_app → bake subprocess runs bake_serve_payloads
3. resolve_entry_file → None, prints "sealing without serve payloads"
4. bake_serve_payloads returns True → subprocess exit 0          ← WRONG: "no entry" treated as success
5. _precompile_app checks only the exit code → continues
6. precompile --seal writes _precompiled/MANIFEST.json → gate passes
7. tar step: stage/.jac/serve_manifest.json is not a file → skipped   ← WRONG: silently skipped
8. pack_jab returns a .jab; deploy reports success
9. Every pod: "Loading sealed application artifacts" → [Errno 2] ... serve_manifest.json → exit 1 → crash loop
```

### 3.3 What went wrong: stale local manifest

```text
1. Working tree contains an old .jac/serve_manifest.json (from an earlier build)
2. Source copy: _is_bundle_required(".jac/serve_manifest.json") → True → copied into stage + source members   ← WRONG
3a. Entry missing: bake writes nothing, but the stale copy sits in the stage
    → any is_file() check passes → pod boots on wrong metadata
3b. Entry valid: bake writes a fresh manifest, AND the stale one is still a source member
    → .jab has two members named .jac/serve_manifest.json
    → extraction order decides which one the pod sees
```

The issue listed 3.3 as "unverified, for a follow-up". The PR description says you reproduced it on `e8b3d8ad5` ("the pack shipped it twice").

### 3.4 Why it mattered

- According to the issue, on 0.37.12 the pod crash-loops. On 0.37.11 the pod silently recompiled the whole server at boot, which is the 7-minute / 4.5Gi boot measured in #9136.
- The failure appeared on every pod, long after the host had reported success. Yet the host had all the facts it needed to refuse.
- The issue calls this the same class of bug as #7936 and the existing `check_fleet_entries` gate: silent fallback at a decision point.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, not in the pod.** If the seal stage has no `.jac/serve_manifest.json` after the bake, raise an error that names the path and includes the bake's output, and never let a working-tree copy stand in for the fresh one.

The gate lives in the scale bundler because the bake runs inside the pod binary, which may be an older release. Putting the check on the host also leaves `jac build --as jab` (the other caller of `bake_serve_payloads`) unchanged.

**What:**
- `require_serve_manifest` checks the stage for the file. It raises a `RuntimeError` naming the full path and appends `detail`. It returns the path on success.
- `_precompile_app` calls it right after the bake. The `detail` is the last 4000 characters of the bake's stdout, which is where `sealing without serve payloads` is printed.
- The tar step now calls the gate instead of skipping silently.
- `_is_bundle_required` keeps only the `.jac/admin` rule.

**Why:**
- Gate 1 fixes step 4–5 of 3.2.
- Gate 2 fixes step 7 of 3.2.
- The `_is_bundle_required` change fixes 3.3: the only serve manifest in the bundle is the one the seal just baked.

**Things to notice:**
- Gate 1 runs *before* `precompile --seal`, so a bad deploy fails before the expensive precompile.
- The trailing `.rstrip()` drops the dangling space when `detail` is empty, which is the tar-step call.
- Gate 2 is defense in depth. In a normal run gate 1 already passed. It catches a file disappearing between bake and pack, which was the issue's reproduction #1. Per your description, no test exercises it directly.
- `bake_serve_payloads` still returns `True` with no entry. That was a deliberate choice, so `jac build --as jab` keeps its behaviour.
- The rest of `_is_bundle_required` (above line 12) is not in the diff. It looks like the function lists exceptions to a rule that otherwise skips `.jac/` paths, but the diff doesn't show that.
- Greptile asked whether a cached `.jab` returned early by `pack_jab` skips both gates. The cache-return code is not in the diff. Your description answers that the cache key includes the pod binary's hash (see 9 and 11).
- @MusabMahmoodh confirmed this composes with #9615's `_precompile_app` rewrite on main.

### 6.2 `jac build --as jab`

This path is unchanged. `bake_serve_payloads` still warns and returns `True` with no entry, and the gate is only in the scale bundler.

| Scenario | Before | After |
|---|---|---|
| Entry missing, no local manifest | Pack succeeds; pods crash-loop | Pack fails on host after bake, error includes `sealing without serve payloads` |
| Entry missing, stale local manifest | Stale copy shipped; pods boot on wrong metadata (or crash) | Stale copy not staged; pack fails on host as above |
| Entry valid, stale local manifest | Two `.jac/serve_manifest.json` members; extraction order wins | One fresh member |

**Behaviour change users will notice:** a project whose entry does not resolve can no longer be deployed with `jac scale deploy`. Before, such a "successful" deploy could never boot anyway.

## 11. Questions your senior might ask

**Q: Why not fix `bake_serve_payloads` to return `False` when there's no entry?**
The bake runs inside the pod binary, which may be an older release, so a fix there wouldn't protect deploys that use an older binary. It would also change `jac build --as jab`, which deliberately keeps warning and succeeding.

**Q: Why two gates? Isn't one enough?**
The gate after the bake catches the real-world case and includes the bake's `sealing without serve payloads` line in the error. The tar-step gate replaces a silent skip and catches a manifest that disappears between bake and pack, which was the issue's reproduction #1.

**Q: Why remove `.jac/serve_manifest.json` from `_is_bundle_required`?**
The seal always bakes a fresh one. A working-tree copy could either satisfy the gate falsely or end up as a second tar member with the same name, and then extraction order decides which one the pod reads.

**Q: Can a previously cached bad `.jab` still ship?**
Your description says no: the seal cache key includes the pod binary's hash, so a release with this fix never reuses a bundle sealed by an older one. The cache code isn't in this diff, and you haven't replied to Greptile's thread on it.

**Q: Does this break anyone's working deploy?**
Only deploys whose entry doesn't resolve, and those could never boot anyway. Several test fixtures were in exactly that state and needed a `main.jac` or an `entry-point`.

**Q: Why is the tar-step gate not tested?**
@MusabMahmoodh asked to drop the mock-based case, because scale tests stay mock-free and the bake gate is the one a real deploy hits.

**Q: What does the user see now?**
A `RuntimeError` like: `The app stage has no <stage>/.jac/serve_manifest.json, so the deploy cannot produce a .jab a pod can boot from. ... sealing without serve payloads`.

**Q: Why did `archwire.jac` change?**
`require_serve_manifest` and the gate test use `SERVE_MANIFEST_REL`, and archwire is where that name is wired into the modules that use it.

**Q: Is the equivalence failure yours?**
Probably not, since it's a compiler suite and the PR only touches scale code, tests and archwire. That isn't confirmed; check the log or compare with main.
