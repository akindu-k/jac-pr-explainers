## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine (the "host") and ships it to Kubernetes pods. Before packing, a "seal" step pre-compiles the app and "bakes" serving metadata into `.jac/serve_manifest.json`. A pod needs that file to boot.

**The host could pack and ship a `.jab` with no `.jac/serve_manifest.json`, report success, and leave every pod crash-looping at boot.** Three things let this happen:

- The bake step returns success when the app entry does not resolve to a file.
- The tar step quietly skipped the manifest when it was missing.
- A stale copy of the manifest from your working tree could be shipped instead of a fresh one.

The pod error looked like `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`. The issue reports this error on 0.37.12. The PR description quotes it as `Sealed application has no serving manifest`.

**You added `require_serve_manifest(stage, detail)`, which raises on the host when the stage has no serve manifest. It is called right after the bake and again in the tar step. You also stopped force-shipping a working-tree `.jac/serve_manifest.json`.** The deploy now fails on your machine, and the error includes the bake's own `sealing without serve payloads` warning. You also fixed several test fixtures that packed apps with no resolvable entry, because the new gate correctly refuses them.

**Status:** Open, with no approving review. @MusabMahmoodh's latest review (2026-10-13, "commented") said the only remaining red was caused by `_mini_app()` having no entry. Your head commit `f4131ef` fixes that. On the head commit, `build-kit` is still running, and the two jobs that were red before (`test-scale (microservices)` and `jac-check`) are not reported yet.

## 3. The problem, step by step

### 3.1 The setup

On the host, `pack_jab` calls `_precompile_app`, which:

1. Copies the project into a seal stage. Paths are filtered, but `_is_bundle_required` paths are forced in.
2. Runs the **bake** in a pod-binary subprocess, which writes `.jac/serve_manifest.json`.
3. Runs `jac precompile --seal` in another subprocess.
4. Checks that `_precompiled/MANIFEST.json` exists. This was the existing gate.

Then `pack_jab` tars the stage. On boot, the pod reads `.jac/serve_manifest.json` without first checking that it exists.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml says entry-point = "missing"     (or no entry; default main.jac doesn't exist)
2. _precompile_app copies project → stage    stage has no .jac/serve_manifest.json
3. bake subprocess: resolve_entry_file → None
   prints "sealing without serve payloads"
   bake_serve_payloads returns True → exit 0   ✗ WRONG: "no entry" treated as success
4. _precompile_app checks only the exit code → continues
5. precompile --seal runs → _precompiled/MANIFEST.json exists → seal gate passes
6. pack_jab: `if serve_manifest.is_file()` → False → skip   ✗ WRONG: silently ships without it
7. deploy reports success, .jab goes to N pods
8. each pod: jac run --serve → reads .jac/serve_manifest.json → FileNotFoundError → exit 1
9. pod crash-loops
```

### 3.3 What went wrong: a stale local manifest

```text
1. working tree has an old .jac/serve_manifest.json (e.g. from a local `jac build`)
2. _is_bundle_required(".jac/serve_manifest.json") → True
   → stale copy force-copied into the stage and into the source members   ✗ WRONG
3a. entry missing: bake writes nothing, but stage already has the stale file
    → step 6 above finds a file → stale manifest shipped, every gate fooled
3b. entry valid: bake writes a fresh manifest into the stage
    → .jab gets TWO members named .jac/serve_manifest.json (stale + fresh)
    → extraction order decides which one the pod reads                     ✗ WRONG
```

The PR description says both cases were reproduced on `e8b3d8ad5`.

### 3.4 Why it mattered

- Issue #9138: a deploy "succeeds" and the failure is pushed onto every pod. On 0.37.12 the pod crash-loops. On 0.37.11 the pod instead recompiled the whole server side at boot, which is the 7-minute / 4.5Gi boot measured in #9136.
- The host had every fact needed to refuse the pack. The issue lists this as the same class of bug as #7936 and the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Fail on the host, by name, when the seal leaves no serve manifest.** After the bake and again when tarring, require `.jac/serve_manifest.json` in the stage, and never let a working-tree copy stand in for it.

The gate sits in the scale bundler rather than in `bake_serve_payloads` for two reasons. First, the bake runs inside the pod binary, which may be an older release. Second, `jac build --as jab` (the other caller of the bake) should keep its current warn-and-continue behaviour.

## 6. How execution flows after the PR

### 6.1 `jac scale deploy` → `pack_jab`

```text
pack_jab(project_dir, seal_binary)
├─ seal cache hit? → return cached .jab bytes          (unchanged; skips the gates, see §9)
└─ _precompile_app(base, seal_binary, ...)
   ├─ copy project → stage
   │   └─ _is_bundle_required: .jac/serve_manifest.json no longer forced   ← CHANGED
   ├─ bake subprocess (pod binary): bake_serve_payloads
   │   ├─ entry resolves → writes stage/.jac/serve_manifest.json
   │   └─ entry missing → prints "sealing without serve payloads", exit 0
   ├─ exit code != 0 → RuntimeError                     (unchanged)
   ├─ require_serve_manifest(stage, bake stdout tail)   ← NEW
   │   └─ missing → RuntimeError "The app stage has no …/.jac/serve_manifest.json … sealing without serve payloads"
   ├─ precompile --seal subprocess
   └─ _precompiled/MANIFEST.json missing → RuntimeError (unchanged)
└─ tar the stage
   ├─ _precompiled/ artifacts
   ├─ tar.add(require_serve_manifest(staged))            ← CHANGED (was: skip if missing)
   └─ _vendor/ wheels …
```

### 6.2 Pod boot

This flow is unchanged. Pods now only ever receive bundles that contain exactly one, freshly baked serve manifest.

| Scenario | Before | After |
|---|---|---|
| Entry resolves, no local manifest | Ships fine | Ships fine |
| Entry missing, no local manifest | Pack succeeds, pods crash-loop | Pack fails on host after the bake, with the warning in the error |
| Entry missing, stale local manifest | Stale manifest shipped, gates fooled | Pack fails on host (stale copy no longer staged) |
| Entry valid, stale local manifest | Two `.jac/serve_manifest.json` tar members | One fresh member |
| Manifest removed between bake and tar | Shipped without it | Tar-step gate raises |
| `jac build --as jab` with missing entry | Warning, continues | Same (not touched) |
| Cached bundle from before the fix | Returned | Returned (description argues the cache key prevents this; see §9) |

**User-visible change:** projects whose `entry-point` (or default `main.jac`) does not exist now get a hard error from `jac scale deploy`. Their pods could never have booted, so this changes a silent failure into a loud one. A hand-placed `.jac/serve_manifest.json` in the working tree is no longer shipped.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return failure when the entry is missing?**
The bake runs inside the pod binary, which may be an older release, so a fix there would not reach older binaries. It is also used by `jac build --as jab`, which should keep warning and continuing. The host bundler is where the pod's fate is decided.

**Q: Why two gates if the bake gate fires first?**
The bake gate gives the best error, with the bake's stdout. The tar-step gate catches anything that removes the file later, which was reproduction path 1 in the issue. It replaces a silent `is_file()` skip, so it costs nothing.

**Q: Is the tar-step gate tested?**
Not on its own. The only way to reach it without a real bake failure was a mock, and the reviewer asked to drop it because scale tests stay mock-free. The bake gate is the one a real deploy hits.

**Q: Can a cached broken `.jab` still be shipped?**
The cache returns before the gates run. The PR's argument is that the cache key includes the pod binary's hash, so a release with the fix never reuses an older seal. That holds if host and pod binary are upgraded together, which the diff itself does not show.

**Q: Could removing `.jac/serve_manifest.json` from `_is_bundle_required` break someone?**
Only someone relying on a hand-written or stale manifest being shipped. The seal always bakes a fresh one, and keeping the local copy caused duplicate tar members and could hide the missing-manifest bug.

**Q: How does row 2 prove the `_is_bundle_required` change?**
It writes a stale manifest and uses a missing entry. If the stale copy were still forced into the stage, `require_serve_manifest` would find a file and the pack would not raise, so the test would fail.

**Q: What does the user see now?**
A `RuntimeError` on their machine like `The app stage has no …/.jac/serve_manifest.json, so the deploy cannot produce a .jab a pod can boot from. … entry-point '…/main.jac' not found; sealing without serve payloads`.

**Q: Why did so many test fixtures change?**
They packed apps whose entry (default `main.jac`) did not exist, so no pod could have booted them. The new gate correctly refuses those, so the fixtures now ship a real entry. The assertions stay the same, apart from the `app.jac` → `main.jac` filename in `test_pvc_injector`.

**Q: Why is `archwire.jac` touched?**
`require_serve_manifest` uses `SERVE_MANIFEST_REL` without importing it, and the test imports it from `server.sealed_serve`. Both of these uses must be declared in the repo's import wiring graph.
