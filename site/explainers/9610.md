# fix(scale): fail the pack when the seal leaves no serving metadata (#9138)

[#9610](https://github.com/jaseci-labs/jac/pull/9610) by @akindu-k · opened 28 Sept 2026 · +91 −27 in 9 files

<!-- explainer -->

## In short

`jac scale deploy` could build and ship a `.jab` bundle with no `.jac/serve_manifest.json`. The deploy looked successful, but every pod crashed at boot. You changed the host-side packing code so it stops with a clear error when the seal leaves no serve manifest. You also stopped it from copying a stale local manifest into the bundle.

## Words to know

- **`.jab`**: The packed, sealed application bundle (a tar.gz) that `jac scale deploy` ships to the pods.
- **Seal / sealing**: Compiling and preparing the app ahead of time, so the pod can boot it without compiling.
- **Serve manifest** (`.jac/serve_manifest.json`): A JSON file made during sealing. It describes what the app serves. A pod refuses to boot without it (`Sealed application has no serving manifest`).
- **Bake** (`bake_serve_payloads`): The step that writes the serve manifest into the seal stage. It runs inside the pod binary.
- **Pod binary**: The Jac executable that runs the seal. It may be an older release than the host.
- **Stage**: A temporary directory where the app is copied and sealed before packing.
- **Entry point / app entry**: The file the app starts from, set by `entry-point` in `jac.toml`, or `main.jac` by default.
- **Host**: The machine where you run `jac scale deploy`, as opposed to the pods.
- **Bundle-required** (`_is_bundle_required`): A check that says which files must always be copied into the stage and the bundle.
- **Stale file**: An old local copy that no longer matches the current build.
- **Crash-loop**: A Kubernetes pod that keeps starting, failing and restarting.
- **Deterministic packing**: The same input gives the same bytes. Duplicate tar members break this.

## The problem

Before this PR, a missing serve manifest slipped through at three points:

1. `bake_serve_payloads` returns success without writing anything when the entry does not resolve to a file. It only prints a `sealing without serve payloads` warning. `_precompile_app` checked only the exit code, so it saw success.
2. In `pack_jab`, the tar step added the manifest only `if serve_manifest.is_file()`. A missing file was silently skipped.
3. `_is_bundle_required` force-copied a working-tree `.jac/serve_manifest.json` into the stage and the source members. A stale local copy could satisfy the existence checks. With a valid entry, the `.jab` held two `.jac/serve_manifest.json` members, and extraction order decided which one the pod used.

Example: a project with `entry-point = "missing"` packed fine, and the pod exited 1 when booted. Every pod failed, and the host reported success.

## The changes, one by one

### `jac/jaclang/scale/injector/bundle.jac`

This is the main fix.

**New `require_serve_manifest(stage, detail="")`.** It checks that `stage / SERVE_MANIFEST_REL` is a file. If not, it raises a `RuntimeError` naming that path, with `detail` appended. It returns the path when it exists.

```
serve_manifest = stage / SERVE_MANIFEST_REL;
if not serve_manifest.is_file() {
    raise RuntimeError(...f"{detail}".rstrip());
}
return serve_manifest;
```

The check gives a clear error on the host instead of a crash-loop in the pods.

**`_precompile_app`** now calls `require_serve_manifest(stage, ...)` right after the bake. It passes the last 4000 characters of the bake's stdout, so the error includes the `sealing without serve payloads` warning that explains the cause. This closes hole 1.

**`pack_jab` tar step.** The `if is_file()` skip is gone. It now calls `tar.add(str(require_serve_manifest(staged)), ...)`, so a missing manifest is refused. This closes hole 2.

**`_is_bundle_required`.** It no longer returns True for `.jac/serve_manifest.json`. Only `.jac/admin` remains. The seal always bakes a fresh manifest, so a working-tree copy is never staged or shipped. This closes hole 3 and removes the duplicate member.

Why the gate is on the host and not inside `bake_serve_payloads`: the bake runs in the pod binary, which may be an older release. Also, `jac build --as jab` keeps its current behaviour.

### `jac/jaclang/dist/seal.jac`

This comes from #9613 (the portable manifest), which this branch carries until it merges.

- `_without_key(record, dropped)` returns a copy of a dict without one key.
- `_portable_manifest(manifest)` removes the top-level `root` key and the `module` key from each `surface` entry. Both would otherwise hold seal stage paths.
- `build_serve_manifest` uses it for the entry manifest and for each item in `module_manifests`.

The fixture apps now bake a manifest, so the determinism tests need this fix.

### Test fixture files

`test_fat_bundle.jac`, `test_pvc_injector.jac`, `test_seed_determinism.jac` and `test_bundle_jacignore.jac` packed apps with no resolvable entry. The default `main.jac` was missing, so no pod could have booted them. With the new gate they would fail. You renamed `svc.jac` and `app.jac` to `main.jac`. In `test_bundle_jacignore.jac` you write a `main.jac` before packing. The PR says no assertion was weakened.

### `release_notes/unreleased/jaclang/9610.bugfix.md`

A release note: a deploy whose entry does not resolve now fails on your machine with a clear error.

## How it runs now

1. You run `jac scale deploy`, which calls `pack_jab`.
2. `_precompile_app` copies the project into a stage. `.jac/serve_manifest.json` from the working tree is no longer force-copied (changed).
3. The pod binary runs the bake (`bake_serve_payloads`), which writes a fresh manifest, or only warns if the entry does not resolve.
4. `require_serve_manifest(stage, stdout)` runs. If the file is missing, a `RuntimeError` stops the deploy with the warning in the message (new).
5. Precompile continues.
6. In the tar step, `require_serve_manifest(staged)` supplies the manifest to add, and raises if it is absent (changed).
7. The `.jab` holds exactly one fresh manifest.

## Tests

- **`test_app_precompile.jac`**: the test `an unrunnable pod binary fails the seal instead of shipping unsealed` is now a table-driven test named `a seal that cannot yield a bootable .jab fails the pack instead of the pod`. Each row writes a `jac.toml`, a stale `.jac/serve_manifest.json`, and calls `pack_jab`, then checks that an exception was raised.
  - Row 1: an unrunnable binary (`b"not-an-elf"`). It must raise, with no message check.
  - Row 2: `entry-point="missing"` with a stale local manifest, run on the real pod binary. The error must contain `RuntimeError`, the manifest path, and `sealing without serve payloads`. This covers the bake gate and the `_is_bundle_required` change. It skips without the binary, or fails under `JAC_TEST_STRICT`.
  - The tar-step gate is not tested separately, because a real deploy hits the bake gate first.
- **`test_application_preparation.jac`**: it checks that no baked manifest (entry or module) has a `root` key, and that no `surface` record has a `module` key. This proves the portable manifest part.
- The four fixture tests were adjusted as described above. The test count is unchanged.

## Explaining it in one minute

A deploy could ship a `.jab` with no serve manifest, because the bake step silently skipped it when the entry did not resolve, and the tar step skipped a missing file. A stale local manifest could also be copied in, even twice. I added `require_serve_manifest`, which raises on the host with the stage path and the bake's warning. It runs after the bake and in the tar step. I also stopped treating the manifest as bundle-required, so only the freshly baked one ships. The gate is on the host because the bake runs in a pod binary that may be older. I extended the precompile test into a table that includes a real bake with a missing entry over a stale manifest. I also fixed fixtures that had no `main.jac`.
