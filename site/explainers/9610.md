## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine (the "host"), then ships it to Kubernetes pods. Each pod reads `.jac/serve_manifest.json` from the bundle to know how to serve the precompiled app. A "seal" step on the host is meant to produce that file.

**The host could pack and ship a `.jab` with no `.jac/serve_manifest.json`, report success, and leave every pod to crash at boot with `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`.** Three things let the missing file through:

- The bake step returned success without writing the file when the app entry did not resolve.
- The tar step skipped the file when it was missing instead of refusing.
- A stale local copy in your working tree could be force-shipped in its place.

**You added one host-side check, `require_serve_manifest`, and call it after the bake and in the tar step. You stopped force-shipping the working-tree copy, and you made the seal cache skip any cached bundle that lacks the manifest.** A deploy with `entry-point = "missing"` now fails on the host with a `RuntimeError`. The error names the missing path and includes the bake's `sealing without serve payloads` warning.

## 3. The problem, step by step

### 3.1 The setup

- **Host side:** `pack_jab` → staging (filtered by `_is_bundle_required`) → `_precompile_app`, which runs bake, then `precompile --seal` → tar step → `.jab`.
- A seal cache can short-circuit all of this.
- **Pod side:** `_prepare_sealed` in `compiler/driver/application.jac:216` reads `.jac/serve_manifest.json` with no existence check (per the issue).

### 3.2 What went wrong

#### Case A: the entry does not resolve

```text
1. jac.toml: entry-point = "missing"   (or default main.jac, file absent)
2. pack_jab stages the project
3. _precompile_app runs bake subprocess
   resolve_entry_file -> None, prints "sealing without serve payloads" to stdout
   bake_serve_payloads -> return True, exit code 0, NO serve_manifest.json written
4. _precompile_app checks exit code only -> OK                 <- WRONG (no file check)
5. precompile --seal -> _precompiled/MANIFEST.json exists -> OK
6. tar step: if serve_manifest.is_file(): ... -> False, skip  <- WRONG (silent skip)
7. pack_jab returns .jab without .jac/serve_manifest.json; deploy "succeeds"
8. every pod: jac run --serve -> [Errno 2] ... serve_manifest.json, exit 1 -> crash-loop
```

#### Case B: a stale local `.jac/serve_manifest.json` in the working tree

```text
1. working tree has .jac/serve_manifest.json from some earlier run
2. staging: _is_bundle_required(".jac/serve_manifest.json") -> True    <- WRONG
   stale copy copied into the stage AND into the source members
3a. entry missing: bake writes nothing, but the stale file passes any existence check
    -> stale metadata ships
3b. entry valid: bake writes a fresh file
    -> .jab has TWO members named .jac/serve_manifest.json (stale + fresh)
4. pod extraction order decides which one wins
```

#### Case C: a cached bundle from before the gate (found in review by greptile)

```text
1. old host packed a .jab with no serve manifest; seal cache stored it under key K
2. user upgrades the host, pins the same pod binary, no source change -> key still K
3. pack_jab: cached is not None -> return cached bytes                <- WRONG
   (both new checks are never reached)
4. pods crash-loop as in Case A
```

### 3.3 Why it mattered

- On jac 0.37.12 the pods crash-loop, so the deploy looks green and the app is down on every pod.
- On 0.37.11 the pod silently recompiled the whole server at boot. Issue #9136 measured this as about 7 minutes and 4.5Gi.
- The host already knew everything needed to refuse. The issue frames this as the same class as #7936 and the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Refuse the pack on the host whenever the stage has no fresh serve manifest.** Check it right after the bake, again at tar time, and before reusing a cache, and never let a working-tree copy stand in for it.

The pod's fate is decided at pack time on the host, so failing there is cheap and gives a readable error. The check also lives in the scale bundler, not in `bake_serve_payloads`. That keeps it working when the pod binary is an older release, and it leaves `jac build --as jab` alone.

## 11. Questions your senior might ask

**Q: Why not fix `bake_serve_payloads` to return `False` when there is no entry?**
The bake runs inside the pod binary, which may be an older release, so a fix there wouldn't protect deploys that use an old pod binary. Its other caller, `jac build --as jab`, should keep its current warn-and-continue behaviour. The host gate works no matter which binary baked.

**Q: Why check in two places?**
The check after the bake gives the best error, because it includes the bake's stdout with `sealing without serve payloads`. The tar-step check covers the file disappearing between bake and pack, which the issue lists as a second route.

**Q: Is the tar-step gate tested?**
Not on its own. Reaching it needs a mock or a contrived deletion. @MusabMahmoodh asked to drop the mock, since scale tests are mock-free and real deploys hit the bake gate first.

**Q: Could dropping the `_is_bundle_required` rule break anyone?**
Only someone who relied on a hand-made local `.jac/serve_manifest.json` being shipped. The seal always bakes a fresh one, and the old rule caused duplicate tar members. The real-bake test row proves the stale copy is no longer staged.

**Q: Why check the cached bundle's contents instead of changing the cache key?**
The key covers the pod binary and the project inputs, not the host bundler's code. Checking contents catches any manifest-less bundle, however it got cached, without invalidating good caches. The cost is decompressing the cached archive on every cache hit.

**Q: What happens if the cached `.jab` is corrupt?**
`_bundle_ships` would raise from `tarfile.open`. Whether `_cached_seal` already guards against that is not visible in the diff, so check it.

**Q: Why did so many unrelated test fixtures change?**
They packed apps whose default entry, `main.jac`, did not exist. No pod could have booted those bundles, so the new gate correctly refused them. They now have a real entry, and no assertion was weakened.

**Q: What does `archwire.jac` change do, and could it be why jac-check is red?**
It declares `require_serve_manifest` and the test module as users of `SERVE_MANIFEST_REL`. The PR alone doesn't show whether jac-check's failure is related. You need the job log to answer this.

**Q: The issue suggested tightening the positive boot test to assert "Loading sealed application artifacts". Did you?**
No. This PR adds the negative cases and the cache case only. That tightening could be a follow-up.

**Q: Does the pod side get a better error now?**
No. `application.jac:216` still reads the file unguarded. This PR makes sure such a bundle never leaves the host. Boot-side diagnostics are filed separately, per the issue's scope note.
