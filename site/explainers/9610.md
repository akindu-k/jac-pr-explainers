# fix(scale): fail the pack when the seal leaves no serving metadata (#9138)

## In short

Before this PR, `jac scale deploy` could build and ship a `.jab` bundle that had no `.jac/serve_manifest.json`. The deploy reported success, but every pod then crashed at boot. You added a check on the host that stops the pack with a clear error when the seal step produced no serve manifest. You also stopped copying a local, possibly stale, serve manifest into the bundle.

## Words to know

- **`jac scale deploy`**: The jac-scale command that packages a Jac app and deploys it to Kubernetes.
- **Kubernetes / pod**: Kubernetes runs containers on a cluster. A pod is one running copy of a service. Here, each service pod unpacks the `.jab` and boots the app from it.
- **Crash-loop**: When a pod fails at startup, Kubernetes restarts it, it fails again, and this repeats. This is what happened to every pod with a broken bundle.
- **Host**: Your machine, or whatever machine runs `jac scale deploy`. This is different from the pod.
- **`.jab`**: The bundle file that gets shipped to pods. It is a gzipped tar archive.
- **tar / tar member**: A tar file is an archive of files. Each file inside it is a "member". `tar.add(...)` puts one file into the archive.
- **Seal**: The build step that turns the app into a "sealed" application before it is packed into the `.jab`. It runs the pod binary on a copy of the app.
- **Pod binary**: The `jac` executable that will run inside the pod. The seal runs this binary as a subprocess on the host. It may be an older release than the code on your machine.
- **Stage**: A temporary directory where the app's files are copied so the seal can work on them. In the diff it appears as `stage` and `staged`.
- **Bake / `bake_serve_payloads`**: The part of the seal that writes the serving metadata (the serve manifest) into the stage. It runs inside the pod binary.
- **Serve manifest (`.jac/serve_manifest.json`)**: A JSON file that tells a booting pod what the app serves, such as its exposed functions (the "surface"). Without it the pod stops with `Sealed application has no serving manifest`. Its path inside the stage is stored in the constant `SERVE_MANIFEST_REL`.
- **Entry point**: The main `.jac` file of the app. It is set by `entry-point` in `jac.toml` and defaults to `main.jac`. If it doesn't resolve to a real file, the bake has nothing to describe.
- **Precompile**: A later seal step (`jac precompile`) that compiles the app's modules ahead of time so the pod doesn't have to.
- **Bundle-required file**: A file that `_is_bundle_required` says must always go into the bundle and the seal stage, even if it would normally be left out.
- **Working tree**: Your project folder on disk, including leftover files from earlier local runs.
- **Stale file**: An old copy that no longer matches the current app.
- **Deterministic pack / content-address**: Packing the same app twice must give byte-identical `.jab` files, so the bundle's hash (digest) can identify it. `test_seed_determinism` checks this.
- **`JAC_TEST_STRICT`**: An environment variable. When it is set, tests that would normally be skipped (for example because the pod binary is missing) fail instead.

## The problem

Here is what happened before this PR when the app's entry did not resolve. Your reproduction used `entry-point = "missing"`:

1. `_precompile_app` ran the pod binary to bake the serve payloads.
2. `bake_serve_payloads` could not find the entry file. It printed a warning (`sealing without serve payloads`), wrote no manifest, and still exited with success.
3. `_precompile_app` only checked the exit code, so it carried on.
4. In `pack_jab`, the tar step added the manifest only `if serve_manifest.is_file()`. The missing file was silently skipped.
5. The deploy reported success and shipped the `.jab`.
6. Every service pod failed at boot with `Sealed application has no serving manifest` and crash-looped.

There was a second, related bug. `_is_bundle_required` returned `True` for `.jac/serve_manifest.json`, so a copy in your working tree was force-copied into the seal stage and into the bundle's source files. This caused two problems:

- An old local manifest could make any "does the file exist?" check pass, even when the bake wrote nothing.
- When the entry was valid, the `.jab` held **two** `.jac/serve_manifest.json` members: the stale local one and the fresh baked one. Which one the pod got depended on extraction order.

You reproduced both cases on commit `e8b3d8ad5`. The broken entry packed without a manifest and `jac run --serve` exited 1. With a stale local manifest present, the pack contained it twice.

This affected anyone deploying with jac-scale whose entry didn't resolve, or who had a leftover `.jac/serve_manifest.json` locally.

## The changes, one by one

### `jac/jaclang/scale/injector/bundle.jac`: the gate and the stale-copy fix

This is the main fix. It has four parts.

**1. New function `require_serve_manifest(stage, detail)`**

```jac
def require_serve_manifest(stage: Path, detail: str = "") -> Path {
    import from jaclang.server.sealed_serve { SERVE_MANIFEST_REL }

    serve_manifest = stage / SERVE_MANIFEST_REL;
    if not serve_manifest.is_file() {
        raise RuntimeError(
            f"The app stage has no {serve_manifest}, so the deploy cannot "
            f"produce a .jab a pod can boot from. {detail}".rstrip()
        );
    }
    return serve_manifest;
}
```

- It builds the manifest path inside the given stage directory.
- If the file is not there, it raises a `RuntimeError`. The message names the full path and says why this matters: no pod could boot the `.jab`.
- `detail` is extra text added to the end of the message. `.rstrip()` removes the trailing space when `detail` is empty.
- If the file exists, it returns its path, so a caller can use the result directly.

**2. `_precompile_app` calls it right after the bake**

```jac
        require_serve_manifest(stage, (prepared.stdout or "").strip()[-4000:]);
```

- `prepared` is the result of the bake subprocess that was just run. Its exit code was already checked a few lines above.
- You pass the last 4000 characters of the bake's stdout as `detail`. That output contains the `sealing without serve payloads` warning, so the error tells the user *why* the manifest is missing, not only that it is.
- This fixes point 1 of the problem: a "successful" bake that wrote nothing now stops the pack on the host, before precompile runs.

**3. `pack_jab`'s tar step no longer skips silently**

```jac
                tar.add(
                    str(require_serve_manifest(staged)),
                    arcname=SERVE_MANIFEST_REL,
                    filter=det_tar_member
                );
```

- Before, this was wrapped in `if serve_manifest.is_file() { ... }`.
- Now the tar step always asks `require_serve_manifest` for the path. That call raises if the file is missing.
- `arcname` is the name the file gets inside the archive. `filter=det_tar_member` makes the member deterministic (stable metadata), as before.
- This fixes point 2: a missing manifest is refused here too, not left out. In a real deploy the bake gate above fires first. This one is a backstop.

**4. `_is_bundle_required` no longer marks the serve manifest as required**

```jac
-    if len(parts) >= 2 and parts[0] == ".jac" and parts[1] == "admin" {
-        return True;
-    }
-    return len(parts) == 2 and parts[0] == ".jac" and parts[1] == "serve_manifest.json";
+    return len(parts) >= 2 and parts[0] == ".jac" and parts[1] == "admin";
```

- Before: anything under `.jac/admin/` was required, **and** `.jac/serve_manifest.json` was required.
- After: only `.jac/admin/` stays required. The two checks were folded into one `return`.
- The seal always bakes a fresh manifest, so a working-tree copy is never needed. Without this change, a stale local copy would reach the stage and fool the new gate. It would also be shipped as a duplicate tar member.
- This fixes point 3.
- The diff shows only the end of this function. That the local manifest is now left out comes from your description; the full selection logic is not visible here.

**Why the gate lives here and not in `bake_serve_payloads`**: the bake runs inside the pod binary, which may be an older release, so a fix there would not reach every deploy. Putting the gate in the scale bundler means it always runs on the host. It also leaves `jac build --as jab` behaving as it does today, because that command does not go through this bundler code.

### `jac/jaclang/dist/seal.jac`: portable serve manifest (from #9613)

These commits belong to PR #9613. Your branch carries them until #9613 merges.

- New helper `_without_key(record, dropped)` returns a copy of a dict without one key.
- New helper `_portable_manifest(manifest)`:
  - drops the top-level `'root'` key;
  - drops the `'module'` key from each entry under `'surface'`.
- `build_serve_manifest` now passes the entry manifest and every module manifest through `_portable_manifest`. Before, it copied the entry manifest with `dict(...)` and used module manifests as they were.

Why: according to the commit message ("bake a serve manifest free of seal stage paths") and the new test, those keys held paths of the seal stage. The stage is a temporary directory on the host, so those paths mean nothing inside the pod.

Why your PR needs it: your PR changes the test fixtures so they now bake a real serve manifest. You state that the determinism tests depend on #9613. The likely reason (my inference, not stated in the PR) is that the temporary stage path changes on each pack. A manifest containing it would make two packs of the same app differ byte for byte.

New assertions that the baked manifest has no stage paths. This is covered in Tests.

## How it runs now

1. The user runs `jac scale deploy`, which calls `pack_jab` with the project directory and the pod binary.
2. Project files are selected for the bundle. `_is_bundle_required` no longer forces `.jac/serve_manifest.json` in, so a working-tree copy is not staged or shipped. **(changed)**
3. `_precompile_app` copies the app into a stage directory and runs the pod binary to bake the serve payloads (`bake_serve_payloads`).
4. Inside the bake, `build_serve_manifest` writes a manifest without `root` or surface `module` paths. **(changed, from #9613)**
5. `_precompile_app` checks the bake's exit code. A non-zero code raises, as before.
6. `_precompile_app` calls `require_serve_manifest(stage, <bake stdout>)`. If the bake wrote no manifest, the pack stops here with a `RuntimeError` that names the path and includes the bake's warning. **(new)**
7. `_precompile_app` runs `jac precompile` on the stage.
8. Back in `pack_jab`, the tar step adds the precompiled artifacts. It then adds the manifest through `require_serve_manifest(staged)`, which raises if the manifest is missing instead of skipping it. **(changed)**
9. Vendored wheels and the rest are added, and the `.jab` is returned and shipped.
10. Pods unpack the `.jab` and boot from the single fresh serve manifest.

## Tests

**`test_app_precompile.jac`: the old test "an unrunnable pod binary fails the seal instead of shipping unsealed" is now "a seal that cannot yield a bootable .jab fails the pack instead of the pod"**

It is now a table of two cases. Each case does the same setup:

- create a small app;
- write a `jac.toml` with `fat_bundle = false` and an optional entry line;
- write a **stale** `.jac/serve_manifest.json` containing `{"stale": true}`;
- call `pack_jab`, catch any exception, and turn it into a `"Type: message"` string.

The checks:

- **"an unrunnable pod binary"**: the binary is `b"not-an-elf"`. The test only checks that *some* error was raised. This keeps the old test's coverage.
- **"a bake that writes no manifest over a stale local copy"**: `entry-point="missing"`. The binary is `b""`, so `binary or require_pod_binary().read_bytes()` uses the **real** pod binary. The test checks that the error text contains `RuntimeError`, the `SERVE_MANIFEST_REL` path, and `sealing without serve payloads`.

What this proves:

- The bake gate in `_precompile_app` fires, and the bake's warning reaches the error message.
- The `_is_bundle_required` change works. If the stale local manifest were still copied into the stage, `require_serve_manifest` would find it and no error would be raised, so the test would fail.

Notes:

- If the pod binary is missing, `require_pod_binary()` skips the test. Under `JAC_TEST_STRICT` it fails instead. Because the first row runs before `require_pod_binary()` is called, the first row has already run when that happens.
- The column was named `entry_line` because `entry` is a keyword in Jac (see the commit "rename the precompile table's entry column").
- The tar-step gate in `pack_jab` is not tested on its own. As you note, the bake gate is the one a real deploy hits.
- The test count stays at 17.

**`test_fat_bundle.jac`**: the helper `_app` now writes `main.jac` instead of `svc.jac`, so the app has a resolvable entry.

**`test_pvc_injector.jac`**: the app file is now `main.jac` instead of `app.jac`. The assertion `"app.jac" in names` became `"main.jac" in names`. It checks the same thing for the renamed file. The secret-stripping checks are unchanged.

**`test_seed_determinism.jac`**: the source file is now `main.jac` instead of `svc.jac`. The test still checks that two packs of the same content give identical bytes. Because a real manifest is now baked, it relies on #9613's portable manifest.

**`test_bundle_jacignore.jac`**: it now writes a `main.jac` before packing, so the seal can produce a manifest. The check that parked trees are left out of the `.jab` is unchanged.

**`test_application_preparation.jac` (from #9613)**: for the entry manifest and every module manifest, it asserts there is no `'root'` key and no surface entry with a `'module'` key. This proves the baked manifest does not contain seal stage paths.

## Explaining it in one minute

"`jac scale deploy` could ship a `.jab` with no serve manifest, and then every pod crash-looped at boot. Three things let that through. The bake exits successfully even when the entry file is missing. `pack_jab` skipped the manifest instead of refusing it. And `_is_bundle_required` copied any local `.jac/serve_manifest.json` into the stage, which could hide the missing file and could also ship two manifests. I added `require_serve_manifest`, which raises on the host with the stage path and the bake's own warning. It runs right after the bake and again in the tar step. I also stopped treating the local manifest as bundle-required, since the seal always bakes a fresh one. The check lives in the scale bundler and not in the bake, because the bake runs inside the pod binary, which might be an older release, and this way `jac build --as jab` doesn't change. I tested it by turning the existing precompile test into a table. One new row runs the real pod binary on an app with a missing entry and a stale local manifest, and checks the error. I also fixed four test fixtures that were packing apps with no entry file, without weakening any assertion. The branch also carries #9613's portable-manifest commits, which the determinism test needs."
