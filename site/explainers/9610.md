## 1. The short version

`jac scale deploy` builds a `.jab` (a tar.gz app bundle) on your machine and ships it to every service pod. To boot from the sealed bundle, a pod needs `.jac/serve_manifest.json`, the "serving metadata" file. **Before this PR, the host could pack and ship a `.jab` with no serve manifest and still report success. Every pod then crash-looped at boot with `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`.**

Three host-side gaps let this through:

- The bake step returns success without writing the file when the app entry doesn't resolve (for example, `entry-point = "missing"`).
- The tar step silently skipped a missing manifest.
- A stale working-tree copy of the manifest was force-copied into the bundle. That copy could hide the problem, or end up as a duplicate tar member.

**You added `require_serve_manifest(stage, detail)`, which raises a `RuntimeError` on the host when the stage has no serve manifest. You call it right after the bake (with the bake's stdout attached) and in the tar step. You also stopped treating `.jac/serve_manifest.json` as a bundle-required file, so only the freshly baked one can ever ship.** The gate sits in the scale bundler, not in `bake_serve_payloads`. That leaves `jac build --as jab` unchanged and doesn't depend on which release the pod binary comes from.

**Status:** Open. @MusabMahmoodh requested changes on 2026-09-30. His latest review (2026-10-13, "commented") lists only things that later commits address, but there is no approval yet. On head commit `1b42738`, `jac-check` and `test-compiler (toplevel)` fail and `test-compiler (passes-native)` is still running. All `test-scale` jobs pass.

## 3. The problem, step by step

### 3.1 The setup

- **Host:** `pack_jab` → stage the app (with `_is_bundle_required` forcing some files in) → `_precompile_app` runs the **bake** subprocess, then the **seal** subprocess → tar the stage into the `.jab`.
- **Pod:** extract the `.jab` → `jac run --serve` → `_prepare_sealed` reads `.jac/serve_manifest.json` unguarded.

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml has entry-point = "missing"; working tree has no .jac/serve_manifest.json
2. pack_jab copies the app into stage/
3. _precompile_app runs the bake subprocess with the pod binary
4. resolve_entry_file → None; prints "sealing without serve payloads"
5. bake_serve_payloads returns True → exit code 0              ← WRONG: "no entry" became "success"
6. _precompile_app checks only the exit code → continues
7. seal subprocess writes _precompiled/MANIFEST.json → gate passes
8. pack_jab: stage/.jac/serve_manifest.json is_file()? → False → skip   ← WRONG: silent skip
9. Host prints success and ships the .jab (no serve manifest inside)
10. Every pod: "Loading sealed application artifacts" → Errno 2 on serve_manifest.json → exit 1 → crash-loop
```

### 3.3 What went wrong: stale local manifest

```text
1. Working tree has an old .jac/serve_manifest.json (e.g. {"stale": true})
2. _is_bundle_required(".jac/serve_manifest.json") → True
3. Stale file is force-copied into stage/ AND kept as a source member   ← WRONG
4a. Entry missing: bake writes nothing, but the stale copy is in stage/,
    so any is_file() check passes → pod gets stale metadata
4b. Entry valid: bake writes a fresh manifest into stage/
    → .jab has TWO members named .jac/serve_manifest.json (stale + fresh)
    → extraction order decides which one the pod sees
```

### 3.4 Why it mattered

- Per #9138, on jac 0.37.12 the pod crash-loops. On 0.37.11 (before #9088) the pod silently recompiled the whole server side at boot. #9136 measured that at 7 minutes and 4.5Gi.
- The failure surfaced in every pod as a generic "Error loading". It should have surfaced once, on the host, where the deploy can still stop cheaply.
- The issue frames this as the same class as #7936 (fail-fast client build) and the existing `check_fleet_entries` gate.
- The issue's scope note (c) listed the stale-manifest problem as an "unverified" follow-up. Your description says you reproduced it on `e8b3d8ad5` (shipped twice) and folded it in.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, not in the pod.** If the seal stage has no freshly baked `.jac/serve_manifest.json` at the moment it is checked, raise an error that names the path, instead of shipping a bundle no pod can boot.

This fits because the host already gates `_precompiled/MANIFEST.json` the same way. The host also has every fact needed to decide. Putting the check in the scale bundler, rather than in `bake_serve_payloads`, avoids depending on the pod binary's release and leaves `jac build --as jab` alone.

**(a) `_is_bundle_required` no longer forces the serve manifest in**

- **What:** Only paths under `.jac/admin/` are force-included now. A working-tree `.jac/serve_manifest.json` is treated like any other `.jac/` file, which (per your description) means it is no longer staged or shipped.
- **Why:** Fixes case 3.3. A stale local copy can't satisfy the gate anymore, and there can't be two members with the same name.

```diff

+    serve_manifest = stage / SERVE_MANIFEST_REL;
+    if not serve_manifest.is_file() {

+            f"produce a .jab a pod can boot from. {detail}".rstrip()

```

- **What:** Checks the file and raises with the full path plus optional `detail`. It returns the path so callers can use it inline.

- **Things to notice:**

### 6.2 Booting in the pod

There is no change in this PR. A `.jab` built after the PR always contains exactly one, freshly baked `.jac/serve_manifest.json`. The pod's unguarded read is left as is; the issue's scope note lists a better boot-side message as separate work.

| Scenario | Before | After |
|---|---|---|
| Entry resolves, no local manifest | Ships, pod boots | Same |
| Entry missing, no local manifest | Host "succeeds", pods crash-loop | Host fails in `_precompile_app` with path + `sealing without serve payloads` |
| Entry missing, stale local manifest | Stale manifest shipped, pods get wrong metadata | Host fails (stale copy not staged) |
| Entry resolves, stale local manifest | Two `.jac/serve_manifest.json` members; extraction order wins | Only the fresh one ships |
| Manifest removed between bake and tar | Silently skipped | Tar step raises |
| Pod binary unrunnable | Fails (bake error) | Same |
| `jac build --as jab` | Warning, `.jab` without payloads | Same, per your description (not visible in the diff) |

**User-visible behaviour change:** projects with no resolvable entry now fail to deploy. This includes projects that relied on the default `main.jac` without having one. That is intended, and it is exactly what broke several test fixtures (section 7).

## 11. Questions your senior might ask

**Q: Why not fix `bake_serve_payloads` to return failure when the entry is missing?**
The bake runs inside the pod binary, which may be an older release, so a fix there wouldn't protect deploys that use older binaries. It would also change `jac build --as jab`, which deliberately keeps warning instead of failing. The host-side scale bundler is where the pod's fate is decided.

**Q: Why gate in two places?**
The `_precompile_app` gate catches the real-world case early and attaches the bake's stdout, which explains why. The tar-step gate catches any later loss of the file between bake and pack (the issue's reproduction path 1), so the `.jab` can never be written without the manifest.

**Q: Is it safe to stop force-shipping `.jac/serve_manifest.json`?**
Yes. The seal always bakes a fresh one into the stage. A working-tree copy could only be stale, could mask a failed bake, or could create a duplicate tar member. @MusabMahmoodh agreed.

**Q: Can a cached bad `.jab` still be shipped?**
Per your description, no: the seal cache key includes the pod binary's hash, so a release with this fix won't reuse a seal made by an older one. The diff doesn't show the cache code, so be ready to point to it.

**Q: How does the test prove the `_is_bundle_required` change, not just the gate?**
Row 2 writes a stale `.jac/serve_manifest.json`. If the stale file were still force-staged, `require_serve_manifest` would find it and no error would be raised, so the assertion would fail.

**Q: Why weren't there mocks for the tar-step gate?**
The scale tests are mock-free by convention. Patching `subprocess.run` affects the whole test process. The reviewer preferred covering the gate a real deploy hits.

**Q: Why did so many unrelated fixtures change?**
