## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine and ships it to every Kubernetes pod. Before packing, a "seal" step pre-compiles the app and "bakes" a small JSON file, `.jac/serve_manifest.json`. A pod needs that file to start serving.

**The host could pack and ship a `.jab` with no `.jac/serve_manifest.json`, report success, and then every pod failed at boot with `Sealed application has no serving manifest`.** This happened in three ways:

- The bake returned success without writing anything when the app entry did not resolve (for example `entry-point = "missing"`).
- The tar step skipped the file quietly when it was absent.
- A stale working-tree copy of the file was force-copied into the bundle. It could hide the problem, or end up as a second tar member next to the fresh one.

**You added `require_serve_manifest(stage, detail)`, which raises on the host when the stage has no serve manifest. It is called right after the bake and again in the tar step. You also stopped force-shipping the working-tree `.jac/serve_manifest.json`.** The deploy now fails on your machine. The error names the missing path and includes the bake's `sealing without serve payloads` warning.

This branch also carries #9613's commits (the changes to `seal.jac` and `test_application_preparation.jac`). Several test fixtures now bake a real manifest, and the determinism test needs #9613's path-free manifest to stay byte-stable.

**Status:** Open. No approval yet. @MusabMahmoodh requested changes on 2026-09-30, and his later "good to go once renamed" review (2026-10-08) was dismissed. ## 3. The problem, step by step

### 3.1 The setup

- **Host side (`bundle.jac`):**
  - `pack_jab` copies the app into a stage. It keeps files picked by the usual rules plus anything `_is_bundle_required` says.
  - It then calls `_precompile_app`, which runs the pod binary twice: bake, then `precompile --seal`.
  - Finally it tars the stage into the `.jab`.
- **Bake (`seal.jac`):** `bake_serve_payloads` → `resolve_entry_file` → `build_serve_manifest` → writes `.jac/serve_manifest.json`.
- **Existing gate:** `_precompile_app` already raises "App seal did not complete" when `_precompiled/MANIFEST.json` is missing (per the issue, `bundle.jac:762-776`). The serve manifest had no such gate.
- **Pod side:** `_prepare_sealed` does `json.loads((image_root / SERVE_MANIFEST_REL).read_text())` with no existence check.

### 3.2 What went wrong

#### Case A: the entry does not resolve

```text
1. jac.toml has entry-point="missing"; no .jac/serve_manifest.json locally
2. pack_jab stages the app                       stage: no serve manifest
3. bake subprocess: resolve_entry_file -> None
   stdout: "...sealing without serve payloads"   bake returns True, exit 0
4. _precompile_app checks only the exit code      -> OK            ← WRONG (gate 1 missing)
5. precompile --seal writes _precompiled/MANIFEST.json  -> existing gate passes
6. tar step: if serve_manifest.is_file() -> False, skip silently    ← WRONG (gate 2 missing)
7. pack_jab returns a .jab; deploy reports success
8. every pod: _prepare_sealed reads .jac/serve_manifest.json
   -> "Error loading web/main.jac: [Errno 2] No such file ..." exit 1 -> crash-loop
```

#### Case B: a stale local manifest hides it

```text
1. working tree has an old .jac/serve_manifest.json ({"stale": true}); entry missing
2. _is_bundle_required(".jac/serve_manifest.json") -> True             ← WRONG
   stale copy is copied into the stage and the source members
3. bake writes nothing (as in case A)
4. tar step: is_file() -> True (stale file)  -> ships the stale manifest
5. pods boot with metadata that doesn't match the code
```

With a **valid** entry, the bake writes a fresh manifest. The `.jab` then has two members with arcname `.jac/serve_manifest.json`: the stale one and the fresh one. Which one the pod gets depends on extraction order.

#### Case C: the manifest disappears between bake and pack (issue repro 1)

```text
1. bake writes .jac/serve_manifest.json
2. something between bake and the tar step removes it (failure/cleanup)
3. _precompiled/MANIFEST.json still present -> seal gate passes
4. tar step skips the missing file silently                        ← WRONG
5. .jab ships without serving metadata
```

### 3.3 Why it mattered

- On jac 0.37.12, every pod crash-loops. The cause shows up only as a generic "Error loading" at boot, far from the host where it could have been caught.
- On 0.37.11 the pod silently recompiled the whole server side instead: the 7 minute / 4.5Gi boot measured in #9136.
- Per the issue, the gaps came from #9088 (the tar guard and the bake step) and #7258 (`return True` on a `None` entry). In #7258 the only caller was `jac build --as jab`, where a terminal warning was enough.

## 4. The idea of the fix (one sentence)

> **Check for the serve manifest on the host and refuse to pack without it.** After the bake, and again when tarring, `require_serve_manifest` raises with the stage path and the bake's output, and the working-tree copy is no longer allowed to stand in for a fresh one.

This puts the decision where the issue's root cause says it belongs: on the host, where failing is cheap. It also follows the shape of the existing `_precompiled/MANIFEST.json` gate. It leaves `bake_serve_payloads` alone, so an older pod binary and `jac build --as jab` behave as before.

## 11. Questions your senior might ask

**Q: Why not make `bake_serve_payloads` return `False` when there's no entry?**
The bake runs inside the pod binary, which may be an older release, so a change there wouldn't reach every deploy. `jac build --as jab` also relies on its current warn-and-continue behaviour. The host bundler is where the pod's fate is decided.

**Q: Why two gates? Isn't the one after the bake enough?**
The bake gate catches the real-world case (entry missing) and attaches the bake's stdout. The tar-step gate covers the manifest disappearing between bake and tar (issue repro 1). The `_precompiled` gate already has the same two-step shape.

**Q: Why remove `.jac/serve_manifest.json` from `_is_bundle_required`?**
A stale working-tree copy would land in the stage and satisfy `is_file()`, so the gate would never fire. With a valid entry, the `.jab` also got two members with the same arcname. The seal always bakes a fresh one, so the local copy is never needed.

**Q: Does any user lose something?**
Projects whose entry doesn't resolve can no longer deploy. Those bundles were unbootable anyway. A locally committed `.jac/serve_manifest.json` is now ignored by `jac scale deploy`.

**Q: Why did you change four unrelated test fixtures?**
They packed apps with no `main.jac`, so the new gate fails them. They were testing bundles no pod could boot. Renaming to `main.jac` keeps every assertion as strict as before.

**Q: Why does this PR depend on #9613?**
The fixtures now bake a real manifest into the `.jab`. Without #9613 that manifest contains absolute temp-stage paths, so `test_seed_determinism` ("identical content packs to identical bytes") would fail.

**Q: Is the tar-step gate tested?**
No. Only the bake gate is tested, through a real pod binary. The reviewer asked you to drop the mocked tar-step case rather than keep a mock.

**Q: What happens on a dev machine without the pod binary?**
Row 1 still runs and asserts. Then row 2 calls `require_pod_binary()`, which marks the test skipped. On CI, `JAC_TEST_STRICT=1` turns that skip into a failure.

**Q: Why is microservices CI red?**
The logs aren't in the PR data. It's no longer the `entry` keyword error, since jac-check passes. It needs investigating before merge.

**Q: Should the pod side also guard the read in `_prepare_sealed`?**
Not in this PR. The issue scopes that out and lists boot-side diagnostics and a manifest format stamp as separate follow-ups.
