## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine and ships it to Kubernetes pods. Each pod boots from that bundle. To boot quickly, the pod needs one file inside it: `.jac/serve_manifest.json`, the "serving metadata" that a step called the bake writes during the seal.

**Before this PR, the host could pack and ship a `.jab` with no serve manifest and still report success. Every pod then crash-looped with `Sealed application has no serving manifest` (or, per the issue, `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`).** There were three leaks:

1. The bake returns success even when the app entry (for example `entry-point = "missing"`) does not resolve to a file.
2. The tar step skipped the file when it was missing instead of refusing.
3. A stale working-tree copy of the manifest was force-copied into the bundle.

Code review found a fourth leak: the seal cache could hand back an old, broken bundle and skip all the checks.

**You added one host-side gate, `require_serve_manifest`, and call it right after the bake and again at the tar step. You stopped shipping the working-tree manifest. The seal cache is now reused only when the cached bundle is a readable archive that carries the manifest.** The deploy now fails on your machine with a message that names the missing path and includes the bake's `sealing without serve payloads` warning.

**Status:** Open. @MusabMahmoodh's latest review (2026-10-13, "commented") says the core change is right. His last blocker (the reuse test failing) was addressed in f4131ef. There is no approval yet. On head commit 403144c, `build-kit` is still running, and the test-scale and jac-check jobs do not appear in the reported checks.

## 3. The problem, step by step

### 3.1 The setup

- **Host side (`bundle.impl.jac`):** `pack_jab` → (cache check) → `_precompile_app` runs the bake subprocess, then the seal subprocess → `pack_jab` tars the stage into a `.jab`.
- **Inside the bake (`seal.jac`, run by the pod binary):** `resolve_entry_file` returns `None` if the entry is missing, and the bake then returns `True` without writing the manifest.
- **Pod side (`application.jac:216`, per the issue):** it reads `.jac/serve_manifest.json` with no existence check, so it fails with a generic "Error loading".

### 3.2 What went wrong: entry does not resolve

```text
1. jac.toml says entry-point = "missing"; there is no missing.jac
2. pack_jab → no cache hit → _precompile_app(stage)
3. bake subprocess: resolve_entry_file → None, prints "sealing without serve payloads"
4. bake returns True → exit code 0                      ← WRONG: "no entry" treated as success
5. _precompile_app only checks exit code → continues
6. precompile --seal writes _precompiled/MANIFEST.json  (this file IS gated)
7. tar step: stage/.jac/serve_manifest.json missing → `if is_file()` skips it  ← WRONG
8. pack_jab returns a .jab; deploy reports success
9. every pod: reads .jac/serve_manifest.json → ENOENT → exit 1 → crash-loop
```

### 3.3 What went wrong: stale manifest in the working tree

```text
1. Working tree has an old .jac/serve_manifest.json (from an earlier local run)
2. _is_bundle_required(".jac/serve_manifest.json") → True  ← WRONG
3. The stale copy is copied into the stage and into the source members
4a. Entry missing: bake writes nothing, but the stale file now exists in the stage
    → any existence check passes → pod gets stale metadata
4b. Entry valid: bake writes a fresh manifest, and the .jab ends up with TWO members
    named .jac/serve_manifest.json (stale + fresh); extraction order picks one
```

You reproduced both cases on `e8b3d8ad5`.

### 3.4 What went wrong: old cached bundle (found in review)

```text
1. Earlier deploy (before this fix) cached a .jab with no serve manifest under key K
2. Host upgrades Jac, pod binary version stays pinned, sources unchanged → key still K
3. pack_jab: _cached_seal(K) returns the old bytes → returned immediately  ← WRONG
4. Neither new gate runs → broken bundle ships again
```

@greptile-apps flagged this, and you confirmed it in your reply.

### 3.5 Why it mattered

- The deploy said "success", but the failure showed up only on the pods, N times, after shipping.
- On 0.37.12 the pod crash-loops. On 0.37.11, the missing manifest meant a full recompile at boot: 7 minutes and 4.5Gi, as measured in #9136.
- The issue names the root cause as a "silent fallback at a decision point" on the host, the same kind of problem as #7936 and the existing `check_fleet_entries` gate.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, never trust anything but a freshly baked manifest.** After the bake, at the tar step and at the cache, the host checks that the serve manifest really exists, and fails the deploy with a clear message if it doesn't.

The host is the last cheap place to fail, and it has all the facts. The gate goes in the scale bundler, not in `bake_serve_payloads`, because the bake runs inside the pod binary. That binary may be an older release, and `jac build --as jab` should keep its current behaviour.

```text

├─ key = input_key(base, seal_sources)
├─ cached = _cached_seal(base, key)
```

```text

└─ bake_serve_payloads (unchanged: still returns True with a warning if the entry is missing)
```

This path does not go through the scale bundler, so its behaviour is unchanged. That is deliberate.

| Scenario | Before | After |
|---|---|---|
| Entry missing, no local manifest | Pack succeeds; pods crash-loop | Host raises `RuntimeError` naming the path, plus `sealing without serve payloads` |
| Entry missing, stale local manifest | Stale manifest shipped; pods get wrong metadata | Host raises (stale copy no longer staged) |
| Entry valid, stale local manifest | `.jab` has two `.jac/serve_manifest.json` members | One fresh member |
| Cached `.jab` with no manifest | Reused; broken bundle shipped again | Resealed; the gate decides |

**What users will notice:**

1. A deploy of a project whose entry does not resolve now fails on the host. You found test fixtures that relied on this being allowed, so some real projects may have too.
2. A local `.jac/serve_manifest.json` is no longer shipped.
3. The first deploy after upgrading may reseal instead of reusing the cache.

## 11. Questions your senior might ask

**Q: Why not just make `bake_serve_payloads` return `False` when the entry is missing?**
The bake runs inside the pod binary, which may be an older release, so a fix there wouldn't protect deploys that pin older pods. It would also change `jac build --as jab`, which you deliberately left alone.

**Q: Why two gates? Isn't the post-bake check enough?**
The post-bake check gives the best error, because it carries the bake's stdout. The tar-step check is a backstop for the file disappearing between bake and tar (issue reproduction path 1). It also replaces a silent skip that should never have existed.

**Q: The tar-step gate has no test. Is that OK?**
The reviewer asked you to drop the mock-based case. Scale tests stay mock-free, and the bake gate is the one a real deploy hits. Without a mock, it is hard to reach the tar step with no manifest, because the bake gate fires first.

**Q: Could removing `.jac/serve_manifest.json` from `_is_bundle_required` break anyone?**
Only someone relying on a hand-placed manifest. The seal always bakes a fresh one, and shipping the local copy caused duplicate members. The reviewer agreed it should go.

**Q: Why not bump the cache key instead of inspecting the cached bundle?**
The key covers the pod binary and inputs, not the host bundler. A content check catches any broken entry, including old or corrupt ones, without inventing a version stamp. The cost is one archive scan per cache hit.

**Q: What if the cached file is truncated or not gzip?**
`_bundle_ships` catches `OSError`, `EOFError` and `TarError` and returns `False`, so the pack reseals. The reuse test covers `b"not a bundle"`.

**Q: Why did so many test fixtures change?**
They packed apps whose default entry `main.jac` didn't exist, so no pod could have booted them. The gate now refuses those apps, so the fixtures gained a real entry. No assertion was weakened.

**Q: Does this change user behaviour?**
Yes. A deploy whose entry doesn't resolve now fails on the host with a clear error instead of reporting success. A local `.jac/serve_manifest.json` is no longer shipped, and old cache entries without a manifest are resealed.
