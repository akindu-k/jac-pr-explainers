## 1. The short version

`jac scale deploy` packs your app into a `.jab` bundle on your machine and ships it to every pod. Each pod needs `.jac/serve_manifest.json` inside the bundle to boot. That file is the serving metadata the seal step bakes.

**Before this PR, the host could pack and ship a `.jab` with no serve manifest, report success, and leave every pod crash-looping with `Error loading web/main.jac: [Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`.** The easiest way to trigger it was an `entry-point` that does not resolve to a file. The bake then prints `sealing without serve payloads`, still returns success, and the tar step quietly skips the missing file. A second problem made it worse: a stale working-tree copy of `.jac/serve_manifest.json` was force-copied into the bundle, so the archive could hold two members with that name.

**You added one host-side gate, `require_serve_manifest`, and call it right after the bake and again in the tar step. You also stopped shipping the working-tree manifest, and the seal cache is now reused only when the cached bundle actually contains the manifest.** A broken deploy now fails on your machine. The error names the missing path and includes the bake's own `sealing without serve payloads` warning.

**Status:** Open, with no approval yet. @MusabMahmoodh requested changes on 2026-09-30, and his later reviews were "dismissed" and then "commented". You fixed the points he raised, but he has not reviewed the latest commits (the archwire wiring and the cache check). On the head commit, `test-compiler (equivalence)` and the `Everything Passed` aggregate are failing. A second CI run was cancelled.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. `.jac` files are source. Implementations of declared functions live in `impl/*.impl.jac` files, as `impl name(...) { ... }`. |
| jac-scale / `jac scale deploy` | The plugin that deploys a Jac app to Kubernetes. It runs on **the host** (your machine or CI), builds a bundle and ships it to **pods**. |
| Pod | One running container in Kubernetes. Many pods boot from the same bundle, so one bad bundle breaks all of them. |
| Pod binary (`seal_binary`) | The `jac` executable that runs inside the pod. The host also runs it to seal the app. It may be an older or newer release than the host's jac. |
| `.jab` | A gzip tar archive with your app, its precompiled code and its metadata. It is what the pod extracts and boots. |
| Stage (`stage`, `staged`) | A temporary directory on the host where the app is copied and sealed before it is tarred into the `.jab`. |
| Seal | Precompiling the app inside the stage (`jac precompile --seal`), so the pod does not compile at boot. It produces `_precompiled/MANIFEST.json`. |
| Bake (`bake_serve_payloads`) | The step before the seal that writes the serving metadata. It runs as a subprocess using the pod binary. If the entry can't be resolved, it prints `sealing without serve payloads` and still returns success. |
| Serve manifest (`.jac/serve_manifest.json`, `SERVE_MANIFEST_REL`) | The serving metadata file the bake writes. The pod reads it unguarded at boot (`application.jac:216` per the issue). `SERVE_MANIFEST_REL` is the constant holding its relative path. |
| `resolve_entry_file` | Finds the app's entry file from `jac.toml` (`entry-point = "svc"` → `svc.jac`, default `main.jac`). It returns `None` when the file is not there. |
| `_precompile_app` | Host function that runs the bake and then the seal in subprocesses. Before this PR it only checked exit codes. **This is where the bug is** (first of three places). |
| `pack_jab` | Host function that builds the `.jab`: it picks files, checks the seal cache, calls `_precompile_app` and tars the stage. **This is where the bug is** (the `if serve_manifest.is_file()` skip). |
| `_is_bundle_required` | Decides which `.jac/...` files from your working tree are always copied into the bundle. It force-copied `.jac/serve_manifest.json`. **This is where the bug is** (stale copy). |
| `require_serve_manifest(stage, detail)` | New function. It raises `RuntimeError` naming the missing path when the stage has no serve manifest, and otherwise returns its path. **This is what the PR adds.** |
| Seal cache (`_cached_seal`, `_remember_seal`, `input_key`) | Stores sealed `.jab` bytes under `.jac/seal-cache/`, keyed by the pod binary plus the project inputs. If the key matches, `pack_jab` reuses the bytes and skips sealing. |
| `_bundle_ships(raw, member)` | New function. It opens cached bytes as a tar.gz and returns `True` only if `member` is inside. It returns `False` on unreadable bytes. |
| archwire (`archwire.jac`) | A wiring file that declares which modules get or import which symbols, for example `SERVE_MANIFEST_REL`. The new function uses `SERVE_MANIFEST_REL` without a local import, so it must be wired here. The diff does not show how archwire works internally. |
| `require_pod_binary()` | Test helper. It returns the built pod binary, or skips the test when it is missing. With `JAC_TEST_STRICT=1` (set on CI) a missing binary fails the test instead. |
| Fail closed / fail fast | Refuse early, on the host where failing is cheap, rather than let a broken artifact reach N pods. |

## 3. The problem, step by step

### 3.1 The setup

```text
host: jac scale deploy
  └─ pack_jab(base, pod_binary)
       ├─ copy sources into stage   (_is_bundle_required force-adds some .jac/ files)
       ├─ seal cache hit?  → return cached bytes
       ├─ _precompile_app
       │    ├─ subprocess: bake_serve_payloads   → writes .jac/serve_manifest.json
       │    └─ subprocess: jac precompile --seal → writes _precompiled/MANIFEST.json (gated)
       └─ tar stage → .jab   (serve manifest added only "if is_file()")
pod: tar xzf app.jab && jac run --serve → reads .jac/serve_manifest.json
```

### 3.2 What went wrong

#### 3.2.1 Entry does not resolve

```text
1. jac.toml says entry-point = "missing"; there is no missing.jac in the stage
2. bake subprocess: resolve_entry_file → None
3. bake prints "sealing without serve payloads", returns True → exit 0
4. _precompile_app checks the exit code only → OK                  ← WRONG: no file check
5. seal runs, writes _precompiled/MANIFEST.json → seal gate passes
6. tar step: stage/.jac/serve_manifest.json is_file()? no → skipped ← WRONG: silent skip
7. pack_jab returns a .jab; the deploy reports success
8. every pod: "Loading sealed application artifacts" →
   Error loading ...: No such file ... serve_manifest.json → exit 1 → crash-loop
```

#### 3.2.2 Stale working-tree manifest

```text
1. your working tree has an old .jac/serve_manifest.json (from an earlier local run)
2. _is_bundle_required(".jac/serve_manifest.json") → True → copied into the stage and source members
3a. bad entry: the stale copy now sits in the stage → any "does it exist?" check passes ← WRONG
3b. good entry: bake writes a fresh manifest; the tar has the source member (stale)
    AND the staged one (fresh) under the same arcname                                 ← WRONG
4. the pod's extraction order decides which one wins
```

#### 3.2.3 Cached bundle bypasses the new gate (found in review by greptile)

```text
1. a .jab without a serve manifest was cached before this PR (key = pod binary + inputs)
2. the host upgrades jac; the pod version stays pinned; the sources are unchanged → same key
3. pack_jab: cache hit → returns the old bytes before either new gate runs  ← WRONG
4. the broken bundle ships again
```

### 3.3 Why it mattered

- Issue #9138: on 0.37.12 every pod crash-loops. On 0.37.11 the same gap made pods silently recompile at boot, which is the 7-minute, 4.5Gi boot in #9136.
- The host already has every fact it needs to refuse, and nearby code already fails closed: the `_precompiled/MANIFEST.json` gate and `check_fleet_entries`. Only this file had no gate.
- It came from #9088 (tar guard plus bake on the scale path) combined with #7258 (bake returning `True` on no entry). The second was fine when `jac build --as jab` was its only caller.

## 4. The idea of the fix (one sentence)

> **Refuse on the host, not on the pod.** If the seal stage has no serve manifest after the bake, at tar time, or in a cached bundle, stop the pack (or reseal) instead of shipping.

The bake runs inside the pod binary, which may be an older release, so you can't rely on fixing it there. The scale bundler on the host is the one place that always runs your current code and decides what every pod receives. This also leaves `jac build --as jab` unchanged.

```text

├─ subprocess: bake (pod binary)
│   └─ non-zero exit → RuntimeError (unchanged)
├─ require_serve_manifest(stage, bake stdout tail)                                ← NEW
```

| Scenario | Before | After |
|---|---|---|
| Entry does not resolve | Pack succeeds, pods crash-loop | Pack fails on host after the bake, with the warning in the message |
| Manifest vanishes between bake and tar | Pack succeeds without it | Pack fails at tar step |
| Stale local `.jac/serve_manifest.json`, valid entry | Two members with the same name; the pod may get the stale one | Only the freshly baked one ships |
| Stale local manifest, bad entry | Stale file could mask the problem | Pack fails at bake gate |

## 11. Questions your senior might ask

**Q: Why not just make `bake_serve_payloads` fail when the entry is missing?**
The bake runs inside the pod binary, which can be an older release than the host's jac. A fix there would not protect deploys that use older pod binaries. Changing it would also alter `jac build --as jab`, which still wants the warning-only behaviour. The host bundler always runs the current code.

**Q: Why two gates, after the bake and at tar time?**
The bake gate catches the real-world case early and attaches the bake's stdout, so the error explains itself. The tar gate replaces a silent skip and also catches the manifest vanishing between bake and tar, which is the issue's first repro route.

**Q: Is it safe to stop shipping the working-tree `.jac/serve_manifest.json`?**
Yes. Every pack bakes a fresh one into the stage, and the gate refuses a pack without one. Shipping the local copy only added a stale duplicate member.

**Q: Why not add the host bundler version to the cache key instead of opening the archive?**
That would invalidate every cache on each host upgrade. Checking the cached bytes directly targets exactly the broken entries, and also handles corrupt files. The cost is a gzip listing of the cached archive per deploy. The PR doesn't measure that cost.

**Q: What happens with a corrupt cache file?**
`_bundle_ships` catches `OSError`, `EOFError` and `TarError`, returns `False`, and the pack reseals. The `b"not a bundle"` test row covers it.

**Q: Why isn't the tar-step gate tested?**
The only way to reach it without a real bake failing first is to mock the bake. Scale tests stay mock-free, and the reviewer asked to drop that case. A real deploy hits the bake gate first.

**Q: What does the second test row prove that the first doesn't?**
It runs the real pod binary with a missing entry over a stale local manifest. The error must name `.jac/serve_manifest.json` and include `sealing without serve payloads`. This shows that the bake gate fires and that the stale copy no longer satisfies it.

**Q: Why did so many fixtures change?**
They packed apps whose entry (default `main.jac`) didn't exist. No pod could boot those bundles, and the new gate correctly refuses them. The fixtures now ship a real entry, and no assertion was weakened.

**Q: Will existing users see new failures?**
Only users whose `entry-point` doesn't resolve. Their deploys were already producing pods that crash-loop on 0.37.12, so they now get a host error instead.

**Q: Is the red equivalence check yours?**
The PR doesn't touch compiler code, so it is likely unrelated, but that hasn't been shown yet. Check the log or compare with main before merging.
