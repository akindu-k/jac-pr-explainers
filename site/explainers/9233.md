## 1. The short version

When a Jac app starts in a pod, `prepare_application` picks one of two paths. It either loads the app's **sealed** code, which was compiled ahead of time and shipped in the bundle, or it compiles the app from source. It decides with one call, `sealed_root_for(entry)`, and before this PR it only printed a line when it took the sealed path.

**Before this PR, a pod could have a whole sealed image on disk, skip it, and compile everything from source without saying why. A sealed bundle that lacked its serve manifest crashed with a bare `[Errno 2] No such file or directory: '.../.jac/serve_manifest.json'`.** That silence is what made the P1 investigation in #9136 so hard.

**You added a log line, `Sealed image at /app does not list web.jac; preparing from source`, for the "image present but not used" case. You also added a named `RuntimeError`, `Sealed application has no serving manifest: <path>; rebuild the bundle so the seal step writes it`, for the missing-manifest case.** The rule for when a pod uses sealed code is unchanged. To support the new line, you added a lookup `unlisted_image_root` in `server/sealed_serve.jac`. You also refactored both lookups onto a single ancestor walk, `_image_roots`.

**Status:** Merged on 2026-09-22. Approved by @MusabMahmoodh after his three comments were addressed, and by @MalithaPrabhashana. Every CI check on head commit `4400b69` passed or was skipped.

| `jac.toml` | Project config file. Its folder marks a project root. |
| Nested project | A project, with its own `jac.toml`, that sits inside another project's sealed image. Example: jacBuilder stages user projects under `/app/.jachome/.jac-ide/projects`. |
| `prepare_application` | In `compiler/driver/application.jac`. It chooses sealed or source at boot. **This is where the bug is** (the silent fallback). |
| `_prepare_sealed` | Loads the sealed artifacts. It raises named `RuntimeError`s for missing pieces, except for the serve manifest. **This is where the bug is** (the bare crash). |
| `sealed_root_for(path)` | Returns the first image root above `path` that lists it, or `None`. `None` means two different things: "no image" and "image doesn't list me". |
| `unlisted_image_root(path)` | New. Returns the nearest image root when that image is in the file's own project and does *not* list the file. Otherwise returns `None`. **This is what the PR adds.** |
| `_image_roots(abs_path)` | New private generator. It walks up from the file and yields `(image_root, nested)` for each image it finds. |
| Generator / `yield` | A function that hands back values one at a time. `next(gen, None)` takes the first value, or `None` if there is none. |

## 3. The problem, step by step

### 3.1 The setup

- **Build host:** jac-scale seals the app and packs `_precompiled/` into the bundle. It adds `.jac/serve_manifest.json` only if the seal step wrote it (per #9136).
- **Pod:** extracts the bundle (e.g. to `/app`) and runs `jac start <entry>`, which reaches `prepare_application`.
- **Decision:** `sealed_root_for(entry)` walks up the folders looking for `_precompiled/MANIFEST.json` and checks that the entry's key is listed.
  - Found and listed: it prints `Loading sealed application artifacts` and calls `_prepare_sealed`.
  - Otherwise: it compiles from source.

### 3.2 What went wrong: case A, image present but not used

```text
1. Pod extracts bundle to /app. /app/_precompiled/MANIFEST.json exists, lists "svc.jac" only.
2. Pod runs entry /app/web.jac.
3. prepare_application → sealed_root_for("/app/web.jac")
4.   finds image at /app, key "web.jac" not in manifest keys → keeps walking → reaches "/" → None
5. prepare_application sees None. Same value as "no image anywhere".     ← WRONG: no line printed
6. Prints only "Compiling server modules and placement metadata..."
7. Full source compile (≈7 min, 4.5Gi per pod on jaclang.org, per #9136); operator has no clue why.
```

### 3.3 What went wrong: case B, sealed bundle without serve manifest

```text
1. Bundle sealed by a pre-0.37.12 scale seal (or the #9138 case): .jac/serve_manifest.json never written.
2. sealed_root_for(entry) → "/app" (entry is listed)
3. Prints "Loading sealed application artifacts" → _prepare_sealed(...)
4. Artifact manifest check passes.
5. json.loads((Path(image_root) / SERVE_MANIFEST_REL).read_text())       ← WRONG: unchecked read
6. FileNotFoundError: [Errno 2] No such file or directory: '/app/.jac/serve_manifest.json'
7. CLI prints "Error loading svc.jac: [Errno 2] ..." — the path is the only clue.
```

### 3.4 Why it mattered

- #9136 was a P1. Live jaclang.org pods shipped 184 `.jir` files plus a manifest that listed the entry, yet they recompiled at every boot. They took about 7 minutes and 4.5Gi, and OOM-looped on a 4Gi limit. The logs never said that a seal was found and skipped.
- #9139 calls the root cause a "missing observable at a decision point". The fallback policy from #9088 is correct, but it says nothing. The issue author notes that the other `_prepare_sealed` misses already name what is missing (e.g. `Sealed application is missing executable artifact: <path>`). The serve manifest was the odd one out.
- The issue also notes that the in-process host (`scale/server/inprocess.jac`) and the sealer (`dist/seal.jac`) call the same function. So they inherit both the silence and the fix. This comes from the issue; those files are not in the diff.

## 4. The idea of the fix (one sentence)

> **Make the sealed-vs-source gate say which way it went and why.** When an image in the app's own project is present but unused, log it; when the serve manifest is missing, raise a named error.

This is the right idea because the issue asks only for diagnostics, not a policy change. Both additions run after the existing decision, so they cannot change which pods boot sealed.

## 5. Every code change, explained

### 5.1 `jac/jaclang/server/sealed_serve.jac`: one ancestor walk, two lookups

```diff

-    abs_path = os.path.normpath(os.path.abspath(path));

+        }
+        if os.path.isfile(os.path.join(d, "jac.toml")) {

-            return None;
+            break;
         }

     }
 }

+def sealed_root_for(path: str) -> (str | None) {               # SAME behaviour, new shape
+    abs_path = os.path.normpath(os.path.abspath(path));
+    for (img_root, _) in _image_roots(abs_path) {
+        if _image_key(abs_path, img_root) in _image_module_keys(img_root) {
+            return img_root;
+        }
+    }
+    return None;
+}
+
+def unlisted_image_root(path: str) -> (str | None) {           # NEW
+    abs_path = os.path.normpath(os.path.abspath(path));
+    nearest = next(_image_roots(abs_path), None);
+    if nearest is None { return None; }
+    (img_root, nested) = nearest;
+    if nested or _image_key(abs_path, img_root) in _image_module_keys(img_root) {
+        return None;
+    }
+    return img_root;
+}
```

**What:** `_image_roots` walks from the file's folder up to `/`. Each time it finds a folder holding `_precompiled/MANIFEST.json`, it yields that folder plus a `nested` flag. `nested` becomes true once a `jac.toml` has been passed *below* that image.

- `sealed_root_for` takes the first yielded image that lists the file. It ignores `nested`, exactly as before.
- `unlisted_image_root` takes only the nearest image. It returns that image when the image is not across a project boundary and does not list the file.

**Why:** `prepare_application` needs to tell "no image" apart from "image here but it doesn't list me". That is the gap in case A.

**Things to notice:**
- **Order matters.** The image check runs before the `jac.toml` check in each folder. So a `jac.toml` sitting in the image root itself (the normal app layout) does not set `nested` for that image. Only a `jac.toml` strictly between the file and the image does.
- **Why the single walk:** your first version (146ae07) had a separate walk for `unlisted_image_root` with its own `jac.toml` stop. @MusabMahmoodh pointed out that "where an image's reach ends" would then be defined twice, and that this rule already changed once (#7957). Commit 842c87c moved both lookups onto `_image_roots`.
- **Equivalence check:** you ran old and new `sealed_serve.jac` over 9 layouts and got identical results. @MalithaPrabhashana ran 14 jacBuilder layouts against the real 152-module manifest and found that `sealed_root_for` matched main in all of them.
- **"One walk" means one definition, not one execution.** On the source-fallback path, `prepare_application` calls both functions, so the walk (and the manifest-key read) runs twice. Whether `_image_module_keys` caches is not visible in the diff.
- **Corrupt manifest:** an unreadable manifest has no keys, so `unlisted_image_root` names that image. The log will then say "does not list", even though the real issue is a corrupt manifest. The test pins this on purpose (5.x / 7.2).

## 6. How execution flows after the PR

### 6.1 Booting an app (`prepare_application`)

```text
jac start / jac run --serve <entry>
└─ prepare_application(entry, ...)
   ├─ entry = realpath(entry)
   ├─ image_root = sealed_root_for(entry)            ← CHANGED (same result, via _image_roots)
   │   └─ for each (img, _) in _image_roots: first img whose keys contain _image_key(entry, img)
   ├─ image_root found?
   │   ├─ yes → print "Loading sealed application artifacts" → _prepare_sealed (6.2)
   │   └─ no:
   │       ├─ unlisted = unlisted_image_root(entry)                         ← NEW
   │       │   ├─ no image above → None
   │       │   ├─ nearest image behind a nested jac.toml → None
   │       │   ├─ nearest image lists entry → None
   │       │   └─ else → nearest image root
   │       ├─ unlisted? → print "Sealed image at <dir> does not list <rel>; preparing from source"  ← NEW
   │       └─ "Compiling server modules and placement metadata..." → source compile
```

### 6.2 Loading the sealed artifacts (`_prepare_sealed`)

```text
_prepare_sealed(entry, program, image_root, entries)
├─ artifact manifest missing? → RuntimeError "no artifact manifest"   (existing)
├─ serve_manifest = image_root/.jac/serve_manifest.json
├─ not a file? → RuntimeError "Sealed application has no serving manifest: ...;
│                rebuild the bundle so the seal step writes it"       ← NEW
├─ manifest = json.loads(serve_manifest.read_text())
└─ ... rest unchanged (missing serving metadata / .jir / bytecode checks)
```

| Scenario | Before | After |
|---|---|---|
| Image lists the entry | `Loading sealed application artifacts` | unchanged |
| Image in the same project doesn't list the entry | `Compiling server modules...` only | `Sealed image at /app does not list web.jac; preparing from source`, then compile |
| No image anywhere | compile, no reason | unchanged (no new line) |
| Nested project (own `jac.toml`) inside another image | compile | unchanged (no false "does not list") |
| #7957: inner image unlisted, outer lists it | sealed from outer | unchanged (`unlisted_image_root` never runs) |
| Unreadable manifest | compile | new line names that image |
| Listed, but serve manifest never written | `[Errno 2] No such file or directory` | named `RuntimeError` |

**Behaviour change users will notice:** one extra log line on pods that fall back while an image is present, and a different error text for a missing serve manifest. No change to which pods boot sealed.

## 11. Questions your senior might ask

**Q: Can this change which pods boot sealed?**
No. The new code runs only after `sealed_root_for` returned `None`. `sealed_root_for` was rewritten but gave identical results on 9 layouts (your run) and 14 jacBuilder layouts (@MalithaPrabhashana).

**Q: Why not just check "is there any manifest above me"?**
Because a nested project inside someone else's image, like jacBuilder user projects, would then log a false "does not list" line on every boot. The `nested` flag from `jac.toml` prevents that.

**Q: Why does `_image_roots` check the image before `jac.toml` in the same folder?**
So that the image's own project root, which normally holds both files, isn't treated as a boundary. Only a `jac.toml` strictly between the file and the image marks it nested.

**Q: What if a workspace member has its own `jac.toml` in a subfolder (e.g. `web/jac.toml`) under `/app`?**
Then `nested` would be true and no line would print for an unlisted entry there. The diff and tests don't cover that layout, so whether workspace members have their own `jac.toml` can't be told from this PR.

**Q: Isn't the walk now done twice at boot?**
Yes, on the fallback path: once in `sealed_root_for`, once in `unlisted_image_root`. "One walk" refers to one definition of image reach. The cost is a directory walk plus a manifest read. Whether that read is cached isn't visible here.

**Q: What does the line say for a corrupt manifest?**
It says "does not list <file>", because an unreadable manifest yields no keys. The test pins this. It's slightly imprecise, but it still points the operator at the right image.

**Q: Why a `RuntimeError` instead of letting `FileNotFoundError` through?**
It matches the four other named misses in `_prepare_sealed`. It also tells the operator what to do (rebuild so the seal step writes the manifest). And it reaches the pod log through the same "Error loading" handler.

**Q: How do we know an operator actually sees the line?**
The real pod binary test asserts it on process stdout in CI. A temporary MicroK8s job using this PR's kit binary showed `Sealed image at /app does not list web.jac; preparing from source` in the `web` pod log.

**Q: The `web` pod still failed with `Dependency installation failed after 40.0s`. Is that this PR?**
No. It happened identically with main's binary, after the new lines. Your note attributes it to the #9136 source-compile path on that runner.

**Q: Does this fix #9136?**
No. It makes that failure visible. The causes are addressed by #9228 (seal the served app) and #9138 (host-side manifest gate), and this PR's error becomes the second line of defence.
