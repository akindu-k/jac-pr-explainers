## 1. The short version

`jac.toml` can hold values like `${OPENAI_API_KEY}`. When Jac reads the file, it swaps in the environment variable of that name. This is called **interpolation**. The docs say `${VAR}` and `${VAR:?message}` are errors when `VAR` is not set.

**Before this PR, the code that walks the config caught that error and kept the raw text, so an unset variable became a literal value.** The result was silent and wrong. `jac scale deploy --dry-run` could print `namespace: ${K8S_NAMESPACE:?set K8S_NAMESPACE}` in every Kubernetes manifest, or a Secret holding the string `${OPENAI_API_KEY}`, and still exit 0.

Your first version made the error fatal at load time. Every command loads `jac.toml`, so `jac check`, `jac fmt` and `jac lsp` then failed on deploy-only variables. **The final version never fails at load. It records each unresolved reference, with the setting that holds it, on `JacConfig.unresolved`, and each command decides what to do.** `jac run` warns on a bare `${VAR}` and exits 2 on `${VAR:?}`, but only in the sections it reads. `jac scale deploy` exits 1 on any unresolved `[scale.secrets]` or `[scale.kubernetes]` value it is about to ship. Tooling commands say nothing.

**Status:** Closed, not merged according to the data given. @MusabMahmoodh approved the *first* (fail-at-load) version on 2026-09-08. The reworked design (0cfe278 onward) has no approval on record. On head `ca4a17f`, `test-jac-pack-smoke` and the "Everything Passed" gate failed. Issue #8773 is closed. #9184 says the deploy check and "record every reference" behaviour exist on `main` through #9350, so this work appears to have landed through another PR. The data here cannot confirm that.

| `_interpolate_recursive` | The old walker over the whole config. It caught the `ValueError` and returned the raw text. **This is where the bug is.** Removed in this PR. |
| `resolve_env_refs(data, environ, path)` | **New.** The replacement walker. It returns `(resolved_data, list_of_refs)` and never raises. |
| `UnresolvedRef` | **New.** One record: `path` (such as `scale.secrets.API_KEY`), `var`, `required`, `message`, `raw` (the original string) and `keys` (the path as a list of real keys, such as `["scale","secrets","API_KEY"]`). |

| `deploy_setting()` | **New.** Tells whether a ref is a deploy setting. It returns `("secrets" or "kubernetes", remaining_keys)` or `("", [])`. |

## 3. The problem, step by step

### 3.1 The setup

- `_parse_toml_data` reads `jac.toml` and calls `_interpolate_recursive` on the whole dict.
- `merge_from_toml_file` (profile and local files) and `merge_apps_table` call the same walker.
- `interpolate_env_vars` raises `ValueError` on an unset `${VAR}` or `${VAR:?}`.
- jac-scale reads `[scale.secrets]` (which become a Kubernetes Secret) and `[scale.kubernetes]` (which shape every manifest) from the loaded config.

### 3.2 What went wrong

#### Case A: `${VAR:?}` namespace (issue #8773)

```text
1. jac.toml: [scale.kubernetes] namespace = "${K8S_NAMESPACE:?set K8S_NAMESPACE}"
2. K8S_NAMESPACE is not exported
3. _interpolate_recursive -> interpolate_env_vars raises ValueError("...is required: set K8S_NAMESPACE")
4. except ValueError: return obj              ← WRONG: error dropped, raw text kept
5. config namespace = "${K8S_NAMESPACE:?set K8S_NAMESPACE}"
6. jac scale deploy --dry-run builds 5 manifests with that namespace
7. "check: no errors or warnings", exit 0     ← WRONG: plan reported as clean
```

#### Case B: a bare `${VAR}` secret

```text
1. [scale.secrets] SOME_API_KEY = "${A_VAR_NOBODY_SET}"
2. walker catches "not set" and keeps raw text          ← WRONG
3. Secret stringData: SOME_API_KEY: ${A_VAR_NOBODY_SET}
4. deploy exits 0; pods get a literal placeholder as the API key
```

#### Case C: the first fix over-reached (your earlier commits)

```text
1. abb08ff: delete the except, so the ValueError propagates from JacConfig.load
2. Project has [scale.secrets] API_KEY = "${OPENAI_API_KEY}", unset on dev laptop
3. jac check / jac fmt / jac run / jac lsp load jac.toml -> exit 2   ← WRONG: none read that value
4. jac lsp exits before answering "initialize"
5. jac-scale: pods boot against the shipped jac.toml -> could fail to load (per @MusabMahmoodh, as cited in the description)
6. jac-scale: variables from project .env are read after config load -> load fails first
```

The two jac-scale points in steps 5 and 6 come from the PR description, which credits @MusabMahmoodh. Those exact comments are not in the review data shown.

### 3.3 Why it mattered

- `:?` exists to stop a bad deploy. Instead, it produced the bad value and let the deploy go ahead (#8773, filed by @MalithaPrabhashana's team after it hit a real namespace).
- `--dry-run` said "no errors", so operators had no warning before shipping.
- Secrets could ship as literal `${...}` strings into a live cluster.
- The first fix showed that a single "fail at load" switch breaks editors and local tooling for anyone without deploy variables.

## 4. The idea of the fix (one sentence)

> **Record, don't decide, at load time.** Loading keeps a list of every unresolved reference and where it lives, and each command applies its own policy to the settings it actually uses.

The old code answered "did this resolve?" and then threw the answer away, which left only "fail all" or "fail none." Keeping the answer lets `jac fmt` ignore deploy variables while `jac scale deploy` refuses to ship them.

## 11. Questions your senior might ask

**Q: Why not just make `:?` fatal at load, as #8773 suggested?**
Every command loads `jac.toml`. Your first version did this, and `jac check`, `jac fmt` and `jac lsp` failed on deploy-only variables. Two jac-scale paths also broke: pods loading the shipped `jac.toml`, and `.env` read after load.

**Q: Why does an unresolved string still keep its raw `${...}` text?**
So that commands which don't apply a policy behave exactly as before. The policy lives in the consumers (`_env_refs_resolve`, `_check_deploy_settings_resolve`).

**Q: How does a profile that fixes a value clear the base file's record?**
`_record_unresolved` computes every leaf the new layer sets (`_replaced_keys`) and drops any existing ref under one of those paths. Lists are leaves, so `[]` clears them. Empty tables have no leaves, so they clear nothing.

**Q: Why compare the deploy value to `ref.raw` instead of trusting the record?**
A record can be stale relative to what the builder actually uses, for example when an active profile replaced a secret. Comparing against the real value means the deploy fails only if the literal `${...}` is what would ship.

**Q: Why is `[scale.kubernetes]` checked on the host and not only by #9199's pod check?**
Pods receive `K8S_NAMESPACE` set to the configured value. A literal `${K8S_NAMESPACE:?…}` namespace therefore looks resolved from inside the pod, and only the host can catch it.

**Q: Why an allow-list of sections for `jac run`?**
So `[scripts]`, `[test]`, dependency tables and unknown tables never stop a run. A deny-list would block on any new or unknown table. The unknown-table test row pins this.

**Q: Does `jac run` ignore all of `[scale]`?**
No. Only `scale.secrets` and `scale.kubernetes` are skipped. Other `scale.*` subsections fall under `CAPABILITY_SECTIONS`, so a `${VAR:?}` there stops a run.

**Q: What still slips through?**
`${VAR:+alt}` and `${VAR:0:3}` don't match `ENV_REF_PATTERN`, so no ref is recorded and the deploy check misses them. This is tracked as #9184 gap 1. `service_urls.jac` keeps its `"${"` guard for this reason.

**Q: Why remove `os.path.expandvars` from `service_urls`?**
It was a second interpolator with different rules, such as expanding `$VAR` without braces. The loader is now the only source of resolved values.

**Q: Is the `.env` ordering for deploys guaranteed by this diff?**
Not visibly. The manual run shows `.env` values passing, but the diff does not show where `.env` is loaded relative to `get_config_for_path`.
