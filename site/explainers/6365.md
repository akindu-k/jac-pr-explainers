## 1. The short version

The Jac CLI command `jac start main.jac --client desktop --dev` does two things. It starts a **Vite dev server**, which serves the app's frontend with live reload. It also opens a **PyTauri desktop window** that shows that frontend. Two integration tests check this flow, one in `jac-client` and one in `jac-desktop`. Each test waits for Vite's port to open and then fetches a page from it.

**In headless CI (no screen, no WebKit library), the PyTauri window crashed on import with `ImportError: libwebkit2gtk-4.1.so.0`. Because the dev orchestrator stops every dev process when the window exits, Vite was stopped too, and the jac-desktop test failed with `TimeoutError: Timed out waiting for 127.0.0.1:5173`.** The `jac-client` copy of the test never hit this. It was skipped by a `has_display()` guard, and that skip hid a second bug: it waited on port `5173` while Vite actually listened on `8000`.

**You fixed this in three parts:**
- CI now installs WebKit and Xvfb (a virtual screen) and runs the client/desktop suite under `xvfb-run`, so both GUI tests really run.
- The jac-desktop test gets the same `has_display()` skip guard as its sibling, as a fallback for machines with no display.
- Both tests now pick a free port and pass it with `--port`, so they wait on the port Vite actually uses.

**Status:** The PR is **closed**. The metadata does not say whether it was merged. All 12 CI checks on head commit `dbdcb54` passed. Linked issue #6364 is closed. No other person reviewed or approved the PR. The only comments are your own.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. Test files end in `.jac` and use blocks like `test "name" { ... }`. |
| `jac-client` | Plugin that builds web/desktop frontends for Jac apps. It has its own test suite. |
| `jac-desktop` | Plugin that packages a Jac app as a desktop app. It also has its own test suite. |
| `jac start ... --client desktop --dev` | CLI command that runs the app in desktop *development mode*: Vite plus a GUI window. |
| Vite | A frontend dev server. Here it serves the app UI over HTTP, for example at `http://127.0.0.1:<port>/`. |
| PyTauri | A Python binding for Tauri, a toolkit for desktop windows that render web content. The dev flow runs it as `python app.py`. |
| WebKit / `libwebkit2gtk-4.1-0` | The Linux browser engine library that PyTauri uses to draw web pages. Without the file `libwebkit2gtk-4.1.so.0`, `import pytauri` fails. |
| Dev orchestrator | The code behind `--dev` that starts Vite and the GUI. Per the PR description, it calls `py_proc.wait()` on the GUI and then stops **all** dev processes in a `finally` block. **This is where the bug is.** The GUI crash takes Vite down with it. |
| `DISPLAY` / `WAYLAND_DISPLAY` | Environment variables that tell GUI programs which screen to draw on. CI machines normally have neither. |
| Headless | A machine with no screen, such as a CI runner. |
| Xvfb / `xvfb-run -a` | Xvfb is a fake X screen that lives only in memory. `xvfb-run` starts one, sets `DISPLAY`, and runs your command. `-a` picks a free display number automatically. |
| `has_display()` | Test helper that returns `False` when there is no `DISPLAY`/`WAYLAND_DISPLAY` (according to issue #6364). Tests use it to skip GUI tests. |
| `pytest.skip(...)` | Marks a test as skipped rather than failed. |
| `get_free_port()` | Test helper that returns a TCP port no other program is using right now. |
| `wait_for_port(host, port, timeout)` | Test helper (in `_helpers.jac`) that polls until something listens on the port. It raises `TimeoutError` if nothing does in time. |
| `Popen` | Python's way to start a child process without waiting for it to finish. |
| `pytest -n auto` | Runs tests in parallel across several worker processes (pytest-xdist). Tests that use the same fixed port can collide. |
| `pytest -x` | Stops the whole run at the first failure. |
| `DEFAULT_VITE_PORT` | Constant `5173` in `PyTauriDesktopTarget.dev`. Per the description, it is only used when `port <= 0`. Since `--port` defaults to `8000`, it is effectively never used. |
| Flaky test | A test that passes sometimes and fails other times without any code change. |

## 3. The problem, step by step

### 3.1 The setup

- **CI job `test-client`** in `.github/workflows/test-jaseci.yml` runs `pytest -x jac-client jac-desktop -n auto` on a headless Linux runner.
- **Test A:** `jac-client/.../test_it_desktop.jac` → `desktop dev mode starts`. It has a `has_display()` guard. Before the PR it waited on port `5173`.
- **Test B:** `jac-desktop/.../test_it_desktop.jac` → `desktop dev mode starts vite server`. It had **no** display guard. It used `vite_port = 5173`.
- **The dev orchestrator** starts Vite, then the GUI, and stops everything when the GUI exits.

### 3.2 What went wrong: Test B crashes in headless CI

```text
1. CI runner: no DISPLAY, no libwebkit2gtk-4.1.so.0 installed
2. Test B: no has_display() guard → test keeps going
3. Test B runs: jac start main.jac --client desktop --dev   (vite_port = 5173)
4. Orchestrator starts Vite → "✔ Vite dev server ready"      (port is open briefly)
5. Orchestrator starts `python app.py` (PyTauri)
6. app.py line 21: from pytauri import Commands
   → ImportError: libwebkit2gtk-4.1.so.0 not found           ← WRONG: GUI dies
7. py_proc.wait() returns → finally: "Stopping dev processes..."
8. Vite is stopped too → port closes                         ← WRONG: Vite tied to GUI
9. Test B: wait_for_port("127.0.0.1", 5173)
   - if it polls during step 4–6 → it sees the port → may pass
   - if it polls after step 8   → TimeoutError               ← "flaky" result
```

The outcome depends on whether the poll happens before or after the teardown. That is why the failure looked random even though its cause was always present.

### 3.3 What went wrong: Test A had a hidden port mismatch

```text
1. CI runner: no DISPLAY
2. Test A: has_display() == False → pytest.skip(...)         (the bug stays hidden)
--- after you add WebKit + Xvfb, the test really runs ---
3. Test A runs: jac start ... --dev   (no --port given)
4. --port defaults to 8000; DEFAULT_VITE_PORT (5173) is only used if port <= 0
5. Vite listens on 8000
6. Test A: wait_for_port("127.0.0.1", 5173)                  ← WRONG: wrong port
7. 90 s later → TimeoutError → test fails (failed in CI per PR description)
```

There was also a smaller risk. Under `-n auto`, Tests A and B could run at the same time. If both used port 5173, they would fight over it.

### 3.4 Why it mattered

- Test B failed at random in unrelated PRs. You linked one example, a CI run on PR #6294. Because the job uses `-x`, one failure stops the whole `test-client` job.
- The error message was a bare `TimeoutError` with no hint about the missing WebKit library.
- Test A gave false confidence. It was always skipped, so the desktop dev flow was never tested in CI, and its port bug went unnoticed.

## 4. The idea of the fix (one sentence)

> **Give CI a real GUI runtime, keep a skip guard for machines without one, and make each test wait on the port it actually asked for.** Installing WebKit and running under Xvfb lets the desktop dev tests run for real, and passing a free `--port` makes the wait target match where Vite listens.

This is better than only adding the skip guard, which is what issue #6364 first proposed. A skip-only fix would keep the desktop dev flow untested in CI, and that is exactly how Test A's port bug stayed hidden.

## 5. Every code change, explained

### 5.1 `.github/workflows/test-jaseci.yml`: install the GUI runtime and run tests on a virtual screen

```diff
     - name: Set up Bun
       uses: oven-sh/setup-bun@v2
 
+    - name: Install desktop GUI runtime (WebKit + Xvfb)
+      run: |
+        sudo apt-get update
+        sudo apt-get install -y libwebkit2gtk-4.1-0 xvfb
+
 ...
     - name: Run all client tests (including E2E in parallel)
-      run: pytest -x jac-client jac-desktop -n auto
+      run: xvfb-run -a pytest -x jac-client jac-desktop -n auto   # NEW: sets DISPLAY
```

- **What:** Before installing Python dependencies, the job installs the WebKit runtime library and Xvfb. The pytest command then runs inside `xvfb-run`, which starts a virtual X server and sets `DISPLAY` for pytest and every child process.
- **Why:**
  - With the library present, `import pytauri` works, which fixes step 6 of 3.2.
  - With `DISPLAY` set, the PyTauri window can open, and `has_display()` returns `True`, so Test A stops skipping.
- **Things to notice:**
  - All `-n auto` workers share one Xvfb display. That is fine because every window just draws to the same virtual screen.
  - `apt-get update` adds some time to every `test-client` run.
  - Only this one job (the one with Bun) gets the change. Other jobs do not need a GUI.
  - The size summary counts this file as "production" (+6 −1), but it is CI config. No runtime or compiler code changed.

### 5.2 `jac-desktop/jac_desktop/tests/test_it_desktop.jac`: guard plus free port

```diff
     if not is_jac_setup_available() {
         pytest.skip("'jac setup' CLI command not available");
     }
+    if not has_display() {                                   # NEW: same guard as Test A
+        pytest.skip("No display available for GUI tests");
+    }
     require_pytauri_setup_target();
 ...
-        vite_port = 5173;                                     # OLD: fixed port
+        vite_port = get_free_port();                          # NEW: free port per run
```

- **What:** Test B now skips when there is no display, and it picks a free port instead of `5173`.
- **Why:** The guard prevents the crash described in 3.2 on any machine without a screen. The free port removes the collision risk with Test A under `-n auto`.
- **Things to notice:**
  - The hunk does **not** show the `Popen` argument list for Test B. So the diff alone cannot confirm that `vite_port` is passed with `--port`. Before the PR, the test already stored the port in a variable, so it most likely already passed `--port str(vite_port)`. Only a one-line change would then be needed, and the passing CI and the 10× probe support this reading. Check the full file before you present.
  - The guard sits *before* `require_pytauri_setup_target()`, so a missing display is reported first.
  - The issue's second idea is not visible in this hunk: "Harden `wait_for_port`'s failure path ... to detect an early dev-process exit." If Test B does not already do this, it was dropped. Be ready to explain why.

### 5.3 `jac-client/jac_client/tests/test_it_desktop.jac`: pass a free `--port` and wait on it

```diff
+        vite_port = get_free_port();                                  # NEW
         dev_process = None;
         try {
-            print("[DEBUG] Starting desktop dev mode");
+            print(f"[DEBUG] Starting desktop dev mode on port {vite_port}");
             dev_process = Popen(
-                [*jac_cmd, "start", "main.jac", "--client", "desktop", "--dev"],
+                [ *jac_cmd, "start", "main.jac", "--client", "desktop", "--dev",
+                  "--port", str(vite_port),                           # NEW
+                ],
 ...
-                wait_for_port("127.0.0.1", 5173, timeout=90.0);       # OLD: wrong port
+                wait_for_port("127.0.0.1", vite_port, timeout=90.0);  # NEW
 ...
-                with urlopen("http://127.0.0.1:5173/", timeout=10) as resp {
+                with urlopen(f"http://127.0.0.1:{vite_port}/", timeout=10) as resp {
```

- **What:** Test A chooses a free port, tells `jac start` to use it, and then waits on and fetches from that same port. The debug prints show the port.
- **Why:** This fixes the 5173-vs-8000 mismatch from 3.3, and it avoids port collisions with Test B.
- **Things to notice:**
  - Test A already had a good failure path. On `TimeoutError` it checks `dev_process.poll()` and calls `pytest.fail(...)` if the process exited.
  - The new list has a stray blank line after `str(vite_port),`. This is cosmetic only.
  - You deliberately left production code alone. The dead `DEFAULT_VITE_PORT` default in `PyTauriDesktopTarget.dev` is "tracked separately", but the PR does not link that issue.
  - There is a tiny race: another process could take the free port between `get_free_port()` and Vite binding to it. This is a common, accepted pattern, and the description says both test files already use `get_free_port()`. The diff alone cannot confirm that.

No release notes or docs changed.

## 11. Questions your senior might ask

**Q: Was this really flaky or deterministic?**
Deterministic. The GUI crashed every time in CI. Only whether `wait_for_port` saw Vite before teardown depended on timing.

**Q: If you install WebKit and Xvfb, why add `has_display()` too?**
It is a fallback for local headless runs or runners without the setup. With Xvfb, `DISPLAY` is set and the guard does nothing.

**Q: Why did the jac-client test fail once it started running?**
It waited on 5173, but `jac start --dev` binds Vite to `--port`, which defaults to 8000. `DEFAULT_VITE_PORT` is only used when `port <= 0`. The skip had hidden this bug.

**Q: Does `has_display()` protect someone who has a display but no WebKit?**
No. It only checks `DISPLAY`/`WAYLAND_DISPLAY`. That person would still see a crash and then a timeout. Test A does fail clearly in that case because it checks `dev_process.poll()`. Test B's handling is not shown in the diff.

**Q: Why a free port instead of a fixed one?**
With `pytest -n auto`, the two tests can run at the same time. A fixed port lets them collide, and a free port per test avoids that.

**Q: Why not fix the orchestrator so Vite survives a GUI crash, or fix `DEFAULT_VITE_PORT`?**
Stopping everything when the GUI exits is how dev mode is meant to work. The default port is a separate production concern that you kept out of this PR on purpose, and it should get its own issue.

**Q: What does this cost in CI time?**
One `apt-get update` plus install, and two GUI tests that now run instead of skip. The probe measured about 29 s for both together. The exact `apt` time is not in the PR.

**Q: How do you know it is not flaky now?**
A temporary CI step ran both tests 10 times in a row: 20/20 passed, with runtimes between 28.6 and 29.2 s. That step was then removed in `88f7e44`.

**Q: Did any shipped code change?**
No. Only the CI workflow and two test files changed.
