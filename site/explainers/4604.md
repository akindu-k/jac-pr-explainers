## 1. The short version

The `jac-scale` API server turns Jac walkers and functions into HTTP endpoints, built on FastAPI. Some of those endpoints need a login token. The server also has three API key endpoints: `/api-key/create`, `/api-key/list` and `/api-key/{api_key_id}`.

**Before this PR, every endpoint that needed auth declared `Authorization` as an ordinary header parameter, so Swagger UI showed a separate "Authorization" text box on each of these endpoints.** A user who had already clicked the lock icon to log in still saw a second place to paste a token. The handlers read the token from that declared parameter. Some got it through `kwargs.pop('Authorization')`, others through a named function argument.

**You removed every `Authorization` `APIParameter` and changed the handlers to read the token straight from the incoming request with `request.headers.get('Authorization')`.** To make that work, you taught the FastAPI wrapper builder in `jfast_api.impl.jac` to pass the `Request` object to callbacks that ask for it. This includes callbacks with no other parameters, which had no such path before. After review, the wrapper's own request variable was renamed to `__jac_request__` so it is less likely to clash with user field names.

Clients see no change on the wire. They still send `Authorization: Bearer <token>`. What changes is the Swagger page and the internal plumbing.

**Status:** Merged on 2026-02-20. @musab-mah-7 approved on 2026-02-18. @Thamirawaran requested changes on 2026-02-18 and approved on 2026-02-20 after the rename. All 9 CI checks passed on head commit `39b1eee`.

## 3. The problem, step by step

This is a refactor and UI clean-up, not a crash fix. No issue is linked.

### 3.1 The setup

- `serve.impl.jac` builds the endpoints. For any walker or function that needs auth, and for all three API key endpoints, it added an `APIParameter` named `Authorization` of type `HEADER`.
- `jfast_api.impl.jac` turns those `APIParameter`s into a FastAPI handler. A `HEADER` parameter becomes a visible input on the Swagger page.
- The callbacks then got the token as a normal argument:
  - Static walker and function callbacks used `kwargs.pop('Authorization', None)`.
  - Dynamic handlers had an explicit `Authorization: str | None = None` argument.
  - API key methods (`self.create_api_key`, and so on) were wired directly as callbacks, with `Authorization` marked `required=True`.

### 3.2 What was missing

```text
1. Server starts. Walker `MyWalker` needs auth.
   create_walker_parameters("MyWalker") → [ ..fields.., APIParameter('Authorization', HEADER, required=False) ]
2. JFastApiServer builds the handler; OpenAPI now lists `Authorization` as a header param.
3. User opens /docs and clicks the lock icon, entering "Bearer abc123".
4. User opens MyWalker in Swagger → sees ANOTHER text box called "Authorization".   ← the confusing part
5. Same on /api-key/create, /api-key/list, /api-key/{id}, where the box is marked required.
6. The callback reads the token from that declared parameter (kwargs.pop / function arg),
   not from the request itself, so auth is tied to the parameter declaration.
```

The release note says the new behaviour is "consistent with the `update_username` and `update_password` endpoints." That means those endpoints already read the header without declaring it. The walker, function and API key endpoints were the odd ones out.

### 3.3 Why it mattered

- Swagger users saw two ways to give a token on every protected endpoint. You posted a screenshot on 2026-02-15, but its contents cannot be read from the PR text.
- On API key endpoints the text box was `required=True`, so Swagger pushed users to fill it in even after authorizing with the lock icon.
- The handlers depended on `Authorization` being declared as a parameter. Removing the box from the docs was not possible without changing how the token reaches the handler. That is why the PR touches the wrapper builder too.

## 4. The idea of the fix (one sentence)

> **Stop declaring the token; read it from the request.** Every auth-aware handler takes the FastAPI `Request` and calls `request.headers.get('Authorization')`, and the wrapper builder makes sure that `Request` is passed through in every code path.

This is the right approach because FastAPI always has the raw request available. Reading the header directly keeps the docs clean and does not change what clients send.

**What:** When an endpoint has no declared parameters, the wrapper checks whether the callback has a parameter named `request`. If it does, the wrapper passes the FastAPI `Request` as `request=`.

- For callbacks with `**kwargs`, the request is merged with the query string.
- For callbacks without `**kwargs`, a new wrapper variant that takes `__jac_request__: Request` is created. Before, that branch had no access to the request at all.

**Why:** After 5.1 and 5.4, some auth-requiring callbacks end up with no declared parameters, such as a field-less walker or `/api-key/list`. Without this change they would be called without `request` and fail with a missing-argument error.

**Things to notice:**
- FastAPI injects the request because of the `Request` **type annotation**, so naming the variable `__jac_request__` is safe.
- In `{'request': __jac_request__, **query_params}`, later keys win. A URL such as `?request=x` would **overwrite** the `Request` object with the string `"x"`. The callback would then fail on `request.headers` and return a 500. This edge case is not handled.
- The four wrappers differ only in sync/async and whether they pass `request`, so the change adds a lot of near-duplicate code.

## 6. How execution flows after the PR

### 6.1 Calling a walker or function that has fields (generated wrapper)

```text
Client: POST /walker/MyWalker   Authorization: Bearer abc123   body {...}
└─ FastAPI handler generated by _create_endpoint_function
   ├─ FastAPI injects Request into __jac_request__ (by type)          ← CHANGED (was `request`)
   ├─ builds callback_args from declared params (no Authorization)    ← CHANGED (param removed)
   ├─ callback_args['request'] = __jac_request__                      ← CHANGED (via param_mapping)
   └─ await callback(request=..., **fields)
      ├─ if requires_auth:
      │   └─ authorization = request.headers.get('Authorization')     ← NEW
      ├─ parse "Bearer ..." → username (unchanged)
      └─ run walker → TransportResponse → JSONResponse
```

### 6.2 Walker or function with no fields, or `/api-key/list` (no-params path)

```text
Client: GET /api-key/list   Authorization: Bearer abc123
└─ _create_endpoint_function: parameters == []
   ├─ needs_request_no_params = 'request' in sig.parameters → True   ← NEW
   ├─ callback has **kwargs?
   │   ├─ yes → wrapper(__jac_request__) → callback(request=..., **query_params)   ← CHANGED
   │   └─ no  → wrapper(__jac_request__) → callback(request=...)                   ← NEW variant
   └─ list_api_keys_handler(request)
      ├─ authorization = request.headers.get('Authorization')        ← NEW
      └─ self.list_api_keys(authorization)
```

### 6.3 Dynamic walker or function route

```text
Client: POST /walker/{walker_name}[/{nd}]   Authorization: Bearer abc123
└─ dynamic_walker_handler(request, walker_name, nd)                    ← CHANGED (no Authorization arg)
   ├─ parse body / query → kwargs
   ├─ Authorization = request.headers.get('Authorization')             ← NEW
   ├─ if is_auth_required_for_walker(walker_name): validate token
   └─ run walker
```

### 6.4 Creating or revoking an API key

```text
Client: POST /api-key/create  {name, expiry_days}   Authorization: Bearer abc123
└─ generated wrapper → create_api_key_handler(request, name, expiry_days)   ← NEW
   ├─ authorization = request.headers.get('Authorization')
   └─ self.create_api_key(name, expiry_days, authorization)
```

| Scenario | Before | After |
|---|---|---|
| Swagger page for a protected endpoint | Shows an "Authorization" text box | No text box; use the lock icon |

## 11. Questions your senior might ask

**Q: Do clients need to change anything?**
No. They still send `Authorization: Bearer <token>` as a header. Only the Swagger page and the internal plumbing changed.

**Q: Why does renaming the wrapper variable to `__jac_request__` not break FastAPI's injection?**
FastAPI injects `Request` by its type annotation, not its name. The generator then maps it back to the callback's `request` key with `param_mapping['request'] = '__jac_request__'`.

**Q: Why did you have to touch the no-params branch at all?**
Removing the `Authorization` parameter left some endpoints with an empty parameter list: field-less auth walkers and `/api-key/list`. That branch never passed the request before, so those callbacks would have been missing their `request` argument.

**Q: What happens now if someone calls `/api-key/create` without a header?**
Before, FastAPI rejected the request because the header was `required=True`. Now the handler passes `None` to `create_api_key`. Its handling of `None` is outside this diff.

**Q: Could a walker field named `request` still collide?**
At the generated wrapper level, no, because the wrapper uses `__jac_request__`. The callbacks in `serve.impl.jac` still name their parameter `request`, so a field with that name could still clash there. The diff does not show a guard for it.

**Q: Is there any risk in `{'request': __jac_request__, **query_params}`?**
Yes. Later keys win, so `?request=x` replaces the `Request` object with a string. Auth would then fail with a 500 on `.headers`.
