## 1. The short version

The Jac server (in `jaclang`, with the `jac-scale` plugin on top) turns every walker into an HTTP endpoint. A client POSTs JSON, the server builds the walker from that JSON with `walker_cls(**fields)`, and runs it. The server also publishes an OpenAPI schema that describes what each endpoint accepts.

**Before this PR, a walker field whose type is a custom `obj` (for example `has user: User;`) received the raw JSON dict, not a `User` instance, and the API schema did not describe the object's inner fields.** So `self.user.address.street` inside the walker would be run against a plain dict instead of a `User`. From the diff alone, you can't tell exactly which error that raised, or how the old schema showed a `User` type.

**You added recursive "dict → Jac object" conversion before the walker is built (`_resolve_object_fields`), a shared recursive introspector (`_introspect_fields`) that emits `type: 'object'`, `object_type` and `properties`, and nested Pydantic model generation in jac-scale's `_get_python_type`, so the OpenAPI body shows the nested shape.** Lists such as `list[User]` are handled too, through `_get_list_item_type`.

**Status:** Closed (the metadata says "closed", not "merged"). @Thamirawaran's last review was **changes requested**. Their later comment, "can we utilize already existing implementations?", has no reply. The `jac-check` CI check **failed** on the head commit `8446ae7`. All other checks passed.

| `report` | Jac statement that adds a value to the response's `reports` list. |
| `cls.init` | In Jac, `init` is the constructor, Python's `__init__`. The code reads its signature to learn the field names and types. |
| `jaclang.runtimelib` server | The core HTTP server in the `jac` package: `ExecutionManager`, `ModuleIntrospector`, `ExecutionHandler`. |

| `ModuleIntrospector` | Reads a Jac module and describes its walkers and functions (field names, types, required, default). jac-scale uses this to build API schemas. |
| `introspect_walker` / `introspect_callable` | Methods returning those descriptions for a walker or a function. |
| `_introspect_fields` | New shared helper that describes a class's `init` fields and recurses into nested Archetype fields. **This is what the PR adds** (schema side). |
| `_resolve_object_fields` | New method that turns nested dicts into Jac object instances before the walker is built. **This is what the PR adds** (runtime side). |
| `_get_list_item_type` | New helper: `list[User]` → `User`, using `typing.get_origin` and `typing.get_args`. |

| Field schema entry | A dict such as `{'type': 'object', 'object_type': 'User', 'required': True, 'default': None, 'properties': {...}}`. |
| jac-scale | The plugin that serves a Jac app with FastAPI and deploys it to Kubernetes. |

## 3. The problem, step by step

### 3.1 The setup

- **Schema side (startup):** `ModuleIntrospector.introspect_walker` → jac-scale `create_walker_parameters` → `APIParameter` list → `generate_body_model` → Pydantic model → OpenAPI.
- **Runtime side (each request):** JSON body → `fields` dict → `ExecutionManager.spawn_walker` → `walker_cls(**fields)`.
- Fixture types (from the new test fixture):

```jac
obj Address { has street: str, zip: int; }
obj User    { has name: str, address: Address, tags: list[str] = [], metadata: dict[str, str] = {}; }
walker NestedWalker     { has user: User; ... }
walker NestedListWalker { has users: list[User]; ... }
```

### 3.2 What went wrong: a single nested object

```text
1. Client POSTs /walker/NestedWalker
   body = {"user": {"name": "Alice", "address": {"street": "123 Main St", "zip": 90210}}}
2. Server parses JSON → fields = {"user": {...dict...}}
3. spawn_walker calls walker_cls(**fields)
   → walker.user = {"name": "Alice", "address": {...}}        ← WRONG: a dict, not a User
4. Walker runs: self.user.address.street
   → attribute access on a dict, not a User                     ← fails (exact error not shown in diff)
```

### 3.3 What went wrong: a list of objects

```text
1. Client POSTs /walker/NestedListWalker
   body = {"users": [{"name": "Bob", "address": {...}}, {"name": "Charlie", ...}]}
2. fields = {"users": [dict, dict]}
3. walker_cls(**fields) → walker.users = [dict, dict]            ← WRONG: items are dicts
4. [u.name for u in self.users] → attribute access on dicts       ← fails
```

### 3.4 What went wrong: the schema

```text
1. introspect_walker reads `user: User` → {'type': 'User', 'required': True, ...}
2. jac-scale passes data_type='User' to _get_python_type('User')
3. No knowledge of User's inner fields                            ← WRONG: OpenAPI lacks name/address/...
```

The diff doesn't show what `_get_python_type` returned for an unknown name like `'User'` before this PR.

### 3.5 Why it mattered

There is no linked issue. Your PR comments link a reference on OpenAPI JSON parameters and include screenshots and a video, presumably of the new schema in `/docs`. The jac-scale release note states the user impact. Walkers could not take structured parameters, and generated clients had no shape for them. People had to flatten objects into primitive fields, or accept a dict and read it by key.

## 4. The idea of the fix (one sentence)

> **Use the type information you already introspect, recursively.** Describe nested `obj` fields as `object` schemas with `properties`, and before building a walker, turn every dict whose target type is an Archetype (or a list of them) into an instance of that type.

The same introspection drives both the OpenAPI schema and runtime construction. That should keep "what the docs say" and "what the server builds" in step. Whether it fully does so is questioned in 5.1 and section 11.

`server.jac` adds the declarations of the two new methods and the new `field_schema` parameter. It also adds `get_origin` and `get_args` to the `typing` import.

**What:** Before the walker is built, every field value goes through `_resolve_object_fields`. The method decides each field's expected type in one of two ways:
- **Schema path:** from a passed-in schema, looking up `object_type` by name in `builtins`, then in the walker's module.
- **Fallback path:** from `get_type_hints(cls.init)`.

When a value is a dict and the expected type is an Archetype, the method recurses and builds an instance. When a value is a list of dicts and the expected type is `list[SomeArchetype]`, it builds each item.

**Why:** This fixes 3.2 and 3.3. The walker now receives `User`/`Address` instances.

**Things to notice:**
- **Construction failures are silent.** If `expected_type(**...)` raises, the raw dict is kept and no error or log is produced. The walker then fails later with a less clear error.
- **Name-based class lookup on the schema path.** An `object_type` is only found if that exact name is in `builtins` or in the module of the class being resolved. An object type imported under an alias, or defined in another module and not imported by name, will not resolve. The field then silently stays a dict.
- **Possible gap: lists on the schema path.** `_get_expected` returns `None` for any entry whose `type` is not `'object'`. A `list[User]` field gets `type` from the type's name (something like `'list'` or `'list[User]'`), not `'object'`. `_introspect_fields` only adds `properties` for direct Archetype types, not for `list[Archetype]`. So when a schema is passed, the `elif` list branch seems unable to fire. Yet `ExecutionHandler.spawn_walker` always passes a schema, and `test_nested_list_walker` passes in CI. Either jac-scale reaches `ExecutionManager.spawn_walker` without a schema (fallback path), or something outside the diff converts the list. The diff doesn't show which. You should check this before presenting.
- `field_name in ('self','args','kwargs')` fields are dropped from the resolved dict, not passed through.
- The helpers are defined conditionally inside `if`/`else` branches. That is unusual and could be relevant to the `jac-check` failure, but the logs aren't available, so this is a guess.

## 6. How execution flows after the PR

### 6.1 Schema generation (jac-scale startup)

```text
JacAPIServer.create_walker_parameters(walker)
├─ ModuleIntrospector.introspect_walker(walker_cls)
│  └─ _introspect_fields(walker_cls)                         ← NEW (shared helper)
│     ├─ user: User → {'type':'object','object_type':'User',
│     │                'properties': _introspect_fields(User)} ← NEW (recursive)
│     │                 └─ address: Address → {'type':'object', ..., properties} ← NEW
│     └─ users: list[User] → {'type': <list name>, ...} (no properties)
├─ api_data_type = 'object' if 'properties' in entry           ← NEW
└─ APIParameter(..., properties=..., object_type=...)          ← CHANGED
   └─ JSONBodyParameterHandler.generate_body_model
      ├─ has properties → _get_python_type('User', props, 'User') ← NEW

```

### 6.2 Spawning a walker (each request)

```text
POST /walker/NestedWalker  {"user": {...}}
└─ ExecutionHandler.spawn_walker
   ├─ introspector.introspect_walker(walker) → cached_schema       ← NEW (runs per request)
   └─ ExecutionManager.spawn_walker(cls, fields, user, cached_schema) ← CHANGED
      ├─ _resolve_object_fields(cls, fields, schema)               ← NEW
```

## 11. Questions your senior might ask

**Q: Why convert in `ExecutionManager` instead of letting Pydantic build the objects?**
A: Pydantic gives you validated Pydantic models, not Jac archetype instances. The core server (without jac-scale) also has no Pydantic layer. The conversion in `jaclang` works for both servers.

**Q: What happens if a client sends a nested object with a missing required field?**
A: `expected_type(**...)` raises, the exception is swallowed, and the raw dict is passed to the walker. The walker then fails later on attribute access. With jac-scale, Pydantic validation may reject the request first, but the diff doesn't show that.

**Q: Does `list[User]` really work end-to-end?**
A: The test passes, but on the schema path `_get_expected` returns `None` for list entries, so the list branch appears unreachable there. I need to confirm which path jac-scale uses before claiming it works in general.

**Q: How is the class found from `object_type`?**
A: By name: first `builtins`, then the module of the class being resolved. Types that are aliased, or defined elsewhere and not imported by name, silently fail to resolve.

**Q: Is the schema really cached per request?**
A: Not in the code shown. `introspect_walker` recomputes it, including `get_type_hints`, on every call, recursively.

**Q: What about recursive types like `obj Tree { has child: Tree; }`?**
A: Neither `_introspect_fields` nor `_get_python_type` tracks types it has already visited. A self-referencing type could recurse with no end at startup. This isn't tested.

**Q: Could two objects with the same name clash in the OpenAPI models?**
A: Yes. `_get_python_type` caches models in `self._models` by `object_type` name only.

**Q: Did you change behaviour for plain functions too?**
A: Yes. `introspect_callable` now marks Archetype parameters as `type: 'object'` with `properties`. Only walker spawning got runtime conversion, though; there is no matching change for function calls in the diff.

**Q: Why did `jac-check` fail?**
A: The log isn't in the PR data. Likely suspects are the conditional nested `def`s and the comment-only `except` block in `_resolve_object_fields`.

**Q: Was the reviewer's "use existing implementations" point addressed?**
A: Only partly. `introspect_walker` now shares `_introspect_fields`, but `introspect_callable` still duplicates that logic, and there was no reply to the comment.
