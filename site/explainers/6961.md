## 1. The short version

The webhook test file (`test_webhook.jac`) runs the same webhook checks twice: once without a database and once against a real MongoDB. MongoDB is a document database. The real MongoDB comes from a throwaway Docker container that the `testcontainers` library starts for the test.

**Before this PR, each of the 10 "with mongo" tests started its own `mongo:latest` container, ran one check, and stopped it. The file paid for 10 full container start/stop cycles.** No test was wrong. The time went to setup, not to the assertions. Issue #6956 measured `test_webhook.jac` at 98.9s, about 21% of the slow jac-scale server test group.

**You replaced the per-test container with one shared container per process. The first "with mongo" test starts it lazily, later tests reuse it, `atexit` stops it, and `jac_db` is dropped after each test so the next one starts empty.** The 10 copy-pasted test bodies became one helper, `_run_with_shared_mongo`, and each test is now a one-line call to it. Your measurement: about 1.9s per test with a fresh container, against about 0.7s with a shared container plus a drop.

**Status:** Merged on 2026-07-01. The only reviewer was the Greptile bot. Both of its findings were fixed in later commits. No human review appears in the data. All test jobs passed. One job, `microk8s real-app smoke`, failed.

## 3. The problem, step by step

This is a performance change, not a bug fix. Nothing was failing. The cost came from repeated setup.

### 3.1 The setup

- `test_webhook.jac` has 23 tests. 13 run "without mongo" (file storage). 10 run "with mongo".
- Each "with mongo" test needs a MongoDB, a fresh `jac start` server subprocess pointed at it, and one `run_webhook_*_test(base_url)` check.
- All 10 tests need the same thing: an empty MongoDB.

### 3.2 What went wrong

```text
1. Test "with mongo - endpoint exists" starts
2. MongoDbContainer("mongo:latest").start()      → container #1 boots  (~seconds)   ← waste
3. MONGODB_URI = uri of #1; _start_server(...)     → server subprocess up
4. run_webhook_endpoint_exists_test(base_url)     → one assertion
5. finally: stop server, unset MONGODB_URI, container #1 .stop()             ← waste
6. Test "with mongo - normal walker not in webhook" starts
7. MongoDbContainer(...).start()                  → container #2 boots         ← same cost again
   ... repeated for all 10 tests → 10 boots + 10 stops
```

There was also a smaller problem. `_start_server` was called before the `try`. If it raised, the `finally` never ran. The container leaked and `MONGODB_URI` stayed set. A fresh container per test hid the dirty state. The bot pointed out that sharing a container would make this matter (see 3.3 and section 9).

### 3.3 Why it mattered

- Issue #6956 says the jac-scale server test group takes about 7m47s. `test_webhook.jac` alone is 98.9s across 23 tests. The issue blames "fixed per-test overhead", meaning costs that are identical across tests.
- Container start/stop is one such overhead. Your measurement: about 1.9s per test with a fresh container, about 0.7s shared. You note that container start is usually slower on CI than on a local Docker daemon, so the CI saving may be larger.
- The issue has a rule: "Isolation must be preserved … correctness over speed." The fix had to keep each test starting from an empty DB.
- The larger cost in this file, cold-compiling the fixture on every `jac start`, is out of scope. #6956 tracks it.

## 4. The idea of the fix (one sentence)

> **Start MongoDB once, empty it between tests.** Keep one container per process and drop `jac_db` after each test, so every test still sees an empty database without paying for a container boot.

Dropping a database takes milliseconds, while booting a container takes seconds. Both leave the next test with an empty `jac_db`, so isolation holds as long as the server only writes to `jac_db`.

## 6. How execution flows after the PR

This PR changes only how tests run. Product behaviour is unchanged.

### 6.1 First "with mongo" test in a process

```text
test "webhook with mongo - endpoint exists"
└─ _run_with_shared_mongo(run_webhook_endpoint_exists_test)          ← NEW
   ├─ port = get_free_port(); base_url = http://localhost:<port>
   ├─ uri = _shared_mongo_uri()                                      ← NEW
   │  ├─ _wh_mongo_container is None → create MongoDbContainer("mongo:latest")
   │  ├─ .start()                                (one-time boot cost)
   │  ├─ atexit.register(_stop_shared_mongo)
   │  └─ return get_connection_url()
   ├─ os.environ["MONGODB_URI"] = uri
   ├─ _cleanup_db_files(fixtures)
   ├─ sp = None
   └─ try
      ├─ sp = _start_server(...)                 ← CHANGED: now inside try
      ├─ run_test(base_url)
      └─ finally
         ├─ if sp is not None: _stop_server(sp)  ← CHANGED: guard
         ├─ pop MONGODB_URI
         ├─ _reset_shared_mongo(uri) → drop jac_db   ← NEW (errors are raised)
         └─ _cleanup_db_files(fixtures)
```

### 6.2 Later "with mongo" tests

```text
_run_with_shared_mongo(run_X)
├─ _shared_mongo_uri() → container already set → return URI   ← NEW: no boot
├─ (same steps as 6.1: start server, run test, finally-cleanup)
└─ jac_db was dropped by the previous test → starts empty
```

### 6.3 Server fails to start

```text
_run_with_shared_mongo(run_X)
└─ try
   ├─ _start_server raises → sp stays None
   └─ finally
      ├─ skip _stop_server (sp is None)
      ├─ pop MONGODB_URI                     ← now always runs
      ├─ drop jac_db                         ← now always runs
      └─ _cleanup_db_files
   (original exception then propagates → test fails)
```

### 6.4 Process exit

```text
Python interpreter exits normally
└─ atexit → _stop_shared_mongo()                                  ← NEW
   ├─ container is not None → stop(), errors suppressed
   └─ set global to None
```

| Scenario | Before | After |
|---|---|---|
| 10 mongo tests, all pass | 10 container boots and 10 stops | 1 boot, 10 drops of `jac_db`, 1 stop at exit |
| `_start_server` raises | `finally` skipped: container leaked, `MONGODB_URI` left set | `finally` runs: env cleared, DB dropped, files cleaned |
| `drop_database` fails | n/a | Exception raised, so the test fails visibly |
| Container stop fails at exit | n/a (stop was in `finally`, so it would raise) | Suppressed silently, since there is nothing useful to report at exit |
| Only "without mongo" tests run | No container | No container (lazy start) |

The visible change for developers is that a failing DB reset now fails the test. Users of jac-scale see nothing different.

### 7.2 `test_webhook.jac`: `_shared_mongo_uri` and `_stop_shared_mongo`

```diff
+def _shared_mongo_uri -> str {
+    global _wh_mongo_container;
+    if _wh_mongo_container is None {
+        _wh_mongo_container = MongoDbContainer("mongo:latest");
+        _wh_mongo_container.start();
+        atexit.register(_stop_shared_mongo);
+    }
+    return _wh_mongo_container.get_connection_url();
+}
+
+def _stop_shared_mongo {
+    global _wh_mongo_container;
+    if _wh_mongo_container is not None {
+        with contextlib.suppress(Exception) {
+            _wh_mongo_container.stop();
+        }
+        _wh_mongo_container = None;
+    }
+}
```

**What:** `_shared_mongo_uri` starts the container on first call and returns its URI every time. `_stop_shared_mongo` stops it once at exit.

**Why:** This removes the 9 extra boots. Because the container starts lazily, runs that only touch the "without mongo" tests never start Docker.

**Things to notice:**
- The global is assigned *before* `.start()`. If `.start()` raises (for example, Docker is unavailable), the global holds an unstarted container and `atexit` is not registered. The next mongo test skips the `if`, calls `get_connection_url()` on it, and most likely fails with a less clear error. Assigning to a local variable first and setting the global after a successful start would avoid this. Nobody raised it.
- `atexit` runs only on a normal interpreter exit. A killed worker can leave the container running. testcontainers usually has a reaper container (Ryuk) for this, but the diff doesn't show whether it is enabled here.
- Suppressing errors in `_stop_shared_mongo` is a reasonable choice. At exit there is no test to fail, and raising would only add noise.

### 7.3 `test_webhook.jac`: `_reset_shared_mongo`

```diff
+def _reset_shared_mongo(uri: str) {
+    client = MongoClient(uri);
+    try {
+        client.drop_database('jac_db');      # no suppress: failure must be visible (bde60ff)
+    } finally {
+        client.close();
+    }
+}
```

**What:** Opens a client, drops `jac_db`, and always closes the client.

**Why:** This keeps the "each test starts empty" guarantee that a fresh container used to provide.

**Things to notice:**
- The first version wrapped the drop in `contextlib.suppress(Exception)`. Greptile flagged that a failed drop would silently leak data into the next test. Commit bde60ff removed the suppression.
- Only `jac_db` is dropped. If the server ever writes to another database, that data would carry over between tests. Nothing in the diff shows another database name.

### 7.4 `test_webhook.jac`: `_run_with_shared_mongo`

```diff
+def _run_with_shared_mongo(run_test: Callable[[str], None]) {
+    port = get_free_port();
+    base_url = f"http://localhost:{port}";
+    uri = _shared_mongo_uri();
+    os.environ["MONGODB_URI"] = uri;
+    _cleanup_db_files(wh_fixtures_dir);
+    sp = None;
+    try {
+        sp = _start_server(wh_fixtures_dir, wh_test_file, port, base_url);   # moved inside try (857179d)
+        run_test(base_url);
+    } finally {
+        if sp is not None {
+            _stop_server(sp);
+        }
+        os.environ.pop("MONGODB_URI", None);
+        _reset_shared_mongo(uri);
+        _cleanup_db_files(wh_fixtures_dir);
+    }
+}
```

**What:** One place for the setup and teardown that was copy-pasted 10 times.

**Why:** It shares the container, and it fixes the old cleanup gap where a failing `_start_server` skipped `finally`. Greptile marked that gap P1, and commit 857179d fixed it.

**Things to notice:**
- The drop happens **after** each test, in `finally`, not before. The first test is safe because its container is brand new.
- Steps inside `finally` run in order. If `_stop_server` or `_reset_shared_mongo` raises, the steps after it are skipped. For example, `_cleanup_db_files` would not run. That exception also replaces the test's own exception. Python still shows the original as context in the traceback.
- `MONGODB_URI` is set *before* `try`. If `_cleanup_db_files` raised before the `try`, the variable would stay set. That is unlikely, and the old code had the same order.
- Each test still gets a **fresh server subprocess**. Only MongoDB is shared.

## 11. Questions your senior might ask

**Q: Is isolation really the same as a fresh container?**
For anything in `jac_db`, yes. It is dropped after every test, even when the server fails to start, and the first test gets a brand-new container. Data in any other database would persist, but the diff shows no other database.

**Q: Why drop after instead of before each test?**
Teardown in `finally` already holds the URI and runs even on failure. The first test doesn't need a drop because its container is new. Your PR description says "before", so be ready to correct that.

**Q: What happens if a DB drop fails?**
The exception is raised and the test fails. You originally suppressed it. Greptile pointed out that this would hide broken isolation, so commit bde60ff removed the suppression.

**Q: What if `_start_server` raises?**
After 857179d it runs inside `try`. `finally` still unsets `MONGODB_URI`, drops `jac_db` and cleans local DB files, so the next test isn't polluted.

**Q: How is the container cleaned up?**
`atexit.register(_stop_shared_mongo)` stops it on normal process exit and ignores errors. On a hard kill, `atexit` doesn't run. Cleanup then depends on testcontainers' own reaper, which this PR doesn't control.

**Q: What if tests run in parallel?**
Each worker process has its own global, so each gets its own container and its own `jac_db`. Workers don't share state. The diff doesn't show whether this suite actually runs with several workers.

**Q: How much time does it save?**
Locally, about 1.9s against about 0.7s per mongo test. Across 10 tests that is roughly 12s, and likely more on CI. No CI timing comparison is in the PR. The remaining big cost in this file, cold compiles on each `jac start`, is tracked separately under #6956.

**Q: What happens if Docker can't start the container?**
The first mongo test fails. Because the global is assigned before `.start()`, the following mongo tests would probably fail with a less clear error instead of retrying. This is a small, known weakness.

**Q: Did any user-facing behaviour change?**
No. No production files changed. Only the test harness and a release note changed.
