## 1. The short version

jac-scale keeps one special node per deployment called `system_root`, the "super root" with the all-zeros ID `00000000-0000-0000-0000-000000000000`. Apps often hang "singleton" nodes off it: one node that should exist exactly once, created by a walker that checks "is it there? if not, create it". This pattern is called find-or-create.

**Before this PR, every in-flight request in a process shared the very same `system_root` object (cached live in `_process_cache`). Concurrent find-or-create requests therefore created duplicate singletons, and the losers failed with `500 WriteConflict: anchor 00000000-... changed concurrently (expected v0, found v1)`.** In production this piled up 82 copies of `CommunityHub` and 68 of `StripeEventIndex` on one super root.

**You give each request its own deep copy of the super root. You refresh the cached copy (the "template") from committed store state under a lock. You re-read the super root before an optimistic-concurrency retry. And you stop rollback from deleting pre-existing nodes from the database.** With these changes, 40 concurrent requests create exactly one hub and none fail (8 hubs before the fix, per your description).

## 3. The problem, step by step

### 3.1 The setup

- Each HTTP request gets a `JScaleExecutionContext`.
- At `init`, the old code took the anchor in `_process_cache['system_root']` and put that same object into the request's L1 `__mem__`.
- On commit, `ScaleTieredMemory.commit` writes the change set to L3. In Mongo, `_put_node_atomic` CAS-checks `version` and raises `WriteConflict` if it moved.
- `_run_function_with_occ` retries on conflict, but did not re-read the super root.
- `TieredMemory.abort` deleted every modified anchor from L3 on rollback.

### 3.2 What went wrong: duplicates + WriteConflict (Mongo + Redis)

This is the issue's reproduction, shown at the level the PR and issue explain it.

```text
1. Process starts. _process_cache['system_root'] = ROOT (one object, v0, 0 edges).
2. Request A context: __mem__[000..0] = ROOT        (same object)
3. Request B context: __mem__[000..0] = ROOT        (same object)
4. A runs touch_hub: [ROOT-->] has no Hub → creates Hub_A, ROOT ++> Hub_A
5. B runs touch_hub: also saw no Hub     → creates Hub_B, ROOT ++> Hub_B
   ← WRONG: both edits land on the one shared ROOT object. Each request's
     change tracking (hash / read version) no longer matches what it did.
6. A commits: CAS "000..0 at v0?" yes → root becomes v1. Hub_A persisted.
7. B commits: CAS "000..0 at v0?" found v1 → WriteConflict
   ← WRONG: B's Hub_B may already be persisted; request returns 500
     (or, on the close-path commit, the error is logged and the write lost).
8. A retry (if any) reuses stale root state, so it does not "see" Hub_A.
Result in the issue: version=2, 2 edges on root, 3 Hub anchors, 4× HTTP 500.
```

### 3.3 Mongo only (no Redis)

```text
1-5. Same as above: shared ROOT, several requests each create a Hub.
6.   The CAS does not fire in this setup (per the issue).
     ← WRONG: no error, but each request still persisted its own Hub.
Result in the issue: 7 Hub anchors, 1 edge on the super root.
```

### 3.4 Rollback deleting shared data

```text
1. Attempt modifies existing ROOT (adds an edge). ROOT.hash != new hash → "dirty".
2. Attempt hits WriteConflict → abort().
3. Old abort: dirty → pop from L1, invalidate L2, AND l3.delete(ROOT.id)
   ← WRONG: deletes a pre-existing node that other writers committed to.
```

Your description states this risk. The diff confirms the old code deleted any dirty persistent anchor from L3.

### 3.5 Why it mattered

- `system_root` is shared by all users, so it is a deployment-wide hot spot. The problem gets worse with more replicas.
- Production (8 replicas) showed 82 and 68 duplicates. There were also 294 `WriteConflict` warnings in 15 minutes, swallowed on the context-close path.
- Code that "takes the first match" picks different copies at different times. State written through one copy is invisible through another.
- No safe workaround existed in user code (issue #7605).

## 4. The idea of the fix (one sentence)

> **Stop sharing one mutable super root.** Each request works on its own copy, the shared template is only ever rebuilt from what the store committed, and a losing writer re-reads that state and re-runs.

This removes the actual cause: shared mutable state corrupting per-request bookkeeping. It also lets the existing OCC retry work as designed, instead of adding a new locking scheme or a database unique index.

**What:** At request start, the context gets a deep copy of the template. If no template exists yet, it loads the root from memory/store, or creates it, then publishes a detached copy as the template.

**Why:** This fixes the core cause. One request's edits can no longer appear in another request's root.

**Things to notice:**
- The declaration in `context.jac` exists because Greptile flagged that the bootstrap compiler would not emit a loose helper in an `.impl.jac` file (fixed in `494c6b1`).
- The cost is a full serialize/deserialize of the super root on every request, even for requests that never touch it. For a root with many edges (production had 151) this is real overhead. You list copy-on-write as a follow-up.
- The template is never handed out directly. Even the cold-start path publishes a copy, not the request's own object.

### 5.2 `jac/jaclang/scale/memory/memory_hierarchy.jac`: locked template publishing

```diff
+import threading;
 glob logger = ...,
-     _process_cache: dict[str, any] = {};
+     _process_cache: dict[str, any] = {},
+     _super_root_template_lock = threading.Lock();
+
+def _publish_super_root_template(snapshot: (NodeAnchor | None)) -> None {
+    with _super_root_template_lock {
+        latest = _process_cache.get('system_root');
+        if isinstance(latest, NodeAnchor) and latest.version >= snapshot.version { return; }  # keep existing if same or newer
+        _process_cache['system_root'] = snapshot;
+    }
+}
+
+def _publish_super_root_from_store(store: PersistentMemory, sr_id: UUID) -> None {
+    with _super_root_template_lock {
+        try {
+            store_cache = store?.__mem__;
+            if isinstance(store_cache, dict) { store_cache.pop(sr_id, None); }  # force a real read
+            row = store.get(sr_id);
+            snapshot = Serializer.deserialize(Serializer.serialize(row, include_type=True)) if isinstance(row, NodeAnchor) else None;
+        } except Exception { return; }
+        latest = _process_cache.get('system_root');
+        if isinstance(latest, NodeAnchor) and latest.version > snapshot.version { return; }  # equal is allowed
+        _process_cache['system_root'] = snapshot;
+    }
+}
 ...
+    def _refresh_super_root_template(applied: list) -> None;
```

**What:** There are two ways to set the template, both under one process-wide lock.
1. `_publish_super_root_template` is the cold-start path. It only fills the template if it is empty or strictly older.
2. `_publish_super_root_from_store` is the post-commit path. It drops L3's in-process cached row, re-reads the committed row, copies it, and publishes it unless the cached template is strictly newer.

**Why:** The template must never go backwards to an older or partial view. Otherwise new requests miss the committed hub and create another one.

**Things to notice:**
- Read and publish happen inside the same lock. So refreshes run in lock order, and a later refresh reads later committed state. This answers Greptile's "Older Snapshot Replaces Newer State".
- The two paths compare versions differently, on purpose:
  - The cold-start path uses `>=` (equal versions are not replaced).
  - The store path uses `>`, so equal versions are replaced. A fresh store read at the same version may carry newer content, such as grants.
  
  The history shows this went back and forth: `70b0394` rejected equal versions, then `fd0e43a` let the post-commit refresh supersede an equal-version template.
- Errors during the store read are swallowed silently (`except Exception { return; }`), with no log. If that fails, the template simply stays as it was.
- The lock is per process. Other replicas each keep their own template, so cross-replica safety still depends on the database CAS plus retry.

**What:** After a commit, if the super root was among the anchors that actually persisted, the template is rebuilt from the store.

**Why:** It keeps the template in step with committed edges and grants, so the next request sees the existing hub.

**Things to notice:**
- The refresh runs before `raise conflict` on purpose (`b3cb100`). A commit can persist the root write and then hit a conflict on another intent. Without this ordering, the retry could find the hub and never write the root again, leaving the template stale (Greptile's "Refresh applied root writes").
- It is safe to run before the conflict check only because it reads from the store, not from the request's local copy. That was Greptile's "Conflicted Commit Publishes Local Topology", fixed in `57166e5`.
- It was made a method declared in `memory_hierarchy.jac` so the bootstrap compiler emits it (`54d7c61`).
- `self.changes.clear()` still runs before the raise. The issue pointed out that this prevents replaying the change set. You rely on re-running the walker instead, as stated in your follow-ups.

## 6. How execution flows after the PR

### 6.1 A request context starts

```text
JScaleExecutionContext.init
├─ template = _process_cache['system_root']
├─ copy = _independent_super_root(template)                    ← NEW (deep copy)
├─ copy exists?
│  ├─ yes → __mem__[000..0] = copy                             ← CHANGED (was shared object)
│  └─ no  → mem.get(000..0) or create Root()
│           └─ _publish_super_root_template(copy of it)        ← NEW (locked, only if newer)
└─ system_root = user_root = entry_node = this request's copy
```

### 6.2 A commit that writes the super root

```text
ScaleTieredMemory.commit
├─ apply change set to L3 (Mongo CAS on version)
├─ _post_apply(report); changes.clear()
├─ _refresh_super_root_template(report.applied)                ← NEW
│  └─ 000..0 in applied?
│     └─ _publish_super_root_from_store (under lock)           ← NEW
│        ├─ drop L3 in-process row, store.get(000..0)
│        ├─ deep copy
│        └─ replace template unless cached version is newer
├─ conflict? → raise WriteConflict
└─ _mark_committed
```

### 6.3 A writer that loses the race

```text
_run_function_with_occ (retry loop)
├─ walker runs on its own root copy → creates Hub_B, edge
├─ commit → WriteConflict (root moved to v1)
├─ abort()
│  ├─ Hub_B is brand_new → removed from L1/L2 and deleted from L3   ← CHANGED (only brand-new hit L3)
│  └─ root copy is dirty but not brand_new → L1/L2 dropped, L3 kept ← CHANGED
├─ backoff sleep
├─ ctx.arefresh_system_root()  → loads root v1 with Hub_A edge     ← NEW
├─ ctx.aset_user_root(root_id)
└─ walker re-runs → finds Hub_A → reports it, no new write
```

| Scenario | Before | After |
|---|---|---|
| 40 concurrent find-or-create, cold DB | Duplicates (8 in your repro; 3 or 7 in the issue's), some 500s | 1 hub, all 200 (per your description and test) |
| Loser hits `WriteConflict` | Retry reused stale shared root, or the request failed | Retry re-reads the root, converges |
| Rollback of a modified existing node | Deleted from L3 | Kept in L3; only L1/L2 dropped |
| Grant on `system_root` in the startup entry | Visible via the shared object | Propagates via the post-commit store refresh |
| Request that never touches the root | Free | Pays one deep copy of the root |

User-visible behaviour changes:
- There are no more 500s or duplicates in this race.
- Walker bodies may run more than once on a conflict. Non-idempotent side effects, such as sending an email, repeat. You note this as existing behaviour.

## 11. Questions your senior might ask

**Q: Why deep-copy per request instead of locking the shared root?**
A: The bug came from shared mutable state corrupting per-request change tracking. Copies isolate requests without serialising all traffic. The CAS plus retry handles real conflicts.

**Q: What does the per-request copy cost?**
A: One serialize/deserialize of the super root per request, including requests that never touch it. With large fan-out (production had 151 edges) this is non-trivial. Copy-on-write is listed as a follow-up.

**Q: Why accept equal versions in `_publish_super_root_from_store` but not in `_publish_super_root_template`?**
A: The store path reads committed state under the lock, so a same-version read can still carry newer content, such as grants. It should win. The cold-start path publishes a request's own copy, so it only fills an empty or older template.

**Q: Why refresh the template before raising the conflict?**
A: `apply()` can persist the root write and then conflict on another intent. If the refresh were skipped, the retry might find the hub and never write the root again, leaving a stale template. Reading from the store makes the early refresh safe.

**Q: Does the abort change affect anything besides the super root?**
A: Yes. Any pre-existing anchor modified in an aborted attempt is now kept in L3 instead of deleted. Only brand-new anchors (`hash == 0`) are deleted.

**Q: Does this fix races across multiple replicas?**
A: Partly, and by design. Each replica has its own template and lock. Across replicas, convergence relies on the Mongo CAS plus `arefresh_system_root` on retry. The test runs one server, so the multi-replica case is not covered by CI.

**Q: Can `arefresh_system_root` get a stale root from Redis?**
A: It drops L1 and calls `mem.aget`, which may check L2 first. Abort invalidates dirty anchors in L2, which should cover the loser's root. The diff does not show the full retry loop, so this cannot be fully confirmed here.

**Q: What about non-idempotent walkers?**
A: On conflict the whole walker re-runs, so side effects repeat. This is existing OCC behaviour that the fix relies on. It is noted in the description.

**Q: Does this address the close-path commit the issue blamed for 294 swallowed conflicts?**
A: This diff does not change `jfast_api.impl.jac`. If that path still commits outside the OCC retry, conflicts there would still be logged and dropped. That needs checking in the codebase.

A: The logs are not available here. It is the only real failure, and `Everything Passed` is the aggregate that depends on it.
