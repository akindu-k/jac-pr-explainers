## 1. The short version

jac-scale is the plugin that deploys Jac apps to Kubernetes. It uses one Redis instance for two jobs. The first is an **anchor cache**: copies of graph data whose real copy lives in MongoDB. The second is the **event bus**: Redis Streams such as `jc.run.<id>`, which carry a run's live output to the client. That Redis was set up with `maxmemory 200mb` and `maxmemory-policy allkeys-lru`. In plain terms: "when full, delete whichever key was touched longest ago."

**A live run stream is written in bursts and then sits idle while the agent thinks, so it is always the least recently used key, and `allkeys-lru` deleted it before the client had read it.** The flat 200mb cap made this happen sooner. It stayed at 200mb even when the pod limit was raised to 1Gi. On `jac-builder-dev` the issue shows `used 190.42M`, `evicted_keys 7875`, and the consumer failing with `NOGROUP No such key 'jc.run.…'`. The user saw a turn finish on the server while the client received nothing.

**You changed the default policy to `volatile-lru`, which only evicts keys that have an expiry. Cached anchors have one and streams don't, so streams leave the eviction pool.** You also made `maxmemory` default to 70% of the pod memory limit. Around that you added:
- a fallback to `allkeys-lru` when the cache TTL is 0;
- trimming of each stream to `stream_maxlen` (10000) on publish;
- a startup warning when the connected Redis can evict streams;
- `NOGROUP` reported as data loss at error level, with 3 retries instead of 1;
- eviction info in `health()`.

**Status:** Closed as a draft on or after 2026-07-24, not merged. One commit (`3ec7747`). The Greptile bot gave confidence 3/5 and left one P1 comment, which is still open. "Contribution Checks" and the "Everything Passed" gate failed; all functional test jobs passed. Issue #7615 shows as closed. Nothing in the PR says why the PR or the issue was closed.

## 3. The problem, step by step

### 3.1 The setup

- **Provisioner** (`kubernetes_redis.jac`). It writes `redis.conf` from `[scale.database]`. Before this PR it used `redis_max_memory` defaulting to `200mb` and `redis_eviction_policy` defaulting to `allkeys-lru`. It parsed `redis_memory_limit` only to print a warning.
- **Anchor cache.** About 1353 `anchor:*` keys on dev. They are read and written all the time. Per the PR text they are written with a TTL. The cache write code is not in this diff, so you can't confirm it from here.
- **Event bus** (`redis.jac`). Usually one `jc.run.<id>` stream at a time, with no TTL.
- **Consumer.** It calls `XREADGROUP` in a loop. On `NOGROUP` it recreates the group once and retries once.

### 3.2 What went wrong: the idle stream is evicted

```text
1. Pod limit 1Gi, but redis.conf says maxmemory 200mb, policy allkeys-lru
2. Run 1f3b2407 starts: XADD jc.run.1f3b2407 (chunk events), group jc.coder.peer.1f3b2407 created
3. Agent thinks / user types → stream untouched; anchor:* keys keep getting read and written
4. Used memory reaches ~190M of 200M
5. Redis must free memory → picks the least recently used key → jc.run.1f3b2407   ← WRONG: unread events have no other copy
6. Stream key gone (EXISTS = 0)
7. Consumer: XREADGROUP → "NOGROUP No such key 'jc.run.1f3b2407' or consumer group …"
8. Buffered events lost; client receives nothing
```

### 3.3 What went wrong: the self-heal loses the race

```text
1. 05:00:22.925  NOGROUP → WARN "missing; recreating" → _ensure_group(force=True) makes an EMPTY stream
2. Redis is still at the cap → the fresh, idle key is evicted again
3. 05:00:22.954  retry _xreadgroup → NOGROUP again (29 ms later)          ← WRONG: retry not wrapped
4. Raw error falls to outer "XREADGROUP failed …" ERROR; batch lost
5. Even when the recreate works, the stream is empty: the old events are already gone
```

### 3.4 Why it mattered

Downstream on jacBuilder / jac-coder, the issue lists these effects:
- the turn ran on the server, but the UI got nothing and replayed the previous assistant message as a duplicate;
- `ai_processing` stayed set, so later turns were rejected with "A turn is already in progress";
- the problem got worse with load and with more replicas.

The issue's author checked `noeviction` and found it unsafe: once Redis is full it rejects every write, including `anchor:*` writes.

## 4. The idea of the fix (one sentence)

> **Make the cache evictable and the bus not.** Use `volatile-lru` so Redis only evicts keys with a TTL (cached anchors), size `maxmemory` from the pod limit, and bound stream growth by trimming.

This uses a split that already exists: per the PR, cache keys have a TTL and streams don't. Redis's only per-key eviction control is "has a TTL or not", so no new infrastructure is needed. Note that this goes further than the issue suggested. The issue said to keep `allkeys-lru` as a backstop and fix the size.

**What:** You split one long `_load_redis_config` into small resolvers: TTL, samples, policy and max memory. The rules change in three ways:
1. The default policy is `volatile-lru`.
2. A `volatile-*` policy combined with TTL ≤ 0 becomes `allkeys-lru`, with a warning.
3. An unset `redis_max_memory` becomes 70% of the pod limit, written in bytes.

The sizing warning now fires above 70% of the limit, or below 35% of it.

**Why:** Rule 1 takes streams out of the eviction pool. Rule 3 fixes the flat 200mb. The fallback stops the case where `volatile-lru` has nothing it may evict and Redis rejects writes. The low-memory warning flags the exact jacBuilder misconfiguration (200mb in a 1Gi pod).

**Things to notice:**
- The old 2x rule assumed a BGSAVE fork. The PR says persistence is off, so this Redis never forks. You can't check that from the diff.
- The derived value is exactly `int(limit × 0.7)`, which is not `> limit × 0.7`, so the default does not warn. An existing test checks this.
- `_warn_on_memory_sizing` passes the derived value, a bare byte string like `"751619276"`, into `_parse_size_to_bytes`. The diff doesn't show whether that helper accepts plain numbers. If it returns `None`, the function returns early and silently skips the warning. That is harmless for derived values, but worth confirming.
- The `in-file` TTL default moved from 0 to 3600. That only matters when `db_config` lacks the key, as in tests with fake configs. The real config loader already defaults to 3600.
- An empty-string policy now falls through to the default because of the `or`.
- A user who explicitly sets `volatile-lru` together with `redis_default_ttl = 0` is also overridden to `allkeys-lru`.

**What:**
- Every publish now trims the stream to roughly `stream_maxlen` entries. A value of 0 disables trimming.
- On first connect, the broker reads the Redis eviction settings and warns if they are `allkeys-*` with a memory cap.
- `NOGROUP` is logged as an ERROR that says events were lost. The broker then retries up to 3 times, with a 50 ms backoff that respects stop, and finally re-raises.
- `health()` reports `evicted_keys`, `maxmemory` and `maxmemory-policy`.

**Why:**
- Trimming keeps streams bounded now that they can't be evicted.
- The startup warning covers Redis instances that jac-scale did not provision.
- The retries and the ERROR level answer the race in 3.3 and make loss visible.
- The health fields let monitoring see eviction.

**Things to notice:**
- **The trim ignores consumer progress.** This is Greptile's open P1. If a slow or offline group has not read the oldest entries, `MAXLEN ~` drops them anyway. That is a new, silent way to lose events, and it applies to every topic, not only `jc.run.*`.
- Approximate trim means the length stays at or above 100 in the test and well below 600, never exactly at the cap.
- `_eviction_settings` swallows errors with a debug log. If a managed Redis blocks `CONFIG GET`, the managed-Redis warning will never fire. Many hosted Redis services restrict `CONFIG`. The PR doesn't test against one.
- The ERROR message says "undelivered events are gone" every time it sees `NOGROUP`. That includes a stream that was never created yet, if that can happen. Whether `_ensure_group` normally prevents this can't be seen in the diff.
- `wait_or_stop` returning true makes `_read_group` return `None`. How callers treat `None` is not in the diff.
- `health()` now runs two more Redis commands per call.

## 10. Is it ready to merge?

**Not yet.**

1. The PR is closed and still a draft. It would have to be reopened, or the work moved to a new PR.
2. Greptile's P1 is unanswered. The trim is a new way to lose events, the same failure this PR exists to stop.
3. "Contribution Checks" and "Everything Passed" are failing.
4. The default `redis_memory_request` (128Mi) stays far below the new ≈717Mi cap. The PR says so itself, which leaves a node-eviction risk.
5. The PR says managed Redis gets a warning on connect, but that warning depends on `CONFIG GET`. Many managed services restrict `CONFIG`, and the code then stays silent.
6. Issue #7615 is already closed. Check whether another change fixed it before redoing this work.

**Before merging:**
- Answer the P1. Options: trim only `jc.run.*` streams, raise or scope the cap, trim by minimum ID based on group progress, or document the trade-off and test it.

## 11. Questions your senior might ask

**Q: Why `volatile-lru` instead of the issue's suggestion of keeping `allkeys-lru` and just sizing memory?**
Sizing only delays eviction. Under `allkeys-lru`, the idle stream is still the first key to go once Redis fills. `volatile-lru` takes streams out of the pool entirely. Your test table shows `allkeys-lru` losing the stream and `volatile-lru` keeping it under the same load.

**Q: How do you know cache keys have a TTL and streams don't?**
The PR description says so, and the default `redis_default_ttl` is 3600. The anchor write path is not in this diff. The tests simulate it with `SETEX`. You should point to the cache code before presenting.

**Q: What happens if all non-TTL data (streams plus control keys) fills `maxmemory`?**
Redis rejects writes, as in the "no ttl" test. Trimming bounds each stream's length, and the issue says only one run stream exists at a time. Nothing bounds the number of streams or the other no-TTL keys.

**Q: Doesn't trimming reintroduce event loss?**
Yes, for consumers lagging more than about 10000 entries. That is Greptile's open P1. Redis 7.2 `MAXLEN` has no "only acknowledged" option, so a fix would need per-topic caps, `MINID` based on group progress, or a documented limit.

**Q: Why write `maxmemory` in bytes?**
Redis accepts `mb`/`gb`, not the Kubernetes `Mi`/`Gi`. 0.7 × 1Gi is a fractional MiB value, so bytes is the safe choice.

**Q: Why drop the 2x BGSAVE headroom rule?**
The PR says persistence is off, so Redis never forks. Under the old rule, any `maxmemory` above 50% of the limit would warn, including the new 70% default. The new rule warns above 70%, or below 35% to catch the 200mb-in-1Gi case.

**Q: What does the user see on upgrade?**
The ConfigMap changes, so the Redis pod restarts once with a cold cache. The cap grows to about 717Mi on a 1Gi pod. Deployments with explicit `redis_max_memory` keep their size but still switch to `volatile-lru`, unless their TTL is 0.

**Q: Is 3 NOGROUP retries enough?**
It isn't meant to recover data. Once `NOGROUP` happens the events are gone, and the message says so. The retries reduce the "recreate then re-evicted" race, and the ERROR log plus `evicted_keys` in health make loss visible.

**Q: Why not raise `redis_memory_request` too?**
The PR leaves it out on purpose. Raising it changes what every cluster must reserve and could leave pods unschedulable. It is a real gap: a pod requesting 128Mi but using about 717Mi can be evicted by the node.

**Q: Does the startup warning work on ElastiCache or Memorystore?**
Only if `CONFIG GET` is allowed. Otherwise the error is logged at debug level and no warning appears. The PR has no test against a managed Redis.
