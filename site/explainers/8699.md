## 1. The short version

Jac Scale deploys a Jac app to Kubernetes. One deploy creates the app, a gateway, a Postgres database, some storage volumes and a namespace that holds them all. `jac scale destroy` is supposed to remove all of it.

**Before this PR, `destroy` deleted only objects matching `managed=jac-scale,jac-scale.role in (microservice,gateway)`. The Postgres StatefulSet, every PVC and the namespace itself survived.** The database kept running, the volumes kept billing (EBS on AWS), and the namespace stayed `Active`. `destroy` also ignored its `component` argument, so `--component database` ran a full teardown.

**You made namespace ownership something destroy can check. `ensure_namespace_exists` now stamps `jac-scale.jaseci.org/owned-by=<app>` on any namespace it creates. `destroy` deletes the namespace whole only when this app created it, no other app is in it, and monitoring teardown succeeded. In every other case it keeps the namespace and removes only this app's own objects, matching them by exact name or by owner label.** It also honours `component`, removes the external-database connection secret, scopes the RBAC sweep to the app, and logs a warning that names any co-tenant whose workloads were removed. A new real-cluster e2e runs on every scale PR.

**Status:** Merged on 2026-09-04. @MusabMahmoodh approved on 2026-08-26 and posted two more "commented" reviews afterwards. All CI checks on head `765ce3a` passed, including `test-scale-k8s`, which runs the new e2e.

## 3. The problem, step by step

### 3.1 The setup

- **Deploy** (`KubernetesTarget`, plus `DatabaseProvisioner`):
  - ensures the namespace exists;
  - creates the app and gateway Deployments, Services, Ingress, PodDisruptionBudgets and autoscalers;
  - creates the Postgres StatefulSet, its Service, Secret and ServiceAccount;
  - creates the PVCs (bundle, Postgres data, shared volumes) and the ops RBAC;
  - deploys monitoring, which owns cluster-scoped ClusterRoles.
- **Destroy** (`KubernetesTarget.destroy`) found objects to delete by label selector.
- **Creation and deletion disagreed about labels.** Postgres was labelled only `{'managed': 'jac-scale'}`, and its data PVC had no labels at all.

### 3.2 What went wrong

#### 3.2.1 Main bug: destroy leaks the database, volumes and namespace (#7968)

```text
1. deploy todo into ns "jb-x-todo"     → ns Active; Deployments todo, gateway (role labels);
                                          StatefulSet todo-postgres {managed: jac-scale};
                                          PVCs todo-bundles, todo-postgres-data-todo-postgres-0
2. destroy todo
3.   delete Deployments by FLEET_SELECTOR → todo, gateway gone
4.   autoscalers, PDBs, Ingress, Services, source ConfigMaps, monitoring → gone
5.   StatefulSet todo-postgres            → no jac-scale.role label → NOT MATCHED   ← WRONG
6.   PVCs                                 → no PVC call at all → still Bound       ← WRONG
7.   namespace                            → no namespace call → Active forever     ← WRONG
8.   destroy reports success; the caller deletes its record → leftovers are orphaned
```

#### 3.2.2 `component` was ignored

```text
1. user runs destroy with component="database"
2. old destroy() never reads component
3. full fleet teardown runs: app, gateway and monitoring removed     ← WRONG (asked for DB only)
4. database itself still not removed (see 3.2.1)
```

#### 3.2.3 The obvious fix ("call the parent teardown") would delete other teams' data

```text
1. user sets namespace = "production" (shared, already exists)
2. ensure_namespace_exists → adopt path; records nothing
3. parent teardown: delete_namespace("production"); its only guard is "skip if default"
4. "production" deleted with every other team's workloads             ← DATA LOSS
```

#### 3.2.4 Hazards found while building the fix (each became a review point or commit)

```text
a) Owner label naming only "jac-scale" (first cut)
   app A creates ns → label says jac-scale made it; app B adopts it
   destroy B → reads "owned" → deletes A's namespace                    ← DATA LOSS (fixed 617c914)

b) Label correct, but a co-tenant moved in later
   A creates ns (owned-by=A); billing adopts it (label stays A)
   destroy A → owned → namespace deleted with billing-postgres           ← DATA LOSS (fixed 040b4c5)

c) Unstamped namespace in practice
   DatabaseProvisioner calls ensure_namespace_exists FIRST, with no owner → ns created unlabelled
   later target call → adopt path → label never added
   destroy → reads "adopted" → namespace leaks again                    ← found by e2e (fixed d60c829)

d) PVCs matched by name prefix
   "uploads" shared volume has no prefix  → missed
   bundle created as k8s_safe_name("My_App")-bundles, matched as "My_App" → missed
   "todo-analytics-..." starts with "todo" → sibling app's PVC deleted   ← WRONG

e) Unowned shared volumes swept by "!jac-scale.owner" (one intermediate commit)
   A and B share ns, neither shared PVC labelled; A redeploys and gains a label
   destroy A → deletes B's unlabelled volume, silently                  ← DATA LOSS (fixed 8c574fa)

f) Monitoring failure logged at info, namespace deleted anyway
   ClusterRoles {ns}-{app}-prometheus stay, named after a namespace that is gone  ← untraceable leak

g) External DB secret <app>-external-db: nothing deleted it
   only a namespace delete collected it → in a kept namespace, live credentials remain
```

### 3.3 Why it mattered

- The issue reports the leak on EKS, in a dev cluster and in PR-preview environments. **Every destroy left one `Active` namespace, a running database pod and bound volumes**, one of them EBS, which bills until someone deletes it by hand.
- The caller (jacBuilder) deletes its record on a successful destroy, so nothing could find the leftovers afterwards. jacBuilder added its own `kubectl delete namespace` sweep as a workaround.
- jacBuilder's UI promised to "tear down the production namespace". Only the subdomain half was true.
- Cases 3.2.3 and 3.2.4(a, b, e) show that a careless fix would turn a leak into **data loss** in shared namespaces. That is why @MusabMahmoodh called the ownership question "a new data-loss path".

## 4. The idea of the fix (one sentence)

> **Record who created the namespace, and delete it only when nobody else is using it.** Every other object destroy removes is matched by exact name or by an owner label, never by a broad query.

Deleting the namespace removes the whole "this object lacked the right label" class of leaks at once. Gating that delete on recorded, per-app ownership plus a live co-tenant check is what keeps it from destroying data that belongs to someone else.

### 5.1 `utils/kubernetes_utils.jac` and `kubernetes_utils.impl.jac`: record and read ownership

```diff
         if (e.status == 404) {
+            create_labels: dict = dict(default_pss_labels());
+            if owner {

+impl namespace_is_owned(core_v1, namespace, owner) -> bool {
+    if (namespace == 'default') or not owner { return False; }
+    try { ns = core_v1.read_namespace(name=namespace); }
+    except ApiException as e {
+        if (e.status == 404) { return False; }
+        raise;                                                    # 503 etc. → fail loudly
```

- **What:** The create path now adds `owned-by=<owner>`. The adopt path is unchanged and does not add the label. `namespace_is_owned` returns true only when the label equals this app.
- **Why:** This answers 3.2.3 and 3.2.4(a). An adopted namespace can never read as owned, and a namespace created for app A never reads as owned by app B.
- **Things to notice:**
  - `default` is refused without reading the cluster.
  - Labels that read as `None` are treated as `{}`.
  - A 404 means "not owned", because there is nothing to reclaim.
  - Any other error is raised. An unreachable cluster must not be read as "adopted", or the leak would come back silently.
  - `owner` is required, but an empty string still creates an unstamped namespace because of `if owner`. The description says a new call site "cannot silently create an unstamped namespace". That holds against a missing argument, not against `""`.
  - @MusabMahmoodh praised the deliberate choice not to patch the label onto an adopted namespace in his approval. Patching would turn "adopted" into "owned" on the second deploy.

### 5.4 `target.jac`: the new `destroy()` decision

```diff
+        if component {
+            self._destroy_named_component(...);                # NEW: honour component
+            return;
+        }
+        self._destroy_fleet_workloads(namespace, apps_v1, core_v1, policy_v1, networking_v1);
+        monitoring_reclaimed = self._destroy_monitoring(app_name, namespace, apps_v1, core_v1);
+        owner: str = k8s_safe_name(app_name);
+        created_namespace: bool = namespace_is_owned(core_v1, namespace, owner);
+        co_tenants: list[str] = (
+            self._foreign_app_resources(app_name, namespace, apps_v1, core_v1)
+                if created_namespace else []
+        );
+        sole_tenant: bool = created_namespace and not co_tenants;
+        if sole_tenant {
+            if monitoring_reclaimed {
+                if self._reclaim_namespace(namespace, core_v1) { return; }   # whole ns gone
+                ...warning "Not permitted to delete namespace ..."           # 403 → fall through
+            } elif self.logger { ...warning "Keeping namespace ...: its monitoring RBAC ..." }
+        } elif co_tenants and self.logger {
+            ...warning "Keeping namespace ...: this app created it, but X belongs to another app"
+        } elif not created_namespace {
+            self._warn_co_tenant_workloads_removed(...);      # adopted path: name co-tenants
+        }
+        self._destroy_in_shared_namespace(app_name, namespace, apps_v1, core_v1, sole_tenant);
```

- **What:**
  1. A full destroy always removes the fleet first, then monitoring.
  2. It then deletes the namespace only if three things hold: this app created it, no foreign resources are inside, and monitoring teardown succeeded.
  3. Otherwise, it warns with the reason and removes only this app's objects inside the kept namespace.
- **Why:** This fixes 3.2.1 (reclaim), 3.2.2 (component), 3.2.3 and 3.2.4(a, b, f).
- **Things to notice:**
  - The co-tenant scan runs only when the namespace is owned. On the adopted path the namespace will be kept anyway, so the scan there is only used to write a warning (`_warn_co_tenant_workloads_removed`, which is best-effort).
  - The owned-path scan uses `_foreign_app_resources` directly, so a non-404 API error **raises**. That is the safe choice, because the result gates a namespace delete.
  - A 403 on the namespace delete no longer stops the destroy. It falls through to the in-place cleanup (commit 3a8a10a). Before that, the database and volumes stayed behind.
  - When this app is the sole tenant but the delete was refused, `sole_tenant=True` is passed down, so unlabelled shared volumes are also swept.

## 11. Questions your senior might ask

**Q: Why not just call the parent class's teardown, as the issue suggested?**
That teardown deleted any non-`default` namespace. `ensure_namespace_exists` adopts existing namespaces as readily as it creates them, so a shared `production` namespace would be deleted with other teams in it. The parent teardown is also gone now (#7709).

**Q: The namespace is labelled `owned-by=A`. Why isn't that enough to delete it?**
The label records who created the namespace, not who is in it now. A second app adopts it without changing the label. So destroy also scans for foreign bundle PVCs, foreign labelled shared volumes and foreign StatefulSets before deleting.

**Q: What happens to apps deployed before this release?**
Their namespaces have no owner label, so they take the kept path. The database, its secrets, the app PVCs and the RBAC are removed, and the namespace stays. Legacy shared volumes are kept and named in a warning.

**Q: Why gate the namespace delete on monitoring?**
Monitoring creates ClusterRoles named `{namespace}-{app}-...`. A namespace delete doesn't collect cluster-scoped objects. If monitoring teardown failed and the namespace went anyway, those roles would be orphaned with nothing left to trace them to.

**Q: Why not delete all PVCs with `managed=jac-scale`?**
- The Postgres data PVC comes from `volumeClaimTemplates` and has no labels.
- In a shared namespace that sweep would hit the co-tenant's volumes.

So app PVCs go by exact name and shared volumes go by owner label.

**Q: In a shared namespace, does destroying one app still hurt the other?**
Yes. The fleet sweep is still namespace-wide, so the co-tenant loses its Deployments, Services, Ingress, PDBs and autoscalers. Its data survives, and destroy now names it in a warning. A real fix needs a per-app label on those objects at creation, tracked as #8816.

**Q: What if the API server is unreachable during destroy?**
`namespace_is_owned` raises on any non-404 error, so destroy fails loudly instead of guessing "not owned". By then the fleet and monitoring are already removed, so a retry is needed.

**Q: Why did the mock tests pass while the namespace was still unstamped?**
They tested `ensure_namespace_exists` called with an owner. The real deploy first called it from `DatabaseProvisioner` with no owner, which created the namespace unlabelled. Only the e2e saw that, and it led to commit d60c829.

**Q: Does `--component database` break the running app?**
No. It removes the Postgres StatefulSet, Service, secrets, ServiceAccount and data PVC, but keeps the bundle PVC that the app pods mount. A unit test pins this.

**Q: Are raw `app_name` and `k8s_safe_name(app_name)` used consistently?**
Not everywhere:
- `k8s_safe_name` is used for the bundle name and the owner labels.
- The raw name is used for the Postgres names and the RBAC `app=` selector.

Whether that matches the creation side for names like `My_App` can't be confirmed from this diff. It is worth checking.
