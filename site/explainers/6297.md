## 1. The short version

jac-scale stores graph data in three layers. L1 is in-process memory. L2 is a Redis cache shared by all pods. L3 is MongoDB, which is the source of truth. When a node gains or loses edges, `MongoBackend._put_node_atomic` merges the change into MongoDB on the server side. That merge came from #5644.

**The bug: after the MongoDB merge, `ScaleTieredMemory.commit()` wrote the node's old, un-merged in-memory copy into Redis, so Redis could say a node had no edges while MongoDB had the edge.** In production on jac-builder, a user's `Root` had `data.edges = [<edge → UserProfile>]` in MongoDB and `data.edges = []` in Redis. As a result, `[-->(?:UserProfile)]` returned nothing. The `me` walker then created a duplicate profile, and other walkers returned "User profile not found." No error was raised.

**The fix: `_put_node_atomic` now writes and reads back the merged edge list in one MongoDB call, repairs the in-memory anchor, and deletes the Redis entry. `commit()` then skips the stale `l2.put()` for those anchors.** The next reader misses Redis and loads the correct edges from MongoDB.

Cross-pod L1 eviction, which the issue also asked for, was prototyped in this PR and then removed. It moved to #6313.

**Status:** Merged on 2026-06-01. All test checks on the head commit `d1f4e3f` passed. No reviewer review appears in the data, only two comments from you.

| jac-scale | A plugin that runs Jac apps on Kubernetes with many replicas (pods). |
| Pod | One running copy of the app. Production in the issue had 10. |
| L1 | In-process dict (`__mem__`). Per the author's comment, it lives per request and per pod. |
| L2 / `RedisBackend` | Redis cache shared by all pods. Keys look like `anchor:<id>`. It is on by default (`use_cache=True`, with no override). |

| `MongoBackend.sync()` | Writes changed L1 anchors to MongoDB. It used to return `None`. It now returns a `set` of IDs. |
| Edge-delta | Instead of overwriting the whole edge list, compute "added" and "removed" edges relative to a baseline (`_initial_edge_ids`) and send only those. This is safe when two pods write at once. |
| `_initial_edge_ids` | A `frozenset` of edge UUIDs: the node's edge set when it was loaded. It is the baseline for the delta. |
| `_put_node_atomic` | The MongoDB write for a node that applies the edge-delta on the server. **The fix lives mostly here.** |
| `$setUnion` / `$setDifference` | MongoDB set operators. The merge is `union(difference(current, removed), added)`, and it runs inside MongoDB. |
| `find_one_and_update` | A pymongo call that updates one document and returns it. With `ReturnDocument.AFTER`, it returns the version after the update. It is a write, so it runs on the primary. |
| `upsert=True` | Insert the document if it does not exist yet. |
| `projection={'data.edges': 1}` | Return only `data.edges` (plus `_id`) to keep the response small. |
| Primary / secondary / replica lag | A MongoDB replica set has one primary that takes writes and secondaries that copy it with a delay. A read from a secondary can show old data. |
| Invalidate | Delete a cache entry so the next read has to go to the source. `self._l2_ref.invalidate(anchor.id)`. |
| `_l2_ref` | MongoBackend's pointer to the Redis backend, set by `set_cache_ref`. |
| `_atomic_written` | A new set on `MongoBackend` holding IDs written by `_put_node_atomic` during the current `sync()`. |
| `by postinit` | Jac syntax: this field is set in `postinit()`, not by the constructor. |
| `_snapshot_field_hashes` | Records per-field hashes after a write, so the next commit only sends changed fields. Its body is not in the diff. |
| Find-or-create race (#6266) | Two walkers both see "no profile" and both create one. Empty L2 reads made this much worse. |

## 3. The problem, step by step

### 3.1 The setup

- **`ScaleTieredMemory.commit()`** in `memory_hierarchy.main.impl.jac` runs at the end of a request.
- **`MongoBackend.sync()`** loops over L1 anchors and writes the changed ones. Node edge changes go through `_put_node_atomic`.
- **`RedisBackend.put(anchor)`** serializes the in-memory anchor as-is, including its `edges`.
- The merge result existed only inside MongoDB. Nothing copied it back to the in-memory anchor or to Redis.

### 3.2 What went wrong: one edge write

```text
1. Mongo:  root.data.edges = []            Redis: (no key)
2. Request on pod A reads root → L1 miss, L2 miss, L3 hit
   → Redis now: anchor:root  edges = []
   → L1 anchor: edges = [], _initial_edge_ids = {}
3. Walker runs  root ++> UserProfile
   → L1 anchor: edges = [E1]
4. commit(): l2_pending = [root]                       (snapshot of dirty anchors)
5. l3.sync() → _put_node_atomic(root)
   → Mongo runs $setUnion(... , {E1})
   → Mongo: edges = [E1]  ✅
   → in-memory _initial_edge_ids still {}   (baseline not refreshed)
6. for anchor in l2_pending: l2.put(root)                ← WRONG STEP
   → Redis serializes the in-memory view, not the merged one; per the issue, Redis
     ends up with edges = [] ❌ while Mongo has [E1]
7. Next request (any pod) reads root from L2 → edges = []
   → [-->(?:UserProfile)] = []  → walker creates another UserProfile
```

The issue's reproduction shows this result: Mongo `edges.length = 1`, Redis `edges.length = 0`.

The issue describes the stale value as "the local writer's un-merged view." The diff alone does not show exactly why the in-memory list held `[]` at step 6 rather than `[E1]`. For example, the root may be re-loaded or the request may carry a different anchor copy. The observed end state, Mongo 1 versus Redis 0, comes from the issue's reproduction.

### 3.3 Second case: manual repair does not stick

```text
1. Operator runs  DEL anchor:root  in Redis   → Redis: (no key)
2. Any later request that touches root and commits
   → l2.put(root) writes the stale in-memory snapshot again  ← WRONG STEP
3. Redis: edges = [] again
```

### 3.4 Why it mattered

- Every edge traversal served from L2 could return a wrong or empty list, with HTTP 200 and no error.
- It turned #6266 into a loop. The issue reports 2 duplicate profiles per login, about 16 seconds apart, again and again.
- There was no mitigation. `use_cache` is hardcoded `True`, and turning it off needs a code change.

## 4. The idea of the fix (one sentence)

> **Invalidate, don't snapshot.** After MongoDB merges a node's edges, take the merged result from MongoDB, delete the Redis entry, and tell `commit()` not to write the stale copy back.

This matches the first option in issue #6295. Deleting the key is cheaper than writing the merged doc to Redis. It also cannot be wrong, because the next read fetches the real value from the source of truth.

## 5. Every code change, explained

### 5.1 `jac-scale/jac_scale/memory_hierarchy.jac`: declare the new field and return type

```diff
         put_count: int = 0;
+        put_count: int = 0,
+        _atomic_written: set by postinit;
 ...
-    # PersistentMemory-specific
-    def sync -> None;
+    def sync -> set;
```

**What:** `MongoBackend` gets a private `_atomic_written` set, created in `postinit`. `sync()` now declares that it returns a `set`.

**Why:** `commit()` needs to know which anchors were written atomically and already invalidated. Returning the set from `sync()` is the contract that tells it.

**Things to notice:** Only `MongoBackend.sync` changes type. Per the description, other backends such as `SqliteMemory` still return `None`. The caller handles that with `or set()`. The SQLite code is not in the diff, so this can't be confirmed from here.

(The diff above is trimmed. The real code builds `merged_ids` from `merged_doc.get('data', {}).get('edges', []) or []`.)

**What:**
1. The update and the read-back are now one MongoDB call that returns the merged `data.edges`.
2. The anchor ID is recorded in `_atomic_written`.
3. The Redis key is deleted.
4. The in-memory anchor is repaired. `_initial_edge_ids` becomes the merged set, and `anchor.edges` drops stubs that the server did not keep, for example because a sibling pod removed them.
5. The hash and field-hash bookkeeping continues as before. `_snapshot_field_hashes` is now in its own `try`.

**Why:** Steps 2 and 3 fix the stale Redis entry. Step 4 fixes the stale baseline, so the next `edge_delta()` on this pod is computed against the real post-merge state.

**Things to notice:**
- **Order matters.** Commit `ec164eb` ("invalidate L2 before post-write bookkeeping") moved invalidation in front of the read-back. A crash in the read-back can no longer skip the invalidation.
- **Replica lag.** Commit `a9adbac` first tried a separate `find_one` with `read_preference=PRIMARY`. The final code merges it into `find_one_and_update`, so there is no second round-trip.
- **Failure paths:**
  - If `find_one_and_update` itself raises, the outer `except` logs it. The ID is **not** added to `_atomic_written`, so `commit()` will still `l2.put()` that anchor's in-memory copy. That is the old behaviour, and it only applies when the Mongo write failed.
  - If `invalidate` raises, the ID **is** already in `_atomic_written`, so `commit()` skips the put. The pre-write Redis entry then stays as it was, with only a `debug` log.
- **The edge filter only removes.** It drops edges that the server did not keep. It does not add edges that siblings added on the server. So after a concurrent add, `_initial_edge_ids` can contain an edge ID that is not in `anchor.edges`. Whether that matters depends on how `edge_delta()` computes "removed." That code is not in the diff (see Q8).
- **`object.__setattr__`** sets `_initial_edge_ids` directly, which suggests the anchor class guards normal attribute setting. The class is not in the diff.

## 6. How execution flows after the PR

### 6.1 Committing a request (Mongo + Redis)

```text
ScaleTieredMemory.commit()
├─ l2_pending = dirty anchors with write access
├─ atomic_ids = self.l3.sync() or set()                         ← CHANGED
│   └─ MongoBackend.sync()
│       ├─ no _mem_ref / client → return set()                  ← CHANGED (was None)
│       ├─ _atomic_written = set()                              ← NEW
│       ├─ for each persistent changed anchor:
│       │   ├─ node edge-delta path → _put_node_atomic (6.2)
│       │   └─ other paths (not visible in diff) → unchanged
│       └─ return _atomic_written                               ← NEW
└─ if self.l2:
    └─ for anchor in l2_pending:
        ├─ anchor.id in atomic_ids → skip                       ← NEW
        └─ else → l2.put(anchor)
```

### 6.2 `_put_node_atomic(anchor)`

```text
_put_node_atomic
├─ build set_doc (dirty fields + $setUnion/$setDifference edge merge)   (unchanged)
├─ merged_doc = find_one_and_update(..., AFTER, projection data.edges)  ← CHANGED
├─ _atomic_written.add(anchor.id)                                        ← NEW
├─ _l2_ref.invalidate(anchor.id)   (try; debug log on failure)           ← NEW
├─ try: read-back                                                        ← NEW
│   ├─ _initial_edge_ids = frozenset(merged ids)
│   └─ anchor.edges = only stubs whose id is in merged ids
├─ anchor.hash = compute_hash
├─ pop __jac_dirty_fields__
└─ try: _snapshot_field_hashes                                           ← CHANGED (wrapped)
```

### 6.3 Next read of that node

```text
mem.get(root_id)
├─ L1 miss
├─ L2 miss (key was invalidated)                                ← effect of NEW step
└─ L3 hit → edges = [E1] → re-populates Redis with merged edges
```

The test shows that a tiered read writes the result into Redis, through `_raw_after_read`.

### 6.4 Backend without the atomic path

```text
commit() → sync() returns None → `or set()` → empty → every pending anchor is put into L2, as before
```

| Scenario | Before | After |
|---|---|---|
| Single edge write, same pod | Mongo `[E1]`, Redis `[]` | Mongo `[E1]`, Redis key absent; next read loads `[E1]` |
| `DEL anchor:<id>` by an operator | Re-poisoned on the next commit | Stays deleted unless a non-atomic path writes it |
| In-memory baseline after a write | `_initial_edge_ids` = pre-commit set | = merged set from Mongo |
| Sibling pod removed an edge concurrently | Local `anchor.edges` still holds it | Local stub dropped |
| Sibling pod L1 copies | Stale | Still stale (deferred to #6313) |
| Backend returns `None` from `sync` | Puts all pending | Puts all pending (unchanged) |

**Behaviour change users will notice:** After a node edge write, that node's Redis key disappears until the next read. The Redis key count after a write is one lower for each such node, which is why the existing test changed from 6 to 5. The first read after the write costs one extra MongoDB round-trip.

## 11. Questions your senior might ask

**Q: Why invalidate Redis instead of writing the merged value into it?**
Invalidation is cheaper and always correct, because the next read loads from Mongo, the source of truth. The issue listed write-through as a "higher-cost alternative." The cost is one extra Mongo read on the first access after a write.

**Q: Why `find_one_and_update` instead of `update_one` followed by `find_one`?**
It is one round-trip, and as a write it runs on the primary and returns the post-merge document. A separate read could hit a lagging secondary. Commit `a9adbac` tried forcing `PRIMARY` on a separate `find_one`, and the final version folds it into the write.

**Q: Why return the ID set from `sync()` instead of having `commit()` read `l3._atomic_written`?**
It keeps the field private. It also avoids `isinstance` checks on the backend type, and other backends work unchanged by returning `None`.

**Q: What if the Redis invalidation throws?**
It is caught and logged at `debug`. The ID is already in `_atomic_written`, so `commit()` skips the put. Redis keeps whatever it had before the write, which could be stale, until something else replaces it.

**Q: Does this fix multi-pod deployments fully?**
No. It fixes L2 and the writing pod's L1. Sibling pods' in-memory copies are not evicted, and that is #6313. A pub/sub version was built in this PR and removed in `681c743` because of thread-lifecycle and self-message concerns.

**Q: Why did the Redis count in the "write cycle" test drop from 6 to 5?**
The parent node's key is now deleted after its edge write instead of being rewritten. It comes back on the next read.

**Q: Why is the test's Redis assertion inside `if l2_raw is not None`?**
It accepts either "invalidated" or "holds the correct merged edges," so it checks the property (never stale) rather than the mechanism. It does not strictly prove that the key was deleted.

**Q: After a concurrent add by another pod, `_initial_edge_ids` includes that edge but `anchor.edges` doesn't. Could the next delta remove it?**
The filter only removes stubs and never adds sibling-added edges. If `edge_delta()` computes "removed" as `_initial_edge_ids − current edge ids`, a second commit of the same anchor in the same L1 lifetime could send a removal for the sibling's edge. `edge_delta()` is not in the diff, so this needs checking against its code. Per your comment, L1 lives per request, which limits the window.

**Q: Does the SQLite path change?**
Per the description, no. `sync()` returns `None` there, and `or set()` makes every anchor be cached as before. The SQLite code is not in the diff.

**Q: Was the merge pipeline itself changed?**
