## 1. The short version

`jac-scale` serves each HTTP request statelessly. For every request it builds a fresh execution context on top of three storage tiers: L1 (in-process), L2 (Redis) and L3 (MongoDB). Two older performance bugs once made every request do extra MongoDB work:

1. Each request opened a new MongoDB connection just to check that the database was reachable.
2. Each request re-read the system root node, which never changes.

Both bugs were fixed in the product some time ago. The test `test_connection_overhead.jac` was not updated. **The test still asserted that the old bugs were present, for example "expected >= 8 new connections", so it failed once CI started auto-discovering tests (#6850) and was moved to `tests/quarantine/`.** Its second check also measured the wrong thing. It counted all MongoDB queries (40 for 10 requests), not system-root reads specifically.

**You rewrote the test so it guards the correct behaviour.** The connection check now requires at most 1 new MongoDB connection over 10 requests. The system-root check now turns on MongoDB's server-side profiler and requires 0 `find`s for the system root `_id` after warm-up. Both tests have "non-vacuity" checks so they cannot pass just because nothing happened. The file now lives in `tests/data/`. No product code changed.

**Status:** Merged on 2026-08-03. @kugesan1105 reviewed it as "commented" and called it "the right approach and looks good to merge". All of that reviewer's inline points were addressed in `c377a08`. All CI checks passed or were skipped (release jobs).

## 3. The problem, step by step

### 3.1 The setup

- A real `jac start` server runs the fixture app `race_app.jac` against a real MongoDB in Docker.
- A test user registers, gets a token, and calls the `ListItems` walker repeatedly.
- The test observes MongoDB from outside: connection counters and (in test 2) the profiler.
- Product side (from the PR text and review, not in this diff):
  - `MongoBackend` shares one `MongoClient` through `_process_cache` and caches `is_available()`.
  - `JScaleExecutionContext.init` seeds the cached system root into L1.

### 3.2 What went wrong

#### Case 1: connection probe check asserted the old bug

```text
1. Long ago: each request ran is_available() with a throwaway MongoClient
   -> 10 requests = ~10 new connections
2. Old test written to PROVE that bug: assert new_connections >= 8
3. Product fixed: shared client in _process_cache + cached probe
   -> 10 requests = 0 new connections
4. Test not updated; still asserts >= 8                          <-- WRONG
5. #6850 turns on auto-discovery -> test runs in CI
   FAIL: AVAILABILITY PROBE: 10 requests created 0 new MongoDB connections (expected >= 8)
6. Test moved to tests/quarantine/, issue #6862 opened
```

#### Case 2: system-root check measured the wrong thing

```text
1. Long ago: each request re-read the system root from MongoDB
2. Old test measured TOTAL MongoDB queries for 10 read-only requests
3. Product fixed: system root cached per process, seeded into L1
4. Reality per request (measured with the profiler, 4 queries):
     users             (user lookup / JWT)
     _anchors_aliases  (alias preload)
     _anchors_quarantine (quarantine check)
     _anchors _id=<user's own root>
   system root finds = 0
5. Old test sees 40 queries (4.0/request) and fails                <-- WRONG measure
   FAIL: COLD SYSTEM ROOT: 10 read-only requests issued 40 MongoDB queries total
6. Issue #6862 read this as "a real, still-present perf issue"     <-- misreading
   Your profiling showed none of the 4 reads is the system root
```

### 3.3 Why it mattered

- The quarantined test gave no protection. Both performance fixes had no live regression guard. @kugesan1105 notes that "the connection-reuse path had no other coverage at all". `test_memory_hierarchy.jac` only checks `_process_cache['system_root']` in-process (white-box), not through real HTTP requests.
- The failing test was misleading. #6862 suggested case 2 might need a product fix. Your profiling showed it does not.
- Without a guard, a future change could quietly add back a per-request Mongo connection or system-root read. That would cost latency and throughput on every request.

## 4. The idea of the fix (one sentence)

> **Invert the test from "prove the bug exists" to "prove the bug stays gone", and make each zero provable.** Each check now asserts the efficient behaviour (≤1 new connection, 0 system-root finds), and each first asserts that real work was observed.

This is the right idea because the product is already correct. The only gap was a guard that fails on regression and cannot pass by accident. @kugesan1105 notes it matches the pattern the testing-trophy migration (#7628) established.

## 5. Every code change, explained

There is **no production code, release-note or docs change** in this PR. The only file is a new test file. Its two `test` blocks are explained in section 7. This section covers the helper functions at the top of that file, because they are the measuring tools the tests depend on.

### 5.1 `jac/jaclang/scale/tests/data/test_connection_overhead.jac`: measurement helpers

```diff
+glob FIXTURES_DIR = Path(__file__).parent.parent / "fixtures",
+     JAC_FILE = FIXTURES_DIR / "race_app.jac";
+
+def mongo_total_created(client: MongoClient) -> int {
+    status = client.admin.command("serverStatus");
+    return int(status["connections"]["totalCreated"]);     # NEW: server-wide connection counter
+}
+
+def profiled_filter_ids(doc: dict) -> set {
+    raw = (doc.get("command") or {}).get("filter", {}).get("_id");
+    if isinstance(raw, dict) {
+        return {str(v) for v in (raw.get("$in") or [])};     # NEW: handles batch $in reads
+    }
+    return {str(raw)} if raw is not None else set();        # NEW: handles _id == x
+}
+
+def count_profiled_anchor_finds(client, since, id_filter = None) -> int {
+    query = {"ts": {"$gte": since}, "ns": "jac_db._anchors", "op": "query"};
+    docs = list(client["jac_db"]["system.profile"].find(query));
+    if id_filter is None { return len(docs); }              # all _anchors finds
+    matched = [d for d in docs if id_filter in profiled_filter_ids(d)];
+    return len(matched);                                     # finds for one _id
+}
+
+def user_root_anchor_id(client, username) -> str {
+    user = client["jac_db"]["users"].find_one({"identities.value_normalized": username});
+    assert user is not None , ...;
+    return str(UUID(cast(str, user["root_id"])));            # canonical uuid string
+}
```

**What:**
- `mongo_total_created` reads MongoDB's lifetime connection count.
- `count_profiled_anchor_finds` reads profiler entries for `_anchors` queries since a timestamp. It either counts all of them or only those that filtered on one `_id`.
- `profiled_filter_ids` pulls the `_id` values out of a profiled query and turns them into strings. It handles both `{_id: x}` and `{_id: {$in: [...]}}`.
- `user_root_anchor_id` looks up the test user's root id and turns it into a canonical UUID string.

**Why:**
- The old check counted all queries. These helpers let the test count system-root reads only.
- They also let the test prove the counting itself works.

**Things to notice:**
- The `_id` matching moved out of the server-side profiler query into the Python helper in `c377a08`. You explained why: the old version would have counted zero if a read ever moved to the batch `$in` path. That was a second way the guard could go quiet.
- `user_root_anchor_id` was added in response to @kugesan1105's hardening idea (see 9.2).
- The user-root id is normalised (`str(UUID(...))`). `Con.SUPER_ROOT_UUID` is passed in as-is. The guard only works if that constant is a string in the same form as `str()` of the stored `_id`. This diff does not show its type. If it were a `UUID` object, `id_filter in {strings}` would always be false. See section 11.
- The fixture app `race_app.jac` and the `server_support` helpers are not in this diff. Their behaviour is assumed from how they are used.

### 5.2 The "move" out of quarantine

There is no deletion hunk in the diff. Only the add is shown. As @kugesan1105 points out, #7628 already removed `tests/quarantine/test_connection_overhead.jac` from `main` after your branch was cut. ### 7.1 `jac/jaclang/scale/tests/data/test_connection_overhead.jac`

**Test 1: "authenticated requests reuse the pooled MongoDB connection"**
- **Sets up:** a fresh Mongo container, a real `jac start` server, one registered user, and one warm-up call.
- **Checks:**
  - All 10 `ListItems` calls returned a walker report.
  - MongoDB's `totalCreated` grew by at most 1.
- **Proves:** requests reuse the shared `MongoClient` and the cached `is_available()`.
- **Why 1 and not 0:** the comment says one pooled top-up or keep-alive reconnect is tolerated. A per-request probe would add about one connection per request, so 1 out of 10 still clearly separates good from bad.

**Test 2: "system root is served from process cache, never re-fetched from MongoDB"**
- **Sets up:** same as test 1, then turns on full profiling after warm-up.
- **Checks, in this order:**
  1. At least 10 `_anchors` finds were captured. This proves the profiler is live.
  2. At least 10 finds matched the user's own root id. This proves the `_id` matching works on real traffic.
  3. Exactly 0 finds matched the system root id.
- **Proves:** the system root comes from L1 cache after warm-up.
- **Note:** check 1 is now implied by check 2, because user-root finds are a subset of all `_anchors` finds. It is harmless, and it gives a clearer error message if profiling itself is off.

**Why per-test containers instead of a shared one:**
- Sibling tests share one container through `_get_mongo()`.
- Here, `totalCreated` and db-wide profiling would pick up noise from other tests.
- You added a comment in both tests saying so, at @kugesan1105's request.

**Regression demo (from the description):** you disabled cache seeding in `context.impl.jac`, and test 2 failed with 10 finds, then passed again after you reverted. The description does not say whether you repeated this after the `c377a08` helper refactor.

## 11. Questions your senior might ask

**Q: Did this PR change any product behaviour?**
No. It adds one test file. The fixes it guards (shared `MongoClient` with cached `is_available()`, and `_process_cache['system_root']` seeded into L1) shipped earlier.

**Q: The issue said the system-root problem looked real. Why didn't you fix the product?**
You profiled MongoDB over 10 requests. The 4 queries per request were the user lookup, alias preload, quarantine check and the user's own root. System-root finds were 0. The old test counted total queries, so it confused legitimate reads with system-root reads.

**Q: Why allow 1 new connection instead of 0?**
To tolerate a pool top-up or keep-alive reconnect without flaky failures. A per-request probe would add about 10 connections over 10 requests, so a limit of 1 still catches the regression clearly.

**Q: How do you know a "0" isn't just the test seeing nothing?**
- Test 1 asserts all 10 calls returned a walker report.
- Test 2 asserts the profiler captured at least 10 `_anchors` finds, and at least 10 matched the user root through the same `_id` filter. Only then does it trust 0 system-root finds.

**Q: Is the system-root comparison itself safe? You normalise the user root id but not `SUPER_ROOT_UUID`.**
It relies on `Con.SUPER_ROOT_UUID` being a string like `00000000-0000-0000-0000-000000000000`. The PR's error output prints it in that form, but its type is not visible in this diff. It is worth confirming, and re-running the disable-seeding demo on the final code.

**Q: Why not reuse the shared Mongo container like `test_memory_hierarchy.jac`?**
`totalCreated` is server-wide and the profiler is database-wide. Traffic from other tests would skew both counts. The in-code comment says so to stop someone consolidating them later.

**Q: Could clock differences break the `since` timestamp filter?**
`since` comes from the test process clock. The profiler's `ts` comes from the Mongo container. Both run on the same host here, so in practice they agree. The test also sleeps 0.3s after warm-up before setting `since`, which limits overlap with warm-up reads.

**Q: Why handle `$in` filters?**
If a future change loads the system root through a batch `{_id: {$in: [...]}}` read, an equality-only match would count 0 and hide the regression. `profiled_filter_ids` counts both forms.

**Q: What happens if setup fails halfway, for example the server never starts?**
Everything after creating the container object is inside `try`. `finally` closes the client, terminates the server if it exists, turns profiling off if it was on, restores `MONGODB_URI`/`REDIS_URL`, stops the container and deletes the data dir. This was fixed after Greptile's P1 comment.

**Q: Is this test redundant with `test_memory_hierarchy.jac`?**
According to @kugesan1105, no. That file checks the cache white-box, in-process. This one checks real HTTP requests against a real MongoDB. The connection-reuse path had no other coverage.
