## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. When the sealed app boots, jac reads that file to learn which endpoints exist and who may call them. The file's layout has changed twice: #9088 added a `module_manifests` table, and #9355 added `surface`.

**The file never said which layout it used, so a bundle sealed by one jac generation and booted by another either crashed with an unrelated error (`Error loading main.jac: 'module_manifests'`) or booted with endpoints silently missing.** The two readers of the file also disagreed. `_prepare_sealed` crashed, while `serve_manifest_for` quietly returned `None`.

**You now stamp the file with `format: 3` and the building `jaclang_version`, and you route both readers through one new function, `read_serve_manifest()`. That function refuses any other format with one sentence naming both sides and telling the user to rebuild.** Only the format number decides refusal. The version is only there to make the message useful. A test pins the manifest's key layout to format 3, so a layout change without a decision fails CI.

**Status:** Open. @MusabMahmoodh approved twice (2026-09-24 and 2026-10-09), but his second approval came before your last two real commits (3486cb5, dc8ab31). The head commit 4378118 is **failing CI**: `test-compiler (toplevel)`, `jac-check` and the `Everything Passed` gate. An open Greptile P1 comment from 2026-10-12 says the recorded shape in your test is stale, and it is the likely cause of the toplevel failure.

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `dist/seal.jac build_serve_manifest()` produces the dict that is saved as `.jac/serve_manifest.json`.
- **Reader 1:** `compiler/driver/application.jac _prepare_sealed()` runs at boot. It did `json.loads(...)` and then indexed `manifest['module_manifests']`.
- **Reader 2:** `server/sealed_serve.jac serve_manifest_for()` does per-module lookup. It did `data.get('module_manifests', {}).get(relative)` and swallowed every error into `None`.
- Neither reader checked any version or format, because there was none to check.

### 3.2 What went wrong: flat (pre-#9088) bundle on a newer runtime

```text
1. jac 0.37.11: `jac build --as jab` writes flat serve_manifest.json   { "app": ..., "client": ..., ... }  (no module_manifests, no format)
2. Bundle is deployed to a pod running jac 0.37.12+
3. _prepare_sealed reads the file, json.loads OK
4. manifest['module_manifests']  → KeyError                             ← WRONG: no check, unrelated exception
5. Log: "Error loading main.jac: 'module_manifests'", exit 1, crash-loop
```

@kugesan1105 reproduced this on the real 0.37.12 release.

### 3.3 What went wrong: bundle missing `surface` (pre-#9355)

```text
1. jac 0.37.21 (before #9355) seals: module_manifests present, no `surface`, no format
2. Newer runtime boots it; _prepare_sealed finds module_manifests → no error
3. Server starts "ready"
4. Endpoint discovery finds no surface entries → /walkers is empty              ← WRONG: silent
5. POST /walker/X → 405; nothing in logs
```

The PR description says #9369 now catches this case later, at server start. Your fix catches it immediately, at read time.

### 3.4 What went wrong: the two readers disagree

```text
1. Same flat file as 3.2
2. _prepare_sealed → KeyError (crash)
3. serve_manifest_for → data.get('module_manifests', {}) → {} → .get(rel) → None   ← WRONG: same file, opposite verdict
4. Bad JSON or a non-dict file → also None silently
```

### 3.5 Why it mattered

- The issue (#9140) explains that every jachammer deploy seals with builder-sv's own jac-scale (0.34.x). That bundle then lands on pods running a different jac. Skew is the normal case, not an edge case.
- The 0.37.11 scale deploys never wrote the file. They failed with `FileNotFoundError`. That case keeps #9233's "no serving manifest" message and has its own fix in #9138.
- @kugesan1105 confirmed the crash on a real 0.37.11 `.jab` booted on 0.37.12.
- The errors never said "your bundle and runtime are different generations", so operators could not tell what to do.

## 4. The idea of the fix (one sentence)

> **Stamp the file with a layout number and gate every read on it.** The writer records `format: 3` plus the jac version, and one shared reader refuses any other format with a sentence that says rebuild.

A layout number changes only when the file's layout changes. That makes it neither too strict, like a jac version or compiler digest that changes on unrelated edits, nor too loose, like a digest that doesn't cover `seal.jac` or `sealed_serve.jac`. A shape test covers the weak spot of a hand-bumped number, which is that people forget to bump it.

**What:** You add the format constant. You add `serve_manifest_stamp()`, which builds the stamp the writer uses and which the reader also uses to name the running version. You add `read_serve_manifest()`, which owns the missing-file error and the new format error. `serve_manifest_for` now goes through it.

**Why:** These fix 3.2, 3.3 and 3.4. Any unknown layout now produces one clear refusal, from either reader.

**Things to notice:**
- The version comes from `resolve_cli_version()`, so it is correct under `JAC_DEV_SOURCE`. This was Greptile's P2, fixed in 3486cb5. The import is lazy, inside the function.
- @MusabMahmoodh's first review praised *not* importing from `compiler/driver/jir.jac`, because #9369 came from a server module reaching into the compiler. The current version imports from `jaclang.cli.manifest_route` instead. He has not commented on that import since 3486cb5.
- The two readers still differ on a **missing** file. `serve_manifest_for` checks `isfile` first and returns `None`. `_prepare_sealed` raises. They now agree only on wrong formats and bad JSON.
- `serve_manifest_for` returns the in-memory `prepared_manifest` first, so a booted app's lookups never hit the format check.
- **Behaviour change:** invalid JSON now raises from `serve_manifest_for` instead of returning `None`. Note that `json.loads` raises `JSONDecodeError`, which is a `ValueError`, not the `RuntimeError` used for the other cases.
- A non-dict file, such as a JSON list, is treated as unstamped and refused.
- A file with `format: 3` but no `module_manifests` would still `KeyError` in `serve_manifest_for`. The format promises the key is there.
- If `format` is present but `null`, the message prints `format None`.

## 6. How execution flows after the PR

### 6.1 Sealing a bundle

```text
jac build / jac-scale deploy
└─ build_serve_manifest(entry_file, proj_root)
   ├─ prepare application, collect manifests
   ├─ build result + result['module_manifests'] = {rel_path: record, ...}
   ├─ result.update(serve_manifest_stamp())                      ← NEW
   │   └─ resolve_cli_version()  (falls back to "0.0.0")         ← NEW

```

### 6.2 Booting a sealed app

```text
jac run --serve main.jac (sealed image)
└─ _prepare_sealed(entry, program, image_root, entries)
   ├─ check _precompiled artifact manifest (unchanged)
   ├─ read_serve_manifest(image_root)                            ← CHANGED (was inline read)
   │   ├─ file missing?        → RuntimeError "no serving manifest" (same text)
   │   ├─ json.loads           → bad JSON raises
   │   ├─ format != 3?         → RuntimeError "built by ... format N; this runtime reads 3. Rebuild..."  ← NEW
   │   └─ return dict
   ├─ manifest['root'] = image_root
   └─ build PreparedApplication ...
```

```text
serve_manifest_for(path)
├─ prepared_manifest(path) not None? → return it (no file read)
├─ sealed_root_for(path) is None or file missing → return None  (unchanged)
└─ read_serve_manifest(img_root)['module_manifests'].get(relative)   ← CHANGED

```

## 11. Questions your senior might ask

**Q: Why not refuse on `compiler_digest` or the jac version?**
The digest doesn't hash `seal.jac`, `sealed_serve.jac` or the scale packer, so a layout change there would slip through. It would also refuse every app on any compiler change. The version is identical across all dev builds of `main`, which is how #9355 slipped through, and it would force a rebuild on every patch release.

**Q: Why start at 3, not 2 as the issue suggested?**
#9355 already changed the layout a second time (adding `surface`). So flat = 1, `module_manifests` = 2, `surface` = 3.

**Q: What stops someone from forgetting to bump it?**
The writer test compares the manifest's key sets to `SERVE_MANIFEST_SHAPES[3]` and fails with a "bump or record" message. Right now it is failing for the wrong reason: the fixture is stale after `_portable_manifest`.

**Q: If `_portable_manifest` removed `root` and surface `module`, doesn't your own rule say bump to 4?**
No stamped bundles have shipped yet, because the stamp only exists in this PR. Every older bundle is unstamped and refused anyway. Format 3 can therefore just describe the current portable shape. Also, `_prepare_sealed` re-sets top-level `root` at read. Whether readers need module-level `root` or surface `module` can't be told from this diff.

**Q: Does `persistence` (#9375) or the #9848 surface fields need a bump?**
No. `persistence` is read with `.get('persistence', ())`. @MusabMahmoodh checked that the #9848 fields are optional on read and that older `SurfaceEntry.from_dict` ignores unknown keys.

**Q: Do both readers now behave identically?**
For a wrong format or bad JSON, yes: both raise. For a missing file, no: `serve_manifest_for` still returns `None`, while boot raises the "no serving manifest" error. Lookups also return the in-memory `prepared_manifest` without touching the file.

**Q: Who gets newly blocked?**
Dev bundles sealed from `main` after #9355 but before this lands. Released older bundles were already failing other checks, according to the description. All of them just need a rebuild.

**Q: Why does a server module now import from `jaclang.cli`? Isn't that the #9369 smell?**
It's a lazy import of `resolve_cli_version`, chosen so the stamp matches `jac --version` under `JAC_DEV_SOURCE` (Greptile's P2). It avoids the compiler, which was @MusabMahmoodh's specific concern. He hasn't explicitly reviewed this newer import.

**Q: Why are `jac-check` and the toplevel lane red?**
The toplevel failure is very likely the stale shape fixture (Greptile P1). The `jac-check` cause isn't visible from the PR material and needs the log.

**Q: What about the pack side, so a bundle can't ship without a serve manifest?**
Out of scope here. That is #9138.
