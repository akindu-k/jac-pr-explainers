## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. That file lists the app's modules, endpoints and access rules. When a sealed app boots, jac reads the file to decide what to serve. Two places read it: `_prepare_sealed()` in the compiler driver, and `serve_manifest_for()` in the server.

**The file never said which layout it used, so a bundle sealed by one jac and booted by another either crashed with an unrelated error such as `Error loading main.jac: 'module_manifests'`, or booted with endpoints silently missing.** The layout had changed twice: once in #9088, which added the `module_manifests` table, and once in #9355, which added `surface`. The two readers also disagreed. One crashed on an old layout, and the other quietly returned `None`.

**You now stamp the file with `format: 3` and the jac version at seal time, and both readers go through one new function, `read_serve_manifest()`. That function refuses any bundle whose format is not 3, with one sentence naming both sides and telling the user to rebuild.** Only the format number decides whether a bundle is refused. The version is there to make the message useful. A test compares the manifest's key layout to a recorded layout, so a forgotten bump fails CI.

**Status:** Open. @MusabMahmoodh approved three times; the latest approval is from 2026-10-13. All CI checks on head `57b73de` pass. The head commit (2026-10-20) is newer than the last approval, but the commits since then are only merges from `main` and an archwire layout tidy-up.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. It compiles to Python bytecode, and the runtime serves Jac walkers as HTTP endpoints. |
| Walker / endpoint | A Jac walker can be exposed as an HTTP route, e.g. `POST /walker/Hi`. `/walkers` lists them. |
| Sealing ("seal") | Building an app into a deployable bundle with precompiled code, so the pod doesn't compile at boot. The code is in `dist/seal.jac` and `dist/impl/seal.impl.jac`. |
| Bundle / `.jab` / image | The sealed output. A `.jab` is a packed bundle. The "image root" is the folder the bundle is unpacked into. |
| `_precompiled/MANIFEST.json` | A sibling file in the bundle. It already carries a `format` number, and the runtime checks it (`MANIFEST_FORMATS_ACCEPTED`). It was the model for this fix. |
| Serve manifest (`.jac/serve_manifest.json`) | JSON written at seal time that says what to serve: `module_manifests`, `surface`, `client`, and so on. Its path is the constant `SERVE_MANIFEST_REL`. **This is where the bug is.** |
| `module_manifests` | A table inside the serve manifest, keyed by project-relative path (e.g. `"main.jac"`). Added in #9088. Before that, the file was one flat dict. |
| `surface` | Per-module entries describing exposed endpoints (route, access, kind, …). Added in #9355. |
| Layout / shape | The set of key names at each level of the file. The test records it as `{'manifest': {...}, 'module': {...}, 'surface': {...}}`. |
| Generation skew | The bundle was made by one jac "generation" and run by another, with nothing checking the boundary. Issue #8753 named this class of bug. |
| `SERVE_MANIFEST_FORMAT` | New constant, value `3`. It is the layout number the running jac writes and accepts. **This is what the PR adds.** |
| `serve_manifest_stamp()` | New. Returns `{'format': 3, 'jaclang_version': <version>}`. |
| `resolve_cli_version()` | Existing function in `cli/manifest_route`. It gives the jac version and is source-aware (it handles running from a dev checkout). |
| `read_serve_manifest(img_root)` | New. It is now the single reader. It raises on a missing file or a wrong format, and otherwise returns the parsed dict. |
| `serve_manifest_for(path)` | Existing server helper. It returns the manifest record for one module, or `None`. |
| `_prepare_sealed()` | Existing compiler-driver step that loads a sealed app at boot. |
| `build_serve_manifest()` | Existing seal step that writes the serve manifest. |
| `archwire.jac` | From the diff, a central file that declares which module imports which names, in a `graph import { a ++> [b { name }] }` style. New imports must be wired here. |
| Bump | Raising `SERVE_MANIFEST_FORMAT` when old readers can no longer read the new layout. |
| `compiler_digest` | A hash of the compiler's input files, stored in `_precompiled/MANIFEST.json`. It was proposed as an alternative check and rejected. |

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `build_serve_manifest()` writes `.jac/serve_manifest.json` during sealing.
- **Reader A:** `_prepare_sealed()` reads it at boot and indexes `manifest['module_manifests']` directly.
- **Reader B:** `serve_manifest_for()` reads it during serving with `data.get('module_manifests', {}).get(relative)`. It returns `None` on anything odd.
- **Nothing in the file** said which layout it was. Compare `_precompiled/MANIFEST.json`, which has had a `format` since #7135.

### 3.2 What went wrong: old flat-layout bundle (pre-#9088)

```text
1. jac 0.37.11: `jac build --as jab` writes serve_manifest.json as ONE FLAT dict (no 'module_manifests')
2. Bundle is unpacked on a pod running jac 0.37.12
3. Boot → _prepare_sealed() → json.loads(file) → manifest = {flat keys...}
4. manifest['module_manifests']                       ← WRONG: KeyError
5. Output: "Error loading main.jac: 'module_manifests'"; exit 1; pod crash-loops
```

@kugesan1105 reproduced this exactly on the 0.37.12 release.

### 3.3 What went wrong: bundle missing `surface` (between #9088 and #9355)

```text
1. jac 0.37.21 bundle: has 'module_manifests', but module records have no 'surface'
2. Boot on newer jac → _prepare_sealed() finds 'module_manifests' → no error
3. Server comes up "ready"
4. Endpoint lookup finds no surface entries               ← WRONG: silent
5. /walkers is empty; calling an endpoint returns 405; nothing in the logs
```

Your description says this case is partly caught later by the #9369 check at server start. It also says one path was not caught at all. The diff doesn't show which path is which.

### 3.4 What went wrong: the two readers disagree

```text
Same flat file:
  Reader A (_prepare_sealed)    → KeyError (crash)
  Reader B (serve_manifest_for) → .get('module_manifests', {}) → None (quietly "no manifest")
                                  ← WRONG: same input, different verdicts
```

### 3.5 Why it mattered

- Issue #9140: jachammer deploys sealed bundles with builder-sv's own jac-scale (0.34.x), while pods run newer jac. Every mismatch showed up as an unrelated exception with a crash-loop, and nothing told the user "rebuild with the jac that runs it."
- The silent case is worse. A "healthy" app serving nothing.
- #9088's release note said "rebuild existing artifacts", but nothing enforced it.

## 4. The idea of the fix (one sentence)

> **Stamp a layout number into the file, and refuse any other number in one shared reader.** The seal writes `format: 3` plus the jac version, and every reader checks the format before touching any other key.

A format number changes only when the file's layout changes. That is exactly what breaks old readers. A jac version or compiler digest would miss dev-build changes (every `main` build reports the same version) or block bundles that still work. This reasoning comes from @MusabMahmoodh's comment, which you followed.


**What:**
- `serve_manifest_stamp()` builds the two stamp keys.
- `read_serve_manifest()` is the single reader. It raises on a missing file, keeping the #9233 wording. It raises the new skew sentence when `format` is not 3. Otherwise it returns the data.
- `serve_manifest_for()` keeps returning `None` for "not sealed" and "no file". Every other case goes through the gated reader.

**Why:** This fixes both failing cases (§3.2, §3.3) and makes the two readers agree (§3.4).

**Things to notice:**
- **Only an exact match is accepted.** There is no accepted *set* like `MANIFEST_FORMATS_ACCEPTED`, even though the issue suggested one. A newer format (4) and an older format (2) are both refused.
- **The unstamped message names one version.** If the file has no version, the message says "an older jac" and names only the runtime's version.
- **`format: null` edge case.** A file whose `format` is present but `null` would print `format None`, not `unstamped`. No writer produces this.
- **Bad JSON now raises `json.JSONDecodeError` from `serve_manifest_for`.** This is a `ValueError`, not a `RuntimeError`. Your description calls it "an error … matches the other reader", which is true. But any caller that catches only `RuntimeError` won't catch it. Whether such callers exist can't be told from the diff.
- **The missing-file split is deliberate.** `serve_manifest_for` still returns `None` for a missing file, while `_prepare_sealed` raises. That is the one place the readers still differ, on purpose.
- **In-memory manifests skip the gate.** `prepared_manifest(path)` returns early, before any format check. This is the background to @MusabMahmoodh's open question about the `surface` guard (§9).
- **Version source.** The version comes from `resolve_cli_version()`, not `importlib.metadata`. Greptile flagged the earlier version, and you fixed it in `3486cb5`. Per @MusabMahmoodh, keeping this lookup local, instead of importing from `compiler/driver/jir.jac`, avoids a server→compiler dependency like the one behind #9369.

## 6. How execution flows after the PR

### 6.1 Sealing an app

```text
jac build / seal
└─ build_serve_manifest(entry, base)
   ├─ prepare application, collect per-module manifests
   ├─ result['module_manifests'] = {...}
   ├─ result.update(serve_manifest_stamp())                       ← NEW
   │  └─ resolve_cli_version()  (falls back to "0.0.0" on error)  ← NEW
   └─ written to .jac/serve_manifest.json  → {..., "format": 3, "jaclang_version": "0.37.21"}
```

### 6.2 Booting a sealed app

```text
jac run --serve main.jac (sealed)
└─ _prepare_sealed(entry, program, image_root, entries)
   ├─ load/register _precompiled image (unchanged)
   ├─ read_serve_manifest(image_root)                              ← CHANGED (was inline read)
   │  ├─ file missing?  → RuntimeError "no serving manifest" (same text as before)
   │  ├─ json.loads(file)
   │  ├─ format != 3?   → RuntimeError "built by <origin> (serve manifest format <n>);
   │  │                    this runtime (jac <v>) reads format 3. Rebuild ..."   ← NEW
   │  └─ return data
   ├─ manifest['root'] = image_root
   └─ continue preparation with manifest['module_manifests']
```

### 6.3 Looking up one module's manifest while serving

```text
serve_manifest_for(path)
├─ prepared_manifest(path) in memory? → return it (no format check)
├─ no sealed root, or no manifest file? → None
└─ read_serve_manifest(img_root)['module_manifests'].get(relative)   ← CHANGED
   └─ wrong format → RuntimeError (was: None)                        ← NEW
```

| Scenario | Before | After |
|---|---|---|
| Flat layout (pre-#9088), boot | `KeyError: 'module_manifests'` | Skew sentence, "an older jac … unstamped" |
| Flat layout, `serve_manifest_for` | `None` | Same skew sentence |
| Unstamped but has `module_manifests` (e.g. 0.37.21 dev) | Boots; endpoints may be missing | Refused at boot |
| `format: 4` from newer jac | Unpredictable failure | Skew sentence naming jac 0.38.0 and format 4 |
| No manifest file, boot | "no serving manifest" | Unchanged |
| No manifest file, `serve_manifest_for` | `None` | `None` (unchanged) |
| Invalid JSON, `serve_manifest_for` | `None` | `JSONDecodeError` raised |
| Bundle from current jac | Works | Works |

**Behaviour change users will notice:** dev bundles built from `main` after #9355 but before this PR have no stamp, so they are now refused and must be rebuilt. Your description says released bundles were already blocked by other checks.

## 11. Questions your senior might ask

**Q: Why a format number and not the jac version or `compiler_digest`?**
The digest doesn't hash `dist/seal.jac`, `server/sealed_serve.jac` or the scale bundler, so a layout change there would slip through. It would also refuse every app after any compiler change. The jac version is identical across `main` dev builds, which is how #9355 slipped through, and it would refuse bundles on every patch release.

**Q: Why start at 3?**
There have been three layouts: flat, then `module_manifests` (#9088), then `surface` (#9355). Every older file is unstamped, so the exact earlier numbers never appear in real files.

**Q: Why exact match and not an accepted set like `MANIFEST_FORMATS_ACCEPTED`?**
Only one format exists today, and nothing reads older layouts. When a format 4 arrives, someone can widen the check if format 3 is still readable. Right now the check is `!=`.

**Q: What stops someone from changing the layout without bumping?**
The shape test in `test_application_preparation.jac`. Any key change at the manifest, module or surface level fails CI with instructions. It only covers keys the small test app produces, though.

**Q: Does adding `persistence` (#9375), `runtime_imports` or #9848's surface fields need a bump?**
No. Each is read with a default, so old readers handle them. The rule: bump only for a rename, a removal, or a newly required key.

**Q: Why does a missing file still get the old message, not the skew sentence?**
It keeps #9233's wording, and @MusabMahmoodh agreed because #9138 will stop such bundles from shipping at all. In `serve_manifest_for`, a missing file still returns `None`.

**Q: Does anything that works today stop working?**
According to your description, released bundles were already blocked elsewhere. Dev bundles built from `main` after #9355 and before this PR are now refused and need a rebuild. Also, `serve_manifest_for` now raises on bad JSON or a wrong format instead of returning `None`.

**Q: Are in-memory manifests checked?**
No. `prepared_manifest()` returns before the gate. That is why the `surface` guard question is still open.

**Q: What if `resolve_cli_version()` fails at seal time?**
The stamp records `"0.0.0"`, and sealing continues. Refusal still works, because only the `format` field decides it.

**Q: Why not take @kugesan1105's ready branch?**
It was a policy change: a sealed app would have to run on exactly the compiler that built it, including host loads via `register_image`. The reviewer argued the digest is the wrong signal anyway, and you went with the format-only approach.
