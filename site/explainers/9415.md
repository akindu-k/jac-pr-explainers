## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. When the sealed app boots, jac reads that file to learn which endpoints exist and who may call them. The file's layout changed twice, first in #9088 and then in #9355. **The file never said which layout it used, so a bundle built by one jac and booted by another either crashed with an unrelated error (`Error loading main.jac: 'module_manifests'`) or booted with endpoints silently missing.**

**You now stamp the file with a format number (`SERVE_MANIFEST_FORMAT = 3`) and the building jac's version, and both readers go through one function, `read_serve_manifest()`. That function refuses any format other than 3 with one message that names both jac versions and says to rebuild.** The jac version only makes the message readable. The format number alone decides whether a bundle is refused.

A test stops people from forgetting to bump the number. It seals a small app, collects the manifest's key names, and compares them to a recorded layout for format 3. If the layout changes, the test fails and tells the developer to decide whether a bump is needed.

**Status:** merged on 2026-10-21. @MusabMahmoodh approved three times (09-24, 10-09, 10-13). On the head commit `4d81e80`, `build-kit` was still in progress at merge time, and no `test-compiler` or `test-client` result is listed (see section 8).

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `build_serve_manifest()` runs at seal time and produces the JSON.
- **Reader 1:** `_prepare_sealed()` runs at boot and loads the whole file.
- **Reader 2:** `serve_manifest_for(path)` is used by `client.artifact.prebuilt_bundle` (per `archwire.jac`) to look up one module's record.
- **The deploy path:** per #9140, jachammer deploys sealed with builder-sv's own jac-scale (0.34.x). The pod could run a newer jac, so the builder and the runtime often differed.

### 3.2 What went wrong: flat manifest (built before #9088)

```text
1. jac 0.37.11 `jac build --as jab` writes serve_manifest.json in the FLAT layout (no 'module_manifests')
2. File has no 'format' key → nothing records which layout it is
3. Pod runs jac 0.37.12, boots the bundle → _prepare_sealed()
4. manifest = json.loads(...)                          → {'app': ..., 'surface'?: ...}
5. for ... in manifest['module_manifests'].items()     ← WRONG: KeyError
6. Output: "Error loading main.jac: 'module_manifests'", exit 1, crash-loop
```

@kugesan1105 reproduced this on the real 0.37.12 release.

### 3.3 What went wrong: no serve manifest at all

```text
1. Any 0.37.11 jac-scale deploy never wrote serve_manifest.json
2. _prepare_sealed() → file missing → "Sealed application has no serving manifest: ..." (from #9233)
```

This PR keeps this message on purpose. That case is tracked in #9138.

### 3.4 What went wrong: `module_manifests` but no `surface` (before #9355)

```text
1. Bundle sealed by v0.37.21, with module_manifests but no 'surface' in the records
2. Booted on a jac that expects 'surface'
3. _prepare_sealed() passes (the key it indexes exists)
4. Server starts "ready"                                ← WRONG: no check at the boundary
5. /walkers is empty; calling an endpoint returns 405; nothing in the logs
```

Your description says two different things about this case. The table says #9369 catches it later at server start. "What was wrong" item 3 says it was not caught at all. Most likely the silent version happened before #9369 landed. Be ready to say which one is true on current `main`.

### 3.5 What went wrong: the two readers disagreed

```text
Flat manifest → _prepare_sealed():    KeyError (crash)
Flat manifest → serve_manifest_for(): data.get('module_manifests', {}).get(rel) → None (silent)
```

The same file was treated as an error by one reader and as "nothing here" by the other.

### 3.6 Why it mattered

- Production deploys crash-looped with errors that never said "your bundle and your runtime don't match" (#9140).
- The silent case is worse: a pod looks healthy but serves no endpoints.
- Version numbers alone could not catch this. Per your description, #9355 changed the layout between releases, and every dev build of `main` reports the same version.

## 4. The idea of the fix (one sentence)

> **Stamp the file with a layout number and refuse any other number at the single read point.** The writer adds `format` and `jaclang_version`, and one function, `read_serve_manifest()`, checks `format` before anyone uses the data.

A format number changes only when the layout changes. It catches real incompatibility without forcing a rebuild on every compiler change or release. That is the weakness of `compiler_digest` and of the plain jac version. The same pattern already protects `_precompiled/MANIFEST.json`.

### 5.2 `jac/jaclang/server/impl/sealed_serve.impl.jac`: the stamp, the single reader, and reader #2 rewired

```diff
+impl serve_manifest_stamp -> dict[str, (int | str)] {
+    try { jac_version = resolve_cli_version(); }
+    except Exception { jac_version = "0.0.0"; }      # NEW: never fail the seal over a version lookup
+    return {'format': SERVE_MANIFEST_FORMAT, 'jaclang_version': jac_version};
+}
+
+impl read_serve_manifest(img_root: str) -> dict[str, any] {
+    mf = Path(img_root) / SERVE_MANIFEST_REL;
+    if not mf.is_file() {
+        raise RuntimeError(f'Sealed application has no serving manifest: {mf}; ...');  # same text as before (#9233)
+    }
+    data = json.loads(mf.read_text(encoding="utf-8"));
+    meta = data if isinstance(data, dict) else {};
+    if meta.get('format') != SERVE_MANIFEST_FORMAT {
+        built_by = meta.get('jaclang_version');
+        origin = f'jac {built_by}' if built_by else 'an older jac';
+        runtime = serve_manifest_stamp()['jaclang_version'];

+            f'Sealed application at {img_root} was built by {origin} '
+            f'(serve manifest format {meta.get("format", "unstamped")}); '
+            f'this runtime (jac {runtime}) reads format {SERVE_MANIFEST_FORMAT}. '
+            'Rebuild the bundle with the jac that will run it.'
+        );
+    }
+    return data;
+}

     ...
-    if img_root is None { return None; }
-    mf = os.path.join(img_root, SERVE_MANIFEST_REL);
-    if not os.path.isfile(mf) { return None; }
-    try { data = json.loads(...); } except Exception { return None; }   # OLD: bad JSON → None
-    if not isinstance(data, dict) { return None; }                     # OLD: non-dict → None

+        or not os.path.isfile(os.path.join(img_root, SERVE_MANIFEST_REL)) {
+        return None;                                                   # still quiet when there's no file
+    }

```

**What:** `serve_manifest_stamp()` builds the stamp. `read_serve_manifest()` reads the file and enforces the format. `serve_manifest_for()` now reads through it.

**Why:** This fixes the missing contract and makes the two readers agree (3.5). @MusabMahmoodh said one shared reader is better than the two parallel checks he sketched in the issue.

**Things to notice:**
- **Behaviour change in `serve_manifest_for`:**
  - A missing file still returns `None`.
  - Invalid JSON now raises. The error is a `json.JSONDecodeError`, not a `RuntimeError`.
  - A non-dict file or a wrong format now raises a `RuntimeError` instead of returning `None`.
  - Callers that expected `None` will now see exceptions. The diff doesn't show how `client.artifact.prebuilt_bundle` handles that.
- After the check passes, `['module_manifests']` uses bracket access. This is safe only because every format-3 file has that key.
- Edge case: a file with a `format` but no `jaclang_version` (for example a future format 4 without a version) produces "built by **an older jac** (serve manifest format 4)". That is misleading.
- `serve_manifest_for` checks `isfile` before the call, and `read_serve_manifest` checks it again. The double check is harmless.
- Why the version comes from `resolve_cli_version()`: Greptile pointed out that `importlib.metadata.version("jaclang")` can report the wrong version under `JAC_DEV_SOURCE`. Commit 3486cb5 fixed it. @MusabMahmoodh also approved keeping the version lookup out of `compiler/driver/jir.jac`, to avoid the server-imports-compiler trap behind #9369.

## 6. How execution flows after the PR

### 6.1 Sealing an app

```text
jac build --as jab / jac-scale seal
└─ build_serve_manifest(path, base)
   ├─ prepare application, collect per-module manifests
   ├─ result = entry module manifest + 'module_manifests' (portable: no root / surface module)
   ├─ result.update(serve_manifest_stamp())                      ← NEW
   │   └─ resolve_cli_version()  (fallback "0.0.0")             ← NEW
   └─ written to .jac/serve_manifest.json (by the seal; this part isn't in the diff)
```

### 6.2 Booting a sealed app

```text
prepare_application(entry, program, root, dev=False)
└─ _prepare_sealed(...)
   ├─ image_for_bundle_dir / register_image   (unchanged; "no artifact manifest" if None)
   ├─ read_serve_manifest(image_root)                            ← CHANGED (was inline read)
   │   ├─ file missing      → RuntimeError "no serving manifest"   (same text)
   │   ├─ json.loads
   │   ├─ format != 3       → RuntimeError "built by ... (format X); this runtime reads 3. Rebuild..."  ← NEW
   │   └─ return data
   ├─ manifest['root'] = image_root
   └─ continue preparing from module_manifests
```

### 6.3 Looking up one module's record

```text
serve_manifest_for(path)
├─ prepared_manifest(path) not None → return it (in-memory, no format check)
├─ no sealed root or no file        → None
└─ read_serve_manifest(img_root)['module_manifests'].get(relative)   ← CHANGED
    └─ wrong format / non-dict → RuntimeError; bad JSON → JSONDecodeError   ← NEW
```

| Scenario | Before | After |
|---|---|---|
| Flat manifest at boot | `KeyError: 'module_manifests'` | Refusal: "older jac (format unstamped)" |
| Unstamped `module_manifests` file (with or without `surface`) at boot | Boots, or a later check (#9369) catches it | Refusal, right away |
| Format 4 from a newer jac | Undefined failure | Refusal naming jac 0.38.0, format 4 |
| No file at boot | "no serving manifest" | Same |
| No file via `serve_manifest_for` | `None` | `None` |
| Old or non-dict file via `serve_manifest_for` | `None` | `RuntimeError` |
| Bad JSON via `serve_manifest_for` | `None` | `JSONDecodeError` |
| Fresh bundle from the current jac | Works | Works |

**Users will notice:** dev bundles sealed from `main` after #9355 but before this PR are unstamped, so they are now refused and must be rebuilt. Your description calls this out.

## 11. Questions your senior might ask

**Q: Why not just compare jac versions?**
Every dev build of `main` has the same version, so #9355's layout change would have slipped through. And every patch release would force a rebuild even when the layout didn't change.

**Q: Why not use `compiler_digest`, which the bundle already records?**
It hashes `compiler_inputs.txt`, which doesn't include `dist/seal.jac`, `server/sealed_serve.jac` or `scale/injector/bundle.jac`. A layout change there keeps the same digest, so it is too loose. Any compiler change would also refuse every sealed app, including `register_image` host loads, so it is too strict.

**Q: What stops someone from changing the layout and forgetting to bump?**
The shape test in `test_application_preparation.jac`. Any change to the key names at the top level, module level or surface level fails it, with a message saying to decide on a bump and record the new shape.

**Q: Why is adding `persistence` not a bump?**
Its only reader uses `.get('persistence', ())`, so older readers ignore it. You bump only for renames, removals, or newly required keys.

**Q: Why is the missing-file case not given the "generation" message?**
@MusabMahmoodh agreed to keep #9233's message. That case has its own fix, #9138, which stops the build from shipping without the file.

**Q: Does this block any bundle that works today?**
Only unstamped dev bundles sealed from `main` after #9355. Older released bundles were already failing other checks. Fresh bundles work.

**Q: Can `serve_manifest_for` now throw where it used to return `None`?**
Yes, for a wrong or unstamped format, a non-dict file, or bad JSON. A missing file still returns `None`. In-memory prepared manifests skip the check entirely.

**Q: What if `resolve_cli_version()` fails while sealing?**
The stamp falls back to `"0.0.0"`. The seal still succeeds, and refusal depends only on `format`.

**Q: Why did you drop `root` from the recorded shape without bumping?**
Since #9923 the seal strips `root` and the surface `module`. No released jac writes or reads format 3 yet, and `_prepare_sealed` sets `root` from the boot folder.

**Q: Is the old `surface` guard in the server still needed?**
It's still open. All file-backed manifests are now format-gated, so it may only see in-memory ones. @MusabMahmoodh agreed this can be a follow-up.
