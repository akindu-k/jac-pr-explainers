## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. This file lists the app's endpoints and who may call them. At boot, jac reads it back. Two places read it: `_prepare_sealed` in `compiler/driver/application.jac`, and `serve_manifest_for` in `server/sealed_serve.jac`.

**The file never said which layout it used, and its layout changed twice (#9088, then #9355), so a bundle sealed by one jac and booted by another either crashed with an unrelated error like `Error loading main.jac: 'module_manifests'` or booted with endpoints silently missing.** The two readers also disagreed. One crashed on the old layout. The other quietly returned `None`.

**You now stamp the file with `format: 3` and the building jac's version when sealing. Both readers now go through one new function, `read_serve_manifest()`, which refuses any bundle whose format is not 3.** The refusal names both sides, for example: `Sealed application at w_future was built by jac 0.38.0 (serve manifest format 4); this runtime (jac 0.37.21) reads format 3. Rebuild the bundle with the jac that will run it.` You also added a test that fails if the manifest's key layout changes without someone deciding whether to bump the format.

**Status:** Open. @MusabMahmoodh approved twice, on 2026-09-24 and 2026-10-09. Both approvals came before your last two real commits (3486cb5 and dc8ab31). On the head commit d591f21, CI did not actually test anything: `build-kit` was cancelled, almost every test lane was skipped, and `Everything Passed` failed.

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `build_serve_manifest()` in `dist/seal.jac`. It runs at seal time, on whatever jac the builder has.
- **File:** `.jac/serve_manifest.json` inside the bundle. Before this PR it carried no format or version.
- **Readers at boot:**
  - `_prepare_sealed()` read the file and then did `manifest['module_manifests']`.
  - `serve_manifest_for()` did `data.get('module_manifests', {}).get(relative)`, which returns `None` on any surprise.
- Per the issue, jachammer deploys sealed with builder-sv's own jac-scale (0.34.x), while pods ran 0.37.12+. So the builder and the runtime were often different generations.

### 3.2 What went wrong: case A, an old flat bundle crashes

```text
1. jac 0.37.11 seals the app (jac build --as jab)
   → serve_manifest.json = { "app": ..., "client": ..., ... }   (flat, format "1", no stamp)
2. Bundle is unpacked on a pod running jac 0.37.12
3. _prepare_sealed reads the file → dict with no 'module_manifests'
4. for (source, metadata) in manifest['module_manifests'] ...
   → KeyError: 'module_manifests'                              ← WRONG: no hint about versions
5. Output: "Error loading main.jac: 'module_manifests'", exit 1, crash-loop
```

@kugesan1105 reproduced this on the real 0.37.12 release.

### 3.3 What went wrong: case B, a pre-`surface` bundle

```text
1. jac 0.37.21 seals the app → has module_manifests, no 'surface'  (format "2", no stamp)
2. A newer runtime (main after #9355) boots it
3. _prepare_sealed: 'module_manifests' exists → no KeyError, passes
4. Later code expects 'surface'
   → caught at server start by the #9369 guard, OR
   → (per your description) server reports ready, /walkers empty, endpoint → 405,
     nothing in the logs                                       ← WRONG: silent failure
```

Your description is not fully consistent here. The table says this case was "caught later at server start by #9369". The "What was wrong" list says one v0.37.21 case was "not caught at all". The diff alone cannot tell which path leads to the silent result. Be ready to explain this.

### 3.4 What went wrong: case C, a newer bundle on an older runtime

```text
1. A future jac seals a layout this runtime does not know
2. Older runtime reads it with the same assumptions
3. Fails "somewhere random", or serves partially               ← WRONG
```

### 3.5 What went wrong: case D, the two readers disagree

```text
Same flat file:
  _prepare_sealed     → KeyError (crash)
  serve_manifest_for  → None     (silently "no manifest for this module")  ← WRONG: inconsistent
```

### 3.6 Why it mattered

- Every jachammer deploy could hit this, because the builder and the pod jac were different generations. The result is a crash-looping pod with an error that points nowhere useful.
- #9088's release note said "rebuild existing artifacts", but nothing enforced that.
- The layout changed a second time (#9355) during development on `main`. Every dev build reports the same version, so the change went unnoticed.

## 4. The idea of the fix (one sentence)

> **Stamp the file with a layout number, and check it in one place.** The seal step writes `format` and `jaclang_version`, and a single reader refuses any bundle whose `format` is not the one this runtime understands, naming both versions.

The format number changes only when the layout changes. That avoids both mistakes of the alternatives: a version check would miss dev builds and would block every patch release, and a compiler digest does not even hash the files that write and read this manifest. A shape test turns "forgot to bump" into a test failure.

### 5.1 `jac/jaclang/server/sealed_serve.jac`: the constant, the stamp and the single reader

```diff

 glob SERVE_MANIFEST_REL: str = os.path.join(".jac", "serve_manifest.json"),
```

```diff
+def serve_manifest_stamp -> dict[str, (int | str)] {
+    import from jaclang.cli.manifest_route { resolve_cli_version }
+    try {
+        jac_version = resolve_cli_version();
+    } except Exception {
+        jac_version = "0.0.0";                       # NEW: never let the stamp crash a seal
+    }
+    return {'format': SERVE_MANIFEST_FORMAT, 'jaclang_version': jac_version};
+}
+
+def read_serve_manifest(img_root: str) -> dict[str, any] {
+    mf = Path(img_root) / SERVE_MANIFEST_REL;
+    if not mf.is_file() {
+        raise RuntimeError(                          # moved from application.jac, same text
+            f'Sealed application has no serving manifest: {mf}; '
+            'rebuild the bundle so the seal step writes it'
+        );
+    }
+    data = json.loads(mf.read_text(encoding="utf-8"));
+    meta = data if isinstance(data, dict) else {};   # non-dict JSON counts as "unstamped"
+    if meta.get('format') != SERVE_MANIFEST_FORMAT {
+        built_by = meta.get('jaclang_version');
+        origin = f'jac {built_by}' if built_by else 'an older jac';
+        runtime = serve_manifest_stamp()['jaclang_version'];
+        raise RuntimeError(
+            f'Sealed application at {img_root} was built by {origin} '
+            f'(serve manifest format {meta.get("format", "unstamped")}); '
+            f'this runtime (jac {runtime}) reads format {SERVE_MANIFEST_FORMAT}. '
+            'Rebuild the bundle with the jac that will run it.'
+        );
+    }
+    return data;
+}
```

**What:**
- `SERVE_MANIFEST_FORMAT = 3` names the current layout.
- `serve_manifest_stamp()` builds the stamp.
- `read_serve_manifest()` is the one reader. It raises the old "no serving manifest" error if the file is missing, raises the new generation error on a wrong format, and otherwise returns the dict.
- `serve_manifest_for()` keeps returning `None` when there is no sealed root or no file. Otherwise it reads through the gate.

**Why:** This fixes cases A, B and C, because the format is checked before any key is used. It also fixes case D, because both readers now share one check.

**Things to notice:**
- **Exact match, not an accepted set.** The issue suggested an "accepted set" like `MANIFEST_FORMATS_ACCEPTED`. You compare with `!=` against one value. After a bump to 4, every format-3 bundle is refused. That is consistent with "rebuild with the jac that runs it".
- **Starting at 3, not 2.** The issue suggested 2. You chose 3 because #9355 already changed the layout once more. @MusabMahmoodh agreed.
- **Missing-file case keeps its old message** (from #9233) instead of the generation sentence. The issue asked for the generation sentence there too. @MusabMahmoodh accepted this, since #9138 handles that case.
- **Intended behaviour change:** `serve_manifest_for()` now raises where it used to return `None`. This happens for wrong format, non-dict JSON, and invalid JSON (a `json.JSONDecodeError`, not a `RuntimeError`). The diff does not show the callers of `serve_manifest_for`, so whether they handle a raise cleanly cannot be confirmed here.
- **Version source changed in 3486cb5.** It switched from `importlib.metadata.version("jaclang")` to `resolve_cli_version()`, per Greptile, so `JAC_DEV_SOURCE` checkouts report the right version. The `"0.0.0"` fallback only triggers if that lookup throws.
- **A small import-direction point.** @MusabMahmoodh praised keeping the version lookup out of `compiler/driver/jir.jac`. Since 3486cb5, though, the server module imports from `jaclang.cli`. The import is lazy (inside the function). He has not commented on this since.

## 6. How execution flows after the PR

### 6.1 Sealing a bundle

```text
jac build / jac-scale seal
└─ build_serve_manifest(entry_file, proj_root)
   ├─ prepare apps, build result dict + module_manifests (unchanged)
   ├─ result.update(serve_manifest_stamp())                  ← NEW
   │   └─ resolve_cli_version()  (fallback "0.0.0")          ← NEW
   └─ return result → written as .jac/serve_manifest.json
       e.g. {..., "format": 3, "jaclang_version": "0.37.21"}
```

### 6.2 Booting a sealed app

```text
prepare_application(..., dev=False) → _prepare_sealed(entry, program, image_root, entries)
├─ artifact manifest missing? → RuntimeError (unchanged)
├─ read_serve_manifest(image_root)                           ← CHANGED (was inline read)
│   ├─ file missing → RuntimeError "no serving manifest ..." (same text)
│   ├─ json.loads(...)  (invalid JSON → JSONDecodeError)
│   ├─ format != 3 → RuntimeError "built by <origin> (serve manifest format <n|unstamped>);
│   │                 this runtime (jac <v>) reads format 3. Rebuild ..."   ← NEW
│   └─ format == 3 → return dict
├─ manifest['root'] = image_root
└─ continue preparing (unchanged)
```

### 6.3 Looking up one module's manifest at serve time

```text
serve_manifest_for(path)
├─ prepared_manifest(path) not None → return it (in-memory, no gate)
├─ sealed_root_for(path) is None → None
├─ no serve_manifest.json at root → None
└─ read_serve_manifest(img_root)                             ← NEW
    ├─ wrong format / bad JSON → raises                      ← CHANGED (was None)
    └─ ['module_manifests'].get(relative)
```

| Scenario | Before | After |
|---|---|---|
| Flat layout (pre-#9088) | `_prepare_sealed`: `KeyError 'module_manifests'`. `serve_manifest_for`: `None` | Both: "built by an older jac (serve manifest format unstamped) ..." |

## 11. Questions your senior might ask

**Q: Why not refuse on `compiler_digest` or `jaclang_version` instead of a hand-maintained number?**
The digest does not hash `dist/seal.jac`, `server/sealed_serve.jac` or `scale/injector/bundle.jac`, the files that own this manifest. So it would miss real layout changes, yet block every app after any compiler change. The version is the same on every dev build from `main`, which is how #9355 slipped through, and it would block every patch release. The format changes only when the layout does.

**Q: What stops someone from forgetting to bump the format?**
The writer test compares the real manifest's key sets with `SERVE_MANIFEST_SHAPES[3]`. Any added, removed or renamed key at those three levels fails the test with a message telling the developer to decide on a bump and record the shape.

**Q: Why is it 3 and not 2, as the issue suggested?**
The layout has already changed twice: flat (1), then `module_manifests` (2, #9088), then `surface` (3, #9355). @MusabMahmoodh agreed.

**Q: #9375 added `persistence` after you opened the PR. Why no bump?**
Its only reader uses `.get('persistence', ())`, so older and newer readers both handle its absence. Only renames, removals or newly required keys need a bump.

**Q: Does this block anything that works today?**
Bundles built by the current jac still work. Released bundles that are old enough were already failing in other ways. The newly blocked ones are unstamped dev bundles built from `main` after #9355. They need a rebuild.

**Q: `serve_manifest_for` used to return `None` on a bad file. Is raising safe for its callers?**
The change is deliberate, so both readers agree. The callers are not in this diff. I'd need to check them, or rely on the test lanes once CI actually runs.

**Q: Why does a missing file not get the generation message?**
It keeps the existing #9233 message. The missing-file case (old scale deploys that never wrote the file) is being handled separately in #9138, and @MusabMahmoodh was fine with this.

**Q: Why an exact match rather than a set of accepted formats?**
There is only one layout today, and the policy is "rebuild with the jac that runs it". If a future runtime should accept an older format, the check can become a set then.

**Q: What if `resolve_cli_version()` fails?**
The stamp records `"0.0.0"`, so sealing never crashes on it. Refusal depends only on `format`, so a bad version string only affects the wording of the error.

**Q: Can the `surface` guard in `server.impl.jac` be removed now?**
Possibly, if only in-memory manifests reach it and those always have `surface`. The PR doesn't check this. It is left as a follow-up, as @MusabMahmoodh agreed.
