## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. At boot, jac reads that file to learn which endpoints exist and who may call them. The layout of this file changed twice: in #9088 (a flat dict became a `module_manifests` table) and in #9355 (a `surface` field was added).

**The file never said which layout it used, so a bundle sealed by one jac and booted by another either crashed with an unrelated error (`Error loading main.jac: 'module_manifests'`) or booted "ready" with endpoints silently missing.** The two code paths that read the file also disagreed. One raised a `KeyError`. The other quietly returned `None`.

**You stamp the file with `format: 3` and the building jac's version, and you route both readers through one new function, `read_serve_manifest()`. It refuses any other format with one sentence that names both jac versions and says to rebuild.** A test now records the key layout of format 3, so a later layout change fails CI until someone decides whether to bump the number.

**Status:** Open. @MusabMahmoodh approved twice (2026-09-24 and 2026-10-09). His second approval says that "everything since my approval is merges from main", so it predates your four later commits (`3486cb5`, `dc8ab31`, `e44a565`, `35e91e1`). All CI checks on `d19eb84` pass or were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `dist/seal.jac` `build_serve_manifest()` makes the dict. The diff does not show which code writes it to `.jac/serve_manifest.json`.
- **Reader #1:** `compiler/driver/application.jac` `_prepare_sealed()` reads the whole file at boot and needs `manifest['module_manifests']`.
- **Reader #2:** `server/sealed_serve.jac` `serve_manifest_for()` reads it per module path, using `.get('module_manifests', {})`.
- **No stamp:** unlike `_precompiled/MANIFEST.json`, nothing in the file said which layout it used.

### 3.2 What went wrong

#### 3.2.1 A flat (pre-#9088) manifest booted on a post-#9088 jac

```text
1. jac 0.37.11: `jac build --as jab` writes a flat serve_manifest.json   (no module_manifests, no format)
2. Pod runs jac 0.37.12: `jac run --serve main.jac`
3. _prepare_sealed: file exists → json.loads → manifest = {flat keys...}
4. Code reads manifest['module_manifests']                                 ← WRONG: KeyError
5. Output: "Error loading main.jac: 'module_manifests'"; exit 1; crash-loop
```

@kugesan1105 reproduced this on the 0.37.12 release.

#### 3.2.2 A manifest without `surface` (pre-#9355 layout) booted on a post-#9355 jac

```text
1. jac 0.37.21-era build writes module_manifests, but records lack `surface`
2. Newer jac boots it; the file parses; module_manifests exists → no KeyError
3. Endpoints are built from `surface`, which is missing                   ← WRONG: silently empty
4. Server reports ready; /walkers is empty; calling an endpoint → 405; no log line
```

The description gives two outcomes for this case. Its table says #9369 catches it later at server start. Its prose says one variant "was not caught at all". Both describe late or missing detection, not a clear refusal.

#### 3.2.3 The two readers disagreed

```text
1. Same flat manifest on disk
2. _prepare_sealed → KeyError (crash)
3. serve_manifest_for → data.get('module_manifests', {}).get(rel) → None   ← WRONG: silently "no record"
```

A pre-#9088 jac-scale deploy that never wrote the file at all produced `FileNotFoundError` / "no serving manifest". That case keeps its existing message (#9233) and is tracked separately in #9138.

### 3.3 Why it mattered

- Production deploys crash-looped with messages that did not say "your bundle and runtime are from different generations" (#9140). Per the issue, every jachammer deploy seals with an older jac, so this mismatch is the normal case, not a rare one.
- The silent case is worse: the pod looks healthy but serves no endpoints, and nothing appears in the logs.
- The sibling artifact `_precompiled/MANIFEST.json` solved this long ago with a format number (#7135). The serve manifest was the only payload in the image without one.

## 4. The idea of the fix (one sentence)

> **Stamp a layout number at seal time and check it in one place at read time.** The bundle records `format: 3` and the jac that built it, and every reader goes through `read_serve_manifest()`, which refuses any other format with a sentence naming both jac versions.

The format number changes only when the layout breaks, unlike the jac version (identical across all dev builds of `main`) or `compiler_digest` (it does not cover the files that write and read this manifest). So it catches real skew without forcing a rebuild on every release.

## 5. Every code change, explained

### 5.1 `jac/jaclang/server/sealed_serve.jac`: the constant, the stamp, and the single reader

```diff
 glob SERVE_MANIFEST_REL: str = os.path.join(".jac", "serve_manifest.json"),
+     SERVE_MANIFEST_FORMAT: int = 3,

+def serve_manifest_stamp -> dict[str, (int | str)] {
+    import from jaclang.cli.manifest_route { resolve_cli_version }   # lazy import
+    try { jac_version = resolve_cli_version(); }
+    except Exception { jac_version = "0.0.0"; }                       # never fail the seal over a version lookup
+    return {'format': SERVE_MANIFEST_FORMAT, 'jaclang_version': jac_version};
+}

+def read_serve_manifest(img_root: str) -> dict[str, any] {
+    mf = Path(img_root) / SERVE_MANIFEST_REL;
+    if not mf.is_file() {
+        raise RuntimeError(f'Sealed application has no serving manifest: {mf}; '
+                           'rebuild the bundle so the seal step writes it');   # same text as before (#9233)
+    }
+    data = json.loads(mf.read_text(encoding="utf-8"));                         # bad JSON → JSONDecodeError
+    meta = data if isinstance(data, dict) else {};                             # non-dict → treated as unstamped
+    if meta.get('format') != SERVE_MANIFEST_FORMAT {
+        built_by = meta.get('jaclang_version');
+        origin = f'jac {built_by}' if built_by else 'an older jac';
+        runtime = serve_manifest_stamp()['jaclang_version'];
+        raise RuntimeError(... 'Rebuild the bundle with the jac that will run it.');
+    }
+    return data;
+}

 def serve_manifest_for(path: str) -> (dict[str, any] | None) {
     ...prepared_manifest(path) first (unchanged)...
     img_root = sealed_root_for(path);
-    if img_root is None { return None; }
-    mf = os.path.join(img_root, SERVE_MANIFEST_REL);
-    if not os.path.isfile(mf) { return None; }
-    try { data = json.loads(...); } except Exception { return None; }   # OLD: swallow bad JSON
-    if not isinstance(data, dict) { return None; }
+    if img_root is None
+        or not os.path.isfile(os.path.join(img_root, SERVE_MANIFEST_REL)) {
         return None;
     }
     relative = os.path.relpath(path, img_root).replace(os.sep, '/');
-    return data.get('module_manifests', {}).get(relative);            # OLD: tolerant of old layout
+    return read_serve_manifest(img_root)['module_manifests'].get(relative);   # NEW: format-gated
 }
```

**What:**
- Adds the format constant, a stamp builder, and one reader that checks the format.
- `serve_manifest_for` now delegates to that reader.

**Why:**
- It fixes 3.2.1 and 3.2.2: any unstamped or other-numbered file is refused by name.
- It fixes 3.2.3: both readers share one code path, so they behave the same.

**Things to notice:**
- The check is **exact equality**, not an accepted set like `MANIFEST_FORMATS_ACCEPTED`. A future runtime at format 4 will refuse every format-3 bundle. That is intended: a bump is only for breaking changes.
- Error text for the three kinds of bad file:
  - an unstamped file says "an older jac … format unstamped";
  - a newer file says "jac 0.38.0 … format 4";
  - an explicit `"format": null` would print `format None`. That is minor.
- `serve_manifest_for` keeps returning `None` when there is no sealed root or no file. The other cases are new behaviour:

  | File state | Before | After |
  |---|---|---|
  | Invalid JSON | `None` | `JSONDecodeError` |
  | Not a dict | `None` | `RuntimeError` |
  | Format 3 but no `module_manifests` | `None` | `KeyError` |

  The description mentions only the JSON case.
- `isfile` is checked twice: once in `serve_manifest_for` to keep the "return None" path, and again inside the reader. This is harmless.
- `resolve_cli_version` is imported lazily, inside the function. @MusabMahmoodh approved keeping the version lookup local here instead of importing from `compiler/driver/jir.jac`. His reason: "#9369 is what happens when a server module reaches into the compiler." `cli/manifest_route` replaced `importlib.metadata` in `3486cb5` after Greptile's comment.
- The `"0.0.0"` fallback means the stamp never blocks a seal. Refusal depends only on `format`.

## 6. How execution flows after the PR

### 6.1 Sealing an app

```text
seal step (caller not shown in diff)
└─ build_serve_manifest(entry_file, proj_root)
   ├─ load config, prepare application(s)
   ├─ result = entry module's manifest + module_manifests table
   ├─ result.update(serve_manifest_stamp())                  ← NEW
   │  └─ resolve_cli_version()  (fallback "0.0.0")            ← NEW
   └─ return result → written to .jac/serve_manifest.json
       e.g. {..., "format": 3, "jaclang_version": "0.37.21"}
```

### 6.2 Booting a sealed app

```text
prepare_application(path, ..., dev=False)
└─ _prepare_sealed(entry, program, image_root, entries)
   ├─ check _precompiled artifact manifest exists            (unchanged)
   ├─ read_serve_manifest(image_root)                        ← CHANGED (was inline read)
   │  ├─ file missing → RuntimeError "no serving manifest"    (same text as before)
   │  ├─ json.loads
   │  ├─ format != 3 → RuntimeError "built by <origin> (serve manifest format <n>);
   │  │                 this runtime (jac <v>) reads format 3. Rebuild…"   ← NEW
   │  └─ return data
   ├─ manifest['root'] = image_root
   └─ build PreparedApplication, publish
```

### 6.3 Looking up one module's serve record

```text
serve_manifest_for(path)
├─ prepared_manifest(path) is not None → return it           (unchanged; in-memory, no format check)
├─ sealed_root_for(path) is None → return None
├─ serve_manifest.json not a file → return None              (unchanged)
└─ read_serve_manifest(img_root)['module_manifests'].get(rel)  ← CHANGED
   └─ wrong/missing format → RuntimeError                   ← NEW (was: None)
```

| Scenario | Before | After |
|---|---|---|
| Bundle sealed by current jac | Works | Works (stamped, format 3) |
| Flat pre-#9088 file, booting | `KeyError: 'module_manifests'` | Clear refusal, "an older jac … unstamped" |
| Unstamped file lacking `surface`, booting | Boots; endpoints missing, or caught later by #9369 | Clear refusal at load |
| Format 4 from a newer jac | Undefined failure | Clear refusal naming `jac 0.38.0` and format 4 |
| No serve manifest file, booting | "no serving manifest" error | Same |
| `serve_manifest_for` on an old/unstamped file | `None` | `RuntimeError` |
| `serve_manifest_for` on invalid JSON | `None` | `JSONDecodeError` |
| Dev bundle built from `main` after #9355, before this PR | Works | **Refused, must rebuild** |

The last row is the one intended change users will notice. Per the description, no released bundle that works today is newly blocked, because those are already stopped by other checks.

## 11. Questions your senior might ask

**Q: Why a hand-bumped format number instead of the jac version or `compiler_digest`?**
The digest hashes `compiler_inputs.txt`, which does not include `dist/seal.jac`, `server/sealed_serve.jac` or `scale/injector/bundle.jac`. So it misses real layout changes, and it refuses on unrelated compiler edits. The jac version is identical across all dev builds of `main`, which is how #9355 slipped through, and it would refuse every patch release.

**Q: What stops someone from forgetting to bump it?**
The writer test compares the sealed manifest's key names at three levels against `SERVE_MANIFEST_SHAPES[3]`. Any added, removed or renamed key fails CI with instructions. It does not catch value-type changes, or keys the sample app never produces.

**Q: Why start at 3, not 2 as the issue suggested?**
#9355 already changed the layout once by adding `surface`. So flat = 1, `module_manifests` = 2, `surface` = 3. @MusabMahmoodh agreed.

**Q: Why exact match instead of an accepted set like `MANIFEST_FORMATS_ACCEPTED`?**
A bump is reserved for changes that old readers cannot handle, so accepting older numbers would defeat the purpose. The cost is that every format bump forces all deployed bundles to be rebuilt on upgrade.

**Q: Did `persistence` (#9375) or the #9848 `surface` fields need a bump?**
No. `persistence` is read with `.get('persistence', ())`. Per @MusabMahmoodh, the #9848 fields are optional on read, and the older `SurfaceEntry.from_dict` ignores unknown keys.

**Q: Why does the missing-file case keep its old message instead of the generation sentence?**
That case has its own fix in #9138, which stops the build from shipping a bundle without the file. @MusabMahmoodh agreed to keep #9233's message.

**Q: Does this affect dev mode or in-memory manifests?**
No. `serve_manifest_for` returns `prepared_manifest(path)` first, without a format check. Only file-backed sealed manifests are gated.

**Q: Why does `sealed_serve.jac` import `resolve_cli_version` lazily instead of reusing the compiler's version helper?**
To avoid a server module depending on compiler internals; #9369 was caused by exactly that. The `"0.0.0"` fallback keeps a failed lookup from breaking a seal, and refusal never depends on the version string.

**Q: Which working bundles become newly blocked?**
Only unstamped dev bundles built from `main` after #9355. They need a rebuild. Per the description, released older bundles were already failing through other checks.

**Q: Can the `surface` guard in `ModuleIntrospector._load_surface` now be removed?**
Possibly, if only in-memory manifests reach it after this gate. That cannot be confirmed from this diff. It is left as an open follow-up per @MusabMahmoodh.
