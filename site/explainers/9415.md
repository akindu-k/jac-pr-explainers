## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. That file lists the app's endpoints and who may call them. On boot, the runtime reads it in two places: `_prepare_sealed` in `compiler/driver/application.jac`, and `serve_manifest_for` in `server/sealed_serve.jac`.

**The file never said which layout it used, so a bundle sealed by one jac and booted by another either crashed with an unrelated error (`Error loading main.jac: 'module_manifests'`) or booted with endpoints silently missing.** The layout had changed twice: in #9088 (flat file → `module_manifests` table) and in #9355 (added `surface`). The two readers also disagreed. One crashed on an old file; the other quietly returned `None`.

**You now stamp every serve manifest with `{"format": 3, "jaclang_version": ...}` at seal time. On boot, both readers go through one new function, `read_serve_manifest()`, which refuses any file whose `format` is not exactly 3.** The refusal names both jac versions and says to rebuild. Example: `Sealed application at w_future was built by jac 0.38.0 (serve manifest format 4); this runtime (jac 0.37.21) reads format 3. Rebuild the bundle with the jac that will run it.` A test also pins the manifest's key layout to format 3, so a future layout change cannot slip in without someone deciding whether to bump the number.

**Status:** Open. @MusabMahmoodh approved twice (2026-09-24 and 2026-10-09). Both approvals came before your later commits `3486cb5`, `dc8ab31`, `e44a565` and `35e91e1`. All CI checks on head `35e91e1` passed; four were skipped.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac / jaclang | The language and its Python package (`jaclang`). It includes the compiler, the runtime and the server. |
| Seal / sealing | Building an app into a self-contained, precompiled bundle for deployment. Code: `dist/seal.jac`. |
| Bundle / `.jab` / sealed image | The sealed output, unpacked on a pod. Its folder is the **image root** (`img_root` / `image_root`). |
| jac-scale / jachammer / builder-sv | The deploy tooling. Per #9140, builder-sv seals with its *own* jac version, so the sealing jac can differ from the pod's jac. |
| `_precompiled/MANIFEST.json` | A sibling file in the bundle for compiled bytecode. It already carries `format` and `MANIFEST_FORMATS_ACCEPTED`, so it was already protected. |
| Serve manifest (`.jac/serve_manifest.json`, `SERVE_MANIFEST_REL`) | JSON describing each module's endpoints, access rules, client info and so on. Before this PR it had no format field. **This is where the bug is.** |
| `module_manifests` | A table inside the serve manifest, keyed by project-relative path (e.g. `"main.jac"`). Added in #9088. Older bundles have a flat file without it. |
| `surface` | Per-module endpoint records (route, exposure, access…). Added in #9355. A record lacking it boots with no walkers. |
| Generation skew | An artifact made by toolchain version A is read by version B, with nothing at the boundary checking that they match (the #8753 class of bug). |
| Format stamp | A number written into a file that says which layout it uses, so readers can refuse layouts they don't understand. |
| `SERVE_MANIFEST_FORMAT` | New constant, `3` (flat = 1, `module_manifests` = 2, `surface` = 3). Bump it only on changes old readers can't handle. |
| `resolve_cli_version()` | Existing function in `jaclang.cli.manifest_route`. It returns the same version `jac --version` prints and handles source checkouts (`JAC_DEV_SOURCE`). |
| `serve_manifest_stamp()` | New. Returns `{'format': 3, 'jaclang_version': <version>}`, with `"0.0.0"` if the version lookup throws. |
| `build_serve_manifest()` | The writer in `dist/seal.jac`. It builds the dict that becomes the file. |
| `read_serve_manifest(img_root)` | New. The single reader: checks the file exists, parses it and checks the format. **This is what the PR adds.** |
| `_prepare_sealed()` | Boot-time loader for a sealed app, in `compiler/driver/application.jac`. It reads the whole manifest. |
| `serve_manifest_for(path)` | Server-side lookup: given a module path, returns its record from `module_manifests`, or `None`. |
| `prepared_manifest(path)` | In-memory manifest from an already-prepared app. `serve_manifest_for` tries it first, and it skips the file entirely. |
| `compiler_digest` | A hash of compiler input files. It was discussed as an alternative check and rejected (see §9). |
| `SERVE_MANIFEST_SHAPES` | New test fixture: the recorded key names for format 3 at three levels (`manifest`, `module`, `surface`). |

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `build_serve_manifest()` in `dist/seal.jac` runs at seal time.
- **Reader A:** `_prepare_sealed()` in `compiler/driver/application.jac` runs at boot. It read `manifest['module_manifests']` directly.
- **Reader B:** `serve_manifest_for()` in `server/sealed_serve.jac`. It used `data.get('module_manifests', {}).get(relative)` and returned `None` on any problem.
- **The deploy path:** the sealing jac (for example builder-sv's) can differ from the jac on the pod.

### 3.2 What went wrong

#### 3.2.1 A pre-#9088 (flat) bundle on a newer runtime

```text
1. jac 0.37.11 seals app      -> serve_manifest.json = flat dict, no 'module_manifests', no format
2. Bundle lands on a 0.37.12 pod
3. _prepare_sealed reads file -> manifest = {...flat keys...}
4. manifest['module_manifests'] -> KeyError                         <-- WRONG: unrelated error
5. Output: "Error loading main.jac: 'module_manifests'", exit 1, crash-loop
```

@kugesan1105 reproduced this on the 0.37.12 release.

#### 3.2.2 A bundle missing `surface` (pre-#9355 dev build)

```text
1. A dev build of main before #9355 seals  -> records have module_manifests, but no 'surface'
2. A newer runtime boots it                -> no format check, file "looks" fine
3. Readers pass it through                 <-- WRONG: layout mismatch not detected
4. Pod reports ready; /walkers empty; calling an endpoint -> 405; nothing in logs
```

The PR description says two slightly different things here. Its table says this case "passed this step; caught later at server start by #9369". Its "What was wrong" list says one v0.37.21 case was "not caught at all". You can't tell from the diff which path produces which result. Be ready to explain that difference.

#### 3.2.3 A bundle from a *newer* jac

```text
1. A future jac seals with a changed layout
2. The current runtime boots it -> assumes its own layout
3. It fails "somewhere random", or silently misreads                <-- WRONG
```

#### 3.2.4 The two readers disagree

```text
Same flat file:
  _prepare_sealed     -> KeyError (crash)
  serve_manifest_for  -> None (silent; module treated as having no manifest)   <-- inconsistent
```

### 3.3 Why it mattered

- Deploys crash-loop with a message that doesn't say "your bundle and runtime are from different generations" (#9140).
- The silent case is worse. The app looks healthy but serves no endpoints.
- The #9088 release note said "rebuild existing artifacts", but nothing enforced it. The sibling `_precompiled/MANIFEST.json` already had a format stamp; this file was the one unstamped artifact in the image.

## 4. The idea of the fix (one sentence)

> **Stamp the layout version into the file and check it before reading.** The seal writes `format: 3` plus the jac version, and one shared reader refuses any other format with a sentence naming both sides.

The format number changes only when the layout does, so it catches real incompatibility without blocking working bundles on every compiler change or release. The jac version and compiler digest would be either too loose or too strict (§9).

## 5. Every code change, explained

### 5.1 `jac/jaclang/server/sealed_serve.jac`: format constant, stamp, single reader

```diff
 glob SERVE_MANIFEST_REL: str = os.path.join(".jac", "serve_manifest.json"),
+     SERVE_MANIFEST_FORMAT: int = 3,                          # NEW
 ...
+def serve_manifest_stamp -> dict[str, (int | str)] {
+    import from jaclang.cli.manifest_route { resolve_cli_version }
+    try { jac_version = resolve_cli_version(); }
+    except Exception { jac_version = "0.0.0"; }
+    return {'format': SERVE_MANIFEST_FORMAT, 'jaclang_version': jac_version};
+}
+
+def read_serve_manifest(img_root: str) -> dict[str, any] {
+    mf = Path(img_root) / SERVE_MANIFEST_REL;
+    if not mf.is_file() {
+        raise RuntimeError(f'Sealed application has no serving manifest: {mf}; '
+                           'rebuild the bundle so the seal step writes it');   # same #9233 text
+    }
+    data = json.loads(mf.read_text(encoding="utf-8"));
+    meta = data if isinstance(data, dict) else {};
+    if meta.get('format') != SERVE_MANIFEST_FORMAT {
+        built_by = meta.get('jaclang_version');
+        origin = f'jac {built_by}' if built_by else 'an older jac';
+        runtime = serve_manifest_stamp()['jaclang_version'];
+        raise RuntimeError(... built by {origin} (serve manifest format {meta.get("format", "unstamped")});
+                           this runtime (jac {runtime}) reads format {SERVE_MANIFEST_FORMAT}. Rebuild ...);
+    }
+    return data;
+}
 
 def serve_manifest_for(path: str) -> (dict[str, any] | None) {
     ... prepared_manifest(path) first (unchanged) ...
     img_root = sealed_root_for(path);
-    if img_root is None { return None; }
-    mf = ...; if not os.path.isfile(mf) { return None; }
-    try { data = json.loads(...); } except Exception { return None; }   # OLD: swallowed errors
-    if not isinstance(data, dict) { return None; }
+    if img_root is None
+        or not os.path.isfile(os.path.join(img_root, SERVE_MANIFEST_REL)) {
+        return None;
+    }
     relative = ...;
-    return data.get('module_manifests', {}).get(relative);             # OLD: tolerated old shape
+    return read_serve_manifest(img_root)['module_manifests'].get(relative);   # NEW: format-gated
 }
```

**What:** Adds the format constant, a stamp builder and one reader that checks existence, parses the JSON and checks the format. `serve_manifest_for` now uses that reader.

**Why:** It fixes the missing stamp on the read side (§3.2.1–3.2.3) and makes both readers behave the same (§3.2.4).

**Things to notice:**
- The check is **exact equality**, not an accepted set. #9140 suggested an accepted set, like `MANIFEST_FORMATS_ACCEPTED`. Today only one format is readable, so equality is equivalent, but a senior may ask.
- The issue suggested starting at 2. You start at 3 because #9355 already changed the shape once. @MusabMahmoodh agreed.
- The missing-file case keeps #9233's message rather than the "generation" sentence. @MusabMahmoodh accepted this because #9138 handles that case.
- `serve_manifest_for` still returns `None` when the file is missing. It raises only when the file exists but is wrong.
- Behaviour change: invalid JSON in `serve_manifest_for` now raises `json.JSONDecodeError`, not `RuntimeError`, because `json.loads` isn't wrapped. Valid JSON that isn't a dict gets the "unstamped" refusal.
- A stamped file without `jaclang_version` is described as "an older jac".
- The version lookup is local to `sealed_serve.jac` and imported lazily from `jaclang.cli.manifest_route`. @MusabMahmoodh preferred this over importing from `compiler/driver/jir.jac` (citing #9369). You can't tell the full import graph from the diff.
- `3486cb5` replaced an earlier `importlib.metadata.version("jaclang")` lookup with `resolve_cli_version()`, per Greptile.

## 6. How execution flows after the PR

### 6.1 Sealing an app

```text
jac build / seal
└─ build_serve_manifest(entry_file, proj_root)
   ├─ prepare app, collect per-module manifests into 'module_manifests'
   ├─ result.update(serve_manifest_stamp())                       ← NEW
   │  └─ resolve_cli_version()  (fallback "0.0.0")               ← NEW
   └─ written to .jac/serve_manifest.json  -> {"format": 3, "jaclang_version": "0.37.21", ...}
```

### 6.2 Booting a sealed app

```text
prepare_application(..., dev=False)
└─ _prepare_sealed(entry, program, image_root, entries)
   ├─ artifact manifest check (unchanged)
   ├─ read_serve_manifest(image_root)                             ← CHANGED (was inline read)
   │  ├─ file missing      -> RuntimeError "no serving manifest" (same text as before)
   │  ├─ json.loads
   │  ├─ format != 3       -> RuntimeError "built by ... reads format 3. Rebuild ..." ← NEW
   │  └─ return data
   ├─ manifest['root'] = image_root
   └─ build PreparedApplication ...
```

### 6.3 Looking up one module's serve record

```text
serve_manifest_for(path)
├─ prepared_manifest(path) is not None -> return it (no file read, unchanged)
├─ sealed_root_for(path) is None or file missing -> None
└─ read_serve_manifest(img_root)['module_manifests'].get(relative)   ← CHANGED
   └─ raises on wrong/missing format or bad JSON                     ← NEW
```

## 11. Questions your senior might ask

**Q: Why a format number instead of the jac version or `compiler_digest`?**
The digest doesn't hash `dist/seal.jac`, `server/sealed_serve.jac` or `scale/injector/bundle.jac`, so it misses real layout changes. It would also refuse sealed apps on any compiler change. Dev builds of `main` all share one version, which is how #9355 slipped through, and a version check would also refuse every patch release.

**Q: What stops someone from changing the layout and forgetting to bump?**
The writer test compares the real manifest's keys at three levels to `SERVE_MANIFEST_SHAPES[3]`. Any key change fails the test with instructions to bump if needed and record the new shape.

**Q: Why start at 3, not 2 as the issue suggested?**
The layout has already had three generations: flat, then `module_manifests` (#9088), then `surface` (#9355). @MusabMahmoodh agreed.

**Q: Didn't #9375's `persistence` and #9848's `surface` fields need a bump?**
No. `persistence` is read with `.get('persistence', ())`. The #9848 fields are optional on read, and the older `SurfaceEntry.from_dict` ignores unknown keys, per @MusabMahmoodh. Optional keys don't break old readers.

**Q: Why exact equality and not an accepted set like `MANIFEST_FORMATS_ACCEPTED`?**
Only format 3 is readable today, so the two are equivalent. An accepted set can be added when a reader learns to handle two formats.

**Q: Why doesn't a missing file get the new "built by" sentence?**
It keeps #9233's existing message. The ship-side fix for missing manifests is #9138, and @MusabMahmoodh agreed.

**Q: Does this newly break any working bundle?**
Every pre-PR bundle is unstamped and is refused. The description says released bundles were already blocked elsewhere, so only post-#9355 dev bundles are newly blocked, and they need a rebuild. That claim depends on code not in the diff.

**Q: Did `serve_manifest_for` change behaviour beyond the format check?**
Yes. Invalid JSON now raises `JSONDecodeError` instead of returning `None`. Non-dict JSON and wrong formats raise `RuntimeError`. A missing file or a missing sealed root still returns `None`, and in-memory prepared manifests skip the file entirely.

**Q: What if `resolve_cli_version()` fails?**
The stamp records `"0.0.0"`. Refusal depends only on `format`, so this affects the message, not the decision.

**Q: Is the `surface` guard in `_load_surface` now dead code?**
