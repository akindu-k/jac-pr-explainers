## 1. The short version

When jac seals an app for deployment, it writes `.jac/serve_manifest.json` into the bundle. A sealed bundle is a frozen, prebuilt copy of the app, such as a `.jab` file. At boot, jac reads this file to learn which endpoints exist and who may call them. The file's layout has changed twice: once in #9088 and once in #9355. **The file never said which layout it used, so a bundle sealed by one jac and booted by another either crashed with an unrelated error (`Error loading main.jac: 'module_manifests'`) or booted "ready" with endpoints silently missing.**

The two code paths that read this file also disagreed. `_prepare_sealed` crashed with a `KeyError`. `serve_manifest_for` quietly returned `None`.

**Your fix stamps every serve manifest with `format: 3` and the building `jaclang_version`. Both readers now go through one function, `read_serve_manifest()`. That function refuses any bundle whose format is not 3, with one sentence that names both jac versions and says to rebuild.** A test now records the key layout for format 3, so a layout change without a decision about the format number fails CI.

Example of the new refusal:
`Sealed application at w_future was built by jac 0.38.0 (serve manifest format 4); this runtime (jac 0.37.21) reads format 3. Rebuild the bundle with the jac that will run it.`

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Jac | The programming language in this repo. Files end in `.jac`. `jaclang` is its Python package. |
| Walker / endpoint | A walker is a Jac unit of work that the server can expose as an HTTP endpoint, e.g. `POST /walker/Hi`. |
| Sealing | Building an app into a frozen, deployable bundle with precompiled artifacts. Code: `dist/seal.jac`. |
| `.jab` / sealed bundle / image | The output of sealing. `image_root` / `img_root` is the folder it unpacks into. |
| jac-scale | Plugin that deploys Jac apps to Kubernetes. A builder seals with one jac, then a pod boots the bundle with possibly another jac. |
| Serve manifest (`.jac/serve_manifest.json`) | JSON in the bundle listing each module's endpoints, access rules (`surface`), client info and more. **This is where the bug is.** |
| `module_manifests` | Key added in #9088: a table of per-module records keyed by relative path, e.g. `{"main.jac": {...}}`. Before that, the file was one flat dict. |
| `surface` | Per-module key added in #9355 describing each exposed endpoint (`route`, `exposure`, `kind`, …). |
| `_precompiled/MANIFEST.json` | A sibling file in the bundle for bytecode. It already had a `format` stamp, checked by `jac0core/sealed.py`. The serve manifest did not. |
| Generation skew | The bundle was produced by one jac and is consumed by another that doesn't share its assumptions. This is the "#8753 class" of bug. |
| Format number (`SERVE_MANIFEST_FORMAT`) | An integer that names the file's layout. It is 3 in this PR: flat = 1, `module_manifests` = 2, `surface` = 3. **This is what the PR adds.** |
| `serve_manifest_stamp()` | New function. Returns `{'format': 3, 'jaclang_version': <version>}`. |
| `resolve_cli_version()` | Existing function in `jaclang.cli.manifest_route`. It gives the same version `jac --version` shows, and works with source checkouts too. |
| `read_serve_manifest(img_root)` | New function and the only file reader now. It handles the missing file, parses the JSON, checks the format, and returns the dict. |
| `_prepare_sealed` | Function in `compiler/driver/application.jac` that loads a sealed app at boot. It is reader #1. |
| `serve_manifest_for(path)` | Function in `server/sealed_serve.jac`. Returns one module's record for a file path inside a sealed image. It is reader #2. |
| `prepared_manifest(path)` | In-memory manifest from an already prepared app. `serve_manifest_for` checks it first, before any file. |
| `compiler_digest` | A hash of the compiler's input files. It was suggested as an alternative stamp and rejected (see section 9). |
| `SERVE_MANIFEST_SHAPES` / `serve_manifest_shape()` | Test-only record of the expected key names for each format, plus a helper that collects the actual key names. |
| Optional vs breaking key | Optional means old readers cope, e.g. `persistence`, read with `.get('persistence', ())`. Breaking means a rename, a removal, or a newly required key. Only breaking changes need a format bump. |

## 3. The problem, step by step

### 3.1 The setup

- **Writer:** `dist/seal.jac build_serve_manifest` builds the dict and writes it into the bundle.
- **Reader #1:** `compiler/driver/application.jac _prepare_sealed` reads it at boot and loops over `manifest['module_manifests']`.
- **Reader #2:** `server/sealed_serve.jac serve_manifest_for` reads it to answer "what is this module's record?".
- **Packer/deployer:** in jac-scale deploys, the bundle is often sealed by a different jac than the one in the pod. The issue mentions builder-sv on 0.34.x and pods on 0.37.12.

### 3.2 What went wrong: a pre-#9088 bundle (flat file) on a newer jac

```text
1. jac 0.37.11 seals app      → serve_manifest.json = {app, client, surface?, ...}  (flat, no "format")
2. Bundle shipped to pod running jac 0.37.12
3. _prepare_sealed reads file → dict has no 'module_manifests'
4. manifest['module_manifests'] → KeyError                                   ← WRONG
5. User sees "Error loading main.jac: 'module_manifests'", exit 1, crash-loop
```

@kugesan1105 reproduced this on the real 0.37.12 release.

### 3.3 What went wrong: a #9088–#9355 bundle (no `surface`) on a newer jac

```text
1. jac 0.37.21 seals app      → {module_manifests: {main.jac: {...no surface...}}}
2. Booted by a jac from main after #9355 (same version number on dev builds)
3. _prepare_sealed: 'module_manifests' exists → no error
4. Server builds routes from 'surface'          → nothing found                ← WRONG (silent)
5. Server reports ready; /walkers is empty; calling an endpoint → 405, no log line
```

The PR description says some of these cases were later caught at server start by #9369, but one case was not caught at all.

### 3.4 What went wrong: the readers disagree

```text
Same flat file, two readers:
  _prepare_sealed     → KeyError crash
  serve_manifest_for  → data.get('module_manifests', {}).get(rel) → None (silently "not sealed")  ← WRONG
```

### 3.5 What went wrong: a bundle from a newer jac

There was no way to tell. The failure appeared wherever the new layout first broke an old assumption.

### 3.6 Why it mattered

- jac-scale deploys routinely mix generations, per the issue.
- The errors never said "your bundle and runtime are from different jac versions". Users saw a `KeyError`, a `FileNotFoundError`, or a 405.
- #9088's release note said "rebuild existing artifacts", but nothing enforced it.

## 4. The idea of the fix (one sentence)

> **Stamp the layout, check it first.** The writer records a format number that changes only when the layout breaks old readers, and the single reader refuses any other number with a sentence naming both jac versions.

This is the right idea because it matches what `_precompiled/MANIFEST.json` already does. It also avoids two problems that @MusabMahmoodh spelled out. A compiler digest misses the files that own this manifest, and it would force every app to be rebuilt after any compiler change. A version number is identical across dev builds of `main`, which is how #9355 slipped through.

### 5.1 `jac/jaclang/server/sealed_serve.jac`: the format constant, the stamp, and the single reader

+def serve_manifest_stamp -> dict[str, (int | str)] {
+    import from jaclang.cli.manifest_route { resolve_cli_version }
+    try { jac_version = resolve_cli_version(); }
+    except Exception { jac_version = "0.0.0"; }          # never let stamping break a seal
+    return {'format': SERVE_MANIFEST_FORMAT, 'jaclang_version': jac_version};

+def read_serve_manifest(img_root: str) -> dict[str, any] {
+    mf = Path(img_root) / SERVE_MANIFEST_REL;

+    data = json.loads(mf.read_text(encoding="utf-8"));

+        origin = f'jac {built_by}' if built_by else 'an older jac';

+            f'(serve manifest format {meta.get("format", "unstamped")}); '
+            f'this runtime (jac {runtime}) reads format {SERVE_MANIFEST_FORMAT}. '
+            'Rebuild the bundle with the jac that will run it.');
+    }
+    return data;
+}

**What:**
- `SERVE_MANIFEST_FORMAT = 3` sits next to the path constant, with a one-line rule for when to bump it.
- `serve_manifest_stamp()` builds the stamp. It is used by the writer, by the error message, and by tests.
- `read_serve_manifest()` reads the file and refuses any format other than 3 before anything uses the content.
- `serve_manifest_for` now delegates to `read_serve_manifest()`.

**Why:** This fixes all three failures in section 3. The skew is detected at one place, with one message, and both readers share it.

**Things to notice:**
- **Only `format` decides refusal.** A bundle stamped `format: 3` by jac 0.37.20 is accepted by jac 0.37.21. The version is only used in the message. This was a deliberate choice after review.
- **The missing-file case still differs between the readers.** `serve_manifest_for` still returns `None` when the file is missing, because it checks `isfile` before calling the reader. `_prepare_sealed` raises. The description's "both readers behave the same" is true for the format check, not for a missing file.
- **Behaviour change on bad JSON.** `serve_manifest_for` used to return `None`. It now lets `json.loads` raise `JSONDecodeError`, which is not a `RuntimeError`. Your description mentions this.
- **Non-dict JSON** (for example a list) becomes `meta = {}`, so it is reported as "unstamped".
- **Unchanged paths:** the in-memory path (`prepared_manifest`) is checked first and is not gated. That is the subject of @MusabMahmoodh's still-open question about the `surface` guard.
- **No `+1` scheme.** The issue suggested starting at 2. You start at 3 because #9355 already changed the layout once. The reviewer agreed.
- **Reading the version lazily inside the function** keeps the server module from importing compiler internals (`compiler/driver/jir.jac`). The reviewer called this right and pointed to #9369 as what goes wrong otherwise. The import from `jaclang.cli.manifest_route` happens inside the function body.
- **Why `resolve_cli_version()`:** an earlier version used `importlib.metadata.version("jaclang")`. Greptile flagged that this is wrong under `JAC_DEV_SOURCE`. Commit `3486cb5` fixed it.

## 6. How execution flows after the PR

### 6.1 Sealing a bundle

```text
jac build (seal)
└─ dist/seal.jac build_serve_manifest(entry_file, proj_root)
   ├─ prepare the app, collect per-module manifests
   ├─ result = copy of entry module record
   ├─ result['module_manifests'] = {relpath: record, ...}
   ├─ result.update(serve_manifest_stamp())                      ← NEW
   │  └─ resolve_cli_version()  (fallback "0.0.0" on any error)  ← NEW
   └─ written to .jac/serve_manifest.json  → {..., "format": 3, "jaclang_version": "0.37.21"}
```

### 6.2 Booting a sealed app

```text
jac run --serve main.jac (sealed)
└─ _prepare_sealed(entry, program, image_root, entries)
   ├─ check _precompiled artifact manifest (unchanged)
   ├─ read_serve_manifest(image_root)                            ← CHANGED (was inline read)
   │  ├─ file missing?   → RuntimeError "has no serving manifest" (same text as before)
   │  ├─ json.loads
   │  ├─ format != 3?    → RuntimeError "built by <origin> (serve manifest format <n|unstamped>);
   │  │                     this runtime (jac <v>) reads format 3. Rebuild ..."  ← NEW
   │  └─ return dict
   ├─ manifest['root'] = image_root
   └─ loop module_manifests → PreparedApplication (unchanged)
```

### 6.3 Looking up one module's record

```text
serve_manifest_for(path)
├─ prepared_manifest(path) in memory? → return it (not gated)
├─ sealed_root_for(path) is None, or no serve_manifest.json? → return None   ← CHANGED (combined)
└─ read_serve_manifest(img_root)['module_manifests'].get(relative)           ← CHANGED
   ├─ bad JSON  → JSONDecodeError (was: None)                                ← behaviour change
   └─ wrong format → RuntimeError (was: None or a record)                    ← behaviour change
```

## 11. Questions your senior might ask

**Q: Why not refuse on `compiler_digest` or on the jac version?**
The digest doesn't hash `dist/seal.jac`, `server/sealed_serve.jac` or `scale/injector/bundle.jac`, so it misses layout changes. It would also block every sealed app after any compiler change. The version is the same on every dev build of `main`, which is how #9355 slipped through, and it would block every patch release.

**Q: What stops someone from changing the layout and forgetting to bump the number?**
The writer test compares the real manifest's key names at three levels with `SERVE_MANIFEST_SHAPES[3]`. Any added, removed or renamed key fails CI with an instruction to decide on a bump.

**Q: Then why didn't `persistence` (#9375) bump it?**
Its only reader uses `.get('persistence', ())`, so older readers cope without it. Bumps are for renames, removals and newly required keys. The key was still added to the recorded shape.

**Q: Why does a missing file still give the old message instead of the new one?**
That case has its own fix in #9138, which blocks shipping a bundle without the file. Keeping the #9233 text avoids changing it twice.

**Q: Can `serve_manifest_for` now crash code that used to get `None`?**
Yes, for an unstamped or wrong-format file (`RuntimeError`) or bad JSON (`JSONDecodeError`). That is intended, so the two readers agree. A missing file or a path outside a sealed image still returns `None`. The callers of `serve_manifest_for` are not in the diff, so how they handle the exception can't be checked from here.

It keeps the server module from pulling in compiler or CLI code at import time, which is the kind of coupling behind #9369. It also gives the source-aware version that Greptile asked for.
