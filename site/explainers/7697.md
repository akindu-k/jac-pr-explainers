## 1. The short version

Jac's tiered memory keeps each request's nodes in a local cache. It writes them to a shared store when the request commits. When a commit fails with a `WriteConflict`, `TieredMemory.abort` cleans up the failed attempt so a retry can start fresh.

**On `main`, that cleanup deleted every changed persistent node from the database, including shared nodes that already existed before the request started.** Example: two requests both "find-or-create" a `Hub` under `root.shared`. One wins and commits. The loser's rollback then deleted `root.shared` itself. Later requests found the shared root missing ("Shared root unavailable", per your PR description). That loses data, which is worse than a duplicate node.

**Your fix makes rollback delete a node from the database only when the failed attempt created it (`anchor.hash == 0`). Changed nodes that already existed are only evicted from the caches and reloaded on the next read.** The production change is about 11 lines in one file. You also added a 40-way concurrency regression test against SQLite and Mongo+Redis.

You deliberately left `system_root`, the node the issue was filed against, unchanged. You argue apps should use `root.shared` instead.

**Status:** The PR is **closed**. The data given does not show whether it was merged. No human reviewed it. The only review is the Greptile bot (confidence 5/5). CI on head commit `6628357` has **two failures**: `test-scale (data)` and the `Everything Passed` gate. Linked issue #7605 is closed.

## 2. Words you need to know

| Term | Simple meaning |
|---|---|
| Node / walker | Jac's graph building blocks. A node holds data. A walker is code that moves over nodes. `walker:pub` makes a walker callable over HTTP, e.g. `POST /walker/touch_hub`. |
| `++>` / `[x-->]` | `a ++> b` creates an edge from `a` to `b`. `[a-->]` lists the nodes `a` points to. |
| Anchor | The runtime wrapper around a node. It holds the id, the persistence flags, the version and the `hash`. |
| `anchor.hash` | A hash of the anchor's serialized content, taken when it was loaded or saved. `0` means the anchor has never been hashed, i.e. it was created in this attempt. The PR relies on this. |
| Dirty | An anchor whose current content no longer matches its stored `hash`, i.e. it was changed in memory. |
| jac-scale | The plugin that runs Jac apps as servers with real databases (SQLite, MongoDB, Redis). |
| `TieredMemory` | The memory layer with three tiers: `__mem__` (per-request local dict), L2 (shared cache, e.g. Redis) and L3 (the database, e.g. Mongo or SQLite). |
| L2 `invalidate` / L3 `delete` | Invalidating drops a cached copy, so the next read reloads it from L3. `delete` removes the row from the database for good. |
| OCC (optimistic concurrency control) | Writers don't lock. Each save checks that the version is still the one it read. If not, the save fails and the writer can retry. |
| CAS / version check | The "compare-and-set" save in Mongo (`_put_node_atomic`). It filters on `data.version` and raises `WriteConflict` when the version changed. |
| `WriteConflict` | The exception raised when a version check fails, e.g. `anchor 000…0 changed concurrently (expected v0, found v1)`. |
| `TieredMemory.abort` | Runs when an attempt fails. It throws away that attempt's local changes. **This is where the bug is.** |
| Find-or-create | "Look for X; if it's not there, make it." Under concurrency, several requests can all see "not there". |
| `root.shared` | The documented per-app shared root for public data. Per your description, it is loaded fresh per request via `mem.get(root_id)`. |
| `system_root` | The internal all-zeros "super root" (`00000000-…`). Per the issue, it is cached in a process-global `_process_cache` and the same object is shared by every request. |
| `on_conflict = "retry"` | Per your description, the default OCC retry setting: re-run the walker up to 5 times after a `WriteConflict`. |
| testcontainers | A Python library that starts real Mongo/Redis Docker containers for a test. |

## 3. The problem, step by step

### 3.1 The setup

- Many requests run at once. Each request has its own `__mem__`.
- They share L2 (Redis, optional) and L3 (Mongo or SQLite).
- A shared node `S` (`root.shared`) is at version v0 with no `Hub` under it.
- Each request runs find-or-create for a `Hub` under `S`.
- On `WriteConflict`, the runtime calls `abort()` and (per your description) retries the walker.

### 3.2 What went wrong: rollback deletes the shared node (any shared node)

```text
1. Request A loads S (v0, hash=h0). Request B loads S (v0, hash=h0).
2. A sees no Hub, creates HubA (hash=0), adds edge S->HubA.     S in A is dirty
3. B sees no Hub, creates HubB (hash=0), adds edge S->HubB.     S in B is dirty
4. A commits: L3 has S v1 (edge to HubA) and HubA.               OK
5. B commits: CAS on S expects v0, finds v1 -> WriteConflict.    OK (expected)
6. B's abort() walks its __mem__:
     HubB: hash==0 -> dirty -> pop, invalidate L2, delete L3     fine (never stored)
     S:    hash!=h0 -> dirty -> pop, invalidate L2, l3.delete(S) <-- WRONG: deletes A's committed S
7. L3 no longer has S. HubA is now cut off from the shared root.
8. Next request: root.shared can't be loaded -> "Shared root unavailable".
```

### 3.3 The case this PR does not change: `system_root`

The issue (#7605) is about `system_root`. According to the issue, that anchor is one shared object in `_process_cache`, injected into every request's `__mem__`. So one request's edits are visible to all others in the same process. That breaks per-request change tracking and leads to duplicates:

- 3 `Hub`s in the repro.
- 82 `CommunityHub`s and 68 `StripeEventIndex` nodes in production.

The issue also lists more causes:

- `commit()` clears `changes` before re-raising.
- The request-close commit in `jfast_api` swallows conflicts.
- The retry only wraps the walker call.

**This PR changes none of these.** Its position is that `system_root` is internal and apps should move such data to `root.shared`.

### 3.4 Why it mattered

- The issue reports production impact: 82 and 68 duplicate singletons, and 294 `WriteConflict` warnings in 15 minutes.
- The downstream report is jaseci-labs/jacBuilder#688.
- For `root.shared`, the abort bug did more than duplicate: it destroyed the shared root that every user reads from.

## 4. The idea of the fix (one sentence)

> **Rollback forgets, it doesn't destroy.** An aborted attempt may only delete database rows for nodes it created itself; any other dirty node is just dropped from the caches so it reloads fresh.

This is the right line to draw because an aborted attempt never committed anything. The only L3 rows that "belong" to it are rows for brand-new nodes. Any pre-existing row may hold another writer's committed data.

## 5. Every code change, explained

### 5.1 `jac/jaclang/runtimelib/impl/memory.impl.jac`: only delete brand-new nodes on abort

```diff
         if not anchor.persistent or not anchor.is_populated() {
             continue;
         }
-        dirty = anchor.hash == 0;
+        brand_new = anchor.hash == 0;          # NEW: remember "created in this attempt"
+        dirty = brand_new;
         if not dirty {
             try {
                 dirty = Serializer._compute_hash(anchor) != anchor.hash;
             } except Exception {
                 dirty = True;
             }
         }
-        if dirty {
-            self.__mem__.pop(id, None);
-            if self.l2 { self.l2.invalidate(id); }
-            if self.l3 { self.l3.delete(id); }    # OLD: deleted pre-existing nodes too
-        }
+        if not dirty {
+            continue;
+        }
+        self.__mem__.pop(id, None);
+        if self.l2 {
+            self.l2.invalidate(id);
+        }
+        if brand_new and self.l3 {               # NEW: L3 delete only for new nodes
+            self.l3.delete(id);
+        }
```

**What:** For each persistent, populated anchor in the request's memory:

1. If it isn't dirty, skip it.
2. If it is dirty, remove it from `__mem__` and invalidate it in L2.
3. Delete it from L3 only if `hash == 0`, meaning it was created in this attempt.

**Why:** This removes step 6's `l3.delete(S)` from the timeline in 3.2. The winner's committed `S` survives. The loser just reloads it on the next read.

**Things to notice:**
- The `if dirty {…}` block became an early `continue`. That is a style change only.
- When `_compute_hash` throws, the anchor still counts as dirty. It is no longer deleted from L3, only evicted. This is safer than before.
- L2 is still invalidated for pre-existing nodes. That may evict the winner's fresh cached copy, but the next read goes to L3, which has the right data.
- The function's beginning and end are not in the diff. I cannot see how `abort` is called or whether it runs inside the retry loop.
- `system_root` handling (`context.impl.jac`), `commit()`'s `changes.clear()`, and the `jfast_api` close path are not touched.

### 5.2 `docs/.../unreleased/jaclang/7697.bugfix.md`: release note

```diff
+- **Fix: concurrent find-or-create on a shared node no longer duplicates nodes or fails with WriteConflict**: ... a losing writer's rollback no longer deletes the shared node it was attaching to ...
```

**What:** A user-facing note for the bug fix.

**Things to notice:** The headline claims too much. The code change only stops the deletion. "No longer duplicates" and "no longer fails with WriteConflict" depend on the retry loop already existing. The issue also says the `system_root` case still duplicates and its close-path conflicts are swallowed. The note says "a shared node such as `root.shared`", which a reader could take to include `system_root`.

## 6. How execution flows after the PR

### 6.1 A losing writer aborts

```text
Request B commit
├─ CAS on S fails -> WriteConflict
└─ TieredMemory.abort()
   ├─ for each anchor in __mem__
   │  ├─ not persistent / not populated -> skip
   │  ├─ brand_new = hash == 0                       ← NEW
   │  ├─ dirty = brand_new or hash changed
   │  ├─ not dirty -> continue                        ← CHANGED (early exit)
   │  ├─ pop from __mem__, invalidate L2
   │  └─ brand_new? -> L3 delete (HubB)               ← CHANGED
   │     else      -> keep L3 row (S survives)        ← CHANGED
   └─ return
```

### 6.2 The retry (as described; this code is not in the diff)

```text
WriteConflict caught by OCC retry (on_conflict="retry", up to 5)
├─ walker re-runs
├─ root.shared re-resolved via mem.get -> loads S v1 from L3
├─ finds HubA -> no create
└─ commit succeeds -> 200, exactly one Hub
```

| Scenario | Before | After |
|---|---|---|
| Loser aborts, shared `S` was dirty | `S` deleted from L3 | `S` evicted from cache, kept in L3 |
| Loser aborts, node it created | Deleted | Deleted (same) |
| 40 concurrent find-or-create on `root.shared` | Shared root can disappear | 0 failures, 1 Hub (per your local SQLite run) |
| Same on `system_root` | Duplicates and 500s | Unchanged. Not fixed by this PR. |
| Hash computation throws on abort | Row deleted | Row kept, only evicted |

**Behaviour change users will notice:** shared roots no longer vanish after a conflict. Apps anchoring data on `system_root` must move it to `root.shared` to benefit.

## 11. Questions your senior might ask

**Q: How do you know `hash == 0` means "created in this attempt"?**
The old code already treated `hash == 0` as automatically dirty, and your description states it means never loaded or saved. I can't verify where `hash` gets set from the diff alone. Be ready to point to the load and save code that sets it.

**Q: Could a brand-new node have been committed by someone else under the same id?**
New nodes get fresh ids, so another writer shouldn't own that row. The diff doesn't show id generation, so confirm this in the code.

**Q: Why still invalidate L2 for pre-existing nodes?**
The local copy holds uncommitted edits. Dropping L2 forces the next read to load the committed version from L3. At worst this costs one extra L3 read.

**Q: Does this fix the issue as reported?**
Only partly. It fixes data loss for any shared node, and convergence for `root.shared`. `system_root` stays a process-global shared object. You chose to treat it as internal rather than fix it.

**Q: The issue says the retry wraps only the walker call, and the close-path commit swallows conflicts. Why would retry save you?**
Your description says the retry re-runs the walker and re-resolves `root.shared`. The issue's point about `jfast_api`'s close-path `finally` still stands and isn't addressed here. Be honest that this is open.

**Q: Why did `test-scale (data)` fail?**
I can't tell from the data given. The new test is in that group, so check it first.

**Q: Why not merge #7612 instead?**
#7612 is about 300 lines with a lock and clone logic, and it makes `system_root` safe for direct use. This PR fixes the general data-loss bug in about 11 lines. #7612 could be layered on top if the project wants `system_root` to be public.

**Q: Does the test cover multiple replicas?**
No. It uses one server. The issue's repro and production setup used several replicas.

**Q: What happens to an anchor whose hash computation throws?**
Before, it was deleted from L3. Now it is only evicted from the caches, so a serializer error can no longer cause data loss.
