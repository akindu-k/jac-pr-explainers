## 1. The short version

`RedisEventStream` is the jac-scale message broker built on Redis Streams. Publishers append events to a Redis key such as `jc.run.<id>`. Readers pull events through a **consumer group**, which is a bookmark that Redis stores *inside* that key. The broker keeps an in-memory set, `_ensured_groups`, that remembers "I already created this group" so it does not ask Redis again on every read.

**When Redis evicted a stream key (for example under `allkeys-lru` memory pressure), the group was destroyed along with it, but the cache still said "exists". Every later read then failed instantly with `NOGROUP`, and `consume()` returned `[]` forever.** Because the failure was instant, the read loop spun with no pause. On prod this gave ~600 ERROR lines per second per run, a pinned CPU core, and a jacBuilder chat log that froze mid-answer.

**You made the broker self-heal. On `NOGROUP` it forgets the stale cache entry, recreates the group, and retries the read once. `_ensure_group` now caches only when Redis confirms the group exists. Any read that still fails waits 0.5 s before returning, so loops can't spin.** A second commit passes each handler's `start_from` through `consumer_loop`, so a recreated group starts at the position the handler asked for. With the issue's repro, `got2` goes from `0` (bug) to `1`.

**Status:** Merged on 2026-07-15. @udithishanka approved it. All CI checks on head commit `49f2e55` passed. The release jobs were skipped. Linked issue #7487 is closed.

## 3. The problem, step by step

### 3.1 The setup

- A publisher calls `publish(topic, event)`, which runs `XADD` on the stream key.
- A reader calls `consume(topic, group, ...)`:
  1. `_ensure_group`: if `"topic::group"` is in `_ensured_groups`, skip. Otherwise run `XGROUP CREATE ... MKSTREAM` and add the key to the cache.
  2. `XREADGROUP` with `block=timeout`.
  3. On any exception, log ERROR and return `[]`.
- Background handlers run `consumer_loop`, which calls `consume` again right away in a `while` loop.

### 3.2 What went wrong: eviction (the issue's repro)

```text
1. publish("evict.topic", e.one)       Redis: key exists, no group      cache: {}
2. consume(..., "t_evict")             XGROUP CREATE ok                 cache: {"evict.topic::t_evict"}
                                       XREADGROUP -> [e.one]            got1 = 1 ✓
3. Redis evicts "evict.topic"          Redis: no key, no group          cache: still {"evict.topic::t_evict"}
4. publish(e.two)                      XADD recreates key, NO group     cache: unchanged
5. consume(...)                        _ensure_group sees cache → skip   ✗ WRONG: trusts stale cache
6.                                     XREADGROUP -> NOGROUP (instant)
7.                                     log ERROR, return []             got2 = 0 ✗
8. consumer_loop calls consume again   steps 5–7 repeat with no wait    → ~600 ERRORs/s, CPU pinned
```

### 3.3 A second way the cache got poisoned: a failed create

The old `_ensure_group` ran `self._ensured_groups.add(key)` at the end **no matter what**. That included the case where `XGROUP CREATE` failed with something other than `BUSYGROUP`.

```text
1. consume(...)          XGROUP CREATE raises e.g. a connection error   logged as warning
2.                       falls through to add(key)                      ✗ cache says "exists"
3. every later consume   skips create forever → NOGROUP forever
```

This is not the path the issue's repro hits; there the cache entry was legitimately set in step 2. It is the same kind of bug, though, and the issue's "Suggested fix" names it.

### 3.4 Why it mattered

- jacBuilder's AI-chat path is browser WS → `drain_events` → `_drain_run_events` → `broker.consume(jc.run.{run_id}, ...)`. After an eviction mid-turn, the browser stopped getting events while the agent kept working. Only a process restart fixed it.
- On prod: 77k+ ERROR lines in 15 minutes, and a pinned CPU on the coder service.
- Higher-level relay/resume logic never noticed, because `consume()` swallowed the error and returned `[]`.
- The only workaround was to avoid eviction (more `maxmemory`, or no `allkeys-lru`). The issue says this was not verified.

## 4. The idea of the fix (one sentence)

> **Don't trust the cache; heal on `NOGROUP`.** Only cache a group Redis has confirmed exists, and when a read says the group is gone, recreate it and try once more, pausing briefly if that still fails.

A missing group is a recoverable state: `XGROUP CREATE ... MKSTREAM` can always rebuild it. Fixing it inside the broker repairs every caller (jacBuilder, `consumer_loop`) at once, with no caller changes.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/events/streams/redis.jac`: cache only on success, recover on `NOGROUP`, back off on errors

**Backoff constant**

```diff
-glob _logger = logging.getLogger(__name__);
+glob _logger = logging.getLogger(__name__),
+     _CONSUME_ERROR_BACKOFF: float = 0.5;   # NEW: seconds to wait after an unrecoverable read
```

**`_ensure_group`**

```diff
+    """Create the consumer group, caching only on success or BUSYGROUP."""
+    def _ensure_group(
+        topic: str, group: str, start_from: str = "latest", force: bool = False   # NEW: force
+    ) -> None {
         key = f"{topic}::{group}";
-        if key in self._ensured_groups {
+        if not force and key in self._ensured_groups {      # NEW: force skips the cache
             return;
         }
         try {
             ...                                              # XGROUP CREATE (not shown in diff)
         } except Exception as e {
             if "BUSYGROUP" not in str(e) {
                 _logger.warning(f"XGROUP CREATE failed for {topic}/{group}: {e}");
+                self._ensured_groups.discard(key);           # NEW: forget any stale entry
+                return;                                      # NEW: don't cache a failure
             }
         }
         self._ensured_groups.add(key);                       # now reached only on success or BUSYGROUP
```

**New helpers `_xreadgroup` and `_read_group`**

```diff
+    def _xreadgroup(topic: str, group: str, max_messages: int, block_ms: int) -> any {
+        return self._get_client().xreadgroup(
+            groupname=group, consumername=self._consumer_name,
+            streams={topic: ">"}, count=max_messages, block=block_ms
+        );
+    }
+
+    """Read from the group, recreating it once if it was evicted (NOGROUP)."""
+    def _read_group(topic, group, max_messages, block_ms, start_from) -> any {
+        try {
+            return self._xreadgroup(topic, group, max_messages, block_ms);
+        } except Exception as e {
+            if "NOGROUP" not in str(e) {
+                raise;                                        # other errors go to consume()
+            }
+        }
+        _logger.warning(f"Consumer group {group} missing for {topic}; recreating");
+        self._ensure_group(topic, group, start_from, force=True);
+        return self._xreadgroup(topic, group, max_messages, block_ms);   # one retry
+    }
```

**`consume`**

```diff
         self._ensure_group(topic, grp, start_from);
         block_ms = max(1, int(timeout_seconds * 1000));
         try {
-            result = self._get_client().xreadgroup(...);
+            result = self._read_group(topic, grp, max_messages, block_ms, start_from);  # NEW
         } except Exception as e {
             _logger.error(f"XREADGROUP failed for {topic}/{grp}: {e}");
+            wait_or_stop(self, _CONSUME_ERROR_BACKOFF);       # NEW: pace failures
             return [];
         }
```

**`register_handler`**

```diff
         def _loop {
-            consumer_loop(broker, topic, grp, handler, retry_policy);
+            consumer_loop(broker, topic, grp, handler, retry_policy, start_from);
         }
```

**What:**
- The cache now holds only groups Redis confirmed: a clean create or `BUSYGROUP`.
- A `NOGROUP` read triggers a forced recreate and one retry.
- Any read that still fails waits up to 0.5 s before returning `[]`.
- Background handlers now pass their `start_from` down.

**Why:**
- The `_ensure_group` change fixes the failed-create poisoning (3.3).
- `_read_group` fixes the eviction case (3.2), where the cache entry was valid when written but went stale later.
- The backoff stops the hot loop when recovery isn't possible.

**Things to notice:**
- `MKSTREAM` is not visible in the diff, because the `XGROUP CREATE` call sits in an unchanged hidden line. The PR description and @udithishanka both say it is used.
- `force=True` does not clear the cache first. It skips the cache check. If the forced create fails, the `discard` removes the stale entry. The retry then raises `NOGROUP`, which reaches `consume`'s `except` (error log + backoff). The next `consume` tries a fresh create.
- If two broker instances recover at once, the second gets `BUSYGROUP`, which counts as success. That is safe.
- Behaviour change: the 0.5 s backoff applies to **every** read error that reaches `consume`, not just `NOGROUP`. A connection error, for example, now also waits 0.5 s.
- Error detection is a string match (`"NOGROUP" in str(e)`). @udithishanka called this fragile but consistent with redis-py convention.
- Only one retry, so recovery cannot loop.
- Recovery restores delivery from the recreated stream only. Events lost in the eviction stay lost.

### 5.2 `jac/jaclang/scale/events/streams/_stream_common.jac`: `consumer_loop` takes `start_from`

```diff
     handler: Callable[[Event], any],
-    retry: RetryPolicy
+    retry: RetryPolicy,
+    start_from: str = "latest"                       # NEW, defaults to the old behaviour
 ) -> None {
     while not broker._stop_event.is_set() {
         events = broker.consume(
-            topic, group=group, max_messages=10, timeout_seconds=5.0
+            topic, group=group, max_messages=10, timeout_seconds=5.0,
+            start_from=start_from                    # NEW: forwarded
         );
```

**What:** `consumer_loop` passes the handler's `start_from` to every `consume` call.

**Why:** Previously the handler's `start_from` was never passed to `consume`, so the loop always used `"latest"`. That made no difference while the group existed, because `start_from` only matters when a group is created. With the new recovery path, a handler registered with `"earliest"` would have its group recreated at `$` and would drop entries already in the re-created stream. Greptile flagged this.

**Things to notice:** The default keeps the old behaviour for any caller that doesn't pass the argument.

### 5.3 `jac/jaclang/scale/events/streams/local.jac`: same call-site update

```diff
-            consumer_loop(broker, topic, grp, handler, retry_policy);
+            consumer_loop(broker, topic, grp, handler, retry_policy, start_from);
```

**What / Why:** This keeps the in-memory broker consistent with the new `consumer_loop` signature. The PR says behaviour is unchanged because the local broker cannot be evicted. Whether `LocalEventStream.consume` actually uses `start_from` can't be seen from the diff.

## 6. How execution flows after the PR

### 6.1 Calling `consume` directly

```text
consume(topic, group, max_messages, timeout_seconds, start_from)
├─ _ensure_group(topic, grp, start_from)
│  ├─ in cache? → return
│  └─ XGROUP CREATE
│     ├─ ok / BUSYGROUP → add to cache
│     └─ other error → warn, discard key, return            ← CHANGED
├─ block_ms = max(1, timeout*1000)
├─ _read_group(...)                                          ← NEW
│  ├─ _xreadgroup(...) ok → result
│  ├─ error without "NOGROUP" → re-raise
│  └─ NOGROUP
│     ├─ warn "Consumer group ... missing; recreating"       ← NEW
│     ├─ _ensure_group(..., force=True)                      ← NEW
│     └─ _xreadgroup(...) again (one retry)                  ← NEW
├─ on any exception from _read_group
│  ├─ log ERROR
│  ├─ wait_or_stop(self, 0.5)                                ← NEW
│  └─ return []
└─ convert entries → list[Event]
```

### 6.2 Background handler

```text
register_handler(topic, handler, group, retry, start_from)
└─ Thread → _loop
   └─ consumer_loop(broker, topic, grp, handler, retry_policy, start_from)   ← CHANGED
      └─ while not stopped:
         ├─ consume(..., start_from=start_from)                              ← CHANGED
         └─ handle each event
```

| Scenario | Before | After |
|---|---|---|
| Normal read, group exists | Delivers | Delivers (same path, no added latency) |
| Read times out, no data | `[]` after `block` | Same |
| Key evicted, then re-published | `NOGROUP` forever, hot loop | One warning, group recreated, event delivered |
| Key evicted, not re-published | `NOGROUP` forever | `MKSTREAM` makes an empty stream; the retry blocks normally |
| `XGROUP CREATE` fails (non-BUSYGROUP) | Cached as "exists" forever | Not cached, retried on next call |
| Recovery fails, or another read error | `[]` immediately, hot loop | `[]` after up to 0.5 s |
| `"earliest"` handler recovers after eviction | (no recovery at all) | Group recreated at earliest |

Changes users will notice:
- Evicted streams now resume delivery instead of dying.
- A new WARNING line, "Consumer group ... missing; recreating", appears when recovery happens.
- Failing reads now return after up to 0.5 s instead of instantly.

## 11. Questions your senior might ask

**Q: Why did the issue's repro fail if the old `_ensure_group` only mis-cached failed creates?**
In the repro the cache entry was valid when written in step 2. It went stale when the key was evicted, and nothing ever invalidated it. The `_ensure_group` change alone wouldn't fix that. `_read_group`'s `NOGROUP` recovery is what fixes it.

**Q: Why recover in `_read_group` instead of checking that the group exists before every read?**
A pre-check would add a Redis round-trip to every `consume`. Reacting to `NOGROUP` costs nothing on the happy path and only does extra work when the group is really gone.

**Q: Why retry only once?**
It keeps `consume` bounded. If the forced create or the retry fails, the error reaches `consume`, which waits 0.5 s and returns `[]`. The next call starts fresh because the failed create was not cached.

**Q: What if two pods hit `NOGROUP` at the same time?**
One create succeeds. The other gets `BUSYGROUP`, which counts as success and is cached. Both retries then read from the same group.

**Q: Does recovery lose or duplicate messages?**
Messages in the evicted key are gone; that is inherent, as @udithishanka noted. The recreated group reads from the new stream at `start_from`. That is why threading `start_from` through `consumer_loop` matters for `"earliest"` handlers. The diff doesn't show evidence of duplicates.

**Q: Does the backoff slow normal consumers?**
No. It only runs inside the `except` branch. Empty or timed-out reads return as before. Non-`NOGROUP` errors such as connection failures now also wait up to 0.5 s, which is intended pacing.

**Q: Why match on the string `"NOGROUP"`?**
redis-py has no dedicated exception class for it, and the code already matched `"BUSYGROUP"` the same way. The reviewer accepted it as a known fragility.

**Q: Why change `local.jac` if it can't be evicted?**
`consumer_loop` is shared, and both brokers' `register_handler` call it. Passing `start_from` keeps them consistent. `test_local_stream.jac` (8 tests) still passes.

**Q: Is `_ensured_groups` thread-safe across handler threads?**
The diff doesn't show. The PR only adds `discard` and `add` calls on the existing set and doesn't change locking.

**Q: How was this verified beyond unit tests?**
You and @udithishanka both ran the issue's repro against Redis 7: `got2=0` with a `NOGROUP` flood on `main`, versus `got2=1` with one warning on this branch. CI ran the new Redis test in the scale suites.
