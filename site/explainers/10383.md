## 1. The short version

On the Kubernetes target, every `jac start --scale` deploy uploads the app's code as a bundle file (and sometimes a toolchain tarball) onto a shared volume called `<app>-bundles`. Pods unpack the file their revision names. Older revisions keep their files so you can roll back to them.

**Nothing ever deleted a bundle, so the volume grew by one bundle per deploy, forever.** In the issue, one app (`jac-builder-dev`) had 551 unreferenced files taking 89,999 MB. A second bug sat underneath. The function that lists which bundles are still in use could return an empty set when the cluster was only partly readable. A pruner would read that empty set as "delete everything", including the live bundle.

**You now prune during seeding: before uploading, `seed()` deletes every file under `bundles/<app>/` and `toolchain/<app>/` that is not in the "keep-set" (retained revisions plus Deployment templates plus this deploy's own files). It skips the prune when the keep-set is empty or unreadable.** You also made the keep-set strict. A failed Deployment list or ReplicaSet read now raises an error instead of quietly returning less. In a later commit you added Deployment templates to the keep-set, after a review comment from the Greptile bot.

**Status:** Open. No human review yet. The only review is from @greptile-apps[bot], and its one inline comment is addressed by commit c00996b. On the head commit, `jac-check` failed, so the aggregate `Everything Passed` check also failed. All test jobs passed.

## 3. The problem, step by step

### 3.1 The setup

- `KubernetesTarget.apply_manifests` calls `injector.seed(app, namespace)`.
- `PvcInjector.seed` starts the loader pod and uploads any artifact whose digest is not already on the volume. Then it removes the pod.
- The new Deployment is applied, Kubernetes cuts a new ReplicaSet, and old ReplicaSets beyond `revision_history_limit` are deleted.
- `referenced_bundle_keys` could already compute the keep-set, but nothing called it to delete anything.

### 3.2 What went wrong: the volume only grows

```text
1. Deploy #1: seed writes bundles/app/A.jab            volume = {A}
2. Deploy #2: seed writes B.jab                         volume = {A, B}
...
12. Deploy #12: RS for A falls out of history (limit 10)
    keep-set = {B..L}                                   volume = {A..L}
    ✗ A is unreferenced but nothing deletes it
13. Deploy #639 on jac-builder-dev                      volume ≈ 90 GB, 13 referenced
14. An interrupted upload leaves B.jab.41.part          ✗ never removed either
```

### 3.3 What went wrong: an empty "strict" keep-set

```text
1. referenced_bundle_keys(app) runs in strict mode
2. _fleet_deployment_names → list Deployments → RBAC error   (RBAC = permissions)
3. ✗ exception swallowed, returns []                          owned names = []
4. ReplicaSet list succeeds, but no RS belongs to a name in [] 
5. keep-set = {}  (should have raised)
6. a pruner reads {} as "nothing referenced" → deletes the live bundle
```

The same kind of gap existed in `_revision_entries`. A failure reading one ReplicaSet hit `continue`, so that ReplicaSet's key silently dropped out of the keep-set.

### 3.4 What went wrong: a Deployment ahead of its ReplicaSet (found in review)

This case comes from @greptile-apps[bot]'s comment on the first commit:

```text
1. Older RS references A; deploy of B is interrupted
2. Deployment template asks for B, but the controller has not yet created B's RS
3. Next deploy (C): keep-set from ReplicaSets only = {A}, plus seeded {C}
4. ✗ prune deletes B
5. If deploy C then fails during upload, the Deployment still wants B → new pods can't start
```

### 3.5 Why it mattered

- Every jac-scale app on Kubernetes is affected, in proportion to how often it deploys. CI-driven apps deploy once per merge.
- The issue estimates about $27/month on EFS for one app, growing about 0.5 GB per deploy.
- jacBuilder was writing its own pruner that parses jac-scale's init-container args. That ties it to the current arg format, which has already changed on `main` (`jac-pvc-bootstrap` → `jac-bootstrap`).
- The issue asks for a 0.34.x backport too.

## 4. The idea of the fix (one sentence)

> **Prune inside `seed`, using a strict keep-set, and never prune blind.** Before uploading, the loader pod deletes every file in this app's bundle and toolchain folders that no retained revision, no Deployment template and no file in this deploy refers to, and the prune is skipped when that set is empty or could not be read.

Doing it in `seed` reuses a pod that already mounts the volume, so no second pod is needed. Making the keep-set strict is what makes deletion safe: a wrong answer now fails loudly instead of meaning "delete everything".

**What:** Once the loader pod is running and before any upload, `seed` runs one shell command in the pod. The command walks the top-level entries of `bundles/<app>/` and `toolchain/<app>/`. It deletes each regular file whose relative path is not in the keep-set. The keep-set is the `retained` argument plus every key this deploy is about to seed.

**Why:** This is the missing "delete what is not referenced" half of the retention contract (section 3.2). `.part` files never match a key, so they are removed too.

**Things to notice:**
- The keep-set is matched as a space-padded string (`*" $f "*`). That works because keys are sha-named paths with no spaces.
- `app_name` is placed into the glob unquoted. It comes from `k8s_safe_name(...)` in `apply_manifests`, which is presumably DNS-safe. The diff does not show `k8s_safe_name`.
- The glob is one level deep and `-f` skips directories, so nothing is deleted recursively. `.cache/` and other apps' folders are outside the glob. If a folder is empty, the glob stays literal, `-f` fails, and nothing happens.
- This deploy's own artifacts are added to the keep-set on purpose. The upload loop skips digests that already exist, so a reused bundle must not be deleted just before that check.
- `if retained` treats both `None` and `set()` as "skip". That covers the first deploy and the unreadable case.
- Only `RuntimeError` from the exec is caught. That is what `run_kubectl_command` raises in the test fake. Whether it can raise other types in real use can't be told from the diff.
- Pruning happens before the upload. If the upload then fails, unreferenced files are already gone, but everything referenced, including Deployment templates since c00996b, is kept.

```text

├─ injector present?
│  ├─ referenced_bundle_keys(app)                         ← CHANGED (strict + templates)
│  │  ├─ success → retained = {keys}
│  │  └─ any exception → emit "skipping bundle prune…", retained = {}   ← NEW
│  └─ injector.seed(safe_app, namespace, retained)        ← CHANGED (3rd arg)
│     ├─ create loader pod, wait for Running
│     ├─ if retained non-empty:                           ← NEW
│     │  ├─ keep = retained ∪ this deploy's keys
│     │  ├─ kubectl exec … sh -c prune_unreferenced_script(app, keep)
│     │  │  └─ for f in bundles/app/* toolchain/app/*: rm if file and not kept
│     │  └─ RuntimeError → logger.warning, continue
│     ├─ upload artifacts not already present (unchanged)
│     └─ delete loader pod
```

```text

├─ _revision_entries(strict=True)                         (call not shown in diff)
```

### 6.3 `list_revisions` / `rollback_to`

These are unchanged. They still use lenient mode, so an unreadable cluster gives an empty history rather than an error. The test checks this.

| Scenario | Before | After |
|---|---|---|
| Normal deploy, old bundles out of history | Kept forever | Deleted on this deploy |
| Stale `.part` from an interrupted upload | Kept forever | Deleted |
| First deploy (no revisions) | No prune | No prune (empty keep-set) |
| Deployment list forbidden (RBAC) | Strict keep-set returned `{}` | Raises → warning, prune skipped |
| One RS unreadable | Its key silently missing | Raises → prune skipped |
| Deployment template ahead of its RS | Not counted (would be deleted by a prune) | Kept |
| `kubectl exec` prune fails | n/a | Warning, deploy continues |
| `.cache/`, other apps' folders | Untouched | Untouched |

**Behaviour change users will notice:** the bundle PVC stops growing. On the first deploy after upgrading, a large backlog may be deleted in one go (for example about 90 GB for `jac-builder-dev`). After that, the size stays near the retained revisions plus one.

## 11. Questions your senior might ask

**Q: Why prune in `seed` and not after "Fleet is ready", as the issue suggested?**
A: `seed` already has a running loader pod that mounts the PVC, so pruning costs one `exec`. After rollout, a second pod or Job would be needed. Kubernetes also removes old ReplicaSets asynchronously, so neither point is exact. A bundle that drops out of history is removed on the next deploy.

**Q: Can this delete the bundle the live pods are using?**
A: The keep-set is read before the new Deployment is applied. The live bundle is in the live Deployment's template and its ReplicaSet, so it is in the keep-set. If the read fails or returns empty, the prune is skipped.

**Q: Why add this deploy's own keys to the keep-set?**
A: `seed` skips uploading a digest that already exists. Without those keys, the prune could delete a file this deploy is about to reuse. The upload would then redo it, or worse, not happen if the check had already run.

**Q: What happens when the Deployment list is forbidden by RBAC?**
A: `_fleet_deployment_names` (strict) raises, and so does the new template loop. `apply_manifests` catches the error, emits "skipping bundle prune, revisions unreadable", and seeds without pruning. `list_revisions` still returns `[]` (lenient).

**Q: Are toolchain tarballs protected for retained revisions?**
A: Only if `bundle_keys_from_pod_spec` extracts `.tar.gz` keys. Its body isn't in this diff, and the tests only check `.jab` keys from the cluster side. This should be confirmed before merge.

**Q: What about two deploys of the same app at once?**
A: One deploy's prune can delete a bundle (or a `.part` file) the other just seeded but hasn't applied. The description accepts this risk, because concurrent same-app deploys already clash on the shared `<app>-bundle-loader` pod.

**Q: Does a failed prune fail the deploy?**
A: No. A `RuntimeError` from the `kubectl exec` is logged as a warning and the upload continues. Other exception types are not caught there.

**Q: Could the shell script delete outside the app's folders?**
A: The script `cd`s to the mount path and only globs `bundles/<app>/*` and `toolchain/<app>/*`, top level only, and only regular files. The keep-set string is `shlex.quote`d. `app_name` is not quoted, but it comes from `k8s_safe_name`.

**Q: What will users see on the first deploy after upgrading?**
A: A one-time cleanup of the whole backlog. For example, about 90 GB on `jac-builder-dev`. After that the volume stays at roughly the retained revisions plus one.

**Q: Why is `jac-check` red?**
A: The log isn't in the data, so you need to open it. All test jobs passed, so it is most likely a static or type/format issue in the changed files, not a behaviour problem.
