## 1. The short version

On Kubernetes, every `jac start --scale` deploy uploads a **bundle** (a packed copy of the app) to a shared disk called `<app>-bundles`. Pods unpack the bundle their version names when they start. When the toolchain changes, the deploy also uploads a toolchain tarball to the same disk.

**Nothing ever deleted these files, so the disk grew by one bundle per deploy, forever.** In issue #10095 one app (`jac-builder-dev`) held 551 unused files, about 90 GB, while only 13 were still referenced. There was also a hidden trap. If the cluster refused to list Deployments, `_fleet_deployment_names` swallowed the error and returned `[]`. The "which bundles are in use" answer could then come back empty, and a naive clean-up would read that as "delete everything".

**Your fix: each deploy now builds a "keep list" of every bundle that a retained revision or a current Deployment template names, plus the bundle being uploaded. It then deletes every other file under `bundles/<app>/` and `toolchain/<app>/`. If the list can't be read, or is empty, it deletes nothing.** The delete runs inside the loader pod that `PvcInjector.seed` already starts, just before the upload. Each removed file prints `pruned <file>`.

**Status:** Open. @udithishanka requested changes and has not re-reviewed since your replies. @MusabMahmoodh left a comment review. On the head commit `85cf7e1`, nothing has failed, but `build-kit` is still running and the main test `suite` was skipped.

## 3. The problem, step by step

### 3.1 The setup

- **`KubernetesTarget.apply_manifests`** runs during a deploy. It calls `injector.seed(...)` and then applies the Kubernetes objects.
- **`PvcInjector.seed`** creates the loader pod, waits for `Running`, and copies `bundles/<app>/<sha>.jab` (and maybe a toolchain) onto the PVC. Before this PR, its only check was whether that exact file already existed.
- **`referenced_bundle_keys`** already computed which bundles retained revisions use. The 0.34.17 release notes promised "a bundle referenced by a retained revision is never deleted". Nothing ever deleted anything, so only half of that promise was written.

### 3.2 What went wrong

#### Case 1: the disk only grows

```text
1. Deploy 1 of shop  -> PVC: {b1.jab}                         RS kept: [b1]
2. Deploy 2          -> PVC: {b1, b2}                         RS kept: [b1, b2]
3. Deploy 3          -> PVC: {b1, b2, b3}                     RS kept: [b2, b3] (limit 2)
4. Deploy 4          -> PVC: {b1, b2, b3, b4}                 RS kept: [b3, b4]
5. Deploy 5          -> PVC: {b1..b5}                         RS kept: [b4, b5]
   ✗ WRONG: b1, b2, b3 are named by no template, but stay on disk forever
6. Interrupted upload -> b6.jab.41.part also stays forever
7. After 639 deploys (jac-builder-dev): 551 dead files, ~90 GB
```

#### Case 2: the hidden trap (an empty keep set from an unreadable cluster)

```text
1. referenced_bundle_keys("shop") runs in strict mode
2. _owned_replica_sets(strict=True) calls _fleet_deployment_names(apps_v1, ns)   (no strict flag existed)
3. list_namespaced_deployment raises "deployments is forbidden: RBAC"
4. _fleet_deployment_names catches it and returns []
   ✗ WRONG: the error is gone
5. ReplicaSet list succeeds, but no RS is owned by a known Deployment -> nothing kept
   (the per-RS read in _revision_entries also did `continue` on any error)
6. referenced_bundle_keys returns set()   -> "no bundle is in use"
7. A pruner trusting that answer would delete every bundle, including the live one
```

Before the PR, nothing pruned, so this trap was harmless. Any prune built on top of it would have been dangerous, which is why the PR fixes it first.

#### Case 3: a Deployment asks for a bundle that has no ReplicaSet yet

@greptile-apps raised this against an early version of the PR, where the keep set came only from ReplicaSets:

```text
1. RS history names bundle A; the Deployment template was patched to bundle B,
   but the controller has not created B's ReplicaSet yet (e.g. an interrupted deploy)
2. Next deploy uploads C; keep set = RS keys {A} + new {C}
   ✗ WRONG: B is not on the list -> pruned
3. If this deploy then fails, the Deployment still asks for B -> new pods can't start
```

### 3.3 Why it mattered

- **Cost:** on EFS at about $0.30/GB-month, `jac-builder-dev` alone cost about $27/month in dead files and grew by about 0.5 GB per deploy. Every jac-scale app on Kubernetes is affected in proportion to how often it deploys. CI-deployed apps, which deploy once per merge, are hit hardest.
- **Workarounds were fragile:** jacBuilder had to parse jac-scale's init-container args itself and delete files from outside. On `main` the unpack moved from `jac-pvc-bootstrap` into `jac-bootstrap`, so a reader that only looks at the old container would find nothing. The issue says that would silently stop the pruning (not tested).
- **Safety:** without the strict fix, the first real pruner could wipe the live bundle after a single RBAC hiccup (a permissions error from the cluster).

---

## 4. The idea of the fix (one sentence)

> **Delete only what no template names, and delete nothing when unsure.** On each deploy, inside the loader pod that is already running, remove every file under the app's `bundles/` and `toolchain/` folders that no retained ReplicaSet, current Deployment template, or the new upload references, and skip the clean-up entirely if that list is empty or can't be read.

Age is never the reason to delete; only "nobody names it" is. That makes the rule match the retention promise exactly, and rollbacks keep working. Reusing the existing loader pod means no new pod or Job is needed.

### 5.1 `jac/jaclang/scale/injector/impl/pvc_injector.impl.jac`: the prune script and the prune step in `seed`

```diff
+impl prune_unreferenced_script(app_name: str, keep: set[str]) -> str {
+    import shlex;
+    kept = shlex.quote(" " + " ".join(sorted(keep)) + " ");   # NEW: " k1 k2 k3 ", shell-safe
+    return (
+        f"cd {BUNDLE_MOUNT_PATH} && keep={kept} && "
+        f"for f in bundles/{app_name}/* toolchain/{app_name}/*; do "   # NEW: only this app's folders
+        'case "$keep" in *" $f "*) ;; '                                 # on the list -> do nothing
+        '*) [ ! -f "$f" ] || { rm -f "$f" && echo "pruned $f"; };; esac; done'  # else delete + log
+    );
+}
```

**What:** `seed` now takes an optional `keep_set` function. After the loader pod is Running, it calls that function. If the result is empty, it logs and skips. Otherwise it adds this deploy's own artifacts to the list and runs one `kubectl exec` with a shell loop. The loop walks `bundles/<app>/*` and `toolchain/<app>/*`, keeps every path that is on the list, and deletes and echoes every other regular file. After that, the old upload loop runs as before.

**Why:** this fixes Case 1, the disk only growing. Reading the list after `wait_for_pod_phase` comes from @MusabMahmoodh's race comment. The `echo "pruned $f"` and the `logger.info` come from @udithishanka's nit.

**Things to notice:**
- The list is space-separated, with a space at each end, so `*" $f "*` matches whole keys only. A key that is a prefix of another key does not match by accident. `shlex.quote` keeps the shell from interpreting the keys. Keys are hashes, so they contain no spaces.
- `[ ! -f "$f" ] || ...` skips anything that isn't a regular file. That covers sub-folders, and also the literal unexpanded `bundles/x/*` the shell leaves when a folder is empty.
- `*` does not match dotfiles. That is fine here, because bundle and `.part` names don't start with a dot.
- `.part` leftovers are deleted because no template names them, which closes the issue's point about stale `.part` files.
- Other apps' folders and `.cache/` (the pip cache) are never in the glob.
- A failed prune (`RuntimeError`) only logs a warning, and the upload still runs. That matches the issue's "best-effort" requirement.
- If `keep_set()` itself raised, that error would not be caught by the inner `try`. `KubernetesTarget._bundle_keep_set` never raises, so this only matters for other callers.
- Each deploy's own artifacts are always kept. This protects a redeploy whose bundle already sits on the disk under the same hash.
- This prunes **before** the upload and rollout. The issue suggested pruning after `"Fleet is ready"`. You chose the earlier point so you could reuse the loader pod; section 11 covers why it is safe.

## 6. How execution flows after the PR

### 6.1 A deploy seeds the bundle volume

```text
jac start --scale  (Kubernetes target)
└─ KubernetesTarget.apply_manifests(bundle)
   └─ injector.seed(safe_app, namespace, self._kubectl, self._bundle_keep_set)   ← CHANGED (4th arg)
      ├─ create loader pod <app>-bundle-loader
      ├─ wait_for_pod_phase(... {"Running"})
      ├─ retained = keep_set()                                                ← NEW (see 6.2)
      ├─ if retained is empty
      │    └─ logger.info("no retained bundle keys; skipping the prune.")     ← NEW
      ├─ else
      │    ├─ keep = retained ∪ this deploy's artifact keys                   ← NEW
      │    └─ kubectl exec loader -- sh -c prune_unreferenced_script(...)     ← NEW (see 6.3)
      │         └─ on RuntimeError: logger.warning(...), carry on             ← NEW
      ├─ upload loop: kubectl cp each artifact (unchanged)
      └─ loader pod torn down (unchanged)
   └─ apply Deployments → rollout (unchanged)
```

### 6.2 Building the keep set

```text
KubernetesTarget._bundle_keep_set()                                     ← NEW
└─ referenced_bundle_keys(app_name)
   ├─ _revision_entries(strict=True)
   │   ├─ _owned_replica_sets(strict=True)
```

```text
for f in bundles/<app>/* toolchain/<app>/*
├─ " $f " appears in " k1 k2 ... "  → keep
└─ otherwise
   ├─ not a regular file → skip
   └─ rm -f "$f" && echo "pruned $f"     (printed in the deploy output)
```

### 6.4 Lenient readers (unchanged)

```text
list_revisions / rollback_to
└─ strict=False → unreadable cluster still yields [] (no raise)
```

| Scenario | Before | After |
|---|---|---|
| Normal redeploy, cluster readable | All old files stay | Files no template names are deleted, with `pruned ...` lines |
| First deploy (nothing retained) | Upload only | Log "skipping the prune", upload only |
| RBAC denies ReplicaSet or Deployment list | Nothing deleted (no pruner existed) | Warn event "skipping bundle prune", nothing deleted, deploy continues |

| `referenced_bundle_keys` with Deployments unreadable | Could return a too-small or empty set | Raises |

**Behaviour users will notice:** old bundle files disappear from the PVC; deploy logs gain `pruned bundles/<app>/<sha>.jab` lines; a new warning event appears when the cluster can't be read. You can no longer roll back to a revision outside the retained history, which was already the documented contract.

### 7.1 `test_superseded_deployment_reap.jac`

- what `referenced_bundle_keys` returns, or `None` if it raised;

## 11. Questions your senior might ask

**Q: Why prune before the upload instead of after the rollout succeeds, as the issue suggested?**
`seed` already has a running pod with the PVC mounted, and the issue noted that pruning after the rollout would need its own pod or Job. It's safe early because the keep list covers every retained ReplicaSet, every current Deployment template, and this deploy's own artifacts. If the rollout then fails, everything any template still names is on disk.

**Q: What stops a cluster permissions error from wiping the live bundle?**
Two things. First, strict mode now raises instead of returning `[]` (`_fleet_deployment_names`, the per-RS read, and the new Deployment listing). Second, `_bundle_keep_set` turns that error into a warning plus `set()`, and `seed` treats an empty set as "skip". The `replicasets` and `deployments` test rows check this.

**Q: Why is an empty keep set "skip" and not "delete everything"?**
From the caller's side you can't tell an empty set apart from a failed read, and on a first deploy there is nothing to clean anyway. The rule from the issue is "never prune on an empty or failed keep-set".

**Q: Can two concurrent deploys still delete each other's bundle?**
Yes, in a narrow window. One deploy could change the Deployments between another deploy's keep-set read and its `exec`. Reading after `wait_for_pod_phase` shrinks that window to one `exec`, and same-app deploys already collide on the shared `<app>-bundle-loader` pod.

**Q: How do we know rollback still works after pruning?**
The new e2e stage uses `revision_history_limit=1`, does three code redeploys, requires a `pruned bundles/` line, rolls back to the retained release, waits for the rollout, and checks the live bundle digest. It passed on kind on your fork. It runs nightly, not in PR CI.

**Q: Could the prune touch another app or the pip cache?**
No. The loop only globs `bundles/<app>/*` and `toolchain/<app>/*`, and only deletes regular files. The unit test keeps `bundles/billing/old.jab` and `.cache/pip/wheel` and asserts they survive.

**Q: Why both the `strict` flag on `_fleet_deployment_names` and a direct Deployment listing in `referenced_bundle_keys`?**
The flag fixes the trap at its source, so ReplicaSet ownership is never computed from a fake empty list. The direct listing exists to keep pending templates' bundles (Case 3). Because that listing also raises, the "deployments" test row doesn't prove the flag on its own.

**Q: Does this change what SDK users see from `ScaleClient.bundle_keys`?**
Likely yes. The issue says it uses the same keep set, so it would now include pending Deployment template keys and raise when Deployments can't be read. The call path isn't in this diff, so confirm it in the code.

**Q: How large will the disk stay?**
About `revision_history_limit` retained bundles (default 10), plus the live one, any pending template's bundle and the new upload, each with its toolchain if it changed. With the issue's sizes (about 345 MB per bundle, about 143 MB per toolchain), that is a few GB instead of 90.

**Q: What about the 0.34 line that jacBuilder uses?**
Not in this PR. The description says it will be a cherry-pick after this merges.
