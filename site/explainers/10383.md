## 1. The short version

On the Kubernetes target, every `jac start --scale` deploy uploads a **bundle** (a `.jab` file holding the app code, named by a hash of its contents) into the app's `<app>-bundles` volume. When the toolchain changes, it also uploads a toolchain tarball. Pods unpack only the bundle their revision names. Older revisions are kept for rollback.

**Nothing ever deleted a bundle, so the volume grew by one bundle per deploy forever.** One app in issue #10095 held 551 dead files, about 90 GB on EFS. A second, hidden bug sat underneath: `_fleet_deployment_names` turned a failed Deployment list into `[]`. As a result, the "strict" keep-set could come back empty instead of raising. Any pruner would read that as "delete everything".

**You now prune inside `PvcInjector.seed`. After the loader pod is Running, one `exec` deletes every file under `bundles/<app>/` and `toolchain/<app>/` that no Deployment template, retained ReplicaSet or current seed names.** The keep-set read is now strict. An empty keep-set skips the prune, and an unreadable one warns and skips. A failed prune only logs a warning. Each deleted file shows up in the deploy log as `pruned bundles/shop/b1.jab`.

**Status:** Open. @udithishanka requested changes and has not re-reviewed since your fixes. @MusabMahmoodh left a "commented" review. On head commit `f42d70c`, `build-kit` and the `Everything Passed` gate fail, and almost every test job, including `jac-check` and `test-scale`, was skipped.

## 3. The problem, step by step

### 3.1 The setup

- `KubernetesTarget.apply_manifests` calls `injector.seed(...)`. `seed` starts the loader pod and uploads the new bundle to `bundles/<app>/<sha>.jab`. Its only check is whether that exact file already exists.
- Pod templates on Deployments and ReplicaSets name the bundle to unpack, for example `/jac-bundles/bundles/shop/b5.jab`.
- `referenced_bundle_keys` already computed the keep-set from ReplicaSets (0.34.17 "retention contract"). Nothing used it to delete anything.

### 3.2 What went wrong: the volume only grows

```text
1. deploy #1  -> seed writes bundles/shop/b1.jab        volume: b1
2. deploy #2  -> seed writes b2                         volume: b1 b2
3. deploy #3  -> seed writes b3; RS history keeps b2,b3 volume: b1 b2 b3
   ...
4. deploy #639 -> history (limit 10) references ~11     volume: ~639 bundles
   ✗ no code path deletes b1..b628, plus any .part leftovers
```

### 3.3 What went wrong: the "strict" keep-set could be empty

This is the case that would have made a naive pruner dangerous.

```text
1. referenced_bundle_keys -> _revision_entries(strict=True)
2.   -> _owned_replica_sets(strict=True)
3.     -> _fleet_deployment_names(apps_v1, ns)        # no strict parameter
4.        list Deployments raises "forbidden: RBAC"
5.        ✗ except Exception: return []                # error swallowed
6.     owned = []; list ReplicaSets succeeds
7.     every RS is filtered out (no owner in [])
8. keys = set()                                        # looks like a valid answer
9. a pruner reads set() as "nothing referenced"
   ✗ it would delete the live bundle
```

The per-ReplicaSet read in `_revision_entries` also did `continue` on error even in strict mode. That would silently drop one revision's keys.

### 3.4 What went wrong: a requested bundle with no ReplicaSet yet

This was raised by Greptile on the first version of this PR.

```text
1. ReplicaSets reference A; deploy of B patches the Deployment, then is interrupted
2. Deployment template names B; its controller has not created B's RS yet
3. next deploy of C: keep-set from ReplicaSets only = {A} + {C}
4. ✗ B is pruned while the Deployment still asks for it
5. if C's upload then fails, new pods of the Deployment cannot start
```

### 3.5 Why it mattered

- Every jac-scale app on Kubernetes was affected, in proportion to how often it deploys. The issue's table: jac-builder-dev had 551 unreferenced files (89,999 MB), newsletter 481 MB, jaseci-blogs 384 MB.
- EFS cost was about $27/month for one app, growing about 0.5 GB per deploy.
- jacBuilder was writing its own pruner that parses init-container args. Those args already changed on `main` (`jac-pvc-bootstrap` → `jac-bootstrap`), so the issue says that pruner could silently stop working (the issue notes this is from reading code, not tested).

## 4. The idea of the fix (one sentence)

> **Prune during the seed, against a strict keep-set, and never prune blind.** Right before uploading, delete every file in the app's bundle and toolchain folders that no Deployment template, retained ReplicaSet or current seed names, and skip the delete whenever that set is empty or cannot be read.

The issue suggested a separate pod after "Fleet is ready". You chose to reuse the loader pod that already mounts the volume. That avoids a second pod and keeps everything in one place. The cost is that a bundle leaving history is only removed on the *next* deploy, so the volume holds the retained revisions plus one.

### 5.1 `jac/jaclang/scale/injector/impl/pvc_injector.impl.jac`: the prune script and the prune step in `seed`

```diff
+impl prune_unreferenced_script(app_name: str, keep: set[str]) -> str {
+    import shlex;
+    kept = shlex.quote(" " + " ".join(sorted(keep)) + " ");     # " k1 k2 k3 "
+    return (
+        f"cd {BUNDLE_MOUNT_PATH} && keep={kept} && "
+        f"for f in bundles/{app_name}/* toolchain/{app_name}/*; do "
+        'case "$keep" in *" $f "*) ;; '                           # in keep-set: skip
+        '*) [ ! -f "$f" ] || { rm -f "$f" && echo "pruned $f"; };; esac; done'
+    );
```

**What:**
1. The script builds one space-padded string of keep keys. It loops over the top-level entries of `bundles/<app>/` and `toolchain/<app>/` and deletes every regular file not found in that string. It prints `pruned <path>` for each deletion.
2. `seed` waits for the loader pod, then calls the keep-set callable.
3. If the result is empty, it logs and skips.
4. Otherwise it adds the keys it is about to upload and runs the script in one `kubectl exec`.
5. A `RuntimeError` from that exec is logged, and the upload continues.

**Why:** This is the missing "delete what is not referenced" half of the retention contract (3.2), with the empty-set guard from the issue (3.3).

**Things to notice:**
- **Callable, not a set.** This was @MusabMahmoodh's request. Reading the keep-set after `wait_for_pod_phase` shrinks the race with a concurrent same-app deploy to one `exec`, down from the whole pod start. You said in the thread that the window shrinks but does not close.
- **Prune runs before upload.** If the upload then fails, the live and retained bundles are still there, because they are in the keep-set.
- **Scope.** Only `bundles/<app>/*` and `toolchain/<app>/*` are touched. `.cache/` and other apps' folders are outside the glob. `.part` files are not in the keep-set, so they are deleted.
- **Not recursive.** The glob is one level deep, and `[ ! -f "$f" ]` skips directories. An unmatched glob stays a literal string that is not a file, so it is skipped too.
- **Matching uses spaces as separators.** This is safe because keys are hash names with no spaces. `shlex.quote` protects the shell.
- **The echo was @udithishanka's suggestion.** `run_kubectl_command` does not capture stdout, so the lines reach the deploy output.
- **Only `RuntimeError` is caught.** Any other exception type from the exec would propagate. I can't tell from the diff what else `run_kubectl_command` can raise.
- The diff does not show the end of this `try` block, so I can't confirm from it how the loader pod is cleaned up.

## 6. How execution flows after the PR

### 6.1 A deploy that seeds a bundle

```text
KubernetesTarget.apply_manifests(bundle)
└─ injector.seed(safe_app, ns, self._kubectl, self._bundle_keep_set)   ← CHANGED
   ├─ raise if prepare() was not called
   ├─ create loader pod, wait_for_pod_phase(... "Running")
   ├─ retained = keep_set()                                            ← NEW
   │  └─ _bundle_keep_set()                                            ← NEW (see 6.2)
   ├─ retained empty?
   │  ├─ yes → logger.info("... skipping the prune.")                  ← NEW
   │  └─ no  → keep = retained ∪ keys being seeded                     ← NEW
   │          └─ kubectl exec loader -- sh -c prune_unreferenced_script ← NEW
   │             ├─ each unreferenced file → rm, print "pruned <path>"
   │             └─ RuntimeError → logger.warning, continue            ← NEW
   └─ upload each artifact (unchanged)
```

### 6.2 Building the keep-set

```text
_bundle_keep_set()                                                     ← NEW
├─ referenced_bundle_keys(app)
│  ├─ _revision_entries(strict=True)
│  │  └─ _owned_replica_sets(strict=True)
│  │     ├─ _fleet_deployment_names(..., strict=True)                  ← CHANGED (re-raises)
│  │     └─ list ReplicaSets (raises in strict, as before)
│  │     per-RS read error → re-raise                                  ← CHANGED
│  ├─ add keys from each retained RS's pod spec
│  └─ add keys from each fleet Deployment's template                   ← NEW
├─ ok    → return keys
└─ error → _emit("apply","warn","skipping bundle prune, ...")
           → return set()                                              ← NEW
```

### 6.3 `list_revisions` / `rollback_to`

These are unchanged. They still use the lenient path: a read error gives an empty or shorter list instead of raising.

| Scenario | Before | After |
|---|---|---|
| Normal redeploy, old bundles out of history | All bundles stay forever | Unreferenced bundles, toolchains and `.part` files deleted, with a `pruned …` line each |
| First deploy (no Deployment/RS yet) | Nothing deleted | Keep-set empty, so prune skipped, with an info log |
| Deployment or RS list forbidden | Keep-set unused; if used, it could come back empty (3.3) | `referenced_bundle_keys` raises, so a warn event fires, prune skipped, deploy continues |
| Deployment requests bundle B, its RS not created yet | n/a (no prune) | B kept via the template keys |
| Prune `exec` fails | n/a | Warning logged, upload continues, nothing deleted |
| Other apps' folders, `.cache/` | Untouched | Untouched |

**Behaviour change users will notice:** deploy output now has `pruned …` lines, and the volume shrinks over time. Bundles older than `revision_history_limit` can no longer be rolled back to. That was already true at the ReplicaSet level, because the revision no longer exists.

### 7.3 `sdk_deploy_real_e2e.sh` and `sdk_deploy_driver.jac` (nightly, real cluster)

The driver gains:
- `SDK_DEPLOY_REVISION_HISTORY_LIMIT`, which sets `revision_history_limit` in `extra`;
- `revisions`, which prints `ScaleClient().revisions(...)` as JSON;
- `rollback N`, which prints `ROLLBACK_OK` or exits 1 with `ROLLBACK_FAILED`.

The new stage, after the #8115 config-redeploy stage:
1. Set the history limit to 1.
2. Three times: append a `glob` line to `main.jac`, deploy, and wait for the rollout.
3. Require at least one `pruned bundles/` line in the log.
4. Read revision index 1 (the retained release) and its `bundle_digest`.
5. Roll back to it, then wait for `rollout status` to succeed.
6. Check that the live `bundle_digest` (index 0) equals the rolled-back one.

## 11. Questions your senior might ask

**Q: Why prune in `seed` instead of after "Fleet is ready", as the issue suggested?**
A: `seed` already has a pod mounting the volume, and the issue notes `seed` tears that pod down before rollout. Pruning there avoids a second pod or Job. The cost is that a bundle leaving history is only removed on the next deploy, so the volume holds the retained revisions plus one.

**Q: Can this delete the bundle the live pods are using?**
A: Not by design. The keep-set includes:
- every retained ReplicaSet's bundle;
- every fleet Deployment's current template bundle;
- the bundle being seeded.

If any read fails, `_bundle_keep_set` returns `set()` and the prune is skipped. The one remaining risk is two deploys of the same app at once, which you documented in the PR.

**Q: What happens on an RBAC error while reading Deployments?**
A: `_fleet_deployment_names(strict=True)` now re-raises, so `referenced_bundle_keys` raises. `_bundle_keep_set` then emits `apply`/`warn` "skipping bundle prune, revisions unreadable" and returns `set()`. The deploy continues with no deletion.

**Q: Why pass a callable instead of the set itself?**
A: So the keep-set is read after the loader pod is Running, not before the wait. That shrinks the race with another deploy to a single `exec`. @MusabMahmoodh asked for this.

**Q: Does the prune run before or after the upload, and why?**
A: Before. If the upload fails afterward, nothing referenced has been lost, and the new bundle key is already in `keep`, so a partial earlier copy of it is not wrongly removed.

**Q: Does the `"deployments"` test row really prove the `_fleet_deployment_names` fix?**
A: Not on its own. The new template loop also lists Deployments and would raise anyway, so the row would likely pass without the re-raise. A fake that fails only the first Deployment call would isolate it.

**Q: What does a user see in the deploy output?**
A: One `pruned bundles/<app>/<sha>.jab` (or `toolchain/...`) line per deleted file. When nothing is retained yet, there is an info log saying the prune was skipped. A failed prune shows a warning.

**Q: Is rollback still safe after pruning?**
A: For any release still in history, yes. Its bundle is in the keep-set. The new e2e stage sets the history limit to 1, prunes over three redeploys, rolls back to the retained release, and checks that the live bundle digest matches it. Releases beyond `revision_history_limit` were already not rollback targets.

**Q: Why is CI red, and why didn't the scale tests run?**
A: `build-kit` failed and the summary gate followed. The data here doesn't say why. `test-scale`, `test-scale-k8s` and `jac-check` were skipped on the merge head commit, so they need to be triggered before merge.

**Q: What about the 0.34 line and `ScaleClient.bundle_keys`?**
A: The 0.34 line is planned as a cherry-pick after merge. `ScaleClient.bundle_keys` is not touched in this diff, so whether it now also includes template keys depends on whether it calls `referenced_bundle_keys`. That can't be told from this diff.
