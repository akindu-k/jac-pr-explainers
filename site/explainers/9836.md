# fix(serve): pool and reuse keep-alive connections in the serving client (#7907)

<!-- explainer -->

## In short

The serving client opened a new TCP (and TLS) connection for every request and closed it afterward. You changed it to keep idle connections in a pool and reuse them when it is safe. You also fixed the server, which told clients to keep a connection alive just before the worker shut down.

## Words to know

- **Keep-alive**: An HTTP/1.1 feature where one TCP connection carries many requests in a row, instead of one connection per request.
- **Connection pool**: A set of idle, already-open connections kept for later use. Taking one from the pool skips the cost of opening a new one.
- **Origin**: The triple `(scheme, host, port)`. Pools are kept per origin.
- **TCP / TLS handshake**: The setup steps before data can flow. TLS adds encryption setup on top of TCP. Both take time.
- **`Connection: close`**: An HTTP header meaning "I will close this connection after this message. Don't reuse it."
- **Framing**: How a receiver knows where an HTTP message body ends. Options here are `Content-Length` (fixed size), chunked encoding (a series of size-prefixed chunks), or no body.
- **Chunked encoding and trailers**: The body is sent in chunks, each with a size line. A `0` size ends it. Optional trailer headers can follow, then a final blank line.
- **Bodiless response**: A response that never has a body: replies to `HEAD`, and status 204 and 304.
- **Interim 1xx response**: A provisional response like `100 Continue` that comes before the real one.
- **Idempotent method**: A method that is safe to repeat (`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`). `POST` and `PATCH` are not.
- **Event loop**: The asyncio scheduler that runs async code. Here each loop owns its own pool.
- **`request_budget` / recycling**: A worker handles a set number of requests, then stops so a fresh one can replace it.
- **Gateway / forward**: The part of the server that proxies requests to other services (`raw_forward`, `stream_forward`).
- **kube-proxy**: The Kubernetes component that spreads connections across pods. Long-lived connections can pin traffic to old pods, so connections are retired after a maximum age.

## The problem

Every call through `jaclang.server.serving.client.arequest` did this:

1. `_open_stream` opened a new connection with `asyncio.open_connection`. For HTTPS it also built a new `ssl.create_default_context()` each time.
2. The request always carried `Connection: close`.
3. When the response ended, the writer was closed.

So every gateway hop, SSO token exchange and admin probe paid for a full TCP and TLS setup. The issue (#7907) blames aiohttp sessions, but those were removed in the #7969 rewrite, so the cost now sits in this client.

The client also could not have reused connections safely:

- The chunked reader left the final CRLF and trailers unread, which would corrupt the next response on the same connection.
- Bodiless responses (`HEAD`, 204, 304) were not handled specially.
- A caller's `Content-Length` was sent next to the computed one.

The server had a matching bug. The response that used up a worker's `max_requests` budget went out with `Connection: keep-alive`, and only afterward was the worker stopped. A pooling client would send its next request into a connection that was about to die.

## The changes, one by one

### `jac/jaclang/server/serving/client.jac`

This is the main change.

**New settings.** `IDLE_TIMEOUT` (30s, below the server's 65s keep-alive), `MAX_CONNECTION_AGE` (120s, so kube-proxy can rebalance), `MAX_IDLE_PER_ORIGIN` (32), `_IDEMPOTENT_METHODS`, and `_FRAMING_HEADERS`.

**`_PooledConn`.** A small object holding an origin, reader, writer, the time it was opened, and the time it went idle.

**`ClientResponse` changes.**
- New fields: `bodiless`, `reusable`, `_conn`, `_drained`.
- In `aiter_raw`, bodiless responses stop at the head and are marked drained.
- Chunked reads now consume the trailer lines after the `0` chunk, then set `_drained`.
- For `Content-Length` bodies, `_drained` is set only if `remaining == 0`.
- `aclose` now releases the connection to the pool only if it is `reusable` and `_drained`. Otherwise it closes it. This is the "always close an undrained response" commit.

**Pool helpers.**
- `_idle_pool` stores a dict on the running loop (`loop._jac_idle_conns`), so each loop has its own pool.
- `_usable` checks that the writer is not closing, the reader is not at EOF, the reader buffer is empty (no stray bytes), and the connection is within idle and age limits.
- `_take_idle` pops connections until it finds a usable one and discards the rest.
- `_release` first sweeps all expired entries across origins, then adds the connection if it is usable and the bucket is under 32.
- `_close_idle` closes everything. `_closing_pool` wraps a coroutine and calls `_close_idle` in `finally`.
- `_tls_context` is cached with `@cache`, so the TLS context is built once.

**`_exchange`.** Writes the payload, reads the head, and skips interim 1xx heads (except 101, the protocol upgrade). On failure it discards the connection and raises `ClientRequestSent`.

```jac
while 100 <= head[1] < 200 and head[1] != 101 {
    head = await _read_response_head(conn.reader, timeout);
}
```

This keeps reading heads while the status is an interim 1xx other than 101.

**`_read_response_head`** now also returns the HTTP version (`parts[0]`), so `arequest` can check for `HTTP/1.1`. `aws_connect` was updated to ignore that new value.

**`arequest`.**
- Drops caller `content-length` and `transfer-encoding` headers, so the client owns request framing.
- No longer sends `Connection: close`.
- Builds one `payload` (head plus body), takes an idle connection or opens a new one.
- If a reused connection fails before the response head, the request is retried once on a fresh connection. This applies only to idempotent methods and never to `ClientReadTimeout`.
- Computes `reusable`: HTTP/1.1, no `Connection: close`, and framed by `Content-Length`, chunked, or no body.
- For non-stream calls it drains the body and calls `aclose()` in `finally`, which returns the connection to the pool.

**Sync entry points.** `run_blocking` and `post_stream_aware_sync` wrap their coroutine in `_closing_pool`, so their private loop's pool is closed when it finishes.

### `jac/jaclang/server/serving/server.jac`

The recycle decision now happens before the response is written. `requests_served` is incremented right after dispatch, and `recycle` is true when the budget is reached. `keep_alive` also requires `not recycle`, so the budget-spending response carries `Connection: close`. After logging, `if recycle` calls `request_stop(EXIT_RECYCLE)`. The old late `keep_alive = False` is removed.

### Tests and release note

See Tests. `release_notes/unreleased/jaclang/9836.bugfix.md` adds a one-line bugfix note.

## How it runs now

1. A caller (for example `raw_forward`) calls `arequest(...)`. (changed)
2. Caller framing headers are dropped, and one payload is built without `Connection: close`. (changed)
3. `_take_idle(origin)` looks for a usable pooled connection. (new)
4. If none exists, `_connect` opens one. The TLS context is cached. (changed)
5. `_exchange` sends the payload and reads the head, skipping 1xx heads. (new)
6. If a reused connection died before the head and the method is idempotent (and it was not a read timeout), it reconnects and tries once more. (new)
7. `arequest` decides `reusable` and builds the `ClientResponse` holding the connection. (changed)
8. The body is drained, including chunked terminators and trailers. (changed)
9. `aclose` calls `_release` if the response was reusable and drained, otherwise `_discard`. `_release` sweeps expired entries first. (changed)
10. On the server, a response that uses up the budget now has `Connection: close`, and then the worker is stopped. (changed)
11. In the sync wrappers, the pool is closed when the private loop ends. (new)

## Tests

**`test_serving_client_errors.jac`: "connection reuse follows the response framing".** It is table-driven and uses real loopback sockets with a helper keep-alive server (`_keep_alive`). Each case counts how many connections the server saw:
- `Content-Length`, chunked, 204, and a `100 Continue` followed by the real response: three GETs share 1 connection.
- `Connection: close`, and a `Content-Length` overrun (extra bytes after the body): two GETs use 2 connections, so they are not reused.
- Dead pooled GET: the server drops the reused connection, the GET is retried, and there are 2 connections.
- Dead pooled POST: the POST is not replayed and raises `ClientRequestSent`, with 1 connection.

This proves pooling, correct framing, the safety rules and the retry rules. The PR description shows that before the fix the first, second, third and last cases failed with 3 or 2 connections.

**`test_serve_disconnect.jac`: "a worker at its request budget closes the connection it answers on".** It starts a server with `request_budget=1`, sends one GET, and asserts status 200 and `Connection: close`. This proves the server fix.

## Explaining it in one minute

"Our serving client opened a new connection for every request and sent `Connection: close`, so gateway hops, SSO and admin calls paid full TCP and TLS setup each time. I added a per-event-loop pool in `client.jac`, keyed by origin, with idle and age limits and a cap of 32. A connection is reused only if the response was HTTP/1.1, had clear framing, was fully drained and left nothing in the reader. I also fixed chunked reading and bodiless responses, and made the client own request framing. Idempotent requests are retried once if a reused connection was dead, while POST and PATCH are never replayed. On the server, the response that spends the worker's request budget now says `Connection: close`. I tested with a table-driven loopback-socket test for reuse and non-reuse cases, plus a server test for the budget case. Service-to-service sync calls are not pooled yet, because they use private loops."
