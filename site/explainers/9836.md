## 1. The short version

Jac's serving layer has its own small HTTP client, `arequest` in `jaclang/server/serving/client.jac`. The jac-scale gateway uses it for every request it forwards (`raw_forward`, `stream_forward`). Per your description, SSO token exchanges and admin probe, log and trace fetches also go through it.

**Before this PR, the client never reused a connection.** Each call opened a new TCP connection, built a new TLS context, sent `Connection: close`, and closed the socket when the response ended. Every gateway hop paid the full TCP setup cost, plus the TLS setup cost for HTTPS. Issue #7907 reported this against aiohttp sessions. You found that the cost had moved into `arequest` after the #7969 serving rewrite.

**The PR keeps idle keep-alive connections in a per-event-loop pool, keyed by origin, and reuses a connection only when the previous response was cleanly framed and fully read.** To make reuse safe, you also fixed these:

- chunked reads now consume the terminator and trailers;
- bodiless responses (`HEAD`, 204, 304) are handled;
- interim `1xx` heads are skipped;
- the client now owns request framing;
- an idempotent request is retried once if a reused connection turns out to be dead.

On the server side, a worker that is about to recycle now sends `Connection: close` on its last response instead of `keep-alive`.

**Status:** Open. Approved by @MusabMahmoodh on 2026-10-09 after his one blocker (the 100-continue desync) was fixed in `38627c2`. All CI checks pass on head `c360029`. After the approval, @greptile-apps[bot] left two P1 comments and one P2 comment (2026-10-10 and 2026-10-11). None of them has a reply or a fix yet.

## 3. The problem, step by step

### 3.1 The setup

- **Gateway**: one long-lived event loop. It calls `arequest` once per forwarded request.
- **`arequest` (old)**: `_open_stream` → write the request with `Connection: close` → read the head → read the body → `writer.close()`.
- **Worker (`ServingServer`)**: supports keep-alive (65s, per your description). It counts requests against `request_budget`.

### 3.2 What went wrong: no reuse at all

```text
1. Gateway forwards request A to worker 10.0.0.5:8000
2. arequest → _open_stream → new TCP connect (+ new ssl.create_default_context() if https)
3. Request sent with "Connection: close"                  ← WRONG: opts out of keep-alive
4. Response read; writer.close()                          ← WRONG: socket thrown away
5. Gateway forwards request B to the same worker
6. arequest → new TCP connect again (+ TLS again)         ← full setup cost on every hop
```

Your fork run ([37568349795](https://github.com/akindu-k/jaseci/actions/runs/37568349795)) shows this. Three GETs used `connections=3` when 1 was expected.

### 3.3 Why reuse could not simply be switched on

Even with `Connection: close` removed, the old client would have desynced pooled sockets:

```text
Chunked response:   ...2\r\nok\r\n0\r\n   ← client stopped here
                    \r\n                   ← unread; next request would read this as its status line  ← WRONG
204 / HEAD:         client tried to read a body that never comes  ← WRONG (hang or misread)
Caller Content-Length: passed through by build_forward_headers AND computed one sent
                    → two Content-Length headers                   ← WRONG framing
```

### 3.4 The matching server-side bug

```text
1. Worker has request_budget=1, requests_served=0
2. Request arrives; keep_alive = True
3. Response written with "Connection: keep-alive"         ← WRONG: promises reuse
4. requests_served=1 ≥ budget → request_stop(EXIT_RECYCLE); keep_alive=False (too late)
5. A pooled client sends its next request on that socket → worker is dying → error
```

### 3.5 The interim-1xx case (found in review)

@MusabMahmoodh found this one in the first commit, `16cb741`:

```text
1. Caller sends "Expect: 100-continue" (build_forward_headers passes it through)
2. Server writes "100 Continue" right away (server.jac:540)
3. Client takes 100 as the final status; treats it as bodiless and reusable  ← WRONG
4. Socket goes back to the pool with the real "200 ..." still unread
5. Next request on that origin, possibly from another user, reads the 200 meant for request 1
```

### 3.6 Why it mattered

The issue labels this high-severity performance work. The gateway is the single entry point for the whole fleet, so per-request connection setup is "the first throughput ceiling the system hits" and inflates tail latency. Without the safety fixes, though, pooling would turn a performance bug into a correctness and privacy bug, as 3.5 shows.

## 4. The idea of the fix (one sentence)

> **Pool a connection only when the response proved where it ended.** A socket goes back to the pool only after an HTTP/1.1 response without `Connection: close`, framed by length, chunks or no body, that was fully read with nothing left in the buffer.

This puts reuse in the one function every forward already goes through, so all callers benefit without changing them. Being strict about when a socket counts as "clean" is what keeps pooling from leaking responses between requests.

### 5.3 `client.jac`: the pool itself

```diff
     async def aclose {
-        if self.writer is not None {
-            try { self.writer.close(); } except Exception {}
+        conn = self._conn; self._conn = None; self.reader = None; self.writer = None;
+        if conn is None { return; }
+        if self.reusable and self._drained { _release(conn); }   # NEW: back to pool
+        else { _discard(conn); }
+    }
+def _idle_pool -> dict[...] {            # pool lives on the running loop
+    loop = asyncio.get_running_loop();
+    if not hasattr(loop, '_jac_idle_conns') { loop._jac_idle_conns = {}; }
+    return loop._jac_idle_conns;
+}
+def _usable(conn, now) -> bool {
+    return not conn.writer.is_closing() and not conn.reader.at_eof()
+        and len(conn.reader._buffer) == 0                 # no stray bytes
+        and now - conn.idle_since < IDLE_TIMEOUT
+        and now - conn.opened < MAX_CONNECTION_AGE;
+}
+def _take_idle(origin) { ... bucket.pop() ... discard unusable ... }
+def _release(conn) { sweep every origin; discard expired; append if < 32 }
+def _close_idle { discard everything; pool.clear() }
+async def _closing_pool(coro) { try { return await coro; } finally { _close_idle(); } }
+@cache
+def _tls_context -> any { return ssl_lib.create_default_context(); }
```

**What:**
- `aclose` decides between "return to pool" and "close".
- `_take_idle` hands out the most recently idled socket that passes `_usable`.
- `_release` sweeps expired sockets across all origins, then stores this one if there is room.
- The TLS context is built once.

**Why:** This is the reuse mechanism. The `_buffer` check is what rejects the "Content-Length overrun" case, where extra bytes after the declared body would poison the next response.

**Things to notice:**
- The pool is **per event loop**, not global. asyncio streams belong to one loop, so this is required. It also means the sync wrappers (new loop per call) get no reuse, which your description lists under "Not addressed".
- `_usable` reads `reader._buffer`, a private attribute of `asyncio.StreamReader`. The pool is stored by setting an attribute on the loop object. Whether this works on a non-default loop such as uvloop can't be told from the diff.
- `bucket.pop()` is last-in, first-out, so the warmest socket is reused first.

**What:**
- Takes a pooled socket or opens one, then sends and reads the head.
- Retries once only when all three hold: the socket was reused, the error was not a read timeout, and the method is idempotent.
- Computes `reusable`.
- In non-stream mode, drains the body and then always calls `aclose()`, which pools or discards.

**Why:**
- Removing `Connection: close` turns on keep-alive.
- Dropping caller framing headers fixes the double `Content-Length`.
- The retry covers the race where a pooled socket was closed by the server while idle. A write into a dead socket often "succeeds" into the kernel buffer and only fails at read time, which is why the retry hangs off `ClientRequestSent`.

**Things to notice:**
- `POST` and `PATCH` that hit a dead pooled socket now fail with `ClientRequestSent`. Before, they always got a fresh socket. This is a deliberate trade: no duplicate side effects, at the cost of an occasional error.
- The `finally` was added in `38627c2`. A malformed `Content-Length` raises `ValueError`, which the `except` doesn't catch. The `finally` makes sure that socket is discarded instead of leaking until garbage collection.
- **Open (Greptile P1, 1 of 2):** a caller-supplied `Connection: close` on the *request* is still forwarded, and `reusable` only looks at the *response*.
- **Open (Greptile P1, 2 of 2):** `resp_headers.get('Connection')` reads only one value. If there are several `Connection` headers, a `close` in a later one can be missed. Greptile says `get` returns the first; the `Headers` class isn't in the diff, so this can't be confirmed here.
- With `stream=True`, the caller must call `aclose()`. Otherwise the socket is neither pooled nor closed.

## 6. How execution flows after the PR

### 6.1 Non-stream `arequest` (for example an admin fetch on the gateway loop)

```text
arequest(method, url, ...)
├─ drop caller content-length / transfer-encoding            ← NEW
├─ build head with computed Content-Length (no Connection: close)   ← CHANGED
├─ _take_idle(origin)                                         ← NEW
│   ├─ found usable socket → reused=True
│   └─ none → _connect → _open_stream (cached TLS context)   ← CHANGED
├─ _exchange: write, drain, read head, skip 1xx except 101    ← NEW
│   └─ on ClientRequestSent:
│       ├─ reused AND not timeout AND idempotent → _connect + _exchange once  ← NEW
│       └─ otherwise → raise
├─ compute chunked / bodiless / reusable                      ← NEW
├─ aiter_raw → reads exactly to the end, sets _drained        ← CHANGED
└─ finally aclose()                                           ← NEW
    ├─ reusable and _drained → _release (sweep, store if ≤32)
    └─ else → _discard (close)
```

### 6.2 Streaming `arequest(stream=True)` (gateway `stream_forward`)

```text
arequest(..., stream=True)
├─ same steps up to the ClientResponse
├─ return response (holds _conn)
└─ caller iterates, then calls response.aclose()
    ├─ fully read + reusable → pooled                          ← NEW
    └─ partly read / error → discarded                         ← NEW
```

### 6.3 Sync entry points

```text
run_blocking / post_stream_aware_sync
└─ asyncio.run(_closing_pool(coro))                            ← CHANGED
    ├─ coro runs; pool exists only on this loop
    └─ finally _close_idle()                                   ← NEW
```

### 6.4 Worker answering a request

```text
connection handler
├─ _dispatch(request)
├─ requests_served += 1                                        ← MOVED
├─ recycle = budget hit?                                       ← NEW
├─ keep_alive = should_keep_alive and not stopping and not recycle  ← CHANGED
├─ _write_response(..., keep_alive)   → "Connection: close" when recycling
└─ if recycle → request_stop(EXIT_RECYCLE)
```

| Scenario | Before | After |
|---|---|---|
| 3 GETs, `Content-Length` response | 3 connections | 1 connection |
| 3 GETs, chunked response | 3 connections | 1 |
| 3 GETs, 204 response | 3 connections | 1 |
| `100 Continue` then 200 | 3 connections, worked | 1 connection, 200 returned (on `16cb741` it returned 100) |
| Server sends `Connection: close` | new connection each time | new connection each time |
| Body longer than `Content-Length` | new connection each time | socket discarded, new connection |
| Pooled socket dead, `GET` | n/a (always fresh) | retried once on a fresh socket |
| Pooled socket dead, `POST` | n/a (always fresh) | raises `ClientRequestSent` |
| Worker's last request under its budget | `Connection: keep-alive` | `Connection: close` |
| Sync call (`request_sync`) | new connection | still a new connection per call |

**Behaviour change users may notice:** a `POST`/`PATCH` can now fail with `ClientRequestSent` when the server closed the reused socket while it was idle. Callers that previously never saw this on a healthy upstream may now see it occasionally.

The test uses the file's existing `_start_server`, which returns `held`. Judging by `len(held) == connections`, `held` is the list of accepted connections, though the harness itself isn't in the diff.

Your fork run shows four rows failing before the fix: content-length, chunked, 204 and POST. The close, overrun and GET-retry rows pass on the old code too. They are guards against reusing sockets too eagerly. A new test was needed because no existing test exercised reuse.

## 11. Questions your senior might ask

**Q: Why pool inside `arequest` instead of a gateway-level session as the issue suggests?**
The aiohttp sessions named in the issue no longer exist after #7969. Every forward goes through `arequest`, so pooling there covers all callers with no change to them. @MusabMahmoodh agreed this is the right layer.

**Q: Why is the pool stored on the event loop?**
asyncio stream readers and writers belong to one loop and can't be used from another. A per-loop dict keeps sockets with the loop that owns them. The cost is that sync calls, which use a new loop each time, get no reuse.

**Q: How do you avoid handing one user's response to another user?**
A socket is pooled only when all of these hold:
- the response is HTTP/1.1 without `Connection: close`;
- it is framed by length, chunks or no body;
- it was fully drained (`_drained`);
- the reader buffer is empty and the socket is not at EOF.

1xx heads are skipped. The overrun and 100-continue rows test this.

**Q: What happens when the server closed the idle socket just before reuse?**
The error shows up as `ClientRequestSent`. Idempotent methods retry once on a fresh socket. `POST`/`PATCH` raise to the caller. Read timeouts never retry. The 30s idle limit, below the server's 65s, makes this rare against Jac workers.

**Q: What about upstreams with a keep-alive shorter than 30s, such as an external SSO provider?**
The PR doesn't handle this specially. A `POST` to such a host could hit a dead pooled socket and fail without retry. Whether SSO token exchange goes through the pooled async path can't be told from the diff. Worth checking.

**Q: Why stop the 1xx loop at 101?**
`arequest` never asks for an upgrade. Skipping a 101 would wait for a next head that never comes and hang until the timeout. Returned as final, it has no framing, so it is never pooled.

**Q: Why drop the caller's `Content-Length`/`Transfer-Encoding`?**
`build_forward_headers` passes them through, and the client also adds its own `Content-Length`. Two framing headers are ambiguous and can desync a reused socket. The client now owns framing.

**Q: Does the server change alter recycle counting?**
The count now happens after `_dispatch` and before the write, so the last response can say `Connection: close`. If `_dispatch` ever raises, that request is no longer counted. Whether it can raise depends on code not shown in the diff.

**Q: Isn't relying on `reader._buffer` fragile?**
It is a private `asyncio.StreamReader` attribute, so a Python upgrade or an alternative loop could break it. It is the only direct way to see stray bytes without reading them, which is how the overrun case is rejected.

**Q: What's left for #7907?**
Two things, per your "Not addressed" section:
- service-to-service sync calls (`sv_client`, `rpc.jac`) still connect once per call, which needs a long-lived client loop;
- the rest of the hop-by-hop headers (`te`, `trailer`, `upgrade`, `proxy-*`) is a separate header-forwarding fix.
