## 1. The short version

The serving client (`jaclang.server.serving.client`) is the small HTTP client Jac's own server code uses to call other HTTP servers. The jac-scale gateway forwards user requests through it (`raw_forward`, `stream_forward`), and so do SSO token exchanges and admin probe, log and trace fetches.

**Before this PR, every call through `arequest` opened a brand-new TCP connection (and TLS handshake for `https`), sent `Connection: close`, and threw the connection away when the response ended.** Issue #7907 reported this against the gateway's old aiohttp sessions. Your description says that code is gone since the #7969 rewrite, so the cost now sits in `arequest`. The client also could not have reused a connection safely. It left chunked terminators unread, had no handling for `HEAD`, 204 or 304, and could send two `Content-Length` headers. The server had a matching bug: when a worker spent its request budget, the last response still said `Connection: keep-alive`.

**The PR keeps idle connections in a per-origin pool on the running event loop, returns a connection to the pool only after a fully drained, properly framed HTTP/1.1 response, and retries an idempotent request once if a reused connection turns out to be dead.** The server now decides to recycle before writing, so the budget-spending response says `Connection: close`. Your fork run before the fix showed `connections=3` where 1 was expected. That run is linked in the description.

**Status:** Open. @MusabMahmoodh requested changes on 2026-10-07 and approved on 2026-10-09. After that approval, greptile-apps[bot] left two open comments (one P1, one P2) on 2026-10-10, and you merged `main` in (074fa0d). The `build-kit` check is still running.

## 3. The problem, step by step

### 3.1 The setup

- **Gateway → upstream service:** each forwarded user request calls `arequest(...)`.
- **`arequest` (old):** `_open_stream` creates a new socket and a new `ssl.create_default_context()`, then writes the request with `Connection: close`, reads the response, and closes the writer.
- **`ServingServer`:** answers on a connection. With `request_budget > 0`, it stops itself after N requests.

### 3.2 What went wrong: no reuse at all

```text
1. Gateway gets user request A        → arequest("GET", http://svc:8000/x)
2. _open_stream                        → new TCP socket #1 (+ new SSLContext, + TLS handshake if https)
3. Request sent with "Connection: close"
4. Response read, writer.close()       → socket #1 closed                       ✗ WRONG: thrown away
5. Gateway gets user request B        → same origin
6. _open_stream                        → new TCP socket #2, full setup again      ✗ WRONG
...
N. Every hop, SSO exchange, admin probe = 1 connection each
```

Your fork run before the fix shows this directly: `content-length: ... connections=3, expected ... over 1`.

### 3.3 Why the client could not simply skip closing

Reuse needs the reader to stop exactly at the end of each response. The old code did not:

```text
Chunked response:   "2\r\nok\r\n0\r\n\r\n"
1. reader reads "2", "ok", then "0"   → loop breaks
2. final "\r\n" (and any trailers) still on the socket     ✗ WRONG if reused
3. next request's head read starts with "\r\n" → garbage

204 / 304 / HEAD:
1. no Content-Length, not chunked → old code fell to "read until EOF"
2. server keeps connection open → read blocks                ✗ WRONG if reused

Caller passes Content-Length (build_forward_headers forwards it):
1. arequest writes "Content-Length: <computed>"
2. arequest also writes caller's "Content-Length: <original>"   ✗ WRONG: two framings
```

### 3.4 The server side: a dying connection advertised as alive

```text
request_budget = 1
1. Request #1 arrives on connection C
2. keep_alive = True → response written with "Connection: keep-alive"   ✗ WRONG
3. requests_served = 1 → budget spent → request_stop(EXIT_RECYCLE)
4. A pooled client puts C back in its pool
5. Next request goes into C → worker is gone → error
```

The new disconnect test failed with `AssertionError: keep-alive` on the fork run.

### 3.5 Found in review: interim 1xx desyncs a pooled connection (fixed in 38627c2)

@MusabMahmoodh found this in your first commit:

```text
1. Caller sends Expect: 100-continue (build_forward_headers passes Expect through)
2. Server replies "100 Continue" right away (server.jac:540, per the reviewer)
3. Client takes 100 as the final status; 1xx was in the bodiless set → reusable  ✗ WRONG
4. Connection returns to pool with the real "200 ..." still unread
5. The next request on that origin (maybe another user's) reads the previous 200
```

Your reply confirms that on 16cb741 "its first request returned status 100 with an empty body".

### 3.6 Why it mattered

From #7907 (severity high, performance): the gateway is "the single ingress for the whole fleet", so per-request connection setup is "the first throughput ceiling the system hits" and inflates tail latency. Section 3.5 is a correctness and security risk: one user could receive another user's response.

## 4. The idea of the fix (one sentence)

> **Keep a connection only when you can prove the response ended cleanly.** Pool idle connections per origin on the running loop. Put one back only after a fully drained HTTP/1.1 response with clear framing and nothing left in the buffer. Otherwise close it.

Pooling at the client layer fixes every caller of `arequest` at once (gateway, SSO, admin). The strict "prove it's clean" rule keeps one exchange's leftovers from spilling into the next.

### 5.3 `client.jac`: `aclose` and the pool helpers

```diff
     async def aclose {
-        if self.writer is not None {
-            try { self.writer.close(); } except Exception {}
+        conn = self._conn;
+        self._conn = None; self.reader = None; self.writer = None;
+        if conn is None { return; }
+        if self.reusable and self._drained {

+        } else {

+        }

+def _idle_pool -> dict[...] {           # pool stored on the running loop
+    loop: any = asyncio.get_running_loop();
+    if not hasattr(loop, '_jac_idle_conns') { loop._jac_idle_conns = {}; }
+    return loop._jac_idle_conns;
+}
+def _usable(conn, now) -> bool {
+    return not conn.writer.is_closing()
+        and not conn.reader.at_eof()
+        and len(conn.reader._buffer) == 0          # no leftover bytes
+        and now - conn.idle_since < IDLE_TIMEOUT
+        and now - conn.opened < MAX_CONNECTION_AGE;

+def _take_idle(origin) -> (_PooledConn | None) { ... pop newest, discard unusable ... }
+def _release(conn) { ... sweep all origins, then append if usable and bucket < 32 ... }
```

**What:** `aclose` is now the single point that decides "pool or close". The pool is a dict from origin to a list of connections, attached to the running event loop. `_take_idle` pops the most recently used connection (last in, first out) and closes stale ones it finds. `_release` sweeps expired entries for every origin, then adds the connection if it is still usable and the bucket has room.

**Why:** This is the core of the fix: connections survive between requests. Attaching the pool to the loop matters because asyncio sockets cannot cross loops.

**Things to notice:**
- `len(conn.reader._buffer) == 0` reads a private attribute of `asyncio.StreamReader`. It is the check that catches the "Content-Length overrun" case (extra bytes after the body). A senior may ask about it (see section 11).
- The sweep in `_release` walks every origin on every release. That is cheap at 32 per origin, but it is a full scan.
- The TLS context is cached for the whole process with `@cache`. `SSLContext` can be shared, so this is safe.

`aws_connect` is updated to unpack the extra version field: `(_, status, reason, resp_headers)`.

2. `Connection: close` is no longer sent.
3. An idle connection is taken from the pool, or a new one is opened.
4. If a *reused* connection fails before the head arrives, the request is retried once on a new connection. This happens only for idempotent methods and never after a read timeout.

- `POST` and `PATCH` on a dead pooled connection now fail with `ClientRequestSent`. Before, they never reused connections, so this failure mode is new. It is the intended trade-off.

## 6. How execution flows after the PR

### 6.1 Non-streaming `arequest` (SSO, admin fetches)

```text
arequest(method, url, headers, data)
├─ drop caller content-length / transfer-encoding                ← NEW
├─ build head (no "Connection: close")                           ← CHANGED
├─ _take_idle(origin)                                            ← NEW
│   ├─ found usable → reused = True
│   └─ none → _connect(origin) (cached TLS context)              ← NEW
├─ _exchange(conn, payload)                                      ← NEW
│   ├─ write + drain
│   ├─ read head; skip 1xx except 101                            ← NEW
│   └─ on error → _discard(conn), raise ClientRequestSent
├─ on ClientRequestSent:
│   ├─ reused AND idempotent AND not ReadTimeout → _connect + _exchange once ← NEW
│   └─ else → raise
├─ compute chunked / bodiless / reusable                          ← NEW
├─ aiter_raw: read body exactly; set _drained                     ← CHANGED
└─ finally aclose()                                               ← NEW
    ├─ reusable AND drained → _release (sweep, pool if usable & <32)
    └─ else → _discard
```

### 6.2 Streaming `arequest` (gateway `stream_forward`)

```text
arequest(..., stream=True)
├─ same steps as 6.1 up to building ClientResponse
└─ return response (caller reads it)
    └─ caller calls aclose()
        ├─ read to the end → _drained → pooled                    ← NEW
        └─ stopped early → not drained → closed                   ← NEW
```

How `stream_forward` calls `aclose` is not in this diff.

### 6.3 Sync wrappers (`run_blocking`, `post_stream_aware_sync`)

```text
request_sync(...) → run_blocking(coro)
└─ asyncio.run(_closing_pool(coro))                               ← CHANGED
    ├─ arequest (pool lives only on this private loop)
    └─ finally _close_idle()                                      ← NEW
```

### 6.4 Server answering a request

```text
connection handler loop
├─ _dispatch(request)
├─ requests_served += 1                                           ← CHANGED (moved earlier)
├─ recycle = budget > 0 and served >= budget                      ← NEW
├─ keep_alive = should_keep_alive and not stopping and not recycle ← CHANGED
├─ _write_response(..., keep_alive)   → "Connection: close" when recycling
└─ if recycle → request_stop(EXIT_RECYCLE)
```

| Scenario | Before | After |
|---|---|---|
| 3 GETs, Content-Length response | 3 connections | 1 connection |
| 3 GETs, chunked response | 3 | 1 |
| 3 GETs, 204 | 3 | 1 |
| `100 Continue` then `200` | 3 (first commit of this PR: wrong 100 result) | 1, body `ok` |

**Behaviour changes users will notice:**
- Upstream servers now see persistent connections from the gateway.
- Caller-set `Content-Length` and `Transfer-Encoding` are ignored.
- A `POST` can fail with `ClientRequestSent` if its pooled connection dies, and it will not be replayed.

### 7.1 `jac/tests/runtimelib/test_serving_client_errors.jac`

New helpers:
- **`_recv_request`** reads one full request (head plus `Content-Length` body) and keeps any extra bytes for the next one.
- **`_keep_alive(reply, drop_reused)`** is a socket handler that answers each request with `reply`. It closes after `Connection: close`, or on the second request when `drop_reused` is set, to simulate a server that killed an idle connection.
- **`_send_each`** runs `arequest` for each method in turn and records either the body or the error type.

The test reuses the file's `_start_server` and `_stop_server` harness. `len(held)` serves as the count of accepted connections; that is inferred from use, since the helper body is not in the diff.

The test **"connection reuse follows the response framing"** is table-driven. Failures are collected and reported together.

## 11. Questions your senior might ask

**Q: Why pool in `client.jac` instead of in the gateway as #7907 suggests?**
The aiohttp code named in the issue is gone since #7969. Every forward, SSO call and admin fetch goes through `arequest`, so pooling there fixes all of them at once.

**Q: Why store the pool on the event loop instead of in a global?**
asyncio streams belong to the loop that created them. A global pool could hand a socket to a different loop, such as the private loops in `run_blocking`.

**Q: How do you know a connection is safe to reuse?**
Five checks must all pass:
1. The response is HTTP/1.1.
2. The response has no `Connection: close`.
3. The body is framed by `Content-Length`, chunked encoding, or no body.
4. The body was fully drained.
5. At pool time, `_usable` finds the socket not closing, not at EOF, no leftover buffered bytes, and within the idle and age limits.

**Q: Isn't `reader._buffer` a private API?**
Yes, it is `asyncio.StreamReader` internals. It is what catches the "Content-Length overrun" case. The PR offers no public alternative. The risk is a Python version changing that attribute.

**Q: Why is retrying a GET safe but not a POST?**
The retry happens only on a *reused* connection that failed before a response head, which usually means the server closed it while idle. Replaying idempotent methods is harmless. `POST` and `PATCH` could run twice, so they raise `ClientRequestSent`. Read timeouts are never retried, because the server may still be working on the request.

**Q: Why 30 s idle and 120 s max age?**
30 s is under the server's 65 s keep-alive (the value is from the description), so the client drops a connection before the server does. 120 s forces reconnects so kube-proxy can spread load after a scale-out.

**Q: Why is 101 not skipped like other 1xx?**
`arequest` never requests an upgrade. Skipping a 101 would wait for a final response that never comes. Returned as final, it has no framing and is never pooled.

**Q: What about a caller sending `Connection: close`?**
It is still forwarded, and pooling ignores it. That is greptile's open P1, and it needs a fix or an explanation before merge.

**Q: Do service-to-service calls benefit?**
No. `request_sync` and `post_stream_aware_sync` use a new loop per call, and the pool is closed when that loop ends. Your description says pooling them needs a long-lived client loop.

**Q: Why does the server change belong in this PR?**
Without it, a pooled client would reuse the connection of a worker that is about to recycle, and its next request would fail. The new test proves that the budget-spending response now carries `Connection: close`.
