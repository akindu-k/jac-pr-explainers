# fix(serve): pool and reuse keep-alive connections in the serving client (#7907)

[#9836](https://github.com/jaseci-labs/jac/pull/9836) by @akindu-k · opened 7 Oct 2026 · +387 −48 in 5 files

<!-- explainer -->

## In short

Every HTTP request made by Jac's own serving client opened a brand-new TCP (and sometimes TLS) connection and closed it right after the response. That client is used for gateway forwarding, SSO token exchange and admin probes. Your PR keeps finished connections in a small pool and reuses them for the next request to the same server. It also fixes the client and server bugs that would have made reuse unsafe.

## Words to know

- **Serving client (`client.jac`)**: Jac's small hand-written HTTP/1.1 client. Its main function is `arequest`. The gateway's forwarding helpers (`raw_forward`, `stream_forward`) go through it, and so do SSO and admin calls.
- **Gateway / hop**: the front process that receives a request and forwards it to a backend worker. Each forward is one "hop".
- **Serving server (`server.jac`, `ServingServer`)**: Jac's own HTTP server that answers those requests.
- **TCP / TLS handshake**: the setup messages that must be exchanged before any data can flow on a new connection. TLS (HTTPS) adds extra round trips and CPU work. This is the cost the PR avoids paying on every request.
- **Keep-alive**: HTTP/1.1 lets one connection carry many requests in a row. Sending `Connection: close` turns this off.
- **Connection pool**: a store of open, idle connections that can be handed out again instead of opening new ones.
- **Origin**: the triple `(scheme, host, port)`, for example `("http", "10.0.0.5", 8000)`. A pooled connection is only reused for the same origin.
- **Event loop (asyncio)**: the scheduler that runs Python async code. asyncio connections belong to the loop that created them and cannot be used from another loop.
- **Response framing**: how the client knows where a response body ends. There are three ways:
  - **`Content-Length`**: the response says how many bytes the body has.
  - **Chunked transfer encoding**: the body comes in pieces, each prefixed by its size in hex. A size of `0` ends the body. After it can come **trailers** (extra header lines), and then an empty line made of a **CRLF** (`\r\n`).
  - **No body**: responses to `HEAD` requests, and status codes `204 No Content` and `304 Not Modified`, never have a body.
- **Drained**: the whole response body has been read from the connection, so the next bytes on it belong to the next response.
- **Interim 1xx responses**: status codes like `100 Continue` that a server may send before the real response. `101 Switching Protocols` is different: it is used for WebSockets and is a final answer.
- **Idempotent method**: an HTTP method that is safe to send twice (`GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`). `POST` and `PATCH` are not, because they could create something twice.
- **`ClientRequestSent` / `ClientRequestNotSent` / `ClientReadTimeout`**: the client's error types.
  - `ClientRequestSent` means "the request may have reached the server, so it is not safe to retry blindly".
  - `ClientReadTimeout` is treated as one kind of `ClientRequestSent`. The `isinstance` check in the diff relies on that.
- **Request budget / recycle**: a worker setting, `request_budget`. After a worker has served that many requests, it stops itself so a fresh one can replace it.
- **kube-proxy**: the Kubernetes component that spreads connections across pods. It only balances new connections. A connection that lives forever stays pinned to one pod, even after new pods are added (a "scale-out").
- **SSL context**: the Python object that holds TLS settings and trusted certificates. It is fairly expensive to build.
- **`functools.cache`**: a decorator that remembers a function's return value, so the function body only runs once.
- **Hop-by-hop headers**: headers like `Connection`, `TE` and `Upgrade` that apply to a single connection and should not be forwarded to the next hop.

## The problem

The issue (#7907) blamed the gateway's aiohttp sessions. Those were removed in the #7969 rewrite, but the same cost had moved into `arequest`. Before your PR, every call did this:

1. `_open_stream` called `asyncio.open_connection` to make a new connection. For HTTPS it also built a fresh `ssl.create_default_context()` each time.
2. The request always included `Connection: close`.
3. After reading the response, the client closed the writer.

So every gateway hop, every SSO token exchange and every admin probe, log fetch or trace fetch paid the full TCP setup, plus TLS setup for HTTPS.

You could not just remove `Connection: close`. The client had bugs that only matter when a connection is reused:

- **Chunked bodies**: the reader stopped at the `0` size line. It left the final CRLF and any trailers unread, so the next response on that connection would start with leftover garbage.
- **Bodiless responses** (`HEAD`, 204, 304): these had no special case. The client could try to read a body that would never arrive.
- **Duplicate `Content-Length`**: `build_forward_headers` passes the caller's `Content-Length` through. The client also added its own. Two different lengths on one request make the framing ambiguous.

The server had a matching bug. When a worker served the request that used up its `request_budget`, the flow was:

1. It wrote that response with `Connection: keep-alive`.
2. Only after that did it decide to stop the worker.

A pooled client would believe the connection was still good and send its next request into a worker that was shutting down.

## The changes, one by one

### `jac/jaclang/server/serving/client.jac`: the pool

You added settings and a pooled-connection type:

```jac
glob DEFAULT_TIMEOUT: float = 30.0,
     IDLE_TIMEOUT: float = 30.0,
     MAX_CONNECTION_AGE: float = 120.0,
     MAX_IDLE_PER_ORIGIN: int = 32,
     _IDEMPOTENT_METHODS: set[str] = {...},
     _FRAMING_HEADERS: set[str] = {'content-length', 'transfer-encoding'};
```

- `IDLE_TIMEOUT`: a connection that has sat unused for 30 seconds is not reused. Per your description, the server keeps idle connections for 65 seconds. Staying well below that means the client gives up first, so it does not pick a connection the server is about to close.
- `MAX_CONNECTION_AGE`: a connection older than 120 seconds is retired, even if it is busy. This lets kube-proxy send new connections to new pods after a scale-out.
- `MAX_IDLE_PER_ORIGIN`: at most 32 idle connections are kept per server.
- `_PooledConn` holds `origin`, `reader`, `writer`, `opened` (when it was created) and `idle_since` (when it was last returned to the pool).

The pool functions:

- **`_idle_pool()`** stores the pool as an attribute, `_jac_idle_conns`, on the running event loop. Each loop gets its own pool. This matters because asyncio connections cannot be shared across loops.
- **`_usable(conn, now)`** decides whether a connection is still safe to reuse. All of these must be true:
  - the writer is not closing,
  - the reader has not reached end-of-file,
  - the reader's internal buffer is empty, so there are no stray unread bytes,
  - it has been idle for less than `IDLE_TIMEOUT`,
  - it is younger than `MAX_CONNECTION_AGE`.

  Note: the empty-buffer check reads `conn.reader._buffer`, which is a private attribute of asyncio's `StreamReader`.
- **`_take_idle(origin)`** pops connections from the end of the list, so the most recently used one comes first. It closes any that fail `_usable` and returns the first good one, or `None`.
- **`_release(conn)`** puts a connection back. It works in two steps:
  1. It sweeps every origin's list and closes expired connections. This is the "expired entries are swept on every release" from your description.
  2. It stamps `idle_since` on `conn` and adds it to its origin's list. If `conn` is not usable, or that list already has 32 entries, it closes `conn` instead.
- **`_discard(conn)`** closes the writer and ignores any errors.
- **`_close_idle()`** closes and clears every connection in the current loop's pool.
- **`_closing_pool(coro)`** runs a coroutine, then calls `_close_idle()` in a `finally` block.
- **`_tls_context()`** is decorated with `@cache`, so one SSL context is built once and shared. `_open_stream` now uses it instead of building a new one each call.
- **`_connect(origin, timeout)`** opens a new stream and wraps it in a `_PooledConn` with both timestamps set to now.

### `client.jac`: `ClientResponse` and reading bodies

`ClientResponse` has four new fields:

- `bodiless`: the response has no body.
- `reusable`: the response's headers allow reuse.
- `_conn`: the pooled connection this response came on.
- `_drained`: the body was fully read.

Changes in the body reader:

- **Bodiless responses**: the reader marks `_drained = True` and returns immediately, without trying to read a body.
- **Chunked bodies**: after the `0` size line it now keeps reading lines until an empty line, which skips the trailers. Then it marks the response drained:
  ```jac
  if size == 0 {
      trailer: bytes = await self.reader.readline();
      while trailer not in (b'\r\n', b'\n', b'') {
          trailer = await self.reader.readline();
      }
      self._drained = True;
      break;
  }
  ```
  - Line 2 reads the line right after the `0` chunk.
  - Lines 3–5 keep reading while that line is a trailer, meaning it is not empty. An empty `b''` means end-of-file, which also stops the loop.
  - Line 6 records that the connection now sits cleanly at the start of the next response.
- **`Content-Length` bodies**: `_drained = remaining == 0`. It is only true if every promised byte was read.
- **Read-until-close bodies** (no framing at all): `_drained` is never set to true. These connections are never reused.

`aclose()` used to just close the writer. Now it does this:

```jac
conn = self._conn;
self._conn = None;
self.reader = None;
self.writer = None;
if conn is None { return; }
if self.reusable and self._drained { _release(conn); } else { _discard(conn); }
```

- Lines 1–4 detach the connection from the response. Calling `aclose()` twice is then harmless, and the caller can no longer touch a connection that may now belong to another request.
- Lines 5–6 return the connection to the pool only if the headers allowed reuse and the body was fully read. Otherwise they close it.

This is the "always close an undrained response" part of your third commit. If a caller stops reading a stream partway, the connection is closed, not pooled.

### `client.jac`: `_read_response_head`, `_exchange` and `arequest`

**`_read_response_head`** now also returns the HTTP version string (`parts[0]`, for example `HTTP/1.1`). The client needs it because only HTTP/1.1 responses are pooled. `aws_connect`, the WebSocket connect function, was updated to unpack the new four-value result and ignore the version.

**`_exchange(conn, payload, timeout)`** is the old write-and-read-head block moved into its own function:

1. It writes the request and waits for it to be sent (`drain`).
2. It reads the response head.
3. It skips interim heads with `while 100 <= head[1] < 200 and head[1] != 101`. So a `100 Continue` is ignored, but a `101` is still returned as the answer. This is from your third commit.

On a network error it closes the connection and raises `ClientRequestSent`, the same error the old inline code raised.

**`arequest`** changes:

1. Caller headers named `content-length` or `transfer-encoding` are skipped. The client now owns request framing, so only its own computed `Content-Length` is sent.
2. `Connection: close` is no longer added.
3. The request bytes (`payload`) are built before any connection is chosen. The same bytes can then be sent again on a retry.
4. It tries `_take_idle(origin)` first and falls back to `_connect`. `reused` records which one happened.
5. The retry rule:
   ```jac
   } except ClientRequestSent as e {
       if not reused
           or isinstance(e, ClientReadTimeout)
           or verb not in _IDEMPOTENT_METHODS {
           raise;
       }
       conn = await _connect(origin, timeout);
       (version, status, reason, resp_headers) = await _exchange(conn, payload, timeout);
   }
   ```
   - It retries only when all three of these are true:
     - the connection came from the pool (an old idle connection the server may have closed quietly),
     - the error is not a read timeout (the server may be busy processing the request),
     - the method is idempotent.
   - The retry happens once, on a fresh connection. If the retry also fails, that error goes to the caller.
   - Only failures before the response head are retried. A connection lost mid-body is raised as before.
6. Reuse eligibility is decided from the response head:
   ```jac
   bodiless = verb == 'HEAD' or status in (204, 304);
   reusable = version == 'HTTP/1.1'
       and 'close' not in (resp_headers.get('Connection') or '').lower()
       and (bodiless or chunked or resp_headers.get('Content-Length') is not None);
   ```
   - Line 1: these responses never carry a body.
   - Lines 2–4: the connection is reusable only if all of these hold:
     - the response is HTTP/1.1,
     - the server did not say `Connection: close`,
     - the response has a known end (no body, chunked, or `Content-Length`).
7. For **streaming requests**, the response is returned holding the connection. When the caller calls `aclose()`, the connection is either released to the pool or closed.
8. For **non-streaming requests**, the body is read and `await response.aclose()` now runs in a `finally` block. So the connection is always either pooled or closed, including when an error happens mid-body.

### `client.jac`: the sync helpers

`run_blocking` and `post_stream_aware_sync` each run their work with `asyncio.run` on a private, short-lived loop. You wrapped that work in `_closing_pool(...)`, so pooled connections are closed before the loop ends instead of being left open.

As your "Not addressed" section says, these sync paths still get little benefit from pooling. Each call has its own loop, so its pool starts empty. Only requests made inside the same call could reuse a connection.

### `jac/jaclang/server/serving/server.jac`: close on the budget-spending response

Before, the counting and the recycle decision happened after the response was written. Now they happen before it:

```jac
response = await self._dispatch(request);
self.requests_served += 1;
recycle = self.request_budget > 0
    and self.requests_served >= self.request_budget;
keep_alive = self._should_keep_alive(request)
    and not self._stopping
    and not recycle;
```

- Line 2 counts the request right after it is handled, before the response goes out.
- Lines 3–4 check whether this request uses up the budget.
- Lines 5–7 turn off keep-alive for that response. `_write_response` therefore sends `Connection: close`, and a pooled client will not reuse the connection.

After the access log, `if recycle { ... self.request_stop(EXIT_RECYCLE); }` stops the worker as before. The old `keep_alive = False` line there was removed because `keep_alive` is already false at that point.

One side effect: `requests_served` is now incremented before `_log_access` runs, where before it was after. The diff does not show whether `_log_access` reads that counter.

## How it runs now

Example: the gateway forwards a `GET` to a backend.

1. The gateway's `raw_forward` or `stream_forward` calls `arequest(...)`.
2. `arequest` builds the request and drops any caller `Content-Length` or `Transfer-Encoding` headers. **(changed)**
3. It writes `Host` and the computed `Content-Length`, but no `Connection: close`. It builds the full `payload` bytes. **(changed)**
4. `_take_idle(origin)` looks in this event loop's pool for a usable connection to the same server. **(new)**
5. If there is none, `_connect` opens a new one through `_open_stream`. For HTTPS this uses the cached `_tls_context()`. **(changed)**
6. `_exchange` sends the payload, reads the response head, and skips any `100 Continue`-style heads. **(new)**
7. If step 6 fails on a pooled connection, the request is idempotent, and the failure is not a timeout, `arequest` opens a fresh connection and repeats step 6 once. Otherwise the error goes to the caller. **(new)**
8. `arequest` computes `bodiless` and `reusable` from the method, status, version and headers. **(new)**
9. It reads the body:
   - Bodiless responses stop at the head.
   - Chunked responses read through the trailers.
   - `Content-Length` responses read exactly that many bytes.

   Each case records whether the body was fully drained. **(changed)**
10. `aclose()` runs. For non-streaming requests it runs inside `finally`; for streaming requests the caller calls it.
    - If the response was reusable and drained, `_release` sweeps expired connections and puts this one back in the pool.
    - Otherwise the connection is closed. **(changed)**
11. On the server side, the worker counts the request before writing. If this request uses up its `request_budget`, the response says `Connection: close` and the worker then recycles. **(changed)**
12. For sync callers (`run_blocking`, `post_stream_aware_sync`), `_closing_pool` closes all pooled connections before the private loop exits. **(new)**

## Tests

### `test_serving_client_errors.jac`: "connection reuse follows the response framing"

This test runs several cases against a real loopback socket server, using the file's existing `_start_server` / `_stop_server` helpers. `held` appears to be the list of accepted connections, so `len(held)` counts how many TCP connections the client opened.

Three new helpers:

- **`_recv_request`** reads one full request from the socket: the head plus a `Content-Length` body. Extra bytes are kept for the next request.
- **`_keep_alive(reply, drop_reused)`** builds a server handler. It answers each request on a connection with the same canned `reply`. It closes the connection when the request or the reply says `Connection: close`. With `drop_reused=True`, it receives the second request on a connection and then hangs up without answering. This simulates a pooled connection that died.
- **`_send_each`** sends the listed methods one after another with `arequest` (body `b"{}"`). For each one it records either the response body or the error type.

The cases:

| Case | What it proves |
|---|---|
| `content-length`: 3 GETs | Reuse works with `Content-Length` framing. Expects 1 connection. |
| `chunked`: 3 GETs | The chunk terminator is fully read, so the connection is clean for reuse. Expects 1 connection. |
| `bodiless 204`: 3 GETs | 204 responses stop at the head and are reused. Expects 1 connection. |
| `interim 100 continue`: 3 GETs | `100 Continue` is skipped, and the real `200` body comes back. Expects 1 connection. |
| `connection close`: 2 GETs | The client respects the server's `Connection: close`. Expects 2 connections. |
| `content-length overrun`: server sends `okEXTRA` with length 2 | The leftover bytes in the buffer stop reuse (`_usable`'s buffer check). Expects 2 connections. |
| `dead pooled GET is retried` | The second GET hits a dead pooled connection and is retried on a new one. Both succeed. Expects 2 connections. |
| `dead pooled POST is not replayed` | A GET, then a POST on the dead pooled connection. The POST raises `ClientRequestSent` and is not resent. Expects 1 connection. |

Failures are collected and reported together. Your description shows the earlier run without the fix: 3 connections where 1 was expected, and the POST case failing the same way.

### `test_serve_disconnect.jac`: "a worker at its request budget closes the connection it answers on"

This test starts a `ServingServer` with `request_budget=1` and one `/ping` endpoint. It sends a single GET with Python's `http.client` and checks two things:

- the status is 200,
- the `Connection` header is `close`.

This proves the server fix: the response that uses up the budget tells the client not to reuse the connection.

`stop()` is wrapped in `except RuntimeError`. Presumably this is because the worker has already stopped itself by recycling. The diff does not say why.

## Explaining it in one minute

"Our serving client opened a new TCP connection, and a new TLS context, for every request. It also sent `Connection: close`. So every gateway hop, SSO exchange and admin probe paid full connection setup.

I added a per-event-loop pool of idle connections. There are at most 32 per origin. A connection is dropped after 30 seconds idle, which is below the server's 65-second keep-alive, and retired after 120 seconds so kube-proxy can rebalance. The TLS context is now cached.

To make reuse safe, I fixed how responses are read. Chunked bodies now consume their terminator and trailers. `HEAD`, 204 and 304 stop at the head. Interim 1xx heads are skipped. The client owns `Content-Length` now. A connection goes back to the pool only if the response was HTTP/1.1, not marked close, properly framed, fully read, and left no stray bytes.

If a pooled connection turns out to be dead before the response head arrives, idempotent requests retry once on a fresh connection. `POST` and `PATCH` are never replayed, and timeouts are never retried.

On the server, the worker now decides to recycle before writing, so its last response says `Connection: close`.

Tests: one table-driven client test covers reuse, no-reuse and retry cases. It counts real connections on a loopback server. A second test checks the budget response carries `Connection: close`.

The sync `request_sync` path still opens one connection per call, because each call runs on its own short-lived loop. That needs separate work."
