## 1. The short version

The jac-scale runtime keeps graph data in layers. Redis is the "L2" cache, a shared fast store that sits between in-process memory and MongoDB. When a walker needs many nodes at once, `RedisBackend.batch_get()` loads them from Redis. It used to send one `GET` per node, so loading 25 nodes cost 25 network round-trips. That was later fixed: it now sends one `MGET` for the whole batch.

**The bug was in a test, not in production code: `test_redis_batch_overhead` asserted that the Redis command count grows by at least N, so it only passed while the slow per-node `GET` behaviour existed.** Once the `MGET` fix shipped, the test failed. Its own message even said *"If delta < ANCHOR_COUNT the fix is already applied."* PR #6850 then moved it to `tests/quarantine/` so CI would stop breaking.

**You replaced it with a guard that asserts the opposite: reading 5 nodes and reading 25 nodes must cost about the same number of Redis read commands, and `MGET` must actually be used.** The test reads exact `mget`/`get` call counts from `INFO commandstats`. It computes a per-node "marginal cost", which is about 0 with `MGET` and about 1 with one `GET` per node, and it requires that cost to be `< 0.5`. In its final form the test reuses the shared helpers in `server_support.jac` instead of carrying its own copies.

## 3. The problem, step by step

### 3.1 The setup

- **Production:** `batch_get()` in `memory_hierarchy.redis.impl.jac` already uses one `MGET`. This PR does not touch it.
- **Old test:** `test_redis_batch_overhead.jac` lived in `tests/quarantine/`. According to the description and @greptile-apps[bot], it was two near-identical ~150-line tests.
- **Test harness:** Redis and Mongo containers, a `jac start` server subprocess running `race_app.jac`, and HTTP walker calls.

### 3.2 What went wrong

```text
1. Old test seeds N anchors (ANCHOR_COUNT) via a walker.
2. Reads total_commands_processed from Redis            -> before = B
3. Calls the read walker; batch_get loads the N anchors from L2
4. Reads total_commands_processed again                 -> after = A, delta = A - B
5. Before the fix: batch_get sent N GETs                -> delta >= N   -> test PASSES (bug confirmed)
6. The fix ships: batch_get sends 1 MGET                -> delta ≈ 3 (per issue #6863)
7. Old assertion `delta >= ANCHOR_COUNT` now FAILS      <- WRONG: the test punishes the fix
8. PR #6850 moves it to tests/quarantine/               -> no test protects the MGET optimisation
```

### 3.3 Why it mattered

- The test broke CI the moment the optimisation landed, which is why it was quarantined (#6850, tracked under #6853).
- While quarantined, nothing stopped someone from reverting `batch_get` to N `GET`s. That regression would cost N round-trips per bulk read and would pass CI silently.
- Issue #6863 asked for three things: re-run against live Redis, invert the assertions into a guard, and move the file back to `tests/data/`.

---

## 4. The idea of the fix (one sentence)

> **Assert that the L2 read cost stays constant as N grows.** Measure exact `mget` and `get` counts for 5 nodes and for 25 nodes, and require the per-node difference to be near zero, with at least one `MGET` used.

Comparing two sizes cancels every fixed per-request cost (auth, root load, `INFO` itself). That means no hard-coded command ceiling that drifts over time. The separate `MGET >= 1` check makes sure the test is really hitting the batched L2 path and not passing because nothing reached Redis.

### 5.2 Same file: the `redis_cmd_calls` helper

```diff
+def redis_cmd_calls(r: redis.Redis, commands: list[str]) -> int {
+    stats = cast(dict, r.info("commandstats"));
+    total = 0;
+    for command in commands {
+        entry = stats.get(f"cmdstat_{command}");
+        if entry {
+            total += int(entry["calls"]);
+        }
+    }
+    return total;
+}
```

**What:** It sums the `calls` counter for the named commands from `INFO commandstats`.

**Why:** This replaces the noisy `total_commands_processed`. The `INFO` call shows up under `cmdstat_info`, so measuring does not change the numbers being measured.

**Things to notice:**
- If a command has never run, its `cmdstat_*` key is missing. The `if entry` check treats that as 0.
- `cast(dict, ...)` is only for the type checker. Commit `1689881` mentions "tighten redis test types".

### 5.3 Same file: the `measure_l2_reads` helper

```diff
+def measure_l2_reads(base_url, token, redis_client, count) -> dict[str, int] {
+    call_walker(base_url, "BulkCreate", token, {"count": count});
+    time.sleep(0.3);
+    # Warm-up read so first-touch writes settle into a steady state.
+    call_walker(base_url, "ListItems", token);
+    time.sleep(0.2);
+    mget_before = redis_cmd_calls(redis_client, ["mget"]);
+    get_before = redis_cmd_calls(redis_client, ["get"]);
+    call_walker(base_url, "ListItems", token);      # the measured read
+    time.sleep(0.2);
+    return {"mget": ... - mget_before, "get": ... - get_before};
+}
```

**What:** It seeds `count` nodes, does one warm-up read, then measures `mget` and `get` deltas across one more read.

**Why:** The warm-up keeps one-time first-access effects out of the measurement. Having one helper for both sizes is how the two duplicated old tests became one.

**Things to notice:**
- The `sleep`s are timing assumptions that let background writes settle.
- Background Redis traffic could, in theory, add `GET`s in the window. Since it would add equally to both sizes, it mostly cancels out.

### 5.4 Same file: setup, assertions and cleanup

```diff
+    redis_container = None; mongo_container = None; redis_client = None; server = None;
+    try {
+        redis_container = RedisContainer("redis:latest"); redis_container.start();   # NEW: inside try
+        ...
+        os.environ["REDIS_URL"] = redis_url;
+        mongo_container = MongoDbContainer("mongo:latest"); mongo_container.start();

+        assert small["mget"] >= 1 and large["mget"] >= 1 , ...;
+        marginal = (reads_large - reads_small) / (LARGE_COUNT - SMALL_COUNT);
+        assert marginal < 0.5 , ...;
+    } finally {
+        # close client, terminate server, pop env vars, stop containers, remove .jac/data
```

**What:** It starts the containers and the server, measures twice with separate users, asserts, and always cleans up.

**Why:** Starting the containers inside `try` fixes greptile's container-leak finding: if `start_server` raises, the `finally` still stops them.

**Things to notice:**
- Two users (`batch_small`, `batch_large`) give each measurement its own graph, so the 5-node read doesn't include the other user's nodes.
- `REDIS_URL` and `MONGODB_URI` are set before `start_server`, presumably so the server subprocess inherits them.
- Every cleanup step is wrapped in `contextlib.suppress`, so one failing step doesn't skip the rest.

Production code does not change. The PR adds a CI test that exercises the existing `batch_get` → `MGET` path.

### 6.1 Running the new test

```text
test "batch_get loads N anchors ..."                                     ← NEW
├─ remove fixtures/.jac/data (clean state)
├─ start Redis container → set REDIS_URL
├─ start Mongo container → set MONGODB_URI
├─ start_server(race_app.jac, free port)          (server_support)
├─ register_user "batch_small" → measure_l2_reads(5)
│   ├─ BulkCreate 5 → sleep → ListItems (warm-up)
│   ├─ snapshot cmdstat_mget / cmdstat_get
│   ├─ ListItems → server → batch_get → MGET (1 command)
│   └─ return {mget: Δ, get: Δ}
├─ register_user "batch_large" → measure_l2_reads(25)  (same steps)
├─ assert mget ≥ 1 for both                       → proves the batched path ran
├─ assert (reads_large − reads_small)/20 < 0.5    → proves cost does not grow with N
└─ finally: close client, kill server, pop env, stop containers, delete data dir
```

| Scenario | Old test | New test |
|---|---|---|
| `batch_get` uses one `MGET` (current code) | FAIL → quarantined | PASS (14.1s locally, per description) |
| `batch_get` reverted to N `GET`s | PASS | FAIL on the `mget ≥ 1` check (`mget=0`, per description). The marginal check would also fail (≈ (25−5)/20 = 1). |
| `batch_get` skips Redis entirely (e.g. all served from L1) | — | FAIL on the `mget ≥ 1` check |

## 11. Questions your senior might ask

**Q: Why compare two sizes instead of asserting "≤ 3 commands"?**
A fixed number breaks whenever per-request overhead changes. The difference between 5 and 25 cancels every constant cost and only measures what grows with N.

**Q: Why the threshold 0.5?**
It sits halfway between the two cases: about 0 with `MGET` and about 1 with per-node `GET`. That gives a wide margin either way.

**Q: Why count `get` and not only `mget`?**
A regression to per-node `GET`s would add `get` calls. Summing both catches that, and also catches a mix such as an `MGET` plus some single `GET`s.

**Q: Does the `INFO` call distort the numbers?**
No. It is counted under `cmdstat_info`, which the test never reads.

**Q: What if `batch_get` switched to a pipeline of `GET`s?**
Redis counts each pipelined `GET` in `cmdstat_get`, so this test would fail even though it is one round-trip. The guard is specific to `MGET`. Issue #6863 mentioned "MGET/pipeline", so that is a deliberate narrowing you should be ready to defend.

**Q: Why two different users?**
Each user has its own graph, so the 5-node read doesn't include the 25-node population, and vice versa.

**Q: Why a warm-up read and the sleeps?**
The first read after `BulkCreate` may do one-time writes or cache fills. The sleeps let async writes settle so the measured read is steady-state. The sleeps are a timing assumption, though, not a guarantee.

**Q: How do you know the test actually catches a regression?**
Per the description, you temporarily reverted `batch_get` to per-node `GET`s. The test failed with `mget=0`, and the production code was then restored.

**Q: Was the quarantined copy removed?**
Not in this diff. Check `main` directly.
