## 1. The short version

The jac-scale plugin can export Prometheus metrics. Every metric name starts with a prefix called the **namespace**, for example `jac_shop` in `jac_shop_http_requests_total`. The prefix comes from `jac.toml`. If `[scale.monitoring] namespace` is set, that value is used. If it is not set, the value falls back to `[scale.kubernetes] namespace`. Prometheus only allows `[a-zA-Z0-9_]` in names, so a helper called `sanitize_prometheus_namespace` cleans the value first.

**The bug: the sanitizer only ran on the Kubernetes fallback path. A namespace you set under `[scale.monitoring]` reached `prometheus_client` exactly as typed.** The client then cleaned it with its own, different rules. So `jac--shop` exported `jac__shop_http_requests_total` from one path and `jac_shop_http_requests_total` from the other. `2024app` became `_024app_...` (digit lost) on one path and `_2024app_...` (digit kept) on the other. Nothing reported an error, but dashboards and alerts built for one form went blank on the other. The admin traffic panel was also empty. It builds its queries from the raw value (`jac--shop_...`), and that never matched any exported name.

**The fix: one private function, `_resolve_prometheus_namespace`, now picks the source *and* always sanitizes the result. When it rewrites a value you configured, it logs a warning that names the old and the new prefix.** The warning fires once per loaded project. `reset_scale_config()` clears the flag. A non-string value such as `namespace = 2024` is first turned into a string, so it no longer crashes. The release note files this under `breaking`, because some users' metric names change once.

**Status:** Merged on 2026-09-07. @MusabMahmoodh approved on 2026-08-26. All CI checks on head commit `dd6a1fb` passed or were skipped.

## 3. The problem, step by step

### 3.1 The setup

- **Config source:** `jac.toml`, with an optional `[scale.monitoring] namespace` and an optional `[scale.kubernetes] namespace` (default `"default"`).
- **Resolver:** the code inside `get_monitoring_config()` in `config_loader.impl.jac`.
- **Consumers of `["namespace"]`:**
  - the metrics collector, which passes it to `prometheus_client`;
  - the gateway middleware, per the maintainer update;
  - the admin traffic query builder `_metrics_namespace`.

### 3.2 What went wrong: configured namespace skipped the sanitizer

The old code:

```jac
namespace = monitoring_config.get('namespace');
if not namespace {
    k8s_config = config.get('kubernetes', {});
    k8s_namespace = k8s_config.get('namespace', 'default');
    namespace = sanitize_prometheus_namespace(k8s_namespace);   # only here
}
```

```text
1. jac.toml has [scale.monitoring] namespace = "jac--shop"
2. get_monitoring_config(): namespace = "jac--shop"            (truthy)
3. `if not namespace` is False, so the sanitizer is skipped     ← WRONG STEP
4. config["namespace"] = "jac--shop"
5. Collector → prometheus_client normalises it → "jac__shop_http_requests_total"
6. Admin panel builds PromQL "jac--shop_http_requests_total" → matches nothing → empty panel
```

The same value through the fallback path:

```text
1. jac.toml has [scale.kubernetes] namespace = "jac--shop", no monitoring namespace
2. namespace is None, so the fallback branch runs
3. sanitize_prometheus_namespace("jac--shop") = "jac_shop"
4. Exported names: "jac_shop_http_requests_total"
```

Same input, two outputs:

| Input | via `[scale.monitoring]` (client rules) | via fallback (jac-scale sanitizer) |
|---|---|---|
| `jac--shop` | `jac__shop_...` | `jac_shop_...` |
| `2024app` | `_024app_...` | `_2024app_...` |
| `-prod-` | `_prod__...` | `prod_...` |
| `---` | `____...` | `jaclang_scale_...` |

### 3.3 Second failing case: non-string value (found during maintainer validation)

```text
1. jac.toml has [scale.monitoring] namespace = 2024     (a TOML integer)
2. After the first fix, the value is passed to sanitize_prometheus_namespace(2024)
3. The sanitizer's regex gets an int → TypeError at config read     ← WRONG STEP
```

Commit `9eb173e` fixed this by coercing with `str(configured)` first. Before the PR, the int was handed to `prometheus_client` raw. The diff does not show what the client did with it.

### 3.4 Why it mattered

- **Silent breakage.** Dashboards and alert rules written for one path showed nothing on the other, and nothing logged an error (issue #8688).
- **Admin panel.** @MusabMahmoodh noted the traffic panel was "silently empty for anyone with a dashed namespace".
- **Older client.** According to the maintainer update, `prometheus_client` 0.21.0 (the lowest supported version) raised `Invalid metric name` at startup for such names. That makes it a startup failure there, not just a naming difference.
- @kugesan1105 spotted the problem while reviewing #8427.

## 4. The idea of the fix (one sentence)

> **One function decides the namespace, and it always sanitizes.** Both the configured value and the Kubernetes fallback go through `_resolve_prometheus_namespace`, which cleans the value and warns once per project if it had to rewrite what you typed.

This removes the branch that let one input path skip the cleanup. With no way around the sanitizer, the two paths cannot drift apart again. The warning turns an unavoidable one-time rename into something users can see.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/config/impl/config_loader.impl.jac`: the resolver, the call site, the reset

```diff
+impl _resolve_prometheus_namespace(configured: str | None, k8s_namespace: str) -> str {
+    configured = "" if configured is None else str(configured);   # NEW: int 2024 -> "2024"
+    if not configured {
+        return sanitize_prometheus_namespace(k8s_namespace);       # fallback: same as before
+    }
+    sanitized = sanitize_prometheus_namespace(configured);         # NEW: configured path sanitized
+    if sanitized != configured and not _prometheus_namespace_warned {
+        _prometheus_namespace_warned = True;
+        import logging;
+        logging.getLogger(__name__).warning(
+            f"jac.toml [scale.monitoring] namespace '{configured}' is not a valid "
+            f"Prometheus prefix; metrics are exported under '{sanitized}' instead. "
+            "Update dashboards and alert rules that reference the old prefix."
+        );
+    }
+    return sanitized;
+}
...
-    namespace = monitoring_config.get('namespace');
-    if not namespace {
-        k8s_config = config.get('kubernetes', {});
-        k8s_namespace = k8s_config.get('namespace', 'default');
-        namespace = sanitize_prometheus_namespace(k8s_namespace);
-    }
+    k8s_config = config.get('kubernetes', {});
+    namespace = _resolve_prometheus_namespace(
+        monitoring_config.get('namespace'), k8s_config.get('namespace', 'default')
+    );
...
 impl reset_scale_config -> None {
     _scale_config_instance = None;
+    _prometheus_namespace_warned = False;     # NEW: each project gets its own warning
     _app_scale_cache.clear();
 }
```

**What:**
- `get_monitoring_config()` no longer branches. It reads both raw values and hands them to the resolver.
- The resolver turns `None` into `""` and anything else into a string.
- If the result is empty, it uses the Kubernetes value. Otherwise it sanitizes the configured value.
- It warns only when the configured value actually changed, and only once until the flag is reset.

**Why:**
- Sanitizing the configured value fixes the "two names for one input" bug.
- `str()` fixes the `TypeError` for non-string TOML values.
- Resetting the flag in `reset_scale_config` fixes review point 1. Without it, a second project in the same process would be renamed silently.

**Things to notice:**
- **Warnings only cover the configured path.** The fallback path never warns, because its behaviour did not change.
- **The fallback path is not coerced.** A non-string `[scale.kubernetes] namespace` (for example an int) would still reach the sanitizer as an int. The PR does not cover that case.
- **Falsy non-`None` values behave differently now.** Before, `namespace = 0` hit `if not namespace` and used the fallback. Now `str(0)` is `"0"`, which is truthy, so it becomes `_0` and logs a warning. `false` becomes `"False"`. These are unlikely configs, but the behaviour is different.
- **The type hint is `str | None`, but the code accepts any type** because of the coercion.
- **`import logging;` inside the body is deliberate.** @MusabMahmoodh checked it matches `get_config_schema` and `_metrics_namespace`.
- **"Warns at startup" in the docs really means "warns on the first `get_monitoring_config()` call".** That is presumably at server start; the diff doesn't show where it is first called.
- **The sanitizer's own rules are unchanged** (stated as out of scope in the PR body).

### 7.1 `test_config_loader.jac`

**Helper `_load_monitoring_namespace(scale_body)`** does the following:

**Test "the monitoring namespace is sanitized on every path, and only a rewrite warns":**

| Row | Input | Expected | Must warn naming | Proves |

| 1 | monitoring `"jac--shop"` | `jac_shop` | `jac--shop` | the configured path is sanitized and the warning fires |

## 11. Questions your senior might ask

**Q: Why not just make the fallback stop sanitizing, so both paths use the client's rules?**
A: The client's rules lose data (`2024app` → `_024app`), and older clients (0.21.0) reject such names outright. The admin panel also builds PromQL from the config value, so the config value must already be the final name.

**Q: Is this really "breaking"?**
A: Yes, for anyone whose configured namespace had characters outside `[a-zA-Z0-9_]`. Their metric names change once. That is why the note is `.breaking.md` and why there is a warning.

**Q: Why a global flag instead of warning on every read?**
A: `get_monitoring_config()` can be called many times, and warning every time would spam the log. Resetting the flag in `reset_scale_config()` keeps it once per project, not once per process.

**Q: What happens with `namespace = 2024` in TOML?**
A: It is coerced to `"2024"`, sanitized to `_2024`, and a warning is logged. Before commit `9eb173e`, the branch raised `TypeError` from the sanitizer's regex.

**Q: Does the Kubernetes fallback get the same coercion?**
A: No. Only the configured value goes through `str()`. A non-string `[scale.kubernetes] namespace` would still reach the sanitizer as-is.

**Q: Are there edge cases where behaviour changed beyond dashed names?**
A: Yes. Falsy non-`None` values like `0` or `false` used to fall back to the Kubernetes namespace. Now they become `"0"`/`"False"`, are sanitized, and warn.

**Q: Why did you drop the subprocess test the reviewer praised?**
A: In a dev checkout, the subprocess ran the installed jaclang instead of the branch and failed. Capturing logs in-process tests the same warning reliably. The exposition check moved to `test_metrics.jac`.

**Q: Do the other consumers of the namespace now agree?**
A: According to the maintainer update, yes. The collector, the gateway middleware and the admin query builder all use `jac_shop_*`, and the admin PromQL parses. Those files aren't in this diff, so this rests on that manual validation, not on new tests.

**Q: Did the sanitizer's rules change?**
A: No. The PR only changes which inputs the sanitizer is applied to.
