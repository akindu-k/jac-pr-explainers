## 1. The short version

`jac start --scale` deploys a Jac app to Kubernetes and then waits for the "fleet" (all its services) to come up before printing "Fleet ready". The waiter, `_wait_for_fleet_rollout`, polls each Kubernetes Deployment until it judges it ready.

**On a re-deploy, the old gate (`d.status.ready_replicas >= 1`) was satisfied by the previous revision's pods, so the command reported "Fleet ready" on the first poll, before the new code had a single pod running.** The reason is that `readyReplicas` counts pods from every ReplicaSet the Deployment owns, old and new, and nothing checked that Kubernetes had even seen the new spec (`observedGeneration`). Two other places, `get_status` (the source of `ScaleClient.resource_status()`) and the ops deploy view, had their own weaker copies of the same check.

**You moved readiness into a new `rollout.jac` that only counts replicas provably from the new ReplicaSet (`available - (total - updated) >= 1`) and only after `observedGeneration` has caught up. You also added an opt-in `--wait full` / `rollout_wait = "full"` mode that waits for the whole rollout, and made all three surfaces use this one reader.** A stalled rollout (`ProgressDeadlineExceeded`) now fails right away, but only when Kubernetes stamped that verdict during *this* deploy. A verdict left over from the previous deploy is ignored. Config values are validated when the deploy starts, not when the config is loaded.

This deliberately changes the default. A re-deploy now takes minutes instead of seconds, and it ships with a `breaking` release note.

**Status:** Open. @MusabMahmoodh approved twice (2026-08-12 and 2026-08-18). All CI checks on head `b93d229` pass or were skipped. One fix commit (`9f46329`, 2026-08-20) and two merges from `main` came after the last approval.

## 3. The problem, step by step

### 3.1 The setup

- The Deployment `products-app-deployment` already exists with revision 1 and 3 healthy pods.
- You run `jac start --scale` again with changed code. jac-scale patches the same Deployment, so `generation` goes 1 → 2.
- `_wait_for_fleet_rollout` polls `read_namespaced_deployment` every 10s and counts a service ready if `status.ready_replicas >= 1`.

### 3.2 What went wrong: the re-deploy

```text
1. Before deploy:     generation=1 observedGeneration=1  RS-v1: 3 ready   readyReplicas=3
2. jac patches spec:  generation=2 observedGeneration=1  (controller hasn't seen it yet)
3. Poll #1 (t=0s):    readyReplicas=3  (all from RS-v1)
4. Gate: 3 >= 1  →  "Fleet ready: N/N deployments serving"     ← WRONG: no new pod exists
5. Command exits success.
6. Later:             controller creates RS-v2, starts draining RS-v1
7. Later:             RS-v2 pod may crash, fail to pull, or stall — the deploy already "succeeded"
```

### 3.3 What went wrong: the same weakness in status readers

```text
get_status (ScaleClient.resource_status):
1. desired=3, RS-v1 3 ready, RS-v2 0 pods
2. ready_replicas(3) == replicas(3)  →  RUNNING            ← WRONG: new code not live

Ops view _rollout_status:
1. desired=2, updated=2, available=2, total=3 (one old pod still draining)
2. updated==desired and available==desired  →  "complete"  ← WRONG: old pod still there
3. Any ProgressDeadlineExceeded, even on an unobserved spec  →  "stuck"
```

### 3.4 What went wrong: the stall trap a naive fix would hit

```text
1. Deploy A stalls: Progressing=False, reason=ProgressDeadlineExceeded @10:00
2. You fix it and run deploy B (patch)
3. Right after the patch, the controller re-asserts the A verdict (same @10:00 stamp)
4. A waiter that fails on sight would reject B using A's timeout   ← WRONG
```

Your first version waited three polls (30s) before trusting a stall. @MusabMahmoodh pointed out that a new RS's first pod can sit behind PVC binding for longer than that, so the trap was still open.

### 3.5 Why it mattered

- CI and wrappers that run `jac start --scale` got a success result for code that was not running yet. Issue #7768 notes that pipelines had to run their own `kubectl rollout status` loops.
- Stalls (quota, scheduling, node-pool issues) after the gate were reported as success.
- `resource_status()` answered `RUNNING` mid-rollout. @MusabMahmoodh notes that jachammer polls this.
- #7768 only asked for an opt-in `full` mode and wanted the default kept. Your diagnosis shows the default itself was wrong on re-deploys, not just weak.

## 4. The idea of the fix (one sentence)

> **Count only what provably belongs to the revision you applied, and only trust a stall verdict stamped after you started.** Every readiness and status check now goes through one reader that requires `observedGeneration` to catch up and subtracts old-RS pods, and the waiter fingerprints any stall on first sight so only a newly stamped one fails the deploy.

This is the right idea because it uses the fields Kubernetes itself provides (`observedGeneration`, `updatedReplicas`, the condition's `lastUpdateTime`) rather than timing guesses. It undercounts while old pods drain but never overcounts.

## 5. Every code change, explained

### 5.1 `jac/jaclang/scale/deploy/target/kubernetes/rollout.jac`: the shared reader (new)

```diff
+def normalize_rollout_wait(mode: any) -> str {
+    candidate = str(ROLLOUT_WAIT_READY if mode is None else mode).strip().lower();
+    if candidate not in ROLLOUT_WAIT_MODES { raise ValueError(...) }   # "" is rejected
+def normalize_rollout_timeout(value: any) -> int {
+    try { seconds = int(value); is_whole = seconds == float(value); }
+    except (TypeError, ValueError) { (seconds, is_whole) = (0, False); }
+    if isinstance(value, bool) or seconds < 1 or not is_whole { raise ValueError(...) }
+def _field(source, name)   # dict.get or getattr — works on client objects and dicts
+def _stall_condition(status) -> (reason, message, last_update_time)  # Progressing + ProgressDeadlineExceeded only
+obj RolloutStatus {
+    def is_observed -> bool { return self.observed_generation >= self.generation; }
+    def updated_available -> int {
+        outdated = max(self.total - self.updated, 0);
+        return max(self.available - outdated, 0);
+    }
+    def is_complete -> bool {
+        return self.updated >= self.desired and self.total <= self.updated
+            and self.available >= self.desired;
+    }
+    def satisfies(mode: str) -> bool {
+        if not self.is_observed() { return False; }
+        if mode == ROLLOUT_WAIT_FULL or self.desired <= 0 { return self.is_complete(); }
+        return self.updated_available() >= 1;
+    }
+    def stall_mark -> str { return f"{self.stall_reason}@{self.stall_marked_at}" if self.stall_reason else ""; }
+    def stall(inherited: str = "") -> str {
+        mark = self.stall_mark();
+        if not mark or not self.is_observed() or mark == inherited { return ""; }
+        ...
+    def stall_caveat -> str { ... "(recorded {t}, may predate the current rollout)" }
+    def stall_note -> str { stall = self.stall(); return f"{stall} {self.stall_caveat()}" if stall else ""; }
+}
+def read_rollout_status(deployment: any) -> RolloutStatus { ... }
```

**What:** One place that reads a Deployment (client object or dict) and answers four questions: has the controller seen the spec, how many new-revision pods are available, is the rollout complete, and is there a stall verdict. It also holds the two config validators.

**Why:** It fixes the core counting bug and removes the three diverging copies of "is it done".

**Things to notice:**
- `updated_available` is a floor. It assumes every unavailable pod could be an old one, so it may undercount but never counts an old pod as new.
- `desired <= 0` falls back to `is_complete()`, so a service scaled to zero does not block the `ready` gate forever.
- `stall()` stays silent until `is_observed()` is true. A verdict on a status that still describes the old spec is never trusted.
- `normalize_rollout_timeout` accepts `"1200"` (because env interpolation yields strings) and `120.0`. It rejects `""`, `"soon"`, `"30.5"`, `30.5`, `true`, `0` and negatives. The `isinstance(value, bool)` check came from @greptile-apps (`87ea441`). Empty and fractional rejection came from `8ac04a8`.
- `_non_negative_int` turns missing or `None` k8s counters into 0. k8s omits zero counters, so this matters.

### 6.2 One poll of the waiter

```text
for each Deployment name:
├─ read_namespaced_deployment
│  ├─ ok → rollout = read_rollout_status(d)                           ← NEW
│  │  ├─ rollout.satisfies(mode) → ready += 1                         ← CHANGED
│  │  ├─ first sight → inherited_stalls[name] = stall_mark()          ← NEW
│  │  └─ stall(inherited) non-empty → stalls[name]                    ← NEW
│  └─ error → last_read_error = "name: exc"                           ← NEW (was swallowed)
├─ ready == total → log "Fleet ready: N/N deployments {serving|fully rolled out}" → return
├─ crash-loop / image-pull / heal checks (unchanged)
├─ stalls → raise "deployment 'x' stalled: ProgressDeadlineExceeded: ..." + pod details  ← NEW
└─ sleep 10s; loop until timeout
timeout → "timed out after Ns (k/N deployments ...)" + read note if last poll failed + pod details  ← CHANGED
```

**Behaviour change users will notice:** a re-deploy with the default mode now takes as long as scheduling, image pull, boot, the readiness probe and `minReadySeconds`. That is minutes, not seconds.

## 11. Questions your senior might ask

**Q: Why not just compare `readyReplicas` of the new ReplicaSet directly?**
A: That needs extra API calls to find the current RS. `available - (total - updated)` uses only the Deployment's own status. It is a safe floor: it can undercount while old pods drain but can never count an old pod as new.

**Q: Why change the default when #7768 asked to keep it?**
A: On a re-deploy the old default reported success against the pods it was about to delete. That is not a fast gate, it is a wrong one. The cost is real time that was always being spent, so it ships as a breaking note.

**Q: How does the waiter tell a new stall from an inherited one?**
A: On first sight it stores `reason@lastUpdateTime`. Kubernetes keeps `lastUpdateTime` when it re-asserts an identical condition, so an inherited verdict keeps the same mark and stays silent. A verdict stamped for this rollout gets a new time and fails at once.

**Q: What if the very first poll already sees a new stall from this rollout?**
A: It would be stored as the baseline and ignored, so the deploy runs to `rollout_timeout` and fails there with pod diagnosis. A fresh stall needs `progressDeadlineSeconds` to pass after the patch, so this is unlikely on poll 1. The tests don't cover that exact case.

**Q: Why validate in `_rollout_gate()` and not in `KubernetesConfig`?**
A: `from_dict` also runs in-pod where callers swallow exceptions. A bad knob there would silently blank the whole config, for example an empty namespace in the admin logs view. Failing on the deploy path only fails the operation the knob controls.

**Q: Why accept `"1200"` as a timeout?**
A: `jac.toml` env interpolation always produces strings, so `"${ROLLOUT_TIMEOUT:-1200}"` must work. Values are strict: `"soon"`, `30.5`, `true`, `0` and negatives are rejected.

**Q: Can `get_status` and the ops view tell an inherited stall apart?**
A: No. They are single reads with no baseline. They report the stall with the controller's timestamp and "may predate the current rollout", so a caller who knows when it deployed can judge for itself.

**Q: Do the unit tests prove real k8s fills the counters as assumed?**
A: No, they use mocked objects. That is why the e2e now re-deploys twice on a real cluster, once per mode. It checks the revision advanced and the gate condition holds on an independent read.

**Q: What happens with an HPA (autoscaler) resizing during `--wait full`?**
A: `spec.replicas` is read on every poll, so the target moves with it, the same as `kubectl rollout status`.

**Q: Could the new `PENDING` rule hide a broken deploy forever?**
A: `PENDING` only says something is serving or rolling out. A stall shows up in `message`, and the deploy gate itself still fails on stalls and on `rollout_timeout`.
